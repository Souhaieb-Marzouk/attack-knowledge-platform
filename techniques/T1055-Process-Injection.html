T1055 Process Injection

Process injection means placing attacker-controlled code into the memory of another running process and making that process run it. After that, the activity looks like it comes from trusted software. This guide explains how the trick works, how defenders see it, and how to build detections that catch it.

What it is

Attacker code runs inside another process's memory space, instead of inside the attacker's own program on disk.

Why attackers use it

It blends into trusted software, can bypass process-based controls, and the injected code inherits the target process's rights.

Main risks

Hidden command-and-control (C2) traffic, credential theft from system memory, and staging for ransomware.

Detection focus

Cross-process access, remote threads (a thread is one running task inside a process), and executable memory that has no file on disk (so-called "unbacked" memory).

Contents

1Overview

A plain-language tour of process injection: what a process is, why its memory matters, and where this technique sits in a real attack. No prior knowledge of operating system internals is needed.

What is a process?

When you start a program, the operating system loads it and creates a process. A process is a working area: the program's code, its data, and its running tasks all live inside it. svchost.exe, explorer.exe, and your web browser are all processes.

Every process runs with an identity. Some run as the logged-in user. Others, such as Windows services, run with higher rights and can reach more of the system.

What is process memory?

Each process gets its own private memory — a protected area of addresses where its code and data live. Normally only that process may read or write its own memory. Many security tools treat memory content as trusted, because it belongs to a program that is already installed and running.

Process injection abuses that trust. The attacker writes code into another process's memory and gets that process to run the code, as if it were its own.

Evasion

Security tools trust processes. A well-known system process is less likely to be blocked or inspected than a strange new program on disk. Running inside it gives the attacker's code cover.

Privilege

The injected code inherits the rights of the process it lives in. Inject into a service running as SYSTEM, and the code now acts as SYSTEM — without needing a new exploit.

Stealth

No new suspicious process appears in the task list. Analysts see one familiar process doing something unfamiliar — which is much harder to notice than a new program.

Where it fits in the attack chain

Injection usually comes after initial access and execution. The attacker already has code running in a user session, for example from a phishing attachment or a loader. Injection is the next move: it hides the implant, raises its privileges, and prepares later steps.

In ATT&CK terms it commonly supports Stealth (TA0005), Privilege Escalation (TA0004), and Credential Access. TA0005 was named Defense Evasion before ATT&CK v20. From an injected, elevated process the attacker can read sensitive memory, steal passwords, and move to other machines.

Written story — text alternative for the animation

  1. Step 1 — Foothold. A user opens a phishing attachment. Office starts a script host, and a small attacker agent appears in the user session. Defender view: Sysmon EventID 1 shows Winword.exe spawning cmd.exe and powershell.exe — a suspicious process tree.

  3. Step 3 — Handle acquisition. The agent calls OpenProcess on the target and asks for broad rights, receiving a handle — a permission ticket to access that process. Defender view: Sysmon EventID 10 (ProcessAccess) logs the cross-process access with its requested rights.
  4. Step 4 — Memory allocation. The agent calls VirtualAllocEx to create a read-write-execute (RWX) memory region inside the trusted process. Defender view: EDR flags an executable memory allocation in a process that should never need one.
  5. Step 5 — Payload written. WriteProcessMemory copies the payload bytes into that region. Defender view: the region has no matching file on disk — "unbacked" memory holding executable code.
  6. Step 6 — Remote thread. CreateRemoteThread makes the trusted process start a new thread at the payload. Defender view: Sysmon EventID 8 shows a remote thread created by an unrelated user process — a high-value alert.
  7. Step 7 — Hidden C2. The payload beacons to the attacker's command-and-control (C2) server — from inside the trusted process. Defender view: network logs show a familiar service process making an odd outbound connection.
  8. Step 8 — Response. The analyst links the alerts into one chain, isolates the host, and captures memory before any cleanup. Defender view: a triage timeline from first alert to containment, with the isolated host as the outcome.

3Red team perspective

This section explains, at concept level only, why attackers inject code, the classic Windows API sequence behind it, and where it appears in real tooling. Everything here is for building detections and lab exercises — never for harming real systems.

Hide

Malware on disk is easy to find and delete. Code inside a trusted process has no file of its own and inherits the good reputation of the host process, so scanners and allow-lists are less likely to flag it.

Inherit trust and tokens

A process carries a token — its security identity, with the groups and rights attached to it. Injected code uses the target's token, so it can reach whatever the target can reach, including sensitive system memory.

Bypass per-process mitigations

Some defenses apply per process, for example blocked child processes or exploit protections on a browser. If the implant runs inside an allowed process instead of starting a new one, those checks never fire.

The classic Windows API sequence (concept only)

Nearly every basic injector on Windows follows the same four steps using the native API — the set of system functions that programs use to talk to the operating system kernel.

Each call has one job. OpenProcess gets access to the target; VirtualAllocEx makes room; WriteProcessMemory fills it; CreateRemoteThread starts execution. Every step leaves a trace that defenders can log, which is exactly what section 5 builds on.

Danger — lab only

This sequence is shown to help defenders understand what to log. Do not write or run injector code against systems you do not own and do not have written permission to test. Use your own isolated lab, and keep payloads inert.

Where it applies in real operations

Injection is everywhere in post-exploitation tooling. Frameworks offer it as a built-in feature: think of the "migrate" action in common C2 frameworks, which moves the agent into another process, or "spawnto" settings that choose which trusted process to spawn and inject into. Loader malware (the first stage that unpacks and runs the real implant) and crypters (services that wrap malware to hide it) use injection as their standard delivery step.

Ransomware crews inject helper components into service processes before encryption starts, so the encryption and deletion tools run with system rights and look legitimate.

Prerequisites

  • Code execution in a session — the attacker needs one running process of their own first.
  • Rights to reach the target. Injecting into another user's or a SYSTEM process needs administrator rights or the SeDebugPrivilege privilege, a special right given to administrators and debuggers.
  • Matching architecture. A 32-bit (x86) payload cannot simply run inside a 64-bit (x64) process; the injector must match or bridge the bitness.
  • Knowledge of what the target is allowed to do, so the injected behavior does not look absurd.

Practical lab examples

Safe ways to see this technique without risk:

  • Run a small virtual machine with no network access to your real environment.
  • Study the "migrate" feature of open-source C2 frameworks in that lab and watch the Sysmon events it produces.
  • Read the source of open teaching injectors used in security courses to understand the API order.

Purple-team exercises then replay the same events to test your detections.

Warning — keep the lab isolated

Use snapshots, disable shared folders, and block the lab network from production. Injection exercises easily damage a test machine — that is acceptable; harming a real system is not.

Variations and common mistakes

Variations: DLL injection (T1055.001) makes the target load a library; PE injection (T1055.002) writes a full program image; thread hijacking (T1055.003), APC (T1055.004), and TLS callbacks (T1055.005) run code through existing threads; process hollowing (T1055.012) starts a real program in a suspended state and swaps its memory content. Other variations use fibers (lightweight threads) or window memory. All reach the same goal: code running inside someone else's process.

Common operator mistakes: picking a heavily monitored target such as lsass.exe on hosts with strong EDR; using an obvious RWX pattern that basic memory scanners catch; mismatching x86 and x64 and crashing the target; and enumerating processes so noisily that even a weak EDR flags the burst.

4Blue team perspective

Injection leaves fingerprints even when the process name looks innocent. Here is what defenders can see, where to look, and a short triage flow you can put directly into your playbooks.

Visibility sources

  • Sysmon EventID 8 (CreateRemoteThread) and EventID 10 (ProcessAccess) — the two core Windows events for this technique.
  • EDR behavioral engines that watch API call patterns, not just files.
  • ETW Threat-Intelligence providers — Windows event tracing feeds that expose memory allocation and thread start details to endpoint agents.
  • Memory scanning — periodic or on-demand scans that find executable code in regions with no file behind them.

Artifacts to look for

  • Cross-process handles opened with write or all-access rights.
  • RWX private memory regions, especially "unbacked" ones with no file on disk.
  • Threads whose start address lies outside any loaded module.
  • Network connections from an unusual parent process, for example a service process reaching a fresh internet IP.

Where to look

Start in your EDR console: filter process relationships for "opened process" and "thread created" edges around trusted processes. Then check the Sysmon pipeline — EventID 8 and 10 should land in your log platform (SIEM), a central system that stores and searches logs. For deep cases, capture a triage memory image and run malfind-style scanning (a memory-forensics technique that lists suspicious injected regions) with a tool such as Volatility.

Why it matters for the chain

Injection is rarely the goal — it is the staging ground for what follows. Credential access tools read password memory from elevated processes; lateral movement tools borrow network access; ransomware stages its encryptor inside service processes. Catching injection early breaks the chain before data theft or encryption starts.

Triage flow — six steps

  1. Validate the alert. Confirm the event is real: check that the logging source is healthy and the event was not replayed by a test.
  2. Identify source and target. Note both processes, their full paths, the user account, and whether the source is signed or not.
  3. Collect the process tree and handle information. Pull the parent chain of the source process and the requested access rights from EventID 10.
  4. Capture triage memory. Take a memory image or an EDR memory dump of the target process before killing anything — once the process dies, the evidence is gone.
  5. Isolate if confirmed. Cut the host from the network with the EDR isolate action and escalate to incident response.
  6. Hunt the pattern fleet-wide. Search all endpoints for the same source process name, hash, or target combination over the last 30 days.
Good practice — preserve before you kill

Memory is the strongest evidence in injection cases. Always capture it before terminating the process or reimaging the host.

5.3Threats ranking

Five realistic injection threats, ranked by severity, each with the preconditions an attacker needs and the impact if it succeeds. Section 5.4 gives the logs for each, and section 5.5 gives one detection rule per threat.

T1 — C2 implant injects into a trusted process via remote thread

CriticalWindows

Description: after a foothold, a Cobalt Strike-style beacon — an implant that regularly calls home for commands — moves itself into a trusted process such as svchost.exe using a remote thread, then beacons out from there.

Preconditions: code execution in a user session; target process reachable; matching architecture.

Impact: hidden command-and-control under a trusted identity; long dwell time; platform for credential access and later ransomware.

Justification: the full stealth chain — cross-process access, unbacked memory, and hidden C2 — documented in countless real intrusions.

T2 — Suspicious handle access to LSASS

HighWindows

Description: a user-mode tool opens lsass.exe (the Windows process that stores logon credentials) with read rights — the standard preparation step for credential dumping.

Preconditions: elevated rights or SeDebugPrivilege; a tool or injected code that requests handle access.

Impact: stolen logon credentials allow domain-wide access; one dump can compromise every account that logged into the host.

Justification: LSASS access is a near-certain indicator of credential theft preparation, and it is often the injected payload's first task.

T3 — Cross-process memory-write access from an unsigned user process

MediumWindows · Linux · macOS

Description: an unsigned user application gets write access to another process's memory — with a write handle on Windows, with ptrace (the Linux debugger interface) on Linux, or with task_for_pid (the macOS call that hands over a process port) on macOS. This is the earliest, quietest precursor of injection.

Preconditions: user-mode code execution; on the same user's processes no special rights, on system processes administrator or root rights.

Impact: a precursor signal; on its own limited, but it marks tools that will complete the injection chain next.

Justification: strong signal but not conclusive — some legitimate software (input remappers, game anti-cheat, accessibility tools, debuggers) also opens cross-process write access, so it ranks Medium.

T4 — Remote thread starting in unbacked memory

HighWindows

Description: a new thread begins executing at an address that belongs to no file on disk — code that was placed in memory by an injector.

Preconditions: a local injection capability; memory allocation and write already completed.

Impact: active code execution inside the target; the implant is live regardless of what process name it hides in.

Justification: on workstations a remote thread with no start module is almost always malicious; only .NET just-in-time compilation adds noise.

T5 — Office or script host performs cross-process injection

HighWindows

Description: a macro document or script host (Word, Excel, Outlook, wscript, mshta, PowerShell) opens another process for memory access — the injection stage runs directly from the delivery document.

Preconditions: a user opened a malicious document or script; macro or script execution allowed.

Impact: direct pivot from phishing to implant without a distinct malware stage on disk.

Justification: office processes have no business writing into other processes' memory; the fidelity of this chain marker is very high.

5.4Logs and patterns

Every threat T1–T5 above maps to specific Sysmon fields. Learn these eight fields once, and each rule in section 5.5 becomes easy to read.

FieldMeaning
EventIDThe Sysmon event number: 8 = CreateRemoteThread, 10 = ProcessAccess.
SourceImageFull path of the process performing the action — the potential injector.
TargetImageFull path of the process being touched — the potential victim.
StartModuleThe module (file) where a new remote thread begins. A dash means "no module" — typical for injected code.
StartFunctionThe function name where the thread starts. A dash means the start point is not a known exported function.
GrantedAccessThe hexadecimal rights mask requested on a handle. For example 0x1010 = read memory, 0x143A = create thread plus memory read, write, and operation rights, 0x1FFFFF = all rights.
CallTraceThe call stack: which modules made the call. An entry like UNKNOWN(00007FF...) means code running with no module behind it — injected or shellcode.
UserThe account under which the source process runs.

T1 — remote thread into trusted process

Critical

Log sources: Sysmon EventID 8, EDR process behavior, network flow logs.

Normal: user applications essentially never start threads inside svchost, lsass, winlogon, or explorer. Updates and security agents do — and they run from C:\Windows or a known agent path.

Suspicious: the source lives in a user-writable folder (Temp, AppData, Downloads) and the target is a trusted process.

Detection logic: EventID 8 AND TargetImage ends with a trusted process name AND SourceImage does not start with C:\Windows.

T2 — suspicious LSASS handle access

High

Log sources: Sysmon EventID 10, EDR credential-access detections.

Normal: antivirus, EDR, and backup agents regularly open lsass.exe to read process information; they run from known installed paths.

Suspicious: GrantedAccess 0x1010 (read memory), 0x1410, 0x1470, or 0x1FFFFF (all rights) from a Temp/AppData path or any unsigned binary.

Detection logic: EventID 10 AND TargetImage ends with lsass.exe AND GrantedAccess in the high-risk set AND SourceImage not on the tool allowlist.

T3 — cross-process memory-write access

Medium

Log sources: Sysmon EventID 10 (Windows); EDR alerts on ptrace attach and writes to /proc/<pid>/mem (Linux); EDR alerts on task_for_pid and task-port access (macOS).

Normal: some legitimate tools (input remappers, anti-cheat, accessibility software, debuggers) open cross-process write access; they are usually signed and version-stable.

Suspicious: write-level access masks (0x1F0FFF, 0x1F1FFF, 0x1FFFFF, 0x143A) aimed at system processes from an unsigned user process on Windows; ptrace calls from non-debug software, or writes to another process's memory through /proc, on Linux; task_for_pid success for an unsigned binary on macOS.

Detection logic: on Windows — EventID 10 AND GrantedAccess in the write set AND TargetImage in the system-process list AND SourceImage not under C:\Windows. On Linux and macOS — EDR behavioral rules for cross-process memory access from unsigned or unexpected software.

T4 — remote thread in unbacked memory

High

Log sources: Sysmon EventID 8, EDR memory scanning.

Normal: the .NET runtime compiles code in memory (just-in-time), so a small share of EventID 8 events shows an empty start module on .NET hosts.

Suspicious: StartModule or StartFunction is a dash, especially combined with a user-writable source path.

Detection logic: EventID 8 AND (StartModule is dash or empty OR StartFunction is dash or empty).

T5 — office or script host performs cross-process injection

High

Log sources: Sysmon EventID 8 and EventID 10, EDR office-macro detections.

Normal: Word, Excel, PowerPoint, Outlook, wscript, cscript, mshta, and PowerShell do not inject into other processes. Document-linked add-ins are the rare exception and are signed.

Suspicious: any of these hosts opening a different process (EventID 10) or creating a remote thread in one (EventID 8).

Detection logic: (EventID 8 OR EventID 10) AND SourceImage ends with an office or script host name AND TargetImage differs from SourceImage.

5.5Sigma rules and Splunk SPL

One Sigma rule per threat (R1–R5), each followed by a matching Splunk query. Sigma is an open rule format that converts to many SIEM languages; SPL is Splunk's search language.

R1 — Remote thread into a trusted process (T1)

Mapping note: the Splunk Add-on for Microsoft Windows parses Sysmon XML into CIM fields — the event id arrives as EventCode rather than EventID. Adjust index=sysmon to your local index name, and keep the sourcetype exactly as configured in your inputs.

R2 — Suspicious LSASS handle access (T2)

The | where count >= 2 line is an SPL aggregation gate that suppresses one-off events; it is not part of the Sigma logic.

R3 — Cross-process write handle (T3)

Mapping note: the eval marks Tier-0 targets (identity and logon processes) so triage can prioritize them. Tune the count threshold after a week of baseline data; Medium severity means weekly review, not pager alerts. This rule covers Windows only; on Linux and macOS, match the T3 threat with EDR rules for ptrace and task_for_pid cross-process access instead (see T1055.008 and T1055.009 for the Linux variants).

R4 — Remote thread in unbacked memory (T4)

Mapping note: tuning — on .NET-heavy servers this rule can get noisy. Add a filter for known managed runtimes (for example sources under a trusted Program Files path) and watch the ratio of empty StartModule events per host before raising the alert level.

R5 — Office or script host performs cross-process injection (T5)

Mapping note: the where clause enforces "different process", matching the Sigma fieldref filter. Field names assume the Splunk Add-on for Microsoft Windows with CIM extraction; verify with a quick | head search on one event before scheduling.

Good practice — validate before you deploy

Replay each rule against a week of baseline data in search-only mode first. Record the false positives you find, update the falsepositives list, and only then enable alerting. A rule nobody trusts is worse than no rule, because it trains analysts to ignore the channel.

6Real-world case study

A Conti ransomware intrusion from 2021, reconstructed for teaching. It shows exactly where process injection fit into a real attack — and the one alert that could have stopped it.

Note — educational reconstruction

This case study is an educational reconstruction based on public reporting by The DFIR Report of a real Conti ransomware intrusion. Hostnames, user names, and addresses below are illustrative; the behavior sequence follows the public timeline.

Context

In September 2021, an employee of a mid-sized US company received a phishing email with a link to a fake document site. The site delivered BazarLoader, a loader that brings in the Cobalt Strike attack framework. Over the following days the operators stole credentials, moved through the network, copied data out, and finally detonated Conti ransomware across file servers. Process injection connected the whole chain: the Cobalt Strike beacon placed itself inside trusted Windows processes almost immediately after arrival.

Timeline

  1. Day 0 · 09:14 A user on host ACC-WKS-22 opens the phishing link. BazarLoader runs in the user session and starts a suspicious process tree: browser to script host to loader.
  2. Day 0 · 10:02 Detection point The Cobalt Strike beacon injects into svchost.exe using a remote thread. A Sysmon EventID 8 remote-thread alert fires: source from a user AppData path, target svchost, empty start module. It should have been the chain-ender — the queue held it unreviewed.
  3. Day 0 · 11:26 The beacon reads lsass.exe memory with a broad access mask. Credential theft begins; two domain admin accounts are captured.
  4. Day 1 · 08:40 Operators use RDP lateral movement with the stolen accounts and run ADFind to map the directory — standard reconnaissance before encryption.
  5. Day 2 · 22:15 Large data volumes leave to a cloud storage service. The exfiltration runs from an injected process, so per-process network alerts stay quiet.
  6. Day 4 · 02:10 Conti ransomware detonates on file servers. Backups are encrypted, ransom notes appear, and a leak-site deadline is set.

Detection point

The Day 0 Sysmon EventID 8 event — a remote thread from an AppData binary into svchost with no start module — matches rule R1 and R4 from section 5.5 exactly. Had it been triaged, the intrusion ends before any credential was stolen.

Containment

After discovery: isolate every affected host with the EDR isolate action, disable the stolen accounts, and block the C2 IP ranges at the firewall. Containment happened on Day 4, only after encryption started.

Eradication

Remove all beacon artifacts and operator tools (ADFind copies, RDP jump points), delete scheduled tasks and services the crew created, and reimage every host where injection was confirmed rather than trusting cleaners.

Recovery

Restore from offline backups after verifying them clean, reset all credentials touched by the environment, and run two weeks of heightened monitoring focused on EventID 8/10 patterns and odd parent-child process trees.

Impact

Multi-day outage of file and print services, a ransom demand in the millions, and a leak-site threat against the exfiltrated data. Recovery costs and business interruption far exceeded any security spend that was skipped.

Team response and communication

An incident commander ran the response from an IR bridge; executives received twice-daily written updates; legal advised on the ransom and disclosure questions; and the IR firm coordinated forensic timelines. Clear ownership kept decisions fast during encryption response.

Lessons learned

  • Server EDR coverage: the file servers had no agent, so injection and encryption ran blind. Cover servers, not just laptops.
  • Sysmon baseline: the EventID 8 alert existed but nothing defined a normal baseline, so nobody trusted it. Build baselines before incidents.
  • Segmentation: flat networks let one workstation reach every server. Segment so a workstation compromise cannot reach backup infrastructure.
  • Tested playbooks: isolation and account-disable steps worked only where they had been rehearsed. Purple-team the injection chain annually.

Home and small office

You will not run a SIEM at home, and you do not need to. Do this instead: keep the built-in antivirus on (it contains injection protection since recent Windows versions); install updates within days; use a standard, non-administrator account for daily work; keep 3-2-1 backups (three copies, two media types, one offline); and never install cracked software, which is the most common injection loader outside companies.

8Common mistakes and best practices

Twelve blue-team mistakes that repeatedly break injection detection, each with the symptom you will notice, the root cause, the fix, and the prevention habit that keeps it from returning.

1 — Relying on signature antivirus alone

Symptom: no injection alerts, yet incidents happen. Root cause: signatures match files, not memory behavior. Fix: enable an EDR with behavioral injection protection. Prevention: require behavior-based coverage in every tool procurement.

2 — Sysmon 8/10 missing or using the stock config

Symptom: the SIEM has no EventID 8 or 10 events at all. Root cause: Sysmon installed without a tuned configuration file. Fix: deploy a config that includes CreateRemoteThread and ProcessAccess with sensible filtering. Prevention: version the config in git and roll it out with MDM or GPO.

3 — Over-broad rules causing alert fatigue

Symptom: thousands of LSASS events per day, all ignored. Root cause: rules without allowlists or baselines. Fix: add the agent allowlist, lower severity for known-good paths, keep only high-fidelity conditions at high level. Prevention: a written noise budget per rule, reviewed monthly.

4 — Allowlists never maintained

Symptom: the same benign tool alerts every week. Root cause: no owner or process for allowlist updates. Fix: move the allowlist into a tracked data model with expiry dates. Prevention: quarterly allowlist review tied to change management.

5 — Logs stay on the endpoint

Symptom: evidence vanishes when the attacker cleans up. Root cause: forwarding pipeline missing or undersized. Fix: forward Sysmon events to the SIEM within minutes and monitor forwarder health. Prevention: pipeline-coverage dashboards per site.

6 — Ignoring EDR "informational" events

Symptom: incidents where the EDR had seen everything at low severity. Root cause: telemetry-only channels never reviewed. Fix: route informational injection telemetry into hunting queries, not the alert queue. Prevention: weekly hunt over low-severity injection events.

7 — No memory-triage capability

Symptom: teams kill the process first and lose all evidence. Root cause: no trained person or tooling for memory capture. Fix: add memory capture to the triage runbook and train two analysts per shift. Prevention: practice on a lab host monthly.

8 — Trusting process names

Symptom: "svchost did it" gets closed as a false positive. Root cause: name spoofing — malware reuses system names from wrong paths. Fix: validate the full image path and signature on every trusted-name alert. Prevention: path-based allowlists, never name-based.

9 — Clock skew breaks correlation

Symptom: event chains do not line up across hosts. Root cause: endpoints without time sync. Fix: enforce NTP on everything and normalize to UTC in the SIEM. Prevention: clock-drift alerting per host.

10 — Orphaned detections with no owner

Symptom: rules nobody tuned, nobody trusts, nobody deletes. Root cause: detections live outside a team structure. Fix: assign an owner and a review cadence to every rule. Prevention: a detection catalog with owner fields, audited quarterly.

11 — Rules never tested against a real baseline

Symptom: rules fire on day one in ways nobody predicted. Root cause: deployed straight to alerting. Fix: run every new rule in search-only mode for one week first. Prevention: a written promotion process: draft, baseline, tune, alert.

12 — False-positive rationale undocumented

Symptom: rules silently deleted months later when the person who understood them leaves. Root cause: tuning decisions never written down. Fix: document every exclusion in the rule's falsepositives and in tickets. Prevention: require a linked ticket for any rule change.

Operating habits

Daily

Review new injection alerts and their triage decisions; check that Sysmon and forwarder health dashboards show no silent gaps; glance at the overnight EDR quarantines.

Weekly

Tune the noisiest rule of the week; review new vendor reports on injection behavior; sample ten informational events from the hunt queue for missed patterns.

Monthly

Quality-check a random sample of rules for stale allowlists; run one purple-team injection test; review detection coverage against the sub-technique list.

Response checklist — first 30 minutes

  1. Validate the alert is real and the pipeline is healthy.
  2. Identify source and target processes, full paths, and user account.
  3. Isolate the host with the EDR isolate action if confirmed.
  4. Capture memory of the target process before anything dies.

Response checklist — first 24 hours

  1. Hunt the source name, hash, and target pattern fleet-wide.
  2. Rotate credentials for accounts that logged into the host.
  3. Review C2 traffic from the injected process window.
  4. Write the incident note and file tuning changes found along the way.
