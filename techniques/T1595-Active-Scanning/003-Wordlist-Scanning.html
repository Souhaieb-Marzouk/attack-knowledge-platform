T1595.003 Wordlist Scanning

Wordlist scanning means trying many names from a prepared list against a service until something answers. Attackers use it to find hidden pages, backup files, admin portals, or valid usernames. This page shows how it works, what the request flood looks like in logs, and how to catch it.

  • Parent: T1595 Active Scanning
  • Tactic: Reconnaissance (TA0043)
  • Platforms: PRE (attacker infrastructure, pre-compromise)
  • Data source: Web / Application Logs
  • Typical tools: gobuster, ffuf, dirb, wfuzz
  • Guide version: v2.0
What it is
Trying thousands of words from a list against one service, waiting for a hit.
Signature
Long runs of 404 (not found) answers from one source, with a few 200s inside.
Main risk
One exposed backup or .git folder can hand over source code and secrets.
Best defense
Remove sensitive files, alert on 404 bursts, and rate-limit request floods.

Overview

What wordlist scanning is, where it fits in the scanning family, and what you will learn.

Wordlist scanning is a guessing game played with a file. A wordlist is a text file that holds thousands of likely names: folder names, page names, file names, or usernames. A tool asks the web server for every name on the list, one after another, and writes down which names answer. Security teams also call this directory brute force: the tool works through directory (folder) and file names until real ones answer. The server answers every request with an HTTP status code — the three-digit number that reports the result of one web request.

The common codes are easy to read. 404 means "not found". 200 means "OK — it exists". 403 means "it exists, but you may not see it". 302 means "moved — follow the redirect". So a 404 is a miss, and a 200, 403, or 302 is a hit. Every hit is a finding, and one hit is all an attacker needs.

Why it matters

Wordlist scanning finds things that were never meant to be public. A forgotten backup.zip, a stray .env file, or an exposed .git folder can bypass every perimeter control at once. The .env file holds configuration secrets. The .git folder holds the source-code history.

The same method also lists valid usernames on login and password-reset pages. That list powers password attacks later, so this cheap trick feeds the next stage of the intrusion.

Where it fits in ATT&CK

T1595.003 is a child of T1595 Active Scanning. Attackers usually scan IP blocks (T1595.001) first, then probe for known software flaws (T1595.002). A CVE is a published identifier for a known software flaw. Wordlist scanning then maps the content of the chosen service.

Usernames and portals found this way feed T1110 Brute Force (password guessing). A related behavior is T1592 Gather Victim Host Information.

What ATT&CK says

ATT&CK describes this technique as iterative probing with brute-forcing and crawling. The goal is to identify content and infrastructure, not to discover valid credentials. Wordlists hold generic names, software-specific terms, or custom lists built from other reconnaissance. ATT&CK also names cloud storage buckets as targets: tools such as s3recon and GCPBucketBrute guess bucket names.

ATT&CK's mitigation guidance is direct: you cannot easily prevent someone from asking your server questions (M1056 Pre-compromise). You can remove what should not be there (M1042 Disable or Remove Feature or Program) and watch the answers you give. The official detection strategy DET0868 (analytic AN2000) says to watch for large request quantities from one source.

Caption

Defender view

  1. Load the wordlist — The attacker loads a wordlist: thousands of likely names for hidden files and folders. Wordlist scanning is simply trying each name against the website. Defender view: These lists are public and free, so assume every common name is being tried against your site every day, by many sources.
  2. Try common paths — The scanner requests name after name. Most answers are 404, which means not found. Each request is tiny, but thousands of them form a clear pattern. Defender view: A long run of 404 answers from one source is the signature of this technique. One or two 404s are browsing; hundreds per minute are a wordlist.
  3. A backup appears — The wordlist contains backup.zip and the server answers 200 OK. The attacker just found a database backup sitting in the web root. Defender view: Alert on 200 answers for sensitive paths: .zip, .sql, .bak, .git, .env. These should never exist in a public web root, so one hit is worth investigating.
  4. Source code exposed — The scanner also finds an exposed .git folder. That folder can contain the whole source code history, including passwords that were once committed. Defender view: An exposed .git or .env file is a critical finding. Treat any download of it as a secret-leak incident, not a web nuisance.
  5. Download everything — The attacker downloads the backup and the source history. The recon step is over; the data itself now gives the attacker usernames, hashes, and configuration secrets. Defender view: Watch egress from web servers. Large outbound transfers right after probing starts mean the attacker found and is taking something.
  6. WAF fights back — The web application firewall starts rate-limiting and returns 429 answers. The scan slows down, but the important files are already gone. Defender view: Rate limiting is containment, not prevention. It reduces noise and cost, but detection should fire long before the WAF becomes the only defense.
  7. Attacker switches source — The attacker continues from a new IP address with the same wordlist. Blocking single addresses barely matters when the pattern is what matters. Defender view: Tune detections on behavior — 404 bursts, sensitive-path hits, egress spikes — so a rotated source changes nothing for your alerts.
  8. Fix the root cause — The team removes the backup and the .git folder from the server, rotates every secret inside them, and adds alerts for this exact pattern. The attack surface is gone. Defender view: Fix the cause, not the symptom: build a deployment process that cannot ship backups or repositories, and verify with your own monthly wordlist scan in the lab.

Red Team / Hacker Perspective

How attackers enumerate names and why one lucky guess is all they need.

Attackers enumerate a service when they list out its names one by one. They do this when a web application has no public sitemap. The goals: admin portals, staging sites, API documentation, exposed repositories, and backups. A second goal is username enumeration on login and password-reset pages, because a list of valid usernames powers later credential attacks (T1110). One lucky guess — one forgotten archive — is enough to change the whole story.

Tooling

  • gobuster, ffuf, dirb, wfuzz, and DirBuster all send the same simple requests, only very fast.
  • Feroxbuster-style walkers follow found links and scan deeper levels.
  • Tools such as amass run the same trick against subdomain names.

Wordlists

  • Public collections such as SecLists or the dirb wordlists.
  • Software-specific lists for WordPress, phpMyAdmin, and similar products.
  • Custom lists built from company names, product names, and words found on the target's own site.

Tuning

  • Extensions: try each name again with .php, .asp, .bak, .zip.
  • Threads: many requests in parallel.
  • Filters: keep only chosen status codes or response sizes, so noise drops and hits stand out.

Username enumeration

  • Different error text for "unknown user" and "wrong password".
  • Different response size for the same two cases.
  • Different answer time, because a real user costs a password check.

Where it runs

  • Public websites and APIs (Application Programming Interfaces — machine-facing web services).
  • Storage buckets: cloud storage with globally unique names, so tools such as s3recon and GCPBucketBrute guess bucket names too.
  • CI/CD artifacts (build outputs published by mistake). CI/CD means Continuous Integration/Continuous Delivery — the pipeline that builds and ships software.
  • Mail portals and admin panels.

Preconditions

  • The service is reachable from the attacker's network.
  • Most path scans need no login.
  • Answers must differ between hits and misses — if every path answers the same way, the scan learns nothing.
Lab only — legal and ethical use

Run scanning commands only against systems you own, systems you have written permission to test, or designated practice targets such as scanme.nmap.org or the documentation range 203.0.113.0/24. Scanning systems without permission is illegal in many countries and violates responsible security practice.

Lab example — directory scan against your own local container
gobuster dir -u http://localhost:8080 -w /usr/share/wordlists/dirb/common.txt

# dir  directory mode: try folder and file names
# -u   target URL (here: your own lab container on port 8080)
# -w   the wordlist file with the names to try

Variations defenders should expect

  • Virtual host and subdomain enumeration: a virtual host (vhost) is a second website served under another name by the same server. Lists of likely names, such as staging or dev, are tried against DNS (Domain Name System — the internet's name lookup service).
  • Parameter fuzzing: testing values inside query strings — the part of a URL after the ? — to find hidden behavior.
  • Recursive scanning: every found directory is scanned again, level by level.
  • Many-source scanning: requests spread over many source addresses so per-IP limits never trigger.
Scanner mistakes (learn the pattern)
  • Hammering without rate control gets the scanner banned. A rate limit caps how many requests one client may send in a time window. A WAF (Web Application Firewall) enforces it.
  • Ignoring 403 answers misses hidden content — 403 often means "this exists".
  • Trusting status codes alone fails when apps answer 200 for everything. Filter by response size too.

Blue Team / SOC Perspective

Wordlist scanning is the noisiest reconnaissance technique on the web — if you keep web logs.

The blue team (defenders) and the SOC (Security Operations Center — the team that watches alerts) already receive this technique as a data stream. Every miss the attacker makes lands in your web access log. You rarely need new sensors; you need to read the streams you already have.

Web access logs

The strongest source. Every request is logged with its status code, so one client's 404 stream shows the scan directly, request by request.

WAF events

A WAF (Web Application Firewall) filters requests in front of the app. Its logs show rate-limit triggers and tool fingerprints. A user agent is the program name a browser or tool sends with every request. Scanner agents such as gobuster or ffuf stand out.

Proxy and egress logs

Egress means traffic leaving your network. Large downloads from a web server right after scanning starts mean the attacker found something and is taking it.

Application logs

Failed lookups and unusual record-by-record requests show enumeration inside the app itself, especially on login and password-reset endpoints.

Artifacts to hunt

  • 404 and 403 floods from one source address.
  • Paths requested in list order — alphabetical or wordlist order.
  • Scanner user-agents such as gobuster, ffuf, or dirbuster.
  • Sudden 200 answers on sensitive paths.
  • Egress spikes shortly after the burst.

Where to look

  • SIEM dashboards (SIEM: Security Information and Event Management — your central log search platform) on status-code distribution per client.
  • WAF top-talker lists, which rank the noisiest clients.
  • Web-root integrity monitoring, which reports files that appear or change.
Why it matters

The scan tells you what attackers believe might exist on your site. A 200 answer on a sensitive path is an incident, not just an alert — treat it like one.

Triage flow — five steps

  • Step 1Confirm the burst. Check the request rate and how many distinct paths the client tried.
  • Step 2List every non-404 answer from that client. That list is the attacker's loot list.
  • Step 3Verify that none of those paths should exist. Remove any that do.
  • Step 4Block or rate-limit the source and keep watching — attackers rotate addresses.
  • Step 5Fix the pipeline that shipped the sensitive file and rotate every secret it exposed.

5.2 Threat Intelligence

Use outside knowledge to size the threat, then add your own sightings. These source types cover most needs.

MITRE ATT&CK

Free knowledge base of attacker behavior. Use it to name what you see, map detections, and plan coverage. Confidence in behavior mapping: high.

Vendor reporting

Blogs and reports from security vendors (CrowdStrike, Mandiant, Microsoft, Palo Alto Unit 42, Cisco Talos, Recorded Future). Usually high or medium confidence; check their stated evidence.

Government advisories

CISA advisories and the Known Exploited Vulnerabilities (KEV) catalog. High confidence. Use KEV to prioritize patching of what attackers actually scan for and exploit.

OSINT scanner context

GreyNoise classifies internet scanners so you can tell mass scanners from targeted ones. Shodan and Censys show what attackers can see about your exposure. AbuseIPDB collects abuse reports. Confidence: medium to high, verify before blocking.

ISACs

Sector Information Sharing and Analysis Centers (for example MS-ISAC, FS-ISAC, H-ISAC) share member sightings with high trust. Useful for early warning inside your sector.

Internal telemetry

Your own firewall, flow, IDS, and honeypot history. Highest confidence for your environment. Keep 90+ days searchable so you can hunt for patterns you only notice later.

5.4 Logs and Patterns

Six outcomes matter, and each has a log shape you can learn once and reuse. Card N pairs with Threat N in Section 5.3 and Rule N in Section 5.5.

1. Path guessing at scale

  • Sources: web access logs, WAF logs.
  • Fields: client, path, status, user agent.
  • Normal: mostly 200 answers, with a few 404s from real browsing.
  • Suspicious: hundreds of 404 or 403 answers from one client within minutes.
  • Logic: 404-burst counting per client (Rule 1), backed by tool user agents (Rule 3).

2. Sensitive files and directories

  • Sources: web access logs, WAF logs, file integrity monitoring.
  • Fields: client, path, status, bytes.
  • Normal: no 200 answers on sensitive paths.
  • Suspicious: any 200 on .git, .env, or archive paths, often inside a 404 burst.
  • Logic: match the path pattern plus status 200 (Rule 2); pair with 404 bursts (Rule 1).

3. Admin portals and hidden content

  • Sources: web access logs, WAF logs, application logs.
  • Fields: client, path, status, user agent.
  • Normal: staff use the portal from known ranges.
  • Suspicious: a first-ever 200 on admin-style paths from an unknown client. In APIs, one client cycling many object IDs is the IDOR variant.
  • Logic: first-time 200 per source on watched paths; flag fuzzing-tool user agents (Rule 3); read application logs for IDOR.

4. Username enumeration

  • Sources: application auth logs, access logs with body fields.
  • Fields: username, result, response time, bytes.
  • Normal: one or two failed logins per user; similar sizes.
  • Suspicious: many different usernames from one source, with sizes split into two groups.
  • Logic: count per client plus response-size variance (Rule 4).

5. Backup and archive probing

  • Sources: web access logs (Apache and IIS), file integrity monitoring.
  • Fields: client, path, status.
  • Normal: no requests at all for archive extensions.
  • Suspicious: any request for .bak, .sql, .zip, .old, or .copy — even 404 answers prove the hunt.
  • Logic: extension matching regardless of status (Rule 5); correlate with the 404 burst (Rule 1).

6. Subdomain and vhost enumeration

  • Sources: DNS logs (Zeek dns.log), DNS server logs.
  • Fields: query, client, answer code.
  • Normal: few NXDOMAIN answers (the name does not exist) per client.
  • Suspicious: long NXDOMAIN runs against your own zone.
  • Logic: count queries per source in a short window (Rule 6).

In IIS logs, cs_uri_stem is the requested path and sc_status is the answer code. Note the third line: custom scripts often send no cs(User-Agent) at all, so your rules must not require a user-agent to fire.

Application log — username enumeration leaking through timing and text
2026-06-10 10:31:02 POST /login user=admin result=unknown_user (23ms)
2026-06-10 10:31:03 POST /login user=root result=unknown_user (24ms)
2026-06-10 10:31:04 POST /login user=j.smith result=bad_password (140ms)

Timing and message differences betray the enumeration. "Unknown user" answers fast because no password check runs. "Bad password" costs 140 milliseconds — and quietly confirms that j.smith exists.

5.5 Sigma Rules and Splunk SPL

Sigma is an open rule format for detections; SPL is Splunk's search language. Each rule below has matching SPL and the field assumptions you must check. Rule numbers match the threats in Section 5.3 and the log cards in Section 5.4: Rule N detects Threat N.

Rule 1 — High Rate of 404 Answers from a Single Client

Sigma YAML — 404 burst from one client
title: High Rate of 404 Answers from a Single Client
id: 6c2f8a17-3b95-4d02-ae74-9f5c1e8d3b60
status: stable
description: >
  One client generates more than 100 not-found answers within five minutes. Long 404 runs are
  the signature of wordlist scanning for hidden paths (ATT&CK T1595.003).
references:
  - https://attack.mitre.org/techniques/T1595/
  - https://attack.mitre.org/techniques/T1595/003/
author: Detection Engineering Team
date: 2026-10-20
logsource:
  category: webserver
  product: apache
detection:
  selection:
    status: 404
  timeframe: 5m
  condition: selection | count() by client_ip > 100
fields:
  - client_ip
  - url
  - status
  - UserAgent
falsepositives:
  - Broken links pushed by a site redesign
  - Aggressive legitimate crawlers
level: medium
tags:
  - attack.reconnaissance
  - attack.t1595
  - attack.t1595.003
Splunk SPL — same logic
index=web sourcetype=access_combined status=404
| bin _time span=5m
| stats count dc(url) AS distinct_paths by _time, client_ip, useragent
| where count > 100
| sort - _time - count

Field assumptions: Apache combined logs parsed into client_ip, url, status, and useragent. For IIS, use sourcetype=iis with c_ip, cs_uri_stem, and sc_status.

Rule 2 — Sensitive Path Answered with HTTP 200

Sigma YAML — 200 on a path that should not exist
title: Sensitive Path Answered with HTTP 200
id: d9e4b7f2-1a63-4c85-90bd-2e8f6a4c17d9
status: stable
description: >
  A web server returns 200 OK for a path that should never exist in a public web root, such
  as .git, .env, or archive files. One hit can mean source code or secret leakage and matches
  the goal of wordlist scanning (ATT&CK T1595.003).
references:
  - https://attack.mitre.org/techniques/T1595/003/
author: Detection Engineering Team
date: 2026-10-20
logsource:
  category: webserver
  product: apache
detection:
  selection_status:
    status: 200
  selection_path:
    url|re: '(?i)(\.git/|\.env$|\.env\.|\.bak$|\.sql$|\.zip$|\.tar\.gz$|backup|dump)'
  condition: selection_status and selection_path
fields:
  - client_ip
  - url
  - status
falsepositives:
  - Intentionally public downloads that match the pattern (verify naming)
  - Marketing archives served on purpose
level: critical
tags:
  - attack.reconnaissance
  - attack.t1595
  - attack.t1595.003
Splunk SPL — same logic
index=web sourcetype=access_combined status=200
| regex url="(?i)(\.git/|\.env$|\.env\.|\.bak$|\.sql$|\.zip$|\.tar\.gz$|backup|dump)"
| stats count values(client_ip) AS clients by url
| sort - count

Field assumptions: as in Rule 1. Review the regex against your own file naming, so approved download pages do not wake the on-call analyst.

index=web sourcetype=access_combined
| regex useragent="(?i)(gobuster|ffuf|dirbuster|wfuzz|dirb|feroxbuster)"
| stats count dc(url) AS distinct_paths values(status) AS statuses by client_ip, useragent
| sort - count

Field assumptions: useragent is parsed from the trailing quoted field of combined logs. Adjust the name if your parser uses user_agent or cs_user_agent. Expect misses when attackers blank the agent, so keep the behavior rules running too.

Rule 4 — Username Enumeration via Response Size Difference

Sigma YAML — login burst; size variance in the description and SPL
title: Username Enumeration via Response Size Difference
id: 8b7e2d51-4c09-4f7a-a2e6-1d3c5b9f04a2
status: experimental
description: >
  One client posts more than 30 login attempts to /login within ten minutes. The rule flags the
  burst; the response size then separates the two outcomes. When the answer size varies between
  users, the application tells "unknown user" and "wrong password" apart, so attackers can
  collect valid usernames that later feed password guessing (ATT&CK T1110; enumeration phase of
  ATT&CK T1595.003).
references:
  - https://attack.mitre.org/techniques/T1595/003/
  - https://attack.mitre.org/techniques/T1110/
author: Detection Engineering Team
date: 2026-10-20
logsource:
  category: webserver
  product: apache
detection:
  selection:
    url: /login
    method: POST
  timeframe: 10m
  condition: selection | count() by client_ip > 30
fields:
  - client_ip
  - url
  - method
  - status
  - bytes
falsepositives:
  - Load or penetration tests from known scanner sources
  - One user who forgot a password and retries well below the threshold
level: high
tags:
  - attack.reconnaissance
  - attack.t1595
  - attack.t1595.003
  - attack.t1110
Splunk SPL — burst plus response-size variance
index=web sourcetype=access_combined url="/login" method=POST
| bin _time span=10m
| stats count AS attempts dc(username) AS distinct_users stdev(bytes) AS size_var avg(bytes) AS avg_bytes by _time, client_ip
| where attempts > 30
| sort - _time - attempts

Field assumptions: username must be extracted from the POST body or the application's auth log; plain access logs carry no body. The SPL filters on the same burst as the Sigma rule — more than 30 attempts in ten minutes. The grouping uses the same bin _time span=10m. It adds triage columns: distinct_users and size_var, the spread of answer sizes. A size_var in the hundreds of bytes means the app answers differently, so usernames are enumerable. If your access logs carry no username at all, ship the application's own login log and count distinct users there.

Rule 5 — Backup Extension Probes Regardless of Status

Sigma YAML — extension probes on IIS, any status
title: Backup Extension Probes Regardless of Status
id: 51c9e7a3-2b46-4d18-9f0c-7e5a3d6b82f4
status: stable
description: >
  A client asks for files with backup or copy extensions such as .bak, .sql, .zip, .old, or
  .copy. Even a 404 answer proves that someone is hunting for leftover archives; a 200 answer
  means the file is really there. Correlate this with the 404-burst rule (ATT&CK T1595.003).
references:
  - https://attack.mitre.org/techniques/T1595/003/
author: Detection Engineering Team
date: 2026-10-20
logsource:
  category: webserver
  product: iis
detection:
  selection:
    cs_uri_stem|contains:
      - .bak
      - .sql
      - .zip
      - .old
      - .copy
  condition: selection
fields:
  - c_ip
  - cs_uri_stem
  - sc_status
  - cs(User-Agent)
falsepositives:
  - Public download areas that really serve .zip archives (verify the path)
  - Internal CI/CD build artifacts published on purpose
level: medium
tags:
  - attack.reconnaissance
  - attack.t1595

Splunk SPL — same logic
index=web sourcetype=iis
| regex cs_uri_stem="(?i)\.(bak|sql|zip|old|copy)"
| stats count values(sc_status) AS statuses values(c_ip) AS clients by cs_uri_stem
| sort - count

Field assumptions: IIS W3C logs parsed into cs_uri_stem, sc_status, and c_ip. Check your own archive naming first, so legitimate download paths do not generate noise.

Rule 6 — Subdomain Enumeration against DNS

Sigma YAML — NXDOMAIN flood against your zone (Zeek)
title: Subdomain Enumeration against DNS
id: a4d08b6f-9e13-4c57-b2a8-3f6c1e9d5b07
status: stable
description: >
  One source asks DNS (Domain Name System — the internet's name lookup service) for more than
  50 names under your own zone within ten minutes. Most answers are NXDOMAIN ("no such name"),
  the classic sign of subdomain enumeration with a wordlist. The scan maps staging and admin
  systems before any attack (ATT&CK T1595.003).
references:
  - https://attack.mitre.org/techniques/T1595/003/
author: Detection Engineering Team
date: 2026-10-20
logsource:
  category: dns
  product: zeek
detection:
  selection:
    query|endswith: .target-company.example
  timeframe: 10m
  condition: selection | count(query) by id_orig_h > 50
fields:
  - id_orig_h
  - query
  - rcode_name
falsepositives:
  - Corporate DNS resolvers that answer for many users at once (allowlist them)
  - Monitoring jobs that check a fixed list of names
level: medium
tags:
  - attack.reconnaissance
  - attack.t1595
  - attack.t1595.003
Splunk SPL — same logic
index=dns sourcetype=zeek:dns query="*.target-company.example"
| bin _time span=10m
| stats count(query) AS lookups values(query) AS sample_names values(rcode_name) AS answers by _time, id_orig_h
| where lookups > 50
| sort - _time - lookups

Field assumptions: Zeek dns.log shipped as JSON (sourcetype=zeek:dns). id_orig_h is the asking host and rcode_name with the value NXDOMAIN marks a miss. Replace target-company.example with your own zone.

Real-World Case Study

A documented campaign tried wordlists against roughly 51,000 domains. The victims never noticed it, one request at a time.

Composite case — read this first

The campaign facts below come from public research published by Imperva in 2019. The victim story is a composite built from the documented pattern, not a single named company. Campaign facts are reported as published.

February 2019 — the campaign

Imperva documents a campaign brute-forcing hidden directories and files across approximately 51,000 domains. It used a rotating pool of thousands of source IPs, so no single address crossed per-IP thresholds.

What it hunted

Classic finds: backup archives, .git folders, admin panels, phpMyAdmin, and configuration files. That list is the same watchlist this page recommends for your own alerts.

March 2019 — follow-up

Analyses note the same pattern continuing from cloud and residential sources. Rotation, not raw volume, was the design choice.

Composite victim timeline

The victim below is a composite built from the documented pattern: a mid-sized e-commerce company.

  • Day 0During a migration, a developer leaves backup.zip — a full database dump — in the public web root.
  • Day 3A wordlist scan finds /backup.zip. The 84 MB dump is downloaded.
  • Day 4Credentials inside the dump are extracted. An admin login appears from a new source.
  • Day 5The anomaly team notices admin access from an unknown ASN (Autonomous System Number). The ASN names the network provider an address belongs to. An investigation starts.
  • Day 7The exposure is confirmed. A customer-data notification is filed.

Attack chain

StepMappingWhat happened
Wordlist scanT1595.003The scan found the exposed archive within three days.
Exposed archive foundRecon result/backup.zip answered 200 and was downloaded.
Credential extractionOffline workUsernames and password hashes came out of the dump.
Valid loginT1078Extracted credentials opened the admin portal.
Data theftCollectionCustomer data was read and taken out.

Detection point

The 200 answer on /backup.zip sat in the web logs on day 3. The admin login's source ASN sat in the identity logs on day 4. Both were searchable weeks before the notification.

Containment

The WAF rate-limited and blocked the scanning pool, the archive was taken offline, and active sessions were revoked.

Eradication

Teams removed all archives from web roots, rotated every database and admin credential, and audited other web roots for the same mistake.

Recovery

The site was redeployed from a clean pipeline. The sensitive-path rule and the 404-burst alert were added, and an internal wordlist scan verified the fix.

Impact

Customer-data exposure, a notification duty under GDPR, and weeks of engineering time — the direct cost of one forgotten file.

Team response

Security and engineering ran a joint review and a blameless postmortem. The migration checklist now includes a web-root hygiene gate.

Lessons learned
  • Deployment pipelines must not ship backups — gate this in CI.
  • 404 monitoring is cheap and catches the hunt itself.
  • Secrets in dumps outlive the file. Rotate immediately.
  • "Hidden" is not "protected". Assume every path is discoverable.

Mitigation and Defense

You cannot stop someone from asking questions — ATT&CK's M1056 Pre-compromise mitigation says so. But you control what answers exist and how loud the answers are. Work the nine areas below.

Policy

  • Web-root hygiene policy: no archives, no version-control metadata such as .git.
  • Deployment pipeline gates: CI checks block stray files before release.

Identity

  • Uniform login errors: one message — "wrong username or password".
  • Constant response times on login and reset pages.
  • MFA (Multi-Factor Authentication) on admin portals.

Endpoint

  • File Integrity Monitoring (FIM) on web roots — an alert when files appear or change.
  • Strip version-control metadata from builds.

Network

  • WAF rate limiting per client.
  • Tarpitting for scanner pools: answer very slowly so scanning costs time.
  • Block datacenter ASNs from admin paths where feasible.

Cloud

  • Storage buckets private by default, with access logs enabled.
  • CDN/WAF in front of all public apps (CDN: Content Delivery Network).

Logging

  • Full access logs including response size.
  • WAF logs shipped to the SIEM.
  • Egress logs for web servers — downloads after scans.

Monitoring

  • 404-burst alerts.
  • Sensitive-path 200 alerts, rated critical.
  • Response-size variance alerts on login endpoints.

Backup

  • Backups stored off the web root, with access control.
  • Verify that no test data ships in deployments.

Response

  • Wordlist-scan runbook: confirm the burst first.
  • List non-404 answers, verify the paths.
  • Remove and rotate, then tune the alerts.

Home and small-office additions

Hosting hygiene

  • Remove old site files from hosting — yesterday's site is today's leak.
  • Disable directory listing in the web server configuration.

Hosting protection

  • Keep the CMS (Content Management System, for example WordPress) and its plugins updated.
  • Use the hosting provider's WAF where available.

Priority actions
