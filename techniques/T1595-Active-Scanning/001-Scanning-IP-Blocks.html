T1595.001 Scanning IP Blocks

Scanning IP blocks means testing many addresses in a network range to find live hosts. Attackers sweep whole ranges, such as a /24 block of 256 addresses, before they choose a target. This page shows how the sweep works, what it leaves in logs, and how to detect it.

  • Parent: T1595 Active Scanning.
  • Tactic: Reconnaissance (TA0043).
  • Platforms: PRE (attacker infrastructure, pre-compromise).
  • Data source: Network Traffic Flow.
  • Typical tools: masscan, zmap, nmap.
  • Guide version: v2.0.
What it is
A sweep of many IP addresses in one range to find live systems and open doors.
Signature
One source touches hundreds of addresses in minutes, usually with tiny packets.
Main risk
Finds every internet-facing device you forgot about, including IoT (Internet of Things) devices and old gear.
Best defense
Edge filtering plus flow monitoring: see the sweep, then shrink what answers.

Overview

What this sub-technique is, how it differs from its parent, and what you will learn.

Every device on a network has an IP (Internet Protocol) address — a number such as 203.0.113.10. Providers and companies get these addresses in blocks, which are ranges of numbers next to each other. A smaller range inside a block is often called a subnet. Blocks are written in CIDR (Classless Inter-Domain Routing) notation: the number after the slash counts fixed bits of the address. A /24 block holds 256 addresses; a /16 block holds 65,536. In this sub-technique the attacker does not attack one server. The attacker sends a small, cheap probe to every address in a block. Each live host answers. The answers draw a map of what exists.

The simplest sweep is a ping sweep: one small test message to every address, waiting to see which ones answer. That test message uses ICMP (Internet Control Message Protocol) — the helper protocol that the ping tool uses. Faster tools usually send TCP SYN packets instead. A SYN packet is the first packet of a normal connection, so its presence rarely alarms anything.

Wide sweeps matter because they find forgotten assets: an old test server, a smart camera, or a storage box somebody plugged in years ago. Sweeps run constantly against every public range. Attackers also sweep one company’s range right before a targeted intrusion. A sweep can be the first visible sign that someone is studying your network.

Where it fits in ATT&CK

MITRE ATT&CK is a free knowledge base that names attacker behaviors. This technique is the child of T1595 Active Scanning, tactic TA0043 Reconnaissance. The sweep feeds later steps: T1595.002 Vulnerability Scanning probes the found hosts for known flaws, and T1190 Exploit Public-Facing Application uses those flaws for entry. The sibling technique T1046 Network Service Scanning does the same job from inside a network after a breach.

What you will learn on this page

  • Read the sweep pattern in flow and firewall logs.
  • Tell mass internet scanners from targeted attackers.
  • Write Sigma and Splunk rules that alert on breadth, not just volume.
  • Run the response loop: verify answers, block, shrink the exposed surface.

Defender view

The story in eight steps

  1. Pick a range — The attacker wants to map the whole company range, not one server. Public records show which ranges the company owns, so a /24 with 256 addresses becomes the target. Defender view: Attackers read the same public records you do. If you do not know which addresses are yours and live, they will know before you do.
  2. Sweep the range — The attacker fires fast probes at every address in the range. Tools such as masscan can try all 256 addresses in seconds, which looks like a short burst of traffic. Defender view: A sweep is easy to see in flow data: one source, hundreds of destinations, tiny packets, almost no reply bytes. Breadth matters more than speed.
  3. Live hosts answer — Four addresses answer. Those are live hosts. The attacker now knows exactly which machines exist and can plan what to do with each one. Defender view: Every host that answers should be in your inventory. Match the answering addresses against your asset list; unknown hosts are an immediate finding.
  4. Collect the results — The attacker saves the list of live hosts and open ports. The recon phase is cheap for them and already gave a map of the company edge. Defender view: Compare your flow logs against this list. A camera or an old storage box answering from your public range is exactly the asset this technique is designed to find.
  5. Defender sees the flood — On the defender side, the firewall and flow records show the sweep clearly: one source touched every address. This is one of the easiest techniques to see — if someone is watching. Defender view: Build an alert on breadth, not just volume: a source touching more than 100 unique addresses in 5 minutes is a sweep, whatever the packet rate.
  6. IDS confirms a scan — The intrusion detection system raises a scan alert that matches known tool signatures. The analyst can now name the technique: scanning IP blocks, MITRE ATT&CK T1595.001. Defender view: Map alerts to ATT&CK IDs so reports and dashboards use one language. It also makes it easy to pull related detections later.
  7. Block at the edge — The team adds a block for the scanning source at the edge. The noise stops. But blocking one address is a pause, not a victory — the attacker can rent another. Defender view: Blocks buy quiet time for response. The durable fix is the next step: shrink the number of addresses and services that answer at all.
  8. Attacker rotates — Minutes later a new source sweeps the same range. The pattern is identical, only the address changed. Defenders who alert on the pattern stay ahead. Defender view: This is why breadth-based and pattern-based detections beat simple IP blocklists. Report the behavior, automate the block, and review what scanners keep finding.

Red Team / Hacker Perspective

Why attackers sweep ranges instead of single hosts, and how a sweep is performed.

Why sweep a whole block?

  • Find the unknown. Single-host checks only learn about hosts the attacker already knows. A sweep finds everything that answers, including forgotten systems.
  • Cheap per target. Each probe is one small packet. Cost per host is near zero, so testing 256 or 65,536 addresses is practical.
  • Build target lists. The output — live host plus open port — is raw material for later stages like vulnerability scanning and password attacks.
  • Sell the results. Initial access brokers (criminals who sell ready-made entry points into companies) buy and sell these live-host lists.

How the sweep is done

  • Tooling. masscan is built for speed; zmap sends a single research-style packet per host; nmap gives detail and service guesses.
  • Source rotation. The attacker spreads probes over many rented VPS hosts (virtual private servers), so no single address carries the whole sweep.
  • Timing. Sweeps often run at night or on weekends, spread across hours, to slip under busy-hour noise.
  • Protocol choices. SYN probes hit the top ports. ICMP pings cover pure host discovery. UDP (a protocol that sends packets without a handshake) reaches services such as DNS, NTP (time sync), and SNMP (device management).

Where sweeps happen

  • Whole-internet sweeps run by botnets and recruitment scanners.
  • Targeted sweeps of one company’s ranges. The attacker finds the ranges through public records: WHOIS listings (public ownership registries), RPKI routing data (proof of range ownership), DNS, and certificate transparency logs.
  • Cloud provider ranges, hunting for exposed management consoles and stray instances.

What the attacker needs

  • Reachability: the target ranges must answer from the internet.
  • No credentials, no malware, no victim software — probes only.
  • Some operational security, but attackers accept being seen; they expect to rotate sources.
Lab only — legal and ethical use

Run scanning commands only against systems you own, systems you have written permission to test, or designated practice targets such as scanme.nmap.org or the documentation range 203.0.113.0/24. Scanning systems without permission is illegal in many countries and violates responsible security practice.

Lab examples — documentation range 203.0.113.0/24 (TEST-NET-3).
nmap -sn 203.0.113.0/24                            # host discovery across a documentation range
masscan 203.0.113.0/24 -p80,443,3389 --rate 1000   # fast sweep of three ports (lab only)
zmap -p 443 203.0.113.0/24                         # single-port scan example

Variations you will meet

  • Distributed sweeps. Hundreds of sources each take one slice of the range, so no source shows breadth on its own.
  • Scan after breach. The same tooling runs inside the network to map it; that overlaps with T1046 Network Service Scanning.
  • IPv6 prefix probes. IPv6 (the newer, much larger address format) is too large to scan fully, but attackers probe chosen prefixes, and forgotten IPv6 assets do answer.

Common attacker mistakes

  • Ignoring legal scope and sweeping networks they were never allowed to touch.
  • Sweeping too fast and waking rate-based IPS (intrusion prevention) rules.
  • Not recording results, so the quiet advantage of a slow sweep is wasted on a re-scan.

Blue Team / SOC Perspective

How a sweep looks in your telemetry and how to triage it fast.

NetFlow / IPFIX and Zeek

NetFlow and IPFIX are standard summaries of network connections. Zeek (an open-source network monitor) writes the same facts to its conn.log. Both give the key measure: unique destinations per source, per time window.

Firewall deny logs

Deny records at the edge carry the sweep almost line by line. One source, hundreds of destinations, action deny, zero bytes answered. Cheap to search, hard to hide.

IDS scan signatures

An IDS (intrusion detection system) matches probe patterns against known tool signatures, for example the ET SCAN rules for masscan and nmap. The IDS names the tool; flow data names the breadth.

Cloud VPC flow logs

Virtual Private Cloud (VPC) flow logs record accepted and rejected connections inside cloud ranges. REJECT rows with one source and many dstaddr values are the cloud version of the same sweep.

ISP and DDoS-provider notices

Your internet provider and any DDoS (Distributed Denial of Service) protection service see the sweep from outside. They send abuse notes or rate-limit notices — route them into your triage queue.

Why it matters

A sweep announces interest in your range. It also silently inventories your forgotten assets for whoever runs it. Treat every sweep as both an alert and a free audit question: what answered, and do we know all of it?

Artifacts of a sweep

  • One source touches hundreds of destinations within minutes.
  • Packets are tiny and uniform — same size, same shape, machine-made.
  • SYN probes with no answer: in Zeek’s conn.log the state S0 means “SYN seen, never answered”.
  • Probes land in unused address space where no real client should be.
  • Only a handful of addresses answer — the live map the attacker wanted.

Where to look first

  • Flow analytics: dashboard of unique destinations per source in 5-minute buckets.
  • Firewall deny summary grouped by source address.
  • IDS ET SCAN alerts, grouped by scanning tool.
  • VPC flow logs for every public cloud range you own.

Five-step triage flow

  • Step 1 — ConfirmMeasure the breadth and the window: how many unique addresses, from how many sources, in how many minutes. One number decides if this is a sweep.
  • Step 2 — AnswersCheck what answered, and whether every answering address is a known, intended asset. Unknown answers are findings of their own.
  • Step 3 — ClassifySort the source with reputation feeds, whois records (public ownership data), and ASN lookups: known scanner, researcher, or unknown. GreyNoise-style context saves an hour per alert.
  • Step 4 — ContainBlock or rate-limit the source, and record why. A written note now saves the next analyst the same question.
  • Step 5 — Fix the rootReduce the answering surface: close unneeded services, pull forgotten hosts off the range, and document the exceptions you keep.

MITRE ATT&CK

Free knowledge base of attacker behavior. Use it to name what you see, map detections, and plan coverage. Confidence in behavior mapping: high.

Vendor reporting

Blogs and reports from security vendors (CrowdStrike, Mandiant, Microsoft, Palo Alto Unit 42, Cisco Talos, Recorded Future). Usually high or medium confidence; check their stated evidence.

Government advisories

CISA advisories and the Known Exploited Vulnerabilities (KEV) catalog. High confidence. Use KEV to prioritize patching of what attackers actually scan for and exploit.

OSINT scanner context

GreyNoise classifies internet scanners so you can tell mass scanners from targeted ones. Shodan and Censys show what attackers can see about your exposure. AbuseIPDB collects abuse reports. Confidence: medium to high, verify before blocking.

ISACs

Sector Information Sharing and Analysis Centers (for example MS-ISAC, FS-ISAC, H-ISAC) share member sightings with high trust. Useful for early warning inside your sector.

Internal telemetry

Your own firewall, flow, IDS, and honeypot history. Highest confidence for your environment. Keep 90+ days searchable so you can hunt for patterns you only notice later.

5.4 Logs and Patterns

Each card below carries the number of the threat it detects from 5.3. Card N pairs with threat N and with Sigma rule N in 5.5. Together the six cards cover every ranked scenario.

Threat 1 — Internet-wide management-port sweep

Sources: firewall denies, flow records, IDS.
Fields: src_ip, dest_ip, dest_port, action.
Normal: a VPN (virtual private network) gateway or backup host touching dozens of endpoints.
Suspicious: one external source, 50+ addresses, port 22/23/3389, all denied.
Logic: breadth per source per 10 minutes, grouped by destination port.

Threat 2 — Targeted sweep of one organization’s ranges

Sources: flow data, firewall denies, honeypots.
Fields: id.orig_h, id.resp_h, conn_state (Zeek).
Normal: scanners you approved, inside change windows.
Suspicious: unknown source walks your whole range in minutes; state S0 everywhere.
Logic: unique destinations per source in 5 minutes, compared against the approved-scanner list.

Threat 3 — Residential and ISP IoT recruitment sweep

Sources: ISP notices, flow data, device logs.
Fields: source address, destination port 23/2323, bytes.
Normal: almost nothing reaches inbound Telnet on a clean network.
Suspicious: any Telnet probe wave, especially from consumer-looking source ranges.
Logic: deny count on port 23 per source; zero legitimate use makes even low thresholds safe.

Threat 4 — Cloud CIDR scanning

Sources: VPC flow logs, cloud load-balancer logs.
Fields: srcaddr, dstaddr, action (AWS naming).
Normal: NAT (network address translation) gateways and load balancers that legitimately touch many addresses.
Suspicious: one external source rejected at 100+ addresses in five minutes.
Logic: unique dstaddr per srcaddr per 5 minutes; exclude your NAT gateways after baselining.

Threat 5 — Distributed low-and-slow sweep

Sources: flow analytics over hours, firewall denies.
Fields: src_ip, dest_ip, timestamps.
Normal: steady background of a few probes per source.
Suspicious: many fresh sources, each small, together covering one block.
Logic: count of unique sources per destination block per hour; the inverse of the classic rule.

Threat 6 — IPv6 prefix probing

Sources: IPv6 flow records, edge firewall denies, IDS.
Fields: src_ip, dest_ip (both IPv6), action.
Normal: almost no inbound probes to the global unicast prefixes you own.
Suspicious: one source denied across 20+ addresses inside one of your prefixes.
Logic: unique IPv6 destinations per source per 15 minutes; alert at low counts because clean prefixes stay quiet.

5.5 Sigma Rules and Splunk SPL

Sigma is a standard format for writing detection rules once. You can run the same rule on many SIEMs (Security Information and Event Management systems). Rules are written in YAML, a simple indented text format. Splunk SPL is the search language of the Splunk platform. Rule numbers match the threats: rule N detects threat N from 5.3 and 5.4. Each rule has a matching SPL query with the same fields, the same count, and the same time window. You can test the logic in both places.

Sigma rule 1 (YAML) — Port Sweep of Remote Management Ports · covers threat 1.
title: Port Sweep of Remote Management Ports
id: 9e1c7a52-3d84-4f0b-b6a9-1c2e5d8f7a30
status: stable
description: >
  One source probes the same management port (here RDP 3389) across many destination
  addresses. Sweeps of management ports often precede brute-force attempts against exposed
  systems and match ATT&CK T1595.001.
references:
  - https://attack.mitre.org/techniques/T1595/001/
author: Detection Engineering Team
date: 2026-10-20
logsource:
  category: firewall
  product: paloalto
detection:
  selection:
    dest_port: 3389
    action: deny
  timeframe: 10m
  condition: selection | count(dest_ip) by src_ip > 50
fields:
  - src_ip
  - dest_ip
  - dest_port
  - action
falsepositives:
  - Corporate VPN concentrator connecting to many remote endpoints
  - Approved remote-access scanning tools
level: high
tags:
  - attack.reconnaissance
  - attack.t1595
  - attack.t1595.001
Splunk SPL — rule 1 · Port Sweep of Remote Management Ports.
index=firewall sourcetype=pan:traffic dest_port=3389 action=deny
| bin _time span=10m
| stats dc(dest_ip) AS unique_dests by _time, src_ip
| where unique_dests > 50

Field assumptions: Palo Alto traffic events; dest_port and action map straight from the log. Exclude your VPN gateway source IP in a search src_ip!=10.10.0.5 filter after measuring your own baseline. The Sigma timeframe (10m) and the SPL bin _time span=10m match, and both count dc(dest_ip) per source.

Corroboration note: an IDS strengthens this rule without a second Sigma pair. Suricata ET SCAN signatures (for example ET SCAN masscan or ET SCAN Nmap) name the tool directly, while this rule names the breadth. Treat both signals on the same source as one confirmed case for threat 1.

| bin _time span=5m
| stats dc(dest_ip) AS unique_dests count AS hits by _time, src_ip

Field assumptions: Palo Alto traffic events; action=deny keeps the rule cheap; adapt to zeek:conn with id.orig_h/id.resp_h if that is your flow source. The 5-minute window and the count of 100 match the Sigma condition exactly.

Escalation note: a sweep that found an open service is the highest-value case. Correlate later allow events from the same source with these denies — same fields, same 10-minute window. Escalate any source that shows sweep breadth followed by successful connections. That pairing means real exposure, so handle it as a critical case even though it shares this rule’s data.

Real-World Case Study: Mirai Botnet Recruitment (2016)

The best-documented scanning campaign in history: how a sweep of the whole internet built a DDoS army.

Dates and figures below are as reported by researchers and vendors. DDoS (Distributed Denial of Service) means many machines flood one target until real users cannot get through.

Background

Mirai was malware with one job: recruit smart devices into a rentable DDoS army. It had no exploit for the devices it took over. It swept huge IP blocks for open Telnet, tried a short list of factory passwords, and installed itself on whatever answered. Cameras, home routers, and video recorders made up most of the army. The whole build ran on one cheap trick: nobody had fixed the defaults.

Timeline (as reported)

  • August 2016Mirai appears. It sweeps the entire IPv4 space for Telnet (ports 23 and 2323). The tool carries a list of about 61 default credential pairs — factory usernames and passwords such as admin/admin.
  • 20 September 2016Record DDoS against the blog of security journalist Brian Krebs, about 620 Gbps as reported by Akamai.
  • 30 September 2016Mirai source code is released publicly; copycat variant waves multiply within weeks.
  • 21 October 2016Attack on DNS provider Dyn from roughly 100,000 infected devices. DNS (Domain Name System) is the internet’s address book. Twitter, Netflix, Reddit, CNN, Spotify, and others became unreachable for hours in parts of North America.
  • December 2016Researchers attribute the operations to three young actors; guilty pleas follow later.

Attack chain

The chain is pure reconnaissance economy. First, sweep IP blocks for open Telnet (T1595.001). Next, try the 61 default credential pairs (T1110.001 Brute Force). Then infect the device, and the device joins the botnet. The botnet was then rented out for DDoS attacks. No exploit was needed — the sweep plus factory passwords was enough to build an army of about 100,000 devices.

Detection points

ISPs and campus networks saw the Telnet sweeps in flow data: single sources walking large address ranges on port 23. Honeypots (decoy systems that record attacks) logged the full credential list as the bots tried it. IDS signatures flagged the login attempts. All three signals were visible before the big attacks — the industry just was not watching breadth at scale yet.

Containment

ISPs filtered inbound Telnet toward their customer ranges. Device owners patched firmware or reset factory credentials. Dyn absorbed the October attack using anycast capacity. The same address was announced from many data centers, so the flood spread across hundreds of sites.

Eradication

Full eradication never happened. Arrests and takedowns removed the operators and some command servers. But every unpatched device on the internet stayed recruitable. The released source code meant new variants kept appearing for years.

Recovery

Most attacked services returned the same day. Some sites needed extra hours because DNS caches had to expire. Confidence in single-provider DNS designs never fully recovered, and multi-provider DNS became the standard advice.

Impact and consequences

  • The first household proof that forgotten devices are a global risk.
  • Hours of downtime for major platforms, including Twitter, Netflix, and Reddit.
  • A lasting market for DDoS-for-hire services built on recruited devices.
  • New pressure on ISPs, whose customer devices caused outbound attack traffic.

Team response and communication

The NOC (Network Operations Center — the engineers who run a network around the clock) led the technical side. Its teams worked with upstream providers on two filters. Flowspec rules told provider routers to drop the attack traffic. Blackhole routing removed the worst destination prefixes for a short time. Dyn published short, factual status updates during the attack and a detailed report afterwards. That plain “here is what we know” style is still the model for incident communication.

Lessons learned

  • Default credentials are a scanning goldmine; remove them everywhere.
  • Block inbound management ports at the border before someone sweeps for them.
  • Breadth monitoring catches recruitment sweeps that volume dashboards miss.
  • Resilience (anycast, rate limiting) matters as much as prevention.
  • Patch the whole fleet; takedowns do not fix a single device.

Mitigation and Defense

You cannot stop someone probing you, but you can decide what answers — and make every answer boring.

Note

ATT&CK itself lists only one mitigation class for this technique: Pre-compromise (M1056). The technique happens outside your network, so preventive controls cannot stop the probing itself. The practical goal is to minimize what the outside world can learn: fewer answers, fewer services, fewer secrets in the replies.

Policy

  • Know your ranges: keep IPAM (IP address management) records current.
  • Run a sanctioned quarterly external sweep of your own address space.
  • Every public-facing exception needs an owner and an expiry date.

Identity

  • No shared default credentials anywhere in the estate.
  • MFA (multi-factor authentication) on every remote door: VPN, RDP, consoles.
  • Lock accounts that fail repeated logins from one source.

Endpoint

  • Keep router, camera, and NAS (network-attached storage) firmware updated.
  • Disable unused services on devices that face the internet.
  • Replace devices that no longer get vendor updates.

Network

  • Default-deny inbound at the edge.
  • Block management ports (22, 23, 3389, 445) from the internet.
  • Tarpit or rate-limit known scanners instead of hard-dropping them.

Cloud

  • Security groups closed by default; open ports need a ticket.
  • VPC flow logs on in every region and account.
  • Daily public-exposure report for every cloud range you own.

Logging

  • Keep deny and flow records for at least 90 days.
  • Make sure logs survive scan storms; sample if you must.
  • Send edge logs to a system the scanner cannot touch.

Monitoring

  • Alert on breadth: unique destinations per source.
  • Alert on answers from undocumented addresses.
  • Run honeypots on unused ranges; any touch is a signal.

Backup

  • Standard immutability: backups that cannot be changed.
  • Restore tests on schedule, not just in theory.
  • Sweeps precede ransomware — treat recon as a backup trigger too.

Response

  • Sweep runbook: breadth → answers → source intel → block → shrink surface.
  • Pre-agree who can block at the edge and how fast.
  • Log the ATT&CK mapping in every sweep ticket.

Home and small office

Router and network

  • Update router firmware, then check monthly.
  • Disable WAN-side management and UPnP (auto port opening).
  • Put smart-home devices on a guest network, away from laptops.

Accounts and habits

  • Change every default password to a unique one.
  • Check the router log once a month for port scans.
  • Turn off services you never use (FTP, Telnet, media servers).

Common Mistakes and Best Practices

Twelve failure patterns teams hit with range sweeps. Each row gives the symptom you will see, the root cause, the immediate fix, and the prevention that keeps it fixed.

#MistakeSymptomRoot causeFixPrevention
1IP blocklists as the only defense.The same sweep reappears within hours from a fresh address, and the queue refills with near-identical alerts.Blocking is tied to the address, not to the behavior, so source rotation defeats every block.Re-tune the existing alerts to fire on breadth and pattern, and document the campaign instead of the single source.Keep breadth alerts as the primary tripwire, tune on behavior, and automate blocking of repeat patterns.
2Only watching volume, not breadth.Dashboards stay green while a patient, low-rate sweep walks the whole range over several days.Monitoring counts bytes and packets per link, so spread-out probes never cross a volume threshold.Add unique-destinations-per-source panels and alerts to every edge dashboard this week.Build flow analytics around breadth per source, and review new sweep techniques quarterly.
3Ignoring what answered.The sweep is closed as noise, but three unknown addresses had answered and stayed exposed.The triage runbook has no step that checks answering addresses against the asset inventory.Re-open recent sweep tickets, match every answering address to an owner, and ticket the gaps.Make answer review a mandatory triage step that blocks ticket closure until it is recorded.
4No IPv6 coverage.IPv4 dashboards look clean while probes arrive over IPv6 prefixes nobody watches.Flow collection, IDS sensors, and dashboards were built for IPv4 only.Enable IPv6 flow export and IDS inspection now, then backfill dashboards for both address families.Keep a coverage matrix that lists every log source for IPv4 and IPv6 side by side.
5Deny logs dropped at scale.After a real incident, the edge denies that would prove the sweep were never stored.Log storage was cut for cost, and the high-volume deny streams were dropped first.Restore retention for edge denies, and add sampled storage plus hourly flow summaries for volume.Write a retention policy per log source, and test that evidence survives a scan storm.
6Allowing scanners without records.Every approved scan season floods the queue with false positives nobody can explain.There is no scan registry that maps approved scans to dates, ranges, and source addresses.Register all approved scanners, then match current alerts against the registry before escalation.Integrate scan approvals with change tickets, and give every allowlist entry an expiry date.
7Thresholds copied from the internet.Rules either storm the queue on day one or never fire, and analysts mute them.The numbers were copied from another network instead of measured on your own baseline.Measure unique destinations per source over 30 days, then set thresholds from that data.Re-baseline and review thresholds quarterly, and record why each value was chosen.
8Public management ports “temporarily” open.A rule opened for a migration months ago is still reachable from the internet today.Temporary exceptions have no owner and no expiry, so nobody ever closes them.Review every open exception now, close the ones with no ticket, and set expiry dates on the rest.Use auto-expiring firewall rules and a monthly port-exposure review with named owners.
9Assuming cloud is someone else’s problem.Cloud sweeps go unseen because VPC flow logs were never enabled in the accounts.Teams confuse the provider’s duties with their own under the shared-responsibility model.Turn on VPC flow logs in every region and account, and route them into the SIEM.Make cloud flow logging and public-exposure reporting a written company standard.
10No owner for the external range.Sweep findings sit in tickets for weeks because nobody owns the external address space.The range grew over years across teams, and ownership was never assigned.Name an external-exposure owner this week and route all sweep findings to them.Record the duty in a RACI chart (who is responsible, accountable, consulted, informed) and review it yearly.
11Treating researchers as attackers.The team blocks Shodan ranges and escalates measurement scans as intrusions.Source classification has no step that checks who runs the known research scanners.Add whois and GreyNoise checks to triage, then unblock the sources you classify as research.Put a source-classification step in the runbook before any block or escalation.
12Never testing your sweep detections.A log field rename silently broke the breadth rule, and nobody noticed for months.Detections are deployed once and never replayed against synthetic sweep data.Run a controlled lab sweep against a test range and confirm every rule fires as written.Schedule purple-team sweep drills, and keep detection regression tests in the pipeline.

Habits that keep the edge honest

Daily

  • Review sweep alerts from the queue.
  • Check the answers list against the asset inventory.
  • Skim top talkers for new external sources.
  • Confirm deny and flow logs are still arriving.

Weekly

  • Reconcile inventory against answered addresses.
  • Tune one detection rule with last week’s data.
  • Review the blocked-source list for stale entries.
  • Compare the scan calendar with the allowlist.

Monthly

  • Update the detection coverage matrix.
  • Run a purple-team sweep drill (attack and defense together).
  • Report sweep metrics to leadership.
  • Review thresholds against the last 90 days.
