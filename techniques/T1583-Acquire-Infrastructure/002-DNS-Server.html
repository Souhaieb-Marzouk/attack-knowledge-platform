MITRE ATT&CK · SUB-TECHNIQUE OF T1583

T1583.002 DNS Server

Some attackers do not abuse other people’s DNS (Domain Name System: the service that turns names into IP addresses). They build their own: they register domains, rent cheap servers, and run authoritative nameservers on them. With fast flux the answers change every minute, so C2 (command and control: the channel an attacker uses to send commands to malware) and malware delivery stay hard to block.

Overview

What this technique is in plain words, why attackers build their own DNS, and where it sits in the attack chain.

DNS (Domain Name System) is the service that turns names such as bank.example into IP addresses. An authoritative nameserver is the DNS server that holds the official answers for a domain. With T1583.002, the adversary sets that server up themselves instead of using a normal provider. They register a domain (see T1583.001). They rent one or more cheap virtual private servers (VPS: a rented slice of a physical server). Then they install DNS software such as BIND, NSD, or PowerDNS and answer queries on their own terms.

Owning the DNS server gives the attacker real power. They can point one name at many IP addresses and change those addresses every minute. They can give different answers to different askers, for example only answering malware that asks in a special way. They can also hide data inside DNS records. This family of tricks is called fast flux: IP flux when the A records (address records) rotate, and NS flux when the nameserver records themselves rotate.

Own server, not a hijack

The attacker does not break into someone else’s DNS. They build their own. That is cheaper, faster, and leaves no victim who could raise an alarm. It also gives full control of every answer, including the TTL (time to live: how long a DNS answer may be reused).

IP flux vs NS flux

IP flux: one domain returns many rotating A records with a low TTL, for example 60 seconds. NS flux: the nameserver hostnames for the domain rotate too, so even the “who answers for this zone” layer keeps moving. Big campaigns use both at once.

Why attackers like it

Cheap VPS nodes are easy to replace. If one IP is blocked, the next answer already waits. If one nameserver is seized, another takes over. This spreads C2 and malware delivery across many throwaway servers and gives takedown resistance.

Where it fits: T1583.002 belongs to the Resource Development tactic. The DNS infrastructure built here is used later by T1071.004 (DNS application layer protocol C2), T1568.001 (Fast Flux DNS), and delivery techniques such as T1566 (phishing) and T1189 (drive-by compromise). The page teaches you what the infrastructure looks like, what it leaves behind, and how to detect it.

Animated Simulation

Watch the full fast-flux story play out: setup, rotation, abuse, and the SOC answer.

Step 1 of 8: The attacker registers a domain and rents two cheap VPS nodes. The domain will soon answer for both servers.

SOC view

Nothing is visible inside the estate yet. The only early clue sits outside: a fresh domain registration with unknown nameservers.

Evidence left behind: registrar WHOIS record; VPS hosting order
Written version of all steps (accessibility)
  1. 1. Register and rent. The attacker registers a domain and rents two cheap VPS nodes. The domain will soon answer for both.
  2. 2. Install DNS, TTL 60. They install authoritative DNS software and set the TTL (the reuse time for DNS answers) to 60 seconds, so old answers expire fast.
  3. 3. IP flux. They rotate the A records across both nodes. One name now points at many IP addresses that change every minute (IP flux).
  4. 4. NS flux. They also rotate the nameserver records themselves, so the “who answers this zone” layer keeps moving (NS flux).
  5. 5. Victim resolves. The victim resolves the name again and again and gets a different IP each time, because the TTL is only 60 seconds.
  6. 6. Payload and C2. The payload download and the C2 (command and control) traffic go through whichever flux node answered last.
  7. 7. SOC spots flux. The SOC’s passive DNS system counts the answers: high IP cardinality, a 60-second TTL, and constant NS churn for one domain. A flux-detection alert fires.
  8. 8. Block and report. The SOC blocks the domain at the resolver and reports the nameservers to the hosting provider for abuse. They keep watching for re-delegation.

The players

  • Attacker — registers the domain, rents the nodes, and controls the DNS zone from one control host.
  • Auth DNS — the attacker-run authoritative nameserver. It answers every query for the zone with a 60-second TTL.
  • Flux node A / B — cheap rented VPS servers. Their IPs go in and out of the A and NS records while they serve payloads or C2.
  • Victim — an internal workstation that resolves the flux name and connects to whichever IP answered.
  • Resolver — your recursive DNS server. Its logs are the single best place to spot flux.
  • SOC — the security operations center, watching passive DNS and resolver telemetry.

What to watch

  • IP cardinality — how many unique IPs one parent domain returns in a short window. Normal sites stay low.
  • TTL floor — answers with a 60-second (or lower) TTL for a young domain are a classic flux marker.
  • NS churn — nameserver records that change several times a day. Normal domains change NS a few times a year.
  • NXDOMAIN bursts — many failed lookups followed by success is the signature of hard flux.
  • Egress shape — one host connecting to many short-lived IPs on the same name and port.

Red Team Perspective

Why attackers build their own DNS, how the setup works in principle, and where it usually breaks.

When and why attackers use it

Attackers rent their own DNS servers when they need the infrastructure to survive. A single web host can be blocked in minutes; a fast-flux network cannot. Running the nameserver also lets them shape the answers: the same name can return a benign page to a curious analyst and a payload to the malware that asks the right way. ATT&CK documents this control advantage explicitly for T1583.002.

The costs are low. Two or three small VPS nodes, one cheap domain, and free DNS software are enough to start. That is why ransomware crews, banking trojan operators, and information-stealer campaigns all reuse this pattern.

How the setup works (conceptual)

  1. Register one or more short, harmless-looking domains (T1583.001).
  2. Rent two or more VPS nodes from different hosters (T1583.003).
  3. Install authoritative DNS software (BIND, NSD, PowerDNS) on the nodes.
  4. Set the zone TTL to 60 seconds or lower so answers expire fast.
  5. Put several A records in the zone and rotate them with a small script.
  6. Optionally rotate the NS records through the registrar’s API (NS flux).
  7. Keep the flux controller on a separate, well-hidden “mother node”.
lab-zone: db.corp-lab.net (lab-only)
; Lab-only example — never use against systems you do not own.
; Documentation IPs (RFC 5737) and a lab-only zone name.
$TTL 60
@  IN SOA ns1.corp-lab.net. hostmaster.corp-lab.net. (
      2026010201 ; serial
      900        ; refresh
      300        ; retry
      604800     ; expire
      60 )       ; minimum / negative-caching TTL
@   IN NS  ns1.corp-lab.net.
@   IN NS  ns2.corp-lab.net.
@   IN A   203.0.113.10
@   IN A   203.0.113.11
ns1 IN A   203.0.113.10
ns2 IN A   203.0.113.11

This zone shows the shape of a flux zone: a low TTL on every record, several A answers for one name, and nameservers that resolve to the same rotating hosts. In a real campaign the attacker adds automation that rewrites these records every few minutes.

Prerequisites

  • A registered domain with a registrar that allows fast NS changes (T1583.001).
  • Two or more rented servers, ideally spread over hosters and countries (T1583.003).
  • DNS software and a small rotation script; no special hardware is needed.
  • Patience to warm the domain so it does not look freshly created (domain aging).

Variations you will meet

IP flux (soft flux)

A records rotate across rented nodes with a 60-second TTL. The client never notices; the SOC sees one name with dozens of answers. This is the delivery workhorse.

NS flux (hard flux)

The NS records of the zone rotate too, so the zone itself jumps between nameservers. Takedowns must chase the delegation, not just the IPs. Seizing one node is not enough.

TXT-record C2

The attacker hides commands in TXT record answers, as reported for the HEXANE group’s custom DNS servers. Traffic looks like normal lookups and sails past many proxies.

Common attacker mistakes

  • The rotation is too regular. Passive DNS still shows one name with extreme IP cardinality — the pattern does not hide from statistics.
  • They reuse the same bulletproof nameserver across campaigns, which links the campaigns together.
  • They forget the TTL on the NS records, so the old delegation stays cached and the flux lags behind.
  • They keep the registrar account weak after abuse reports, which is how seizures succeed.
Warning

Lab only. Everything on this page is for defense and education. Stand up flux-like DNS only in a lab zone you own and only with documentation IPs. Running DNS infrastructure to attack, scan, or deceive systems you do not own is a crime in most countries, and hostile traffic from rented nodes is traced back to the paying customer quickly.

Blue Team Perspective

What fast-flux DNS looks like from inside your network, and where to look first.

You will almost never see the attacker’s servers directly. They live outside your estate. What you see is your own resolver’s view of the world. It shows the names your users ask for and the answers that came back. It also shows how long those answers stay valid and where your endpoints connect afterwards. That view is enough. Fast flux cannot hide its defining behavior — one name, many answers, short TTL, moving nameservers.

Artifacts a flux campaign leaves on your side

  • Passive DNS history for the domain: dozens of unique A answers with a 60-second TTL.
  • NS change history: the nameserver set changes several times within a day or week.
  • Resolver logs: the same parent name answered by different IPs for the same client within minutes.
  • Proxy and firewall logs: one internal host opening short connections to many unrelated IP ranges on one name.
  • NXDOMAIN bursts followed by success for the same parent name (hard flux settling).
  • A young domain (days or weeks old) doing all of the above.

Where to look

  • Resolver query logs — Unbound, BIND, InfoBlox, Windows DNS, or cloud resolver logs shipped to the SIEM.
  • Zeek DNS logs — dns.log with query, answers, and TTL fields.
  • Endpoint DNS events — Sysmon EventID 22 (DNS query) shows which process asked.
  • Passive DNS — vendor console or feed for A/NS history and first-seen dates.
  • Threat-intel feeds — blocklist hits for the domain or its nameservers.
  • Egress flow records — which internal hosts talked to the answered IPs.

Why it matters

DNS is the last common hop before C2. Almost every malware family must resolve a name before it can fetch a payload or beacon out. A block at the resolver costs nothing to deploy, works for every device that uses the resolver, and cannot be uninstalled by the malware. That is why flux detection belongs at the resolver, not only in endpoint tools.

It also matters for scope: one flux domain often serves a whole campaign, so a single well-documented block can protect thousands of hosts at once.

Quick triage flow

  1. Pull the passive DNS record for the suspicious domain: first seen, unique IPs, NS history.
  2. Count the answers: unique IPs in the last 5 minutes, lowest TTL observed.
  3. Check the nameservers: are they young, shared with many other zones, or known bulletproof hosts?
  4. Find your clients: which internal hosts queried the name, which process asked, and how often.
  5. Follow the answers: did anyone connect to the returned IPs? Collect the flow records as evidence.
  6. Block and report: add the domain (not just the IPs) to the resolver RPZ, then report the nameservers to the hoster and the blocklist feeds.
Danger

Do not block flux IPs one by one. The attacker rotates answers faster than you can paste them into a blocklist, and each block entry ages out with the TTL. Block the domain at the resolver, and only use IP blocks for immediate containment of an active session.

Good practice

Force every endpoint to use your internal resolvers and block direct outbound DNS (TCP/UDP 53) to the internet. Without this one network control, malware can pick its own nameserver and your resolver logs — your best flux sensor — stay empty.

5.2 Threat Intelligence

Threat intelligence for T1583.002 is mostly about history. Passive DNS collects DNS answers at many observation points and stores them as a time series. It turns one suspicious answer into a full story: when the domain appeared, how many IPs it used, and how fast they rotated. It also dates how often the nameservers changed. Build your intel workflow around that story.

Passive DNS providers

Farsight DNSDB and RiskIQ PassiveTotal (now Microsoft Defender Threat Intelligence) store years of A and NS answers. Use them to measure cardinality, TTL, and NS churn over time, and to date a domain’s first malicious use.

Blocklist trackers

The abuse.ch URLhaus and ThreatFox feeds, Spamhaus DBL, and SURBL list flux domains hours after they appear. Consume them at the resolver as an RPZ (response policy zone: a feed-driven blocklist) and watch the hit counts.

Sample repositories

MalwareBazaar ties malware samples to the C2 domains they used. When you find new flux nameservers, report them so the feeds and the research community benefit.

Research and vendor blogs

Academic fast-flux studies (for example the long-running measurements by Holz and colleagues) and vendor posts on cases such as Sea Turtle or the Lyceum DNS backdoor describe patterns worth copying into rules.

ISAC and peer sharing

Sector ISACs exchange sinkhole lists and re-delegation warnings. Contribute your own blocked domains — sharing cuts the community’s response time sharply.

Internal telemetry

Your resolver logs, NXDOMAIN statistics, and your own passive DNS view are the freshest sources you own. They see the campaign before any vendor does.

Note

Known infrastructure patterns. The Avalanche fast-flux platform carried dozens of malware families until its takedown in November 2016 (see section 6). Long-running fast-flux botnets are built from infected home devices and routers. Bulletproof NS providers — hosting firms that ignore abuse reports — share one nameserver across many low-reputation zones, which is itself a detection signal.

Collect, analyze, apply

  1. Collect: subscribe to at least one passive DNS source, two blocklist feeds, and your own resolver logs. Keep a sinkholed-domains watchlist.
  2. Analyze: for every candidate domain, measure IP cardinality, TTL floor, NS churn, and domain age. Compare against the CDN allowlist before you call it flux.
  3. Apply: push confirmed domains to the resolver RPZ, name the nameservers in abuse reports, and feed your detections back into the watchlist.

log: zeek dns.log (JSON)

5.5 Sigma Rules and Splunk SPL

One Sigma rule and one matching SPL query for each of the top six threats (T1–T6). All rules assume Zeek-style DNS logs; adjust field names if your pipeline renames them.

T1 — IP-flux malware delivery domain

Fires when one parent domain answers with extreme IP cardinality across the estate within 5 minutes. This is the primary flux alarm.

sigma: dns_ip_flux_cardinality.yml
title: Estate-Wide IP Flux on One Domain Within 5 Minutes
id: a3f8c2d1-7b4e-4c9a-9f2e-6d5b8a1c4e70
status: stable
description: >
  One parent domain answers with more than 20 unique A-record IPs across the
  estate within 5 minutes. Fast-flux operators rotate answers like this
  (MITRE ATT&CK T1583.002) so that IP blocks expire immediately. Check the
  passive DNS history and the domain age before you judge the alert.
references:
  - https://attack.mitre.org/techniques/T1583/002/
  - https://en.wikipedia.org/wiki/Fast_flux
author: Detection Engineering Team
date: 2025-11-18
logsource:
  category: network
  product: zeek
  service: dns
detection:
  selection:
    qtype_name: 'A'
  filter_internal:
    query|endswith:
      - '.corp.local'
      - '.internal'
  condition: selection and not filter_internal | count(distinct answers) by query > 20
  timeframe: 5m
fields:
  - id.orig_h
  - query
  - answers
  - TTLs
falsepositives:
  - Large CDN or cloud frontends that answer per region for big SaaS names
  - Round-robin load balancers on popular internal-facing services
level: high
tags:
  - attack.resource_development
  - attack.t1583
  - attack.t1583.002
  - attack.t1568.004
spl: ip_flux_cardinality.spl
index=network sourcetype=zeek:dns.log qtype_name="A" NOT query=*.corp.local
| eval min_ttl=mvmin(TTLs)
| bin _time span=5m
| stats dc(answers) AS unique_ips, values(answers) AS sample_ips,
        dc('id.orig_h') AS clients, min(min_ttl) AS lowest_ttl
        BY _time query
| where unique_ips > 20
| sort - unique_ips

Field assumptions: Zeek dns.log at index=network, with the fields query, answers, TTLs, and id.orig_h as parsed by your DNS sourcetype.

  • Mapping: Resource Development / T1583.002, with operational overlap into T1568.001.
  • False positives: CDNs and big mail platforms; require the CDN allowlist before judging.
  • Tuning: raise the threshold for your busiest sites; add domain-age enrichment so 30-year-old names rank lower than 3-day-old names.

T2 — NS-flux C2 domain

Fires when the nameserver answer set of one external domain keeps changing. Normal domains change NS a few times a year, not five times a day.

title: Nameserver Record Churn on One External Domain (NS Flux)
id: b21e9f47-5c3a-4d86-8a4b-1e9f7c2d5a33

Fires on TXT bursts or very long subdomain labels to one external name. Marked tunneling-adjacent: legitimate services use TXT too, so keep the allowlist close.

status: test
description: >
  Detects bursts of TXT queries to one external domain, or queries whose first
  label is very long, which is how DNS tunneling (data hidden inside DNS

T6 — Low-TTL rotation to defeat IP blocks

Fires when the same client receives different A answers for one external name within 5 minutes while TTLs stay low. This is the answer-flip behavior that outruns IP blocks.

sigma: dns_answer_flip_low_ttl.yml
title: DNS Answer Changes for the Same Client Before TTL Expiry
id: f7a04c92-3b6e-4d9a-8c57-9c4e5d6f0b83
status: test
description: >
  The same client gets different A answers for one external name within 5
  minutes while the advertised TTL is still valid. This low-TTL rotation
  (MITRE ATT&CK T1583.002 fast flux) dodges IP blocklists. Validate against
  passive DNS, because some multi-CDN answers also rotate between regions.
references:
  - https://attack.mitre.org/techniques/T1583/002/
  - https://attack.mitre.org/techniques/T1568/001/
author: Detection Engineering Team
date: 2026-01-08
logsource:
  category: network
  product: zeek
  service: dns
detection:
  selection:
    qtype_name: 'A'
  filter_internal:
    query|endswith:
      - '.corp.local'
      - '.internal'
  condition: selection and not filter_internal | count(distinct answers) by id.orig_h,query > 3
  timeframe: 5m
fields:
  - id.orig_h
  - query
  - answers
  - TTLs
falsepositives:
  - Multi-CDN names that answer per region for the same client
  - Mobile clients roaming between networks during the window
level: medium
tags:
  - attack.resource_development
  - attack.t1583
  - attack.t1583.002
  - attack.t1568.004
spl: answer_flip_low_ttl.spl
index=network sourcetype=zeek:dns.log qtype_name="A" NOT query=*.corp.local
| streamstats current=f window=2 values(answers) AS prev_answers BY 'id.orig_h' query
| where answers != prev_answers
| eval lowest_ttl=mvmin(TTLs)
| stats count AS answer_flips, values(prev_answers) AS earlier_answers,
        values(answers) AS later_answers, min(lowest_ttl) AS min_ttl
        BY query 'id.orig_h'
| where answer_flips >= 2 AND min_ttl <= 300
| sort - answer_flips

Field assumptions: Zeek dns.log; the comparison uses successive answers per client and query, and the min_ttl <= 300 filter approximates “inside the TTL window”. If your pipeline stores only one TTL per record, drop the multivalue helpers.

  • Mapping: Resource Development / T1583.002; the evasion goal is T1568.001 (Fast Flux DNS).
  • False positives: CDN rotation and roaming clients; enrich with ASN before alerting.
  • Tuning: raise the flip threshold for busy engineering networks; pair with the CDN allowlist from Rule 1.

Real-World Case Study

Avalanche (2016): the largest fast-flux takedown of its time, and the reason passive DNS matters.

For roughly seven years, the criminal platform known as Avalanche sold fast-flux hosting as a service. It ran its own DNS infrastructure: thousands of domains that rotated answers across rented and infected nodes, plus bulletproof nameservers that ignored abuse reports. Reporting by Europol and partners described a network that carried more than 30 malware families and sent millions of malware-laced emails per day. Estimates put the fronted domains in the hundreds of thousands, though reported figures differ by source.

In late November 2016, after about 45 days of preparation, law enforcement from five countries seized the platform’s command servers and sinkholed its C2 traffic. The action was coordinated with Europol, Eurojust, and partners including the German BKA and US agencies. It also blocked or sinkholed more than 800,000 associated domains (reported). Researchers had tracked the network for years with passive DNS measurements, which made the target list possible.

  • 2009–2016 · Context

    A fast-flux platform as a service

    Avalanche grows into a shared criminal cloud: bulletproof nameservers, rotating A records, and rented nodes. Any crew can rent delivery and C2 capacity for its malware family of choice.

  • 2010–2016 · Attack chain

    Delivery and C2 on rotating answers

    Spam links and drive-by downloads point victims at flux domains. Payloads and C2 (command and control) come from whichever node answers, so blocking single IPs does almost nothing.

  • Years before 2016 · Detection point

    Researchers measure the flux

    Academic and vendor teams use passive DNS to map one domain after another: extreme IP cardinality, low TTLs, shared nameservers. The measurements connect the dots into a target list for law enforcement.

  • T−45 days · Preparation

    Five countries coordinate

    Investigators, prosecutors, CERTs, and financial-sector partners plan the action: server seizures, sinkhole takeover, victim notification, and domain blocking move in one coordinated window.

  • 29–30 November 2016 · Containment

    Servers seized, C2 sinkholed

    The coordinated action takes control of command servers and redirects C2 traffic to sinkholes. Infected systems still call out, but now they meet researchers instead of criminals.

  • December 2016 · Eradication

    Domains blocked at scale

    Registrars, registries, and filter vendors block or sinkhole hundreds of thousands of associated domains (reported figures exceed 800,000). Financial institutions are told which customers connected to the C2.

  • Dec 2016–2017 · Recovery and impact

    Cleanup and rebuilds

    Cleanup guidance goes out through banks and CERTs worldwide. Some affected crews rebuild on new infrastructure — and a share of blocked domains re-delegates to new nameservers within months.

  • 2016–2017 · Team response and communication

    Public, coordinated messaging

    Europol, national police, and the US Department of Justice publish jointly. That helps banks, hosters, and registrars act on the same indicators at the same time.

  • Ongoing · Lessons

    What the operation taught

    The takedown validated years of quiet measurement work — and showed that seized domains tend to come back. Monitoring never stops.

Lessons

Flux detection belongs at the resolver. The measurements that enabled Avalanche’s takedown came from DNS observations, not from endpoints. International cooperation works — five countries moved in one window. Domains come back — keep watching re-delegations long after the headlines fade.

Mitigation and Defense

ATT&CK rates this technique M1056 “Pre-compromise”: you cannot prevent an attacker renting servers. You can remove the advantage the infrastructure gives them.

The mitigation goal is simple: every host must use resolvers you control, those resolvers must log, and the logs must feed analytics that know what flux looks like. The cards below group the controls by area.

Policy

Write a DNS standard: approved resolvers, blocklist feeds, NS-change monitoring for your own domains, and registrar lock plus registry lock for company-owned domains. Name the abuse contact for your own IP space so others can report you fast.

Identity

Treat registrar and DNS-provider accounts as privileged identity: hardware second factors, separate accounts per domain, and alerts on NS record changes or transfer requests. Stolen registrar access enables re-delegation attacks against your own names.

Endpoint

Enable Sysmon EventID 22 (DNS query) and ship it centrally. EDR rules should flag processes that resolve many different external names in bursts — that is how tunneling looks from the client side.

Network

Force all DNS through internal resolvers and block direct outbound TCP/UDP 53 to the internet. Run RPZ (response policy zone) blocklists at the resolvers. Never expose an open resolver to the internet.

Cloud

Turn on query logging for managed DNS (for example Route 53 Resolver query logging or the equivalent in your cloud) and send it to the SIEM. Cloud VPCs without DNS logs are the classic blind spot for flux detection.

Logging

Resolver query logs, Zeek dns.log, and a passive DNS subscription form the minimum sensor set. Retain them for at least a year — flux campaigns are found by history, not by single events.

Monitoring

Run the flux analytics from section 5.5: IP cardinality, TTL floors, NS churn, NXDOMAIN baselines, and re-delegation watchlists. Alert on NS changes for your own domains within minutes, not weeks.

Backup

Keep snapshots of your own zone files, registrar configurations, and passive DNS exports. They are your evidence set when you must prove what a lookalike or re-delegated domain changed.

Response

Pre-stage abuse-report contacts for the big hosters and registrars, a takedown playbook, and RPZ change procedures. Join an ISAC so inbound warnings about shared flux networks reach you in hours.

Warning

Test the DNS lock-down before you enforce it. Hard-blocking outbound port 53 breaks devices with hardcoded resolvers, printers, and some cloud agents. Run it in monitor mode for two weeks, keep an allowlist for the stragglers, then enforce.

Home and small office

Point your router at a filtering resolver such as Quad9 (9.9.9.9) or Cloudflare malware-blocking (1.1.1.2) — both refuse answers from known malware domains. Keep router firmware current, change the router admin password from the default, and disable remote administration from the internet. Home routers are the favorite recruits for fast-flux node pools, so a patched router protects others too.
