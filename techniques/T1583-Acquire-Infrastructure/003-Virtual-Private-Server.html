MITRE ATT&CK · SUB-TECHNIQUE OF T1583

T1583.003 Virtual Private Server

Attackers do not need to hack a server to get one. They rent it. A virtual private server (VPS: a slice of a physical machine sold by a cloud provider as if it were a full computer) costs a few dollars. It boots in seconds and can be deleted just as fast. Paid with cryptocurrency, it gives the attacker a disposable base for C2 (command and control: the channel an attacker uses to send commands to malware). The same box can host phishing pages, scanners, and data hops. To your defenses, it looks like ordinary cloud traffic.

Overview

What a rented virtual private server is, why it is the workhorse of modern attack infrastructure, and what this guide teaches you to see.

A virtual private server (VPS) is a slice of one physical server that a provider sells as if it were a complete machine. You get your own IP address, disk, and root access, but you share the hardware with other customers. Legitimate companies rent VPS machines every day to host websites, run build agents, and test software. That is exactly why attackers love them: a malicious VPS is indistinguishable in paperwork from a developer’s test box.

MITRE ATT&CK describes T1583.003 in one short paragraph. It says: adversaries rent virtual private servers that can be used during targeting. Cloud providers sell virtual machines as a service. A VPS makes it hard to physically tie operations back to the attacker. It is also fast to provision, modify, and shut down. Finally, a VPS benefits from the trust attached to reputable cloud networks. Some attackers also pick providers that ask for minimal registration information, so the account is nearly anonymous. This page turns that paragraph into working detection knowledge.

Cheap and disposable

An hourly VPS costs a few cents. Attackers can burn an IP in minutes, drop it, and deploy the next one. Blocking one IP address buys you almost nothing.

Fast to replace

A fresh server boots in under a minute from a saved template with C2 tooling already installed. Rebuilding after a takedown takes minutes, not days.

Trusted network, hostile host

Commercial provider networks (for example DigitalOcean AS14061 or OVH AS16276) also carry real business traffic. That shared reputation is the attacker’s camouflage and your tuning problem.

Where it fits in the attack chain

T1583.003 is a Resource Development technique: it happens before the intrusion, on the attacker’s side. The rented server then shows up inside many other ATT&CK tactics. That is why you see it in so many incidents.

Note

Keep the parent and child roles straight: T1583.003 is about acquiring the server (the account, the payment, the deployment). Using that server for phishing delivery is T1584 (Compromise Infrastructure) territory only when the infrastructure was hacked — rented infrastructure used for C2 is T1583.003 plus the command-and-control technique. The account creation and crypto payment are attacker-side actions; you will rarely see them in your logs, which is why detection leans on external intelligence.

Animated Simulation

Watch a rented server go from crypto-paid account to blocked-and-reported C2 host in eight steps.

Step 1 of 8: The attacker opens an account at a VPS provider and pays with cryptocurrency, so the account has almost no real identity behind it.

SOC view

Nothing in your estate is affected yet. The billing, the payment, and the deployment all happen on the provider side, which is why acquisition is invisible to internal logs.

Evidence left behind: provider account with crypto payment; cloud console audit trail (attacker-side only)
Written version of all steps (accessibility)
  1. 1. Account with crypto. The attacker registers at a VPS provider and pays with cryptocurrency. The account is real, active, and nearly anonymous.
  2. 2. Deploy and harden. The attacker deploys an Ubuntu virtual machine from a template and hardens it: SSH key-only login, a firewall that allows only the C2 port, and the provider’s monitoring disabled where possible.
  3. 3. Install tooling. The attacker installs C2 or redirector tooling (for example a reverse-proxy front end and a teamserver) and points a recently registered domain at the new IP.
  4. 4. Scan the edge. The VPS probes the target perimeter: port scans and service fingerprinting against the victim’s public IP ranges. Every denied packet lands in the victim’s firewall logs.
  5. 5. Lure and beacon. The attacker sends a phishing lure. The victim clicks, the implant executes, and it beacons out to the VPS on a steady schedule.
  6. 6. Commands flow. The attacker issues commands through the VPS. Traffic is now two-way between the implant and the rented server.
  7. 7. SOC spots the beacon. The SOC sees a client making evenly spaced connections to an external IP whose ASN is on the VPS intel list. Beacon periodicity plus VPS ASN raises the alert.
  8. 8. Block, hunt, report. The SOC blocks the IP, hunts for other hosts talking to the same range, and files an abuse report with the provider so the machine gets removed.

The players

  • Attacker — pays for and controls the rented server; never touches your network directly, everything goes through the VPS.
  • Cloud provider — sells the VPS. It holds the real identity trail: payment method, signup IP, console logs. Your best lever is its abuse team.
  • VPS — the rented virtual machine. Cheap, replaceable, and sitting on a trusted provider network like AS14061 or AS16276.
  • Victim — your estate: the workstation that beacons out and the perimeter that gets scanned.
  • SOC — the security operations center. It connects three clues: periodicity, external ASN, and reputation data.

What to watch

  • Periodicity — beaconing means evenly spaced connections (for example every 60 seconds, plus or minus a little). One connection proves nothing; rhythm does.
  • ASN enrichment — a plain IP tells you little; the network it belongs to (DigitalOcean, OVH, Hetzner, Vultr) tells you where to look next.
  • Young provider accounts — on the attacker side this is invisible to you; on your side the counterpart is a first-seen external IP with no history.
  • Scan patterns — many denied packets from one source across many ports is recon, and it often arrives before any lure.
  • Abuse feedback — a reply from a provider abuse team confirms the host was malicious. Feed it back into your blocklists.

Red Team Perspective

How a professional adversary (and, in a controlled lab, an authorized red team) builds and operates rented infrastructure — written so defenders understand exactly what to look for.

Danger

Ethical use only. Everything in this section describes either public incident reporting or lab-only setups on machines you own. Renting a server to attack systems you do not own is a crime in almost every jurisdiction, and provider abuse teams cooperate with law enforcement. Never use these examples against real targets.

When and why attackers choose a rented VPS

Renting beats hacking. Taking over someone else’s server means keeping the foothold alive, hiding from the real owner, and leaving traces on a victim. A rented VPS gives full root control from minute one, an hourly bill instead of a traceable identity, and an IP on a clean provider network that no blocklist has ever seen. ATT&CK’s own procedure examples name many groups for this technique. APT38 used VPS providers, including Hostwinds, for C2 hosting. APT42 used anonymized infrastructure and VPSs to reach victim environments. The ArcaneDoor campaign ran dedicated, adversary-controlled VPSs for command and control. In the 2021 HAFNIUM Exchange campaign, exploit traffic came from US-based rented VPSs. Attackers pay with cryptocurrency or stolen prepaid cards because it breaks the link between the server and a person.

How it is performed (conceptual)

The operational pattern appears in nearly every intrusion report that mentions rented infrastructure. It has five phases.

  1. Acquire — create an account with a provider that accepts crypto or asks few questions; fund it; keep below fraud-detection thresholds by mimicking normal usage.
  2. Deploy — boot a Linux image from a saved template; the template already contains the tooling, so deployment is one API call.
  3. Harden — attackers protect their own servers the way admins do: SSH key-only login, default-deny firewall, nothing that reveals the server’s purpose in banner strings.
  4. Weaponize — install the C2 listener, redirector, or phishing site; point a young domain at the IP; obtain a TLS certificate so the channel looks like any HTTPS site.
  5. Rotate — burn the server when it is blocked or reported; rebuild from template on a new IP in minutes. Infra structure as code, in the worst sense.

Lab-only example: a test beacon to validate your own detection

The snippet below does not attack anything. It makes a machine you own contact a second machine you own at a fixed 60-second rhythm, which produces exactly the periodicity pattern that Sigma rules 1 and 6 in Section 5.5 should catch. Run it in an isolated lab, watch your SIEM, then tune the thresholds before a real incident arrives.

bash: lab_beacon_test.sh — lab-only, two hosts you own
#!/bin/bash
# Lab-only example - never use against systems you do not own.
# Simulates beacon periodicity so you can verify detection rules.
VPS_IP="203.0.113.50"        # your own lab "VPS" box
while true; do
  curl -s -o /dev/null --max-time 5 "http://${VPS_IP}/pixel.gif?c=$(date +%s)"
  sleep 60                    # fixed 60-second rhythm = beacon signature
done

Lab-only example: the same hardening a real operator applies

Attackers harden rented boxes exactly like careful admins, which is why the box itself reveals nothing. Knowing this stops you from hoping for lazy-attacker tells: assume the server is well configured and hunt the traffic instead.

bash: hardened lab host baseline (attacker-style)
# Lab-only example - apply to a host you own, for detection testing.
ufw default deny incoming && ufw default allow outgoing
ufw allow 443/tcp                      # only the C2/redirector port
sed -i 's/#PasswordAuthentication yes/PasswordAuthentication no/' /etc/ssh/sshd_config
systemctl restart ssh                  # key-only SSH, like a real operator

Where it applies and what it needs

Typical roles of the rented box

  • C2 server — the implant’s home base (most common).
  • Redirector / proxy — a front that forwards to a deeper server, so the deep one never exposes its IP.
  • Phishing host — fake login pages with TLS, live for a few days.
  • Scanner — source of perimeter scans before the intrusion.
  • Staging & data-theft hop — first stop for payloads in, stolen data out.

Prerequisites from the attacker’s view

  • A payment rail the provider accepts: crypto, prepaid card, or a stolen identity.
  • A saved template or script so the box is ready in minutes.
  • A domain (see T1583.001) and TLS for cover.
  • OpSec discipline: never log into the VPS from a personal IP.

Three variations you will meet in reports

VariationWhat changesReported byDetection angle
Mainstream-provider VPSBig networks (DigitalOcean, OVH, Hetzner, Vultr, AWS); high reputation, huge legitimate traffic to hide inMost vendor reports, incl. HAFNIUM 2021Periodicity + reputation feeds; expect false positives from real SaaS
Bulletproof hosterLow-registration providers that ignore abuse reports and host spam/malware openlyabuse.ch, Spamhaus, sinkhole operatorsThe ASN itself is the signal; reputation lists do the work
Trial and stolen-card abuseFree-trial accounts, throwaway cards, reseller abuse; short-lived boxesProvider trust & safety teamsShort lifetimes: an IP that appears, acts, and vanishes in days

Mistakes attackers make (and what they teach you)

  • Reusing one VPS IP across campaigns and victims — one abuse report then lights up every campaign that touched it.
  • Skipping TLS on the phishing page — plain-HTTP fake logins stand out in proxy logs.
  • Beaconing on a perfect fixed interval with no jitter — the cleanest possible input for periodicity analytics.
  • Scanning from the same box that later hosts C2 — joining your firewall-deny and EDR-connection data links the two phases.
  • Logging into the C2 box from an IP in a residential range of their home country — providers see this even if you cannot.

Each mistake is a detection gift: fixed rhythm, reused IP, shared infrastructure between phases. Section 5 turns all five into working rules.

Blue Team Perspective

You will never see the rental agreement — you will see the traffic, the logs, and the traces the rented box leaves in and around your estate.

The blue-team reality of T1583.003 is asymmetry: the acquisition happens entirely outside your visibility, but everything the server does afterwards crosses a boundary you can log. A VPS used for C2 must receive outbound beaconing from your hosts. A VPS used for scanning must send packets at your perimeter. A VPS used for phishing must receive clicks through mail and proxy paths. Each role produces a different artifact family, and all three benefit from the same enrichment: knowing that an IP belongs to a hosting ASN instead of a consumer ISP or a business SaaS.

Artifacts a rented server leaves in your estate

Network artifacts

  • Outbound connections to a first-seen IP in a hosting ASN, repeating on a schedule.
  • Inbound denied packets from one source across many ports (scan).
  • TLS sessions to a young certificate on a VPS IP.

Endpoint artifacts

  • Sysmon EventID 3 network events from a server process (not a browser) to a VPS IP.
  • A process that wakes every 30–120 seconds with tiny uploads.
  • EDR telemetry showing the same destination across several hosts.

Email & identity artifacts

  • Inbound mail whose sending IP resolves to a VPS ASN with failed SPF.
  • Authentication failures against VPN or SSO from provider ranges (stuffing).
  • Password-spray patterns: one VPS IP, many usernames.

Note

ASN enrichment is the single most useful change you can make. Most SIEM pipelines can add the originating organization name for every public IP at ingest or search time (MaxMind GeoLite2 ASN, Team Cymru, or a commercial feed). Once asn_org exists as a field, every query in Section 5.5 becomes a one-line join instead of a research project.

Why it matters and how it fits the chain

Detecting the rented server early buys time back. A scan from a VPS today is often a C2 beacon next week from a different box in the same ASN. Because providers rotate IPs, the durable unit of detection is not the address but the behavior plus network: periodic outbound connections to hosting ranges, joined with reputation. Teams that only block IPs chase the attacker’s tail; teams that detect the pattern catch the replacement box too.

Triage flow when a VPS-ASN alert fires

  1. Confirm the enrichment. Is the destination really in a hosting ASN, and is it on your allowlist (SaaS vendors also live there)?
  2. Measure the rhythm. Pull 24 hours of connections to that IP; compute the interval spread. Regular intervals plus small payloads suggest beaconing.
  3. Identify the process. Join with EDR data: which process owns the connection? A browser is noise; a server binary is signal.
  4. Check reputation. Look the IP up in abuse.ch Feodo/SSL Blacklist, Spamhaus, GreyNoise, and urlscan.io history.
  5. Scope. Search the whole estate for the same destination IP and for sibling IPs in the same /24; find every affected host.
  6. Contain. Block the IP at the egress firewall, isolate endpoints with active C2, and force a credential reset if identity systems were touched.
  7. Report. File an abuse complaint with the provider (include timestamps, IPs, ports, and payloads). This is what actually kills the box.
  8. Feed back. Add the IP and ASN context to your intel store and re-check the rule that fired — should it have fired earlier?

Steps 2–4 are the difference between an IP block and an incident: rhythm plus process plus reputation turns a random cloud IP into an attribution-ready C2 host.

5.2 Threat Intelligence

Because the acquisition happens outside your logs, external intelligence does the heavy lifting for this technique. Build a small, maintained stack rather than a big, stale one:

IP reputation feeds

abuse.ch Feodo Tracker and SSL Blacklist list C2 hosts, many of them on VPS ranges. Spamhaus marks spam and bulletproof networks with SBL/XBL listings. Pull these daily into a lookup table your searches join against.

ASN intelligence

Maintain a curated list of hosting networks: DigitalOcean AS14061, OVH AS16276, Hetzner AS24940, Linode/Akamai AS63949, Vultr AS20473, AWS AS16509, plus known bulletproof ASNs. Tag each with abuse contact and risk tier — mainstream ranges need allowlists, bulletproof ranges do not.

Scanning context

GreyNoise tells you whether an inbound scan from a VPS IP is mass internet noise or a targeted probe. The urlscan.io service shows what a VPS-hosted domain serves before you click anything, such as a fake login page or an exploit kit.

Vendor reporting & ISACs

Vendor blogs name the VPS ranges actors use. Examples: Microsoft’s HAFNIUM reporting, Cisco’s ArcaneDoor research, and Microsoft’s Moonstone Sleet write-up. Sector ISACs share blocklists after incidents. Subscribe to the two that match your industry.

Collect → analyze → apply

  1. Collect: pull reputation feeds and ASN data on a schedule; keep first-seen and source tags so you can expire entries safely.
  2. Analyze: join your telemetry against the feeds nightly; note which internal hosts touched flagged IPs and which VPS ASNs appear most in your deny logs.
  3. Apply: feed high-confidence matches into blocking and alerting (rules below), medium-confidence matches into hunting queries, and low-confidence items into a watchlist only.

5.5 Sigma Rules and Splunk SPL

One complete Sigma rule and one matching Splunk SPL query for each of the top six threats (T1–T6 in Section 5.3). Every rule assumes your pipeline adds ASN enrichment (is_vps_asn or an asn_org field) and that you keep a small SaaS allowlist lookup. Adapt field names to your schema before deploying, and validate each rule in a lab as Section 7 recommends.

T1 — Outbound beaconing to a VPS ASN (Zeek conn)

Fires when one internal host makes more than 25 short connections to a single hosting-ASN IP inside 30 minutes. This is the primary C2 alarm for rented infrastructure.

sigma: vps_beacon_zeek_conn.yml
title: Outbound Beaconing to a Virtual Private Server ASN
id: fbeec293-a01f-46c0-9470-a1c680858ab6
status: stable
description: >
  Detects an internal host making more than 25 outbound connections to one
  external IP in a hosting ASN within 30 minutes. Rented VPS machines used
  for C2 (MITRE ATT&CK T1583.003) show exactly this periodic rhythm with
  small, near-constant payloads. Check the SaaS allowlist before escalating.
references:
  - https://attack.mitre.org/techniques/T1583/003/
  - https://feodotracker.abuse.ch/
author: Detection Engineering Team
date: 2025-11-20
logsource:
  category: network
  product: zeek
  service: conn
detection:
  selection:
    is_vps_asn: true
    network_transport: tcp
  filter_internal_dst:
    id.resp_h|startswith:
      - '10.'
      - '192.168.'
      - '172.16.'
      - '127.'
  filter_allowlisted:
    resp_asn_allowlisted: true
  condition: selection and not 1 of filter_* | count() by id.orig_h, id.resp_h > 25
  timeframe: 30m
fields:
  - id.orig_h
  - id.resp_h
  - asn_org
  - orig_bytes
  - resp_bytes
falsepositives:
  - Backup, sync, or MDM agents on the allowlist that sit inside a hosting ASN
  - Long-lived tunnels or proxies to approved SaaS in the same networks
level: critical
tags:
  - attack.resource_development
  - attack.t1583
  - attack.t1583.003
  - attack.command_and_control
  - attack.t1071
spl: vps_beacon_zeek_conn.spl
index=network sourcetype=zeek:conn is_vps_asn=true
| lookup saas_allowlist.csv id.resp_h OUTPUT allowlisted
| where NOT allowlisted="true" AND NOT (cidrmatch("10.0.0.0/8", id.resp_h) OR cidrmatch("192.168.0.0/16", id.resp_h) OR cidrmatch("172.16.0.0/12", id.resp_h) OR cidrmatch("127.0.0.0/8", id.resp_h))
| bin _time span=30m
| stats count AS conns avg(orig_bytes) AS avg_out by _time id.orig_h id.resp_h asn_org
| where conns > 25 AND avg_out < 1000
| eval note="periodic small-payload pattern to hosting ASN = beacon candidate"
| sort - conns

Field assumptions: Zeek conn logs at index=network sourcetype=zeek:conn; is_vps_asn is added by an ingest-time enrichment lookup (MaxMind GeoLite2 ASN or Team Cymru) against a maintained vps_asn table; saas_allowlist.csv maps destination IPs you have approved.

  • Mapping: tactic Resource Development (T1583.003) enabling Command and Control via T1071.
  • False positives: agent traffic on the allowlist; developer tooling talking to CI hosts in the same ASNs.
  • Tuning: raise the count or window for backup servers; require avg_out < 1000 bytes only for user endpoints.

Fires when a client retrieves an executable file type from a hosting-ASN host. Staging servers live for days, so this rule keys on the network role, not a fixed IP list.

title: Executable Download from VPS-Hosted Server

Real-World Case Study

HAFNIUM against Microsoft Exchange, March 2021: the best-documented example of rented VPS infrastructure powering a global exploitation campaign.

In early March 2021, Microsoft’s threat intelligence team (MSTIC) reported a group it tracks as HAFNIUM. Microsoft assessed that the group operates out of China on behalf of the state. It was actively exploiting on-premises Microsoft Exchange Server. The critical detail for this page: the exploit traffic came from US-based virtual private servers that the group had rented. The attackers did not hack the servers they used. They followed the exact acquisition pattern of T1583.003, then used those trusted-looking cloud IPs to deliver exploit code to many thousands of organizations.

  • Late January 2021

    Infrastructure rented, exploitation begins

    HAFNIUM rents US-based VPS machines and starts probing Exchange endpoints. CVE-2021-26855 (an SSRF flaw) plus post-authentication flaws CVE-2021-26858, CVE-2021-26867, and CVE-2021-27065 let unauthenticated requests write files and execute commands.

  • February 2021

    Webshell planting at scale

    The group drops China Chopper web shells into ...\FrontEnd\HttpProxy\owa\auth\ and similar paths, giving persistent, authenticated-feeling access through ordinary IIS requests. Multiple other actors copy the pattern once the exploit code spreads.

  • 26–28 February 2021

    Detection closes in

    Microsoft and partner incident-response firms correlate two evidence streams: exploit POSTs to /ews/Exchange.asmx originating from VPS ranges, and webshell artifacts on disk. Logs such as CVE-2021-26855_Exploit.log and IIS/WAF records tie the requests to hosting ASNs.

  • 2 March 2021

    Public disclosure and patches

    Microsoft publishes the HAFNIUM report and out-of-band security updates. The disclosure is unusual in style — a straight, technical call to patch — because the exploitation is already industrial in scale.

  • March 2021

    Global containment race

    SOCs worldwide block the reported VPS IP ranges, apply patches, and hunt for webshells. CERTs and ISACs echo indicators. Because the infrastructure is rented, new VPS IPs keep appearing as old ones are blocked — the rotation pattern this page teaches.

  • 9–12 March 2021

    Impact and consequences

    The cost became clear within days. By 9 March, researchers estimated that about 250,000 Exchange servers had been compromised worldwide, including roughly 30,000 organizations in the United States and 7,000 servers in the United Kingdom. Microsoft reported that a new ransomware family, later tracked as DearCandy, had encrypted some exploited servers. Microsoft also reported that webshell access to some victims was being sold. Most affected organizations were small and mid-size; they had to buy incident response, rebuild servers, and rotate credentials.

  • March–April 2021

    Eradication, recovery, and fallout

    Organizations remove webshells, rebuild trust (credential rotation, token invalidation), and hunt for follow-on activity such as directory harvesting. Reported scope: roughly 30,000 organizations in the United States alone, and an estimated 250,000 servers worldwide (see the impact entry above).

Detection point, in this guide’s terms

HAFNIUM is a textbook Sigma 3 (inbound scan / exploitation source from a hosting ASN) plus WAF-correlation scenario. The VPS-sourced exploit POSTs were visible in IIS and WAF logs days before public disclosure, for anyone enriching source IPs with ASN data. After disclosure, egress-side rules (Sigma 1 and 6) caught callbacks from compromised servers to replacement VPS boxes.

Lessons

1. Patch internet-facing systems fast — the window between exploit availability and disclosure was five weeks. 2. Keep IIS/WAF logs; they carried the whole case. 3. Enrich with ASN intel: “cloud IP doing exploit POSTs” was detectable before any CVE name existed. 4. Expect rotation — blocking one VPS IP was never enough, so pattern rules beat static lists. 5. Assume follow-on access: patching stops the entry, but webshell removal and credential rotation decide whether the attacker stays.

Sources: Microsoft MSTIC “HAFNIUM targeting Exchange Servers” (2 March 2021) and Microsoft’s 12 March 2021 ransomware reporting; CISA Emergency Directive 21-02; contemporaneous press and IR-firm reporting on server counts.

Mitigation and Defense

You cannot stop anyone from renting a server — mitigation means shrinking what a rented box can do to you and shortening the time you tolerate it.

ATT&CK’s only listed mitigation for T1583.003 is M1056 Pre-compromise: the action happens on the attacker’s side of the fence, so no preventive control inside your environment stops it. Everything below therefore works on your half of the boundary: know your logs, enrich them, constrain egress, harden identity, and make the abuse-report channel routine. Treat the grid as an architecture review checklist.

Policy

Write down which business services legitimately live in hosting ASNs. The allowlist is a policy artifact first and a lookup file second; without it, every ASN rule in Section 5.5 will be argued away.

Identity

Enforce MFA everywhere, apply conditional access with risk and geo signals, and rate-limit authentication attempts per source. Stuffing from rented boxes dies quickly against rate limits plus MFA.

Endpoint

Deploy Sysmon (or equivalent EDR network events) on all Windows hosts. Process-level network context is what turns “some IP” into “updater.exe in Downloads”.

Network

Log perimeter denies and egress flows; add ASN enrichment at ingest. Consider default-deny egress with an allowlist for high-risk segments such as payment systems.

Cloud

Cloud workloads also beacon to rented VPS machines; apply VPC flow-log analysis and marketplace or egress policies in your own tenants.

Logging

Retain firewall, proxy, IIS/WAF, mail gateway, and identity logs for at least 90 days searchable. HAFNIUM showed that IIS/WAF logs carry the whole case.

Monitoring

Deploy the six Sigma rules with their tuning notes; review their thresholds monthly against false-positive counts, not vibes.

Backup

Rented-infrastructure incidents often precede ransomware; offline or immutable backups keep a C2 channel from becoming unrecoverable downtime.

Response

Keep a current list of provider abuse-report contacts and a template report (IPs, timestamps, payloads). Blocking is local and temporary; the abuse report is global and permanent.

Note

Two habits make ASN intel trustworthy: refresh feed-based lists daily with expiry dates, and re-validate the allowlist quarterly with the business. A stale bulletproof-ASN list is harmless; a stale allowlist is how business traffic ends up blocked.

Home and small office

What a household or 10-person office can do

Enable automatic updates on every device and the router. Use a DNS filtering service (many are free for families) so known VPS-hosted malware and phishing domains never resolve. Turn on MFA for email and banking. If you run a small website, keep WAF or at least access logging on, and patch the web stack — the HAFNIUM story started with an unpatched internet-facing server. Report phishing that reached you to the mail provider; the report feeds the same abuse channels enterprises use.

Habits that keep the program honest

Daily

  • Check beacon and mail rules fired overnight; document verdicts in tickets.
  • Confirm ASN enrichment jobs succeeded on all four log families.
  • Skim top deny sources for new hosting-ASN entries.

Weekly

  • Review false-positive counts per rule; adjust only with a note.
  • Cross-check new intel (abuse.ch, ISAC) against the last 7 days of logs.
  • Follow up abuse reports filed; record provider replies.

Monthly

  • Re-validate one Sigma rule in the lab on rotation.
  • Refresh the VPS ASN table and the SaaS allowlist diffs.
  • Report rule coverage and tuning changes to stakeholders.

Cheat Sheet and Quick Reference

The one-screen summary: key facts, top detections, response checklist, and related pages.

Key facts

ATT&CK ID
T1583.003 — Acquire Infrastructure: Virtual Private Server (sub-technique of T1583)
Tactic
Resource Development · Platforms: PRE (pre-compromise) · Added in ATT&CK v8, 01 October 2020 (version 1.1)
What the adversary does
Opens a cloud-provider account (often crypto-paid), deploys a virtual machine, hardens it, and installs C2, redirector, phishing, or staging tooling; rotates servers as they burn
What it enables
C2 hosting (T1071), phishing hosting (T1566), scanning (T1595), payload staging (T1105), stuffing egress (T1110), data-theft hops (T1041)
Where to detect
Your perimeter and egress: firewall and Zeek logs with ASN enrichment, proxy, Sysmon 3, mail gateway — plus reputation feeds and provider abuse teams
Golden rule
Match behavior plus network (periodic, small, regular traffic to hosting ASNs) — never block a whole ASN without an allowlist, and never trust one IP block to hold
Distinction
T1583.003 = renting the server; T1584 = compromising infrastructure someone else owns; T1583.004 Server = broader hosting acquisition, incl. dedicated machines

Response checklist

  • Confirm the alert IP is really in a hosting ASN and not on your allowlist.
  • Pull 24 hours of connections to it; measure interval spread and payload sizes.
  • Identify the owning process via EDR (Sysmon 3) for every internal host involved.
  • Look the IP up in abuse.ch Feodo/SSL Blacklist, Spamhaus, GreyNoise, and urlscan.io.
  • Search the whole estate for the IP and its /24 neighbors; scope every affected host.
  • Block the IP at egress; isolate endpoints with active C2 sessions.
  • Reset credentials for accounts that authenticated from or toward the pattern.
  • File an abuse report with the provider, including timestamps, IPs, ports, and samples.
  • Add indicators to your intel store; schedule a re-check in 30 days for rotation.
  • Close the loop: update the rule thresholds and the allowlist if they misled you.
