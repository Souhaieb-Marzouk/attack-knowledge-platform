    Overview

    A short tour of the technique: what data destruction means, how wiping differs from plain deletion, and what this guide teaches you.

    Data Destruction means an attacker deletes or destroys data on purpose. The goal is to interrupt availability: files, folders, databases, virtual machines, or whole cloud storage areas stop working. This is an Impact technique in MITRE ATT&CK. Impact techniques appear late in an attack, when the intruder already controls the system and no longer needs to stay quiet.

    There is an important difference between deleting a file and destroying it. The del command on Windows and rm on Linux only remove the pointer to the file, not the data itself. The bytes stay on the disk until the system reuses that space, so a trained forensics team can often recover them. A wiper goes further: it overwrites file contents with random bytes, zeros, or even political images before or instead of deleting them. Overwritten data is gone for good, and no tool can bring it back.

    Attackers destroy data for three main reasons. Sabotage teams want the damage itself, as the wiper attacks against Ukrainian organizations showed in 2022. Extortion crews destroy data and backups when a victim refuses to pay, or instead of encrypting at all, so there is no decryptor and no negotiation. Some intruders also run secure-delete tools on their own traces, so investigators cannot recover the evidence of what they did.

    Where it sits in the attack chain

    Reaching this stage takes control. The attacker needs admin rights on a machine, or powerful permissions in a cloud account, because ordinary users cannot destroy much. Some destructive malware also spreads on its own. It steals passwords (OS Credential Dumping) and reuses valid accounts (Valid Accounts). Then it copies itself over admin shares on the network, like a worm. A few minutes of that can erase thousands of machines.

    Note

    T1485 targets files and data. Two sibling techniques target the disk instead: Disk Structure Wipe (T1561.001) destroys partition tables and boot records, and Disk Content Wipe (T1561.002) overwrites the whole disk surface. In real incidents they overlap: a boot wipe touches both, and this guide covers it as threat 5 (THR-005). Attackers often pair data destruction with T1490 Inhibit System Recovery, which removes shadow copies and backups first, so nothing can be rolled back.

    Written version of the simulation

    The same story in text, for screen readers and for printing. Each step names the action, the evidence it leaves, and what the defender should notice. Two log names come back often: Sysmon, a free Windows add-on that records process and file activity in detail, and auditd, the Linux audit service that records system calls.

    Step 1 — Sign in with stolen admin rights

    The attacker connects to FILE01, a Windows file server, using an admin account stolen by an infostealer. Nothing looks broken yet, but they now control the machine that stores shared company files. Evidence: a Security event 4624 logon from an unusual source address. The SOC should compare logon sources with known admin workstations.

    Step 2 — Map the shares and count files

    The attacker lists the shares and counts the files with dir. This is recon: they are learning where the valuable folders are and how much they can destroy. Evidence: process events plus a high-volume directory walk on the share. The SOC should treat share enumeration from an unexpected account as an early warning.

    Step 3 — Launch the deletion storm

    A bulk delete command such as del /s /q sweeps the share, and file tiles vanish in groups while the deleted counter climbs into the thousands. Evidence: Sysmon event 23 file deletes and a burst of Security event 4663 with DELETE access. The SOC should alert on deletion rate per process and host, not on single events.

    Step 4 — Overwrite the freed space

    The attacker runs cipher /w, which makes three overwrite passes over the free space on that volume. No forensics tool can recover the deleted files afterwards. The wipe bar fills pass after pass. Evidence: a process event for cipher.exe with the /w flag. The SOC should treat any secure-delete tool on a server as critical.

    Step 5 — Destroy the boot structures

    Now the attacker destroys the boot structures: diskpart with clean on Windows, or dd if=/dev/zero of=/dev/sda on Linux. The server goes dark and will not start again, because the boot records and partition table are gone. Evidence: a process event for diskpart.exe on Windows, or an auditd EXECVE record for dd writing to a whole-disk device on Linux. The SOC should page immediately on any of these.

    Step 6 — The SOC sees the storm

    The SIEM (the central log search system) counts thousands of delete events from one process on one host and raises a single critical incident. Evidence: correlated Sysmon 23, Security 4663, and PowerShell 4104 records. The SOC should build this rate correlation before an attack, with host and user in the alert context.

    Step 7 — Isolate and freeze the backups

    The SOC isolates FILE01 from the network and freezes the backup vault, so nothing left in the estate can be deleted. The attacker's path back is closed. Evidence: the EDR isolation action and the vault lock event. The SOC should keep an isolation and vault-lock runbook ready, and rehearse it twice a year.

    Step 8 — Restore and patch the entry path

    The team rebuilds the server from a golden image (a clean, tested system install). Then they restore data from the immutable backup copy the attacker could not change. Then they reset the stolen account and close the entry path. Evidence: the restore job and the follow-up ticket. The lesson: one immutable copy defeats data destruction.

    3

    Red team / hacker perspective

    Understanding how attackers destroy data helps you predict the move and place your sensors. Everything here is described for defense and for labs you own.

    When and why attackers use it

    Sabotage teams use data destruction as the goal itself. In February 2022, wipers such as HermeticWiper, CaddyWiper, and WhisperGate hit Ukrainian organizations hours before the invasion. Older campaigns such as Shamoon (2012) and Olympic Destroyer (2018) followed the same idea: destroy as much as possible, as fast as possible. These teams usually remove backups and shadow copies first (that is T1490), so victims cannot simply roll back.

    Extortion crews destroy data when pressure fails or instead of encryption. Storm-0501 destroyed data and backup files in the cloud after its extortion attempts. LAPSUS$ deleted systems and resources both on-premises and in the cloud, and ShinyHunters used the DeleteBucket API call to remove cloud storage outright. After this kind of destruction there is no decryptor and no key to buy, which is what makes it different from ransomware.

    The third reason is quietest: hiding. SDelete is a legitimate Microsoft Sysinternals utility that overwrites files so they cannot be recovered, and intruders run it on their own tooling and on stolen data before they leave. Destruction can also spread by itself. Destructive malware has moved through networks using stolen credentials, dumped password hashes, and admin shares. The Shai-Hulud worm of 2025 did the same through the npm (JavaScript package manager) supply chain. It overwrote and deleted everything in the user's home directory.

    How it is performed

    The core moves are simple, which is why they are also easy to detect. The commands below are the classic sequence for each platform, shown for lab study only. Run them exclusively inside disposable virtual machines that you own, take a snapshot first, and treat every command as if a real SOC were watching.

    Each block leaves a different trace. cipher /w makes three overwrite passes over free space, so plain file recovery tools find nothing afterwards. shred does the same for single files on Linux. The dd command, pointed at a whole-disk device such as /dev/sdb, destroys the partition table and boot records. The machine then cannot start. In the cloud, DeleteObjects removes up to 1000 objects per call, and every call lands in CloudTrail with the exact identity that made it.

    Documented destructive malware and tools

    ATT&CK procedure records name many destructive families. They repeat the same patterns: overwrite contents, spread with stolen credentials, and remove recovery options first. The table below summarizes the most useful ones for detection planning.

    Prerequisites and conditions

    What the attacker needs first

    • Local admin or SYSTEM rights on the target machine, or root on Linux.
    • Write access to the share, volume, bucket, or database they want to destroy.
    • For network-wide damage: stolen credentials and reach into admin shares, or a spreading worm.
    • For cloud damage: an IAM identity (a cloud user or role) with delete permissions.
    • For containers: permission to exec into pods or to create privileged DaemonSets.

    What limits them

    • Immutable or offline backup copies cannot be overwritten or deleted by a stolen admin account.
    • Overwriting large volumes takes time, which gives defenders a window to react.
    • Application control can block sdelete, shred, cipher, and dd on servers.
    • Cloud audit logs record every delete call, even when on-premises logs were wiped.
    • Mass deletion produces huge event volumes that no attacker can switch off.

    Common variations and attacker mistakes

    Variations follow the platform. On Kubernetes, TeamPCP ran privileged DaemonSets (pods that start on every node) and deleted files on mounted volumes. In the cloud, T1485.001 shows the patient variant: an attacker edits a bucket lifecycle rule so data quietly expires without any loud delete call. Some wipers also spread like worms: HermeticWiper shipped with a companion tool, HermeticWizard, that copied it to other machines, including through Group Policy.

    Attacker mistakes help defenders. Tools that run without admin rights fail and still appear in process logs. Typos in tool names leave odd process records that are trivially detectable. Fast campaigns forget machines: hosts that were offline, network segments they could not reach, or the one backup copy outside their control. And the biggest mistake of all is timing: a deletion storm is so loud that even a small SOC can catch it in minutes, if the rule exists before the attack.

    Danger · lab-only

    Never run the commands above on a production or shared system. Bulk deletes, overwrite passes, and boot wipes permanently destroy data. Use isolated virtual machines with fresh snapshots, separate lab cloud accounts, and treat every run as if it were being logged by a real SOC.

    4

    Blue team / SOC perspective

    Data destruction is loud if you count events, and silent if you do not. Here is how to see it, what it leaves behind, and how to triage it fast.

    How defenders can see it

    Process telemetry

    Sysmon event 1 or Security event 4688 with command-line auditing shows the exact tool and flags: sdelete -p 3, cipher /w, shred, dd. These tools are rare on servers, so a single event can be worth a page.

    File deletion telemetry

    Sysmon events 23 and 26 record file deletes, and Security events 4663 (DELETE access) plus 4660 (object deleted) record each removal with the user and process behind it. One event means little; a storm means everything.

    Rate analytics

    Count delete events per process and per host over rolling 5-minute windows and compare with a 30-day baseline. A wiper deletes hundreds of files per minute; normal activity deletes a handful per hour.

    Script and shell logs

    PowerShell event 4104 shows script blocks such as Clear-RecycleBin, and Linux auditd shows execve of shred, dd, or rm with their arguments. Both reveal intent that plain file events hide.

    Cloud audit logs

    AWS CloudTrail records DeleteObjects, DeleteBucket, TerminateInstances, and DeleteDBInstance with the exact identity and source address. Object-level data events must be enabled for S3, or multi-object deletes stay invisible.

    Container audit logs

    Kubernetes API server audit logs show who created privileged DaemonSets or exec'd into pods. TeamPCP-style attacks leave their whole path here, because every destructive step went through the API.

    Why it matters and how it fits the chain

    Deletion signals matter in two very different moments. Before an encryption event, wiping the backups is often the last step a ransomware crew takes, so a delete storm can be the final warning you get. During pure destruction, the storm is the attack, and every minute of delay costs data. Either way, the signal is rate: no legitimate process deletes thousands of files from user shares in minutes.

    There is also a forensics angle. Once an attacker runs a real wipe, the overwritten files are gone, so evidence must be captured early. Preserve memory and disk images of affected machines before you reboot or clean them, and assume that anything the attacker touched with SDelete cannot be recovered. The accounts, hosts, and parent processes in the delete events then become your main path to scope the incident.

    Short triage flow

    1. Confirm the burst is real

      Count the delete events per process, host, and user in the last hour. Rule out known cleanup jobs, build agents, and scheduled rotations with your change calendar.

    2. Identify the source

      Read the process image, command line, parent process, and logon for the deleting account. A stolen admin account from a workstation is the classic pattern.

    3. Scope across the estate

      Search all hosts for the same command lines and for other delete storms in the last 24 hours. Multiple hosts mean an active campaign, not a mistake.

    4. Protect what is left

      Isolate affected hosts, freeze or lock the backup repository, and revoke the deletion permissions of the accounts involved. Speed here decides how much data survives.

    5. Preserve and escalate

      Capture memory and disk images before any reboot, page the incident commander, and start the restore plan from the immutable copy.

    Good practice

    Write the triage steps above into your incident runbook before you need them. During a live storm, the team that follows a prepared checklist freezes backups minutes faster than the team that improvises.

    Detection engineering deep dive

    This is the practical core of the guide. It covers regulation mapping, threat intelligence, ranked threats, and real log examples. It ends with five Sigma rules and matching Splunk queries you can adapt today.

    5.1 Regulation mapping

    Data destruction attacks the availability of information, and almost every security framework asks you to protect exactly that. Auditors want proof that data can be restored, that deletion is controlled, and that destruction attempts are monitored. The table below shows what each framework expects and the evidence a detection program provides.

    Framework and controlWhy it appliesExpected evidence
    GDPR — Article 32 (security of processing) Requires the ability to restore availability of and access to personal data after an incident. Destroyed data can become a prolonged, reportable breach. Documented restore procedures, tested restoration records, alerts on mass deletion, incident reports showing recovery time.
    HIPAA Security Rule — §164.308(a)(7) contingency plan Covered entities must keep a data backup plan and disaster recovery plan for electronic protected health information, which a wiper destroys in place. Written contingency plan, backup success reports, restore test results, monitoring evidence for deletion attempts on health data stores.
    ISO/IEC 27001:2022 — A.8.13 (information backup), A.8.15 (logging), A.8.16 (monitoring) Backup copies must be protected and monitored, and destructive activity must be detected. T1485 is the direct failure case for all three controls. Backup policy with immutable copies, deletion-monitoring rules, alert tickets for wipe attempts, logging coverage across file servers and cloud.
    SOC 2 — A1.2 (recovery infrastructure), CC7.4 (incident response) Availability commitments expect tested recovery, and incident criteria expect detection and response. Destruction of storage defeats both if unnoticed. Runbooks, restore drills with timings, detection rule documentation, records of alerts and response for destructive activity.
    PCI DSS — 12.10.x (incident response plan and testing) Organizations handling cardholder data must prepare for scenarios that destroy or lock data, which is exactly what a wiper or delete storm does. IR plan covering wiper scenarios, response tests, records of delete-rate alerts and containment actions.
    NIST SP 800-53 Rev.5 — CP-9 (system backup), CP-10 (recovery), AU-6 (audit review) Federal-aligned controls require protected backups, tested recovery, and review of audit records for destructive events. Control implementation statements, backup protection configuration, audit-review procedures tuned to deletion storms, test logs.

    5.2 Threat intelligence

    Intelligence turns a generic rule into a justified priority. For data destruction the picture is unusually rich, because destructive campaigns are public and well documented. State-linked wiper teams publish nothing themselves. Vendors and CERTs (computer emergency response teams) document their tools in detail. Collect from several source types, and record how confident you are in each finding before you change a rule or a runbook.

    MITRE ATT&CK

    Start with the T1485 technique page and its long procedure list. It names the tools, the actors, and the platforms, which makes rule coverage easy to justify.

    Vendor reporting

    ESET, Symantec, and CrowdStrike documented HermeticWiper in depth, and Microsoft tracked WhisperGate. Their reports contain exact behaviors you can turn into detections.

    OSINT sources

    Open-source intelligence (OSINT) is public information anyone can read: security blogs, researcher threads, and free government advisories such as CISA StopRansomware. Destructive campaigns draw heavy OSINT coverage, so this source is strong for T1485.

    ISACs and CERTs

    An Information Sharing and Analysis Center (ISAC) is a member group that shares attack data for one sector, such as energy or finance. CERTs are national response teams. Both share wiper indicators fast, often before public reports appear.

    Commercial feeds

    Paid feeds add actor tracking and early warning about new wipers or supply-chain worms. Use them for context and prioritization, not as a replacement for your own logs.

    Internal telemetry

    Your own history is the most valuable source. Past cleanup jobs, failed delete attempts, and near misses define the baselines that make rate alerts trustworthy.

    5.3 Threats ranking and categorization

    Five realistic threats cover this technique well. The rank reflects how likely the threat is and how much damage it causes when it works. Preconditions describe what an attacker must already have; the justification explains the rank so you can defend it in planning meetings.

    IDThreatRankPlatformDescription and preconditionsImpact and justification
    THR-001 Wiper or secure-delete utility execution Critical Windows Linux macOS Someone runs sdelete, cipher /w, shred, or dd. Preconditions: local admin or root, or write access to the target data. Makes recovery impossible, not just delayed. Rare on servers, so even one event is decisive. Highest severity because it removes every later option.
    THR-002 Bulk file deletion storm High Windows Linux Containers One process deletes far more files than any baseline allows, with del /s /q, rm -rf, or scripted loops. Preconditions: write access to many files. The most common destruction pattern across wipers and manual intrusions. Very detectable through rate, but plain deletion may still be recoverable, hence High.
    THR-003 Mass deletion on file servers and shares, including recycle bin purge High Windows Bursts of 4663 DELETE plus 4660 events on shares, often ending with Clear-RecycleBin. Preconditions: an account with share write access, often stolen admin. Hits the data employees work with every day and is the visible half of a file-server wipe. Strong 4663/4660 signals make it catchable in minutes.
    THR-004 Cloud storage destruction High IaaS Multi-object DeleteObjects calls, DeleteBucket, batch TerminateInstances, or DeleteDBInstance. Preconditions: an IAM identity with delete permissions. Destroys data across regions in minutes, as Storm-0501 and ShinyHunters showed. Fully loggable, but only if object-level data events are enabled.
    THR-005 Boot-critical wipe Critical Windows Linux dd writing to a whole-disk device, diskpart clean, or direct MBR and partition destruction. Preconditions: root or admin with raw disk access. Machines cannot start and file data on them is likely lost too. Almost never legitimate outside imaging hosts, so it alerts on any occurrence.
    Container variant

    The same threats exist inside Kubernetes clusters. An attacker with cluster rights can exec into pods and delete files on mounted volumes, or create privileged DaemonSets that wipe data on every node. ATT&CK documents this behavior for TeamPCP. Ship the API server audit log to your SIEM. Rule 2 in section 5.5 carries the matching Kubernetes queries.

    5.4 Logs and patterns

    Each threat below lists the log sources that see it and the fields that matter. It also describes normal behavior, suspicious behavior, and the detection logic in plain words. Threats 2, 3, and 4 are rate-based, so their logic is written as a precise threshold rule you can tune. A realistic event example follows each table so you can validate your pipeline against real shapes.

    Threat 1 — Wiper or secure-delete utility execution (THR-001)

    AspectDetails
    Log sourcesSysmon event 1 (process creation) and Security event 4688 with command lines. On Linux, auditd EXECVE records. EDR process telemetry adds coverage.
    Key fieldsImage, CommandLine, ParentImage, User, host, Hashes, and on Linux a0 to a3.
    Normal behaviorStorage teams may run cipher /w on decommissioned disks, and imaging hosts may run dd. shred can appear in approved maintenance scripts. All of it should map to change tickets.
    Suspicious behaviorsdelete with pass flags, cipher /w, or shred on file servers or user machines. The caller runs them from cmd, PowerShell, or SSH sessions, outside change windows. Script-driven rm -rf, dd, or srm from /tmp or /private/tmp (the Linux and macOS temp folders) is another sign.
    Detection logicAlert on any process image containing sdelete, any cipher.exe command line containing /w, and any shred, srm, or dd execution. Keep a small allow list of imaging and maintenance hosts. No rate is needed: one hit is enough.

    Threat 2 — Bulk file deletion storm (THR-002)

    AspectDetails
    Log sourcesSysmon events 23 (file delete archived) and 26 (file delete detected). Security event 4660 (object deleted) counts each removal. On Linux, auditd unlink, unlinkat, and rmdir syscalls. EDR file events add coverage.
    Key fieldsTargetFilename, Image (deleting process), User, host, ProcessId, and on Linux exe, uid, syscall.
    Normal behaviorBuild agents, log rotation, and temp cleanup delete many files, but steadily and from known binaries. A healthy host shows tens of deletes per hour, not thousands.
    Suspicious behaviorOne process or one account deletes hundreds of files per minute. The command line shows wildcards such as del /s /q or rm -rf. Deletes run from interactive sessions on servers, or the process shows its first-ever bulk delete.
    Detection logicThreshold rule: more than 200 file-delete events from one process on one host within a rolling 5-minute window. The rule also checks that this host-process pair sat below 20 deletes per hour over the last 30 days. Sum by host and Image, exclude allow-listed build agents and rotation jobs, and page when the count crosses 10 times baseline.

    Threat 3 — Mass deletion on shares and recycle bin purge (THR-003)

    AspectDetails
    Log sourcesThis threat runs on Windows file servers. Security event 4663 (object access with DELETE) and 4660 (object deleted) carry the details. Sysmon 23 covers UNC paths. PowerShell event 4104 shows Clear-RecycleBin.
    Key fieldsObjectName, AccessList (contains %%4424 for Delete), AccessMask (0x10000), SubjectUserName, ProcessName, host, and ScriptBlockText for 4104.
    Normal behaviorUsers delete their own files and empty their recycle bins; scheduled cleanups touch temp folders. Per-server delete rates stay in the tens per hour and each user touches only their own folders.
    Suspicious behaviorOne account sends DELETE access across many folders it does not own. Recycle bin purges on servers and deletes at unusual hours also count. So does one interactive session that sweeps whole share trees.
    Detection logicThreshold rule: more than 100 events 4663 with DELETE access from one account on one file server within a rolling 5-minute window. A second trigger is more than 20 objects deleted per user folder by a single session. Alert on any Clear-RecycleBin on a server, and raise severity when the same account also matched threat 1 or 2.

    Threat 4 — Cloud storage destruction (THR-004)

    AspectDetails
    Log sourcesAWS CloudTrail management events plus S3 object-level data events. Azure Activity Log and Google Cloud audit logs cover the other clouds. Data events must be enabled, or DeleteObjects stays invisible.
    Key fieldseventName, eventSource, userIdentity.arn, sourceIPAddress, userAgent, requestParameters.bucketName, requestParameters.delete.objects, awsRegion, errorCode.
    Normal behaviorLifecycle automation expires old versions under fixed role identities, and cloud teams decommission test buckets with tickets. Both come from known roles, user agents, and source ranges.
    Suspicious behaviorManual delete calls by interactive or unfamiliar identities. One call removing hundreds of keys, batch termination of instances, or database deletion also counts. So do calls from new source IPs or user agents, and any delete against backup buckets.
    Detection logicThreshold rule: more than 10 destructive calls from one identity within 15 minutes, or a single DeleteObjects call carrying more than 100 keys. Alert on any DeleteBucket, DeleteDBInstance, or TerminateInstances batch of 3 or more instances outside approved changes. Page when the target is a backup bucket.

    Threat 5 — Boot-critical wipe (THR-005)

    AspectDetails
    Log sourcesLinux auditd EXECVE and SYSCALL records for dd and shred. Sysmon event 1 covers diskpart.exe on Windows. Kernel and storage subsystem logs and EDR telemetry add depth.
    Key fieldsOn Linux a0 to a3 (command arguments), exe, uid, host; on Windows Image, CommandLine, User, host.
    Normal behaviorAlmost none. Only imaging and provisioning hosts write to whole-disk devices, and diskpart belongs to OS deployment tasks. Everything else is a misconfiguration at best.
    Suspicious behaviordd with of= pointing at /dev/sda, /dev/nvme0n1, /dev/vda, or another whole disk instead of a partition. Shred on a device node is another sign. So is diskpart running with a script that contains clean, or any interactive session touching raw devices.
    Detection logicAlert on any dd or shred command whose output target is a whole-disk device node, and on any diskpart clean. Compare the device name against your imaging-host allow list; exclude partition suffixes such as sda1 so only whole-disk writes stay. This needs no rate: a single event is critical by itself.

    5.5 Sigma rules and Splunk SPL

    Five complete Sigma rules follow, one per threat, each with a matching Splunk query. MITRE defines the official detection strategy for this technique as DET0146, Detection of Data Destruction Across Platforms via Mass Overwrite and Deletion Patterns. Its analytics cover command-line wipe tools, mass deletes on Linux, script-driven overwrites, cloud delete APIs, virtual disk destruction, and container file operations. The rules below implement the analytics your log sources can see. Sigma is a standard YAML format for log detections, so these rules convert to most SIEM products. The Splunk queries use the index and sourcetype conventions listed below; adjust the index names to your environment and document the change.

    Field assumptions for Splunk

    index=sysmon holds Sysmon XML events with fields like Image, CommandLine, and TargetFilename. index=wineventlog holds Security and PowerShell events. index=linux holds auditd records with a0 to a3 arguments. index=aws holds aws:cloudtrail data with JSON fields like eventName. index=k8s holds Kubernetes API server audit records with fields like objectRef.resource and verb. Field extraction must be enabled for XML inputs before these queries work.

    Rule 1 — Secure-delete or wipe utility execution (covers THR-001)

    Mapping note: Sigma Image|contains becomes a wildcard path match. The two contains|all terms collapse into one CommandLine="* /w*" filter. False positives: approved wipe jobs on decommissioned disks. Tuning: allow-list your imaging and disposal hosts, and raise priority when the parent process is cmd, PowerShell, or an SSH shell on a file server. The Linux half of this threat (shred, dd) follows the same logic on the linux index and appears in rule 5.

    Rule 2 — Bulk file deletion storm (covers THR-002)

    Mapping note: the Sigma count condition expresses the threshold. The Splunk version makes the 5-minute bucket and the 200-event cut explicit for Windows, Linux, and Kubernetes in one block. False positives: build agents, rotation jobs, and approved container work. Tuning: keep a 30-day per host and process baseline and exclude allow-listed binaries. Raise severity when the deleting process is a shell or the host is a file server.

    Rule 3 — Share deletion burst and recycle bin purge (covers THR-003)

    Mapping note: the %%4424 DELETE token carries over unchanged. The Splunk wildcard match uses it verbatim, and the threshold moves into the stats plus where pair. False positives: user-driven deletes on workstations and documented cleanup jobs. Tuning: restrict the share path filter to your file servers and keep a per-server baseline. Pair any hit with rule 1 or 2 matches on the same host before you close the case.

    Rule 4 — Cloud storage destruction (covers THR-004)

    Mapping note: CloudTrail JSON fields map directly to Splunk extractions. The Sigma event-name lists become the SPL IN clause. False positives: scheduled lifecycle deletions under fixed automation roles. Tuning: allow-list those role ARNs, then page on any interactive identity, new source IP, or a target bucket that holds backups. DeleteBucket and DeleteDBInstance deserve an alert-on-any variant, because no normal workflow calls them in bulk.

    Rule 5 — Boot-critical disk wipe (covers THR-005)

    Mapping note: the Sigma rule checks the third argument slot (a2). dd if= of= arguments usually arrive in that order, and the Splunk version covers all slots at once. The Windows boot-wipe variant (diskpart with clean) appears in the same SPL block. False positives: imaging and provisioning hosts. Tuning: allow-list those hosts by name and exclude partition suffixes such as sda1, so only whole-disk writes stay. Match diskpart script files through EDR or command-line content when the clean keyword sits inside the script instead of the command line.

    Real-world case study

    HermeticWiper, 23 February 2022: a destructive attack that hit Ukrainian organizations shortly before the invasion, documented in detail by ESET, Symantec, and CrowdStrike.

    Source label

    This case study is based on public reporting (ESET, Symantec, CrowdStrike). Dates follow those reports, and clock times are approximate.

    Context

    In the last hours before the invasion of Ukraine, several families of wiper malware activated against Ukrainian government, nonprofit, and technology organizations. HermeticWiper was one of them: pure destruction, no ransom note, no decryptor. It did not travel alone. A companion tool, HermeticWizard, moved the wiper to other machines, including through Group Policy (central Windows settings pushed to many computers at once). One intrusion could therefore turn into an estate-wide wipe. The attack is a textbook T1485 case: files overwritten with random bytes, boot structures corrupted, and recovery options removed first.

    Attack chain at a glance

    Initial Access→ Lateral Movement (HermeticWizard)→ Privilege Escalation (signed driver)→ T1490 — stop VSS→ Impact — T1485 wipe

    Timeline

    1. 23 Feb 2022 · hours before the invasion
      First machines execute the wiper

      Security teams observed HermeticWiper running on machines of Ukrainian organizations that day. The timing, so close to the invasion, was chosen for maximum disruption.

    2. Next hours
      The companion tool spreads the payload

      HermeticWizard copied the wiper to other machines over remote execution paths and Group Policy. The wipe therefore spread inside the network without new external deliveries.

    3. On each host
      A legitimate signed driver unlocks raw disk access

      The malware loaded a legitimate, signed driver. That driver gave it direct access to the raw disk, an operation normal programs are never allowed to do.

    4. Minutes before the wipe
      Recovery options removed (T1490)

      HermeticWiper stopped the Volume Shadow Copy service, so local restore points could not help afterwards. This pairing of T1490 and T1485 is the standard destructive sequence.

    5. Impact moment
      Boot structures corrupted, files overwritten

      The wiper corrupted the MBR (the small boot program and partition list at the start of a disk) and other partition structures. It wiped files in system folders through recursive FSCTL_MOVE_FILE calls. It also overwrote large files in My Documents and on the Desktop with random bytes. Many machines became unbootable.

    6. Days after
      Rebuilds and partial recovery

      Organizations rebuilt machines from golden images. Where files had been overwritten, they were gone for good; data survived only on copies the wiper never reached.

    Detection point

    The best window opened between driver load and the first overwrite. Three signals appeared together: a driver load event for a legitimate signed driver in an unusual context, a process event for the wiper binary, and unusual disk I/O as raw write volume exploded. Stopping the Volume Shadow Copy service was a fourth signal. An organization with Sysmon and the rules in section 5 would have seen the attack minutes before damage, which is exactly the margin this technique leaves you.

    Containment

    Teams isolated affected networks, blocked the wiper and companion tool by hash, and disabled the Group Policy path the spread used. Accounts used for the lateral movement were reset, and untouched machines were protected while responders hunted for the binary across the estate.

    Eradication

    Because files were overwritten, cleaning was pointless: every affected machine needed a full rebuild from golden images. Responders removed the companion tool, the signed driver, and any remaining wiper binaries, and verified that the deployment channels used for the spread were closed.

    Recovery

    Recovery came from backups and from machines that never received the payload. Overwritten data could not be restored, so the depth of loss depended on how recently the last protected copy had been taken. Organizations with offline or immutable copies returned to service fastest.

    Impact and consequences

    Dozens of organizations lost machines minutes before a war began, and some lost data permanently because overwritten files are unrecoverable. The campaign showed that destruction can be the goal, not a failed extortion. It also shifted budgets: after February 2022, many organizations treated wipers, not only ransomware, as a planning scenario, and CISA published advisories that turned the campaign's indicators into public defensive guidance.

    Team response and communication

    Response teams faced an unusual problem: the attack and the war started together, so communication channels were under stress while the incident ran. Teams that had out-of-band channels and printed procedures kept coordinating, and sector partners shared indicators within hours. Daily short briefings kept one priority: stop the spread first, then rebuild in business-critical order. The episode confirmed that destructive attacks need rehearsed coordination between IT, security, and leadership.

    Lessons learned

    • Overwritten data stays overwritten; only copies outside the attacker's reach survive.
    • Driver load plus raw disk I/O on normal servers is a critical signal, not noise.
    • Stopping the Volume Shadow Copy service is a destruction warning, tie it to your T1490 rules.
    • Spread through Group Policy means one stolen admin path can wipe an estate; segment and monitor it.
    • Rebuild plans from golden images halve recovery time; test them before you need them.

    Mitigation and defense

    You cannot stop every attacker from reaching one machine, but you can make destruction pointless. The controls below follow the three ATT&CK mitigations for T1485 and add the practical layers around them.

    The three ATT&CK mitigations

    M1053 — Data Backup

    Keep protected copies on separate systems. The copy that matters is immutable (locked for a retention period) or offline, so an attacker with full admin rights still cannot overwrite it. This is the control that decides whether a wiper is a disaster or an inconvenience.

    M1032 — Multi-factor Authentication

    Require a second authentication step for destructive actions. In cloud storage, MFA delete means deleting an object version needs extra proof beyond the account, which blocks a stolen credential from emptying a bucket. Extend the same idea to backup consoles and cloud root accounts.

    M1018 — User Account Management

    Limit who can delete or change storage. In cloud environments, keep bucket lifecycle policy rights to the few accounts that need them, and use service control policies to restrict the PutBucketLifecycle API call. Separate backup administration from server administration, remove standing delete rights from everyday identities, and review cloud IAM permissions for destructive actions on a schedule.

    Enterprise controls by domain

    Backup architecture

    Follow the 3-2-1-1-0 pattern: three copies, two media types, one offsite, one immutable or offline, and zero restore-test errors. Keep at least one copy credential-separated, so the same stolen admin account cannot reach the data and its backups at once.

    Cloud storage hardening

    Turn on S3 versioning with Object Lock, enable MFA delete on critical buckets, and deny destructive APIs with service control policies. Use deletion protection for databases and disable API termination on critical instances, so a single identity cannot destroy a region in minutes.

    Endpoint hardening

    Use application control to block sdelete, shred, cipher, dd, and diskpart on servers where they have no business running. Remove local admin rights from everyday accounts, because every threat in this guide starts with too much privilege.

    Logging coverage

    Enable Sysmon FileDelete events (23 and 26). Set object-audit SACLs (access lists that say which actions to log) on file shares so 4663 and 4660 appear. Deploy auditd rules for unlink and execve on Linux. Ship PowerShell 4104, and turn on S3 object-level CloudTrail data events.

    Containers and virtualization

    Use admission control to block privileged DaemonSets and unrestricted exec, and ship the Kubernetes API audit log to your SIEM. On ESXi, protect snapshots and keep hosts patched. ATT&CK documents attackers destroying virtual disks, images, and snapshots on ESXi with commands such as vim-cmd.

    Response readiness

    Write a destruction runbook: who isolates, who freezes the backup vault, who revokes delete permissions, who decides on restoration. Rehearse it twice a year with the real teams, and keep out-of-band communication ready for the worst day.

    Home and small office advice

    Protect your own files

    • Keep one backup copy on an external drive that stays disconnected.
    • Keep one cloud copy with file version history, so deleted files roll back.
    • Turn on two-step verification for the cloud account that holds your files.
    • Never store the only copy of important documents on the same disk as the originals.

    Small-office quick wins

    • Use a separate account for backup administration, with two-step verification.
    • Once a quarter, restore one important file and time how long it takes.
    • Limit who can delete shared folders on the file server or NAS.
    • Keep a printed page with the backup vendor support number and license keys.
    Good practice

    The strongest message from every destructive incident: attackers cannot destroy what they cannot reach. One immutable or offline copy, plus delete permissions kept tight, turns a wiper campaign from a catastrophe into a rebuild exercise.

    Everything important on one screen, for the wall and for the incident channel.

    Key facts

    Technique
    T1485 — Data Destruction.
    Tactic
    Impact.
    What it does
    Deletes or overwrites data so it stops being available; wipers make it unrecoverable.
    Typical timing
    Endgame: after extortion pressure, or right before and during a destructive attack.

    Response checklist

    • Confirm the burst: count delete events per process, host, and user.
    • Isolate affected hosts from the network immediately.
    • Revoke the delete permissions of the accounts involved and reset them.
    • Freeze or lock the backup repository before anything else touches it.
    • Search all hosts and cloud accounts for the same commands in the last 24 hours.
    • Capture memory and disk images before any reboot, for the forensic record.
    • Start the restore plan from the immutable copy and verify one restore works.
    • After containment, close the entry path that gave the attacker admin rights.
