Windows Remote Management (WinRM)

WinRM is the built-in remote management service of Windows. PowerShell Remoting runs on top of it, so an admin can run commands on another computer without a screen, a window, or any extra software. An attacker with one stolen admin password can use the same trusted channel to command many servers at once.

Written for beginners, SOC analysts, and detection engineers. Every example here is for learning and defense only. This guide shows the attack steps, the logs the attack leaves behind, and how to catch it.

Red Team Perspective

Why WinRM is the quietest way to command a Windows server fleet.

Attackers do not always need exploits. On a Windows network, the admin tools are already installed on every machine. WinRM turns those tools into a remote channel, and PowerShell turns that channel into a shell. This section explains the technique from the attacker's side so you can understand what it looks like on yours.

What WinRM is

WinRM (Windows Remote Management) is a management service that ships with Windows. It lets one computer send management commands to another computer over the network. It speaks a protocol called WS-Management, which is plain XML messages over HTTP or HTTPS. You can picture it as a mailbox for admin commands. A client drops a command in. The service on the target runs it, and the answer comes back through the same mailbox.

PowerShell Remoting is the most common client, and it is not a separate service. It is simply PowerShell sending its commands through WinRM. Two cmdlets do most of the work. Enter-PSSession opens an interactive shell on a remote computer. Invoke-Command runs one command or script on one computer or on many at once.

  • TCP 5985 - the default listener. This is plain HTTP with Windows authentication layered on top. It is not TLS.
  • TCP 5986 - the HTTPS listener. Same traffic, wrapped in TLS with a certificate.
  • Default state - enabled on Windows Server after setup. Usually off on client Windows until someone runs winrm quickconfig.
Why this matters: WinRM is a trusted admin channel, not malware. When it moves through your network it uses built-in binaries, valid credentials, and ports you approved. There is no file to scan and no exploit signature to match. Only logs and behavior give it away.

Why attackers love it

  • It is a native admin tool, so application allow lists do not stop it.
  • No files are dropped on the target. Commands live in memory inside wsmprovhost.exe.
  • One Invoke-Command line can hit many servers at once.
  • The traffic blends in with normal automation, patch jobs, and monitoring tools.
  • It needs no window and no desktop session, so nobody sees it happen.

Prerequisites

  • Valid credentials - a password, a Kerberos ticket, or in rare setups a certificate.
  • Membership of the local Administrators group or the Remote Management Users group on the target.
  • A running listener on TCP 5985 or 5986 - default on servers, often off on workstations.
  • A firewall path from the attacker to the target on that port.

Session settings worth knowing

Three WinRM settings shape who can connect, and attackers touch them too:

  • TrustedHosts - a list on the target that names which computers may connect without a domain trust. Domain-joined machines normally use Kerberos instead. Workgroup servers need entries here, so a changed TrustedHosts list is worth an alert.
  • CredSSP - an option that forwards your credentials to a second computer, the "double hop". Admins turn it on with Enable-WSManCredSSP. If abused, a copy of the credentials lands on the hop machine.
  • AllowRedirection - a session option (New-PSSessionOption -AllowRedirection) that lets WinRM send a session to a different machine than the one you asked for.
Tip: These settings live in the registry under the WSMAN key, so Sysmon event 13 records changes to them. The listener rule in section 4 catches part of this.

How it is done - lab example only

Three commands on an admin workstation tell the whole story. First ask if a listener answers, then open a session, then run one command on two servers at once.

powershell
# 1. Is a WinRM listener alive on the target?
Test-WSMan -ComputerName APP-SRV-02

# 2. Open an interactive remote PowerShell session
Enter-PSSession -ComputerName APP-SRV-02 -Credential CORP\admin_mike
[APP-SRV-02]: PS C:\Users\admin_mike\Documents> hostname
[APP-SRV-02]: PS C:\Users\admin_mike\Documents> Exit-PSSession

# 3. One command, many servers
Invoke-Command -ComputerName APP-SRV-02,FS01 -ScriptBlock { hostname; whoami }

From a Linux attack box the same technique looks like this:

bash
# Find servers in the lab range that answer on 5985 and accept the login
netexec winrm 10.1.20.0/24 -u admin_mike -p 'Autumn2026!'

# Open an interactive WinRM shell on one of them
evil-winrm -i 10.1.20.62 -u admin_mike -p 'Autumn2026!'
Watch out (OPSEC and noise): On a target without logging, this attack is very quiet. There is no disk write, no window, and no new account at first. But on a target that collects logs, it is loud in a different way. Every session creates a 4624 Type 3 event, a wsmprovhost.exe process, and a 4104 script block with the full command text. Red teams should assume the command text is captured.
Ethics: Only run these commands against systems you own or have written permission to test. Using stolen credentials against systems you do not own is a crime in most countries, even if you call it a test. Build a small lab with two virtual machines instead. Real defenders learn from safe labs just as well.

Blue Team / SOC Perspective

A quiet channel that still leaves a loud trail - if you collect the right logs.

From the defender's chair, a WinRM attack is a chain of small, boring-looking events that add up to something serious. Each step below is a normal admin action. That is exactly why a single event proves nothing, but the pattern proves a lot. Your job is to collect all the pieces and look at them together.

The artifact story, step by step

1. The logon - event 4624 with Logon Type 3. WinRM sessions are network logons, not desktop logons. There is no Type 10 event, no RDP window, and no 21 session event. Look for Logon Type 3 with AuthenticationPackageName "Negotiate", plus the source IP address and WorkstationName of the connecting machine. A server that suddenly accepts Type 3 logons from a user workstation deserves a question.

2. The process - wsmprovhost.exe. Windows starts this process to host every remote PowerShell session. Its parent is usually the WinRM service, which runs inside a svchost.exe. Every command the visitor runs appears as a child of wsmprovhost. This parent-child pair is the golden signal of the whole technique: if wsmprovhost.exe runs anywhere except an approved jump server, someone is remoting in.

3. The command text - event 4104. PowerShell script block logging records the full text of every script block it runs. Even better, it records decoded content: a payload hidden with -EncodedCommand appears in plain text in the 4104 event. This is often the single most useful log in the whole case. Event 4103 (module logging) is a second, noisier source. It still shows command activity when script block logging is off.

4. The process line - event 4688. With command line auditing on, process creation events show the full command, including powershell.exe -nop -w hidden -enc SQBF... and rundll32 lines that abuse comsvcs.dll.

5. The network - Sysmon event 3. With Sysmon installed, you see the client side and the server side of every connection to TCP 5985 or 5986. A workstation talking to many servers on 5985 in minutes is a sweep in progress.

6. The service log - Microsoft-Windows-WinRM/Operational. This log records listener and client activity. It is thin on its own, but it correlates well with 4624 and 4104 when you rebuild a timeline.

Watch out: Port 5985 does not use TLS. Windows authentication protects the message content, but the channel itself is plain HTTP. Only port 5986 is TLS. Teams that assume "5985 is encrypted" often skip basic network controls on it.

Where it fits in the attack chain

ATT&CK places WinRM under Lateral Movement, and that is where you will meet it. The attacker has already stolen credentials (Credential Access) and now needs to move. After WinRM takes them into servers, the same session usually serves Persistence (new accounts) and Collection (copying files). Treat one confirmed hostile WinRM session as a full intrusion, not a small event.

First response ideas

When an alert fires, do not reboot the server. Rebooting loses the live process evidence. First preserve the logs you have, then act:

powershell
# Who is remoting in right now, and since when?
Get-Process wsmprovhost -ErrorAction SilentlyContinue |
  Select-Object Id, StartTime, Path

# Last 20 script blocks that ran on this host
Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-PowerShell/Operational'; Id=4104} -MaxEvents 20

# Containment: end all remote PowerShell sessions
Stop-Process -Name wsmprovhost -Force

Stopping wsmprovhost kicks the visitor off immediately. It also kicks off any legitimate admin, so do it as a deliberate containment step, not as a reflex.

Where to look

  • Security log on servers: 4624 Type 3 logons from workstations, and 4625 failures right before them.
  • Microsoft-Windows-PowerShell/Operational on every server: event 4104 script blocks with -ComputerName or -enc, and event 4103 module logs as a backup.
  • Sysmon: event 1 for wsmprovhost and its children, event 3 for connections to 5985/5986, event 10 for LSASS access, event 13 for WinRM registry keys.
  • Microsoft-Windows-WinRM/Operational: listener changes and client connection errors.
  • Security log on domain controllers: 4720 account creation and 1102 log clearing.
  • Firewall or NetFlow: internal TCP 5985/5986 sessions that do not start from the management subnet.

Threat Intelligence

Threat intelligence (CTI) turns reports about attackers into detections you can run. The workflow has three steps. Collect: pull reports and indicators from sources you trust. Analyze: extract the behavior - which tools, which protocols, which events - and match it to ATT&CK techniques like T1021.006. Apply: turn that behavior into the Sigma rules, hunts, and hardening steps in this guide. Behavior outlives indicators: an attacker can change an IP address in seconds, but the way they move through a network changes slowly.

Where CTI teams get their data

  • MITRE ATT&CK - the technique page for T1021.006 lists groups and tools that use WinRM.
  • CISA and national CERT advisories - free reports with real attack details.
  • Vendor blogs - EDR and cloud vendors publish deep dives after big incidents.
  • MISP and AlienVault OTX - shared indicator feeds you can pull into your SIEM.
  • Commercial feeds - paid reports with actor tradecraft, useful for prioritization.

Hunting hypotheses

A hunting hypothesis is a question you ask your logs before any alert exists. Try these three against your own data:

  • Remoting where nobody remotes: wsmprovhost.exe running on machines that have no admin purpose - SQL servers, HR apps, print servers. Someone is using a trusted channel to reach them.
  • Sweeps from workstations: 4104 events containing -ComputerName that originate from user workstations instead of jump servers or automation hosts.
  • Encoded commands from service contexts: 4688 or 4104 events with -enc payloads running as WSMAN, SYSTEM, or within minutes of a Type 3 logon. Encoded commands from service accounts are rarely good news.

Logs & Patterns

Each threat above gets its own log pattern below. The samples are realistic Windows event XML and text. In your SIEM they arrive through the Windows event channel or Sysmon. Every sample ends with a short list of what to look for.

Threat 1 - Domain-wide remote execution with a stolen domain admin account

Use the Security log on every server. The arrival of a Type 3 logon from a workstation, for a domain admin, is the pattern. A WinRM logon shows AuthenticationPackageName Negotiate and the source address of the connecting machine.

Threat 2 - Remote LSASS memory dump via comsvcs.dll

Use Sysmon event 10 (process access) and event 1 (process creation). lsass.exe is the Windows process that holds logon material in memory. A read access of 0x1010 from rundll32 loading comsvcs.dll is a dump in progress.

Threat 6 - Account creation through a WinRM session

Use the Security log on servers and domain controllers. Event 4720 records the new account. On a domain controller, net user /add creates a domain account. On a member server it creates a local one. Both are persistence. What often follows is event 1102, the attacker clearing the log to hide the account. Clearing is itself recorded and cannot be undone.

xml
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>

Sigma Detection Rules

Sigma is a free, open format for writing detection rules once and running them in any SIEM. Each rule below matches one threat from the ranking. Under every rule you find the matching Splunk SPL query. SPL (Search Processing Language) is the search language used in Splunk. Adjust the index names to your own environment before you run them.

Rule 1 - WinRM remote PowerShell session on a non-jump host

Looks for wsmprovhost.exe, or anything it spawns, starting on a machine that is not an approved jump server. This is the core remote-session rule: one hit usually means someone is remoting in right now.

yaml — sigma
title: WinRM Remote PowerShell Session on Non-Jump Host
id: 2b1fa62f-7044-483a-a0ee-2f558df221a1
status: stable
description: >
  Detects wsmprovhost.exe, the process that hosts remote PowerShell commands,
  starting on a machine that is not an approved jump server. The rule also
  matches its children, because every remote command runs inside it. One hit
  outside the admin tier is the strongest single sign of WinRM lateral movement.
references:
  - https://attack.mitre.org/techniques/T1021/006/
author: Detection Engineering Team
date: 2026/09/29
tags:
  - attack.lateral_movement
  - attack.t1021.006
logsource:
  product: windows
  service: sysmon
detection:
  selection_session:
    EventID: 1
    Image|endswith: '\wsmprovhost.exe'
  selection_children:
    EventID: 1
    ParentImage|endswith: '\wsmprovhost.exe'
  filter_jump:
    Computer:
      - 'JUMP-SRV-01.corp.local'
      - 'JUMP-SRV-02.corp.local'
  condition: (selection_session or selection_children) and not filter_jump
falsepositives:
  - An approved jump server that is missing from the filter list
  - Management tools that use PowerShell remoting from a monitoring host
level: high

The SPL keeps both selections and removes the jump servers with a host filter. The stats line turns raw events into a per-user, per-host summary that is easy to triage.

spl — splunk
index=sysmon sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=1 (Image="*\\wsmprovhost.exe" OR ParentImage="*\\wsmprovhost.exe")
| search NOT host IN ("JUMP-SRV-01.corp.local", "JUMP-SRV-02.corp.local")
| stats count, dc(host) AS hosts BY user, host, Image
| sort - count

Rule 2 - Encoded PowerShell remote command

Watches PowerShell script block logging for encoded payloads. Event 4104 records decoded text, so this rule finds the encoding markers, and the 4104 content itself hands you the decoded payload. The 4688 command line field is a useful second source.

yaml — sigma
title: Encoded PowerShell Command via WinRM
id: 9abdd8d0-231c-446d-88ef-8f1a4213ae2c
status: stable
description: >
  Detects PowerShell script blocks that carry an encoded command, seen in
  event 4104 or on the command line in event 4688. Attackers encode payloads
  with -EncodedCommand or FromBase64String to hide them from plain-text rules.
  The 4104 event records the decoded content, so the rule leads straight to
  the payload.
references:
  - https://attack.mitre.org/techniques/T1021/006/
author: Detection Engineering Team
date: 2026/09/29
tags:
  - attack.lateral_movement
  - attack.execution
  - attack.t1021.006
  - attack.t1059.001
logsource:
  product: windows
  service: powershell
detection:
  selection_encoded:
    EventID: 4104
    ScriptBlockText|contains:
      - '-enc'
      - '-EncodedCommand'
      - 'FromBase64String'
  condition: selection_encoded
falsepositives:
  - Approved deployment scripts that encode long payloads on purpose
level: high

The SPL uses regex so it catches the short and the long spelling, then groups by host and user. If you also collect command line auditing, add a second search on event 4688 with the same regex.

spl — splunk
index=wineventlog sourcetype=WinEventLog:Microsoft-Windows-PowerShell/Operational EventCode=4104
| regex ScriptBlockText="(?i)(-enc\s|-EncodedCommand|FromBase64String)"
| stats count, dc(host) AS hosts BY host, user
| sort - count

Rule 3 - Remote LSASS dump via comsvcs.dll

Two independent signals in one rule: rundll32 loading comsvcs.dll with the MiniDump export, or any process opening lsass.exe with read access. Either signal alone is worth a page when the parent is a remote session.

yaml — sigma
title: LSASS Memory Dump via comsvcs.dll
id: f43f7746-7e02-4b48-a6af-2ca8aebeb034
status: stable
description: >
  Detects rundll32 loading comsvcs.dll with the MiniDump export against
  lsass.exe, or a process opening lsass with read access (Sysmon event 10,
  GrantedAccess 0x1010). Attackers favor this pair because rundll32 is signed
  and no dump tool ever lands on disk. Correlate with the WinRM session that
  carried the command.
references:
  - https://attack.mitre.org/techniques/T1021/006/
author: Detection Engineering Team
date: 2026/09/29
tags:
  - attack.credential_access
  - attack.lateral_movement
  - attack.t1021.006
  - attack.t1003.001
logsource:
  product: windows
  service: sysmon
detection:
  selection_rundll:
    EventID: 1
    Image|endswith: '\rundll32.exe'
    CommandLine|contains|all:
      - 'comsvcs'
      - 'MiniDump'
  selection_lsass_access:
    EventID: 10
    TargetImage|endswith: '\lsass.exe'
    GrantedAccess: '0x1010'
  condition: selection_rundll or selection_lsass_access
falsepositives:
  - Some backup and endpoint products read lsass memory for their own features
level: critical

The SPL joins both signals with an OR and uses a where clause so the rundll32 half really requires the MiniDump keyword, not just the DLL name.

spl — splunk
index=sysmon sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational (EventCode=1 Image="*\\rundll32.exe") OR (EventCode=10 TargetImage="*\\lsass.exe" GrantedAccess="0x1010")
| where (EventCode=1 AND match(CommandLine, "(?i)comsvcs") AND match(CommandLine, "(?i)MiniDump")) OR EventCode=10
| stats values(CommandLine) AS command, values(Image) AS image BY host, user, _time
| sort - _time

Rule 4 - Account created during a WinRM session

This is a near-correlation rule. It ties a 4720 account creation to a Type 3 logon on the same host within five minutes. Alone, neither event means much. Together they are the classic persistence move.

yaml — sigma
title: Account Created During WinRM Session
id: 20352119-244f-498d-8f4b-ea5112a47852
status: stable
description: >
  Detects a user account creation (event 4720) on a host that had a WinRM
  network logon (event 4624, Type 3, Negotiate) moments earlier. The near
  operator ties the two events together within the timeframe on the same
  machine. Attackers create accounts this way to keep access even after the
  stolen password is reset. On a domain controller the new account is a
  domain account; on member servers it is a local one.
references:
  - https://attack.mitre.org/techniques/T1021/006/
author: Detection Engineering Team
date: 2026/09/29
tags:
  - attack.lateral_movement
  - attack.persistence
  - attack.t1021.006
  - attack.t1136.001
logsource:
  product: windows
  service: security
detection:
  selection_4720:
    EventID: 4720
  selection_4624:
    EventID: 4624
    LogonType: 3
    AuthenticationPackageName: 'Negotiate'
  condition: selection_4720 | near selection_4624
  timeframe: 5m
falsepositives:
  - Planned account provisioning by IT during approved change windows
level: high

The SPL builds a transaction per host with a five minute span and keeps only groups that contain both event codes. On busy hosts, tighten it by adding the account name to both searches.

spl — splunk
index=wineventlog source="WinEventLog:Security" (EventCode=4720 OR (EventCode=4624 Logon_Type=3 AuthenticationPackageName="Negotiate"))
| transaction host maxspan=5m
| search EventCode=4720
| search EventCode=4624
| stats count BY host, TargetUserName, user
| sort - count

Rule 6 - Mass WinRM execution from one source

This is the network shape of a sweep: one machine opening WinRM connections to five or more targets inside ten minutes. Sysmon event 3 gives you the connections with source and destination.

yaml — sigma
title: Mass WinRM Network Connections from One Source
id: 3a5b7c0e-8945-489a-b581-c0360d775f1f
status: stable
description: >
  Detects one machine opening WinRM connections (TCP 5985 or 5986) to five or
  more different targets within ten minutes. This is the network shape of an
  Invoke-Command sweep across many servers. Check the source against the admin
  tier before you judge it, because patching tools also fan out.
references:
  - https://attack.mitre.org/techniques/T1021/006/
author: Detection Engineering Team
date: 2026/09/29
tags:
  - attack.lateral_movement
  - attack.t1021.006
logsource:
  product: windows
  service: sysmon
detection:
  selection:
    EventID: 3
    DestinationPort:
      - 5985
      - 5986
  condition: selection | count(dest) by SourceIp >= 5
  timeframe: 10m
falsepositives:
  - Patching, monitoring, and backup servers that legitimately use remoting
level: high

The SPL bins events into ten minute windows and counts distinct destinations per source. The last line applies the threshold, matching the Sigma condition.

spl — splunk
index=sysmon sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=3 (DestinationPort=5985 OR DestinationPort=5986)
| bin _time span=10m
| stats dc(DestinationIp) AS targets, count AS connections BY _time, SourceIp, host
| where targets >= 5
| sort - targets

Real-World Scenario

Twelve servers in four minutes - a night in the SOC.

This story is a realistic composite. The attack steps follow the official ATT&CK record for this technique. Wizard Spider, the group behind the Conti ransomware operation, has used WinRM to move laterally through victim networks. APT29 used WinRM via PowerShell during the SolarWinds Compromise. The company, the people, and the dates are invented. The attack steps are not.

Setting: A mid-size company runs a Windows estate with about 40 servers. WinRM is enabled on all of them, as it is on most Windows Server estates. PowerShell Remoting works from any machine to any server. There is one problem: tiering. Domain admins sometimes work from their normal laptops, so the admin tier leaks into the workstation network.

The timeline

NIGHT 1 — 22:40
One phishing email, one stolen password

An accountant opens a fake invoice page and types her password. The criminals use the session to reach her laptop and run a credential dump. At 22:52 they hold the password of CORP\admin_mike, a domain admin who had logged into that laptop the week before. WinRM was never the first step. Stolen credentials were.

NIGHT 1 — 01:58
Who is listening on 5985?

From the owned workstation WS-A, the attacker runs Test-WSMan against a list of servers. APP-SRV-02 answers, like every other server in the estate. The only trace is a handful of Sysmon 3 network events to port 5985 from a workstation. Nobody is watching that pattern yet.

NIGHT 1 — 02:05
A remote PowerShell opens

Enter-PSSession signs the attacker into APP-SRV-02 as admin_mike. The server records a Type 3 logon and starts wsmprovhost.exe. No window appears on any screen. The attacker is now standing inside a server using only built-in tools.

NIGHT 1 — 02:06
The four-minute sweep

One Invoke-Command line lists twelve servers. The command dumps LSASS memory with rundll32 and comsvcs.dll on each one and stages the results. It takes four minutes. On most of the twelve servers, the only sign is a short burst of process and network events in the middle of the night.

NIGHT 1 — 02:07
The first alert fires

EDR on APP-SRV-02 flags "LSASS dump via comsvcs.dll" and blocks the write. The alert lands in the SOC queue. The analyst on duty starts reading. On nine of the other eleven servers the same attempt succeeds, because their EDR policy is older. On the last two, the EDR blocks it as well.

NIGHT 1 — 02:12
A backdoor account on the domain controller

From APP-SRV-02 the attacker runs Invoke-Command against DC01 and creates the account backup_svc. Event 4720 records it. The stolen password now has a second way back in.

NIGHT 1 — 02:19
Erasing the trail

wevtutil cl Security wipes the Security log on DC01. Event 1102 records the clearing itself. On a domain controller at 2 a.m., that event is an automatic page. The SOC now has two critical alerts pointing at the same account.

NIGHT 1 — 02:24
The pattern gives it away

The SIEM rule "wsmprovhost on a non-jump host" fires for the sixth time that night, and the EDR blocks a second dump attempt on another server. The on-call responder correlates the alerts: one workstation, one admin account, twelve servers, four minutes. This is lateral movement. The incident bridge opens at 02:31.

NIGHT 1 — 02:40
Containment

The team disables backup_svc and admin_mike, stops all wsmprovhost processes across the estate, and isolates the nine hosts that show LSASS access. Kerberos tickets for the account stop working within minutes, because the password is reset. The attacker retries twice from WS-A and fails both times.

DAY 2 - DAY 3
Recovery and rebuild

The team rebuilds two hosts from clean images because their EDR policy was outdated. It resets every admin password, including the domain admin tier. It also removes the WinRM path from workstations to servers. They verify no persistence: no new scheduled tasks, no new services, no unexpected accounts. The estate returns to normal after 36 hours.

The attack chain

1. Stolen DA password→ 2. Test-WSMan probe→ 3. Enter-PSSession→ 4. Invoke-Command sweep, 12 servers→ 5. LSASS dumps→ 6. Account on DC01→ 7. Log clearing→ 8. Detected and contained

What contained it

  • EDR blocking the comsvcs.dll dump at 02:07 and again at 02:24.
  • The SIEM rule that treats wsmprovhost on a non-jump server as a page.
  • Event 1102 on the domain controller, which no attacker can suppress.
  • Fast account disable and password reset, which killed the stolen ticket.

What made it possible

  • Domain admin credentials used on a workstation, so they leaked into memory there.
  • WinRM reachable from any internal machine to any server on port 5985.
  • No JEA, so a stolen admin password meant full control everywhere.
  • Uneven EDR coverage: 9 servers still ran an old policy, and 9 dumps succeeded.

Consequences: No ransomware deployed and no data left the network, so the business avoided the worst case. The costs were still real: two rebuilt servers, a full admin password rotation, two days of overtime for the SOC, and a week of extra change freezes. The lasting change was governance: PowerShell Remoting became a managed service with a defined admin tier, instead of a feature that was simply on.

  • An app owners list was ready in advance, so every touched server had a human to call within the hour.

  • One written containment decision log captured who approved each isolation and reset, which later made the report and the insurance claim easy.

Mitigation & Defense

Make WinRM a narrow, logged, tiered service instead of an open door.

You do not have to break WinRM. Admins and automation genuinely need it. The goal is to shrink it: fewer machines listen, fewer machines may connect, every session is logged, and every session is checked against rules. The table below orders the work by what it stops.

Official MITRE mitigations: The ATT&CK page for T1021.006 lists three mitigations. M1042 - Disable or Remove Feature or Program: disable the WinRM service where nothing needs it. M1030 - Network Segmentation: where WinRM must stay, lock critical zones behind their own WinRM infrastructure and host firewall rules that only allow management hosts. M1026 - Privileged Account Management: use separate WinRM accounts and permissions for those zones. The priority table below puts these three into practice.

Priority actions for enterprise

ActionStops whatEffort
Disable WinRM on workstations via GPOWorkstations becoming remoting hops, like WS-A in the scenario.Low
Firewall TCP 5985/5986 to the management subnet onlySweeps from user networks. The four-minute sweep dies at the first hop.Low
PowerShell script block logging + transcription org-wideInvisible commands. Every remote command leaves decoded text.Low
Deploy the monitoring rules from section 4Non-jump wsmprovhost, encoded commands, sweeps, backdoor accounts.Low
EDR behavioral blocks for LSASS accesscomsvcs.dll dumps, even when the command arrives over WinRM.Low

Turn on the PowerShell evidence with GPO or registry

Script block logging writes the decoded text of every PowerShell command into event 4104. Transcription saves a full session transcript to a file share. Push both to servers and workstations with GPO, or set the registry keys directly:

cmd
:: Enable script block logging (fills event 4104)
reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging" /v EnableScriptBlockLogging /t REG_DWORD /d 1 /f

:: Enable transcription to a central share (keeps a session record)
reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows\PowerShell\Transcription" /v EnableTranscripting /t REG_DWORD /d 1 /f
reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows\PowerShell\Transcription" /v OutputDirectory /t REG_EXPAND_SZ /d \\fileserver\pslogs /f
reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows\PowerShell\Transcription" /v EnableInvocationHeader /t REG_DWORD /d 1 /f

Harden the listener itself

On servers that must keep WinRM, move the listener to HTTPS and keep the service config strict. Run winrm quickconfig first if the listener is missing, then create the HTTPS listener with a real certificate:

cmd
:: One-time setup (as admin): enable WinRM with defaults
winrm quickconfig

:: Replace the plain HTTP listener with an HTTPS one
winrm delete winrm/config/Listener?Address=*+Transport=HTTP
winrm create winrm/config/Listener?Address=*+Transport=HTTPS @{Hostname="APP-SRV-02"; CertificateThumbprint="AA11BB22CC33DD44"}

:: Keep encryption on and restart the service
winrm set winrm/config/service @{AllowUnencrypted="false"}
net stop winrm && net start winrm

:: Then restrict who may connect: firewall 5986 to the management subnet only
Tip: Before deleting the HTTP listener, check what still uses it. Run your patch and monitoring teams through the change first, or their jobs will fail on Monday morning.

Defense in layers

1. Tiered admin→ 2. Jump servers only→ 3. HTTPS 5986, firewall scoped→ 4. JEA roles→ 5. Logging everywhere→ 6. EDR blocks→ 7. SIEM rules page a human

Each layer alone can fail. Together they turn a four-minute sweep into a short, loud, contained event.

For home users

Home Windows machines rarely need WinRM at all. Leave it off. It is off by default on client Windows, so the rule is simple: do not run winrm quickconfig, and check that no listener exists. To check, open a Command Prompt and run:

cmd
winrm enumerate winrm/config/listener

If the command reports no listener, or fails because the WinRM service is stopped, you are in the default safe state. If a listener answers on your home PC and you did not create one, remove it and scan for malware. Keep Windows Update on, because the service is patched through the same channel as everything else.

Common Mistakes & Best Practices

Nine traps detection teams fall into with WinRM - and the way out of each one.

Most WinRM detection failures are not exotic. They are the same handful of mistakes, repeated across teams. Read the table before you write your first rule, and it will save you a week of tuning.

Common mistakes and their fixes

MistakeWhy it hurtsThe fix
Assuming port 5985 is encrypted with TLSTeams leave 5985 open everywhere because they believe it is HTTPS. It is plain HTTP with Windows authentication.Remember: only 5986 is TLS. Move listeners to 5986 and firewall 5985 to the management subnet.
Not collecting PowerShell Operational or 4104 on serversWithout script block logging you see that a session happened, but never what ran inside it.Push script block logging with GPO to every Windows machine. It is one registry key and nearly free.
Ignoring wsmprovhost.exe because it is a Microsoft binaryBeing signed is the point: it lets the attacker hide inside trusted tooling.Alert on wsmprovhost.exe outside jump servers, and on everything it spawns.
No baseline of normal PowerShell remotingReal admin work and an attack look identical on a single event, so alerts either spam or get ignored.Build an allow list of jump servers, automation accounts, and patch windows. Alert on everything outside it.
Only watching the Security logThe Security log shows the logon, but the best signals live in Sysmon and PowerShell logs.Collect Sysmon 1, 3, 10, and 13 plus PowerShell 4104 from every server.
Forgetting attackers who come from LinuxTools like evil-winrm and netexec leave no Windows events on the attacker side, so teams miss them completely.Lean on target-side telemetry and network monitoring of 5985/5986 flows.
No JEA, so one account controls everythingA stolen domain admin password becomes full remote control of the whole estate in minutes.Use Just Enough Administration roles so each admin only gets the commands their job needs.
Static thresholds that never changeA threshold of five connections is either bypassed by slow sweeps or floods you during patch night.Tune per asset group, review quarterly, and let the allow list do the heavy lifting.
Trusting the source IP on its ownAttackers pivot through owned servers, so the "source" is often just another victim.Correlate the 4624 source with Sysmon 3 flows and the wsmprovhost process chain before you judge.

Best practices for day-to-day detection work

  • Treat a WinRM session like a visit: who logged in (4624 Type 3), from where, and what did they run (4104).
  • Keep the jump server allow list short, reviewed, and owned by a named person.
  • Decode every -EncodedCommand payload you find and turn its text into new detection content.
  • Page instantly on 1102 from a domain controller. Log clearing is never routine.
  • Test your rules monthly with a safe lab: one client, one server, one legitimate session, one hostile session.
  • Watch the negative space too: servers that normally see no remoting but suddenly do.
  • Track listener inventory with the Sysmon 13 rule, so new or changed listeners are noticed.
  • Write your findings back to CTI: which actor tradecraft your rules caught, and which gaps remain.
  • Rehearse containment: disabling the account, stopping wsmprovhost, and isolating hosts should be muscle memory.
Remember: WinRM attacks are built entirely from normal admin actions. Your advantage is not a magic signature. It is collection, baselining, and correlation - knowing what normal looks like, and paging when the shape breaks.
