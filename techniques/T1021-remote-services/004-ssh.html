Secure Shell (SSH)

SSH (Secure Shell) is the standard way to open an encrypted text terminal on another machine. Attackers love it because one stolen key file can open many servers, quietly, with no password guessing and no exploit. It also runs on ESXi hosts (VMware servers that hold many virtual machines), where attackers sometimes switch the SSH service on.

Written for beginners, SOC analysts, and detection engineers. All examples are for learning and defense only.

Red Team Perspective

Why a plain text-login protocol is one of the best doors in the building.

Red teams use SSH for the same reason administrators do: it is already there, it is trusted, and it works everywhere on Linux, macOS, and in the cloud. This section explains the parts of SSH that matter for attacks, where the valuable files are, and what a real intrusion looks like step by step.

What SSH is, in plain words

SSH is a program and a protocol that opens a safe, encrypted text terminal on another machine. You type ssh user@server, and your keyboard connects to a shell (a command line) on that server. Most Linux servers, network devices, and cloud virtual machines run an SSH server on port 22 by default. macOS has SSH built in too, but it stays off until someone turns it on.

Instead of passwords, SSH normally uses a key pair. The private key is a secret file that stays on the user's machine. The public key is a small text line that sits on the server, inside the file ~/.ssh/authorized_keys. The math links the two parts, so the server can check that you hold the private key without ever seeing it. The result is simple: whoever has the private key file can log in as that user, from anywhere, with no password.

Agent forwarding adds a twist. The ssh-agent is a small helper program that keeps unlocked private keys in memory. With ssh -A, the next server may "borrow" your agent and use those keys to hop one step further. That is convenient for admins, but it also means anyone controlling the middle server can use your keys while your session is open.

TermPlain meaning
Port 22The network door SSH listens on. If it is reachable, the attacker can try to log in.

Why attackers love SSH

  • It is everywhere. Linux servers, routers, and cloud VMs usually ship with SSH already on. No install needed.
  • Keys need no guessing. A stolen key logs in on the first try. There are no lockouts and no failed-login noise.
  • Tunnels hide traffic. An SSH tunnel is normal encrypted admin traffic to most network tools.
  • Cloud VMs all have it. SSH is the default management door into cloud compute instances.
  • ESXi hosts can open it. ESXi is the VMware software that runs many virtual machines on one server. Its SSH service is normally off, and attackers sometimes switch it on to reach the whole host.
  • One key, many doors. Developers and CI/CD (Continuous Integration / Continuous Delivery) systems often hold keys that open dev, build, and production.
  • Agent forwarding chains trust. One key on one host can reach hosts that never faced the attacker.
Why this matters: T1021.004 sits in the Lateral Movement tactic. Attackers rarely attack SSH from the internet first. They get one machine, steal its keys, and then use SSH to travel.

Where SSH keys hide on a machine

An attacker who lands on any Linux or macOS box looks at ~/.ssh first. This folder is the treasure chest of the account.

Tip: Keys without a passphrase (a password that protects the key file) can be used the moment they are stolen. Keys with a passphrase still leak the public part and the server list.

What an attacker needs (prerequisites)

  • A valid private key, or a working username and password on servers that still allow password login.
  • A valid account name — the key must be listed in that account's authorized_keys.
  • Network reachability to port 22 on the target, directly or through a bastion (a guarded jump server).
  • Optional: agent forwarding on a middle host, or a ~/.ssh/config file that reveals the next hop.

Notice what is missing: no exploit, no crash, no error message. If the key file is readable, the login is a normal, allowed action. That is what makes this technique so quiet.

How it looks in a lab (safe commands)

These commands show the normal SSH workflow on your own lab machines. They are also exactly the commands an attacker runs after stealing a key, which is why watching for their side effects matters.

bash
# --- LAB ONLY: run these on machines you own ---

# 1. Log in as the deploy user with a specific key file
ssh -i ~/.ssh/lab_key deploy@10.2.10.15

# 2. Check which account you got and where you are
id && hostname

# 3. Add a lab key to a TEST account (this is the backdoor
#    move that defenders must alert on)
echo "$(cat ~/.ssh/lab_key.pub)" >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys

# The admin way to add a key is ssh-copy-id. It also fixes
# file permissions. Attackers skip it and append directly.
ssh-copy-id -i ~/.ssh/lab_key.pub deploy@10.2.10.15

# 4. Local forward: localhost:8443 reaches DB port 5432
ssh -L 8443:10.2.10.30:5432 deploy@10.2.10.15

# 5. Copy a file out with scp
scp -i ~/.ssh/lab_key deploy@10.2.10.15:/tmp/report.txt ./
Watch out: On a real intrusion, step 3 (a new line in authorized_keys) means persistence. Even if you reset the user's password or remove the stolen key, the attacker keeps their own way in.

Common tools

ToolWhat it does in an attack
sshThe client itself. Flags do the work: -i picks a key and -A forwards the agent. -L forwards a local port to a remote service, -R does the reverse. -D opens a SOCKS proxy, a proxy that can carry any program's traffic.
scp / sftpCopy files over the encrypted SSH channel, in or out.
nmapFinds port 22 and reads the SSH banner with the server version.
hydraGuesses passwords fast on servers that still allow password login.
sshuttleRoutes whole subnets through one SSH connection. One stolen key becomes a cheap VPN.
chiselBuilds reverse tunnels that carry attacker tools through firewalls.

Operationally, attackers keep SSH use slow and boring: one login, a few commands, then sleep. Noise comes from volume, not from any single action. A scan of port 22 or a burst of logins from one source is what finally gives them away.

Ethics: Only test systems you own or have written permission to test. Reading other people's key files, logging into servers without approval, or adding keys to accounts is a crime in most countries, even "just to see if it works". Use a small lab of your own virtual machines.

Blue Team / SOC Perspective

What a completely normal-looking login can hide.

SSH leaves small, clean logs. A successful key login is one line that looks like every other admin login. The SOC (Security Operations Center, the team that watches alerts) wins by joining many small facts: the source subnet, the account, the fingerprint of the key, and writes to .ssh files. In the attack chain, this technique sits in the middle: the attacker already holds one machine, and SSH is how they reach the next ones.

Which artifacts SSH activity leaves behind

ArtifactWhere you find itWhat it tells you
Accepted publickey for USER from IP port N ssh2: ED25519 SHA256:.../var/log/auth.log (Debian, Ubuntu) or /var/log/secure (RHEL, Fedora, SUSE)A key login succeeded, with source IP, account, and (with VERBOSE logging) the key fingerprint.

Why VERBOSE matters: With LogLevel VERBOSE in the SSH server config, every key login logs the fingerprint (a short hash of the public key). Without it, you know only that a key logged in — not which key. Fingerprints are what let you find one key on many hosts.

Where to look first

  • Jump hosts and bastions first. Every production SSH session should pass through them. A key login to production that does not come from a bastion is your highest-value signal.
  • CI/CD runners and build servers. They hold deploy keys with wide reach. TeamTNT-style crews hunt them because one runner often touches many environments.
  • Developer laptops (macOS included). macOS keeps the same ~/.ssh layout. A key read by a browser helper or a fake updater is theft, not development.
  • Cloud instances and their metadata. An attacker with code on a VM can query the cloud metadata service and sometimes mint temporary credentials or keys, then SSH with them. Watch for sessions that start from an internal instance instead of a bastion.
  • ESXi hosts. Their SSH service is normally off. Treat the service being enabled, or any new SSH login to a host, as a high-value signal.
  • Database and file servers. The final stop of most SSH attack chains. Direct SSH from app servers to them is often legitimate — check the account and time, not only the path.

What to look for — quick checklist

  • Public key logins into production from workstation subnets, cloud ranges, or any source that is not a bastion.
  • Writes or appends to any authorized_keys file that did not come from your configuration management tool.
  • The same key fingerprint appearing on several servers within a day.
  • Private key files read by processes that are not ssh, git, or the user's normal tools.
  • ssh processes started with -D, -R, -L, or -w flags on servers.
  • SSH connections in unusual directions, for example database server back to a workstation.
  • Large data volume over port 22, especially outbound from production.
  • Failed password bursts against exposed servers (port 22 open to the internet).
  • Direct root logins accepted over SSH, which your baseline should forbid.
  • New cron jobs, systemd services, or startup scripts created soon after an SSH login.
First response: If you suspect a stolen SSH key, do not only kill the session. Kill the session, remove unknown lines from authorized_keys, rotate the key, and search your whole estate for that key's fingerprint — on servers, runners, and in code repositories. Sessions end; keys stay valid until you revoke them.

Threat Intelligence

Cyber threat intelligence (CTI) turns reports about attackers into detection ideas. The workflow is simple: collect reports from sources, analyze which behaviors apply to your estate, and apply them as hunts and rules. Good free sources for SSH abuse are MITRE ATT&CK, the technique catalog this guide follows. Others are CISA advisories, vendor threat blogs, and community feeds such as MISP and OTX. Those feeds share attacker IP lists and malware samples.

  • Collect: save reports about Linux and cloud intrusions. Note the exact commands and log lines.
  • Analyze: mark which steps touch SSH: key theft, brute force, tunnels, authorized_keys edits.
  • Apply: turn each step into a hunt query, then into a Sigma rule with a named owner.
  • Review: every quarter, check which rules fired and which actors shifted tools.

Hunting hypotheses to run this month

  • Hypothesis 1: a public key login reaches a production server from a workstation subnet. Search: Accepted publickey where src_ip is inside office or VPN user ranges and dest is in production.
  • Hypothesis 2: an authorized_keys file changed outside config management. Search auditd watches for writes, then join with change tickets.
  • Hypothesis 3: the same key fingerprint logs into many hosts. With LogLevel VERBOSE, count distinct dest per SHA256: fingerprint over 24 hours.

Each threat below lists the logs to use, a realistic sample, and the exact things to look for. Field names differ by log shipper, but the raw lines are what the host really writes.

Threat 1 — Stolen SSH key used for production access

Logs: auth.log or /var/log/secure on the production server, plus SIEM joins against a list of bastion IPs and workstation subnets. This is the single most important SSH line to ship centrally.

log — /var/log/auth.log
Oct 14 08:11:03 prod-app-01 sshd[24112]: Accepted publickey for deploy from 10.2.5.20 port 53214 ssh2: ED25519 SHA256:AbCdEf1234567890QRSTUVWXyz0123456789abcDEFg
Oct 14 08:11:04 prod-app-01 sshd[24112]: pam_unix(sshd:session): session opened for user deploy(uid=1000) by (uid=0)
Oct 14 08:11:09 prod-app-01 sudo:   deploy : TTY=pts/1 ; PWD=/home/deploy ; USER=root ; COMMAND=/bin/su
  • Accepted publickey where the source is a workstation, VPN user range, or cloud IP instead of a bastion.
  • Service and deploy accounts logging in interactively — they should come from pipelines, not people.
  • A key fingerprint that has never been seen for this account before.
  • Login at hours or from subnets the account never used before.

Threat 2 — ESXi / Linux ransomware reached over SSH

Logs: auditd EXECVE records on the target, auth.log for the entry login, and EDR process events. Ransomware crews often use plain SSH with stolen or bought keys, then run an encryption script from the shell. On ESXi, the SSH service ships off, so its use at all is already a signal.

Threat 3 — SSH brute force on exposed port 22

Logs: auth.log lines Failed password, Invalid user, and Too many authentication failures. Aggregate by source IP; single lines are harmless-looking.

Oct 14 03:12:40 prod-app-01 sshd[9033]: Failed password for root from 203.0.113.9 port 41230 ssh2
Oct 14 03:12:44 prod-app-01 sshd[9038]: Failed password for invalid user admin from 203.0.113.9 port 41244 ssh2
Oct 14 03:12:48 prod-app-01 sshd[9041]: Failed password for invalid user oracle from 203.0.113.9 port 41258 ssh2

  • A success from the same source shortly after failures (the real danger moment).
  • Port 22 reachable from the internet at all — fix the exposure, not just the alert.

Threat 8 — Dev and CI/CD misconfigurations (false positives)

Logs: auditd and EDR will happily flag pipelines. Examples: a deploy job appending its own key, a runner opening agent sockets, or Ansible rewriting authorized_keys on every run. Filter these with identities, not by turning rules off.

Sigma Detection Rules

Each rule below matches one threat from the ranking. Under every rule you find the matching Splunk SPL query. Start with the auth.log shipper on all Linux servers, and deploy the auditd watches the rules need: auditctl -w /home -p wa -k authkey-watch (scoped per home), auditctl -w /etc/ssh/sshd_config -p wa -k sshd-config-watch, and an execve rule with key exec-watch.

Rule 1 — SSH public key login from an unusual source subnet

Catches a successful key login that does not come from your bastions or admin subnets. This is the core "stolen key" rule, and it is the rule that would have caught the simulation at step 3.

Real-World Scenario

The build farm key theft — a realistic composite based on the documented TeamTNT and WatchDog cloud attacks.

This story is a realistic composite. The attacker behavior follows the publicly documented 2020–2021 TeamTNT and WatchDog campaigns. Those crews scanned for exposed Docker and SSH services, brute-forced credentials, stole cloud and SSH keys, installed coin miners, and added their own authorized_keys entries for persistence. We adapt that playbook to an enterprise with a CI/CD build farm, because that is where the same moves hurt most.

The setting

A mid-size company runs a build farm: eight Linux runners called CI-CD-01 to CI-CD-08. The runners deploy to production with a shared deploy SSH key. The key has no passphrase. The Docker API on one runner is bound to 0.0.0.0:2375 after a misapplied config change — no authentication at all. Production servers trust logins from the runner subnet.

1. Exposed Docker API → 2. Keys read on runner → 3. SSH into production → 4. Backdoor key + agent hijack → 5. Tunnel and exfiltrate → 6. Caught by joined signals
DAY 1 — 03:12
The exposed Docker API is found

An automated crawler finds port 2375 open on CI-CD-03. The attacker starts a privileged container on the runner and escapes to the host shell, exactly the pattern TeamTNT used against cloud hosts. There is no login event, because the Docker API needs none.

DAY 1 — 03:40
The build user's keys are read

The attacker reads /home/build/.ssh: an id_ed25519 key with no passphrase, a config file that lists prod-app-01 and prod-db-01, and the runner's environment variables with a cloud storage token. They copy everything and install a small miner to keep the host busy while they work.

DAY 1 — 08:11
First SSH hop into production

The attacker logs in as deploy on PROD-APP-01 with the stolen key. auth.log records a clean Accepted publickey line from the runner subnet. The SOC has no rule for that source. The attacker checks sudo -l, reads sshd_config, and maps the network.

DAY 1 — 09:05
The backdoor key goes in

The attacker appends their own public key to /home/deploy/.ssh/authorized_keys. Even if the stolen key is rotated later, this new key keeps working. The runner keeps deploying all day; nobody reads the file.

DAY 2 — 10:26
Agent hijack reaches the database

From PROD-APP-01, the attacker finds the agent socket that a DBA's morning session left behind, because the DBA logged in with ssh -A. They run SSH_AUTH_SOCK=/tmp/ssh-4gXk2/agent.4121 ssh dbadmin@10.2.10.30. The live agent signs the way into PROD-DB-01, and no key file is needed. A psql session opens, and the customer table (2.4 million rows) is counted, sampled, and dumped to /tmp.

DAY 2 — 14:03
The tunnel starts

Backups and the staged dump are packed with tar and pushed over SSH to the compromised runner: 1.8 GB on the wire. To the network team it looks like a big admin copy. The miner on the runner hides inside normal CPU load.

DAY 2 — 14:26
Detection fires

Two alerts land in the same minute. The EDR flags authorized_keys modified on PROD-APP-01. The SIEM rule publickey from workstation-style subnet to prod flags the Day 1 login, and a fan-out rule counts one key reaching two production hosts. The on-call analyst opens a war room channel.

DAY 2 — 14:50
Containment

The firewall cuts the runner subnet from production. All deploy and dbadmin sessions are killed. The backdoor key is removed from every authorized_keys file, the stolen key is revoked, and the build farm is rebuilt from clean images.

DAY 3 — 10:00
Recovery and hardening

Deploy keys are replaced with short-lived SSH certificates issued per job. Agent forwarding is disabled server-side. Auditd watches cover authorized_keys and sshd_config. A canary key (a fake key that should never be used) is placed on every production server.

Consequences and lessons

The company ran a full key hygiene audit: 41 unknown keys were found on 60 servers, most from staff who left years ago. Short-lived SSH certificates replaced static keys for humans and pipelines. The miner on the runner was removed, and the exposed Docker API incident became a change-management case study.

LessonWhat it means in practice
Keys need passphrases and rotationA passphrase turns a stolen file into a dead file. Rotation caps how long any leak stays useful.
Agent forwarding off by defaultSet AllowAgentForwarding no on servers. Enable it only for documented admin paths.
Bastion plus just-in-time accessProduction SSH only through audited jump hosts, with access granted per request, per hour.

How the team communicated

  • Joint channel: the app team and security shared one war room channel, so deploy freezes and evidence requests never collided.
  • Clear roles: security hunted and contained; platform staff rotated keys and rebuilt runners; nobody did both.
  • Daily exec notes: five lines every morning: what happened, what is contained, what is next, what is needed, what customers must hear.
  • Single fact source: one running incident document. Screenshots and log excerpts went there, not into chat scroll.
Why this matters: The 35-hour dwell time shrank because two separate signals — a file write and a login pattern — were joined early by people who talked to each other.

Mitigation & Defense

Make keys short-lived, servers picky, and every login visible.

SSH hardening is mostly configuration, not budget. The table below orders the actions by what they stop. Then you get a ready-to-copy sshd_config baseline and a short version for home users.

Enterprise priority table

ActionStops whatEffort
SSH certificates with short lifetimes, issued by an internal CAStolen long-lived keys — a leaked key dies within hoursMedium
Passphrases on all key files, hardware keys (FIDO2) for adminsKey theft from laptops and runnersLow
PermitRootLogin no and named AllowGroupsDirect root entry and account guessingLow
PasswordAuthentication no on all serversBrute force and password spraying completelyLow
SSH service off where it is not needed (ESXi hosts, macOS Remote Login)Attacker-enabled SSH on hypervisors and laptopsLow
AllowAgentForwarding no except documented admin hostsAgent-forwarding hijack between hopsLow

Official MITRE mitigations: ATT&CK lists three mitigations for this technique. M1042 (Disable or Remove Feature or Program): turn SSH off where it is not needed, especially on ESXi hosts. M1032 (Multi-factor Authentication): protect SSH with a second factor, such as passphrase-protected keys. M1018 (User Account Management): limit which accounts may log in over SSH. The priority table above maps to all three.

Hardened sshd_config baseline

Apply this to servers, then test with sshd -t before restarting the service. The LogLevel VERBOSE line matters most for detection: it makes sshd log the key fingerprint of every public key login, which powers the fan-out and key-tracking rules.

bash — /etc/ssh/sshd_config
# Hardened baseline — test with `sshd -t`, then reload sshd
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
AllowGroups ssh-users deploy-admins
AllowAgentForwarding no          # kills agent-forwarding hijacks
AllowTcpForwarding no            # set to yes ONLY where tunnels are really needed
X11Forwarding no
ClientAliveInterval 300
ClientAliveCountMax 2
LoginGraceTime 30
MaxAuthTries 3
LogLevel VERBOSE                 # logs SHA256 key fingerprints of every publickey login
Watch out: AllowTcpForwarding no breaks tools that legally use tunnels. Keep an exception list of hosts, and make the exceptions loud — monitored, documented, and few.
Tip: Pair this file with an auditd watch (Rule 6) so any change to it fires an alert. A hardened config that can be silently rewritten is not hardened.

For home users

  • Do not expose port 22 to the internet. Use a VPN to reach home machines, or leave SSH inside the LAN only.
  • Use keys, not passwords, and give every key a passphrase. Generate with ssh-keygen -t ed25519.
  • Install fail2ban (or enable rate limiting) so scanners get locked out automatically.
  • Keep the system updated — SSH server bugs are patched regularly, and old versions are scanned for.
  • Check your router firewall twice a year: no port 22, 23, 3389, or admin panels open to the internet.

Defense in layers

1. Prevent: certificates, no root, no passwords → 2. Contain: bastion, segmentation, no forwarding → 3. Detect: auditd watches, VERBOSE fingerprints, Sigma rules → 4. Respond: revoke keys, kill sessions, search fingerprints

No single layer is strong enough alone. The prevention layers fail quietly. A laptop is lost, a runner is exposed. The detection layers turn that failure into a one-day incident instead of a one-month one.

Common Mistakes & Best Practices

Nine habits that make SSH attacks invisible — and how to drop each one.

Most missed SSH attacks are not tooling failures. They are habits: logs that never leave the host, rules tuned to silence, and the comfortable feeling that SSH is "safe because it is encrypted". Check your own team against this table.

Common mistakes and their fixes

MistakeWhy it hurtsFix
Logs rotate on the host and are never shippedauth.log holds 7 days of evidence and then deletes itShip auth.log, audit.log, and Sysmon for Linux to a SIEM with 90+ day retention
Only watching auth.log on app serversThe attack story lives on jump hosts, runners, and database serversCover every Linux and macOS host, and make bastions the loudest source
Treating SSH as "safe, so unmonitored"Encrypted is not trusted; SSH is the attacker's favorite vehicleMonitor SSH harder than most protocols — it is the path to privilege
Ignoring authorized_keys writesOne appended line is permanent, silent accessAuditd watch on all .ssh paths plus Rule 3, paging-level severity
No key inventoryNobody knows which keys exist or who owns themInventory owner, purpose, fingerprint, and rotation date; review quarterly
Missing tunnel detectionExfiltration rides inside "normal" SSHAlert on -D/-R/-L/-w flags and on gigabyte-scale flows over port 22
LogLevel INFO everywhereNo fingerprints, so one key cannot be tracked across hostsSet LogLevel VERBOSE fleet-wide; index the SHA256 fingerprints
Static thresholds everywhereCI accounts blow past limits daily; real attacks move slowerBaseline per account type, alert on deviation, review thresholds quarterly
Forgetting macOSDeveloper laptops hold the richest .ssh foldersShip macOS logs (including EDR) and watch key file reads there too

Best practices for detection engineers

  • Ship auth.log / secure, auditd, and Sysmon for Linux from every server, and keep the raw lines searchable.
  • Turn on LogLevel VERBOSE so key fingerprints are logged, then build rules on fingerprints, not just usernames.
  • Keep an always-fresh list of bastion IPs, runner accounts, and config management tools for rule filters.
  • Alert page-level on authorized_keys writes and publickey logins from non-bastion sources into production.
  • Test every Sigma rule against replayed log samples — the ones in this guide are a good start.
  • Watch direction and volume, not just events: SSH from a database server to a workstation is a story.
  • Place canary keys on production servers and alert on any use. It should never fire falsely.
  • Join SSH telemetry with change tickets so pipeline noise has a reason and a name.
  • Rotate stolen or exposed keys immediately, then search the estate for their fingerprints.
  • Rehearse the scenario in section 5 once a year as a tabletop exercise with the platform team.
Closing thought: T1021.004 is the quietest lateral movement technique on Linux and macOS. You will not catch it with antivirus or with a failed-login dashboard. You catch it by knowing which keys exist, which sources may log in where, and by making every key file write and every unusual source a small, loud event.
