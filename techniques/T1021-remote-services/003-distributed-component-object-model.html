Distributed Component Object Model (DCOM)

DCOM is a built-in Windows feature. It lets a program on one computer start and use an object inside a program on another computer over the network. Attackers use it to run commands on a remote machine with plain PowerShell — no hacking tools, no files dropped, and only valid credentials needed.

Written for beginners, SOC analysts, and detection engineers. Every example here is for learning and defense only. This guide shows the attack steps, the logs the attack leaves behind, and how to catch it.

In this story, an attacker has already taken over one workstation (WS-A) and stolen the password of CORP\svc_admin, an account that is a local administrator on another workstation (WS-B) and on an app server (APP01). The attacker never installs a tool. They only type PowerShell. First they create a MMC20.Application COM object on WS-B and run a command through it. What to notice

Notice the footprints that never go away. Every DCOM activation creates a 4624 logon with Type 3 (a network logon, no one at the keyboard). Red Team Perspective

Why attackers use DCOM — and how a few lines of built-in PowerShell can replace a whole toolkit.

This section explains the attacker's view. Knowing how attackers work is the first step to stopping them. Everything here is public knowledge, written for defenders and students.

Ethics first: You must never try these actions against computers you do not own or do not have written permission to test. Running commands on someone else's computer without approval is a crime in almost every country. Red teams work under strict written rules.

What is COM, in simple words?

COM (Component Object Model) is a very old Windows system for reusable software building blocks. Think of it like this: a big program is built from many small parts. Each part is a COM object, and each object has a name (for example MMC20.Application) and a list of things it can do. Any program can ask Windows: "please give me the object called X and let me press its buttons". The buttons are called methods. This is why Windows programs can share features — one team writes the spell-checker, another team uses it.

What is DCOM, then?

DCOM is COM plus the word Distributed. It means the object does not have to live on the same computer as the program that uses it. PowerShell on computer A can create an object that lives inside a program on computer B, and press its buttons from far away. The traffic between the two computers is RPC (Remote Procedure Call) — a protocol whose whole job is "please run this small piece of code for me and send back the answer".

The connection works in two stages, and this detail matters for defenders:

  • Stage 1 — the receptionist. The client first talks to the RPC endpoint mapper on TCP port 135 of the target. The client asks: "where can I find object X?" The mapper answers with a random high port, usually between 49152 and 65535.
  • Stage 2 — the real work. The client then talks to that high port, sends the credentials, and Windows starts (or finds) the program that owns the object. The attacker's method calls now run on the target.
Why this matters: If your firewall rules only watch port 135, you still miss half of the traffic. The real DCOM session runs on a dynamic port that changes every time. Windows offers ways to pin RPC ports to a fixed range — see the mitigation section.

The famous abuse objects

In 2017, the researcher Matt Nelson (writing as enigma0x3) published a series of posts that showed how easy DCOM abuse is. His work made this technique public knowledge, and red teams adopted it everywhere. Four objects became the classics:

Object nameMethod usedWhat it does on the target
MMC20.ApplicationDocument.ActiveView.ExecuteShellCommandStarts the Microsoft Management Console (mmc.exe) on the target, then asks it to run any command. Very reliable. Needs local admin rights.
ShellWindowsDocument.Application.ShellExecuteAsks a hidden Explorer shell window to start any program on the target.
ShellBrowserWindowDocument.Application.ShellExecuteSame idea, a different hidden Explorer window. Popular on Windows 10 and Server 2016+ because it is always available.
Excel.ApplicationRegisterXLLAsks Excel on the target to load an XLL add-in (a DLL built for Excel) from a network share. Works on hosts with Office installed.

The pattern is always the same: find the object on the remote computer, create it, and call one method that starts a program. The program then runs as a child of a normal Windows program — mmc.exe or explorer.exe — which is exactly the clue defenders can hunt for.

What does an attacker need?

  • Valid credentials with the right local rights. For MMC20.Application the account must be a local administrator on the target. The Shell* objects often work with weaker rights, which makes them popular too.
  • Network reach: TCP 135 open on the target, plus the high dynamic RPC ports. Inside one company network this is almost always open, because normal administration depends on it.
  • DCOM enabled on the target. It is enabled by default on every Windows client and server.
  • Nothing else. No hacking tool, no exploit, no file. Plain PowerShell (GetTypeFromProgID plus Activator.CreateInstance) is enough.

Why do attackers like it?

  • Built in. DCOM and PowerShell ship with Windows. There is nothing to download and nothing to lose if a copy is captured.
  • No files on the target. The attacker sends a method call, not a program. Antivirus that only looks for bad files sees nothing.
  • Blends in. MMC and Explorer are admin tools. The process tree looks almost like daily administration — until you check the parent-child pair.
  • Crosses blocked doors. If RDP or WinRM are closed but RPC is open (very common between internal subnets), DCOM still works.
  • Fast to type. One long one-liner equals full remote command execution.
  • Loud in logs, quiet on disk. The attack is invisible to file scanning, but it must create events: a Type 3 logon, a process creation with an odd parent. The blue team section builds on this.
  • Well documented. Public research from 2017 means every red team knows it, and so can every defender.

How does it look in practice?

The following sequence is the whole attack on one lab workstation. It is taken from the public research above and is shortened for teaching. Run it only against machines you own, such as a home lab.

powershell
# Lab only: attacker host with creds for a local admin of the target
# 1) Check that the RPC door (port 135) is open on the target
Test-NetConnection WS-B -Port 135

# 2) Find the object on the remote computer and create it there
$t = [type]::GetTypeFromProgID('MMC20.Application', 'WS-B')
$c = [Activator]::CreateInstance($t)

# 3) Press its "button": run a command inside MMC on WS-B
$c.Document.ActiveView.ExecuteShellCommand('cmd', $null,
    '/c whoami > \\WS-B\C$\out.txt', $null)

# 4) Read the result back over the admin share
type \\WS-B\C$\out.txt

The same trick with the Explorer-based objects needs no admin rights in many setups, and it is a favorite for moving from a web server to an internal server:

powershell
# Lab only: ShellBrowserWindow on a second target
$c = [Activator]::CreateInstance(
        [type]::GetTypeFromProgID('ShellBrowserWindow.Application', 'APP01'))
$c.Document.Application.ShellExecute('powershell.exe',
    '-enc SQBFAFgA...', $null, 'C:\Windows\System32', 1)

Tools that wrap this technique

Attackers do not always type the one-liner themselves. Public tools wrap the same COM calls. MITRE ATT&CK lists three such tools as the official procedure examples for T1021.003:

  • Cobalt Strike (S0154) — a commercial red-team framework that criminal groups also abuse. It can deliver its Beacon payload to a new host through remote COM execution.
  • Empire (S0363) — an open-source post-exploitation framework. Its Invoke-DCOM PowerShell module runs lateral movement through remote COM objects.
  • SILENTTRINITY (S0692) — a .NET-based attack tool. It uses System namespace methods to run lateral movement over DCOM.

On Linux, the Impacket collection ships dcomexec.py. It runs one command through DCOM and reads the output back over SMB:

bash
# Lab only: run one command on the target through DCOM (Impacket)
dcomexec.py CORP/svc_admin:'Lab-Password-123'@APP01 'whoami'
Watch out (OPSEC / noise): DCOM abuse is quiet on disk but loud in logs. It always creates a 4624 Type 3 logon on the target, a Sysmon process-creation event with an unusual parent (mmc.exe or explorer.exe), and often a PowerShell 4104 script-block log on the attacker's own host. Good red teams report these as expected findings.

Blue Team / SOC Perspective

What DCOM lateral movement looks like in your logs — and why the process tree is your best friend.

An attacker using DCOM cannot switch off every signal. The attack touches at least four log sources on the target machine. Your job is to collect them, and to look at relationships, not single events.

Where it fits in the attack chain

1. First entry (web shell, phishing)→ 2. Steal credentials→ 3. DCOM activation on a second host→ 4. Run commands, dump memory→ 5. Reach data or ransomware

DCOM sits at step 3: it is a way of moving, not a way of getting in. That is why it lands under the Lateral Movement tactic in MITRE ATT&CK.

The artifacts it leaves behind

Log sourceEvent IDWhat it shows
Windows Security4624 (Type 3)A network logon on the target from the attacker's host, with no interactive session. This is the DCOM activation itself.
Windows Security4688Process creation on the target: cmd.exe or powershell.exe with mmc.exe as the creator (if command-line auditing is on).
Sysmon1Process creation with full parent-child detail — the key artifact. Parent mmc.exe or explorer.exe, child a shell.
Sysmon3Network connections to TCP 135 and then a dynamic RPC port (49152–65535), logged on the host that starts the connection.
PowerShell4104Script-block logging on the attacker's host: the DCOM one-liner with the object name in plain text.
Windows Security5145Admin share (C$, ADMIN$) reads that often follow DCOM execution to fetch output.
Windows Security4648A logon with explicit credentials — logged on the host that supplies a password (for example after runas /netonly). A source-side clue when the attacker does not reuse the session token.
DCOM Operational10036A COM activation was rejected by permissions — a small but precious record of who tried.
Sysmon10If the pivot is followed by credential dumping: an open of lsass.exe from rundll32.exe or similar.

Two details help you read these records correctly. The DCOM activation itself runs inside svchost.exe -k DcomLaunch — the DCOM Launcher service on the target. The shells you hunt for then run under mmc.exe or explorer.exe. For deep hunts, you can also record remote calls with the Microsoft-Windows-RPC provider of Event Tracing for Windows (ETW), a built-in Windows logging system.

Why parent-child relationships are the strongest clue

Every event on its own can look normal. A cmd.exe starting is normal. An explorer.exe running is normal. A Type 3 logon happens thousands of times a day. The magic is in the pairing:

mmc.exe spawning a shell

mmc.exe is the Microsoft Management Console — a window an administrator clicks through. It almost never starts cmd.exe or powershell.exe by itself, and it never does so while its only user sits at another computer. This pair on a server is nearly always DCOM abuse.

explorer.exe spawning a shell — on a server

explorer.exe is the Windows desktop. On a workstation it starts programs all day. On a server, nobody is logged in to the desktop — so a server's explorer.exe launching powershell.exe -enc means something activated a hidden desktop window remotely. This is the signature of the ShellWindows and ShellBrowserWindow tricks.

Why this matters: A single event is easy to fake or explain. A relationship between two processes is a story. Detection rules that compare parent and child, plus the logon that came seconds before, catch DCOM abuse with very few false positives.

First-response ideas

  • Do not unplug in panic. Note the time, the account, and both host names first.
  • Search sideways. Query every host for the same account, the same source IP, and the same parent-child pair. DCOM pivots are rarely used once.
  • Collect before you contain. Export the PowerShell 4104 lines and Sysmon events for the timeline — isolation may stop further logging.
  • Isolate the target, rotate the account. Cut the host from the network, kill active sessions, and reset the credentials the attacker used.

What to look for — quick checklist

  • A 4624 logon with Logon Type 3 from a workstation to a host that the same account does not normally touch.
  • Sysmon 1 where ParentImage ends in mmc.exe and the child is cmd.exe, powershell.exe, or wscript.exe.
  • Sysmon 1 where ParentImage ends in explorer.exe on a server, especially with -enc in the child's command line.
  • PowerShell 4104 lines containing MMC20.Application, ShellWindows, ShellBrowserWindow, or GetTypeFromProgID together with a remote host name.
  • Sysmon 3 connections to port 135, then to a high port, from one host to many targets in minutes.
  • Event 10036 in the Microsoft-Windows-DCOM/Operational log — a rejected activation from an unexpected source.
  • Event 4648 (explicit-credential logon) on a workstation you manage — it shows that someone supplied a password by hand before touching other hosts.
  • Admin share reads (5145 on C$ or ADMIN$) from the same source host within minutes of a Type 3 logon.

Threat Intelligence

Threat intelligence (CTI) answers one question for the SOC: who uses this technique, and how? The workflow has three steps.

  • Collect. Watch MITRE ATT&CK, CISA advisories, vendor research blogs, and sharing platforms such as MISP or OTX. Note which groups touch T1021.003 and which tools they use.
  • Analyze. Compare the reports with your own logs. Ask: do we collect 4104 on servers? Do we see MMC on servers at all? Turn each report into a concrete data question.
  • Apply. Write or tune detection rules, save hunting queries, and brief the SOC on the actor names so an alert can be read in context.

Context for this technique: the DCOM abuse pattern was publicly documented by Matt Nelson (enigma0x3) in 2017, who showed remote command execution through MMC20.Application and the ShellWindows/ShellBrowserWindow objects. MITRE ATT&CK keeps a short official record for this sub-technique. It lists three tools that use DCOM for lateral movement: Cobalt Strike, Empire, and SILENTTRINITY. Hunting hypotheses

  • H1 — shells from MMC on servers. Any Sysmon 1 event where mmc.exe is the parent of a shell on a server. Baseline first: in most companies this count is zero. See rule 3.
  • H2 — COM ProgIDs with remote host names in 4104. PowerShell script-block logs that mention GetTypeFromProgID, CreateInstance, or a known object name together with another computer's name. See rules 1 and 2.
  • H3 — Type 3 logon then admin-share read, same pair. A 4624 Type 3 from host A to host B, followed within 10 minutes by a 5145 read of C$ or ADMIN$ from A to B. This is the echo of "run a command, fetch the output". See rule 7.

Threats Ranking & Categorization

DCOM itself is a feature, not a threat. The danger is what people do with it. This table ranks the threats a detection program should cover, from most to least severe.

Logs & Patterns

Each threat below gets its own sample log block. The samples are realistic but simplified. All XML samples are Sysmon or Windows Security events as they arrive through XmlWinEventLog.

Threat 1 — Remote command execution via MMC20.Application

Use PowerShell 4104 (script-block logging) on the host that launches the attack, plus Sysmon 1 on the target. The 4104 record keeps the whole one-liner in plain text — including the object name and the remote host name.

log — PowerShell 4104 (text)
TimeCreated : 2026-09-29T11:42:07.1130000Z
EventID     : 4104
Source      : Microsoft-Windows-PowerShell
Computer    : WS-A.corp.local
Message     : Creating Scriptblock Text (1 of 1):
              $t = [type]::GetTypeFromProgID('MMC20.Application','WS-B');
              $c = [Activator]::CreateInstance($t);
              $c.Document.ActiveView.ExecuteShellCommand('cmd',$null,
              '/c whoami > \\WS-B\C$\out.txt',$null)
Path        : UserHost
RunspaceId  : a1c3e5f7-2b4d-4c6e-8a90-1b2d3f4e5a6b
  • Object names: MMC20.Application, ShellWindows, ShellBrowserWindow.Application.
  • GetTypeFromProgID or CreateInstance combined with a remote computer name.
  • ExecuteShellCommand anywhere in a script block.

Threat 6 — COM activation permission abuse from an unusual source

Use the Microsoft-Windows-DCOM/Operational log, event 10036. When the server rejects a COM activation, the record names the caller's user and source address. After Microsoft's 2022 DCOM hardening (KB5004442), this event also appears for old clients that do not meet the new bar, so pair it with a logon check.

log — DCOM 10036 (text)
Log Name   : Microsoft-Windows-DCOM/Operational
Source     : Microsoft-Windows-DCOM
EventID    : 10036
Level      : Error
Computer   : APP01.corp.local
TimeCreated: 2026-09-29T11:47:29.6400000Z
Message    : The server-side authentication level policy does not allow the
             user CORP\svc_admin (SID: S-1-5-21-1004336348-...-1107) from
             address (10.1.30.31) to activate the DCOM server. Please raise
             the activation authentication level at least to
             RPC_C_AUTHN_LEVEL_PKT_INTEGRITY in the server application's
             authentication level if it is below that value.
  • Client IP in the message that is not a known admin workstation.
  • Repeated 10036 events from the same pair — a sign of retry before success or failure.
  • Match the IP against your Type 3 logons at the same minute.

Threat 7 — Legacy DCOM misconfiguration left in the estate

Use the System log, event 10016, and the June 2022 hardening guidance (KB5004442). Machines that still log wide-open COM permissions are the ones that never got inventoried.

  • COM launch permissions granted to broad groups such as Everyone.
  • Build an inventory: which hosts still accept remote activation from any account?

Threat 8 — Legitimate remote MMC use (baseline noise)

Use Windows Security 4624 Type 3 from your management sources. This baseline is what makes rule 3 safe: you learn who may activate remote consoles, so everyone else stands out.

  • Source IP is a workstation, not a jump server or management zone.

Sigma Detection Rules

Sigma is a text format for detection rules. A SIEM (Security Information and Event Management system) can turn each rule into a search. Each rule below is followed by the same logic as a Splunk SPL query. Adjust the index names to your environment.

Rule 1 — DCOM lateral movement via MMC20.Application

This rule reads PowerShell script-block logs. If anyone creates MMC20.Application in PowerShell, you hear about it. This is the highest-value, lowest-noise rule in the set.

yaml — sigma
title: DCOM Lateral Movement via MMC20.Application (PowerShell 4104)
id: 9c4d2f18-6a3e-4b7d-8f21-5c9e1d0a4b77
status: stable
description: Detects PowerShell script blocks that create the MMC20.Application
  COM object on a remote computer and call ExecuteShellCommand. This is the
  classic DCOM lateral movement pattern published by enigma0x3 in 2017.
references:
  - https://attack.mitre.org/techniques/T1021/003/
  - https://enigma0x3.net/2017/01/05/lateral-movement-using-the-mmc20-application-com-object/
author: Detection Engineering Team
date: 2026/09/29
tags:
  - attack.lateral_movement
  - attack.t1021.003
logsource:
  product: windows
  service: powershell
detection:
  selection:
    EventID: 4104
    ScriptBlockText|contains: 'MMC20.Application'
  condition: selection
falsepositives:
  - Authorized remote administration that intentionally automates MMC20
level: high
spl — splunk
index=wineventlog source="WinEventLog:PowerShell/Operational" EventCode=4104

Real-World Scenario

Operation BRASSGATE — a two-server intrusion where no malware file ever landed.

Is this a real case? Operation BRASSGATE is a realistic composite, not a documented public incident. It is built on the publicly documented DCOM tradecraft (enigma0x3 research, 2017) and on vendor-reported DCOM use, such as the Lizar toolset (Kaspersky, 2021). Company names, host names, and figures are invented for teaching.

A mid-size logistics company runs IIS web servers in a DMZ. The web application team holds an account called svc_admin that is a local administrator on several internal servers. Nobody watched this account. That is the whole story in one line.

The attack chain

1. Web shell on IIS server WEB01→ 2. Steal svc_admin from memory→ 3. DCOM pivot to BKUP01→ 4. LSASS dump on BKUP01→ 5. Second pivot to FS01→ 6. Data staged — then caught

Timeline

DAY 1 — 02:10
Web shell lands on WEB01

An attacker uploads a small web shell through an unpatched upload page. The shell runs as the IIS app pool account. Antivirus sees nothing, because the shell is one short script file that many tools share.

DAY 1 — 03:05
Credentials taken from memory

The attacker runs an encoded PowerShell download cradle from the shell and reads lsass.exe memory on WEB01. Among the saved credentials: CORP\svc_admin, a local administrator on the backup and file servers. The only traces are Sysmon 10 and an outbound TLS flow.

DAY 1 — 04:40
DCOM pivot to BKUP01

From WEB01, the attacker creates a ShellBrowserWindow.Application object on the backup server BKUP01 and calls ShellExecute with an encoded PowerShell command. No tool file crosses the network. BKUP01 logs a Type 3 logon and an explorer.exe spawning powershell.exe -enc — on a server where nobody is logged in.

DAY 1 — 05:20
LSASS dump on BKUP01

Using rundll32 with comsvcs.dll, the attacker copies LSASS memory on BKUP01. The dump gives them more admin rights, including the file server FS01. A 4688 event and a Sysmon 10 record capture both moments.

DAY 2 — 23:15
Second pivot to FS01, data staged

Over four quiet nights, the attacker DCOM-executes robocopy commands on FS01 and stages about 38 GB of finance folders into a hidden folder, then reads it back over the admin share. Each night produces the same small pattern: one Type 3 logon, one admin-share read, one shell with a GUI parent.

DAY 4 — 06:02
EDR flags the impossible parent

The EDR platform raises one alert: explorer.exe started powershell.exe -enc on BKUP01 — a server. Nobody is logged in to a server desktop at 04:40. An analyst reads the process tree and the Type 3 logon next to it, and opens a critical incident.

DAY 4 — 07:30
Containment begins

The SOC isolates WEB01 and BKUP01, kills the active sessions, and rotates svc_admin. The attacker's path is closed within 40 minutes of the first alert.

Impact

pivoted over DCOM (BKUP01, FS01)
4 days

The lesson: zero malware files on the pivoted servers, and every step still left a log. The attack failed because the company collected process parent-child data and PowerShell 4104 — not because they got lucky.

Containment, recovery, and consequences

Containment

  • Isolated WEB01 and BKUP01 at the switch and EDR level.
  • Killed all active sessions for svc_admin.
  • Rotated svc_admin and every credential found in the LSASS dump.
  • Blocked the RPC/DCOM path from the DMZ to internal servers.

Recovery

  • Rebuilt WEB01 from a clean image and patched the upload page.
  • Verified backups on BKUP01 were untouched before restoring anything.
  • Removed the staged data folder and measured how much data had already left.
  • Hunted the same pattern across all servers for 30 days: no repeat.

Consequences: the company started a full audit of local admin rights and removed svc_admin from every server where it was not needed. They also began a DCOM hardening project, using Microsoft's KB5004442 guidance, to decide which machines really need remote COM at all.

Lessons learned

LessonWhat it means in practice
Parent-child telemetry is decisiveThe alert that ended the case was one relationship: explorer.exe spawning an encoded shell on a server. Single events would have been ignored.
Servers should never spawn shells from GUI parentsexplorer.exe and mmc.exe on a server have no business starting cmd or powershell. Make this a hard detection, not a curiosity.
Restrict who has local adminOne shared admin account turned one web shell into two pivoted servers. Tiered admin rights and unique passwords (LAPS) shrink this blast radius.
DCOM hardening is a project, not a patchKB5004442 changes remote COM defaults; you must inventory which applications still need DCOM before you tighten it.

How the team communicated

The SOC opened a war room channel and invited the application team — not to blame them, but because they knew svc_admin and the IIS setup best. The incident lead posted a short status update every two hours: what was confirmed, what was guessed, and who had an action. The application team fixed the upload page within a day. The final report went to management with three asks: fund the admin-rights audit, fund the DCOM hardening project, and approve log collection on every server. All three were approved.

Mitigation & Defense

Layered controls that make DCOM pivots hard — and make the ones that still happen loud.

You cannot remove COM from Windows, but you can remove the paths an attacker needs: local admin rights, open RPC across zones, and default DCOM settings nobody reviewed. Each layer below also improves your logging, so detection gets better as a side effect.

Official MITRE mitigations

The ATT&CK page for T1021.003 lists four mitigations for this technique. They map to the priority table below.

  • M1048 — Application Isolation and Sandboxing. Keep all COM alerts and Protected View enabled. This matters for Office, because DCOM can start Office application objects too.
  • M1042 — Disable or Remove Feature or Program. Consider disabling DCOM through Dcomcnfg.exe (Component Services). Do it on servers that need no remote COM.
  • M1030 — Network Segmentation. Enable the Windows firewall. It blocks remote DCOM activation by default, so host firewalls are a real control here.
  • M1026 — Privileged Account Management. Tighten COM launch and activation permissions with Dcomcnfg.exe, or with the AppID registry keys under HKLM\SOFTWARE\Classes\AppID.

GPO / PowerShell configuration example

Two registry keys give you the PowerShell records that most of this guide depends on. Deploy them through Group Policy, or set them with the commands below and check with your compliance tool.

powershell
# 1) Turn on script-block logging (event 4104) machine-wide
New-Item -Path 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging' -Force
Set-ItemProperty -Path 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging' `
    -Name 'EnableScriptBlockLogging' -Value 1

# 2) Turn on transcription, so every PowerShell session writes a copy to disk
New-Item -Path 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\Transcription' -Force
Set-ItemProperty -Path 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\Transcription' `
    -Name 'EnableTranscripting' -Value 1
Set-ItemProperty -Path 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\Transcription' `
    -Name 'OutputDirectory' -Value 'C:\Logs\PS-Transcripts'

# 3) Turn on module logging for wide coverage
Set-ItemProperty -Path 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ModuleLogging' `
    -Name 'EnableModuleLogging' -Value 1

Defense in depth, layer by layer

1. Admin rights (LAPS, tiering)→ 2. Network (pin RPC, block 135)→ 3. Config (DCOM hardening)→ 4. Logging (4104, Sysmon)→ 5. Detection (rules 1–9)→ 6. Response (isolate, rotate)

For home users and home labs

  • Your home lab rarely needs DCOM exposed. Client-to-client COM over the network is almost never required outside old enterprise software.
  • Keep Windows updated. Modern versions already ship the stricter DCOM activation default from the 2022 hardening change.
  • Do not open port 135 in a router port-forward. It is for internal RPC, not for the internet.
  • Use separate admin accounts for testing, so a lab machine cannot borrow your daily-account rights.

Ten traps teams fall into with DCOM detection — and the fix for each one.

Most misses with this technique are process problems, not technology problems. Compare your program with the table below.

Best practices for detection engineers

  • Turn on PowerShell script-block logging (4104) and transcription on every Windows host, and verify collection monthly.
  • Keep Sysmon event 1 with full command lines, and treat the parent-child pair as your primary detection surface.
  • Deploy rules 1–9 from section 4, then tune them with your own baselines — servers first.
