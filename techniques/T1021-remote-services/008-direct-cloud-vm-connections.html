Direct Cloud VM Connections (Cloud-Native VM Access)

Cloud providers give administrators special tools to reach virtual machines (VMs) without public IP addresses, VPNs, or open firewall ports. Examples are AWS EC2 Instance Connect, GCP OS Login, and Azure Bastion. Attackers with stolen cloud credentials can use the very same tools to open a door that no port scan will ever see.

Written for beginners, SOC analysts, and detection engineers. Every example here is for learning and defense only. This guide shows the attack steps, the cloud and system logs each step leaves behind, and how to catch it.

Animated Attack Simulation

Watch how a leaked cloud token opens a private VM with no public IP — and see the logs every step creates.

In this story, an attacker finds a leaked IAM (Identity and Access Management) token in a public code repository. An IAM token is a set of cloud credentials that says who you are and what you may do. The attacker never touches the firewall. Instead, they ask the cloud control plane itself to build a connection path and to push a short-lived SSH key onto a private production VM. Every request is an API call, and every API call is written to CloudTrail, the AWS activity log.

How to read the panels

The canvas shows the actors. The attacker sits on the left, far outside the cloud. The AWS Cloud box is the control plane, the part of the cloud that accepts API calls. The IC Endpoint is an Instance Connect Endpoint, a cloud-managed tunnel into the private network. On the right sits EC2-PROD-01, a production VM with only a private IP address (10.4.7.20).

The attacker terminal shows the commands used at each step. The security telemetry panel shows the log events defenders would see at the same moment. Amber and red chips are the ones that deserve an alert.

What makes this different

There is no open port 22 on the internet. There is no VPN. The attacker "moves sideways" (this is called lateral movement) using the cloud provider's own front door. That is why old network-focused detections stay silent, while rare control-plane events become the strongest signal.

Tip: Watch step 3 and step 4 closely. Creating the endpoint and pushing the key are both rare events. If a human or pipeline does them once a quarter, a single new event is already worth a page.
Why this matters: In this attack the only thing the attacker needs is one valid cloud identity with the right permissions. The VM stays private, the security groups stay closed, and yet a shell opens. The evidence, however, is excellent: the control plane writes down every step with a name attached.

Red Team Perspective

What direct cloud VM connections are, why attackers love them, and how the access chain works.

Direct cloud VM connections are provider-built tools for administrators. Their job is simple: let an approved person open a shell on a virtual machine without exposing that machine to the internet. No public IP, no bastion host to patch, no VPN client. The cloud provider carries the connection for you.

Why this matters: These tools are healthy and widely used. The problem is not the tool. The problem is who holds the credentials that are allowed to use it. When those credentials leak, the "safe admin path" becomes an attacker door that sits completely outside the network perimeter.

The five tools, explained simply

ToolCloudWhat it doesHow the connection arrives
EC2 Instance Connect (EIC)AWSOne API call pushes a temporary SSH public key onto the instance. It is valid for about 60 seconds. Then you SSH in as a normal user.Direct SSH to the instance, or through the endpoint below.
EC2 Instance Connect Endpoint (EICE)AWSA cloud-managed tunnel inside your VPC (Virtual Private Cloud, the private network). It lets you reach private VMs with no public IP and no VPN.SSH through the endpoint on TCP 443 to the private IP.
EC2 Serial ConsoleAWSA root-level recovery door. It connects to the VM's serial port, like a keyboard and screen plugged directly into the box. It works even when networking is broken.Cloud console or CLI, then a serial shell on the OS.
OS Login + IAP tunnelingGoogle CloudOS Login ties SSH access to IAM accounts. Identity-Aware Proxy (IAP) forwards TCP to private VMs through Google's front end.gcloud compute ssh --tunnel-through-iap.
Azure Bastion + Serial ConsoleAzureBastion is a managed jump box in the cloud. You point your browser at it and reach private VMs over TLS. Serial Console gives raw console access.Browser session (RDP/SSH inside HTTPS) to the private IP.

Why attackers use them

1. They skip network segmentation entirely. Security groups, subnet rules, and firewalls only guard the network path. Direct connection tools do not walk that path. They enter through the control plane, the API layer that manages the cloud. An attacker with valid IAM credentials does not need to break through anything; the cloud itself opens the door.

2. Ephemeral keys defeat old key-hunt thinking. The pushed SSH key lives for roughly one minute and then disappears on its own. Teams that hunt for stolen key files on disk will find nothing. The evidence is not on the VM. It is in the cloud log.

3. The activity looks like admin automation. SendSSHPublicKey calls look exactly like a deployment pipeline doing its job. On the instance, the login line even contains the friendly word ec2-instance-connect. Nothing "looks broken" unless you know what normal looks like in your own account.

4. A leaked CI/CD role is a ready-made identity. Continuous integration systems (CI/CD, the robots that build and deploy code) often hold broad permissions and static keys. Those keys end up in code repositories far too often. An attacker who finds one inherits the robot's powers.

How it is done (lab only)

The full chain for AWS takes two commands. First push a temporary key, then connect. In this lab example the instance is one we own, in an isolated test account.

bash
# LAB ONLY — run against an instance you own, in an isolated test account
# 1. Push a temporary public key to the instance (valid ~60 seconds)
aws ec2-instance-connect send-ssh-public-key \
  --instance-id i-0def456 \
  --availability-zone eu-west-1a \
  --instance-os-user ec2-user \
  --ssh-public-key file://tmpkey.pub

# 2. SSH to the private IP; the Instance Connect Endpoint routes it
ssh ec2-user@10.4.7.20

The same pattern exists on the other clouds. One identity, one command, one shell:

bash
# Google Cloud: SSH to a private VM through Identity-Aware Proxy
gcloud compute ssh vm-prod-01 --tunnel-through-iap --zone europe-west1-b

# Azure: SSH to a private VM through Bastion
az ssh vm --resource-group prod-rg --name vm-prod-01
Watch out (OPSEC and noise): This technique is loud in the control plane. CreateInstanceConnectEndpoint is so rare that many accounts have zero events in their whole history. SendSSHPublicKey from a CI role that never used it before is another flag. Attackers accept this noise because the reach is huge; defenders should accept the small alert volume because the precision is huge.

Tools used with this technique

ToolRole in the chain
Trufflehog / GitleaksScan public repositories and file systems for leaked API keys.

Blue Team / SOC Perspective

The witnesses this attack leaves behind, the myth it breaks, and what to do first.

For defenders, this technique is a gift wrapped in a scare. The scare: the network perimeter never sees anything. The gift: the cloud control plane records every single step, with a named identity attached. Your job is to collect those records and alert on the rare ones.

The witnesses

WitnessWhere it livesWhy it is strong
SendSSHPublicKeyCloudTrail (AWS)Only key-push requests land here. Most accounts have a handful per month, all from known roles. A new principal is a strong alert.
CreateInstanceConnectEndpoint / DeleteInstanceConnectEndpointCloudTrail (AWS)So rare that "first ever in this account" is a normal description, not an exaggeration. Also a network change you did not review.
SendSerialConsoleSSHPublicKeyCloudTrail (AWS)The serial console is a root-level recovery door. Any key push for it deserves a page.
OS auth line via ec2-instance-connectInstance /var/log/secure or auth.logsshd literally writes the string ec2-instance-connect into the accepted-login line. No parsing tricks needed.
VPC flow logsCloudWatch / S3 / your SIEMThey show TCP 443 traffic to the IC endpoint, then SSH to the private IP. Flow logs prove the path, even if the key is long gone.
GuardDuty findingsGuardDuty console / EventBridgeManaged detections flag odd API patterns and credential misuse without you writing rules.

The "private means private" myth

Many teams treat a private IP address as a safety boundary. "Nobody can reach it, so why collect its logs?" A private IP only blocks one road: a direct connection from the internet. The cloud control plane is a second road, and IAM credentials are the ticket.

Think of it like a hotel. The room door (the network) is locked. But anyone who talks to the front desk (the control plane) with a valid name (an IAM identity) can ask the staff to open the room. The lock never saw them. The guest book did.

Correlate three things

One log source is good; three joined together are proof. For every suspicious connection, try to link:

  • The IAM identity that pushed the key (from CloudTrail: userIdentity.arn).
  • The key fingerprint that was pushed (from CloudTrail: requestParameters.SSHPublicKey).
  • The OS session that accepted it (from auth.log: fingerprint, user, source).

If the fingerprint in CloudTrail matches the fingerprint in auth.log, you have end-to-end proof of who opened the box and when.

First response, step by step

When a rare control-plane alert fires, work in this order:

  • Identify the principal. Read userIdentity.arn in the CloudTrail event. Is it a human admin, a pipeline role, or something nobody recognizes?
  • Pull the chain. Search CloudTrail for everything that identity did in the last 24 hours. Look for DescribeInstances, CreateInstanceConnectEndpoint, SendSSHPublicKey, and key deletes.
  • Check the instance. Read auth.log or /var/log/secure on the target. Match the key fingerprint from CloudTrail to the login line.
  • Contain quietly. Revoke the credentials first (disable the access key or role session). Delete any endpoint the attacker created. Then decide whether to stop the instance for forensics.
  • Look for the follow-up. After SSH access, attackers mine coins or build tunnels. Check EDR, flow logs, and the cloud bill for surprises.
Watch out: Do not stop at "the key expired". The key is gone after 60 seconds, but the CloudTrail records, the OS login line, and the flow logs stay. The session itself may also still be alive — SSH does not die just because the key that opened it expired.

What to look for — checklist

  • CloudTrail enabled in all regions, including the ones you do not use.
  • Any CreateInstanceConnectEndpoint event — compare it against your infrastructure-as-code pipeline identity.
  • SendSSHPublicKey from principals that never used it before (first-ever baseline).
  • SendSSHPublicKey or serial console events outside working hours or outside your admin ranges.
  • OS login lines containing ec2-instance-connect, especially for users like ec2-user on production.
  • Key fingerprints in auth.log that do not match your known admin keys.
  • Flow log entries from an IC endpoint subnet to instances on port 22, matched against CloudTrail times.
  • GuardDuty findings about unusual API call patterns or instance credential use.
  • New outbound tunnels or mining processes on instances shortly after any Instance Connect event.

Hunting hypotheses

  • First-ever key push by a role. Search 90 days of CloudTrail for SendSSHPublicKey. Group by userIdentity.arn. Any ARN (Amazon Resource Name, the full identity string) that appears for the first time, especially a CI/CD role, deserves a look.
  • Endpoint created outside the IaC pipeline. If your infrastructure is built by Terraform or CloudFormation, endpoint creation should come from that pipeline identity only. Anything else is an unreviewed network change.
  • OS session whose key fingerprint does not match inventory. Keep a list of known admin key fingerprints. Alert on any auth.log line with ec2-instance-connect whose fingerprint is not on the list.

Logs & Patterns

Each threat below gets the logs that detect it, one realistic sample, and the details that matter. All names, keys, and addresses are fictional teaching examples.

Threat 1 — Ephemeral-key access to private VMs

Logs: CloudTrail (the event SendSSHPublicKey), plus the instance auth log. The CloudTrail record names the identity, the instance, the OS user, and the fingerprint of the pushed key — everything you need for the correlation described in section 3.

json — CloudTrail
{
  "eventVersion": "1.09",
  "userIdentity": {
    "type": "AssumedRole",
    "arn": "arn:aws:sts::111122223333:assumed-role/dev_ci_automation/runner-01",
    "accountId": "111122223333",
    "sessionContext": {
      "sessionIssuer": { "type": "Role", "principalId": "AROA3XEFEXAMPLE",
        "arn": "arn:aws:iam::111122223333:role/dev_ci_automation", "userName": "dev_ci_automation" }
    }
  },
  "eventTime": "2026-09-29T11:31:04Z",
  "eventSource": "ec2-instance-connect.amazonaws.com",
  "eventName": "SendSSHPublicKey",
  "awsRegion": "eu-west-1",
  "sourceIPAddress": "203.0.113.7",
  "userAgent": "aws-cli/2.15.0 md/awscrt",
  "requestParameters": {
    "instanceId": "i-0def4567890abcdef",
    "instanceOSUser": "ec2-user",

  • userIdentity.arn — is this principal approved for key pushes? First-ever from a role is the strongest signal.
  • sourceIPAddress — cloud CLI traffic from a home IP or hosting provider, not from your office or pipeline runner.
  • requestParameters.instanceOSUser — pushes for ec2-user, ubuntu, or root on production instances.
  • SSHPublicKey fingerprint — compare with the fingerprint that appears in the OS auth log.

Threat 2 — Serial console root recovery abuse

Logs: CloudTrail SendSerialConsoleSSHPublicKey, plus the OS serial console audit trail. On the instance, serial sessions appear on the console device ttyS0, and logins there are rare in normal operations.

log — instance console audit
Sep 29 11:40:58 EC2-PROD-01 systemd-logind[1210]: New session 44 of user root on ttyS0.
Sep 29 11:41:05 EC2-PROD-01 login[4420]: ROOT LOGIN on '/dev/ttyS0'
Sep 29 11:43:10 EC2-PROD-01 sudo:   root : TTY=ttyS0 ; PWD=/root ; COMMAND=/bin/passwd ec2-user
  • Any SendSerialConsoleSSHPublicKey in CloudTrail — treat as high severity by default.
  • Logins on ttyS0 in the OS log — normal servers almost never see them.
  • Password or SSH key changes shortly after a serial session — a classic persistence step.

Threat 4 — OS Login / Bastion use from unmanaged devices (OS-level marker)

Logs: the instance auth log (/var/log/secure on Amazon Linux and RHEL, /var/log/auth.log on Ubuntu). The SSH daemon writes the literal string ec2-instance-connect into the accepted-login line. This is the moment where the cloud event meets the machine.

log — /var/log/secure
Sep 29 11:31:09 EC2-PROD-01 sshd[4417]: Accepted publickey for ec2-user from 10.4.99.10 port 51344 ssh2: RSA SHA256:9xYzKq3mVbN8pL2wRtUvXyZ0aBcDeFgHiJkLmNoPqRs
Sep 29 11:31:09 EC2-PROD-01 sshd[4417]: Received public key from EC2 Instance Connect for ec2-user (fingerprint SHA256:9xYzKq3mVbN8pL2wRtUvXyZ0aBcDeFgHiJkLmNoPqRs, source ec2-instance-connect)
Sep 29 11:31:09 EC2-PROD-01 sshd[4417]: User child is on pid 4419
  • The words ec2-instance-connect in the login line — the provider itself marks the entry path.
  • The fingerprint — if it is not one of your known admin keys, escalate.
  • The source IP (here the endpoint-side address) — match it to the CloudTrail time within seconds.
  • On GCP and Azure, the same idea: OS Login sessions and Bastion connections from devices outside your management ranges.

Threat 5 — Reverse tunnel out of a private subnet

Logs: VPC flow logs (records of network connections), EDR process events, and the instance auth log. Flow logs cannot read the content, but the pattern gives it away: small steady outbound connections to one outside host, long-lived, on a strange port. The default format is one line per flow: version, account, ENI, source, destination, ports, protocol, packets, bytes, start, end, action, status.

log — VPC flow logs
2 111122223333 eni-0a1b2c3d4e5f6a7b8 10.4.7.20 203.0.113.9 44912 9999 6 1240 512000 1790681500 1790682100 ACCEPT OK
2 111122223333 eni-0a1b2c3d4e5f6a7b8 10.4.7.20 203.0.113.9 44914 9999 6 980 404000 1790682100 1790682700 ACCEPT OK
2 111122223333 eni-0a1b2c3d4e5f6a7b8 10.4.7.20 203.0.113.150 443 51222 6 210 98000 1790681520 1790681600 ACCEPT OK
2 111122223333 eni-0a1b2c3d4e5f6a7b8 10.4.7.20 203.0.113.150 443 51224 6 480 224000 1790681600 1790681720 ACCEPT OK
  • Long-lived outbound flows to a single external IP on a non-standard port such as 9999.
  • EDR or process logs showing ssh -R (a reverse SSH tunnel) started by any user.
  • Steady outbound byte counts from a VM that normally serves inbound traffic only.
  • Connections to fresh domains or IPs first seen minutes after an Instance Connect event.
  • Custom flow log formats can add the flow-direction field. It tells you who started the connection, which separates inside-out tunnels from normal traffic.

Threat 6 — Enumeration of connection configuration

Logs: CloudTrail read events (DescribeInstances, DescribeSubnets, DescribeSecurityGroups). One call is normal; bursts from a new identity are recon (reconnaissance, the attacker's mapping phase).

}
  • Read events at odd hours, from unfamiliar IPs, or in long bursts (many pages of results).
  • A CI/CD role reading the full fleet inventory — pipelines usually touch their own stack, not everything.
  • Enumeration immediately followed by endpoint or key events — the chain in motion.

Threat 7 — IaC automation false positives

Logs: your pipeline's own audit trail plus CloudTrail. The fix for noise is a baseline: know exactly which identity and user agent your infrastructure-as-code (IaC, e.g. Terraform) uses, and whitelist that pattern instead of reacting to every event.

log — approved pipeline (expected)
2026-09-29T02:10:11Z CI terraform-apply role=terraform_planner sourceIP=10.99.4.12  agent=HashiCorp/1.9 (go-aws-sdk)
2026-09-29T02:10:14Z CI CreateInstanceConnectEndpoint ice-0cc55 subnet-0abc123def456  change=CHG-4021
2026-09-29T02:10:14Z CI endpoint state=create-complete  drift=none  approvedBy=policy-as-code
2026-09-29T02:41:52Z CI DeleteInstanceConnectEndpoint ice-0cc55  reason=ephemeral-test  change=CHG-4021
  • Expected: endpoint events from the pipeline role, inside a change window, with a change ticket ID.
  • Expected: consistent user agent (the IaC tool) and consistent source IPs (runner subnets).
  • Suspicious: the same APIs from an interactive CLI user agent, or outside change windows.
  • Keep this table small and reviewed; every exception should map to a ticket.

Sigma Detection Rules

Sigma is a standard way to write detection rules once and run them in many SIEM tools (SIEM: Security Information and Event Management, the system that stores and searches logs). Each rule below is followed by its equivalent Splunk search (SPL) and a short explanation of the logic.

Sigma 1 — Instance Connect Endpoint created (rare control-plane event)

yaml
title: AWS EC2 Instance Connect Endpoint Created
id: a3f6c2e1-9b4d-4e87-a1c5-6f2d8b0e7c93
status: stable
description: >
  Detects the creation of an EC2 Instance Connect Endpoint. This API is a direct
  change to the private network path of a VPC and is rare in most accounts. Attackers
  who hold a valid IAM role use it to reach private VMs without a public IP or VPN.
references:
  - https://attack.mitre.org/techniques/T1021/008/
  - https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/connect-with-instance-connect-endpoint.html
author: Detection Engineering Team
date: 2026/09/29
tags:
  - attack.lateral_movement
  - attack.t1021.008
logsource:
  category: cloud
  product: aws
  service: cloudtrail
detection:
  selection:
    eventName: CreateInstanceConnectEndpoint
  condition: selection
falsepositives:
  - Approved infrastructure-as-code pipelines creating endpoints during change windows
level: critical

The logic is a single rare event name, so no filtering is needed. Alert immediately and compare the identity against your pipeline roles.

spl — splunk
index=cloudtrail sourcetype=aws:cloudtrail eventName=CreateInstanceConnectEndpoint
| stats count values(requestParameters.subnetId) AS subnets values(sourceIPAddress) AS src_ips
        values(userIdentity.arn) AS principals by awsRegion
| where count >= 1

yaml

id: 9a3e7f1d-5b2c-46b8-a4d9-e1f8c3b6d507
status: stable
description: >
  Aggregation rule: the same principal or account deletes an Instance Connect Endpoint

  group by identity and compare against the change calendar.
references:
  - https://attack.mitre.org/techniques/T1021/008/
author: Detection Engineering Team
date: 2026/09/29
tags:
  - attack.lateral_movement
  - attack.t1021.008
logsource:
  category: cloud
  product: aws
  service: cloudtrail
detection:
  selection_create:
    eventName: CreateInstanceConnectEndpoint
  selection_delete:
    eventName: DeleteInstanceConnectEndpoint

level: medium

Read it as: both event types from the same identity inside one day. The Splunk search below counts both sides of the pair.

spl — splunk
index=cloudtrail sourcetype=aws:cloudtrail
  (eventName=CreateInstanceConnectEndpoint OR eventName=DeleteInstanceConnectEndpoint)
| bin _time span=5m
| stats count(eval(eventName="CreateInstanceConnectEndpoint")) AS creates
        count(eval(eventName="DeleteInstanceConnectEndpoint")) AS deletes
        values(sourceIPAddress) AS src_ips
        by _time, userIdentity.arn
| where creates > 0 AND deletes > 0

Real-World Scenario

"The miner behind the private fence" — a realistic composite story based on vendor-reported cloud mining campaigns.

How real is this story? In 2024, cloud security teams — including Sysdig Threat Research and peer vendors — documented cryptomining crews abusing AWS identity paths, including Instance Connect Endpoint-style access, to reach private VMs with no public exposure. Public incidents that name this exact sub-technique are still rare, because the technique is new (added to ATT&CK in 2023). The story below is a realistic composite built from those vendor reports and standard red-team practice. The company, people, and numbers are fictional, but every step matches reported attacker behavior.

The setting. Meridian Analytics runs its data pipeline on AWS in eu-west-1. Its crown jewels sit on private VMs with no public IP addresses. The team is proud of that: "Our production is behind a private fence." Their CI/CD system uses a static access key for a role called dev_ci_automation. The key lives in a pipeline config file that was committed to a public repository by mistake, two months earlier.

DAY 1 — 09:20
The token is found

An automated key scanner (and, minutes later, an attacker running the same idea) finds the AKIA... key in the public repository. The attacker verifies it works and discovers it is an IAM role token with broad EC2 permissions. No cloud logs exist yet.

DAY 1 — 11:05
Enumeration from outside

The attacker calls describe-instances and maps the fleet. One instance stands out: i-0def456 / EC2-PROD-01, private IP 10.4.7.20, no public IP, no SSM agent. CloudTrail records DescribeInstances from the CI role — an event nobody looks at, because pipelines call it all day.

DAY 1 — 11:22
The door is built — first ever

The attacker creates an EC2 Instance Connect Endpoint with the CLI. This is the first CreateInstanceConnectEndpoint in the account's entire history, and it does not come from the Terraform pipeline. The SOC's new rare-event alert fires. At this moment, the story is already over — if someone reads the page.

DAY 1 — 11:31
A 60-second key, a lasting shell

SendSSHPublicKey pushes a temporary key to ec2-user. Seconds later the attacker SSHes through the endpoint. The instance auth log writes the line with ec2-instance-connect in it. The attacker installs a cryptominer and opens a reverse tunnel to 203.0.113.9. The pushed key expires after 60 seconds. The shell stays.

DAY 2 — 06:40
FinOps notices money, not malware

The compute bill for EC2-PROD-01 spikes. A cost-anomaly alarm that was built for budget reasons emails the FinOps team. Nobody links it to security yet. The miner burns CPU all night.

DAY 2 — 07:12
The SOC ties the chain — 40 minutes

An analyst opens the rare-event ticket from the day before, joins it with the cost alarm, and pulls CloudTrail for dev_ci_automation. In 40 minutes the full chain is on one page: endpoint created, key pushed, login accepted, miner installed, tunnel out. The team moves to containment.

DAY 2 — 08:05
Containment

The team revokes the leaked token, deletes the attacker's endpoint, and stops the instance for forensics. The miner dies mid-block. Flow logs confirm the tunnel went quiet at the same second.

DAY 3–5
Recovery

A clean instance is built from a golden image. All CI/CD keys are replaced with short-lived federated roles. Secret scanning with push protection is switched on for every repository. The rare-event alerts are codified so they survive staff changes.

The attack chain at a glance

1. Leaked CI token→ 2. Enumerate fleet→ 3. Create IC endpoint→ 4. Push ephemeral key→ 5. SSH to private VM→ 6. Miner + reverse tunnel→ 7. Cost alarm→ 8. CloudTrail chain review

Consequences that stuck

  • A repository secret-scanning program with push protection, so new leaked keys are blocked at commit time.
  • IAM permission boundaries: the CI role lost ec2:CreateInstanceConnectEndpoint forever; key-push rights moved to a break-glass role.
  • The "rare control-plane event" alerts were codified as detection-as-code, with tests and an owner.
  • FinOps and security now share a queue. Cost anomalies are treated as potential security signals.
  • Static keys were removed from CI/CD and replaced with short-lived federated roles.
  • The private fence stayed — but the team stopped calling it a boundary. Identity is the boundary.

Lessons learned

LessonWhat it means in practice
Rare events are goldFirst-ever CreateInstanceConnectEndpoint was a perfect alert with zero tuning. Build first-seen baselines for rare APIs.
Private IP does not mean unreachableThe control plane is a second door. Monitor private VMs as if they were public, because a valid identity makes them reachable.
Ephemeral keys are not "no evidence"The key expired in 60 seconds, but CloudTrail, auth.log, and flow logs kept the whole story. Hunt by principal, not by key file.

How the team communicated

One joint channel. Security, platform, and FinOps sat in one war-room channel with a single incident commander. Every hour, one written update: what we know, what we are doing, what we need. The CI/CD owners joined early because their role was the story.

Plain words for leadership. The executive summary was three sentences: "A leaked automation key let an outsider reach one private server. It mined cryptocurrency for about 20 hours and cost about 4,800 dollars. No customer data was touched, and the entry path is closed."

Numbers over blame. Updates used the impact stats above and never guessed at facts. When the team did not know something, the update said "checking".

The follow-up note. Five days later the team sent a short closure note: what changed (secrets program, IAM boundaries, codified alerts), what it cost, and the one metric to watch next quarter — first-ever events page time. Keeping it short made it read.

Mitigation & Defense

Layered defenses: limit who can build the door, watch the door, and remove the keys that open it.

You do not have to ban these tools. They save administrator time and reduce public exposure. The defense pattern is: restrict the permission, alert on the rare events, prefer fully audited alternatives, and remove long-lived keys that could fall into the wrong hands.

Priority table for enterprises

#ActionStops whatEffort
1Restrict who may create IC endpoints — IAM condition or explicit deny, pipeline role onlyA leaked interactive or CI role becoming a network engineerLow
2Alert on Create / DeleteInstanceConnectEndpoint as rare events with first-seen baselinesQuiet infrastructure change used as an attack doorLow
3Prefer Session Manager (SSM) with full audit over ad-hoc Instance Connect for daily adminUntracked shells; SSM logs every command by identityMedium
4Disable the EC2 serial console unless a documented recovery process needs itRoot-level recovery door abuseLow
5GCP: enforce OS Login with 2FA and IAP allowlists per projectAnonymous or stolen-identity SSH via IAP tunnelsLow
6Azure: Bastion with NSG scopes, and no public RDP/SSH on VMs at allDirect exposure and unscoped Bastion reachMedium
7Replace static keys with short-lived federated roles (OIDC) in CI/CDThe leak that starts the whole chainMedium
8VPC endpoint policies and subnet scoping for Instance Connect endpointsOne endpoint reaching the entire VPCMedium
9Monitor OS ec2-instance-connect logins and compare key fingerprints to an inventoryPushed keys that do not belong to your teamLow
10Canary private VMs with decoy data and an alert on any connectionAttackers testing a new path on cheap targetsLow

Policy example: deny Instance Connect to broad principals

This policy, attached to a permission boundary or a guardrail SCP (Service Control Policy), denies the key-push and endpoint actions to everyone except one break-glass admin role. It is valid JSON, so you can test it with the IAM policy simulator.

json — IAM policy
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyDirectCloudVMConnectionExceptBreakGlass",
      "Effect": "Deny",
      "Action": [
        "ec2-instance-connect:SendSSHPublicKey",
        "ec2-instance-connect:SendSerialConsoleSSHPublicKey",
        "ec2:CreateInstanceConnectEndpoint",
        "ec2:DeleteInstanceConnectEndpoint",
        "ec2:EnableSerialConsoleAccess"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": [
            "arn:aws:iam::111122223333:role/break-glass-admin",
            "arn:aws:iam::111122223333:role/terraform_planner"
          ]
        }
      }
    }
  ]
}

The same idea as commands, for a quick review of who currently holds the rights:

bash
# LAB/READ ONLY — audit which roles can push Instance Connect keys
aws iam list-roles --query "Roles[].RoleName" --output text | tr '\t' '\n' |
  while read -r role; do
    aws iam simulate-principal-policy \
      --policy-source-arn "arn:aws:iam::111122223333:role/$role" \
      --action-names ec2-instance-connect:SendSSHPublicKey ec2:CreateInstanceConnectEndpoint \

Tip: Session Manager (SSM) is the better default for daily work. It needs no open port 22 and no SSH keys. CloudTrail logs a StartSession event, and the session transcript can go to CloudWatch or S3 with the identity attached. Keep Instance Connect for edge cases, and let the alerts treat every use as notable.

For home and personal cloud accounts

  • Turn on MFA for the root account and every user in your personal cloud account.
  • Never put static access keys in code, notes, or chat messages. Use short-lived roles where possible.
  • Review IAM users and their keys once a month; delete the ones you do not recognize.
  • Turn on CloudTrail (the free management-events trail is enough) and glance at it after anything odd.
  • If you use Instance Connect for your hobby servers, you will see SendSSHPublicKey — just make sure it is always you.
  • Set a billing alarm. Miners show up as money long before they show up as logs.

How the layers stack

1. No static keys→ 2. Least-privilege IAM→ 3. Rare-event alerts→ 4. OS log + fingerprint watch→ 5. Cost anomaly alarms→ 6. Tested response plan

Layer 1 removes the most common starting point. Layers 2 and 3 make the door hard to build and loud when built. Layers 4 to 6 catch what slips through, and make sure the response is fast and calm.

Best practices for day-to-day detection engineers

  • Write down the "normal" identity, user agent, and IP range for every pipeline that touches Instance Connect APIs.
  • Build first-seen baselines for SendSSHPublicKey, CreateInstanceConnectEndpoint, and SendSerialConsoleSSHPublicKey.
  • Join CloudTrail events to OS auth.log by fingerprint at least once in a test — prove the correlation works before you need it.
  • Keep one dashboard: key pushes per day by role, endpoint count per account, serial console events per month.
  • Run a purple-team exercise: push a key in a lab account and time how long until each alert fires.
  • Review IAM permissions for Instance Connect APIs every quarter; remove what nobody justified.
  • Treat cost anomalies as security signals and route them into the SOC queue.
  • Test your containment steps: revoke a role session, delete an endpoint, stop an instance — know the buttons before the incident.
  • Document break-glass use, so a real responder can tell planned recovery from an attack in one minute.
  • Re-read this guide's scenario with your team and ask: "which of our alerts would have fired, and when?"
Final thought: Direct cloud VM connections are good tools doing a good job in the wrong hands. The clouds wrote down every step of this attack by design. Detection here is not about catching clever malware — it is about noticing that a quiet, rare, named event happened once. Build those baselines, and this technique becomes one of the easiest lateral movement paths to catch.
