SMB & Windows Admin Shares (T1021.002)

SMB (Server Message Block) is the Windows service that shares files and printers over the network. Every Windows computer also has hidden admin shares like C$ and ADMIN$. Attackers who hold an admin password or its hash use them to copy files and run code on other computers — a classic lateral movement step.

Written for beginners, SOC analysts, and detection engineers. All examples are for learning and defense only. This guide shows the attack steps, the logs the attack leaves behind, and how to catch it.

Red Team Perspective

Why attackers love SMB admin shares, what they need, and how the attack works.

This section explains the attacker side. The goal is to understand the technique well enough to detect it. Everything here is described at a high level, and the commands are safe, lab-only examples.

What SMB is

SMB (Server Message Block) is the protocol Windows uses to share files and printers over the network. When you open a folder on another computer in File Explorer, that is SMB at work. It uses TCP port 445. Very old systems also used port 139 over NetBIOS, an older name service. SMB is on almost every Windows machine, so it is nearly always reachable from inside a network.

The hidden admin shares

Every Windows computer creates special shares whose names end with a dollar sign. The dollar sign makes them hidden: they do not show up in normal share listings, and normal users have no rights on them. Administrators use them to reach the system drive from far away. The three important ones are:

  • ADMIN$ — maps to the Windows folder (C:\Windows) of the remote computer.
  • C$ — maps to the whole C: drive of the remote computer, so every file on it can be read or changed.
  • IPC$ — a communication channel, not a folder. It lets other systems talk to shared services through named pipes. Tools use it first to connect and list things.

To use these shares, you must be a local administrator on the target, or a domain admin. That is the attacker's problem — and pass-the-hash is a common way to solve it.

Pass-the-hash in one paragraph: Windows does not compare your password directly. For NTLM authentication it stores a one-way fingerprint of your password, called a hash. To prove who you are, the client answers a server challenge with math based on the hash. This means the hash is enough — an attacker never needs the real password. Tools can pull logged-on hashes out of the memory of lsass.exe, the Windows process that keeps logon material. If a domain admin once typed their password on a normal office computer, their hash lives there. The attacker uses the hash to authenticate to admin shares on any machine in the domain.

Prerequisites

  • An admin password or password hash of a local admin or domain admin.
  • SMB reachable — TCP 445 open from the attacker's machine to the target.
  • Local admin rights on the target, because only admins can map the hidden shares.
  • Admin shares not disabled by policy (they exist by default).

The three remote execution patterns

Copying a file is not the goal — running code is. Attackers use three main patterns, all of them old and all of them built into Windows or in free admin tools:

  1. PsExec-style service: copy the payload to ADMIN$, then ask the remote Service Control Manager (SCM) to create and start a service. The service runs as SYSTEM, the strongest local account. Classic PsExec does this with a tool named PSEXESVC; attackers rename it.
  2. One-shot commands: WMI runs a command through the remote WMI service (RPC, port 135). Impacket's smbexec.py rides on SMB instead: it writes a small batch file to the admin share and starts it through a service. atexec.py creates a scheduled task. The output comes back as a temp file.
  3. Scheduled task: create a task on the remote host with schtasks /S (or impacket atexec.py) that runs the command once.
cmd

:: 1) See which shares a server offers (hidden ones need /all)
net view \\FS01 /all

:: 2) Map the hidden ADMIN$ share with a lab account

:: 3) Look around inside it (ADMIN$ = the Windows folder)

:: 4) Ask the remote Service Control Manager for status

Watch out (OPSEC and noise): This technique is loud. Writing to ADMIN$ creates a 5145 event on the target. Creating a service creates 7045. A service starting spawns a process under services.exe, which Sysmon logs. Default tool names like PSEXESVC or known impacket service names are famous tells. Ethics: Using admin shares to run code on machines you do not own is illegal in most countries and will end a career. Security professionals do this only inside a written agreement, on lab systems, or in an approved test window. If you are a student, set up your own lab and practice there.

Blue Team / SOC Perspective

What admin-share abuse looks like in logs, which event IDs matter, and what to check first.

To defenders, SMB admin-share abuse is a chain of small, boring-looking events. Each event alone can look normal. The chain is the alarm: a network logon, then a share connection, then a file written to ADMIN$, then a new service, then a process under services.exe. Your job is to collect all pieces and see the chain.

5140 vs 5145 — the two share events

Windows logs two different share events, and people mix them up all the time:

  • 5140 — "someone connected to a share." It fires once per share, per logon session. It tells you who connected to IPC$, ADMIN$, or C$, and from which IP. It does not tell you which files were touched.
  • 5145 — "here is which file or folder inside the share was touched." It needs the Detailed File Share audit policy, which is off by default. Turn it on, or you will never see what happened inside the share.
Watch out: 5145 is chatty on busy file servers. It can log thousands of events per hour. Plan storage, filter with care, and keep the rules focused on hidden shares like ADMIN$, C$, and sensitive folders.

The other logs that complete the picture

LogWhat it recordsWhy it matters here
4624 (Logon Type 3)A network logon succeeded — no interactive session, someone connected from the network.Every share action starts with a Type 3 logon. A Type 3 logon by an admin account from a workstation is suspicious.
5140 / 5145Share connection / file access inside the share.The core evidence: who touched which hidden share and which file.
7045A new service was installed on the system.The classic payload runner: a service created by a network logon, starting a command.
4688 process creationA process started, with its command line (if enabled).Shows the attacker commands: cmd /c, rundll32, wmic /node:.
Sysmon 11A file was created, with its full path.The write lands on the target — the file is logged where the file lands, so you must run Sysmon on servers too, not just laptops.
Sysmon 1 / 3Process started / network connection.Shows services.exe spawning the payload, and SMB connections to port 445.
NTLM vs Kerberos in one line: Kerberos is the modern ticket-based Windows authentication (preferred, harder to steal and replay); NTLM is the older challenge-and-response method that works with just a password hash — which is exactly why pass-the-hash abuses it.

A useful pass-the-hash tell: in a 4624 Type 3 event with NTLM authentication, the field KeyLength is often 0 when a hash was used without a real password. On its own it is not proof, but combined with share access it is a strong signal.

Where this fits in the attack chain

1. Phishing→ 2. Credential theft→ 3. Admin-share lateral movement→ 4. SYSTEM on servers→ 5. Staging and ransomware

Admin-share abuse usually happens after the first compromise. It is the bridge between one infected laptop and the whole domain. If you catch it here, the story ends early.

First response when you see it

  • Isolate the source computer (the one with the odd Type 3 logons) — pull its network cable or use EDR network containment.
  • List every 5145 write from that source in the last 24 hours — this is the blast radius.
  • Check every target for new services (7045) and unexpected files in ADMIN$\Temp.
  • Rotate the password of the abused account and revoke its tickets.
  • Keep the evidence before cleanup: export the Security and Sysmon event logs.

What to look for — SOC checklist

  • Type 3 logon (4624, Logon Type 3) by an admin-like account from a workstation, not from a jump server.
  • Connections to hidden shares — 5140 or 5145 for ADMIN$, C$, IPC$ from unusual sources.
  • Executable files written into ADMIN$ — 5145 with Relative_Target_Name ending in .exe or .dll.
  • Service installs from the network — 7045 with random names or command lines that use cmd or rundll32.
  • Processes under services.exe — Sysmon 1 with parent services.exe spawning cmd, powershell, or rundll32.
  • NTLM with KeyLength 0 — a hash-only logon that no human typed.
  • Bursts of IPC$ connections — one host touching many others is share enumeration.
Tip: Write the checklist into your SOC playbook. When the alert fires, analysts should know exactly which five searches to run first — not spend an hour remembering event IDs.

Detection Engineering Deep Dive

The complete work of a detection engineer for this technique: regulations, intel, ranking, logs, Sigma rules, and queries.

A detection engineer turns threats into working alerts. This section walks through the full job: mapping the technique to rules and regulations, studying the actors who use it, ranking the threats, reading real log samples, and writing Sigma rules plus Splunk queries. This is the reference part of the guide — take your time here.

Laws and standards do not say "detect SMB abuse". They say "control access", "monitor systems", and "report breaches". 1. Collect→ 2. Analyze→ 3. Apply→ 4. Feed back

Hunting hypotheses — start a hunt when no rule is watching yet:

  • H1: An .exe or .dll is written to ADMIN$ and a new service starts on the same host within 5 minutes.

Logs & Patterns

Each threat below gets its own evidence pack: which logs to use, a realistic sample, and what to look for. The samples are Windows Security event XML or Sysmon XML. Field names match what Splunk and most SIEMs show after parsing.

1. Remote SYSTEM code execution via ADMIN$ + service — Event ID 7045

Use the Security log on the target. The service install event is the loudest artifact of PsExec-style execution.

xml
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Service Control Manager" Guid="{555908d1-a6d7-4695-8e1e-26931d2012f4}" />
    <EventID>7045</EventID>
    <TimeCreated SystemTime="2025-04-12T09:42:07.551034200Z" />
    <Computer>FS01.corp.local</Computer>
  </System>
  <EventData>
    <Data Name="ServiceName">PGMsgSvc</Data>
    <Data Name="ImagePath">%COMSPEC% /c rundll32.exe \\FS01\ADMIN$\Temp\tool.dll,Run</Data>
    <Data Name="ServiceType">user mode service</Data>
    <Data Name="StartType">demand start</Data>
    <Data Name="AccountName">LocalSystem</Data>
  </EventData>
</Event>
  • What to look for: ImagePath that starts with %COMSPEC% or cmd, or that runs powershell/rundll32 from a UNC path.
  • A service created minutes after a Type 3 logon from a workstation.
  • Service names that look random, or that repeat across many hosts at the same minute (worm).
  • StartType "demand start" and AccountName LocalSystem — common for tooling.

2. NotPetya-style worm propagation — Sysmon 3 (network connection)

Use Sysmon on infected hosts. A worm makes many SMB connections outward in a short window, from a process that should not do that.

xml
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Sysmon" Guid="{5770385f-c22a-43e0-bf4c-06f5698ffbd9}" />
    <EventID>3</EventID>
    <TimeCreated SystemTime="2025-04-12T09:44:51.204773900Z" />
    <Computer>WS-ACCOUNTING-12.corp.local</Computer>
  </System>
  <EventData>
    <Data Name="Image">C:\Windows\System32\svchost.exe</Data>
    <Data Name="User">NT AUTHORITY\SYSTEM</Data>
    <Data Name="Protocol">tcp</Data>
    <Data Name="DestinationIp">10.1.20.24</Data>
    <Data Name="DestinationHostname">SALES-PC01.corp.local</Data>
    <Data Name="DestinationPort">445</Data>
    <Data Name="DestinationPortName">microsoft-ds</Data>
  </EventData>
</Event>
  • What to look for: one host opening dozens of port 445 connections in minutes.
  • SMB from SYSTEM processes that never talk to the network normally.
  • The same source spreading to every reachable subnet at once.
  • Combine with 5140 on each destination: every hop accepts a share connection first.

3. Pass-the-hash over admin shares — Event ID 4624, Logon Type 3

Use the Security log on the target. The logon that opens the share session carries the pass-the-hash clues.

    <TimeCreated SystemTime="2025-04-12T09:41:58.112908400Z" />

  </System>
  <EventData>
    <Data Name="TargetUserName">admin_mike</Data>
    <Data Name="TargetDomainName">CORP</Data>
    <Data Name="LogonType">3</Data>
    <Data Name="AuthenticationPackageName">NTLM</Data>

  • What to look for: LogonType 3 plus KeyLength 0 — the classic hash-only pattern.
  • Admin-like TargetUserName logging on from workstation IP ranges.
  • The same account authenticating to many hosts within minutes.
  • Correlate with the following 5145 events from the same source IP.

4. Payload staging via ADMIN$ — Sysmon 11 (file create)

Use Sysmon on the target. The file write is logged where the file lands — which is the remote host, not the attacker's machine.

xml
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Sysmon" Guid="{5770385f-c22a-43e0-bf4c-06f5698ffbd9}" />
    <EventID>11</EventID>
    <TimeCreated SystemTime="2025-04-12T09:42:02.861332700Z" />
    <Computer>FS01.corp.local</Computer>
  </System>
  <EventData>
    <Data Name="RuleName">technique_id:T1021.002,technique_name:Remote Services: SMB/Windows Admin Shares</Data>
    <Data Name="Image">System</Data>
    <Data Name="User">NT AUTHORITY\SYSTEM</Data>
    <Data Name="TargetFilename">C:\Windows\Temp\tool.dll</Data>
    <Data Name="CreationUtcTime">2025-04-12 09:42:02.719</Data>
  </EventData>
</Event>
  • What to look for: TargetFilename inside C:\Windows (that is what ADMIN$ maps to) or other admin-only folders.
  • Executable extensions (.exe, .dll, .ps1) written by System — the SMB server writes the file on behalf of the remote user.
  • The same copy also produces Sysmon 11 on the source host, with a UNC path like \\FS01\ADMIN$\Temp\tool.dll. Rule on both sides.
  • No Sysmon on servers means this event simply does not exist — fix collection first.

5. NTLM relay against SMB services — Event ID 5140

Use the Security log on the relay target. Relay shows up as a share connection whose authentication the victim never intended.

xml
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Security-Auditing" Guid="{54849625-5478-4994-a5ba-3e3b0328c30d}" />
    <EventID>5140</EventID>
    <TimeCreated SystemTime="2025-04-12T09:43:11.603315500Z" />
    <Computer>DC01.corp.local</Computer>
  </System>
  <EventData>
    <Data Name="SubjectUserName">helpdesk_jane</Data>
    <Data Name="SubjectDomainName">CORP</Data>
    <Data Name="ObjectType">File</Data>
    <Data Name="ShareName">\\*\IPC$</Data>
    <Data Name="IpAddress">10.1.30.31</Data>
    <Data Name="IpPort">52390</Data>
  </EventData>
</Event>
  • What to look for: a user connecting to IPC$ on a server they never log on to.
  • The source IP belongs to a workstation that should not perform admin actions.
  • Anonymous or guest NTLM logons (4624 with Anonymous Logon) before the share connect.
  • Enforcing SMB signing kills most relay attacks — see section 6.

6. Sensitive share access C$ / HR / Finance — Event ID 5145

Use the Security log with Detailed File Share auditing enabled. This event names the exact file inside the share.

xml
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Security-Auditing" Guid="{54849625-5478-4994-a5ba-3e3b0328c30d}" />
    <EventID>5145</EventID>
    <TimeCreated SystemTime="2025-04-12T09:47:34.221768800Z" />
    <Computer>HR-PC05.corp.local</Computer>
  </System>
  <EventData>
    <Data Name="SubjectUserName">admin_mike</Data>
    <Data Name="SubjectDomainName">CORP</Data>
    <Data Name="ShareName">\\*\C$</Data>
    <Data Name="RelativeTargetName">Users\hr_lead\Documents\Salary_2024.xlsx</Data>
    <Data Name="AccessList">%%4416</Data>
    <Data Name="AccessMask">0x1</Data>
    <Data Name="IpAddress">10.1.30.31</Data>
  </EventData>

  • What to look for: admin accounts opening HR, salary, or finance files they have no work reason to open.
  • AccessList %%4416 means read; %%4417 means write — both matter.
  • First-time ever access of a user to a given share (baseline it).
  • Large read counts from one source in one session can mean bulk copying.

7. Share enumeration recon — Event ID 4688 with tool command lines

Use process creation logging on the source host. Enumeration tools betray themselves in the command line.

xml
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Security-Auditing" />
    <EventID>4688</EventID>

  • What to look for: command lines with --shares, -H (hash flag), or CIDR ranges like /24.
  • Known tool names: netexec, crackmapexec, smbmap, impacket.
  • Network commands running from user-writable folders like C:\Tools or %TEMP%.
  • The same pattern from a server account would be even more suspicious.

8. Legit remote administration — Sysmon 1 under services.exe

Use Sysmon on the target. This is what a normal admin action looks like — learn its shape so the malicious one stands out.

xml
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Sysmon" Guid="{5770385f-c22a-43e0-bf4c-06f5698ffbd9}" />
    <EventID>1</EventID>
    <TimeCreated SystemTime="2025-04-12T03:15:09.774220100Z" />
    <Computer>FS01.corp.local</Computer>
  </System>
  <EventData>
    <Data Name="Image">C:\Windows\System32\cmd.exe</Data>
    <Data Name="CommandLine">cmd.exe /q /c C:\Scripts\nightly_choco_upgrade.cmd</Data>
    <Data Name="ParentImage">C:\Windows\System32\services.exe</Data>
    <Data Name="User">NT AUTHORITY\SYSTEM</Data>
    <Data Name="IntegrityLevel">System</Data>
  </EventData>
</Event>
  • What to look for: a known management process chain, from a known tool, at a known time window.
  • Legit use comes from the admin jump server, not from random workstations.
  • Same shape as the malicious case — the difference is the source, name, and schedule.
  • Baseline this list; alert on everything that is not on it.

Sigma Detection Rules

Sigma is an open format for detection rules. You write the logic once in YAML, and converters turn it into queries for Splunk, Elastic, Sentinel, and others. Each rule below is followed by its ready-to-run Splunk SPL equivalent. Field names in the SPL use the Splunk Windows add-on style (EventCode, Share_Name, Relative_Target_Name, Source_Address).

Sigma 1 — Executable written to ADMIN$ share

The strongest single signal in this technique: someone pushes a runnable file into the hidden admin share. The rule watches 5145 for the ADMIN$ share and an executable extension.

yaml
title: Executable or Script Written to ADMIN$ Share
id: 3f8a9c2e-7d41-4b6e-9a35-c1d84e2f7a90
status: stable

Real-World Scenario: NotPetya, June 2017

The worst SMB-driven lateral movement event in history — and the reason this technique ranks so high.

Note on facts: This section follows the documented public story of the NotPetya attack of 27 June 2017. The dates, figures, and company names come from public reports: company statements (Maersk, Merck, FedEx, Mondelez, Rosneft), the White House damage estimate, and court records from the insurance disputes. Where reports differ, the figure is marked as approximate.

NotPetya looked like ransomware. It was not. It was a wiper — it destroyed data — wrapped in a self-spreading engine that used exactly the technique of this guide: stolen credentials, SMB admin shares, and remote execution through services and WMI, plus the EternalBlue exploit against old SMBv1.

How it started

The attackers got in through a trusted path. M.E.Doc, a Ukrainian tax software used by thousands of companies, shipped updates from its own servers. The attackers poisoned one of those updates. Every company that installed the update on 27 June 2017 got the malware silently. From that single trusted channel, the worm was free inside thousands of networks at once.

DAY 0 — 27 JUNE, EARLY MORNING
The poisoned update lands

M.E.Doc pushes a tampered update to its customers in Ukraine. Government offices, banks, power companies, and shipping firms install it. The malware starts quietly on their machines.

DAY 0 — WITHIN THE HOUR
Credentials stolen, engine armed

On each infected machine, the malware pulls passwords and hashes from memory, Mimikatz-style. It also packs the EternalBlue exploit that targets the old SMBv1 protocol. Both engines are now loaded.

DAY 0 — MINUTES LATER
Self-spreading over SMB

Using stolen hashes with PsExec- and WMIC-style remote execution, the worm copies itself to other machines over admin shares. Where credentials fail, it tries EternalBlue. No human clicks anything. Whole networks fall in minutes.

DAY 1 — 27–28 JUNE
Global detonation

Victims appear in about 76 countries: Maersk (shipping), Merck (pharma), FedEx TNT (logistics), Mondelez (food), Rosneft (oil), WPP (advertising), and many more. Master Boot Records and files start getting encrypted. Machines reboot and show the ransom note — but paying does not restore anything.

FIRST 72 HOURS
Containment triage

Companies disconnect everything: unplugging cables, shutting down VPNs, blocking SMB between sites. Maersk grounds its IT, ships sail with paper processes, and a small team starts mapping the damage on whiteboards and phones.

DAYS 3–10
The Maersk rebuild

Maersk finds one surviving domain controller in Ghana, offline because of a power cut during the attack. From that clean copy, the team rebuilds about 45,000 PCs, 4,000 servers, and 2,500 applications in 10 days — one of the fastest full recoveries ever documented.

The attack chain

1. Poisoned update→ 2. Credential theft→ 3. SMB admin-share spread→ 4. EternalBlue fallback→ 5. MBR + file wipe

Notice the middle of the chain. Steps 2 to 4 are the technique of this guide, running at machine speed with no operator watching. Every detection in section 4 targets exactly those steps.

Containment (what teams actually did): Cut network links between sites and to partners. Block SMBv1 and port 445 where possible. Kill the M.E.Doc update client. Force password resets and hash invalidation domain-wide. Share indicators of compromise with other victims within hours — many teams learned the details from each other before any official advisory.
Recovery (what worked): Restore from a clean, offline domain controller. Rebuild endpoints from images, not from the infected network. Verify backups before trusting them — NotPetya destroyed data that backup software still "saw". Prioritize the business-critical path first: for Maersk, the booking system before email.

Consequences that changed the industry

  • Attribution: In February 2018, the US, UK, and other governments attributed NotPetya to the Russian military (GRU) unit known as Sandworm. It was widely called a cyber weapon aimed at Ukraine that escaped its target.
  • Insurance battles: Insurers refused payouts citing "act of war" clauses. Mondelez and Merck fought their insurers for years; both disputes settled in 2024. The cases reshaped how cyber policies define war.
  • Board-level change: After NotPetya, patching cycles, network segmentation, and "prove you can recover" tests became board topics, not IT topics. Many companies disabled SMBv1 within weeks.

Lessons learned

How they communicated

  • War room: A single command center with IT, security, legal, and communications in one room (physical or virtual), deciding priorities together.
  • One source of truth: A single status channel and a single owner for updates, so teams did not contradict each other under pressure.
  • Regular cadence: Short updates every few hours to executives and staff, even when the update was "no change" — silence creates panic.
  • Honest external statements: Companies named the problem plainly and avoided blame language. Regulators were notified where data protection rules required it.
Why this matters: NotPetya is the proof that this "boring admin technique" is strategic. No zero-day in the payload itself — just stolen hashes, hidden shares, and a service call. The detections in section 4 exist to make that chain visible at step one.

Mitigation & Defense

Layered fixes: make the shares less reachable, the credentials less reusable, and the abuse loudly visible.

No single control stops admin-share abuse, because the abuse uses the channel administrators themselves need. Defense means layers: remove what you can, constrain what you must keep, and watch everything.

Enterprise priority table

ActionStops whatEffort
Disable SMBv1 everywhere (servers, workstations, printers, NAS)EternalBlue and NotPetya-style worm propagationLow
Enforce SMB signing and SMB encryption on serversNTLM relay and traffic tamperingMedium
Rotate local admin passwords automatically (Windows LAPS)Pass-the-hash and hash reuse across machinesMedium
Tiered admin model: domain admins only on jump serversAdmin hashes landing on ordinary workstationsHigh (process)
Disable admin shares where not needed and restrict the File and Printer Sharing firewall rule per profileRemote writes into ADMIN$/C$ from unexpected networksMedium
Firewall: block workstation-to-server SMB except approved admin pathsWorm spread and lateral movement at scaleMedium
Reduce NTLM; prefer Kerberos-only where possiblePass-the-hash and relay at the rootHigh
EDR on servers + collect 5140/5145 and Sysmon + deploy section 4 rulesDetection of every pattern aboveMedium
Immutable, offline backups with tested restoreBusiness impact when prevention failsMedium

Practical configuration checks

Run these checks on a lab server first. The first block verifies and removes SMBv1. The second block shows the SMB server hardening settings and how to drop the hidden shares on systems that do not need them.

powershell
# --- Check and remove SMBv1 (lab first, then change control) ---
Get-WindowsFeature FS-SMB1
Disable-WindowsOptionalFeature -Online -FeatureName SMB1Protocol -NoRestart

# --- Harden the SMB server configuration ---
Get-SmbServerConfiguration | Select-Object EncryptData, RejectUnencryptedAccess, RequireSecuritySignature
Set-SmbServerConfiguration -RequireSecuritySignature $true -Force
Set-SmbServerConfiguration -EncryptData $true -Force

# --- Check which shares exist, including hidden ones ---
net share

# --- Disable hidden admin shares on servers that do not need them ---
Set-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Services\LanmanServer\Parameters" -Name AutoShareServer -Value 0
Restart-Service LanmanServer -Force
Watch out: Disabling admin shares breaks some management and update tools. Test in a lab, and prefer the firewall-per-profile restriction when removal is too disruptive. Reboot or restart the LanmanServer service for the registry change to apply.

Layered defense flow

1. Patch and disable SMBv1→ 2. Harden credentials (LAPS, tiering)→ 3. Constrain SMB (signing, firewall)→ 4. Collect 5140/5145 + Sysmon→ 5. Detect with Sigma rules→ 6. Tune and rehearse

For home users and home offices

  • Never expose SMB to the internet. Port 445 must not be open on your router. Remote access belongs in a VPN.
  • Do not share folders publicly. If your NAS offers a "public link" feature, treat it like posting the files to a stranger.
  • Strong NAS passwords. Home NAS boxes hold whole drives behind one password — make it long and unique.
  • Disable guest access on the NAS and on Windows sharing settings, so nobody maps a share with an empty password.
  • Update the NAS firmware — consumer NAS devices have had serious SMB vulnerabilities, and worms scan for them.

Common Mistakes & Best Practices

The traps that real SOC teams fall into with SMB detection — and the habits that avoid them.

Most missed detections in this area are not exotic. They are collection gaps, wrong assumptions about field names, and thresholds copied from another network. Check your own environment against this table.

Watching only 5140 without 5145You see that a share was opened, but never which file was staged or read.Enable Detailed File Share auditing and collect 5145 from servers.

Best practices for day-to-day detection engineers

  • Enable Detailed File Share auditing and verify 5145 arrives from every file server and DC.
  • Run Sysmon everywhere, with at least events 1, 3, 10, and 11, and confirm servers report in.
  • Alert on executable writes to ADMIN$ or C$ — it is the highest-value single rule in this space.
  • Pair events into chains: 4624 Type 3, then 5145 write, then 7045, then Sysmon 1 under services.exe.
  • Baseline admin-share usage per account and per source host; treat first-time use as a candidate alert.
  • Watch for KeyLength 0 in NTLM Type 3 logons as a pass-the-hash hint.
  • Require SMB signing and track progress toward Kerberos-only authentication.
  • Keep SMBv1 off and verify it monthly with a report, not with memory.
  • Test every Sigma rule against a real event sample in your SIEM before calling it deployed.
  • Rehearse the response: know who isolates the source, who rotates the credentials, and who calls legal.
Final tip: Start with one rule — executable written to ADMIN$. Prove it works end to end, from event log to analyst playbook. Then add the rest. One working detection beats seven half-tested ones.
