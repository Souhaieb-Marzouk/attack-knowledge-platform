Overview

What the technique is, why it matters, and what this page teaches.

Plain-language definition

When malware gets onto a computer, the attacker still needs a way to send it orders and to receive stolen data. This channel is called command and control (C2). The technique T1102 - Web Service describes a C2 channel that runs through a legitimate public web service that businesses already trust and allow. Examples are paste sites with "raw" text pages, social networks, chat platforms with bot APIs, personal cloud storage, and code hosting sites.

The abuse works because the traffic looks normal. A workstation that talks to a well-known website is expected. The defender usually cannot just block the whole service, because real employees and real business processes depend on it. The malware often fetches ordinary-looking URLs and hides orders inside them. The orders may look like random text, sit inside image pixels, or appear as posts on a platform.

Why it matters

Web-service C2 gives attackers a stable, cheap, and hard-to-block channel. It survives IP blocklists, blends with daily browsing, and needs little attacker infrastructure. Both advanced state groups and mass-market malware use it.

Where it sits in the attack chain

It belongs to the Command and Control tactic (TA0011). An implant typically uses it after the initial infection. The same channel often also carries exfiltration — stolen files uploaded to a file host count as data theft over the C2 path.

What this page teaches

You will learn the three sub-techniques. You will watch an 8-step animated attack. You will see the exact log lines and Sigma rules that catch it, study a real case (APT29 HAMMERTOSS), and get a response checklist.

The three sub-techniques

The direction of the channel splits the family into three sub-techniques. The same abused service can appear in all three; what differs is whether orders go in, data goes out, or both.

IDNameWhat it meansTypical signalGuide
T1102.001 Dead Drop Resolver The malware reads a public page that holds an encoded pointer to the real C2 server. The public page is a "dead drop" — a fixed hiding place. Non-browser process fetching a paste-site raw URL on a schedule Open guide
T1102.002 Bidirectional Communication Orders flow in and results flow out through the same web service. Chat bots and social posts are common carriers. Regular polling of a bot API plus uploads of results Open guide
T1102.003 One-Way Communication Only one direction carries meaning — usually orders in, with no reply traffic. The implant acts silently. Repeated downloads from one account or page, no uploads back Open guide

This page covers the shared behavior of the whole family. Each sub-technique page adds direction-specific logic and rules. Read this page first if you are new to the topic.

Terms you will meet on this page

Every term is explained again where it appears. This grid collects them in one place so you can return here while reading.

C2 (command and control)

The channel an attacker uses to send orders to malware and receive answers or stolen data. Think of it as the attacker's remote control line.

Beacon

A regular check-in request the malware sends to its controller. Beacons often run on a fixed schedule, which makes them visible in history.

Dead drop

A fixed hiding place that both sides can reach — here, a public page holding an encoded pointer. The attacker writes, the malware reads.

Exfiltration

Stealing data out of the network. With T1102 it often rides the same web services, for example an upload to a personal cloud.

EDR

Endpoint Detection and Response — software on computers that records processes, files, and network connections, and can isolate the machine.

Sysmon

A free Windows add-on that writes detailed event logs, such as Event ID 3 for every network connection a process makes.

Proxy

A gateway that sees every outbound web request: who asked, which site, which path, how many bytes. The main evidence source for this technique.

CASB

Cloud Access Security Broker — a control that watches activity inside cloud services, such as uploads to storage apps.

TLS / SNI

TLS is the encryption of HTTPS. SNI is the hostname a client announces before encrypting — often the only name a defender can see.

OAuth

A permission system for apps. A malicious or over-privileged app can read company files without touching any endpoint.

Sigma

An open rule format for log detections. You write the logic once and translate it to your SIEM tool.

SPL

Search Processing Language — the query language of Splunk, a common log search platform.

Written story — the same 8 steps as text

This is the static text alternative to the canvas. Each step names what the attacker does and what the defender can see.

  1. 1 · Infection in place. A phishing email earlier infected the workstation WKSTN-4417 with a small backdoor. The malware sleeps and waits for its fixed evening time. Defender view: no network signal yet; only the mail-gateway phishing report points at risk.
  2. 2 · Beacon to the paste site. The malware wakes and sends an HTTP request to the raw endpoint of a public paste site. This first touch is its beacon. Defender view: the proxy shows a non-browser process fetching a paste-site raw page — rare and worth a look.
  3. 3 · Dead drop decoded. The fetched page looks like random text but holds an encoded pointer to the real C2 server. The malware decodes it in memory. This is a dead drop resolver (T1102.001). Defender view: a plain text download on the wire; content inspection or EDR memory rules are the only ways to see the decode.
  4. 4 · Real C2 contact. The malware connects to the attacker-owned C2 server whose address it just learned. Defender view: EDR, proxy, and DNS all record a first-seen domain or bare IP from a workstation process.
  5. 5 · Command through a chat service. The operator hides an order in a post on a public chat or social platform. The malware polls the platform API and reads it. Defender view: a python-requests or curl user agent hitting a bot API endpoint from a workstation is a classic T1102.002 pattern.
  6. 6 · Local recon runs. The malware executes the ordered command: it lists files, reads system info, and packs the results as text. Defender view: EDR sees a suspicious parent-child chain — PowerShell spawning whoami, ipconfig, and net commands within seconds.
  7. 7 · Upload to the file host. The malware archives the collected files and uploads the archive to a public file hosting service for the attacker to collect later. Defender view: tens of megabytes of bytes-out to a personal file host — a top exfiltration signal for proxy and CASB rules.
  8. 8 · SOC correlates and contains. The SOC joins proxy, DNS, and EDR events into one timeline, blocks the abused services, and isolates the host. Defender view: one proxy hit is noise; proxy plus non-browser process plus recon commands is a case. Block, isolate, then hunt the same pattern fleet-wide.

Red team / hacker perspective

Concept-level view of how attackers use web services for C2 — written so defenders can predict and detect it. This section is educational; it contains no working abuse recipe.

When and why attackers use it

  • Egress is locked down. Many offices allow HTTPS to popular sites but block unknown IPs. A public service rides the allow list.
  • Cheap and durable. Free accounts replace rented servers. Blocking one IP does not break the channel — the service stays up.
  • Blends in. Traffic to big platforms is normal. Volume hides the implant among thousands of real requests.
  • Distance. Content sits on a third-party host, so the attacker's own servers never touch the victim network.

Prerequisites an attacker needs

  • An implant already running on the target host.
  • Network egress from that host to the chosen service.
  • One or more attacker-controlled accounts or endpoints on the service.
  • A shared encoding scheme — a rule for hiding orders in posts, pages, or images.
  • Patience: most web-service channels are slow by design (polling intervals, rate limits).

How it is performed (concept level)

  1. Choose the service. Pick a platform the target network already allows: a paste site, a chat platform with a bot API, a social network, or a cloud file host.
  2. Set up the tasking point. Create an account, bot, or page that will hold the orders. This is where the attacker writes, the implant reads.
  3. Encode the channel. Wrap orders in something innocent: base64 text, an image with hidden pixels, or a filename. Encoding keeps casual readers from spotting the orders.
  4. Teach the implant the schedule. The implant polls or fetches at fixed times or intervals. Fixed timing keeps the traffic pattern small and regular.
  5. Collect results. For bidirectional channels, the implant posts results back — text replies or file uploads. For one-way channels, results are never sent back.

Blue team / SOC perspective

What defenders see, which artifacts the abuse leaves, and a short triage flow to run when an alert fires.

How defenders see it

You rarely see a single "this is C2" event. You see small oddities in different systems, and they only make sense together. Examples: a process that is not a browser fetching a paste page; a workstation polling a chat API; a sudden large upload to a personal cloud. The skill is correlation — joining two or three weak signals into one strong case.

Artifacts the abuse leaves

  • Proxy rows for the fetches and uploads, with user, host, domain, URI, user agent, and byte counts.
  • DNS queries for the service domains, sometimes at fixed intervals.
  • EDR network events that bind the connection to a process name, path, and user (for example Sysmon Event ID 3).
  • EDR process events for the commands the implant runs after receiving orders.
  • CASB and SaaS audit records when the channel uses cloud storage or a chat platform: logins, bot messages, downloads, and uploads.
  • File system traces: downloaded archives, decoded payloads in temp folders.

Note

Why it matters: web-service C2 keeps the attacker inside your network for months. Every extra day the attacker stays inside means more stolen data and more systems touched. Catching the channel early — at the first paste-site fetch — is far cheaper than cleaning up after exfiltration.

Fit in the attack chain: the web-service channel is the plumbing for everything after the first infection. It delivers tools (T1105), carries commands, and moves stolen data out (T1567.002). Blocking it cuts the attacker's hands off even if the implant survives.

Short triage flow

  1. Identify the process. From EDR, get the image path, user, and parent process of the client that made the web request. Browser? Expected tool? Or a scripting host?
  2. Check history. Does the same host fetch the same domain on a fixed schedule? Pull 7 to 30 days of proxy and DNS history.
  3. Inspect the request. Raw endpoint paths, bot API URIs, or odd user agents raise confidence. Note the exact URI and user agent.
  4. Look for the next hop. Did the host contact a new domain or bare IP shortly after? That supports a dead drop resolver.
  5. Hunt fleet-wide. Search all hosts for the same domain, URI pattern, and process pair. One host is an incident; many hosts are a campaign.
  6. Decide containment. If confidence is high: block the domains, isolate the host, and start the response checklist in Section 9.

5.2 Threat intelligence

Detections get better when they are aimed at real behavior. This subsection lists where intelligence comes from, how to process it, and the documented actors that abuse web services for C2.

Sources and method

  • MITRE ATT&CK — the shared language for the behavior. Start at the official page for T1102 and its sub-technique pages.
  • Vendor reporting — security company blogs and advisories that name tools and tradecraft, with dates you can cite.
  • OSINT — open sources such as malware sample repositories and researcher threads. Verify before you trust.
  • Commercial feeds — paid indicators and reports. Treat them as a shortcut to context, not as truth.
  • ISACs — sector sharing groups (finance, health, energy) that circulate member-verified behavior reports.
  • Internal telemetry — your own past incidents. The most under-used source; every old case is a free pattern.
  1. Collect. Pull reports that mention web-service C2, paste sites, bot APIs, or cloud staging.
  2. Analyze. Extract behavior, not just indicators: which process fetched what kind of endpoint, on what schedule, in which direction. Map each behavior to ATT&CK.
  3. Apply. Turn behavior into detections (Section 5.5), hunts (Section 4), and blocks (Section 7). Record detection coverage per actor.

How to read confidence levels

High

Two or more independent public sources describe the same behavior, or a vendor published technical detail (code paths, captured traffic). Safe to build a detection on.

Medium

One solid public source, or details differ between reports. Build the detection, but keep the threshold conservative and re-check the reporting.

Low

A single unverified claim or an inference from samples. Use for awareness and hunting hypotheses only — not for blocking.

5.4 Logs and patterns

For each major threat: the logs to collect, the fields that matter, what normal looks like, and the detection logic. Then six real-shaped event examples, each explained field by field. All hosts, users, and IPs are documentation examples.

THR-01 · Paste-site dead drop (Windows)

Log sources: Sysmon Event ID 3, EDR network events, proxy, DNS.
Key fields: Image, DestinationHostname, DestinationIp, User, Initiated.

Normal: browsers and office tools visit paste sites occasionally during work hours; user agents start with Mozilla.

Suspicious: a scripting host or system binary fetches a raw paste page; the same host touches a brand-new domain within a minute after.

Detection logic: alert on (process not in browser allow list) AND (destination in paste-site list). Separately, alert on the two-step pair "paste fetch, then first-seen domain" within 10 minutes.

THR-02 · Raw endpoint fetch by scripting host (Windows)

Log sources: proxy (URI visibility), Sysmon Event ID 3.
Key fields: url_domain, uri containing /raw/, user_agent, Image.

Normal: almost none for raw endpoints from servers; rare for workstations, always from a real browser.

Suspicious: python-requests, curl, Invoke-WebRequest signatures against raw paths; repeats at the same minute each day.

Detection logic: (raw path pattern) AND (user agent not browser) AND (count ≥ 3 in 24 h), grouped by host and process.

THR-03 · Server polling a chat-bot API (Linux)

Log sources: Suricata EVE HTTP, proxy, Zeek-like http logs, Linux auditd for process context.
Key fields: hostname (bot API host), uri (/bot…/getUpdates), http_user_agent, src_ip mapped to server VLAN.

Normal: zero consumer chat API traffic from server subnets; CI/CD (continuous integration and delivery) tools may post to approved webhooks from named hosts.

Suspicious: any getUpdates-style polling from a server; polling interval constant to the second.

Detection logic: (bot API hostname) AND (server subnet) AND (scripting user agent), with interval regularity as a score boost.

THR-04 · Large upload to personal cloud (Cloud)

Log sources: proxy, CASB, firewall flow totals.
Key fields: bytes_out, url_category, method (POST/PUT), url_domain.

Normal: approved sync tools with known user agents; business-hours uploads to the corporate tenant.

Suspicious: archive uploads to consumer hosts; single sessions above 50 MB to unapproved categories; uploads from servers.

Detection logic: sum bytes_out per user per destination category per day; alert over baseline + threshold; cross-check process on EDR.

THR-05 · OAuth app mass-downloads SaaS files (Identity/Cloud)

Log sources: Microsoft 365 unified audit (SharePoint/OneDrive workloads), CASB, identity protection alerts.
Key fields: Operation, UserId, UserType, ObjectId, ClientIP, UserAgent.

Normal: known backup, eDiscovery, and sync services download in bulk from named subnets during maintenance windows; humans download a handful of files per day.

Suspicious: a service principal (UserType 5 or 6) downloads hundreds of files from sensitive sites at an unusual hour, from a subnet the service never used, with a scripting user agent.

Detection logic: count file-download operations per identity per day; alert when the distinct-file count crosses the identity's baseline; boost severity when the site is sensitive or the subnet is first-seen.

THR-06 · Odd user agent to social pages (Network)

Log sources: proxy, Suricata EVE, Zeek.
Key fields: user_agent, url_domain, client_ip, request _time.

Normal: rich browser user agents with version churn; human gaps between fetches.

Suspicious: one exact user agent string, repeated daily, no referer, page never opened by a human session on the same host.

Detection logic: group by (host, domain, user agent) over 7 days; alert when the triple repeats daily with near-constant timing.

THR-07 · DNS bursts to short-lived paste domains (Network)

Log sources: DNS resolver logs, passive DNS.
Key fields: qname, client_ip, first-seen age of domain, TTL.

Normal: popular paste domains resolved by many clients slowly; TTL cache hits.

Suspicious: many new paste-like domains in one day; each resolved by one or two clients only; short TTLs.

Detection logic: per-day count of newly observed paste-pattern domains; alert on burst; use to hunt, not to page alone.

5.5 Sigma rules and Splunk SPL

Seven complete rules covering every threat ranked in 5.3. Each block gives a Sigma rule (vendor-neutral YAML), a matching Splunk SPL query, field-mapping assumptions, false positives, and tuning advice. Sigma is an open rule format for log detections; SPL is Splunk's search language. Replace index and sourcetype names with your own before running.

Rule 1 — Non-browser process connects to a paste site Critical · THR-01/02

  • Mapping note: Sigma Image, DestinationHostname, Initiated map 1:1 to Sysmon fields in XmlWinEventLog:Microsoft-Windows-Sysmon/Operational. If you ingest EDR network events instead, rename fields to your vendor schema (for example process_path, remote_domain). The SPL groups by host for triage; delete the stats line for a strict one-event-one-alert match with the Sigma rule.
  • False positives: scheduled automation that reads public text files; break-glass scripts. Keep an allow list of known admin paths and users.
  • Tuning: start in shadow mode for two weeks; export the (Image, DestinationHostname) pairs that fired; allow list legit pairs; then enforce. Add severity boost when User is a service account.

Rule 2 — Raw paste endpoint fetched by a scripting user agent High · THR-02

  • Mapping note: assumes Zscaler-style fields: url_domain (host), uri, useragent, user, client_ip, bytes_in. On other gateways these appear as cs-host, c-uri, cs(User-Agent). Adjust both the Sigma product tag and the SPL names to your gateway export. The SPL uses the same positive scripting-agent list as the Sigma rule; the 5-minute window with a count of 3 is a hunt threshold — remove the bin and where lines for strict one-event parity.
  • False positives: developer automation against gists; known data-loss-prevention or research crawlers from proxy egress.
  • Tuning: the regex on the user agent is the highest-precision part; keep it anchored (^). Exclude your source-code-review team's build subnet or specific user values after review.

Rule 3 — Linux server polls a chat-bot API High · THR-03

  • Mapping note: Sigma hostname/uri/http_user_agent correspond to Suricata EVE http.hostname, http.url, http.user_agent in suricata:eve. The rule fires on the same three conditions as the SPL (host, URI shape, agent); the SPL adds a hunt threshold of 10 polls over 10 minutes to confirm a live loop. Scope src_ip to your server CIDRs for the THR-03 intent.
  • False positives: alerting integrations that post to Slack or Discord webhooks from named automation hosts. Allow list those hosts by IP.
  • Tuning: require at least 10 polls over 10 minutes to confirm a live polling loop. Add an eval on interval regularity if you record deltas; constant-to-the-second intervals raise severity.

Rule 4 — Bulk upload to personal cloud or file host High · THR-04

  • Mapping note: the Sigma aggregation (sum of bytes_out per user over one day, over 100 MB) and the SPL one-day window compute the same thing; the SPL adds client_ip-free grouping plus sample URIs for triage. bytes_out must be the client-to-server byte count of the request body; some gateways expose it as sc-bytes inverted — verify the direction with one test upload. url_category values are gateway-specific; replace with your taxonomy.
  • False positives: large legitimate business uploads (media, backups to approved hosts). Keep an approved destination allow list and subtract it.
  • Tuning: 100 MB per user per destination per day is a starting line; baseline your real 95th percentile and set the threshold just above it. Cross-check the top hit's process on EDR to confirm it is not a browser upload.

Rule 5 — Service principal mass-downloads SaaS files High · THR-05

  • Mapping note: assumes Microsoft 365 unified audit logs via o365:management:activity. In that schema UserType 5 = Application and 6 = ServicePrincipal, so both sides of the rule select automation identities. The Sigma aggregation counts distinct ObjectId values per UserId per day — exactly what dc(ObjectId) does in SPL. If your normalization renames the field (for example user.type), adjust both rule and SPL. On other SaaS vendors use their download/count fields — the logic stays identical.
  • False positives: sanctioned backup jobs, eDiscovery exports, migration tooling. Maintain an approved service-principal list with expected volumes.
  • Tuning: the 100-files-per-day line is a starting point — measure your approved bulk readers and set per-identity baselines. Combine with an IP allow list: a known backup principal downloading from an unknown subnet is an immediate page.

Rule 6 — Same social page fetched daily by a scripting agent Medium · THR-06

  • Mapping note: the Sigma rule is per-event (any non-browser fetch of a social host); the SPL is the 7-day periodicity hunt from 5.4 — run both. The per-event alert gives early leads; the hunt confirms the fixed-schedule pattern before you open a case.
  • False positives: monitoring that screenshots social accounts; approved publishing tools. Allow list their hosts and agents.
  • Tuning: require the missing-referer check when your proxy records it; referer-less library fetches are the stronger half of the signal.

Rule 7 — DNS burst to paste-like domains from one client Medium · THR-07

  • Mapping note: Sigma counts matching queries per client over one hour; the SPL counts distinct queried names — the same intent, since repeat lookups of one name are cache behavior. Zeek dns.log fields are id.orig_h/query natively; both blocks assume they are normalized to client_ip/query. Adjust the regex to the paste-domain pattern you see in your region.
  • False positives: deliberate enumeration by research teams; sandboxes. Exclude their subnets.
  • Tuning: join the burst with passive-DNS first-seen age — domains younger than 7 days raise this from hunt lead to incident lead. Use it to corroborate THR-01/THR-02 alerts rather than to page alone.
Good practice

Test every rule before enforcing it. Replay the example events from 5.4 against your SIEM, confirm the alert fires with the right fields, then run in shadow mode for two weeks. A detection that has never fired on known-good data is a guess.

Case study: APT29 HAMMERTOSS

The clearest public example of T1102 done well: a Russian-state group that ran an entire C2 channel through Twitter and imgur. Reported by FireEye in July 2015 (high confidence for the tooling details).

Context

APT29 (also known as Cozy Bear, group G0016) targeted diplomatic and government organizations. In 2014-2015 their backdoor HAMMERTOSS stood out. Instead of renting C2 servers that defenders could block, it used Twitter for tasking, imgur for hidden commands and stolen data, and its companion tool CloudDuke used OneDrive accounts as storage. Public reporting described accounts that tweeted tasking data with specific hashtags, and images on imgur that carried commands inside pixel data (steganography — hiding one file inside another). The implant checked these accounts on a schedule, and reporting noted beacon variants tied to a fixed 18:00 evening time.

Note

FireEye's reporting covers the malware and its tradecraft. The victim-side incident response below (containment through lessons) is a clearly-labeled SOC reconstruction — a realistic, experienced-informed walkthrough of how a defender would have handled this chain, not a leaked incident report.

Timeline

Attack chain summary

  1. Spearphishing delivers the implant (initial access, outside T1102).
  2. Implant beacons at a fixed evening hour to public services (T1102 family behavior).
  3. Twitter hashtag tasking gives orders — inbound channel (T1102.003-style one-way, or T1102.002 when results flow back).
  4. Imgur image hides the actual command; implant decodes and executes (data encoding plus T1102.001-style resolution).
  5. Implant uploads screenshots and files to imgur — exfiltration over the same trusted services (aligned with T1567.002).
  6. Operator retrieves data at leisure; no victim-facing connection ever points at attacker-owned infrastructure.
Detection point

The chain is invisible per-request but loud in aggregate: one workstation, non-browser process, fixed evening fetch of social and image hosts, every day. Proxy correlation (same host + same platforms + same minute window) plus EDR process context (scripting host, no browser session) would have caught it within days. This combination — not any single event — is the detection.

SOC reconstruction — response walkthrough

Containment

  • Block twitter/imgur access for the affected host at the proxy; the channel dies even if the implant lives.
  • Isolate the workstation from the network while preserving memory for analysis.
  • Reset credentials used on the host, starting with the logged-in user.

Eradication

  • Collect the implant and scheduled task for analysis; identify the exact binaries.
  • Reimage the host rather than trusting on-disk cleanup.
  • Remove attacker content (posts, images, accounts) from your report to the platforms.

Recovery

  • Return the rebuilt host with EDR coverage verified and Sysmon enabled.
  • Monitor the user and host closely for two weeks; watch for re-tasking via new platforms.
  • Keep the proxy blocks in place; review monthly against business needs.

Impact and consequences

  • Screenshots and files left the network for an unknown period — treat as data breach until proven otherwise.
  • Attacker had code execution daily at a known time; assume credentials and documents were read.
  • Cost: rebuild, investigation hours, and reporting duties, all before any visible damage.

Team response and communication (reconstruction)

A realistic response assigns roles early. The case lead owns the timeline. The network analyst feeds proxy and DNS history. The endpoint analyst owns forensics and rebuild. Management handles legal, HR, and any breach-notification decision. The team communicates twice daily in a fixed channel, keeps a single evidence timeline, and writes the incident report while containment is still fresh. Leadership gets one clear message: the channel is cut, the host is contained, the hunt for other hosts is running.

Lessons learned

Fixed times are a gift

The 18:00 beacon pattern is easy to detect in proxy history. Schedule regularity is one of the cheapest high-value detections you can build.

Block raw paths, not platforms

You cannot block Twitter for marketers. You can block non-browser access to raw paste and image-host endpoints from servers — narrow rules keep the business running.

Correlate two sources minimum

Proxy alone says "someone browsed imgur". Proxy plus EDR process context says "PowerShell fetched imgur". Only the pair is a case.

Hunt by behavior

Indicators (hashtags, image IDs) change weekly. Behaviors — fixed-time fetch, non-browser agent, upload bursts — survive tool rewrites.

SaaS is part of the estate

CloudDuke showed storage services as C2 warehouses years before CASB tooling was common. Audit-log coverage is not optional.

Report to platforms

Abused accounts and content can be taken down. Platform trust-and-safety teams respond faster when you send exact URLs and timestamps.

Mitigation and defense

ATT&CK lists no way to "remove" a public web service — the defense is to make the abuse visible and to constrain what your hosts may do. The official ATT&CK mitigations for T1102 are M1021 - Restrict Web-Based Content (enforce external communication policy through web proxies) and M1031 - Network Intrusion Prevention (signature-based blocking at the network edge). The controls below implement both, grouped so an owner can be named for each.

Enterprise controls by group

ATT&CK mitigation mapping

M1021 - Restrict Web-Based Content: the Policy, Network, and Cloud groups below — proxy category rules, raw-endpoint blocks, and external-sharing limits all enforce external communication policy. M1031 - Network Intrusion Prevention: the Network and Monitoring groups — feed the Sigma rules in 5.5 to your IPS as signatures where the platform supports it, and alert on matching egress flows.

Policy

  • Write an acceptable-use clause that names paste sites, personal cloud, and chat bots on servers.
  • Require security review before any new OAuth app receives tenant-wide file permissions.
  • Define which teams may bypass web categories, and log every exception with an owner and expiry.

Identity

  • Inventory service principals and their permissions; remove broad file-read grants.
  • Enforce MFA and device checks for any identity that can mass-read storage.
  • Alert on new app consents with high-privilege scopes.

Endpoint

  • Deploy EDR with network event logging on all workstations and servers.
  • Turn on Sysmon with Event ID 1 and 3 coverage plus a baseline config.
  • Constrain PowerShell and block Office-child scripting where the business allows.

Network

  • Route all egress through the proxy; block direct HTTPS where feasible.
  • Deny non-browser processes to raw paste and image-host endpoints on servers.
  • Log DNS resolver queries centrally; watch for short-TTL paste-like domains.

Cloud

  • License a CASB or use built-in SaaS audit streams; ingest them into the SIEM.
  • Restrict external sharing on storage tenants; watermark sensitive sites.
  • Set per-identity download baselines and alert on deviations.

Logging

  • Centralize proxy, DNS, firewall, EDR, and SaaS audit logs with 12-month retention.
  • Keep time synchronized with a network time service (NTP) so cross-source correlation is trustworthy.
  • Document field names per source so rules survive vendor changes.

Monitoring

  • Run the seven rules in Section 5.5, in shadow mode first, then enforced.
  • Add bytes-out baselines per user and per destination category.
  • Review top talkers weekly; investigate new first-seen domains on servers.

Backup and response

  • Keep offline backups tested with restore drills — C2 often precedes destructive attacks.
  • Maintain an isolation runbook: who can isolate a host, and how fast.
  • Prepare a platform-abuse report template (URLs, timestamps, accounts) for takedowns.
Good practice

Home and small office: you may not have a proxy or a SIEM. Three things still work. Keep your router's DNS filtering on. Uninstall browser extensions you do not use. Treat any "PowerShell opened a website" warning from your anti-virus as worth a full scan. If a device starts uploading heavily, disconnect it from the internet and investigate.

Common mistakes and best practices

Twelve concrete mistakes blue teams make with web-service C2 detection — each with the symptom, the root cause, the fix, and the prevention that keeps it from returning.

1 · Blocking whole trusted platforms

Symptom: marketing and support file tickets the day a block lands; the block is rolled back.
Root cause: a rule without scoping hit everyone.
Fix: scope by process and endpoint type, not by domain alone.
Prevention: every egress rule lists allowed processes and user groups; changes go through review.

2 · Alerting only on known-bad IPs from feeds

Symptom: alerts fire on ancient botnet ranges, never on the live campaign.
Root cause: T1102 infrastructure changes weekly; IP lists lag.
Fix: shift rules to behaviors — process, endpoint shape, timing, volume.
Prevention: quarterly review of rule coverage versus ATT&CK behaviors.

3 · Ignoring bytes-out baselines

Symptom: exfiltration is discovered weeks later by finance, not by SOC.
Root cause: no volume model per user or category.
Fix: build the baseline, alert above the 95th percentile, test with a controlled upload.
Prevention: revisit baselines each quarter and after org changes.

4 · Trusting user-agent strings as truth

Symptom: a "browser" user agent hides an implant; a real browser update trips the rule.
Root cause: user agents are self-reported and spoofable.
Fix: join proxy user agent with EDR process identity before judging.
Prevention: document that agent fields are weak signals; never page on them alone.

5 · No network logging on servers

Symptom: the Linux rule (THR-03) has nothing to fire on.
Root cause: EDR or Sysmon-class telemetry never deployed server-side.
Fix: deploy network event logging to the server fleet in waves.
Prevention: build server coverage into the golden image and provisioning.

6 · Alert fatigue from generic "possible C2" alerts

Symptom: hundreds of low-value alerts per week; analysts skim and close.
Root cause: rules built on broad categories without conditions.
Fix: add the high-precision conditions (raw paths, scripting agents, fixed timing).
Prevention: every rule ships with false-positive notes and a tuning plan.

7 · Alerts with no owner

Symptom: a two-week-old critical alert sits unopened.
Root cause: rule deployed without routing or runbook.
Fix: map every rule to a queue, an owner, and a response SLA (a promised response time).
Prevention: deployment checklist requires owner sign-off before enable.

8 · SaaS audit logs kept too briefly

Symptom: investigation needs last month's download events; retention is 7 days.
Root cause: default SaaS retention, no export.
Fix: stream audit logs to the SIEM with 12-month retention.
Prevention: include SaaS sources in the retention policy, not just network logs.

9 · "TLS means we are blind"

Symptom: team assumes encrypted traffic prevents all detection.
Root cause: overlooking SNI/hostname metadata, process context, timing, and volume.
Fix: build the hostname-and-process rules in Section 5.5 that need no payload.
Prevention: document which detections work without TLS inspection.

10 · Allow-listing a whole vendor "because marketing uses it"

Symptom: one exemption grows into a permanent blind spot.
Root cause: exceptions without scope, owner, or expiry.
Fix: narrow the exemption to specific users, hosts, and destinations.
Prevention: every exemption expires automatically and needs renewal.

11 · Never joining proxy to EDR

Symptom: two teams hold half a case each and never meet.
Root cause: no shared key (host, time window) in the workflow.
Fix: build the correlation join into the alert itself (host + timestamp).
Prevention: case templates require both sources before escalation.

12 · Detections never tested

Symptom: rule "enabled" for a year; nobody knows it broke after a log format change.
Root cause: no validation pipeline.
Fix: replay the 5.4 example events monthly; alert on silence.
Prevention: purple-team exercises and pipeline tests in CI.

Habit lists

Daily

  • Review new high-severity proxy and EDR alerts with owner routing.
  • Check first-seen domains contacted by servers.
  • Confirm isolation tooling is reachable (test one action).

Weekly

  • Review top bytes-out users and unapproved categories.
  • Tune the noisiest rule; retire one useless rule.
  • Hunt one T1102 behavior (raw fetch, bot API poll, odd agent).

Monthly

  • Replay example events to prove rules still fire.
  • Review OAuth consents and service principal permissions.
  • Report rule coverage and fatigue metrics to leadership.
