MITRE ATT&CK · SUB-TECHNIQUE · SEARCH OPEN TECHNICAL DATABASES

T1596.005Scan Databases

Somebody has already scanned your network. Services like Shodan and Censys index the whole internet — your open ports, banners, and old appliances included. Attackers just search that index. This guide shows what they see, why it matters, and how to keep the list short.

  • Tactic: Reconnaissance
  • Platform: PRE (Pre-attack)
  • Parent: T1596
  • Created: October 2020
  • ATT&CK page ↗

What it is

Searching public internet-scan indexes for a victim’s exposed systems — with zero contact to the victim.

What attackers learn

Exposed services, software versions, banners, certificates, and devices with default passwords.

Why detection is hard

Indexing is continuous, distributed, and expected. The search itself leaves no victim-side trace.

Defensive start

Run your own external scans, alert on NEW exposures, and give every finding an owner.

1

Overview

This section explains what “scan databases” are, why attackers love them, and what this guide will teach you. No prior knowledge is needed — every term is explained on first use.

The idea in one minute

Companies run services on the public internet: websites, mail servers, remote access gateways, cameras, and more. To reach those services, you must first find them. Finding them means sending packets to IP addresses and watching what answers.

Some companies specialize in doing this for the entire internet. They scan all public IPv4 addresses on common ports, day after day. They record what answers: open ports, protocol banners, software versions, Transport Layer Security (TLS) certificates, and the organization that owns each address. They store all of this in a big searchable index — a scan database.

MITRE ATT&CK calls searching these indexes T1596.005 - Scan Databases. It belongs to the parent technique T1596 - Search Open Technical Databases, and to the Reconnaissance tactic. “PRE” means the activity happens before an attacker touches the target’s systems.

The key fact: when an attacker searches a scan database, no packet reaches your network. The attacker queries a third-party service. From your side, it is silent.

How internet-wide scanning works

  1. Sweep. The scanner sends a light probe (for example a TCP SYN) to every public IP address on a chosen port.
  2. Grab the banner. For addresses that answer, it waits for the small welcome text a service often sends. This text is called a banner. Many banners include product names and versions.
  3. Enrich. The scanner adds context: geolocation, the organization that owns the IP range, the routing network (ASN), and TLS certificate details for HTTPS services.
  4. Index. Everything is stored in a searchable database with a refresh cycle — popular services are re-checked every few days, less common ones less often.
  5. Serve. Anyone with a web browser (and sometimes a free account) can search the index.

What gets stored in the index

  • IP address, open ports, and protocol type
  • Protocol banners, often with product and version strings
  • HTTP response details, page titles, and technology fingerprints
  • TLS certificate subjects, issuers, and validity dates
  • Geolocation, organization name, and ASN (routing network number)
  • Historical views, so changes over time are visible

A banner is the short identification text a service sends when a client connects, for example a web server name or an SSH version line.

Small glossary

Internet-wide scan
A project that probes all public IP addresses on many ports and records what answers.
Banner
The identification text a service sends on connect. It often leaks a product version.
Index
The searchable database that stores scan results.
Netblock
A block of nearby IP addresses, written like 203.0.113.0/24.
ASN
Autonomous System Number — the ID of a routing network, for example one ISP or one company network.
Refresh cycle
How often a scanner re-checks one IP address or service.
Crawler
The scanning component that visits services. Web crawlers announce themselves with a user agent.
User agent
A text label sent in HTTP requests, for example Shodan or CensysInspect/1.1.
EASM
External Attack Surface Management — tools that continuously map an organization’s internet-facing assets and alert on change.
PRE
MITRE’s label for pre-attack activity: actions taken before any access is gained.

Where it fits in the attack chain

This is typically the first step of a planned intrusion, in the Reconnaissance tactic (PRE). It feeds later steps:

  • T1595 - Active Scanning: after the index, the attacker probes only the interesting targets, quietly.
  • T1592 - Gather Victim Host Information: banner and version data enrich the target list.
  • T1190 - Exploit Public-Facing Application: an exposed vulnerable service becomes the entry point.
  • T1133 - External Remote Services: exposed VPN or RDP becomes the door.

Its sibling sub-techniques under T1596 search other open sources: Domain Name System (DNS) records, WHOIS registration data, digital certificates, and content delivery network (CDN) data.

Good practice

Treat scan databases as a mirror. Whatever they show about you, an attacker can see too. If you look at that mirror regularly and fix what you find, the attacker’s list gets short — and old.

Written story — the same eight steps in text

  1. Step 1 — Search the index by organization. The attacker opens a public scan-database service in a browser and searches for the organization name org:"Ridgeline Utilities". The service returns a tidy list: internet-facing IP addresses, open ports, and product names. What the SOC sees: nothing. The query never touched Ridgeline.
  2. Step 2 — Review service banners. The attacker reads the stored banners. One Windows host answers on RDP port 3389, open to the whole internet. An old VPN appliance reports its firmware version right in the banner — and that version is years out of date. What the SOC sees: the same banners, if the SOC looks — crawler user agents like Shodan and CensysInspect appear in web logs as expected baseline noise.
  3. Step 3 — Find forgotten systems. A second query lists every service on Ridgeline’s address range. It shows a test FTP server with a default install page — a system nobody remembered. What the SOC sees: an EASM platform diff would have flagged this host as “new” weeks ago — if someone read the report.
  4. Step 4 — Spot default-credential devices. The camera banner reveals the exact model. That model ships with well-known default passwords. This is a flag for the attacker. What the SOC sees: IoT with default credentials is a critical finding — segment or replace it.
  5. Step 5 — Build the target shortlist. The attacker ranks targets: the VPN appliance first, because its old firmware has a known flaw; the RDP host second, for password guessing. What the SOC sees: internet-facing remediation should follow the same order — fix by exposure.
  6. Step 6 — SOC view: change detection. On the defender side, the EASM platform compares this week’s scan with last week’s and flags a new exposure. Crawler user agents remain in the web logs as a steady baseline — useful for correlating what changed. What the SOC sees: the early warning that the attacker already has this data.
  7. Step 7 — One careful verification probe. The attacker wants to be sure the index is current, so they send a single, quiet probe to the VPN appliance and read the banner directly. One packet. What the SOC sees: almost nothing — a lone connection among thousands. Assume indexed data is enough for attackers; do not wait to catch this probe.
  8. Step 8 — Defenders close the gaps. The SOC responds: the FTP server is closed, the VPN appliance is patched with multi-factor authentication (MFA) enforced, RDP moves behind the VPN, the camera is segmented. A weekly EASM review becomes routine. What the SOC sees: a shorter list in next week’s index — the goal of the whole exercise.

Red Team Perspective

This section explains how attackers and authorized penetration testers use scan databases, why the method is so popular, and where it goes wrong. Everything here is described for education and defense. Practice only against systems you own or have written permission to test.

Why attackers start here

  • Silent. The victim’s network sees nothing. There are no packets to detect during the search.
  • Cheap. A browser and a free account are enough. No attack infrastructure is needed yet.
  • Broad. One query maps a whole organization, ASN, or address range at once.
  • Historical. The index remembers the past, so changes and long-forgotten systems appear.
  • Safe for the attacker. Active scanning can be blocked or traced back to a source IP. A search cannot.

When it is used

  • PRE phase, target selection: pick victims by exposed technology, for example “utility with an old VPN”.
  • Before active scanning (T1595): narrow the list first, then probe only the shortlist. This cuts attacker noise a lot.
  • Before exploitation (T1190, T1133): match indexed versions against public vulnerability databases to pick a working exploit.
  • During operation: re-check the index to find newly exposed systems inside an already-compromised organization.

How a scan-database recon run looks

  1. Query by organization or ASN. Search the victim’s legal name, brand names, and routing network. This returns the known exposed surface.
  2. Read the banners. Collect product names, versions, and default pages. Note anything old, unusual, or administrative.
  3. Pivot. Use one finding to find more: the same netblock, the same certificate, or the same product across other customers.
  4. Match versions to vulnerabilities. Compare banner versions with public Common Vulnerabilities and Exposures (CVE) data — public IDs for known software flaws.
  5. Shortlist. Rank targets by ease and value: old remote access first, exposed admin panels second, weak IoT third.
  6. Verify sparingly. Optionally send one low-noise probe to confirm a banner. Every probe risks a victim-side log line, so good attackers keep this to a minimum.

Prerequisites: a normal web browser, a free account on a scan service, and one anchor value: the victim’s organization name, ASN, or netblock. No attack infrastructure is needed for this step.

Lab only — safe exercise

This exercise touches only your own organization’s assets and public documentation ranges. Do not query third parties, do not share API keys in screenshots or commits, and never use results to access a system you do not own.

  • Open a scan-database website in a normal browser. No API key is needed for a basic search.
  • Search for your own organization name, your public IP ranges, and your main domains.
  • Compare every result with your asset inventory. Each mismatch is a task: unknown service, unexpected version, or unexpected port.
  • If your organization has no public assets, search a documentation range like net:203.0.113.0/24 and expect no meaningful results — that range is reserved for examples.
  • In your own lab, grab banners from systems you own to see what a scanner would record.

Common variations

Netblock pivots

Instead of the org name, search the victim’s IP ranges. This catches subsidiaries, renamed companies, and cloud ranges the org search missed.

Banner-string searches

Search for one exact product string, for example an old appliance model. Attackers run these searches across the whole internet to build target lists for a single vulnerability.

TLS certificate pivots

Certificate Transparency (CT) log records and scan-index certificate entries link hostnames, internal names, and issue dates. One certificate often reveals a family of related, forgotten hosts.

Mistakes attackers make (and why they get caught)

  • Over-probing to “verify”. A burst of direct probes creates firewall and web logs. Silent recon dies the moment the attacker gets impatient.
  • Trusting stale data. Index entries can be days or weeks old. Attacks against patched or decommissioned systems waste time and can trigger intrusion alerts.
  • Ignoring defender parity. EASM platforms watch the same data. A new exposure the attacker enjoys is usually a new alert on the defender’s queue too.
  • Assuming the index is complete. Well-filtered perimeters, geo-blocking, and non-standard ports often do not appear in the index — and neither does internal scope.
  • Reusing third-party accounts. Search accounts leave their own trail at the scan service; careful operators separate their research identity from operations.

Blue Team Perspective

Here is the honest, slightly uncomfortable truth for defenders: the search itself is invisible. You cannot alert on a query that never touched your network. What you can see is the around-the-search activity — and, most importantly, the change the attacker is looking at.

What you cannot see

  • The search query on the scan-database platform
  • The attacker’s account, location, or intent
  • Banner reads of stored (cached) results

Do not build detections for the search. Build detections for the result: exposed services that should not be there.

What you can see

  • Crawler user agents in web and edge logs — for example Shodan and CensysInspect. This is expected, continuous baseline noise.
  • Periodic connections from crawler IP ranges in firewall and flow records.
  • Change — a new open service, a new banner, a new certificate. This is the key signal, caught by EASM platforms and by your own periodic scans.

Note — the key signal is change

Attackers and defenders read the same index. The winner is the side that reacts faster to diffs. If you know within hours that a new service appeared, you can close or harden it before an attacker even reads the next scan refresh. That race, not the crawler noise, is what this technique is really about.

Artifacts this technique leaves

  • Web or edge logs with user agent Shodan or CensysInspect/1.1 (and research tools such as zgrab)
  • Firewall and Zeek connection records to and from known crawler ranges, repeating on a schedule
  • EASM platform reports and diffs listing your exposed services over time
  • Your own vulnerability scan results — useful to compare against what the index claims
  • Occasional threat reports that mention a sector’s exposure being indexed

Where to look

Web / edge logs
Filter for crawler user agents. Build a baseline of how often they appear and from which ranges.
Firewall / flow logs
Look for repeating, polite connections from crawler ranges to many public hosts. They are normal; a sudden pattern change is not.
EASM platform
Review the weekly diff: new, changed, and disappeared services. Assign every finding an owner.
CMDB / asset inventory
Reconcile index results with the inventory. Unknown items are the highest-priority finding.
Vulnerability scans
Compare your authenticated scan versions with the banner versions in the index. Differences mean drift.

Why it matters

Scan-database recon is the shopping phase. Attackers pick their victims here, before any noisy action. If your exposures sit in public indexes for weeks, you are on a list. Closing exposures fast removes you from that list — and from the next automated campaign that targets a specific old version.

Attack-chain fit

T1596.005 is PRE-phase reconnaissance that powers later techniques: T1595 (active scanning of the shortlist), T1190 (exploiting the exposed application), and T1133 (abusing external remote services such as VPN and RDP). Detecting the downstream techniques is essential; detecting the exposure first is better.

Triage flow — a new exposure was reported

  1. Step 1Confirm the finding.

    Check the EASM diff or scan result. Is the service really reachable from the internet right now? Re-test from outside if possible.

  2. Step 2Find the owner and the purpose.

    Use the CMDB, change tickets, and cloud tags. Unowned is worse than unpatched.

  3. Step 3Classify: needed or forgotten.

    Needed services move to the hardening queue. Forgotten services go straight to decommission.

  4. Step 4Close or harden.

    Close what is not needed. For what stays: restrict source ranges, enforce MFA, remove verbose banners, put it behind a VPN or proxy.

  5. Step 5Patch on an exposure-based SLA.

    Internet-facing criticals get days, not months. A 72-hour target for critical internet-facing flaws is a common, realistic goal.

  6. Step 6Update monitoring and verify.

    Add the asset to monitoring, refresh the baseline, and re-scan to confirm the exposure is gone.

5.2

Threat Intelligence

Threat intelligence is information about attackers that helps you make better decisions. For this technique you need three things: awareness that exposed-device abuse is constant, sources that tell you which products are being targeted, and a way to act on both.

1. Collect

Pick sources you will actually read: ATT&CK for behavior, vendor reports for campaigns, your own logs for ground truth, one EASM view of your perimeter. Fewer, well-used sources beat many ignored ones.

2. Analyze

Ask three questions per item: Does it apply to our exposed products? Does it change our threat ranking (5.3)? Does it suggest a new detection (5.5)? Write one line of conclusion, or discard.

3. Apply

Turn conclusions into actions: a patch priority, a tuned rule, an EASM search, or a note in the risk register. Intelligence that produces no action is just reading.

Working with confidence levels

High
Verified against your own data or a primary source. Act now: patch, tune a rule, close an exposure.
Medium
Plausible but not verified, for example a vendor report about your appliance vendor. Track it and look for your own confirming signal.
Low
Rumor, single-report, or weakly sourced. Note it in the backlog; do not spend alerting budget on it.

State confidence explicitly in reports (“medium confidence, single vendor report”). Never present a feed item as fact without checking it against your environment.

Internet-exposed device targeting is a staple of both criminal and state-linked intrusion sets; ransomware crews favor exposed VPN and remote-access appliances, and opportunistic bots constantly harvest IoT devices. 5.3

Threats Ranking and Categorization

These are the six realistic threats that scan-database recon enables, ranked by how much damage they cause and how often they are used. Each is tagged with platforms: where the vulnerable system lives. The ranking assumes a mid-size organization with some internet exposure.

#ThreatPlatformsSeverity
T1Exposed remote access (RDP, SSH, VPN) discovered via scan databaseNetworkWindowsLinuxCritical
T2Exposed databases and admin panelsNetworkCloudCritical
T3IoT / OT devices with default credentialsNetworkOTCritical
T4Banner and version disclosure enables precise CVE targetingNetworkMedium
T5Forgotten test and development systemsCloudNetworkHigh
T6Legacy protocols (FTP, Telnet) still exposedNetworkMedium

T1 — Exposed remote access Critical

Description: RDP, SSH, or VPN endpoints visible in scan indexes, often without MFA.

Preconditions: port open to the internet; weak or no MFA; known appliance flaw.

Impact: direct entry path; credentials or an exploit give a foothold, then ransomware.

Justification: the most common serious intrusion path. Exposed RDP without MFA is a top ransomware entry point.

T2 — Exposed databases and admin panels Critical

Description: database engines or admin UIs reachable from the internet and visible in indexes.

Preconditions: service bound publicly; default or weak credentials; no access list.

Impact: direct data theft or full server compromise; indexes make these trivial to find at scale.

Justification: data at rest behind a public port with no MFA; automated bots harvest these within hours.

T3 — IoT / OT with default credentials Critical

Description: cameras, building controls, or industrial devices whose banners reveal models with public default passwords.

Preconditions: device indexed; default password unchanged; flat network access.

Impact: video or process exposure, and a pivot point into IT or OT networks.

Justification: in utility contexts a pivot toward OT is unacceptable; default passwords are public knowledge.

T4 — Banner version disclosure Medium

Description: verbose banners let attackers match exact versions to public CVEs before touching the target.

Preconditions: service reveals product and version in its banner.

Impact: precise, low-noise exploit selection; shorter attacker reconnaissance.

Justification: an enabler, not an entry by itself — it needs another weakness to exploit, hence Medium.

T5 — Forgotten test and dev systems High

Description: temporary systems spun up quickly and left public: test servers, staging copies, dashboards.

Preconditions: created outside change control; no owner; default install page visible.

Impact: weakly patched entry point, often with copied production data.

Justification: outside normal patch and monitoring coverage, so they age badly — High, not Critical, because they are often low-value.

T6 — Legacy protocols exposed Medium

Description: FTP, Telnet, and similar plaintext services still reachable and indexed.

Preconditions: legacy service kept for compatibility; no replacement deployed.

Impact: credentials captured in transit; unpatched software; easy footholds.

Justification: plaintext and abandonment make them risky, but they usually guard less valuable systems.

Note

Rankings are starting points. A Medium threat on a payment server outranks a Critical threat on a lab VM. Adjust with your asset values and the regulation drivers from 5.1.

change: "new"This service was not visible in the previous scan — the diff is the signal
asset.owner: "unassigned"No CMDB owner — the classic forgotten-system signature (T5)
service.bannerThe exact string an attacker would read, including product and version (T4)
first_seenISO 8601 timestamp of the first observation — drive your response SLA from it

Normal: an approved launch appears here once, with an owner and a matching change ticket. Suspicious: owner unassigned, or the same finding reappearing week after week.

Event sample D — firewall traffic records (JSON)

Pattern to alert on: one external source touching many distinct dst_port values in a short window — that is an active scanner (compare T1595), not a database lookup. Note the third line: an allow on port 21 proves the forgotten FTP (T5/T6) actually answered. Denied probes are background noise; allows to unexpected ports are the real finding.

5.5

Sigma Rules and Splunk SPL

Sigma is a free, open format for describing detections in YAML; most SIEMs can translate it. Splunk SPL is the Splunk search language. Each rule below comes as a Sigma YAML file plus a matching SPL query, with field assumptions, false positives, and tuning notes. All IP addresses are documentation examples — replace ranges and field names with your own.

RuleDetectsData sourceLevel
R1Known scan-database crawler user agents on public webWeb server logsLow (informational)
R2External port sweep against your public rangeFirewall / ZeekMedium
R3New externally exposed service (EASM diff)EASM platformHigh
R4Unexpected external connection to a newly opened portFirewall / cloud flowMedium

Honest scope note

R1 and R2 observe scanner activity; R3 and R4 observe the result that scan-database recon feeds on. None of them detects the database search itself — nobody can. R3 is the closest practical answer to T1596.005: the moment a service becomes indexable, you know at the same time the index does.

R1 — Known Scan-Database Crawler User Agents on Public Web Low

Purpose: build a baseline of crawler activity and correlate it with EASM changes. These hits are expected — route them to a dashboard, not to a pager.

Field assumptions

index=web sourcetype=access_combined follows the Splunk Add-on for Apache/Nginx, which extracts the user agent as http_user_agent and the client as clientip. Adjust names to your web add-on (for example src or useragent).

False positives

None — the pattern matches only the crawlers themselves. The real trap is the opposite: blocking these user agents at the web application firewall (WAF) and believing indexing stopped. It did not; other vantage points still see you.

Tuning

Do not alert — visualize. Add | timechart span=1d count BY http_user_agent to a weekly dashboard and read spikes next to your EASM diff. A new UA worth adding: *InternetMeasurement* and your EASM vendor’s crawler names.

R2 — External Port Sweep Against Public Range Medium

Purpose: catch active scanners probing your range — the step that often follows quiet index research. This does not fire on database lookups.

Field assumptions

index=firewall sourcotype=pan:traffic with fields src_ip, dest_ip, dest_port, action follows the Palo Alto Networks add-on. Adjust to your firewall TA (Cisco, Fortinet, or Zeek zeek:conn:json where action does not exist — use connection state instead).

False positives

Scheduled monitors, CDN health checks, penetration tests, and your own vulnerability scanner. Allowlist known scanner source ranges before go-live.

Tuning

Raise the threshold (>30 ports) if monitors trip it; lower the window to 1m for fast sweeps. Combine with the R1 dashboard: a sweep right after a crawler burst suggests targeted interest.

R3 — New Externally Exposed Service Detected High

Purpose: the core answer to this technique. Fire the moment any service becomes newly visible from the internet. This is what the attacker’s index will show next refresh.

Field assumptions

index=easm sourcotype=easm:alerts is a custom source, clearly marked as an example. Fields assume the platform’s JSON is auto-extracted (KV_MODE=json), so asset.ip becomes asset_ip. Rename to match your shipper; every commercial EASM can send JSON events to Splunk via HEC.

False positives

Approved launches, cloud autoscaling ports, and marketing campaign hosts. Correlate with change tickets in the alert workflow instead of suppressing broadly.

Tuning

Split severity by asset tags: Critical for unowned or OT-tagged assets, Medium for tagged and ticketed ones. Add a no-owner filter (owner="unassigned") as a separate, louder alert.

R4 — Unexpected External Connection to Newly Opened Port Medium

Purpose: catch the moment someone actually uses an unexpected public service — attacker verification probes and early exploitation both look like this.

Field assumptions

Same firewall fields as R2. service_baseline is a lookup table you maintain: one row per approved public port with approved=true. Refresh it monthly from the EASM inventory (see Section 7). If your firewall TA lacks direction, filter on your public dest_ip range instead.

False positives

Legitimate new services before the baseline update; health checks; partner APIs. The lookup makes tuning a data change, not a rule edit.

Tuning

Join with EASM tags in SPL (| lookup easm_assets dest_ip OUTPUT owner, asset_type) to raise severity for unowned assets. For high-value hosts, alert on a single connection instead of counting.

Good practice — validate before you trust

Test each rule in a lab: replay the sample events from 5.4 through your pipeline, confirm the rule fires, then confirm it stays quiet for normal traffic. From an external test VM you own, a single request with the user agent Shodan against your own web server safely exercises R1 end to end.

Real-World Case Study

The story below is a fictional composite written for training. It is built from patterns that appear repeatedly in public incident reporting, but the organization, dates, and numbers are invented. Any resemblance to a real incident is coincidental.

Warning — training scenario

“Ridgeline Utilities VPN appliance breach” is fictional. Use it to practice triage, communication, and detection design — not as a factual report about any real organization.

Context

Ridgeline Utilities is a mid-size energy and water utility (fictional). It runs office IT, a corporate data center, and a segmented OT network for plant control. Remote workers connect through a VPN appliance at the perimeter. The security team is small: four SOC analysts, one detection engineer, and an IT team that also handles security tickets when time allows.

Timeline — how the incident unfolded

TimeEvent
T-30dThe weekly EASM report flags the VPN appliance: outdated firmware version visible in public indexes. The ticket lands in a shared queue with no owner.
T-21dAn attacker (unnamed criminal group) searches a scan database for the utility’s organization name and netblock. The appliance, its version, and several forgotten hosts appear in the results. The victim sees nothing.
T-14dThe attacker sends one verification probe to the appliance and reads the live banner. One allowed connection in the firewall log — no alert exists for it.
T-0The attacker exploits a known flaw in the appliance web interface and gains appliance-level access.
T+1dNew local admin accounts appear on the appliance; MFA is quietly disabled for one test account.
T+3dThe attacker uses stolen VPN sessions to reach file servers; reconnaissance of the IT network begins.
T+7dData staging: archives are collected on a forgotten test server — the same class of system the EASM report had flagged.
T+13d detectionThe SIEM correlates two signals: the EASM inventory lists the outdated appliance, and the auth log shows VPN admin logins from an unusual country at an unusual hour. The SOC investigates.
T+14dContainment: the appliance is isolated, all remote access is disabled, and forced password resets begin.
T+21dEradication and recovery complete: appliance patched and replaced, credentials rotated, systems restored from verified backups.
T+30dLessons-learned review closes. A weekly exposure review with named owners becomes policy.

The attack chain

  1. T1596.005: organization and netblock search in a scan database — silent.
  2. T1595: one verification probe to the shortlisted appliance.
  3. T1190: exploitation of the public-facing appliance flaw.
  4. T1133: abuse of the external remote service for access and persistence.
  5. Lateral movement and staging on the IT network, ending in ransomware deployment.

Operations were disrupted for four (fictional) days. The OT network was spared — segmentation held.

The detection point

The breakthrough was not a single clever rule. It was a correlation. Signal one: the EASM inventory flagged the asset as outdated. Signal two: abnormal admin authentication on that same asset. Either signal alone sat in noise; together they were decisive. Thirteen days of dwell time is the price of ignoring the T-30d exposure ticket.

Containment

  • Appliance isolated from the network; remote access disabled org-wide.
  • Attacker-known credentials forced to reset; all active VPN sessions killed.
  • Firewall blocks added for attacker infrastructure observed in logs.

Eradication

  • Appliance firmware patched; model replaced at the next maintenance window.
  • Credential rotation across VPN, admin accounts, and service accounts.
  • Persistence hunt: unauthorized accounts removed, scheduled tasks and startup items audited.

Recovery

  • Staged restoration from verified, offline backups — cleanest systems first.
  • Two weeks of enhanced monitoring on remote access and lateral movement paths.
  • Weekly EASM review adopted with named owners and a 72-hour critical-fix SLA.

Impact and consequences

  • Four days of operational disruption (fictional); billing and customer portal downtime.
  • A regulatory report filed with the (fictional) utility regulator; customer advisory published.
  • No OT impact — network segmentation prevented the spread.

Team response and communication

The SOC led containment with a pre-agreed playbook; IT executed patching and resets; leadership handled the regulator and the customer advisory within two days. One person owned external communication so engineers could work. The incident bridge ran twice daily until recovery closed.

Lessons learned

  • EASM reports need owners and SLAs. A finding in a shared queue is a finding nobody owns.
  • Patch internet-facing systems in days. The T-30d flag was accurate; the response was not.
  • MFA on all remote access — and monitor for MFA being disabled.
  • Banner hygiene matters. The appliance advertised its own obsolescence.
  • Segmentation saved the OT network. Fund it and test it.

Mitigation and Defense

You cannot stop internet-wide indexing, so the goal is simple: make the index boring. Fewer exposures, fresh versions, quiet banners, and a fast reaction to change. The controls below are grouped by area; the priority table at the end tells you what to do first.

Policy

Write an exposure management standard: every internet-facing asset needs an owner, a purpose, and a review date. Set a patch SLA for internet-facing systems — for example 72 hours for critical flaws.

Identity

MFA on every remote access path: VPN, RDP gateways, SSH bastions, admin panels. Alert when MFA is disabled for any account, even briefly.

Endpoint

EDR on all servers that host public services. Hardening baselines that disable unused components and remove version banners where feasible.

Network

Default-deny at the perimeter; publish only what must be public. Segment IoT and OT away from user and server networks. Move RDP and SSH behind a VPN.

Cloud

Run cloud security posture checks for public buckets, open security groups, and unexpected load balancers. Tag internet-facing resources so EASM diffs can be attributed fast.

Logging

Retain web/edge, firewall, and flow logs — the crawler baseline and the R4 rule live there. Ship EASM alerts into the SIEM like any other log source.

Monitoring

EASM diff review on a fixed cadence; new-exposure alerts with owners; the four rules from Section 5.5 tuned and tested.

Backup

Tested restores for everything that faces the internet. An exposure you cannot afford to lose must have a backup you have actually restored at least once.

Response

A short playbook for “new exposure detected”: confirm reachability, find the owner, close or harden, verify, and record. Rehearse it once a quarter.

Home and small-office advice

  • Open your router’s admin page and check what is forwarded to the internet; remove forwards you do not recognize.
  • Disable UPnP if you do not need it — it opens ports by itself.
  • Update router and camera firmware; old firmware is what the index loves.
  • Do not expose NAS or camera web interfaces directly; use the vendor’s app or a VPN.
  • Change every default password, especially on cameras and storage boxes.

Prioritized actions

ActionEffortOwnerExpected risk reduction
