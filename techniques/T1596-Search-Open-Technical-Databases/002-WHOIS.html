T1596.002WHOIS

Every domain carries a public paper trail. A WHOIS query shows who registered it, when, and through which registrar. Attackers read that paper trail to map a company, find related domains, and catch names about to expire. This guide shows the query, the risk, and the defenses.

Tactic: Reconnaissance Platform: PRE (Pre-attack) Parent: T1596 Created: October 2020 ATT&CK page ↗
What it is Asking public registration databases about a domain. The classic way is the WHOIS protocol on TCP port 43. The modern way is RDAP, which returns JSON over HTTPS port 443.
What attackers learn Registrant organization and contacts, registrar, name servers, creation and expiry dates, status codes, and — through reverse WHOIS — every domain that shares a contact.
Why detection is hard The data is public on purpose. Queries hit registrar servers, not yours. Your best signals are WHOIS tools running on your own endpoints and third-party alerts about your own brand.
Defensive start Turn on WHOIS privacy, registrar lock, and auto-renew for every domain. Use role-based registration emails. Alert when whois or RDAP tools run inside your network.

Overview

This section explains WHOIS in plain words. You will learn what a WHOIS record shows, who runs the service, why attackers read it, and which words you will meet in this guide.

What WHOIS is

When a person or a company registers a domain name, the registrar must keep some details about that registration. WHOIS is a simple, old directory service that lets anyone ask for those details.

The classic way works like a phone call: a client program connects to a WHOIS server on TCP port 43, sends a domain name as plain text, and receives a plain-text record back.

The modern replacement is RDAP (Registration Data Access Protocol). It answers with structured JSON over HTTPS on port 443, so it works better with scripts and with web browsers. New WHOIS lookups often use RDAP behind the scenes.

Why it matters

Attackers use WHOIS during reconnaissance — the stage where they study a target before any attack. One query can reveal an organization's domain portfolio, its naming habits, its vendors, and its weak spots.

For defenders, the same public data is a mirror. It shows exactly what an attacker can learn for free. Reading your own records is one of the cheapest security checks you can run.

There is a catch for detection: the queries never touch your network. They go to registrar servers. You can only see WHOIS activity when it happens inside your estate, for example an endpoint running a WHOIS client.

Reverse WHOIS: one contact, many domains

A normal WHOIS query starts from a domain. A reverse WHOIS search starts from a contact detail and lists every domain that mentions it. Attackers love this, because companies often reuse one admin email or one legal name across dozens of registrations.

Search keyWhat it usually revealsDefensive takeaway
Registrant emailEvery domain registered with that address, often across years and registrars.Use role-based addresses like dns-ops@company.example, never personal mailboxes.
Organization nameCurrent and past holdings, including renamed subsidiaries.Accept that the group name is public. Track what it exposes.
Name serverAll domains hosted on the same DNS provider account.Segregate DNS hosting for sensitive brands if needed.
Street address or phoneOlder records, especially historical snapshots from before privacy rules.Prefer postal proxies; check historical archives for legacy data.

Where this fits in the attack chain

In MITRE ATT&CK terms, this sub-technique sits in the Reconnaissance tactic and runs on the PRE platform, meaning before any victim system is touched. It is one of the search options inside the parent technique T1596 Search Open Technical Databases.

The results feed later steps of a real intrusion:

  • Infrastructure decisions — registration dates and name servers guide which domains an attacker buys or imitates (see T1583 Acquire Infrastructure).
  • Target profiling — registrant contacts enrich profiles of people and subsidiaries (see T1589 Gather Victim Identity Information).
  • Phishing setup — a lookalike or an expiring domain becomes a believable sender (see T1566 Phishing).
  • Targeted questions — registration details support crafted requests for information (see T1598 Phishing for Information).
Key takeaways
  • WHOIS data is public by design. Assume everything in your records is readable by attackers.
  • The dangerous fields are contacts, name servers, and — above all — the expiry date.
  • Reverse WHOIS turns one careless email into a map of your whole portfolio.
  • You cannot stop the queries. You can shrink what they return and watch for abuse of your brand.

Written version of the simulation

The list below is the same story in words. It covers every animated step, so nothing is lost if you cannot use the canvas. You can also jump straight to it.

  1. Step 1 — The target is picked. On a recon virtual machine, the attacker runs a WHOIS query for atlashealth.example. The request travels across the internet to the registrar WHOIS server on TCP port 43. Defender view: none — the query hit the registrar's server, not your network.
  2. Step 2 — The record comes back. The server answers with the public record: registrant organization Atlas Health Group, an admin email, the name servers, the creation date, and the expiry date. The attacker now knows who owns the domain and how it is hosted. Defender view: this data is public by design; minimize it with WHOIS privacy and role-based emails.
  3. Step 3 — Reverse WHOIS pivot. The attacker feeds the admin email into a reverse WHOIS service. It returns three related domains, including an old vendor portal that the company forgot about. One contact detail mapped the whole portfolio. Defender view: reverse WHOIS on your email leaks every domain that mentions it — use role-based registration emails.
  4. Step 4 — Expiry check finds a weak spot. The attacker checks dates on each related domain. One, grants.atlashealth.example, expires in 9 days. It has no auto-renew and no registrar lock. That is an open door. Defender view: registrar lock plus auto-renew removes this window entirely.
  5. Step 5 — Watch and wait; the domain drops. The attacker sets a watch on the domain and waits. Nobody renews it. The registration lapses and the name becomes available to anyone, anywhere, within seconds. Defender view: silence while the attacker waits — this is exactly why domain hygiene matters before the drop.
  6. Step 6 — Re-registration and mail hijack. The attacker registers the dropped domain through a fast registrar, points its MX records (the mail routing rules in DNS) at their own mail server, and puts up a clone of the old portal. Mail for that domain now flows to the attacker. Defender view: brand monitoring plus certificate transparency watching catch this within hours.
  7. Step 7 — Defenders see it. The SOC (Security Operations Center) brand monitor flags a new registration containing the company name. At the same time, a new TLS (Transport Layer Security) certificate for the domain appears in public Certificate Transparency logs. The SOC correlates the two alerts and sees the MX change. Defender view: correlate new registrations and new certificates for your brand strings into one case.
  8. Step 8 — Response. The team files an abuse report with the registrar, starts a UDRP dispute (the arbitration process for domain ownership), audits mailboxes for mail that was silently swallowed during the drop, and re-secures every other domain in the portfolio. Defender view: check mail logs for messages you may have missed during the drop window.

Red Team Perspective

This section explains how security testers and attackers use WHOIS, and why. Everything here is for learning and for authorized testing in your own lab. Use it to understand the attacker's notebook, not to attack anyone.

When and why attackers use it

  • Early mapping. WHOIS needs no access to the target. It is usually one of the first steps, long before any exploit.
  • Portfolio discovery. Reverse WHOIS turns one contact into a list of related domains, subsidiaries, and forgotten projects.
  • Phishing personalization. Real registrant names, dates, and vendors make fake emails more believable.
  • Timing attacks. Expiry dates show which names will lapse soon. A dropped domain can be registered legitimately.
  • Infrastructure choices. Name servers and registrars show which providers the target trusts. Some name server patterns also reveal a content delivery network (CDN) or a web application firewall (WAF) in front of the site. Both facts guide lookalike setups.

Prerequisites and effort

The barrier is almost zero, which is why this sub-technique is so common:

  • A network connection and a domain name to query. No accounts, no cost.
  • Optional: free RDAP endpoints, or paid reverse-WHOIS and monitoring services for deeper pivots.
  • Optional: automation scripts for bulk lookups, since rate limits are the main limit.

Where it applies: any target that owns domain names — which is effectively every organization. The technique runs on the PRE platform, before victim contact.

How the lookup is performed

MethodTransportWhat it givesNotes for defenders
WHOIS client (whois CLI) Plain text over TCP port 43 Full record for one domain, straight from a registry or registrar server. Client execution is visible on endpoints — endpoint detection and response (EDR) tools and process logs both see it. The network flow to port 43 is visible on egress.
Web WHOIS pages HTTPS Same data in a browser form, often with extra history and monitoring offers. Visits appear in proxy logs. Easy to miss among normal browsing.

Reverse-WHOIS services HTTPS web apps and APIs Every domain matching an email, name, or keyword. The portfolio pivot. Invisible at your edge. Third-party monitoring of your brand is the counter.

Lab only — authorized targets

Run the commands below only against domains you own or that are published for testing, such as example.com. The goal here is to understand what the output looks like, so you can shrink what your own records reveal. Do not use these techniques against systems you do not have permission to assess.

Variation: historical snapshots

Commercial archives store old versions of records. Privacy redaction only hides the present. Attackers look for old personal emails and names, then pivot on those in reverse-WHOIS databases.

Variation: registrar-specific lookups

Thin-model registries return only a pointer to the registrar. The attacker repeats the query against the registrar's own WHOIS server. Some registrars expose more detail than the registry does.

Variation: brand-adjacent enumeration

Instead of starting from known domains, the attacker searches WHOIS keyword fields for the brand string and tries common shapes: brand-vendors, brandportal, brand-research. Forgotten names surface here.

Common attacker mistakes

  • Personal infrastructure. Running lookups from home IPs and personal accounts links the attacker's identity to the research. Professionals use burner VMs and shared services.
  • Trusting redacted fields. Post-GDPR records show proxy data. Attackers who treat a privacy service as the real registrant waste pivots on dead ends.
  • Ignoring drop-catch competition. Expired domains are snatched within seconds by automated services. An attacker who waits manually usually loses the name — or gets it and inherits attention from researchers who track drops.
  • Noisy bulk queries. Hundreds of scripted lookups from one host trip rate limits and, on compromised endpoints, trip detections like the ones in section 5.

Blue Team Perspective

Defenders cannot see queries that attackers send to registrar servers. But WHOIS activity inside your own walls — and abuse of your brand outside — does leave traces. This section shows where to look and how to triage what you find.

Set expectations first

A stranger running whois yourcompany.example from a coffee shop is invisible to you and harmless by itself. Your detection goals are narrower and achievable. First, notice WHOIS tooling running on your endpoints. Second, notice unusual port-43 or RDAP traffic leaving your network. Third, notice when someone else registers, certifies, or re-points your brand names.

What visibility you actually have

Endpoint telemetry

If an internal host runs a WHOIS client, your EDR or Sysmon logging sees the process: the image path, the command line, the user, and the parent process. This is the strongest internal signal.

Network telemetry

Outbound TCP/43 traffic is rare in normal business and stands out in firewall, Zeek, or NetFlow data. RDAP and web-WHOIS visits blend into HTTPS, but proxy logs still show the destination URL.

Third-party signals

Registrar notices, brand monitors, newly-registered-domain feeds, and Certificate Transparency logs report what happens to your names on the outside. They are your eyes where you have none.

Artifacts this technique leaves behind

ArtifactWhere it appearsWhat it tells you
Process creation with whois.exe or shell whois Sysmon Event ID 1, EDR process logs, shell history An insider or an intruder is collecting registration data from inside. Check what domains were queried and why.
Connections to remote TCP port 43 Zeek conn.log, firewall logs, NetFlow Classic WHOIS protocol use. Normal for almost no business role. One lookup is curiosity; a pattern is recon.
Proxy requests to rdap.org, registrar WHOIS pages, reverse-WHOIS panels Proxy / web gateway logs Someone prefers web or JSON lookups. Note the user, the queried domains, and the hour.
Registrar notification emails Mailbox of the registration contact Lock changes, transfer attempts, expiry warnings. If nobody reads these mailboxes, you learn it only after an incident.
New registration or certificate matching your brand Brand monitors, NRD feeds, Certificate Transparency logs Someone registered a name that looks like yours, or obtained a certificate for it. The first visible step of a hijack or impersonation.

Why this matters to the SOC

WHOIS sits at the quiet start of the attack chain. Nobody breaches a firewall with it, but nearly every serious intrusion against a company starts with the attacker knowing the company's names, vendors, and dates. When you catch WHOIS recon from inside, you usually catch the planning phase of something bigger: insider misuse, an intruder staging reconnaissance, or a well-meaning employee about to paste data into a shady open-source intelligence (OSINT) website. When you catch third-party registrations of your brand, you catch hijacks before mail starts flowing to the wrong server.

Triage flow: a whois.exe alert just fired

Step 1 · 2 minutes

Identify the host and user

Which machine ran the client, under which account, and from which parent process? A server or a service account is more worrying than a developer workstation.

Step 2 · 3 minutes

Check user intent

Read the full command line. Is the queried domain your own, a partner's, or something unrelated? Ask the user if the context is unclear. Most alerts end here as legitimate research.

Step 3 · 5 minutes

Look at the queried domains

A list of your own brand names, checked in sequence, is a different story from one lookup. Repeat queries for many domains suggest mapping — treat as suspicious recon.

Step 4 · same day

Correlate with brand monitoring

Cross-check the queried domains against NRD feeds and registrar alerts. If someone outside also probed these names recently, escalate.

Step 5 · same day

Check registrar lock status

If the recon touched your portfolio, verify locks, auto-renew, and privacy on the affected names before closing the case. Recon today, hijack next month.

Step 6 · close or escalate

Respond to fit

Benign one-off: close with a note and tune the rule. Mapping pattern: open a case, preserve artifacts, involve IT and domain owners. Confirmed insider recon: involve your insider-threat process.

Blue team habits that pay off
  • Keep a domain inventory with owners, registrars, expiry dates, and lock status — it turns every WHOIS alert into an answer instead of a hunt.
  • Forward registrar notification mailboxes into your ticket system so lock and transfer notices never die unread.
  • Treat TCP/43 egress as "allowed for named teams only" — then any other source is a small, high-signal alert.

5.1

Regulation Mapping

Auditors rarely ask "is your WHOIS safe?" They ask whether domains are managed assets, whether personal data is minimized, and whether registrar access is controlled. The mapping below gives you the control language for each framework and the evidence you can show.

5.2

Threat Intelligence

WHOIS abuse is not tied to one actor. Drop-catching services, fraud kits, and criminal ecosystems all use registration data. Instead of chasing names, build a small collection plan: know the sources, what each one gives you, and how much to trust it.

Treat confidence as High when…

  • The event is in your own logs (EDR, proxy, Zeek).
  • The registrar itself reports a change to your domain.
  • ATT&CK describes the technique behavior itself.

Treat confidence as Medium when…

  • A feed flags a brand match that still needs a human look.
  • An ISAC relays a peer report without full detail.
  • A vendor names a campaign but evidence is thin.

Treat confidence as Low when…

  • Redacted WHOIS fields are your only pivot.
  • A keyword match could be coincidence (common words).
  • Historical data is years old and unverified.

Known abuse patterns and actors

Keep the phrasing honest and generic. No single named group owns this technique; several criminal ecosystems feed on registration data. Three patterns come up again and again in public reporting:

  • Expired-domain hijacking with mail interception. Public incident reports describe it repeatedly: a lapsed domain is re-registered and its mail is quietly captured. Medium-High confidence
  • Lookalike and BEC registration abuse at scale. Fraud kits register names one edit away from real brands and use them for payment fraud and credential theft. High confidence
  • WHOIS redaction since GDPR (2018). Privacy rules stripped personal data from most records, so lookups today return far less than they did before. High confidence

Specific actor mappings change over time — check the official ATT&CK page for this sub-technique for current group and software references, and let your ISAC tell you which campaigns touch your sector.

Collect

Pick three sources to start: registrar notifications, one NRD feed filtered by brand strings, and your own EDR/proxy telemetry. Wire them into your ticket queue, not into a folder nobody reads.

Analyze

Score each hit with the confidence levels above. A new registration matching your exact brand is High interest. A match on a common word is Low. Time-box the review: ten minutes a day is enough.

Apply

Feed confirmed findings into three places: the risk register (section 5.1), detection tuning (section 5.5), and the response playbook (section 7). Intelligence that changes nothing is decoration.

Threats Ranking and Categorization

Here are the six realistic ways this sub-technique turns into harm. Each has a severity, the platforms where it lives, and the reason for the rating. Severity reflects realistic worst-case impact for a typical organization, not just technical elegance.

1 · Domain drop / expiry hijack Critical Identity Network

A domain with public expiry data, no auto-renew, and no registrar lock lapses. A drop-catcher registers it within seconds. The new owner controls its DNS — including the MX records that decide where the domain's email goes.

Preconditions
Expiry date visible in public data; auto-renew off or payment failure; no registrar lock; registration contact mailbox unmonitored.
Impact
Full mail interception for the domain, cloned web services, believable sender identity, lost invoices and contracts.
Why this rating
It is a complete compromise of a domain's email plane with no malware and no exploit — just a calendar gap. Attack chains from real BEC cases start exactly here.

2 · BEC and brand impersonation High Identity

Harvested registrant names, emails, and dates give a fake message or portal the ring of truth: correct legal names, real vendor relationships, plausible timelines.

Preconditions
Registration data exposed (no privacy), plus a payment-fraud or credential-harvesting motive.
Impact
Persuasive phishing and invoice fraud that passes casual review; reputational damage when customers are targeted in your name.
Why this rating
BEC is one of the costliest crime types by losses, and personalized registration data measurably improves the bait.

3 · whois CLI from an internal host High Windows Linux macOS

With a foothold or a malicious insider, the WHOIS client becomes a quiet recon tool: no target-side alerts, no scanning, just public records fetched from your workstation.

Preconditions
Endpoint access (compromise or insider) and a WHOIS client available or downloaded.
Impact
Portfolio mapping, partner discovery, and timing data feeding the next stage of an intrusion.
Why this rating
The activity itself is low-impact, but it is a reliable early indicator of hands-on-keyboard recon — catching it early is worth a High.

4 · Reverse WHOIS corporate mapping Medium Identity

One reused registration contact links subsidiaries, acquisitions, vendors, and abandoned projects into a single map for the attacker.

Preconditions
The same email, name, or organization string on multiple records; historical data strengthens it.
Impact
Wider target surface, forgotten weak domains, better social engineering context.
Why this rating
It rarely causes harm alone, but every later technique gets cheaper and quieter.

5 · Bulk RDAP portfolio scraping Medium Network

RDAP is JSON over HTTPS and easy to script. Automation can enumerate every name in a portfolio, plus dates and statuses, in minutes.

Preconditions
A list of known domains (from threat 4) or brand keywords; no access needed.
Impact
Fresh, structured portfolio data including expiry dates — the shopping list for threat 1.
Why this rating
Same outcome as reverse WHOIS with better structure; defender visibility is poor, but impact is preparatory.

6 · Name server enumeration Low Network

Name server fields reveal which provider hosts DNS for each domain, and sometimes that one account or provider is shared across the estate.

Preconditions
Any WHOIS or RDAP access; nothing else.
Impact
Guidance for follow-on attacks: provider outages to watch, shared nameservers to target, hosting relationships to imitate. The same data helps attackers match exposed services to known Common Vulnerabilities and Exposures (CVE) entries.
Why this rating
Useful context, but by itself it changes no security posture. Keep it listed so future detections make sense.
5.4

Logs and Patterns

For each threat: where the evidence lives, which fields matter, what normal looks like, what suspicious looks like, and the detection logic in one line. Event samples are JSON-shaped and use the fictional Atlas Health Group world.

Threat 1 · Domain drop and MX hijack

Log source
Registrar / registry notifications, NRD feeds, your DNS provider change logs, mail-flow (MX) monitors.
Key fields
domain, event (registration, nameserver or MX change), registrar, created, mx_host.
Normal
Registrations and record changes for your own names, made by named admins, through your registrar, during work hours.
Suspicious
A brand-matching name registered by someone else; an MX change on any of your domains that no change ticket explains; MX pointing to a host nobody knows.
Detection logic
Alert when a new registration or an MX/nameserver change matches your brand strings, or when any MX change lacks a matching approved change.

Field notes: mx_changed: true plus an unknown mx_record host, within a day of a fresh registration, is the hijack signature. match_string is your brand keyword; tune it to exact strings to keep volume low.

Threat 2 · BEC and brand impersonation

Log source
Brand-monitor alerts, mail gateway logs (sender domains), web gateway logs (lookalike visits).
Key fields
sender_domain, spf_result, domain, cert_issued, match_string.
Normal
Lookalike matches that turn out to be your own subsidiaries, marketing campaign domains, or partners.
Suspicious
A new domain one edit away from yours, sending mail to your staff or customers, or holding a fresh TLS certificate.
Detection logic
Correlate brand-string registrations with mail-gateway blocks and certificate log entries; escalate when the same string appears in two channels within 48 hours.

Field notes: spf_result: fail means the sender domain itself did not authorize the mail. Pair the sender_domain with an NRD lookup: a domain registered days before first send is a strong impersonation signal.

Threat 3 · WHOIS client execution on an endpoint

Log source
Sysmon Event ID 1 (process creation) or your EDR's process feed; optionally shell history.
Key fields
Image, CommandLine, User, Hostname, ParentImage, UtcTime.
Normal
Network or IT staff running lookups during maintenance; security team OSINT during authorized tests; rare, explainable, one or two queries.
Suspicious
Any execution from a server or service account; sequences of different domains; execution shortly after suspicious parent processes or from user-writable paths.
Detection logic
Alert on any process whose image ends in whois.exe or whose command line calls the whois client; tune with an allowlist for named admin teams.

Field notes: Image under C:\Tools means someone dropped a portable tool there — worth knowing on its own. The CommandLine shows the queried domain, which makes triage fast. ParentImage of a script loop hints at automated enumeration.

Threat 4 · Reverse WHOIS portfolio pivot (web service)

Log source
Proxy / web gateway logs; DNS query logs for reverse-WHOIS services.
Key fields
url, user, src_ip, method, status, user_agent.
Normal
Security staff checking their own exposure; IT verifying a vendor; low frequency.
Suspicious
Search queries containing your registrant email or legal entity name from hosts that never touch security tooling; repeated automated-looking requests.
Detection logic
Flag reverse-WHOIS service URLs whose query strings contain your brand strings or registrant contacts, when the requesting user is not on the security team.

Field notes: The url query string carries the pivot key — here the admin email. If that email should be a role mailbox, this hit tells you the record leaked. Frequency matters more than the single visit.

Threat 5 · Bulk RDAP scraping

Log source
Registrar / RDAP abuse alerts (third-party view); your own proxy logs for internal bulk use; self-hosted WHOIS web logs if you run one.
Key fields
source_ip, requests_per_minute, target_domains, user_agent, api_key_owner.
Normal
Your own asset-inventory scripts hitting RDAP from named hosts; general internet scrape volume that does not mention your names.
Suspicious
Alerts from the registrar or RDAP operators about enumeration touching many of your domains; identical user agents querying dozens of your names in sequence.
Detection logic
Rely on registrar-side abuse alerting plus brand-matching on NRD feeds; internally, alert when non-security hosts issue repeated RDAP calls.

Field notes: target_domains_matched is the registrar telling you that someone systematically pulled your names. Treat it like a recon report on your estate: check locks and renewals the same day.

Field notes: The internal view of the same threat is a proxy record. Many rdap.org requests in a burst from one host is enumeration, and rule 3 in section 5.5 turns that pattern into an alert.

Threat 6 · Name server enumeration

Log source
Zeek conn.log (for classic WHOIS port 43) and DNS query logs (for NS record lookups).
Key fields
id.orig_h, id.resp_h, id.resp_p, proto, conn_state; DNS logs: query, qtype.
Normal
No port-43 traffic from workstations; DNS NS lookups by resolvers and monitoring systems only.
Suspicious
Port-43 sessions from user subnets; bursts of NS-record queries for your own domains from a single host.
Detection logic
Alert on outbound TCP/43 from any host not on an approved list, and on unusual volume of NS-record queries for your domains from internal hosts.

Field notes: id.resp_p: 43 with conn_state: SF (started and finished normally) is a completed WHOIS conversation. orig_bytes: 58 is about the size of one queried domain name; several such sessions in a row means enumeration, not curiosity.

5.5

Sigma Rules and Splunk SPL

Four rules cover threats 3 to 6 — the ones that leave evidence on systems you own. Threats 1 and 2 surface through external feeds and gateway alerts instead; their detection logic is in section 5.4. Each rule ships as Sigma YAML with a matching Splunk SPL query, a mapping note, false positives, and tuning advice. Deploy them in a lab first, confirm the field names in your own data, then promote.

SPL environment assumptions

The queries assume: index=main for Windows Sysmon data with sourcetype="XmlWinEventLog:Microsoft-Windows-Sysmon/Operational", index=network for Zeek connection logs as JSON (sourcetype=zeek:conn:json), and index=proxy for web gateway data. Replace indexes and sourcetypes with your own names — one search against real data will tell you.

Rule 1 — WHOIS Client Execution on Endpoint Medium

Covers threat 3. Any execution of a WHOIS client on a managed endpoint. Cheap to run, easy to tune, and one of the few reliable internal signals this technique leaves.

Mapping and field assumptions

Sigma logsource service: sysmon maps to Sysmon Event ID 1 records. The SPL assumes your Sysmon events land in index=main with the XmlWinEventLog sourcetype and that Image, CommandLine, User, and Computer are extracted fields. If you use a Sysmon TA (a Splunk add-on package) with different field names, rename in one place.

Tuning

Allowlist your IT and SecOps admin groups with a lookup table of admin users or admin hosts, then re-alert only on the rest. Keep severity Medium for user workstations; raise it in the rule logic when User matches a service account or Computer matches a server naming pattern.

Rule 2 — Outbound WHOIS Protocol Connection on TCP/43 Low

Covers threats 3 and 6. Any internal host talking the classic WHOIS protocol to an external server. Almost no business tool uses port 43, so volume stays low and every hit is worth a glance.

Mapping and field assumptions

Sigma logsource product: zeek, service: conn maps to Zeek conn.log. The SPL assumes Zeek JSON shipped to index=network with dotted field names ("id.resp_p" must be quoted in SPL because of the dot). Your Zeek JSON may call the transport field transport or network_protocol instead of proto — adjust once. The asset_inventory lookup marks known admin hosts so they can be filtered.

False positives and tuning

Net admins and security tooling are the main benign sources — allowlist them by role in the lookup. If your egress proxy or mail gateway mirrors WHOIS data, add its IPs to the filter. The Sigma startswith filter and the SPL cidrmatch filter now cover the same private ranges exactly.

Rule 3 — Internal Host Accessing RDAP or WHOIS Web Services Low

Covers threats 4 and 5. Web and API lookups are the modern path: RDAP endpoints, registrar WHOIS pages, and reverse-WHOIS panels all travel as HTTPS through your proxy.

Mapping and field assumptions

Sigma logsource category: proxy covers any proxy product. The SPL uses sourcetype=stream:http (Splunk Stream) as a placeholder — swap in the sourcetype of your proxy TA (for example Squid, Zscaler, or Blue Coat). It assumes the full url is a field and that a user field exists; some TAs call it cs_username. The asset_users lookup provides department and team for allowlisting. The SPL regex is case-insensitive and skips the Sigma rule's dot check, because every real URL contains a dot; it also adds the security and IT team allowlist from the tuning notes.

False positives and tuning

Expect a steady drip from security and IT. Filter by team lookup first; only alert on other departments. To cut noise further, require the URL path (not just the host) to contain rdap or whois, or alert only when the query string contains your registrant contacts — that turns it into a data-exposure check.

Rule 4 — High Volume of WHOIS Lookups from a Single Host Medium

Covers threats 3 and 5 at scale. One lookup is curiosity; dozens in minutes is enumeration. This rule is the rate-based backstop for the two exact-match rules above.

Mapping and field assumptions

Same source assumptions as rule 1. The Sigma aggregation (count() by Computer > 10 in a 10-minute timeframe) matches the SPL bin plus stats plus where pattern. The threshold of 10 is a starting point: measure a quiet week in your estate and set the number just above the highest benign run you see.

False positives and tuning

Inventory jobs and registrar-migration work are the expected FPs — exclude their host or account names via lookup. Add dc(CommandLine) > 10 instead of raw count if one process re-tries the same domain. If noise persists, pair this rule with rule 1's allowlists so only non-admin hosts are counted.

Validation checklist before you promote these rules
  • Fire one benign test event per rule in the lab (run whois example.com on a test VM) and confirm the alert fires with readable fields.
  • Confirm every field used in the SPL exists and is extracted in your data; missing field extraction is the number one reason silent rules "do not work".
  • Set the Sigma status: test rules to stable only after two clean weeks in production.
  • Document the owner of each rule in your detection inventory so tuning requests reach a human.

Real-World Case Study

A fictional composite case built for training. It combines the most common steps from public domain-hijack and business-email-compromise reports into one story. Atlas Health Group and everyone in it do not exist.

Fictional composite for training

Names, domains, amounts, and dates are invented. The sequence follows patterns documented in public reports of expired-domain takeovers and invoice fraud, but no real company or incident is described here.

Context

Atlas Health Group runs a small grants program. Years ago, a marketing agency registered grants.atlashealth.example for a campaign site. When the agency contract ended, nobody moved the domain into the corporate registrar account. The record kept a personal email of an employee who left in 2023. Auto-renew was off. There was no registrar lock. No one owned the domain on paper — the classic forgotten asset.

Attack chain in ATT&CK terms

  • T1596.002 WHOIS — the attacker studied expiry dates and registration details of the Atlas portfolio weeks in advance (recon on PRE platform).
  • Expired-domain acquisition — the name was registered legitimately the moment it dropped; no exploit was needed.
  • Infrastructure replay — MX re-pointing and a cloned portal rebuilt the services the domain used to carry.
  • Mail interception and social engineering — captured thread context fed a believable invoice-fraud attempt against finance.
The detection point that mattered

Two cheap third-party signals fired on Day 1, five days before the fraud attempt: the NRD feed matched the brand string, and a new certificate appeared in CT logs. Either one, routed to a human, would have started MX monitoring the same day. The lesson is not better tooling — the tooling worked. The lesson is that nobody owned the queue.

Containment

  • Abuse report to the reseller registrar with registration-evidence pack.
  • Mail gateway: block the attacker's mail host and lookalike domain.
  • Staff notice: do not trust mail or files from the grants portal.
  • Finance: freeze payments referencing invoice 8841 pending verification.

Eradication

  • Mailbox audit on the affected mail flow: search for swallowed messages and silent-reply rules.
  • Portfolio sweep: lock status, auto-renew, and privacy checked on every Atlas domain; gaps fixed within 48 hours.
  • Portal accounts: password resets and session revocation for anyone who used the cloned site.

Recovery

  • Domain recovered via registrar dispute and UDRP preparation; MX re-pointed to corporate mail.
  • Vendors contacted with correct banking details re-confirmed by phone.
  • Monitoring retained on the domain and brand strings for 90 days.

Impact and consequences

Funds lost
None. The verification call stopped the $180,000 transfer (fictional figure for training).
Data exposed
About 40 emails to the hijacked domain, including two vendor invoices with banking data.
Service downtime
Grants portal effectively attacker-controlled for 12 days until recovery.
Trust damage
Awkward conversations with two vendors whose invoices were captured.

Lessons learned

  • Inventory first. Nobody knew the domain existed, so nobody protected it. The inventory fix in section 7 prevents the whole story.
  • Auto-renew, lock, privacy. Three cheap settings would have removed the attack window entirely.
  • Role mailboxes. A departed employee's personal address kept receiving the warnings. Registration contacts must be teams, not people.
  • Vendor domains count. Third-party-registered names need the same lifecycle ownership as core domains.
  • Monitor mail flow. An MX change on any owned domain without a matching ticket should page someone.

Mitigation and Defense

You cannot stop strangers from reading public records. You can control what the records say, lock down the levers that matter, and watch for abuse. The cards below group the controls; the table at the end prioritizes them.

Policy

  • Own the domain lifecycle: one documented procedure for registering, renewing, locking, and transferring names.
  • Standard: privacy or proxy on every record, role-based contact mailboxes only, corporate registrar accounts only.
  • Include third-party and legacy domains in scope with named owners.

Identity

  • MFA on every registrar account; hardware security keys for admins.
  • Least-privilege roles: few people can change DNS or transfer domains.
  • Quarterly access review of registrar accounts, including ex-staff removal.

Endpoint

  • Alert on WHOIS client execution (rule 1) and treat server-side execution as higher severity.
  • Keep portable lookup tools out of user-writable paths.
  • Log process command lines so triage is instant.

Network

  • Egress filter TCP/43 to approved hosts only; alert on the rest (rule 2).
  • Track RDAP and WHOIS web traffic in proxy logs with team allowlists (rule 3).
  • No other protocol needs port 43 — the filter is safe to make strict.

Cloud

  • Use registrar APIs to sync lock status and expiry dates into your inventory automatically.
  • Alert on DNS record changes (especially MX) that no change ticket explains.
  • Scope DNS provider accounts with the same MFA discipline as registrars.

Logging

  • Keep Sysmon/EDR process data long enough for monthly reviews (30–90 days).
  • Ship Zeek or firewall records of port-43 sessions to your SIEM (security information and event management system).
  • Archive registrar notification emails into the ticket system, not personal mailboxes.

Monitoring

  • NRD feed filtered by brand strings, reviewed daily in minutes.
  • Certificate Transparency watch for your domain names.
  • Brand monitor for lookalike registrations; MX monitor for owned domains.

Backup and records

  • Export registrar data (contacts, dates, lock states) as part of asset records.
  • Keep signed evidence of your rights to key names — it speeds up UDRP disputes.
  • Domain recovery is a legal process; your paperwork is the "backup".

Response

  • Write a domain-hijack playbook: registrar abuse contact, UDRP steps, MX re-point, mailbox audit, comms list.
  • Rehearse it like any other playbook — the case study above shows the clock moves fast.
  • Pre-agree who calls legal and who talks to vendors.

Home and small-office advice

  • Turn on WHOIS privacy for personal domains — most registrars offer it free.
  • Turn on auto-renew and keep a valid card on file.
  • Enable registrar lock (sometimes called transfer lock).
  • Use a strong, unique registrar password with two-factor authentication (2FA); the registrar account controls everything.
  • Renew critical names for several years at once to shrink the expiry window.
Do these five things first
  1. Build the domain inventory with owners and expiry dates.
  2. Switch auto-renew and registrar lock on everywhere.
  3. Replace personal registration emails with role mailboxes.
  4. Route registrar notifications into a monitored queue.
  5. Deploy rules 1–4 from section 5.5 in test mode.

Together these steps remove the Critical threat's preconditions and make the remaining risks visible.

Common Mistakes and Best Practices

Ten blue-team mistakes that show up again and again in domain-security reviews. Each row gives the symptom you will notice, the root cause behind it, the fix, and the habit that prevents its return.

#MistakeSymptomRoot causeFixPrevention
1No domain inventory Nobody can answer "which domains do we own?" during an incident. Domains registered ad hoc by marketing, agencies, and devs; never centralized. Build the inventory: registrar, owner, expiry, lock, privacy, contact email. Add "new domain" to the change-management checklist.
2Auto-renew off on "unused" domains A name lapses silently and later reappears under someone else. Saving small renewal fees; assuming a parked name is worthless. Turn auto-renew on; renew critical names for multiple years. Expiry report with 60/30-day warnings owned by a named person.
3Personal staff emails as registrant contacts Reverse WHOIS on one address lists the whole portfolio, including acquisitions. Default registrar forms filled with a person's mailbox. Switch to role mailboxes like dns-ops@company.example; enable privacy. Standard baked into the domain procedure; quarterly WHOIS spot check.
4No registrar lock Transfers or DNS changes possible with a compromised registrar login. Lock options never enabled; multiple registrars, different consoles. Enable registrar/registry lock everywhere; prefer registrars supporting registry lock. Lock status as a column in the inventory; drift alerts via registrar API.
5Treating whois.exe alerts as pure noise Rule 1 fires for months, is muted, then an insider recon case is missed. No tuning loop; no allowlist; ownership gap. Tune with admin-group allowlists; set a rule owner; review monthly. Documented tuning log per rule; false-positive rate tracked.
6No NRD or brand monitoring Lookalike domains run for weeks; the company learns from customers. "Monitoring" seen as a paid extra, not a control. Start free: NRD feed with brand-string filter; CT log watch; review daily. Feed alerts routed to the SOC queue with a response-time target.
7TCP/43 allowed from everywhere Any host can run WHOIS traffic; rule 2 has nothing to compare against. Egress policies written per-application years ago; port 43 forgotten. Restrict port 43 to named hosts; alert on all other sources. Annual egress review that includes uncommon ports.
8No MX change monitoring Mail redirection discovered only when mail stops arriving. DNS changes seen as purely operational, not security events. Alert on MX changes for owned domains without a matching change ticket. Wire registrar/DNS API events into the SIEM.
9No UDRP / dispute playbook After a hijack, days are lost deciding who calls the registrar or legal. Domain recovery assumed to be a support ticket. Write the playbook: evidence pack, abuse contacts, UDRP steps, decision owners. Tabletop the hijack scenario once a year.
10Single-owner domain management Owner leaves; renewals, locks, and alerts all go dark at once. One admin holds all registrar knowledge and credentials. Two-person ownership; credentials in the password vault; runbooks written down. Access review catches single points of failure quarterly.
False positives, alert fatigue, and ownership

Three failure modes decide whether these detections help or harm. False positives: rules 1–3 start noisy until allowlists exist — budget tuning time in the first month, not "someday". Alert fatigue: a rule nobody owns becomes a rule nobody reads; give each rule a named owner and a monthly review. Missing logs: if Sysmon or proxy data is absent in one office, say so in the rule documentation instead of pretending coverage exists. A detection you cannot trust is worse than no detection, because it teaches analysts to ignore the channel.

Daily habits

  • Scan the NRD feed for your brand strings (five minutes).
  • Check that yesterday's domain-related alerts have owners.
  • Glance at MX-change alerts for owned domains.

Weekly habits

  • Run the expiry report for 60- and 30-day windows.
  • Review rule 1 hits that are still unexplained.
  • Confirm registrar notification mailboxes are being read.

Monthly habits

  • Portfolio audit: locks, privacy, contacts, owners.
  • Registrar account access review, including ex-staff.
  • Tuning session for rules 1–4 with false-positive counts.

Response checklist: suspected domain hijack or abuse

  1. Open a case and start a timeline; note the domain, registrar, and first alert time.
  2. Check current WHOIS/RDAP record: registrant, dates, status codes, name servers, MX.
  3. If MX changed on an owned domain: block the unknown mail host at the gateway and alert mail owners.
  4. Audit mailboxes on the affected domain for swallowed messages and forwarding rules.
  5. File the registrar abuse report; start the UDRP evidence pack (proof of rights, dates, screenshots).
  6. Check whether the lookalike holds a TLS certificate; note CT log entries for the case.
  7. Sweep the rest of the portfolio: locks, auto-renew, privacy, contacts — fix gaps today.
  8. Notify affected vendors and staff with verified contact details; freeze related payments pending phone checks.
  9. Keep monitoring the domain and brand strings for 90 days; write the lessons-learned note.
  10. Update the inventory and the playbook with what the case taught you.
