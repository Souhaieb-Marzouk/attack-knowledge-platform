MITRE ATT&CK - Exfiltration - Sub-technique

T1048.001 Exfiltration Over Symmetric Encrypted Non-C2 Protocol

The attacker encrypts stolen data with a symmetric cipher. One shared secret key locks and unlocks the data; AES (Advanced Encryption Standard) is the common example. The encrypted file then streams over a separate channel. That channel is not the command and control (C2) link. It is also not a standard encrypted service such as HTTPS or SSH. The bytes often travel as raw TCP or UDP traffic on an unusual port. This guide was reviewed against MITRE ATT&CK v20 in October 2026.

  • Tactic Exfiltration (TA0010)
  • Parent T1048
  • Platforms ESXi · Linux · Windows · macOS
  • Data source Network traffic

What it is
Data is encrypted with one shared key, such as AES, and sent over a non-standard channel that is not the C2 link.
Why it matters
The content is unreadable to inspectors, so volume and behavior are the only clues left behind.
Main detection source
Traffic volume on rare ports plus endpoint process lineage.
Detection difficulty
Hard - no TLS metadata, no known service.

    1

    Overview

    A plain-language tour of the technique, why it is hard to catch, and what this page teaches you.

    What is this technique?

    Symmetric encryption uses one shared secret key. The same key locks and unlocks the data, like a house key that opens both the front door and the back door. AES (Advanced Encryption Standard) and older RC4 are common symmetric ciphers of this kind. They run fast, and both sides only need the one shared key.

    This sub-technique describes what an attacker does with that cipher. First, the attacker collects stolen files into one archive. Then the archive is encrypted with the shared key. Finally, the attacker streams the encrypted file over a channel that is not the command and control (C2) link. C2 is the management channel that malware uses to receive instructions. The channel is also not a standard encrypted service such as HTTPS or SSH (Secure Shell). Often the data moves as raw TCP or UDP traffic on a port with no known service.

    Why it is dangerous

    Normal encrypted traffic gives defenders useful metadata. A TLS (Transport Layer Security) session - the encryption behind HTTPS - shows a certificate and a server name. This technique shows none of that. There is no handshake to read, so the content stays dark and the metadata stays empty. Defenders must fall back on volume and behavior: how much data left, on which port, and from which process.

    Where it fits in the attack chain

    Exfiltration is the step where data leaves the network for good. It usually comes after Credential Access (stealing logins) and Collection (gathering the files). Before it can start, the attacker needs three things: collected data, a working foothold, and one open egress path out of your network. This sub-technique differs from T1041 (Exfiltration Over C2 Channel): here the data uses a separate channel, not the malware management link.

    Uncommon TCP or UDP ports such as 8443, 4444, 9995, or any port the site allows out.

    Animated Simulation

    Watch the whole attack in eight steps, then read the same story in text. The animation is a teaching model, not a real capture.

    Written step-by-step story
    1. 1. Foothold. A phishing attachment runs on the workstation and hands control to the attacker. Office starts a hidden script process to do the work. The SOC sees one suspicious Office child process in EDR, but the score stays low because nothing else has happened yet.
    2. 2. Stage and encrypt. The malware gathers research files into one archive and encrypts it with a symmetric cipher such as AES. The shared key sits inside the malware configuration. An archive-like file with high entropy (data that looks random) appears in a temp folder; the SOC sees no alert at this point because file writes alone look normal.
    3. 3. Open channel. The malware opens a raw TCP connection to a rented virtual private server (VPS) on port 8443. The firewall records a new flow to a bare IP on a port with no known service. The SOC has not been alerted, but first-seen logs now hold the pair of host and port.
    4. 4. Stream out. The encrypted archive leaves in steady chunks - about 180 MB in total. The connection shows large bytes out, yet the TLS parser finds nothing to decode. To the SOC this means one thing: the flow is encrypted, but it is not TLS.
    5. 5. Decrypt at VPS. The attacker side holds the same shared key and rebuilds the archive from the arriving chunks. The stolen files are now outside the company in readable form. From the inside, the stream still looks like a quiet file transfer.
    6. 6. SOC review. The daily baseline for bytes out per port gets a new high-water mark on 8443. A volume alert fires because a port with no known service owner crossed the line. The analyst opens a case and pulls the flow records.
    7. 7. Correlate. The analyst joins the network story with the endpoint story. EDR lineage (the process family tree) shows the same process wrote the .bin file and then opened the socket. Staging plus egress in one process is a strong sign of exfiltration.
    8. 8. Response. The SOC blocks the destination IP at the firewall and isolates the host from the network. A hunt starts for peer hosts that talked to the same IP or port. The case moves to eradication and recovery.

    Red Team Perspective

    Understanding the attacker's choices shows you where they must leave traces. This section stays defensive: everything here is for building detections in a lab.

    When attackers use it

    Attackers pick this technique when the obvious paths look watched. If a company inspects HTTPS egress or a web proxy blocks unknown sites, a raw socket on an odd port slips past those checks. It also suits them when they already hold a working foothold and a full archive of collected data. Finally, they need control of both ends: the malware on your host and a listener on their own server.

    Prerequisites

    Four things must be true before this technique can run. The attacker needs code execution on a host inside your network. They need collected data worth sending, usually already packed. They need one open egress path, such as a firewall rule that allows any outbound TCP. And they need an external listener - a VPS (virtual private server, a rented server on the internet) that holds the same shared key.

    How it works

    1. Collect and stage. The malware gathers target files into one archive, often in a temp folder. This staging step is the first visible endpoint artifact.
    2. Encrypt with the shared key. The archive is encrypted with a symmetric cipher such as AES-256. The key travels inside the malware configuration, so both sides can read the stream.
    3. Split into chunks. The encrypted file is cut into fixed-size chunks. Chunking lets the transfer survive drops and keeps each write small on disk.
    4. Open the raw channel. The malware opens a plain TCP or UDP socket to the external listener on an agreed, uncommon port such as 8443.
    5. Stream the chunks out. Chunks flow at a steady, low rate - sometimes only at night - to stay under volume limits.
    6. Reassemble and decrypt. The listener collects the chunks and decrypts them with the same key. The attacker now holds a readable copy of the archive.

    Variation: rotating raw TCP

    The stream hops between uncommon TCP ports and sometimes between backup IPs. Port rotation is meant to defeat simple port-based blocks. It still leaves the unknown-service signature on every port it touches.

    Variation: UDP with repair

    Some families send chunks over UDP (a connectionless transport protocol) and add their own error repair. Lost packets are resent from the sender's list. Session-based tools see little structure, so volume baselines matter more.

    Variation: borrowed shapes

    Other variants wrap the encrypted bytes in HTTP-looking headers, inside ICMP (the helper protocol behind ping), or inside tunnel tools such as socat or openssl. The shape looks known; the body does not match the protocol.

    Attackers make repeatable mistakes, and each one is a detection opportunity. They reuse one fixed schedule, so nightly flows look identical. They leave the staging file on disk between transfers. They reuse the same listener IP and key across victims. Build detections for the mistakes, not for the perfect run.

    Blue Team / SOC Perspective

    The defender's job is to catch the behavior, not the bytes. This section lists what the technique leaves behind and where to look first.

    What it leaves behind: network side

    Flows to uncommon ports with a service field of "-" (unknown). Bytes out that grow in a steady, scheduled way. Long sessions with no TLS record for the same 5-tuple (source IP, source port, destination IP, destination port, protocol). A bare IP destination with no domain name.

    What it leaves behind: endpoint side

    A new archive-like file with high entropy in a temp or public folder. A short-lived script or binary that wrote it. A socket opened by the same process soon after. On Linux, the same shape appears as openssl or socat child processes.

    What it leaves behind: timing

    Nightly or hourly cadence is common, because attackers throttle transfers to stay quiet. Chunk sizes repeat. The destination stays the same across runs, which makes first-seen tables very useful.

    What it leaves behind: outside view

    The listener sits on rented infrastructure: a VPS with a fresh IP, sometimes a new network owner (ASN) for your site to contact. Passive DNS shows no domain history. Threat feeds may already flag the IP if it was used before.

    Why it matters in the chain

    This technique is the moment data leaves. Catching it means the loss stops here, and the incident becomes a containment story instead of a breach notification. It is also your best chance to map the attacker's infrastructure: the listener IP, the schedule, and the key reuse all feed the hunt. Miss it, and every earlier detection you had was wasted.

    Triage flow: from alert to closure

    1. Take the alert. Note the host, destination, port, byte count, and first-seen time.
    2. Check the baseline. Is this port and destination new for this host? How large is the flow next to the daily norm?
    3. Prove the absence of TLS. Look for a TLS record for the same 5-tuple. No record means unknown encryption.
    4. Pull endpoint lineage. Find which process wrote files and opened the socket. Get the full family tree.
    5. Scope the blast radius. Hunt for other hosts that reached the same IP or port in the last 30 days.
    6. Decide containment. Block the destination at the firewall and isolate the host if lineage confirms staging plus egress.
    7. Collect evidence. Preserve the staging file, the flow records, and the process history before reimaging.
    8. Report and tune. Write the timeline, feed confirmations back into the rules, and adjust thresholds if needed.

    How to apply intelligence

    1. Pick patterns that fit your exposure. Start with patterns that match the services and ports your site actually allows out.
    2. Turn patterns into baselines. Convert each pattern into a measured normal level, then a threshold, then a rule (section 5.5 gives six examples).
    3. Record expected false positives. Write down which legitimate tools will trip each rule and how you will tell them apart.
    4. Schedule reviews. Re-check every external claim each quarter; infrastructure and tooling change fast.
    5. Feed results back. When a rule confirms real activity, share the artifacts with the source group and your ISAC.

    5.4 Logs and Patterns

    One card per threat from 5.3, in the same order. Each card lists log sources, key fields, normal versus suspicious behavior, one-sentence detection logic, and a realistic example event.

    1) Raw TCP custom encrypted stream High

    Log sources
    zeek:conn, zeek:ssl, pan:traffic
    Key fields
    id.orig_h, id.resp_h, id.resp_p, orig_ip_bytes, service, duration
    Normal
    Known services on known ports; unknown ports carry small flows, if any.
    Suspicious
    One session pushing 100 MB or more to a rare port with service of "-" and no TLS record.
    Detection logic
    Alert when one internal host sends a very large single flow to a rare external port and no TLS session exists for the same 5-tuple.

    Field notes: orig_ip_bytes counts bytes leaving the source at the IP layer, so headers are included. service of "-" means Zeek could not identify any protocol. A matching zeek:ssl record for the same 5-tuple does not exist - that absence is the proof.

    2) Encrypted UDP data flood Medium

    Log sources
    pan:traffic, zeek:conn
    Key fields
    src_ip, dest_ip, dest_port, bytes_out, proto, orig_pkts
    Normal
    UDP to DNS (53), NTP (123), and VPN ports; small per-session sizes.
    Suspicious
    Many large UDP sessions from one host to a bare external IP on a port with no service owner.
    Detection logic
    Alert when one source pushes a large daily UDP total to external hosts on ports without a known service.

    Field notes: bytes_sent is the vendor's raw name; add-on normalizers often expose it as bytes_out. UDP has no session state, so count sessions per source per day rather than trusting one long flow.

    3) AES-encrypted archive staged then uploaded High

    Log sources
    Sysmon EventCode 11 (file create), Sysmon EventCode 3 (network connect)
    Key fields
    TargetFilename, Image, ProcessGuid, DestinationIp, DestinationPort, Initiated
    Normal
    Backups and sync clients write archives in their own folders, from their own signed binaries.
    Suspicious
    A user-space process writes a .bin or .enc archive in a temp folder, then the same process opens an external socket within minutes.
    Detection logic
    Alert when a non-admin process writes an archive-like file in a user-writable folder, and treat a same-process socket as the confirm step.

    Field notes: both events share the same ProcessGuid, which is the join key that turns two unrelated logs into one story. The 5.5 rule alerts on the file event; pull the matching EventCode 3 record by ProcessGuid during triage to confirm the upload.

    4) Encrypted payload inside ICMP Medium

    Log sources
    suricata, zeek:conn
    Key fields
    src_ip, dest_ip, icmp_type, icmp_code, proto, orig_ip_bytes
    Normal
    A few ICMP echo events per host for diagnostics; no large payloads.
    Suspicious
    Hundreds of echo events from one host to external addresses within an hour, or ICMP bytes above the daily baseline.
    Detection logic
    Alert when one internal host sends more than 400 ICMP echo requests to external addresses in one hour.

    Field notes: icmp_type 8 with icmp_code 0 is a normal ping request - the payload inside is what carries data here. Some Suricata builds add flow.bytes_toserver; count events first, bytes second.

    5) Custom channel mimicking HTTP headers Medium

    Log sources
    zeek:http, stream:http
    Key fields
    method, id.resp_p, referrer, uri, resp_mime_types, user_agent
    Normal
    Web traffic on standard ports, with referrers, varied URIs, and common MIME types.
    Suspicious
    Repeated POST requests to a non-standard web port, no referrer, a single URI, and binary response bodies.
    Detection logic
    Alert when a host posts repeatedly to a non-standard web port with binary bodies and no referrer header.

    Field notes: the shape (method, port, status 200) looks like web traffic, but the body is raw encrypted bytes - hence resp_mime_types of application/octet-stream and a constant uri of "/". resp_mime_types is a multivalue field in Zeek.

    6) Repurposed tunnel software (socat, openssl s_client) Medium

    Log sources
    Sysmon EventCode 1 (process create), EDR process logs
    Key fields
    Image, CommandLine, ParentImage, User, Computer
    Normal
    Admins and build systems may run openssl or socat for approved maintenance, from known parent processes.
    Suspicious
    These binaries started by script interpreters or office parents, with command lines that open raw network pipes.
    Detection logic
    Alert when a process starts openssl s_client or socat with command lines that set up a raw network pipe.

    Field notes: the binary location matters - openssl running from a user profile folder is unusual on managed Windows hosts. The -quiet flag shows the operator wanted a raw pipe, not an interactive session. This log line is an example for detection work only; running such tunnels is for LAB-ONLY environments.

    5.5 Sigma Rules and Splunk SPL

    One complete Sigma rule plus a matching Splunk SPL query for each threat from 5.3, in the same order. Sigma (a plain-text rule format that many SIEM tools understand) states the logic; SPL (Search Processing Language, the Splunk query language) runs it. Adjust index names to your environment.

    Threat 1 - Raw TCP custom encrypted stream High

    Field assumptions: index=netdata holds Zeek JSON from the Splunk add-on, fields keep Zeek names such as id.orig_h, and IN needs Splunk 7.3 or newer. Mapping: the SPL applies the same private-source filter, port list, 100 MB floor, and service exclusion as the Sigma. It then proves the TLS absence directly: it groups by the 5-tuple and keeps only flows where the zeek:ssl side never appeared.

    Threat 2 - Encrypted UDP data flood Medium

    Field assumptions: index=netfw holds Palo Alto traffic logs normalized by the vendor add-on to src_ip, dest_ip, dest_port, and bytes_out; rename to match your setup. Mapping: both rules keep allowed UDP sessions of 50 MB or more outside the common ports, then sum the bytes per source and destination port and alert at 200 MB total. Run the SPL search over a 24-hour window to match the Sigma timeframe.

    Threat 3 - AES-encrypted archive staged then uploaded High

    Field assumptions: index=edr holds Sysmon data with sourcetype="sysmon"; the fields EventCode, Computer, Image, and TargetFilename follow the Splunk add-on naming, and \\ marks one literal backslash in the search. Mapping: the SPL applies the same EventCode, extension, folder, and program-folder exclusions as the Sigma, event for event. The stats step only sorts the output; it adds no threshold. For the upload half, pull matching EventCode 3 records by ProcessGuid during triage.

    Threat 4 - Encrypted payload inside ICMP Medium

    Field assumptions: index=ids holds Suricata EVE JSON where ICMP events carry src_ip, dest_ip, and icmp_type; some builds also add flow.bytes_toserver. Mapping: both rules count ICMP type 8 echo events to external addresses per source in a one-hour window and fire at 400 or more. Run the SPL over the last hour to match the Sigma timeframe, and tune the 400 count to your baseline. The dc(dest_ip) column is context only; the threshold stays per source.

    Threat 5 - Custom channel mimicking HTTP headers Medium

    Field assumptions: index=netdata holds Zeek HTTP records; resp_mime_types is a multivalue field, so the OR search matches any value inside it. Mapping: both rules require POST, no referrer, a binary body, and a port outside the standard web set, then count posts per source host and fire above 20 in a one-hour window. Replace the standard-port list with your real web egress ports for better coverage, and run the SPL over the last hour to match the Sigma timeframe.

    Threat 6 - Repurposed tunnel software (socat, openssl s_client) Medium

    Field assumptions: index=edr holds Sysmon process events where CommandLine, Image, and ParentImage come from the Splunk add-on for Sysmon, and \\ marks one literal backslash. Mapping: the SPL applies the same image and command-line filters as the Sigma: openssl with s_client and -connect, or socat with TCP: or TCP-LISTEN:. The stats step only sorts the output; it adds no threshold. Triage decides if the run was approved; treat every match as LAB-ONLY practice until context confirms it.

    Real-World Case Study

    This is a composite case study built from common public incident patterns. Company names are fictional.

    A SaaS vendor lost research source code for nine nights before anyone noticed. A malware family on one R&D workstation collected source folders into an archive, encrypted it with AES-256, and streamed it to a rented VPS on TCP 8443. Each nightly run moved about 20 MB, which stayed under every existing alert threshold. The catch came from two weak signals joined together: an "encrypted but not TLS" volume heuristic and EDR process lineage.

    1. Day 0 - 22:47

      Phishing reaches R&D

      A "build server maintenance" email reaches 40 staff. Three open the attachment; one macro runs and drops a loader.

    2. Day 0 - 23:05

      Quiet foothold

      EDR logs a suspicious Office child process but scores it low. No network action follows, so the case closes itself.

    3. Day 1 - 03:12

      Staging and encryption

      The malware collects source folders into one archive and writes rd_export.bin to a temp folder, encrypted with a key from its config.

    4. Day 1 - 03:26

      First stream out

      A 20 MB flow leaves to a bare IP on TCP 8443. It is logged, not alerted: the threshold was 100 MB per flow.

    5. Day 1-9 - nightly 03:00

      Nine quiet nights

      The same three steps repeat every night. About 20 MB leaves each run, same host, same destination, same port.

    6. Day 9 - 03:41

      Heuristic fires

      A bytes-out heuristic totals the week: 180 MB on port 8443 with zero TLS sessions for that 5-tuple. Encrypted, but not TLS - that combination raises the case.

    7. Day 9 - 03:55

      SOC triage

      Zeek shows service "-" and long durations. The TLS parser finds nothing to decode. The analyst suspects custom encryption, not a misconfigured service.

    8. Day 9 - 04:10

      Lineage completes the story

      EDR lineage shows the same PowerShell process wrote rd_export.bin and then opened the socket. Staging plus egress in one process confirms exfiltration.

    9. Day 9 - 04:35

      Containment

      The firewall blocks the destination IP and the host is isolated from the network. The stream stops mid-transfer.

    10. Day 10-13

      Eradication and recovery

      The team removes persistence, resets the user's credentials, and reimages the host. A 30-day hunt for peer hosts finds none.

    Detection point

    The flow-level heuristic made the catch, not any single event. Nine small transfers each looked harmless; the weekly total on an unknown-service port did not. The lesson is arithmetic: aggregate before you judge.

    Containment

    Two actions happened inside 25 minutes of the case opening. The destination IP was blocked at the firewall, and the host was isolated by EDR. Blocking first stopped the data; isolating second stopped the operator.

    Eradication

    The team traced the loader to its phishing origin and removed two persistence items: a scheduled task and a registry run key. They searched every endpoint for the same loader hash and the same temp-file name.

    Recovery

    The host was reimaged from a known-good image, and the user returned to work the next day. Credentials for the source repository were rotated. Monitoring for the blocked IP stayed in place for 90 days.

    Impact and consequences

    About 160 MB of source code left the network before the stream stopped. The vendor treated it as a likely leak, rotated keys, and rebuilt affected branches. No customer data was involved, so no external notification was required.

    Team response and communication

    The SOC, the network team, and R&D leadership joined one bridge call. The SOC shared a plain-language timeline every two hours. R&D froze non-essential builds for two days while the hunt ran.

    Lessons learned

    First, baseline bytes-out per destination port, because totals reveal what single flows hide. Second, alert on unknown-service flows above a small daily threshold. Third, keep EDR lineage deep, since the file-write-then-socket link was the proof that moved the case.

    7

    Mitigation and Defense

    You cannot block every byte, so reduce the paths and watch the ones that remain. These controls shrink the attack surface for this technique.

    MITRE ATT&CK lists three official mitigations for T1048.001: M1037 Filter Network Traffic, M1031 Network Intrusion Prevention, and M1030 Network Segmentation. The cards below put them to work. Data Loss Prevention (DLP) tooling helps as a complementary enterprise control. Encrypted custom channels can slip past its content checks, so treat the three official mitigations as the base layer.

    Policy and people

    Train staff on phishing, and run attachment simulations monthly. Write an egress policy that names every allowed outbound port and owner. Make exceptions expire.

    Identity and endpoint

    Deploy Sysmon or EDR process logging everywhere, with deep lineage (10 or more process generations). Remove local admin rights so malware cannot install tools such as socat easily.

    Network and egress

    Allow outbound traffic by destination and port, not "any". Block workstations from reaching bare IPs directly, and force traffic through proxies that log it. This covers the official M1037 Filter Network Traffic and M1030 Network Segmentation mitigations.

    Cloud and logging

    Send flow logs to the SIEM within minutes, not daily. Keep 90 days of searchable logs so hunts can look back. Log both the border and the endpoint view.

    Monitoring and response

    Build the six rules from section 5.5, then rehearse the triage flow from section 4. Isolation must be one click, tested quarterly. A Network Intrusion Prevention System (NIPS - a device that blocks known-bad traffic at the border) is the official M1031 mitigation.

    Backup and resilience

    Exfiltration can end in extortion even without ransomware. Keep offline backups, and test restore speed so a stolen-dataset decision does not become a ransom decision.

    Home and small office

    Small networks can do a lot with little. Turn on the router's outbound logging if it exists, and keep a short allowlist of ports. Use one DNS filter for all devices so unknown destinations stand out. Install an EDR or at least Defender with advanced hunting on every machine, and check the weekly security report. Most home exfil attempts stop at the first three controls.

    Common Mistakes and Best Practices

    Ten mistakes that show up again and again in real programs, followed by three habits that keep the detections alive.

    1) Watching only famous bad ports

    Symptom
    Rules list 4444 and 1337, so a stream on 7080 or 9995 sails through.
    Root cause
    Port thinking instead of behavior thinking; attackers change ports freely.
    Fix
    Detect on volume, unknown service, and absence of TLS, with ports as context only.
    Prevention
    Review rules quarterly and delete any rule that is only a port list.

    2) Treating "encrypted" as "safe"

    Symptom
    Flows without TLS metadata are skipped because they look like noise.
    Root cause
    The assumption that encryption means a real service stands behind it.
    Fix
    Invert the check: encrypted traffic with no known service is the highest-priority unknown.
    Prevention
    Track unknown-service bytes out as a weekly metric, not as a filter.

    3) Ignoring UDP traffic

    Symptom
    All egress detections run on TCP sessions only.
    Root cause
    Session tools make TCP easy and UDP awkward, so UDP is never modeled.
    Fix
    Add per-source, per-port UDP daily totals beside the TCP rules.
    Prevention
    Include UDP in the egress policy and in every baseline review.

    4) Trusting port labels instead of baselines

    Symptom
    Traffic on 8443 is marked "HTTPS" and never questioned.
    Root cause
    Port-to-service lookup tables used as proof instead of as hints.
    Fix
    Verify with TLS records: no handshake for the same 5-tuple means the label is wrong.
    Prevention
    Baseline real bytes per port per protocol, and flag mismatches.

    5) Keeping network and endpoint data separate

    Symptom
    Two teams each hold half the story and neither sees the whole picture.
    Root cause
    No shared correlation key such as host plus process plus time.
    Fix
    Join flow records with process lineage by host and time window, as in the threat 3 triage steps.
    Prevention
    Design detections as pairs from day one: one network leg, one endpoint leg.

    6) Missing the staging file

    Symptom
    Detection work starts at the network border and never looks at disk.
    Root cause
    File-create logging not deployed or not retained.
    Fix
    Deploy Sysmon EventCode 11 coverage and alert on archive-like names in temp folders.
    Prevention
    Include staging paths in the log coverage matrix and review them monthly.

    7) Blocking one IP and closing the case

    Symptom
    The flow stops, the ticket closes, and the malware stays.
    Root cause
    Containment treated as the end instead of the start of the hunt.
    Fix
    Hunt for peer hosts that reached the same IP, port, or staging-file name before closing.
    Prevention
    Add a mandatory peer-hunt step to the exfiltration runbook.

    8) Tuning away unknown-service flows

    Symptom
    The rule that would have caught the case was silenced last quarter.
    Root cause
    False-positive pressure answered by broad suppressions, not by scoping.
    Fix
    Re-enable with narrow scope: known noisy hosts in a watchlist, everything else alerts.
    Prevention
    Review every suppression monthly; suppressions need owners and expiry dates.

    9) Keeping shallow EDR lineage

    Symptom
    History stops at the parent process, so the file writer cannot be found.
    Root cause
    Default agent retention or aggressive data pruning.
    Fix
    Raise lineage depth and retention for process, file, and network events.
    Prevention
    Test with a LAB-ONLY drill: can you trace a test file write to its socket?

    10) Forgetting ICMP and admin tools

    Symptom
    The covert ICMP variant and the socat variant have no rule at all.
    Root cause
    Assuming exfiltration always looks like a big TCP flow.
    Fix
    Deploy the ICMP volume rule and the openssl/socat process rule from 5.5.
    Prevention
    Walk the 5.3 threat list every quarter and check each row has a rule.

    Daily habit

    • Review bytes out per port against the baseline.
    • Check new unknown-service destinations.
    • Confirm the top volume rules are still running.

    Weekly habit

    • Read the unknown-service weekly totals.
    • Sample five rare-port flows and trace their owners.
    • Check staging-file alerts for new patterns.

    Monthly habit

    • Validate one Sigma rule against lab traffic.
    • Review suppressions and their expiry dates.
    • Re-walk the 5.3 threat table for coverage gaps.

    Cheat Sheet and Quick Reference

    Everything important on one screen: key facts, top detections, a response checklist, and the official links.

    Key facts

    Technique
    T1048.001 - Exfiltration Over Symmetric Encrypted Non-C2 Protocol (parent T1048, tactic TA0010)
    Core idea
    One shared key (like AES) encrypts the data; a non-standard, non-C2 channel carries it out.
    Best signals
    Large bytes out on rare ports, service "-", no TLS record, archive-like staging file, deep EDR lineage.
    Hardest case
    Low-and-slow nightly chunks that stay under every per-flow threshold.
    Counter move
    Aggregate per source and per port, then join with endpoint lineage.

    Response checklist

    • Note host, destination, port, byte count, and first-seen time from the alert.
    • Compare the flow with the per-port and per-host baseline.
    • Confirm no TLS record exists for the same 5-tuple.
    • Pull EDR lineage for the writing and connecting process.
    • Preserve the staging file and flow records as evidence.
    • Block the destination at the firewall and isolate the host.
    • Hunt for peer hosts that touched the same IP, port, or file name.
    • Write the timeline and feed confirmed artifacts back into the rules.
