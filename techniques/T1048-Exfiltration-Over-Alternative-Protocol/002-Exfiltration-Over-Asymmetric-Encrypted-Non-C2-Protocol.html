MITRE ATT&CK - Exfiltration - Sub-technique

T1048.002 Exfiltration Over Asymmetric Encrypted Non-C2 Protocol

An attacker sends stolen data over a channel that asymmetric encryption protects. This channel is not the one the attacker uses for command and control (C2). Asymmetric encryption uses a key pair: a public key locks the data, like a mailbox anyone can drop letters into. A private key, held only by the owner, opens it. Services built on this model, such as SSH, SCP, and SFTP, are trusted almost everywhere. That trust is exactly why attackers like them. This guide was reviewed against MITRE ATT&CK v20 in October 2026.

What it is
Data leaves through key-pair encrypted services such as SSH, SCP, or SFTP, or through TLS uploads to attacker servers that are not the C2.
Why it matters
These protocols look like normal admin work, so stolen data can hide inside routine operations traffic.
Main detection source
Endpoint process events plus first-seen destination analytics on network flows.
Detection difficulty
Medium-Hard - the protocol itself is legitimate and often business-critical.

    Overview

    A plain-language tour of T1048.002: what it is, why it is hard to spot, and where it sits in the attack chain.

    The idea in one minute

    T1048.002 describes stolen data that leaves a network through a service protected by asymmetric encryption. A key pair does the work: the public key locks the data, and the private key opens it. Picture a street mailbox. Anyone can drop a letter through the slot, but only the owner can open the door and take the mail out. SSH (Secure Shell), SCP (Secure Copy Protocol), and SFTP (SSH File Transfer Protocol) all use this model to prove identity and protect traffic.

    The attacker packs files that were already collected and copies them to a server they control. That server is not the command and control (C2) channel, which is the line the attacker uses for live commands. Keeping the two apart serves them well. The exfiltration hop touches a different destination, so a defense that blocks the C2 address may never see the data theft.

    Where it fits in the attack chain

    This technique sits late in the attack chain. The attacker first gains a foothold, then steals or mints credentials, then collects the data into one place. Exfiltration is the moment the damage becomes real. Once the bytes leave, the response shifts from blocking to notifying, rotating credentials, and sometimes reporting to regulators within fixed deadlines.

    The protocol itself is legitimate, so a firewall cannot simply say no. Administrators use SSH every day, and backups, replication, and file sync look similar on the wire. Detection therefore leans on context: which asset sent the data, which destination received it, how many bytes moved, and whether that pattern was ever seen before.

    Animated Simulation

    Watch the attack unfold step by step, then read the written story below. Nothing plays until you press Play.

    Written step-by-step story
    1. The attacker signs in to the internet-facing build VM with a stolen CI token, so no password or MFA prompt appears. The login comes from a hosting network the company never uses. SOC view: an unusual ASN with MFA absent on a build asset.
    2. Source code and config files are packed into one archive in /tmp under the build account. Keeping everything in one file makes the later copy simple. SOC view: a large archive created by a service account is a staging signal.
    3. ssh-keygen creates a new key pair on the VM. This is a LAB-ONLY example. The private key stays in ~/.ssh and the public key will open the attacker's server. SOC view: key generation is rare on this asset class.
    4. The public key is uploaded to the attacker's server and stored in its authorized_keys file, which opens passwordless trust. SOC view: none, because this step happens on attacker infrastructure.
    5. Five staggered SFTP sessions copy about 900 MB to a first-seen SSH destination over roughly 15 minutes. SOC view: first-seen destination and large session volume fire together.
    6. The archive lands on the attacker's server and the exfiltration is complete. SOC view: the transfer records in your own logs are the only trace; attacker-side storage is invisible to you.
    7. The SOC correlates the egress flow records with endpoint events and gets one strong alert. EDR shows the sftp process and a fresh known_hosts write on the VM. SOC view: correlation turns two weak signals into an actionable case.
    8. The SOC revokes the stolen token, rotates keys, and isolates the VM, then reviews other build VMs. SOC view: containment plus a fleet-wide credential sweep closes the case.

    Red Team Perspective

    Understanding how the attack is performed helps you build better detections. All examples here are LAB-ONLY.

    When attackers use it

    Attackers reach for this technique when they already hold credentials or a private key, and when outbound SSH or HTTPS is allowed. It is common against build systems, developer laptops, and cloud workloads. It also suits them when the C2 channel is small, monitored, or metered. Copying data over a trusted admin protocol keeps their main line free for live commands.

    Prerequisites

    The attacker needs a working foothold and one of these paths:

    • Valid SSH credentials or a private key on the host.
    • Outbound access to port 22, or an SSH-like service on another port.
    • Writable temporary space for staging archives.
    • Enough dwell time for large transfers to finish.
    • A reachable server they control with SSH listening.

    How it works

    1. Stage the loot - the attacker collects files into one or more archives in a temporary folder such as /tmp.
    2. Prepare a key pair - they either generate a key on the host with ssh-keygen or bring a private key they already own.
    3. Probe the path - a small test connection confirms that outbound port 22 reaches their server.
    4. Transfer - sftp or scp copies the archives, often in chunks to survive drops and stay under naive thresholds.
    5. Verify - a checksum on the remote side confirms the copy is complete before cleanup starts.
    6. Clean up - the local archive, shell history, and sometimes the private key are removed to hide the trace.

    Common variations

    SFTP with a fresh key

    A new key pair is minted on the victim and the public half is staged on the attacker's server. The transfer then needs no password at all.

    SCP single shot

    One scp command copies a single archive. It is fast and quiet, but a failed transfer leaves the job half done.

    tar over SSH pipe

    A tar stream is piped straight into a remote ssh session, so no temp file ever appears. Watch for tar and ssh started together by the same parent.

    SSH port forwarding

    A local port forward opens a tunnel that carries data from an internal service to the outside. One SSH session hides many internal destinations behind it.

    Git push mirror

    A mirrored git push sends the whole repository, including history and secrets, to an external remote over SSH. It looks like normal developer work.

    Sync client, attacker tenant

    rclone or a desktop sync app is pointed at the attacker's cloud storage. The traffic comes from a trusted, already signed-in client.

    Attackers make mistakes that become your detection opportunities. Key generation with ssh-keygen is rare on servers. A new known_hosts write right before a transfer is unusual. Archives in /tmp owned by service accounts are odd. Transfer bursts right after a new login deserve a look. And even with encryption, egress flow logs still show the destination and the byte counts.

    Blue Team / SOC Perspective

    What the attack leaves behind, where to look for it, and how to work an alert from first ping to closure.

    What it leaves behind

    Process events

    ssh, sftp, scp, and ssh-keygen show up in endpoint telemetry, often started by a shell or a scheduler instead of a human.

    File events

    New private keys and known_hosts files in ~/.ssh, plus staged archives in /tmp, are strong file-level clues.

    Network flows

    First-seen destinations on port 22, large outbound byte counts, and long session durations stand out in flow records.

    Authentication

    New logins on build assets from unusual networks, with tokens instead of passwords and with MFA absent.

    Cloud grants

    New OAuth grants for sync apps and new access keys appear in cloud audit logs before or during the theft.

    Lookups

    Fresh DNS resolutions for the attacker host appear shortly before the first transfer from the asset.

    Why it matters

    Exfiltration is usually the last active step before the attacker goes quiet. Stopping it protects customers, intellectual property, and the company's duty to report. The technique also leaves a wide footprint across endpoint and network logs, which makes it one of the best teaching cases for correlation. A team that can catch T1048.002 can catch most bulk data theft.

    Triage flow

    1. Validate the alert: confirm the rule logic and pull the raw events behind it.
    2. Identify the host, the account, and the exact process that sent the data.
    3. Scope the destination: who owns the IP or domain, and is it on any asset or allow list?
    4. Size the loss: sum the bytes, list the files, and check archive contents if endpoint telemetry has them.
    5. Classify the data: decide whether personal, health, payment, or source code left the building.
    6. Contain: isolate the host, revoke the token or key, and block the destination at egress.
    7. Close: rotate credentials, remove attacker artifacts, and file the lessons-learned items.

    5.2 Threat Intelligence

    Where to find patterns worth detecting, and how much to trust each source. Never copy a rule blindly; validate it against your own telemetry first.

    MITRE ATT&CK and STIX/TAXII

    The official technique page lists data sources, tactics, and mitigations. STIX and TAXII are open standards for sharing threat data in machine-readable form. Use both to anchor your rule catalog to a common language.

    Vendor threat reports

    Security vendors publish incident patterns several times a year. Look for mentions of SSH or SFTP misuse, cloud sync abuse, and tunneling. Extract behaviors and indicators, not fear.

    CISA and FBI advisories

    These advisories are free and action-focused, and they often list ATT&CK IDs per behavior. Check them for exfiltration patterns tied to your sector. Subscribe to the mailing list.

    OSINT research

    Researcher blogs and DFIR write-ups describe real intrusions in detail. Verify claims before you build a rule on them. Prefer write-ups that include log examples you can test.

    Commercial feeds

    Paid feeds add IP and domain reputation, malware families, and context. They work best as enrichment for first-seen analytics, not as standalone alerts.

    ISACs

    Information Sharing and Analysis Centers share sector-specific reports between member companies. Peer data shortens the time from new pattern to new rule.

    Internal telemetry

    Your own past incidents are the most honest intel you have. Tag them with ATT&CK IDs and feed them back into rule tuning. The first-seen baselines in this guide come from this source.

    5.4 Logs and Patterns

    One card per threat from 5.3, with log sources, key fields, and the normal-versus-suspicious split. Full event examples follow below.

    1) SSH, SCP, or SFTP transfer to an external server

    Log sources
    Sysmon Event ID 1 and 3, Zeek ssh.log, Zeek conn.log, Linux auth logs
    Key fields
    Image, DestinationIp, DestinationPort, auth_attempts, direction, orig_bytes
    Looks normal
    Admins copy files to known jump hosts; transfers start during work hours from approved assets
    Looks suspicious
    scp or sftp binaries talking to public addresses, from build or server assets, with no allow-list entry
    Detection logic
    Alert when an SCP or SFTP client process opens a connection to a destination outside private ranges and outside the approved list

    2) TLS upload to attacker infrastructure that is not the C2

    Log sources
    Zeek conn.log and ssl.log, proxy logs, firewall flow records
    Key fields
    id.resp_p, orig_bytes, duration, SNI or host, first-seen flags
    Looks normal
    Backups and sync tools upload to known cloud ranges at predictable times and sizes
    Looks suspicious
    Large one-way uploads to newly observed destinations, especially right after a new login
    Detection logic
    Alert on TLS sessions pushing far more bytes out than in, to a destination never seen for that asset

    3) Git push to an external repository over SSH

    Log sources
    Linux auditd (file watch), Sysmon Event ID 1, git server audit logs, Zeek ssh.log
    Key fields
    file.path, process.exe, user.name, CommandLine, id.resp_h, direction
    Looks normal
    Pushes go to the corporate GitLab or GitHub organization, from developer laptops, during work hours
    Looks suspicious
    authorized_keys writes on build or dev hosts, then an outbound SSH session to a personal repository host
    Detection logic
    Alert when an authorized_keys write is followed within 30 minutes by an outbound SSH session from the same host

    4) Scheduled SFTP batch job

    Log sources
    Zeek ssh.log, cron and Task Scheduler logs, Zeek conn.log
    Key fields
    direction, auth_attempts, asset_class, first_seen per client and destination pair
    Looks normal
    Known batch jobs repeat to the same partner host at fixed times with stable sizes
    Looks suspicious
    A server asset makes its first outbound SSH or SFTP session to a public IP, then repeats on a schedule
    Detection logic
    Alert on first-time outbound SSH from a server-class asset to a public address, then watch for repeats

    5) SSH tunnel carrying bulk data (port forwarding)

    Log sources
    Zeek conn.log, Sysmon Event ID 1 for ssh with -L or -D flags, netflow
    Key fields
    id.resp_p, orig_bytes, resp_bytes, duration, CommandLine
    Looks normal
    Interactive admin sessions carry kilobytes to a few megabytes and last minutes
    Looks suspicious
    A port 22 session that runs long and pushes hundreds of megabytes in one direction
    Detection logic
    Alert when an SSH session sends more than 250 MB outbound, which interactive work never does

    6) Cloud file-sync client signed in to an attacker account

    Log sources
    Sysmon Event ID 3, proxy logs, OAuth grant logs, AWS CloudTrail for cloud build assets
    Key fields
    Image, DestinationHostname, OAuth grant or consent events, new device registrations
    Looks normal
    Sync clients talk only to the corporate tenant hostnames and known CDN ranges
    Looks suspicious
    rclone running at all, or OneDrive, Dropbox, Box, or Drive clients reaching non-corporate tenants
    Detection logic
    Alert when a file-sync client connects to a destination that is not on the approved tenant list

    Event examples

    IP addresses use the RFC 5737 documentation ranges (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24), so no real system is named. Field names follow Zeek, Sysmon, and auditd conventions; your pipeline may rename them.

    • auth_attempts of 1 with auth_success true means a key or script got in on the first try, which is common for automated transfers.
    • direction OUTBOUND, plus the pipeline enrichment outgoing, marks this host as the SSH client rather than the server.
    • asset_class server and first_seen_dest true come from the asset inventory and are the fields that turn a plain flow into an alert.
    • Image shows the sftp client binary, so the connection belongs to a file transfer, not to an admin shell.
    • DestinationIp 203.0.113.50 with port 22 is a public SSH endpoint; the hostname can look harmless, so resolve who owns it.
    • Initiated true confirms the connection was made outbound by this host, and ProcessGuid joins to the Event ID 1 record that shows the full command line.
    • An auditd watch rule on ~/.ssh/authorized_keys produces this PATH record; the writer here is tee, which points to a script rather than an editor.
    • Mode 0600 looks proper, which is the point: a technically clean write can still be attacker staging.
    • Correlate the timestamp with outbound SSH sessions from the same host; the pair is far stronger than either event alone.
    • orig_bytes of about 900 MB against resp_bytes of 1.3 MB is a strongly upload-heavy session; interactive admin work is the opposite.
    • A duration of 812 seconds with port 22 fits a bulk file copy or a tunnel carrying data out.
    • conn_state SF is a normal close, so the session looks healthy; volume, not errors, is what makes it notable.

    5.5 Sigma Rules and Splunk SPL

    One complete Sigma rule plus a matching Splunk SPL query for each threat in 5.3. Every rule keeps all required keys, a unique UUID, and the technique tags. Adapt indexes, sourcetypes, and filter lists to your own estate.

    1) SSH, SCP, or SFTP transfer to an external server High

    Mapping: data source Process: Network Connection (Sysmon Event ID 3) supports Technique Detection for T1048.002; the Event ID 1 join in SPL adds the command line for the analyst.

    Field assumptions: index=edr holds Sysmon data with sourcetype=sysmon from the Splunk Add-on for Sysmon; Image, DestinationIp, DestinationPort, User, and process_guid use CIM names. The cidrmatch list covers the same private ranges as the Sigma filter_private block, including IPv6 loopback, link-local, and unique-local addresses, so the filter logic matches exactly. Rename once in a macro if your names differ. The Event ID 1 subsearch looks back 15 minutes from now, which approximates the join window for near-real-time alerting.

    Tuning: add an allow-list filter for approved jump hosts before rollout. Track pscp and psftp only if PuTTY is used in your estate. False positives concentrate in backup windows, so baseline them first.

    2) TLS upload to attacker infrastructure that is not the C2 High

    Mapping: data source Network Traffic: Network Connection Flow (Zeek conn) supports Technique Detection; encryption hides content but not volume or destination.

    Field assumptions: index=net holds Zeek with sourcetype=zeek:conn; dotted names like id.orig_h are native Zeek fields, while the Corelight App may expose id_orig_h instead. asset_lookup maps client IPs to asset_class. The per-session threshold orig_bytes>=100000000 sits in the base filter, exactly like the Sigma selection, so the stats grouping by client_ip only shapes the display and does not change the logic.

    Tuning: exclude known backup and CDN ranges with a lookup, and raise or lower the 100 MB threshold per site. On networks that force a proxy, run the same logic on proxy logs where upload size and SNI are visible.

    3) Git push to an external repository over SSH Medium

    Mapping: data source File (auditd PATH record) supports Technique Detection; the SPL adds the follow-on outbound SSH session, and the rule severity is high because the event is rare even though the threat rank in 5.3 is medium.

    Field assumptions: index=nix holds auditd with sourcetype=auditd, where the PATH record name is exposed as file.path. The Sigma rule and the base filter here match the same file event; the SSH join is the documented add-on for the follow-on session. asset_lookup maps hostnames to IPs for the join. On Windows-only estates, add a process rule for git.exe with push and an ssh remote as a complement.

    Tuning: exclude configuration-management hosts such as Ansible controllers from the file watch, and always require the follow-on SSH join so routine key rotations do not page anyone.

    4) Scheduled SFTP batch job Medium

    Mapping: data source Network Traffic: Network Connection Flow (Zeek ssh) supports Technique Detection; asset context turns a generic flow into a server-asset rule. SFTP runs inside SSH, so the ssh.log record covers the batch transfer.

    Field assumptions: index=net holds Zeek with sourcetype=zeek:ssh; the auth_attempts>=1 filter mirrors the Sigma selection and drops sessions with no recorded authentication attempt; asset_lookup maps client IPs to asset_class and owner. The 24-hour first_seen window approximates first-time; for a strict baseline, join against a nightly summary index of client and server pairs.

    Tuning: keep the server-asset filter strict and add business_unit to the stats for faster triage. Suppress approved replication pairs with a lookup, and alert again when a suppressed pair changes its schedule or size.

    5) SSH tunnel carrying bulk data (port forwarding) Medium

    Mapping: data source Network Traffic: Network Traffic Volume (Zeek conn) supports Technique Detection; volume is the tunnel signature, because interactive SSH work never moves hundreds of megabytes.

    Field assumptions: index=net holds Zeek with sourcetype=zeek:conn; dotted Zeek names are native, and the Corelight App may expose id_orig_h instead. asset_lookup adds asset context for triage. The per-session threshold orig_bytes>=250000000 sits in the base filter like the Sigma selection, so the stats grouping by client only shapes the display.

    Tuning: 250 MB suits most estates; lower it for small sites and exclude approved data-center replication over SSH. Pair this rule with the first-seen rule from threat 4, since each catches what the other misses.

    6) Cloud file-sync client signed in to an attacker account Medium

    Mapping: data source Process: Network Connection (Sysmon Event ID 3) supports Technique Detection; tenant filtering separates corporate sync from attacker tenants. Edit the filter list to hold your real tenant names.

    Field assumptions: index=edr holds Sysmon Event ID 3, and approved_saas is a lookup you maintain with sanctioned tenant hostnames. The rclone branch alerts on every connection, matching the Sigma selection_rclone condition; only the named sync clients pass through the tenant lookup. Without endpoint data, run the same logic on proxy logs (index=proxy with sourcetype=zeek:http, using the Host field in place of DestinationHostname).

    Tuning: keep the filter list current with real tenant hostnames, and treat any rclone execution as review-worthy since it is rarely installed on standard builds. Google Drive cannot be tenant-filtered by hostname alone, so tune it with proxy SNI allow-lists.

    Real-World Case Study

    How the pattern plays out end to end, from a leaked token to a rotated fleet.

    This is a composite case study built from common public incident patterns. Company names are fictional.

    Meridian Software - source archive and npm secrets over SFTP

    Meridian is a mid-size software company. An internet-facing CI build runner held the source tree for its flagship product. A developer had committed a config file with a long-lived CI token to a public repository. An attacker found the token, signed in to the runner, created an SSH key pair, and SFTP-ed a 900 MB source archive plus .npmrc files (which hold npm registry tokens) to a personal-looking VPS. The egress team caught it because they watched for first-seen SSH destinations from server assets and for large session volumes. This mirrors the MirrorFace SFTP pattern documented in section 5.2.

    1. Day 1 - 03:12

      Token leak

      A developer pushes a config file with a hardcoded CI token to a public repository. The token never expires and grants broad build permissions.

    2. Day 1 - 03:58

      Harvest

      An automated scraper finds the token within the hour. The attacker now holds a working identity inside the build estate.

    3. Day 3 - 01:58

      First login

      The token is used from a hosting network to sign in to the internet-facing build runner. Token logins do not prompt for MFA, so nothing interrupts the session.

    4. Day 3 - 02:03

      Staging

      A 900 MB tar.gz of the source tree and the .npmrc files appears in /tmp under the build account.

    5. Day 3 - 02:07

      Key pair minted

      ssh-keygen runs on the runner. A new private key lands in ~/.ssh with no passphrase, ready for scripted use.

    6. Day 3 - 02:11

      Transfer

      Five SFTP sessions copy the archive to 203.0.113.50 over 15 minutes. The address shown here is a documentation range used in this guide.

    7. Day 3 - 02:31

      Detection

      The first-seen SSH rule fires, followed by the volume rule. The SOC correlates both with the new known_hosts write and opens a high-priority case.

    8. Day 3 - 03:05

      Containment

      The token is revoked, the runner is isolated, and the destination is blocked at egress. Triage confirms what left: source code and registry tokens.

    9. Day 5 - 10:00

      Recovery

      The runner is rebuilt from a clean image, the npm token and all build SSH keys are rotated, and the leaked file is scrubbed from git history.

    Detection point

    The alert came from egress analytics, not from a signature. First-seen SSH from a server asset fired first, and the volume rule confirmed it seconds later. Neither signal alone would have carried the case; together they removed all doubt.

    Containment

    Responders revoked the token before the attacker could return, then isolated the runner to freeze the scene. Blocking the destination at the firewall kept any second transfer from starting. The containment window stayed under one hour from alert to action.

    Eradication

    Responders removed the attacker's key pair, checked every authorized_keys file on the build estate, and swept other runners for the same token pattern. Two more runners held tokens from the same template, and both were cleaned. The private key never left the isolated disk image.

    Recovery

    The runner was rebuilt from a known-good image, and all npm and SSH credentials were rotated. Git history was rewritten to drop the leaked config file, and secret scanning was added to the pipeline. Normal builds resumed on Day 5.

    Impact and consequences

    Source code for one product line and several registry tokens left the company. No customer data was involved, which kept notification duties limited. The costs were response time, a rebuild, rotation work, and an unwelcome board briefing about secrets hygiene.

    Team response and communication

    The SOC, the platform team, and legal worked from one incident channel with a named incident commander. The platform team handled revocation and rebuilds while the SOC scoped the loss. Legal advised on disclosure, and a plain-language note went to engineering the same day.

    Lessons learned

    Treat SSH egress from build assets as exceptional and put it behind an allow-list. Alert on key generation on servers, because ssh-keygen there is rare and rarely good. Issue short-lived tokens with narrow scopes so a leak expires on its own. Volume analytics pay for themselves the first time they fire.

    7

    Mitigation and Defense

    Layered controls that make this technique hard, ordered so the cheapest wins come first. They map to the official ATT&CK mitigations: Data Loss Prevention (M1057), Filter Network Traffic (M1037), Network Intrusion Prevention (M1031), and Network Segmentation (M1030).

    Policy and people

    Write an SSH egress policy that names which assets may reach which destinations. Train developers on secret hygiene, since leaked tokens start most of these incidents. Keep an exception process with an owner and an expiry date for every allow-list entry.

    Identity and endpoint

    Issue short-lived CI tokens with narrow scopes, and require MFA everywhere a human logs in. Keep EDR on build and server assets. Protect ~/.ssh with permissions, and never share one build account between people and automation.

    Network and egress

    Default-deny outbound port 22 from server segments, with an allow-list for real needs. Run first-seen and volume analytics on everything that is allowed. Log DNS so new attacker domains show up before transfers do.

    Cloud and logging

    Enable CloudTrail org-wide on cloud estates and send VPC flow logs to the SIEM. Add secret scanning to repositories and pipelines. Rotate cloud keys automatically so stolen ones die fast.

    Monitoring and response

    Deploy the six rule pairs from 5.5 and keep a written exfiltration playbook. Tune thresholds quarterly with fresh data. Rehearse the SFTP scenario so the first real page is not the first rehearsal.

    Backup and resilience

    Keep immutable backups of source systems and build images, and test restores. Assume some data will leave eventually; knowing exactly what was in the archive is what keeps the aftermath short.

    Home and small office

    Small teams can copy the same ideas at lower cost. Keep admin accounts separate from daily-use accounts, and never expose SSH to the internet without a key and a firewall. Update the router and devices on a fixed schedule. Back up with the 3-2-1 pattern (three copies, two media types, one off-site), and check the backups by restoring one file every month. If you run a home lab, put it on its own network segment so a mistake there cannot reach family devices.

    Common Mistakes and Best Practices

    Ten mistakes teams really make with this technique, plus the habits that prevent them.

    1) Trusting that encryption means safety

    Symptom
    Outbound port 22 and 443 are open to the world because the traffic is encrypted anyway.
    Root cause
    Confusing confidentiality (nobody reads the content) with authorization (nobody should move this data at all).
    Fix
    Put server egress behind an allow-list and alert on everything else.
    Prevention
    Egress policy with named owners and expiry dates for every exception.

    2) Watching only inbound SSH

    Symptom
    Dashboards show SSH brute-force attempts while 900 MB walks out the back door.
    Root cause
    The SSH threat picture was built around exposed servers, not around data leaving.
    Fix
    Add outbound views: first-seen destinations, direction OUTBOUND, and session volume.
    Prevention
    Review rule coverage by direction, not just by protocol.

    3) No per-asset baseline

    Symptom
    Analysts cannot say whether a destination is new, so every alert feels weak.
    Root cause
    Asset inventory is missing or not joined into network detections.
    Fix
    Join an asset lookup (asset class, owner) into every egress rule, as in 5.5.
    Prevention
    Keep the inventory fresh with automated discovery and owner tags.

    4) Ignoring ssh-keygen on servers

    Symptom
    Key generation events are dismissed as admin noise, including on build runners.
    Root cause
    No asset context on the process rule, so a rare event looks like a common one.
    Fix
    Alert on ssh-keygen on server and build asset classes, and suppress only approved hosts.
    Prevention
    Document where keys may be minted, and monitor the rest.

    5) Long-lived tokens with broad scopes

    Symptom
    A token from a two-year-old leak still works and can read everything.
    Root cause
    Tokens are treated like passwords: set once, forgotten forever.
    Fix
    Move to short-lived tokens with narrow scopes and automatic expiry.
    Prevention
    Token inventory with expiry dates, and alerts on tokens older than policy.

    6) Unprotected private keys on shared accounts

    Symptom
    A passphrase-free private key sits in one shared build account used by five teams.
    Root cause
    Convenience won, and key custody was never assigned.
    Fix
    Unique accounts per team and automation, passphrases on keys, agent forwarding off.
    Prevention
    Custody review as part of quarterly access recertification.

    7) Volume analytics without first-seen (or the reverse)

    Symptom
    Either tiny quiet transfers slip through, or every big-but-normal upload pages someone.
    Root cause
    One analytic was deployed and the pair was never completed.
    Fix
    Run both together, like rules 4 and 5 in 5.5; each catches what the other misses.
    Prevention
    Detection design reviews that ask which sibling signal is missing.

    8) Tuning out first-seen alerts without verification

    Symptom
    First-seen rules are silenced after a noisy month, and the real event arrives later.
    Root cause
    No exception process, so analysts burn out and switch the rule off.
    Fix
    Every suppression gets an owner, a reason, and an expiry; re-alert when patterns change.
    Prevention
    Monthly review of the suppression list as a first-class artifact.

    9) Endpoint-only or network-only detection

    Symptom
    EDR sees a process with no destination; flow logs see bytes with no process name.
    Root cause
    Teams own one data source each and never join them.
    Fix
    Correlate endpoint and network events, as in simulation step 7 and the joins in 5.5.
    Prevention
    Detection engineering that plans rules across data sources from day one.

    10) Narrow containment after an incident

    Symptom
    One VM is rebuilt while its token still works on three other runners.
    Root cause
    Response scoped to the host instead of to the credential.
    Fix
    Rotate everything the credential could reach, then sweep the fleet for the same pattern.
    Prevention
    Playbooks that start from the credential, not from the machine.

    Habit cards

    Daily

    Review first-seen and volume alerts for build and server assets. Check for token-issuance spikes and new logins from unusual networks. Scan the last 24 hours of ssh and sftp process events on server-class assets.

    Weekly

    Review authorized_keys changes across the fleet. Run secret scanning on repositories and pipelines, and triage the hits. Read the egress exception list and chase any entry without an owner or an expiry date.

    Monthly

    Tune thresholds with the previous month of flow data. Rehearse the SFTP exfiltration scenario with the on-call rotation. Verify that allow-lists still match reality, and retire entries nobody defends.

    Response checklist

    • Isolate the affected host from the network.
    • Revoke the stolen token or session immediately.
    • Rotate SSH keys and cloud credentials the host could reach.
    • Block the destination IP, domain, and certificate at egress.
    • Search all logs for the same destination across the fleet.
    • Identify what was in the archive for classification and reporting duties.
    • Remove attacker keys and archives, then rebuild from a clean image.
    • Add the missed signal to detection rules and run a lessons-learned review.
