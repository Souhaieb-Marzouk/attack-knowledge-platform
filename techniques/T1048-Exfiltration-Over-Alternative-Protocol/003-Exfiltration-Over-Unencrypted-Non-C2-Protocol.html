MITRE ATT&CK - Exfiltration - Sub-technique

T1048.003 Exfiltration Over Unencrypted Non-C2 Protocol

Stolen data crosses the network in readable (cleartext) form over protocols that are not the attacker's command and control (C2) channel. Typical choices are File Transfer Protocol (FTP), Trivial FTP (TFTP), plain Hypertext Transfer Protocol (HTTP) uploads, or Telnet. Because there is no encryption, defenders who capture the right logs can read the content directly. This guide was reviewed against MITRE ATT&CK v20 in October 2026.

  • Tactic Exfiltration (TA0010)
  • Parent T1048
  • Platforms ESXi · Linux · Network Devices · Windows · macOS
  • Data source Network traffic (content)
  • ATT&CK T1048.003
What it is
Data is uploaded in cleartext through legacy or simple protocols such as FTP, TFTP, or plain HTTP.
Why it matters
Large transfers often succeed because legacy protocols are trusted and often not logged.
Main detection source
Full-content network logs such as Zeek, plus DLP keyword alerts.
Detection difficulty
Medium. Readable content is an advantage for defenders.

    Overview

    A plain-language introduction to cleartext exfiltration and why simple file protocols are a real exit door for stolen data.

    Exfiltration means an attacker moves stolen data out of a company network. In this sub-technique the data travels in cleartext. Cleartext means the bytes on the wire are readable, because no encryption is applied. The data also does not use the attacker's command and control (C2) channel, which is the private link used to send orders to malware. Instead the files ride on simple protocols such as File Transfer Protocol (FTP), Trivial FTP (TFTP), plain Hypertext Transfer Protocol (HTTP) uploads, or Telnet.

    The official ATT&CK page lists five platforms for this technique: ESXi, Linux, Network Devices, Windows, and macOS. ESXi is VMware's hypervisor, the software layer that runs virtual machines. Network Devices are routers, switches, and firewalls. An attacker who takes over a router or a firewall can copy its whole configuration out by FTP or TFTP. The group Salt Typhoon did exactly this (see Section 5.2). Attackers may also encode data before they send it. Base64 and Base32 are ways to write binary data using plain letters and digits. Encoding is not encryption, so defenders can still decode and read the content.

    Attackers like these protocols for two reasons. First, many networks still allow them because old systems and network devices depend on them. Second, many networks do not log them, so a 40 GB upload can finish quietly over three nights. Because there is no encryption, defenders who capture the right logs can read the content and prove exactly what was stolen.

    In the attack chain this step comes late. The attacker first gains access, steals credentials, and collects the data. Only then does exfiltration happen. ATT&CK lists this behavior under the Exfiltration tactic (TA0010), as sub-technique 3 of parent technique T1048, Exfiltration Over Alternative Protocol.

    Animated Simulation

    Watch the attack unfold step by step. The story mirrors a real incident pattern: a phished workstation, a staged archive, and a 40 GB FTP upload that defenders can read.

    Written step-by-step story
    1. Foothold. A phishing link gives the attacker code execution on one workstation. The security operations center (SOC) sees only a low-severity EDR process event, which is easy to miss.
    2. Stage archive. The malware packs many order files into customers.zip in the TEMP folder. The SOC sees common archive activity; the volume of files is the real clue.
    3. FTP login. The malware logs in to an external FTP server. The username and password cross the wire in cleartext, and the firewall records a new external FTP session.
    4. Upload (STOR). The malware issues STOR commands night after night. Zeek ftp.log shows the commands, the file names, and 40 GB of total size, which is the strongest signal in the whole attack.
    5. Content readable. A DLP tool inspects the stream and finds card-number patterns. The SOC receives a keyword alert that names the data type.
    6. SOC review. The analyst joins the DLP alert with Zeek ftp.log in the SIEM and proves bulk loss. The case is opened with high severity.
    7. Scope check. The analyst searches the host for more staging files and finds a second upload to a different FTP server. The incident grows beyond the first alert.
    8. Response. The team blocks FTP at the edge, isolates the workstation, and removes the backdoor. Passwords are rotated, and an insider and compromise review starts.

    Red Team Perspective

    How attackers use this technique, written for defenders. Knowing the steps shows where each step leaves evidence. Every command example is LAB-ONLY and uses test addresses that cannot reach real systems.

    When attackers use it

    Attackers pick this technique when they must move bulk data out fast and cheap. It is common after big collections such as database dumps, mail archives, or customer records. It also appears when one long transfer is simpler than building an encrypted channel. Intruders with access to old parts of a network often keep using FTP for months.

    Prerequisites

    The attacker needs code execution on one internal host, an outbound path for the chosen protocol, and a server they control outside the network. Anonymous or stolen FTP credentials are enough. TFTP needs no login at all, which makes it attractive for quick dumps. A stolen API token is enough for cleartext API uploads.

    How it works

    1. Collect and pack. The malware gathers target files and compresses them into one or more archives.
    2. Choose the exit. The operator picks FTP, TFTP, plain HTTP, or Telnet, based on what the firewall allows.
    3. Test with a small file. A tiny upload proves the path works before the real data moves.
    4. Upload in batches. Large archives are split, and each batch is sent slowly to stay under volume alerts.
    5. Repeat over nights. Transfers run during quiet hours and often resume where they stopped.
    6. Clean up. Local archives are deleted, and the same FTP account is rarely used again from that host.

    Common variations

    FTP drop site

    A rented FTP server holds one folder. The malware logs in and uses STOR to upload archives. The same site often receives loot from many victims.

    Plain HTTP POST

    A script posts files to a paste site or an upload page. It blends with normal web traffic and needs no special client.

    TFTP push

    A one-line TFTP write moves a file to an external server. It comes from equipment habits and is often missed by policy reviews.

    Database protocol dump

    A tool speaks the MySQL or Postgres protocol to an outside host that pretends to be a database. The dump travels row by row in cleartext.

    Telnet copy

    On legacy hosts, an attacker pipes a file through a Telnet session. It is slow, but it slips past rules that only watch FTP.

    Open API upload

    A stolen API token lets a script push JSON records to a public endpoint. The request body holds the data in cleartext.

    Attacker mistakes create detection chances. Operators reuse the same FTP server across victims, so one report can protect many companies. Test uploads with dummy files leave STOR events before the real data moves. Login bursts at odd hours stand out in ftp.log. Failed resume attempts repeat the same file name many times in a row.

    Blue Team / SOC Perspective

    What the attack leaves behind, where to look for it, and how to work an alert from first sight to closure.

    What it leaves behind

    Readable FTP commands

    Zeek ftp.log records every USER, PASS, and STOR command with file names and sizes. The cleartext login also exposes the account that was used.

    Staging archives

    Compressed files appear in TEMP folders or /tmp before the upload. EDR can report the archive creation and its size.

    DLP keyword hits

    Data loss prevention (DLP) tools read egress streams and match patterns such as card numbers. The hit names the exact data type that left.

    New legacy sessions

    Firewall and Zeek conn.log records show first-time connections on ports 21, 69, and 23. Baselines make these sessions easy to flag.

    Why it matters in the chain

    This technique is the last step, so alerts here mean data has already left. That makes speed more important than elegance. The same logs also show how much left, which drives breach-notification decisions. Clean Zeek and DLP records turn a guess into an evidence-backed number.

    Triage flow: alert to closure

    1. Confirm the alert. Open the Zeek ftp.log or DLP event and note the host, user, server, and file names.
    2. Check external status. Is the destination known-bad, newly registered, or a shared hosting address?
    3. Join the logs. Combine DLP, Zeek, and EDR events for the same host in the SIEM timeline.
    4. Measure the loss. Sum file sizes and count sessions to estimate the total volume that left.
    5. Identify the data. Use DLP hits or a sample of the transfer to name the exact data type.
    6. Contain. Block the destination, block the protocol at the edge, and isolate the host if needed.
    7. Scope wider. Search all hosts for the same server, the same account, or the same staging file names.
    8. Close and report. Rotate exposed credentials, notify data owners, and record lessons in the case file.

    How to apply intelligence

    1. Pick two or three sources that match your sector and language.
    2. Extract behaviors, not just indicators: protocols, ports, file names.
    3. Turn each behavior into a Sigma rule or a SIEM search.
    4. Add fresh indicators to a watchlist with an expiry date.
    5. Review the watchlist monthly and drop stale entries.
    6. Record which intel source led to each true-positive case.

    5.4 Logs and Patterns

    Each card matches a threat from 5.3 by number. It lists the log sources, the fields that matter, and the line between normal and suspicious. Worked JSON examples follow the cards.

    Threat 1: FTP upload of archives High

    Log sources
    zeek:ftp, firewall session logs, EDR process events for ftp.exe or curl
    Key fields
    command, arg (file name), user, reply_code, file_size, src_ip, dest_ip
    Watch two commands
    STOR stores a new file. APPE appends to a file that already exists, so attackers use it to resume a stopped upload.
    Normal
    A few known internal hosts talk to one or two approved partner FTP servers during work hours.
    Suspicious
    A workstation uploads to a never-seen external FTP server at night, in several large STOR commands.
    Logic
    Alert on any STOR command whose destination is not in the approved FTP server list.

    Threat 2: Plain HTTP POST upload High

    Log sources
    zeek:http, stream:http, proxy logs with bytes_out and category
    Key fields
    method, uri, host or site, bytes_out, user_agent, src_ip
    Normal
    Users post small forms; known apps upload to documented endpoints such as your CRM.
    Suspicious
    A large POST (tens of MB or more) goes to an uncategorized or newly seen domain, often from a script user-agent.
    Logic
    Alert on POST requests with bytes_out above the threshold to domains outside the approved list.

    Threat 3: TFTP external write Medium

    Log sources
    zeek:tftp, suricata events on UDP 69, firewall logs
    Key fields
    opcode, source_file, sink_file, id.orig_h, id.resp_h
    Normal
    Network gear saves configs to one internal TFTP server during change windows.
    Suspicious
    Any write request (opcode 2) aimed outside the company, from a user subnet, or outside a change window.
    Logic
    Alert on TFTP opcode 2 where the destination is not the approved internal TFTP server.
    Network device note
    The official ATT&CK analytic AN0427 adds a network-device check. It flags config files, routing tables, or logs sent to untrusted addresses with admin commands such as copy run ftp:.

    Threat 4: Cleartext database protocol elsewhere Medium

    Log sources
    zeek:conn, suricata flow records, firewall application identification
    Key fields
    id.resp_p (dest_port), service or app_proto, id.orig_h, id.resp_h, duration, orig_bytes
    Normal
    Application servers talk to known database servers on known ports inside the network.
    Suspicious
    Database ports (3306, 5432, 1433, 1521) used toward an external host, or a port labeled with a database protocol where Zeek cannot confirm it.
    Logic
    Alert on database-port connections to external destinations that do not identify as a known database server.

    Threat 5: Outbound Telnet Low

    Log sources
    suricata EVE flow records, zeek:conn, pan:threat with application field
    Key fields
    dest_port, proto, bytes_toserver, src_ip, dest_ip
    Normal
    Almost nothing, after you retire old devices; maybe one jump host during migrations.
    Suspicious
    Any Telnet session (port 23 or 2323) that crosses the egress boundary.
    Logic
    Alert on any external TCP connection to port 23 or 2323 from internal hosts.

    Threat 6: Sensitive cleartext API upload Medium

    Log sources
    stream:http (full-content capture), DLP, proxy with body inspection
    Key fields
    method, uri, site, request_body or form_data, bytes_out, dest_ip
    Normal
    Test systems post fake records to internal APIs with fake field values.
    Suspicious
    A POST body that contains real-looking fields such as card_number or date_of_birth going to a public endpoint.
    Logic
    Alert when a cleartext POST body matches sensitive field-name patterns and the destination is external.

    Worked log examples

    The examples below show real event shapes. Field names follow the Zeek and Suricata conventions your log pipeline will use.

    Example A - zeek:ftp event with a STOR upload (Threat 1)
    ts, uid
    Event time and the Zeek connection identifier that links all related records.
    id.orig_h / id.resp_h
    Client and server IP addresses. Here an internal workstation talks to 203.0.113.66, a documentation test address.
    command
    The FTP control command. STOR means store (upload) a file. APPE means append, which continues an earlier upload.
    arg
    The file name being uploaded. Repeated names hint at retries.
    reply_code
    Server reply. 226 means the transfer completed.
    size / file_size
    Bytes transferred. file_size is an enrichment added by the log pipeline.
    Example B - zeek:http event with a large POST body (Threat 2)
    method, uri
    POST to /api/v1/drop, an upload-style path.
    request_body_len
    Size of the request body, about 58 MB. Normal browsing is far smaller.
    user_agent
    A script library on a user workstation is a strong hint of automation.
    host
    Check the domain against your approved list and its proxy category.
    Example C - zeek:tftp event with a write request (Threat 3)
    opcode
    TFTP message type. 2 means WRQ (Write ReQuest), the message a TFTP client sends to upload a file. This is the alert-worthy action.
    id.resp_p
    Port 69, the TFTP well-known UDP port.
    source_file / sink_file
    File names on the client and server sides.
    Example D - Suricata EVE flow record for outbound Telnet (Threat 5)
    event_type
    flow means a session summary, written when the connection ends.
    dest_port
    23, the Telnet port. Port 2323 is a common alternative.
    app_proto
    failed means Suricata could not identify the protocol, which is common for Telnet.
    bytes_toserver
    Small byte counts fit an interactive session; bulk data would raise them fast.

    5.5 Sigma Rules and Splunk SPL

    Sigma is an open rule format for detections, and Splunk SPL is the Splunk Search Processing Language. Every threat from 5.3 gets at least one complete rule pair here. Threat 1 gets two, because an upload and a login are different signals. Severity reflects how much attention each alert needs, which can differ from the threat rank.

    Threat 1a - FTP STOR upload to an external server High

    Maps to 5.3 Threat 1. The rule fires when an FTP STOR command (upload) targets an address outside the private ranges.

    Field assumptions: index=netdata holds Zeek data parsed to fields command, arg, user, file_size, src_ip, and dest_ip. If your Zeek app keeps native names, use id.orig_h and id.resp_h instead. Rename index and sourcetype to match your environment. The stats line groups results for triage only; it does not change which events match.

    False positives: approved partner drops and legacy backup jobs. Tuning: allow-list known partner FTP servers, and raise severity when file_size sums above your daily baseline.

    Threat 1b - FTP authentication success to an external IP High

    Maps to 5.3 Threat 1. A successful PASS reply to an outside server means cleartext credentials left the company, even if no file moved.

    Field assumptions: same Zeek feed as rule 1a; reply_code 230 means the user logged in. Some Zeek pipelines store it as a string, which Splunk matches the same way. The SPL excludes the same four private ranges as the Sigma filter, including 127.0.0.0/8 (loopback).

    False positives: approved partner access. Tuning: alert on first-seen user and server pairs, and add the password field to your incident notes because it is readable in the record.

    Threat 2 - Large HTTP POST upload to an uncategorized domain High

    Maps to 5.3 Threat 2. The rule fires on big POST uploads to domains that your proxy lookup cannot categorize as approved.

    Field assumptions: approved_domains is a lookup table of trusted domains with a category column; site is the Host header recorded by Splunk Stream; bytes_out counts client-to-server bytes. A proxy sourcetype such as pan:threat works too if it records byte counts. The Sigma filter list and this lookup express the same approved-domain exclusion; replace the example domains and the lookup rows with your real list, and keep both in sync.

    False positives: sanctioned file sync and backup clients. Tuning: start at 50 MB, learn your normal upload distribution for two weeks, then set the threshold near the 99.5th percentile.

    Threat 3 - TFTP external write Medium

    Maps to 5.3 Threat 3. Opcode 2 is a TFTP write request, the only TFTP action that should ever be rare.

    Field assumptions: zeek:tftp is parsed with opcode and file name fields; src_ip and dest_ip are the client and server. The SPL excludes the same four private ranges as the Sigma filter, including 127.0.0.0/8. Suricata EVE users can alert on UDP destination port 69 with a WARN-class rule instead.

    False positives: managed TFTP relays during change windows. Tuning: allow only the one internal TFTP server, and alert on any user-subnet source.

    Threat 4 - Cleartext database protocol to a non-database destination Medium

    Maps to 5.3 Threat 4. The rule flags well-known database ports aimed outward, unless the destination really speaks a database protocol.

    Field assumptions: zeek:conn is parsed with dest_port, service, orig_bytes, src_ip, and dest_ip. The service field is Zeek's protocol guess; an empty value means the port does not match the traffic. The SPL excludes the same four private ranges as the Sigma filter, including 127.0.0.0/8.

    False positives: sanctioned cloud replication. Tuning: maintain an allow-list of real database egress, and review any session where service is empty but byte counts are high.

    Threat 5 - Outbound Telnet session Medium

    Maps to 5.3 Threat 5. The data volume is small, but Telnet egress also leaks credentials in cleartext, so the alert level stays medium.

    Field assumptions: suricata is Suricata EVE JSON; flow events carry src_ip, dest_ip, dest_port, and flow.bytes_toserver. The SPL excludes the same four private ranges as the Sigma filter, including 127.0.0.0/8. Firewall users can swap in pan:threat with the application field set to telnet.

    False positives: approved migration jump hosts. Tuning: after retiring legacy devices, drop the rule to any-source blocking instead of alerting.

    Threat 6 - Sensitive body in a cleartext API upload Medium

    Maps to 5.3 Threat 6. The rule reads POST bodies, not just metadata, so it needs a full-content capture such as Splunk Stream.

    Field assumptions: request_body holds the first bytes of the POST body as captured by Splunk Stream; some configs name it form_data or body instead, so adjust the field name once. Both the Sigma and the SPL now exclude private destinations, and both pattern lists match case-sensitively; change both together if you want case-insensitive matching. DLP products can replace this rule with their own keyword alerts.

    False positives: test systems with fake records. Tuning: keep the pattern list short, review hits weekly, and mask the captured body in screenshots and tickets.

    Real-World Case Study

    This is a composite case study built from common public incident patterns. Company names are fictional.

    An online retailer we call Nordkart lost 40 GB of order data over three nights. The attacker uploaded it by FTP to a rented server. Nothing was encrypted, so the Zeek and DLP records could read every step after the fact.

    Timeline

    1. Day 1 - 02:10

      Archive staged

      The backdoor on a finance workstation packs order exports into customers.zip in the TEMP folder. EDR logs the archive creation as a low-severity event.

    2. Day 1 - 02:33

      First FTP login

      The malware logs in to an external FTP server with a single-purpose account. Zeek records USER and PASS, both readable, plus the first STOR command.

    3. Day 1 - 02:47

      DLP fires, nobody sees it

      The DLP tool matches card-number patterns in the upload stream. Without a correlation rule, the alert lands as low priority in a crowded queue.

    4. Day 1 - 03:00

      Nightly rhythm starts

      Transfers stop at dawn and resume the next night. Each night moves about 13 GB, small enough to stay under the daily volume report.

    5. Day 2 - 02:20

      Second night, same server

      The same host repeats the same pattern to the same server. Zeek ftp.log now shows two nights of STOR commands with growing sizes.

    6. Day 3 - 05:52

      Correlation rule fires

      A rule named "new external FTP session, third night, same host" finally fires with high severity. This rule had been added during an earlier tabletop exercise.

    7. Day 3 - 06:15

      Case opened

      The analyst joins the DLP alert with Zeek ftp.log in the SIEM. The picture is complete: 40 GB of order data, one workstation, one external server.

    8. Day 3 - 06:40

      Containment

      The firewall team denies FTP egress and blocks the server. The workstation is isolated from the network within minutes.

    9. Day 3 - 11:00

      Scope grows

      A wider search of ftp.log finds a second upload to a different server two weeks earlier. The incident becomes a full compromise review.

    10. Day 5 - 16:00

      Recovery and report

      The backdoor is removed, all exposed passwords are rotated, and data owners receive the exact record count from the Zeek size fields.

    Phase summary

    Detection point

    The winning signal was correlation, not a single event. Zeek ftp.log held proof from the first night, and DLP named the data type. Together they turned two quiet signals into one loud case.

    Containment

    The team blocked FTP at the edge before they fully understood the attack. This was the right call because the transfer was still active. Blocking a whole protocol bought time without hurting users.

    Eradication

    The backdoor was removed from the workstation, and the phished user reset every password. The team also removed the FTP client shortcut that the malware had abused. A second sweep found no other staged archives.

    Recovery

    Systems returned to normal the same day because FTP was never a business need. The only lasting change was policy. Monitoring stayed on the workstation for a month as a precaution.

    Impact and consequences

    About 40 GB of order records left the company, including cardholder-adjacent fields. Notification duties followed, and the retailer offered credit monitoring. The direct cleanup cost was small next to the trust damage.

    Team response and communication

    Network, endpoint, and privacy teams joined one bridge call within the hour. The analyst shared a Zeek query instead of screenshots, so everyone saw the same data. Legal owned the regulator timeline while engineering owned the host.

    Lessons learned

    Block legacy egress by default. Log full metadata for the transfers you allow. Alert on any external FTP authentication. One low-severity alert is noise; the same alert on three nights is an incident.

    7

    Mitigation and Defense

    This technique is easier to stop than to detect. Most wins come from egress policy: decide which protocols may leave, block the rest, and log what remains. MITRE lists four mitigations for this technique: Data Loss Prevention (M1057), Filter Network Traffic (M1037), Network Intrusion Prevention (M1031), and Network Segmentation (M1030).

    Policy and people

    Write a simple egress policy: which protocols may leave, from which subnets, to which destinations. Train staff to report odd prompts and slow machines. Review the policy when a legacy system retires.

    Identity and endpoint

    Remove Telnet clients and old FTP tools from standard builds. Alert on ftp.exe, tftp.exe, and curl running on user workstations. Rotate any password that ever crossed a cleartext channel.

    Network and egress

    Block outbound FTP, TFTP, and Telnet by default at the firewall. Allow-list the few servers that truly need them. Send every allowed transfer through a point where Zeek can log full metadata. A network intrusion prevention system (NIPS) adds signature-based blocking for known-bad servers.

    Cloud and logging

    In cloud accounts, remove 0.0.0.0/0 egress rules on database ports. Route traffic through gateways that keep flow logs. Keep zeek, proxy, and DLP logs for at least 90 days so three-night patterns are visible.

    Monitoring and response

    Deploy the six rules from 5.5 and give each one an owner. Build the correlation view that joins DLP hits with Zeek records. Practice the containment step in a tabletop, including who can deny a protocol at the edge.

    Backup and resilience

    Backups do not stop exfiltration, but they decide how much a loss costs. Keep offline copies of order and customer data. Test that you can rebuild without the stolen files.

    Home and small office

    You can still apply the core idea without enterprise tools. In your router, block outbound ports 21, 69, and 23 unless you truly need them. Keep your operating system updated, and remove old programs that speak these protocols. If your internet provider offers traffic reports, read them. A home user who knows their normal traffic will notice a 40 GB surprise.

    Common Mistakes and Best Practices

    Ten mistakes teams make with this technique, each with a symptom, a root cause, a fix, and a prevention habit. Three habit cards finish the section.

    1) Blocking only known-bad IP addresses

    Symptom
    Transfers continue from new servers days later.
    Root cause
    Indicator lists age fast, while protocols stay stable.
    Fix
    Deny legacy protocols by default; allow-list exceptions.
    Prevention
    Review egress rules every quarter.

    2) Logging connections but not content

    Symptom
    You know a session happened but not what left.
    Root cause
    Only firewall flow logs are collected.
    Fix
    Deploy Zeek or a full-content tap on egress links.
    Prevention
    Map each egress path to a logging source.

    3) Assuming FTP is safe because no FTP server runs

    Symptom
    A workstation uploads archives nobody expected.
    Root cause
    Policy watched servers, not client-side use.
    Fix
    Monitor and block client FTP too, not just port 21 inbound.
    Prevention
    Include client behavior in the egress policy.

    4) Treating slow nightly transfers as noise

    Symptom
    The same low-severity alert fires for days.
    Root cause
    Alerts lack correlation across nights.
    Fix
    Add a repeat-offender rule that raises severity on the second night.
    Prevention
    Baseline volumes per host and alert on new patterns.

    5) Not watching archive staging on endpoints

    Symptom
    First alert arrives mid-upload, too late.
    Root cause
    EDR rules skip archive creation in TEMP.
    Fix
    Alert on large archives in TEMP from office applications.
    Prevention
    Tune staging rules with the SOC, not around it.

    6) DLP rules tuned until silent

    Symptom
    The queue is quiet, and real leaks pass.
    Root cause
    Thresholds were raised after noisy weeks.
    Fix
    Re-baseline with real samples and split alert tiers.
    Prevention
    Review DLP precision and recall monthly.

    7) Forgetting UDP-based TFTP

    Symptom
    Files leave on port 69 with no session record.
    Root cause
    Rules only covered TCP protocols.
    Fix
    Add zeek:tftp and UDP 69 monitoring.
    Prevention
    Enumerate both TCP and UDP in policy checks.

    8) No baseline of normal external transfers

    Symptom
    Every rule is either too loud or too quiet.
    Root cause
    Nobody knows the normal upload profile.
    Fix
    Build a per-host and per-protocol baseline report.
    Prevention
    Refresh baselines after big system changes.

    9) Evidence kept only on the compromised host

    Symptom
    The reinfected workstation loses its own history.
    Root cause
    Logs lived where the attacker had access.
    Fix
    Ship logs off-host immediately, ideally to a SIEM.
    Prevention
    Check log forwarding in health monitors.

    10) Believing proxy coverage covers everything

    Symptom
    FTP and Telnet bypass the proxy unseen.
    Root cause
    Only web traffic was forced through the proxy.
    Fix
    Monitor the raw egress edge, not only the proxy path.
    Prevention
    Draw the full egress map once a year.

    Habits that keep you ready

    Daily

    Review new external sessions on ports 21, 69, and 23. Skim top uploaders by bytes. Confirm that log forwarding stayed healthy overnight.

    Weekly

    Review the week's DLP hits and their outcomes. Re-run the top Sigma rules by hand once, so parsing drift is caught early. Share one interesting query with the team.

    Monthly

    Revisit the egress policy and the allow-lists. Run one LAB-ONLY purple team test of a small FTP upload in the lab. Update this guide when a rule changes.

    Response checklist

    • Confirm the source host, user, destination, and file names from Zeek.
    • Sum transferred sizes to measure exactly how much left.
    • Block the destination and deny the protocol at the edge.
    • Isolate the workstation and preserve its disk image.
    • Search all hosts for the same server, account, and file names.
    • Rotate every credential that crossed a cleartext channel.
    • Notify data owners and start the breach-notification clock if needed.
    • Write lessons into the egress policy and the rule set.
