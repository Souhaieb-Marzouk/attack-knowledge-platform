Overview

A plain-language summary of the technique, why it matters, and what this page will teach you.

What is this technique?

T1593.002 is a sub-technique of T1593 Search Open Websites/Domains. It covers adversaries using search engines — Google, Bing, Yandex and similar — to collect information about a victim. Beyond normal queries, they use search operators — special words and symbols like site: or filetype: that narrow results. Security people call these queries "dorks". The dorks find things a company never meant to publish: config files with passwords, open directory listings, admin panels, and internal documents.

The engine also holds copies: cached pages and indexed PDFs keep content alive even after it is deleted from the victim's site.

Why it matters to defenders

This is the cheapest exposure audit an attacker can run: no scanning traffic, no alerts, no trace on your side — the engine already did the crawling for them. Everything indexed is a ready-made finding. Documented incidents all start the same way: a query. Examples range from the 2017 voter-records exposure to the steady stream of bug-bounty reports about indexed .env files and admin panels.

The good news: what an attacker can find, you can find first. Searching site:yourdomain is a free, repeated, zero-risk control.

Terminology

A dork is a search query built with advanced operators. A cache is a saved copy of a page that the engine can show even if the live page changes. Indexing is the process by which a crawler reads your public pages and stores them for search results.

Animated Simulation

A step-by-step story of search-engine reconnaissance against a fictional company, Acme: from a simple site: query to an indexed config file with live secrets — and what the security team can see at each moment.

How to use this

The simulation starts paused. Press Play, or click the number chips to jump. Hover any box to see what it is. The written story below repeats the same steps in words.

The written story

  1. Step 1 — Pick the engine and plan queries. The attacker drafts operator queries: site: to map the victim's domains, filetype: for files, intitle: for panels. Nothing touches Acme's servers yet.
  2. Step 2 — site: recon of the domains. A site:acme.example query lists everything indexed — including a forgotten staging.acme.example host nobody remembered.
  3. Step 3 — Dork for files. Queries like filetype:env and intitle:"index of" look for things sites never mean to publish. The dorks run silently.
  4. Step 4 — Hit: an indexed .env file. The staging host serves an unauthenticated .env file, and the engine indexed it. A crawler fetched it weeks ago — that line sits, unnoticed, in the web logs.
  5. Step 5 — The snippet exposes secrets. The cached snippet shows a database password and a cloud access key (a documented example key in this demo). The secret now lives in a third-party cache.
  6. Step 6 — Dork for admin panels. intitle:admin reveals a management console on the same host, reachable without login. Two findings on one forgotten machine.
  7. Step 7 — The SOC sees nothing. Acme's logs are empty for the whole research phase. Only external tools — surface scans, crawler alerts, self-searches — could have raised the flag earlier.
  8. Step 8 — The outcome. The attacker notes the key and console for later. The defenders' play, when they find it: restrict, rotate every exposed secret, check for use, then de-index and clear caches.

Red Team / Hacker Perspective

How search operators turn a public index into a target map, what attackers look for, and where the method fails — described for defenders, with safe lab examples only.

When and why attackers use it

Search-engine research is the fastest way to find exposure: things a company published or left reachable by mistake. It beats scanning because it is silent — the engine's crawler already visited, so the attacker's queries never touch the victim. Attackers use it to:

  • Map the domains: site: reveals subdomains and paths the owner forgot.
  • Find files: config files, database dumps, backups, spreadsheets with real data.
  • Find panels: admin consoles, dashboards and dev tools reachable without login.
  • Learn the stack: indexed pages and error messages name frameworks and versions.
  • Read removed content: caches and archives keep deleted pages alive.

Prerequisites and conditions

  • Content must be crawlable: reachable without authentication and linked or listed somewhere.
  • A robots.txt entry is not protection — it only asks polite crawlers to skip; the page still exists, and other services ignore it.
  • No contact with the victim is needed until the attacker decides to use a finding.

Dork quick reference (safe examples)

Ethics and legality — lab only

Run these queries only against domains you own or are authorized to test (for example, inside a bug-bounty scope). Testing whether an exposure exists on a system you do not own, without permission, can be unlawful even when the data is public. Use example.com or your own domain for every exercise on this page.

Defensive lab exercise: audit your own indexing

checklist — self-audit with search operators (your domain only)
# Replace example.com with YOUR OWN domain. Run monthly.

site:example.com                       # the full indexed site

site:example.com filetype:sql          # database dumps

# For every hit: is it intended to be public? If not:
#   1. protect the path (auth or remove),
#   2. rotate every secret it contained,
#   3. request de-indexing and cache removal.

Common variations

  • Subdomain enumeration: site:*.example.com -site:www.example.com to surface forgotten hosts.
  • Document harvest: filetype:pdf, filetype:xlsx with author metadata to map people and tools.
  • Error harvesting: indexed stack traces and error pages leak versions and paths.
  • Archive reading: web archives complement the cache for long-removed pages.
  • Automated dorking: scripts and wordlists run thousands of operator combos against many targets at once.

Attacker mistakes and limits

  • Nothing to find: if exposure is gone, dorking returns nothing — the technique fails silently.
  • Stale results: the index lags reality; a fixed path can still appear in results, and the reverse.
  • Acting openly: the moment the attacker fetches the live file, your web logs finally see them — carelessness here is detectable.
  • Account noise: heavy automated querying can get the attacker's accounts rate-limited or flagged by the engine.

Blue Team / SOC Perspective

Your logs stay quiet while the search runs. What you can see are the side effects: crawler fetches, scanner findings, and the eventual use of whatever leaked.

Hard truth

The dork queries never touch you. Your only proof that something was indexable is in your own web logs: a crawler fetching a sensitive path. If nobody monitors those lines, the first signal may be an attacker using a found key — much later.

What defenders CAN use

  • Self-search: run the dork table against your own domain monthly. It is free and exactly what the attacker sees.
  • External attack surface management (EASM): continuous checks for open buckets, panels and forgotten hosts.
  • Crawler-log alerting: a search-engine user-agent fetching /.env or /backup/ means "this is now in the index".
  • CSPM (cloud security posture management — tools that check cloud settings) findings: they flag public storage and exposed resources directly.
  • Cloud audit logs: a leaked key being used from a new network is the late-stage confirmation.

What it leaves behind

  • Crawler fetch lines for every indexed sensitive file — with timestamps.
  • Cached copies and indexed snippets that survive deletion of the source.
  • External scanner findings if you run one (you should).
  • Later, the downstream use: logins with exposed credentials, or a panel accessed from an odd IP.

Where to look

SourceWhat you might findValue
Your own monthly dork reviewIndexed files, panels and forgotten hosts — before attackers actCritical

Short triage flow for an exposure finding

  1. Confirm and capture. Visit the finding, record what is exposed and since when (logs, backups, index dates).
  2. Restrict first. Require authentication or remove the path — before any long discussion.
  3. Rotate everything inside. Every password, key and token in the exposed content must be rotated.
  4. Check for use. Search cloud, VPN and SSO (single sign-on) logs for activity with those credentials since the first possible leak.
  5. De-index and clear caches. Submit removal requests; fix the root cause that allowed indexing.
  6. Close the loop. Ticket the finding, name an owner, and re-verify in the next scan cycle.
Why this matters

Every exposure you remove lowers the attacker's return on this technique to zero — silently, without ever seeing them. This is one of the few technique families where defense is genuinely proactive by design.

Detection Engineering Deep Dive

The practical core of this page: regulations, threat intelligence, ranked threats, log patterns, and ready-to-adapt detections. Since dork queries are invisible, every detection watches exposure itself and the downstream use of what leaked.

Official ATT&CK detection strategy

ATT&CK lists analytic AN1943 under detection strategy DET0811 — Detection of Search Engines. The official text says this activity often has a high occurrence and a high false-positive rate, and it usually happens outside the visibility of the target organization, which makes detection difficult. ATT&CK advises focusing detection on related attack stages, such as Initial Access. The detections below follow that advice: they watch your own exposure and the follow-on stages.

How to apply it

  1. Collect. Gather the ATT&CK procedure examples, vendor exposure reports, bug-bounty disclosures and your own crawler logs. Keep a dork audit wordlist in version control so new patterns spread to every team.
  2. Analyze. Turn each public exposure report into a control question: "could our dork audit have found this first?" Treat a hit from a leaked-credential feed as exposure-driven until proven otherwise.
  3. Apply. Feed leaked-credential feeds against your domains monthly; add new dork patterns to the shared wordlist; assign an owner and a fix date to every finding.

For each threat: which logs carry the signal, which fields matter, what normal looks like, and what is worth an alert. Field names differ by vendor; adjust them to your environment.

Threat 1 — Indexed credentials and secrets

Log sources
Web server access logs; external scan findings; crawler user-agent fields

uri, status, useragent, clientip; finding, asset, severity
Normal

Log sources
Web server access logs; external scans; cloud posture (CSPM) findings

Suspicious

Log sources

Sigma Rules and Splunk SPL

Five detections, one per ranked threat. D1 covers threat 1, D2 covers threat 3, D3 covers threat 2, D4 covers threat 4 and D5 covers threat 5. Each card below names the threat it covers. Each Sigma rule is valid YAML; each has a matching Splunk SPL query. Adapt indexes and field names to your environment and test in a measure-only window first.

Detection 1 — Sensitive path fetched on a web server Critical

Covers threat 1 — indexed credentials and secrets.

Sigma — sensitive path accessed (T1593.002)
title: Sensitive Path Accessed on Web Server
id: 2f7b9c64-8d13-4a05-9b76-3e8c1f5d2a90
status: test
description: >
  Detects successful requests for files that should never be public:
  .env files, .git metadata, database dumps and backups. Anything served
  here can be found with basic search operators once a crawler sees it.
references:
  - https://attack.mitre.org/techniques/T1593/002/
  - https://owasp.org/www-project-web-security-testing-guide/
author: Detection Engineering Team
date: 2026-01-15
logsource:
  category: webserver
detection:
  selection:
    cs-method: GET
    cs-uri-stem|contains:
      - '/.env'
      - '/.git/'
      - '/backup/'
      - '/dump/'
      - '.sql'
    sc-status:
      - 200
      - 206
  condition: selection
fields:
  - c-ip
  - cs-uri-stem
  - sc-status
  - cs(User-Agent)
falsepositives:
  - Authorized scans; internal users fetching an ops path on purpose.
level: critical
tags:
  - attack.t1593.002
  - attack.t1552.001
  - attack.tactic.reconnaissance
  - attack.ta0043
Splunk SPL — sensitive path access
index=web sourcetype=access_combined
    uri IN ("*/.env*", "*/.git/*", "*/backup/*", "*/dump/*", "*.sql*")
    status IN (200, 206)
| stats count, values(useragent) AS useragents, values(uri) AS uris,
        first(_time) AS first_seen by clientip
| convert ctime(first_seen)
| sort - count
  • Mapping note: Sigma uses combined-log fields (cs-uri-stem, sc-status); the SPL uses the access_combined extractions uri, status, clientip, useragent. The SPL IN list mirrors every Sigma contains item with wildcards.
  • False positives: your own vulnerability scanners; allowlist their IPs.
  • Tuning: measure for a week, then keep /.env and /.git/ at alert level permanently.

Detection 2 — Search crawler fetched a sensitive file High

Covers threat 3 — indexed documents and PII fetched by crawlers.

    cs(User-Agent)|contains:
      - 'Googlebot'

  - c-ip

Splunk SPL — crawler on sensitive path
index=web sourcetype=access_combined
    (useragent="*Googlebot*" OR useragent="*bingbot*")
    uri IN ("*/.env*", "*/.git/*", "*/backup/*", "*/admin*")
    status=200
| stats count, first(_time) AS first_seen by uri, host
| convert ctime(first_seen)
| sort - first_seen
  • Mapping note: same field family as Detection 1, filtered to crawler user-agents; verify crawler IPs against the engines' published ranges to defeat spoofing. The SPL path list mirrors the Sigma contains list with wildcards.
  • False positives: rare; mostly documentation pages with unfortunate names.
  • Tuning: alert on first occurrence per path per week; every hit means "now in the index".

Real-World Case Study

"Indexed exposure": a composite case built on three real, well-documented incidents, showing the full life of a search-engine-discoverable exposure. Each anchor is real; the combined timeline is simplified for teaching.

About this case study

Single incidents rarely publish every internal step, so this study combines three documented ones. Anchor one: the 2017 Deep Root Analytics voter-records exposure — about 198 million records in an open cloud bucket, found by an UpGuard researcher. Anchor two: the 2019 First American Financial exposure — hundreds of millions of sensitive documents on the public site, reachable by anyone with the URL pattern, reported by a researcher. Anchor three: the recurring bug-bounty pattern of Google-indexed .env files and admin panels with live credentials. The merged timeline below is typical of all three.

Context

A mid-size organization runs a public website, a forgotten staging environment, and cloud storage used by data teams. One path serves files without authentication. A crawler indexes them. For months, anyone with a search engine and one operator can list the content — and, in some of the anchored incidents, read live credentials. Nobody inside the company notices, because nothing in the company logs records a "search".

Timeline

  • Day 0A data pipeline change leaves a directory web-readable. It was meant to be temporary.
  • Day 0–30A search-engine crawler fetches the files. The lines exist in web logs that no one reviews.
  • Month 1–7The content sits in the index — and in caches. The organization is unaware.
  • Discovery (varies)In the anchored incidents, an external researcher finds it and reports responsibly; in the bug-bounty pattern, a participant submits it for a bounty. A hostile actor running the same dork would simply keep the findings.
  • Hours after reportAccess is restricted; the sensitive path requires authentication again.
  • Days afterEvery exposed credential is rotated. Removal requests are filed to de-index the content and clear caches.
  • Weeks afterLog review confirms (or cannot exclude) third-party access; external scans verify nothing else is open; the fix enters the control library.

Attack chain, as a hostile actor would run it

  1. Enumerate: site: queries map the victim's indexed systems, domains and forgotten hosts.
  2. Hunt files: filetype:env, intitle:"index of" and similar operators look for credentials and listings.
  3. Hunt panels: intitle:admin / inurl:admin look for consoles.
  4. Collect: read snippets and caches; record credentials, hosts and versions.
  5. Use: later, quietly — a login with a valid key, or an exploit matched to the fingerprinted stack.

The researchers in the anchored incidents stopped at discovery. Attackers continue to the last step.

Detection point

In all anchored incidents the exposure was found by outsiders, not by internal monitoring. The available internal signals were: crawler fetch lines for sensitive paths, a posture tool's public-resource findings (had it run), and cloud audit events for the exposed credentials. The cloud events come last, at the end of the chain. Detection for this technique is an asset-side discipline: hunt your own exposure.

Containment

Require authentication on the path or take it offline; block anonymous access at the storage account level; snapshot the content as evidence.

Eradication

Rotate every secret found in the content; search for the same secret elsewhere (code, laptops, other environments); fix the pipeline change that caused it.

Recovery

File de-indexing and cache-removal requests; verify removal in results; re-scan the systems and domains; review logs for use of the exposed credentials since the first possible leak.

Impact and consequences

  • Data exposure: in the anchored incidents, personal data at record scale; in the credential pattern, full account risk.
  • Provable negative is impossible: anonymous access leaves no identity — you cannot prove nobody collected it.
  • Regulatory duty: personal data in the index starts breach-notification clocks; PCI environments face ASV findings.
  • Trust and cost: public reporting, customer questions, and a permanent monitoring program that should have existed before.

Team response and communication

The organizations in the anchored incidents secured assets within hours of a responsible report — fast technical response, slow everything else. The pattern to copy: secure first, scope second, communicate third, and say plainly what was open, for how long, who is affected, and what changed. Silence let media define the story in more than one of these incidents.

Lessons learned
  1. robots.txt is a wish, not a control. Authentication decides what is findable.
  2. Assume indexed means collected. Rotate first; the cache outlives the fix.
  3. Crawler logs are exposure detectors. A crawler hit on a sensitive path is a finding, not noise.
  4. Own the search. A monthly dork self-audit finds what researchers found in every anchored incident.
  5. Fix the cause, not the symptom. The path was opened by a change process that allowed "temporary" public access.

Mitigation and Defense

ATT&CK lists Pre-compromise (M1056) for this technique: you cannot stop the query, so remove the answer. Controls below make the index empty of everything sensitive. Home and small office

  • Search yourself: your name in quotes, your email, your old usernames; remove what should not be public at the source.
  • Check your router and NAS: admin pages should not answer from the internet; disable remote administration.
  • Home cloud drives: shared-link settings default to "anyone with the link" — tighten them.
  • Breach check: use a reputable breach-notification service for your email; treat hits as passwords that must be rotated.
  • Small business extras: enable MFA on your public tools; set storage buckets private by default; do the monthly dork check on your domain.

  • Check the sensitive-path alert queue; nothing ages a day.

Weekly habits
