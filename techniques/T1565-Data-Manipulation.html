Data Manipulation T1565

Data manipulation is when an attacker inserts, deletes, or changes information to influence a real-world result or to hide their own activity. The data can sit in files and databases, travel over a network, or live inside a running program. This guide shows how the attack works, what evidence it leaves, and how to detect it with tested rules.

Overview

Start here to learn what MITRE ATT&CK says about T1565, what the technique means in plain words, and how the three sub-techniques differ.

“Adversaries may insert, delete, or manipulate data in order to influence external outcomes or hide activity, thus threatening the integrity of the data. By manipulating data, adversaries may attempt to affect a business process, organizational understanding, or decision making.”

MITRE ATT&CK, T1565 — Data Manipulation (v1.1, modified 2026-05-12)

What this means in plain words

The attacker changes information on purpose. Integrity means data stays complete and correct. Data manipulation breaks integrity while the system keeps working. A stolen file still holds true data. A changed record looks normal, so people act on it and trust it.

The change can be small, like one number in one database row. It can also be large, like wiping many files. MITRE ATT&CK notes that complex targets need special skills and study time, because the attacker must know which data drives the outcome.

ATT&CK's official procedure example is FIN13 (group G1016): FIN13 “has injected fraudulent transactions into compromised networks that mimic legitimate behavior to siphon off incremental amounts of money”. Small, normal-looking changes are the signature of this technique.

Where it sits in the attack chain

ATT&CK places T1565 in the Impact tactic (TA0040). Impact is the stage where the attacker causes real harm. By then, the attacker usually has already gained access, moved through the network, and found the data that matters.

There is one common exception: log tampering. Attackers often change or delete logs during the attack, not at the end, so defenders cannot follow their steps. That behavior overlaps with Defense Evasion, for example T1070 Indicator Removal. Watch for it early too.

Manipulation is different from T1485 Data Destruction. Destruction removes data. Manipulation keeps the system running on false data, which is harder to notice and often more valuable to the attacker.

The three sub-techniques

IDNameData stateWhat the attacker changesOfficial procedure example
T1565.001 Stored Data Manipulation Data at rest — data saved on disks or in databases Files, database rows, stored emails, configuration APT38 used DYEPACK to create, delete, and alter records in databases used for SWIFT transactions
T1565.002 Transmitted Data Manipulation Data in motion — data moving over a network or between processes Messages and fields on the wire, for example payment instructions APT38 used DYEPACK to manipulate SWIFT messages en route to a printer
T1565.003 Runtime Data Manipulation Data in use — data inside a running program's memory What an application displays or produces while it runs APT38 used DYEPACK.FOX to manipulate PDF data as it is accessed, hiding fraudulent SWIFT transactions from the display
Note

Words used in this guide: at rest — data saved on disk; in transit — data moving over a network; at runtime — data inside a running program. SOC (Security Operations Center) is the team that watches alerts. SIEM (Security Information and Event Management) is the system that collects and links logs. FIM (file integrity monitoring) is a tool that records file changes against a known-good baseline.

Typical data and log sources (practitioner guidance)

ATT&CK links T1565 to a Detection Strategy called “Detection Strategy for Data Manipulation” and no longer publishes a fixed data-source list on the technique page. The sources below are our own practitioner list, not an official ATT&CK data-source mapping: database audit logs, file integrity monitoring, endpoint detection (EDR) events such as memory access and injection, Windows event logs (1102, 5136), Linux auditd, Zeek network logs (ssl, dns), cloud audit trails (AWS CloudTrail), and proxy logs. Section 5.4 shows a realistic sample event for each.

    attacker bank system infrastructure defender
    Written version of the attack story (works without JavaScript)
    1. Step 1 — The intruder lands on a server. Using a stolen VPN account, the attacker signs in from a new country and reaches a bank jump server, FIN-JUMP-01. A small backdoor service starts and waits for commands. The VPN allowed the login because the password was valid.
    2. Step 2 — Stored data manipulation (T1565.001). From the server, the attacker opens a database session and changes one customer balance record. The change is small, so it sits below alert thresholds. The database keeps serving traffic; nothing looks broken.
    3. Step 3 — The SOC sees the stored-data hits. Two signals arrive together: the database audit log shows an UPDATE on the accounts table at 02:14, outside any change window, and file integrity monitoring reports a checksum change on the SWIFT export folder. The analyst links both to the same server.
    4. Step 4 — Transmitted data manipulation (T1565.002). The attacker now touches data in motion. A payment message travels from the SWIFT software toward the gateway and the print path. The attacker alters fields on the way, so the printed instruction does not match the stored record.
    5. Step 5 — The SOC sees the transit anomalies. The print server reports an unknown module, and the proxy logs a TLS session with a new certificate on an internal path. Neither alert alone proves fraud, but both point at the same payment flow.
    6. Step 6 — Runtime data manipulation (T1565.003). On the review workstation, the attacker patches the PDF viewer in memory. When the reviewer opens the statement, the viewer hides the fraudulent rows. The disk file stays untouched, so file scans see nothing wrong.
    7. Step 7 — Reviewer and EDR break the illusion. The endpoint platform raises a memory-tamper alert on the viewer process. At the same time, the reviewer compares the statement with the database and finds rows that do not match. The fraud is blocked before the money leaves the bank.
    8. Step 8 — Response and integrity restore. The SOC opens a P1 case, isolates the server and the workstation, and revokes the stolen VPN account. The team restores the changed records from a trusted backup, verifies them against checksums, and reports the incident to the regulator.
    3

    Red Team Perspective

    This section explains how attackers approach data manipulation. It is written for defenders and authorized labs. Everything here is educational; use it only on systems you own.

    When and why attackers use it

    Attackers pick data manipulation when the value of the change is higher than the value of stealing data. Theft usually alarms the victim fast. A quiet change can pay out for months. FIN13's known behavior — many small transfers that mimic normal traffic — is exactly this trade. Other goals are changing grades or medical records, hiding attack activity from logs, or making a report say what the attacker needs.

    In the chain, the technique usually appears after discovery, once the attacker knows which system holds the target data. It can also appear early in a small form: one cleared log file right after the first foothold, so the intrusion stays invisible while the attacker explores.

    What the attacker needs first

    Data manipulation has hard preconditions. The attacker needs write access to the target store, path, or process. They also need to know which data matters. In practice that means one or more of: valid credentials, a compromised host inside the network, a position on the network path, or code execution inside the target application.

    They also need business knowledge. If a report prints at 08:00, the change must land before 08:00. Attackers study change windows, holidays, and staffing times first, because actions during a quiet window are the ones nobody questions.

    How the three variants are performed

    Stored (T1565.001)

    The attacker edits files, database rows, or configuration. Common routes are a database client run from a compromised host, a web shell writing into a web root, or a script that rewrites a config file. The strongest version changes the data and the logs that recorded the change, like the DYEPACK “eraser” behavior reported in the Bangladesh Bank case.

    Transmitted (T1565.002)

    The attacker takes a position on the path: ARP spoofing on a local network, DNS answers that point to a fake service, or a rogue proxy. Then they alter fields while data flows. Strong encryption limits what can be changed, so attackers try to downgrade protection, abuse a trusted endpoint, or sit inside an already-decrypted segment.

    Runtime (T1565.003)

    The attacker changes memory inside a running process: hooking a function, patching values, or injecting code that rewrites what the program shows and sends. ATT&CK's example is DYEPACK.FOX, which changed PDF data as it was accessed so fraudulent SWIFT rows disappeared from the screen. Altered application binaries and changed file associations can cause the same effect.

    A safe lab exercise

    Run this only on a machine and database you own, such as a training VM with a test database. The goal is to see what the logs look like when a stored record changes outside a change window, not to build an attack tool.

    lab-only · observe a stored data change and its audit trail
    # 1. Create a tiny test database (SQLite, single file)
sqlite3 lab.db "CREATE TABLE payments (id INTEGER, amount INTEGER);"
sqlite3 lab.db "INSERT INTO payments VALUES (1, 500);"

# 2. Turn on a simple trail: record every shell command (defensive view)
script -a lab_session.log

# 3. The "attacker" action: change a stored record
sqlite3 lab.db "UPDATE payments SET amount = 99000 WHERE id = 1;"

# 4. The defender questions: who changed what, and when?
stat lab.db            # did the file times move?
sqlite3 lab.db "SELECT * FROM payments;"   # does the value differ from the backup?
grep -a "UPDATE payments" lab_session.log  # is there any trail?
    What you should notice

    The change took one command. Without step 2, no trail would exist at all. This is the core lesson: integrity depends on evidence you collect before the attack, not after.

    Common variations and attacker mistakes

    VariationWhat it looks likeAttacker mistake to expect
    Tiny editsChange one value under alert thresholds, for example a small balance shiftRepeating the pattern creates a trend that analytics can catch
    Log trimmingDelete selected lines instead of the whole file, to avoid a “log cleared” eventFile size, checksums, or shipping gaps still reveal the cut
    Config editsChange hosts files, cron jobs, or app settings to redirect or weaken controlsEditors leave temp files, and file-integrity tools alarm on protected paths
    In-memory display tricksPatch what the user sees without touching server dataEndpoint agents notice cross-process injection into the app
    Transit rewritesAlter fields between two trusted systemsTLS pinning, payload signing, and proxy logs break the illusion
    Danger

    Never test these ideas on systems you do not own. Changing real business, medical, or industrial data can cause harm that is hard to undo and can be a crime. Use isolated labs, fake data, and written permission.

    4

    Blue Team Perspective

    Data manipulation rarely crashes anything, so defenders must look for wrongness, not breakage. This section shows where to look, what the artifacts look like, and how to triage fast.

    How defenders can see it

    Three kinds of visibility work together. Integrity views compare current data with a known-good baseline: file hashes, row checksums, configuration snapshots. Behavior views watch the actions around the data: who wrote, when, from which host, and whether that fits the change calendar. Output views check that two independent sources agree: if the app says one thing and the database says another, something is wrong.

    No single view is enough. The Bangladesh Bank attackers beat each control alone, but the combination of database audit, network monitoring, and a human reviewer exposed them.

    What artifacts it leaves

    Even careful attackers leave traces: file modification times that moved, database audit rows for unexpected accounts, shipped log streams with a gap, TLS sessions with a new certificate, endpoint events for cross-process memory access, and user reports that “the screen looked wrong”. A single trace can be noise; two together are usually a case.

    Log tampering is itself an artifact. A clear event (Windows 1102), a shipping gap, or a truncated file often arrives after the attacker's other steps. Treat it as a high-priority signal, not as routine maintenance noise.

    Where to look

    PlaceWhat to collectWhy it matters
    Database audit logsStatements, accounts, client IPs, row counts for sensitive tablesDirect proof of stored data changes and of who ran them
    File integrity monitoring (FIM)Hashes and times for configs, web roots, and log directoriesCatches edits to files at rest, including hosts and app configs
    EDR telemetryProcess creation, memory access, remote-thread and module eventsShows runtime manipulation and the tooling behind it
    Windows event logs1102 (Security log cleared), 4670, 4688 process eventsReveals log tampering and suspicious process trees
    Zeek, proxy, NetFlowTLS certificates, DNS answers, flow paths between tiersExposes transit-level detours, downgrades, and rewrites
    Cloud audit trailsCloudTrail object writes on buckets that hold exports and backupsShows tampering with data copies held in the cloud
    Backups and exportsLast good backup, row-level diffs, export checksumsYour independent truth when live data is in doubt

    Why it matters for the SOC

    If your SOC only alerts on malware and downtime, data manipulation sails through. The business impact is real even when uptime is perfect: wrong invoices, wrong patient data, wrong safety readings. Correlating integrity signals with behavior signals is what turns three quiet alerts into one clear case. It also changes response priorities: restoring uptime is not enough; you must restore truth.

    Short triage flow

    1. 1. Validate the signal. Confirm the alert is not a known change job. Check the change calendar and the account that made the write.
    2. 2. Scope the change. Find every record or file touched in the window: audit logs, FIM diffs, row counts against the last good backup.
    3. 3. Preserve evidence first. Snapshot the database, export the logs, image the endpoint before anyone “fixes” values by hand.
    4. 4. Contain the path. Isolate the host or account that made the change; block the network path if transit was tampered with.
    5. 5. Restore truth. Recover from a trusted backup and re-verify with checksums or an independent report.
    6. 6. Escalate and report. Notify the data owner, security leadership, and, if rules require it, regulators. Manipulation of financial or health data often has reporting duties.
    Warning

    Do not delete “bad” data during triage. Overwritten values destroy the evidence you need for scope, root cause, and any legal follow-up. Copy first, then act.

    5.1 · Compliance and Regulation Mapping

    Integrity attacks are a compliance problem even when nothing is stolen. Most frameworks treat data integrity as a duty of its own: personal data must stay accurate, health records must not be altered, payment systems must spot tampering, and logs must be protected so you can prove all of this later. A silent change to a database row can therefore be a reportable breach even if the attacker copies nothing. It can also void the trust an auditor checked last year, because the evidence chain now contains data the attacker touched. This matters for planning too: controls that detect manipulation (file integrity monitoring, database audit, protected logs) are not optional extras. They are the evidence base that several frameworks demand, and they decide whether you can even answer the question “was this record changed, by whom, and when?” after an incident.

    How auditors test this

    Across all five frameworks, auditors ask for the same evidence: FIM reports showing protected paths and baselines, database audit configuration for sensitive tables, log review records with named reviewers, change tickets that match audit rows, and restore test results. Keep the rules in 5.5 mapped to the table above, and store one test result per rule. When an assessor asks “how do you detect unlawful alteration?”, you can show the control reference, the rule, and the test in one page.

    5.2 · Threat Intelligence

    Threat intelligence is knowledge about attackers: who they are, how they work, and what they target. For data manipulation it answers three questions: which groups use this technique, in which sectors, and what their tools leave behind. Good intelligence has a source, a confidence level, and an application — a concrete change to a detection or a control.

    Sources. Use MITRE ATT&CK (and its STIX/TAXII feeds) as the shared language for technique and group IDs. Add CISA cybersecurity advisories, vendor reports from FireEye/Mandiant, Cisco Talos, Sygnia, Kaspersky, and ESET, and sector sharing through ISACs such as FS-ISAC for finance. Feeds and platforms help you share at machine speed: MISP servers, AlienVault OTX pulses, and VirusTotal Collections. Your own past incidents and purple-team results are the strongest source of all, because they show which manipulation attempts actually reach your systems.

    Workflow. Collect with a purpose: every feed must map to something you can change. Deduplicate, then map each actor report to ATT&CK IDs, then apply: backtest your Sigma rules against the new indicators, write hunting hypotheses, bias triage toward the actors that target your sector, and brief leadership on what changed. Re-check quarterly, because tooling changes and old indicators stop matching.

    FIN13 (G1016), Mexico-focused finance; ATT&CK procedure example citing Sygnia, 2022 High — ATT&CK procedure example Injected fraudulent transactions into compromised networks that mimic legitimate behavior, to siphon off incremental amounts of money Baseline “normal” money movement; alert on many tiny balance deltas and on out-of-window writes (DET-001)
    APT38 (G0082), bank theft campaign family; FireEye report, Oct 2018 High — ATT&CK procedure example Used the DYEPACK family to alter stored SWIFT records, change messages en route to a printer, and hide fraud from the display (see the case study in section 6) Monitor payment-gateway hosts and DB audit together; treat log erasure on SWIFT systems as P1 (DET-001, DET-002)

    Carbanak / FIN7, banks and retail; Kaspersky reporting, 2013–2016 Medium — multiple public reports Manipulated account balances inside bank systems after learning internal processes and limits Alert on database clients launched from shells on servers; pair with reconciliation reports (DET-001, DET-006)
    How to read the confidence labels

    High means ATT&CK lists the behavior as a procedure example, or a primary vendor report documents it. Medium means several public reports agree but no primary source covers this exact technique. Confidence describes the evidence, not the danger. Track actor tooling, not only names: a group that changes tools still leaves manipulation-shaped traces in your logs.

    Tuning and false positives

    Tune every rule against two weeks of data before you enable alerting. Start with the writer lists: DET-001's approved users, DET-003's installers, DET-008's automation roles. Keep the lists narrow and owned; a list nobody owns grows until the rule is silent. For threshold rules, raise or lower the counts in the SPL eval severity steps to your real traffic. Add a change-ticket lookup where your workflow supports it: joins against tickets auto-close approved changes and keep analysts focused. Review each rule quarterly, and re-test it after every tuning change with the sample events from 5.4 as a regression set.

    Validation

    Validate each Sigma rule with the sigma CLI (sigma check or sigmac -t splunk rule.yml) and test each SPL query against a short window of real data before enabling alerts. Keep one true positive and one known-noisy case per rule in a test dataset, so you can prove the detection still works after every change.

    Real-World Case Study

    The Bangladesh Bank SWIFT heist of February 2016 is the showcase case for the whole T1565 family: one intrusion that used stored, transmitted, and runtime manipulation together. It is also the source of ATT&CK's official procedure examples for T1565.001, T1565.002, and T1565.003. This summary uses only well-documented public facts, mainly the FireEye/Mandiant APT38 report (October 2018) and public court and press records.

    Context

    Bangladesh Bank, the country's central bank, sends payment orders through SWIFT (the global bank messaging network) using software called SWIFT Alliance Access. Attackers later linked by investigators to APT38/Lazarus operated inside the bank's network for weeks before they acted. They studied the payment process, learned the timings, and built tooling for every stage: change records at rest, alter messages on the way out, and hide the traces.

    On 4–5 February 2016 the attackers sent 35 payment requests worth about $951 million through the bank's SWIFT connection. Five of them, totaling $81 million, went through the Federal Reserve Bank of New York. Most of the money went onward to accounts at Rizal Commercial Banking Corporation in the Philippines and then into casinos. The rest was blocked: a routing field misspelled the word “Institution” as “Dinstiution” on a Jupiter Street address, and that typo helped stop further transfers. About $15 million was reported recovered in the Philippines; the bulk of the $81 million was never returned.

    The three sub-techniques in one incident

    Stored — T1565.001

    The DYEPACK tool created, deleted, and altered records in the databases used for SWIFT transactions, so the bank's own records did not show the fraudulent orders. An “eraser” component also deleted logs and database records to hide the intrusion.

    Transmitted — T1565.002

    DYEPACK manipulated SWIFT messages en route to a printer. The printed confirmations are what staff check, so forged messages on the print path kept the fraud invisible while the money moved.

    Runtime — T1565.003

    The same campaign family used DYEPACK.FOX, which manipulates PDF data as it is accessed so fraudulent SWIFT transactions disappear from what the user sees. ATT&CK lists it as the official example for this sub-technique.

    Timeline

    Time (reported)Event
    Weeks before Feb 2016Attackers live in the network, study the payment process, and prepare tooling for records, messages, and display tampering.
    4–5 Feb 201635 payment requests worth about $951M are sent; 5 requests totaling $81M pass through the New York Fed.

    Detection story

    No single control caught the attack. The first strong signal came from outside: SWIFT's own monitoring flagged the bank's environment, and the missing print confirmations raised questions inside the bank. The attackers' biggest cover was trust — the printout matched what staff expected, because DYEPACK had rewritten it. A database activity monitor, file integrity monitoring on the SWIFT folder, and off-host logging would each have produced evidence earlier. The attack is now a standard teaching case for why payment systems need layered integrity controls, not only access control.

    Who responded and how

    The bank's security team worked with FireEye's incident responders from March 2016. SWIFT ran its own investigation of the Alliance Access environment. Bangladesh's central bank leadership and regulators faced public scrutiny, and the governor resigned. Law enforcement agencies in several countries traced the stolen funds through the Philippine banking system, and part of the money was frozen and later returned. SWIFT, as the network operator, responded with the Customer Security Programme, which made security controls mandatory for all member banks from 2017 onward.

    Lessons learned

    • Trust no single view of a payment. The stored record, the wire message, and the printed confirmation were each tampered with. Reconcile at least two independent sources.
    • Logs must leave the host. The eraser worked because evidence lived where attackers could delete it. Ship logs off-host in near real time.
    • Least privilege on payment systems. The attackers needed deep access to SWIFT software, databases, and the print path. Segment those systems and restrict who can write.
    • Integrity monitoring on critical folders. FIM on the SWIFT directories would have flagged the record and file changes within minutes.
    • Rehearse the fraud scenario. The bank had no runbook for “our payment records are lies”. Practice scope, restore, and regulator reporting before you need them.

    Mitigation and Defense

    You cannot prevent every change an attacker attempts, but you can make changes hard, loud, and reversible. This section starts with the mitigations MITRE ATT&CK lists for T1565, then covers enterprise controls, home users, and a prioritized action list.

    ATT&CK does not list Update Software (M1051) as an official mitigation for this technique, but patching still matters in practice: the initial access that leads to manipulation usually uses a known vulnerability. Treat patching as a supporting control, not the answer to integrity attacks.

    Enterprise controls by area

    Identity and access

    Apply least privilege to databases, file shares, and log stores. Separate admin accounts from daily accounts, require MFA for remote access, and rotate service-account credentials. Give payment systems the strictest model: the person who creates a payment never approves it, and no account can both write data and clear logs.

    Endpoint

    Run EDR with tamper protection enabled, application control on servers, and macro blocking for office files. Keep FIM agents on systems that hold critical files and configs, with protected baselines. EDR memory-tamper and injection events (DET-005, DET-006) are your window into runtime manipulation.

    Network

    Segment payment and database systems from office networks, control egress, and use TLS with certificate validation on internal service-to-service traffic. Monitor DNS answers for internal names (DET-007) and watch for new certificates on internal paths (DET-004). These two rules stop the redirection that makes transit tampering possible.

    Logging and monitoring

    Ship logs off-host in near real time, make log stores append-only, and alert on gaps and clear events (DET-002). Enable database audit on sensitive tables (DET-001). Build the eight rules in section 5.5 into your SIEM and test them with the sample events from 5.4.

    Data and backup

    Follow 3-2-1: three copies, two media types, one offsite and immutable. Verify restores quarterly, not only backup jobs. Keep checksums or row counts for critical datasets so a diff after an incident takes minutes, not days. Protect cloud copies with strict write policies (DET-008).

    Policy and response

    Write change-window rules that analytics can read: who may change what, when, and from which host. Add a data-integrity runbook: preserve, scope, restore, report. Rehearse it twice a year with a “record changed” exercise that includes the regulator-notification step.

    Home and small-office advice

    Home users face the same idea at smaller scale: ransomware that rewrites files, scammers who change bank details in emails, and malware that alters what the browser shows. Four habits cover most of it. Keep automatic, offline backups of important files and test one restore. Use a separate administrator account for installs and updates; browse and work as a standard user. Turn on automatic updates for the operating system, browser, and router firmware. Treat any request to change payment details as suspect until you confirm it by a phone call to a number you already know.

    These are the ten failure patterns detection teams hit most often with data-integrity work. Each has the symptom you will notice, the root cause, the fix, and the prevention that keeps it from returning.

    #MistakeSymptomRoot causeFixPrevention

    2 No integrity baselines After an incident nobody can say what the correct values were Checksums, row counts, and FIM baselines were never built Build baselines for critical files and tables now, before an incident Data classification drives which stores get baselines first
    3 Watching only the perimeter Firewall and email alerts look clean while records quietly change Detection budget went to ingress and egress, not to the inside Add internal telemetry: DB audit, FIM, EDR on servers (DET-001, DET-005, DET-006) Monitoring requirements include internal integrity sources per system
    4 Over-privileged DB and app service accounts The fraud runs under a service account and nobody questions it Service accounts hold admin rights and are shared across systems Split duties: read, write, approve; scope each account to one job Quarterly access review of service accounts on payment systems

    Healthy habits

    Daily

    Review new integrity-class alerts. Check log pipeline health: every source in, on time. Skim database audit summaries for sensitive tables.

    Weekly

    Reconcile one critical report against its data source. Review FIM deltas with system owners. Confirm backup jobs completed and shipped copies exist.

    Monthly

    Validate one detection end to end. Re-baseline one system. Review allowlists after change windows. Report integrity metrics to leadership.

    Cheat Sheet

    Everything important from this page, compressed for use during an incident or while writing detections.

    One-line definition

    T1565: the attacker inserts, deletes, or changes data — at rest, in transit, or at runtime — to influence outcomes or hide activity.

    Attack chain in 5 steps

    • Get write access: credentials, a compromised host, a network position, or code execution.
    • Study the process: which data drives the outcome, and when nobody looks.
    • Make the change: at rest (T1565.001), on the wire (T1565.002), or in memory (T1565.003).
    • Hide the change: erase or trim logs, forge confirmations, patch the display.
    • Profit: act on the false data, or let the business act for you.

    What to collect

    Database audit (MySQL audit JSON), FIM, Sysmon (Events 8, 10, 11, 22), Windows Security (1102, 5136), Linux auditd, Zeek ssl.log and dns.log, AWS CloudTrail, proxy logs, and an independent copy of critical data (backup or export with checksums).

    Detection rules (from 5.5)

    DET-001
    Suspicious UPDATE on balance, amount, or status columns in MySQL
    DET-002
    Windows Security log cleared (Event 1102)
    DET-003
    Hosts file written by an unapproved process (Sysmon 11)
    DET-004
    Invalid or self-signed TLS certificate to an internal server (Zeek)
    DET-005
    ptrace syscall by an unusual binary (Linux auditd)
    DET-006
    CreateRemoteThread into a business application (Sysmon 8)
    DET-007
    Internal name resolved to a public IP (Zeek DNS)
    DET-008
    PutObject into a finance-export or backup bucket by a rare principal

    First response

    • Verify with a second source before touching anything.
    • Isolate the writing host or account.
    • Preserve evidence: snapshot data, export logs, image the endpoint.
    • Compare to known-good: backup, checksums, row counts.
    • Restore from a trusted copy and re-verify.
    • Report: data owner, leadership, regulator if required.
