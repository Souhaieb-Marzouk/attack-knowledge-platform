T1561.002 Disk Structure Wipe

Disk Structure Wipe is when an attacker destroys the "map" of a disk instead of the files on it. The master boot record (MBR), partition tables, and file system indexes are overwritten, so the computer can no longer find or load anything, even if much of the data is still physically on the platters.

Overview

What "structure wipe" means, how it differs from erasing files, and why it is one of the most damaging things an attacker can do to a machine.

A hard disk looks complicated, but its layout is simple to picture. A small part of the disk holds the map: where each partition starts, which file system is used, and where every file lives. The rest of the disk holds the streets: the actual bytes of documents, databases, and programs. Disk Structure Wipe attacks the map. When the map is gone, the computer cannot find the streets, cannot load the operating system, and cannot even tell that data exists.

This sub-technique sits under T1561 Disk Wipe in the Impact tactic. The sibling sub-technique, T1561.001 Disk Content Wipe, erases file contents. On this site you can also read the parent guide page and the sibling guide page. Structure wipe is usually smaller and faster than content wipe. Overwriting a few sectors at the very start of the disk can make a whole machine unbootable. It is often harder to recover from, because the file system index itself is damaged.

Structure vs content wipe

Content wipe overwrites file data. Structure wipe overwrites the disk's "map": the master boot record (MBR), the GUID partition table (GPT), the master file table (MFT), or the bootloader. A few thousand overwritten bytes can do more damage than gigabytes of file wiping.

Why it is so damaging

After a structure wipe the host usually cannot start at all. Even bootable rescue media may find no files if the MFT is destroyed. Normal recovery tools fail, so teams must rebuild from images and restore from backups.

Where attackers use it

Mostly in destructive attacks: wiper campaigns, revenge attacks, and "fake ransomware" where the attacker never intended to decrypt. It is often paired with T1490 Inhibit System Recovery so backups and shadow copies cannot help.

Key disk-structure terms

Key disk structure components and what happens when each is wiped
ComponentWhat it isEffect if wiped
MBRMaster Boot Record - the small boot program at the start of a disk (first 512 bytes), plus the old-style partition table.Machine cannot start; "Operating system not found" or garbage at boot.
GPTGUID Partition Table - the modern partition map used with UEFI (Unified Extensible Firmware Interface) boot.Partitions "disappear"; firmware shows no boot device.
MFTMaster File Table - the index of every file on a Windows NTFS (New Technology File System) volume.Windows cannot find any file, even though raw bytes may remain.

Written story (text alternative)

The same eight steps in plain text, for screen readers, printing, or anyone who prefers to read.

  1. Seed. The attacker compromises a software vendor and slips the payload into a signed-looking update. It lands on one finance PC. Defenders see: nothing obvious yet - only a normal-looking update download in proxy logs.
  2. Spread. The payload steals password hashes and tokens from patient zero and uses SMB (Windows file-sharing) exploits and admin shares to copy itself to other machines without any user clicking anything. Defenders see: unusual psexec-style service installs and many SMB sessions from one host.
  3. Arm. On each infected host the payload creates a scheduled task or registry run key that points at the destructive module, set to fire at the next restart. Defenders see: Windows Event ID 4698 (scheduled task created) and Sysmon Event ID 1 process creations writing those keys.
  4. Strike. Machines restart (in the real event, an update server forced reboots). The payload opens the raw disk with admin rights and overwrites the master boot record with its own stub and a ransom note. Defenders see: Sysmon Event ID 9 RawAccessRead targeting \\.\PhysicalDrive0, seconds before each host goes down.
  5. Blind. The master file table is scrambled, so even bootable media finds no files to decrypt. Defenders see: hosts stuck at boot, "operating system not found" screens, and helpdesk tickets spiking.
  6. Mask. A colorful ransom note is displayed at boot, but the key needed to undo the damage was destroyed with the machine - payment could never restore anything. Defenders see: photos of boot screens, not decryption requests; no network contact from the wiper.
  7. Alarm. The SOC connects the dots: a wave of Sysmon raw-access events, then a spike of Kernel-Power 41 (unexpected reboot) events across many hosts at once. Defenders see: the correlation that turns scattered tickets into a single major incident.
  8. Recover. The network is cut into segments to stop the spread, machines are rebuilt from clean images, and data is restored from backups that were offline and untouched. Defenders see: the value of offline backups and a tested fleet-rebuild runbook.

Red Team Perspective

How attackers think about structure wipe: when they use it, how it is done technically, and the mistakes that make wiper campaigns self-defeating.

When and why attackers wipe the disk structure

Structure wipe is the cheapest way to destroy a machine. Overwriting the first few hundred kilobytes of a disk - the boot code and the file system index - is far faster than encrypting or overwriting the whole drive, and the result is just as final. Public incident reporting shows this "corrupt the map, not the streets" approach in the biggest destructive attacks of the last decade. NotPetya, Shamoon, HermeticWiper, and WhisperGate all damaged boot records or file system tables rather than fully erasing disks.

Attackers choose it for three reasons. First, speed at scale: one small write per host can take down a thousand machines in minutes. Second, evidence destruction: a wiped MFT takes forensics with it, because file timelines, registry hives, and logs stored on the system volume may become unreachable. Third, extortion theater: displaying a ransom note after a structure wipe makes a destructive attack look like ordinary ransomware, adding confusion during the incident.

How it is performed

The technical pattern is consistent across platforms:

  • Get privileged code execution. Raw disk writes need Administrator or SYSTEM rights on Windows, root on Linux. Wipers arrive after privilege escalation, or ride on software that already runs with high rights.
  • Open the raw disk. On Windows this means CreateFile on a device path such as \\.\PhysicalDrive0, then WriteFile to specific offsets. On Linux it means writing to the block device node, for example with dd, or calling wipefs. On macOS it can mean diskutil eraseDisk or damaging the boot volume.
  • Corrupt the map. Overwrite the MBR bytes, poison the GPT entries, scramble MFT records, or delete the bootloader (for example GRUB files on Linux servers).
  • Time the blast. Many wipers arm the damage for the next restart using scheduled tasks or registry run keys, so the payload has hours to spread first. NotPetya famously used a fake "chkdsk" screen while it rewrote the MFT.
Danger

Lab only - never run against systems you do not own. Safe practice shapes used by red teams to study this technique: a Sysinternals diskprobe-style raw sector viewer on a scratch VM to read sector 0; dd aimed at a throwaway USB stick; wipefs -n (dry-run, no writes) on a lab disk; breaking a bootloader in a snapshot-reverted VM. All of these teach the same disk-anatomy lessons without destroying anything that matters.

Documented malware behaviors (public reporting)

  • NotPetya (2017): overwrote the MBR with a stub that displayed a ransom note, and encrypted or scrambled MFT structures; the "key" was destroyed, so recovery was impossible.
  • HermeticWiper (2022, Ukraine): abused legitimate signed drivers to write directly to disk partitions and Master Boot Records of fleet hosts.
  • Shamoon (2012/2016/2017, energy sector): replaced the MBR with a burning-fire image and wiped file contents, leaving thousands of workstations unbootable.
  • KillDisk (2015-2016, Ukraine): corrupted MBR and MFT records on government and finance systems during the BlackEnergy-era intrusions.
  • WhisperGate (2022, Ukraine): a multi-stage chain whose first stage corrupted the MBR before later stages destroyed files.
  • APT38 (documented on ATT&CK group pages): used a custom MBR wiper named BOOTWRECK to make systems unbootable.
  • BFG Agonizer (2023 vendor reporting): opened a device handle to \\.\PhysicalDrive0 to wipe a boot sector, a documented example outside classic IT fleets.

Prerequisites and common variations

An attacker needs three things: privileged code execution somewhere in the fleet, a way to distribute the payload (supply chain, wormable exploit, stolen admin credentials), and a trigger time. Variations include wiping only non-system partitions (slower to notice), wiping MFT only (disk looks intact but nothing opens), combining wipe with firmware damage, and "ransom-note-only" attacks where encryption never happened at all.

Warning

Two attacker mistakes worth knowing. Self-lockout: a structure wipe destroys the attacker's own access on that host - any agent, tunnel, or backdoor on the wiped machine is gone, so timing matters and the wipe is usually the last action. Self-defeating extortion: displaying a ransom note while the recovery key is destroyed means victims learn quickly that paying is pointless, which invites aggressive public response and law-enforcement attention.

Blue Team Perspective

What a structure wipe looks like from the SOC: the telemetry that fires, the artifacts left behind, and a triage flow for the worst hour of an incident.

How defenders notice

Ideally, the SOC notices the raw disk write before the damage lands - a Sysmon Event ID 9 (RawAccessRead) or an EDR (Endpoint Detection and Response) alert when a process opens \\.\PhysicalDrive0. In reality, many organizations first notice the aftermath: a wave of helpdesk calls saying "my PC just restarted and shows a weird screen", clusters of Kernel-Power 41 (unexpected reboot) events, EDR alerts about suspicious drivers loading, and a restart storm across one department. Because the wipe happens at reboot, the first few minutes often look like a patching problem, not a major incident - and that confusion costs recovery time.

Artifacts left behind

  • Corrupted MBR bytes at sector 0 (replaced with wiper stub or garbage) and a missing or poisoned partition table.
  • Destroyed MFT - the volume mounts with zero files, or boot media reports "no operating system found".
  • A fake note at boot - a full-screen ransom message on machines that were never really encrypted.
  • Wiper remnants on partially hit hosts - the binary, the scheduled task or run key that armed it, and the driver it abused. These hosts are the best forensic evidence.
  • Log evidence off-host - Sysmon, EDR, and SIEM (Security Information and Event Management) copies of the raw-access and process-creation events that happened seconds before each host died.

Where to look

Why it matters and where it fits

A structure wipe makes the whole host unavailable, not just some files. Recovery may be impossible without golden images, so the SIEM copy of each host's logs becomes the only forensic record. Evidence is destroyed on the victim itself - which is exactly why central log retention matters and why responders should pull volatile logs off surviving hosts early. In the ATT&CK chain, this technique is a late Impact action: it pairs with T1490 (Inhibit System Recovery, deleting shadow copies and backups) and T1485 (Data Destruction). When you see it, look back at the initial-access and lateral-movement stages to scope the campaign - the wiper's blast radius is the end of a story that started days or weeks earlier.

First-hour triage flow

  1. Minutes 0-5Declare a major incident. Correlate the reports: multiple hosts booting into a note or failing to boot is not a helpdesk queue - it is a destructive attack in progress.
  2. Minutes 5-15Contain before the next restart wave. Isolate network segments, suspend scheduled tasks and forced reboots (the update server that triggered NotPetya's reboot is the classic example), and block lateral paths.
  3. Minutes 15-30Identify patient zero and the trigger. Chain Sysmon EID 1 (process creation) and EID 9 (raw access) to find which host first opened the raw disk and which task or update armed the wipe.
  4. Minutes 30-60Protect remaining hosts. Push containment: block the wiper hash and driver, disable the armed tasks fleet-wide, and raise EDR to aggressive mode on high-value systems.
  5. Hour 1-4Assess recoverability. Confirm whether MBR, partition table, or MFT was hit per host group; this decides between quick boot repair and full rebuild.
  6. Hour 4+Restore from trusted images and offline backups. Rebuild from golden images, restore data from copies that were offline or immutable, and verify patches before reconnecting segments.
  7. Days 1-7Review and harden. Post-incident review: enable Sysmon raw-access logging fleet-wide, fix the original access path, and rehearse the fleet-rebuild runbook.
Best practice

The difference between a bad week and a company-ending event is usually one thing: whether Sysmon EID 9 (or equivalent EDR telemetry) was enabled and shipped off-host before the wipe. You cannot alert on, or investigate, telemetry that died with the machine.

5.3 Threats ranking and categorization

The seven concrete threats below drive everything in 5.4 and 5.5. Each threat gets its own log patterns with matching severity. Threats TH-01 to TH-06 also get a Sigma rule and an SPL query in 5.5. TH-07 reuses the raw-access logic from TH-01 and TH-03, so it has no separate rule.

TH-01 Critical Windows

Raw write to \\.\PhysicalDrive0 overwriting the Master Boot Record - the classic structure wipe.

Preconditions
SYSTEM-level code execution on the host.
Impact
Host is unbootable; on-disk evidence is largely destroyed.
Why this rank
The signature move of the biggest destructive incidents (NotPetya, Shamoon, HermeticWiper).
TH-02 Critical Windows

MFT or partition-table corruption - the file system "map" destroyed while the disk looks physically intact.

Preconditions
SYSTEM-level code execution; often a signed driver or backup-style API is abused.
Impact
Even boot media cannot find data, so recovery is far harder than after a content wipe.
Why this rank
Turns a repairable boot problem into a full rebuild problem.
TH-03 High Linux

dd to /dev/sda, wipefs, or bootloader (GRUB) removal on servers.

Preconditions
root code execution on the server.
Impact
Server down; data may survive but is hard to reach without the map.
Why this rank
Linux has fewer endpoint hooks than Windows, so detection depends on auditd being configured.
TH-04 Medium macOS

Destructive erase of the boot volume (diskutil erase) or firmware-level damage on Mac endpoints.

Preconditions
root or an admin user tricked into authorizing the erase.
Impact
Complete endpoint loss; rare in practice.
Why this rank
Low frequency, but when it happens the loss is total and hard to stage back.
TH-05 Medium Cloud

Abuse of cloud APIs to format, detach, or destroy attached disks and instance boot volumes.

Preconditions
Compromised cloud credentials or keys with storage permissions.
Impact
Instant loss of instances without ever touching the guest OS.
Why this rank
A growing pattern, and the cloud audit log is the only reliable control point.
TH-06 High Hypervisor Cloud

Corruption or deletion of virtual disk files (VMDK, VHD) on hypervisor datastores - the virtual equivalent of a structure wipe, done once for many machines.

Preconditions
Root or shell access to the hypervisor, or a compromised storage administrator account.
Impact
Every virtual machine (VM) on the datastore loses its disk at once, including snapshots stored there.
Examples
ESXi shell rm/dd against /vmfs/volumes; public reporting on 2023 ESXi attacks described mass virtual-disk destruction.
Why this rank
One action destroys many hosts; hypervisors often have no endpoint agents, and backup catalogs on the same datastore die with it.
TH-07 Low Windows Linux macOS

Scrambling of removable or external drives - overwriting the partition table or first sectors of USB and backup media when they are briefly attached.

Preconditions
Local malware with write access to removable devices, or direct physical access.
Impact
The media is gone, and with it possibly the only offline copy of important data.
Examples
dd to /dev/sdb; raw writes to external drives; no major campaign is publicly attributed, which keeps the rank low.
Why this rank
Rare in public reporting and scoped to single devices, but it can destroy the exact backups needed to recover.

5.4 Logs and patterns

For each threat: the sources to collect, the fields that matter, what normal looks like, what suspicious looks like, and the detection logic that separates them.

TH-01 - Raw write to \\.\PhysicalDrive0 (Windows, Critical)

Log sources
Sysmon EID 9 RawAccessRead, EDR raw-write detections, Windows Security 4663 on device objects.
Key fields
Image, ProcessGuid, Device (for example \Device\HarddiskVolume2 or \Device\Harddisk0\DR0), User, UtcTime, parent process.
Normal
Backup agents, disk imaging tools, defragmenters, and antivirus scanners touching raw devices - usually from known paths and known service accounts.
Suspicious
Any process in Temp, AppData, or ProgramData opening the system disk; Office or script hosts opening any raw device at all.
Detection logic
Alert when Device matches a physical drive and Image is not on an allowlist of imaging/backup binaries. Treat writes (not reads) as the highest-priority alerts.

TH-02 - MFT or partition-table corruption (Windows, Critical)

Log sources
Sysmon EID 6 driver load, EID 1 process creation, Windows System log (Ntfs 55; disk 153 and 129), EID 7045 service installs.
Key fields
ImageLoaded, driver signature/path, command lines containing fsutil, mkfs-style arguments, NTFS corruption event volume.
Normal
Signed storage drivers from System32\drivers; occasional single Ntfs 55 events after power loss.
Suspicious
Drivers loading from Temp or user-writable paths (HermeticWiper pattern); bursts of NTFS corruption events across many hosts at once; fsutil or vssadmin delete shadows followed by reboots.
Detection logic
Two layers: pre-damage (driver load from writable path) and damage confirmation (Ntfs 55 and Kernel-Power 41 rate per host group).

TH-03 - dd/wipefs/GRUB removal (Linux, High)

Log sources
auditd (EXECVE, SYSCALL, PATH records), journald, EDR for Linux.
Key fields
a0..a3 arguments, exe, uid, name="/dev/sda" in PATH records, tty, session ID.
Normal
Provisioning systems and storage admins running mkfs or wipefs on data disks during build windows, from known hosts and accounts.
Suspicious
dd of=/dev/sd* or of=/dev/nvme*, wipefs -a on the boot disk, GRUB file deletions outside a package transaction, root shell from an unexpected service.
Detection logic
Alert on EXECVE where the output argument targets a whole-disk node, unless the account and host are on the provisioning allowlist.

TH-04 - macOS boot-volume erase (Medium)

Log sources
macOS unified logging (logd), MDM (Mobile Device Management) and endpoint logs, BSM (Basic Security Module) audit records of diskutil invocations.
Key fields
Process name (diskutil, apfs.util), arguments (eraseDisk, eraseVolume), calling TTY and user.
Normal
IT re-imaging during onboarding/offboarding, documented in change tickets.
Suspicious
Erase commands outside change windows, launched by agents or scripts without an interactive IT user.
Detection logic
Correlate diskutil erase* with change tickets; alert on any erase of the boot volume triggered by a background process.

TH-05 - Cloud disk destruction via API (Medium)

Log sources
AWS CloudTrail, Azure Activity Log, GCP Audit Logs - the control-plane record of destructive storage calls.
Key fields
eventName (DeleteVolume, DetachVolume, DeleteSnapshot, TerminateInstances), userIdentity.arn, sourceIPAddress, requestParameters.
Normal
Infrastructure-as-code pipelines and storage admins deleting volumes in sandbox accounts and change windows.
Suspicious
Destructive calls from new principals, unusual geolocations, or the root user; bursts of detach+delete across production within minutes.
Detection logic
Alert on destructive storage API calls where the principal is not a pipeline role, or where the volume is attached to a running production instance.

TH-06 - Virtual disk corruption on datastores (Hypervisor, High)

Log sources
ESXi shell log (/var/log/shell.log), vmkernel log, vCenter events, Windows file-server audit logs for VHD and VMDK paths.
Key fields
Shell command lines, datastore paths (/vmfs/volumes/), source of the admin session, vmkernel disk-error messages, process names (dd, rm, vim-cmd).
Normal
Storage migrations, snapshot backups, and template work inside approved change windows.
Suspicious
rm or dd aimed at datastore paths outside a change window; many .vmdk descriptors disappearing; waves of guest disk errors on VMs of one datastore; several VMs showing "operating system not found" at once.
Detection logic
Alert on destructive shell commands that mention datastore paths; confirm with a burst of VM disk-failure events on the same datastore within minutes.

TH-07 - Removable and external drive scrambling (Low)

Log sources
Sysmon EID 9 RawAccessRead, EDR device-control logs, auditd on Linux, USB attach events.
Key fields
Device and Image (Sysmon 9), device serial and VID/PID (device control), EXECVE arguments (a0-a3), User.
Normal
Imaging teams and documented backup-export jobs touching removable media during change windows.
Suspicious
Raw opens or dd/wipefs/format aimed at removable devices by non-IT users, service processes, or outside change windows; several devices wiped in a row.
Detection logic
Join "removable device attached" events with raw-open events from the same user session; alert outside the allowlist.

Event-shaped log examples

  • EventID 9 - Sysmon logs RawAccessRead whenever a process opens a raw device.
  • Image - the requesting process; Temp here is the red flag.
  • Device \Device\HarddiskVolume2 - a raw open of a system volume; sector 0 of that volume is the MBR. Whole-disk handles appear as \Device\Harddisk0\DR0, which userspace reaches as \\.\PhysicalDrive0.
  • User - the account behind the open; join it to identity data to tell admins apart from services.
  • ProcessGuid - join key to the Sysmon EID 1 record that shows who spawned updater.exe.
  • msg=audit(...:8821) - the shared event ID that ties the SYSCALL, EXECVE, PATH, and PROCTITLE records of the execution together.
  • EXECVE a2="of=/dev/sda" - the clearest clue: dd writing zeros over the whole first disk, 512 bytes at a time.
  • syscall=257 - openat on x86-64. Event B is the destructive open itself, and a2=201 decodes to O_WRONLY|O_TRUNC.
  • PATH name="/dev/sda" rdev=08:00 - confirms the target was block device 8:0, the raw disk node itself.
  • uid=0 with auid=1000 - root ran it, but a named login user was behind the session; check who that is.
  • key="disk-wipe-watch" - the local audit rule tag on the disk nodes; it makes the event easy to find later.
  • Kernel-Power 41 - an unexpected reboot; one is noise, 47 in nine minutes is a campaign.
  • disk 153 / storahci 129 - storage retries and device resets clustered around logical block address 0, the boot-sector area.
  • Ntfs 55 - the file system reporting damage moments before it disappears.
  • BugCheck 1001 with code 0x7B - INACCESSIBLE_BOOT_DEVICE: Windows lost its boot device, the classic end state of a structure wipe.
  • 0xc000000e and "Operating system not found" are boot-screen text, not event-log records; collect them from screenshots and say so in the incident notes.
  • Fleet rollup line - the detection that matters is the rate across hosts, not any single event.

5.5 Sigma rules and Splunk SPL

One complete Sigma rule and one matching Splunk SPL query for each of the six highest-priority threats from 5.3 (TH-01 to TH-06). Adapt paths, indexes, and allowlists to your environment before deploying; the rules are written to be edited, not pasted blind.

TH-01 - Raw physical-drive access (Windows, Critical)

Field assumptions: Sysmon events are ingested as XML with fields EventID, Device, Image, Computer, ProcessGuid auto-extracted; adjust the index and sourcetype to your deployment.

  • Sigma to SPL: the selection maps to the two base filters (EventID and Device wildcard); filter_admin_paths becomes the NOT IN clause on Image.
  • False positives: disk imaging, VM provisioning, backup jobs, and defragmenters performing legitimate raw writes.
  • Tuning: build an explicit allowlist of backup/imaging binaries with hashes, and alert on raw access from anything else; page on the system disk (Harddisk0).
  • Severity: Critical - this is the pre-damage signature of TH-01.

TH-02 - Suspicious driver load preceding MFT corruption (Windows, Critical)

Field assumptions: driver-load events arrive in the Sysmon XML sourcetype with ImageLoaded; System-log corruption events (Ntfs 55, disk 153, storahci 129) arrive in WinEventLog:System using classic EventCode field names; both hosts share the Computer field.

  • Sigma to SPL: the four ImageLoaded|contains values become OR-joined wildcards; the correlation with file-system damage approximates the two-layer detection logic from 5.4.
  • False positives: printer driver installers, vendor updaters, and legitimate fdisk-style work during gold-image builds.
  • Tuning: keep the standalone driver-load alert at High, but raise to Critical when Ntfs 55, disk 153, or disk 129 events follow on the same host within 24 hours.
  • Severity: Critical - driver abuse is the strongest pre-damage indicator of TH-02.

TH-03 - Whole-disk dd or wipefs on Linux (High)

Field assumptions: auditd EXECVE records are ingested to index=unix sourcetype=linux:audit with fields type, a0-a3, uid, and host extracted; the target eval approximates argument position differences between tools.

  • Sigma to SPL: each selection_* block becomes one arm of the OR search; 1 of selection_* is expressed by letting all three arms match in the same query.
  • False positives: legitimate fdisk/mkfs during provisioning, wipefs on USB sticks by storage teams.
  • Tuning: allowlist provisioning accounts and build hosts by uid plus hostname; alert immediately when the target is the boot disk (/dev/sda or /dev/nvme0n1).
  • Severity: High - matches the TH-03 rank; fewer endpoint hooks means higher false-negative risk, so coverage depends on auditd rules being deployed.

TH-04 - macOS boot-volume erase (Medium)

Field assumptions: macOS BSM audit records land in index=osx sourcetype=macos:audit with exec arguments mapped to a0-a2, user, and host; if you ingest unified logs instead, map diskutil process events to the same field names at parse time.

  • Sigma to SPL: the a0/a1|startswith pair becomes two positional filters joined by AND.
  • False positives: scheduled MDM wipes and IT reimaging jobs.
  • Tuning: join with your change-ticket data feed; suppress matches whose asset tag appears in an open change request.
  • Severity: Medium - mirrors TH-04: rare, but total when it happens.

TH-05 - Destructive cloud storage API calls (Medium)

Field assumptions: CloudTrail management events are ingested to index=cloud sourcetype=aws:cloudtrail with eventName, userIdentity.arn, and sourceIPAddress extracted; replace the automation-role filter with your real pipeline role ARNs.

  • Sigma to SPL: the eventName list maps to the IN clause; not filter_automation becomes the NOT assumed-role filter, and the threshold logic adds the burst heuristic.
  • False positives: infrastructure-as-code runs outside standard roles and admins cleaning up after migrations.
  • Tuning: maintain an explicit allowlist of pipeline role ARNs, add a guardrail policy that denies destructive calls outside change windows, and page on any production-account hit.
  • Severity: Medium per TH-05, raise to High once the environment holds stateless-rebuild-only workloads with no snapshots.

TH-06 - Destructive datastore commands on ESXi (Hypervisor, High)

Field assumptions: ESXi syslog is forwarded to index=esxi sourcetype=vmw:esxlog; adjust both to match your syslog add-on. The Sigma keyword lists become plain term searches against _raw, and source="*shell.log" keeps only the shell history.

  • Sigma to SPL: selection_path and selection_action are keyword lists, so each becomes a set of _raw term matches joined the same way (OR inside a list, AND between the two lists).
  • False positives: approved storage migrations and lab rebuilds; add change-window suppression per host.
  • Tuning: also alert on vim-cmd snapshot destruction plus dd in the same session, and on vmkernel bursts of disk-error messages for one datastore.
  • Severity: High per TH-06 - one command can remove every VM disk on a datastore.

Real-World Case Study

NotPetya, 27 June 2017 - the event that turned "disk structure wipe" from a technique row into a board-level risk. Facts below follow widely published reporting.

Sources

Facts in this case study come from public records: CISA alert TA17-181A, vendor analyses, and company statements. Parts marked "illustrative" describe how teams usually respond; they are not a record of one company's actions.

Context

According to public reporting, NotPetya entered through a trojanized update of M.E.Doc, a Ukrainian accounting software package that many companies were required to use for tax filing. The attack landed on the eve of Ukraine's Constitution Day holiday, when offices were thin and IT staffing low - a timing choice that slowed discovery. What looked at first like ordinary ransomware was something worse: a wiper disguised as ransomware. The payload overwrote the master boot record (MBR, the small boot program at the start of a disk) and scrambled the master file table (MFT, the index of every file on an NTFS volume). The key supposedly needed for decryption was destroyed along with the machine, so payment could never restore anything. Public estimates put the number of affected machines in the tens of thousands, across dozens of countries.

Timeline (from public reporting)

  1. Early June 2017Attackers compromise M.E.Doc's update infrastructure; according to later analyses, the backdoor sits quietly inside the update mechanism.
  2. 27 June 2017, morning UTCA malicious update is pushed to M.E.Doc customers (public analyses differ on the exact minute). Finance departments across Ukraine install it, because the software is mandatory for tax workflows.
  3. Hours 0-2Payload harvests credentials on patient-zero hosts and spreads using the EternalBlue and EternalRomance SMB exploits plus stolen administrator credentials - no user clicks required.
  4. Hours 2-3On each infected host, the destructive module is armed for the next restart; a scheduled task and the M.E.Doc process itself trigger mass reboots.
  5. 27 June, middayMachines across Ukraine and then worldwide restart into a fake chkdsk screen while the MFT is scrambled and the MBR is overwritten with a ransom note. Multinationals with Ukrainian offices (Maersk, Merck, FedEx TNT, WPP) are hit through exactly this bridgehead.
  6. Hours 3-12Companies disconnect networks to stop the spread. The SOC picture: restart storms, hosts booting into a note, and encrypted MFTs that no decryptor can fix.
  7. Weeks afterRecovery means rebuilding: Maersk publicly reported reinstalling about 45,000 PCs and 4,000 servers. One domain controller happened to be offline during the attack window, which preserved the domain and sped up recovery.
  8. August 2017 and laterEstimates settle: the US White House puts total damage above 10 billion USD; Maersk's own cost lands around 250-300 million USD. CISA (then US-CERT) publishes alert TA17-181A with detection guidance.

Detection, containment, and recovery

Detection point. In the best-instrumented networks, Sysmon-style raw-access telemetry and EDR alerts fired as the payload opened the raw disk; most organizations instead detected the boot-failure storm - hundreds of hosts restarting into the same screen within minutes. Many SOCs first treated it as a ransomware outbreak, which wasted time on the wrong response: there was nothing to decrypt.

Containment. The actions that worked were blunt: segregating the network into segments, powering off machines before they could reboot into the wiper, and disabling the compromised M.E.Doc update server so the delivery channel closed. Flat networks made the early hours devastating; segmentation was the single biggest factor in who survived.

Eradication and recovery. Because MFTs were destroyed, recovery meant clean rebuilds from golden images and data restored from backups that happened to be offline or otherwise unreachable by the worm. Maersk's rebuild of roughly 45,000 PCs and 4,000 servers became the reference story for fleet-scale recovery, and the accidental survival of one domain controller (offline during the attack window) shows how narrow the margin was.

Impact and communication

Public estimates: above 10 billion USD in total damage (US White House figure), Maersk alone around 250-300 million USD, with weeks of booking, shipping, and manufacturing disruption at Merck, FedEx TNT, WPP, Rosneft, and thousands of others. Communication mattered: affected firms that shared indicators quickly (and CISA's TA17-181A alert) helped others block the update server and patch SMB before their own wave arrived.

Tools observed (public reporting)

  • Delivery: the trojanized M.E.Doc updater; public analyses describe a backdoor planted in the update mechanism itself.
  • Spread: the EternalBlue and EternalRomance SMB exploits, plus stolen credentials used with admin-share execution (PsExec-style services).
  • Credential theft: memory-harvesting tools that dump passwords and tokens; vendor reports describe Mimikatz-class behavior.
  • Impact: the payload's own MBR writer and MFT-scrambling routine, shown behind a fake "chkdsk" screen at reboot.

Response team roles (illustrative)

Large destructive incidents run on clear roles, not on heroes. The split below is an illustrative playbook drawn from public post-incident accounts:

  • Incident commander - declares the major incident, decides on network isolation, and owns the timeline.
  • SOC lead - tracks the host list (wiped, armed, unknown) and keeps the fleet-rate view.
  • Network team - segments the network, blocks the spread path, and watches for new lateral movement.
  • Endpoint and IT teams - run the rebuild factory: golden images, drivers, patch levels, verification.
  • Backup and infrastructure owners - confirm offline copies are intact and manage the restore order for critical services.
  • Forensics and malware analysis - examine surviving hosts and samples to confirm the wipe and find the entry path.
  • Communications and legal - handle regulators, customers, and staff, including breach-notification clocks.

Lessons learned

  • Patch and harden SMB. Disable SMBv1; patch EternalBlue-class bugs fast; flat networks turn one patient zero into thousands of victims.
  • Trust software updates carefully. Pin, verify, and monitor update channels of even "mandatory" vendors - a supply chain is an access path.
  • Keep offline backups. Backups reachable through the same domain as production were lost; offline or immutable copies were the lifeline.
  • Segment the network. Segmentation was the difference between a department and an enterprise being wiped.
  • Destructive attacks are not ransomware. Decide in advance how you will tell them apart - a boot-screen note plus impossible decryptability is the tell.
  • Rehearse fleet rebuild. The organizations that recovered fastest had tested images, documented rebuild runbooks, and practiced responders.

Mitigation and Defense

A structure wipe cannot be "patched away" mid-attack - defense is about privilege control, fast telemetry, and recovery you have actually tested.

Enterprise controls by area

Policy

Maintain a destructive-incident playbook separate from the ransomware runbook. Put software update channels and their vendors under change control, and decide in advance who can declare a major incident and take networks offline.

Identity

Privileged Account Management: tiered admin models, dedicated jump hosts, and credential protection (Credential Guard, LSA protection). Wipers spread with stolen admin rights - fewer reusable credentials means a smaller blast radius.

Endpoint

Operating System Configuration plus EDR: tamper protection on, attack-surface-reduction rules blocking raw writes from Office/script hosts, and application allowlisting on server roles that never need storage tools.

Network

Network Segmentation and SMB hardening: disable SMBv1, patch EternalBlue-class flaws, block admin-share paths between workstation zones. Segmentation is what kept flat-network victims out of the news.

Cloud

Separate disk/snapshot management from instance roles, guardrail destructive APIs with deny-until-approved policies, and keep control-plane audit logs (CloudTrail, Azure Activity, GCP audit) in an account no workload credential can touch.

Logging and monitoring

Sysmon EID 9 (raw access) plus EID 1 and 6, shipped off-host in near-real-time. Monitor for raw-write analytics, boot-failure storms (Kernel-Power 41 rate), and driver loads from writable paths.

Backup

Data Backup that survives the attack: offline or immutable copies, at least one tier unreachable from the production domain, and tested bare-metal restore - a backup nobody has restored cannot be trusted.

Response

Incident Response Plan exercised with fleet-rebuild drills: time how long 100 machines take to reimage, and keep golden images outside the network they rebuild.

Home and small-office version

At home, three habits cover most of it: keep one backup on a drive that is unplugged after each sync, keep the operating system and router firmware updated, and never run downloads as administrator. If a machine boots into a strange screen, disconnect its network and power - then decide, do not panic-click.

Measure one thing this quarter: how long until a wiped host is fully restored, with logs intact, using only what your team actually has. Every mitigation above exists to shrink that number.

Common Mistakes and Best Practices

Twelve blue-team mistakes we see again and again with this technique - each with the symptom, the root cause, the fix, and the habit that prevents it.

01 Sysmon raw-access logging never enabled

Symptom
The SOC learns about a wipe from helpdesk tickets, never from telemetry.
Root cause
Sysmon installed with a default config; EID 9 not in the configuration.
Fix
Deploy a configuration that includes EID 9, 1, and 6; verify events arrive in the SIEM.
Prevention
Coverage report per host per event ID, reviewed monthly.

02 Logs stored only on the host that gets wiped

Symptom
Victim hosts have no forensic record of their own destruction.
Root cause
Local forwarding disabled or buffered; retention never validated.
Fix
Near-real-time shipping to the SIEM; retention measured in months, not days.
Prevention
Pipeline-health alerting when a host stops sending.

03 Boot-failure storm treated as patching gone wrong

Symptom
Hours lost triaging "update broke my PC" tickets while the wiper spreads.
Root cause
No fleet-rate view; every host's Kernel-Power 41 looked isolated.
Fix
Add the boot-failure storm detection from 5.5 and a same-screen-across-hosts rule of thumb.
Prevention
Runbook: N hosts failing to boot in M minutes = major incident.

04 Raw-write alert drowned by imaging noise

Symptom
The EID 9 alert has 4,000 hits a day; nobody reads it.
Root cause
Provisioning and imaging tools legitimately write raw disks; the rule had no allowlist.
Fix
Allowlist known imaging binaries by hash and path; alert on everything else.
Prevention
Change process: new imaging tools get added to the allowlist deliberately.

05 All-or-nothing tuning: alert silenced after first false positive

Symptom
The rule exists but was set to informational (or disabled) "to reduce noise".
Root cause
No severity ladder; one bad week killed the rule instead of narrowing it.
Fix
Split: High on system-disk access from untrusted paths, Medium elsewhere; suppress only specific hosts.
Prevention
Detection reviews require a documented tuning decision, never silent edits.

06 Watching only \\.\PhysicalDrive0

Symptom
Wipe of a secondary volume or a VM's disk caught only by the outage, not the alert.
Root cause
Rule matched one string; device names vary (\Device\HarddiskVolume2, DR0).
Fix
Match the device family (Harddisk, /dev/sd*, /dev/nvme*), then allowlist callers.
Prevention
Unit-test detections against captured real event samples.

07 Per-host thresholds with no fleet correlation

Symptom
Forty-seven low-severity alerts, no pages.
Root cause
Rules evaluated one host at a time; nobody counted the group.
Fix
Aggregate: distinct hosts with boot failure or raw-write events in a sliding window.
Prevention
Include "rate" detections in the standard template for Impact techniques.

08 Backups reachable from the production domain

Symptom
After a destructive event, backup servers are as dead as production.
Root cause
Same domain, same admins, credentials cached on workstations.
Fix
One offline or immutable tier, separate credentials, no interactive logon from workstations.
Prevention
Annual purple-team test: can a simulated admin from production reach backups?

09 No owner for the detection rules

Symptom
Rules break after a Sysmon upgrade and nobody notices for months.
Root cause
Detections with no named owner and no testing cadence.
Fix
Assign owners; run purple-team test events for each rule in 5.5 quarterly.
Prevention
Detection-as-code: changes reviewed like software, with CI tests.

10 Every ransom note assumed to be real ransomware

Symptom
Negotiation and decryption attempts wasted on a wiper with no key.
Root cause
Playbook starts from "ransomware" and never asks "is anything actually encrypted?"
Fix
Add a first triage question: does a sample file decrypt? If not, suspect a wipe.
Prevention
Separate destructive-incident playbook, as in section 7.

11 Golden images and restore tests not maintained

Symptom
Rebuilds fail because images are years old or missing drivers.
Root cause
No scheduled re-imaging of images; restore drills skipped under pressure.
Fix
Automated image pipeline; quarterly bare-metal restore test with timing recorded.
Prevention
Report restore-test age next to backup-coverage numbers in leadership dashboards.

12 Evidence pulled too late

Symptom
Responders image wiped disks and find nothing; timeline is guesswork.
Root cause
Volatile logs and memory not collected from surviving hosts before remediation.
Fix
First-hour step: capture memory and logs from patient-zero and surviving hosts.
Prevention
IR grab-bag with scripts ready; drill the capture step, not just the rebuild.

Habits that keep you ready

Daily

  • Review raw-disk access (EID 9) alerts, especially from Temp or AppData paths.
  • Compare boot-failure counts against the 7-day baseline.
  • Check the log pipeline: is every expected host actually sending?

Weekly

  • Review driver-load alerts and any new drivers in writable paths.
  • Spot-check Sysmon coverage by host and event ID; chase the gaps.
  • Review changes to software update channels and their vendor trusts.

Monthly

  • Run a restore test from the offline backup tier; record the time.
  • Review detection allowlists for sprawl and stale entries.
  • Tabletop one destructive-attack scenario with the on-call team.

Incident response checklist

  1. Declare a major incident; multiple hosts booting into the same screen is not a helpdesk queue.
  2. Isolate network segments and stop forced reboots before the wiper's next wave.
  3. Pull memory and volatile logs from patient zero and surviving hosts now, not later.
  4. Identify the trigger: chain Sysmon EID 1 + 9 to the scheduled task or update that armed the wipe.
  5. Check one file: does anything actually decrypt? If not, you are in a wipe scenario.
  6. Block and disable: wiper hash, abused driver, armed tasks, compromised update server.
  7. Rebuild from golden images and restore from offline backups; verify patches first.
  8. Post-incident: enable missing telemetry (EID 9), close the original access path, and book the next rebuild drill.
