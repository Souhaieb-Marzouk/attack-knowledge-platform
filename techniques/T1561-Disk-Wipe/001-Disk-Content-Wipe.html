T1561.001 Disk Content Wipe

Disk Content Wipe is when an attacker erases the content of files and data stored on a disk. The attacker overwrites (writes new bytes over the old data so it cannot be read back) file contents, databases, or whole shared folders. The disk structure may survive, but the data is destroyed.

Tactic: Impact Parent: T1561 Disk Wipe Platforms: Windows, macOS, Linux Effect: data destroyed even if disk structure survives Version: 2.0 · Reviewed 2026-10-22
ATT&CK ID

T1561.001 · Impact tactic · sub-technique of T1561 (Disk Wipe)

What is destroyed

File and data content: documents, databases, mail stores, virtual disks, and the data inside partitions

Common tools

sdelete, shred, dd, srm, plus custom wipers seen in campaigns such as Shamoon, WhisperGate, HermeticWiper, CaddyWiper

Main data sources

Process creation, file modification, command execution

Overview

What Disk Content Wipe is, how it differs from normal deletion, and why it matters to defenders.

Disk Content Wipe (MITRE ATT&CK T1561.001) is a technique in the Impact tactic. The attacker destroys the content of stored data. A simple delete often leaves the data on disk until the system reuses the space. A wipe is different: the attacker writes new bytes over the old data until the original information is gone.

Think of a file as text written on a whiteboard. Normal deletion is like erasing the table of contents that says where the text is. A content wipe is like scribbling over every word until the board is unreadable. Recovery tools that can sometimes undo a normal deletion usually cannot undo a serious wipe.

What attackers target

  • User files on file servers and shared drives (shares)
  • Database files, logs, and configuration data
  • Virtual machine disks and mail stores
  • Backup catalogs and shadow copies, so restores fail

What survives

  • The file system structure itself (folders, file names, sizes)
  • The operating system, in most content-only wipes
  • Removable or offline media the attacker cannot reach

This is the difference from the sibling sub-technique T1561.002 Disk Structure Wipe, which destroys the file system or partition table so the machine cannot boot. The full guide for the sibling sits next to this page: T1561.002 (v2.0). The parent overview is here: T1561 Disk Wipe (v2.0).

Note

ATT&CK lists the main data sources for this technique as process creation (which tool ran), file modification (what changed on disk), and command execution (what the operator typed or scripted). Every detection in section 5 hangs off those three sources.

Warning

Content wipes often arrive after data has been stolen. Modern groups copy the data first, then wipe, then demand money. If you only restore and move on, you may miss the theft. Always look backward in the logs for exfiltration (data leaving the network).

Animated Simulation

Watch a content-wipe attack unfold across a small company network, and read the SOC view at each step. The animation runs in your browser; nothing is sent anywhere.

The scenario: an attacker buys stolen VPN (Virtual Private Network) credentials, gets into the network, steals data, then wipes files on the file and database servers and empties the backup catalog. A fake ransom note appears, but no files were ever encrypted. Defenders catch the write storm and restore from immutable backups.

Written story (text alternative)

The same eight steps in plain text, for screen readers, printing, and anyone who prefers to read. Each step tells you what the attacker does and what defenders see.

  1. Entry. The attacker logs in with stolen VPN credentials from an outside address. Defenders see an anomalous VPN login with no multi-factor challenge and a new country or provider in the auth logs.
  2. Map. The attacker enumerates (lists) shared drives, database servers, and the backup server. Defenders see unusual SMB (Server Message Block, the Windows file-sharing protocol) share listing, LDAP (directory lookup) queries, and network scans from one account in a short window.
  3. Exfiltrate. The attacker copies gigabytes of data out before destroying anything. Defenders see a large upload to a new destination and compression jobs running at odd hours.
  4. Stage. The attacker drops a small overwrite tool and renames it to look harmless, such as a system utility name. Defenders see a file write followed by an execution with a name that does not match known hashes.
  5. Wipe. The tool loops over thousands of files and overwrites their content with junk bytes. A fake ransom note appears on screens, but there is no encryption key and no encryption events. Defenders see a write storm: extreme file-modification volume from one process, files rewritten at constant size.
  6. Blind. The attacker empties the backup catalog and deletes shadow copies so restores are hard. Defenders see backup job failures and catalog truncation events.
  7. Alarm. File-integrity and EDR analytics catch the mass overwrite. The fake ransom note raises a separate flag because no encryption activity exists anywhere. Defenders confirm a destructive attack, not a normal ransomware event.
  8. Recover. The team isolates hosts, restores from immutable (unchangeable) backups, rebuilds servers, rotates every credential, and reports the fake-ransom pattern. Defenders keep the wiped disks for forensics and hunt for the earlier exfiltration.

Red Team Perspective

Why attackers wipe content instead of just deleting it, how they do it, and what it takes. Written for defenders and authorized lab work, not as an attack guide.

When and why attackers wipe content

Wiping files is an Impact action: it destroys value instead of stealing it. Public reporting shows a few repeat reasons:

  • Destruction after theft. The group copies the data first, then wipes it to slow the response and hide what was taken. This is now standard in double-extortion style operations.
  • Sabotage. State-linked or politically motivated actors wipe to cause damage during a crisis window, not to earn money.
  • Fake ransom. The attacker drops a ransom note but never encrypts anything. Victims who pay find there is no key. This turns a destructive attack into an attempted fraud.
  • Evidence destruction. Wiping specific logs, tools, or documents removes proof of an earlier action.

How it is performed (conceptual shapes)

At a high level, the attacker makes three choices. The scope: user files, database files, shares, or backups. The method: a built-in or downloaded overwriter, or custom code. And often a disguise: rename the tool or run it from a trusted-looking path so alerts look normal. A common pattern is one small executable that walks a directory tree and rewrites every file with constant or random bytes. On databases, the attacker may truncate tables or overwrite the database files directly. On cloud storage, the same idea becomes bulk overwrites or deletes of objects.

The sub-technique name matters: only the content is overwritten. The operating system and the file names usually keep working, which makes the damage look strange: the file is there, the size looks right, but every byte inside is junk. Some campaigns pair content wipes with structure damage from the sibling sub-technique T1561.002, and some display fake ransom notes (T1491.001) on top.

Prerequisites

  • Write or delete permission on the target files, shares, or database objects.
  • Enough time to run the overwrite; large shares take minutes to hours.
  • Local administrator or service rights for wide coverage, shadow-copy deletion, or backup catalog tampering.
  • Some way to deliver the tool: remote execution (T1021), a malicious installer, or an insider account.

Documented wiper behaviors (factual background)

These descriptions come from public vendor reporting and are included so defenders know the shapes to look for. See section 6 for the full WhisperGate and HermeticWiper case study.

  • Shamoon (S0140): overwrote files on infected machines with junk data during the 2012 and 2017 waves against energy-sector organizations, then destroyed the master boot record.
  • WhisperGate (S0689): delivered through malicious installers; first stage overwrote file contents and showed a fake ransom note demanding payment while offering no real decryption.
  • HermeticWiper (S0697): abused a legitimately signed driver to write raw disk structures on hundreds of devices hours before the 2022 invasion of Ukraine.
  • CaddyWiper (S0691): wiped user data and partition information on domains it could reach through group policy.
Danger - lab only

Never run destructive tools against systems or data you do not own. Overwrites cannot be undone. If you want to see these behaviors safely, use throwaway virtual machines with no network links to anything real. Safe lab shapes: Sysinternals sdelete on a scratch folder you created for the exercise, shred -uvz on a lab test file, or dd writing to a disposable USB stick. These commands are named here so you can recognize them in your own logs, not as instructions to attack.

Best practice

Authorized purple teams can simulate the pattern of a wipe without destroying anything. Generate thousands of small file writes in a test share with a benign script. Or fire the same EDR telemetry by creating and truncating files at scale. Detections should fire on the pattern, not only on known tool names.

Common variations and attacker mistakes

  • Partial wipes. The tool stops early or skips locked files, so forensics recovers large fragments. Locked database files often survive because the database engine holds them open.
  • Wiping before exfiltration. If the data is destroyed before it is copied, the attacker loses the ransom leverage. Real campaigns steal first.
  • Tool sprawl. Running sdelete, shred, and a custom wiper on the same host multiplies telemetry and raises the alarm sooner.
  • Forgetting the clocks. Mass writes change timestamps in bulk, which stands out even on hosts without file auditing.
  • Leaving the ransom note blank. A note with no encryption behind it is itself a strong detection signal, because no genuine ransomware encryptor events appear next to it.

Blue Team Perspective

How a content wipe looks in real telemetry, which artifacts survive, and how a SOC triages it.

How defenders notice

Content wipes rarely start as a quiet event. Writing junk over thousands of files is loud. In practice, defenders report four signals:

  • File-integrity storms. File-integrity monitoring (FIM, software that hashes files and reports changes) fires thousands of "modified" events for one host in minutes.
  • EDR write-volume analytics. Endpoint detection tools flag "unusual high disk write volume" or "mass file modification" by a single process.
  • USN journal churn. The Windows USN journal (the change log of the NTFS file system) grows and recycles at abnormal speed.
  • People. Users report missing files, broken applications, or a strange note on the screen. Helpdesk volume is often the first sensor.

Where to look

  • Windows: Sysmon Event ID 1 (process create) and EID 11 (file create), Windows Security 4663 "An attempt was made to access an object" (most useful when Accesses contains WriteData or AddFile), 4656 (handle request), 4660 (object deleted), PowerShell 4104 (script block logging), the USN journal itself.
  • Linux: auditd rules on execve and write, journald entries, file hashing (AIDE or similar), shell history.
  • EDR: file-write counts per process, entropy checks, mass-rename analytics.
  • Backup platform: catalog changes, job failures, VSS/shadow-copy deletion events.
Danger

A ransom note with no encryption events changes the whole incident response strategy. This is a destructive actor, not an extortionist with a working product. Do not pay; there is nothing to buy back. Assume the data was already stolen (check T1567/T1041 patterns), restore from backups, and hunt the earlier stages instead.

Attack chain fit

Content wipe sits at the end of the chain, in the Impact tactic. When you see it, look backward for the entry and the theft. Check valid accounts (T1078) for the stolen VPN login. Check exfiltration over web service or another channel (T1567, T1041) for the data copy. Check inhibit recovery (T1490) for the backup tampering. Mapping the whole chain is what turns a restore job into a full investigation.

Six-step triage flow

5.2 Threat intelligence

Detection engineering works best when rules come from a threat model. Threat intelligence (information about attackers, their tools, and their campaigns) feeds that model in a loop:

  • Collect. MITRE ATT&CK (plus STIX/TAXII feeds, which are standard formats for sharing threat data), vendor blogs, OSINT (public open sources), commercial feeds, ISACs (sector sharing groups), and your own telemetry.
  • Analyze. Ask which actors could hit your sector and platforms, what tools they use, and what they need first (valid accounts, remote access).
  • Apply. Turn the behaviors into the ranked threats below, then into the rules in 5.4 and 5.5. Track ATT&CK updates each release, because sub-techniques and software entries move.

5.3 Threats ranking and categorization

Seven threats cover the realistic ways T1561.001 appears. Each threat has an ID that threads through sections 5.4 (logs) and 5.5 (rules), so every rule traces back to a modeled threat. TH-06 and TH-07 are new in v2.0.

TH-01 · Mass file-server and database wipe Critical Windows

A file-destroying wiper loops over file servers and databases, overwriting content with junk bytes. Preconditions: privileged access plus a staged tool. Impact: mass data loss across shares and database files. Rank justification: documented in major destructive campaigns (Shamoon, WhisperGate) and hits core business data at once.

TH-02 · Post-exfiltration destruction with fake ransom Critical Windows / Cloud

Data is stolen first, then wiped, with a ransom note demanding payment while no encryption exists. Preconditions: prior access, completed exfiltration, note deployment. Impact: double loss - theft plus destruction - and payment without any return. Rank justification: modern extortion standard operating procedure; the fake note is itself a detection opportunity.

TH-03 · Bulk shred or dd over SSH on Linux High Linux

An operator uses shred, dd, srm, or similar over SSH against database or file servers. Preconditions: shell access and sudo or write rights. Impact: destruction with fewer endpoint telemetry hooks than Windows. Rank justification: high impact and thinner telemetry make late discovery likely.

TH-04 · Targeted sabotage of key files Medium Windows

Destruction of specific configuration or database files to break one service, not everything. Preconditions: service account or admin access on one host. Impact: service outage without a full wipe; slower to notice because volume is low. Rank justification: narrower scope, but stealthy and common in insider or pre-positioning scenarios.

TH-05 · Accidental mass deletion by automation Low Cross-platform

A faulty script, backup job, or admin command deletes or overwrites many files without malice. Preconditions: none beyond a mistake. Impact: availability loss, no attacker. Rank justification: frequent in practice; the same volume-based rules catch it, and tuning here keeps TH-01 alerts trusted.

TH-06 · Database record wipe by an abused admin account High Windows / Linux

A stolen database administrator login runs mass DELETE, TRUNCATE, or DROP statements, so records vanish while the table files themselves look normal. Preconditions: valid database credentials with wide write rights. Impact: core business data is gone, although file-level backups may still hold the tables. Rank justification: high business impact through a different telemetry path (database audit logs, not file events), so file-only detection misses it.

TH-07 · Cron-based slow-burn wipe Medium Linux

A scheduled job overwrites a few files or one directory every night, so damage adds up over weeks instead of minutes. Preconditions: persistence on one Linux host plus write rights on data paths. Impact: slow corruption that looks like hardware or application faults. Rank justification: the low daily volume slips under volume thresholds, which makes it hard to catch, but the slow pace also limits instant damage.

TH-01 - Mass file-server and database wipe

Log sources
Sysmon EID 1 and 11, Windows Security 4663/4656, EDR file-write telemetry, USN journal exports
Key fields
Image (process path), CommandLine, User, TargetFilename, ObjectName, AccessMask, WriteMask, host
Normal
Write bursts during backup windows, antivirus scans (reads), scheduled exports; processes are known software with stable paths
Suspicious
One unknown process writing thousands of files per minute, files rewritten at identical sizes, writes at unusual hours from a logon session that started remotely
Detection logic
Group file-modification events by process per host per 5 minutes; alert when count exceeds a high threshold and the process is unsigned or newly seen

TH-02 - Post-exfiltration destruction with fake ransom

Log sources
Proxy or firewall flow logs, Sysmon EID 3 (network connect) and EID 11, EDR, email or file-drop alerts for the note
Key fields
DestinationIp, DestinationHostname, bytes out, Image, TargetFilename (note names), CommandLine
Normal
Steady uploads to known cloud storage; note files only from documented software
Suspicious
Large upload to a fresh destination followed by a write storm on the same host; a note file appearing with zero encryption or cipher events anywhere in the chain
Detection logic
Correlate per-host outbound bytes then file-write count; separately alert on note-file creation when no encryption activity exists on that host

TH-03 - Bulk shred or dd over SSH on Linux

Log sources
auditd (execve, open write), journald, SSH auth logs, sudo logs
Key fields

Normal

Suspicious
shred/dd/srm targeting data directories or wildcard paths, run from an interactive SSH session of a service account, or outside change windows

TH-04 - Targeted sabotage of key files

Log sources
Windows Security 4663 (Accesses: WriteData) and 4660, Sysmon EID 11 and EID 2 (timestamp change), application error logs from the affected service
Key fields
ObjectName, ProcessName, SubjectUserName, file paths in service folders, crash patterns
Normal
Configuration edits through change management; service accounts writing their own working files
Suspicious
Overwrites of web.config, application.ini, or database files by an interactive user or unrelated process; service crash immediately after
Detection logic
Alert on writes to protected config paths by processes outside an allowlist; join with service failures within 10 minutes

TH-05 - Accidental mass deletion by automation

Log sources
Same as TH-01 plus job schedulers (Task Scheduler, cron), CI/CD (build and deployment automation) logs, change tickets
Key fields
ParentImage, Image, CommandLine, User, scheduled task name, cron command
Normal
Cleanup jobs with scoped paths and known service accounts
Suspicious
Cleanup with an over-broad path, a bad variable, or a new parent process; the same volume pattern as TH-01 but from a known automation identity
Detection logic
Use the TH-01 volume rule, then split alerts by parent process and identity so automation noise routes to owners, not the SOC hotline

TH-06 - Database record wipe by an abused admin account

Log sources
Database audit logs (SQL Server Audit, MySQL or MariaDB audit plugin, PostgreSQL logging collector, Oracle unified audit), database gateway logs, Security 4663 on data files, EDR on the database host
Key fields
action_id, statement, server_principal_name, database_name, object_name, client_ip, rows_affected, ObjectName (data files)
Normal
Bulk deletes inside maintenance windows by known jobs; DELETE statements with narrow WHERE clauses; low row counts per statement
Suspicious
DELETE without a WHERE clause, TRUNCATE or DROP on business tables, one login touching many schemas in minutes, statements from an interactive client at unusual hours
Detection logic
Alert on TRUNCATE and DROP of business tables and on high-row DELETE outside change windows; enrich with the source IP and whether the login normally uses that database

TH-07 - Cron-based slow-burn wipe

Log sources
cron syslog lines and journald, auditd (execve plus openat with write flags), AIDE or FIM daily diffs, file hash history
Key fields
comm, exe, a0..a4, syscall, flags field (a2 for openat), PATH record name, uid, CRON command line, files changed per day
Normal
Cleanup jobs with fixed paths and stable daily counts; the daily diff shows only expected config changes
Suspicious
A cron job whose writes creep across new directories, small daily O_TRUNC writes on document or database paths, changes that never appear in the change record
Detection logic
Track file-change counts per cron job per day; alert on upward drift over 7-14 days and on O_TRUNC writes to data paths from jobs without a change ticket

Log example 1 - Sysmon process creation of a wipe tool (TH-01)

  • EventID 1 - Sysmon process creation; this is the strongest single clue for T1561.001 because it names the tool.
  • Image - the binary that ran. A file named after the real winlogon.exe but living in \Temp\ is masquerading (T1036).
  • CommandLine - sdelete64.exe -p 3 -q means three overwrite passes, quiet mode, against a whole share.
  • User - a service-style account running an interactive command is a red flag on its own.
  • Hashes - capture and block this hash; pivot on it across the estate.

Log example 2 - Linux auditd execution of shred (TH-03)

  • type=EXECVE - the auditd record of a program launch; a0..a4 are the argument list.
  • a3="1" a4="/data/exports/2025_close.csv" - one overwrite pass against a close-of-year export file; auditd lists each argument in its own field.
  • exe="/usr/bin/shred" - watch for copies of the binary under other names; path alone is not proof of identity.
  • ses=4711 and tty=pts2 - an interactive SSH session, not a scheduled job.
  • hostname=203.0.113.44 - the SSH source; join this with VPN logs to see whether the session follows a stolen-credential pattern.

Log example 3 - File-create burst from one process (TH-01 / TH-05)

  • EventID 11 - file create (or overwrite). Thousands from one Image in a minute is a write storm.
  • Target - every target sits under one share, and names are business files, not temp files.
  • constant-size - files rewritten to the same size with repeating bytes is the signature of an overwriter, not an editor.
  • USN journal delta - the NTFS change log churning at this speed means the disk is being rewritten wholesale.
  • zero cipher operations - if a note file exists but no encryption events, treat it as a fake-ransom wiper (TH-02).

Log example 4 - Security 4663 write to a protected config file (TH-04)

  • EventID 4663 - the message text is "An attempt was made to access an object"; it records an attempt, so read the Accesses field before judging impact.
  • Accesses - the rights the process tried to use. WriteData (or AddFile) is the write right; plain reads never show it.
  • AccessMask 0x2 - FILE_WRITE_DATA, which matches the Accesses entry.
  • ProcessName - a downloaded editor writing a web config is the sabotage shape; a service account would be normal here, an interactive user is not.
  • SubjectUserName - 4663 only fires where a SACL (System Access Control List, the per-object audit setting) covers the folder, so confirm the SACL is deployed before trusting the absence of events.

Log example 5 - database audit records for mass deletes (TH-06)

  • action_id - the SQL Server Audit two-letter action code: DL is DELETE and DR is DROP; TRUNCATE carries its own code and needs ALTER rights on the table.
  • rows_affected - millions of rows from one interactive login is the wipe signature; maintenance jobs rarely delete at all.
  • server_principal_name - a service-style account behind an interactive client (for example a management studio on a jump host) is a stolen-credential signal.
  • client_ip=192.0.2.88 - documentation IP; join it with VPN and jump-host logs to rebuild the way in.

Log example 6 - auditd openat with truncate flag from a cron job (TH-07)

  • syscall=openat - the modern Linux open call; auditd prints the write flags in the a2 field.
  • a2=O_WRONLY|O_TRUNC - write mode plus truncate: the file is opened and cut to zero length in one step, the exact shape of an overwrite.
  • type=PATH - the record that names the file; the SYSCALL line shows only a pointer, so always collect PATH records too.
  • comm="maint_cache.sh" - a maintenance name writing a cache path looks harmless. The slow-burn threat is the daily repetition across new paths, which volume rules miss but daily diffs and drift checks catch.

5.5 Sigma rules and Splunk SPL

Six Sigma rules (valid YAML) with six matching Splunk SPL queries cover the seven threats. TH-01 to TH-06 each get one rule. TH-07 runs the volume pattern with a daily window (see the deployment note at the end). Sigma is a standard rule format for SIEMs; SPL is Splunk's search language. Every rule carries the same metadata: author SOC Detection Engineering, date 2026-10-22, status stable. Adapt paths, indexes, and thresholds to your estate before deployment. Severity matches the threat rank from 5.3.

TH-01 - Sigma: mass file overwrite on Windows host

Field assumptions: Sysmon EID 11 is parsed into EventCode, Image, CommandLine, User, and TargetFilename. The threat_intel_process lookup flags approved bulk-write agents such as backup and sync tools. Adjust the 500 and 5000 thresholds to your share size.

  • Sigma to SPL mapping: the Sigma count-by-image condition becomes stats count ... by Image; the falsepositive list becomes the lookup exclusion.
  • False positives: backup agents, antivirus quarantine rewrites, legitimate sdelete used by IT on decommissioned machines.
  • Tuning: start with a high threshold, measure daily volumes per share, then lower. Add an exception for documented maintenance windows.
  • Severity: critical (matches TH-01).

TH-02 - Sigma: ransom note without encryption events

Field assumptions: note file names come from your naming watchlist. The subsearch looks back two hours on the same host. It matches process creation (Sysmon EventCode 1) whose command line mentions crypt, cipher, or encrypt. If your EDR supplies a cipher metric, replace the subsearch with it.

  • Sigma to SPL mapping: the endswith list becomes an IN (...) wildcard match; the "no encryption" idea lives in the SPL join because Sigma YAML cannot express absence; the join subsearch keys on process creation (EventCode 1), the only Sysmon event that reliably carries CommandLine.
  • False positives: red-team exercise notes, vendor demo files, users opening archived instructions.
  • Tuning: keep the note-name list short and sourced from your threat intel; drop any name that fires more than once per quarter.
  • Severity: critical (matches TH-02); route straight to IR.

TH-03 - Sigma: shred or dd against data paths on Linux

Field assumptions: auditd EXECVE fields are extracted as a0..aN, ses, uid, and exe. USER_AUTH carries addr and acct. The eval reads uid and euid straight from the EXECVE record, so rename them if your parser differs.

  • Sigma to SPL mapping: the four argument selectors (1 of data_path_*) become one match() regex over coalesced arguments; the tools and ... condition becomes the sequential eval where filter; root rights stand in for the sudo check.
  • False positives: documented space-zeroing jobs, disk provisioning scripts run by storage teams.
  • Tuning: keep an allowlist of host plus command plus window triplets; alert only on triplets outside it.
  • Severity: high (matches TH-03).

TH-04 - Sigma: overwrite of protected configuration files

Field assumptions: Sysmon EID 11 is parsed into EventCode, TargetFilename, Image, and User; keep the real writer allowlist in a lookup and swap the inline NOT list for it. On hosts without Sysmon, run the same logic on Windows Security 4663 with Accesses containing WriteData (or AddFile), using ObjectName instead of TargetFilename (see log example 4).

  • Sigma to SPL mapping: the endswith list becomes the wildcard TargetFilename match; the and not filter_known_writers condition becomes the NOT filter; the 4663 alternative maps ObjectName to TargetFilename and adds Accesses="*WriteData*".
  • False positives: config management agents, admins during change windows, installers.
  • Tuning: build the allowlist from real change tickets; alert only outside windows; join with service failures to raise priority.
  • Severity: medium (matches TH-04).

TH-05 - Sigma: mass write burst from automation identity

Field assumptions: Sysmon EID 11 includes ParentImage; service-account naming follows your convention (svc, backup, cleanup); adjust the automation identity regex to your estate.

  • Sigma to SPL mapping: the regex modifier (|re) becomes match(); the count condition mirrors TH-01 with a lower threshold and an identity split.
  • False positives: by design this rule fires mostly on benign automation; its job is to route noise away from the critical TH-01 alert.
  • Tuning: suppress per scheduled-task name once owners confirm the job; revisit monthly because cleanup jobs change quietly.
  • Severity: low (matches TH-05).

TH-06 - Sigma: write access to database data files

Field assumptions: Windows Security 4663 is parsed into EventCode, ObjectName, ProcessName, SubjectUserName, Accesses, and AccessMask. The event fires only where SACL audit entries cover the database data directories. Accesses strings look like WriteData (or AddFile). Keep the real database engine list in a lookup and swap the inline NOT list for it.

  • Sigma to SPL mapping: the endswith list becomes wildcard ObjectName matches; the contains modifier becomes Accesses="*WriteData*"; the and not filter_db_processes condition becomes the NOT filter.
  • False positives: database upgrades and file moves run by DBAs; pair the alert with change tickets.
  • Tuning: add your real engine binaries and any documented file-copy jobs to the lookup; watch the AccessMask so read-only access never fires.
  • Severity: high (matches TH-06).
Note

Order of deployment matters. Ship the TH-01 volume rule and the TH-03 Linux rule first: they are the broadest nets. The TH-02 note rule is small and cheap. TH-04, TH-05, and TH-06 need tuning data, so run them in monitoring mode for two weeks before alerting. For TH-07, run the TH-05 pattern with a one-day bin and a much lower threshold: slow burns fail a daily-drift check, not a volume check.

Real-World Case Study

WhisperGate and HermeticWiper against Ukrainian organizations, January to February 2022. Facts here follow widely published vendor reporting; anything not public is labeled as illustrative.

Context

In January 2022, weeks before the invasion of Ukraine, destructive attacks began hitting Ukrainian government, technology, and nonprofit organizations. According to public reporting by Microsoft, ESET, and other vendors, two wiper families ran in sequence: WhisperGate in mid-January and HermeticWiper on 23 February. These were not ransomware events that went wrong. There was nothing to buy back. The goal was damage, timed to a military crisis.

WhisperGate arrived, per public reporting, through maliciously crafted installers. ATT&CK maps that delivery to T1195 (Supply Chain Compromise). Its first stage overwrote the content of files with junk bytes (T1561.001) and showed a fake ransom note. The note demanded about $10,000 but offered no working decryption. Later stages damaged the master boot record on some machines, which moves into structure destruction (T1561.002). Microsoft tracked the cluster under the label DEV-0586. On 23 February, hours before the invasion began, HermeticWiper appeared. Public vendor reporting describes how it abused a legitimately signed driver to write to raw disks. It corrupted partition and file-system structures, including NTFS metadata, on hundreds of devices in Ukraine. Reporting also notes victims in Latvia and Lithuania.

Note

Public record versus illustrative: the timeline entries, tool behaviors, and ATT&CK mappings on this page follow published vendor and government reporting, including Microsoft and ESET blogs and CISA alert AA22-057A. The response roles, detection specifics, and recovery details are illustrative composites for teaching, because no two victims published the same playbook. Public reporting has linked parts of this activity to Russian state actors; those assessments are not settled fact, so this page keeps the actors unnamed.

Timeline

  1. 13 January 2022 First WhisperGate samples reported hitting Ukrainian organizations through trojanized (harmful but disguised) installers.
  2. 13-14 January 2022 Files on victim machines are overwritten in place; a fake ransom note appears on screens demanding payment with no real decryption behind it.
  3. 14-15 January 2022 Second-stage components damage the master boot record on some systems; many machines stop booting.
  4. Mid-January to mid-February 2022 Vendors analyze samples; Microsoft reports the cluster as DEV-0586; defenders share indicators across ISACs.
  5. 23 February 2022, early hours HermeticWiper activates on hundreds of devices in Ukraine; reporting later notes victims in Latvia and Lithuania too.
  6. 23 February 2022 The wiper abuses a legitimately signed driver to write raw disks, corrupting partitions and file-system structures.
  7. 23-24 February 2022 Russia invades Ukraine; the destructive attacks are widely read as pre-invasion sabotage rather than extortion.
  8. Following weeks Victims restore where backups existed; several organizations reportedly had no usable backups for targeted hosts, so recovery meant rebuilding.

Detection point

The clearest signals were volume and mismatch. Analytics shaped like the TH-01 rule in section 5 fire during the overwrite window itself, so a tuned SOC would have seen the write storm within minutes of the first bursts on 13-14 January. The fake ransom note raises a second flag because no genuine encryption events exist next to it. Many victims first discovered the attack the human way: users and admins saw the note on screens. Signed-driver abuse shows up in driver-load events and raw-disk writes from user-level processes, the HermeticWiper pattern on 23 February. The lesson for engineering: volume rules plus note-without-encryption rules plus driver-load monitoring cover the whole chain, and each covers a gap the others miss.

Response and lessons

  • Containment: isolate affected hosts from networks, block known file hashes and the abused driver, and freeze domain accounts seen running the tools.
  • Eradication: rebuild systems from clean media; wiping means no trust remains in the installed software.
  • Recovery: restore data from backups where they existed and were reachable; according to public reporting, some organizations lacked backups for targeted hosts, which stretched outages.
  • Impact: destroyed data and systems during the most sensitive week of the crisis, which is exactly the point of pre-invasion sabotage.
  • Communication: rapid sharing of indicators between vendors, government CERTs, and ISACs helped other organizations block the tools before impact.

Response team roles (illustrative playbook)

The public reporting does not name each victim's responders, so this role split is an illustrative composite that matches how destructive incidents are usually run.

  • Incident commander: owns the timeline, declares the destructive incident, and approves the restore order.
  • SOC analysts: scope the write storm, pull the exfiltration timeline, and watch for re-entry.
  • Forensics: keeps wiped disks and memory images, maps the tool chain, and preserves evidence.
  • Backup and infrastructure: isolates backup systems, verifies immutable copies, and runs restores in priority order.
  • Identity team: rotates credentials, resets service accounts, and tightens MFA on remote access.
  • Leadership, legal, and communications: handle regulator clocks, law-enforcement contact, and public statements.
Best practice

Lessons learned: keep immutable, offsite backups. Treat any fake-ransom note as a destructive attack, not extortion, and refuse the payment path. Alert on signed-driver abuse and raw-disk writes. Build the mass-overwrite analytics from section 5 before you need them.

Mitigation and Defense

You cannot stop every wipe attempt, but you can make it hard to reach the data, slow to spread, and quick to recover.

Enterprise controls by layer

Policy

  • Classify data so you know what sits on each share and database.
  • Write a destructive-incident playbook: what to isolate first, who decides on restoration order, who talks to leadership.
  • Define a restore priority list before an incident (revenue systems first).

Identity

  • Least privilege on shares and databases: users and service accounts get write access only where needed (Privileged Account Management).
  • MFA on remote access so stolen VPN credentials alone do not open the door.
  • Separate admin accounts from daily work accounts (Password Policies plus tiered admin model).

Endpoint

  • EDR with behavioral wipe detection and on-write analytics.
  • Application control to stop unknown executables from running on servers (Execution Prevention).
  • Restrict write and delete rights on shares to what each role truly needs (Restrict File and Directory Permissions).

Network and cloud

  • Segment management networks from user networks; restrict SMB (file sharing protocol) to paths that need it.
  • Object storage with versioning or WORM (write once, read many) keeps a pre-attack copy of every file.
  • Snapshot isolation: backups and snapshots live in an account or zone the main credentials cannot touch.

Logging and monitoring

  • Centralize file auditing, USN journal exports, and Linux auditd logs offsite, away from the hosts an attacker would wipe first.
  • Baseline write volume per share; alert on deviations (section 5 rules).
  • Watch backup health daily; a silent backup failure is an open door for T1490.

Backup and response

  • 3-2-1 rule: three copies, two media types, one offline or immutable (Data Backup).
  • Test restores quarterly; an untested backup is a hope, not a control.
  • Rehearse the destructive-incident playbook yearly with the same urgency as ransomware drills.

Home and small-office notes

Small setups need the same ideas, smaller. Turn on backup software with version history and keep one copy offline or on a cloud tier with file versioning. Use a standard user account for daily work and enable MFA on email and remote access. Keep an eye on disk activity; anything writing constantly when nobody is working is worth checking. One tested external drive, disconnected after each backup, defeats most content-wipe scenarios at home.

Measure the program, not just the controls

Track four numbers and review them monthly. Detection time: minutes from a simulated mass-overwrite test to an alert. Restore time: hours from a decision to restore to tier-1 service back. Coverage: percentage of file servers with file auditing and forwarding verified. Tuning debt: number of detection rules with no owner or no review date in the last quarter. If all four improve every quarter, your wipe resilience is real, not theoretical.

Common Mistakes and Best Practices

Twelve mistakes blue teams actually make with content-wipe detection, each with a fix and a prevention habit.

1. Assuming file auditing is on by default

Symptom: no 4663 events after an incident. Root cause: Windows object auditing is disabled until someone enables it. Fix: deploy audit policy and Sysmon through group policy now. Prevention: audit-log configuration drift monthly.

2. Treating backup agents as attacker noise

Symptom: the volume rule fires nightly at 02:00 and gets muted. Root cause: no allowlist for known bulk writers. Fix: add a lookup of approved agents and split their alerts to the backup team. Prevention: review the lookup quarterly.

3. Building wipe detection only on tool names

Symptom: rules for sdelete and shred only; a custom wiper with a new name goes unnoticed. Root cause: name-based thinking. Fix: add the volume and constant-size analytics from 5.4. Prevention: purple-team a benign write-storm exercise twice a year.

4. Ignoring the ransom note as a signal

Symptom: the note is discovered by users, not the SIEM. Root cause: no watchlist for note file names. Fix: ship the TH-02 note rule with an intel-fed name list. Prevention: add new note names from every public campaign within a week.

5. Alert fatigue from untuned thresholds

Symptom: the analyst mutes the channel after a week of noise. Root cause: thresholds guessed, never measured. Fix: baseline per share for two weeks in monitoring mode, then set thresholds at the 99th percentile. Prevention: revisit thresholds after every architecture change.

6. Keeping logs on the host that gets wiped

Symptom: the gap in logs starts exactly when the wipe starts. Root cause: local-only logging. Fix: forward Sysmon, Security, USN, and auditd streams offsite immediately. Prevention: verify forwarding agents daily.

7. No ownership of detection rules

Symptom: nobody knows why a rule fires or who tunes it. Root cause: rules deployed without owners. Fix: give each rule an owner and a review date in the repo. Prevention: quarterly detection review meeting.

8. Restoring without hunting

Symptom: systems come back, then the same actor returns. Root cause: treating the wipe as the whole incident. Fix: mandatory backward hunt for exfiltration and credential use before closing the case. Prevention: add the hunt to the destructive-incident checklist.

9. Weak testing with only benign loads

Symptom: rules pass QA but miss the real pattern. Root cause: tests never generate mass writes. Fix: run a controlled burst test in a sandbox share. Prevention: include a burst test in the standard detection test plan.

10. Forgetting Linux and cloud storage

Symptom: great Windows coverage, none elsewhere. Root cause: telemetry gaps. Fix: deploy the auditd execve rule and cloud object-storage change alerts. Prevention: keep a coverage matrix by platform and review it quarterly.

11. Treating fake-ransom notes like real ransomware

Symptom: time wasted negotiating or waiting for a decryptor that does not exist. Root cause: not checking for encryption events. Fix: the first triage question becomes: is there any cipher activity at all? Prevention: add the check to the triage table in section 4.

12. Backups reachable with the same credentials

Symptom: backups and live data die together. Root cause: one credential space for everything. Fix: separate backup accounts, immutable retention, offline copy. Prevention: access review that specifically tries to delete a backup with production credentials.

Habits that keep coverage honest

Daily

  • Check backup job health and immutability status.
  • Review any write-volume anomaly, even low-score ones.
  • Confirm log forwarding agents are alive on servers.

Weekly

  • Walk the TH-01 to TH-07 rules for new false positives.
  • Review file-audit policy and USN capture on new servers.
  • Read ATT&CK and vendor feeds for new wiper reporting.

Monthly

  • Run one restore test and record the time it took.
  • Tune thresholds with fresh volume baselines.
  • Review least-privilege changes on shares and databases.

Incident response checklist

  1. Confirm the pattern: many files, constant size, one process, short window.
  2. Check for encryption activity; a note without ciphers is a destructive wipe.
  3. Isolate affected hosts; protect remaining backups before touching anything else.
  4. Capture the tool: process path, hash, command line, parent, user.
  5. Hunt backward 7-30 days for exfiltration and stolen-credential logons.
  6. Restore in priority order from immutable copies; rebuild wiped hosts from clean media.
  7. Rotate all credentials that could have been touched, including VPN and service accounts.
  8. Report: regulator clocks (GDPR 72 hours), law enforcement, and sector ISAC.
