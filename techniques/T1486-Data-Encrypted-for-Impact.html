T1486 Data Encrypted for Impact

This is the technique behind ransomware. An intruder scrambles files, databases, and virtual machine stores with encryption keys that only they hold. Access is gone until a ransom is paid. Encryption is usually the last and loudest step of an attack that has been running quietly for weeks.

Adversaries encrypt data on purpose — documents, drives, VM stores, whole file systems — to deny access and demand payment.
Main risk
Operations stop. Recovery speed depends almost fully on backups that survive the attack.

Overview

Plain words first: what this technique is, where it sits in an attack, and what this page will teach you. No prior detection engineering experience is needed.

What this technique is

Data Encrypted for Impact means an adversary locks your data on purpose. They use encryption — math that scrambles data so it is unreadable without a key — and they keep the key. After the encryption finishes, they leave a ransom note that demands payment, usually in cryptocurrency, in exchange for the key or for not leaking stolen data.

ATT&CK describes this as an Impact technique with impact type Availability. In plain words: the goal is to take away your ability to use your own systems. The encryption can target single documents, whole drives, virtual machine files, database stores, or complete file systems. Real groups use this technique with their own tools and file extensions: Akira and Black Basta use ChaCha20, Babuk uses ChaCha8 with ECDH key exchange, and Bad Rabbit uses AES-128-CBC with RSA-2048 key protection.

Where it sits in the attack chain

ATT&CK organizes attacks into tactics — the attacker's goals, in order. A typical ransomware attack walks through many of them:

  1. Initial Access — the way in, often a phishing email or an exposed remote-access portal without MFA (multi-factor authentication — a second proof of identity beyond the password).
  2. Execution, Persistence, Privilege Escalation, Defense Evasion — run tools, keep access, gain more power, stay hidden.
  3. Credential Access, Discovery, Lateral Movement — steal passwords, map the network, spread to servers.
  4. Collection and Exfiltration — copy valuable data out, often several terabytes, to enable double extortion (pay to decrypt and pay to keep data private).
  5. Impact — this is where T1486 lives: delete shadow copies (T1490), stop security and backup services (T1489), then encrypt everything at once.

The motive behind the technique is often T1657 Financial Theft. Neighboring Impact techniques include T1490 Inhibit System Recovery, T1489 Service Stop, T1485 Data Destruction, and T1499 Endpoint Denial of Service. A wiper that destroys data without asking for money is usually T1485 or T1495, not T1486 — the ransom demand is what makes it T1486.

Quick answers to beginner questions

Is ransomware a virus?

Not exactly. A virus copies itself; ransomware is usually deployed by a human operator who already has valid credentials. That is why the days before encryption look like normal admin work.

If we get hit, is all data gone forever?

Only if every copy is encrypted. One immutable or offline copy changes the whole outcome. Attackers know this — which is why backups are their first target (see TH-05).

Can antivirus alone stop it?

Antivirus blocks known files, but ransomware kits change daily. Behavior-based detection (EDR, canary files, rate rules) catches what signatures miss.

Why does this page rank six threats?

Detection work needs a priority order. Ranking forces you to defend the most likely, most damaging paths first instead of writing rules at random.

Words you will meet on this page

Ransomware
Software that encrypts a victim's files and demands payment for the key.
Encryption / decrypt
Scrambling data with a key so it is unreadable; decrypt means making it readable again with the right key.
Entropy
A measure of randomness in data, from 0 to 8 bits per byte. Encrypted files have entropy near 8; normal documents sit near 4 to 6. A sudden jump is a strong signal.
Canary file
A fake file with a tempting name (for example Q1-budget.xlsx) placed so that ransomware touches it early. Nobody opens it legitimately, so any access is an alarm.
EDR
Endpoint Detection and Response — software on computers that records behavior and can block or isolate a host.
SIEM
Security Information and Event Management — the central system (for example Splunk) that collects logs and runs correlation rules.
Sysmon
A free Windows add-on that records detailed events such as process starts (EID 1), file creates (EID 11), and network connections (EID 3). "EID" means Event ID.
ESXi
VMware's hypervisor — the system that runs many virtual machines (VMs) on one physical server. Its storage containers are called datastores, found under /vmfs/volumes/.
SMB share
A shared folder over the network on Windows (or a NAS). Access to it is logged as Windows Event 5145.
NAS
Network Attached Storage — a storage box that serves files to the network, often running Linux inside.
Dwell time
The time an attacker spends inside your network before being detected. Ransomware dwell time is often measured in days or weeks.
Sigma
An open rule format for describing detections in YAML so they can run in many SIEM tools.
SPL
Search Processing Language — the query language of Splunk.
Immutable backup
A backup copy that cannot be changed or deleted for a set time, even by administrators. Ransomware cannot encrypt it.

The same story in words

This written version matches the eight steps above one to one. It is the text alternative to the animation, and it names the exact evidence each step produces — the same evidence Section 5 turns into detections.

  1. Phishing email arrives. A message with a fake invoice attachment lands in one user's mailbox. The user opens the attachment and a hidden loader program starts. Evidence: Sysmon Event ID 1 shows a new process starting from the Downloads folder, and Event ID 11 shows the attachment being written there.
  2. Loader calls home. The loader connects to the attacker's command-and-control (C2) server over HTTPS and downloads the real ransomware toolkit. Evidence: Sysmon Event ID 3 records a network connection to a brand-new external address, and proxy logs show the first request to an unknown domain.
  3. Recon and backup sabotage. The attacker runs discovery commands: they list SMB shares with net share, scan the file server, and stop backup services so restores will fail later. Evidence: service events 7045 and 7036, new service installs, and backup console events showing jobs disabled.
  4. Staging to the file server. The attacker copies the encryptor to FS-01 over SMB or WMI using stolen admin credentials. Evidence: network share events 5140/5145 with admin-share writes, and a process created by wmic on the server (Event 4688, Sysmon 1).
  5. Encryption detonates. The ransomware runs on the workstation and the file server. It rewrites thousands of files and gives them new extensions. The entropy meter on the dashboard climbs sharply. Evidence: a flood of Sysmon Event ID 11 file creates, mass renames, and a Defender behavior block (Event 1121).
  6. Canary file trips the alarm. The ransomware touches a planted canary file. The EDR fires instantly and the SIEM raises a critical correlation alert. The SOC now knows encryption is live. Evidence: one single write to \Canary\ from an unknown process — this is the detection you built in Section 5.5.
  7. Ransom note and backup hit. A file named HOW_TO_RECOVER.txt appears in folders, the desktop wallpaper changes, and the attacker encrypts the backup catalog on BK-01 so normal restores fail. Evidence: note filenames in Sysmon 11, wallpaper registry changes in Event 13, and backup catalog delete events.
  8. Contain and restore. The SOC isolates WS-4417 and FS-01 at the EDR and switch level, blocks the C2 addresses, and restores data from the immutable backup copy. The company recovers without paying. Evidence: EDR isolation actions, firewall blocks, and a verified restore job from BK-01.

Red team perspective

You cannot detect what you do not understand. This section explains, at a conceptual level, why attackers encrypt data, what they need before they can do it, and where they slip up. Every command example is lab-only.

Why attackers choose encryption for impact

Encryption is the most reliable lever an intruder has. A stolen password can be changed, a deleted database can sometimes be restored, but data that is encrypted with a key you do not hold is simply gone. One intrusion gives the attacker three ways to earn money. First, the decryption fee. Second, double extortion — payment to keep stolen data private. Third, in repeated cases, a second extortion attempt by another group. Some attackers also use encryption as pure destruction, hiding a wiper behind a fake ransom note, as Bad Rabbit did with its modified bootloader.

What an attacker needs first

Access and credentials

A way in (phishing attachment, exposed VPN or Citrix portal, a bought password) plus an account with enough rights to reach servers. Mass encryption across shares usually needs domain or file-server admin rights.

Reconnaissance results

A map of what is worth encrypting: SMB shares, ESXi hosts, backup servers, databases. Attackers enumerate shares with built-in commands before choosing targets.

Backup control

Before detonation, most groups disable or encrypt backup software and delete shadow copies (that is T1490). Without this step, their ransom loses its power.

The encryptor itself

A compiled tool, often bought as Ransomware-as-a-Service (RaaS — a paid kit run by the ransomware group), with a public key built in and a per-victim private key kept server-side.

How the attack usually unfolds

  1. Staging. The encryptor and its configuration reach the target host over SMB, WMI, or an RMM (Remote Monitoring and Management) tool.
  2. Preparation. The attacker stops services, deletes shadow copies, and kills backup jobs so nothing interrupts encryption.
  3. Key handling. Most families generate a random key per file or per machine, encrypt that key with an embedded public key, and store only the wrapped key in the encrypted file or the ransom note.
  4. Encryption. Files are read, encrypted (ChaCha20, AES, or similar), renamed with a new extension such as .akira, .lockbit, .avos, or .lock, and a note is dropped in each folder.
  5. Notice. Wallpaper changes, notes appear, and the victim is pointed to a leak site or chat.

Build a mini ransomware lab (defensive, step by step)

You do not need ransomware to study ransomware. A small lab with benign files and real logging teaches the same signals. Assemble it once and reuse it for every rule on this page:

  • One Windows 11 VM with Sysmon installed and the Defender operational log enabled (the victim).
  • One Windows Server VM with three SMB shares, share auditing (5145) switched on (the file server).
  • One nested ESXi host with shell.log, auth.log, and vmkernel.log shipped off-box (the hypervisor).
  • One backup server or container with an audit trail you can read (the backup).
  • One SIEM or even a single Splunk instance with the indexes from Section 5.5 (the SOC).
  • Planted canary files on the victim and the shares, plus a folder of dummy documents for rate tests.

With that in place, the exercises above, the rule-testing procedure in Section 5.5, and your own restores make a complete practice loop — no attack tooling required.

Run it twice and the point lands: the encrypted copy sits near the theoretical maximum of 8 bits per byte while ordinary content sits well below. That single number is what the meter in the simulation shows and what entropy-based detections look for.

Common variations

Full encryption

Every matching file is encrypted. Slow on huge volumes, so modern families avoid it. Classic Bad Rabbit style.

Partial, fast encryption

Only the first megabytes of each file are encrypted — enough to break the file, fast enough for terabytes. Common in Akira and Black Basta.

Rename plus note

Files gain an extension (for example Apostle renames to a random GUID plus .lock; AvosLocker appends .avos / .avos2) and every folder gets a note file.

ESXi and NAS targeting

Linux binaries compiled for VMware ESXi encrypt /vmfs/volumes/ so every VM on the host breaks at once (Akira_v2, Babuk ESXi builds).

Wipers disguised as ransomware

Destruction tools that show a fake ransom demand. If nothing can ever decrypt, it is data destruction (T1485) or firmware corruption (T1495) wearing a T1486 costume.

Cloud and RMM deployment

After stealing cloud or RMM console access, the attacker pushes the encryptor to many hosted servers at once (see TH-06).

Attacker economics in one minute

Ransomware is a business with payroll, affiliates, and customer service. A typical operation splits roles: one team buys or steals access, another runs the encryptor, another negotiates with victims. The encryptor itself is often rented as a kit, which is why families share behaviors (notes, extensions, service stops) and why those shared behaviors are stable detection signals. Understanding the economics also explains the rhythm of an intrusion: attackers maximize what they can demand, so they linger, steal, and sabotage backups before they encrypt. Attackers use extra days inside the network to find more worth stealing.

Mistakes attackers make — and how they help you

  • They trip canary files early. One planted file turns a silent intrusion into an instant alert.
  • They trigger Defender behavior blocks before they disable protection, leaving Event 1121 as a free alarm.
  • They create enormous file-write noise; a 1-minute write-rate rule separates them from any normal process.
  • They run interactive shells on ESXi, leaving python and file paths in shell.log that no normal admin produces.
  • They encrypt before exfiltration finishes, which means backups of stolen data they still need.
  • They reuse notes, extensions, and mutex names across victims, which is why extension and note watchlists work.

Blue team / SOC perspective

How defenders experience T1486: the artifacts it leaves, the places to look, and a first-hour triage flow you can practice. The hard truth comes first.

Warning — most teams learn about T1486 from the detonation

Without canary files, write-rate rules, and backup monitoring, the first signal is usually a user shouting that files will not open. By then encryption has run for minutes or hours. Every control in this section exists to move your first signal earlier in the chain — ideally to recon or staging, at worst to the first seconds of encryption.

Artifacts T1486 leaves behind

On Windows endpoints

Floods of Sysmon EID 11 file creates and renames, files with new extensions, note files such as HOW_TO_DECRYPT.txt, wallpaper and Run-key changes (EID 12/13), Defender blocks (1121/1116), and vssadmin or bcdedit commands if T1490 preceded it.

On file servers

Thousands of Event 4663 handle writes and Event 5145 share accesses from one client in minutes; the USN journal (the NTFS change log) grows at a rate no backup or sync job matches; new note files appear at share roots.

On Linux and NAS

High-rate rename syscalls from one process, CPU and disk saturation, note files at the top of shares, and — on NAS boxes — encrypted file trees with new extensions.

On ESXi

Python or BusyBox activity in shell.log pointing at /vmfs/volumes/, VM files changing while VMs power off, vmkernel write bursts, and new SSH sessions in auth.log.

On backup systems

Jobs disabled, catalogs deleted, repositories renamed or encrypted, and service accounts used from odd IPs (pairs with T1490).

In your SIEM

Correlated burst alerts, EDR behavioral detections named "Ransomware", and — if you are lucky — a canary touch minutes before anything else.

Why early detection is hard

Before detonation, the attacker behaves like an ordinary admin: they log on with valid credentials, use built-in tools, and touch systems that admins touch. That is why pure signature antivirus and threshold rules alone fail. The winning pattern is behavior plus placement: files nobody may touch (canaries), rates nobody may reach (write storms), and systems nobody may reconfigure (backup consoles).

Position in the chain

Expect T1490 (shadow copies, backup sabotage) and T1489 (service stop) immediately before T1486, and extortion activity after it. If you see service stops and backup changes on one host, treat it as a ransomware pre-alarm and start triage even though nothing is encrypted yet.

Questions to ask your logging in the next sprint

  • Are Sysmon Event 11 file-create events from servers reaching the SIEM, or only from laptops?
  • Is the Windows Security log from file servers collecting 5145 events at all (share auditing enabled)?
  • Are ESXi shell.log, auth.log, and vmkernel.log shipped centrally, or do they die with the host?
  • Does the backup application export an audit trail that your SIEM can read?
  • Is retention longer than the dwell time you assume for ransomware (weeks, not days)?

How the SOC week looks when it works

Detection engineering is a rhythm, not a project. A healthy week has four fixed tasks. Tier-one analysts handle canary, 1121, and rate alerts, each with a runbook attached. The detection engineer spends one fixed hour tuning the six rules from Section 5.5 against last week's noise. The backup admin confirms job health and immutability settings. And one person — anyone — opens the ESXi log dashboard, because hypervisors are the most dangerous blind spot. None of these tasks takes a day. Together they are the difference between the Change Healthcare timeline and a five-minute containment.

First-hour triage flow

  1. Validate. Confirm the signal is real: canary touch, Defender 1121, or a write-rate alert. Pull the process tree behind it.
  2. Find patient zero. Which host first showed the encryptor process? Check its phish and C2 evidence (Sysmon 1/3).
  3. Measure scope. Are 5145 write bursts hitting shares? Any ESXi /vmfs/volumes/ activity? Any backup console changes? List affected hosts fast.
  4. Contain. Isolate hosts at the EDR or switch. Do not power off — memory holds encryption keys and evidence.
  5. Cut the exits. Block C2 domains and IPs at the firewall and DNS so stolen data stops flowing and re-infection fails.
  6. Check recovery sabotage. Look for T1490 signs: deleted shadow copies, disabled jobs, changed backup configs. Verify one restore from an offline copy now.
  7. Escalate. Start the incident process: leadership, legal, insurer, and any required regulator notifications (Section 5.1). Preserve logs before they roll over.

Which framework applies to you? Work it from your data, not from fear: if you hold EU personal data, GDPR applies; US health data pulls in HIPAA; card payments pull in PCI DSS; EU essential services pull in NIS2; EU finance pulls in DORA; listed US companies answer to SOX; bulk electric to NERC CIP. 5.2

Threat intelligence

Where the intelligence comes from

  • MITRE ATT&CK and its procedure examples — the T1486 page lists 87 groups and samples with observed behavior, plus MITRE D3FEND for countermeasure vocabulary.
  • Vendor threat reports and blogs — malware families publish (and researchers reverse) extensions, note names, and quirks; this feeds your watchlists.
  • Government advisories — CISA #StopRansomware advisories and national CSIRT bulletins describe actor TTPs and indicators in detail.
  • ISACs — sector Information Sharing and Analysis Centers (health, finance, energy) share near-real-time indicators from peers in your industry.
  • Commercial feeds and your EDR vendor — automated IOC (indicator of compromise) feeds plus cloud reputation of new binaries.
  • Your own telemetry — the most underrated source: your baseline of writes, shares, and logons makes every anomaly real.

Turning intelligence into detections

Follow a simple loop. First, collect actor behavior (what they encrypt, which extensions and note names they use). Second, map behavior to data sources you already own (Sysmon 11, 5145, ESXi logs, backup audit). Third, write rules with a stated confidence, and mark the confidence level in the rule description:

  • High confidence — behavior is specific and documented by multiple credible sources (a write to a canary file). Tune down false positives, not the rule.
  • Medium confidence — behavior is plausible but seen in fewer cases (a mass rename with generic extensions). Add thresholds and a human review step.
  • Low confidence — weak or rumor-level signals. Keep them as context in a dashboard, never as paging alerts.

TH-01 · Endpoint and server mass encryption

CriticalWindows

Description. A ransomware binary runs on one or many Windows machines and rewrites user files, then server shares, with ChaCha20 or AES. Extensions such as .akira or .lockbit appear (patterns seen with Akira and Black Basta).

Preconditions. Code execution on an endpoint, then admin credentials for spread. Shadow copies usually deleted first (T1490).

Impact. Users lose all local data; if the encryptor reaches servers, whole departments stop working.

Why this severity. Highest likelihood of all scenarios — it is the classic ransomware path — and a direct hit on daily operations.

TH-02 · ESXi VM datastore encryption

CriticalESXiLinux

Description. A Linux-based locker (Akira_v2, Babuk ESXi builds) is copied to an ESXi host and encrypts files under /vmfs/volumes/, breaking every VM stored there at once.

Preconditions. SSH or console access to the host, often via stolen root credentials or a vulnerable management interface.

Impact. Dozens of servers and workloads fail together; recovery requires VM-level or file-level restore.

Why this severity. Multiplied impact from one action, and ESXi logging is often disabled — so it is both likely in targeting and hard to see.

TH-03 · Linux server and NAS encryption

HighLinux

Description. Linux builds of Babuk or AvosLocker encrypt /srv, /home, or NFS-exported NAS trees with ChaCha8 and leave notes at share roots.

Preconditions. Stolen SSH keys or passwords, an unpatched internet-facing service, or lateral access from a compromised Windows host mounting the share.

Impact. Shared file services and home directories disappear; source code and export data can vanish for days.

Why this severity. Common target, but usually recoverable from the same immutable backups used for Windows — slightly less blast radius than TH-02.

TH-04 · Remote SMB share encryption

HighWindowsNetwork

Description. The encryptor stays on a workstation and encrypts files through mapped network drives. The file server FS-01 sees thousands of 4663/5145 writes and renames from one client while the client's local disk looks quiet.

Preconditions. A user account with write access to shares; the workstation must stay online during encryption.

Impact. Central shares — the documents everyone depends on — are lost even though no server was breached directly.

Why this severity. Frequent in practice and easy to miss: teams watch server processes but forget the server logs tell the story.

TH-05 · Backup repository and catalog encryption

HighCross

Description. The attacker abuses the backup software's own service account (for example a Veeam-style catalog) to disable jobs, delete the catalog, or encrypt the repository — paired with shadow-copy deletion (T1490).

Preconditions. Access to the backup server or its credentials, which are often domain-joined and over-privileged.

Impact. Removes your only way back. An otherwise minor incident becomes a company-level crisis.

Why this severity. Rare alone but an amplifier of everything else; catching it early is worth more than any other single detection.

TH-06 · Cloud VM ransomware via console or RMM

MediumCloudIaaS

Description. With stolen cloud console or RMM access, the attacker pushes an encryptor to many hosted VMs at once using a run-command feature (for example AWS Systems Manager SendCommand or a GPO (Group Policy) style push).

Preconditions. Console credentials without MFA, or an RMM tenant takeover; VMs must allow the agent to run commands.

Impact. Cloud-hosted services (e-commerce, internal apps) go dark together with on-prem systems.

Why only Medium. Needs an extra, less common access path, and cloud audit logs make the push visible — but when it works, treat it as Critical.

TH-01 · Endpoint and server mass encryption

Log sources. Sysmon Operational log (EID 1 process create, EID 11 file create), Windows Defender Operational log (EID 1121 behavior block), EDR console.

Key fields. Image (the process that wrote), TargetFilename, UtcTime, User, DetectionName, ProcessName.

FieldMeaningWhy your rule cares
ImageFull path of the process that created the fileThe actor of every file event; the write-rate rule groups by it so one bad process stands out.
TargetFilenamePath of the new or rewritten fileCarries the canary path and the ransomware extensions.

DetectionNameDefender's name for a behavior detectionThe word "Ransomware" in it is a near-certain detonation signal.
Normal

Word or Excel writes one document when the user saves; an indexer updates a few files per minute; a sync client writes small batches. Write rates stay in the tens per minute per process.

Suspicious

One unknown process writes hundreds of files per minute, filenames gain a new extension, entropy of written files jumps toward 8, and a planted canary is touched.

Detection logic. Two rules. Rule A (precision): any write to a canary path fires immediately. Rule B (recall): per 1-minute window, per host and process, more than 200 file creates with more than 150 unique filenames indicates mass encryption.

TH-02 · ESXi VM datastore encryption

Log sources. /var/log/shell.log (interactive shell commands), /var/log/auth.log (logins), /var/log/vmkernel.log (storage activity). Ship all three to your SIEM — see mistake 10 in Section 8.

Key fields. host, the command line after the shell prefix, process names like python3 / busybox, and the /vmfs/volumes/ path.

FieldMeaningWhy your rule cares
hostThe ESXi host nameLets you scope and limit rule matches to actual hypervisors.
command lineWhat the shell executedpython + /vmfs/volumes/ in one line is the whole detection.
throughput (vmkernel)Storage write rate per datastore5× above 7-day baseline confirms something abnormal is writing.
Normal

Admins run esxcli, vim-cmd, or df -h during change windows. Storage writes match VM workloads. Almost nobody runs python on ESXi.

Suspicious

A new SSH session followed by python or a hidden /tmp directory touching /vmfs/volumes/, then a vmkernel write burst far above baseline.

Detection logic. Alert on any shell command containing python together with /vmfs/volumes/ (any single hit is critical), and on vmkernel write throughput more than 5× the 7-day baseline for the datastore.

The story is complete in five lines: a root login from outside, a hidden script made executable, python writing straight into the datastore, a write burst nine times normal, and a cleanup attempt. Each line is separately detectable; together they are a full alarm chain.

TH-03 · Linux server and NAS encryption

Log sources. Linux auditd (syscall events), syslog/journald, EDR for Linux, NAS vendor audit logs.

Key fields. syscall (rename/renameat2), name / nametype=CREATE, exe, uid, host.

FieldMeaningWhy your rule cares
syscallWhich system call ran (316 = renameat2)Renames, not creates, are the fingerprint of extension changes.
nameThe new path after the renameCarries the ransomware extension to match.
exeBinary that performed the callProcesses running from /tmp are wrong for a file server.
uid / auidAccount performing the actionDistinguishes a service account from a human login.
Normal

Backup jobs, package managers, and build tools rename files in their own directories at modest rates. Renames of user documents are rare and human-paced.

Suspicious

One process from /tmp performs hundreds of renames per minute across user trees, adding extensions like .lock, .crypt, .avos, or .encrypted.

Detection logic. Count rename events that create files with known ransomware extensions; more than 50 per minute per host, or any hit on the extension list from a process in /tmp, is an alert.

syscall=316 is renameat2 on x86-64. The PATH records carry the new names — the .lock suffix and the exe="/tmp/enc" location are the two details your rule keys on.

Note on NAS devices. Many NAS boxes run Linux inside, so the same rule works — but the logs may arrive as vendor syslog instead of raw auditd. If your NAS can only export generic syslog, watch for its own file-service log producing thousands of rename or open-for-write lines per minute, and treat the NAS vendor's audit guide as the field dictionary for TH-03.

TH-04 · Remote SMB share encryption

Log sources. Windows Security log on the file server (4663 object writes, 5145 share access), USN journal growth, Sysmon 11 on the source host.

Key fields. EventID, ShareName, RelativeTargetName, AccessList (%%1541 = WriteData/AddFile), SubjectUserName, IpAddress.

FieldMeaningWhy your rule cares
ShareNameWhich share was touched (IPC$ and ADMIN$ are admin noise)You filter those two out before rate math.
RelativeTargetNamePath of the file inside the shareNew extensions appear here even when the client hides them.
AccessListWhat was requested (%%1541 = write data)Write-heavy access is the pattern of encryption.
IpAddressClient performing the accessOne IP producing thousands of writes is the alert itself.
Normal

Users open and save a handful of documents per minute; nightly backups and sync jobs produce steady, schedulable bursts from known accounts.

Suspicious

Thousands of 5145 WriteData events per minute from one client IP, renames with new extensions in the relative target names, activity outside backup windows.

Detection logic. Per 1-minute window, per source workstation, more than 200 share-write events (5145 with %%1541) outside the known backup jobs. Confirm by scanning RelativeTargetName values for ransomware extensions.

One such event is routine. The signal is the rate: 4,180 events from 10.20.4.117 in one minute against a baseline of about 120, with %%1541 (write data) in the access list. The file server was never breached — the workstation did the damage through the share.

A second, cheaper signal lives on the file server itself: the USN journal, NTFS's change log. During a share-encryption storm it grows thousands of times faster than during a busy backup window. Read its size remotely and track it over time. A sudden jump, matched with the 5145 burst, proves mass file changes — even on servers where share auditing was never switched on.

Benign look-alike · TH-04 share-write storm

One honest storm source remains: a designer, developer, or build agent syncing a huge asset library over the share in one session. It can reach the same 200-writes-per-minute threshold. The tells: the account is named and expected, the hour matches a work pattern, the paths stay inside one project tree, and no ransomware extension appears in the relative target names. If your baseline shows such users, allowlist the specific account — not the whole subnet — and let the rest of the rule stay strict.

Log sources. Backup application audit log (catalog and job changes), Windows Security log on the backup server (4688, 4663, network logons), EDR.

Key fields. action (CatalogDelete, JobDisable), user, object, clientIp, plus Windows EventID 4688 on the backup server.

clientIpWhere the console call came fromBackup actions should originate from the backup server or jump hosts only.

Backup admins disable a job during maintenance with a change ticket; catalog maintenance runs from the backup server itself, in window, from known IPs.

The backup service account ran from a workstation IP (a backup server or jump host would show its own IP), disabled two jobs, and deleted a catalog in 22 seconds. That sequence is the attacker removing your way back — it must page someone immediately, even though nothing is encrypted yet.

TH-01 · Endpoint and server mass encryption

Mapping note. The Sigma rule maps to Sysmon Event ID 11 (file create) on Windows. The SPL assumes Sysmon lands in index=sysmon with the sourcetype produced by the Splunk Add-on for Windows; if you use CIM-normalized data in index=edr, rename TargetFilename to file_name and Image to process_name. False positives. Admin work on the canary folder; a migration tool copying it once. Tuning. Keep one canary per share and per user profile root, name them like real work, and exclude your canary-maintenance account by user. Lower the write-rate threshold only after a week of baseline data. Severity: Critical — treat one canary event as detonation.

Benign look-alike · TH-01 write-rate rule

The write-rate companion rule counts file creates per process per minute. The honest false positive is the nightly backup or sync agent: it writes thousands of files in bursts, exactly like an encryptor. The quiet version has three tells: it runs at a scheduled hour, from a known service account, and the file names it writes are normal paths — no new extensions.

Tuning answer: allowlist the backup agent by Image path and by its service account, and keep the threshold low for everything else. A user-context process writing at backup rates should still alert.

TH-02 · ESXi VM datastore encryption

Mapping note. The Sigma rule maps to ESXi shell command logging (the /var/log/shell.log events from Section 5.4); ESXi has no native Sigma product, so process_creation/linux is the closest standard category and the SPL does the real work. The SPL assumes ESXi logs are shipped to index=esxi with a VMware add-on; sourcetype names vary by ingestion, so adjust the two listed values to yours. False positives. Storage-team scripts during documented change windows. Tuning. Exclude the two admin hosts and the change-window schedule; keep the threshold at 3 commands, because normal admins simply never run python against datastores. Severity: Critical.

TH-03 · Linux server and NAS encryption

Mapping note. The Sigma rule maps to file events from an EDR agent or osquery file_events on Linux; if you run only auditd, the SPL version is the direct implementation. It assumes auditd events land in index=linux with sourcetype linux_audit and the name field carrying the new path — field names vary slightly by forwarding setup. False positives. Package updates and build jobs (they rename in system paths, so exclude /usr and /var/lib). Tuning. Require the extension list match first (precision), then the rate (recall); add an exclusion list for your archive tool's account. Severity: High.

Benign look-alike · TH-03 rename burst

Legal bulk renames happen on purpose too: a migration script converts a folder of files to a new naming scheme and produces hundreds of rename syscalls in seconds. The tells are the paths (one project folder, not the whole filesystem), the account (a named engineer with a change ticket), and the extensions (the new names keep their real ones — no .lock or .crypt appears).

TH-04 · Remote SMB share encryption

Mapping note. Both map to Windows Security Event 5145 (a detailed File Share access was checked) collected with the Splunk Add-on for Windows into index=wineventlog; %%1541 is the WriteData/AddFile access right. Baseline for two weeks, then set the threshold at three times the busiest normal client minute; add schedule exceptions for your backup window rather than excluding accounts outright. TH-05 · Backup repository and catalog encryption

Mapping note. The Sigma rule maps to the Windows Defender Operational log (Event 1121); most shops forward it into index=wineventlog, and EDR products can supply an equivalent signal in index=edr. Test your rules before you trust them

  1. Build the canary. Create the Canary folder and files on one lab VM and one file server; confirm the file_event rule fires when you edit the file by hand.
  2. Fire the rate rules safely. Copy a large tree of dummy files (empty or random-filled) on the lab host to exceed the write threshold, and watch the SPL return your lab host only.
  3. Check the negatives. Run your normal backup and sync jobs; confirm none of the six rules fires. Every false positive you find now is an alert you will not hate later.
  4. Verify the routing. Confirm critical rules reach the paging channel and high rules reach the queue — an unwatched rule is a decoration.
  5. Document the runbook. For each rule, write the first triage step and owner directly in the rule description, so the alert and the action live together.

Real-world case study: Change Healthcare / ALPHV, February 2024

A documented public incident, not a composite. Change Healthcare — the claims-processing arm of the US health system, part of UnitedHealth Group — was hit by the ALPHV (BlackCat) ransomware in February 2024. Facts below come from public reporting and company statements; details are simplified for teaching.

Context

Change Healthcare processes a huge share of US medical claims and pharmacy transactions. On 12 February 2024, an attacker signed into the environment through a Citrix remote-access portal that did not require MFA (multi-factor authentication — a second proof of identity beyond the password). The account used had been harvested earlier, so the password was correct. That single missing control opened the door to one of the most disruptive cyber incidents in US healthcare.

Why this target mattered

Healthcare runs on timing: claims must be submitted, pharmacy orders verified, and payments settled daily. A company sitting at the center of that flow is a high-pressure target — every hour of downtime is felt by thousands of unrelated organizations. That is exactly why the group could demand a large ransom, and why recovery decisions were made under extraordinary pressure. The lesson generalizes: the more your business depends on one processing pipeline, the more your detection and backup design should treat that pipeline as critical infrastructure.

Attack chain

The chain matches the simulation in Section 2 almost exactly: stolen credentials and a portal without MFA (initial access), nine days of moving between systems and collecting data (lateral movement, exfiltration), then the ALPHV encryptor deployed for impact. The double-extortion model was explicit: encrypt for availability, leak for confidentiality, demand for both.

Detection point

The hard lesson

The intrusion was detected only when the ransomware detonated — after nine days of quiet access and six terabytes of stolen data. Nothing about the early phases tripped an alarm that stopped the attack. This is "detected too late" at scale. The detections in Section 5.5 exist to close this gap: MFA failures, new remote-access logons, admin-share staging, and canary touches all fire long before encryption.

Containment

On discovery, the company disconnected and segregated large parts of the infrastructure to stop encryption from spreading further. This stopped the attack but also took healthy systems offline on purpose — the classic containment trade-off when there is no precise map of what the attacker touched.

Eradication

After disconnecting, teams hunted for attacker persistence: credentials were rotated, systems were rebuilt rather than cleaned where trust could not be proven, and remote access was re-established only with new authentication controls. Eradication ran in parallel with the political reality that every hour offline was measured in patient-facing impact.

Recovery

Recovery was staged: critical services came back first, verified against clean copies, with manual workarounds filling the gaps for weeks. The incident became a public demonstration of the 3-2-1-1-0 backup principle (three copies, two media, one off-site, one immutable, zero restore-test errors) — the difference between days and months of downtime.

Impact and consequences

  • Claims and pharmacy services across the US were disrupted for weeks; providers lost revenue flow and patients faced prescription delays.
  • A reported $22M ransom payment, followed by an affiliate exit scam and a second extortion attempt (RansomHub) using the stolen data — payment bought no guarantee.
  • Total response costs reported by UnitedHealth in the billions of dollars, plus regulatory scrutiny and congressional testimony.
  • Sector-wide lessons: regulators and ISACs pushed MFA on every remote entry point and tested restores as baseline hygiene.

Team response and communication

The response had to run on two tracks at once: technical (isolate, rebuild, restore) and human (clinics, pharmacies, regulators, and the press). Communication was continuous but constrained by the investigation; the ambiguity itself caused harm, because partners could not plan. The takeaway for your team: pre-write your outage comms, agree who speaks, and publish a status page — during the incident is the worst time to design them.

Lessons learned

  1. MFA on every remote entry point — one portal without it undid everything else.
  2. Segmentation — a flat network let nine days of movement reach the most valuable systems.
  3. Immutable backups and tested restores — recovery speed is a designed property, not luck.
  4. Detections before detonation — the phases before encryption are detectable; build for them.
  5. Ransom payment is not a plan — paying did not end the extortion; preparation does.

Mitigation and defense

Controls that measurably reduce T1486 risk, ordered from the ones that remove the attack to the ones that limit the damage. Mitigation is layered: no single card below is enough alone.

Immutable, offline backups

Follow 3-2-1-1-0 and keep one copy immutable (unchangeable for a set time). Test restores quarterly. This single control converts a crisis into an outage.

EDR with behavior blocking

Deploy endpoint detection and response on servers and ESXi management, not just laptops. Turn on ransomware behavior blocking and configure canary files everywhere.

MFA on all remote access

VPN, Citrix, RDP gateways, cloud consoles, and RMM tools. Phishing-resistant methods (FIDO2 keys) preferred. This kills the most common entry path.

Segmentation

Separate users, servers, backups, and management networks. Workstations should not reach backup repositories or hypervisor management at all.

Least privilege

Backup and service accounts get scoped rights and no interactive logon. No domain admin for daily work. Attackers ride over-privileged accounts.

Patch internet-facing systems

Edge devices, remote-access software, and file-transfer tools are favorite doors. Patch on a schedule measured in days, not quarters.

Ransomware SIEM correlation

Deploy the Section 5.5 rules, plus pre-impact correlation: backup job disables, shadow-copy deletion, and new admin-share sessions together.

Logging that survives

Ship Sysmon, Windows Security, ESXi (shell, auth, vmkernel), and backup audit logs off-host. Retention longer than attacker dwell time — weeks, not days.

Incident response plan

A written plan with legal, insurer, and regulator contacts pre-engaged. Decide ransom-policy questions now, calmly, not during the incident.

Home and small office

Keep an offline backup of important files (an external drive that stays unplugged), update your operating system and router, run built-in antivirus, and be slow to open attachments or install "crack" tools. If a "free decryptor" is offered by a random site, assume it is a scam. Test that your backup actually restores before you need it.

Backup design that survives ransomware

Since TH-05 is the attacker's most used attack path, your backup architecture deserves its own checklist. Keep three kinds of protection. One backup copy is immutable — locked against changes and deletion for a retention window. One copy is offline or air-gapped, with no network path at all. And the backup platform's credentials stay outside the domain users and servers live in. Separate the backup admin account from everyday admin accounts, and alert on every change to jobs, catalogs, and repositories (rule TH-05). Finally, rehearse the restore at VM level — ESXi restores are where untested backups usually reveal their secrets.

Common mistakes and best practices

Fourteen concrete blue-team mistakes seen in real T1486 incidents, each with symptom, root cause, fix, and prevention. Read them as a checklist for your own environment.

1 · Backups that were never restore-tested

Symptom: recovery takes days while teams discover the backup is empty or corrupt. Root cause: jobs reported "success" and nobody verified a real restore. Fix: run a full restore test this week, file the result. Prevention: quarterly restore drills with a sign-off owner (the "0" — zero restore-test errors — in 3-2-1-1-0).

2 · Backup server joined to the domain it protects

Symptom: the backup server encrypts along with everything else. Root cause: domain credentials reach it, so one compromised admin account owns the last resort. Fix: move repositories off-domain, use local or dedicated identities. Prevention: treat backup infrastructure as its own tier with its own credentials and MFA.

3 · No canary files anywhere

Symptom: first alert arrives from users, after hours of encryption. Root cause: detections rely on rates and signatures only. Fix: plant canaries per share and per profile root, wire the Section 5.5 rule. Prevention: add canary checks to onboarding of every new share and file server.

4 · Signature-only antivirus

Symptom: AV stays silent while files rename around it. Root cause: ransomware kits morph and use valid tools; hashes change nightly. Fix: enable behavior blocking and tamper protection. Prevention: budget for EDR on all platforms, including Linux and ESXi management.

5 · No EDR on servers or ESXi

Symptom: the attack is only visible where laptops happen to be. Root cause: performance fears and licensing gaps left the most valuable systems unmonitored. Fix: deploy agents server-side, or at minimum centralize ESXi and server logs. Prevention: make "does it log?" a deployment gate like "does it back up?".

6 · Write thresholds set too high

Symptom: the mass-write rule fires after encryption has finished. Root cause: thresholds chosen from a whiteboard (10k/min) instead of baseline data. Fix: measure a real week, set threshold at 3× busiest normal minute. Prevention: re-baseline after major tooling changes.

7 · Ignoring Defender 1121 events

Symptom: 1121 blocks sit unread in a queue and the attack resumes from another process. Root cause: "antivirus handled it" bias. Fix: route every 1121 to the SOC as a triage item, not background noise. Prevention: weekly review of blocked-but-persisting process patterns.

8 · No baseline for 5145 or USN growth

Symptom: share-encryption storms look "normal" to the filter. Root cause: nobody measured what normal file-server traffic is. Fix: baseline 5145 rates per client for two weeks (Section 5.5). Prevention: store baselines in the SIEM and refresh them quarterly.

9 · Log retention shorter than dwell time

Symptom: during response, the logs that would show entry and staging are already gone. Root cause: 7–14 day retention to save storage. Fix: raise retention to 90 days hot, 1 year cold for key sources. Prevention: size retention to your risk model — ransomware dwell time is routinely weeks.

10 · ESXi shell and auth logs disabled

Symptom: the datastore locker ran, and the host has no record of who or what. Root cause: "hypervisors are appliances" thinking. Fix: enable and ship shell.log, auth.log, vmkernel.log (Section 5.4). Prevention: include hypervisors in the logging standard and audit it.

11 · "Paying the ransom" written as the plan

Symptom: in the incident, the only prepared step is a payment decision. Root cause: recovery capability was never built, so payment feels like the only lever. Fix: build restore capability; make payment a legal/insurer decision with a default of no. Prevention: rehearse the IR plan without payment as an option. Remember Change Healthcare: payment did not stop the extortion.

12 · No offline copy of recovery documents

Symptom: the runbooks, network diagrams, and license keys are stored on the systems that just got encrypted. Root cause: convenience beat resilience. Fix: print or store sealed copies of critical runbooks offline. Prevention: add "recovery docs available offline" to the annual DR test.

13 · Alarm fatigue on file-create events

Symptom: analysts auto-close Sysmon 11 alerts without reading them, and the one that mattered slips through. Root cause: raw FileCreate events were routed as alerts instead of being aggregated first. Fix: replace raw event alerts with the aggregated rules of Section 5.5, and keep canary events as the only always-page file alert. Prevention: review alert volumes monthly; if a rule fires mostly noise, tune it rather than teach the team to ignore it.

14 · One backup vendor, no air gap

Symptom: every copy of the data — primary, replicas, backups — was reachable with the same stolen credentials. Root cause: a single vendor stack with shared admin credentials and no offline copy. Fix: add one copy on a different platform or tape, reachable only from the backup network. Prevention: treat credential separation between production and backup as an architecture requirement, not an option.

Signals your ransomware program is maturing

  • Canary self-tests appear in the quarterly report with dates and results, not just "done".
  • The six rules from Section 5.5 have named owners, last-tuned dates, and measured false-positive rates.
  • Restore drills include at least one ESXi VM and one file-server share, end to end.
  • The IR plan references this page's triage flow, and the on-call rotation has run it once this quarter.
  • ESXi and backup dashboards exist — and someone outside the infra team checks them monthly.

Response checklist

  • Isolate affected hosts at EDR/switch — do not power off (memory holds evidence).
  • Preserve logs before they roll: Sysmon, Security, ESXi, backup audit, cloud audit.
  • Identify patient zero and the process tree behind the first canary or 1121 event.
  • Check T1490 indicators: shadow copies deleted, backup jobs disabled, catalogs removed.
  • Verify one restore from the immutable copy, reading it from a clean system.
  • Rotate credentials the attacker could have touched, including backup service accounts.
  • Stage the restore: critical services first, verified before reconnection.
  • Notify legal, insurer, and regulators per Section 5.1 obligations.
  • Block C2 domains and IPs at firewall and DNS; watch for re-entry attempts.
  • After recovery: run the Section 8 checklist against what failed.

Quick questions

Can we stop ransomware with signatures alone?
No. Signatures catch known binaries; every serious family changes its binary per victim. Behavior — canary writes, extension bursts, shadow-copy sabotage — is what holds.
Where do I put canary files?
One per share root and one per user-profile root. Name them like real documents. Protect them from deletion, and alert on any write — a canary with a permissive rule is decoration.
Our backups are on the domain. How urgent is that?
Very. It is the difference between TH-05 firing on a foreign account and the backup server encrypting quietly with everything else. Move credentials off the domain first.
Should we alert on every 1121 event?
Alert on 1121 events whose DetectionName contains "Ransom" or "Encrypt". Other 1121 blocks (PUA, exploit blocks) go to a lower-priority queue so the ransomware ones stay loud.
What single control buys the most time?
MFA on every remote entry point. It does not stop encryption by itself, but it removes the easiest way in and forces attackers onto louder paths.
Encrypt or wipe — how do I tell them apart?
Check the file: encrypted files keep readable names and gain a new extension or note; wiped files shrink to zero or vanish. Also check the clock: encryption takes minutes of steady writes; a wipe is fast and total.
Is paying the ransom a recovery plan?
No. Payment is a business decision with no guarantee: keys fail, groups exit-scam, and re-extortion happens. The only plan that always works is a tested restore.
Where do I start with one hour a week?
Put canary files everywhere, stream the Defender 1121 log into the SIEM, and schedule one restore test. All three are cheap, and each one breaks a different step of the story in section 2.
Do we need EDR on every server?
Yes, or their file events must reach the SIEM another way — Sysmon 11 counts. The 5145 and canary rules catch remote encryption, but local encryption on an unmonitored server is visible only after the fact.
