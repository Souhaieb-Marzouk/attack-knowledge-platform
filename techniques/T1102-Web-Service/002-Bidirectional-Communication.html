Overview

What this technique is, why it is dangerous, and how it differs from its sibling sub-techniques.

Plain-language definition

Bidirectional Communication (T1102.002) is a way for malware to talk to its operator through a legitimate web service. "Bidirectional" means traffic flows both ways over the same service: commands go in to the victim, and stolen data goes out from the victim.

Here is the core idea. The attacker registers a bot or app on a public platform, for example a chat service. The malware on the victim machine holds a secret token (a long password-like string) for that bot. The malware asks the platform API, again and again: "are there new commands for me?" The attacker types a command into the chat. The next poll delivers it. The malware runs the command and uploads the output, or even whole files, back through the same platform API.

No connection is ever made between the attacker's own computer and the victim. Both sides only talk to the popular public service. This hides the attacker and makes blocking painful, because the service is one your business may legally need.

Beacon is a common word for the repeated "any new commands?" check. In this technique the beacon is usually a small inbound request at a fixed rhythm. It is the mirror image of classic command-and-control (C2), where the malware connects to a server that the attacker owns.

Why it matters

Traffic looks normal

The malware speaks to api.telegram.org, discord.com, or a similar trusted host over HTTPS. Every packet looks like a normal chat client. Domain reputation is clean. Certificates are valid. Simple blocklists based on "bad domains" do not work.

Full remote tasking

Because the channel works in both directions, the operator gets an interactive remote control: run commands, pull files, push new tools, update the implant. This is much more powerful than a one-way drop (see the sibling sub-techniques below).

Free, resilient infrastructure

The attacker pays nothing. The platform is global, highly available, and rate-limits abuse gently. If one bot account dies, the operator registers another and pushes a new token in minutes.

Detection is possible

The pattern has a shape: small, regular, automated polls in; larger uploads out; a non-browser program doing chat things; at odd hours; from servers that should never chat. This page turns that shape into concrete detections.

Common misconceptions

"Only Windows is affected"

No — every platform that can run a script and reach the internet qualifies: Linux servers, macOS laptops, and even cloud identities (see THR-04 in section 5.3).

"Blocking the domain solves it"

Blocking helps containment, but the operator registers a new bot in minutes, and your business may need the same domain. Revoking the token and evicting the implant are the real fixes.

"DLP would have caught it"

Only if the content matched a fingerprint and only on inspected channels. Encrypted, encoded, or tenant-internal uploads pass. Behavior rules catch what content rules miss.

"It always needs malware"

Wrong twice: malware-free variants abuse a granted OAuth app, and some malware uses the channel only for exfil. Watch identities and traffic, not just processes.

"Small files mean small risk"

Gamaredon-style small-file exfil is a steady trickle: credentials, keys, contact lists. Ten kilobytes of the right file can cost more than a gigabyte of documents.

"One alert is enough"

As the case study shows, the catch came from fusing two weak signals. Plan coverage so at least two independent rules can see any one operation.

Where it sits in the attack chain

T1102.002 belongs to the Command and Control tactic. It usually appears after the malware is already running on the victim host (after initial access and execution). From that moment it becomes the operator's way to see the machine and act on it. The same channel often carries a second job: exfiltration — copying stolen files out of the network. One web service, two tactics.

Typical chain: phishing message → user runs the attachment → implant starts → poll loop begins → attacker tasking → discovery commands → collection of files → upload through the same platform → escalation to ransomware or deeper access.

Written story — the same eight steps in words

Note — The pattern in one sentence

Polls arrive with a steady, even beat like a metronome; uploads arrive as rare spikes; the client is not a browser; the host should not be chatting at all. Any two of these together deserve a look.

The animation above is a picture of the story below. If you cannot view animations, this text is the full alternative. The names are examples; the mechanics follow publicly documented attacker behavior.

  1. Implant installed with an embedded bot token. A user opens a phishing attachment, and a dropper installs the implant on the workstation. The implant carries a chat bot token in its configuration file or memory. Defender view: EDR sees the process tree and a new scheduled task; the proxy still shows nothing unusual.
  2. Attacker sends a task through the chat platform. From a laptop far away, the operator types a command into the bot chat, for example "screenshot and collect recent documents". The platform stores the message as an update for the bot. Defender view: nothing on your network yet; the message sits on the platform waiting to be polled.
  3. Malware polls getUpdates and receives the task. The implant calls the platform API every 30 seconds with a small request. The next poll returns the pending task. The request is tiny; the rhythm is regular. Defender view: proxy logs show small, evenly spaced POST/GET requests to a chat API domain from a workstation — the first visible beacon.
  4. Malware executes the task. It takes a screenshot, lists directories, and copies selected files into a temp folder. All of this happens inside the host. Defender view: EDR notices the beacon process spawning system tools, touching many files, and writing to a staging directory.
  5. Malware uploads results through the same API. The implant sends the screenshot and collected files back with upload calls (sendDocument-style POST with multipart data). Traffic out is much larger than the polls in. Defender view: proxy shows a big outbound POST to the same chat API — bytes far above any normal poll.
  6. Attacker downloads the results. The operator opens the chat, sees the new documents, and pulls them down from the platform. The attacker's own IP never appears in your logs; only the platform does. Defender view: on SaaS/audit side, a new document appears in the bot's storage; on your side, only the outbound upload was visible.
  7. The loop continues with the next task. The attacker sends another command; the next poll picks it up. Requests in, results out, again and again — this is the bidirectional pattern. Over hours the rhythm stays regular even as content changes. Defender view: a 24-hour proxy timeline shows dozens of identical-size polls plus periodic upload spikes: the classic C2+exfil signature.
  8. SOC responds. CASB flags uploads from a server identity; EDR shows which process made the API calls. The team revokes the bot token by reporting the bot to the platform, blocks the API domain for that host group, and isolates the workstation. Defender view: containment breaks the loop: polls stop, uploads stop, and the implant can no longer hear orders.
Note

Step 5 is the pivot. Polls in are small and boring. The upload out is where volume, file names, and unusual methods appear. If you can keep only one high-signal rule, make it "automated client uploads a large payload to a chat API".

Red team perspective

Concept-level view of how attackers build and use this channel — written so defenders can anticipate it. Nothing here is operational guidance against real systems.

Danger — Ethics and scope

This section describes attacker behavior so defenders can build detections. The lab example talks only to your own machine (127.0.0.1). Using a real platform as an unregistered C2, or touching systems you do not own, is illegal in most jurisdictions. Red teams should use dedicated lab infrastructure and written authorization.

When and why attackers use it

The network is the problem

Corporate firewalls usually allow outbound HTTPS but block inbound connections. Direct C2 needs the attacker to be reachable. A web-service channel solves this: both sides go out to the same public service.

Reputation is borrowed

The traffic speaks to a domain with a clean reputation and a valid certificate. Cheap "block known bad domains" controls see nothing suspicious in the name.

Cost is near zero

Registering a bot or app is free and takes minutes. Compare that with buying, hosting, and rotating dedicated C2 servers that get burned every campaign.

Tasking survives downtime

Commands wait in the platform until the victim polls. The implant can go offline for hours, come back, and pick up the queue — useful for long-dwell espionage-style operations.

How it is performed (concept level)

Every implementation follows the same skeleton, whether the platform is a chat bot API, a social network, or a SaaS storage app:

Where it applies

Windows workstations

Implants talk to chat APIs from user context; scheduled tasks keep the loop alive. Workstations are the classic target.

Linux servers

Web shells and backdoors written in Python or Go poll chat APIs. Servers should never need consumer chat services — a strong anomaly.

macOS endpoints

Less common but documented: social-platform APIs used for tasking and screenshot return.

SaaS abuse

Compromised OAuth apps with storage scopes turn the company's own tenant into the drop box — traffic never leaves the approved SaaS.

Cloud workloads

Compromised CI runners or containers exfiltrate secrets to developer-friendly chat webhooks in seconds.

Consumer devices

Infostealers on home PCs ship browser passwords to Telegram bots; the same pattern small businesses inherit from BYOD (bring your own device).

Prerequisites (what must be true for this to work)

  • Outbound HTTPS to the chosen platform — nearly universal in enterprises.
  • A valid token for a bot or app the attacker controls.
  • An encoder: tasks and results are usually base64-, XOR-, or AES-wrapped so that platform staff and casual observers see noise.
  • Patience: the poll interval trades speed against visibility. Common choices are 5–60 seconds for criminal tools, minutes to hours for espionage implants.

Ethical lab example — safe and local only

The snippet below is a detector training aid, not malware. It emulates the traffic rhythm of a poll loop against a listener on your own loopback interface. It never contacts any real platform and sends no real data. Run it only in an isolated lab to generate sample logs for tuning the detections in section 5.

lab_poll_emulator.py — loopback only · Lab only 
# Lab only: emulate a 30-second poll loop against a LOCAL mock server.
# Target is 127.0.0.1 on your own machine. No external hosts are contacted.
import time, urllib.request, base64

MOCK_API = "http://127.0.0.1:8080/mock/getUpdates"   # your own listener
INTERVAL = 30                                        # seconds between polls

while True:
    try:
        req = urllib.request.Request(
            MOCK_API,
            data=base64.b64encode(b"poll"),
            headers={"User-Agent": "lab-emulator/1.0"},  # non-browser UA on purpose
        )
        with urllib.request.urlopen(req, timeout=5) as resp:
            body = resp.read(4096)
        print("poll done, bytes:", len(body))
    except Exception as err:
        print("listener not running:", err)
    time.sleep(INTERVAL)

Pair it with any 20-line local HTTP listener that answers with a fixed JSON body. The point is to produce realistic log lines — regular intervals, tiny requests, a non-browser user agent — so you can validate the Sigma and SPL rules in section 5.5 against your own stack.

Blue team perspective

How defenders see this technique in practice: the artifacts it leaves, the logs that hold them, and a triage flow you can run today.

How defenders see it

You will almost never see "malware" in a single event. You see a pattern across many small events. Three properties make the pattern stand out from normal chat traffic:

  • Direction and shape. Normal chat is bursts in both directions with wide size variety. This channel is a metronome: many small, equal-sized polls in; rare, much larger uploads out.
  • Client identity. Chat APIs are normally touched by browsers and official apps. A bare HTTP library (python-requests, curl, go-http-client) talking to a chat API from a server is rare and worth a look.
  • Who should be chatting. A workstation user might plausibly use a chat app. A database server, a backup service account, or a CI runner has no business doing so at all. Asset context turns a weak signal into a strong one.

EDR (Endpoint Detection and Response — software that records what processes do on a host) is what ties the network event to a program name. CASB (Cloud Access Security Broker — a gateway that logs which cloud apps move what data) is what ties the upload to a user or app identity.

Artifacts it leaves behind

On the wire

  • Recurring small requests to chat API hostnames (poll pattern).
  • Large multipart POSTs to the same hostnames (upload pattern).
  • TLS client fingerprints of scripting runtimes instead of browsers.
  • DNS lookups for chat platforms from hosts with no chat usage history.

On the host

  • A process whose network sessions match the poll rhythm (EDR correlation).
  • Bot-token strings in config files, registry values, or process memory.
  • Persistence: scheduled tasks, run keys, cron entries, launch agents.
  • Staging directories filling with archives before each upload spike.

In the cloud tenant

  • New bot apps or webhooks created by unexpected users.
  • OAuth grants with chat/storage scopes that nobody in IT issued.
  • Audit trails of file uploads far above the identity's baseline.

In human workflow

  • Users reporting odd messages in a company-relevant channel.
  • The platform itself acting on abuse reports (bot disabled).
  • Helpdesk tickets about slow uploads from one subnet.

Why it matters for defenders

This channel means an intruder has interactive control, not just a data leak. If it is active in your network, assume the operator can run commands today. It also means classic containment — "block the C2 domain" — is a business decision, because the same domain may serve legitimate users. That is why the triage flow below ends with scoped blocking and token revocation, not blanket firewall rules.

How it fits the attack chain

Detection at each stage changes the outcome. Catch the poll (step 3 of the simulation) and you may evict before data leaves. Catch the upload (step 5) and the case becomes incident response plus legal notification. The earlier in the chain you see it, the cheaper the incident.

Field notes for the first hour

  • Do not block the platform globally yet. You may break chat for the whole company and lose your visibility into the operator's next moves.
  • Do not power the host off. Isolate it at the EDR or switch level so memory and agent telemetry stay available for triage.
  • Export the poll timeline now. Proxy retention is often shorter than your incident meeting cadence.
  • Name one decision owner. Token revocation and scoped blocking each need one approver, not a committee.

Short triage flow

  1. Confirm the shape. Pull 24–48 h of proxy events for the host. Count polls, measure intervals, and check for upload spikes. Regular rhythm + asymmetric volume = proceed.
  2. Name the process. In EDR, find which process owns the connections. Note parent process, path, and persistence.
  3. Check the client. Look at the user agent and TLS fingerprint. Browsers or official apps are benign; bare HTTP libraries are not.
  4. Scope it. Search EDR and proxy for the same process hash, token string, or bot ID across all hosts. One hit is malware; many hits are a campaign.
  5. Contain. Isolate affected hosts, revoke or report the bot token so the platform kills it, and block the API path for the affected host group only.
  6. Assess exposure. Sum uploaded bytes and file names from logs; treat everything that left as compromised and notify stakeholders.
  7. Report and tune. File the timeline, add the detected pattern to your detection backlog, and schedule a purple-team replay to prove the rules fire.
Good practice

Write the triage steps above into your incident response runbook before you need them, including who owns token revocation and who approves scoped domain blocks. During an active beacon, minutes matter and decisions should not wait on meeting invites.

5.2 · Threat intelligence

Detection improves when you feed it known attacker behavior. This subsection shows where intelligence on T1102.002-style channels comes from and how to turn it into rules you can actually run.

Sources and method

MITRE ATT&CK

The technique page and its official references list documented groups and tools. Start here; it is free, stable, and maps to detections.

Vendor reporting

Security vendor blogs describe real samples: token names, intervals, API endpoints. Classic example: Kaspersky's 2019 write-up of ComRAT (Turla), which documented a full command channel through a Gmail mailbox — commands read from drafts, output sent back as attachments.

OSINT and ISACs

Open-source researchers and sector ISACs (Information Sharing and Analysis Centers) share indicators and campaign notes. Quality varies — treat every claim as a lead, not a fact.

Commercial feeds and internal telemetry

Feeds give volume; your own proxy/EDR data gives truth. The best indicators are the ones you found yourself, because nobody else can see your environment's baselines.

The working loop: collect → analyze → apply

1 · Collect

Pull behavior descriptions, not just IPs. "Gamaredon tool polls a Telegram bot every ~30 s and sends small files back" outlives any single indicator.

2 · Analyze

Turn reports into objects: what log field, what value, what rhythm, what threshold? Note the confidence of each claim and who reported it.

3 · Apply

Write the rule (sections 5.4–5.5), test it on historical logs, measure false positives, and record the intel source in the rule's references field.

Worked example: from report to rule

  1. Report: "A tool polls a Telegram bot about every 30 seconds and returns small files through the bot" — public CERT-UA advisory describing Gamaredon tooling (2022).
  2. Objects: destination api.telegram.org; path pattern /bot…/getUpdates; interval ≈ 30 s; upload call sendDocument; confidence: high.
  3. Rule: the interval-math proxy rule (rule 1 in 5.5) plus the upload-size rule (rule 2) cover both halves of the behavior.
  4. Test: replay two weeks of your own logs, count hits, build allowlists with owners, and paste the intel source into the rule's references so future reviewers know where it came from.

What the confidence labels mean

  • High confidence — multiple independent sources, or a named vendor reproduced the behavior from samples. Safe to build detections on.
  • Medium confidence — a single credible source, or details that vary between reports. Build the detection; verify thresholds against your own baseline first.
  • Low confidence — rumor, anonymous claim, or a report you cannot verify. Use for hunting hypotheses only, never for automated blocking.

The internal beaconing host, 192.0.2.44 (example: workstation WKSTN-4417.corp.example).
dest_ip / dest_port
The platform edge, 203.0.113.10:443 — the IP rotates, so always key on the hostname, not the address.
http.method + url
A POST to the bot's getUpdates path. The path contains the bot token — treat any log line with a real token as sensitive and redact it before sharing.
http_user_agent
python-requests/2.31.0 — a scripting library, not a browser or official app. This single field does most of the detection work.
length / flow.bytes
A tiny 262-byte response over a 612-byte flow: classic small poll. Collect dozens of these and the interval math (THR-01) becomes trivial.

5.5 · Sigma rules and Splunk SPL

Five complete rules below cover the Critical and High threats from 5.3. Each Sigma rule is followed by a matching Splunk SPL query, a field-mapping note, expected false positives, and tuning guidance. Sigma is a vendor-neutral rule format for log detections; SPL (Search Processing Language) is Splunk's query language. Adapt indexes and field names to your stack before deploying, and test every rule in report-only mode first.

Rule 1 · Regular polling of a chat bot API (THR-01 · Critical)

sigma/rule1_bot_api_polling.yml 
title: Regular Polling of Chat Bot API getUpdates Endpoint
id: 3f7a9c1e-8b2d-4e6a-9c41-7d5e0f2a8b31
status: experimental
description: >
  Detects hosts repeatedly requesting a chat bot API tasking endpoint
  (getUpdates-style). Regular small polls are the inbound half of
  bidirectional communication over a web service (MITRE ATT&CK T1102.002).
references:
  - https://attack.mitre.org/techniques/T1102/002/
  - https://attack.mitre.org/techniques/T1102/
author: Detection Engineering (ATT&CK guide T1102.002)
date: 2025-01-20
logsource:
  category: proxy
  product: any
  service: proxy
detection:
  selection_host:
    cs-host|endswith:
      - 'api.telegram.org'
      - 'discord.com'
  selection_poll:
    cs-method:
      - 'GET'
      - 'POST'
    cs-uri-query|contains:
      - 'getUpdates'
      - 'getUpdates?offset='
  condition: selection_host and selection_poll
fields:
  - ClientIP
  - cs-host
  - cs-method
  - cs-uri-query
  - UserAgent
falsepositives:
  - Security research or monitoring tools that query bot APIs from approved hosts
  - An approved integration server legitimately running a chat bot (allowlist it)
level: critical
tags:
  - attack.command_and_control
  - attack.t1102
  - attack.t1102.002
splunk/rule1_bot_api_polling.spl 
index=$PROXY_INDEX$ sourcetype=zscaler:wss:proxy
    url_domain IN ("api.telegram.org","discord.com")
    cs_uri_query="*getUpdates*"
| bin _time span=1h
| stats count AS polls, min(_time) AS first_seen, max(_time) AS last_seen,
        values(user_agent) AS agents, dc(cs_uri_query) AS query_variants
        BY src_ip, url_domain
| where polls >= 20
| eval span_min = round((last_seen - first_seen)/60, 1)
| eval rhythm_s = round(span_min*60/polls, 1)
| eval is_metronome = if(rhythm_s > 0 AND query_variants <= 3, "true", "false")
| where is_metronome = "true"
| table src_ip, url_domain, polls, rhythm_s, agents, first_seen, last_seen
Field mapping
Sigma cs-host → Splunk url_domain; cs-uri-query and cs-method keep their names; ClientIP → src_ip. Replace $PROXY_INDEX$ and sourcetype with your proxy index (examples: zscaler:wss:proxy, bluecoat:proxy:access).
Severity
Critical — an active polling beacon means live interactive C2.
False positives
A sanctioned chat-bot integration server; an API-monitoring service. Both should exist on an allowlist keyed by src_ip.
Tuning
Start with polls >= 20 per hour; raise to 30 if your official bots run long-lived sessions. The metronome test (query_variants <= 3) kills most noise from human browsing.

Good practice — Rule lifecycle

Real-world case study

A reconstructed incident that follows the publicly documented Gamaredon playbook — and a realistic blue-team response to it.

Warning — How to read this case

The attack mechanics are documented. They follow public CERT-UA advisories and vendor reporting on Gamaredon (G0047) activity in 2022–2023: phishing with VBS/HTA droppers, a tool with an embedded Telegram bot token, polling-based tasking, and small-file exfiltration through the bot. The victim, the dates, and the blue-team response are a reconstruction — a composite built for teaching, with fake names and documentation IP ranges. No real victim data is used.

Context

A regional public-sector organization (fictionalized here as "Org-X") runs a mixed Windows estate. Web filtering allows most categories, including chat platforms, because staff use an official chat client. Endpoint agents log process creation and network events. Proxy logs are retained for 90 days; a CASB monitors the Microsoft 365 tenant. The security team is five people. This profile is common — and it is exactly the environment this technique was built for.

Timeline

  1. Day 1 · 09:14 local

    Phishing delivery

    An employee in the planning office receives a themed lure with a password-protected archive containing a VBS script — the documented Gamaredon delivery pattern. The user extracts and runs it. (Documented mechanic; the specific user is a reconstruction.)

  2. Day 1 · 09:22 local

    Dropper fetches and installs

    The VBS dropper downloads a follow-on payload, installs it under a user-profile folder with a fake "updater" name, and registers a scheduled task. The payload carries an embedded Telegram bot token. (Documented mechanics per public reporting.)

  3. Day 1 · 09:41 local

    Beaconing begins

    The implant starts polling the chat bot API about every 30 seconds — small, regular requests. Nothing alerts yet: the domain is known-good and the requests are tiny. (Mechanic documented; timing reconstructed.)

  4. Day 1 · evening

    First tasking round

    The operator posts a task to the bot chat. The next poll delivers it. The implant runs host discovery commands and returns compressed output through the same API. (Documented pattern; command content reconstructed.)

  5. Days 2–5

    Collection and small-file exfiltration

    Each day brings new tasking: directory listings, document searches, screenshots. Collected files are archived and returned via sendDocument-style uploads — small files only, matching the volume profile described in public advisories. The operator also uses the access to spread shortcuts to removable drives, the documented USB-worm behavior of this actor.

  6. Day 6 · 11:03 local

    Detection — the pivot point

    CASB policy review flags a workstation identity uploading 40+ files through an unrecognized automation. In parallel, the weekly hunt finds the 30-second poll metronome in proxy logs (the Rule 1 logic of section 5.5). EDR names the process. (Detection query reconstructed; both data sources are real, common ones.)

  7. Day 6 · 13:30 local

    Containment

    The team isolates the affected workstation, reports the abusive bot to the platform (which disables the token), and adds a scoped block for chat API endpoints for all host subnets except the one legitimate office client. (Response actions reconstructed from standard practice.)

  8. Days 7–9

    Eradication and recovery

    The team removes the scheduled task, deletes the payload, hunts the process hash and token pattern across all hosts (two more machines found via the USB-spread shortcuts), rebuilds them, and resets exposed credentials. Monitoring continues for 30 days. (Reconstructed.)

Attack chain summary

Initial access

Phishing with encrypted archive + VBS dropper (documented actor pattern).

Execution

Dropper fetches payload; scheduled-task persistence; fake-updater name.

C2 — T1102.002

Chat bot polling for tasking in; results and files out through the same API.

Discovery

Host and file-system recon tasks delivered through the channel.

Collection

Documents and screenshots staged in archives before each upload.

Exfiltration + spread

Small files out via the bot; USB-shortcut propagation to other hosts.

Detection point — what actually caught it

No single loud alert: two weak signals met. The CASB saw volume from a workstation identity; the hunt saw rhythm in the proxy. Either alone was ignorable noise. This is normal for T1102.002 — plan for signal fusion, and make the weekly hunt query part of standing work, not an optional extra.

Containment, eradication, recovery — the response playbook

Containment (hours 0–4)

  • Isolate the workstation from the network (keep forensics alive).
  • Report the bot to the platform so the token dies globally.
  • Scoped block: chat API endpoints for affected subnets, with a documented exception list.
  • Preserve proxy, EDR, and CASB evidence before it ages out.

Eradication (days 1–3)

  • Remove scheduled tasks, payloads, and USB-shortcut artifacts.
  • Hunt the process hash, bot token pattern, and registry changes fleet-wide.
  • Reset credentials for accounts that logged into affected hosts.
  • Rebuild rather than clean where practical — faster and provable.

Recovery (days 3–7)

  • Return hosts with fresh images and verified agent coverage.
  • Deploy the section 5.5 rules in report-only, then alerting.
  • Brief the business with a plain-language summary and timeline.
  • Watch re-infection paths for 30 days; this actor returns often.

Impact and consequences

  • Data exposed: internal documents and screenshots (small-file volume).
  • Downtime: three hosts rebuilt; no ransomware or destructive stage observed.
  • Cost: roughly two analyst-weeks plus rebuild effort.
  • Compliance: personal-data exposure triggered an internal review (reconstructed).

Team response and communication

The five-person team split the incident: one analyst owned timeline and evidence, one owned containment actions, one handled platform reporting and the ISP/legal notification, and the lead ran stakeholder updates twice a day. A shared channel (ironically, the same platform family the attacker abused) carried decisions with timestamps. The single most valuable communication decision was a plain-language one-page summary for leadership: what happened, what data left, what we did, what we need. It turned a frightening term into an approved budget for log retention.

Lessons learned

1 · Rhythm beats reputation

The beacon was invisible to threat-intel blocklists and easy to see with interval math. Trust the interval math.

2 · Fusion is the detection

CASB volume + proxy rhythm + EDR naming = case. Single-source rules alone kept missing it.

3 · Scope your blocks

A blanket chat-platform block would have broken business workflows and stalled containment. Scoped rules plus token revocation was faster.

4 · Assume return visits

Actors with rapid, cheap infrastructure re-attack within weeks. The 30-day watch and the new rules were not optional extras.

Mitigation and defense

You cannot block every public web service. You can make abuse loud, slow, and short-lived. The official ATT&CK mitigations for T1102.002 are M1021 - Restrict Web-Based Content (enforce external communication policy through proxies) and M1031 - Network Intrusion Prevention (signature-based blocking at the edge). Controls grouped by function, then a prioritized action table.

Enterprise controls by function

Policy

  • Define which chat/social/file services are approved, for whom, and on which devices.
  • Require a documented allowlist for any automation that talks to chat APIs.
  • Set data-handling rules: what may never transit consumer platforms.

Identity

  • Inventory every OAuth app with chat/storage/mail scopes; re-review quarterly.
  • Block user consent for unvetted third-party apps in your SaaS tenants.
  • Give service accounts named owners; forbid interactive logons for them.

Endpoint

  • Keep EDR on every host with process–network correlation enabled.
  • Deploy Sysmon (or equivalent) with process and network event coverage.
  • Alert on persistence creation and on service accounts running user-profile binaries.

Network

  • Retain proxy logs with bytes and user agents for at least 90 days.
  • Enforce TLS inspection where policy and privacy rules allow, so UA and paths are visible.
  • Prepare scoped block policies per host group — pre-approved, so containment is one click.

Cloud / SaaS

  • Deploy a CASB or use native audit logs; alert on upload volume anomalies.
  • Restrict webhook creation to approved integrations; inventory the rest.
  • Turn on tenant audit export into your SIEM — the platform-side half of the exchange.

Logging

  • Centralize proxy, DNS, firewall, EDR, and SaaS audit in one place with time sync.
  • Normalize field names (the mappings in 5.5) so rules are portable.
  • Test restoration: logs you cannot query in an incident do not exist.

Monitoring

  • Run the 5.5 detections in report-only first; tune with named allowlists.
  • Add a weekly hunt: interval-math beacon query plus new-domain chat lookups.
  • Track detection coverage against ATT&CK IDs so gaps are visible to management.

Backup and response

  • Backups limit damage when this channel escalates to ransomware deployment.
  • Write the runbook: who revokes tokens, who approves scoped blocks, who notifies.
  • Rehearse a chat-C2 scenario once a year (purple-team replay of section 3's lab loop).

Home and small office

No SOC? You are still a target — commodity infostealers love small networks. Do these five things:

  • Keep the operating system and browser updated.
  • Use your router's ability to block or log outbound traffic if it has one, and read the log weekly.
  • Never install "free tools" from chat links — that is the classic delivery path.
  • If a device uploads far more than usual at night, disconnect it from the network.
  • Back up important files to an offline drive.

If you run a small business, add one more: buy an endpoint security product that reports process network activity, and read its weekly report.

Common mistakes and best practices

Fourteen ways blue teams get this detection wrong — each with symptom, root cause, fix, and prevention.

1 · Blocking the whole platform

Symptom: the moment chat domains are blackholed, the business escalates and the block is reverted within a day.
Root cause: treating a shared service as if it were attacker-owned.
Fix: scoped blocks per host group plus token revocation.
Prevention: pre-approved scoped policies (section 7) with named approvers.

2 · Alerting on domain name only

Symptom: thousands of hits, all of them the office chat client.
Root cause: destination-only logic ignores rhythm, direction, and client identity.
Fix: add interval, bytes, and user-agent conditions (rules 1 and 4).
Prevention: every new rule must state its discriminator, not just its domain list.

3 · No request-size logging

Symptom: the exfil rule cannot run because cs_bytes is always empty.
Root cause: proxy deployed with default logging that drops request sizes.
Fix: enable full URI + bytes logging; verify with a test upload.
Prevention: add "bytes present" to the log-quality checklist.

4 · Fixed thresholds everywhere

Symptom: media teams trigger the 1 MB upload rule daily; the rule gets muted.
Root cause: one global threshold for very different job roles.
Fix: per-subnet and per-role baselines; allowlists with owners.
Prevention: thresholds are config with review dates, not constants in code.

5 · Ignoring non-Windows hosts

Symptom: detections exist only for Windows; the Linux CI runner leaks for weeks.
Root cause: log coverage follows the office, not the attack surface.
Fix: extend proxy/CASB coverage to every subnet; add auditd for servers.
Prevention: quarterly coverage review mapped to the 5.3 threat table.

6 · Allowing unowned exceptions

Symptom: an allowlist entry from 2022 keeps the old alert silent; nobody knows why.
Root cause: exceptions without owners or expiry.
Fix: every allowlist row has an owner, reason, and review date.
Prevention: allowlist review is a standing agenda item, not a favor.

7 · Treating SIEM noise as a tuning problem

Symptom: analysts ignore all chat-related alerts; a real beacon drowns.
Root cause: alert fatigue from rules without discriminators (see mistake 2).
Fix: retire or sharpen noisy rules before adding new ones.
Prevention: track the false-positive (FP) rate per rule; a rule above 80% noise goes back to build.

8 · Missing the SaaS half of the exchange

Symptom: proxy shows nothing; meanwhile an OAuth app empties a document library.
Root cause: no tenant audit export; traffic never crossed the corporate proxy.
Fix: stream SaaS audit logs into the SIEM; deploy rule 5.
Prevention: log-source inventory includes every cloud tenant, not just on-prem.

9 · Hunting with indicators only

Symptom: hunts for known-bad hashes find nothing; the channel persists.
Root cause: this technique is behavioral; indicators rotate weekly.
Fix: hunt the shape — intervals, asymmetry, client identity.
Prevention: each hunt session includes one behavior query and one indicator query.

10 · Redacting nothing

Symptom: a real bot token — a live credential — is pasted into a ticket and a vendor email.
Root cause: no handling rule for secrets inside log lines.
Fix: regex-scrub token patterns at ingest and in exports.
Prevention: add token-pattern scrubbing to the pipeline, not to human memory.

11 · No ownership of detection quality

Symptom: rules never tested; a schema change silently broke three of them months ago.
Root cause: detections treated as write-once artifacts.
Fix: assign each rule an owner; add automated test events.
Prevention: quarterly replay of the lab emulator validates every rule end-to-end.

12 · Stopping at the first host

Symptom: one machine rebuilt, case closed — then a second host phones home a week later.
Root cause: scoping by host, not by token, hash, or account.
Fix: pivot on the token pattern, process hash, and persistence paths fleet-wide.
Prevention: the triage flow (section 4) makes the scoping step mandatory.

13 · Measuring success by alerts closed

Symptom: dashboards look green; the beacon ran for six weeks unnoticed between ticket closures.
Root cause: optimizing for ticket throughput instead of detection coverage.
Fix: report coverage (which ATT&CK behaviors you can see) alongside alert metrics.
Prevention: quarterly coverage review mapped to the 5.3 threat table becomes a standing KPI.

14 · Copying vendor rules without field mapping

Symptom: an imported rule runs "successfully" every day and matches nothing.
Root cause: source fields (cs-host, UserAgent) do not exist in your schema.
Fix: run each rule once against a synthetic event (see the lab events in 5.5) before trusting it.
Prevention: adopt the mapping-note habit from 5.5 for every rule you import.

Operating habits that keep you sharp

Daily

  • Review new alerts for chat-API rules.
  • Check CASB upload anomalies queue.
  • Skim top new external destinations for the server subnet.

Weekly

  • Run the interval-math beacon hunt on fresh proxy data.
  • Review OAuth grants consented in the last 7 days.
  • Check the false-positive rate of each 5.5 rule; note drift.

Monthly

  • Replay the lab emulator; confirm every rule still fires.
  • Review allowlist owners and expiry dates.
  • Report detection coverage vs ATT&CK to stakeholders.

Mini glossary

Every special term used on this page, in one place. Terms are explained in plain words the first time they appear in the text too.

C2
Command and Control — the channel an attacker uses to send orders to malware and receive answers.
Beacon
The repeated "any new commands?" check a malware program makes on a schedule.
Dead drop
A public spot (page, post, account) where one side leaves content for the other to pick up.
Exfiltration
Copying data out of a network to a place the attacker controls or can read.
EDR
Endpoint Detection and Response — software that records what processes do on a computer and helps respond.
Sysmon
A free Windows add-on that logs detailed process, network, and file events to the event log.
CASB
Cloud Access Security Broker — a gateway or tool that logs which cloud apps move what data.
SIEM
Security Information and Event Management — the central system that stores and searches security logs.
Sigma
A vendor-neutral, YAML-based rule format that describes a suspicious log pattern.
SPL
Search Processing Language — the query language used in Splunk.
User agent
A text string a client sends that names its software, for example a browser or curl.
OAuth app
A third-party application that a user grants permission to act inside their cloud account.
Webhook
A special URL that accepts posted messages — often abused as a silent upload endpoint.
TLS inspection
Reading encrypted web traffic at a gateway, after decrypting it, where policy allows.
