Overview

What one-way communication is, why attackers pick it, where it sits in an attack, and what you will learn on this page.

Plain definition

One-Way Communication (T1102.003) is a way for malware to receive commands from public web content that the infected machine simply fetches and reads. Commands hide inside video comments, social posts, RSS items, public pages, or images with hidden data. Nothing goes back through that web service.

From the web service's point of view, the infected machine is just one more reader. From the network's point of view, the traffic is a plain HTTP GET request - the same shape as normal browsing. If the attackers need output, it leaves later over a separate channel, or not at all.

Why it matters

The fetches go to big, trusted platforms that most companies allow. The traffic blends in with ordinary reading, and no attacker-owned server appears in the logs.

Attacker trade-off

There is no built-in return path and very little interactivity. The implant can only read what was posted in advance, so operators work in slow, batched steps.

What you will learn

How the loop works, how it looks from both sides, ranked threats, ready-to-adapt Sigma rules and Splunk SPL queries, a case study, and practical mitigations.

Key terms in thirty seconds

C2

Short for command and control: the channel an attacker uses to send orders to malware and, sometimes, receive results.

Implant

The small malware component that lives on a host, waits, fetches tasking, and runs it. Also called an agent.

Beacon

Repeated check-in traffic from an implant to its controller. Here the "beacon" is a repeated read of one public page.

Dead drop resolver

Sibling sub-technique T1102.001: a public page holds a pointer (an address) to the real C2 or payload. Here, the content itself carries the command.

Steganography

Hiding data inside normal-looking media, such as an image whose pixels carry extra bits, or a video whose description carries a code.

EDR

Endpoint detection and response: agent software that records processes, files, and connections on a host and can isolate the host.

Forward proxy

A gateway that records web requests leaving an organization. Proxy logs are a primary detection source for this technique.

Exfiltration

Stealing data out of a network. With T1102.003, exfiltration uses a different channel than the public-content tasking.

RSS

Really Simple Syndication: machine-readable feed format for posts. Feed items are a compact place to hide tasking text.

Animated simulation

A step-by-step walk-through of one full one-way tasking loop, with the defender's view shown for every step. Press Play, or jump to any step with the number buttons.

Your browser does not support canvas. The written story below describes all eight steps in text.

Step 1 of 8 - Attacker posts the command

The attacker writes an encoded command into the comment section of a public video. The comment looks like ordinary text. Inside it hides a marker that the implant will later find.

Defender hint: Nothing runs on your network yet. There is nothing to alert on until the victim fetches the page.

SOC visibility: None

  • Encoded comment is now public on the video page
  • The page URL is fixed; the implant already knows it
  • No traffic from the victim yet

Written story: the same eight steps

  1. Attacker posts the command

    The attacker writes an encoded blob into the comment section of a public video or post. To a human reader it looks like spam or a strange username string. To the implant it is the next instruction set.

    Defender view: Nothing touches your network yet; this step happens entirely on the attacker's side and on the platform.

  2. Implant fetches the page

    The victim malware requests that exact page on a fixed timer. The request is a plain GET, sent with an HTTP library, not a browser.

    Defender view: Proxy logs show one URL fetched again and again from the same host, at a fixed interval, with a non-browser user agent.

  3. Marker found and decoded

    The implant's parser finds the marker inside the page, pulls out the encoded blob, and decodes it into a task - for example a download or a recon command.

    Defender view: No new network event. EDR shows a helper process writing a small temp file right after the fetch.

  4. Malware executes the task

    The implant runs the decoded task. It may download a payload from a separate server or gather host information. Nothing is sent back through the video platform.

    Defender view: Correlate the order of events: page fetch first, then a child process and a connection to a different host. That ordering is the strongest signal.

  5. Next command - the one-way loop

    The attacker posts the next encoded comment. The implant fetches the same URL again and finds new content. This loop can repeat for weeks or months.

    Defender view: Watch the response byte size drift upward while the URL stays identical. Fixed-interval repeats from a server are rare and loud.

  6. Output leaves via a different channel

    If the attackers need results, the implant sends them later to a different server or cloud service. The one-way channel itself stays read-only.

    Defender view: Tasking and exfiltration live on separate paths. Tie them together with host and time context, not by expecting one flow to do both.

  7. SOC reviews proxy history

    An analyst groups proxy records by source host. One host shows the same URL fetched at a steady, metronome-like beat, an odd user agent, and slow byte growth as comments accumulate.

    Defender view: Group by host, not by URL. One host, one URL, many timestamps is the shape of one-way tasking.

  8. Block, isolate, hunt

    The team blocks the content category at the proxy and isolates the host in EDR. Then it hunts the marker string across proxy history to find every other host that fetched the same page.

    Defender view: Blocking the platform alone is not enough. Hunt the exact URL and the marker text to scope the incident.

Red team / hacker perspective

Why attackers choose this pattern and how it is built, at concept level. Everything here is for understanding and defending - the lab examples run only against your own test machines.

Blend with trusted traffic

Fetches go to huge platforms with good reputations. Egress rules usually allow them, and blocking them outright often breaks business needs, so defenders must tune instead of block.

Almost no infrastructure

The attacker registers no C2 domain, rents no server for the channel itself, and can rotate accounts instead of servers. Discarding and replacing an account costs the attacker nothing.

Costs and limits

The attacker accepts a slow, batched workflow: no live shell, no interactive control, and comments can be removed by moderators or other users. Output needs a second channel.

How it is performed (concept level)

  1. Pick a public platform with free content and a machine-readable surface: comments, posts, RSS, or image files.
  2. Define a marker format the implant can find - a fixed prefix, an unusual character run, or a specific account name.
  3. Encode commands (Base64, custom alphabets, or hidden image data) so the text looks harmless.
  4. Implant polls the page on a timer using a standard HTTP library, often with a plain or fake user agent.
  5. A parser extracts and decodes the marker; an executor runs the task or queues a payload download.
  6. If output is needed, a separate module exfiltrates it later through an unrelated service.

Where it applies and prerequisites

Applies well to: long-term implants on servers and workstations, campaigns that must survive IP blocking, and networks where direct C2 domains get cut fast.

Prerequisites:

  • An implant on a host with outbound HTTPS to the chosen platform
  • Knowledge of the platform's page structure (where comments live in the HTML or API response)
  • A marker format plus encode/decode pair shared between operator and implant
  • Patience: tasking is batched, not interactive
Danger - Lab only

The examples below are safe teaching models. They talk to a server on 127.0.0.1 that you run yourself. Never point them at real platforms, and never run them on systems you do not own. Using this pattern against systems without written permission is illegal in most jurisdictions.

lab_client.py - minimal one-way reader (Lab only)
# Lab only. Run against a test VM and a local page server you own.
# 1) Create ./lab/feed.html containing:
#      <!-- TASK: b64:ZWNobyB0YXNr -->
# 2) Start the server:  python3 -m http.server 8000 --directory ./lab
# 3) Run this client on the same lab machine.

import base64
import re
import urllib.request

URL = "http://127.0.0.1:8000/feed.html"   # lab target only - never a real site

def fetch_page(url):
    # A real implant does exactly this shape of request: one GET, no cookies.
    req = urllib.request.Request(url, headers={"User-Agent": "lab-reader/1.0"})
    with urllib.request.urlopen(req, timeout=5) as r:
        return r.read().decode("utf-8", "replace")

def parse_task(html):
    # The parser looks for the marker and decodes the blob after it.
    m = re.search(r"TASK:\s*b64:([A-Za-z0-9+/=]+)", html)
    if not m:
        return None
    return base64.b64decode(m.group(1)).decode("utf-8", "replace")

task = parse_task(fetch_page(URL))
print("decoded task:", task)   # lab: we only print it, we do not run it
Linux lab poller - the pattern defenders see as THR-02 (Lab only)
# Lab only: poll a local test feed every 30 minutes and store it.
# Place in /etc/cron.d/lab-feed on a VM you own, then watch the logs:
*/30 * * * * svc_lab curl -s http://127.0.0.1:8000/feed.html -o /tmp/feed.html

# A malicious variant chains decode and run in one line - that chain
# (curl | base64 -d | sh) is exactly what Sigma rule "Sigma C" in 5.5 finds.

Attacker mistakes defenders should expect

  • Moderator or user deletion: the command comment disappears, and the implant keeps fetching a page whose size stops changing.
  • Fixed intervals: clean timer values (15 or 30 minutes) show up instantly in proxy grouping.
  • Obvious encoding: long Base64 runs in public comments attract researchers, as happened in the LURK case.
  • One URL reused for months: the repeat pattern becomes a stable fingerprint across the whole estate.
  • Parser assumptions: the implant expects an exact page layout; platform changes break the channel and reveal retry storms.

Blue team / SOC perspective

What defenders actually see, which logs carry the evidence, and a short triage flow you can follow on a busy shift.

A repeating rhythm

The clearest tell is time: the same host requests the same public URL at nearly fixed intervals for days. Group proxy records by host and look for the steady, metronome-like beat.

Process context mismatch

Browsers fetch video pages; servers and tools should not. A python-requests, curl, or unknown agent reading one video page from a workstation or server is a strong lead.

Content drift

The page is a command queue, so its size creeps upward as comments or posts are added. The URL stays identical while the byte count slowly changes.

Artifacts this technique leaves behind

  • Proxy rows: identical URL, fixed interval, odd or constant user agent, drifting response size, status 200 every time.
  • DNS records: repeated lookups of one big-platform name at the tasking interval, usually cached well but still visible.
  • EDR process tree: a non-browser process making network calls; after each fetch, a short-lived parser or shell child process.
  • Persistence config: a scheduled task, cron entry, run key, or launch agent that owns the timer.
  • Local traces: small temp files or decoded blobs written after each fetch; sometimes the raw page cached on disk.
  • Network sensors (Zeek/IDS): HTTP records with the same shape as the proxy rows, plus TLS metadata for the platform.

Why it matters

This technique defeats the usual "block the bad domain" reflex, because the domain is one you need for business. Detection therefore shifts from where traffic goes to who sends it, how often, and what runs next. Teams that only watch for known-bad indicators miss this channel entirely.

Fit in the attack chain

In an incident, this pattern usually appears after initial access, during the quiet phase: the implant checks the public page every few minutes while attackers wait. Finding the loop early cuts off tasking before payloads arrive, which keeps the incident small and cheap.

Triage flow

  1. Confirm the pattern: pull 7-30 days of proxy records for the host; verify one URL, fixed intervals, one non-browser agent.
  2. Identify the fetcher: use EDR to find which process owns the connection at those timestamps.
  3. Capture the content: with approval, record the page (and the specific comment or item) as evidence before it changes.
  4. Decode: analyze the marker offline in a lab; identify the task format without executing it.
  5. Check what ran: correlate the fetch times with EID 1 process starts, file writes, and EID 3 connections on the host.
  6. Scope: hunt the exact URL and marker string across the whole proxy history to find every other host that read it.
  7. Contain: block the URL or category, isolate the host in EDR, disable related accounts, and open the incident record with your findings.

5.2 Threat intelligence

Public reporting on this technique is unusually concrete, because researchers could watch the public pages the malware read. Use that reporting to justify detections, then enrich it with your own telemetry.

Collect

Gather from several layers. MITRE ATT&CK describes the behavior. Vendor reports name tools and campaigns. OSINT adds public research and news. Commercial feeds supply indicators. ISACs (sector sharing groups) send peer alerts. Your own proxy and EDR telemetry shows what is live in your estate.

Analyze

Turn reporting into behavior: which platform, which marker format, which interval, which follow-on actions. Build and rank threats (5.3) and write detection logic (5.4) instead of collecting bare indicators.

Apply

Deploy the Sigma rules in 5.5, add hunt queries, brief the SOC with the story (section 2), and revisit after each new public report. Track which rules fired in which incidents to measure value.

ATT&CK detection-strategy mapping

ATT&CK publishes a formal detection strategy for this technique: DET0581 - Detect One-Way Web Service Command Channels. The rules in 5.5 map to it: Sigma A and E cover AN1599 (outbound fetch without return) and AN1600 (curl/wget/custom clients from uncommon accounts, no response parsing); Sigma F covers AN1601 (URLSession-style fetch without response handling on macOS); the ESXi threat (THR-07) and its rule cover AN1602 (ESXi shell or scheduled tasks fetching instructions).

Log sources: forward proxy, Sysmon (EID 1 process creation, EID 3 network connection), Zeek http.log.

Key fields: proxy url, user_agent, bytes, src_host; Sysmon Image, ParentImage, CommandLine, DestinationHostname.

5.5 Sigma rules and Splunk SPL

Sigma is an open, vendor-neutral format for describing log detections in YAML. SPL (Search Processing Language) is the query language of Splunk. Every threat from 5.3 gets detection coverage below: Critical and High threats get a full Sigma rule plus a matching SPL query, and the Medium threats get scoped or correlation rules. Field names in SPL assume common source schemas; each rule includes its mapping assumptions. Replace $INDEX$ and $SOURCETYPE$ style variables if your indexes differ, or keep the concrete defaults shown.

Sigma A - repeated identical content-page GET with a non-browser agent (THR-01, severity High)

sigma/repeated-content-fetch-non-browser.yml
title: Repeated Identical GET to Public Content Page with Non-Browser User Agent
id: 7c3a1f20-5b8e-4c2d-9a41-8f6e2d5b3c10
status: stable
description: A single source host repeatedly requests the exact same public content
  page (video page, social post, RSS item) with a user agent that does not belong
  to a browser. Malware families such as LURK and PIXSTEAM pulled tasking from video
  comment sections this way (T1102.003).
references:
  - https://attack.mitre.org/techniques/T1102/003/
  - https://attack.mitre.org/techniques/T1102/
author: Detection Engineering Team
date: 2025-05-12
logsource:
  category: proxy
  product: any
  service: proxy
detection:
  selection_method:
    cs-method: 'GET'
  selection_uri:
    c-uri|contains:
      - '/watch'
      - '/status/'
      - '/comments'
      - '/feed'
      - '/posts/'
  selection_ua:
    c-useragent|contains:
      - 'python-requests'
      - 'python-urllib'
      - 'curl/'
      - 'Wget/'
      - 'Go-http-client'
      - 'okhttp/'
      - 'Java/'
  filter_browser:
    c-useragent|startswith: 'Mozilla/'
  timeframe: 1h
  condition: selection_method and selection_uri and selection_ua and not filter_browser
    | count() by cs-ip >= 8
fields:
  - cs-ip
  - cs-host
  - c-uri
  - c-useragent
  - sc-status
falsepositives:
  - Uptime checks and monitoring scripts that poll one public page
  - RSS readers and feed-to-mail services on shared infrastructure
  - Vulnerability scanners and research crawlers with custom agents
level: high
tags:
  - attack.command_and_control
  - attack.t1102
  - attack.t1102.003
Splunk SPL - index=proxy sourcetype=zscaler:wss:proxy
index=proxy sourcetype=zscaler:wss:proxy cs_method="GET"
  (c_uri="*watch*" OR c_uri="*/status/*" OR c_uri="*comments*"
   OR c_uri="*feed*" OR c_uri="*posts*")
  (c_useragent="*python-requests*" OR c_useragent="*python-urllib*"
   OR c_useragent="*curl/*" OR c_useragent="*Wget/*"
   OR c_useragent="*Go-http-client*" OR c_useragent="*okhttp/*"
   OR c_useragent="*Java/*")
| bin _time span=1h
| stats count AS fetch_count earliest(_time) AS first latest(_time) AS last
        values(c_useragent) AS agents sum(bytes_out) AS bytes_total
        by _time cs_ip cs_host c_uri
| where fetch_count >= 8
| eval minutes_span = round((last - first) / 60, 1)
| sort - fetch_count

Mapping note: Sigma c-uri → Splunk c_uri, c-useragent → c_useragent, cs-ip → cs_ip, sc-status → resp_code. On a Blue Coat/Cloudflare-style source, use url, useragent, src instead. The Sigma count() by cs-ip aggregation over timeframe: 1h becomes the bin span=1h + stats by _time cs_ip pattern, and the SPL mirrors Sigma's positive scripting-agent list (drop it to widen the net, but expect more noise).

False positives and tuning: add a filter for hosts owned by monitoring tools and for approved feed readers; require cs_host to be on your content-platform list; raise the threshold to 12+ on large estates first, then tune down.

False positives and tuning: engineering machines dominate; scope the rule to non-engineering groups first, or require the destination to resolve to a content-platform category in proxy data.

Case study: LURK (2013-2016)

The best-documented public case of one-way communication over video comments: a criminal group whose droppers pulled commands from YouTube and delivered banking trojans for large-scale online fraud.

Warning - sourcing note

This study is a reconstruction from public reporting: the Kaspersky Securelist technical report of June 2016 and law-enforcement announcements of the coordinated June 2016 arrests (high confidence). Steps where we connect public facts into a narrative are labeled reconstruction. No victim names or sample hashes are reproduced.

Context

Between 2013 and 2016, researchers tracked a criminal group the industry called LURK. Its multi-stage droppers - small first-stage programs - used an unusual C2 design for their time: commands arrived as comments under public YouTube videos. After decoding a comment, the dropper downloaded banking trojans that operators used for large-scale online bank fraud against corporate customers. Kaspersky's June 2016 report documented the comment-based tasking, and in June 2016 coordinated international arrests disrupted the group.

Timeline

~2013 (reconstruction)

Droppers go live

First versions observed with the fetch-comment-decode loop; tasking delivered through video comment sections.

2014 (public reporting)

Fraud at scale

Banking trojan payloads delivered through the channel; operators run large online-bank fraud campaigns.

2015 (reconstruction)

Iteration

Marker formats and modules evolve; investigators across jurisdictions correlate incidents and samples.

June 2016 (public reporting)

Report and arrests

Kaspersky publishes the technical report; coordinated arrests in several countries; supporting infrastructure is taken down.

2017+ (public reporting)

Pattern persists

PIXSTEAM (Trend Micro, February 2017) and later tooling (2022 reporting) reuse video-comment tasking, showing the idea outlived the group.

Attack chain (reconstruction)

  1. Infection: victims receive a dropper through spam or malicious downloads (public reporting points to spam campaigns).
  2. Tasking fetch: the dropper periodically reads a public video page; its parser scans comments for the marker.
  3. Decode: the encoded comment decodes into module instructions and download links.
  4. Payload delivery: banking trojans download from separate hosts and execute - the video platform never carries the payloads.
  5. Fraud: operators use the trojans for online-bank fraud; stolen funds move through money-mule networks (separate channel entirely).
  6. Takedown: arrests in June 2016 and seizure of supporting infrastructure end the campaign.
Detection point

The realistic detection point was (and still is) the repeat-fetch pattern: infected hosts polling one video URL on a timer with non-browser agents. The comment content itself was public - an analyst who found the URL could read the attacker's queue. That is rare in C2 work and makes early detection genuinely achievable.

Containment

Block egress to the platform from server subnets, isolate confirmed hosts in EDR, disable involved accounts, and record the exact URLs and marker strings as evidence.

Eradication

Remove droppers and trojans, reimage compromised machines, reset exposed credentials, and close the persistence (scheduled tasks, autostart entries).

Recovery

Restore systems from known-good state, keep heightened monitoring on the category for weeks, and watch for repeat fetches that indicate a missed implant.

Impact and consequences

The group ran fraud against corporate banking customers for years; press coverage of the 2016 arrests described losses reported by investigators in the hundreds of millions of rubles (treat the figure as reconstruction from press reporting). Beyond money, the case pushed banks and enterprises to monitor egress from servers, not just inbound traffic.

Team response and communication (reconstruction)

A response of this shape joins SOC (proxy and EDR evidence), fraud and risk teams (transaction damage), incident response (scoping and cleanup), and bank contacts (account protection). Clear single-owner communication matters: the public comment queue is time-sensitive evidence, so one team must own capture and sharing.

Lessons learned

Watch servers "reading"

Video pages fetched by servers are absurd on their face. Fixed-interval reads of one URL outrank any single indicator of compromise.

Content is evidence

The command queue is public and editable. Capture pages fast; they change, and deletion destroys both attacker tasking and your proof.

Blocks must fit behavior

Blocking YouTube company-wide fails. Behavioral blocks (category + non-browser agent + server subnet) keep the business working and the implant starved.

Intel names patterns

The LURK report gave defenders a reusable shape. Every later case (PIXSTEAM, 2022 tooling) matches it, which is why rules in 5.5 are pattern-based, not indicator-based.

Mitigation and defense

You cannot block reading the internet. You can decide who reads, from where, with what, and notice when a machine pretends to be a reader. ATT&CK lists two official mitigations for this technique: M1021 - Restrict Web-Based Content (web proxies enforcing external communication policy) and M1031 - Network Intrusion Prevention (signature-based blocking at the network edge) — the Network and Cloud control groups below implement both.

Policy

  • Document an egress policy that names content platforms and who may reach them.
  • Require server subnets to route through proxy categories with no streaming/social access.
  • Make exception records expire; dead exceptions become attacker cover.

Identity

  • Least privilege for service accounts used by cron and scheduled tasks.
  • MFA (multi-factor authentication) and conditional access so a stolen account cannot silently join devices or read mail APIs.
  • Name owners for every non-interactive identity that fetches web content.

Endpoint

  • EDR on all hosts with process and network telemetry (Sysmon where supported).
  • Application control that blocks user-writable-path executables spawning shells.
  • Block certutil decode and curl | sh chains by policy on standard hosts.

Network

  • Egress filtering per subnet class (servers, workstations, guest).
  • TLS inspection where lawful, to keep URL and user-agent visibility.
  • Retain proxy and DNS logs for at least 90 days to see slow loops.

Cloud

  • Default-deny egress for functions and CI workers; allowlist registries only.
  • CASB to separate human from scripted access to SaaS.
  • No secrets in public-config patterns; use managed configuration stores.

Logging

  • Centralize proxy, DNS, EDR, and Linux audit into one searchable place.
  • Keep command lines and user agents, not just IPs and counts.
  • Version your detection rules and test them against replayed logs.

Monitoring

  • Run the 5.5 rules on schedule with a tuning backlog.
  • Weekly review of repeat-fetch alerts by host group.
  • Hunt the marker/URL strings after every case to scope the fleet.

Backup and response

  • Immutable backups tested quarterly (ransomware often follows C2).
  • EDR isolation drill twice a year including Linux servers.
  • A one-page runbook for "repeat fetch" incidents: who blocks, who isolates, who captures content.

Home and small-office advice

Without a SOC, do four things:

  • Keep your router firmware and security software updated, and let updates run automatically so implants cannot pose as patch tools.
  • Use your security suite's "suspicious process made a web request" notices, and read them.
  • Be suspicious of free tools that ask to run installers you downloaded as scripts.
  • If a device behaves oddly and constantly "loads" something, disconnect it and reinstall from known-good media.

Common mistakes and best practices

Twelve concrete mistakes blue teams make with this technique, each with the symptom, the root cause, the fix, and the prevention. Then the daily, weekly, and monthly habits that keep it from coming back.

1. Trusting category allowlists blindly

Symptom: implant traffic never alerts because the platform domain is on the "trusted" list.
Root cause: category trust applied without process context.
Fix: add non-browser-agent and server-subnet conditions to trusted-category rules.
Prevention: review category exceptions quarterly with data on who actually fetches.

2. Alerting on every repeated GET

Symptom: hundreds of alerts a day about polling apps and dashboards; analysts mute the rule.
Root cause: no interval, agent, or asset-class scoping.
Fix: require fixed intervals plus non-browser agents plus content-page URL shapes.
Prevention: measure false positives per rule and tune on a schedule.

3. Proxy-only detection

Symptom: alerts name an IP but nobody can say which process fetched.
Root cause: no endpoint telemetry joined to network records.
Fix: deploy Sysmon/EDR process logging and join on host + time (as in 5.4).
Prevention: coverage report per subnet as a standing metric.

4. Ignoring byte-size drift

Symptom: the repeat pattern is flagged as a "cache check" and closed.
Root cause: analysts treat identical URLs as identical responses.
Fix: chart response bytes over time; drift on a fixed URL is a queue filling up.
Prevention: add bytes_delta to the repeat-fetch panel.

5. Business-hours filters

Symptom: the 02:15 fetches are filtered out as noise.
Root cause: "working hours" logic tuned for human users.
Fix: exempt only human-use asset classes from night detection, never servers.
Prevention: review filters when asset classes change.

6. Short log retention

Symptom: the loop ran for months but only three days of proxy data exist.
Root cause: retention set by storage comfort, not threat tempo.
Fix: 90 days minimum for proxy/DNS, longer for aggregated indexes.
Prevention: annual retention audit tied to the threat model.

7. Alert fatigue from broad agent rules

Symptom: "any non-Mozilla agent" fires on every SaaS connector.
Root cause: agent matching without URL or asset context.
Fix: scope agent rules to content-page URL shapes (as Sigma A does).
Prevention: keep an approved-agents inventory and diff it monthly.

8. Ownership gaps on exceptions

Symptom: nobody knows why a server subnet can reach a streaming platform.
Root cause: exceptions without expiry or owner.
Fix: add owner + expiry to every exception and re-approve on expiry.
Prevention: exception dashboard reviewed in change meetings.

9. Assuming Linux servers do not browse

Symptom: cron-based fetchers (THR-02) run for months unnoticed.
Root cause: "browsing" detections scoped to workstations only.
Fix: deploy rule C and audit cron/Scheduled-task equivalents on Linux.
Prevention: baseline expected cron per server and alert on new entries.

10. Never capturing the content

Symptom: by the time the team looks, the comment is deleted and the task is unprovable.
Root cause: no capture step in the triage flow.
Fix: make "record the page and the marker" step 3 of the triage flow (section 4).
Prevention: keep a capture tool and approval path ready before the first case.

11. Weak rule testing

Symptom: a Sigma rule deploys and never fires, even in tests.
Root cause: field names in the rule do not match the real schema.
Fix: replay real sample logs through each rule before enabling (mapping notes in 5.5).
Prevention: CI job that validates every rule against a fixture set on change.

12. Treating exfil and tasking as one flow

Symptom: analysts look for upload traffic on the video URL and find nothing, then close the case.
Root cause: assumption that C2 and output share a channel.
Fix: hunt output on separate destinations using host + time correlation (step 6 of the story).
Prevention: document the one-way property in the runbook.

Daily habits

  • Review new repeat-fetch alerts; assign an owner to each.
  • Check EDR for shells spawned by fetch utilities (Sigma B hits).
  • Skim top talkers to content platforms from server subnets.

Weekly habits

  • Run the user-agent frequency report; diff against the approved list.
  • Chart byte drift for the top 20 repeated URLs.
  • Dry-run new Sigma rules against the last week of logs.

Monthly habits

  • Re-approve expiring egress exceptions; kill dead ones.
  • Validate log retention and source coverage per subnet.
  • Replay the full rule set against a golden fixture; record results.
