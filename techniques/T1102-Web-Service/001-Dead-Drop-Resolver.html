Dead Drop Resolver T1102.001

A dead drop resolver is a trick that hides a C2 server. C2 (command and control) is the channel an attacker uses to steer malware. With this trick, the malware remembers only one public web address, such as a paste site. The real C2 address waits there inside an encoded blob. The malware fetches it, decodes it, and calls home. When a C2 server gets blocked, the attacker posts a new drop. No malware update is needed.

Overview

What a dead drop resolver is, why attackers use it, where it sits in the attack chain, and what this page teaches you.

Plain-language definition

In classic spy tradecraft, a dead drop is a public hiding spot for a message. Two people never meet. One person leaves the message in the spot. The other person collects it later.

Malware borrows the same idea. The malware knows only one thing: the address of a public web page. That page can be a paste site, a GitHub gist, a shared cloud-storage file, or an image host. The page holds a small encoded or encrypted blob (a "blob" is just a chunk of data). The blob hides the real C2 address: an IP, a domain, a URL, or a full config block.

The lookup pattern is the key. The malware polls (checks on a schedule) the public page, decodes the blob, and then starts or continues command and control on a different channel. The real C2 server never appears inside the binary, in early DNS traffic, or in the first connections. Attackers rotate burned infrastructure by posting a new drop, so the malware never needs an update.

Note

The dead drop itself is usually a legitimate, well-reputed service. Blocking the whole service often breaks real work (developers use these sites too). Section 7 shows safer ways to respond.

Why it matters

Resilience

When defenders block a C2 server, the attacker posts a new dead drop. The malware finds the new address on its next poll. Nothing on the victim host changes.

Stealth

The binary never contains the real C2 address. Scan pipelines that unpack malware see only a public URL on a trusted platform. The hidden server stays out of blocklists until it is used.

Blending in

Traffic to popular paste, gist, or file-host services looks like ordinary web and developer use. It hides among office traffic, CI jobs, and script downloads.

Where it sits in the attack chain

T1102.001 belongs to the Command and Control tactic. It usually appears after initial access, when an implant already runs on the host. The table shows the usual order.

Written story

The written story below covers the same eight steps as the animation. It is also the text alternative for the canvas.

  1. Stage the hidden server

    The attacker rents a small server and installs C2 software. The victim does not talk to it yet, and the address does not appear in the malware.

    Defender view: Nothing to detect. This happens outside your network, before your logs show anything.

  2. Post the dead drop

    The attacker encodes the C2 address into a blob and posts it to a public paste site or file host. The public raw URL becomes the dead drop that the malware will visit.

    Defender view: Nothing in your logs yet. Only the attacker and the public service are involved.

  3. Poll on a schedule

    The infected host fetches the raw URL on a fixed schedule, for example every 30 minutes. The request looks like ordinary web traffic from a normal client.

    Defender view: The proxy shows periodic GETs to a paste or file host. A small upload is followed by a larger download, and the process is often not a browser.

  4. Decode the blob

    The malware decodes the blob in memory. The hidden C2 domain or IP appears. Everything happens inside the victim host, so there is no network record of the decode itself.

    Defender view: Hard to see directly. EDR may show a short burst of activity in the loader process right before the next connection.

  5. Call home to the real C2

    The malware opens an encrypted connection to the resolved server. The operator now has a live session and can send commands.

    Defender view: This is the clearest evidence: a fresh outbound connection to a new IP or domain, seconds after the paste fetch.

  6. Burn and rotate

    Defenders block the C2 server. The attacker notices, posts a new paste with a fresh C2 address, and lets the old server die. The malware never needed an update.

    Defender view: Watch the paste host: same host, new paste ID. The URL changed but the pattern did not.

  7. Re-resolve and switch

    On the next poll the malware decodes the new blob and switches to the fresh server. The channel moves with no user-visible event. This is why dead drops are so resilient.

    Defender view: The pattern repeats with a different destination IP. Correlation across the two events is your strongest signal.

  8. SOC review, block, and hunt

    The SOC correlates proxy and firewall data: a paste fetch followed by a new-IP connection within a minute. The analyst blocks the C2, deploys a detection, and hunts for other hosts that did the same.

    Defender view: Turn the pattern into a durable rule (Section 5.5), then hunt estate-wide for the same paste IDs and fetch-then-connect timing.

3

Red team perspective

This section explains how attackers use dead drop resolvers and why. The goal is defensive understanding. Everything here stays at concept level, and all hands-on examples run in an isolated lab only.

Danger

This page is educational and defensive. Do not point any tooling at real public services or real networks. Lab exercises use documentation IP ranges (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24) and lab-only hostnames. Never test against systems you do not own.

When and why attackers use it

Burn-proof infrastructure

Public C2 addresses get blocked fast. With a dead drop, blocking a server costs the attacker one paste, not a malware update. The fleet of implants recovers by itself on the next poll.

Scan-resistant staging

Sandbox and static scanners look for suspicious domains. A blob on a popular paste site does not trigger those checks, and the payload can be encrypted so content scanners see noise.

Separation of concerns

The loader needs only one stable URL. Everything else (real C2, backup C2, campaign settings) lives in the drop. One blob can re-task thousands of implants at once.

Low cost

Paste sites, gists, and free cloud storage cost nothing and stay reachable from most networks. No custom hosting is needed for the lookup step.

How it is performed (concept level)

The workflow is simple, which is why it is common across many loader families:

  1. Prepare the real C2 on infrastructure the attacker controls, and keep it hidden from public scans (no scanning surface, no certificates that hint at role).
  2. Encode the config. The C2 address (IP, domain, or URL) is wrapped in base64, XOR, or stronger encryption. Encoding hides it from casual readers and scanners.
  3. Publish the blob to a public service and record the raw URL that returns the plain content.
  4. Embed the raw URL as the only C2 knowledge inside the implant.
  5. Poll on a schedule with jitter, so beaconing is not perfectly regular.
  6. Decode and connect. The implant resolves the drop and opens the real C2 channel.
  7. Rotate when needed. A burned C2 is replaced by posting a new drop; old implants switch on their next check.

Prerequisites

For the implant

  • One hardcoded public raw URL (the resolver address).
  • A decoder for the blob (base64, XOR key, or a crypto routine).
  • A poll timer, ideally with jitter.
  • Permission to open outbound HTTPS from the victim.

For the operator

  • A controlled account or anonymous access on the drop service.
  • Real C2 infrastructure kept hidden until a poll happens.
  • Discipline to keep blobs small and identical across victims (or unique per campaign).
  • A rotation plan: who posts the new drop when a C2 burns.

Lab only: build and decode a dead drop

This exercise shows the mechanics with documentation IPs. It never touches a real public service: the "drop" is a plain file on a lab web server you own.

Lab only · encode a fake config (Python, isolated lab)
# Lab only: run in an isolated lab network. Documentation IPs only.
import base64

# The real "C2" lives on 203.0.113.50 (TEST-NET-3, safe to write down)
config = b"c2=203.0.113.50:443"
blob = base64.b64encode(config).decode()
print("paste body:", blob)          # YzI9MjAzLjAuMTEzLjUwOjQ0Mw==

# The implant side: fetch http://192.0.2.10:8080/raw/aa11.txt from your
# own lab web server, then decode the body back into the config line.
raw = "YzI9MjAzLjAuMTEzLjUwOjQ0Mw=="
print("resolved:", base64.b64decode(raw).decode())
Lab only · fetch the drop with curl (lab web server, no internet)
# Lab only: 192.0.2.10 is a lab host on TEST-NET-1. Never a real service.
curl -sv http://192.0.2.10:8080/raw/aa11.txt
# Watch your lab proxy/pcap: one small GET, one larger response body.
# Then run the decode snippet above to "resolve" the fake C2.

Detection exercise for the lab: search your lab proxy log for the GET to /raw/aa11.txt and your firewall log for the later connection to 203.0.113.50. Note the time gap. That gap is exactly what Section 5.5 turns into a detection.

Common variations and attacker mistakes

Variations defenders see

  • Layered drops: the first blob points to a second drop.
  • Per-victim drops: each implant ID maps to its own paste ID.
  • Image steganography: config bytes hidden inside a PNG.
  • Cloud-native drops: Drive or storage links shared from throwaway accounts.

Mistakes that expose operators

  • Fixed poll times with no jitter, so beacons align to the clock.
  • Reusing one paste ID across many victims and campaigns.
  • Unencoded or weakly encoded blobs that analysts can read.
  • Fetching the drop from the same process that talks to the C2, which makes correlation trivial.

Blue team and SOC perspective

How defenders see a dead drop resolver, which artifacts it leaves, where to look, and a short triage flow you can follow on a normal shift.

How defenders see it

A dead drop resolver hides the C2 server, not the lookup. The lookup is visible: some process on your network must ask a public service for a small file, and then talk to a new server. Your best evidence is the pairing of two events. First, a fetch of a raw paste, gist, or file. Second, a connection within seconds or minutes to a destination the host never used before.

Artifacts it leaves

Proxy artifacts

  • Periodic GETs to raw endpoints (/raw/, /downloads/).
  • Non-browser user agent (python-requests, curl, Go-http-client).
  • Small request, larger response body.

Endpoint artifacts

  • EDR process–network pair: unusual image fetching a paste host.
  • Sysmon Event ID 3 to gist or paste domains.
  • Short CPU/memory burst in a loader process (the decode).

Network artifacts

  • DNS queries for paste/gist/file hosts at beacon time.
  • TLS session to a fresh IP right after the fetch.
  • Repeat of the whole pattern with a new destination after rotation.

Why it matters and how it fits the chain

Catching the resolver before the real C2 session starts stops the attacker at the cheapest point. The implant is on the host, but the operator has no channel yet. One blocked rotation breaks the campaign's whole fleet, because every implant must use a public drop to find its next server. Later steps (tasking, tool transfer, exfiltration) all depend on that channel.

Triage flow

  1. Confirm the pair. Find the paste fetch in the proxy log, then look for a new outbound connection from the same host within the next 60 to 120 seconds.
  2. Identify the process. Open the EDR record: image path, parent, signature, user. A browser is fine; a loader in %TEMP% is not.
  3. Check the pattern. Look for repeats: same host, same paste path, every 15 to 60 minutes. Rotation shows as the same pattern with a new paste ID or new destination IP.
  4. Assess the destination. Is the resolved IP or domain new to your estate? Check threat intel and your own history (first seen date).
  5. Contain. Block the resolved C2 IP/domain at the firewall, and isolate the host if EDR shows post-C2 activity.
  6. Hunt. Search the estate for the same paste IDs and for fetch-then-connect pairs on other hosts.
  7. Report and tune. Record the case, add the paste host to monitoring (not blanket blocking), and refine the Section 5.5 detections.
Warning

Do not blanket-block popular paste, gist, or raw-code hosts. Developers, IT automation, and monitoring use them daily. Block the resolved C2 destination and tune detections by process and pattern instead.

5.2 Threat intelligence

Dead drop resolution is a well-documented pattern. Build your picture from several source types, then turn it into detections and hunts.

MITRE ATT&CK

The T1102.001 page and its software and group links are the neutral baseline for scope and examples.

Vendor reporting

Security vendor blogs describe how named tools resolve C2 from public pages. Note tool names, services abused, and dates.

OSINT

Malware config repositories, sandbox write-ups, and researcher threads reveal which paste IDs and hosts are live this month.

Commercial feeds

Structured feeds of C2 IPs and fresh domains help you verify the "resolved" destination side of the pair.

ISACs

ISACs (information sharing and analysis centers — sector sharing groups) pass along campaign-level indicators, such as Drive files used as drops in your sector.

Internal telemetry

Your own proxy history is a feed: rare raw-endpoint fetches in your logs are campaign leads before any vendor writes about them.

Method: collect, analyze, apply

  1. Collect the sources above on a schedule, and store examples (tool names, service patterns, paste hosts) in one place.
  2. Analyze for behavior, not single values: "loader fetches raw paste, then connects within 60 seconds" is portable knowledge; one paste ID is not.
  3. Apply by writing or tuning the Section 5.5 rules, adding hosts to watchlists, and briefing the SOC on the pattern.

Rule 1 · Non-browser fetch of a paste or gist raw endpoint High THR-01 / THR-02

description: >

Splunk SPL · proxy paste fetch summary
index=$PROXY_INDEX$ sourcetype=zscaler:wss:proxy cs_method="GET"
    cs_host IN ("pastebin.com","gist.githubusercontent.com","pastes.io","hastebin.com")
    cs_uri IN ("*/raw/*","*/downloads/*")
| search NOT match(cs_useragent, "(?i)^Mozilla/5\.0 \((Windows|Macintosh|X11)")

  • Severity: High on its own; escalate to Critical when paired with Rule 3's timing correlation.

Rule 3 · Fetch-then-connect timing correlation Critical THR-01

Sigma · network · paste fetch followed by new destination
title: Paste Raw Fetch of Dead Drop Resolver (network)
id: 9e4a7c3f-2b8d-4f16-a5d9-1c6b3e8f2a74
status: stable
description: >
  Network-level first half of the dead drop pattern (MITRE ATT&CK T1102.001):
  an HTTP fetch of a paste or gist raw endpoint by a non-browser client.
  A single-log rule cannot prove the follow-on connection; pair it with the
  Splunk SPL below, which correlates the fetch with the next TLS session.
references:
  - https://attack.mitre.org/techniques/T1102/001/
author: Detection Engineering Team
date: 2025-02-11
logsource:
  category: network
  product: suricata
  service: eve
detection:
  selection_fetch:
    event_type: 'http'
    http.hostname|endswith:
      - 'pastebin.com'
      - 'gist.githubusercontent.com'
    http.url|contains: '/raw/'
  condition: selection_fetch
fields:
  - src_ip
  - dest_ip
  - http.hostname
  - http.url
  - http.status
falsepositives:
  - Vulnerability scanners fetching benign URLs from admin subnets
  - Approved scripts that read public pastes on a schedule
level: critical
tags:
  - attack.command_and_control
  - attack.t1102
  - attack.t1102.001
Splunk SPL · the full timing pair across proxy and firewall
index=$PROXY_INDEX$ sourcetype=zscaler:wss:proxy
    cs_host IN ("pastebin.com","gist.githubusercontent.com") cs_method="GET"
| fields _time src_ip user cs_host cs_uri
| eval stage="paste_fetch"
| append
    [ search index=$FW_INDEX$ sourcetype=pan:traffic action="allowed"
      | fields _time src_ip dest_ip dest_port
      | eval stage="outbound" ]
| sort 0 src_ip _time
| streamstats window=1 current=f last(stage) AS prev_stage last(_time) AS prev_time BY src_ip
| where stage="outbound" AND prev_stage="paste_fetch" AND (_time - prev_time) <= 120
| stats count AS fetch_then_connect
        min(_time) AS first_pair
        max(_time) AS last_pair
        values(dest_ip) AS c2_candidates
    BY src_ip user
| where fetch_then_connect >= 2
Note

Sigma to Splunk mapping: Suricata EVE http.hostname/http.url correspond to proxy cs_host/cs_uri; the SPL version carries the fetch-then-connect correlation that a single-log Sigma rule cannot express. Assumptions: src_ip is the same internal address in both sources, both indexes are time-synced (NTP — network time service), and $FW_INDEX$ holds traffic logs with dest_ip/dest_port.

  • False positives: browsers prefetch and redirect chains can connect soon after a paste visit; SaaS sync clients poll often.
  • Tuning: exclude browser UAs on the fetch leg, require the destination to be new to the estate (compare with a 30-day first-seen lookup), and raise the threshold to >= 2 pairs before paging.
  • Severity: Critical — this is the strongest confirmable dead drop signal you can own.

| sort - later_dests

Sigma to Splunk mapping: Suricata EVE tls.sni maps to Sigma tls.sni directly. The SPL joins 24 hours of TLS sessions per source to show paste sightings plus how many different destinations followed — the network-only stand-in for the fetch-then-connect pair. Tune the follow-up threshold to your baseline.

  • False positives: analysts and sandboxes in the blind segment; printers or appliances that fetch public content.
  • Tuning: treat every hit as a hunt lead, not a page. Feed the source list to asset owners: the fastest fix is restoring endpoint telemetry to the segment.
  • Severity: Medium — visibility is limited by design here; the risk is the blind spot, not the single event.

Case study: Golden Chickenn (2022)

Public industry reporting in 2022 described Golden Chickenn, tooling linked to Lazarus-group activity (ATT&CK G0032), used against South Korean organizations in the cryptocurrency and defense sectors. The tool resolved its C2 from a Google Drive file and took operator tasking from YouTube comments. Facts here come from that reporting; response phases are marked as reconstruction. For an ATT&CK-verified dead drop case, read the 3CX Supply Chain Attack (C0057), where the trojanized installer fetched attacker-staged content from GitHub — the same pattern at supply-chain scale.

Why this case teaches T1102.001

The malware carried no C2 address. It read its resolver (a Drive file), decoded it, and only then met the operator's server. When infrastructure burned, a new file replaced the old drop — no malware update, no new binary hash. The same resilience logic applies to the paste-site loaders in Section 5, just on a cloud-storage platform.

Timeline

  1. Phase 1 · Day 0 — the lure

    Employees receive a lure that leads to a malicious installer or document. Phishing and fake-job lures were the era's norm for this actor cluster. Sequence per public reporting.

  2. Phase 2 · Day 0 — loader execution

    The loader runs on the victim host and stays quiet. It contains the address of a Drive file and nothing else about the C2. Reconstruction.

  3. Phase 3 · Day 0–1 — dead drop resolution

    The implant downloads the Drive file and decodes the next-stage C2 configuration from it. Network-wise this looks like an ordinary download from Google storage. Behavior per public reporting.

  4. Phase 4 · Day 1+ — C2 and tasking

    The implant connects to the resolved C2 server. Operator tasking arrives separately through comments posted on a YouTube channel — a one-way channel the malware reads. Cross-reference T1102.003.

  5. Phase 5 · as needed — infrastructure rotation

    When a C2 address is blocked or abandoned, the actor posts a fresh configuration to a new Drive file. Implants pick it up on their next read. Reconstruction of the rotation mechanism.

  6. Phase 6 · reconstruction — detection and response

    Response steps below describe what a well-covered team would do, not a specific documented incident timeline. Labeled reconstruction.

Note · Detection point

The best detection point is the pair: a Drive/storage download from a service account or unapproved OAuth client, followed by a TLS session to a previously unseen IP within minutes. On hosts, the process that performed the download is the anchor. Content inspection of the Drive file is rarely available; the pairing is.

Response playbook (reconstruction)

Containment

  • Isolate affected hosts from the network, preserving memory where possible.
  • Block the resolved C2 IP/domain at the egress firewall.
  • Suspend the OAuth client and account that touched the dead-drop file; revoke its tokens.

Eradication

  • Remove the loader and implant using EDR; delete persistence (run keys, scheduled tasks, launch agents).
  • Reset credentials exposed on or reachable from the hosts, prioritizing privileged accounts.

Recovery

  • Restore systems from known-good sources and re-enable accounts with new secrets.
  • Keep the resolved C2 and the dead-drop file IDs on a watchlist for re-activation.
  • Deploy the Section 5.5 detections before reopening the segment.

Impact and consequences

  • Risk of credential and source-code theft in cryptocurrency and defense targets.
  • Service disruption during isolation and rebuilds.
  • Attacker cost is low: one new Drive file defeats a block of the old C2.

Team response and communication

For an incident like this, the SOC lead names a single incident commander. The endpoint team owns isolation, the network team owns blocks and monitoring, the identity team owns OAuth and account actions, and legal plus communications handle notification duties and stakeholder updates on a fixed schedule (for example every 4 to 8 hours). Sharing the dead-drop file IDs and C2 addresses with your ISAC helps other teams see the rotation early. Team structure described generically; not part of the public reporting.

Lessons learned

Watch the resolver, not just the server

Blocklists of C2 IPs always run late. The download that resolves C2 happens first, from a platform you already trust — log it and alert on odd clients.

Cloud audit logs are C2 logs

Drive and storage audit events caught the staging and the resolution here. Without them, only the final connection was visible.

Correlation beats content

The config was encrypted, the SNI looked boring, and the file name was boring. The timing pair — fetch then fresh IP — carried the detection.

Plan for rotation

Assume the actor posts a new drop after your block. Hunt for the pattern again on the next beacon cycle, and keep watching the paste or Drive host.

Mitigation and defense

Controls grouped by area, plus advice for small offices and a prioritized action table. ATT&CK lists two mitigations for T1102.001: M1021 - Restrict Web-Based Content (use web proxies to enforce external communication policy) and M1031 - Network Intrusion Prevention (signature-based blocking at the network edge). The defense is layered: reduce permission to fetch, watch the pattern, and respond fast.

Policy

  • Write an acceptable-use rule for paste, gist, and raw-code hosts by user group.
  • Require risk approval before any service account can reach general internet sites.
  • Add "dead drop resolution" to the C2 section of your detection strategy document.

Identity

  • Least privilege and short-lived credentials for service accounts.
  • Govern OAuth (open standard for token-based app authorization) clients: approved list, monthly review, instant revoke path.
  • Block legacy authentication; require MFA (multi-factor authentication) to limit account misuse for staging.

Endpoint

  • Run EDR on all platforms, including Linux servers and macOS.
  • Enable Sysmon (or equivalent) with network-connection logging.
  • Block execution from user-writable folders where policy allows; sign and pin approved tools.

Network

  • Egress filtering: servers and IoT get explicit allowlists, not open internet.
  • Filter DNS and monitor for raw-endpoint hostnames at odd hours.
  • Use TLS inspection where law and policy allow, at least on server segments.

Cloud / SaaS

  • Turn on Drive/storage audit logs and stream them to the SIEM.
  • Restrict anonymous sharing links; alert on public files created by service accounts.
  • Deploy CASB policies for unsanctioned storage apps.

Logging

  • Centralize proxy, DNS, firewall, EDR, and SaaS audit logs; keep NTP time sync.
  • Retain at least 90 days of searchable events for correlation.
  • Record process context (EDR/Sysmon) next to network events wherever possible.

Monitoring

  • Run the Section 5.5 detections and the timing-correlation search daily.
  • Watch first-seen destinations per host; new IPs right after paste fetches are your best lead.
  • Track intel on paste hosts and drive-file dead drops used in your sector.

Backup and response

  • Keep offline, tested backups — C2 often ends in ransomware or theft.
  • Maintain an isolation runbook and a block-and-hunt playbook for C2 patterns.
  • Rehearse a rotation scenario: you block one server, the malware moves — what next?
Good practice

Blocking the drop service (pastebin, gist, Drive) feels effective and hurts your own developers. Prefer process-aware detections plus egress rules for servers, and reserve domain blocks for the resolved C2, where false-positive cost is low.

Home and small-office advice

Without a SOC, you can still cut most of this risk. Turn on your router's DNS filtering or a resolver with malware blocking. Keep operating systems and browsers updated. Avoid running unknown installers. Use your device's built-in protection. Back up important files offline. If a device beacons to a paste site, you will not see it in a log — so prevention and updates matter most.

Common mistakes and best practices

Twelve concrete blue-team mistakes seen around dead drop detections, each with symptom, root cause, fix, and prevention — plus habit lists that keep the program healthy.

1 · Every paste fetch is treated as an incident

Symptom
Analysts close dozens of paste-site tickets a week as benign.
Root cause
No process context; the rule fires on the domain alone.
Fix
Enrich with EDR process data before alerting; alert only on non-browser images.
Prevention
Write network rules that require host context when a data source exists.

2 · Alert fatigue from static domains

Symptom
The same user triggers daily alerts for reading one paste link.
Root cause
Per-event alerting with no aggregation.
Fix
Aggregate per user and host per day; alert on new paste IDs or new destinations instead.
Prevention
Baseline first, alert on change, not on presence.

3 · No logs from servers

Symptom
The pattern is visible on laptops but servers are dark.
Root cause
EDR/Sysmon deployed only to Windows workstations.
Fix
Roll out EDR and network logging to server and macOS fleets.
Prevention
Track coverage as a KPI (a measured target); new server builds get the agent by default.

4 · SaaS audit logs ignored

Symptom
Cloud-file dead drops are invisible; only the final C2 shows.
Root cause
Drive/storage audit streams never configured.
Fix
Enable audit export and onboard it as a data source.
Prevention
Data source onboarding checklist includes every SaaS in use.

5 · Blocklist-only defense

Symptom
Team blocks known paste IDs and declares victory.
Root cause
IOC thinking; the pattern regenerates IDs instantly.
Fix
Detect the fetch-then-connect pattern; block resolved C2s.
Prevention
Every IOC case must also produce a behavior rule.

6 · Timing correlation never built

Symptom
Proxy team and firewall team each see half the story.
Root cause
No cross-source search; clocks or schemas differ.
Fix
Build Rule 3 and normalize NTP and src_ip across sources.
Prevention
Correlation use cases reviewed per technique, not per tool.

7 · Over-tuned user agents

Symptom
The rule is silent; malware passes with a fake browser UA.
Root cause
Allowlisting everything starting with Mozilla/5.0.
Fix
Combine UA with process context and first-seen destination checks.
Prevention
Never rely on one spoofable field as the only filter.

8 · No owner for the use case

Symptom
Rules decay; nobody answers when they misfire.
Root cause
Detections deployed without named ownership.
Fix
Assign an owner and review cadence for each rule family.
Prevention
Detection catalog with owner, last-tested date, and runbook link.

9 · Chasing single IOCs

Symptom
Searches for one paste ID find one host; the rest keep beaconing.
Root cause
Writing reports before writing logic.
Fix
Pivot from the ID to the pattern, then hunt estate-wide.
Prevention
Intel intake template requires a behavior column.

10 · Windows-only assumptions

Symptom
Linux droppers (THR-03) run for months unnoticed.
Root cause
Detections written only for Windows event channels.
Fix
Port rules to Linux telemetry; add macOS note-service checks.
Prevention
Every new rule lists its platform coverage explicitly.

11 · Stopping at the first block

Symptom
Host reconnects a day later to a new C2; case closed too early.
Root cause
Rotation not modeled in response.
Fix
Keep the case open through at least two beacon cycles; hunt the new drop.
Prevention
C2 playbook includes a rotation watch step.

12 · Weak tuning feedback loop

Symptom
Same false positives return every month.
Root cause
Triage outcomes never flow back into rule edits.
Fix
Link tickets to rules; tune from closed-case data monthly.
Prevention
Metrics: false positive rate and time-to-tune per rule.

Habit lists

Daily

  • Review Rule 2 and Rule 3 alerts with process context attached.
  • Check new first-seen destinations on server segments.
  • Confirm log pipelines are green (proxy, DNS, EDR, SaaS).

Weekly

  • Hunt for fetch-then-connect pairs with relaxed thresholds.
  • Review new OAuth clients and storage shares from service accounts.
  • Skim vendor and OSINT reporting for new dead drop hosts in your sector.

Monthly

  • Re-rank the Section 5.3 threat table with fresh data.
  • Tune rules from closed tickets; record false positive rates.
  • Test detection coverage with a lab-only purple-team replay.
