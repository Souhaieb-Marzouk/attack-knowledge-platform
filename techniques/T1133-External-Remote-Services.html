MITRE ATT&CK · INITIAL ACCESS + PERSISTENCE

T1133 External Remote Services

VPNs, remote desktop, and SSH exist so your people can work from anywhere. Attackers love them for exactly the same reason: with stolen credentials or an unpatched gateway, they can log in from anywhere too - looking like a normal remote employee.

  • Tactic: Initial Access, Persistence
  • Platforms: Windows, Linux, macOS, Containers
  • Added: 2017 (v1.0) · checked vs ATT&CK v20
  • Guide version: 2.0
  • Data sources: Logon session, VPN/appliance logs, Network traffic
  • Detection difficulty: Hard (valid credentials)

What it is

Entering through remote work services with stolen credentials or by exploiting the gateway.

Primary risk

A valid-credential intrusion that looks like everyday remote work.

Where it happens

SSL VPNs, RDP gateways, Citrix/VDI, SSH servers, cloud desktops.

Detection difficulty

Geo, device, and behavior anomalies are the main signals - not malware.

Contents

    1

    Overview

    What external remote services are, why attackers abuse them, and what this page teaches.

    The idea in plain language

    External remote services are the doors your organization keeps open for remote work. Think of VPN gateways, remote desktop (RDP) gateways, Citrix or other VDI portals, SSH servers, and cloud desktops. An attacker gets in three ways. Stolen credentials: phishing, leaks, or access brokers selling logins. Brute force: guessing weak or reused passwords. Or exploiting the gateway software itself (see T1190).

    Once connected, the attacker is a legitimate user on the network - no malware is required to get inside. And because the credentials keep working, this is also a Persistence technique: the attacker can simply log in again tomorrow.

    Why it matters

    Credential-based intrusions defeat the perimeter entirely. Antivirus sees nothing, because nothing malicious was executed to get in. The whole detection burden falls on behavior: impossible travel, fail-then-success patterns, new devices, unusual hours. Organizations that do not baseline these signals usually discover the intrusion only at the ransomware stage.

    Where it fits in the attack chain

    T1133 covers Initial Access and Persistence. It relies on T1078 Valid Accounts for the credentials themselves, and hands off to lateral movement via protocols like T1021.001 RDP. Gateway exploitation chains with T1190.

    What is happening

    Defender hint

    The same story in text

    1. Preparation. The attacker buys leaked employee credentials and scans the company's VPN portal. Defender hint: scan-like traffic against your VPN from hosting providers is an early warning worth alerting on.
    2. Credential stuffing. Dozens of password attempts run against one account from 198.51.100.24 - the VPN logs every failure. Defender hint: many failures from one IP followed by quiet is the classic stuffing signature.
    3. Success. One reused password works. The gateway opens a session without any MFA challenge - the account was excluded during a rollout. Defender hint: fail-then-success from one IP must page someone, every time.
    4. First touch. The attacker lands on a corporate laptop over the VPN tunnel. It looks like a normal remote session. Defender hint: new device fingerprint or country for this user should combine with the login anomaly.
    5. Lateral movement. From the laptop, the attacker connects onward with RDP to fin-file01, the finance file server. Defender hint: logon type 10 (RDP) chains are normal for admins, not for this account.
    6. Collection. Files are copied to the laptop while the VPN session stays alive. Defender hint: watch data volume per session; the account's baseline makes outliers obvious.
    7. Detection. The SOC correlates the VPN anomaly with impossible travel - the same user had a local badge login minutes earlier. Defender hint: impossible travel needs both sources: VPN logs and physical/badge or workstation events.
    8. Response. The session is killed, the account disabled, credentials rotated, and the appliance patched and locked down. Defender hint: hunt everything the account touched during the session before closing the case.
    3

    Red team / hacker perspective

    How attackers obtain and use remote access, in principle. Practice only on systems you own.

    When and why attackers use it

    Remote services are the fastest route from nothing to inside: one working login beats weeks of malware development. The ecosystem is industrialized - access brokers compromise or brute-force logins and sell them on criminal markets, often specialized by product (VPN brand, RDP, cloud consoles). Ransomware crews buy that access and start encrypting within days.

    How access is obtained (concept)

    Leaks and stuffing: passwords reused from other breaches. Spraying: one common password across many accounts, slowly, to avoid lockouts. Phishing: adversary-in-the-middle pages that capture both passwords and MFA codes. Appliance exploitation: gateway bugs that leak credentials directly (chain with T1190). Buying: straight purchase from access brokers.

    Prerequisites

    A reachable service, and credentials that work - or a vulnerable gateway. Plus weak controls: missing MFA, no geo or device checks, generous lockout policies, and portals that advertise their product version on the login page.

    LAB-ONLY: verify your own controls against credential stuffing
    # Test YOUR lab VPN's lockout and logging behavior with a test account.
# Isolated lab only - never target systems you do not own.

# 1) Create test-user 'lab-stuffing' on your lab VPN/RADIUS.
# 2) Attempt 6 wrong passwords from one lab client (stop before lockout).
# 3) Verify your SIEM actually shows 6 x failure events with the same source IP.
# 4) Attempt one correct login; confirm your fail-then-success rule fires.
# 5) Check MFA enforcement: is any account class excluded? Why?

# This validates DETECTION and POLICY - no attacker tooling required.

    Common variations

    Appliance exploit to credential theft (read config files with embedded secrets). Contractor and partner accounts with weaker controls. Session hijacking via AiTM phishing instead of passwords. Legacy protocols: exposed Telnet/VNC on forgotten systems. Cloud consoles: the same pattern against SaaS admin portals.

    Attacker mistakes that help defenders

    Same-IP fail-then-success sequences. Impossible travel when checked against badge and workstation data. Access outside the victim's normal hours. Immediate RDP chains that the account never did before. And reuse of the same credentials across multiple customer victims - which lets defenders cross-report to vendors and CERTs.

    Danger

    Testing credentials against services you do not own is unauthorized access - a crime, even if the password is wrong. Practice only against your own lab gateway with test accounts.

    4

    Blue team / SOC perspective

    Nothing malicious runs to get in - the signals are behavioral. Baselines are everything.

    How defenders can see it

    Four signal families work together. Authentication math: failure counts per source and account, then success - the stuffing signature. Geo and device: new countries, new device fingerprints, impossible travel when badge or workstation data exists. Session behavior: hours, duration, and data volume versus the account's baseline. Downstream logons: RDP/SSH chains the account never used before.

    Gateway artifacts

    VPN auth failures then success from one IP; logins without MFA challenges; sessions from hosting providers; admin-path probes on the portal.

    Identity artifacts

    Logon type 10 (RDP) from public IPs; type 3 (network) chains into file servers; NTLM logons from unusual sources; MFA prompt storms on one user.

    Host artifacts

    New remote-session processes (mstsc.exe, ssh), mapped drives on first use, tools downloaded through the tunnel, off-hours data movement.

    Where to look (log sources)

    • VPN/appliance logs: Fortinet ssl-login-fail, Palo Alto GlobalProtect, Ivanti/Pulse event logs - shipped to the SIEM.
    • Windows Security: 4624/4625 with logon type and source IP; 4778/4779 RDP session reconnects.
    • SSH: auth.log/secure Accepted/Failed password lines with source IP.
    • RADIUS/NPS: events 6272 (grant) and 6273 (deny, with reason codes) for enterprise Wi-Fi/VPN.
    • Identity provider: Entra ID/Okta sign-in logs with device and location context.

    Short triage flow

    1. Validate the anomaly. Confirm fail-then-success, new geo, or new device - exclude known VPN egress and mobile-carrier IPs.
    2. Check the user's reality. Badge data, calendar, or the user themselves: is this plausibly them?
    3. Watch, do not burn. If plausible-but-odd, monitor the session; if impossible, proceed.
    4. Terminate and disable. Kill the session, disable the account, force credential + MFA re-enrollment.
    5. Scope the session. What did the account touch? Pull RDP chains, file access, and data volume for the session window.
    6. Harden. Close the control gap that let it happen: MFA coverage, appliance patch, geo policy.
    Warning

    The attacker in this scenario has valid credentials - if you only disable the account without scoping the session, you evict one login while the attacker returns through another stolen account. Always treat remote-access compromise as credential-compromise-wide, not account-single.

    5.2

    Threat intelligence

    Remote-access abuse is the commodity market of intrusions. Intelligence is abundant and directly operational.

    Sources worth following

    MITRE ATT&CK for structure. CISA advisories for exploited gateway CVEs (Ivanti, Fortinet, Pulse advisories include IoCs). Vendor reporting: FireEye/Mandiant, Sophos, Recorded Future on stuffing waves and access-broker markets. Appliance vendors: exploited-in-the-wild notices. ISACs: sector credential-stuffing warnings. Internal telemetry: your failure-rate baseline is the best stuffing detector.

    How to apply it

    Maintain a watchlist of exploited gateway CVEs mapped to your appliance inventory. Track access-broker market chatter (via reporting) for your sector and VPN products.     5.3

    Threats ranking and categorization

    Five realistic threats built on T1133, ranked and categorized. These five are reused in sections 5.4 and 5.5.

    RankThreatSeverityPlatform
    1Pre-auth exploit of VPN/gateway applianceCriticalNetwork
    2Credential stuffing / password spraying against VPN or RDPHighIdentity / Network
    3Exposed RDP without MFAHighIdentity / Network (Windows)
    4Exposed SSH brute forceMediumNetwork / Linux
    5Legacy remote tools exposed (Telnet/VNC/TeamViewer)LowNetwork

    Threat 1 - Pre-auth appliance exploit Critical

    Description: gateway bugs exploited before login - traversal, SSRF, RCE - often leaking credential stores.

    Preconditions: unpatched appliance on the Internet edge.

    Impact: credential theft plus persistent edge access; straight route inside.

    Justification: repeatedly proven at scale (Pulse 2019-20, Ivanti 2023-24).

    Threat 2 - Credential stuffing / spraying High

    Description: breached or guessed passwords replayed against your remote services.

    Preconditions: users reusing passwords; missing MFA on some accounts.

    Impact: valid-credential access that mimics normal remote work.

    Justification: constant background noise that succeeds wherever MFA gaps exist.

    Threat 3 - Exposed RDP without MFA High

    Description: RDP reachable from the Internet (directly or via weak gateway) protected by password only.

    Preconditions: open 3389 path, no NLA/MFA, weak passwords.

    Impact: full interactive desktop access; the access brokers' favorite product.

    Justification: trivially discoverable and instantly monetizable.

    Threat 4 - Exposed SSH brute force Medium

    Description: password-based SSH hammered by botnets; key theft enables silent entry.

    Preconditions: SSH exposed with password auth enabled and weak keys.

    Impact: server footholds in DMZ or cloud; pivot potential.

    Justification: easy to prevent (keys only), but misconfigurations are endemic.

    Threat 5 - Legacy remote tools exposed Low

    Description: Telnet, VNC, or unmanaged TeamViewer instances reachable from outside.

    Preconditions: forgotten systems, flat networks, shadow IT.

    Impact: unauthenticated control of individual systems.

    Justification: increasingly rare and patchily exposed, but catastrophic when present.

    5.4

    Logs and patterns

    For each of the five threats: log sources, key fields, normal vs suspicious behavior, detection logic, and a realistic event example.

    Threat 1 - Pre-auth appliance exploit Critical

    Log sources: reverse-proxy/web logs in front of the gateway; appliance event logs; WAF.

    Key fields: request, status, remote_addr, user_agent.

    Normal: login POSTs to /dana-na/, /remote/portal, or similar; static resources; nothing touches pre-auth API paths.

    Suspicious: traversal tokens (..;/) on API paths, requests to config/token endpoints without a session.

    Detection logic: match appliance exploit path patterns on the edge; escalate on any hit.

    Example event - reverse-proxy access log
    198.51.100.7 - - [16/Mar/2025:02:44:51 +0000] "GET /api/v1/totp/user-template/..;/rest/auth/login HTTP/1.1" 200 268 "-" "Mozilla/5.0 (Windows NT 10.0; Win64; x64)"

    A pre-auth API request containing the ..;/ traversal token, answered with 200. This matches the Ivanti CVE-2023-46805 exploitation pattern: authentication bypass before any login attempt.

    Threat 2 - Credential stuffing / spraying High

    Log sources: Windows Security 4625/4624; VPN appliance auth logs; identity provider logs.

    Key fields: IpAddress, TargetUserName, SubStatus, LogonType.

    Normal: users fail once or twice then succeed; failures come from many different IPs (typos).

    Suspicious: 10+ failures from one IP, then a success from the same IP; one password tried across many accounts.

    Detection logic: count failures per source and per account; alert when followed by success within the hour.

    Example event - Windows Security 4625 then 4624 (XML, abridged)
    <Event><System><EventID>4625</EventID>
  <TimeCreated SystemTime="2025-03-16T03:05:12.401Z"/></System>
  <EventData>
    <Data Name="TargetUserName">a.mercer</Data>
    <Data Name="IpAddress">198.51.100.24</Data>
    <Data Name="LogonType">10</Data>
    <Data Name="SubStatus">0xC000006A</Data>
  </EventData></Event>
<Event><System><EventID>4624</EventID>
  <TimeCreated SystemTime="2025-03-16T03:09:40.107Z"/></System>
  <EventData>
    <Data Name="TargetUserName">a.mercer</Data>
    <Data Name="IpAddress">198.51.100.24</Data>
    <Data Name="LogonType">10</Data>
  </EventData></Event>

    SubStatus 0xC000006A means wrong password - dozens of these from 198.51.100.24 over four minutes, then 4624 success from the same IP with logon type 10 (RDP). Fail-then-success from one source is the incident.

    Threat 3 - Exposed RDP without MFA High

    Log sources: Windows Security 4624 (logon type 10); firewall logs for 3389; TerminalServices logs.

    Key fields: IpAddress, LogonType, TargetUserName, WorkstationName.

    Normal: RDP logons come from the corporate VPN subnet or bastion only.

    Suspicious: type 10 logons from public IPs, especially hosting providers, at unusual hours.

    Detection logic: alert on successful RDP logons whose source is outside RFC1918/corp ranges.

    Example event - Windows Security 4624 (XML, abridged)
    <Event><System><EventID>4624</EventID>
  <TimeCreated SystemTime="2025-03-16T03:12:02.884Z"/></System>
  <EventData>
    <Data Name="TargetUserName">a.mercer</Data>
    <Data Name="LogonType">10</Data>
    <Data Name="IpAddress">198.51.100.31</Data>
    <Data Name="WorkstationName">DESKTOP-4X9Q1</Data>
    <Data Name="ProcessName">C:\Windows\System32\svchost.exe</Data>
  </EventData></Event>

    Logon type 10 with a public source IP and an unknown workstation name. If your policy says RDP is VPN-only, this single event is a confirmed policy violation and a probable intrusion.

    Threat 4 - Exposed SSH brute force Medium

    Log sources: Linux auth.log/secure; cloud flow logs; PAM/auth tooling.

    Key fields: source_ip, user, result (Failed/Accepted), method (password/publickey).

    Normal: occasional failed attempts by admins; all successes use keys from known sources.

    Suspicious: sustained password failures from one source; any successful password auth; new key added then used.

    Detection logic: count failures per source; alert on any password-based success.

    Example event - sshd auth.log lines
    Mar 16 03:21:07 web-prod-02 sshd[22114]: Failed password for invalid user admin from 198.51.100.61 port 51022 ssh2
Mar 16 03:21:09 web-prod-02 sshd[22116]: Failed password for root from 198.51.100.61 port 51038 ssh2
Mar 16 03:21:44 web-prod-02 sshd[22154]: Accepted password for deploy from 198.51.100.61 port 51190 ssh2

    Three lines tell the whole story: dictionary attempts against admin and root, then a successful password login for the deploy account from the same IP. Password auth should be disabled on Internet-facing SSH; that alone kills this chain.

    Threat 5 - Legacy remote tools exposed Low

    Log sources: firewall allow logs; Suricata EVE; port-scan/attack-surface scans.

    Key fields: action, dst_port, direction, src_ip, dst_ip.

    Normal: Telnet/VNC ports never accept external traffic; no service listens on them at all.

    Suspicious: allowed inbound sessions to port 23/5900/5800; authenticated VNC from unknown sources.

    Detection logic: alert on any allowed external session to legacy remote ports.

    Example event - firewall allow log
    Mar 16 04:02:33 fw-edge-01 allow: proto=tcp src=198.51.100.77 dst=10.30.8.55 dst_port=5900 rule=legacy-vnc-exception bytes=1240

    An allowed VNC session (port 5900) from a public IP to an internal host, permitted by a rule named legacy-vnc-exception - exceptions like this outlive their purpose. Remove the rule, remove the service.

    5.5

    Sigma rules and Splunk SPL

    One complete Sigma rule and one matching Splunk SPL query per threat, with assumptions, false positives, and tuning notes.

    Threat 1 - Pre-auth appliance exploit Rule level: critical

    Sigma rule (YAML)
    title: Path Traversal Token on Remote Access Gateway
id: a6c3d8e1-49f0-4b27-8e5a-2c7f1b9d4e60
status: stable
description: Detects path traversal tokens on authentication or API paths of remote
  access gateways. Matches pre-auth exploitation patterns such as Ivanti
  CVE-2023-46805 against external remote services.
references:
  - https://attack.mitre.org/techniques/T1133/
  - https://www.mandiant.com/resources/blog/investigating-ivanti-vpn-zero-day-exploitation
author: Detection Engineering Team
date: 2024-12-10
logsource:
  category: webserver
detection:
  selection_traversal:
    c-uri|contains:
      - '../'
      - '..;/'
      - '%2e%2e'
  selection_gateway:
    c-uri|contains:
      - '/api/'
      - '/rest/'
      - '/dana-na/'
      - '/remote/'
      - '/global-protect/'
  condition: selection_traversal and selection_gateway
fields:
  - client_ip
  - c-uri
  - status
falsepositives:
  - Client applications that over-encode relative paths (rare)
level: critical
tags:
  - attack.t1133
  - attack.t1190
  - attack.tactic.initial-access
    Splunk SPL
    index=network sourcetype=access_combined uri_path IN ("/api/*","/rest/*","/dana-na/*","/remote/*","/global-protect/*")
| regex uri_path="(\.\./|\.\;/|%2e%2e)"
| stats count values(status) as codes by client_ip, uri_path | sort - count

    Field assumptions: gateway traffic logged via reverse proxy or appliance syslog into your web-log pipeline. False positives: near zero. Tuning: add appliance-specific CVE paths (Ivanti, Pulse, Fortinet) as dedicated rules during patch windows.

    Threat 2 - Credential stuffing / spraying Rule level: high

    Sigma rule (YAML)
    title: Burst of Failed Logons Followed by Success from One Source
id: d2e94b07-58c1-4a63-9f7d-0b6e2c8a41f5
status: stable
description: Detects a burst of failed interactive/RDP logons from one source IP
  followed by a success - the credential stuffing signature against remote
  services.
references:
  - https://attack.mitre.org/techniques/T1133/
  - https://attack.mitre.org/techniques/T1078/
author: Detection Engineering Team
date: 2024-10-15
logsource:
  product: windows
  service: security
detection:
  selection_fail:
    EventID: 4625
    LogonType:
      - 10
      - 7
      - 3
  selection_success:
    EventID: 4624
    LogonType:
      - 10
      - 7
  condition: selection_fail | count() by IpAddress > 10 near selection_success
fields:
  - IpAddress
  - TargetUserName
  - LogonType
  - SubStatus
falsepositives:
  - Shared kiosks and VPN egress IPs with many users (allow-list by range)
level: high
tags:
  - attack.t1133
  - attack.t1110.003
  - attack.tactic.credential-access
    Splunk SPL
    index=wineventlog sourcetype=WinEventLog:Security (EventCode=4625 OR (EventCode=4624 LogonType=10))
| bin _time span=1h
| stats count(eval(EventCode=4625)) as failures count(eval(EventCode=4624)) as successes values(TargetUserName) as users by _time, IpAddress
| where failures > 10 AND successes > 0
| sort - failures

    Field assumptions: Windows Security events in index=wineventlog; IpAddress holds the source. False positives: VPN egress IPs and kiosks - maintain an allow-list of shared sources. Tuning: raise the threshold gradually; page on calls where failures target privileged accounts.

    Threat 3 - Exposed RDP without MFA Rule level: high

    Sigma rule (YAML)
    title: RDP Logon from Public IP Range
id: f85a0c62-7b13-4d94-8a26-3e9c5d7b1f80
status: stable
description: Detects successful RDP logons (type 10) whose source address is not in
  private/corporate ranges. Policy-valid RDP arrives only via VPN or bastion, so a
  public source means the control was bypassed.
references:
  - https://attack.mitre.org/techniques/T1133/
author: Detection Engineering Team
date: 2024-10-15
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID: 4624
    LogonType: 10
  filter_private:
    IpAddress|startswith:
      - '10.'
      - '192.168.'
      - '172.16.'
      - '172.17.'
      - '172.18.'
      - '172.19.'
      - '172.2'
      - '172.30.'
      - '172.31.'
      - '127.0.0.1'
      - '::1'
      - '-'
  condition: selection and not filter_private
fields:
  - IpAddress
  - TargetUserName
  - WorkstationName
falsepositives:
  - Legitimate third-party support via an approved (documented) public path
level: high
tags:
  - attack.t1133
  - attack.t1021.001
  - attack.tactic.initial-access
    Splunk SPL
    index=wineventlog sourcetype=WinEventLog:Security EventCode=4624 LogonType=10
| regex IpAddress="^(?!10\.|192\.168\.|172\.(1[6-9]|2[0-9]|3[01])\.|127\.|::1|-$)"
| table _time host, TargetUserName, IpAddress, WorkstationName | sort -_time

    Field assumptions: standard Windows Security fields. The SPL regex uses a negative lookahead to exclude private ranges. False positives: approved vendor support paths - document and allow-list them. Tuning: add your public VPN egress ranges to the filter if they are not RFC1918.

    Threat 4 - Exposed SSH brute force Rule level: medium

    Sigma rule (YAML)
    title: SSH Brute Force Burst from One Source
id: 19cf6e38-7a20-4b45-9d83-5f2b8c6e0a17
status: stable
description: Detects bursts of failed SSH password attempts from a single source.
  Any subsequent password-based success from the same source is a compromise.
references:
  - https://attack.mitre.org/techniques/T1133/

  service: sshd
detection:

    'message|contains': 'Failed password'
  condition: selection_fail | count() by source_ip > 20

  - user
falsepositives:
  - Shared CI runners and jump hosts with mistyped keys (allow-list)
level: medium
tags:
  - attack.t1133
  - attack.t1110.001
  - attack.tactic.credential-access

    Real-world case study

    Travelex, New Year's Eve 2019: an unpatched VPN gateway opened the door to one of the most expensive ransomware cases of its era.

    Context

    Travelex was the world's largest foreign-exchange specialist, running currency services for banks, supermarkets, and travelers. Like many enterprises it operated a Pulse Secure VPN gateway. Pulse had patched a critical pre-auth flaw (CVE-2019-11510, allowing arbitrary file reads) in 2019 - but this gateway, among thousands worldwide, stayed unpatched. Attackers later linked to REvil used the flaw to read files, harvest credentials, and enter the network.

    Timeline

    • Aug 2019Pulse Secure patches CVE-2019-11510 and publishes advisories.
    • Late 2019Mass scanning exploits unpatched Pulse appliances globally; Travelex's gateway is reached and credentials harvested.
    • 31 Dec 2019Attack activates on New Year's Eve: REvil ransomware begins encrypting while most staff are away.
    • Jan 2020Travelex takes services offline; website and branch systems down for weeks; staff revert to pen and paper.
    • Jan-Feb 2020Negotiations; a reported ~USD 2.3M (289 BTC) payment; phased service restoration.
    • Jun-Aug 2020Travelex announces deep job cuts (1,300+ UK roles) and enters administration in August 2020, with the attack named as a contributing factor.

    Detection point

    There was no early detection - the intrusion surfaced as ransomware. The gateway vulnerability had been public for four months with a working patch. This is the T1133 lesson at its harshest: when the entry door is a remote service, the first "alert" may be the business stopping.

    Containment

    Services were taken offline to stop the spread; external forensic teams were engaged; the VPN path was closed and rebuilt. Payment infrastructure was isolated from corporate systems, limiting (but not preventing) the blast radius.

    Eradication

    Systems were rebuilt from clean images; credentials were rotated across the estate. Restoration was phased over weeks - some services returned faster than others, but customer-facing currency services stayed impaired long enough to do permanent commercial damage.

    Recovery

    Services returned in phases, starting with the payment flows customers depended on. Each system came back only after clean scans, and the patched VPN with MFA stayed in place. Gateway logs were watched closely for repeat attempts during the recovery window.

    Impact and consequences

    Weeks of disrupted service, a multimillion-dollar ransom payment, retailer partners switching to competitors, administration within six months, and 1,300+ job losses. Regulators and courts later examined the governance around the unpatched gateway.

    Team response and communication

    The response involved IR firms, payment partners, and regulators under intense public attention. Communication with supermarket and bank partners - whose counters depend on Travelex rates - was critical and difficult during the outage. The case became a boardroom benchmark for third-party and patching risk.

    Lessons learned

    1. Internet-facing gateways need emergency patch SLAs measured in days.
    2. MFA on remote access is a baseline, not an enhancement.
    3. Segment payment/critical infrastructure so VPN compromise is not business-wide.
    4. Tested, offline backups turn extortion into an inconvenience.
    5. Plan for days-long outages: manual procedures, partner communication, decision authority.

    Mitigation and defense

    Make remote access hard to steal, quick to notice, and limited in blast radius.

    Policy

    No direct RDP/SSH from the Internet - gateways only. Emergency patch SLA for edge appliances. Documented exception process with expiry dates for any public exposure.

    Identity

    Phishing-resistant MFA (FIDO2/certificates) on every remote path, with no permanent exclusions. Least-privilege accounts; separate admin accounts. Leaked-credential monitoring with forced resets.

    Endpoint

    NLA enforced on RDP hosts. EDR on jump hosts and laptops that accept remote sessions. Local admin separation for VPN users.

    Network

    Geo/ASN restrictions on gateways. Dedicated management VLAN for appliance administration. Network-level rate limiting on auth endpoints.

    Cloud / SaaS

    Conditional Access with device compliance for cloud desktops. Session timeout and re-auth for sensitive apps. Monitor guest/B2B remote access separately.

    Logging & monitoring

    Ship VPN/appliance/identity logs to the SIEM. Run the section 5.5 rules. Baseline per-account remote behavior (hours, device, volume).

    Backup & resilience

    Offline backups and a documented manual-mode plan for remote-access outages - the business must survive a gateway rebuild day.

    Response

    A credential-compromise runbook: kill sessions, disable accounts, rotate broadly, scope the session, close the control gap that was abused.

    Good practice - home and small office

    Do not expose RDP, SSH, or router admin pages to the Internet. If you need remote access, use a reputable VPN with MFA. Turn off the router's remote-management feature. Use long unique passwords plus MFA everywhere. Update your router firmware monthly.

    Common mistakes and best practices

    Ten blue-team mistakes around remote services, with symptom, root cause, fix, and prevention.

    1. MFA exclusions that never expire

    Symptom Intrusion traced to an account "excluded during the rollout" two years ago.

    Root cause Exclusions without expiry or review.

    Fix Auto-expiring exceptions; weekly review of the exclusion list.

    Prevention Zero-permanent-exclusion policy with time-boxed tickets.

    2. Gateway logs never centralized

    Symptom Stopping incident asks "who logged in?" - nobody can answer.

    Root cause Appliance logging enabled locally only.

    Fix Stream all auth events to the SIEM; verify fields (user, IP, result, MFA).

    Prevention Log-source onboarding checklist for every gateway.

    3. Threshold tuning that hides stuffing

    Symptom "We saw nothing" although logs held 40 failures then a success.

    Root cause Threshold set above realistic attack volumes.

    Fix Count-based rules with allow-lists instead of high thresholds.

    Prevention Quarterly rule review with attack-volume data.

    4. No impossible-travel context

    Symptom VPN login from another continent dismissed as "VPN node".

    Root cause Identity signals not joined with badge/workstation reality.

    Fix Correlate identity, badge, and endpoint events per login.

    Prevention Data-source map per detection use case.

    5. Alert on failure storms only

    Symptom Slow sprays (one guess per hour) go unnoticed.

    Root cause Burst-only detection logic.

    Fix Add low-and-slow patterns: failures per account over 24h, password reuse across accounts.

    Prevention Detection matrix covers burst and slow variants.

    6. Killing the session but not the access

    Symptom Attacker logs in again 20 minutes later.

    Root cause Response = terminate session, not disable credential.

    Fix Terminate + disable + rotate + revoke tokens/sessions globally.

    Prevention Response checklist orders actions explicitly.

    7. Ignoring service and vendor accounts

    Symptom Compromise via a backup-vendor login nobody monitors.

    Root cause Baselines only for human users.

    Fix Baseline and monitor service/vendor accounts separately.

    Prevention Account inventory includes owner and expected behavior.

    8. Legacy exposure accepted as permanent

    Symptom VNC/Telnet rules survive three audits.

    Root cause Exceptions without owners or expiry.

    Fix Re-audit each exception; retire or replace with gateway access.

    Prevention Firewall rule hygiene program with expiry metadata.

    9. Missing MFA-fatigue controls

    Symptom User approves a push at 03:00 to stop the buzzing.

    Root cause Number-matching and rate limits not enabled.

    Fix Number matching, push rate limits, prompt anomaly alerts.

    Prevention MFA policy review covers abuse patterns, not just coverage.

    10. Session scoping skipped

    Symptom Account disabled, then ransomware a month later from the same entry.

    Root cause Case closed at logout.

    Fix Mandatory session reconstruction: logons, shares, data volume.

    Prevention "Scope before close" rule in the IR checklist.

    Response checklist

    • Kill all active sessions for the account (VPN, VDI, cloud).
    • Disable the account; revoke tokens and MFA device trust.
    • Rotate credentials and re-enroll MFA for the user.
    • Reconstruct the session: logons, RDP chains, shares, data volume.
    • Hunt the same source IP and device fingerprint across all gateways.
    • Check for other accounts accessed from the same source.
    • Close the abused gap: MFA exclusion, missing patch, open port.
    • Brief the user and manager; watch for follow-up phishing of the victim.
