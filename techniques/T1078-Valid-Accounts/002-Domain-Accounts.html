T1078.002 Domain Accounts

A domain account is one user identity that works on many machines and services at once. Attackers want it. Steal one password, and one login opens the VPN, file shares, and many servers — like one key card that opens every door in a hotel. This guide shows how the abuse works, what it leaves in the logs, and how to detect and stop it.

Tactics: Initial Access · Persistence · Privilege Escalation · Stealth (formerly Defense Evasion) Platforms: ESXi · Linux · macOS · Windows Typical log sources: Logon Session · User Account Parent: T1078 Valid Accounts

01

Overview

What a domain account is, and why one stolen password can be worth more than a hundred local ones. Plus where this sub-technique sits in the attack chain.

A domain account is a user account that a central directory service manages. On Windows networks, that directory is Active Directory (AD), and its cloud version is Entra ID (formerly Azure AD). The server that holds the directory and hands out logon tickets is called the domain controller (DC). When a computer is "domain joined", it trusts that directory. So the same username and password work on your laptop, the file server, the print server, and the VPN. Domain accounts are not only a Windows topic: domain-joined Linux and macOS machines and ESXi hosts also accept these identities. That is why ATT&CK lists four platforms here.

For defenders this is a gift and a risk. It is a gift because every use of the account creates events you can collect. It is a risk because one stolen credential is valid everywhere. T1078.002 describes exactly this abuse: an attacker uses a valid domain account to log in, move around, and gain more access. The account itself is real and authorized — only the person using it changed.

Kerberos and NTLM, briefly

When you log on to a domain, Windows usually uses Kerberos. You first get a TGT (Ticket Granting Ticket) — think of it as an entry wristband from the DC. To open a specific service, like a file share, you swap the TGT for a TGS. A TGS (Ticket Granting Service ticket) is a ticket for that one service. Older or special cases use NTLM, a challenge-and-response handshake that proves the password without sending it. Both protocols create security events (4768/4769 for Kerberos, 4776 for NTLM) that we will use for detection.

Where it fits in the attack chain

Normal ticket flows (blue) versus the path one stolen domain account opens (red dashed).

Typical chain position for this sub-technique:

  1. Initial access: the attacker signs in to VPN, VDI, or SSO with phished or bought domain credentials.
  2. Lateral movement: the same account opens RDP, WMI, PsExec, and SMB doors on many hosts.
  3. Privilege escalation: weaker privileged accounts (service accounts, old admin accounts) fall to reuse and cracking.
  4. Persistence: a trusted identity with a real history of logons is hard to turn off and rarely suspected.
  5. Stealth (formerly Defense Evasion): the logon step needs no exploit and no malware. Activity looks like a normal employee working.

Small glossary for this page

  • DCDomain controller — the server that stores the directory and issues Kerberos tickets.
  • TGT / TGSEntry ticket to the domain / ticket for one specific service.
  • NTLMOlder challenge-response authentication; still present in many networks.
  • SPNService Principal Name — the label that lets Kerberos find a service account.
  • LDAPThe read/write protocol of the directory; enumeration happens here.
  • gMSAGroup Managed Service Account — Windows rotates its password automatically.
  • krbtgtThe key account of Kerberos; its password hashes can forge any ticket, hence the double-reset rule.
  • Tier 0The highest admin tier: DCs, Domain Admins, and everything that controls the domain.
  • MFAMulti-factor authentication — a second proof beyond the password.
Key fact Every host trusts it

A valid domain logon needs no exploit. The victim's own security design lets it in.

Key fact Tier 0 is the goal

Domain Admin, krbtgt, and DC-related accounts control the whole directory.

Key fact Volume hides noise

Thousands of benign logons per day bury the handful that matter. Baselines beat thresholds.

Key fact Logs are everywhere

DCs, member servers, VPNs, and IdPs all record the same identity. Correlate them.

The written story — all eight steps

If you cannot or do not want to run the animation, this list tells the same story.

  1. Step 1 — The phish. Domain user a.chen receives a realistic email about an expiring password. She clicks through to a fake SSO portal that mirrors the company login page. She types her domain username and password, and the site quietly forwards them to the attacker's server. At this point no security tool fires an alert, because nothing touched the company yet.
  2. Step 2 — VPN login. From a rented residential proxy, the attacker opens the company VPN portal and signs in as a.chen. The VPN accepts the password because it is correct — no exploit needed. The session lands inside the network with the same rights a.chen has. The VPN log now shows a sign-in from a new network provider and a country she never works from.
  3. Step 3 — Enumeration. Using the VPN session, the attacker runs directory queries against the domain controller. Lightweight Directory Access Protocol (LDAP) calls list groups, admin accounts, service accounts, and file share names. The directory answers politely — it cannot tell a curious employee from an attacker. The DC logs an unusual volume of directory access events from this one session.
  4. Step 4 — Share access. The valid account now opens department file shares exactly like an employee would. The attacker lists folders in bulk and opens documents that look interesting: password sheets, finance files, onboarding notes. The share audit trail shows mass reads from one user at an unusual hour.
  5. Step 5 — Service account hit. The attacker requests Kerberos service tickets for accounts with Service Principal Names (SPNs) and finds svc_report. Its password is weak and reused, so the attacker logs into a member server with it. Defenders see two signals at once: a spike of TGS requests (4769), and an interactive logon (4624) for an account that should only ever run services.
  6. Step 6 — Privilege attempt. The same service password works on two more servers, because teams copied the same password years ago. The attacker now touches several machines in minutes, all from one source address. Successful logon storms like this are the clearest lateral movement shape in Windows logs.
  7. Step 7 — SOC alert. No single alert was loud, but correlation changes that: VPN anomaly plus TGS spike plus service-account interactive logon equals one incident. The analyst pulls the timeline and sees the full path from phish to servers. The case moves from "odd logon" to confirmed intrusion in one view.
  8. Step 8 — Response. The team disables a.chen and svc_report, resets their passwords, and isolates the affected member servers. They plan a two-part krbtgt password rotation because domain credential exposure is possible. Recovery starts only after the scope is clear and evidence is saved.
03

Red Team / Hacker Perspective

Why attackers prefer domain accounts, what they need before they can use one, and the mistakes that give them away. All examples are lab-only and use placeholders.

Why attackers pick this technique

  • One password, many doors. A single domain credential opens VPN, file shares, RDP, and internal web apps. No exploit is needed at the logon step.
  • It looks normal. An employee account logging in from the VPN at 9 a.m. is daily noise. Malware-free access passes many controls.
  • It carries history. The account has months of legitimate logons, so simple "new user" logic will not fire.
  • It leads upward. Enumeration shows which other accounts are weaker, reused, or over-privileged.

Where it applies in the chain

  • Initial access: log in to VPN, VDI, or SSO portals from the internet.
  • Discovery: query LDAP to map users, groups, shares, and admin paths.
  • Lateral movement: use RDP (logon type 10), network logons (type 3), and SMB to reach other hosts.
  • Persistence: keep using the account — password resets are the only real eviction.
  • Stealth: operate inside approved tools and admin protocols. The activity comes from a trusted identity over trusted channels.

Prerequisites checklist

  • Valid domain credentials — phished, bought from an access broker, sprayed, or reused from another breached service.
  • A reachable entry point — internet-facing VPN, VDI, RDP gateway, or SSO portal.
  • No multi-factor authentication (MFA), or MFA that a push-bomb or help-desk reset can beat.
  • Basic recon — user naming pattern (first initial + last name), department names, share names.
  • Patience — careful attackers work office hours, avoid lockouts, and stay small.

How the attacker works, step by step

1 · Get the credential

Phishing kits that proxy MFA, credential markets, password spray against the SSO portal, or plain reuse of a password from a breached forum. The domain password is the target because one password opens many systems.

2 · Get in quietly

Log in from residential proxies so the source looks like a home connection. Keep sessions during business hours. Use the VPN client the company issued. Avoid failed logons that raise lockout events.

3 · Blend and expand

Enumerate the directory, read shares, then hunt service accounts and over-privileged groups. Prefer built-in remote tools — WMI, PsExec, RDP — because endpoint telemetry alone rarely flags them.

Timing and the attacker's clock

Red teams and criminals read your schedules. They know your patch windows, your shift changes, and your holidays. Expect the first VPN logon shortly after your help desk closes and enumeration within the same hour. One practical exercise: take the timestamps from your last incident and check what your monitoring would have seen at 03:00 on a Sunday. If the honest answer is "an email nobody reads until Monday", fix that before buying any new tool.

Attacker mistakes defenders should know

  • Logging in from a new country or consumer ASN on day one.
  • Running LDAP enumeration as fast as automated tools allow, straight from the VPN session.
  • Signing in interactively as a service account — an account that should never do that.
  • Using Domain Admin credentials on a workstation, leaving cached secrets everywhere.
  • Triggering lockout storms during careless password spray.
  • Producing 4624 type 3 storms from one source address across many hosts in minutes.

Ethics note. Everything on this page is for education and defense. Using credentials that are not yours — even "just to test" — is illegal and harmful. Run experiments only in labs you own, with accounts created for that purpose.

04

Blue Team / SOC Perspective

How defenders see valid domain account abuse: the artifacts it leaves, where to look first, and a triage flow you can follow during an incident.

Valid account abuse is invisible to controls that only hunt malware. The identity is real, the protocols are approved, and the tools are built in. Your advantage is simple: a stolen identity behaves differently from its owner. It logs in from new places, touches more hosts in less time, and asks the directory questions no human types. Every one of those behaviors writes an event. Your job is to collect the events and compare them to a baseline of the person.

Where you can see it

Logon sessions

4624 success, 4625 failure, 4672 special privileges, 4648 explicit credentials. The core telemetry for who entered which host, when, and from where.

Kerberos traffic

4768 TGT requests, 4769 TGS requests, 4771 failures on the DC. Shows ticket activity, encryption types, and service targets.

Directory access

4662 directory service access on DCs. Volume spikes from one principal reveal LDAP enumeration of users, groups, and shares.

Share audit

5140 share connections and 5145 detailed share checks on file servers. Mass reads from one session expose data discovery.

VPN and IdP logs

VPN auth lines and Entra ID / AD FS sign-ins give geo, ASN, and MFA status. The first place a stolen credential appears.

Account changes

4720 create, 4725 disable, 4738 change, 4740 lockout. Group membership changes show escalation attempts during the intrusion.

Triage flow — first hour

  1. 1 · Validate the signal

    Confirm the logon was actually successful and the source is external or unusual. Rule out misconfigured services and scheduled tasks that reuse accounts.

  2. 2 · Freeze the session

    Kill active VPN sessions for the account and force a password reset. Speed matters more than elegance; evidence stays in logs.

  3. 3 · Build the identity timeline

    Pull 4624/4625, VPN, and Entra sign-ins for the account over the last 30 days. Mark every "first time": first country, first ASN, first hour, first host.

  4. 4 · List touched hosts

    From 4624 type 3/10 events, list every host the account reached. Group by source address to spot storm patterns.

  5. 5 · Check privilege state

    Review the account's group memberships and any recent changes (4728, 4732). Do the same for service accounts it may have touched (4769 targets).

  6. 6 · Hunt related patterns

    Search for TGS spikes, RC4 ticket encryption, mass share reads, and 4662 volume from the same session or IP.

  7. 7 · Contain and escalate

    Disable accounts, isolate hosts, capture volatile evidence, and hand a written timeline to incident response. Notify data owners if shares were read.

Why this matters. The 2021–2022 ransomware wave ran almost entirely on valid domain accounts. Detection that works here shortens intrusions before encryption day — often from weeks to hours.

From collection to action: the intelligence cycle

  1. Collection. Pull the sources above into one review queue; tag each item with the threat (1–5) it touches.
  2. Analysis. Compare reported tradecraft with your logs: do you even record 4769 encryption types? Which actor step would your current rules miss?
  3. Application. Turn gaps into rules (section 5.5), hunts (weekly habit), or tabletop scenarios (quarterly). Feed confirmed detections back as your own internal intel.

How confidence changes what you do

High confidence (multiple independent vendors, verified telemetry): build the detection now, tune later. Ship the rule, then refine false positives with your baseline. Moderate confidence (single credible report, consistent OSINT): write a hunt query first, run it for two weeks, and only alert if your data supports it. Low confidence (one isolated post): keep it as a hypothesis in your hunt backlog, and revisit it when new reporting arrives. This ordering keeps alert quality high while still learning from new intelligence.

5.3 Threats Ranking and Categorization

The five threats below are the realistic ways this sub-technique hurts an organization. The ranking assumes a typical mid-size enterprise: one AD forest, a few domain controllers, VPN or VDI for remote work, and a small SOC. Ranks weigh likelihood, impact, and how often each pattern appears in public incident reporting.

ThreatNamePlatformWhat happensPreconditionsImpactWhy this rank
1 · Critical Privileged domain account used off-tier Windows Identity A Domain Admin or equivalent Tier-0 account logs on to workstations and member servers where it should never appear. Tiering violations; admins reuse their privileged account for daily tasks. Credential exposure at Tier-0 scale; one cached admin credential can unlock the entire domain. Widest impact of any single mistake; it directly precedes domain takeover in real intrusions.
2 · Critical Weak or reused service account logons Windows Identity An account with an SPN and a weak or reused password receives valid logons across many servers. Weak service password; no vaulting or gMSA; service accounts can log on interactively. Silent privilege escalation; the account often has local admin on many hosts. Service accounts are powerful, old, and rarely watched — a favorite escalation path.
3 · High VPN / VDI / SSO logon with stolen credentials Network Identity The attacker authenticates to remote access with a phished or bought domain password, no MFA in the way. Phished or purchased credentials; MFA absent or phishable. Remote access as a real user; full network reach of that identity. The standard entry path of the 2021–2022 ransomware wave; cheap, quiet, and effective.
4 · High Lateral movement storms with valid accounts Windows One source performs 4624 type 3/10 logons against many unique hosts using WMI, PsExec, or RDP. Valid credentials; network reachability; admin shares enabled. Spread, discovery, and payload deployment across many systems within days. Present in nearly every real intrusion with valid accounts; a clean, machine-readable shape.
5 · Medium Stale or legacy privileged accounts still active Identity Departed staff or old admin accounts sign in successfully after months of silence. Weak offboarding; no last-logon review; no honeypot accounts. Unnoticed persistence with trusted history and no owner watching. Less frequent than the others, but almost impossible for defenders to suspect — nobody owns the account.

Severity legend

Critical domain-scale or business-stopping impact. Act immediately. · High serious impact; intrusion progress is likely. Same-day response. · Medium contained impact, but dangerous as persistence. Respond within the week. · Low hygiene risk. Fix in normal operations.

Assumptions. Ranks assume a mid-size enterprise without privileged access management and with partial MFA coverage. If you run phishing-resistant MFA everywhere and vault every service credential, threat 3 drops to Low and threat 2 to Medium in your world. Re-rank annually against your own incident data.

5.4 Logs and Patterns

Each of the five threats maps to specific logs. For every threat you get the sources, the key fields, what normal looks like, and what suspicious looks like. You also get one-sentence detection logic and a realistic event example explained field by field. Placeholder addresses like 203.0.113.x follow the documentation address ranges and are safe to show.

Threat 1 — Privileged domain account used off-tier

Log sourcesKey fieldsNormal looks likeSuspicious looks like
Windows Security 4624 + 4672 on workstations and member servers; asset inventory (which host is a workstation); privileged-group list from AD. EventID, LogonType, TargetUserName, TargetUserSid, Computer, IpAddress, PrivilegeList Tier-0 accounts log on only to domain controllers, and only from a bastion or PAM tool; sessions are short and few. A -adm account gets a type 2 or 10 logon on a finance workstation at 08:41 — the account should never touch that host.

Detection logic in one sentence: alert when a 4624 (type 2/7/10) target account is in a Tier-0 group and the host is not a DC.

  • LogonType 10 — RemoteInteractive (RDP) logon. Type 2 would be at the console, type 3 over the network.
  • TargetUserName j.reed-adm — the privileged account; the -adm suffix marks Tier-0 accounts in this example organization.
  • Computer WS-FIN-1042 — a finance workstation, not a domain controller. That mismatch is the whole alert.
  • IpAddress 10.20.6.31 — the internal machine that initiated the RDP session; useful to find where the admin password was typed.
  • 4672 PrivilegeList — confirms the session held high-value rights, so credentials are now cached on that workstation's memory (LSASS) at Tier-0 scale.

Threat 2 — Weak or reused service account logons

Log sourcesKey fieldsNormal looks likeSuspicious looks like
Windows Security 4769 (TGS) on DCs; 4624 on member servers; service-account naming registry (_svc, svc_) or gMSA list. EventID, ServiceName, ServiceSid, TicketEncryptionType, TargetUserName, IpAddress, LogonType Services request tickets with AES encryption; the account itself never appears in 4624 interactive logons. A burst of 4769 requests with 0x17 (RC4) targeting one service name, followed by 4624 type 3/10 logons as that service account.

Detection logic in one sentence: alert on 4769 requests that use RC4 encryption for service-named accounts. Also alert on any 4624 logon for an account flagged as a service account.

  • TargetUserName a.chen — the identity that asked for the ticket; here it is the phished user, watching which service accounts exist.
  • ServiceName svc_report — the requested service account. Many such requests for different service names from one user is the classic kerberoast-exposure pattern (defensive framing: find and fix those accounts).
  • TicketEncryptionType 0x17 — RC4-HMAC. Tickets for weak RC4-protected credentials can be cracked offline; AES (0x12, 0x13) is the modern choice.
  • IpAddress 203.0.113.24 — the VPN-assigned address of the requesting session; tie it to the VPN log to name the user behind it.
  • Status 0x0 — success. Failed requests (0x6, user not found) in bulk mean discovery instead.

EventID, LogonType, TargetUserName, Computer, IpAddress, WorkstationName A file server sees type 3 logons from many client IPs all day; a jump host contacts servers as admin by design. Detection logic in one sentence: alert when one source IP produces 4624 type 3/10 logons on many unique hosts in a short window.

  • LogonType 3 — network logon (SMB, WMI). Type 10 on APP01 adds an RDP session — both prove interactive-grade access.
  • TargetUserName svc_report — the same service account everywhere: one credential, many doors, exactly the reuse story of threat 2.
  • IpAddress — identical source for all events; in production this is your aggregation key and the loudest single field in the storm.
  • WorkstationName ATTACKER-LAB — an attacker machine name leaking through NTLM; odd names like this are cheap wins for detection.
  • TimeCreated spread — nine hosts in ten minutes is machine speed. Humans share files; they do not visit many servers in minutes.

Threat 5 — Stale or legacy privileged accounts still active

Log sourcesKey fieldsNormal looks likeSuspicious looks like
Windows Security 4771/4740 (failures, lockouts) and 4624 (success) on DCs; AD attribute lastLogonTimestamp enrichment from your directory sync. EventID, TargetUserName, Status, IpAddress, DaysSinceLastLogon (enrichment) Departed staff accounts get zero logons; lockouts are rare and traced to a named device. A spray-style failure burst and a 4740 lockout, then one clean 4624 success on an account silent for 214 days.

Detection logic in one sentence: alert on any successful logon for an account whose lastLogonTimestamp is older than 90 days. Treat a lockout burst followed by a success as critical.

  • 4771 Status 0x18 — wrong password; a flat burst of these across accounts from one IP is password spraying, not one forgetful person.
  • 4740 TargetUserName m.kowalski — the spray tripped the lockout policy. Irony: the lockout told the attacker which account exists.
  • 4624 success at 04:02:51 — the next guess was right: this stale account used the old company password pattern nobody rotated.
  • DaysSinceLastLogon = 214 — enrichment from lastLogonTimestamp; a departed employee's account logging on is an incident by itself, regardless of anything else.

Two more examples worth knowing

NTLM validation and IdP failure storms round out the picture. Both often appear just before or during the threats above.

  • SourceWorkstation ATTACKER-LAB — NTLM leaks the calling machine name; a name you do not recognize is a free lead.
  • TargetUserName svc_backup — a service account doing NTLM validation from a foreign workstation: credential reuse in action.
  • Status 0x0 — success. A run of 0xC000006A (wrong password) ending in 0x0 from one source is spray behavior on NTLM.
  • errorCode 50126 — invalid password at the IdP; many different users, one IP, seconds apart = password spray, not typos.
  • errorCode 0 — the single success that ends the spray; every 50126 burst deserves an automatic search for the 0 that follows it.
  • Same ip 198.51.100.140 — identical to the Windows-side spray in threat 5: one operation, two log surfaces. Join them.

5.5 Sigma Rules and Splunk SPL

Five original Sigma rules — one per threat — each with a matching Splunk SPL query, field mapping notes, false positives, and tuning guidance. Copy them into your pipeline and adapt the enrichment fields (asset role, privileged-group lookup, service-account flag) to your own data. All rules are written for the Splunk Add-on for Windows field names unless noted.

Rule 1 (Threat 1) — Privileged domain account logon on a workstation

Enrichment assumption: the SIEM adds two fields before the rule runs. TargetIsPrivileged is true when the target account is in a Tier-0 group, from a daily group lookup. HostRole comes from the asset inventory — for example workstation, server, or domain_controller. Sigma cannot resolve group membership from the raw event, so the enrichment carries that knowledge.

Field mapping: Splunk maps Sigma's EventID to EventCode and Computer to the host field. ad_tier0_accounts and cmdb_assets are example lookups that stand in for the Sigma enrichment fields — point them at your privileged-group export and CMDB. False positives: approved break-glass use; ticket those hosts in the lookup. Tuning: start with type 10 only for one week, then widen to 2 and 7 once noise is understood. Severity: critical.

Rule 2 (Threat 2) — RC4 service ticket spike and service account logon

Field mapping: the Splunk Add-on renders TicketEncryptionType as Ticket_Encryption_Type; ServiceName and user/src_ip follow CIM normalization. ad_service_accounts is the lookup behind AccountIsService. False positives: old printers, legacy apps, and monitoring that authenticate as service accounts — keep an allowlist. Tuning: if RC4 volume is huge, add | bucket _time span=5m and alert on per-service spikes above the baseline instead of single events. Severity: high.

Rule 3 (Threat 3) — Successful Entra sign-in from a new country or consumer ASN without MFA

Enrichment assumption: production deployments join this rule with a per-user baseline (UEBA) for country and ASN. The Sigma rule below uses the simpler, deployable version: successful single-factor sign-ins from outside the declared home countries. Replace the country list with your own.

Field mapping: in Splunk the nested JSON flattens; the add-on exposes properties.ipAddress (CIM src_ip) and userPrincipalName (CIM user). iplocation supplies the country check that Sigma performs with the location field. False positives: travel, VPN egress in another country, and SaaS integrations. Tuning: add an ASN allowlist for known vendors, and require two failures of the "home country" test before paging — email for the rest. Severity: high.

Rule 4 (Threat 4) — One source, many unique hosts, network logons

Field mapping: Sigma's count aggregation becomes Splunk's dc(Computer) ... by IpAddress over a 10-minute bin; the allowed_sources lookup replaces manual allowlisting. False positives: deployment servers, PAM tools, and monitoring. Tuning: measure your quiet-hour baseline first; if your patch server hits 12 hosts nightly, threshold at 15 or filter it. Also track the type 10 (RDP) twin of this rule for interactive-grade spread. Severity: high.

Rule 5 (Threat 5) — Logon for an account inactive 90 days or more

Enrichment assumption: the SIEM joins a daily directory export that computes LastLogonDays from lastLogonTimestamp. Without enrichment, run the Splunk version, which approximates the baseline from your own stored events.

Field mapping: ad_lastlogon carries the enrichment the Sigma rule expects; the regex filter drops machine accounts. If you lack the lookup, build an approximation. Compare each account's earliest seen event in your retention window against today. Treat missing enrichment as a logging gap, not a pass. False positives: seasonal workers and rare batch accounts. Tuning: exclude accounts with a documented owner and purpose; alert on lockout-burst-plus-success combinations at critical instead of medium. Severity: medium.

Deploying the rules — short checklist

  1. Build the three lookups first: Tier-0 accounts, service accounts, asset roles. The rules are only as good as the enrichment behind them.
  2. Deploy in report mode for one week; review every hit against change tickets.
  3. Switch to alerting for rules 2 and 4 (highest signal), then 1, then 3 and 5.
  4. Record per-rule hit counts and false-positive rates monthly; retire or fix rules that never produce true positives in 90 days.
  5. Keep rule IDs stable across your pipeline so analysts can build runbooks around them.

Validation idea. Test all five rules in a lab. Create a fake "Tier-0" account. Request an RC4 ticket for a lab service account. Sign in from a VPN with a different geo. Then watch each rule fire. A rule you have never seen fire is a hope, not a detection.

Real-World Case Study

A composite intrusion, built from the leaked Conti playbooks and public breach reporting from 2021–2022. It shows how valid domain accounts carried a ransomware attack end to end.

Composite case. This case study is a teaching composite. It merges patterns documented in the 2021–2022 Conti playbook leaks and public breach reports into one fictional victim, "a mid-size industrial company". No single company is described; the timeline, names, and counts are illustrative, the tradecraft is real.

Context

The victim ran a 4,000-seat Windows environment with one AD forest. The VPN concentrator had no MFA. The small SOC watched endpoints well but identities poorly. Like many victims of that period, it had Domain Admins who used their admin accounts for daily email. Service account passwords were set years ago. There were no honeypot accounts. An initial access broker had been selling VPN credentials for this company on a criminal market for about two weeks.

Attack chain in steps

  1. Buy: operator purchases valid VPN/domain credentials from a broker.
  2. Enter: VPN logon with the stolen domain password; no second factor exists.
  3. Map: LDAP queries enumerate groups, admins, service accounts, and shares.
  4. Collect: department shares read in bulk; passwords found in onboarding docs.
  5. Escalate: RC4 tickets requested for service accounts; svc_report cracked offline.
  6. Spread: service account logs on to 9 servers; 4624 type 3 storm begins.
  7. Promote: group membership abuse and off-tier Domain Admin logon secure control.
  8. Deploy: ransomware spreads through the same valid-account channels.

Detection point — what the logs were already saying

The intrusion was detectable for four days before encryption. The clearest signals were 4769 TGS spikes with RC4 encryption on Day 2 and the 4624 type 3 storm from a single source minutes later. Both appear in this guide as Sigma rules 2 and 4. The VPN sign-in from a new country on Day 1 (rule 3) fired into an unmonitored queue. None of the events looked malicious alone; correlation made the pattern visible.

Containment, eradication, recovery

Containment (hours 0–6)

  • Disabled compromised accounts and killed VPN sessions.
  • Isolated the 9 touched member servers at the switch.
  • Blocked the residential proxy ranges seen in the logs.

Eradication (days 1–10)

  • Reset passwords for every exposed account, in waves.
  • Removed attacker-created group memberships and accounts.
  • Rebuilt affected servers; double krbtgt reset after cleanup.

Recovery (days 3–21)

  • Restored AD from validated backups before user data.
  • Staged service restoration, watching for re-infection.
  • Enforced MFA on VPN before reopening remote access.

Why the krbtgt reset happens twice. The krbtgt account signs every Kerberos ticket. Kerberos keeps the current krbtgt password and the previous one. A single reset leaves the old key valid, so forged tickets can still work. Two resets, spaced beyond the maximum ticket lifetime, push both keys out of use. Microsoft publishes the exact schedule in its guidance, and teams rehearse it before they need it.

Impact and consequences

Production ran at reduced capacity for eleven days; some branch sites for three weeks. Costs included emergency response, overtime, hardware rebuilds, and regulatory reporting. The data exfiltrated from the finance shares triggered a leak-threat publication two months later. The reputational damage outlasted the technical recovery.

Team response and communication

The SOC paged the on-call identity owner and the infrastructure lead within 20 minutes of the incident declaration. One incident channel held the timeline. The identity team owned account actions. Infrastructure owned isolation. Communications sent one daily external update. Every action was written down with a timestamp. That log later made the regulatory report and the lessons-learned review far easier.

Lessons learned

  1. MFA on remote access is the cheapest big win. Phishing-resistant MFA on the VPN would have stopped Day 1 entirely.
  2. Tier the admin model. Domain Admin credentials cached on a workstation turned one phish into domain control.
  3. Vault service accounts. gMSA or a password vault removes the password reuse that made svc_report work on so many servers.
  4. Clean the kerberoast-exposed surface. 31 RC4-capable SPN accounts meant 31 offline cracking targets.
  5. Correlate identity signals. VPN + 4769 + 4624 together told the story; none of them did alone.
  6. Rehearse AD recovery. The validated backup and the planned double krbtgt reset saved weeks; both were practiced only two months earlier.

What if detection had fired on Day 2? The 4769 RC4 burst and the 4624 type 3 storm were both in the logs 72 hours before ransomware. With rules 2 and 4 alerting, the SOC would have disabled two accounts in the first hour of the escalation attempt. It would also have isolated nine servers. That is a bad morning, not an eleven-day outage. That difference is the business case for every control in section 7.

Home and small-office advice

One password per place

Use a password manager. Never reuse the password that opens your email — it resets everything else.

Turn on MFA everywhere

An authenticator app beats SMS codes. It kills most stolen-password attacks before they start.

Separate your admin user

On your own PC, use a normal account daily and the admin account only for installs. Malware then cannot reach admin rights.

Update everything

Phones, routers, laptops, and the printer too. Updates close the holes attackers use to get credentials in the first place.

Check before you type

Look at the sender address and the site URL before entering a password. When in doubt, open the site by typing its address yourself.

Watch your accounts

Review sign-in alerts from your email provider. An unfamiliar country is worth checking the same day.

Common Mistakes and Best Practices

Ten concrete mistakes blue teams make with valid-account detection, each with symptom, root cause, fix, and prevention — plus the working habits that keep detections healthy.

1 · Treating all 4624 events as noise

Symptom: the SIEM drops or samples 4624 events to save license.

Root cause: volume feels unbounded, so the team gave up.

Fix: re-enable ingestion from DCs and servers first; filter only obvious machine-account pairs at search time.

Prevention: measure per-host event rates; tune at the search layer, never by deleting the source.

2 · Missing RC4 Kerberos activity

Symptom: 4769 events arrive but the encryption-type field is empty or ignored.

Root cause: the parser never mapped TicketEncryptionType.

Fix: fix the parsing config, then deploy Sigma rule 2 and baseline the RC4 users you still have.

Prevention: field-coverage checks for every ingested event ID, reviewed quarterly.

3 · No per-service-account baseline

Symptom: service accounts trigger alerts for completely normal activity, so analysts auto-close them.

Root cause: rules treat service accounts like people.

Fix: build per-account profiles (which hosts, which hours, which logon types) and alert only on deviation.

Prevention: keep a service-account registry that the rules read automatically.

4 · Domain Admins working daily with no alert

Symptom: hundreds of Tier-0 logons on workstations every morning.

Root cause: admins use privileged accounts for email and browsing.

Fix: deploy rule 1 in report mode, publish the numbers, and drive the tiering fix with data.

Prevention: make off-tier logon a tracked exception, not an accepted habit.

5 · VPN logs never correlated with AD

Symptom: identity investigations start and end in Windows events.

Root cause: the VPN feed was never onboarded to the SIEM.

Fix: onboard the VPN auth log and join it with 4624/Entra by user and time window.

Prevention: an onboarding checklist that requires remote-access sources for identity detections.

6 · Lockout storms ignored

Symptom: 4740 events are treated as help-desk tickets only.

Root cause: nobody looks at lockouts as a spray indicator.

Fix: alert on lockout bursts across multiple accounts from one source; pair with 4771 failures.

Prevention: a standing rule that any cross-account lockout burst gets a security review.

7 · krbtgt never rotated

Symptom: the account's password dates from domain creation.

Root cause: fear of breaking Kerberos.

Fix: run the documented double reset once in a lab, then schedule it after any Tier-0 exposure.

Prevention: a written rotation runbook, tested twice a year.

8 · Trusting "internal" source IPs

Symptom: alerts auto-close because the source was inside the network.

Root cause: internal equals trusted, in the old model.

Fix: treat identity context (which user, which behavior) as primary; treat IP location as one signal among many.

Prevention: review any playbooks that close alerts on IP ranges alone.

9 · Service account passwords that never expire

Symptom: passwords older than the youngest engineer on the team.

Root cause: rotation was seen as outage risk.

Fix: move to gMSA or vault-managed rotation with staged cutover.

Prevention: quarterly report of oldest service credentials still in use.

10 · No honeypot accounts

Symptom: spraying detection relies on thresholds alone.

Root cause: nobody deployed decoys.

Fix: create 2–5 tempting, monitored accounts (old admin, finance) that never legitimately log on.

Prevention: any honeypot logon pages at critical — it is never a false positive.

11 · Log retention too short for timelines

Symptom: investigations hit a 7-day wall; the first VPN logon is already gone.

Root cause: retention set to the license minimum.

Fix: keep authentication and identity sources for at least 90 days searchable, longer archived.

Prevention: a retention table per source, reviewed with legal and compliance once a year.

12 · Shared generic admin accounts

Symptom: an account named admin_helpdesk logs on from ten cities in one week.

Root cause: shared credentials defeat baselines and accountability.

Fix: issue named accounts with scoped roles; retire the shared logins in stages.

Prevention: policy that every authentication maps to one human — no exceptions without a risk sign-off.

The five killers, named. Most failed identity programs die from five things. False positives: rules without baselines. Alert fatigue: thresholds instead of context. Missing logs: VPN, Entra, or 4662 never onboarded. Weak tuning: one static threshold for every host type. Ownership gaps: nobody owns the rule, the account, or the response. Every mistake above maps to at least one of them.

Working habits for a detection engineer

Daily

  • Review Tier-0 logons (rule 1 output) with dispositions.
  • Check VPN-to-AD correlation for new countries or ASNs.
  • Triage TGS and RC4 anomalies; close the loop on every hit.

Weekly

  • Run the kerberoast-exposure report: SPN accounts with RC4-eligible crypto.
  • Review dormant-account logons (rule 5) and disable confirmed leaver accounts.
  • Tune one noisy rule; record what changed and why.

Monthly

  • Verify audit policy and log pipelines from every DC and the VPN.
  • Review tiering exceptions and off-tier logon trends.
  • Purple-test one rule end to end, from event to ticket.
