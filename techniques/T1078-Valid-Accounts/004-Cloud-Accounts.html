T1078.004 Cloud Accounts

Cloud Accounts covers the abuse of valid identities in cloud services. Examples: AWS IAM users and roles, Entra ID users, Google Workspace accounts, and SaaS app logins. Attackers do not break in — they log in. They reuse access keys, OAuth tokens, and session cookies that already work.

  • Tactics: Initial Access · Persistence · Privilege Escalation · Stealth (formerly Defense Evasion)
  • Platforms: IaaS · Identity Provider · Office Suite · SaaS
  • Typical log sources: Cloud service logs · Logon sessions
  • Parent: T1078 Valid Accounts

ATT&CK ID

T1078.004 — a sub-technique of T1078, Valid Accounts.

IAM users, roles, access keys, OAuth tokens, and console sessions.

Why it differs

There is no perimeter to defend. Cloud logs are the only sensor.

Detection difficulty

Moderate — stolen tokens and keys bypass classic MFA checks.

01

Overview

What a cloud account is, why valid credentials are the quietest way into an environment, and what this guide teaches.

A cloud account is an identity inside a cloud service. Examples: an AWS IAM user or role, a Microsoft Entra ID (formerly Azure AD) user, a Google Workspace account, or an app identity in a SaaS product. Every action in the cloud starts with such an identity. The cloud checks two things: who you are (the identity) and what you may do (permissions). If an attacker gets hold of a working identity, the cloud treats them as a trusted user.

Access happens in two ways. The console path opens a browser page: password plus MFA, and the user gets a session. The API path is used by code and tools: it needs no browser. Two terms matter here. An access key is a long-lived secret. It is a key ID plus a secret value. A program shows it on every API call. Role assumption means one identity borrows another identity's permissions and receives temporary credentials that expire by themselves. Attackers like both paths. A leaked key works from anywhere on Earth. An assumed role carries the role's permissions, often without any MFA prompt.

Why does this matter? Valid credentials remove every classic signal. There is no exploit to catch, no malware to scan, and no firewall rule that helps. The traffic flows through the provider's own API — the normal path for every user. The only reliable sensor is logging. Cloud audit logs record who called which API, from which address, with which identity. This page shows the full path: how keys leak, how attackers use them, what the logs look like, and how to turn those logs into working detections.

Where it fits in the attack chain

  • Initial Access — a leaked key or a phished session gives the first entry.
  • Persistence — the attacker creates new keys or registers OAuth apps to keep access.
  • Privilege Escalation — assuming a more powerful role adds permissions.
  • Stealth (formerly Defense Evasion) — API calls look like normal admin work, so alerts stay quiet.

What you will learn

  • How access keys, tokens, and roles differ — in plain words.
  • How a leaked key becomes a full intrusion in minutes.
  • Which cloud logs carry the evidence, field by field.
  • Five ranked threats with matching Sigma rules and Splunk SPL.
  • How to contain, eradicate, and prevent account abuse.

Key terms in plain words

Access keyA long-lived secret pair (key ID + secret) used by programs for API calls. It does not expire on its own and usually skips MFA.
Role assumptionOne identity borrows another's permissions and gets temporary credentials that expire automatically.
Console sessionA browser login with password and MFA. The session cookie can be stolen and replayed elsewhere.
OAuth tokenA permission grant an app holds, for example a SaaS connector. It keeps working even if the user changes password.
Session tokenThe temporary credential set produced by role assumption or console login. Short-lived, but fully powerful while valid.

Fastest leak

Public code repository: bots find committed keys in minutes.

Quietest action

Read-only API calls: List and Get events rarely trip classic alerts.

Loudest signal

New access keys or new IAM users created by an unexpected actor.

Core defense

No long-lived keys; federation, roles, and full audit logging instead.

Animated Simulation

Follow a leaked AWS access key from a public code repository into a live cloud intrusion — and watch what the SOC can see at each step.

Step 1 of 8 — The slip A developer pushes deploy code with a hardcoded AWS access key to a public repository.
Defender view: Push protection with secret scanning would block this commit — if it is enabled.
Attacker asset Cloud asset / victim Credential Defender / SOC Evidence chip

The story in words

  1. The slip. A developer finishes a deploy script late in the day and pastes an AWS access key straight into the source code. The commit lands in a public repository, and the key ID and secret now sit in the open commit history forever.
  2. The harvest. Automated attacker bots scan public repositories for key patterns around the clock. Within minutes, a bot finds the new key and confirms it is syntactically valid, ready to be tested against the cloud.
  3. Valid API use. The attacker configures the stolen key and calls sts get-caller-identity. The cloud answers with the identity behind the key. It works on the first try — no password, no exploit, no malware. To the cloud, the attacker now looks like an ordinary service account.
  4. Discovery. The attacker lists S3 buckets and IAM roles to map the account. These read-only calls are cheap, fast, and rarely covered by classic alerts.
  5. Exfiltration. The attacker finds the customer-data bucket and copies thousands of objects to storage they control. Every GetObject call is authorized by the valid key, so nothing blocks the transfer.
  6. Persistence. Before leaving, the attacker creates a brand-new IAM user and access key. Even if the leaked key is found and deleted later, this fresh key keeps working — that is the whole point.
  7. SOC notice. GuardDuty flags unusual API activity for the principal, and the SOC pulls the CloudTrail timeline: unknown IP, discovery, exfiltration, and the new key. The analyst opens an incident and starts the clock.
  8. Response. The SOC disables the leaked key, deletes the attacker IAM user, and revokes active sessions. Every secret in the repository is rotated, and push protection is switched on so the next slip cannot land.
03

Red Team / Hacker Perspective

How attackers think about cloud identities: what they look for, what they do with it, and the mistakes that give them away.

When and why attackers use cloud accounts

Cloud accounts are the cheapest way into a company. There is nothing to exploit. A working key or session is accepted everywhere it has permission to go. The attacker needs no custom tools — the cloud's own command-line tool is enough and looks harmless.

One key can also be reused many times. Attackers take data, run crypto-mining on the victim's bill, or reach other connected services through the same valid identity.

Prerequisites and conditions

  • A valid credential: access key, session token, OAuth grant, or console cookie.
  • Network reachability to the provider's public API endpoints — almost always true.
  • Permissions attached to the identity that are broad enough to matter.
  • Enough quiet time before the credential is rotated or disabled.

Three common entry paths

Leaked long-lived keys

Keys committed to public repositories, dumped in CI job logs, or posted to paste sites. Bots find them within minutes and test them against the provider API.

CI/CD pipeline identities

Deployment roles and OpenID Connect (OIDC) trusts that are too broad. A compromised pipeline or a misconfigured trust policy gives the attacker admin-level cloud access.

Stolen sessions and tokens

Phished MFA push approvals, cookies stolen by infostealer malware (programs that steal saved logins), or OAuth grants to malicious apps. The session or token keeps working without the password or the MFA device.

Typical actions after the first valid call

Attackers follow a short and very effective pattern. They confirm who the credential belongs to. They map what it can reach. Then they take data or compute power and add persistence. The examples below show those actions in a safe lab setting.

Common variations

  • Token replay — reusing an OAuth token or session cookie from another machine or country.
  • Role chain hopping — assuming role after role to drift into more powerful permissions.
  • OIDC trust abuse — editing a CI trust policy so an attacker-controlled repo can assume a deploy role.
  • Metadata service theft — reading role credentials from a compromised instance's metadata endpoint.

Mistakes attackers make

  • High-volume List and Get bursts from a single new IP in a short window.
  • Default tool user agents and no attempt to blend with normal traffic.
  • Creating persistence (users, keys) before they finish taking data.
  • Reusing the same key from many addresses, which links incidents together.
Ethics note Everything on this page is for defense. Test only systems you own or have written permission to test, use lab accounts and placeholder values, and never touch credentials that belong to someone else.
04

Blue Team / SOC Perspective

What defenders can actually see when a cloud identity is abused, where the artifacts live, and how to triage an incident in order.

Visibility: what you can see, per source

AWS CloudTrail Coverage: high if on

Every control-plane call: who, what, from which IP, with which key or role. Management events are on by default; data events (S3 object reads) must be enabled explicitly.

GuardDuty / UEBA Coverage: behavioral

GuardDuty is AWS managed anomaly detection over CloudTrail, VPC, and DNS logs. UEBA (user and entity behavior analytics) is the general term for such tools. They link a principal to unusual geography, new infrastructure, or credential-exfiltration patterns.

Entra ID sign-in logs Coverage: high

Every console and app sign-in with MFA status, client app, device, and location. This is the main sensor for session and token abuse on the identity plane.

GitHub / repo audit logs Coverage: org plan needed

Shows member additions, token creations, and clone bursts. The upstream sensor for the leak itself — often reviewed too late or not at all.

GCP Cloud Audit Logs Coverage: high

Admin Activity logs are always on; Data Access logs must be enabled per service. Same model as AWS: the control plane is visible, the data plane needs extra work.

CSPM findings Coverage: config only

CSPM (cloud security posture management) tools flag over-permissioned roles, unused keys, and public buckets. They show how much one identity could touch — before an incident, not during it.

Why this matters in the chain Cloud account abuse is rarely the finish line. It is the door into data theft, ransomware staging, or infrastructure abuse. Because every later step reuses the same valid identity, catching the first unusual use of that identity cuts off the whole chain.

Triage flow: from alert to containment

  1. 1 · Validate the alert

    Confirm the finding is real: which principal, which key ID or session, which API calls. Rule out documented automation such as scheduled jobs and CI runners.

  2. 2 · Scope the identity

    Pull 24–72 hours of activity for that principal across all regions. Look for the first unusual call, the source addresses, and every user agent involved.

  3. 3 · Check the identity plane

    Review sign-in and audit logs for the same time window: new MFA registrations, new OAuth grants, new federation settings, or added external members.

  4. 4 · Map what was touched

    List which buckets, databases, or services the identity touched. For data events, count objects read and compare with normal volume for that principal.

  5. 5 · Contain

    Disable the affected keys, revoke active sessions, and remove the identity from role trust policies. Containment must be faster than the attacker's next rotation.

  6. 6 · Eradicate

    Delete attacker-created users and keys, remove malicious OAuth grants, revert trust policy changes, and rotate every secret that shared a path with the leaked one.

  7. 7 · Recover and review

    Re-enable legitimate automation with least privilege, confirm no post-revocation activity in the logs, and record what allowed the leak in the first place.

5.3 Threats Ranking and Categorization

The five threats below are the most likely to hurt a typical mid-size enterprise. The model assumes one or two cloud providers plus a code platform. The ranking weighs how often each threat is seen, how much access it gives, and how hard it is to spot. Threat numbers 1–5 are used consistently in sections 5.4 and 5.5.

ThreatNamePlatformWhat happens PreconditionsImpactWhy this rank
T1 · Critical Leaked long-lived access keys Cloud A key committed to a public repo, dumped in CI logs, or posted to a paste site is harvested and used directly against the API. Key committed and scanned; key still active; identity holds broad permissions. Data theft, infrastructure abuse, billing damage on the victim's account. Found by bots within minutes at internet scale; requires no skill and no target-specific work.
T2 · Critical CI/CD service identity abuse Cloud Identity Over-permissioned pipeline identities — deploy roles, OIDC trusts, bot accounts — are abused to deploy attacker code or exfiltrate data. Pipeline identity holds admin rights; OIDC trust policy is loose; repo or runner is compromised. Supply-chain-grade access: attacker code ships inside trusted deployments. Pipelines often hold admin rights, and their activity is expected. Abuse looks like normal work, so it is hard to notice.
T3 · High Console or Entra sign-ins without MFA Identity Cloud An attacker signs in to a cloud console from a suspicious network where MFA is not enforced — phishable MFA or legacy auth paths. Phishable or absent MFA; legacy authentication allowed; token replay possible. Session theft, mail and data access, follow-up persistence in the identity provider. The standard cloud entry path; MFA push spam and attacker-in-the-middle phishing kits make it reliable for attackers.
T4 · High Anomalous role assumption and token abuse Cloud Unusual AssumeRole chains or stolen session tokens hand the attacker privileges that skip MFA entirely. Token theft or role sprawl; long chain of role-to-role assumptions; wide trust policies. Privilege escalation that console-focused logging never shows. Invisible unless API-plane behavior analytics exist; chains grow quietly over months.
T5 · Medium Root or global-admin account activity Cloud The break-glass root or global administrator account is used outside its documented procedure — or is compromised outright. Root in daily use; break-glass procedure undocumented; shared root MFA. Total control of the account if compromised: billing, IAM, logging, everything. Rare but catastrophic; near-zero baseline makes any use highly detectable.
Severity legend and assumptions Critical likely exploitation now, severe impact · High common path, major impact · Medium lower likelihood, extreme impact if it lands · Low watchlist. Ranks assume a mid-size enterprise with standard cloud logging; re-rank for your own environment using your incident history.

5.5 Sigma Rules and Splunk SPL

Five rules follow, one per threat, each with a matching Splunk SPL query, a field-mapping note, false positives, and tuning guidance. All rules assume the log sources are actually on board — a rule cannot beat a logging gap. Dates use 2025; adapt author and index names to your organization.

Rule 1 — IAM access key used from an unexpected country (Threat 1)

The rule watches API activity performed by long-lived IAM-user keys. It checks the country the call came from. It assumes a GeoIP enrichment pipeline adds the fields geoip.country_code and geoip.as_org before indexing. Enrichment can be a transform in the SIEM, or GuardDuty-style enrichment joined by key ID. Without enrichment, use the Splunk lookup approach shown below.

Mapping note and tuning Sigma userIdentity.type maps to the Splunk field userIdentity.type as extracted by the AWS add-on; geoip.country_code assumes a lookup table named aws_geoip_lookup keyed by IP — adjust the name to your enrichment. Tuning: exclude known CI ASNs, raise the count threshold until daily noise is near zero, and consider a shadow (non-paging) version for the first two weeks.

Rule 2 — CI/CD principal creates IAM identity or changes a trust policy (Threat 2)

Identity creation and trust changes are rare by design, which makes them high-signal. This rule flags CreateUser, CreateAccessKey, and CreateLoginProfile when the actor is an assumed role — your pipelines — plus OIDC trust changes. Keep an allow-list of automation principals that may create identities, and filter them.

Mapping note and tuning userIdentity.arn arrives in Splunk as a string, so the allow-list uses wildcards instead of Sigma's |contains. If your AWS add-on nests session fields, extract the issuing role name with spath or use sessionIssuer.userName. Tuning: start in shadow mode, collect a month of allowed automation actors, then freeze the allow-list; review it at every quarterly access review.

Rule 3 — Successful Entra sign-in without MFA from a new country (Threat 3)

The rule reads Entra ID sign-in logs. It alerts when a sign-in succeeds, used only single-factor authentication, and came from a country outside the approved list. Field names assume the Splunk Add-on for Microsoft Entra ID keeps the properties namespace. If your CIM mapping flattens them, adjust the note below.

Mapping note and tuning Sigma's properties.status.errorCode assumes the raw Entra schema is preserved by the add-on; on CIM-mapped deployments use action=success and authentication_requirement instead — the logic stays identical. Tuning: add service-principal names to an allow-list, consider excluding clientAppUsed values your conditional access already blocks, and track sign-ins from uncompliant devices as a second signal in the same alert.

Rule 4 — Role chaining: an assumed role assuming another role (Threat 4)

Deep or attacker-driven role chains show up as an AssumeRole call whose caller is itself an assumed role. The rule filters known service chains. Extend the filter with your documented chains. Also measure a 30-day baseline per caller, so you catch rare role pairs that slip through the static list.

Mapping note and tuning userIdentity.sessionContext.sessionIssuer.userName is a nested JSON field; the Splunk add-on usually extracts it flat, otherwise use spath. The distinct_roles > 3 clause is the frequency-and-rarity logic: one caller touching many different roles in the window is the anomaly, not the single chain. Tune the threshold against a 30-day baseline per issuer before paging on it.

Rule 5 — Root console login (Threat 5)

Root console use should page regardless of any other signal, because the baseline is near zero. The rule has no allow-list by design. Even a documented break-glass login should produce a ticket that closes with a runbook reference. Correlate with additionalEventData.MFAUsed for extra severity in the alert title.

Mapping note and tuning Root sign-ins come from signin.amazonaws.com and are delivered through the same CloudTrail trail; confirm your trail includes management events for all regions, otherwise this rule silently sees nothing. Tuning: none for the trigger — instead tune the response, for example auto-ticket with severity critical when MFAUsed is No, and link the break-glass runbook in the alert play.

Real-World Case Study

Capital One, 2019 — valid cloud role credentials, obtained from a misconfigured server, used to copy data on about 100 million credit applications.

Context

Capital One ran much of its banking infrastructure on AWS. In March 2019, a former cloud engineer, Paige Thompson, found a misconfigured web application firewall (a ModSecurity WAF) running on an EC2 instance. The configuration let her send crafted requests from the outside — a server-side request forgery (SSRF) trick, which makes a server send requests the attacker chooses. The requests reached the instance metadata service: the endpoint that hands cloud role credentials to workloads on that machine.

The server answered and returned valid IAM role credentials for the application's role. From that point on, every action she took looked like the application itself doing its normal job. This is the exact pattern T1078.004 describes: valid cloud credentials, used through the normal API.

Why it is the perfect example for this page

No exploit reached the data layer. No malware ran. No password was cracked. The attacker listed buckets and copied roughly 100 million credit applications, including about 140,000 Social Security numbers. Every step used valid role-based API calls that the cloud authorized without question.

The case shows both halves of this page: how far valid credentials can go when permissions are broad, and how CloudTrail telemetry, reviewed properly, can tell the whole story afterwards.

Timeline

WhenEvent
March 2019The attacker scans AWS IP ranges and finds the misconfigured ModSecurity WAF instance. Crafted SSRF-style requests reach the metadata service and return valid role credentials for the application's role.
March 22–23, 2019 (widely reported)Using the valid role, she lists S3 buckets and copies data on about 100 million credit applications into buckets she controls.

July 19, 2019Security staff confirm the exposure and trace the access path through CloudTrail; the WAF misconfiguration is fixed and the credential path is cut.

Attack chain, step by step

  1. 1 · Find the entry

    Scan cloud IP ranges for instances that answer crafted SSRF-style requests through a misconfigured WAF deployment.

  2. 2 · Harvest role credentials

    Ask the instance metadata service for its attached role and receive a working, temporary credential set — valid by design.

  3. 3 · Validate and discover

    Call the API as the role: confirm the identity, list buckets, and map what the role can read. All of it looks like normal application activity.

  4. 4 · Exfiltrate

    Copy large volumes of objects from internal buckets into attacker-controlled storage using ordinary GetObject calls authorized by the valid role.

  5. 5 · Surface

    The attacker talks about the stolen data publicly. The victim learns through an external tip, not an internal alert, then confirms the scope in CloudTrail.

Detection point — and the gap

The honest detection point came late: an external tip, followed by a CloudTrail anomaly review. The telemetry to catch it earlier existed. A role that suddenly lists hundreds of buckets and reads millions of objects is a visible spike. What was missing was data-event coverage and automated review of GetObject volume by role.

This is the central lesson of the case for detection engineers: valid credentials shift the detection problem from what was used to how much and from where.

Containment and eradication

Once confirmed, the team fixed the WAF misconfiguration, cut the credential path, and secured the exposed storage. Because the credentials were role-based and temporary, the technical containment was faster than a long-lived-key breach would have been.

Eradication focused on the configuration that allowed metadata access from outside, and on reviewing every permission the role held — how much the role could reach.

Recovery, impact, and communication

Recovery meant verifying that no further unauthorized access occurred and reassuring regulators and customers with concrete evidence. The CloudTrail timeline the team built became the shared source of truth for every follow-up question.

The financial impact was severe: an 80 million dollar regulatory penalty and a 190 million dollar settlement, plus years of reputational cost. Communication ran through external counsel, banking regulators, and direct customer notification — the pattern required for a reportable breach. The security, legal, and communications teams worked from one incident timeline, so every message used the same confirmed facts.

Lessons learned

  • Enforce IMDSv2 so instance metadata resists request-forgery tricks.
  • Apply least privilege to workload roles; one over-broad role leaked it all.
  • Use S3 policy guardrails that block access from unexpected principals.
  • Run organization-wide CloudTrail with data events and GuardDuty everywhere.
  • Alert on behavior — volume and rarity — not just on rare API names.
  • Treat external tips as a real detection channel; this breach surfaced that way.
  • Classify and minimize data; 100 million applications in easy reach amplified everything.

Mitigation and Defense

Controls that remove the attacker's favorite precondition — a working credential — and monitoring that catches the ones that remain.

Enterprise controls by domain

DomainControlHow it helpsWhat "good" looks like
Policy No long-lived keys as a stated standard Removes the asset that leaks. Workloads authenticate with roles; humans with federation. Written policy, exception process, and a key inventory that trends to zero.
Identity SSO with phishing-resistant MFA (FIDO2/WebAuthn) on every console Console sessions start from a protected identity; attacker-in-the-middle phishing and MFA push spam lose their power. All human access federated; MFA enforced by conditional access, not by convention.
Identity Short session TTLs and permission boundaries Stolen sessions and over-scoped roles expire quickly and stay inside limits. Session durations measured in hours, boundaries attached to privileged roles.
Endpoint Managed browsers and infostealer-resistant workstations Session cookies and tokens are harder to steal in the first place. Corporate SSO available only from managed, compliant devices.
Network Metadata service hardening (IMDSv2, hop limits) Blocks the request-forgery path that turns one weak web app into role credentials. IMDSv2 required on every instance; legacy path disabled by policy.
Cloud Service control policies and S3 guardrails Even valid credentials cannot touch buckets or regions outside approved boundaries. SCP guardrails deny public buckets and off-limits services at the org level.
Logging / monitoring Organization-wide CloudTrail to immutable storage, plus GuardDuty or UEBA Every API call is recorded and analyzed; the SOC sees the whole story, not fragments. Org trail with data events, 90-day-hot retention, findings routed to the on-call path.
Backup Immutable, access-segregated backups Limits what a compromised cloud admin can destroy, including logs themselves. Backups and audit logs in a separate account with deny-by-default policies.
Response Rehearsed cloud identity playbook Key disable, session revocation, and user deletion happen in minutes, not days. Tabletop twice a year; measured mean time from alert to containment under one hour.

Home and small-office advice

Lock your logins

Use a unique password for every service and turn on MFA everywhere — app-based or hardware-key MFA beats text messages. A password manager makes this easy to keep up.

Review connected apps

Check the "connected applications" or "third-party access" pages in your cloud and SaaS accounts a few times a year. Remove anything you do not recognize or no longer use.

React to breach news fast

When a service you use reports a breach, change that password immediately and any place you reused it. Breach-notification checkers can tell you which of your addresses appeared in public dumps.

Common Mistakes and Best Practices

Eleven concrete blue-team mistakes seen in real programs, each with the symptom you will notice, the root cause, the fix, and the prevention that keeps it fixed.

1 · Ignoring false positives until analysts tune rules blind

  • Symptom: the same rule fires 200 times a day and gets auto-closed.
  • Root cause: the rule shipped without a baseline or allow-list.
  • Fix: measure the top offenders, add documented allow-lists, lower to shadow mode until noise is low.
  • Prevention: every new rule runs in shadow mode for two weeks before it can page.

2 · Alert fatigue as a staffing problem, not a design problem

  • Symptom: analysts skim queues and close everything as benign.
  • Root cause: too many low-signal rules tuned "on" by default.
  • Fix: rank rules by precision, retire or merge the worst 25 percent.
  • Prevention: a quarterly rule review with a kill list; precision, not volume, is the metric.

3 · Missing logs: S3 data events off, GitHub audit off

  • Symptom: you can prove login but not what was read; exfiltration is invisible.
  • Root cause: data events cost money and GitHub org logs need a plan, so both were skipped.
  • Fix: enable data events on sensitive buckets first; route GitHub audit logs to the SIEM.
  • Prevention: a logging coverage matrix per platform, reviewed each quarter against ATT&CK data sources.

4 · Weak tuning with hardcoded static values

  • Symptom: rules break silently when a new CI runner or country appears.
  • Root cause: allow-lists are frozen lists of IPs, never refreshed.
  • Fix: move to attributes that survive change — ASN, account IDs, principal names — and store allow-lists as data, not in the rule.
  • Prevention: treat detection code like product code: versioned, reviewed, tested.

5 · Ownership gaps: nobody owns cloud detections

  • Symptom: GuardDuty findings sit untriaged in a mailbox nobody reads.
  • Root cause: cloud team and security team each assume the other is watching.
  • Fix: name a detection owner per log source; route findings to a queue with an SLA.
  • Prevention: a named owner and backup for every detection source in the coverage matrix.

6 · Long-lived keys stored as CI variables

  • Symptom: a "deploy key" has worked for two years and nobody knows where the secret lives.
  • Root cause: OIDC federation was "planned" and the key became permanent.
  • Fix: migrate the pipeline to OIDC trust with a scoped role; delete the key.
  • Prevention: CI secret reports feed the quarterly access review; new keys need an expiry date.

7 · CloudTrail enabled in one account only

  • Symptom: incidents jump between accounts and the story stops at account borders.
  • Root cause: the trail was set up per-account during onboarding and never standardized.
  • Fix: an organization trail in a dedicated log-archive account; member accounts cannot stop it.
  • Prevention: guardrail policy (SCP) that forbids disabling the org trail.

8 · Trusting MFA to protect tokens and cookies

  • Symptom: "we have MFA" does not explain how the attacker stayed logged in.
  • Root cause: MFA gates the login, not the session; stolen cookies and OAuth tokens bypass it.
  • Fix: shorten session lifetimes, require re-auth for admin actions, monitor token issuance events.
  • Prevention: include token-abuse scenarios in purple-team exercises.

9 · Alerting only on console logins while data leaves through the API

  • Symptom: dashboards show quiet console activity during a massive GetObject week.
  • Root cause: detections were built for the visible UI path, not the API path.
  • Fix: baseline data-plane volume per principal and alert on cliffs (threat 1 and the case study both show this).
  • Prevention: every console detection gets an API-path sibling.

10 · Root monitored but roles not

  • Symptom: root alerts fire on schedule drills; role-chain sprawl goes unseen for months.
  • Root cause: root is unusual and easy to watch; roles are "normal" and quietly accumulate trust.
  • Fix: deploy the role-chaining rule (5.5 rule 4) and review trust policies quarterly.
  • Prevention: treat role creation like key creation: owner, purpose, expiry.

11 · Non-human identities have no owner

  • Symptom: an app registration or service account keeps calling the API years after the project ended.
  • Root cause: machines get keys and grants, but no human is named as their owner, so nobody removes them.
  • Fix: inventory every non-human identity, name an owner for each, and disable the ones no one claims.
  • Prevention: expiry dates on all machine credentials, checked in the quarterly access review.
The pattern behind the mistakes Most failures here are not rare or clever: missing coverage, unowned alerts, stale allow-lists, and console-only thinking. Each fix is boring, cheap, and available this quarter.

Habits for detection engineers

Daily

  • Review new access keys and IAM users created in the last 24 hours.
  • Check that the org trail and log pipelines delivered data for every region.
  • Look at top alert volumes; anything spiking gets triaged, not closed.

Weekly

  • Triage GuardDuty and UEBA findings end to end, including the ones marked low.
  • Review OAuth grants and app consents added during the week.
  • Test one detection against fresh lab telemetry to prove it still fires.

Monthly / quarterly

  • Quarterly audit of keys, roles, trust policies, and break-glass use.
  • Quarterly OAuth-grant review with service owners, removing dead grants.
  • Retire or retune the worst rules; publish the precision report to stakeholders.

Response checklist

  • Identify the principal and exact key ID or session from the alert.
  • Pull 24–72 hours of activity for that principal across all regions.
  • Disable the affected keys and revoke active sessions immediately.
  • Delete attacker-created users, keys, and OAuth grants; revert trust changes.
  • Rotate every secret connected to the leaked credential, including the repository.
  • Confirm no API activity from that principal after the revocation time.
  • Find and fix the leak source: repo commit, CI log, or misconfigured endpoint.
  • Record the timeline, notify stakeholders, and update the runbook and rules.
