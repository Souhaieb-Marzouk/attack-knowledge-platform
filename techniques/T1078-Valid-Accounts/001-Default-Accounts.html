T1078.001 Default Accounts

Default accounts ship enabled with passwords that anyone can look up on the vendor's website. Attackers use them to get in, keep access after other ways in are closed, and often land straight at admin level. ATT&CK lists this behavior under Initial Access, Persistence, Privilege Escalation, and Stealth (formerly Defense Evasion). This guide shows how the abuse works, what evidence it leaves, and how to detect it with Sigma and Splunk.

Tactics: Initial Access · Persistence · Privilege Escalation · Stealth (formerly Defense Evasion) Platforms: Containers · ESXi · IaaS · Identity Provider · Linux · macOS · Network Devices · Office Suite · SaaS · Windows Typical log sources: Logon Session · User Account (practical picks, not official ATT&CK mappings) Parent: T1078 Valid Accounts

01

Overview

What default accounts are, why attackers love them, and where they sit in the attack chain.

A default account is an account that a vendor or installer creates automatically. Its password is printed in the manual or published on the internet. Examples are the guest account on Windows, an appliance login of admin/admin, and a database account like sa or postgres with a blank or well-known password. The official ATT&CK page also names the root user in AWS, the root user on ESXi hypervisors, and the default service account in Kubernetes. The device or software works out of the box because these accounts exist. That convenience is also the danger.

Two problems combine here. First, the credential is public. The attacker does not need to steal it; they only need to guess the vendor and the model. Second, default accounts often sit outside normal monitoring. Nobody logs into them in daily work, so a login that does happen draws little attention and may not even reach a SIEM. An attacker who signs in with a default account gets a valid, trusted session instead of a loud exploit. That helps them stay hidden.

In the ATT&CK chain this sub-technique serves four jobs at once. It gives initial access when an internet-facing device still runs its factory password. It gives persistence, because a working default login keeps coming back until someone finds and closes it. It gives privilege escalation, because many defaults are admin-level from the first second. And it gives stealth — the tactic once called Defense Evasion — because a normal-looking login attracts far less attention than malware or an exploit. This page focuses on detection: you will learn the following things.

  • How attackers scan for and use default credentials, step by step.
  • Which log sources show default-account logins on devices, databases, cloud platforms, appliances, and endpoints.
  • How to rank the five most realistic threats for a mid-size enterprise.
  • How to write five production-ready Sigma rules and matching Splunk SPL queries, with tuning and false-positive guidance.
  • What the 2016 Mirai botnet teaches us, and which controls and habits close this door for good.

The default credential wall

Each device below shipped with a public factory login. Hardening turns the open badges into closed ones. The same idea applies to your estate: every device that keeps its default credential is a door that only the attacker has the key to.

ATT&CK ID

T1078.001

Child of T1078 Valid Accounts, which covers all use of legitimate credentials.

Tactics served

Four at once

Initial access, persistence, privilege escalation, and stealth (the tactic once called Defense Evasion) in a single login.

The written story, step by step

  1. Scanning. A rented server drives a scan grid that knocks on Telnet port 23 and on well-known admin URLs across huge IP ranges. It is looking for any device that answers with a login form. This is the same behavior the Mirai family made famous, and it never stopped.
  2. Found. One answer comes from a small-office IP camera. Its web banner names an old firmware version, and that version is listed in public default-credential tables as admin/admin. The attacker now has a username, a password, and a target, all without touching the device.
  3. Default login works. The attacker signs into the camera panel with admin/admin from a remote IP. The device writes a syslog line saying the admin login succeeded. Nobody at the office sees anything, because the camera's logs go nowhere.
  4. Malware drop. Using the panel's firmware-update function, the attacker pushes a small bot binary onto the camera. The device reboots and quietly runs the attacker's code with full device rights.
  5. Bot enlisted. The bot calls home, registers the camera with a botnet controller, and starts beaconing on a fixed schedule. From this moment the camera is a soldier in a distributed denial-of-service army, and its default account is the attacker's guaranteed way back in.
  6. Attack traffic. Weeks later the botnet is ordered to attack. The camera sends crafted DNS queries to open resolvers, which send large replies to the victim, hiding the true source. On the office link this shows up as a strong outbound traffic spike at 3 a.m., when nobody is working.
  7. SOC notice. A network monitor flags traffic from the office to a known-bad controller address. The analyst pulls device and firewall logs, finds the NetFlow spike, and traces back to the syslog line: a remote admin login on the camera with the default account. Three evidence chips now line up: the login, the spike, and the controller IP.
  8. Fix. The office owner updates the firmware, replaces the default password with a unique one, disables Telnet, and moves the camera to an isolated IoT VLAN. The device can still do its job, but it can no longer be a door into the office or a hidden attacker on the internet.
03

Red Team / Hacker Perspective

Why attackers pick default accounts first, how they find them at scale, and which mistakes they make. Everything here is framed for authorized lab testing and defense.

When and why an attacker uses defaults

  • Zero cost, zero theft. No phishing, no exploit, no malware needed for the first step. The password is on the vendor's website or in a public list.
  • Scale. One scanning loop can test millions of addresses for the same few hundred username and password pairs. Botnets were built around exactly this loop.
  • Valid login beats exploit. A default login produces a normal, authenticated session. It triggers fewer alarms than a memory corruption exploit and works even on patched software.
  • Built-in persistence. Unless someone finds the account, the attacker can log back in any time, even after passwords elsewhere are rotated.
  • Admin by default. Factory accounts usually have full rights on the device, so the attacker skips privilege escalation entirely.

Where default accounts appear

  • Network gear: routers, switches, access points, modems, VPN concentrators, firewall management interfaces.
  • IoT and physical security: IP cameras, DVRs, door controllers, printers, building management panels.
  • Databases: sa on SQL Server, blank postgres superuser, root on MySQL, default oracle accounts.
  • Cloud, hypervisors, and SaaS: the root account of a cloud tenant with no MFA (AWS names its root user directly), first-run global admin accounts, trial accounts never decommissioned.
  • Containers and hypervisors: the ESXi root user on host consoles, and the Kubernetes default service account that every pod gets when token mounting is left on.
  • Applications: first-run admin logins like admin/admin that setup wizards ask you to change and many people skip.
  • Endpoints: enabled guest or kiosk accounts on Windows and macOS images.

Prerequisites an attacker needs

  • The target service is reachable (internet-facing, or reached from an internal entry point).
  • The default account is still enabled and its password unchanged.
  • A public source matches the model to its factory credential: vendor manuals, support forums, or compiled credential lists.
  • No lockout or rate limit blocks repeated tries across a fleet.
  • No monitoring reacts to a default-account login.

Remove any one of these and the cheap path disappears. Monitoring alone is not enough, but it converts a silent breach into a detected one.

Common variations

  • Mass scan and spray: the botnet approach — probe port 23 and 80/443 banners, try the paired default list, install a bot.
  • Targeted appliance grab: pick one vulnerable appliance model, find exposed instances with a search engine, log in with the known default, change settings for later access.
  • Database landing: from a machine inside the network, try sa or blank-password postgres on discovered DB ports, then use database features to run commands.
  • Cloud root takeover: find tenants where the root or break-glass account has no MFA and is used daily, phish or reuse into it.
  • Guest account hop: log into an enabled guest or kiosk account to gain local access that is hard to tie to a person.
Lab only — ethics and law

Trying credentials against systems you do not own is illegal in most places, even if the password is printed in the manual. The same applies to any system you are not authorized in writing to test. Keep every exercise inside a lab you control, use placeholders like <lab-device-ip>, and never test real production or third-party equipment.

Attacker mistakes defenders should expect

  • Noisy scanning: thousands of connection attempts from one source IP are easy to spot in firewall and flow logs.
  • Default names left in device configs: attacker-set admin users or factory usernames appear in inventory scans.
  • Failed logins on locked-down defaults: the account was renamed or disabled, but the tries still land in auth logs.
  • Reused attacker infrastructure: the same controller IP touches many victim networks, so threat-intel feeds flag it quickly.
  • Beaconing patterns: fixed-interval callbacks from a device that should only talk when someone views its video stream.

What makes this sub-technique attractive in 2025

  • The IoT estate keeps growing faster than its logging and patching.
  • Leaked botnet source code keeps the scanning loop cheap for low-skill actors.
  • Cloud adoption creates new "first-run admin" accounts faster than teams can govern them.
  • Regulators now ask about default passwords directly, so a finding also has compliance weight.
04

Blue Team / SOC Perspective

Default-account use is one of the few techniques where the "normal" state is zero events. That makes detection simple in principle — if the logs reach you.

Why you can see it

A default account has no daily-work role. Any successful login with one is abnormal on its face. The hard part is not the logic; it is getting device, appliance, and database logs into the SIEM at all.

Where it fits in the chain

Default-account logins appear at the start of a chain (initial access) and again later as persistence and privilege escalation. Catching it early removes the attacker's cheapest re-entry door.

What it tells you

A hit means a hardening control failed somewhere: the inventory, the install checklist, or the change process. Treat every hit as both an incident and a process finding.

Device and appliance logs

Camera, router, and appliance syslog lines record admin logins with source IP. Ship them via syslog relay so the device survives without local storage.

Windows event logs

Event 4624 and 4625 record logons with Guest or built-in names; SQL Server writes login success and failure events for sa to the Application log.

Cloud and cluster control planes

CloudTrail captures root console sign-ins; Entra ID sign-in logs show global-admin logins. GuardDuty raises findings for root activity without MFA. ESXi host logs and Kubernetes audit logs cover the same pattern on hypervisors and clusters.

Triage flow when a default-account alert fires

  1. Step 1 — Confirm Confirm the account really is a factory default: check the vendor manual or your credential inventory. Note the exact username, source IP, time, and target.
  2. Step 2 — Scope Ask how wide this is. Search the same alert across all sites, devices, and databases. One hit usually means the same gap exists on sibling systems.
  3. Step 3 — Check what changed Pull config-change and account logs for the last 30 days on that target. Look for new users, changed settings, opened services, or disabled logging.
  4. Step 4 — Contain Disable remote management or block the source IP. Change or disable the default credential. Isolate the device on a management VLAN if it can reach sensitive networks.
  5. Step 5 — Hunt deeper For cloud and database hits, review actions taken in the session: what did the login do afterwards? For devices, look for beaconing after the login time.
  6. Step 6 — Eradicate Update firmware, remove attacker-added accounts or scheduled jobs, and factory-reset devices you cannot verify.
  7. Step 7 — Fix the process Feed the finding back: the install checklist, the golden image, or the vendor-procurement questions failed. Add the model to the external default-credential scan.
  8. Step 8 — Verify and report Re-scan to prove the default is gone. Confirm the alert fires a test event. Write a short report with the root cause and the closure evidence.
Practical tip

Build a one-page "default account registry": every default account that exists in your estate, its intended state (renamed, disabled, break-glass only), and its owner. Detection tuning becomes trivial when the registry answers "is this use ever legitimate?" for the analyst.

5.1Regulation Mapping

Default credentials are no longer only a technical hygiene issue. Several frameworks and laws now name them directly, and auditors ask for evidence that they were changed at install time and monitored afterwards. Use this table to connect your detection rules to the controls your auditors already track.

Why this helps detection

Framing rules this way turns a noisy "login with admin" alert into an auditable control test. Each Sigma rule in section 5.5 is evidence for at least one row above. That makes conversations with compliance teams much easier.

How confidence changes your action

High confidence means deploy: the behavior is verified by several credible sources, so write the detection and run the scan now. Moderate confidence means tune and observe: deploy in monitor mode or a lab first, because a single source may overstate scope. Low confidence (a lone unverified post) means document it and wait — do not burn an emergency change on it. In all cases, weight the intel against your own asset inventory. A campaign that targets devices you do not own is context, not a fire drill.

5.3Threats Ranking and Categorization

The five threats below are ranked for a typical mid-size enterprise. Assume it has some internet-facing devices, a mixed Windows and Linux server estate, one cloud tenant, and a handful of internal appliances. Re-rank them for your own estate: the ranking moves as soon as the preconditions change.

Threat #SeverityNamePlatform What happensPreconditionsImpactWhy this rank
T1 Critical Internet-exposed devices with vendor default credentials (IoT cameras, routers, NAS) Network A scan finds the device, the default login works, and the attacker enlists it into a botnet or pivots from it into the LAN. Device reachable from the internet; defaults unchanged; no lockout. Device enlisted into DDoS botnets; a pivot point into the internal network; your bandwidth and reputation abused. Mass exploitation at internet scale — the Mirai pattern still runs every day against every exposed address.
T2 Critical Enabled database default accounts (sa, postgres, MySQL root) Windows Linux An internal entry point or an exposed DB port is used to log in as the database superuser with a blank or well-known password. DB service reachable; default account not disabled or renamed; blank/known password. Full read and write on the data, plus code execution through database features; a direct path to the most sensitive data you hold. One login equals total data access; historical campaigns show destructive and ransom follow-ups.
T3 Critical Cloud root or global-admin accounts without MFA still in daily use Cloud Identity The most powerful account in the tenant is logged into directly, with no MFA and no break-glass process to prove who it was. The same pattern covers ESXi hypervisor root logins and the Kubernetes default service account. No MFA on root/global admin; no dedicated break-glass workflow; credentials guessed, reused, or phished. Total cloud control: billing, data, identity, and every workload can be changed or destroyed. One account owns everything. A single guessed or reused credential puts the whole tenant at risk.
T4 High Default admin portals on internal appliances (printers, UPS, VPN concentrators, switches) Network Someone with internal access — or reachability to an exposed admin UI — logs into the appliance with its factory password and changes settings. Admin UI reachable; appliance never hardened; management network not separated. Config changes, new hidden admin users, traffic interception, or relay attacks from the appliance. Appliances are rarely patched or re-imaged, so a default that survives install often survives for years.
T5 Medium Enabled guest or kiosk default accounts on endpoints Windows macOS Someone logs into a leftover guest account at the console or over the network, gaining an unattributed local session. Guest/kiosk account left enabled in the image; no lockout policy covering it. Local access without attribution; a base for staging; possible escape to higher rights if the OS is old. Limited rights keep the impact down, but it is a free, quiet way in that defeats attribution.

Severity legend

  • Critical — single event can cause enterprise-wide damage or total compromise of a system class.
  • High — serious damage to a system class or site; containment is straightforward but urgent.
  • Medium — bounded impact, useful for attackers mainly as a stepping stone.
  • Low — minor or local impact; mostly hygiene and compliance value.
How to read the ranking

Ranks assume a typical mid-size enterprise as described above. If your databases are never exposed and your cloud root is already locked, T2 and T3 drop; if you run hundreds of customer-facing cameras, T1 dominates. Severity answers "how bad if it happens", while the rank answers "how likely and how bad together".

5.4Logs and Patterns

Each threat below gets the same treatment: which logs carry the signal, which fields matter, what normal looks like, and what suspicious looks like. Each also gets the detection logic in one sentence. One realistic event example per threat follows, with a field-by-field explanation. The sources listed are practical picks chosen for this guide — not an official ATT&CK mapping.

T1 — Internet-exposed devices with vendor defaults

Log sourcesDevice syslog, appliance web/admin logs, firewall logs showing admin UI access, flow records
Key fieldshost, process, message, user, src_ip, action, uri, bytes_out
What normal looks likeAlmost nothing: admin logins only from the management VLAN during business hours, no inbound Telnet, flat outbound traffic.
What suspicious looks likeA successful admin or vendor-default login from a public IP, at 3 a.m., followed by firmware or setup pages being fetched, then new outbound flows.
Detection logic in one sentenceAlert when a successful login with a known default username arrives from outside the management address space.
  • Jan 12 03:14:07 — timestamp, not business hours; the classic window for automated scanning.
  • ipcam-cam14 — the device host; lets you jump straight to the asset record and its firmware level.
  • login[812] — the process that checked the password, so you can tell device logins from panel logins.
  • user=admin — the factory username; in a hardened estate this string should never authenticate successfully.
  • from 203.0.113.77 — a documentation-range stand-in for the external source; compare it against your public ranges.
  • GET /setup/firmware.cgi — the second line shows the session being used immediately: configuration pages fetched right after login.

T2 — Enabled database default accounts

Log sourcesSQL Server error/audit log (forwarded to the Windows Application log as 18454/18456), PostgreSQL and MySQL auth logs, Windows 4624/4625 for the underlying service logons
Key fieldsEventID, Message, ClientIp, user, database, state
What normal looks likeNo sa logins at all (the account is renamed or disabled); application service accounts authenticate from a small set of app-server IPs.
What suspicious looks likeAny successful 'sa' login, or bursts of 18456 failures for 'sa' followed by one success — a brute force that just landed.
Detection logic in one sentenceAlert on any login success or failure burst for a database default superuser name.
  • Error: 18456 — the failed-login event; State 8 means a wrong password, so repeated lines of this kind are a guessing attack.
  • Login succeeded for user 'sa' — the success event (18454 in event-log form); on a hardened server this line should be impossible.
  • Connection made using SQL Server authentication — SQL auth rather than Windows auth; a sign of a direct, script-driven client.
  • [CLIENT: 198.51.100.24] — the source address; attribute it to an app server, a workstation, or an external host.
  • The 84-second gap — failure burst then success is the fingerprint of the password being found.

T3 — Cloud root or global admin without MFA

Log sourcesAWS CloudTrail (ConsoleLogin), GuardDuty root-activity findings, Entra ID sign-in logs for global-admin roles, ESXi hostd and shell.log for root logins, Kubernetes audit logs for default service-account use, platform login alert emails
Key fieldseventName, userIdentity.type, sourceIPAddress, additionalEventData.MFAUsed, eventTime, responseElement.ConsoleLogin
What normal looks likeZero root console logons — root is stored in a vault, MFA-protected, and used only through a documented break-glass procedure a few times a year.
What suspicious looks likeAny root ConsoleLogin without a matching change ticket, especially with MFAUsed: No or from a new country or ASN.
Detection logic in one sentenceAlert on every root console sign-in, and raise the severity when MFA was not used.
  • userIdentity.type: Root — the decisive field; this is the tenant-owner account, not an assumed role.
  • eventName: ConsoleLogin — an interactive console sign-in, so a human (or a stolen cookie) was at the login page.
  • additionalEventData.MFAUsed: No — the second problem: the account worked with a password alone.
  • sourceIPAddress: 198.51.100.44 — attribute and compare with known admin locations; also note the missing arn user section, which is normal for root.
  • responseElement.ConsoleLogin: Success — failures carry FailedAuthentication; watch for failure bursts before a success.

T4 — Default admin portals on internal appliances

Log sourcesAppliance admin and config-change syslog, TACACS+/RADIUS accounting for managed devices, web server logs of embedded admin UIs, DHCP/inventory records
Key fieldssrc_ip, user, action, message, uri, status
What normal looks likeAdmin access only from the management subnet, tied to named accounts via TACACS+/RADIUS; config changes match change tickets.
What suspicious looks likeAdmin login or config change from a user or server subnet, with the factory account name (admin, root, vendor names), or from any IP that is not a jump host.
Detection logic in one sentenceAlert when an appliance admin action comes from outside the management subnet, or uses a default account name.
  • printer-3f — a floor printer, not a server; appliances like this are the classic forgotten estate.
  • 192.0.2.44 — source of the request; check whether this subnet is your management VLAN or an ordinary user network.
  • admin in the ident field — the factory username in use.
  • POST .../hpConfig with 200 — the configuration page accepted a change, not just a view.
  • configuration changed by ... (admin session) — the appliance's own confirmation that settings were altered; pair the two lines to get actor and action in one story.

T5 — Enabled guest or kiosk accounts on endpoints

Log sourcesWindows Security event log (4624/4625, 4722/4726), macOS unified log (loginwindow), EDR process and session data
Key fieldsEventID, TargetUserName, LogonType, IpAddress, WorkstationName, AuthenticationPackageName
What normal looks likeNo 4624 events for Guest — the account is disabled in the golden image and stays disabled.
What suspicious looks likeA 4624 success for Guest, or 4722 "account enabled" events flipping it back on, or guest logons over the network (LogonType 3).
Detection logic in one sentenceAlert on any successful logon with the guest account and on any event that re-enables it.
  • EventCode=4624 — a successful logon; the failed variant is 4625, useful to spot earlier attempts.
  • TargetUserName=Guest — the built-in default account; the built-in ANONYMOUS LOGON sessions are excluded from this rule to keep the signal clean.
  • LogonType=3 — a network logon, meaning someone reached shared resources remotely, not just the console.
  • IpAddress=192.0.2.55 — the peer that used the guest path.
  • Status=0x0 — success with no error; nothing here suggests a legitimate business process, because the guest account has no role in one.
Pattern to remember

All five threats share one shape: default username + success + wrong source or wrong time. If you can only afford a few rules, start with success events for default names; almost every estate can tolerate that alert volume, which is close to zero.

5.5Sigma Rules and Splunk SPL

Five original rules, one per threat. Each rule keeps the same promise: the condition should almost never be true in a hardened estate, so even a low alert volume is meaningful. Every rule is followed by a matching Splunk SPL query, the field-mapping assumptions, and tuning guidance. Adapt subnets and account names to your environment before deploying.

Threat 1 — Default admin login on a device from outside management High

Mapping note. The rule assumes a syslog TA that extracts user and src_ip; if your sourcetype keeps raw text only, extract them with rex from message (for example rex field=_raw "user=(?<user>\S+)"). The startswith filters in Sigma translate to cidrmatch() here, which is the cleaner way to express "outside management space".

Tuning

Start in monitor mode for two weeks. If first-run setups from vendors trigger, add their jump-host IPs to the filter list, never the account names. For VPN concentrators, raise the level to critical — a default login there is one step from your whole remote-access estate.

Threat 2 — SQL Server sa login Critical

Mapping note. Sigma EventID becomes Splunk EventCode, and the Windows TA maps the provider to Provider_Name. The client address lives inside Message text, so the query extracts client_ip with rex instead of relying on a CIM field. If your DBAs forward the SQL error log separately, point the same logic at that sourcetype.

Tuning

Add a companion search for 18456 failure bursts (EventCode=18456 Message="*'sa'*" with streamstats count over 5 minutes) — a burst followed by silence often means the password was found. The success rule itself should never be tuned down; migrate the application instead.

Threat 3 — AWS root console sign-in High

Mapping note. The AWS TA keeps CloudTrail field names nearly one-to-one, so userIdentity.type and responseElement.ConsoleLogin work as written; the account shows up as userIdentity.accountId (some TAs also expose aws_account_id — pick one and standardize). The nested additionalEventData.MFAUsed is a valid Splunk field reference once indexed.

Tuning

Add a second branch for ConsoleLogin failures from root (responseElement.ConsoleLogin=Failure) at low severity — failure bursts against root often precede a success. If your break-glass process uses a known source network, keep the alert anyway and check the ticket in triage; root use is rare enough to review every time.

The same idea extends beyond AWS. A root shell login on an ESXi host (from hostd or shell.log) deserves a sibling rule, and so does API activity that carries the Kubernetes default service-account token. Copy the rule shape and swap the logsource; the logic — alert on any use of an account that should be unused — stays the same.

Threat 4 — Appliance admin action from a non-management subnet Medium

Mapping note. Same syslog assumptions as Threat 1: src_ip and user must be extracted fields; on raw-only feeds use rex against _raw. The Sigma startswith name filter becomes a single match() regular expression in SPL, which behaves the same for these prefixes.

Tuning

For VPN concentrators and switches, treat the same event as high severity — a managed device with a changed config can reroute or mirror traffic. Keep a quarterly check that every appliance model in inventory is actually shipping logs to this index; silent appliances are the number-one reason this rule looks "quiet".

Threat 5 — Guest account logon on Windows Medium

Mapping note. The Splunk Add-on for Windows maps Sigma EventID to EventCode; TargetUserName, LogonType, IpAddress, and WorkstationName keep their names in CIM. The ANONYMOUS LOGON exclusion is kept implicit here — a 4624 for ANONYMOUS LOGON is indexed with that value in TargetUserName, so it cannot match Guest exactly; the Sigma |contains filter documents the intent for other backends.

Tuning

Add event 4722 (account enabled) with TargetUserName="Guest" as a second rule at high severity — re-enabling is the louder half of the pair. If kiosk devices legally use guest, list their hostnames in an allowlist lookup and alert only on hosts outside it.

06

Real-World Case Study

Mirai, 2016 — the largest default-credential campaign in history, and the reason this sub-technique has its own detection literature.

In 2016 a small group of actors built Mirai, a botnet that did almost nothing clever. It scanned the internet for Telnet-enabled devices. It tried a published table of about 61 default username/password pairs. Then it installed its bot on everything that answered. The victims were IP cameras, DVRs, and home routers — devices that nobody had hardening on any checklist. Hundreds of thousands of them joined the botnet.

With that army, Mirai produced the largest denial-of-service attacks the internet had seen at the time. The technical lesson is thin — change default passwords. The operational lesson is deep. An entire attack industry grew out of unmanaged, unlogged, default-credential devices, and it still shapes how we detect this technique today.

Timeline of public events

  • August – September 2016 Mirai scans and grows quietly. Security researchers notice record numbers of devices answering Telnet with factory credentials, but the botnet has not yet made headlines.
  • 20 September 2016 A DDoS attack of roughly 620 Gbps — a figure widely reported at the time — hits the security journalist Brian Krebs's website. It knocks the site offline and forces the hosting provider to drop it. It is one of the largest attacks ever measured at that point.
  • Late September 2016 French hosting provider OVH reports an attack peaking around 1 Tbps, as widely reported. The flood came from a botnet of cameras and DVRs — the same device classes that answer Telnet with default logins.
  • 30 September 2016 The author, using the alias "Anna-senpai", publishes the Mirai source code and the default credential table online, then disappears. Within days, dozens of forked botnets appear, which keeps the technique active to this day.
  • 21 October 2016 Mirai-derived attacks flood DNS provider Dyn. Major sites — Twitter, Netflix, Reddit, Spotify, and many others — become unreachable or unreliable for users on the US East Coast for hours.
  • 2017 and after Regulators and insurers begin asking about default credentials. The UK's PSTI Act and the EU Cyber Resilience Act later make shipping universal default passwords non-compliant for connected products.

Attack chain in six steps

  1. Scan the internet for devices answering on Telnet port 23.
  2. Match banners to a table of about 61 default username/password pairs.
  3. Log in with the default pair; the device grants full admin rights.
  4. Download the Mirai bot; the device joins the C2 network.
  5. The bot reports in and waits for attack commands.
  6. The controller orders DNS-amplification floods at the chosen victim.

Where detection would have fired

  • Best point: the default login itself — device syslog showing user=admin from an external IP (Threat 1 rule).
  • Second point: inbound Telnet attempts on port 23 at internet edge firewalls — volume alone is the signal.
  • Third point: the beaconing and NetFlow spike after enlistment — the SOC notice in our simulation (step 7).
  • What actually happened: almost none of these devices shipped logs anywhere, so detection happened only when attack traffic made the victim's provider call.

Containment and eradication

Providers blocked Telnet at the edge and sinkholed controller addresses. Device owners rebooted or reset infected hardware — often just by unplugging it. That cleared the bot, but not the default login.

Recovery

Victims of the DDoS attacks recovered by rerouting traffic and adding capacity; device owners recovered only when they changed factory passwords and updated firmware, or replaced the devices.

Impact and response

Hours of outage for major consumer services, reputational damage for the attacked brands, and a market-wide scare that pushed IoT security into boardrooms and then into law.

Team response and communication

No single company could stop Mirai, so the response worked as a chain of teams passing information to each other:

  • Researchers shared evidence fast. Teams who analyzed the Krebs attack published their findings, and the leaked source code was studied in public within days. This turned a mystery into shared knowledge.
  • Providers coordinated. Hosting companies and ISPs compared notes on scan sources, blocked abusive traffic, and sinkholed controller addresses.
  • Victims communicated status. During the Dyn attack, the provider posted frequent public status updates. That is now a standard incident-communication practice.
  • Device owners were reached late. Most camera and router owners never heard about the risk until vendors and ISPs sent advisories. The gap showed why default-credential warnings must reach buyers, not only security teams.

Lessons learned

  1. Change defaults at install, and verify. Trust the checklist, then scan anyway — the Mirai table worked because verification did not exist.
  2. Block legacy management protocols. Telnet had no place on these devices in 2016; it still does not.
  3. Segment IoT. A camera that cannot reach the office LAN cannot be a pivot, even when it is owned.
  4. Monitor device behavior, not just servers. The botnet was visible in flow data long before any victim felt it.
  5. Vendors must ship unique credentials. Regulation now enforces what operationally sane vendors already did.
  6. Assume the code is out there. After a leak, the technique becomes background radiation — detection must be permanent, not campaign-specific.
Why this case study fits T1078.001

Mirai used no exploits against the login step. Every infection started with a valid, expected username and a password printed in a manual — the purest form of default-account abuse. That is why external default-credential scanning and device-login monitoring became standard practice.

Mitigation and Defense

Closing the default-account door is mostly a process problem, not a technology problem. Find every default. Change or disable it at install time. Then verify with scans and logs forever after.

Home and small-office advice

Change the factory passwords

On your router, camera, and NAS, set a unique password on every admin account the day you unbox the device. Five minutes per device removes the easiest attack on your home network.

Turn off Telnet and UPnP

These convenience protocols are the paths botnets use. If a feature needs Telnet to work, the device is too old — replace it.

Update the firmware

Check for updates every few months. Vendors ship fixes for the exact bugs and default-logins that scanners hunt.

Use the guest network for IoT

Put cameras and smart devices on the guest SSID. If one is taken over, it cannot see your laptops or backups.

Do not expose admin panels

Never forward a camera or router admin page to the internet. Use the vendor's app or a VPN if you need remote access.

Ask before you buy

Prefer vendors that force a new password at first setup. Products sold in the UK and EU are now required not to ship universal defaults.

08

Common Mistakes and Best Practices

Ten concrete blue-team mistakes, each with the symptom you will notice, the root cause behind it, the fix, and the prevention that keeps it fixed. False positives, alert fatigue, missing logs, weak tuning, and ownership gaps all appear on this list on purpose — they come up again and again in real incidents.

1. Assuming "internal, so defaults are fine"

Symptom: a tester working from inside the network reaches the database tier in minutes during an exercise.
Root cause: the team treats network position as a credential control.
Fix: disable or rename every default DB and appliance account regardless of network zone.
Prevention: run internal default-credential checks in the annual test plan, not only external ones.

2. Scanning only from inside

Symptom: clean internal scan reports, yet an external researcher reports an exposed device.
Root cause: the scan ran from the management VLAN, which never sees the internet-facing exposure path.
Fix: add an authorized external sweep for admin panels and management ports.
Prevention: monthly external default-credential scan with a documented scope and a diff report.

3. Blocking port 23 but not admin HTTP

Symptom: devices stay reachable on 80/443/8080 with login forms after "Telnet is closed".
Root cause: the control targeted the protocol, not the exposure.
Fix: restrict all management interfaces to the management VLAN or VPN, whatever the port.
Prevention: external sweep checks web admin URLs too, and the firewall review includes them.

4. Renaming sa but leaving a blank-password postgres

Symptom: the SQL rule is quiet, yet the PostgreSQL host accepts a superuser session.
Root cause: default-account hardening was scoped to one product instead of the whole tier.
Fix: inventory every database product and disable or password its defaults the same week.
Prevention: tier-level hardening baseline with per-product checks and an owner each.

5. Cloud root has MFA but is used daily with no break-glass

Symptom: the root alert fires every day and everyone ignores it.
Root cause: MFA was treated as the whole control; the process side was never built.
Fix: move daily admin work to named roles, vault the root account, and require a ticket per break-glass use.
Prevention: a dashboard shows root usage — target zero, and investigate every point on it.

6. Guest account "disabled" — until a golden image re-enables it

Symptom: 4624 Guest events appear only on machines built after a certain date.
Root cause: the image template drifted from the hardening baseline and nobody diffed it.
Fix: fix the template, re-image affected hosts, and hunt for 4722 events that flipped it back on.
Prevention: image builds run the compliance scan in CI, and the guest rule alerts on enablement events.

7. Inventory misses shadow IoT

Symptom: the sweep finds cameras and DVRs that appear on no asset list.
Root cause: discovery relies on CMDB entries instead of network observation.
Fix: classify unknown devices from DHCP and flow data; give each one an owner or quarantine it.
Prevention: passive discovery runs continuously; new device classes trigger an onboarding review.

8. Vendor portal credentials shared across staff

Symptom: appliance logs show one "admin" user doing everything from many addresses.
Root cause: the device only supports one local account, and the team shared it.
Fix: front the device with TACACS+/RADIUS or a bastion that issues named sessions.
Prevention: procurement requires per-user identity support; shared accounts fail the purchase review.

9. Trusting "we changed it" instead of verifying

Symptom: attestation sheets say changed; the external sweep says otherwise.
Root cause: the control is a paper process with no verification loop.
Fix: test every attested change with a harmless authentication probe in the lab pattern and flag failures.
Prevention: monthly reconciliation between attestations and scan results, with an owner for the delta list.

10. Appliance logs onboarded but never tuned

Symptom: the rule fires constantly on background SNMP and web noise, so the SOC mutes it — alert fatigue wins.
Root cause: the rule shipped with no baseline window and no false-positive review; a classic weak-tuning and ownership gap.
Fix: spend two weeks in monitor mode, document the noise sources, add precise filters, then enable alerting with a named rule owner.
Prevention: every rule needs an owner, a tuning review each quarter, and a documented false-positive list.

The pattern behind the list

Almost every mistake above is a control that exists on paper but lacks a verification loop or an owner. Detection engineering is the discipline of closing exactly that gap.

Habits for a detection engineer

Daily

  • Check that cloud root usage is zero.
  • Review any default-account alert and link it to an asset and owner.
  • Glance at new external admin-panel exposure in the attack-surface feed.

Weekly

  • Diff the asset list against devices actually sending syslog.
  • Triage the false-positive backlog for the five rules; tune with data, not opinions.
  • Confirm golden-image compliance scans still show defaults disabled.

Monthly / quarterly

  • Run the monthly external default-credential sweep and assign findings.
  • Quarterly vendor-default review: new models in, old models out.
  • Re-verify attestations against scans and report the delta to the control owner.

Response checklist

  • Confirm the account is a documented factory default and note the exact username, source IP, target, and time.
  • Scope the search to all sibling devices, databases, and tenants before touching anything.
  • Check config-change and account-management logs for the last 30 days on the target.
  • Contain: block the source, change or disable the default credential, disable remote management if needed.
  • Hunt for follow-on activity: beaconing after device logins, data queries after database logins.
  • Eradicate: update firmware, remove attacker-added accounts, factory-reset devices you cannot verify.
  • Fix the process that let the default survive, and add the model to the external sweep scope.
  • Verify the fix with a re-scan and confirm the alert fires on a test event; close with a short report.
