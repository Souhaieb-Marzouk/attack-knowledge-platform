01

Overview

What a local account is, why attackers target it, and why password reuse turns a small problem into a fleet-wide one.

A local account lives on one device only. Its name and password are checked by the device itself, not by a central server. Windows stores local accounts in the SAM database (Security Account Manager — a protected file that holds password hashes for every local user). Linux and macOS keep local users in files such as /etc/passwd and /etc/shadow. Because the check is local, the same user name on two machines can have two different passwords — or, unfortunately, the same one.

Attackers care about local accounts for three reasons. First, reuse: many organizations install Windows from one golden image and set the same local admin password everywhere. One recovered credential can then unlock hundreds of machines. Second, power: a local administrator has full control of that endpoint — they can install services, read any file, and turn off protections. Third, blind spots: security teams usually watch domain logons closely, but local logons are monitored far less, so abuse goes unnoticed for longer.

In the attack chain, T1078.003 usually appears after the attacker already controls one machine. The attacker extracts a local credential, reuses it to reach other hosts, and keeps it for persistence. The official page lists four tactics. Initial Access — the valid credential can be the way in. Persistence — a valid account survives reboots. Privilege Escalation — a local admin account grants full endpoint control. Stealth (formerly Defense Evasion) — logons with valid credentials look like normal admin work.

How does this differ from domain account abuse (T1078.002)? A domain account is one identity valid everywhere in the domain. A local account is one identity per machine. It becomes dangerous when the same password is reused across machines.

Identity type Machine-local Checked by the device itself. No domain controller involved.

Core defense Unique passwords per host Windows LAPS gives every machine its own rotating admin password.
Term: RID 500

Windows gives every account a numeric Relative Identifier (RID). The first local administrator account created during setup always gets RID 500 and is called “Administrator”. Attackers target it for three reasons. It exists on every Windows machine. It cannot be deleted. And it often keeps a weak or old password — even after someone renames it.

Good to know

Renaming the RID 500 account hides its name but not its SID. Detection should match the SID pattern (S-1-5-21-…-500), not the account name. You will see this idea again in the Sigma rules in section 5.5.

STORYThe written story — eight steps

  1. Entry. The attacker sends an employee a fake installer. The employee runs it, and the attacker gets code execution on the laptop WKS-0231 as a normal user. Nothing about local accounts has happened yet — but the way in is open.
  2. Harvest. From the laptop, the attacker runs a small tool that reads the SAM database, the protected file that stores every local password hash. From those hashes the attacker recovers the password of the local admin account svc-backup. Any read of the SAM should be treated as credential theft.
  3. First hop. The attacker opens a remote desktop session to server SRV-A and logs on as svc-backup. The logon succeeds because the same local admin password was used when SRV-A was built. This is the first lateral movement with a valid account.
  4. Password reuse. The attacker tries the same credential on SRV-B. It works there too, because the golden image carried the same password. Two servers now answer to one recovered secret.
  5. Service install. To keep access after a reboot, the attacker installs a fake “backup” service on SRV-B. The service runs with local admin rights and starts automatically. A new service install on a server is always worth a look.
  6. Broad sweep. The attacker tries the credential across the whole subnet. Five more machines accept it, and a burst of failed logons (4625) mixes with successful ones (4624). That mixed pattern is loud, but only if someone is counting.
  7. SOC alert. The SOC correlates the alerts: one local admin account, many unique hosts, and a brand-new service. Three weak signals become one strong incident instead of three ignored ones.
  8. Response. Analysts isolate the affected hosts, rotate every local admin password with LAPS, remove the fake service, and review recently created accounts. After rotation, the recovered password opens nothing.

03

Red Team / Hacker Perspective

Why an attacker picks local accounts, what they need before starting, and which habits give them away. All commands below are lab-only and use placeholders — never run techniques against systems you do not own.

Persistence

A valid local account keeps working after reboots, malware cleanups, and password policy changes. It does not need a running process, so it survives most cleanup scripts that only remove binaries.

Privilege escalation

If the harvested account is a member of the local Administrators group, the attacker instantly owns the endpoint: any file, any service, any scheduled task. On servers, that means data and the next hop.

Stealth (formerly Defense Evasion)

Logons with valid credentials look like routine admin work. Antivirus sees nothing malicious in a successful logon, so the attacker stays hidden instead of fighting the security tools.

When and where attackers use it

Local account abuse fits two moments in an intrusion. Early: right after the first compromised machine, to reach nearby servers. Late: before ransomware deployment, when operators spread with valid admin credentials and remote-management tools. It works best in flat networks where workstations and servers share subnets. It also works wherever remote services (RDP, SSH, WinRM) accept local accounts.

Prerequisites — what must be true first

  • Code execution or interactive access on at least one host.
  • Admin or SYSTEM rights on that host to read the local credential store — or a guessable password.
  • RDP, SSH, or WinRM reachable from the attacker’s position.
  • Local logon rights not restricted to specific accounts.
  • No unique per-host password management (no LAPS, no key rotation).
  • No baseline of “which local account logs on where”.

METHODHow it is performed — four moves

  1. Harvest. Extract local credential material from the compromised host (Windows SAM, Linux password files, macOS local records). This is the step defenders must alert on.
  2. Crack or reuse. Recover plaintext from hashes offline. Or replay the stolen hash itself — a method called pass-the-hash, where the secret proof is used without ever learning the password. Weak local passwords fall in seconds.
  3. Log on remotely. Use the valid credential against RDP, SSH, or WinRM on other machines. Every successful logon writes a clean, verifiable event.
  4. Persist. Create or enable another local account, install a service, or plant an SSH key so access survives reboots.

VARIANTSCommon variations

RID 500 rename and reuse

Attackers (and sloppy admins) keep using the built-in Administrator even when it is renamed. The SID still ends in -500, so SID-based detection catches it regardless of the name.

Rogue accounts disguised as services

New accounts with names like svc-sqlagent, backup_adm, or support look boring on purpose. Without an inventory or a baseline, nobody questions them for months.

Planted SSH keys for root

On Linux, adding a line to /root/.ssh/authorized_keys is the key-based version of creating a local account. It leaves almost no log noise until the key is used.

Hidden macOS admin users

On macOS, accounts with a UID below 500 do not appear on the login window. A hidden admin account is a quiet persistence trick that a simple user-list review will catch.

Attacker mistakes defenders should expect
  • Logging on from a workstation that has never touched that server before — a hard anomaly to miss.
  • Using the same account on many hosts within minutes, which turns quiet logons into a countable pattern.
  • Leaving a burst of 4625 failed-logon events behind a subnet sweep.
  • Creating several accounts with sequential timestamps, all from the same admin session.
  • Installing services with obvious names or script interpreters in the service path.
04

Blue Team / SOC Perspective

Local account abuse leaves surprisingly complete records. This section shows where to look, which events matter, and a triage flow you can run during an incident.

VISIBILITYWhere defenders can see it

Windows Security event log

The richest source. Logon events (4624/4625), special privileges (4672), account creation (4720), and service installs (7045) together tell the whole story. Forward with LogonType preserved.

Linux auth logs

auth.log or secure records accepted and failed SSH logons, sudo use, and account changes. Ship them to your SIEM; they are small and high-value.

macOS unified log

The unified log records logon window activity, sudo, and OpenDirectory events. Collect at least the security-relevant streams from macs in your fleet.

EDR telemetry

Endpoint agents see process trees and file access: who read the SAM, who touched /etc/shadow, who ran net user /add. This is often the earliest signal.

SIEM correlation

Single events look innocent. Correlation across hosts — one account, many machines, minutes apart — is what turns logons into an incident.

LAPS rotation logs

Windows LAPS records every password rotation. Gaps in rotation history point to stale passwords — the fuel for threat 1 and threat 5.

Why it matters here

Rules 1 and 2 in section 5.5 only look at LogonType 2 and 10. Those are the types that mean “a person, or something pretending to be one, is using this account”. Service and network logons (5 and 3) are constant background noise that would bury the signal.

Why this matters in the chain

Credential harvesting (T1003.002), remote services (T1021.001 / T1021.004), and account creation (T1136.001) all feed T1078.003. If you can answer “which local account logged on to which host, from where, and when”, you can catch the whole chain early — usually at the first hop, before data theft or encryption.

TRIAGETriage flow — first 60 minutes

  1. 1 · Confirm the account

    Which local account fired the alert? Check its SID: does it end in -500? Is it in the local Administrators group? Does it exist in your account inventory?

  2. 2 · Check the logon pattern

    Count unique hosts the account touched in 24 hours, with LogonType and source IP. More than a handful of hosts for a local account is already abnormal.

  3. 3 · Look for credential access

    Search EDR and Sysmon for SAM, /etc/shadow, or LSASS access on the source machine. Harvest explains how the password leaked.

  4. 4 · Sweep for persistence

    Query 4720/4722/4724 and 7045 on every host the account touched. Look for new services, new accounts, and new SSH keys in the same window.

  5. 5 · Map every affected host

    List all successful logons (4624) by the same account across the fleet, plus failed logons (4625) from the same source. This is your containment list.

  6. 6 · Contain and rotate

    Isolate affected hosts, disable the account, force rotation of local admin passwords (LAPS) on the whole subnet — not just the obvious hosts.

  7. 7 · Close the loop

    Remove persistence, review how the first host was reached, and file the detection gaps you found as engineering tickets.

5.3Threats Ranking and Categorization

The five threats below are the realistic ways T1078.003 hurts an organization. Ranking assumes a typical mid-size enterprise: a few hundred to a few thousand Windows endpoints, plus some Linux servers. One SOC team handles alerts; there is no dedicated identity team. Numbers 1–5 are used consistently in sections 5.4 and 5.5.

ThreatNamePlatformWhat happensPreconditionsImpactWhy this rank
1 Critical Same local admin password reused across many hosts Windows One harvested credential unlocks dozens or hundreds of machines; the attacker spreads without any exploit. Golden-image deployment habits; no LAPS or equivalent; flat network reachability. Fleet-wide takeover from one endpoint; ransomware pre-staging everywhere. Widest exposure of any local-account flaw — one secret equals the whole fleet.
2 High RDP logons with local accounts, especially RID 500 Windows Attackers log on to servers over RDP with the built-in Administrator or another local admin. 4 High Attacker-created local account used for access and persistence Windows · Linux · macOS After gaining admin on one host, the attacker creates a new local account (or enables a disabled one) and uses it to return. Admin rights on at least one host; no baseline of expected local accounts. Durable, quiet access that survives reboots and malware cleanups. New accounts look legitimate unless someone compares them against an inventory.
5 Medium Stale local service or backup accounts still enabled Windows macOS Forgotten service/backup accounts with old passwords remain active and are discovered by the attacker (or already known from old breaches). Severity legend

Critical — one step from fleet compromise; fix within days. High — reliable attacker path with major impact; fix this sprint. Medium — real risk, often needs luck or time to exploit; fix this quarter. Low — hardening item; schedule normally.

Ranking assumptions

These ranks shift with your reality. An internet-exposed RDP box pushes threat 2 toward critical. A hard-isolated OT network can push threat 1 down. Revisit the ranking after every architecture change — and after every incident.

5.4Logs and Patterns

For each threat you get the log sources that cover it, the fields that matter, and one event-shaped example you can hand to your SIEM team. You also see what normal looks like, what suspicious looks like, and the detection logic in one sentence. Field names follow the raw Windows event and standard syslog formats; your SIEM may rename them (see the mapping notes in 5.5).

Threat 1 — Same local admin password reused across many hosts

Critical
  • Log sourcesWindows Security log (4624/4625) from every host into one SIEM; EDR credential-store alerts; LAPS rotation logs.
  • Key fieldsEventID, TargetUserName, LogonType, Computer, IpAddress, WorkstationName
  • NormalEach local admin account logs on rarely and locally: a few times per month on one or two known hosts. LAPS rotates passwords silently.
  • SuspiciousOne local account name appearing on many unique Computer values within minutes, with logons flowing from a workstation subnet toward server subnets.
Detection logic

Count distinct destination hosts per local account per 15 minutes; any account crossing a small threshold (5–10) is lateral movement, not admin work.

Before the logons happen, the attacker must read the credential store. EDR or Sysmon shows that first:

  • alert_name/target_file — a read of the SAM hive is credential theft in progress; legit software almost never does it.
  • user — a normal user context (not SYSTEM) reading SAM means the process already escalated. Treat as incident, not anomaly.
  • process/cmdline — the technique tag links to T1003.002 (SAM), the usual feeder for T1078.003.

And the reuse itself, seen as one row per host in the SIEM:

  • LogonType=10 — remote interactive (RDP) logon. Type 2 means at the console; both are “interactive” for our purpose.
  • TargetUserName=svc-backup — a local account logging on remotely; the real signal comes from many hosts showing the same name.
  • TargetUserSid — a machine SID prefix unique to one host proves the account is local, not domain.
  • IpAddress=10.20.4.61 / WorkstationName=WKS-0231 — the same source appearing on dozens of hosts turns quiet reuse into a countable pattern.

Right next to those successes live the failures — and the ratio between them is often the loudest single clue during a sweep:

  • SubStatus=0xC000006A — “wrong password”. A run of 0xC000006A from one source means guessing; 0xC0000072 means the account is disabled, which tells you the sweep found a stale account (threat 5).
  • FailureReason=%%2313 — “unknown user name or bad password”; pair it with SubStatus for the precise story.
  • LogonType=10 — the attacker is still using RDP; failed RDP attempts against many servers from one workstation is a critical-hunt query on its own.

Threat 2 — RDP logons with local accounts, especially RID 500

High
  • Log sourcesWindows Security log 4624 (LogonType 10) with TargetUserSid preserved; 4672 for privilege confirmation; RDP gateway logs if you have one.
  • Key fieldsLogonType, TargetUserSid (ends -500), TargetUserName, IpAddress, WorkstationName
  • NormalOnly named break-glass hosts (jump hosts) reach servers over RDP; RID 500 itself logs on at the console a few times a year, if ever.
  • SuspiciousA -500 SID logging on with LogonType 10 from any source that is not a registered jump host — especially from a user workstation or the internet.
Detection logic

RDP (LogonType 10) logon where the target SID ends in -500 and the source is not an approved jump host is an alert every time; the SID survives renames.

  • TargetUserSid …-500 — the account was renamed to adm-service, but the SID still marks it as the built-in Administrator.
  • LogonType=10 — remote interactive; the built-in admin almost never needs RDP in a well-run shop.
  • WorkstationName=WKS-0231 — a user laptop as the RDP client is the tuning filter this page’s Sigma rule uses to cut jump-host noise.

Threat 3 — Root SSH keys or root password valid on many servers

High
  • Log sourcesLinux auth.log / secure (sshd, sudo, useradd); file-integrity monitoring on authorized_keys; bastion session logs.
  • Key fieldssshd Accepted password/publickey for root, src IP, host, sudo USER=root, COMMAND=
  • NormalEngineers log on with personal accounts and elevate with sudo, from a small set of jump hosts. Direct root logon is disabled or rare.
  • Suspicious“Accepted password for root” from anywhere; “Accepted publickey for root” from a source that is not your bastion; sudo-to-root from new IPs.
Detection logic

Any accepted root logon (password or key) that does not come from the registered bastion subnet is an incident — root should never authenticate remotely in a hardened fleet.

  • Accepted password for root — the exact phrase to alert on; password root logons are forbidden on hardened servers.
  • from 10.20.4.61 — a workstation IP, not the bastion; this is the “unexpected source” half of the rule.
  • sudo … USER=root ; COMMAND= — the normal escalation path, useful as a baseline to compare against direct root logons.

Threat 4 — Attacker-created local account used for access

High
  • Log sourcesWindows Security 4720/4722/4724 (create, enable, reset) paired with 4624 for the same name; Linux useradd/usermod in auth logs; macOS OpenDirectory events.
  • Key fieldsTargetUserName, SubjectUserName, TargetSid, UserWorkstations, UserAccountControl, later LogonType
  • NormalLocal account creation is rare and planned: helpdesk tools, build agents — each with a change ticket. New accounts log on rarely at first.
  • SuspiciousAn account created and then used for an interactive logon within the hour, created from a session that just harvested credentials, or named like a service.
Detection logic

Pair every 4720 with a 4624 for the same account within one hour; creation plus immediate use is the attacker pattern, since real provisioning takes longer.

  • SubjectUserName=svc-backup — the actor is itself the compromised local admin; creation happened inside the attacker’s session.
  • TargetUserName=svc-sqlagent — a deliberately boring, service-like name; the disguise only works where no inventory exists.
  • UserAccountControl=%%512 %%2080 — 512 = normal account enabled; watch for 66048 (password never expires) too.
  • AccountExpires=<never> — attacker accounts never expire; real, managed accounts usually do or are reviewed.

Threat 5 — Stale service/backup accounts, and the 7045 trail

Medium
  • Log sourcesWindows System log 7045 (service installed); SCM operational logs; EDR service-creation events; configuration-management drift reports.
  • Key fieldsServiceName, ImagePath, AccountName, ServiceType, StartType
  • NormalNew services arrive from software deployment with matching tickets, run from Program Files, and use managed service accounts or LocalSystem with signed binaries.
  • SuspiciousA new service that runs as a named local account (.\svc-…), or as LocalSystem with a script interpreter in the path, installed from a Temp folder.
Detection logic

Flag every 7045 whose run-as account is a named local user, or whose ImagePath points at an interpreter or a user-writable directory; allowlist the rest by exact path.

  • ServiceName=WinRmBackupSvc — a name chosen to blend in with management tooling; compare against your service inventory, not against a feeling.
  • ImagePath=C:\Windows\Temp\… — services never legitimately live in Temp; path alone is worth an alert.
  • AccountName=LocalSystem — the most common run-as for both real software and malware, which is why the rule pairs it with the ImagePath filter.
  • StartType=auto start — persistence: the service returns after every reboot without any user action.
Putting the patterns together

One threat on its own can be argued away. The combination cannot. A store-access alert (threat 1), a first RDP hop (threat 2), a created-then-used account (threat 4), and a Temp-path service (threat 5) tell one intrusion story from four angles. Your correlation rule in 5.5 rule 1 is the glue.

5.5Sigma Rules and Splunk SPL

Five original rules — one per threat. Each rule is valid Sigma YAML with the full key set. Each is followed by a matching Splunk SPL query, a field-mapping note, false positives, and tuning guidance. Sigma is a vendor-neutral rule format; SPL is Splunk’s search language. Adapt index names, subnets, and allowlists to your environment before deploying.

Rule 1 — Fleet-wide logon spread by one local account

CriticalWindows
  • Field mappingSigma Computer is the destination host; Splunk keeps it as Computer (or CIM dest). TargetUserName maps to TargetUserName / CIM user. Adjust index (wineventlog) to your naming.
  • False positivesDeployment tooling, monitoring agents that test logons, mass reimages during refresh cycles.
  • TuningStart in monitor mode with the threshold at 10; lower to 5 after you learn your deployment patterns. Keep the jump-host source allowlist current.

Rule 2 — RID 500 over RDP from a non-jump workstation

HighWindows
  • Field mappingThe Splunk Add-on for Windows renames Sigma TargetSid to Target_User_SID; WorkstationName and IpAddress keep their raw names (CIM: src/src_ip).
  • False positivesLegacy applications that must log on as RID 500; missed allowlist entries during a server migration.
  • TuningKeep the allowlist on WorkstationName prefixes and review it quarterly. If you must allow one host permanently, document it as break-glass with an owner.

Rule 3 — Direct root logon or sudo-to-root from an unexpected source

HighLinux
  • Field mappingSigma message is the raw syslog line; the Splunk Add-on for Unix/Linux extracts src, user, and host from sshd lines. sudo lines often lack src — pair with bastion session logs for full source data.
  • False positivesCI runners with passwordless sudo; break-glass sessions from an unlisted VPN pool.
  • TuningKeep the bastion list as data, not in the rule text, if your SIEM supports lookups. Add host allowlists for database clusters that must self-manage.

Rule 4 — Local account created and used for logon within one hour

HighWindows
  • Field mappingBoth events carry TargetUserName, so the correlation key transfers directly. Sigma’s near operator approximates time proximity; exact account matching is what the SPL transaction adds. Note: transaction is memory-hungry — for busy estates replace it with streamstats over a 1-hour window.
  • False positivesAutomated provisioning that verifies the account by logging on; gold-image build pipelines.
  • TuningExclude known provisioning servers by SubjectUserName allowlist. If volume stays high, add a TargetUserName naming filter (for example svc-, adm-) and review the rest weekly.

Rule 5 — New service installed to run as a local account

MediumWindows
  • Field mapping7045 lives in the System log, not Security — the SPL source and Sigma logsource reflect that. AccountName=".\\*" means a literal dot-backslash prefix (a named local user). Some agents render LocalSystem as NT AUTHORITY\SYSTEM; normalize before matching.
  • False positivesBackup agents, printers, and legacy apps that run as a named local account; deployment systems staging script wrappers.
  • TuningAllowlist exact ImagePath values for reviewed software, never whole folders. Add StartType=disabled tracking so a flagged service cannot silently return.
Coverage summary

Rule 1 catches the spread, rule 2 the RID 500 hop, rule 3 the Linux mirror, rule 4 the created-and-used account, and rule 5 the persistence install. Together they cover all five threats from section 5.3 with one or two log sources per platform — a realistic starting pack for any SOC.

06

Real-World Case Study

SamSam ransomware, 2016–2018 — the clearest public example of valid-credential abuse at scale, including the City of Atlanta incident.

Between 2016 and 2018, the SamSam operators ran a ransomware business with a simple model. They skipped phishing. They bought working remote-access credentials on criminal markets. They also brute-forced weak passwords on internet-facing RDP endpoints. Once inside, they moved quietly with valid admin credentials, studied the network, and encrypted targets manually — city governments, hospitals, and universities. The US Department of Justice indicted two Iranian actors for the campaign in November 2018.

TIMELINEContext and timeline

WhenWhat happenedWhy it matters here
2016–2017SamSam campaign begins; victims found through exposed RDP and weak credentials.Valid local/admin credentials were the product being traded — exactly T1078.003 territory.
Early 2018SamSam hits healthcare and public-sector victims including hospitals and lab networks.Operators used purchased access, so logons came from “valid” accounts — hard to block, easy to spot if watched.
March 2018City of Atlanta infected: about 342 applications affected; the city refused the ransom.Recovery widely reported at roughly $17M, with days-to-weeks of downtime for city services.
November 2018DOJ indictment details the playbook: RDP access, credential use, manual deployment.Public record confirms the detection points this page teaches: 4624 Type 10, 7045, service churn.

CHAINAttack chain, step by step

  1. Acquire access. Buy working RDP credentials from an access market, or brute-force weak passwords on internet-exposed RDP endpoints.
  2. Log on with valid credentials. Enter through RDP using local admin accounts. Logons succeed on the first try — no exploit noise, no failed-logon storm.
  3. Reconnoiter quietly. Map servers and shares using built-in tools, staying inside sessions that look like normal administration.
  4. Disable safety nets. Stop or uninstall security services and delete backup jobs — actions that are invisible unless service and process events are monitored.
  5. Stage and spread. Copy the encryption tooling to multiple hosts, installing services or scheduled tasks to launch it everywhere at once.
  6. Encrypt and demand. Trigger encryption across their targets manually, then leave ransom notes. The manual pace is why log evidence piles up for days before the encryption starts.
The detection point that was missed

Every step above wrote evidence: RDP logons (4624 LogonType 10) from unexpected sources, new services (7045), and security-tool changes. In the SamSam pattern, weeks passed between the first valid logon and encryption. A single 4624 Type 10 alert on the RID 500 account would have surfaced the intrusion. A “one account, many hosts” correlation would have found it too — while containment was still cheap.

Containment

Cut remote access at the gateway, isolate known-affected hosts, and rotate every credential the attackers could hold — local admin passwords first, because they unlock the most doors.

Eradication

Remove attacker services and tasks, review every local account created or enabled during the window, and close the RDP exposure that let them in.

Recovery

Restore from clean offline backups, verify integrity before reconnecting, and watch re-entry attempts — operators return to check if their credentials still work.

IMPACTImpact, consequences, and communication

The real economics are stark. Widely reported figures put Atlanta’s recovery cost at roughly $17M — against a ransom demand of about $51,000 in cryptocurrency. The ransom is the small number. Some city systems were down for days, some for weeks. Courts, police record requests, and utility payments moved to manual paper processes. The incident team faced a second problem beyond technology — communication. Council members, courts, and the public needed honest, regular updates. Responders avoided details that could help the attackers. The lesson for any SOC: prepare the communication track before you need it.

LESSONSLessons learned

  • Never expose RDP directly to the internet. Gate it behind VPN plus MFA or an RD Gateway; most SamSam victims were reached through open RDP.
  • Watch 4624 Type 10 closely. Remote interactive logons by local accounts, especially RID 500, are the entry signature of this entire class of attack.
  • Manage local admin passwords centrally. LAPS-style unique, rotating passwords would have blunted every purchased credential in the campaign.
  • Keep offline backups and test restoration. Atlanta refused to pay partly because recovery was possible — but the cost shows how much restoration practice matters.
  • Treat new services and account changes as incidents in waiting. 7045 and 4720 events during the quiet weeks were the advance warnings.
  • Plan communications in advance. A practiced notification path keeps leadership, staff, and the public aligned while responders work.

HOMEHome and small-office advice

Use a standard account daily

Do everyday work in a normal (non-admin) user account. Malware that runs as you cannot change system settings or read other users’ files.

Keep one separate admin account

Create one account for installing software, with a strong, unique password. Enter it only when a task truly needs it.

Disable the guest account

The built-in guest account is a free door. Turn it off on every home Windows machine and check that no extra “helper” accounts exist.

Never reuse the admin password

Give each computer its own admin password — even at home. Write them in a password manager, not on the router box.

Close remote access

Home routers should not forward RDP, SSH, or VNC ports. Use your VPN app if you must reach a machine from outside.

Update the router and devices

Firmware updates close the holes that let attackers reach local login screens in the first place.

Common Mistakes and Best Practices

Ten blue-team mistakes we see again and again, each with the symptom, the root cause, the fix, and the prevention. If your team owns only one section of this page, make it this one.

1 · One local admin password in the golden image

  • SymptomThe same account name appears on hundreds of hosts in 4624 logs.
  • Root causeThe image was built with a static admin password “to make deployment easy”.
  • FixDeploy LAPS and rotate every host immediately; treat the old password as compromised.
  • PreventionBlock image publication until per-host secrets are verified by pipeline check.

2 · RDP open “temporarily” — forever

  • SymptomDaily failed-logon storms from foreign IPs on port 3389.
  • Root causeA vendor fix-it session in 2019; nobody owned closing it.
  • FixClose the port, route through VPN/RD Gateway, force MFA.
  • PreventionContinuous external attack-surface scan with alerting on new open ports.

3 · Only domain logons are monitored

  • SymptomThe SIEM has rich domain-controller coverage but almost no server Security logs.
  • Root causeLogon monitoring was scoped to the DCs; local accounts were “out of scope”.
  • FixForward Security/System logs from all servers and at least a workstation sample.
  • PreventionCoverage report per host class reviewed quarterly — log absence is a finding.

4 · 4720 events ignored

  • SymptomRogue accounts found during an incident existed for months.
  • Root causeNo alert, no owner — creation events were never reviewed.
  • FixAlert on 4720 (rule 4) and reconcile against the inventory weekly.
  • PreventionWeekly new-local-account review as a standing SOC task with a checklist.

5 · Service installs never reviewed

  • SymptomPersistence found only because ransomware fired, not because 7045 was watched.
  • Root cause“Services are normal” — true, which is why nobody looked closer.
  • FixDeploy rule 5; review every new service on servers within one business day.
  • PreventionService allowlist per host class, fed by the deployment system.

6 · LAPS deployed but rotation disabled

  • SymptomLAPS reports “managed”, but PasswordLastSet is years old on many hosts.
  • Root causeRotation broke during a policy migration; nobody monitored the health check.
  • FixRe-enable rotation, force immediate reset on stale hosts.
  • PreventionMonthly LAPS health check with a dashboard and an owner (see habits below).

7 · Root SSH “just for troubleshooting”

  • SymptomAccepted root logons from many source IPs in auth.log.
  • Root causeA hardening exception from a rushed project; the exception outlived the project.
  • FixSet PermitRootLogin no, rotate root keys, move access behind sudo + bastion.
  • PreventionConfig-management check that reverts PermitRootLogin on drift; rule 3 alerting.

8 · No inventory of local accounts

  • SymptomNobody can answer “which local accounts should exist on SRV-B?”
  • Root causeInventory focused on AD; local identities fell between teams.
  • FixScheduled scan (Get-LocalUser, /etc/passwd) feeding a central inventory.
  • PreventionAlert on any account that is active but absent from the approved list.

9 · 4624 alerts without a LogonType filter

  • SymptomThe alert fires thousands of times a day and analysts mute it.
  • Root causeRule counts all logons, including service (type 5) and network (type 3) noise.
  • FixFilter to LogonType 2 and 10; baseline per account before paging.
  • PreventionEvery logon rule must state its LogonType logic and expected daily volume.

10 · No baseline of normal local logons

  • SymptomTrue positives were lost among “unusual” logons that were actually routine.
  • Root causeDetections written without first learning the environment’s normal.
  • FixTwo-week learning period per rule; per-account/per-host baselines in the SIEM.
  • PreventionRe-baseline after major changes; document expected logon pairs (account × host).
The five traps behind most failures

False positives — every rule needs documented FPs and a tuning owner, or it dies. Alert fatigue — volume targets belong in rule design: if a rule averages 200 alerts a day, it is broken, not the analysts. Missing logs — a detection you cannot test against real data is a guess; verify collection before writing logic. Weak tuning — allowlists must be exact values with owners, never whole ranges “for now”. Ownership gaps — every rule, allowlist, and exception needs a name attached; unowned rules rot silently.

HABITSDetection engineer habits

Daily

  • Review new 4720/7045 events on servers.
  • Check rule health: volumes vs. expected.
  • Close or escalate open local-account alerts.

Weekly

  • Review new local accounts fleet-wide (rule 4 hits).
  • Reconcile services against the allowlist.
  • Test one detection with a synthetic event.

Monthly

  • LAPS health check: rotation coverage and age.
  • Update FP documentation and thresholds.
  • Re-run the account inventory diff.
Quarterly

Audit local Administrators group membership on every host, re-rank the threats in 5.3 against your current architecture, and table-top the rotation playbook from section 7 with the response team.
