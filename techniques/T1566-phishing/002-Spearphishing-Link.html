T1566.002 Spearphishing Link

Spearphishing Link is a targeted email attack that uses a link instead of an attachment. The message looks like it comes from a trusted person or service. When the victim clicks the link, a fake page steals their password, a multi-factor code, or even their signed-in browser session. This guide explains the whole attack and shows you how to detect it step by step.

    Overview

    Before you can detect an attack, you must understand it. This section explains what Spearphishing Link is, why it is so effective, and where it sits in the attack chain.

    What is this technique?

    In a spearphishing link attack, an attacker sends a targeted message that contains a link instead of a file attachment. The word “spear” means the message is written for one person or a small group, not for millions of random victims. The attacker researches the target first and makes the message look like normal work email.

    The link points to a website the attacker controls. In the most dangerous form, called adversary-in-the-middle (AiTM), the fake page sits between the victim and the real login portal. The victim sees a perfect copy of the real page. When the victim types their password and approves a push notification or a one-time code, the attacker collects all of it in real time, plus the session cookie that proves the victim is already logged in.

    Why it matters

    Most big security incidents start with one clicked link. A link is harder to catch than an attachment because the email itself is often clean: no malware, no suspicious file, and sometimes a sender domain that passes SPF, DKIM, and DMARC checks. Classic email filters focus on attachments, so a text-only message with one URL can slip through.

    AiTM kits defeat ordinary multi-factor authentication (MFA). They do not break the cryptography of MFA. They simply steal the login result: the password, the code, and the session cookie, while the victim completes the real login. This is why organizations with MFA still get breached this way.

    Where it fits in the attack chain

    Spearphishing Link is an Initial Access technique. It is usually the first step. After a successful click and theft, attackers commonly:

    • Use the stolen session cookie to sign in (T1557, T1539)
    • Read mail and move inside the tenant (T1078.004)
    • Create inbox rules to hide their activity (T1114.003)
    • Register their own MFA device (T1098.005)
    • Move laterally or launch business email compromise

    The same attack, in words

    1Stage the infrastructure

    The attacker registers a look-alike domain such as sso-login-portal-example[.]com, gets a TLS certificate for it, and installs a phishing kit that copies the company login page. The kit proxies the real site, so the victim sees a genuine page while the attacker records everything. Certificate Transparency logs already show the new domain, but no alarm sounds because nobody is watching them.

    2Send the link

    The attacker sends a short, targeted email: “Action required: confirm your VPN certificate before Friday.” It contains only text and one link. The mail gateway checks the sender domain, SPF, DKIM, and DMARC. Everything passes because the sender is real or well forged. There is no attachment to scan, so the message is delivered.

    3Victim clicks the link

    The victim opens the mailbox and clicks. The browser first jumps through a redirect and then resolves the fresh domain. DNS and proxy logs record the query, but the domain has no reputation yet and no category, so the proxy allows it.

    4The fake page loads

    The phishing site renders a pixel-perfect copy of the real sign-in portal, fetched live through the kit. The victim has no reason to doubt it. On the network side, the only clues are a very young TLS certificate and a page fingerprint that matches a known AiTM kit.

    5Credentials and MFA are captured

    The victim types their username and password and approves the MFA push, exactly as trained. The kit forwards each value to the real portal in real time and saves the resulting session cookie. At this moment there is still no alert, because from the identity provider’s view this is a normal successful login.

    6Session cookie replay

    The attacker imports the stolen cookie into their own browser from a different network and opens the mailbox. The identity provider sees a successful, non-interactive sign-in with a new device and a new country, and no matching password entry event. This mismatch is the strongest detection opportunity of the whole attack.

    7Access and persistence

    Inside the mailbox, the attacker reads documents, hunts for financial requests, and creates a hidden forwarding rule so every future message is copied to them. Audit logs record the new inbox rule, which is the second strong detection point.

    8Defender responds

    The SOC correlates the suspicious sign-in with the new inbox rule, disables the account, revokes all sessions and tokens, blocks the phishing domain at DNS, proxy, and mail level, and adds a new detection: alert when a sign-in succeeds without a password event.

    Red Team / Hacker Perspective

    Understanding the attacker’s choices helps you predict and detect them. This section explains why attackers prefer links, how they build the attack, and what a safe, lab-only practice setup looks like. Everything here is for defense and education.

    Ethics and law

    Everything in this section describes attacker behavior so that defenders can recognize it. Running phishing infrastructure against real people without written authorization is illegal in most countries. All commands in this guide are labeled lab-only and are meant for your own test environment.

    When and why attackers use a link

    Attackers pick the link variant for three reasons. First, mail filters watch attachments closely; a text-only email gives them almost nothing to scan. Second, a link is reusable and flexible: the attacker can change what the page shows after sending, block researchers, or show a harmless page to datacenter IPs and the real lure to residential ones. Third, links enable AiTM session theft, which beats ordinary MFA and produces a ready-to-use session instead of just a password.

    How the attack is performed

    A typical build looks like this: register a look-alike or brand-adjacent domain, age it for a few days, get a TLS certificate, deploy a phishing kit that reverse-proxies the real portal, then send a small number of tailored emails through a compromised mailbox, a look-alike sender, or a legitimate bulk-mail platform. The kit filters out bots and researchers by user agent, IP reputation, and JavaScript checks, and shows the real lure only to plausible victims.

    Prerequisites and conditions

    The attacker needs four things before the first email is sent. Understanding these helps you break the attack early.

    • Target research: names, roles, tools, current projects, and a believable reason to log in. This comes from professional networks, leaked data, and the target’s own website.
    • Infrastructure: a fresh domain, a certificate, a server or serverless function, and the kit itself. Fresh domains are a weakness defenders can watch.
    • Delivery path: a mailbox to send from, a look-alike domain, or an abused legitimate sender. DMARC failures of the target are free intelligence for the attacker.
    • A believable story: urgency plus authority, such as a payroll deadline, an expiring certificate, or a shared document.

    Practical lab exercise (lab-only, safe)

    To build detections, you need a copy of the attack in your own lab. This exercise creates a fake login page for a domain you own and generates telemetry, without touching any real user or any real brand.

    Then practice the detection side: query your proxy or web server logs for the marker utm=lab-aitm-test, and try to write the same logic in Sigma and SPL as you would for a real newly-registered domain. The point is to exercise the full detection loop safely.

    Common variations

    • URL shorteners and redirects to hide the final destination and break link filters.
    • HTML attachments or QR codes that carry the link past text-only filters.
    • OAuth consent phishing: the link leads to a real Microsoft or Google consent page for an attacker app (T1528).
    • Search-engine poisoning: the attacker pays to rank a fake support page, so the victim finds the link themselves.
    • Conversation hijacking: the link arrives inside a real reply thread taken from a compromised mailbox.

    Common attacker mistakes

    • Using infrastructure that is too new: same-day domain plus certificate is a strong signal.
    • Reusing kit fingerprints across campaigns, so one blocklist helps everyone.
    • Testing their own page from a known scanner IP and leaving it exposed.
    • Sending to too many people at once, which triggers volume rules.
    • Logging into the stolen account from a datacenter ASN right after a residential victim session.

    Blue Team / SOC Perspective

    The attack leaves traces even when no alert fires. This section shows where defenders can see it, which artifacts matter, and how to triage quickly when something looks wrong.

    How defenders can see this attack

    No single log tells the whole story, because the attack spans mail, network, endpoint, and identity. The realistic goal is a chain of weak signals that becomes strong when joined: a fresh domain at the proxy, a delivered mail with one unclassified URL, a sign-in without a password event, and a new inbox rule. Each signal alone is noisy; together they are a confirmed incident.

    Artifacts the attack leaves

    • Mail layer: the delivered message with one URL, header anomalies, or a display-name mismatch.
    • DNS layer: a query for a domain registered days ago, sometimes through a shortener or redirect chain.
    • Proxy layer: an HTTP session to the fresh domain with login-style paths and a young TLS certificate.
    • Identity layer: a successful sign-in with a new device and ASN, often non-interactive, with no password event.
    • Audit layer: new inbox rules, new OAuth consents, new MFA registrations, or mailbox permission changes.

    Where to look, in order

    1. Mail gateway or mail security logs for the URL and the delivery verdict.
    2. DNS and proxy logs around the click time, per user.
    3. Identity provider sign-in logs: device, ASN, interactive flag, error codes.
    4. Cloud audit logs for rules, consents, and MFA changes in the following hours.
    5. Endpoint logs if anything was downloaded from the phishing site.

    Why it matters for the SOC

    This technique is the front door for most serious incidents, from ransomware to business email compromise. The damage after the click grows every hour the attacker keeps the session: reading mail teaches them the organization, rules make the access persistent, and MFA enrollment makes it permanent. Detecting the chain early turns a potential crisis into a routine account reset. It also protects the one thing training cannot fully fix: any employee can have a busy, distracted moment.

    Short triage flow

    Use this sequence when a signal fires. Each step answers one question.

    1. Confirm the click: did this user hit a flagged, newly-registered, or uncategorized domain? Pull the exact URL and timestamp.
    2. Check identity: any successful sign-in for that user in the next 24 hours from a new device, ASN, or country? Was it interactive or cookie-based?
    3. Check persistence: any new inbox rule, OAuth consent, MFA registration, or mailbox delegation after the sign-in?
    4. Decide containment: if yes to any of the above, disable the account, revoke all sessions and refresh tokens, and force re-authentication from a trusted device.
    5. Collect and report: save the mail, the URL, the domain, and the log excerpts; notify affected users; request a domain blocklist addition and, if needed, a takedown.

    Common triage trap

    Resetting a password is not containment for AiTM phishing. The attacker may hold a valid session cookie that survives password changes. Always revoke sessions and refresh tokens, and check what the account did while the session was live.

    5.2Threat intelligence

    Threat intelligence answers three questions for this technique: who does this, how do they do it right now, and which signals are worth alerting on. Good programs combine free and paid sources and always record a confidence level: High means multiple reliable sources agree, Medium means one good source or partial agreement, Low means a single unverified report.

    MITRE ATT&CK

    Use the technique page for T1566.002, its parent T1566, and the follow-on techniques listed in section 1. ATT&CK gives you the vocabulary for detections, heatmaps, and coverage gaps. Confidence in the data: High, but it describes behavior, not current campaigns.

    Vendor reporting

    Microsoft Threat Intelligence, Proofpoint, Mandiant, and Talos publish AiTM campaign analyses with kit names, infrastructure patterns, and IOC lists. Confidence: High for observed behavior, Medium for actor attribution.

    OSINT sources

    Certificate Transparency logs, urlscan.io, newly-registered-domain feeds, and URL open-source lists let you hunt the infrastructure side before mail arrives. Confidence: High for facts about domains, Low for intent.

    Commercial feeds

    URL reputation, domain age, and phishing kit fingerprint feeds plug directly into proxy and mail rules. Confidence: Medium to High; always test precision on your own traffic before blocking.

    ISACs and sector groups

    Sector trusts (FS-ISAC, MS-ISAC, H-ISAC) share working campaigns and subject lines that hit your industry first. Confidence: High for sector relevance; verify before acting.

    Internal telemetry

    Your own mail gateway, proxy, and IdP logs are the best intelligence on what actually targets you. Mine reported phish monthly; your users are the most timely feed you own. Confidence: High for your environment.

    5.4Logs and patterns

    Each ranked threat maps to specific log sources. For every threat this subsection lists the sources, the fields that matter, what normal looks like, what suspicious looks like, and the detection logic in one sentence. Event examples are representative but realistic; field names differ slightly per vendor, so always confirm them against your own data.

    Threat 1 — AiTM credential and session theft

    Sources: identity provider sign-in logs (Entra ID, Okta), proxy or SWG logs, DNS logs, mail security logs.

    Key fields: userPrincipalName, ipAddress, clientAppUsed, isInteractive, authenticationRequirement, deviceDetail, location, proxy cs_host, domain_age_days.

    Normal: users sign in interactively, enter a password, satisfy MFA from devices seen before, from known ASNs and countries. Non-interactive token refreshes come from the same device and network shortly after an interactive sign-in.

    Suspicious: a successful sign-in where no password authentication preceded it, from a new ASN or country, non-interactive, on a browser client — especially within hours of a proxy hit on a young domain.

    Detection logic: alert on successful non-interactive browser sign-ins with a new device or ASN and no corresponding password event in the prior 24 hours, then join that user to any recent hit on a newly registered domain.

    Field notes: isInteractive: false means the sign-in was completed by a token or cookie, not by a fresh password entry. incomingTokenType: nonMfaSignedInAutoSuggest indicates a session cookie was presented. authenticationRequirement: singleFactorAuthentication on an account that normally requires MFA is a strong anomaly. errorCode: 0 means success, which is what makes this event dangerous.

    Threat 2 — Malware download via link

    Sources: proxy logs, DNS logs, endpoint (EDR) process and file events, mail security logs for the original message.

    Key fields: cs_host, cs_uri_path, rs_content_type, sc_bytes, EDR Image, ParentImage, TargetFilename, MotW (Mark of the Web) flags.

    Normal: downloads from sanctioned CDNs and vendor domains; script hosts execute only signed, well-known parents; files in Downloads are opened by Office with protected view.

    Suspicious: browser downloads an archive, ISO, or script-like file from a young domain; Office or the browser spawns cmd.exe, wscript.exe, or mshta.exe; mounted ISO files appearing in temp paths.

    Detection logic: join the download event (young domain, executable-like content type) with a later process event where an Office or browser process becomes the parent of a script interpreter.

    Field notes: application/octet-stream plus a 24 MB response on a 3-day-old domain is the suspicious pair; CATEGORY:uncategorized means no reputation existed; the username lets you join this event to identity telemetry. Domains are shown defanged with [.] for safe sharing; real logs contain plain dots.

    Threat 3 — OAuth consent phishing

    Sources: Entra ID audit logs (Consent to application), Okta system log, cloud audit platforms, proxy logs.

    Key fields: operationName (Consent to application), targetResources (app id, display name, delegated permissions), actor UPN, consent time.

    Normal: consents for verified publisher apps from your allowlist, requested by IT, or low-privilege scopes like User.Read.

    Suspicious: consents for unverified publishers, apps with names imitating your tenant or vendors, scopes like Mail.ReadWrite, Mail.Send, Files.ReadWrite.All, or offline_access combined with them, especially outside IT change windows.

    Detection logic: alert on any consent where the app is unverified or not allowlisted and the permission set includes mail write, mail send, or full files access; enrich with whether the consenting user recently clicked a flagged URL.

    Threat 4 — Payroll and finance diversion (BEC follow-on)

    Sources: mail security logs, Entra/Exchange audit (inbox rules), HR or finance application logs, DLP systems.

    Key fields: inbox rule Parameters (ForwardTo, DeleteMessage), message subject and recipients, HR app bank_account_changed events.

    Normal: HR and finance staff communicate with known vendors; payroll changes happen during business hours with documented tickets.

    Suspicious: a payroll or vendor bank-detail change shortly after an anomalous sign-in; hidden inbox rules that delete or move messages with words like “payment” or “invoice”; replies sent from a new device.

    Detection logic: correlate anomalous sign-ins on finance or HR identities with sensitive process events (bank detail change, payroll update) and new inbox rules within a 24-hour window.

    Field notes: a rule named . is a classic hiding trick; DeleteMessage: True on mail from a known partner shows intent to hide; the ClientIPAddress matches the replayed session from Threat 1, which is exactly the correlation your SIEM should join.

    Threat 5 — Mobile-targeted link delivery

    Sources: mobile threat defense (MTD) alerts, EMM/UEM app inventory, iOS/Android web filtering, DNS resolver logs for remote users.

    Key fields: device ID, app bundle ID, requested URL, domain age, certificate age, clipboard or deep-link activity.

    Normal: employees use sanctioned apps; mobile browsing goes through the EMM proxy or at least through enterprise DNS on VPN.

    Suspicious: personal browser or unsanctioned app opens a brand-look-alike domain; an MFA authenticator app is opened right after a mobile web session to a young domain.

    Detection logic: on mobile, alert on brand-look-alike domains with young age visited from devices that also hold corporate mail, and always pair the alert with an identity check for that user.

    Field notes: the first query is the uncategorized look-alike; the second is the real portal. In AiTM attacks both appear close in time because the kit proxies the real portal. A NOERROR answer plus later proxy traffic confirms the click path; a query alone without proxy traffic often means the link was scanned, not clicked.

    Threat 6 — Recon and tracking pixels

    Sources: mail security logs, proxy logs for tiny image requests, DNS logs for tracking domains.

    Key fields: mail has_pixel, pixel domain, proxy sc_bytes (very small responses), rs_content_type: image/*, user agent.

    Normal: legitimate marketing pixels from known senders; users open normal newsletters.

    Suspicious: pixels from unknown domains in mail that impersonates internal departments; repeated opens from datacenter IPs; pixel hits across many employees from the same campaign ID.

    Detection logic: aggregate pixel loads by campaign and domain; alert when one unknown tracking domain is touched by many users within days, because it marks an active targeting campaign.

    Coverage tip

    Threats 1, 2, 4, and 5 generate the most valuable alerts; threats 3 and 6 are lower volume but confirm campaigns early. Make sure at least one detection exists per threat before you tune anything for precision.

    5.5Sigma rules and Splunk SPL

    Each rule below covers one of the ranked threats. The Sigma rules are vendor-neutral YAML; the Splunk SPL mirrors the same logic. Field names in SPL depend on your data sources — the assumptions are stated under each query, and indexes are examples you should adapt.

    Rule 1 — Proxy hit on newly registered domain with login path (Threat 1/2)

    Field assumptions: domain_age_days is enriched by a threat-intel lookup (build it from an NRD feed and refresh daily). cs_user, cs_host, cs_uri_path come from Blue Coat style proxy data; for Squid use squid:access and map clientip, url. Tuning: suppress your known SaaS and vendor domains with a lookup; require a login path to reduce noise. False positives: legit new portals — mitigate with an allowlist review process.

    Rule 2 — Entra ID non-interactive sign-in without password event (Threat 1)

    Field assumptions: Entra sign-in logs land in index=identity sourcetype="azure:aad:signin"; nested JSON is parsed with spath so the query survives add-on differences. Instead of a fragile join, streamstats carries each user’s most recent interactive (password-bearing) event forward in time order, so every non-interactive success can be compared against it. Replace 203.0.113.* with your real corporate egress ranges. Tuning: raise the window to 72 hours for privileged roles and exclude known service principals. False positives: background mail-app refreshes — filter by appDisplayName allowlist and deviceDetail compliance status.

    Rule 3 — Okta SSO success from unknown device (Threat 1, Okta variant)

    Field assumptions: Okta system log via the Splunk Add-on for Okta Identity Cloud (Okta:IMX). The query reads one stream: device enrollments are stamped, sorted, and carried forward with streamstats, so an SSO from an unknown device is kept only when no enrollment happened for that user in the previous hour. If your tenant names the enrollment event differently, adjust eventtype. Tuning: baseline which groups legitimately show client.device=Unknown (new hires); add per-user first-seen logic for lower noise. False positives: browser updates that reset device identifiers; score with new-ASN checks before paging.

    Rule 4 — Mail gateway link to young look-alike domain (Threat 1/4)

    Field assumptions: Proofpoint style mail data (ppp:mail) with a parsed url_domain and enrichment url_domain_age_days; for Microsoft E5 use index=o365 sourcetype="o365:management:activity" plus Defender for Office 365 data instead. Tuning: keep a domain allowlist for your own subsidiaries; raise the age threshold if your sector rotates marketing domains often. False positives: legitimate new SaaS vendors — route through a quick allowlist review rather than auto-blocking.

    Rule 5 — Inbox forwarding rule created (Threat 4, persistence)

    Field assumptions: Unified Audit Log via o365:management:activity; Parameters is a JSON object that Splunk auto-extracts. Tuning: maintain a short allowlist of service mailboxes with legitimate forwarding; alert at high when the rule creator IP does not match any prior sign-in device for that user. False positives: executive-assistant setups — confirm with the mailbox owner before containing.

    Validation checklist for all five rules

    Test each rule in your lab with generated events (see the Section 3 lab exercise), confirm the Sigma YAML validates with sigma-cli check or your pipeline, measure alert volume for one week before paging on them, and record owner, runbook link, and expected weekly count in your detection catalog.

    Real-World Case Study

    In August 2022, the communications company Twilio disclosed a breach that began exactly the way this guide describes: SMS spearphishing with links to cloned Okta login pages. The case is public, well documented, and ideal for learning, because another victim in the same campaign (Cloudflare) resisted it and explained why.

    Context

    Twilio provides phone and messaging services, including the MFA used by thousands of other companies. Attackers (tracked as “0KT0UR” by Group-IB and as “0ktapus” by Unit 42) sent SMS messages to current Twilio employees. The texts claimed that password expiry or schedule changes required an urgent account action, and carried a link. The link opened a page that looked exactly like Twilio’s Okta sign-in portal — an AiTM clone on rotated domains, each with a name mixing the company brand with words like okta, sso, and support.

    Timeline

    • Late July – early August 2022Attackers register and age multiple look-alike domains, deploy an Okta-proxy phishing kit, and start an SMS wave that impersonates Twilio’s IT department.
    • August 4, 2022Twilio becomes aware of unauthorized access to a limited number of customer accounts. Employees had entered credentials and one-time MFA codes on the clone pages, and the attackers replayed the stolen sessions.
    • August 4–7, 2022Investigation opens with an outside forensic firm; carriers, registrars, and hosting providers are engaged to stop the malicious numbers and URLs. Affected customer accounts are notified.
    • August 7, 2022Twilio publishes its first public note on the incident.
    • August 9, 2022Cloudflare publishes its parallel analysis: 76 of its employees were targeted with the same lure, 3 entered credentials on the clone page, and FIDO2 hardware security keys blocked the attackers from completing the login.
    • Later 2022Investigators connect the same actor ecosystem to further attacks on other SaaS providers, showing how one campaign reused its infrastructure. Twilio later confirms 163 customer accounts (of more than 270,000) and 93 Authy end-user accounts were affected.

    Attack chain mapped to ATT&CK

    • Research: employee phone numbers and roles gathered beforehand.
    • Delivery: T1566.002 — spearphishing link via SMS to the clone domains.
    • Credential capture: AiTM page collected password + TOTP + session cookie.
    • Valid accounts: T1078 / T1078.004 — replayed sessions into internal tools.
    • Data access: customer data retrieved through legitimate application features.

    Detection point

    The decisive signal was human reporting, fast: employees flagged the texts within days, which triggered the investigation. The technical signals that existed — brand-look-alike domains with fresh certificates, and Okta clone pages — were visible in Certificate Transparency logs before any message arrived. The lesson is to automate that early watch instead of relying only on user reports.

    Containment

    Phishing numbers were blocked with carriers; hosting accounts for the clone domains were terminated; affected accounts had credentials reset and sessions revoked; access to impacted customer data was stopped and reviewed.

    Eradication and recovery

    Investigators mapped every domain and sender in the campaign and worked with providers to remove them. Impacted customers were notified with specifics, and service access was restored with new authentication hygiene for affected staff.

    Impact

    Data of 163 customer accounts and 93 Authy end-user accounts was exposed — a small share of the base, but heavily public. The company faced remediation costs and scrutiny. No ransomware followed, but the same actor ecosystem used stolen MFA access to pursue other victims in the wider campaign.

    Team response and communication

    Twilio combined security, legal, and communications early, coordinated takedowns through external providers, and disclosed within days of detection. Cloudflare, hit in parallel, published a detailed technical breakdown of the campaign on August 9. Both behaviors are now the reference playbook: report fast, share infrastructure, and explain what users should check.

    Lessons learned

    • TOTP and push MFA are phishable. The campaign collected one-time codes in real time. Cloudflare’s hardware keys, which bind to the real domain, stopped it. Phishing-resistant MFA is the structural fix.
    • Watch new domains before they email you. Every clone domain was visible in CT logs days in advance.
    • Rotated domains defeat single blocks. The kit used many short-lived domains; detection must key on the pattern (brand + keywords + young age), not one name.
    • Make reporting one tap. Employee reports worked here because they were fast and low-friction.
    • Rehearse identity triage. Knowing how to revoke sessions and hunt replayed sign-ins in hours, not days, contained the damage.

    Mitigation and Defense

    No single control stops every phishing link. Defense works in layers: make the attack harder to deliver, harder to trust, and easier to catch. This section lists enterprise controls, home-office advice, and a prioritized action plan.

    Identity and authentication

    • Roll out phishing-resistant MFA (FIDO2 security keys, passkeys) for admins and executives first, then everyone.
    • Use conditional access: device compliance, named locations, and token protection where available.
    • Set session lifetimes short for risky apps and require re-authentication for sensitive actions.
    • Make session revocation part of every password reset runbook.

    Email and network

    • Enforce SPF, DKIM, and DMARC at quarantine/reject; monitor reports monthly. They stop cheap spoofing, though not AiTM from look-alike domains.
    • Enable URL rewriting, detonation, and click-time checks in your mail security service.
    • Block or warn on newly registered domains at proxy and DNS; add a brand look-alike watch on CT logs.
    • Consider browser isolation for uncategorized and NRD categories.

    Endpoint and cloud

    • Keep EDR on all endpoints with SmartScreen and Office macro defaults hardened.
    • Enforce app consent policies: block unverified publishers, require admin approval for high-privilege scopes.
    • Restrict OAuth app creation and review existing consents quarterly.

    Logging, monitoring, response

    • Ship IdP sign-in logs, mail logs, proxy, and DNS to your SIEM; keep 90 days hot.
    • Deploy the Section 5 detections; assign an owner and runbook to each.
    • Run quarterly phishing simulations and track report rates, not just click rates.
    • Write a session-replay response playbook: disable, revoke, hunt persistence, notify.

    Home and small-office advice

    Without a SOC, the same principles shrink but still work. Use a password manager and only let it autofill on the exact real domain — it will refuse on clone sites, which is a free phishing alarm. Turn on the strongest MFA your provider offers and prefer passkeys or a hardware key for your main email. Keep your browser and phone updated, because they block known phishing sites automatically. Pause before urgency: real companies never expire your account in two hours. If you clicked and typed a password, change it immediately from a trusted device, sign out everywhere, and check forwarding rules and connected apps.

    Common Mistakes and Best Practices

    These are the failure modes detection teams meet most often with this technique. Each card gives the symptom, the root cause, the fix, and the habit that prevents it from returning.

    1. Treating DMARC as a phishing verdict

    Symptom
    Clean-sender phish is delivered and nobody looks at it.
    Root cause
    Mail filter or analyst trusts DMARC as a content judgment.
    Fix
    Alert on DMARC-pass mail with one unclassified URL and no attachments.
    Prevention
    Document that DMARC proves sender identity only, never intent.

    2. Resetting passwords without revoking sessions

    Symptom
    Attacker keeps reading mail after a password reset.
    Root cause
    Runbook lacks token and session revocation steps.
    Fix
    Add “revoke sessions + refresh tokens” to every reset action; verify by log.
    Prevention
    Quarterly runbook drills with a stolen-cookie scenario.

    3. No DNS or proxy logging per user

    Symptom
    Cannot confirm who clicked a known phishing domain.
    Root cause
    Network logs are aggregated or user-mapping missing.
    Fix
    Enable per-user proxy identity and DNS logging to the SIEM.
    Prevention
    Coverage matrix: every detection lists required sources.

    4. Ignoring non-interactive sign-ins

    Symptom
    Session replay is invisible in dashboards built on interactive logons.
    Root cause
    Analysts filter to interactive events only.
    Fix
    Add non-interactive success monitoring (Rule 2).
    Prevention
    Include token/cookie events in identity dashboards by default.

    5. Alert fatigue from raw URL clicks

    Symptom
    Analysts mute the NRD alert within a week.
    Root cause
    Rule fires on every uncategorized domain without scoring.
    Fix
    Require login-path + young-age + first-seen-user conditions; auto-allowlist reviewed domains.
    Prevention
    Weekly precision review with a target signal ratio.

    6. Single-domain blocklists

    Symptom
    Same campaign returns on a new domain and bypasses blocks.
    Root cause
    Detection keys on exact domain names instead of patterns.
    Fix
    Add pattern rules (brand + sso/login + young age) and CT-log watch.
    Prevention
    Post-incident review always produces a pattern, not just an IOC.

    7. Testing detections only with attachments

    Symptom
    Rules tuned on file-based tests miss the whole link class.
    Root cause
    Test plan copied from malware use cases.
    Fix
    Add link-only lab tests (Section 3 exercise) to the pipeline.
    Prevention
    Validation checklist includes one test per ranked threat.

    8. No owner for identity detections

    Symptom
    Sign-in rules rot; new log fields break queries silently.
    Root cause
    Detections owned by “the team”, so by nobody.
    Fix
    Assign a named owner and review date to each rule.
    Prevention
    Detection catalog with owner, runbook, last-validated columns.

    9. Blind trust in gateway link rewriting

    Symptom
    Clicks on phish never rewritten (encrypted mail, QR, chat, forwarded mail).
    Root cause
    Assuming one control covers all delivery paths.
    Fix
    Extend URL defense to internal mail, chat, and QR; keep proxy telemetry as backstop.
    Prevention
    Red-team test delivery paths outside the gateway each quarter.

    10. Forgetting OAuth consents after incidents

    Symptom
    Access persists after full credential reset.
    Root cause
    Response scope stops at passwords and sessions.
    Fix
    Check and revoke app consents and app passwords in every account investigation.
    Prevention
    Consent review is a checklist item in the phishing playbook.

    11. Weak tuning from missing baselines

    Symptom
    “New device” alerts page on every traveler.
    Root cause
    No first-seen baseline per user and ASN.
    Fix
    Add 30-day first-seen logic and known-ASN allowlists.
    Prevention
    Tuning PRs require a measured false-positive rate.

    12. Reporting without feedback

    Symptom
    Employees stop reporting; click rates rise again.
    Root cause
    Reporters never hear what happened.
    Fix
    Auto-thank reporters and publish anonymized outcomes monthly.
    Prevention
    Track report rate as a first-class awareness KPI.

    Cheat Sheet and Quick Reference

    Everything important on one screen. Use it during an incident or when writing new detections.

    Key facts

    Technique
    T1566.002 — Spearphishing Link (sub-technique of T1566)
    Tactic
    Initial Access
    Delivery
    Email/chat/SMS with a link; no attachment needed
    Prime target
    Passwords, MFA codes, session cookies (AiTM)
    Strongest signals
    Young domain + login path; sign-in without password event; new inbox rule
    Best counter
    Phishing-resistant MFA + session revocation + pattern-based domain watch

    Top detections

    • Proxy: login path on a domain younger than 14 days (Rule 1)
    • Identity: successful non-interactive sign-in, no password event in 24h (Rule 2)
    • Okta: SSO success from unknown device (Rule 3)
    • Mail: link to young look-alike domain at delivery (Rule 4)
    • Audit: inbox rule with forward or delete actions (Rule 5)

    Response checklist

    • Identify the clicked URL, timestamp, and user from proxy/DNS/mail logs.
    • Confirm whether credentials or MFA were entered on the page.
    • Disable the account and revoke all sessions, refresh tokens, and app passwords.
    • Review sign-ins for the last 30 days for that user (new devices, ASNs, countries).
    • Hunt persistence: inbox rules, OAuth consents, MFA registrations, delegations.
    • Check mail access: search the mailbox for the attacker’s activity and reads.
    • Block the domain at DNS, proxy, and mail; add the pattern to the watchlist.
    • Reset the password from a trusted device; re-enroll MFA if codes were captured.
    • Notify affected users and, if data left the tenant, follow breach procedures.
    • Write the postmortem: add one new pattern-based detection from what you learned.
