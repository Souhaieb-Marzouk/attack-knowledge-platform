T1091 Replication Through Removable Media

A USB drive can cross an air gap that no network traffic ever will. Malware that copies itself onto removable media rides from machine to machine - into networks that are deliberately disconnected from the Internet. This page shows how that works and how to catch it.

  • Tactic: Initial Access, Lateral Movement
  • Platforms: Windows
  • Added: 2017 (v1.0) · checked vs ATT&CK v20
  • Guide version: 2.0
  • Data sources: File monitoring, USB device events, Process creation
  • Detection difficulty: Medium

What it is

Malware copying itself onto USB media and executing when the media reaches another computer.

Primary risk

Crossing air gaps into isolated, high-value networks.

Where it happens

Corporate fleets, kiosks, OT/SCADA sites, engineering rooms, field laptops.

Detection difficulty

File writes and executions from removable paths are visible - if telemetry exists.

Contents

    1

    Overview

    What removable-media replication means, why it still matters, and what this page teaches.

    The idea in plain language

    Replication through removable media is malware that spreads by copying itself onto USB drives and similar media. When the drive is inserted into another computer, the malware runs. Historically this abused autorun - a Windows feature that executed programs on media automatically. Today worms trick the user into opening a malicious shortcut (.lnk) that looks like a folder, or they exploit the way Windows renders shortcuts.

    This is the classic way infections cross an air gap - a network deliberately disconnected from the Internet. No packet can cross that gap, but an employee with a USB drive can.

    Why it matters

    Exactly because isolated networks are trusted more, malware that reaches them finds rich, unprotected targets - industrial controls, engineering workstations, classified systems. Stuxnet (2010) proved the concept by reaching Iran's Natanz facility; USB worms still surface regularly against enterprises and OT sites. For regular networks, USB worms remain a self-spreading lateral-movement channel that ignores segmentation.

    Where it fits in the attack chain

    T1091 covers Initial Access and Lateral Movement. Execution on the new host pairs with T1204.001 Malicious File, and the reverse direction - stealing data out via media - is T1052.001 Exfiltration over USB. Deliberate hardware introduction is T1200.

    What is happening

    Defender hint

    The same story in text

    1. Infected host. An office laptop already carries the worm (infected days earlier via a dropped drive). Defender hint: retrohunt the laptop's history - the first infection was probably a missed removable-path execution.
    2. Media mounted. The employee inserts a USB drive to copy training slides. Windows mounts it as drive E:. Defender hint: device-insert events (6416) start the clock for every removable-media story.
    3. Copies and shortcuts. The worm writes its components and malicious .lnk shortcuts onto the drive. Defender hint: Sysmon file-create events on removable paths are the paper trail - alert on executable and .lnk writes there.
    4. Across the gap. The employee carries the drive into the air-gapped engineering room and inserts it into a PC with no network connection at all. Defender hint: transfer stations - dedicated, monitored media kiosks - are the control point for air-gapped sites.
    5. Tricked click. The user opens what looks like a folder. It is a malicious shortcut that launches the worm via the shell. Defender hint: execution whose command line references the drive letter is the smoking gun.
    6. Established. The worm installs persistence on the isolated PC and checks for other drives and shares to copy itself to. Defender hint: on isolated hosts, any process from a removable path deserves an instant alert.
    7. Detection. The EDR flags execution from a removable path on the engineering PC; the SOC pulls the file history. Defender hint: the same hash across hosts and media ties the outbreak together.
    8. Response. The PC is isolated, media quarantined, fleet scanned for the hash, autorun and device-control policies tightened. Defender hint: treat every drive the user owns as compromised until scanned.
    3

    Red team / hacker perspective

    How media-borne worms work, in principle. Conceptual and lab-only.

    Why attackers use removable media

    It is the only reliable path into networks that refuse outside connectivity - OT sites, defense networks, payment enclaves. It also survives where phishing fails: the "document" arrives physically, from a colleague's own drive. And for opportunistic criminals, infected drives are self-propagating: every user who borrows the drive becomes a new patient zero.

    Propagation mechanics (concept)

    Modern Windows disables autorun by default. Current worms therefore use malicious shortcuts: the worm renames or hides real folders and replaces them with .lnk files. Their icons look like folders, but launching them runs the worm.

    Prerequisites

    Write access to media - a worm needs an infected host first. A user who moves media between trust zones. Windows endpoints that allow execution from user-writable paths. And, on the target, no device control or media scanning. Air-gapped sites without transfer stations are ideal targets.

    LAB-ONLY: observe shortcut-based behavior safely
    # On an isolated lab VM with a spare USB drive, study the MECHANICS safely:

# 1) Insert the drive, note the letter (e.g., E:). Confirm autorun is disabled:
reg query HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\Explorer /v NoDriveTypeAutoRun

# 2) Create a harmless .lnk that opens Notepad (no malware anywhere):
#    Target: %SystemRoot%\System32\notepad.exe
#    Icon: %SystemRoot%\System32\shell32.dll (folder icon index)
# 3) Double-click it: confirm your telemetry shows explorer.exe spawning
#    the target with the drive-letter context.
# 4) Write the Sigma rule that matches THIS harmless event, then replay it.
# Never build or distribute working malware - not even "for testing".

    Common variations

    Enterprise worms (Raspberry Robin-style chains spreading via media and then pivoting to network C2). OT-crossers (Stuxnet/Horab-style toolkits carrying exploit payloads). Credential harvesters that sit quietly and copy password stores to the drive. Drop attacks in parking lots and lobbies. Insider media carrying payloads on purpose.

    Attacker mistakes that help defenders

    Identical file hashes across every host - perfect for fleet-wide hunts. .lnk metadata leaking build-machine paths. Leftover autorun.inf files that AV flags instantly. Worm traffic when a "media-only" host rejoins the network. And media that keep getting re-inserted into the same monitored kiosks.

    Danger

    Developing or deploying working media worms is illegal and dangerous - including "just to test". Build detections against harmless synthetic events in your lab, as shown above.

    4

    Blue team / SOC perspective

    Media-borne worms are chatty on disk. Every hop leaves file and process evidence.

    How defenders can see it

    Three reliable views. File telemetry: executables and .lnk files written to removable paths (Sysmon EID 11, auditd-equivalents on Windows are the core signal). Process telemetry: anything executing with a drive-letter path on media (E:\..., F:\...) - legitimate users rarely launch programs this way. Device telemetry: insert events (6416) that link media to hosts and times, letting you reconstruct the worm's travel itinerary.

    File artifacts

    New .lnk shortcuts pointing at hidden payloads, autorun.inf remnants, worm components in recycler or system folders on media, identical hashes appearing on multiple hosts.

    Process artifacts

    Explorer spawning targets from drive letters; cmd with /c E:\... patterns; msiexec or curl launched with removable paths; persistence (run keys, scheduled tasks) added right after media use.

    Device artifacts

    6416 mass-storage inserts correlated to hosts and times; device-control blocks; the same USB serial appearing on multiple machines during the window.

    Where to look (log sources)

    • Sysmon: Event ID 11 (file create, removable paths), Event ID 1 (process creation), Event ID 13 (run keys).
    • Windows Security: 6416 (device recognized), 4663 (file writes to removable objects), 4698 (scheduled task created).
    • EDR: file and process lineage with device context; USB telemetry modules.
    • AV/Defender: detections for worm families and autorun abuse.
    • OT sites: transfer-station kiosk logs - scan results and insert events.

    Short triage flow

    1. Confirm execution origin. Is the flagged process really running from a removable path? Capture the command line.
    2. Freeze and quarantine. Isolate the host; quarantine the media (log its serial and device ID).
    3. Hash pivot. Search the fleet for the payload hash; list every host with the file or its .lnk.
    4. Reconstruct the itinerary. Join 6416 inserts across hosts for that serial: which machines, which order.
    5. Assess persistence. Run keys, tasks, services on each affected host; look for secondary payloads.
    6. Respond. Rebuild infected hosts, scan/clean media or destroy it, tighten device control, brief the site.
    Warning

    On air-gapped and OT networks, assume the worm reached every machine whose operator shares media routines with the first victim. The infection map is a people map: whose drives circulate together. Scope by human workflow, not just by logs.

    5.2

    Threat intelligence

    Media worms have a rich, well-documented history - use it to justify controls and tune detections.

    Sources worth following

    MITRE ATT&CK for structure. Vendor reporting: ESET (USBCulasis/GoldenCube, PlugX USB), Check Point (Sonesia), Cisco Talos (Raspberry Robin). OT-focused: Dragos and Claroty for media-borne threats to industrial sites. Historical literature: Stuxnet analyses (the deepest public malware studies ever written). Internal telemetry: your 6416 insert history shows real media workflows.

    How to apply it

    Maintain hash and filename watchlists from published worm reports and load them into EDR custom detections. Map reported families to your exposure (OT sites first). Use historical cases in awareness training - the "found USB in the parking lot" story lands better than abstract advice.

    5.3

    Threats ranking and categorization

    Five realistic threats built on T1091, ranked and categorized. These five are reused in sections 5.4 and 5.5.

    RankThreatSeverityPlatform
    1Cross-air-gap propagation into OT/SCADA (Stuxnet/Horab style)CriticalWindows / OT
    2Enterprise USB worm (Raspberry Robin-style LNK chain)HighWindows
    3USB as covert exfiltration channel from restricted networksHighWindows / OT
    4autorun.inf-era self-replication on shared/kiosk machinesMediumWindows
    5Malicious USB drop (social engineering initial access)LowWindows

    Threat 1 - Cross-air-gap into OT Critical

    Description: toolkits that ride media into isolated industrial networks and carry destructive or surveillance payloads.

    Preconditions: media workflows between corporate and OT zones without transfer stations.

    Impact: physical-process manipulation or long-term espionage in the crown-jewel zone.

    Justification: proven historically; consequences are physical, not just digital.

    Threat 2 - Enterprise USB worm High

    Description: self-copying chains (.lnk/.msi) that hop drives and hosts, often pivoting to network C2 when possible.

    Preconditions: unrestricted media use plus users without execution discipline.

    Impact: fleet-wide infections, precursor access for ransomware crews.

    Justification: actively spreading today; ignores network segmentation.

    Threat 3 - Media as exfil channel High

    Description: data staged to removable media on restricted networks and carried out by insiders or by malware (pairs with T1052.001).

    Preconditions: unrestricted writes to media on networks where egress is otherwise blocked.

    Impact: bulk data loss with zero network trace.

    Justification: invisible to network DLP; needs endpoint DLP and volume analytics.

    Threat 4 - autorun-era replication on kiosks Medium

    Description: legacy or unmanaged machines where autorun or weak user discipline lets worms self-execute.

    Preconditions: kiosks/shared machines without device control.

    Impact: local outbreaks on shared systems; a springboard into managed fleets.

    Justification: narrow but real; fixes are cheap (disable autorun, block execution from media).

    Threat 5 - Malicious USB drop Low

    Description: planted or mailed drives that rely on curiosity; the media itself is the whole attack.

    Preconditions: physical placement plus a curious user.

    Impact: single-host foothold; often caught by device control or awareness.

    Justification: well-known story; awareness and controls keep it low-residual.

    5.4

    Logs and patterns

    For each of the five threats: log sources, key fields, normal vs suspicious behavior, detection logic, and a realistic event example.

    Threat 1 - Cross-air-gap into OT Critical

    Log sources: Sysmon EID 11 (file create on removable paths); Windows Security 6416/4663; transfer-station kiosk logs.

    Key fields: TargetFilename, Image, Hash, ObjectType, device serial.

    Normal: on OT hosts, almost no media activity; transfers happen only at the dedicated station, logged and scanned.

    Suspicious: executable or script writes to media on OT-adjacent hosts outside the transfer station; unknown binaries staged to media.

    Detection logic: alert on file writes to removable paths on hosts in or near OT zones; treat every hit as policy violation plus possible propagation.

    Example event - Sysmon Event ID 11 (XML)
    <Event>
  <System>
    <Provider Name="Microsoft-Windows-Sysmon"/>
    <EventID>11</EventID>
    <TimeCreated SystemTime="2025-03-18T11:47:02.330Z"/>
    <Computer>ENG-OT-WS-04</Computer>
  </System>
  <EventData>
    <Data Name="Image">C:\Windows\explorer.exe</Data>
    <Data Name="TargetFilename">F:\transfer\update_v2.zip</Data>
    <Data Name="CreationUtcTime">2025-03-18T11:47:02.30Z</Data>
    <Data Name="Hash">SHA256=6A21F8C3D54E0B9A7C2F1D8E5B4A3C6D0E9F2A5B8C1D4E7F0A3B6C9D2E5F8A1B</Data>
  </EventData>
</Event>

    Host ENG-OT-WS-04 is an engineering workstation adjacent to the OT zone. An archive named like an update, written straight to media, bypassing the transfer station: either policy violation or worm staging. The hash decides - check it against known-good packages.

    Threat 2 - Enterprise USB worm High

    Log sources: Sysmon EID 1 (process creation with removable path); EDR; AV detections.

    Key fields: ParentImage, Image, CommandLine, User.

    Normal: users open documents from media, not executables; corporate policy blocks execution from user-writable paths.

    Suspicious: explorer.exe spawning msiexec/curl/wscript with arguments pointing at drive letters; hidden-window installs from media.

    Detection logic: alert on process creation where the image or command line references a removable drive letter.

    Example event - Sysmon Event ID 1 (XML, abridged)
    <Event><System>
  <EventID>1</EventID>
  <TimeCreated SystemTime="2025-03-18T11:52:40.118Z"/>
  <Computer>FIN-W7-118</Computer>
</System><EventData>
  <Data Name="ParentImage">C:\Windows\explorer.exe</Data>
  <Data Name="Image">C:\Windows\System32\msiexec.exe</Data>
  <Data Name="CommandLine">msiexec /i E:\packages\update.msi /qn /norestart</Data>
  <Data Name="User">CORP\j.reyes</Data>
</EventData></Event>

    A silent MSI install (/qn) launched by a double-click from a USB path - users do not run silent installs manually. This is the Raspberry Robin-style pattern: .lnk to MSI from media, quiet execution, then C2.

    Threat 3 - Media as exfil channel High

    Log sources: Sysmon EID 11 (volume to removable paths); Windows 4663; endpoint DLP.

    Key fields: TargetFilename, ProcessName, AccessMask, byte volume.

    Normal: small document copies on approved media; DLP-encrypted containers on corporate drives only.

    Suspicious: large or sustained writes to media (hundreds of MB), archives of restricted folders, writes outside work hours.

    Detection logic: sum bytes written to removable paths per host/user per day; alert on volume outliers and on restricted-folder staging.

    Example event - Windows Security 4663 (abridged)
    Log Name:      Security
Event ID:      4663
Time:          2025-03-18T23:14:22Z   (off-hours)
Subject:       CORP\a.mercer
Object Name:   E:\backup\fin-export-2025.7z
Object Type:   File
Process Name:  C:\Windows\System32\7zG.exe
Accesses:      WRITE_DATA, WRITE_ATTRIBUTES

    An archiver writing a finance-labeled archive to media at 23:14. Off-hours plus the word export plus 7z staging is a classic insider-exfil triad. Join with the 6416 insert event to bind the media's identity.

    Threat 4 - autorun-era replication on kiosks Medium

    Log sources: Sysmon EID 11 (autorun.inf writes); AV events; registry (NoDriveTypeAutoRun policy).

    Key fields: TargetFilename, Image, policy values.

    Normal: NoDriveTypeAutoRun policy set to block autorun org-wide; no autorun.inf files ever created.

    Suspicious: any autorun.inf creation on media or shares; policy value reverted on unmanaged machines.

    Detection logic: alert on autorun.inf file creation anywhere, and monitor the policy value on kiosks.

    Example event - Sysmon Event ID 11 (XML, abridged)
    <Event><System>
  <EventID>11</EventID>
  <TimeCreated SystemTime="2025-03-18T12:03:15.002Z"/>
  <Computer>KIOSK-LOBBY-02</Computer>
</System><EventData>
  <Data Name="Image">E:\setup\installer.tmp</Data>
  <Data Name="TargetFilename">E:\autorun.inf</Data>
  <Data Name="Hash">SHA256=31C4F1A9B2D8E7053C6A9B0D4E7F1A2B3C4D5E6F7A8B9C0D1E2F3A4B5C6D7E8F</Data>
</EventData></Event>

    A temporary installer process writing autorun.inf onto the media on a lobby kiosk - self-replication in one event. Whatever that installer is, the kiosk needs immediate isolation.

    Threat 5 - Malicious USB drop Low

    Log sources: Windows Security 6416; EDR device control; AV.

    Key fields: DeviceDescription, DeviceId, SubjectUserName, time.

    Normal: approved, inventoried media only; unknown media blocked by device control with a logged event.

    Suspicious: insert of never-before-seen media followed by execution attempts; media with unusual device strings.

    Detection logic: alert on first-seen media device IDs on sensitive hosts; pair with any execution from the same drive letter.

    Example event - Windows Security 6416 (abridged)
    Event ID:      6416
Time:          2025-03-18T10:41:03Z
Subject:       CORP\a.mercer
DeviceDescription: SanDisk Cruzer Blade
DeviceId:      USB\VID_0781&amp;PID_5567\4C530001234567890123
ClassId:       {4d36e967-e325-11ce-bfc1-08002be10318}   (DiskDrive)
Status:        0x0

    The class GUID identifies a disk drive. If device control is set to "read-only for unknown media", the next event to check is whether anything executed from that volume. First-seen media on a finance host is worth a look on its own.

    5.5

    Sigma rules and Splunk SPL

    One complete Sigma rule and one matching Splunk SPL query per threat, with assumptions, false positives, and tuning notes.

    Threat 1 - Cross-air-gap into OT Rule level: high

    Sigma rule (YAML)
    title: Executable File Written to Removable Media on OT-Adjacent Host
id: 97c3d5a1-68e2-4b70-9d34-2f5a8c0e1b96
status: stable
description: Detects executable or archive files written to removable media paths
  on hosts near OT/air-gapped zones. Legitimate transfers only happen at dedicated
  transfer stations, so any other media write is a policy violation and a possible
  worm staging event.
references:
  - https://attack.mitre.org/techniques/T1091/
author: Detection Engineering Team
date: 2024-11-15
logsource:
  category: file_event
  product: windows
  service: sysmon
detection:
  selection_drive:
    TargetFilename|re: '^[D-Z]:\\.*'
  selection_ext:
    TargetFilename|endswith:
      - '.exe'
      - '.dll'
      - '.ps1'
      - '.bat'
      - '.vbs'
      - '.lnk'
      - '.zip'
      - '.7z'
  filter_transfer_station:
    Computer|startswith: 'TRANSFER-KIOSK'
  condition: selection_drive and selection_ext and not filter_transfer_station
fields:
  - Computer
  - Image
  - TargetFilename
  - Hash
falsepositives:
  - Approved workflows not yet registered to a transfer station
level: high
tags:
  - attack.t1091
  - attack.tactic.lateral-movement
  - attack.tactic.initial-access
    Splunk SPL
    index=edr sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=11
| regex TargetFilename="^[D-Z]:\\.*"
| regex TargetFilename="\.(exe|dll|ps1|bat|vbs|lnk|zip|7z)$"
| lookup ot_hosts host OUTPUTNEW zone
| where zone IN ("ot-adjacent","ot")
  AND NOT (host="TRANSFER-KIOSK*")
| stats count values(TargetFilename) as files by host, zone | sort -_time

    Field assumptions: drive letters D-Z treated as removable (align with your own letter map); ot_hosts lookup tags zones. False positives: workflows missing from the station policy - onboard them rather than filtering. Tuning: on strict OT zones raise severity to critical and page immediately.

    Threat 2 - Enterprise USB worm Rule level: high

    Sigma rule (YAML)
    title: Suspicious Process Execution from Removable Drive
id: 5b9e2f70-31c4-48a6-8e07-9d6a3c1b4f82
status: stable
description: Detects processes whose image or command line references a removable
  drive letter - the signature of shortcut-based worms executing from USB media.
references:
  - https://attack.mitre.org/techniques/T1091/
  - https://attack.mitre.org/techniques/T1204/001/
author: Detection Engineering Team
date: 2024-11-15
logsource:
  category: process_creation
  product: windows
  service: sysmon
detection:
  selection_image:
    Image|re: '^[D-Z]:\\.*'
  selection_cmd:
    CommandLine|re: '(?i)(msiexec|wscript|cscript|mshta|curl|certutil|cmd).{0,120}[D-Z]:\\'
  condition: selection_image or selection_cmd
fields:
  - ParentImage
  - Image
  - CommandLine
  - User
falsepositives:
  - Approved portable tools executed from media (allow-list by hash)
level: high
tags:
  - attack.t1091
  - attack.t1204.001
  - attack.tactic.execution
  - attack.tactic.lateral-movement
    Splunk SPL
    index=edr sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=1
| regex Image="^[D-Z]:\\.*" OR match(CommandLine, "(?i)(msiexec|wscript|cscript|mshta|curl|certutil|cmd).{0,120}[D-Z]:\\\\")
| stats count values(CommandLine) as cmdlines by host, ParentImage, Image | sort -_time

    Field assumptions: Sysmon process events; drive-letter map aligned with your fleet. False positives: sanctioned portable tools - inventory and hash allow-list them. Tuning: ParentImage=explorer.exe plus media path is the high-fidelity core; keep the broader rule for coverage.

    Threat 3 - Media as exfil channel Rule level: medium

    Sigma rule (YAML)
    title: High Volume of File Writes to Removable Media
id: c61d8a34-95f7-42b8-8d19-4e7b0a2c5e93
status: experimental
description: Detects unusually high numbers of file writes to removable media
  paths by one host in a day - the endpoint footprint of media-based exfiltration.
references:
  - https://attack.mitre.org/techniques/T1091/
  - https://attack.mitre.org/techniques/T1052/001/
author: Detection Engineering Team
date: 2024-11-15
logsource:
  category: file_event
  product: windows
  service: sysmon
detection:
  selection:
    TargetFilename|re: '^[D-Z]:\\.*'
  condition: selection | count() by Computer > 100
fields:
  - Computer
  - Image
  - TargetFilename
falsepositives:
  - Legitimate large media syncing for approved backups
level: medium
tags:
  - attack.t1091
  - attack.t1052.001
  - attack.tactic.exfiltration
    Splunk SPL
    index=edr sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=11
| regex TargetFilename="^[D-Z]:\\.*"
| bin _time span=1d
| stats count as writes sum(eval(len(TargetFilename))) as pathbytes by _time, host, user
| where writes > 100
| sort - writes

    Field assumptions: Sysmon file events with drive-letter map; true byte counts need DLP - path-length summing is a proxy. False positives: approved backup-to-USB jobs. Tuning: add restricted-folder name matching (fin*, hr*, export) as a high-severity variant.

id: 28a4c6b0-73d5-49e1-8f62-5b0c8d3e7a15
status: stable
description: Detects creation of autorun.inf files. Modern Windows ignores them by
  default, so their creation indicates worm-era tooling, legacy systems, or tampering
  with media that will move to weaker machines.
references:
  - https://attack.mitre.org/techniques/T1091/
author: Detection Engineering Team

    Real-world case study

    Agent.btz (2008): a USB worm that reached classified US military networks and changed how a superpower organizes cyber defense.

    Context

    In 2008, a self-replicating worm known as Agent.btz appeared on US military networks, including the classified SIPRNet environment. Public reporting describes infection via removable media - reportedly a USB drive used in the field. The worm replicated across drives, installed persistence, and collected system and network information for exfiltration when connectivity allowed. The intrusion happened in the era before aggressive removable-media controls.

    Timeline

    • 2008Agent.btz infections surface on DoD networks; removable media identified as the spread vector.
    • November 2008Response effort named Operation Buckshot Yankee begins; media use suspended DoD-wide.
    • 2008-2009Network-wide scans and cleanups; autorun disabled; media policies rewritten.
    • 2009-2010The strategic response: creation of U.S. Cyber Command, stood up in 2010.

    Detection point

    Detection was largely manual: operators noticed unusual files and registry persistence on machines that shared media. The era's monitoring was thin - a fact the response acknowledged by building far stronger telemetry afterward.

    Containment

    The DoD banned removable media across its networks (an extraordinary, mission-impacting step), then scanned and cleaned systems. The worm's registry and file artifacts gave responders fingerprints for fleet-wide hunts.

    Eradication

    Infected machines were rebuilt and swept for the worm's indicators. All removable media was checked or destroyed, and spread paths were closed: autorun disabled, device control applied, and shortcut handling hardened.

    Recovery

    Networks returned to service only after clean rescans. Media use resumed under the new policy - signed, approved devices only. USB-related detections and periodic hunts stayed in place afterward.

    Impact and consequences

    Sensitive but unclassified operational data was exposed to collection. The organizational consequence was historic: the incident is widely credited with accelerating the creation of U.S. Cyber Command - a single worm reshaping a national command structure.

    Team response and communication

    The response required coordinated policy change across a global organization: suspend a daily-workflow capability (media), communicate why, and hold the line under operational pressure. It remains a benchmark for incident-driven governance.

    Lessons learned

    1. Media policy is security policy: unrestricted USB defeats segmentation on paper and in practice.
    2. Disable autorun everywhere; it costs nothing and removes a whole worm class.
    3. Detection needs device and file telemetry - not just network monitoring.
    4. Incidents can justify organizational change; capture the lessons formally.
    5. Human workflow (who shares drives) is part of the threat model.

    Mitigation and defense

    Media control is one of the cheapest high-impact control families you can deploy.

    Policy

    Approved-media-only policy with an inventory. Transfer-station requirement for OT/air-gapped zones. Media destruction rules for decommissioned drives.

    Identity / access

    Device control tied to user identity: media works only for approved users on approved hosts. Break-glass access logged and reviewed.

    Endpoint

    Disable autorun/autoplay org-wide. Block execution from user-writable and removable paths. EDR with removable-media telemetry on every endpoint, including kiosks.

    Network

    Nothing direct - but segmentation limits what a media-borne foothold can reach. Treat media entry points as untrusted interfaces.

    Cloud / SaaS

    Sync clients replace sneaker-net: give users a sanctioned path so they do not invent one. CASB policies for offline exports.

    Logging & monitoring

    6416 inserts, file writes to media, executions from media - all in the SIEM. Volume analytics for exfil patterns (section 5.5).

    Backup & resilience

    Imaging capability for small outbreaks; known-good golden images for kiosks and engineering workstations.

    Response

    A media-outbreak runbook: quarantine hosts and media, hash-pivot across the fleet, reconstruct the media's travel itinerary, rebuild, and tighten policy.

    Good practice - home and small office

    Never plug in a USB drive you found or were handed at a conference. Turn off autorun (modern Windows does this - keep it that way). If you must move files, scan the drive first and prefer cloud sync or direct cable transfer between your own devices. Encrypt sensitive drives.

    Common mistakes and best practices

    Ten blue-team mistakes around removable media, with symptom, root cause, fix, and prevention.

    1. Assuming USB worms are history

    Symptom Raspberry Robin outbreak reaches hundreds of hosts via media.

    Root cause "Stuxnet-era problem" assumptions removed the controls.

    Fix Reinstate autorun-off, execution blocks, device control.

    Prevention Threat reviews include current worm reporting annually.

    2. Blocking storage but not execution

    Symptom Files cannot be copied, yet a .lnk still executed from E:.

    Root cause Policy models writes, not reads/execution.

    Fix Execution-prevention rules for removable and user-writable paths.

    Prevention Control matrix covers read/write/execute per device class.

    3. Wrong drive-letter assumptions in rules

    Symptom Rules tuned to E: miss infections on F:/G:.

    Root cause Hard-coded letters from one machine's setup.

    Fix Letter-range matching (D-Z) or device-based context.

    Prevention Rule reviews include letter-map verification.

    4. No media insert telemetry

    Symptom Outbreak reconstructed from memory and interviews.

    Root cause 6416/device-control events never collected.

    Fix Enable and ship device events; retain 12 months.

    Prevention Log-source coverage checklist for endpoint classes.

    5. Ignoring kiosks and shared machines

    Symptom Outbreak starts on a lobby kiosk nobody monitors.

    Root cause "Low-value" hosts excluded from tooling.

    Fix EDR + device control on kiosks; they touch everything.

    Prevention Coverage KPIs include shared endpoints.

    6. OT transfers without stations

    Symptom Media crosses zones at whichever desk was convenient.

    Root cause No sanctioned path, so users invent one.

    Fix Build the transfer station; make it the easy option.

    Prevention Zone-entry procedures with logged scans.

    7. One-host closure

    Symptom Rebuilt PC reinfected within days.

    Root cause Media and colleagues' hosts never scoped.

    Fix Hash pivot + itinerary reconstruction as mandatory steps.

    Prevention IR checklist includes media scoping.

    8. Hash allow-lists gone stale

    Symptom Approved-tool rule silently admits a repackaged worm.

    Root cause Allow-list never reviewed.

    Fix Quarterly allow-list review with owner sign-off.

    Prevention Allow-list items carry expiry and owner metadata.

    9. Exfil variant unmonitored

    Symptom Data leaves on media for months; network DLP sees nothing.

    Root cause Endpoint DLP and volume analytics absent.

    Fix Endpoint DLP + write-volume rules (section 5.5 Threat 3).

    Prevention DLP strategy explicitly covers offline channels.

    10. Awareness that shames instead of trains

    Symptom Users hide media use instead of reporting found drives.

    Root cause Blame-first culture around policy violations.

    Fix Reward reporting; simple drop-box for found media.

    Prevention Metrics on reports received, not violations punished.

    Daily habits

    • Review exec-from-media and autorun.inf alerts.
    • Check device-control blocks for patterns by user/site.
    • Verify transfer-station scans ran on schedule.

    Weekly habits

    • Hash-pivot any new media alert across the fleet.
    • Review insert telemetry for unusual site patterns.
    • Check kiosk and shared-host policy compliance.

    Monthly habits

    • Review the media allow-list with owners.
    • Replay section 5.5 test events; validate rules.
    • Audit OT/air-gap transfer procedures end to end.
