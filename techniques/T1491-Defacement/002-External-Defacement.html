Overview

What external defacement means in ATT&CK, how it differs from its sibling technique, and why it matters to defenders.

MITRE ATT&CK technique T1491 Defacement covers attacks that change the visual content of a system. The sub-technique T1491.002 External Defacement is the public version. The attacker alters pages that people on the internet see, such as a company homepage, a news site, a government portal, or a product page. The change is visible to anyone, not only to users inside the victim network.

A content management system (CMS) is the software many sites use to edit pages, for example WordPress, Joomla, or Drupal. Most external defacements happen when an attacker gets write access to that CMS, or to the web server files behind it. They then edit a template or upload a new page. A web shell (a hidden page that gives attackers command access through the browser) is often left behind so they can come back.

Note

The word "external" refers to who sees the change, not where the attacker sits. A defacement is external when visitors outside the organization's network can see it. The sibling technique T1491.001 Internal Defacement changes content that only internal users see, for example a login page or an intranet portal.

Why this technique matters

Defacement is a small edit with a large effect. Three reasons make it a priority for detection engineering:

It is public proof of compromise

Customers, press, and attackers all see the same page. Trust damage starts before your team even opens a ticket, and screenshots spread on social media within minutes.

It rarely comes alone

The same access that changed the page can read customer data, inject payment-page scripts, or plant backdoors. Treat every defacement as the visible tip of a possible data breach.

It is usually preventable to detect

Changing a public page leaves clear traces in web logs, file integrity monitoring, and CMS audit trails. Good logging plus a few tuned rules catch it early.

How attackers typically get in

Public reporting shows a small set of repeated entry paths. Knowing them tells you where your logs should point:

  • Exploiting a public-facing application (T1190): an unpatched plugin, an unsafe file upload, or SQL injection (a trick that sends database commands through web form input) in the CMS.
  • Using valid accounts (T1078): stolen or reused CMS admin passwords, sometimes phished, sometimes bought from other criminals.
  • Persisting with a web shell (T1505.003): after entry, a hidden server-side page keeps the access alive.
  • Changing content (T1565): the defacement itself is stored data manipulation.
  • Attacking the DNS layer (DNS is the system that turns domain names into server addresses): instead of touching the server, the attacker changes DNS records at the registrar so the domain shows attacker content.

Written story (text alternative)

This list says the same as the animation in words. It is also what prints when you print this page.

  1. Step 1 - Recon. Attacker: fingerprints an old CMS on the public site and finds an unpatched plugin by reading version files and probing plugin paths. Defenders see: quiet, low-rate GET requests for files like /CHANGELOG.txt and /readme.html; a good baseline of normal traffic makes this stand out.
  2. Step 2 - Entry. Attacker: logs in to the CMS admin panel with stolen or guessed admin credentials, or reaches it through SQL injection. Defenders see: a successful POST to the admin login from a new country or ASN (an internet provider network) and an unusual user agent such as python-requests.
  3. Step 3 - Persist. Attacker: uploads a web shell and creates an extra admin account for later access. Defenders see: a new file in an upload directory with executable behavior, and a new admin account in the CMS audit trail.
  4. Step 4 - Alter. Attacker: edits the homepage template and replaces the real content with an attacker banner. Defenders see: the file integrity monitor diffs the web root and flags a changed template hash.
  5. Step 5 - Publish. Attacker: does nothing more; the site now serves the defaced page, and the CDN caches spread it to visitors and search engines. Defenders see: a sudden traffic spike, external reports, and content-check monitors failing.
  6. Step 6 - Signal. Defenders see: the FIM diff lands in the SIEM (the central log platform where alerts are built), and the WAF flags a burst of admin-session requests from a new country. Two independent signals now point at the same host.
  7. Step 7 - Triage. Defenders: correlate web access logs, the CMS audit trail, and FIM diffs; they confirm one stolen session made the template edit. They do: preserve evidence, snapshot the web root, and start the incident process.
  8. Step 8 - Recover. Defenders: restore the template from a verified backup, remove the web shell, rotate all CMS credentials, invalidate CDN caches, and patch the vulnerable plugin. Defenders see: integrity checks pass again and monitoring confirms the content is back.

Red Team Perspective

How attackers think about external defacement: motives, methods, and the mistakes they make. All examples here are lab-only.

When and why attackers deface

External defacement has a few clear motives, and each motive leaves a different operational signature:

  • Hacktivism and protest. The page itself is the message. Attackers leave political text, slogans, or images. They want attention, so they often announce the act on social media or Telegram channels and link to defacement archives.
  • Bragging rights and reputation. Some groups measure status by how many sites they defaced. Public defacement mirrors (archives that copy defaced pages, similar to the well-known zone-h style services) count and rank them. This creates a useful side effect for defenders: if your site appears in such an archive, you have an external notification channel.
  • Smoke screen (a distraction). A loud defacement pulls attention while the same attacker exfiltrates data quietly. Public reporting repeatedly describes defacements that happened during or shortly before data theft. This is why every defacement response plan must include a data-breach check.
  • Opportunistic mass defacement. Most defacements are not targeted at all. Attackers scan the internet for one vulnerable CMS or plugin, exploit hundreds of sites with the same command, and swap the homepage on all of them. One exploit, many victims.

How it is performed

The typical attack chain is short and repeats across public incidents:

  1. Recon of the CMS and plugins. Attackers fingerprint versions from files like CHANGELOG.txt, readme.html, generator meta tags, and predictable plugin paths.
  2. Entry. Either an exploit of the public application (T1190), such as SQL injection or an unsafe file upload, or valid credentials (T1078) phished, reused, or bought.
  3. Persistence. A web shell (T1505.003) or an extra admin account keeps access after the first session ends.
  4. Content modification. Editing a template, swapping index.html/index.php, or injecting a script tag (T1565 Stored Data Manipulation).
  5. Optional DNS route. Instead of touching the server, some attackers take over the DNS or registrar account and point the domain elsewhere. The server stays clean, which confuses naive investigations.

Where it applies and what it needs

Defacement happens wherever an attacker gains write access to something the public sees. That includes web roots and templates, CMS content stores, third-party JavaScript files loaded by your pages, and DNS records. The prerequisites are simple: a public-facing application and a way to write to it. The way in can be an admin account, an upload flaw, an injection, or a forgotten subdomain. Nothing exotic is required, which is exactly why it stays common.

Danger - Lab only - never run against systems you do not own

Everything below describes benign shapes used in a lab you own. A legal first step is a simple header check with curl -I https://lab-vm.example, which only reads response headers. A fingerprinting pass with nikto -h http://lab-vm.example or wapiti -u http://lab-vm.example against your own lab VM shows which version files leak. Running sqlmap -u "http://lab-vm.example/dvwa/vulnerabilities/sqli/?id=1" against a deliberately vulnerable lab app such as DVWA shows what a SQL injection probe looks like in logs. Change the hostnames to your lab; run nothing against production or third-party sites.

Common variations

  • Single-site defacement by a targeted actor, usually hand-made content and a claim of responsibility.
  • Mass defacement of one platform: the same vulnerable plugin, hundreds of victims, near-identical pages.
  • Script injection instead of a full page swap: a single <script src=...> tag added to a template, sometimes to skim payment pages (a PCI compliance issue) rather than to show a banner.
  • DNS or registrar takeover: the defacement lives at the DNS layer and the content is served from attacker infrastructure.
  • Subdomain takeover: a dangling DNS record pointing to a retired cloud service is claimed by anyone and used to host fake or defaced content under your brand.

Attacker mistakes defenders should expect

Mass defacers work fast and leave traces. Common errors include reusing the same IP (internet protocol) address or hosting provider across victims. Others test the web shell from their normal accounts. Some deface before they finish exfiltrating data. Many reuse a nickname that appears in other incidents. And many edit templates through the admin UI (user interface), which writes a clean CMS audit trail. Your detection content in Section 5.5 is built to catch exactly these habits.

Blue Team Perspective

How the SOC sees a defacement, which artifacts to collect, and a triage flow you can follow line by line.

How defenders usually find out

In an ideal world, your own alerts fire first. Public incidents often start worse. A user or partner reports a strange page. A CDN or WAF alert arrives. A file integrity monitor flags the web root. An uptime or content check fails. Or the site appears in a defacement mirror and someone forwards a screenshot hours later. Every channel after "our own alert" adds public exposure, so the goal of Section 5 is to make your own tools notice first.

Artifacts to collect early

Files

Modified HTML and template files with odd modification times; unexpected files in upload directories; web shells; changed file hashes that FIM recorded.

Accounts

New admin users in the CMS, password resets nobody requested, logins from new ASNs or countries, sessions that span impossible travel.

Network

WAF records for the admin panel, bursts of POSTs to login or template endpoints, spikes in GETs of the homepage from many small networks.

DNS

Changed A, CNAME (alias), and NS (name server) records, registrar audit logs, dangling CNAMEs, and certificate issuance you did not request.

Where to look

  • Web access logs (nginx/apache/IIS): who logged in, who POSTed what, and from where.
  • WAF and CDN logs: blocked and allowed attack patterns, admin-panel exposure, cache purge events.
  • CMS audit trail: which account edited which template at which time.
  • File integrity monitoring such as AIDE (Advanced Intrusion Detection Environment), Wazuh, or OSSEC: hash diffs of the web root.
  • DNS and registrar logs: record changes and account activity.
  • Backups: the last known-good copy that proves what the page looked like before.
Warning

WAF and CDN logs often have the shortest retention in the company, sometimes days. If you do not centralize them now, the exact requests behind the next defacement may already be gone by the time you investigate.

Why it matters

Defacement is visible proof that an outside party had write access to your public site. The page is the symptom; the access is the problem. Before you declare recovery, check what else that access touched. Look at customer data in the CMS database, injected scripts on payment pages (a PCI issue even when nothing else was stolen), stored credentials, and email or notification systems reachable from the CMS. Public defacement also has regulatory weight. If personal data was in the same system, GDPR (General Data Protection Regulation) timelines (Section 5.1) start ticking whether or not you are sure data left.

Triage flow

  1. T+0 to 15 minConfirm. Verify the defacement yourself (direct fetch and through the CDN), scope which pages and subdomains are affected, and stop assuming it is a mistake.
  2. T+15 to 60 minPreserve. Snapshot the web root, export relevant log slices (web, WAF, CMS, FIM, DNS), and record hashes before anything is repaired.
  3. T+1 to 2 hContain. Disable the compromised accounts and sessions, block the attacker infrastructure, take the site or admin panel offline if the business allows, and enable WAF rules.
  4. Day 1Evict. Remove web shells and rogue admin accounts, patch the entry vulnerability, and rotate all credentials with access to the CMS, hosting panel, and registrar.
  5. Day 1 to 2Restore. Rebuild from verified backups or fresh deployment, purge CDN caches, and re-enable integrity monitoring before traffic returns.
  6. Week 1Review. Check for data access and exfiltration, run the breach-notification decision with legal, and write the timeline from logs.
  7. Week 2Harden. Close the logging gaps found during triage and add the detections from Section 5.5 that did not exist yet.

5.2Threat intelligence

Threat intelligence turns "a site got defaced" into "actors like this, using this path, hit sites like ours last month". A lightweight workflow is enough:

  1. Collect. Subscribe to a small, high-signal set: MITRE ATT&CK updates (STIX/TAXII feeds where available), vendor blogs, free feeds such as the CISA Known Exploited Vulnerabilities (KEV) catalog and abuse.ch trackers, ISAC sharing groups such as FS-ISAC (financial sector) or MS-ISAC (US state and local government), commercial feeds your budget allows, and OSINT sources like defacement mirrors and national CERT advisories. Add your own telemetry: what your WAF blocked last month is your best baseline.
  2. Analyze. Ask which entry paths and platforms are rising. A new exploit chain for a popular plugin will hit mass defacers within days; one vendor blog post can buy you a week of lead time to patch.
  3. Apply. Turn findings into detection content (new regexes for 5.4, new Sigma rules in 5.5), into patch priorities, and into WAF rules. Review quarterly: retire rules for dead campaigns, keep the evergreen ones.

5.3Threats ranking and categorization

These seven threats cover the realistic paths to an external defacement for most organizations. Sections 5.4 and 5.5 are built on them: every log pattern below maps back to one of these IDs, and six of the seven have a matching Sigma rule and SPL query. TH-07 is covered by external content checks instead of a webserver rule.

Critical TH-01 Network

Exploit of a public-facing application leading to homepage replacement

Description: an internet-reachable CMS or plugin with a remote code execution or SQL injection flaw is exploited; the attacker then replaces homepage content.

Preconditions: an unpatched, internet-reachable application with web-writable files or a database-backed CMS.

Impact: public defacement within hours, plus possible data theft through the same exploit before anyone notices.

Rank justification: this is the dominant real-world path in defacement archives and vendor telemetry; frequency plus public blast radius earns Critical.

High TH-02 Identity

CMS admin credential compromise used to edit templates

Description: phished, reused, or weakly protected admin credentials log in to the CMS and change templates through the official editor.

Preconditions: an admin account without MFA, a password reused from a breached service, or shared credentials.

Impact: defacement through legitimate-looking edits, which complicates attribution and cleanup; attacker can also read stored content.

Rank justification: very common, but detected reliably by credential controls (MFA, new-device alerts, audit trails) when organizations deploy them.

High TH-03 Network

Compromised third-party JavaScript altering pages for every visitor

Description: a supply-chain compromise of an analytics, marketing, or chat widget script injects attacker code into every page that loads it - defacement or silent skimming.

Preconditions: third-party scripts loaded without integrity checks, subresource integrity not enforced, no script allowlist.

Impact: largest possible blast radius: all visitors affected at once; payment-page skimming risk makes it a PCI 6.4.3/11.5.2 issue.

Rank justification: rarer than TH-01/TH-02, but one incident affects every visitor; High is justified by blast radius, not frequency.

Medium TH-04 Network

DNS or registrar hijack pointing the domain to attacker content

Description: attacker changes DNS records at the registrar or DNS host; your domain serves attacker content from their infrastructure while your servers stay untouched.

Preconditions: registrar account without MFA, expired domain, API token leakage, or a compromised email inbox able to reset registrar access.

Impact: full brand control for the attacker: visitors, mail routing, and certificate issuance can all be redirected.

Rank justification: lower frequency than web exploits, but trust and availability impact is severe and recovery can take longer than the intrusion itself.

Medium TH-05 Cloud

Abandoned subdomain takeover hosting fake or defacement content

Description: a DNS record still points to a decommissioned cloud resource (for example a retired hosting plan); anyone can claim that resource and publish content under your subdomain.

Preconditions: dangling CNAMEs, no periodic DNS hygiene scans, cloud resources deleted without record cleanup.

Impact: phishing and fake content under your brand; possible cookie abuse on scoped domains.

Rank justification: cheap for attackers and medium in impact, but trivially fixed with DNS hygiene, so Medium with easy remediation.

High TH-06 Web Cloud

Malicious plugin or theme supply-chain backdoor causing mass defacement

Description: an attacker compromises a plugin or theme vendor and ships a poisoned update (T1195.002). Every site that installs the update installs the backdoor, which the attacker later triggers to replace homepage content on many sites in one wave.

Preconditions: sites that install third-party code quickly or without review, no file-integrity baseline of plugin directories, and one vendor whose update path is weak.

Impact: mass defacement in a single wave, web shells on every site the update reached, and cleanup work that repeats per site.

Rank justification: rarer than TH-01, but vendor compromises have repeatedly hit popular platforms, and one event multiplies across every customer of the vendor, so High is justified by scale.

Medium TH-07 Network Cloud

CDN or edge cache poisoning serving attacker content from your own domain

Description: the attacker abuses a caching layer (CDN or reverse proxy) so edge servers store and serve a defaced copy of a page while the origin server stays clean. Routes include cache-key confusion, web cache poisoning tricks, or a compromised CDN account.

Preconditions: a CDN in front of the site, cache rules that let attacker input influence what gets stored, and no multi-region content checks.

Impact: visitors see attacker content on your trusted domain, while server-side FIM and CMS logs show nothing at all.

Rank justification: low frequency and quick to fix with a cache purge, but it bypasses every origin-side control, so it earns Medium with a strong monitoring requirement.

5.4Logs and patterns

For each threat: where the evidence lives, which fields matter, what normal looks like, what suspicious looks like, and the detection logic. All IP addresses below use the RFC 5737 documentation ranges (203.0.113.0/24, 198.51.100.0/24) so nothing here points at a real victim or attacker.

TH-01CriticalExploit of public-facing app
Log sources
nginx/apache/IIS access logs, WAF logs, FIM diffs, CMS database logs.
Key fields
client_ip, method, uri, uri_query, status, user_agent, bytes, FIM path/old_hash/new_hash.
Normal behavior
Admin logins from known office/VPN ranges and standard browsers; uniform SQL queries; no writes to web root outside deploy windows; FIM changes only during releases.
Suspicious behavior
SQL keywords (UNION SELECT, information_schema) in queries; admin POSTs with tool user agents (sqlmap, python-requests); file writes in /uploads/ or template directories outside deploys; response sizes jumping for probe-like requests.
Detection logic
Alert on (a) SQLi-shaped queries against CMS parameters, or (b) any write to web-root content outside a deploy window, correlated within one hour to the same source IP.
  • 203.0.113.7 - client IP; here the attacker. Flag first-seen ASNs for admin endpoints.
  • [22/Oct/2026:09:05:12 +0000] - request timestamp; keep timezone consistent to correlate with WAF and FIM.
  • GET /index.php?option=...id=-1%20UNION%20SELECT... - percent-encoded SQL (%20 is a space) inside a CMS parameter: a SQL injection probe (T1190).
  • 200 5123 - status and response size. A probe that returns 200 with a large body often means data came back, not an error page.
  • sqlmap/1.8 / python-requests/2.31 - user agents that never belong in a CMS admin path.
  • POST /administrator/index.php with 200 - a successful admin request from the same IP nine minutes later: move from "probe" to "likely compromise".
TH-02HighStolen CMS admin credentials
Log sources
CMS audit trail, web access logs (login endpoints), WAF, identity provider logs if SSO is used.
Key fields
username, action (login, template.save, user.create), client_ip, asn/geo, user_agent, session_id, object (edited template).
Normal behavior
Logins from office/VPN ranges during business hours; edits by named content editors; sessions last minutes to hours.
Suspicious behavior
Login from a new country or ASN without SSO; admin edits at 03:00 local; template.save followed by homepage change; new admin user created by another admin minutes after login; same session used for recon pages first.
Detection logic
Alert when a template or media-object edit is followed by an external content change, or when admin login + new admin user + template edit happen in one session.
  • event: user.create with role: admin - a brand-new privileged account; on many CMSs this is exactly what an attacker does right after login (persistence).
  • actor: cmsadmin - the account that logged in from a new ASN nine minutes earlier; the same session ID ties the whole chain together.
  • session: 4f2a9c - the correlation key: one session covering login, account creation, file upload, and the template edit is the TH-02 pattern.
  • ip / geo - the ASN and country fields power the "first-seen source for admin actions" rule; document your normal admin sources.
  • ts in UTC - keep one timezone across web, WAF, CMS, and FIM logs or correlation windows will silently miss.
TH-03HighThird-party script compromise
Log sources
Content Security Policy violation reports, CDN edge logs, script-integrity scanners, browser telemetry.
Key fields
CSP report: document-uri, violated-directive, blocked-uri; CDN: script_url, content_hash, e_tag.
Normal behavior
Only allowlisted script origins appear; script hashes stable between releases; occasional CSP reports from browser extensions.
Suspicious behavior
A new external script origin on your pages; a hash change on a third-party script without a vendor announcement; CSP reports naming a script origin you never approved.
Detection logic
Diff the set of script origins served by your pages on a schedule (hourly crawl) and alert on any origin not in the allowlist; treat hash drift on payment pages as immediate (PCI 11.5.2).
TH-04MediumDNS or registrar hijack
Log sources
Registrar/DNS provider audit logs, DNS monitoring services, certificate transparency logs, web access logs.
Key fields
record_type (A, CNAME, NS), old_value, new_value, actor_account, source_ip, cs_host (Host header).
Normal behavior
Record changes only via change tickets during business hours; certificates renewed by known automation; Host headers always match your hostnames.
Suspicious behavior
Record change from a new country or via API token first used that day; NS record changes (a nameserver move is the most drastic change); certificate issuance for your domain from a new registrar account; requests arriving at your origin with a Host header that is not one of your names.
Detection logic
Alert on any DNS record change touching public domains, with severity escalating for NS records and for changes without an open change ticket; poll public DNS every few minutes and compare against a golden record set.
TH-05MediumSubdomain takeover
Log sources
DNS hygiene scan results, web access logs, certificate transparency logs, external brand-monitoring alerts.
Key fields
subdomain, cname_target, nxdomain flags, http_status (404/not-found fingerprints of cloud services), scanning_actor.
Normal behavior
Every CNAME resolves to a live resource you own; 404s on your hosts only for genuine missing pages.
Suspicious behavior
CNAME pointing to a service fingerprint that answers "there is no such app here" (typical takeover signal); anyone can register the resource; 404 bursts probing forgotten subdomains from scanning ranges.
Detection logic
Weekly job resolves every DNS record of your zones, flags CNAMEs to known takeover-able fingerprints, and alerts; monitor certificate transparency for certificates issued to your subdomains by unknown parties.
TH-06HighPlugin supply-chain backdoor
Log sources
FIM/file-integrity events for web roots, CMS audit trail (plugin and theme updates), package or deployment logs, vendor release feeds.
Key fields
path, change_type (added/modified), actor, old_hash/new_hash, CMS event (plugin.update, theme.update), host.
Normal behavior
Plugin files change only during announced vendor releases or deploy windows, made by the deploy account, with a matching vendor changelog.
Suspicious behavior
PHP files added or modified in plugin/theme directories outside a deploy window; a plugin update followed by new files in upload directories; the same file hash appearing on many unrelated sites at once (mass event).
Detection logic
Alert on any PHP file added or modified under plugin/theme paths by an actor that is not a registered deploy account, and group FIM events per day to spot the mass pattern.
  • path - a new PHP file inside a plugin directory on a day with no vendor release: the backdoor drop.
  • actor: www-data - the web server user wrote the file, not the deploy account; plugin updates should arrive through the deploy user or a package manager.
  • change_type: added plus new_hash - gives you the baseline to hunt every other site for the same hash.
  • 03:41 - outside deploy windows; correlate with the CMS audit trail to prove no human started an update.
TH-07MediumCDN cache poisoning
Log sources
CDN edge logs (cache status, cached object metadata), external multi-region content-hash checks, CDN configuration audit logs, origin access logs.
Key fields
cache_status (HIT/MISS), cache_key, url, e_tag or content_hash, pop (edge location), actor_account for config changes.
Normal behavior
Page content hashes are stable across all regions between deploys; cache purges only follow deploys; CDN config changes only via change tickets.
Suspicious behavior
One or more edge locations serving a different content hash for the same URL than the origin; a purge or cache-rule change nobody requested; visitor reports of content your origin cannot reproduce.
Detection logic
Compare page hashes from several regions plus the origin on a schedule; alert on any region that differs, and on any CDN config change without a ticket.
  • fr-par-1 serves a different e_tag than us-east-1 and the origin check for the same URL: one region holds a poisoned copy.
  • cache=HIT - the attacker content comes from cache, so origin FIM and origin logs stay clean; only edge-side or external comparison sees it.
  • The third line is the scheduled origin check; hashing the same URL at the origin makes the diff automatic.

Two more event-shaped examples complete the picture: a file-integrity diff (the strongest single signal of TH-01/TH-02 success) and a WAF verdict line.

  • added: /var/www/html/uploads/helper.php - a new file in an upload directory is how a web shell (T1505.003) often appears; uploads must never be executable.
  • changed: .../templates/home/index.php - the homepage template changed outside a deploy; this is the defacement moment in file form (T1491.002).
  • old_sha512 / new_sha512 - the before/after hashes; they become evidence and the baseline for the restore check.
  • mtime_old / mtime_new - the last known-good modification was during a release window; the new one (09:26) sits between deploys and matches the admin-session times in the access log.
  • [client 203.0.113.7:51244] - the same source IP as the access-log probe: one attacker, two logs; correlation multiplies confidence.
  • Access denied with code 403 (phase 2) - the WAF blocked this attempt; note that "blocked" here does not mean safe overall, other attempts may have been allowed.
  • Pattern match ... at ARGS:task - the injection sat in a CMS request parameter; map which parameters your CMS exposes.
  • [id "942100"] - the OWASP CRS rule ID; use these IDs for tuning rather than rewriting rules from scratch.
  • [severity "CRITICAL"] - WAF severity is not SOC priority; feed it into a rule like the TH-01 Sigma below with your own thresholds.

Seven threats, six Sigma rules, six Splunk queries. Rules and queries TH-01 to TH-06 map one to one; TH-07 (cache poisoning) is detected outside the webserver with the external content-hash checks from 5.4, because origin logs stay clean during a cache event. Real-World Case Study

The Police Federation of England and Wales defacement (April 2019): what happened, the ATT&CK chain, and the lessons for detection engineering.

Widely reported in April 2019: attackers hit the website estate of the Police Federation of England and Wales (PFEW), the staff association for police officers. Public reporting described a SQL injection (a trick that sends database commands through web form input) against a legacy CMS, attacker content shown on the public sites, and officer personal data potentially exposed. Some reports mentioned card-related details for some accounts. The affected sites were taken offline, the UK Information Commissioner's Office (ICO, the data protection regulator) was informed, and the services were later rebuilt on updated infrastructure.

Note

Exact dates, counts, and data-scope details vary between reports. The timeline below is hedged on purpose; treat it as a teaching reconstruction, not a forensic record.

Public record vs illustrative

Public record (widely reported): the April 2019 attack, SQL injection as the reported method, officer personal data potentially exposed, sites taken offline, ICO informed, and a later rebuild. Illustrative (teaching reconstruction): the number of affected sites, the attacker tooling, the internal triage steps, and the exact detection and response actions described below. Reports differed on the counts, so this page keeps them vague on purpose.

Context

PFEW is a staff association for police officers in England and Wales. Like many membership organizations, it ran a main site plus many branch websites on the same CMS platform. That pattern matters: one vulnerable component shared across all branch sites means one exploit defaces all of them, and one cleanup has to cover all of them too. Legacy CMS platforms are common in this exact situation because branch sites get built once and then run untouched for years.

Timeline (public reporting, hedged)

  1. Before April 2019Weakness present. A legacy CMS with a SQL injection flaw runs across the branch sites; it is internet-reachable and part of nobody's active patching scope.
  2. Days before discoveryExploitation. Attackers exploit the injection (T1190), reach the database behind the CMS, and gain enough control to alter site content.
  3. Discovery dayDefacement goes public. The public sites show attacker content (T1491.002). According to public reporting, visitors and media see it before the organization publishes any statement.
  4. Same periodData exposure surfaces. Investigations indicate officer personal data, including card-related records in some reports, was potentially accessed in the same compromise (T1213 Data from Information Repositories).
  5. Hours afterContainment. The affected sites are taken offline entirely; the organization chooses availability loss over serving attacker content.
  6. Days afterRegulatory notification. The ICO is informed; the organization communicates with members about the potential data exposure.
  7. Following weeksRebuild. Services are rebuilt on updated infrastructure rather than patched in place, and the compromised platform is retired.

Attack chain mapped to ATT&CK

Detection point: the miss that defines the case

The defacement was discovered publicly and externally, not by an internal alert. That single fact is the lesson. A SQL injection campaign against one CMS usually produces weeks of noisy evidence: UNION SELECT probes in access logs, WAF verdicts, odd response sizes, and finally file or database changes. None of it raised an internal alert, because the detections in Section 5.5 did not exist for those sites. External defacement monitoring (Section 7) would have caught the actual content change within minutes even without web-log coverage.

Containment, eradication, recovery

Containment: sites offline; the fastest honest control when attacker content is live. Public messaging followed so the silence had an explanation. Eradication: the injection paths and the compromised platform were removed by rebuilding on updated infrastructure instead of patching a system no longer trusted. Recovery: services migrated to the new platform and member communications restored confidence step by step.

Impact

  • Reputational: a police staff association publicly embarrassed; the defacement story ran in national media.
  • Regulatory: ICO notification and the burden of proving what data was and was not taken.
  • Operational: the whole branch-site estate offline at once and a full rebuild on a new platform.
  • Human: officers learning their personal and card-related details were potentially exposed, an often-undercounted cost.

Team response and communication

Public reporting shows the pattern that works: a fast statement acknowledging the incident, an explicit warning to members about potential data exposure with practical advice, engagement with the regulator, and a visible rebuild afterward. Compare that with the alternative - a defaced page as the only communication channel - and the value of a prepared communications template (Section 7) becomes obvious.

Tools used (illustrative)

Public reporting did not name the attacker tooling. What this attack class usually leaves behind (illustrative): SQL injection probes or hand-crafted requests for entry, database commands to read member records, and CMS or template edits to place the attacker message. Defenders should expect this class to look ordinary: standard web requests, standard admin paths, and one unusual session doing all of it.

Response team roles (illustrative)

Reporting confirms the visible actions but not the internal roles. A response of this shape typically involves five roles. The web or platform owner takes the sites offline. The security lead runs triage and evidence handling. The data protection lead runs the personal-data assessment and the ICO conversation. The communications lead drafts the member statement. The infrastructure team rebuilds the estate on the new platform. Naming these people before an incident is the actual lesson.

Lessons learned

  1. Inventory the long tail. A whole estate of branch sites on one legacy CMS is one shared attack surface behind one patch process that clearly was not watching it. Keep an asset inventory that includes forgotten subdomains and branch sites.
  2. Parameterize queries. SQL injection is fully preventable with parameterized queries and input validation in the application layer.
  3. Monitor integrity. FIM on web roots plus CMS audit trails turns "the public noticed" into "our alert fired first".
  4. Watch externally too. Defacement mirrors, uptime checks, and content hash monitors are cheap external alarms.
  5. Rehearse breach notification. The 72-hour GDPR clock starts on awareness; the decision tree and template must exist before the incident.
7

Mitigation and Defense

Controls grouped by layer, a prioritized action table, and a small-business path. Mitigation names follow MITRE ATT&CK.

Enterprise controls by layer

Policy

Change management with an approval workflow for content: template edits deploy like code, through review, never through a rogue admin session. Define who owns website security - one named owner beats three committees.

Identity

Privileged Account Management: MFA on every CMS, hosting panel, and registrar account; least-privilege roles for editors; no shared admin accounts; sessions revoked centrally.

Endpoint

Update Software on the whole web stack (CMS core, plugins, PHP runtime, operating system). Add EDR (endpoint detection and response) on admin jump hosts, not necessarily on web servers. Patch internet-facing vulnerabilities (CVEs, published security flaws) within days.

Network

Exploit Protection via a tuned WAF; CDN protections and rate limiting; admin panels restricted by IP allowlist or VPN; Exploit Protection also means disabling dangerous plugin features.

Cloud and hosting

Hardened hosting images, separate deploy credentials from editor credentials, immutable deploys where possible so the web root is not writable at runtime, and Network Segmentation between CMS and internal networks.

Logging and monitoring

Centralize web, WAF, CMS, and DNS logs with retention that outlives an attacker's patience. FIM on web roots, third-party defacement monitors, and content-hash checks on key pages.

Backup

Data Backup with verified, offline copies of site files and the CMS database, tested by actual restore drills. A backup you have never restored may not work when you need it.

Response

A defacement playbook: who takes the site down, who drafts the statement, who calls the regulator, who restores content. Pre-write the comms templates; nobody writes well at 03:00.

Home and small office

Small sites face the same mass-defacers with none of the staff. The short version: use managed hosting that applies automatic updates. Keep only the plugins you actually use. Use a unique password plus MFA (multi-factor authentication) on the admin account. Enable the host's automated backups and verify a restore once. Turn on the host's web application firewall if it exists. Most home defacements are prevented by exactly these five habits.

Best practice

Defense in depth for this technique is one sentence: make write access rare, make writes loud, and make recovery boring. Every control above serves one of those three verbs.

Common Mistakes and Best Practices

Twelve blue-team mistakes seen around defacement incidents, each with symptom, root cause, fix, and prevention, plus a habit list.

FIM noise from deployments

Symptom
FIM alerts flood the channel every release; analysts auto-ignore them.
Root cause
No deploy-window awareness in the FIM rule or the parser.
Fix
Tag deploy events and suppress FIM alerts that overlap them; alert on everything else.
Prevention
Feed CI/CD deploy records into the SIEM so suppression is data-driven, not manual.

Alert fatigue on WAF rules

Symptom
Hundreds of low-quality WAF alerts per day; the real one is missed.
Root cause
Raw WAF severities forwarded as-is with no thresholding.
Fix
Aggregate per source IP and rule ID; alert on clusters, not single hits.
Prevention
Monthly false-positive review with a mute list and documented exceptions.

WAF logs not retained

Symptom
During the incident, the WAF requests that mattered are older than the retention window.
Root cause
WAF logs stay on the appliance or CDN default (often 7 days).
Fix
Ship WAF logs to the SIEM; keep at least 90 days hot, a year cold.
Prevention
Log inventory review each quarter; retention is a control (ISO A.8.15), not a preference.

Tuning done once, never again

Symptom
Rules drift between "always firing" and "silently disabled".
Root cause
No owner and no schedule for detection maintenance.
Fix
Give each rule an owner and a review date; track changes in version control.
Prevention
Quarterly rule review with test log replays (see 5.5 deployment tip).

Nobody owns website security

Symptom
CMS patching is "marketing's job" and security finds out after defacement.
Root cause
Sites bought by departments, operated by vendors, invisible to IT asset lists.
Fix
Named owner per public site, recorded in the asset inventory.
Prevention
Include websites and subdomains in the same CMDB and risk process as servers.

CMS audit trail disabled

Symptom
Template was edited, but by whom is unknowable.
Root cause
Audit plugins never enabled, or their logs not shipped.
Fix
Enable audit logging and centralize it with the web logs.
Prevention
Add "audit trail present" to the site launch checklist.

Admin panel open to the internet

Symptom
Constant credential-stuffing noise against /wp-login.php.
Root cause
Convenience; nobody asked for the allowlist.
Fix
Restrict by IP/VPN, add MFA, and rate-limit what remains.
Prevention
External attack-surface scan flags exposed admin panels automatically.

Backups never restore-tested

Symptom
Restore fails during the incident; wrong plugin version, DB schema mismatch.
Root cause
Backups exist, restores are assumed.
Fix
Scheduled restore drill to a scratch environment.
Prevention
Drill twice a year; record RTO actually achieved.

No external view at all

Symptom
Customers report the defacement before any internal system does.
Root cause
All monitoring is inside the perimeter; CDN caches hide changes.
Fix
Add uptime plus content-hash checks that fetch from outside the network.
Prevention
Weekly check that external monitors cover every public hostname.

Shared admin accounts

Symptom
Audit trail says "admin" did it; four humans had the password.
Root cause
Legacy habits and vendor handovers.
Fix
Named accounts only; shared accounts disabled after handover.
Prevention
Quarterly account review; orphan accounts disabled automatically.

Forgetting DNS and registrar

Symptom
Site rebuilt, then defaced again through the registrar account.
Root cause
Response plan covers the server, not the domain layer.
Fix
Rotate registrar credentials, enable registrar lock and MFA.
Prevention
Add DNS record change alerting to the same SIEM as web logs.

Over-trusting the CDN cache

Symptom
"Site looks fine to me" while some regions see attacker content.
Root cause
Checking from one location through one cache node.
Fix
Purge CDN caches during containment; verify from multiple regions.
Prevention
Multi-region content checks in the external monitor set.

Habits that keep the defenses honest

Daily

  • Review FIM and WAF alert queues with a deploy-window filter applied.
  • Glance at the external content-check dashboard for every public site.
  • Triage any new admin login from an unseen country or ASN.

Weekly

  • Check CMS and plugin advisories for anything internet-facing you run.
  • Review top 10 client IPs hitting admin endpoints; allowlist or block.
  • Confirm backups completed and one restore path was spot-checked.

Monthly

  • False-positive review of the 5.5 rules; tune or retire.
  • DNS record diff against inventory; close dangling records.
  • Verify log retention actually covers web, WAF, CMS, and DNS sources.
