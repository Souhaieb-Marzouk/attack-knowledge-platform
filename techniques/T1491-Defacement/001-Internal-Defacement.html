T1491.001Internal Defacement

Internal Defacement is when an attacker changes content that a victim's own staff see inside their network. Think of an intranet page, a staff dashboard, a login screen, or even the screen a computer shows when it starts. This page explains the technique, shows an animated attack walk-through, and gives detection engineers ready-to-use rules.

Tactic: Impact Parent: T1491 Defacement Platforms: ESXi, Linux, Windows, macOS Version: 2.0 · Reviewed 2026-10-22

ATT&CK ID

T1491.001 under the Impact tactic. Parent technique T1491 (Defacement).

Where it happens

Inside the victim network: intranet pages, internal app screens, login screens, and boot screens.

Data layer

The text and images often live in SQL databases or in server-side includes (SSI), so attackers edit data, not just files.

Main data sources

Process creation, file modification, database audit, and registry or GPO change logs.

Overview

What internal defacement is, how it differs from public website defacement, and why it usually means an intrusion has already gone far.

When people hear "defacement", they picture a public website with a rude message. Internal Defacement (T1491.001) is different. Here, the attacker changes content that only the victim's own staff can see, inside the victim's network. The audience is employees, not the internet. Because the attacker must already be inside the network to do this, internal defacement is often a late-stage action. It can be a sign of intimidation, a distraction, or proof that the attacker controls important systems.

MITRE ATT&CK is a public knowledge base that describes what real attackers do. In ATT&CK terms, this sub-technique sits under the parent technique T1491 (Defacement) in the Impact tactic. The Impact tactic covers actions attackers take to break availability, damage trust, or destroy data. ATT&CK notes that internal defacement can be carried out by modifying content in SQL databases or through server-side includes (SSI). SSI files are small server commands placed inside web pages that tell the server to insert other content when the page loads. Attackers who edit that layer change what every visitor of the internal page sees, without touching the page template itself.

What attackers change

  • Intranet portal pages and news boxes that staff read every morning.
  • Internal dashboards fed by SQL tables, so the "data" itself shows attacker-chosen text.
  • Windows login screens and desktop wallpapers, pushed through registry keys or Group Policy.
  • Boot screens. Destructive malware can replace the Master Boot Record (MBR, the small boot program at the start of a disk) with an image.
  • Container platform default pages and internal app assets.

Where the content lives

  • Rows in SQL databases behind portals and dashboards.
  • Server-side includes (SSI) and page templates on internal web servers.
  • Registry values such as the per-user wallpaper path or logon UI keys.
  • Group Policy Objects (GPOs, the central Windows settings store in Active Directory).
  • Disk boot sectors and firmware-adjacent boot files.

Note

The sibling sub-technique T1491.002 (External Defacement) targets public-facing web pages. The attacker's goal and audience are different: outside embarrassment versus inside confusion and fear.

Key terms in plain words

ATT&CK
MITRE ATT&CK, a public catalog of attacker behaviors, grouped into tactics (the "why") and techniques (the "how").
Intranet
A private internal website that only company staff can reach.
GPO
Group Policy Object. A central Windows setting that admins push to many computers at once, often used for wallpapers and login banners.
MBR
Master Boot Record. The small boot program at the start of a disk. If it is replaced, the machine shows attacker-chosen content at startup or fails to boot.
Sysmon
A free Windows add-on that logs detailed process, file, and registry events to the Event Log.
EDR
Endpoint Detection and Response. Security software on endpoints that records behavior and can block actions.
SIEM
Security Information and Event Management. The central system (for example Splunk) that collects and searches logs.
VLAN
Virtual Local Area Network. A way to split one physical network into isolated logical segments.

How this technique fits the attack chain

Internal defacement almost never stands alone. Attackers usually need valid accounts (T1078) and some lateral movement before they can reach internal content. It often appears next to destructive techniques such as T1561 (Disk Wipe), T1485 (Data Destruction), or T1486 (Data Encrypted for Impact). That is why defenders treat it as an escalation signal, not as a harmless prank.

Best practice

Watch internal content the way you watch public pages. If staff can see it, attackers can change it, and you should have a log trail for every change.

Written story (text alternative)

This list says the same thing as the animation, in words. It also serves as the printed version of this section.

  1. Foothold. The attacker sends a phishing email with an infected document. An employee opens it. The document starts PowerShell, and the attacker now runs commands on workstation WKS-2211. Defenders later see one Office application spawning a scripting process, a common first clue.
  2. Escalate. The attacker steals saved credentials from the workstation and uses them to log on to other systems, including the database server and the domain controller. Defenders see several new logons with the same account within minutes, from machines the user never touches normally.
  3. Tamper. The attacker runs an UPDATE statement against the internal database that feeds the staff dashboard. Headlines change to attacker-chosen text. Defenders find a database audit row showing an unusual service account writing to a content table outside the release window.
  4. Deploy. The attacker copies a destructive payload to a file share that many machines can reach. Defenders see a new unknown binary appear on an admin share, written by the compromised workstation.
  5. Spread. The payload runs on many machines through scheduled tasks and share access. Files on documents, images, and portals are overwritten. Defenders see a flood of file-write events across one subnet in a few minutes.
  6. Disguise. The payload writes an attacker-chosen image into the Master Boot Record. Rebuilt machines boot into a fake screen instead of the normal startup. Defenders see raw disk sector writes to device paths such as the harddisk0 device.
  7. Alarm. Helpdesk tickets spike, and Sysmon floods with file events. The SOC links the dashboard change from step 3 and the file flood from step 5 to the same intrusion and declares a major incident.
  8. Recover. The affected VLAN is isolated at the switch. Machines are rebuilt from trusted golden images, the database is restored from a clean backup, and all exposed credentials are rotated. Defenders keep one affected disk for forensics before wiping it.

Red Team Perspective

Why attackers change internal content, how they find it, and what they need first. All examples here are lab-only descriptions, not attack instructions.

Why attackers deface internal content

Attackers pick internal defacement for four main reasons. First, intimidation: a threatening message on every staff dashboard spreads fear faster than an email. Second, distraction: while the helpdesk receives many "the screen looks wrong" tickets, the attacker steals data elsewhere. Third, proof of access: showing attacker-chosen text inside a network is a loud way to prove the intrusion is real, often used in extortion conversations. Fourth, psychological impact on staff: people trust what they see on the intranet, so fake notices can cause real confusion, for example a fake "payroll is delayed" message.

How it is done, stage by stage

The attacker first needs internal access. That comes from a phished user, a purchased set of credentials, or an exposed remote service. Next, the attacker looks for where the content is stored. Common places are SQL tables behind portals, template and include files on internal web servers, Group Policy settings that push wallpapers, and, for destructive tooling, the boot records of disks. The last stage is the modification itself: a database UPDATE, a file overwrite, a registry write, or a raw disk write.

Order matters to the attacker. Changing content too early wastes their access for a short-term effect. Careful groups stage everything first, keep a way back to the data, and only then deface, often at the same time as wiping or encrypting files.

Where the change shows up

  • Intranet portals and news pages: database rows or include files edited directly.
  • Internal dashboards: the data layer behind charts and headline boxes is modified.
  • Login screens and wallpapers: registry values such as the desktop wallpaper path, or a GPO that pushes a fake corporate notice to every desktop.
  • Boot screens: destructive malware replaces the Master Boot Record or boot files, so machines show attacker-chosen content at startup. Public reporting links this behavior to wiper families such as Shamoon.
  • Container platforms: default pages of web pods or internal portal assets in the cluster registry are replaced.

What attackers need first

Minimum requirements are a foothold inside the network and write access to the target content. Editing a dashboard row needs the database account the app uses, or stolen credentials for it. Pushing a fleet-wide wallpaper needs admin rights or the right to edit a GPO. Replacing boot records needs SYSTEM-level code execution on each machine. In short: more visible defacement needs more privilege, which is exactly why it signals a deep intrusion.

Common variations

  • Database-first: change rows instead of files, so backups of web roots stay "clean".
  • Template-only: edit one include file that many pages pull in, for maximum reach with minimum writes.
  • Timing-based: deface during a real maintenance window so the change blends into planned work.
  • Destructive bundle: pair the defacement with wiping (T1561) or encryption (T1486) so recovery is the only option.

Mistakes attackers make

Attackers often deface too early, before their foothold is stable, and the alert arrives while they are still on the machine. Some use accounts that have never touched the content system before, which makes the audit row trivial to flag. Others leave the payload on shares with obvious names or forget that file servers log every write. Good defenders study these sloppy patterns, because they describe the boundary where attacker behavior crosses into visible noise.

Blue Team Perspective

How defenders notice internal defacement, which artifacts it leaves, and a triage flow that keeps the response fast and orderly.

How defenders see it first

Detection usually starts in one of four ways. The human way: staff report that "the screen looks wrong", a dashboard shows a strange message, or a machine boots into a picture nobody made. The file way: a file-integrity monitor or EDR shows a burst of writes to a web or portal root. The database way: an audit alert fires because a content table changed outside the release window. The endpoint way: EDR flags a mass file-modification pattern, or Sysmon event volume jumps in a way that no business process explains.

Artifacts to expect

Where to look, log source by log source

  • Sysmon EID 1: process creation. Look for scripting shells whose parents are Office apps, and for command lines that copy files into web roots or reference raw disk devices.
  • Sysmon EID 11: file creation. Look for writes under portal roots, admin shares, and many-user directories within short windows.
  • Sysmon EID 13: registry set events. Look for wallpaper values and logon UI keys changed by non-standard processes.
  • Windows Security 4663: attempts to write objects, useful when Sysmon is not deployed; the SACL must be configured.
  • PowerShell 4104: script block logging, which captures the content of scripts that copy or overwrite content at scale.
  • Database audit logs: statements and accounts touching content tables, with client IP and time.
  • AD and GPO change auditing: Windows Security event 5136 ("A directory service object was modified") shows who changed a Group Policy object; event 5137 ("A directory service object was created") shows who created one. GPO edits also write files into the SYSVOL share, so file-create events on \\domain\SYSVOL paths are a second signal that a policy changed.
  • SharePoint and Microsoft 365 Unified Audit Log: for intranet content on SharePoint, the Unified Audit Log (UAL) records operations such as PageViewed, PageModified, and FileModified with the acting user, the site URL, and the client IP. A page or file changed by a non-editor account is a strong lead.
  • EDR: behavior-based detection of mass overwrites, raw disk writes, and tampering attempts.

Warning

Treat internal defacement as an escalation, not a prank. Public reporting shows it often travels with wiping or ransomware. If you see the defacement, assume destruction is happening right now and check backup health immediately.

Fit inside the attack chain

Internal defacement usually follows Valid Accounts (T1078) and lateral movement, because the attacker needs trusted access to content systems. It can co-occur with T1561 (Disk Wipe), T1485 (Data Destruction), or T1486 (Data Encrypted for Impact). The practical rule: when a defacement alert fires, pull the process tree, check for staged payloads on shares, and review whether credentials used for the change match known admin activity. If the account is new to that system, you are likely looking at an intrusion, not a maintenance task.

Seven-step triage flow

Triage flow for a suspected internal defacement alert
StepQuestionAction
1Is the change real?Screenshot the visible content, confirm with the content owner, and pull the audit row or file event that produced it.
2Who made the change?Map the account, client IP, and process. Compare against the approved change calendar and release accounts.
3Is it still happening?Check live EDR for active overwrites, running scripts, or raw disk writes. If yes, prepare isolation.
4How wide is the blast radius?Count affected hosts, tables, and shares. Search the SIEM for the same account and binary across the estate.
5Is destruction part of it?Look for wipe or ransomware indicators: boot record writes, shadow copy deletion, mass extension changes.
6What is preserved?Snapshot one affected machine and export the audit rows before any rebuild so forensics keeps its evidence.
7What is the decision?If destructive activity is confirmed, declare a major incident, isolate affected segments, and activate the destructive-attack playbook.

One scoping note: GDPR Article 33 asks you to notify a regulator within 72 hours when a personal data breach happens. A defacement that touches no personal data may not trigger that duty. Decide with your privacy team, and document the decision either way.

The common thread: auditors do not ask whether you blocked one attack. They ask whether changes are controlled (configuration management), recorded (logging), watched (monitoring), and recoverable (backup). A detection program for T1491.001 answers all four with the same small set of logs.

5.2 Threat intelligence

Threat intelligence answers one question for this technique: who has done this before, and what did their tooling look like? Public reporting gives enough shape to build detections even without a commercial feed.

Sources worth using

  • MITRE ATT&CK plus STIX/TAXII: the technique pages and the official ATT&CK data feeds give machine-readable mappings you can sync into your SIEM.
  • Vendor blogs: endpoint vendors publish teardown reports of wipers with indicators such as file names, registry paths, and boot-screen behavior.
  • OSINT reporting: news and research write-ups document campaigns, victim profiles, and attribution debates.
  • Commercial feeds: structured indicators and context, useful when they include campaign-to-technique mappings.
  • ISACs: sector trust groups share what members actually saw, often faster than public blogs.
  • Internal telemetry: your own past incidents. The best intel source for tuning thresholds on your file servers and databases.

Collect, analyze, apply

  1. Collect: pull ATT&CK updates, wiper reports, and ISAC notes into one intel register. Tag anything that mentions boot screens, portal tampering, or wallpaper changes.
  2. Analyze: for each report, extract behaviors (not just hashes): which log sources would have caught it, which fields matter, and how fast the impact phase ran.
  3. Apply: turn behaviors into the Sigma rules in section 5.5, adjust thresholds in section 5.4, and add missing log sources to the backlog.

5.3 Threats ranking and categorization

The seven threats below describe realistic ways T1491.001 shows up in an enterprise. They are ranked by expected damage, and they thread through sections 5.4 and 5.5 unchanged: each threat has a log pattern, and the six rules in 5.5 cover TH-01 to TH-06. TH-07 is covered by the hunt pattern in 5.4 and the cheat sheet.

TH-01 · Destructive wiper replaces boot content Critical Windows

Description
A destructive wiper writes an attacker-chosen image into the Master Boot Record, so staff see attacker-chosen screens at startup. This is internal defacement delivered by destructive malware.
Preconditions
SYSTEM-level access on endpoints plus a destructive payload deployed and executed.
Impact
Mass unbootable machines, staff fear, and a heavy rebuild effort. Documented in major campaigns such as Shamoon.
Rank justification
Catastrophic availability impact combined with psychological effect; historical campaigns show it can disable tens of thousands of machines.

TH-02 · Database or template tampering on internal dashboards High Identity / Cloud

Description
The attacker edits rows in internal databases or server-side templates so staff dashboards and intranet pages render false content.
Preconditions
Write access to the application database or template store, usually via a stolen service or admin account.
Impact
Misinformation inside the organization and eroded trust in internal systems; staff may act on fake notices.
Rank justification
High reach and trust damage without destroying data, which makes it attractive for extortion and distraction.

TH-03 · Login screen or wallpaper tampering via registry or GPO High Windows / Identity

Description
The attacker changes the per-user wallpaper value or logon UI keys, or edits a GPO that pushes a fake notice image fleet-wide.
Preconditions
Administrator rights on endpoints or permission to edit and link a GPO.
Impact
Visible harassment or fake corporate notices on every affected login and desktop.
Rank justification
Fleet-wide reach through central management, but lower data impact than database tampering.

TH-04 · Container platform default pages replaced Medium Cloud

Description
The attacker replaces default pages of internal web pods or portal assets in the cluster, for example by executing into a pod and writing new files into the document root.
Preconditions
Cluster or registry access, such as a leaked service account with exec permissions.
Impact
Confusing or misleading internal content and slower trust in platform services.
Rank justification
Scoped to platform users; recovery is quick because pods are redeployed from images.

TH-05 · Insider edits internal communications pages Medium Identity

Description
An insider misuses publishing rights to post or alter content on internal communications pages.
Preconditions
Legitimate publishing rights and an oversight gap in the approval flow.
Impact
Limited audience, but it bypasses all outer controls because the person is already trusted.
Rank justification
Low technical impact and easy rollback, yet it tests the governance controls that all other threats rely on.

TH-06 · Fake "urgent HR or IT notice" pages used for credential harvesting High Windows / Identity / Web

Description
The attacker creates a page inside the intranet that looks like an urgent HR or IT notice, then sends staff a link by email or chat. The page asks staff to sign in again and collects their credentials.
Preconditions
Write access to an internal web server or CMS, plus a channel to distribute the link, such as a compromised mailbox or chat account.
Impact
Stolen staff credentials widen the intrusion, and fake notices erode trust in real internal messages.
Rank justification
High because it directly harvests credentials, but it needs a working distribution channel before it pays off.
Known use
Public reporting describes fake internal notices used during extortion and intrusion campaigns; phishing kits reused on intranets are documented by vendors.

TH-07 · Digital signage and meeting-room display tampering Low Windows / Linux / IoT

Description
The attacker overwrites the media files or content feed behind lobby screens, digital signage, or meeting-room displays, so office screens show attacker-chosen content.
Preconditions
Network reach to the signage players and write access to their media folders or content management console.
Impact
Very visible embarrassment in offices and lobbies, but little data impact and a quick fix by redeploying media.
Rank justification
Low damage, yet worth a rule because signage devices are often weakly monitored and share networks with staff systems.
Known use
Public reporting on red-team exercises and intrusions includes lobby and building-screen tampering; device management consoles are the common entry path.

5.4 Logs and patterns

Each threat below lists the log sources that catch it, the fields that matter, what normal looks like, what suspicious looks like, and the detection logic used by the rules in 5.5.

Detection pattern for TH-01 (boot content replacement)

Log sources
Sysmon EID 1 (process creation), EID 11 (file create on device paths), EDR behavioral events, Windows System log boot failures.
Key fields
CommandLine, Image, TargetFilename, User, Computer, EventID.
Normal behavior
Disk utilities and backup agents read raw devices; Windows writes boot files only during updates or image servicing.
Suspicious behavior
Any non-servicing process writing to \Device\Harddisk paths or opening \\.\PhysicalDrive handles, especially followed by boot failures.
Detection logic
Alert when a process command line references a raw disk device, or when a file-create event targets the harddisk device namespace, excluding known disk and backup tooling.

Detection pattern for TH-02 (database and template tampering)

Log sources
Database audit logs (SQL Server audit, PostgreSQL logs), CMS application logs, web server access logs.
Key fields
AccountName, ClientIp, Statement, DatabaseName, ObjectName, timestamp.
Normal behavior
Release service accounts update content tables during published release windows; editors use the CMS interface.
Suspicious behavior
UPDATE statements on content tables from personal or never-before-seen accounts, from unusual client IPs, or outside release windows.
Detection logic
Alert on content-table UPDATE statements whose account is not on the approved release list, or whose client IP is outside the application subnet.

Detection pattern for TH-03 (wallpaper and logon UI)

Log sources
Sysmon EID 13 (registry set), Windows Security 5136 (GPO directory object change), EDR registry events.
Key fields
TargetObject, Details, Image, User, EventID, GPO display name.
Normal behavior
Intune, SCCM, or the approved wallpaper GPO writes these values from management processes on a schedule.
Suspicious behavior
Wallpaper or logon UI values written by script interpreters, admin tools, or processes with no management lineage.
Detection logic
Alert on writes to wallpaper and logon UI keys, then filter the approved management binaries; also alert on GPO edits that reference wallpaper settings.

Detection pattern for TH-04 (container default pages)

Log sources
Kubernetes audit logs, container platform logs, ingress access logs for internal portals.
Key fields
verb, objectRef.resource, objectRef.subresource, objectRef.namespace, user.username, sourceIPs.
Normal behavior
CI/CD service accounts create exec sessions during deployments from the pipeline subnet.
Suspicious behavior
Exec into web pods or asset writes from user accounts, interactive IPs, or outside pipeline windows.
Detection logic
Alert on pod exec sessions and config or asset writes where the user is not a pipeline identity and the source is not the pipeline network.

Detection pattern for TH-05 (insider publishing misuse)

Log sources
Web server access logs of the internal CMS, CMS application audit trail, SSO login logs.
Key fields
cs-method, cs-uri-stem, csUsername, c-ip, sc-status, timestamp.
Normal behavior
Editors publish through the CMS workflow during business hours from managed devices.
Suspicious behavior
Direct POST requests to publishing endpoints from accounts outside the editors group, or large publishes at unusual hours.
Detection logic
Alert on successful publishing POSTs where the account is not a known editor or the request bypasses the approval workflow.

Detection pattern for TH-06 (fake notice pages and credential entry)

Log sources
Intranet web server logs (IIS or nginx), SharePoint and Microsoft 365 Unified Audit Log (UAL), SSO login logs, and mail or chat gateway logs for the link distribution.
Key fields
cs-method, cs-uri-stem, csUsername, c-ip, sc-status; in the UAL: Operation (PageViewed, PageModified, FileModified), UserId, ObjectId, ClientIP.
Normal behavior
Real credential entry happens on the known SSO endpoints, and editors create pages through the CMS workflow.
Suspicious behavior
Successful form posts to a page path that looks like an urgent notice, is not a known authentication path, and was created shortly before; a new page or file in an HR folder written by a non-editor.
Detection logic
Alert on credential-entry POSTs to notice-like paths outside the SSO allowlist, and join with UAL PageModified or FileModified events for the same page in the previous day.

Detection pattern for TH-07 (digital signage and displays)

Log sources
Sysmon EID 11 file-create events on signage players, EDR on the players, device management or kiosk software logs, and network logs for the signage VLAN.
Key fields
TargetFilename, Image, Computer, User, EventID; device logs: device ID, package or playlist ID, push timestamp.
Normal behavior
Media updates arrive from the approved signage CMS push account on a schedule, from the management subnet.
Suspicious behavior
Media files (images, videos) written by script interpreters or unknown processes, or pushes from outside the signage CMS window.
Detection logic
Alert on writes into signage media folders by processes outside the push pipeline, and correlate with helpdesk tickets that mention odd screen content.

Worked log examples

The examples below show what the real events look like, one per threat. Names, hosts, and IPs are fictional; external addresses use the reserved documentation ranges (203.0.113.x and 198.51.100.x) so nothing here points at a real system.

  • EventID 1: a new process started; this is the highest-value Sysmon event for spotting content tampering tooling.
  • Image and ParentImage: cmd.exe spawned by a hidden PowerShell, which itself is unusual. An Office or scripting lineage deserves a look.
  • CommandLine: the command copies an HTML file into the portal web root share. This is the write that changes what staff see.
  • User: a regular employee account writing into a server web root is the core anomaly, not the tooling.
  • Hashes: capture the SHA256 for threat-intel matching and for hunting the same file elsewhere.
  • EventType SetValue: a value was written, not just read; reads are not logged as EID 13.
  • TargetObject: the per-user desktop wallpaper value. Legitimate writers are management agents, not temp-folder executables.
  • Details: the new wallpaper points to a user temp path, a classic fake-notice setup.
  • Image: an unknown executable in C:\Windows\Temp is the writer. This combination is the alert.
  • action=UPDATE with table=news: a content table behind the staff dashboard changed.
  • account=CORP\svc_dash_writer: the service account is plausible, but app="PowerShell" is not. The dashboard app connects through its own driver, so a PowerShell client means someone reused the account interactively.
  • client=198.51.100.24: the client IP is a workstation subnet, not the application server subnet. Pair the account with the client to spot credential reuse.
  • rows=12: a bulk headline change matches the "tamper" step of the simulation and explains what staff saw.
  • verb=create with subresource=exec: an interactive exec session opened into a web pod.
  • user.username=dev67: a personal account, not a pipeline identity, which is the core anomaly for the TH-04 rule.
  • sourceIPs: the client address uses a documentation range here; in your cluster, compare it with the pipeline subnet allowlist.
  • POST /admin/pages/save.aspx: a direct publish against the CMS save endpoint, the action the TH-05 rule watches.
  • The dash in the username position means no authenticated CMS account was presented, so the request rode an existing session.
  • 21:38 local time is outside the publishing window, and the client address is not an office or editor subnet. Time plus identity is what makes this row stand out.
  • Operation=PageModified: a SharePoint page changed; sibling operations include PageViewed and FileModified.
  • UserId=s.valdez@corp.example.org: check whether this account belongs to the HR site editors; if not, the page creation itself is the lead.
  • ObjectId: the path contains the notice-style name the TH-06 rule matches, so pair this event with the form-post alert that follows it.
  • TargetFilename: the media loop file of the lobby player was replaced, which is what staff would see on screen.
  • Image: a script interpreter wrote the file. The approved push runs from the signage agent, so this writer is the alert.
  • User: the push service account appears, but the process does not match it. Account plus process mismatches point at credential reuse.

5.5 Sigma rules and Splunk SPL

Six complete Sigma rules and six matching Splunk SPL queries sit below. TH-01 to TH-05 keep one rule each, and v2.0 adds the TH-06 rule; TH-07 is covered by the hunt pattern in 5.4. Sigma is an open rule format for log detections; the YAML below is valid and ready to paste into a converter such as sigma-cli. The SPL runs in Splunk after you adjust index and sourcetype names to your environment. Every rule references this technique, uses spaces for indentation, and carries the v2.0 review date.

Rule for TH-01 · Boot content replacement (Critical)

Field assumptions: Sysmon XML events land in index=sysmon with CommandLine, TargetFilename, and Computer auto-extracted; adjust the index, sourcetype, and the host and count thresholds to your estate.

  • Mapping note: the Sigma contains modifier becomes the SPL wildcard "*...*"; the startswith on TargetFilename becomes a left-anchored wildcard; EventID: 9 maps to a bare EventID=9 term.
  • False positives: backup agents, defragmentation tools, and disk encryption clients opening raw devices.
  • Tuning: build an allowlist of signed disk and backup tool paths and filter them; keep the rule at critical until raw-device noise is baselined, then re-evaluate.
  • Severity: critical, matching TH-01.

Rule for TH-02 · Database and template tampering (High)

Field assumptions: SQL Server audit records are shipped to index=db_audit with AccountName, ClientIp, Statement, DatabaseName, and ObjectName extracted; rename the release accounts to match your change process.

  • Mapping note: the Sigma contains|all list becomes two wildcards in one SPL filter; the Sigma filter_release list becomes the SPL NOT AccountName IN (...) clause.
  • False positives: emergency comms fixes and manual data corrections during incidents.
  • Tuning: maintain the release account list as a lookup table and add a change-window join if your CMS publishes under rotating accounts.
  • Severity: high, matching TH-02.

Rule for TH-03 · Wallpaper and logon UI tampering (High)

Field assumptions: Sysmon EID 13 events are in index=sysmon with TargetObject, Details, and Image extracted; replace the management process list with your own wallpaper management agents.

  • Mapping note: Sigma endswith becomes a right-anchored SPL wildcard; Sigma contains becomes "*...*"; the not filter_management clause becomes NOT Image IN (...).
  • False positives: scheduled corporate wallpaper pushes and IT personalization tools.
  • Tuning: keep the management allowlist current, and add a second rule on Security 5136 for GPO edits whose filtered attributes mention wallpaper.
  • Severity: high, matching TH-03.

Rule for TH-04 · Container default page replacement (Medium)

Field assumptions: Kubernetes audit records are in index=k8s with verb, objectRef.*, and user.username extracted from the JSON body; this is a clearly labeled placeholder index, so rename it to your platform index.

  • Mapping note: Sigma dotted keys map to the same dotted SPL fields because the JSON is flat-searchable; the two Sigma startswith filters collapse into two SPL NOT user.username=... terms.
  • False positives: platform engineers debugging web pods and scheduled chaos or test jobs.
  • Tuning: restrict objectRef.namespace to the namespaces that serve internal content, and allowlist the pipeline identity prefix used by your CI system.
  • Severity: medium, matching TH-04.

Rule for TH-05 · Insider publishing misuse (Medium)

Field assumptions: access logs are in index=web as combined format with method, uri_path, user, clientip, and status extracted; adjust the CMS path prefix admin/pages to your platform.

  • Mapping note: Sigma cs-method maps to the Splunk Common Information Model field method, cs-uri-stem to uri_path, csUsername to user, and sc-status to status; the startswith filters become the two NOT user=... terms.
  • False positives: approved campaign publishing and scheduled content jobs.
  • Tuning: sync the editor prefix with HR-driven role changes, and alert harder on publishes outside business hours.
  • Severity: medium, matching TH-05.

Rule for TH-06 · Fake notice pages and credential entry (High, new in v2.0)

Field assumptions: intranet access logs are in index=web as combined format. Expect method, uri_path, user, clientip, and status extracted, the same mapping as the TH-05 rule. Tune the notice-path keywords and the SSO allowlist to your portal.

  • Mapping note: the Sigma contains lists become four SPL wildcard terms; the filter_sso exclusions become the NOT clause; csUsername maps to user and c-ip to clientip.
  • False positives: genuine HR campaigns and IT self-service pages under these paths.
  • Tuning: join with the SharePoint UAL PageModified or FileModified event that created the page, and with mail or chat logs that spread the link; require both signals before paging.
  • Severity: high, matching TH-06.

Real-World Case Study

Shamoon at Saudi Aramco in August 2012: the most widely documented internal defacement event, where tens of thousands of machines displayed the same attacker image at boot.

Context

Saudi Aramco runs one of the largest oil production operations in the world. In August 2012, according to public reporting, the Shamoon wiper (also called Disttrack, ATT&CK software S0140) spread through the corporate network. It overwrote files and replaced the Master Boot Record with a burning-flag image, so affected machines displayed that image at startup. This is internal defacement in its most destructive form: the "content" shown to staff was delivered by the boot process itself.

MITRE's software entry S0140 links Shamoon to the Iranian group "Cutting Sword of Justice", and several vendors have made similar public assessments. Attribution is not the lesson of this case, so the rest of this page does not depend on it. Facts below come from public reporting, such as news coverage and vendor reports. Details that were never published are marked illustrative.

What happened, as far as public reporting agrees

  1. Before Aug 2012Access. Attackers obtained privileged credentials. Public reporting points to an infected file or credential theft as the start; exact details were never fully published.
  2. Aug 2012Lateral spread. The wiper moved through the corporate network using stolen credentials and network shares, reaching machines across the enterprise.
  3. Aug 15, 2012Impact phase. On each machine, the payload overwrote user and system files and replaced the MBR with the flag image.
  4. Same dayVisible defacement. Staff who tried to boot their machines saw the burning flag screen instead of the operating system.
  5. Days afterScale confirmed. Aramco's public statement put the damage at roughly 30,000 of about 45,000 corporate workstations.
  6. ImmediatelyContainment. The company cut remote access and isolated parts of the network to stop the spread.
  7. Same periodOperations protected. The operational technology (OT) network that runs production was separate, so oil production continued while office machines were down.
  8. Weeks afterRecovery. Teams rebuilt machines from pre-staged golden images in a large phased effort, and credentials were rotated.
  9. LaterAttribution. Public reporting linked the campaign to Iran-linked actors; the case remains a standard study for destructive impact planning.

Detection point

The event that surfaced was human, not automated: mass helpdesk reports of machines showing the flag image and failing to boot. A fast automated alert would have needed the signals described in section 5: raw disk writes (TH-01), mass file overwrites on shares, and logon bursts from the stolen accounts. According to public reporting, the destruction unfolded over hours, so a mass-file-change analytic could have bought meaningful time even in 2012.

Containment, eradication, recovery

Containment focused on stopping the spread: remote access was cut and network segments were isolated. Eradication meant assuming every machine in the blast radius was compromised, since the payload spread with valid credentials. Recovery leaned on preparation: pre-staged golden images let teams rebuild thousands of machines in a repeatable way, and credentials were rotated so the stolen accounts lost their value.

Impact

Roughly 30,000 workstations were hit, office work stopped for days, and the rebuild took weeks. The critical outcome: no production outage, because the OT network was segmented from the corporate network. The attack damaged office work, not production control.

Tools and attacker behaviors (public record)

  • Shamoon / Disttrack (S0140): the wiper payload itself, documented in vendor teardowns and MITRE ATT&CK's software entry.
  • RawDisk driver and Filerase component: named in MITRE's S0140 entry as components used for raw disk access and wiping.
  • Stolen privileged credentials and network shares: public reporting describes the payload spreading through shares with valid accounts.
  • Overwrite payload: vendor teardowns report that files were overwritten with fragments of a JPEG image before the boot record was replaced. The exact file list per machine is illustrative; the overwrite behavior is public record.
  • Boot-record image: the burning-flag image written to the Master Boot Record, reported widely at the time.

Response team roles and communication

Public accounts describe an organization that kept the business running while managing a large IT response. Aramco did not publish its exact response structure, so the roles below are the standard set for this scenario and are illustrative. Communication matters in defacement events: staff saw frightening content, and the company had to explain what was true.

  • Incident commander: ran the response, set priorities, and made isolation decisions. (Illustrative role.)
  • Network security team: cut remote access and isolated network segments to stop the spread. (Public reporting covers the isolation.)
  • Desktop and endpoint teams: rebuilt thousands of machines from pre-staged images in a phased effort. (Public reporting covers the rebuild.)
  • Identity team: rotated credentials so the stolen accounts lost their value. (Illustrative detail; credential theft was publicly reported.)
  • Communications and HR: told staff what was real, because the flag image itself spread fear. (Illustrative role; the fear effect is public record.)
  • Executive liaison: kept leadership and the business units informed while systems were rebuilt. (Illustrative role.)

A prepared message flow to employees is part of the destructive-attack playbook, not an afterthought.

Lessons learned

  • Segmentation saves operations. The OT network survived because it was separate. Put content systems and admin planes on their own segments too.
  • Credential hygiene limits blast radius. The wiper moved with stolen privileged accounts; least privilege and tiered admin shrink what one theft can do.
  • Golden images and offline backups are the recovery engine. Rebuild speed came from preparation, not from the incident response itself.
  • Mass-file-change alerting buys time. A fleet-wide overwrite is loud in file and audit logs. Alert on volume, not just on known names.

Mitigation and Defense

Controls that make internal defacement hard to reach, hard to miss, and quick to undo, grouped from policy to response.

Policy

Put content publishing and GPO edits under change control. Every wallpaper push, portal release, and login banner change should trace to a ticket. Make an owner for each internal content system.

Identity

Privileged Account Management and User Account Management: least privilege, MFA on admin paths, and tiered administration so workstation credentials cannot reach content databases. Rotate service account secrets.

Endpoint

Run EDR with tamper protection on. Use application control so script interpreters cannot run from user-writable paths. Restrict File and Directory Permissions on web roots and shares.

Network

Network Segmentation: keep content servers in their own zone and restrict SMB and admin shares to the systems that need them. This is the control that protected production in 2012.

Cloud and containers

Keep a registry of approved internal apps. Harden cluster RBAC so exec into web pods is a pipeline-only capability. Pin deployments to trusted images.

Logging

Deploy Sysmon with file, registry, and process coverage; turn on database audit for content tables; centralize both into the SIEM so thresholds can be computed.

Monitoring

File-integrity monitoring on portal roots, alerting on GPO changes that touch wallpapers, and the mass-file-change analytics from section 5. Watch the content layer like production.

Backup

Data Backup done properly: golden images kept current, plus offline or immutable copies of content databases. Test restores on a schedule, not after an incident.

Response

A destructive-attack playbook: isolate, preserve evidence, rebuild from images, rotate credentials, and tell staff what is true. Practice it with a tabletop once or twice a year.

Home and small office

Small teams cannot run a SIEM, but the ideas shrink well. Keep one admin account per person and use a standard account for daily work. Turn on automatic updates and built-in security tools. Keep an offline copy of important files and a recovery USB made from a clean installer. If a screen suddenly shows a message you did not put there, disconnect the machine from the network first and ask for help second.

Incident response checklist

  1. Confirm the visible change with the content owner and capture a screenshot with timestamps.
  2. Identify the writing account, client IP, and process from audit logs; compare to the change calendar.
  3. Check for active destruction: raw disk writes, mass overwrites, shadow copy deletion, encryption behavior.
  4. If destruction is active, isolate affected segments at the switch and cut remote access.
  5. Preserve evidence: image one affected machine and export the database audit rows before rebuilding.
  6. Rebuild from golden images and restore content from a known-good backup.
  7. Rotate exposed credentials, including service accounts that touched content systems.
  8. Send staff a clear message about what was real, and brief leadership on impact and recovery status.
