T1499.003 — Application Exhaustion Flood

Some web requests are cheap. Others force the server to work very hard. In this attack, an attacker sends a small number of requests that are deliberately expensive to process. Each request can cost the server as much as thousands of normal ones. This guide explains the technique in simple words, shows a safe lab simulation, and gives defenders ready-to-use detection ideas.

1

Overview

What "application exhaustion flood" means, and why one request can hurt more than a thousand.

A denial of service (DoS) attack tries to make a service unavailable to real users. MITRE ATT&CK tracks this as sub-technique T1499.003 — Application Exhaustion Flood. The official description is short. Attackers target resource intensive features of applications. They send repeated requests to those features. The requests exhaust system resources and deny access to the application, or to the server itself. Source: attack.mitre.org/techniques/T1499/003/ (technique revision 1.3, last modified 24 October 2025).

Think of a library desk. A normal visitor asks a short question and the librarian answers fast. An attacker asks questions that force the librarian to search every shelf in the building for each answer. Only a few such questions fill the whole day. The attack does not break the door (the network). It clogs the work itself.

Ways to make one request expensive

Crafted search and API parameters

A search box that allows many wildcards can force a full table scan. A full table scan means the database reads every row instead of using an index (a sorted lookup structure). A query like q=%25%25%25 with LIKE patterns can turn a fast lookup into minutes of disk work.

ReDoS — evil regular expressions

A regular expression (regex) is a text pattern matcher. Some patterns, when they fail to match, re-try the same text in many orders. This is called catastrophic backtracking. CPU time can explode from milliseconds to hours. This abuse is called ReDoS: Regular expression Denial of Service.

XML entity expansion — "billion laughs"

XML is a data format with tags. It allows entities, which are named shortcuts. An attacker defines entity A as ten copies of entity B, B as ten copies of C, and so on. A tiny file of a few kilobytes then expands to billions of characters in memory while the parser works through it.

Hash-collision POST floods (hashDoS)

Web frameworks store POST form fields in hash tables (fast key-value stores). In 2011, Alexander Klink and Julian Wälde showed that an attacker can craft thousands of fields whose keys collide, that is, land in the same bucket. The table then behaves like a slow list, and parsing one small POST request takes hours. ASP.NET needed an emergency fix, tracked as CVE-2011-3414 (a CVE is the public identifier scheme for published vulnerabilities). Vendors responded with parameter limits such as PHP's max_input_vars, which caps how many form fields one request may carry.

Login floods that force password hashing

Good password storage uses slow hashing such as bcrypt or Argon2. Slow by design is good for security, but it also means each login attempt costs real CPU. A flood of fake logins makes the server burn CPU on passwords that will never match.

Oversized or complex API and GraphQL queries

GraphQL is an API style where the client shapes the query. Without limits, one query can ask for thousands of linked records in one call. Deep nesting and huge page sizes make the backend do enormous work per request. The same idea applies to REST APIs (standard HTTP-style application programming interfaces) that allow huge page sizes or deep filters.

Compression bombs in uploads

A compression bomb is a small compressed file that expands to a huge size. If the application unzips uploads before checking the final size, a 10 MB upload can grow to gigabytes of memory and CPU during decompression.

Why defenders should care

MITRE's official detection strategy for this sub-technique is DET0415 ("Application Exhaustion Flood Detection Across Platforms"). Its analytics point to repeated calls of high-resource endpoints or GUI components (a GUI is a graphical user interface) that cause CPU and memory spikes. The logs show elevated request volumes and high 5xx error rates (HTTP status codes 500–599, which mean server errors). Cloud logs may show autoscaling alarms. In plain words: watch what each client makes your backend do, not only how many requests it sends.

Note The MITRE page lists platforms IaaS, Linux, Windows, and macOS, and the impact type is Availability. Its only listed mitigation is M1037 Filter Network Traffic. It means filtering upstream with Content Delivery Networks (CDNs — global caching services) or DoS-filtering providers. The filter blocks attack sources, ports, and protocols at the boundary. This guide adds the application-level controls that real teams also need.

Danger — lab only Every technique on this page is shown for education and defence only. Run test traffic only against isolated lab machines that you own. Sending such traffic to systems you do not own is a crime in most countries and can cause real harm.

Step 1 of 8 — Normal day: cheap requests, healthy database.

Defender hint: baseline first. Know what normal CPU and normal latency look like.

Written version of the animation (text alternative)

  1. Normal traffic. A legitimate user sends small search requests. Tokens move from the user through the application to the database and back. The database CPU gauge is green, around 20 percent. The SOC panel is quiet.
  2. The crafted request. The attacker sends one search with wildcards everywhere (q=%%%a%%%). A tooltip on the attacker node shows the payload. The application accepts it because it looks like a normal search.
  3. The expensive query walks in. The query token moves to the database. The CPU gauge climbs. One application worker now blocks and waits for the database instead of serving other users.
  4. Replay from several accounts. The attacker sends a burst of copies from a few different accounts. More workers block. A queue of waiting requests grows in front of the workers.
  5. Everything pegs red. The database CPU gauge reaches 100 percent. The queue keeps growing. The legitimate user's request times out and the application returns HTTP 504 Gateway Timeout.
  6. The SOC panel lights up. APM (Application Performance Monitoring) shows a slow-query spike. The access log shows a wave of 5xx errors and one client with very high upstream_response_time (the time the upstream application server needed to answer).
  7. Mitigation kicks in. The team enables a query timeout, parameter rules, and WAF (Web Application Firewall) rate limiting. Attack tokens are dropped at the WAF and never reach the database.
  8. Recovery. The database cools down. The legitimate user's request is served and marked with a green check. The SOC panel records the recovered state.

3

Red team / attacker perspective

Understanding how attackers think about request cost helps you find the same weak spots first. All examples here are lab only.

Why an attacker picks this technique

  • Low traffic, big effect. A flood of cheap requests is loud and easy to block. A few expensive requests look almost normal and can hurt more.
  • Hard to tell apart from real users. The requests use valid features. Basic rate limits may never trigger.
  • No special hardware needed. A small virtual machine or even a laptop can generate the traffic.
  • Also useful as cover. Noise and outages can distract defenders during a bigger operation.

Prerequisites the attacker needs

  • A public endpoint that does heavy server-side work: search, reports, exports, file conversion, login, GraphQL.
  • Parameters the attacker can control: query text, page size, filters, uploaded files.
  • No per-client limit on cost, only maybe a limit on request count.
  • Basic knowledge of the app: endpoint paths, parameter names, error behaviour.

The conceptual attack flow

  • Step 1 — Recon

    Browse the target application like a normal user. Note every endpoint that feels slow on large inputs: search, sorting, reports, exports, password login.

  • Step 2 — Measure

    Time one request with harmless but heavy parameters. If one request takes seconds while normal ones take milliseconds, the attacker has found an amplifier.

  • Step 3 — Parameterize

    Turn the heavy call into a template: change the query text, the page size, or the account name for each request so caching does not help.

  • Step 4 — Replay at volume

    Send the template in a loop, often from several accounts or addresses. Keep the rate low enough to look plausible.

  • Step 5 — Impact

    Workers block on slow queries, queues grow, timeouts (5xx) spread to real users, and the application becomes unavailable or unusably slow.

Danger — lab only The commands below must run only against an isolated lab host that you own, such as 10.0.0.10 or lab.local on a private network. Never point these tools at systems you do not own. Tools named here (wrk, ab, hey) are standard load-testing tools that developers use every day on their own services.

Common variations

  • Slow variants: many small expensive calls instead of a burst, spread over hours.
  • Distributed variants: the same template replayed from many addresses or accounts.
  • Protocol variants: the same idea over email (huge parsing work), DNS, or file upload pipelines.
  • Mixed variants: combined with T1499.002 floods so defenders chase two symptoms at once.

Common attacker mistakes

  • Replaying with the identical parameters, so the cache answers and the effect fades.
  • Forgetting timing spread; one source IP at constant rate is easy to block.
  • Sending payloads that crash the parser, which turns a stealthy attack into an obvious error storm.
  • Testing on production-like endpoints of a system they do not own, which is illegal.

Blue team / SOC perspective

What this attack looks like in your telemetry, and the first ten minutes of a good response.

Artifacts this attack leaves behind

  • 5xx waves: bursts of HTTP 500, 502, 503, and 504 answers, often tied to one feature.
  • Slow-query logs: database entries with query times of many seconds and huge rows-scanned counts.
  • High upstream_response_time: in nginx-style access logs, the upstream field shows how long the application needed. One client stands out.
  • APM traces: spans stuck in database calls; queue depth rising; connection pool exhaustion.
  • Host symptoms: CPU pegged on the DB or app tier, worker pools full, OOM (out of memory) events.
  • WAF logs: blocks, rate-limit hits, or parser alarms tied to odd parameter values.

Where to look first

  • Reverse proxy and load balancer access logs (nginx, IIS — Microsoft's Internet Information Services, cloud load balancers).
  • Database slow-query log and performance schema (MySQL, PostgreSQL).
  • APM tools: distributed traces, service maps, error rates per endpoint.
  • Application logs: timeouts, pool exhaustion, regex or XML parser errors.
  • Cloud metrics: autoscaling triggers, 5xx rates, latency percentiles.
  • WAF and CDN logs: per-client request and block counts.

Official ATT&CK detection strategy ATT&CK maps this sub-technique to detection strategy DET0415 — "Application Exhaustion Flood Detection Across Platforms". Its four analytics (AN1165–AN1168) describe exactly the telemetry above. AN1165: repeated calls of high-resource application endpoints or GUI components (GUI means graphical user interface). They cause CPU and memory spikes. Logs show elevated request volumes, prolonged handle locks, or frequent crash recoveries. AN1166: automated scripts or repeated CLI/API requests that make application backends consume high CPU or memory (for example Apache/PHP, MySQL, mail servers), producing syslog errors and excessive process spawning. AN1167: repetitive GUI or backend workflows logged in unified logs as spin reports or crash dumps. AN1168: automated abuse of cloud-hosted applications (web apps, REST endpoints, internal APIs). It causes compute exhaustion, high 5xx error rates, or frequent autoscaling triggers in app insights or CloudWatch logs. Every rule in section 5.5 implements one of these analytics.

Warning A single slow query happens in every system. What matters is the pattern: the same endpoint, the same parameter shape, the same small set of clients, again and again, together with rising errors. Judge the pattern, not the single event.

Why it matters and where it fits in the attack chain

T1499.003 sits in the Impact tactic, so it is usually a goal, not a first step. It still appears in real chains. It can apply extortion pressure ("pay or we keep you offline"). It can distract defenders while another intrusion runs. It can sabotage a rival, or test how defenders react before a more serious attack. Availability is also a security duty: many laws and standards (see section 5.1) treat an outage as a reportable security failure.

First-response triage flow

  • Minute 0 — Detect

    Alert fires: 5xx rate above threshold, or slow-query count above baseline, or a client with extreme upstream_response_time.

  • Minute 1 — Confirm scope

    Which endpoint? Which parameters? One client or many? Is a legitimate campaign (sale, exam, launch) running at the same time?

  • Minute 3 — Capture evidence

    Save sample requests from access logs, slow-query entries, and WAF samples. Note client IPs, user agents, and accounts. Timestamps in UTC (coordinated universal time).

  • Minute 5 — Contain

    Apply per-client rate limits at the WAF or CDN; block abusive clients; enable or tighten the query timeout. Keep changes documented.

  • Minute 10 — Communicate

    Open an incident ticket, tell the on-call engineering owner and the service owner. If customer impact is likely, involve communications per your policy.

5.2 Threat intelligence

Threat intelligence is knowledge about who attacks, how, and why. For T1499.003, intelligence answers a practical question: who is likely to attack my expensive endpoints, and what will it look like?

Sources worth following

  • MITRE ATT&CK: the parent T1499 page and its sub-techniques; group and software pages that reference them.
  • Government alerts: CISA and FBI joint advisories on DDoS and extortion campaigns.
  • Vendor reports: annual DDoS landscape reports from network and CDN providers; WAF telemetry summaries.
  • OSINT: open-source intelligence such as conference talks, research blogs, and CVE databases. The 2011 hashDoS research (Klink and Wälde, 28C3) is a good example: public, detailed, and it changed how every web framework parses POST data.
  • ISACs: sector sharing groups such as MS-ISAC (state and local government), FS-ISAC (finance), and H-ISAC (health).
  • Commercial feeds: paid indicator lists; useful for client IP reputation, weaker for technique detail.
  • Internal telemetry: your own logs and WAF data. The best source for "what does this look like on our stack".

A simple four-step workflow

  1. Collect. Pull reports from two or three sources on a fixed schedule. Note claims with dates and links.
  2. Analyze. Ask: does this apply to our stack? Which of our endpoints match the described pattern? How credible is the source?
  3. Apply. Turn findings into detections and tests: new Sigma rules, WAF rules, a load test in the lab, a story in the backlog.
  4. Review. After a quarter, check which intelligence actually changed a control. Drop sources that never do.

1 · Expensive search / parameter flood Critical Network Cloud

Description. An attacker finds a search or filter endpoint that accepts wildcards or huge ranges, then replays crafted values so every request forces a full table scan.

Preconditions. Public search/filter API; no query cost budget; no per-client latency limit.

Impact. Database CPU saturates; all queries slow down; 5xx timeouts spread to every feature.

Why this rating. A handful of requests can take down the whole backend, and the traffic looks like normal search usage, so it is rated Critical.

2 · ReDoS High Network

Description. Attacker input reaches a vulnerable regex (for example nested quantifiers like (a+)+), and one request pins a worker for minutes or hours through backtracking.

Preconditions. A vulnerable pattern on a request path; no regex execution time limit; often an untested user-supplied field.

Impact. Worker threads vanish into the pattern; the service stalls with normal request volume.

Why this rating. Devastating per request, but it needs a specific vulnerable pattern, so slightly less universal than threat 1 — rated High.

3 · Hash-collision POST flood High Network Linux Windows

Description. Thousands of crafted form fields with colliding keys force the framework's hash table into linear work, as demonstrated publicly in 2011 against many languages and platforms.

Preconditions. Framework without a max-POST-parameter limit (rare today, but old or custom stacks still exist); POST endpoints reachable without authentication.

Impact. CPU pegged during request parsing; one small POST costs hours of processing.

Why this rating. Modern frameworks mostly fixed it after CVE-2011-3414, but legacy systems remain exposed, so it stays High.

4 · XML entity expansion Medium Network

Description. A small XML upload uses nested entity definitions ("billion laughs") to expand into billions of characters while the parser processes it.

Preconditions. An XML parser with entity support enabled; an upload or API path that accepts attacker XML.

Impact. Memory and CPU spike; parser threads hang; possible process crash.

Why this rating. Many modern parsers disable entities by default, and the blast radius is usually one process — rated Medium.

5 · Login flood with password hashing Medium Identity Network

Description. A stream of fake login attempts forces the server to run slow password hashing (bcrypt, Argon2) for every attempt, which is expensive by design.

Preconditions. Login endpoint without per-client or per-account throttling; hashing cost factor tuned high without a capacity check.

Impact. CPU saturates on useless hashes; real logins slow down; lockout storms annoy users.

Why this rating. The cost per request is bounded and captchas or throttling are common, so it is rated Medium.

6 · Complex API / GraphQL query flood Medium Cloud Network

Description. Deeply nested or oversized queries (huge page sizes, deep relation chains) make each API call do enormous backend work.

Preconditions. API without depth limits, pagination caps, or a query cost budget; introspection open to anonymous users.

Impact. Backend fan-out multiplies; database and downstream services saturate; cloud bills spike with autoscaling.

Why this rating. Cost is high but spread across many small services, and standard limits are widely available — rated Medium.

7 · Compression-bomb uploads Medium Network Cloud

Description. A tiny compressed archive is uploaded, then expands to gigabytes while the application decompresses it, filling memory, CPU, and disk.

Preconditions. An upload path that decompresses archives before checking the expanded size; no expansion-ratio or size cap.

Impact. Disk or memory fills within seconds; the process crashes or stalls; the host may hit cloud storage limits.

Why this rating. Devastating when it works, but modern upload guards and archive-size checks are common — rated Medium.

5.4 Logs and patterns for each threat

For every threat from 5.3: where the evidence lives, which fields matter, what normal looks like, what suspicious looks like, and the detection logic in words. The patterns implement the official analytics AN1165–AN1168 from section 4. Example lines use RFC 1918 lab addresses (the private ranges such as 10.0.0.x) and documentation addresses (203.0.113.x, 198.51.100.x) only.

Threat 1 · Expensive search / parameter flood

Log sources. Reverse proxy access log (nginx), database slow-query log (MySQL, PostgreSQL), APM traces.

Key fields. client_ip, request_uri (with the crafted q parameter), status, upstream_response_time (seconds the app spent on the request), database Query_time, Rows_examined (rows the database read to answer).

Normal behavior. Search requests return 200 in well under one second; Rows_examined stays in the hundreds or thousands; response times per client look alike.

Suspicious behavior. One client repeatedly sends wildcard-heavy queries; the same endpoint shows multi-second times; Rows_examined jumps to millions while Rows_sent stays tiny.

Detection logic.

  • Group access-log events by client_ip over 5 minutes.
  • Flag clients with 20 or more responses of 500/504 and upstream_response_time of 5 seconds or more.
  • Independently flag slow-query-log entries with Query_time over 10 seconds and Rows_examined over 1,000,000.
  • Correlate: if the same time window shows both, raise severity to Critical.

Field notes. 203.0.113.77 is the client address. The bracketed stamp is the local request time. 504 is the HTTP status returned to the client (gateway timeout). rt is $request_time: total seconds nginx spent on the request. urt is $upstream_response_time: how long the application behind nginx took — here 15 seconds, which is the real story.

Field notes. Query_time is seconds the statement ran. Rows_sent is what the client received; Rows_examined is what the engine had to read. Reading 24 million rows to send 12 is the definition of an amplifying query.

Field notes. The prefix shows time, process id (88041), and user@database. duration: is milliseconds. With log_min_duration_statement = 10000, every statement slower than 10 seconds lands here.

Threat 2 · ReDoS

Log sources. PHP-FPM (the PHP FastCGI Process Manager that spawns PHP workers) / application server logs, nginx access log, APM spans, syslog.

Key fields. message (worker pool warnings), pool (worker pool name), status 499/504, upstream_response_time, APM span duration on the regex-using function.

Normal behavior. Worker pools occasionally hit limits during deploys or traffic peaks and recover; few 499s (clients giving up).

Suspicious behavior. Repeated max_children warnings without a traffic peak; requests to one endpoint stuck near the timeout limit; one client with many 499/504 pairs.

Detection logic.

  • Alert on 3 or more "server reached max_children" events per host in 15 minutes.
  • Join with access logs: were those minutes full of requests to a single endpoint from a small client set?
  • Flag any single request whose upstream_response_time sits within 2 percent of the proxy timeout — a fingerprint of a worker stuck in a regex loop.
  • Check deploys: if warnings coincide with a release, treat as a code bug, not an attack.

Field notes. Status 499 is nginx's own code: the client closed the connection before the answer arrived. rt=60.003 means the worker spent a full timeout window — often a regex in trouble. max_children (5) means all 5 PHP worker processes were busy; a small lab pool is realistic.

Threat 3 · Hash-collision POST flood

Log sources. IIS W3C logs, web framework logs (ASP.NET, PHP, Java), Windows event log, nginx access logs.

Key fields. IIS time-taken (seconds the request occupied the server), c-ip (client), cs-method POST, sc-status, request body size, framework CPU counters.

Normal behavior. POST requests to forms finish in well under a second even at busy hours; time-taken rarely exceeds 1–2 seconds.

Suspicious behavior. POSTs with absurdly many parameters (thousands of fields) to one endpoint; time-taken in the hundreds of seconds; CPU pegged on the web tier with low request volume.

Detection logic.

  • Select POST requests with time-taken of 5 seconds or more.
  • Count per client over 5 minutes; alert when one client exceeds 30 such requests.
  • Flag requests whose parameter count (from framework or WAF logs) exceeds a sane limit such as 100 fields.
  • Correlate with CPU: web-tier CPU above 90 percent while requests per second are low means parsing cost, not load.

Field notes. The #Fields: line names every column — always read it first. Here each POST occupied the server for 1452 and 1501 seconds (time-taken). Status 200 looks innocent; the time column tells the truth. This is the classic hashDoS signature on IIS/ASP.NET.

Threat 4 · XML entity expansion (billion laughs)

Log sources. Application exception logs (Java, .NET), WAF/ModSecurity audit logs, system OOM (out-of-memory) events.

Key fields. Exception class and message, request_id, client_ip, WAF rule_id, content length of the uploaded body.

Normal behavior. Well-formed small XML documents parse in milliseconds; occasional validation errors from genuine integration mistakes.

Suspicious behavior. Entity-expansion limit errors; tiny request bodies followed by parser hangs; the same client uploading XML repeatedly right before memory alarms.

Detection logic.

  • Alert when parser exceptions mention entity limits or "DOCTYPE disallowed" more than 3 times per hour.
  • Flag XML uploads larger than a few KB whose processing exceeds 5 seconds.
  • Correlate WAF rule hits for DOCTYPE/entity payloads with client reputation; one client repeating is an attack probe.

Field notes. The JDK caps entity expansions at 64,000 by default and logs this exact sentence when the cap stops a document. body_bytes=1187 versus a parser event is the billion-laugh fingerprint: a kilobyte of XML causing megaseconds of work.

Threat 5 · Login flood with expensive password hashing

Log sources. nginx access log (login route), identity provider logs, database CPU metrics, WAF.

Key fields. client_ip, request_uri (/login), http_method POST, status (401 vs 200), upstream_response_time, account names tried.

Normal behavior. Login latency reflects hashing cost (for example 0.2–0.5 seconds); failures are a small share of attempts; clients are many and varied.

Suspicious behavior. One client making 30+ POSTs per minute to /login; elevated average latency during the burst; most attempts return 401 (authentication failure).

Detection logic.

  • Count POSTs to the login route per client over 1 minute; alert above 30.
  • Require corroboration: average upstream_response_time for that client above 1 second (proof of hashing cost, not just scanning).
  • Watch lockout counters: many distinct accounts from one client means credential stuffing plus CPU pressure.
  • Compare with CAPTCHA (a bot-check challenge) or MFA (multi-factor authentication) events to separate bots from humans.

Field notes. Two failed logins one second apart, each costing roughly 0.9 seconds of application time — that is bcrypt doing its job against a flood. Multiply by hundreds of requests and the CPU bill becomes visible.

Threat 6 · Complex API / GraphQL query flood

Log sources. nginx or gateway access logs, GraphQL server logs, APM traces, cloud provider metrics.

Key fields. request_uri (/graphql), status, bytes sent, upstream_response_time, query depth/complexity from the server, autoscaling events.

Normal behavior. GraphQL responses return in hundreds of milliseconds; payload sizes match the requested fields; complexity metrics stable.

Suspicious behavior. Requests with response sizes tens or hundreds of times the median; deep nesting flagged by the server; autoscaling firing repeatedly with no business reason.

Detection logic.

  • Flag 20 or more responses of 500/504 per client in 5 minutes with upstream_response_time of 5 seconds or more on API routes.
  • Compare each response's byte size to the endpoint median; alert when a client's ratio stays above 50x.
  • Alert on query depth above the configured maximum (for example deeper than 8 levels).
  • Track cloud autoscaling events per hour as a lagging but loud signal.

Field notes. A 504 on /graphql with a 10-second upstream time shows the resolver tree ran out of patience, not the network. Pair this with the GraphQL server's own complexity log for the full picture.

Field notes. A distributed trace records one request's journey as linked spans. This server span lasted 9.993 seconds (duration_ms). The attributes show depth 11 (deep nesting), 18.4 million rows read, and a 504 — the application-side fingerprint that pairs with the nginx record above.

Threat 7 · Compression-bomb uploads

Log sources. Upload-service application logs, WAF/ModSecurity audit logs, host disk and memory alarms, cloud storage metrics.

Key fields. message (decompression guard line), client_ip, uploaded body_bytes, expanded size, expansion ratio, action (accepted or rejected).

Normal behavior. Uploaded archives expand to sizes close to their compressed size; ratios stay near 10x or less; disk usage tracks business volume.

Suspicious behavior. Expansion ratios in the hundreds; a tiny request body followed by multi-second decompression and a disk-write spike; repeated uploads of the same archive shape from one client.

Detection logic.

  • Alert when an upload's expanded size exceeds 100 MB, or its expansion ratio exceeds 100x.
  • Flag any client that triggers 5 or more decompression-guard events within 5 minutes.
  • Correlate guard events with disk-write spikes or OOM (out-of-memory) events in the following 10 minutes.

Field notes. The guard compares compressed size with expanded size and stops the job at the limit. A 10.2 MB upload that wanted 4.1 GB of disk is the bomb fingerprint. action=rejected proves the control worked — but five rejections from one client means someone is probing the upload path.

5.5 Sigma rules and Splunk SPL

Sigma is an open format for writing detection rules once and using them in many SIEM products. SPL (Search Processing Language) is Splunk's query language. Below, each of the seven threats from 5.3 gets one Sigma rule and one matching SPL query. Field names assume a common setup; rename them for your environment. Each SPL query opens with an earliest=- window that mirrors the Sigma timeframe, so the two logic sets stay equal. All rules reference the ATT&CK technique and are safe: they only read logs.

Rule 1 · PostgreSQL slow-query flood (threat 1)

Severity: High

Mapping. Sigma message → SPL _raw; Sigma host → SPL host. The regex extracts duration_ms for numeric comparison.

False positives. Legitimate analytics jobs, month-end reports, a missing index after a schema change.

Tuning. Raise the duration threshold if batch reporting is normal for you; exclude known reporting service accounts; require correlation with 5xx waves for Critical severity.

SPL assumption. index=db, sourcetype=postgresql:log, host field present, 15-minute lookback (earliest=-15m) mirroring the Sigma timeframe — rename for your environment.

Rule 2 · PHP-FPM worker pool exhaustion (threat 2)

Severity: High · Mapping. Sigma message → SPL _raw; Sigma host → SPL host. False positives. Traffic peaks, deploy warm-up, an undersized pool with no attack. Tuning. Pair with access-log context (same minutes dominated by one endpoint); size the pool deliberately so the warning is meaningful.

Rule 3 · IIS time-taken flood (threat 3)

Severity: High · Mapping. Sigma c_ip → SPL c_ip; Sigma cs_method/sc_status/time_taken → the same names in Splunk's IIS sourcetype. False positives. Huge legitimate uploads or exports on POST routes. Tuning. Exclude known file-transfer endpoints; add a parameter-count check from WAF logs for stronger hashDoS evidence.

Rule 4 · WAF block storm per source (threat 4)

Severity: Medium · Mapping. Sigma message → SPL _raw; Sigma client_ip → SPL client_ip extracted with rex from the ModSecurity line; Sigma rule_id → SPL rule_id. False positives. A real vulnerability being hammered by scanners (still an incident); one aggressive penetration test you approved. Tuning. Keep a small allow-list for corporate egress addresses; alert on the count of distinct rules hit, not only volume.

Rule 5 · Login endpoint POST burst (threat 5)

Severity: Medium · Mapping. Sigma client_ip → SPL clientip; Sigma http_method → SPL method; Sigma request_uri → SPL uri; Sigma upstream_response_time → SPL field of the same name (custom nginx log format). False positives. One user with a stuck password manager; a load test you forgot to tag. Tuning. Require the latency condition so plain scanning does not trigger; exempt the corporate VPN range; keep hash-cost logging enabled to corroborate.

Rule 6 · nginx 5xx wave with slow upstream (threats 1 and 6)

Severity: Critical · Mapping. Sigma client_ip → SPL clientip; Sigma status → SPL status; Sigma upstream_response_time → same name; Sigma request_uri → SPL uri. False positives. A real bug released to production; a downstream service outage unrelated to any client. Tuning. The per-client grouping is the key: infrastructure faults hit all clients evenly, exhaustion floods concentrate on a few. Alert only when one client dominates.

Rule 7 · Decompression-bomb upload attempts (threat 7)

Severity: Medium

Mapping. Sigma message → SPL _raw; Sigma client_ip → SPL client_ip, extracted with rex from the guard line; the expansion ratio is extracted the same way for tuning.

False positives. A legitimate bulk-data export uploaded as an archive; an approved internal restore job.

Tuning. Exclude internal backup addresses; adjust the ratio threshold to your data mix; single rejections prove the guard works — page only when one client repeats.

SPL assumption. index=app, sourcetype=upload:service, guard lines parsed with rex, 5-minute lookback (earliest=-5m) mirroring the Sigma timeframe.

Good practice Test each rule on historical data before arming it. Record the alert volume it produced, then tune. A rule nobody tunes is a rule the team will mute within a month.

6

Real-world case study

One documented historical event that shaped every web framework, plus one representative scenario that shows the full incident lifecycle.

Documented anchor: the 2011 "hashDoS" disclosure

In December 2011, security researchers Alexander Klink and Julian Wälde presented at the 28C3 conference (Chaos Communication Congress, Berlin) how many web language runtimes built their hash tables. An attacker could send a POST request with thousands of form fields whose keys were crafted to collide, turning request parsing into hours of CPU work. The talk covered PHP, Java, Python, Ruby, JavaScript, and ASP.NET. Microsoft shipped an emergency out-of-band fix for ASP.NET, tracked as CVE-2011-3414, on 29 December 2011. Vendors across the industry then added limits on the number of POST parameters — a structural fix that most frameworks still carry today.

  • 2011-12-28

    Klink and Wälde present the hash-collision research at 28C3. Coordinated vendor contact happened before the talk.

  • 2011-12-29

    Microsoft releases the out-of-band security fix for ASP.NET (CVE-2011-3414) — one day after the public talk, an unusually fast vendor response.

  • Early 2012

    PHP, Python, Ruby, Java, and JavaScript runtime maintainers ship their own limits: max POST fields, bounded hash seeds, or both.

  • Ongoing

    The technique stays in attacker playbooks wherever old or custom stacks miss the limits — a permanent lesson in "parsing cost is attack surface".

Warning — representative scenario The incident below is a composite, representative scenario based on public incident reports (wildcard-query floods against SaaS search endpoints). Company names, counts, and timings are illustrative and chosen to be realistic. The 2011 hashDoS section above, in contrast, is documented fact.

Representative scenario: "SlowSearch" — a SaaS search endpoint flood

A mid-size SaaS (software-as-a-service) company ("ShopFlow") offers product search to retail customers. The search endpoint passes user text straight into database LIKE patterns, with no query cost budget and no per-client latency limit. An attacker discovers that a single wildcard-heavy query keeps the database busy for 15 seconds.

Impact and consequences

  • About 36 minutes of degraded checkout for real customers.
  • No data breach — the attack targeted availability only.
  • Support load spike; two enterprise customers asked for written incident summaries.
  • Engineering time: roughly two team-days for response plus follow-up work.

Team response and communication

  • SOC opened the ticket at 10:44 and paged the service owner at once.
  • One incident commander; a scribe kept the timeline — which later made the report easy.
  • Status page updated twice: "investigating" then "mitigated".
  • Post-incident review within 3 working days; no blame, only fixes.

Lessons learned

Cost, not count

Rate limiting alone missed the attack because request volume was modest. Query cost budgets caught what request count limits cannot.

Timeouts are safety nets

A 3-second statement timeout turned "15 seconds of deadlock" into "3 seconds of error", saving the whole backend.

Per-client visibility

The detection worked because logs carried upstream_response_time and client identity. Instrument first, detect second.

Rehearse the chain

The team recovered in under 4 hours because roles, status-page wording, and escalation paths had been drilled before.

7

Mitigation and defense

Concrete, verifiable controls that make expensive requests cheap again — or make them fail fast.

Policy

Write a capacity and abuse policy: which endpoints may cost how much, who approves load tests, and how DoS incidents are escalated. Review it twice a year.

Identity

Throttle logins per client and per account; add exponential backoff; require MFA (multi-factor authentication) where possible so fake login floods lose their value.

Endpoint

On hosts: cap worker pools sensibly, enable process-level CPU and memory alarms, and keep hash-cost factors benchmarked against real capacity.

Network

Put a WAF or CDN in front; enforce per-client rate limits and body-size limits; block obviously malformed payloads at the edge so they never reach application code.

Cloud

Use provider DDoS protection tiers; set autoscaling ceilings so a flood cannot become a billing incident; isolate expensive features in their own service.

Logging

Enable slow-query logs, keep upstream_response_time in access logs, ship everything to the SIEM, and retain long enough to compare with history.

Monitoring

Alert on the patterns from section 5: 5xx waves per client, slow-query counts, worker exhaustion, parser limit hits. Page on correlation, not on single spikes.

Backup and recovery

Availability work still needs the boring basics: tested backups, a second region or site, and a documented recovery runbook.

Response

Pre-approve containment actions (rate-limit bumps, blocking address families) so the on-call engineer can act in minutes, not hours.

Home and small-office advice

Good practice Running a small website or home server? Turn on your reverse proxy's basic rate limiting (nginx limit_req, or your host panel's built-in throttling). Keep your CMS (content management system, for example WordPress) and its plugins updated. Choose hosting that includes DDoS protection, and keep nightly backups. You do not need an enterprise SIEM to be a harder target than the average opportunistic bot expects.

Common mistakes and best practices

Twelve blue-team mistakes seen again and again with this technique — and the fix for each.

1 · Alerting on every slow query

Symptom: dozens of slow-query alerts a day; nobody reads them.

Root cause: single events alerted instead of patterns.

Fix: alert on counts and repetition within a window, not on one entry.

Prevention: baseline first; tune thresholds against a week of history.

2 · Counting requests, not cost

Symptom: attack lands, request-rate dashboard stays calm.

Root cause: only volume metrics exist; cost per request is invisible.

Fix: add latency and rows-scanned metrics per endpoint and per client.

Prevention: make upstream_response_time a mandatory log field.

3 · Missing logs

Symptom: during the incident nobody can say which parameters were sent.

Root cause: query strings or body sizes never logged; retention too short.

Fix: log full request URIs, client IP, and status; keep at least 90 days searchable.

Prevention: log reviews as part of every new service's launch checklist.

4 · Every 5xx wave treated as a bug

Symptom: teams argue about deploys while an attack runs.

Root cause: no check separating code faults from abusive traffic.

Fix: triage question: do errors concentrate on a few clients? If yes, suspect abuse.

Prevention: a shared runbook page for "5xx wave" triage.

5 · One catch-all alert (alert fatigue)

Symptom: a single "web problems" alert fires for everything.

Root cause: rules written once, never split by meaning.

Fix: split into distinct, named alerts with their own runbook links.

Prevention: quarterly alert review; delete or fix rules nobody acts on.

6 · No per-client grouping

Symptom: dashboards show totals; the single abusive client hides inside them.

Root cause: aggregation without a group-by key.

Fix: group by client IP, account, and endpoint in every exhaustion rule.

Prevention: reuse the Sigma rules in 5.5 as templates.

7 · Rules never tested on history

Symptom: new rule fires 200 times in hour one, then gets disabled.

Root cause: no backtest against past data before arming.

Fix: replay 30 days of logs; adjust thresholds; record expected volume.

Prevention: a "test before arm" step in the detection review process.

8 · Ownership gaps

Symptom: alert pages a rotation that only knows how to restart a server.

Root cause: no named service owner for the expensive endpoint.

Fix: map every alert to a team and an escalation path; keep the map current.

Prevention: ownership listed in the alert metadata itself.

9 · Rate limits tuned for averages

Symptom: limit blocks real users during sales events, not the attacker.

Root cause: limits chosen from average traffic, not burst behaviour.

Fix: set limits from p95/p99 (the levels 95 and 99 percent of real traffic stays under); add separate authenticated tiers.

Prevention: revisit limits each quarter and after major features.

10 · Never rehearsing

Symptom: first real flood becomes improvised theatre at 3 a.m.

Root cause: no tabletop exercise for DoS scenarios.

Fix: run a 60-minute lab tabletop twice a year using the case study in section 6.

Prevention: schedule it like backups — repeating, boring, essential.

11 · WAF logs ignored

Symptom: the WAF blocked the attack, but the SOC only learns a week later.

Root cause: WAF logs not shipped to the SIEM or never alerted on.

Fix: ship WAF logs, alert on block storms (rule 4 in 5.5).

Prevention: treat the WAF as a sensor, not just a shield.

12 · Weak tuning culture

Symptom: thresholds set at project start, never touched again.

Root cause: tuning is nobody's backlog item.

Fix: time-boxed tuning sprints with before/after alert volumes documented.

Prevention: track false-positive rate as a team metric.

Habits that keep the detections alive

Daily

Scan the top-10 slowest requests and the 5xx rate per endpoint. Two minutes, same time each day.

Weekly

Review new alert sources and muted rules; check WAF block counts per client; confirm slow-query log still enabled after deploys.

Monthly

Backtest one Sigma rule on fresh history; re-benchmark one expensive endpoint; update the capacity notes and this guide's thresholds if needed.
