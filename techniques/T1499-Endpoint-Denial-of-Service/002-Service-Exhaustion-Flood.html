T1499.002 — Service Exhaustion Flood

This guide explains how an attacker can flood one network service until the service runs out of its own worker slots and stops answering. It also shows defenders where this attack leaves traces in logs, how to write detection rules, and how to stop it. All attack examples here are lab only: run them only on isolated test machines that you own.

  • Tactic: Impact
  • Parent: T1499 Endpoint Denial of Service
  • Platforms: IaaS · Linux · Windows · macOS
  • Primary target: Service worker and connection limits
  • Created: 20 February 2020 · ATT&CK v20 · Last modified: 24 October 2025

Attack cost

Low bandwidth, many slow connections — or raw request volume. One small host can hold every worker of a busy service.

Key evidence

Service error logs plus a sharp rise in concurrent connections from one source.

Signature artifact

worker_connections are not enough in the nginx error log; server reached MaxRequestWorkers for Apache.

Core control

Short timeouts, concurrency limits, rate limits, and a web application firewall (WAF).

    1

    Overview

    What this technique is, in plain words, and how it differs from its sibling techniques.

    A network service, such as a web server, can only talk to a limited number of clients at the same time. Think of the service as a small shop with eight chairs. Each visitor sits on a chair, gets served, and leaves. A Service Exhaustion Flood (MITRE ATT&CK sub-technique T1499.002) is when an attacker fills all the chairs and then refuses to leave. New real customers find no free chair and give up.

    ATT&CK (Adversarial Tactics, Techniques and Common Knowledge) is a public catalog that describes how attackers operate. T1499.002 sits under the parent technique T1499 Endpoint Denial of Service, in the Impact tactic. The goal is availability loss: the service still runs, but nobody can use it. The attacker does not break the software and does not steal data. The attack just occupies the service's own capacity until it exhausts its limits: its worker pool, thread pool, maximum client count, or request queue.

    The official ATT&CK description names two patterns for this sub-technique, so they come first here. The first is the simple HTTP flood. The attacker sends a large number of ordinary HTTP requests at the web server. Each request looks normal. The raw volume exhausts the resources the victim software needs to answer: CPU time, memory, threads, or connection slots. The second is the SSL renegotiation attack. SSL/TLS (Secure Sockets Layer, and its successor Transport Layer Security) is the protocol family that encrypts HTTPS. Some versions allow renegotiation: while a connection is open, the two sides can redo the agreement on the encryption algorithm they use. Doing that many times costs the server a meaningful amount of computation, so it can break service availability.

    The two patterns ATT&CK names

    Official pattern

    Simple HTTP flood (raw volume)

    Thousands of complete, valid requests hit one service as fast as the attacker can send them. Nothing is malformed and nothing is slow. The service does real work on every request until its worker pool, memory, or connection slots run out. These floods often come from many machines at once, which makes per-source limits harder to apply.

    Official pattern

    SSL renegotiation flood

    The attacker opens TLS connections and asks the server to renegotiate the crypto agreement again and again. The server pays a heavy computational cost each time; the client pays far less. TLS 1.3 removed renegotiation, and many TLS 1.2 servers refuse client-initiated renegotiation, so this pattern mostly hits older or misconfigured endpoints.

    Other service-exhaustion patterns

    Attack pattern

    Slow HTTP headers (slowloris style)

    HTTP (Hypertext Transfer Protocol) is the language web browsers and web servers speak. An HTTP request starts with a small text block called the header. The attacker sends only the first header lines, then stops and waits. The server keeps a worker (one unit of serving capacity, like a process or thread) waiting for the rest. The attacker repeats this with hundreds of connections until every worker waits for bytes that never arrive.

    Attack pattern

    Slow POST body (RUDY style)

    A POST request sends data to the server, for example a form or an upload. The attacker announces a large body, then sends it one tiny piece at a time, with long pauses. The worker stays busy holding a half-finished upload. This is the same trick as slow headers, aimed at the body instead of the header.

    Attack pattern

    Fast connection flood to one daemon

    A daemon is a program that runs in the background and serves requests, such as a web server, DNS server, or mail server. Here the attacker simply opens as many network connections as the daemon allows, as fast as possible, and keeps them open. The daemon runs out of connection slots.

    Attack pattern

    Service-specific floods

    The same idea works on any service with its own limits. A DNS (Domain Name System) resolver can drown in name lookups. An SMTP (Simple Mail Transfer Protocol) mail server can drown in mail connections. An LDAP (Lightweight Directory Access Protocol) server can drown in bind (login) requests. A database can lose its connection pool through the application in front of it.

    One boundary to keep in mind: the renegotiation attack is expensive work, yet ATT&CK places it here, not under T1499.003. The difference is the layer. Renegotiation exhausts a service-level protocol feature of the TLS endpoint itself. T1499.003 targets expensive features inside an application, such as a heavy search page.

    Note

    ATT&CK lists the official platforms for T1499.002 as IaaS (Infrastructure as a Service, meaning rented cloud servers), Linux, Windows, and macOS. The threat scope is wider: any service with a worker or connection limit can be a target. This guide therefore also uses the broader labels Network, Cloud, and Identity for its threat cards.

    The same story in writing

    1. Normal traffic. Real visitors send quick requests. The eight workers serve them one after another. In the SOC panel, connections per source stay low and steady.
    2. The attacker arrives. One host opens many connections to the web server. On each connection it sends only the first header lines, such as GET / HTTP/1.1 and Host:, then it stops sending and waits.
    3. All chairs are taken. Every worker now waits for header bytes that never come. Each worker holds a timer, but the timeout is long, so they wait for minutes.
    4. A real user is shut out. A normal visitor connects, waits in the queue, and finally gives up. The request times out and shows up as status 408 or 499 in the logs.
    5. The SOC sees it. The metric "concurrent connections per source" jumps for one address. The nginx error log prints worker_connections are not enough. These two signals together are a strong alert.
    6. The defender tunes, the attacker adapts. Shorter header timeouts and rate limits free workers faster. The attacker spreads the connections or slows the pace to stay under the new limits.
    7. The source is blocked. The firewall and WAF drop the attacking address upstream of the server. The workers free up at once.
    8. Recovery. Real users are served again. The team records the incident and adds the per-source baseline to its monitoring.

    Red team perspective

    Why an attacker picks this technique and how it works, so you can understand the traces it leaves. Every command here is lab only.

    An attacker picks service exhaustion when the goal is simple downtime and the budget is small. Unlike a bandwidth flood (T1498), this attack needs very little traffic. A single laptop can hold hundreds of half-open connections. The attack is quiet on the network but loud in the service's own error logs, which is exactly what section 4 and section 5 use.

    When and why attackers choose it

    • Low cost: no rented botnet or wide pipe is needed; slow connections are cheap to keep open.
    • Small footprint: few packets per second, so volume-based network alarms stay quiet.
    • Known weak defaults: many servers ship with long request timeouts and small worker pools.
    • Cover: a flood of slow clients looks a little like normal mobile users on bad links.

    Prerequisites the attacker looks for

    • A service that keeps a slot open while waiting for client bytes (a long timeout is the time the server waits before giving up).
    • A small worker or connection limit compared to expected traffic, for example Apache MaxRequestWorkers 150 or nginx worker_connections 512.
    • No reverse proxy or WAF in front that closes slow clients early. A reverse proxy is a middle server that speaks to clients first and forwards only finished requests.
    • No per-source connection limit at the firewall.

    Conceptual flow of a slow-header attack

    1. Open a TCP (Transmission Control Protocol) connection to the web service.
    2. Send a partial request header: the request line and one or two header lines, then stop. The request is unfinished, so the worker must wait.
    3. Every few minutes, send one more harmless header line to keep the connection alive before the server's timeout closes it.
    4. Open more connections in parallel until all workers are held.
    5. Keep topping up the connections; the service stays unusable for as long as the attacker keeps going.

    The slow POST variant is the same, but the attacker announces a big body and then drips it in tiny pieces. The fast connection flood variant does not even need HTTP: it just fills the daemon's connection table with idle sessions.

    The raw-volume HTTP flood

    The official ATT&CK example works the opposite way to slowloris. The requests are complete, valid, and fast, but there are enormous numbers of them. The attacker repeats ordinary GET or POST requests as fast as the target and its own uplink allow. Every request consumes worker time, memory, and upstream calls. So the service exhausts even though every individual request is harmless. Public reporting shows these floods usually come from many machines at once, because one host rarely has enough bandwidth to outrun a service alone.

    In a lab you can show the mechanism at tiny scale. Run a short burst of normal benchmark requests against your own test server, then watch worker usage and response times climb while the traffic stays perfectly valid.

    The SSL renegotiation attack

    Here the attacker opens one or more TLS connections and then triggers renegotiation repeatedly. Renegotiation makes the server redo the key exchange and the cipher agreement. That costs the server far more computation than the client. Done in volume, it burns CPU on the TLS endpoint and slows or stalls every connection it serves. Because TLS 1.3 removed renegotiation and most modern stacks refuse client-initiated renegotiation, first check whether your services allow it at all. If they do, treat that as a finding even before any attack.

    Warning — Lab only

    Both checks below touch only the reserved lab address 10.0.0.10, on a test server you own and on an isolated network. The first sends ordinary requests, only faster than a human would. The second asks the server once whether it allows renegotiation. Never point these tools at systems you do not own.

    shell — tiny raw-volume flood demonstration against your own lab server
    ab -n 2000 -c 50 http://10.0.0.10/index.html

    ab is the ApacheBench load-test tool. -n is the total number of requests and -c is how many run at once. While it runs, watch worker usage on the server, then compare with the access-log fingerprint in section 5.4.

    shell — ask your lab server whether renegotiation is allowed
    openssl s_client -connect 10.0.0.10:443 -tls1_2
# after the handshake appears, press R once and press Enter, then close with Ctrl+C

    If the server renegotiates, one connection can make it redo that expensive work forever. If it refuses, the pattern is already closed on that service. Record which servers still accept renegotiation, because that list drives the mitigation in section 7.

    Warning — Lab only

    Run the following only against a test web server you own, on an isolated network such as a home lab or a virtual lab. The example targets are the reserved lab addresses 10.0.0.10 and lab.local. Never point these tools at systems you do not own; in most countries that is a crime (see section 5.1).

    shell — slow-header test against your own lab web server
    slowhttptest -c 200 -H -i 10 -r 50 -t "GET / HTTP/1.1" -u http://10.0.0.10/index.html -p 3 -l 60

    Flags: -c number of connections, -H slow-header mode, -i seconds between keep-alive bytes (small periodic bytes that stop the server closing an idle connection), -r connections per second, -p probe timeout, -l test duration. On the lab server, watch the effect in another terminal:

    shell — watch the artifacts on your own lab server
    tail -f /var/log/nginx/error.log
ss -tan state established '( dport = :80 )' | wc -l

    Common variations

    • Slowing only the request body on upload endpoints (RUDY style).
    • Hitting several services at once: web plus DNS plus LDAP.
    • Running the flood from many small sources at low rate each, so per-source limits are harder to apply.
    • Mixing slow clients and fast floods at the same time, so each signature stays weaker.
    • Abusing SSL/TLS renegotiation as described above; the official ATT&CK page lists this variant for T1499.002.

    Common attacker mistakes (your detection opportunities)

    • Opening too many connections from one IP address, which makes the per-source count spike obvious.
    • Keeping perfectly regular timing between keep-alive bytes, unlike human traffic.
    • Leaving the default tool User-Agent string (such as slowhttptest) in every request.
    • Forgetting to top up connections after the server timeout closes them, so the attack fades in minutes.
    • Attacking through a reverse proxy that enforces short header timeouts, so the origin never feels it.
    4

    Blue team perspective

    What defenders can see, which artifacts this attack leaves, and a short triage flow for the SOC.

    Defenders rarely catch this attack on the network wire first. They catch it in the service's own logs and metrics. The service is the best witness: it knows exactly how many workers are busy, who holds them, and when it runs out.

    Artifact

    Daemon error messages

    nginx prints worker_connections are not enough. Apache prints server reached MaxRequestWorkers. MySQL prints Too many connections. These lines are precise and rare in normal operation.

    Artifact

    Waves of 408 and 499

    Status 408 means the client sent the request too slowly. Status 499 means the client gave up before the answer. A wave of these codes from many victims, while one source holds the workers, is the classic pattern.

    Artifact

    Concurrency spike per source

    The number of simultaneous connections from one address grows far above the baseline. Latency (response time) climbs because new requests queue behind held workers.

    Artifact

    Tiny requests, long holds

    Access logs show requests with almost no bytes sent and very long request_time values, often ending in timeout codes.

    Artifact

    TLS handshake and renegotiation counts

    TLS logging tools such as Zeek or Suricata write one event per handshake, and WAF or CDN (content delivery network) dashboards count handshakes per source. Renegotiation itself should be nearly absent today: TLS 1.3 removed it, and most TLS 1.2 servers refuse client-initiated renegotiation. A handshake storm from one source, or any renegotiation at all, is a strong signal.

    Where to look

    • Service error logs: /var/log/nginx/error.log, Apache error_log, Windows DNS Server event log, MySQL error log.
    • Access logs with timing: status, bytes, and request_time per request.
    • TLS visibility: Zeek ssl.log, Suricata TLS events, and WAF or CDN handshake and renegotiation counters.
    • Connection tables: ss -tan or netstat on the host, and firewall or load balancer connection counts per source.
    • Metrics: busy workers, queue depth, and connections per source on dashboards.

    Why it matters and where it fits in the attack chain

    MITRE ATT&CK places T1499.002 in the Impact tactic, usually as the final step of an operation. It can also be a smokescreen: a noisy availability attack that keeps responders busy while a quieter intrusion happens elsewhere. For many organizations the business impact is direct lost revenue or lost public trust, which is why availability controls appear in laws and audit standards (section 5.1).

    Short triage flow

    1. Step 1 — ConfirmCheck service health and worker usage. Is the daemon up but not answering? That points to exhaustion, not a crash.
    2. Step 2 — Rank sourcesCount concurrent connections per source address. A single address far above the baseline is the prime suspect.
    3. Step 3 — Match the waveLook for 408 and 499 waves, TLS handshake or renegotiation counts, and the matching error-log line. This confirms the mechanism.
    4. Step 4 — ContainBlock or rate-limit the source upstream (firewall, edge, or WAF), not only on the origin server.
    5. Step 5 — Harden while it hurtsShorten the relevant timeouts now; they were too long by definition.
    6. Step 6 — RecordSave logs, note the timeline, and file the incident. Add the new baseline and alert to monitoring.
    Official mapping

    MITRE ATT&CK ties this sub-technique to detection strategy DET0173, "Detection Strategy for Endpoint DoS via Service Exhaustion Flood". Its analytics describe the signals above:

    • AN0489 — high-frequency, repetitive service requests such as HTTP or TLS renegotiation from one or a few source addresses, ending in CPU or memory exhaustion.
    • AN0490 — excessive inbound HTTP or TLS connections to services such as Apache or Nginx, exhausting worker threads.
    • AN0491 — TLS or HTTP(S) connection floods against macOS-hosted services, causing high CPU use and unresponsiveness.
    • AN0492 — automated, scripted HTTP or TLS flooding from one cloud instance against another service.

    The recipes in section 5 turn these analytics into rules on logs you already collect.

    Good practice

    Ship service error logs to your central log platform (SIEM, Security Information and Event Management) in real time. Most of the detections in section 5 are cheap and reliable only if those logs arrive within seconds.

    5.3 Threats ranking and categorization

    Below are the eight realistic service-exhaustion threats this guide tracks, in severity order. The two official ATT&CK patterns (raw-volume HTTP flood and SSL renegotiation flood) sit beside the slow-client and service-specific variants. Severity reflects how much damage a typical attacker can do with modest resources, and how often the pattern appears in real incidents.     1. Slow HTTP headers (slowloris class) High

    Preconditions: an exposed web server with long header timeouts, a small worker pool, and no reverse proxy or WAF closing slow clients.

    Impact: all workers wait for header bytes that never finish; the whole site or API stops answering while the machine stays healthy.

    Why High: one low-bandwidth host can take a full daemon offline, and the required skill is beginner level.

    2. Slow POST body (RUDY class) High

    Preconditions: an endpoint that accepts POST bodies (forms, uploads, APIs) with a long body-receive timeout.

    Impact: workers stay busy holding half-finished uploads; buffers and temp files fill; the endpoint and often the whole server slow down.

    Why High: same cheap one-host effect as slow headers, and upload endpoints are common.

    3. Raw-volume HTTP flood (official pattern) High

    Preconditions: an exposed HTTP service whose per-request work (dynamic pages, API calls, upstream lookups) adds up; attacker capacity high enough to out-pace the service.

    Impact: CPU, memory, or worker slots exhaust while every request still looks normal; caches often miss, so each request hits the backend.

    Why High: it is the canonical pattern named by ATT&CK, it is trivially automated, and per-request cost means even moderate rates break the service.

    4. Fast connection flood to a single daemon High

    Preconditions: a service reachable on the network with a fixed connection-slot limit and no per-source limit at a firewall.

    Impact: the listen backlog and connection table fill; new clients are refused or reset even though bandwidth is barely used.

    Why High: trivially automated, works against almost any daemon, and is often spread over several sources.

    5. DNS resolver query flood High

    Preconditions: a resolver (a server that answers name-lookup questions) reachable by the attacker, with per-source query limits off or high.

    Impact: query slots and threads exhaust; every service that depends on names (web, mail, logins) fails at once.

    Why High: small attack, big blast radius: DNS is the phone book of the network.

    6. SSL/TLS renegotiation flood (official pattern) Medium-High

    Preconditions: a TLS endpoint that still accepts client-initiated renegotiation (older TLS 1.2 servers, some appliances), reachable by the attacker.

    Impact: the server spends heavy cryptographic work per renegotiation; CPU saturates and legitimate TLS connections stall or fail.

    Why Medium-High: modern stacks mostly closed it, so reach is shrinking, but where it exists one host can still exhaust the TLS service.

    7. LDAP bind flood on a domain controller Medium

    Preconditions: network access to an LDAP (directory login) port on a domain controller, plus weak bind throttling; unauthenticated binds often work with default settings.

    Impact: directory worker threads saturate; logons, lookups, and applications that query the directory become slow or fail.

    Why Medium: usually needs internal network access and the effect can be throttled, but the business damage is high when it lands.

    8. Database connection pool exhaustion via the app Medium

    Preconditions: an application with a limited database connection pool (a fixed set of reusable database sessions) that attackers can slow down or hold.

    Impact: the pool empties; the application throws errors; new customers cannot check out or log in while the database itself looks fine.

    Why Medium: often limited to one application and can self-heal after timeouts, but it converts a small flood into a business outage.

The recipes implement the official detection strategy DET0173 and its analytics (AN0489–AN0492) on logs you already collect. Example log lines use documentation addresses such as 203.0.113.x (attacker) and 10.0.0.x (your servers).

    Threat 1 — Slow HTTP headers (slowloris class)

    • Log sources: nginx error log; nginx access log with timing fields; Apache error log; reverse proxy logs.
    • Key fields: message text, worker process id (pid), connection id, client address, status code, request_time, bytes sent, User-Agent.
    • Normal: few timeouts per hour, spread over many sources; concurrency per source usually below 10.
    • Suspicious: the exhaustion message in the error log, at the same time as one source holds hundreds of connections. Requests have tiny sizes and long times, ending in 408 or 499.
    • Detection logic:
      • Error log contains "worker_connections are not enough" (nginx) or "server reached MaxRequestWorkers" (Apache).
      • AND, in the same 5-minute window, one source has more than 50 open connections or more than 50 timeout statuses.
      • Tie-break with request_time above 55 seconds on those requests.
    nginx error.log — exhaustion message
    2026/02/14 03:12:40 [alert] 5678#0: *23456 worker_connections are not enough while connecting to upstream, client: 203.0.113.50, server: lab.local

    5678#0 is the worker process and its generation; *23456 is the connection id; the alert level marks a resource limit; client is the remote address that triggered the line.

    Threat 2 — Slow POST body (RUDY class)

    • Log sources: access logs of the origin or reverse proxy (POST endpoints), WAF logs, application error logs.
    • Key fields: method (POST), URI (the requested path), status, request_time, body_bytes_sent, client address, content-length announced.
    • Normal: uploads take seconds, not minutes; 408 codes are rare; bytes flow at a steady rate.
    • Suspicious: POST requests that last minutes with almost no bytes completed, several from the same source, and a 408 wave right after.
    • Detection logic:
      • method = POST AND request_time above 60 seconds AND status in (408, 499).
      • Group by source; alert when a source has more than 20 such requests in 10 minutes.
      • Correlate with Apache "server reached MaxRequestWorkers" if the origin is Apache.
    nginx access.log — slow POST held until timeout
    203.0.113.51 - - [14/Feb/2026:03:20:07 +0000] "POST /upload HTTP/1.1" 408 0 "-" "RUDY-lab" rt=119.98 uct="-" uht="-" urt="-" bytes=0

    rt is request_time (about 120 seconds here), uct/uht/urt are upstream connect, header, and response times (empty because the request never reached the backend), and bytes=0 shows nothing useful was delivered. The User-Agent string here is from a lab tool; real attacks often copy a browser string instead.

    Threat 3 — Raw-volume HTTP flood (official pattern)

    • Log sources: nginx or Apache access logs, WAF and CDN request logs, load balancer logs, service CPU and memory metrics.
    • Key fields: client address, method, path, status, bytes, request_time, User-Agent, requests per second per source, cache-hit ratio.
    • Normal: request rates follow the daily traffic shape; paths spread across the site; cache-hit ratio is stable; one source rarely dominates.
    • Suspicious: one or a few sources send hundreds of requests per minute. Most answers are 200, because every request is valid. The same few paths repeat, and CPU or memory climbs on the service. This is the AN0489 shape: high-frequency, repetitive requests that end in resource exhaustion.
    • Detection logic:
      • Count GET and POST requests per client per minute; alert above a baseline-derived threshold, for example 300 per minute from one address.
      • Strengthen the signal when the same small path set repeats and the cache-hit ratio drops.
      • Correlate with service CPU or worker metrics, because volume alone on a static site may be harmless.
    nginx access.log — valid requests at flood rate
    203.0.113.60 - - [14/Feb/2026:04:05:11 +0000] "GET /products/42 HTTP/1.1" 200 5123 "-" "python-requests/2.31.0" rt=0.31 uct="0.001" uht="0.02" urt="0.29"
203.0.113.60 - - [14/Feb/2026:04:05:11 +0000] "GET /products/42 HTTP/1.1" 200 5123 "-" "python-requests/2.31.0" rt=0.33 uct="0.001" uht="0.02" urt="0.30"

    Two lines from the same source, 220 milliseconds apart, same path, both status 200, both doing real upstream work (urt about 0.3 seconds). Multiply by hundreds of requests per minute and the worker pool and CPU burn continuously. Contrast with the slow attacks: here statuses are 200 and request_time is short; there statuses are 408 or 499 and request_time is long. The User-Agent names a script, but real floods often copy browser strings.

    Threat 4 — Fast connection flood to a single daemon

    • Log sources: firewall or load balancer connection logs, host connection tables (ss -tan snapshots), service logs (listen queue overflows), nginx or HAProxy connection counters.
    • Key fields: source address, destination port, connection state (ESTABLISHED, SYN_RECV), timestamp, accept-queue depth, kernel messages about SYN flood or listen overflows.
    • Normal: steady connection counts per source; queue depth near zero; established sessions match real users.
    • Suspicious: hundreds of ESTABLISHED sessions from one source to one port; kernel logs about listen queue overflow; connections open for the maximum allowed time.
    • Detection logic:
      • Count connections per source per minute against one service port; alert above 300 from one source.
      • Alert on kernel messages "possible SYN flooding" or "listen queue overflow" for that port.
      • Alert when total service connections reach the daemon's configured slot count.
    kernel log — the queue behind the daemon is full
    Feb 14 03:31:02 web01 kernel: TCP: request_sock_TCP: Possible SYN flooding on port 80. Sending cookies.  Check SNMP counters.

    The kernel says the accept queue for port 80 is overflowing, so it switched on SYN cookies. SYN cookies are a defense that answers half-open handshakes without storing them. This message appears when too many connection attempts arrive faster than the service can finish the handshakes. A flood of completed idle sessions may instead saturate the daemon's own slot limit without any kernel message. That is why the per-source connection count in the firewall or proxy log is the stronger signal for threat 4.

    Threat 5 — DNS resolver query flood

    • Log sources: BIND query log (the "queries" logging category; you enable it once, and BIND then writes one line per query it answers), Windows DNS Server analytic log, dnsdist or unbound logs, network flow records to port 53.
    • Key fields: client address and port, queried name, record type, response code (REFUSED, SERVFAIL), queries per second per client.
    • Normal: a few queries per second per client; names repeat across the whole client base.
    • Suspicious: one source sending hundreds of queries per second, often random names, and REFUSED or SERVFAIL answers rising for everyone.
    • Detection logic:
      • Count query-log lines per client per minute; alert above 300.
      • Alert when the share of REFUSED or SERVFAIL answers jumps above 30 percent.
      • Flag random-looking names from one source (possible random-subdomain storms).
    BIND query log — one line per query
    14-Feb-2026 03:41:22.101 queries: info: client @0x7f8b1c02d0e0 203.0.113.7#53123 (example.com): query: example.com IN A +E(0)K (10.0.0.53)

    client @0x... is an internal handle; 203.0.113.7#53123 is the asking address and port; (example.com) is the zone view; IN A is the record type; +E(0)K are query flags; (10.0.0.53) is your resolver. The address before the hash is the field your detection should count.

    Threat 6 — SSL/TLS renegotiation flood (official pattern)

    • Log sources: Zeek ssl.log (one record per TLS session, with a history field that marks renegotiation), Zeek conn.log for handshake counts, Suricata TLS events, WAF or CDN TLS handshake counters, and web server or load balancer TLS logs (nginx, HAProxy, IIS).
    • Key fields: source address, destination address and port, TLS version, server name (SNI, the name the client asked for), handshake or renegotiation marker, handshakes per source per window.
    • Normal: a handful of handshakes per source per minute; no renegotiation at all, because TLS 1.3 removed it and most TLS 1.2 servers refuse client-initiated renegotiation.
    • Suspicious: a handshake storm from one source, or any renegotiation marker from a client. Renegotiation should simply not happen on a current service.
    • Detection logic:
      • Count TLS handshakes per source per 5 minutes; alert above a baseline-derived threshold, for example 200 from one address.
      • Alert on any client-initiated renegotiation marker, for example the r history entry in Zeek ssl.log; tune only for the rare legitimate application.
      • Correlate with TLS endpoint CPU: the damage is computational, so the CPU graph is the confirming artifact.
    Zeek ssl.log (tab-separated) — renegotiation markers in the history field
    1739510407.612345  CsOaGl1yxBxU8mQJ9c      203.0.113.80    53124   10.0.0.10       443     TLSv12  TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256   -       lab.local       F       -       -       T       THrr    -

    Read the line left to right. The fields are: timestamp, connection id, source 203.0.113.80, destination 10.0.0.10:443, TLS version, cipher, curve, server name lab.local, not-resumed flag, alert, next protocol, and established flag. The interesting part comes last: the ssl_history field THrr. T marks the TCP setup. H marks a completed handshake. Each r marks a renegotiation the server accepted. Two renegotiations on one connection is already abnormal, so count them per source. History letters vary slightly between Zeek versions. If yours does not mark renegotiation, count handshakes per source instead. The same logic works on Suricata TLS events (one event per handshake, counted by src_ip) or on WAF and CDN handshake counters.

    Threat 7 — LDAP bind flood on a domain controller

    • Log sources: Windows Directory Service event log (event ID 2889 records bind types), Security event log (4625 failed logons, if credentials are tried), domain controller performance counters (LDAP bind time, threads).
    • Key fields: event ID, client IP and port, bind type (0 = unauthenticated, 1 = simple, 2 = NTLM/negotiate), count per client, LDAP bind time metric.
    • Normal: bind type 0 is rare and mostly from old devices; binds per client are low; bind times are under milliseconds.
    • Suspicious: thousands of unauthenticated binds (type 0) from one address in minutes, with LDAP bind time climbing.
    • Detection logic:
      • Event ID 2889 with "Bind type: 0", grouped by client IP; alert above 100 in 5 minutes from one client.
      • Correlate with a rise in LDAP bind time or a drop in successful logon speed.
      • One 2889 flood source is also a finding by itself: unauthenticated binds should not exist on modern servers.
    Windows Directory Service event — event ID 2889
    Log Name:      Directory Service
Source:        Microsoft-Windows-ActiveDirectory_DomainService
Event ID:      2889
Level:         Information
Computer:      DC01.lab.local
Message:       Client IP and type of bind for successful binds.
               Client IP: 203.0.113.77:51234
               Bind type: 0 (unauthenticated)

    Each 2889 event records one successful bind. Bind type: 0 means the client sent no credentials at all. A storm of these from one address is either a misconfigured old device or a bind flood.

    Threat 8 — Database connection pool exhaustion via the app

    • Log sources: MySQL or PostgreSQL error log, application server logs (pool timeout errors), cloud load balancer logs showing 5xx errors, APM traces (application performance monitoring).
    • Key fields: message text, connection id, database name, user, client host, pool name, pool active and waiting counts.
    • Normal: "Too many connections" is absent in steady state; pool wait time is low; connections are released in milliseconds.
    • Suspicious: repeated "Too many connections" or pool-timeout errors in a short window, together with a request storm on the front end.
    • Detection logic:
      • Error log contains "Too many connections" (MySQL) or "connection timed out" pool errors (app side); alert above 5 in 5 minutes.
      • Correlate with a rising rate of held app requests (slow POST) from a small set of sources.
      • Check Aborted connection warnings: they show clients being dropped when the limit hits.
    MySQL error log — the pool is full
    2026-02-14T03:52:44.123456Z 12 [Warning] Aborted connection 8123 to db: 'appdb' user: 'appuser' host: '10.0.0.20' (Too many connections)

    12 is the internal thread id; 8123 is the connection id; the parentheses hold the reason. This warning appears when the server drops a new client because max_connections is already used.

    5.5 Sigma rules and Splunk SPL

    Sigma is an open rule format for log detections; any SIEM (central log platform) that supports Sigma can run these rules. SPL is the Splunk search language. Each of the eight threats below has one Sigma rule and one matching SPL query, plus one support rule that correlates timeout waves across the slow attacks. Together they implement the official detection strategy DET0173 on common logs. Every rule was reviewed for false positives and tuned to stay quiet until real exhaustion appears. Copy, adjust the field names to your environment, and test in a lab first. All YAML blocks use spaces, never tabs.

    Threat 1 — Slow HTTP headers (slowloris class)

    sigma — nginx worker exhaustion
    title: Nginx Worker Connection Exhaustion Alert
id: 6f92ef76-3581-45eb-8a71-b8d695d1a0b4
status: stable
description: Detects the nginx alert that appears when a worker runs out of
    connection slots. Slow-header or connection floods hold every socket open
    until this message appears (MITRE ATT&CK T1499.002).
references:
  - https://attack.mitre.org/techniques/T1499/002/
author: Detection Engineering
date: 2025-03-12
logsource:
  product: nginx
  service: error
detection:
  selection:
    message|contains: 'worker_connections are not enough'
  condition: selection
fields:
  - pid
  - connection_id
  - client
falsepositives:
  - A legitimate traffic spike that fills all worker slots.
  - A worker_connections value set far below real demand.
level: high
tags:
  - attack.impact
  - attack.t1499.002
    spl — same logic for Splunk
    index=web sourcetype=nginx:error "worker_connections are not enough"
| stats count AS exhaustion_events, values(client) AS clients, earliest(_time) AS first_seen, latest(_time) AS last_seen BY host
    • Field mapping: Sigma message maps to the Splunk raw event (_raw); client maps to the extracted client field.
    • Assumptions: index=web, sourcetype=nginx:error — rename for your environment.
    • False positives: real demand spikes; capacity too small by design.
    • Tuning: alert only when the message repeats twice within 5 minutes, and join with the timeout wave support rule.
    • Severity: high — the message means the service already stopped serving some clients.

    Support rule — timeout wave per source (supports Threats 1 and 2)

    sigma — 408 and 499 wave from one source
    title: Nginx Slow Client Timeout Wave From One Source
id: 73a05adf-bb07-4ee3-8a26-8cf13fe66615
status: experimental
description: Counts HTTP 408 (client too slow) and 499 (client gave up)

fields:

    • Field mapping: Sigma client_ip maps to the Splunk client_ip extraction; status maps to status.

    Real-world case study

    The documented history of the slowloris tool, then a clearly labeled representative scenario that shows how a full response plays out.

    The documented anchor: slowloris, June 2009

    In June 2009, the researcher known as RSnake (Robert Hansen) published slowloris on his website ha.ckers.org. The tool sent partial HTTP headers and held web server workers open with almost no bandwidth. The release post explained that classic detection methods and many firewalls would miss it. The attack looks like a crowd of very slow clients, not like a flood. Security journalists and bloggers widely covered the release, and server administrators around the world could suddenly test the weakness themselves.

    Slowloris was then used in the wild in a politically visible way. During the 2009 Iranian election protests, activists used slowloris against Iranian government websites. Press and security-blog reporting at the time documented that the tool was chosen partly because it produced little network noise and could be run by individuals with limited resources. Slowloris is widely treated as the classic service-exhaustion tool, because it exhausts the web server's own worker capacity rather than the operating system or the network pipe. That is exactly the mechanism this sub-technique describes.

    What the team did right, and what it cost

    Response

    Attack chain and detection point

    The chain was short: a single host, a slow-POST flood, worker exhaustion, and a database pool emptied from behind. The decisive detection point was the combination of two cheap signals: a per-source timeout wave and the Apache worker saturation line. Neither signal alone was as convincing.

    Response

    Containment and eradication

    Containment happened at the edge, not on the origin: the WAF rule and the firewall block removed the load before workers were touched. Eradication was simple because the attack left no foothold: nothing to remove, only a source to keep blocked.

    Response

    Recovery and impact

    Recovery was quick once the source was gone: workers drained in minutes. Total degraded time was about 38 minutes, with checkout errors for part of it. No data was lost. The main cost was engineering time and a handful of failed customer transactions.

    Response

    Communication and lessons

    Support received one clear message instead of guesswork: "checkout may be slow, engineers are on it". Lessons learned: keep error logs in the SIEM with low delay, alert on per-source concurrency, shorten request timeouts by default, and keep a one-page runbook so the first responder does not improvise.

    Mitigation and defense

    Controls that stop service exhaustion floods, from quick server settings to organization-wide policy, plus simple advice for small setups.

    Policy

    Runbook and ownership

    Write a one-page response runbook: who decides to block, who calls the provider, what to measure. Assign an owner for the WAF and proxy configuration. Rehearse the runbook quarterly with a short tabletop, and run a full load-test drill twice a year.

    Web server

    Short timeouts and limits

    nginx: set client_header_timeout (default wait for headers) and send_timeout to 10–15 seconds, and use limit_req plus limit_conn for per-source rates and connection counts. Apache: enable mod_reqtimeout with RequestReadTimeout so slow headers and slow bodies are cut off automatically.

    Endpoint

    Server hardening

    Keep web and TLS stacks patched. Size worker pools against available RAM instead of raising them blindly. Cap per-source keep-alive sessions (nginx keepalive_requests, Apache KeepAliveTimeout kept short), and set request-body limits on upload endpoints. Export worker, queue, and connection metrics from the server itself.

    TLS

    Disable renegotiation where feasible

    TLS 1.3 removed renegotiation, so preferring TLS 1.3 closes the pattern outright. On TLS 1.2 endpoints, disable client-initiated renegotiation (for example OpenSSL's SSL_OP_NO_RENEGOTIATION option, the renegotiation limits in HAProxy or F5, or the platform's equivalent setting). Verify each service with the openssl check in section 3 and record the result.

    Network

    Filter upstream (M1037)

    Put a CDN (content delivery network) or DDoS protection provider in front of origins, and block attacking sources at the edge firewall, not only on the server. Use a reverse proxy so slow clients never reach the application workers.

    WAF

    Slow-attack rules

    Enable the WAF rule groups for slowloris and slow-POST patterns, and cap request duration and body rate per source. Test the rules with your own lab load tests before you rely on them.

    Cloud

    Provider protection and quotas

    Turn on the cloud provider's DoS protection (for example the managed edge protection on major clouds), set autoscaling maxima, and know the billing effect of a flood before an incident starts.

    Identity

    Protect the directory

    Keep LDAP ports off the internet, require authenticated binds, firewall domain controllers to expected client ranges, and monitor bind counts per source as in rule 7.

    Logging

    Ship error logs fast

    Send web, DNS, and database error logs to the SIEM within seconds. Keep access-log timing fields (request time, upstream time) enabled; the detections in section 5 need them.

    Monitoring

    Per-source baselines

    Dashboard concurrent connections and request rates per source, plus worker usage and queue depth. Alert on deviations from the baseline, not on fixed magic numbers alone.

    Backup and response

    Assume downtime will happen

    Backups do not stop floods, but tested recovery and a status page keep the business running during one. Define the incident roles before the incident.

    Good practice — Home and small office

    Do not run web, DNS, or mail services directly on your home or small-office connection. If you must: hide them behind a reverse proxy with short timeouts, enable the router's built-in flood protection, keep the default connection limits, and turn off port forwarding you do not need. For anything important, use a small cloud server or a provider with DDoS protection instead of exposing your own box.

    Common mistakes and best practices

    Eleven concrete blue-team mistakes around this technique, each with symptom, root cause, fix, and prevention. Then the habits that keep detections healthy.

    1. Treating every 408 as an attack

    Symptom: constant alerts about timeout statuses.

    Root cause: 408 also happens when a mobile user walks into an elevator; the status alone is not an attack.

    Fix: require volume (many timeouts from one source in a window) before alerting.

    Prevention: baseline first, then set thresholds from data.

    2. One giant alert, then alert fatigue

    Symptom: responders ignore the DoS alert channel.

    Root cause: a single high-volume rule with no severity tiers fires all day.

    Fix: split into information (trend), warning (wave), and critical (saturation message) tiers.

    Prevention: review alert noise weekly and prune.

    3. Error logs never shipped to the SIEM

    Symptom: the first place you learn of exhaustion is a user complaint.

    Root cause: only access logs were onboarded; the error log holds the exhaustion messages.

    Fix: ship nginx, Apache, DNS, and database error logs with low delay.

    Prevention: add "error logs in SIEM" to every new service checklist.

    4. Timeouts left at unsafe defaults

    Symptom: a few dozen connections take the service down.

    Root cause: header or body timeouts of minutes let one slow client park a worker for a long time.

    Fix: set 10–20 second read timeouts as in section 7.

    Prevention: include timeout review in server build standards.

    5. Rate limits on the wrong scope

    Symptom: limits pass lab tests, but a real flood still saturates the service.

    Root cause: the limit is per worker or global, not per source address.

    Fix: apply limit_conn / limit_req per source, and per source behind the proxy use the real client header only when you trust it.

    Prevention: test limits with many connections from one lab address.

    6. No owner for the WAF and proxy config

    Symptom: slow-attack rules are off, and nobody knows why.

    Root cause: the WAF console has no named owner, so changes stall.

    Fix: assign an owner and a change process; document the rule set.

    Prevention: quarterly review of WAF coverage against this technique.

    7. Blocking only at the origin

    Symptom: the attack returns from new addresses and workers keep filling.

    Root cause: blocks applied on the origin server, after the proxy already opened connections to it.

    Fix: block upstream (edge, CDN, firewall) so the origin never sees the traffic.

    Prevention: keep the edge blocklist as the documented first step.

    8. Only raising the worker limit

    Symptom: the server runs out of memory instead of workers.

    Root cause: "fix" means doubling MaxRequestWorkers without checking RAM per worker.

    Fix: size limits against memory, and keep short timeouts as the real control.

    Prevention: capacity math documented for every profile change.

    9. No capacity testing before big events

    Symptom: a product launch or election-night traffic looks exactly like an attack.

    Root cause: limits and baselines were never exercised.

    Fix: run staged load tests; record the worker and connection profiles they produce.

    Prevention: schedule tests twice a year and before major launches.

    10. No runbook, so responders improvise

    Symptom: the first responder spends the incident deciding who may block what.

    Root cause: no documented decision path or contact list.

    Fix: write the one-page runbook from section 7 and rehearse it.

    Prevention: include a DoS scenario in yearly incident exercises.

    11. No TLS handshake or renegotiation visibility

    Symptom: a renegotiation flood or handshake storm is invisible, and the team blames "mysterious CPU load" on the TLS endpoint.

    Root cause: only web access logs are collected; no Zeek, Suricata, WAF, or load balancer TLS counters exist.

    Fix: enable TLS logging (Zeek ssl.log, Suricata TLS, or WAF handshake metrics) and deploy rule 6 from section 5.5.

    Prevention: add TLS handshake visibility to the same service onboarding checklist that covers error logs.

    Habits that keep detections healthy

    Daily

    Check the pulse

    Review worker usage, timeout waves, and per-source connection trends for the last 24 hours. One glance at the dashboard is enough when the baselines exist.

    Weekly

    Prune noise

    Read the week's false positives, tune thresholds, and confirm error logs still arrive from every web and DNS server. Retire alerts that fired only on noise.

    Monthly

    Rehearse and update

    Run one rule in a test search, re-read the MITRE page for updates, and check the WAF and proxy configs still match section 7. Update the runbook if people changed roles.
