OS Exhaustion Flood T1499.001

This guide explains how a flood can fill the small queues inside an operating system until real users cannot connect. It is written for beginners who build defenses. Every command here is labeled for a lab only: use isolated machines that you own.

  • Tactic: Impact
  • Parent: T1499 Endpoint Denial of Service
  • Platforms: Linux · Windows · macOS
  • Primary target: OS connection and state limits
  • Created: 20 February 2020 · ATT&CK v20 · Last modified: 24 October 2025
  • Technique revision: 1.2
  • Guide v2.0

Attack cost: low

The attacker needs no account and no software on the target. Fake packets are enough, so there is nothing to log in and nothing to steal first.

Key evidence: kernel messages + firewall counters

The kernel reports queue pressure. Firewalls count dropped packets. Together they confirm a flood quickly.

Signature artifact: a kernel log line

The message Possible SYN flooding appears when the half-open queue overflows and SYN cookies start.

Core control: SYN cookies + upstream scrubbing

SYN cookies answer handshakes without using queue slots. Scrubbing services filter the flood before it reaches you.

Contents

1

Overview

An OS exhaustion flood attacks the operating system itself, not one program. The attacker sends a large stream of packets that the kernel must track, until the small queues inside the kernel are full.

1.1What the technique is

The kernel is the core of an operating system. It manages memory, the processor, and the network card. To handle network traffic, the kernel keeps small tables and queues with strict size limits. A flood is a stream of packets sent far faster than normal. An OS exhaustion flood fills those queues so new, honest traffic is refused.

MITRE ATT&CK describes this technique as a denial of service (DoS) attack against an endpoint's operating system. The attack does not need to use up real memory or processor power. It only needs to fill the limits the kernel sets for itself.

1.2The main flood types

The official ATT&CK description names two TCP state-exhaustion patterns for this technique: SYN floods and ACK floods. The first two cards cover them. The rest of the cards cover related floods that pressure the same kernel limits.

SYN flood

TCP is the protocol behind most internet connections. A TCP connection starts with a three-way handshake: the client sends a SYN packet, the server answers with SYN-ACK, and the client finishes with ACK.

In a SYN flood, the attacker sends many SYN packets and never sends the final ACK. Each unfinished handshake holds a slot in the kernel's SYN backlog, a small queue for half-open connections. When all slots are taken, new connections are refused. This is a half-open connection: started, never completed.

ACK flood (second official pattern)

A stateful firewall or the kernel itself keeps a state table: the list of established connections. An ACK flood sends ACK packets for connections that do not exist. Each packet forces the kernel to search its state table and confirm that no match exists. Millions of pointless searches burn processor time, so the server becomes sluggish or unresponsive. SYN cookies cannot stop this, because no handshake queue was ever used.

ICMP flood (ping flood)

ICMP is a support protocol used for status messages. A ping is an ICMP echo request that asks "are you there?". A ping flood sends echo requests at a very high rate. The kernel must read each packet and send answers, which costs processor time and kernel buffers.

UDP flood against closed ports

UDP is a connectionless protocol used by DNS (the name-lookup service) and video calls. When a UDP packet arrives at a port (a numbered door for network services) that nothing is listening on, the kernel answers with an ICMP "port unreachable" message. A UDP flood against closed ports forces the kernel to send thousands of such answers.

Connection-state table exhaustion

On Linux, conntrack is a kernel feature that tracks every connection through the firewall. Its table has a fixed maximum. When it is full, the kernel drops new packets. One line in the kernel log says it plainly: nf_conntrack: table full, dropping packet.

Fragmentation and ARP pressure

Large packets can be split into fragments that the kernel must reassemble. A flood of crafted fragments makes the kernel waste memory on reassembly. On a local network, an ARP flood (ARP maps IP addresses to hardware addresses) overflows the small kernel table that stores those mappings.

1.3Why it matters

Availability is a security goal, just like secrecy. If customers cannot connect, the service is effectively down even though every file and database is untouched. These attacks are also cheap. The attacker needs no password, no software on the target, and often no real address, because source addresses can be spoofed (forged). An attack from many machines at once is a DDoS: a distributed denial of service.

2.1Written story (text alternative)

  1. Normal traffic. A real client sends SYN, the server answers SYN-ACK, the client returns ACK. One backlog slot is used for a moment, then freed. The service stays healthy.
  2. The first fake SYN. The attacker sends one SYN with a forged source address, shown with a "?" badge. The address belongs to nobody who will ever reply.
  3. A slot is held. The server places the half-open handshake in a SYN_RECV slot and retransmits SYN-ACK several times, waiting for an answer that never comes.
  4. The queue fills. More fake SYNs arrive. Slots fill one by one until the backlog is full.
  5. A real client is refused. A legitimate client sends SYN. The kernel has no free slot, so it drops the packet. The drop counter climbs.
  6. The SOC sees it. The kernel log shows Possible SYN flooding on port 443. Sending cookies. Firewall flood counters rise at the same time.
  7. The defender turns on SYN cookies. With net.ipv4.tcp_syncookies=1, the kernel answers each SYN with a cookie encoded in the reply, so no queue slot is needed.
  8. Balance returns. Fake SYNs never complete, so they die out. The legitimate client completes its handshake, and the queue stays healthy.
  9. A second pattern: bare ACKs. The attacker now sends ACK packets with no handshake behind them. Each packet claims to belong to an established connection, and no connection does.
  10. State-table pressure, then the filter. For every unknown ACK, the OS searches its whole connection state table and finds no match. At flood scale the processor burns on searches while useful work stays flat. The defender rate-limits bare ACKs upstream, and the load falls.
Note

This picture is a teaching model. Real hosts tune many queue sizes at once, and real floods often come from thousands of machines. The behavior shown here still matches what defenders see in kernel logs.

3

Red team perspective

This section explains how attackers think about OS exhaustion, so you can predict and detect it. Everything practical here is restricted to a lab you own.

3.1Why an attacker picks this technique

No foothold needed

There is no login, no malware, and no stolen account. Packets from outside are enough. That removes most of the attacker's risk of being identified through an intrusion.

Cheap to scale

A single laptop can fill a small server's backlog. With a botnet (many hijacked devices acting together), the same method reaches data-center scale. This is why OS floods are common in DDoS-for-hire services.

Hard to trace

SYN floods usually use spoofed source addresses chosen at random. The target replies into the void. Attribution of the real sender is difficult without help from network operators.

3.2Conceptual flow of a SYN flood

  1. Step 1The attacker picks a TCP service that must stay open, often a web port such as 443.
  2. Step 2The attacker generates SYN packets with random fake source IPs. Random sources defeat simple "block one address" filters.
  3. Step 3The target kernel allocates a half-open slot and sends SYN-ACK. The fake source never answers, so the slot waits through several retransmissions.
  4. Step 4Thousands of half-open handshakes fill the backlog. New SYNs, including real ones, are dropped.
  5. Step 5The attacker keeps the pressure on with a steady rate. The service stays unavailable for as long as the flood continues.

An ICMP flood follows the same shape but simpler: a steady stream of echo requests, each consuming kernel time and buffer space. The next subsection shows the ACK flood, which attacks the state table instead of the backlog.

3.3Conceptual flow of an ACK flood

ACK floods are the second pattern the official ATT&CK description names for this technique. They do not fill the SYN backlog. They attack the state table: the kernel's list of established connections. A bare ACK packet claims to belong to a live session. No such session exists, so the kernel has to prove that before it can discard the packet.

  1. Step 1The attacker sends ACK packets to an open TCP port, without any handshake first.
  2. Step 2Each packet claims to belong to an established connection. The kernel must check that claim against its state table.
  3. Step 3No entry matches, so the kernel searches the entire table before dropping the packet.
  4. Step 4At flood scale, millions of fruitless searches consume processor time. The host becomes sluggish and may stop responding.
  5. Step 5SYN cookies do not help, because no queue slot was ever used. The fix is filtering bare ACKs upstream or rate-limiting them at the edge.

Defenders recognize this pattern by host CPU that climbs with the packet rate while useful traffic stays flat, plus firewall connection-limit warnings. Section 4 shows the artifacts, and section 5 adds the matching rules.

3.4Prerequisites and conditions

  • A reachable TCP or ICMP surface on the target, often a public service port.
  • Default or weakly tuned kernel queue sizes on the target.
  • No upstream scrubbing or rate limiting between attacker and target.
  • Either the ability to spoof source addresses (some networks allow it) or many machines, such as a botnet.
  • For ACK floods, any stateful filter or the kernel's own state table is enough to attack; the queue settings on the target do not matter.
Danger - Lab only

Use network attack tools only against isolated machines you own, on a disconnected lab network. Launching these techniques against any system you do not own is a crime in most countries. That includes the US Computer Fraud and Abuse Act and the Council of Europe Cybercrime Convention. The examples below target 10.0.0.10, a private lab address, and lab.local, a name that only exists inside a lab.

# Lab only: observe the SYN backlog settings on YOUR lab server (Linux)
sysctl net.ipv4.tcp_max_syn_backlog
sysctl net.ipv4.tcp_syncookies

# Lab only: generate half-open SYNs against your own lab host 10.0.0.10
hping3 -S -p 443 --flood 10.0.0.10

# Lab only: slower variant so you can watch each retransmission
sudo hping3 -S -p 443 -i u20000 10.0.0.10

# Lab only: ping flood on YOUR OWN lab network, never a shared one
sudo ping -f -s 1200 10.0.0.10

# Lab only: watch the evidence appear on the target
journalctl -k | grep -i "SYN flooding"
nstat -az | grep -E 'ListenDrops|ListenOverflows|SyncookiesSent'

hping3 is a packet-crafting tool. ping -f sends echo requests as fast as the network allows. Both exist for testing, and both are safe to study in a lab with two virtual machines.

3.5Common variations

ACK and RST floods

Packets that claim a connection exists. The kernel burns time searching its state table for matches that are not there. Section 3.3 shows the flow.

ICMP and UDP floods

Echo requests and packets to closed ports make the kernel read and answer every packet. Kernels rate-limit these replies, so raw volume decides the harm.

Randomized ports and sources

Changing the destination port and source address every packet frustrates simple filters and spreads pressure across many queues.

Fragmented packets

Sending many small fragments forces the kernel to hold them and reassemble, pressuring memory on older stacks.

ARP flood on the local segment

A storm of ARP broadcasts overflows the small table that maps IP addresses to hardware addresses, cutting off local machines until it drains.

Low-rate versions

Some attackers stay just below obvious rate limits for hours. This is quieter and harder to notice, but it still shows up in ratio statistics.

3.6Common attacker mistakes

  • Using a real source address, which places a traceable address in the target's logs.
  • Running so fast that upstream anti-DDoS systems trigger before your target even feels pressure.
  • Attacking a modern Linux host with default SYN cookies and wondering why nothing happens.
  • Testing cloud-hosted targets, which breaks the provider's terms and often ends the attacker's account.
  • Keeping one rate all day, which makes the flood easy to separate from normal traffic in a graph.
4

Blue team and SOC perspective

A SOC (security operations center) is the team that watches alerts. This section shows what a flood leaves behind and how to triage it fast.

4.1Artifacts a flood leaves

Kernel messages

Linux prints Possible SYN flooding on port 443. Sending cookies. when the half-open queue overflows. A conntrack gateway prints nf_conntrack: table full, dropping packet.. These lines go to the kernel ring buffer (dmesg) and to syslog.

Firewall flood counters

Most firewalls keep counters for drops and rate-limit hits. Cisco ASA logs message 733100 for SYN-flood detection. pfSense and OPNsense count block actions in filterlog. Rising counters without a maintenance window are a strong signal.

Flow anomalies

A flow record summarizes a connection: source, destination, ports, packets. Zeek's conn.log and NetFlow (router flow records) show many connections stuck in state S0 (SYN seen, no reply) from many sources, or one source with a huge SYN count.

ACK floods and state-table pressure

An ACK flood leaves no half-open queue trail. What shows up instead: many connections with no state (Zeek conn_state OTH or RSTRH). You also see firewall connection-limit and state-table warnings, plus host CPU that climbs with the packet rate while useful traffic stays flat.

Service symptoms

Health checks fail while the host itself stays reachable on other ports. Load balancers mark backends down. Users see timeouts, not error pages.

Official ATT&CK detection mapping

ATT&CK groups its official detections for this technique under strategy DET0356, "Endpoint DoS via OS Exhaustion Flood Detection Strategy". It has three analytics. AN1012: a burst of incomplete TCP handshakes, such as SYN floods, or uncorrelated ACK packets targeting the state table, resulting in OS resource exhaustion. AN1013: a flood of spoofed SYN or ACK packets that exhausts the OS TCP state table, potentially via user-space utilities or kernel-level DoS agents. AN1014: an adversary tool or script issuing mass SYN and ACK floods that degrade OS responsiveness and interrupt service response on macOS endpoints. The rules in section 5.5 put these ideas into practice.

4.2Where to look, in order

  1. On the hostjournalctl -k or dmesg for kernel messages; nstat -az for ListenOverflows, ListenDrops, and SyncookiesSent.
  2. On the firewallDrop counters and rate-limit logs; on Cisco ASA, syslog 733100; on OPNsense, filterlog volume per source. Also check connection-limit and state-table warnings, which matter for ACK floods.
  3. In flow dataZeek or NetFlow: SYN-to-SYN-ACK ratio, new-connections-per-second per source, the share of connections stuck in S0, and the share with no state at all (OTH).
  4. UpstreamYour provider's or CDN's (content delivery network) traffic graphs and their DDoS mitigation status. Many floods are best confirmed and filtered there.

4.3Why it matters to defenders

Endpoint DoS attacks the availability goal directly. It can also act as a smokescreen: a loud flood that keeps the SOC busy while a quieter intrusion happens elsewhere. Treating every flood as only a network event risks missing that. Finally, floods are a common extortion tool, so early detection gives management time to decide on communication before the ransom note arrives.

4.4Triage flow for a suspected flood

  1. Minute 0-5Confirm scope: which host, which port, since when. Check the kernel message and ListenOverflows on the affected host.
  2. Minute 5-15Confirm the shape: flow data should show many half-open SYNs. Rule out a planned load test by checking the change calendar.
  3. Minute 15-30Apply fast mitigations: verify SYN cookies are on, raise the backlog only if memory allows, and enable the provider's scrubbing or rate limit.
  4. Hour 1Communicate: tell the service owner, management, and if extortion is involved, follow the incident response plan. Preserve evidence: export counters and logs before they rotate.
  5. AfterReview: write the incident record, tune the detections in section 5, and schedule a tabletop exercise.
Good practice

Snapshot the counters before and after any change you make. Counter values are short-lived evidence, and auditors ask for them.

5.2Threat intelligence

Threat intelligence answers "who does this, and how?". For OS exhaustion floods, the useful question is which actors have the infrastructure and motive to run them. One official example already anchors the pattern: MITRE ATT&CK's parent technique T1499 lists the ZxShell tool (S0412) with a feature to perform SYN flood attacks on a host.

  • MITRE ATT&CK group and software pages for actor tooling context.
  • CISA and FBI joint alerts for botnet takedowns and current advisories.
  • Vendor reports (CDN and DDoS-mitigation providers publish quarterly trend data).
  • Commercial threat feeds for current botnet, booter, and extortion trends.
  • ISACs (information sharing and analysis centers): MS-ISAC for state and local government, FS-ISAC for finance, H-ISAC for health.
  • Open sources such as news coverage of incidents and researcher write-ups.

DescriptionCrafted fragment streams force the kernel to hold and reassemble packets, spending memory on junk.

DescriptionA storm of ARP requests overflows the kernel neighbor table so local machines cannot resolve each other's addresses.

Rating rationaleRated high because appliances guard the network edge, and their failure removes your mitigation options.

5.4Logs and patterns

For each threat: where to look, which fields matter, what normal looks like, what suspicious looks like, and the detection logic behind it. The first two cards cover the two official patterns. ATT&CK analytics AN1012 and AN1013 describe exactly these: incomplete handshakes, and uncorrelated ACK packets against the state table.

Critical T1. TCP SYN flood

Log sourcesLinux kernel ring buffer via syslog or the journal; firewall counters; Zeek conn.log; load balancer logs.

Key fieldsmessage (kernel text), host, id.orig_h (source IP), id.resp_h (destination IP), id.resp_p (destination port), proto, conn_state (how the connection ended), ListenOverflows, SyncookiesSent.

Normal behaviorMost TCP connections reach state SF (success) or close cleanly. Kernel messages about SYN flooding never appear. SyncookiesSent stays at zero or barely moves.

Suspicious behaviorMany sources send SYNs that never finish; the share of connections stuck in S0 (SYN seen, no reply) jumps; the kernel prints the SYN flooding message; drop counters climb.

Detection logic

  • Alert when the kernel message Possible SYN flooding appears for any host.
  • Alert when one source produces more than 100 connections per minute that all end in S0 or REJ.
  • Alert when ListenOverflows or ListenDrops increases between two samples of nstat.
Log - Linux kernel (syslog)
TCP: request_sock_TCP: Possible SYN flooding on port 443. Sending cookies. Check SNMP counters.

Field meanings: request_sock_TCP names the kernel structure that holds half-open requests; port 443 is the flooded service; Sending cookies means SYN cookies just activated; SNMP counters (SNMP is the standard protocol for reading device counters) points to statistics that confirm the drop volume.

High T2. TCP ACK flood

Log sourcesZeek conn.log (connection-state anomalies); Suricata eve.json stream and state alerts; firewall DoS-policy and connection-limit logs (for example FortiGate tcp_ack_flood anomaly logs or Cisco ASA 733100-family threat-detection messages); host performance metrics for CPU.

Key fieldsid.orig_h (source IP), id.resp_h (destination IP), id.resp_p (destination port), proto, conn_state (how the connection ended), event_type, signature, plus cpu.util-style host metrics and packets-per-second counters.

Normal behaviorAlmost all ACK packets belong to sessions Zeek watched from the start, so conn_state is SF or a clean close. Host CPU tracks the useful traffic volume.

Suspicious behaviorA burst of bare ACKs with no session behind them. Zeek logs OTH (midstream packets with no known state) or RSTRH (a reset for a session Zeek never saw start) at high rate from one or many sources. The firewall warns about connection limits or its state table. CPU rises while throughput stays flat.

Detection logic

  • Alert when one source produces more than 200 connections per minute with conn_state OTH or RSTRH.
  • Alert on any firewall connection-limit or state-table exhaustion message, and on DoS-policy logs naming tcp_ack_flood.
  • Correlate: alert when the packet rate multiplies by ten while useful throughput and session counts stay flat (the CPU-versus-packets signature).
Log - Zeek conn.log (bare ACKs, no state)
1739482301.774510    Cb1xK9tR2mQzL4VwA       198.51.100.7    47011   10.0.0.10       443     tcp     -       0.001   60      0       OTH     F       0       1       60      0       0       -

Field meanings: the timestamp; the connection ID; 198.51.100.7:47011 is the source; 10.0.0.10:443 the destination; OTH means Zeek saw midstream packets with no handshake and no state; a single 60-byte packet went upstream and nothing came back. Thousands of rows like this, one per source packet, are the ACK-flood fingerprint.

Log - firewall DoS policy (illustrative shape)
date=2026-02-11 time=14:22:31 logid="010103994301" subtype="dos" level="alert" attack="tcp_ack_flood" srcip=198.51.100.7 dstip=10.0.0.10 dstport=443 action="clear_session"

Vendor field names differ. FortiGate logs a dos-subtype record with attack="tcp_ack_flood"; Cisco ASA emits 733100-family threat-detection messages; pf-family firewalls warn when their state table fills. Treat any of these as the firewall counterpart to the Zeek signal. (This line is an illustrative sample shaped like real output.)

High T3. Linux conntrack table exhaustion

Log sourcesKernel log of the gateway host (dmesg, journal, syslog); firewall metrics exporters.

Key fieldsmessage, host, plus the exported metric nf_conntrack_count (entries in use) against nf_conntrack_max (table limit).

Normal behaviornf_conntrack_count sits far below the maximum and returns to baseline after traffic spikes.

Suspicious behaviorThe count hugs the maximum for minutes, then the kernel logs the table-full message and drops packets of every kind.

Detection logic

  • Alert on the exact kernel text nf_conntrack: table full, dropping packet.
  • Alert when nf_conntrack_count stays above 85 percent of nf_conntrack_max for five minutes.
  • Correlate with a rise of new connections from few or random sources.
Log - Linux kernel (dmesg)
[ 88123.456789] nf_conntrack: table full, dropping packet.

Field meanings: 88123.456789 is seconds since the kernel started; the rest names the subsystem (nf_conntrack), the condition (table full), and the action (dropping packet). One line can mean thousands of silent drops.

Medium T4. UDP / ICMP flood against the host stack

Log sourcesFirewall drop logs such as OPNsense filterlog; kernel counters (IcmpOutDestUnreachs, IcmpInEchos via nstat or SNMP); IDS (intrusion detection system) alerts.

Key fieldsaction (allow or block), proto (protocol number, 1 for ICMP, 17 for UDP), src_ip, dst_ip, dst_port, and the counters above.

Normal behaviorICMP traffic is a thin trickle of diagnostics. UDP drops come from known scanners in small numbers.

Suspicious behaviorThousands of UDP packets to closed or unused ports per second; ICMP unreachable replies leaving the host at maximum rate; the kernel starts suppressing its own log messages.

Detection logic

  • Alert when blocked UDP or ICMP packets from one source exceed 1000 per minute.
  • Alert when IcmpOutDestUnreachs jumps by more than 10 times its hourly baseline.
  • Treat a burst of net_ratelimit kernel lines as a flood indicator, not noise.
Log - OPNsense filterlog (blocked UDP storm)
Sep 14 02:11:09 fw filterlog[54321]: 5,,,1000000103,em0,match,block,in,4,0x0,,64,54321,none,17,udp,60,198.51.100.7,10.0.0.10,39000,53,

Field meanings: block is the action; in the direction; 17 the protocol number for UDP; udp repeats it in words; 198.51.100.7,39000 is the source, 10.0.0.10,53 the destination. Port 53 here is DNS, a favorite target of UDP floods.

Medium T5. IP fragmentation flood

Log sourcesIDS alerts (Suricata eve.json); firewall fragment counters; kernel statistics for reassembly failures.

Key fieldsevent_type, signature (the rule name that fired), src_ip, dest_ip, proto, and firewall counters such as IpFragOKs, IpFragFails, IpFragCreates.

Normal behaviorFragmented traffic is rare on healthy internal networks, mostly limited to specific tunnels and some DNS over UDP setups.

Suspicious behaviorStreams of fragments with strange offsets or overlaps; a jump in IpFragFails; IDS decoder alerts for malformed fragments.

Detection logic

  • Alert on IDS decoder or signature alerts whose names contain fragment or flood.
  • Alert when IpFragFails rises by more than 50 events in five minutes.
  • Correlate fragment alerts with a drop in service health on the same destination.
Log - Suricata eve.json (illustrative sample)
{"timestamp":"2026-03-14T02:11:09.123456+0000","flow_id":2213367890123,"event_type":"alert","src_ip":"198.51.100.7","src_port":0,"dest_ip":"10.0.0.10","dest_port":0,"proto":"IPv4","alert":{"signature_id":2200073,"signature":"SURICATA IPv4 fragmented invalid offset","category":"decoder_event","severity":3},"in_iface":"em0"}

Field meanings: event_type: alert marks an IDS event; signature is the rule that fired, here a decoder event about an invalid fragment offset; severity: 3 is the IDS rating. The values are an illustrative sample shaped like real output.

Medium T6. ARP flood on the local segment

Log sourcesKernel log on Linux hosts (neighbour messages); arpwatch-style tools; switch logs for port security events.

Key fieldsmessage, host, and for dedicated ARP tools: IP, old MAC, new MAC, interface.

Normal behaviorThe kernel neighbor table holds a stable list of local devices and rarely logs anything.

Suspicious behaviorThe table hits its limit (gc_thresh3, the third and largest neighbor-table limit); the kernel logs neighbor table overflow; an ARP watcher reports one address flapping between many hardware addresses.

Detection logic

  • Alert on the kernel text neighbor table overflow or arp_cache overflow messages.
  • Alert when one switch port emits more than 500 ARP packets per minute.
  • Alert when arpwatch reports a single IP behind more than 5 hardware addresses in one hour.
Log - Linux kernel (neighbour subsystem)
[ 99881.204317] neighbour: arp_cache: neighbor table overflow!

Field meanings: neighbour is the kernel subsystem that maps IP addresses to hardware (MAC) addresses; arp_cache is that mapping table; overflow means new entries were refused, so local communication fails.

High T7. Half-open flood against appliances and embedded devices

Log sourcesAppliance syslog (Cisco ASA, firewalls, load balancers); filterlog on pfSense and OPNsense; vendor health dashboards.

Key fieldsevent_id or message class (for example ASA 733100), host (the appliance), action, src_ip, dst_ip, dst_port, connection counters.

Normal behaviorAppliance connection tables sit at a small fraction of capacity; flood-detection messages never appear.

Suspicious behaviorFlood-detection messages; management interface latency; the appliance starts flushing connections or failing health checks.

Detection logic

  • Alert on vendor flood messages such as ASA 733100 with a SYN-flood reason.
  • Alert when any appliance's established-connection count nears its licensed or configured maximum.
  • Alert when the appliance's own health checks begin to fail while upstream traffic continues.
Log - Cisco ASA (flood detection)
%ASA-4-733100: [0x2b1f4f9d] drop Rate-1) ... TCP SYN-flood: 512 half-open connections in 1 second.

Field meanings: %ASA-4 is severity 4 (warning); 733100 is the message class for threat detection; the bracketed value identifies the triggering rate object; the text names the flood type and the measured burst.

6

Real-world case study

Two stories: the documented 1996 Panix SYN flood that started this whole field, and a clearly labeled representative scenario built from public incident reports.

6.1Historical anchor: the Panix SYN flood, September 1996

This is a documented public incident. On 6 September 1996, an attacker flooded Panix, a New York internet provider, with TCP SYN packets carrying fake source addresses. Panix's mail, name, and web servers filled their half-open queues and stopped accepting connections. The attack continued for about a week and made national news. The attacker was never publicly identified.

  1. 6 September 1996The flood begins. Panix staff see servers stop answering while the machines themselves stay up. No public playbook for SYN floods exists yet.
  2. Following daysEngineers across the internet community analyze the packets and confirm the half-open mechanism.
  3. 23 September 1996CERT releases Advisory CA-1996.21, TCP SYN Flooding and IP Spoofing Attacks, which describes the attack and short-term defenses.
  4. September 1996Daniel J. Bernstein describes SYN cookies in the same month: encode the connection state inside the SYN-ACK itself, so the kernel needs no half-open queue at all. Vendors ship filters and tuning guidance over the following years; Linux added SYN cookies in 1997.
  5. LegacySYN cookies, backlog tuning, and upstream filtering all trace back to this period. The kernel message on your Linux host today still mentions "SYN flooding" because of it.
Note

Exact dates and figures vary slightly between press reports. The mechanism, the duration, and the CERT advisory are well documented; the attacker's identity is not.

6.3Lessons from both stories

Detection point

In both cases the kernel spoke first. A cheap alert on one kernel log line would have cut minutes off the 1996 confusion and the composite response.

Containment

The fastest wins were upstream: provider scrubbing and rate limits. Fighting the flood at the target host alone rarely works.

Eradication and recovery

There is no malware to remove. Recovery means restoring healthy traffic patterns, verifying counters, and watching for the attacker's next move.

Communication

Service owners, support teams, and management need updates on a fixed schedule, even when nothing has changed. Silence creates its own incident.

7

Mitigation and defense

MITRE lists one mapped mitigation for this technique: M1037, Filter Network Traffic, including SYN cookies. This section turns that into concrete, verifiable controls per layer.

7.1Controls by layer

Policy and process

Write a DoS runbook with an escalation matrix that names the ISP (internet service provider) and provider contacts. Test it quarterly with a short tabletop exercise. Record every change you make during an incident.

Identity

Identity controls do not stop packets, but they protect the incident itself. Require multi-factor authentication on firewall, cloud, and host management interfaces. Otherwise a flood can be paired with a password guess to take over your defenses.

Endpoint and kernel

Enable SYN cookies and size the queues to your memory budget. Keep hosts patched so fragmentation handling is modern. The sysctl fragment below is a tested starting point for a lab Linux server.

Network

Enable SYN-flood thresholds on firewalls and rate-limit new connections per source. Deploy source address validation at the edge, so spoofed packets die close to their origin; the common form is uRPF (unicast reverse path forwarding), where the router drops packets that arrive by an impossible path. Rate-limit or drop bare ACK packets that match no connection. Prefer scrubbing services over manual IP blocklists.

Cloud and edge

Put public services behind a CDN or the provider's DDoS protection. Scrubbing filters floods upstream, where there is bandwidth to spare. Verify the protection covers every public port, not just HTTP.

Logging and monitoring

Ship kernel logs and firewall counters to a central store that survives host reboots. Alert on the kernel SYN-flooding message, conntrack fullness, and appliance flood detections (section 5.5 has the rules).

Backup and recovery

Floods rarely destroy data, but backups still matter: they let you rebuild an overloaded appliance quickly and recover if the flood hides a destructive follow-up attack.

Response

During an event: enable provider scrubbing first, verify kernel protections second, communicate on a schedule, and export counters as evidence before they rotate.

7.2Kernel settings that matter

Config - /etc/sysctl.d/99-syn-protection.conf (lab Linux host)
# Lab only: test these values on machines you own before production use
# Answer half-open floods without queue slots
net.ipv4.tcp_syncookies = 1
# Half-open queue size: raise only if memory allows
net.ipv4.tcp_max_syn_backlog = 4096
# Fewer SYN-ACK retries releases dead slots faster
net.ipv4.tcp_synack_retries = 2
# Conntrack table sized for a busy gateway
net.netfilter.nf_conntrack_max = 262144
# Shorter half-open timeout in conntrack
net.netfilter.nf_conntrack_tcp_timeout_syn_recv = 30

Apply with sudo sysctl --system, then verify each value with sysctl net.ipv4.tcp_syncookies. Raising the backlog costs memory per slot; measure before and after.

7.3Home and small office

Good practice

Home networks rarely face real SYN floods. The same habits still help. Keep the router firmware updated. Turn off remote management from the internet. Disable services you do not use. Reboot the router if it behaves strangely. If your ISP offers DDoS protection, note the support number before you need it. Never run the lab commands from section 3 on a home router; most consumer devices have tiny connection tables and will simply fall over.

8

Common mistakes and best practices

Twelve mistakes real blue teams make with this technique. Each has a symptom, a root cause, a fix, and a prevention habit.

1. Alerting on every SYN burst

SymptomAlerts fire each morning when offices open and every marketing email goes out.

Root causeStatic thresholds with no baseline.

FixSwitch to ratios (SYN to SYN-ACK) and per-source counts, and compare against the same hour last week.

PreventionRe-baseline thresholds every quarter.

2. Ignoring the kernel message

SymptomThe team dismisses Possible SYN flooding because the service recovered by itself.

Root causeSelf-healing hides recurrence, so a probing attacker is never seen.

FixAlert on the message and count occurrences per host per day.

PreventionTreat any availability log line as an incident candidate.

3. Trusting SYN cookies alone

SymptomCookies are on, yet the gateway still drops traffic during a mixed flood.

Root causeCookies protect the SYN queue, not the conntrack table or an appliance's small connection table.

FixLayer controls: cookies plus conntrack sizing plus upstream scrubbing.

PreventionTest each threat from section 5.3 separately in the lab.

4. Losing kernel logs

SymptomAfter a reboot, the only evidence of the flood is gone.

Root causeThe journal keeps logs in memory by default on many systems.

FixPersist logs: enable persistent journal storage or ship syslog to a central server.

PreventionVerify log retention monthly.

5. Alert fatigue from duplicate rules

SymptomFive alerts page for one flood, and analysts start ignoring all of them.

Root causeKernel, firewall, and IDS rules fire on the same event with no correlation.

FixGroup into one incident and deduplicate by host and time window.

PreventionReview duplicate alerts in the weekly operations meeting.

6. Raising the backlog too far

SymptomThe host survives the flood but runs out of memory and slows down anyway.

Root causeEvery queued slot costs kernel memory; tuning one number without measuring others trades one failure for another.

FixSize the backlog in a lab with realistic memory, then apply.

PreventionRecord before-and-after memory in the runbook.

7. Ownership gaps

SymptomNobody knows who calls the ISP at 02:00, so scrubbing starts three hours late.

Root causeThe runbook has no named roles or phone numbers.

FixAdd an escalation matrix with names, backups, and provider contacts.

PreventionCall-test the contacts twice a year.

8. Untested mitigations

SymptomThe first real flood is also the first time SYN cookies and thresholds are exercised.

Root causeControls exist only in documents.

FixRun a lab test against a machine you own, using the section 3 lab commands, and record results.

PreventionSchedule a capacity test each quarter.

9. Treating DoS as only a network problem

SymptomThe network team mitigates while application and platform teams learn about the outage from users.

Root causeNo shared incident channel.

FixPage both teams; floods often need a change on hosts, firewalls, and the provider at once.

PreventionList all responders in the runbook.

10. Manual IP blocklists at scale

SymptomAnalysts spend the whole incident adding addresses that keep changing.

Root causeSpoofed and rotating sources defeat manual blocking.

FixUse upstream scrubbing and rate limits; keep manual blocks for few, confirmed sources.

PreventionMeasure how many blocks each incident actually needed.

11. False positives from the office network

SymptomThe Zeek SYN-no-reply rule fires for the vulnerability scanner every Tuesday.

Root causeKnown-good scanners were never exempted.

FixAdd an allowlist of scanner addresses with an expiry date.

PreventionKeep the allowlist next to the rule, not in a private notebook.

12. No evidence capture

SymptomCounters were reset by the fix before anyone exported them, so the report has no numbers.

Root causeEvidence capture was not a runbook step.

FixExport counters, kernel logs, and flow samples before changing anything.

PreventionMake "export evidence" step one of the runbook.

8.1Habits that keep you ready

Daily

Review availability alerts and kernel messages. Check that yesterday's thresholds still match today's traffic.

Weekly

Walk the triage flow once with a colleague. Confirm log pipelines from hosts and firewalls are still shipping.

Monthly

Verify kernel settings on a sample of hosts. Review new provider capabilities. Re-tune one rule using fresh data.

9.3Response checklist

  • Confirm scope: which host, which port, since when.
  • Export evidence: counters, kernel logs, flow samples - before changing anything.
  • Check the change calendar for a planned load test.
  • Verify SYN cookies and record the exact sysctl values.
  • Enable the provider's scrubbing or CDN protection for the affected service.
  • Apply firewall SYN-flood thresholds and per-source connection limits.
  • If state-table load is high while useful traffic stays flat, rate-limit bare ACK packets at the edge (ACK-flood shape).
  • Check appliances and gateways for flood messages and table pressure.
  • Watch for extortion messages and follow the incident response plan.
  • Communicate status to owners and support on a fixed schedule.
  • After recovery: verify counters return to baseline, write the incident record, and tune one rule.
