MITRE ATT&CK - Exfiltration - Parent Technique

T1048 Exfiltration Over Alternative Protocol

Stolen data leaves the network over a channel that is not the attacker's main Command and Control (C2) link. C2 is the standing connection an attacker keeps open to send commands to a computer they control. For the theft step, the attacker switches to other protocols, for example the Domain Name System (DNS), the File Transfer Protocol (FTP), or a custom encrypted stream. This page explains the technique and shows how to detect it. This guide was reviewed against MITRE ATT&CK v20 in October 2026.

What it is
Stolen data is sent out over protocols like DNS, ICMP, FTP, or a custom encrypted stream instead of the C2 channel.
Why it matters
It hides inside protocols that web-focused tools often ignore, so large volumes can leave quietly.
Main detection source
Network traffic analysis: volume, protocol, and destination anomalies.
Detection difficulty
Hard - traffic often looks like normal protocol use.

    1

    Overview

    A plain-language look at what this technique is, where it sits in an attack, and what a detection team needs to know first.

    In this technique, an attacker moves stolen data out of a network using a protocol that is not their main Command and Control (C2) channel. C2 is the standing connection an attacker keeps open to send commands to a computer they control. For the data theft step they switch to something else. Common choices are the Domain Name System (DNS), the Internet Control Message Protocol (ICMP), the File Transfer Protocol (FTP), or a custom encrypted stream on a rare port.

    This matters because many security tools focus on web traffic. DNS, ICMP, and similar protocols are often allowed out of the network by default. An attacker can abuse that trust and copy data out slowly and quietly. The traffic usually looks like normal use of the chosen protocol.

    In the attack chain, this step comes late. The attacker first gets access, then collects the data, and only then exfiltrates it. MITRE ATT&CK tracks exfiltration under tactic TA0010. Stopping earlier steps is cheaper, but you still need eyes on the exit paths.

    The platform list comes straight from the official ATT&CK page. ESXi is a hypervisor that runs virtual machines. IaaS and SaaS are cloud services: infrastructure as a service rents raw servers, and software as a service delivers ready-made apps. Network Devices means routers, switches, and firewalls. Office Suite means email and productivity cloud services. Windows, Linux, and macOS cover the usual laptops and servers.

    The three sub-techniques

    ATT&CK splits this technique into three children. They differ only in how the outgoing data is protected. Knowing the difference helps you pick the right detection ideas for each child.

    T1048.001

    Symmetric encrypted non-C2 protocol. The data is encrypted with a symmetric cipher. This means the same secret key encrypts and decrypts it. The channel is not the C2 channel.

    T1048.002

    Asymmetric encrypted non-C2 protocol. The data is encrypted with an asymmetric cipher. A public key encrypts the data, and only a private key can decrypt it.

    T1048.003

    Unencrypted non-C2 protocol. The data leaves in plain form. Plain DNS queries, plain FTP uploads, or the Trivial File Transfer Protocol (TFTP) fit here.

    Animated Simulation

    A fictional but realistic scene: an attacker moves a 1.2 GB customer export out through a DNS tunnel over 12 nights. Press Play, or click a step chip.

    Written step-by-step story
    1. A user clicks a phishing link and runs a fake update, which gives the attacker a small foothold on the workstation. The plan is to move data out over DNS, not over the main C2 channel. The SOC sees a low-severity EDR event about an Office app starting a shell.
    2. The attacker reads many files from the file server and packs them into an archive in a temp folder. If anyone reviewed file server logs, they would see one account reading far more files than usual. No alert fires yet.
    3. The attacker probes the exit paths and finds that DNS to any resolver is allowed. The firewall stays silent. That silence is exactly the gap the attacker wants.
    4. The tunnel tool starts and hides data inside long names for a brand-new domain. The resolver forwards the queries out. The volume is still too small for any threshold.
    5. The tool pushes hundreds of encoded chunks every night. DNS analytics finally flag long labels and a high query count to one domain, around 400 queries per minute.
    6. The attacker's outside server reassembles the pieces into the original 1.2 GB file. DLP never saw the data because it hid inside DNS queries.
    7. An analyst joins the DNS volume alert with the new-domain context and rates the case high. Resolver and firewall logs confirm the tunnel pattern.
    8. The team sinkholes the domain and isolates the workstation. They then hunt for other hosts that touched the same domain.

    Red Team Perspective

    Understanding the attacker's choices shows you where they can slip and where your logs will catch them.

    When attackers use it

    Attackers pick this technique after they have collected valuable data. They often move away from the C2 channel when that channel is small, slow, or watched. A large dump over a web beacon would be loud, so they spread the same data over DNS or another quiet channel.

    Groups that plan ransomware also use it first. They copy out files before they encrypt, so they can demand payment twice. That is one more reason to watch the exit paths early.

    Prerequisites

    • Data already collected and packed, usually in an archive.
    • A small tunnel tool or script on one internal host.
    • An attacker-controlled domain or server on the internet.
    • Allowed egress for the chosen protocol, for example DNS to any resolver.
    • Patience, because slow transfers avoid volume alerts.

    How it works

    1. Collect and compress the target files into one or more archives.
    2. Test the exit paths and find a protocol that leaves the network without checks.
    3. Encode the archive into small pieces that fit inside the chosen protocol.
    4. Send the pieces out on a slow, steady schedule, often at night.
    5. Receive the pieces on an outside server the attacker owns.
    6. Reassemble and decode the archive, then remove the traces.

    Common variations

    DNS tunnel

    The tool hides pieces of the archive in long names inside DNS queries. The TXT record type, which carries text, is a favorite. One gigabyte can take many thousands of queries, so it runs for days.

    Custom TCP stream

    The tool opens a raw connection to a rare port and pushes an encrypted stream. It is not the C2 channel and not standard TLS, which is the common encryption for the web. Only volume and timing give it away.

    Legacy or odd protocol

    Plain FTP or TFTP uploads, or data hidden inside ICMP ping payloads. These are old and simple, which is why some networks never log them.

They run the same volume every night on a fixed schedule. And they forget that internal resolvers log every query. Each mistake is a detection opening.

    Blue Team / SOC Perspective

    What the technique leaves behind, where to look for it, and a triage path from first alert to closed case.

    Network side artifacts

    Long random labels inside DNS queries, often of type TXT. One domain repeated many times per minute. Big outbound flows on uncommon ports, or plain FTP uploads to outside addresses.

    Endpoint side artifacts

    An archive file in a temp folder. A small tunnel tool or an unknown script. A new scheduled task that starts it at night. The Endpoint Detection and Response (EDR) agent may log a new process tree.

    Identity side artifacts

    One account reading far more files than usual. Access at strange hours from a host that never did this before. The file server audit log is the key source here.

    Side channel artifacts

    Workstations joining Wi-Fi networks that are not yours. USB or cellular modems attached to laptops. These bypass the egress firewall completely, so they need their own logs.

    Where to look

    Log sourceWhat to look forWhy it helps
    DNS query logs (Zeek dns.log, resolver logs)Long labels, rare record types, high query counts to one domainDNS tunneling is the most abused variant, and it always touches the resolver
    Firewall session logsOutbound sessions to rare ports, or plain FTP and TFTPShows which exit path the data actually used
    Flow records (NetFlow, Suricata EVE flow)Large one-way byte counts, ICMP with big payloadsVolume evidence that survives encryption

    EDR process logsUnknown binaries, archives in temp folders, scheduled tasks at nightNames the tool and the account behind the transfer
    Wireless controller or endpoint WLAN logsNew Wi-Fi associations to unknown networksCovers out-of-band paths that skip the firewall

    Why it matters

    This technique is the last step of the attack chain, which means it is your last chance to stop a data breach. Collection and C2 alerts may have been missed earlier. One confirmed exfiltration event tells you the attacker already had deep access. That changes the response from simple cleanup to full incident handling.

    Triage flow: from alert to closure

    1. Open a case and record the alert, the host, and the user account.
    2. Pull all DNS queries from that host for the last 24 hours and compare with its baseline.
    3. Check query length, record types, and query counts against the thresholds in section 5.5.
    4. Review firewall and flow logs for large outbound transfers from the same host.
    5. Confirm staging evidence on the endpoint, such as an archive in a temp folder.
    6. If the pattern is confirmed, isolate the host and block the destination domain or address.
    7. Hunt for peer hosts that touched the same domain or port.
    8. Close the case with a short report: what left, when, and which controls failed.

    Security vendors describe patterns they saw in real incidents. Use them for context and tuning, not as direct evidence.

    These government advisories are free and high signal. They often list detection ideas you can copy into your rules.

    Open-source intelligence means public blogs, conference talks, and tool documentation. They show what a technique looks like in a capture.

    Paid feeds add indicator lists, such as bad domains. Weigh the cost against what your own logs already show.

    Information Sharing and Analysis Centers are sector groups, for example finance or health. Members share patterns that hit their industry.

    5.4 Logs and Patterns

    Each numbered card below matches threat number 1 to 6 from the table in 5.3. Every card lists the logs, the key fields, and one full example event in JSON format.

    1) DNS tunneling exfiltration

    Logs
    Zeek dns.log, resolver query logs, firewall DNS allow rules.
    Fields
    Client IP, full query name, record type, answers, timestamp.
    Normal
    Short names, many different domains, low queries per client.
    Suspicious
    Long random labels, one domain repeated, hundreds of queries per minute from one client.
    Logic
    Alert when one client sends more than 100 long-label queries in a short window.

    Field notes: id.orig_h is the asking client, query is the full name it asked for, and the part before the dot is the hidden data. qtype_name TXT means the query carries text, which tunnel tools like. A normal business query almost never has a 60-character label.

    2) Encrypted custom TCP stream (non-TLS)

    Logs
    Zeek conn.log, NetFlow, firewall session logs.
    Fields
    Source and destination IP, destination port, bytes, packets, duration, service label.
    Normal
    Large transfers only to known services on standard ports.
    Suspicious
    Tens or hundreds of megabytes out to an external address on a port with no known service.
    Logic
    Alert when one host sends more than three sessions of over 50 MB each to uncommon ports outside private ranges.

    Field notes: orig_ip_bytes counts all bytes the client pushed out, here about 740 MB in one session of about 31 minutes. service says unknown, meaning Zeek could not name the protocol. One-way volume with no service name is the core signal.

    3) Unencrypted FTP/TFTP upload

    Logs
    Zeek ftp.log and tftp.log, firewall logs.
    Fields
    Client IP, server IP, FTP user, command, file name, reply code.
    Normal
    Uploads only to approved internal servers, or rare approved partner jobs.
    Suspicious
    An FTP STOR or APPE upload, or a TFTP write request, aimed at any external address.
    Logic
    Alert on FTP STOR or APPE commands aimed outside private ranges, and separately on TFTP write requests aimed outside private ranges.

    Field notes: command STOR means the client sent a file to the server, and arg names it. The reply code 226 means the transfer finished. Plain FTP also exposes the password field, which is why the value here is redacted.

    4) Exfiltration inside ICMP payloads

    Logs
    Suricata EVE flow records, firewall ICMP counters, Zeek conn.log.
    Fields
    Source and destination IP, protocol, packets and bytes per flow.
    Normal
    Small pings for reachability checks, low bytes per flow.
    Suspicious
    One host sending megabytes inside ICMP to one external peer.
    Logic
    Alert when one host sends more than three ICMP flows of over 1 MB each to outside addresses.

    Field notes: bytes_t counts bytes to the destination, here about 19 MB inside ping traffic in 29 minutes. icmp_type 8 is an echo request, a normal ping. Equal send and receive counts with huge byte totals point at a payload channel, not a health check.

    5) Chunked transfers to bypass size limits

    Logs
    Firewall traffic logs (for example pan:traffic), proxy logs, cloud upload logs.
    Fields
    Source, destination, bytes sent, application, rule, session count.
    Normal
    Upload sizes spread widely across sessions and destinations.
    Suspicious
    Many uploads from one host to one destination, each just under the DLP size limit.
    Logic
    Alert when more than five allowed uploads of 40-50 MB from one host reach one external address.

    Field notes: bytes_sent is the upload volume for the session, here about 49.4 MB, just under a 50 MB DLP alert line. One such session is normal. A run of them to the same address is a split file.

    6) Out-of-band medium (Wi-Fi or cellular)

    Logs
    Wireless controller logs, Windows WLAN-AutoConfig event 8001, modem device logs.
    Fields
    Computer, user, network name (SSID), authentication type, timestamp.
    Normal
    Company networks only, or approved home and travel networks.
    Suspicious
    A corporate laptop joining an open unknown network while holding sensitive data.
    Logic
    Alert on WLAN join events whose network name is not on the approved list.

    Field notes: event 8001 records a successful Wi-Fi join. SSID is the network name, and the example name is not a company network. Authentication Open with Cipher None means no encryption, so any data sent there bypasses the egress firewall. Exact field names depend on your log forwarder.

    5.5 Sigma Rules and Splunk SPL

    Each threat from 5.3 gets at least one Sigma rule and one matching Splunk SPL query, and threat 3 gets two pairs, one for FTP and one for TFTP, so this section holds seven rule pairs. Sigma is a plain-text rule format that many security tools can translate. SPL is the Search Processing Language used by Splunk. Copy a pair, change the index names to fit your logging setup, and test in a lab before rollout. The badge next to each title matches the rank from 5.3.

    1) DNS tunneling exfiltration High

    Field assumptions: index=network holds Zeek JSON logs, and the fields query and id.orig_h are extracted. The SPL groups by client host only, exactly like the Sigma condition, and shows the longest label with max(len(query)). If you also want a per-domain view, first cut the parent domain out of query with rex, for example rex field=query "(?<parent_domain>[a-z0-9.-]+\.[a-z]{2,})$", and then add parent_domain to the stats. The SPL expresses the same logic as the Sigma rule above.

    False positives
    Scanners and content delivery networks can use long generated labels.
    Tuning
    Raise the count for busy clients, and add allowlisted domains from your own baseline. Start with a count of 100 per hour per client.

    2) Encrypted custom TCP stream (non-TLS) High

    Field assumptions: orig_ip_bytes, id.resp_h, and id.resp_p come from zeek:conn. The SPL groups by client host (id.orig_h), exactly like the Sigma condition, and alerts when one host has more than three large sessions. The byte total and the destination count are context only. Adjust the index name and the common port list to your environment.

    False positives
    Approved backup jobs or media uploads that use rare ports.
    Tuning
    Keep an allowlist of approved destinations and ports. Lower the byte threshold only after you know your normal top talkers.

    3) Unencrypted FTP/TFTP upload High

    Field assumptions: command, arg, and user come from zeek:ftp. The SPL counts upload commands per client host, exactly like the Sigma condition, with the same external-destination filter and the same more-than-five threshold. TFTP writes are covered by the second rule pair below.

    Field assumptions: wrq is the file name field Zeek fills only for TFTP write requests, so wrq=* keeps write requests only. cidrmatch uses the same private ranges as the Sigma filter. Every write to an external address matches, so this pair has no count threshold. The SPL expresses the same logic as the Sigma rule above.

    False positives
    Approved partner transfers that still use FTP by contract.
    Tuning
    Best fix is prevention, so block outbound FTP and TFTP. Keep the rule as a backstop and allowlist known partner servers.

    4) Exfiltration inside ICMP payloads Medium

    Field assumptions: Suricata EVE JSON is flattened by the add-on. If your deployment keeps the flow object nested, adjust the out_bytes eval. The SPL groups by src_ip, exactly like the Sigma condition, and alerts when one source has more than three flows above 1 MB. The byte total and the peer count are context only.

    False positives
    Monitoring tools that measure paths with big ping series.
    Tuning
    Exclude your own monitoring hosts first. Consider blocking outbound ICMP except from management systems.

    5) Chunked transfers to bypass size limits Medium

    Field assumptions: bytes_sent, src, and dst come from pan:traffic. Both rules count uploads from one source to one destination and alert on more than five. The one-hour bucket keeps the count per hour; drop the bucket line to count across the whole search window. If you use a proxy instead of a firewall, swap in stream:http or your proxy sourcetype and use its upload byte field.

    False positives
    Backups and video calls that send similar payload sizes on purpose.
    Tuning
    Match the 40-50 MB band to your real DLP limit. Group by one hour first, then loosen to a day if the noise stays low.

    6) Out-of-band medium (Wi-Fi or cellular) Low

    Field assumptions: WLAN events are forwarded as XML Windows event logs. The SSID is read from the raw message text, so the rex pattern may need small changes for your forwarder. The SPL groups by Computer only, exactly like the Sigma condition, so five joins to five different unknown networks still alert. The network count is context only.

    False positives
    Approved travel and home networks.
    Tuning
    Fill the approved list from your own history before enabling the alert. Pair it with a policy that forbids unknown Wi-Fi on data-bearing laptops.

    Real-World Case Study

    This is a composite case study built from common public incident patterns. Company names are fictional.

    A regional insurance company with about 900 staff keeps its customer records on an internal file server. Its egress rules allow DNS to any resolver on the internet. A web proxy and a size-based data loss prevention (DLP) tool watch HTTP and HTTPS traffic. DNS is not logged centrally. This mix is common, and it is exactly the mix this technique abuses.

    An attacker who already had one foothold wanted the customer database. They staged a 1.2 GB export on a workstation and built a DNS tunnel to carry it out. The transfer ran across 12 nights and was caught by DNS volume analytics, not by DLP.

    Timeline

    1. Day 1 - 02:10

      Foothold

      A finance user opens a phishing link and runs a fake update. The EDR agent logs a low-severity event about an Office app starting a shell. Nobody looks at it that night.

    2. Day 2 - 01:30

      Staging

      The attacker copies customer tables from the file server with one account. They pack 1.2 GB into an archive in a temp folder. File server logs record the read burst.

    3. Day 2 - 03:05

      First test

      Twenty long-label queries go to a domain registered three days earlier. The tunnel works end to end. No alert exists for long labels.

    4. Day 3 - 00:40

      Tunnel starts

      The tool sends steady nightly batches at about 400 queries per minute. Each query carries an encoded piece of the archive. The firewall forwards everything.

    5. Day 8 - 02:20

      Halfway

      About 600 MB has left. DNS logs exist on one resolver but nobody reviews query volume. The DLP tool sees only normal-looking sessions.

    6. Day 11 - 09:15

      Analytics hit

      A new DNS analytics pilot flags one host sending hundreds of long-label queries per minute to a never-seen domain that is about twelve days old. The score is high.

    7. Day 11 - 11:40

      Case opened

      An analyst reads the queries and sees Base32 text in the labels. Base32 is a way to write binary data using plain letters and digits. Resolver logs show one-way volume with almost no responses. The case is rated high.

    8. Day 12 - 10:05

      Containment

      The resolver starts answering the domain with a sinkhole address, which is a harmless fake answer. The workstation is isolated from the network at the same time.

    9. Day 13 - 14:00

      Eradication

      The tunnel tool is removed and the phishing account credentials are reset. The team checks for persistence and finds none. Three peer hosts are cleared in the hunt.

    10. Day 16 - 09:00

      Recovery

      The isolated host returns to service after a rebuild. The team writes the lessons into the egress policy. DNS logging moves to a central store the same week.

    Detection point

    The alert that mattered was DNS volume analytics joined with new-domain context. Neither signal alone was enough. DLP never fired because the data hid inside DNS queries. The gap was not the sensor but the missing review of DNS.

    Containment

    The team sinkholed the attacker domain first, so any further queries died at the resolver. They isolated the workstation next. This stopped the transfer about halfway through the export.

    Eradication

    Analysts removed the tunnel tool and reset every credential the account had touched. They searched for scheduled tasks and new services and found none. A hunt for peers that used the same domain found three hosts with only harmless lookups.

    Recovery

    The workstation was rebuilt from a clean image and returned to the user. No customer-facing service was interrupted. The security team used the incident to push two fixes through in days, not months.

    Impact and consequences

    About 1.2 GB of customer records left the company. Legal reviewed the exposure and filed the required regulatory report. The company spent staff weeks on response and later funded central DNS logging and egress allowlisting.

    Team response and communication

    The team ran a daily bridge and kept one case channel for updates. Executives got one short note each morning. The handler wrote a two-page report that named the failing controls plainly.

    Lessons learned

    First, centralize DNS logging so volume is visible. Second, watch newly registered domains, because twelve days old was a strong signal. Third, allowlist egress so DNS leaves only to approved resolvers. Each lesson maps to a control in section 7.

    7

    Mitigation and Defense

    There is no single patch for this technique. The fixes are configuration: restrict egress, log it well, and watch the volumes. MITRE lists six mitigations for T1048: M1057 Data Loss Prevention, M1037 Filter Network Traffic, M1031 Network Intrusion Prevention, M1030 Network Segmentation, M1022 Restrict File and Directory Permissions, and M1018 User Account Management. The cards below show where each one fits.

    Policy and people

    Write a short egress policy that names which protocols may leave. Teach staff why plain FTP or unknown Wi-Fi is banned. Add data handling rules to onboarding.

    Identity and endpoint

    Give file server accounts least privilege, so one account cannot read every table. Enforce multi-factor authentication (MFA), which asks for a second proof at login. Keep EDR on every laptop and server. This card matches M1018 (User Account Management).

    Network and egress

    Send DNS only to approved resolvers and block direct outbound port 53. Block outbound FTP and TFTP. Allow other egress by application, not by port alone. These are M1030 (Network Segmentation) and M1037 (Filter Network Traffic) controls.

    Cloud and logging

    Centralize DNS query logs and keep them at least 90 days. Collect flow records and firewall session logs in the same store. For cloud storage, set access control lists, as M1022 (Restrict File and Directory Permissions) advises.

    Monitoring and response

    Run the seven rule pairs from section 5.5 and tune them monthly. A network intrusion prevention system adds signature-based blocking at the boundary (M1031). Keep DLP on web channels as a second sensor (M1057). Write a playbook for isolate, sinkhole, and hunt, and rehearse it twice a year.

    Backup and resilience

    Keep offline backups and test restores. Backups do not stop theft, but they weaken the second extortion step that often follows exfiltration.

    Home and small office

    Point your router at a trusted resolver and turn off its remote admin page. Keep laptops and phones updated. Use separate devices for work and family, and never join unknown open Wi-Fi with a work laptop.

    Common Mistakes and Best Practices

    Each card below is a mistake teams really make, with the symptom, the cause, the fix, and the prevention.

    1) Only the web proxy watches for exfiltration

    Symptom
    Alerts cover HTTP and HTTPS only, and DNS leaves unnoticed.
    Root cause
    The team assumed data leaves over the web like most apps.
    Fix
    Add DNS, flow, and firewall sources to the monitoring scope.
    Prevention
    Map every outbound protocol yearly and check each has a watcher.

    2) DNS allowed to any resolver

    Symptom
    Tunnel tools reach any domain server on the internet.
    Root cause
    Firewall rules were written as "allow DNS" with no destination.
    Fix
    Restrict port 53 to the approved resolvers, inside and out.
    Prevention
    Review egress rules each quarter for destination-less allows.

    3) DNS queries are not logged at all

    Symptom
    Investigations cannot answer "what did this host resolve".
    Root cause
    Resolver logging was never turned on or shipped anywhere.
    Fix
    Enable query logging and ship it to the central store.
    Prevention
    Put DNS logs on the same coverage list as firewall logs.

    4) Volume alerts get switched off after noise

    Symptom
    A real tunnel hides inside a rule someone disabled last month.
    Root cause
    The rule was tuned once, it got noisy, and it was muted instead of fixed.
    Fix
    Re-enable with scoped thresholds and baselines per host group.
    Prevention
    Require a tuning note before any rule is muted.

    5) No context on domain age

    Symptom
    A twelve-day-old domain looks the same as a ten-year-old one.
    Root cause
    Registration data was never joined into DNS alerts.
    Fix
    Enrich alerts with domain age and reputation where possible.
    Prevention
    Track newly registered domains as a standing watchlist.

    6) Trusting DLP to see every channel

    Symptom
    DLP shows zero findings while data leaves through DNS.
    Root cause
    DLP agents and gateways inspect a limited set of protocols.
    Fix
    Treat DLP as one sensor, and add volume-based network detections.
    Prevention
    List which channels DLP cannot see and cover them another way.

    7) Traffic logs are sampled, not complete

    Symptom
    Metrics look normal, but one in fifty flows holds all the data.
    Root cause
    Sensors sample to save cost, which hides rare big transfers.
    Fix
    Keep full session metadata for egress, sample only payload capture.
    Prevention
    Check sensor sampling settings in every monitoring review.

    8) Egress policy forgets ICMP and rare ports

    Symptom
    Ping and odd high ports leave the network without checks.
    Root cause
    Rules were built per application and never closed by default.
    Fix
    Add a default-deny egress rule and open paths by request.
    Prevention
    Test from a lab host which ports truly leave the network.

    9) No baseline of normal volumes

    Symptom
    Every threshold is a guess, so alerts are either noisy or blind.
    Root cause
    Nobody measured per-host and per-domain normal behavior.
    Fix
    Build 30-day baselines for DNS counts and outbound bytes.
    Prevention
    Refresh baselines after big business changes, not only yearly.

    10) Blocking the domain but skipping the host hunt

    Symptom
    The transfer stops, then reappears next week on another host.
    Root cause
    Response treated one machine as the whole incident.
    Fix
    Hunt all hosts for the same domain, ports, and labels.
    Prevention
    Make peer hunting a required step in the exfiltration playbook.

    Habits that keep you sharp

    Daily

    • Review new DNS alerts and rule hits.
    • Glance at top egress talkers.
    • Check that sensors and resolvers are still logging.

    Weekly

    • Review new domains contacted by endpoints.
    • Confirm resolver and firewall configs are unchanged.
    • Sample one host and read its full outbound story.

    Monthly

    • Refresh baselines and thresholds.
    • Test one detection with a lab capture.
    • Review intel reports for new tunnel patterns.
