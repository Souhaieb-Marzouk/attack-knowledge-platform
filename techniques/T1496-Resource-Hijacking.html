T1496 Resource Hijacking

Resource hijacking means an attacker uses your computers, network links, or cloud services to do their own work. They mine cryptocurrency, resell your bandwidth, or send spam with your accounts. You pay the bill in money, speed, and trust. This guide shows how the attack works, what it leaves in your logs, and how to detect and stop it.

  • ATT&CK v20 · modified 24 Oct 2025

1

Overview

Resource Hijacking means an attacker uses your computers, network links, or cloud services to do their own paid work. After they get in, they turn your systems into free workers for themselves. Most people know this technique in its most common form: cryptojacking (secretly using a victim's computers to mine cryptocurrency). The technique also covers reselling your bandwidth, SMS (mobile text message) fraud, and abuse of cloud services such as email or AI platforms.

What the technique is

An attacker gains some level of control over your systems or cloud accounts. Instead of stealing data or locking files, they quietly run their own workloads. The work is usually legal for them to do on their own machines, but they make you pay for the electricity, bandwidth, SMS fees, or cloud usage. Targets range from one server to IaaS (Infrastructure as a Service, rented cloud computers) and SaaS (Software as a Service, cloud applications you sign in to).

ATT&CK (the MITRE knowledge base that catalogs attacker techniques) describes four main forms: mining cryptocurrency, selling your network bandwidth to proxy networks, generating SMS traffic for profit, and abusing cloud messaging services to send spam. Some groups do several of these at once. For example, the LABRAT campaign did both cryptojacking and proxyjacking (reselling a victim's bandwidth through proxy software) on GitLab servers.

Why it matters

First, money. A hijacked cloud account can add thousands of dollars in compute or SMS charges in a few days. Second, availability. Mining loads can slow or crash servers. Spam waves can exhaust email or SMS quotas, so real customers stop getting messages.

Third, and most important: a miner is a symptom. It means an attacker already got past your patching, exposed APIs (application programming interfaces), or access controls. If you ignore the miner and only delete it, the same entry path lets them return. Next time they might use ransomware instead.

Where it fits in the attack chain

Resource Hijacking lives in the Impact tactic, the last stage of ATT&CK's attack chain. By the time you see it, the attacker has usually finished earlier steps. Common examples are exploiting a public application (T1190), using valid accounts (T1078), and setting up persistence such as cron jobs (T1053.003).

The hijacking itself is often the only step the attacker wants to keep alive. That is also where their evasion effort goes. Attackers rename binaries, throttle CPU use, and hide pool traffic.

Written story of the simulation

The list below covers the same eight steps as the animation. Screen readers and printouts get the full content here.

  1. Step 1 — Scanning. The attacker probes internet-facing services and finds an old web application with a known, unpatched flaw. The firewall sees ordinary scan noise, so no alert fires.
  2. Step 2 — Entry. The attacker sends the exploit and the application runs it. A web shell (a hidden script that passes attacker commands through the web app) gives them command execution on the server. The attacker and the company now share the same server, without the company knowing.
  3. Step 3 — Downloading the miner. The attacker uses the web shell to download a cryptocurrency miner, renames it to look like a system tool, and starts it. The binary lands in a temporary folder, a place normal software rarely uses.
  4. Step 4 — Connecting to the pool. The miner opens a long-lived connection to a mining pool (a server that groups miners and pays them for their work) and starts hashing (doing the miner's arithmetic work). CPU use jumps to about 95% and stays there. The pool now sends mining jobs; the server sends back completed work called shares.
  5. Step 5 — Looking like normal load. The attacker throttles CPU to look like ordinary load and routes pool traffic over a port normally used for HTTPS. Cloud logs show nothing unusual yet.
  6. Step 6 — Defender signals. The SOC sees three signals together: a process named like a system tool running from a temp folder, sustained CPU above baseline, and a 12-hour outbound session to a suspicious host. Correlation raises one high-severity alert.
  7. Step 7 — Response. The SOC isolates the server from the network, kills the miner, and removes the web shell. The mining pool connection drops and CPU returns to normal within minutes.
  8. Step 8 — Recovery and lessons. The team patches the web application, rotates credentials, adds an egress rule that blocks direct pool ports, and tunes the correlation rule. The entry path is closed, not just the symptom.

Red Team / Hacker Perspective

Understanding why attackers like this technique helps you predict where they will show up. This section describes attacker thinking at a conceptual level. All commands shown later are lab-only examples for your own test systems.

When and why attackers use it

Resource hijacking is attractive because it pays without talking to the victim. Ransomware needs a negotiation; a miner only needs the machine to stay up (uptime). Attackers pick it when they have weak but broad access: a foothold in a container cluster, a leaked cloud key, or a web shell on one server. It scales well — the same script that mines one server mines a thousand.

It is also a low-noise goal. Because victims often notice nothing for weeks, attackers treat hijacked systems as long-term infrastructure. Some campaigns run miners for months and still hold the keys for a bigger attack later.

How it is performed (concept)

The pattern is almost always the same four moves: get code execution, download a miner or proxy client, point it at attacker infrastructure, and make it survive reboots and cleanup. Mining malware frequently kills competing miners it finds — a detail visible in logs when one process keeps terminating another.

On cloud accounts the moves shift up one level: instead of installing software, the attacker calls the provider's API to create compute instances, enable messaging services, or raise quotas. Everything then runs "legitimately" inside your subscription.

Ethics and legality

Using these methods against systems you do not own is a crime in almost every country, even "just for testing". Everything in this guide is for defenders and for safe labs you control. Run examples only on isolated machines you own, never against production or third-party systems.

Lab-only example: a safe miner look-alike

This snippet does not mine anything. It shows the shape of a miner launch so you can build a detection for it in your lab. It uses stress-ng, a legitimate load generator, plus a fake pool address that points to nothing.

Common variations

  • Rival-miner wars: an incoming miner kills rival miners, so several miner families appear and disappear over time.
  • Proxy plus miner combo: same host earns from CPU and bandwidth at once (LABRAT did this).
  • Cloud-native hijack: no malware at all — attacker uses provider APIs to spawn GPU spot instances or enable SES.
  • Free-tier abuse: mass sign-ups on a service whose OTP flow sends SMS, no intrusion needed (T1496.003).

Mistakes attackers make

  • Spiking CPU to 100% immediately, which trips simple baselines.
  • Leaving the miner's original filename, so known hash or name alerts fire.
  • Using well-known pool ports (3333, 14444) without hiding behind popular CDN (content delivery network) domains — a trick called domain fronting. Plain port use makes egress rules effective.
  • Reusing one wallet address across victims, letting defenders link incidents.
  • Forgetting log sources exist: auditd, CloudTrail, and Zeek record most of their steps.

Blue Team / SOC Perspective

Resource hijacking is one of the most visible techniques — if you collect the right data. This section shows what it looks like from inside the network and gives you a triage flow you can follow on a busy shift.

How defenders can see it

Four telemetry families catch almost every variant: process telemetry (what runs, from where, with which command line), performance telemetry (CPU, memory, network rates over time), network telemetry (sessions, volumes, destinations), and cloud audit logs (who created what, which service sent what). No single source is enough. The strong detections in Section 5 all join at least two sources.

Remember the chain position: hijacking is an Impact-stage technique. If you see it, earlier chain steps such as entry and persistence have already succeeded. Hunt for those steps before you close the case.

Artifacts it leaves behind

  • Binary in a temp path with a generic name, often with mining config strings inside.
  • Cron entries, systemd services, or scheduled tasks that relaunch the payload.
  • Very long outbound TCP sessions (hours to days) to a small set of destinations.
  • CPU or bandwidth graphs with flat plateaus instead of normal daily waves.
  • Cloud audit entries: new instances, new service enablement, quota changes.
  • SMS or email dashboards: send-volume spikes, high bounce rates, new destination prefixes.

Triage flow: a hijacking alert arrives

  1. Confirm scope. Is it one host, a fleet, or a cloud account? Check whether the same indicator (pool domain, image name, wallet string) appears elsewhere in your estate.
  2. Join two signals. Pair the resource signal (CPU, SMS volume, instance) with a cause signal (process, API caller, source IP). One alone is often a false positive.
  3. Decide containment speed. Host-based miner on an app server: isolate the host now. Cloud API hijack: disable the key and throttle spend first, investigate after — the bill grows every minute.
  4. Preserve evidence. Snapshot the host or export the relevant logs before cleanup. You need the binary hash, config, and the entry path later.
  5. Remove cause, not just effect. Deleting the miner is symptom work. Find and close the entry path, rotate exposed credentials, and confirm with a hunt that no other host kept a copy.
  6. Feed detection. Turn the indicators into new Sigma rules and add the missed log source to your pipeline. Record the case in your threat intel notes.

Why this matters beyond money

Treat every hijacking incident as proof that the outer defenses failed. The attacker had to pass through the same paths ransomware crews use. Closing those paths after a miner case is one of the cheapest ways to avoid a costlier case later.

5.2Threat intelligence

Hijacking actors are well documented. Intelligence work here means keeping four lists fresh: active groups, their tools, their infrastructure (pools, proxies, command-and-control (C2) servers), and their current entry vectors. Feed those lists into your detections from 5.5.

Source types and how to use them

  • MITRE ATT&CK — technique pages list active groups and software (see below). Start here; it is free and vendor-neutral.
  • Vendor reporting — Trend Micro, Palo Alto Unit 42, Sysdig TRT, Trellix, and cloud provider teams (AWS, Azure) publish campaign write-ups with indicators and TTPs (tactics, techniques, and procedures).
  • OSINT (open-source intelligence) feeds — URLhaus and MalwareBazaar (abuse.ch) track miner distribution URLs and samples; GitHub trackers follow pool infrastructure.
  • Commercial feeds — paid feeds add attribution and infrastructure age, useful for confidence scoring.
  • ISACs (Information Sharing and Analysis Centers) / M3AAWG — sector-specific warnings (MS-ISAC, FS-ISAC) and messaging-abuse best practice for SMS pumping.
  • Internal telemetry — your own egress logs and DNS history are the best intel source for your environment; every incident adds a permanent detection.

Confidence levels, in plain words

High means multiple independent sources agree and your own telemetry confirms it. Use it for blocking and alerting. Medium means the report is credible but you have not seen it locally — use for hunts. Low means a single unverified claim — use for awareness only. Re-score every quarter; hijacking infrastructure rotates fast.

Apply intel in three steps: (1) enrich — tag pool and proxy indicators into your SIEM; (2) hunt — search 90 days of history for each new actor's tools; (3) detect — write or tune a Sigma rule per tool family, then retire rules when the campaign dies.

Real-World Case Study: Tesla Cloud Cryptojacking (2018)

In February 2018 the cloud security firm RedLock disclosed that attackers ran cryptocurrency miners inside Tesla's Amazon Web Services environment. The case is a clear teaching example: the entry point was one exposed admin console, and every defense lesson from this guide appears in it.

Context

RedLock researchers found the incident while tracing a set of publicly exposed AWS credentials back to their owner. The trail led to a Kubernetes administration console used by Tesla's cloud environment that was reachable from the internet without a password. RedLock's broader study found hundreds of unprotected Kubernetes consoles at that time, so this was not an exotic weakness — it was common.

Attack chain

  1. Discover the passwordless Kubernetes console.
  2. Run a mining pod inside the cluster using cluster resources.
  3. Find AWS access keys stored in one pod's configuration. The keys open an S3 bucket that holds sensitive data, such as vehicle telemetry.
  4. Keep mining while hiding: a private mining pool, traffic masked behind CloudFlare, non-standard ports, and throttled CPU use to avoid detection.

Timeline

  • 2017 (exact date not published)

    Attackers reach the exposed Kubernetes console and begin mining in Tesla's cloud. Later reporting places the start in 2017.

  • During the intrusion

    The attackers deploy Stratum mining software, configure a private pool behind CloudFlare, and keep CPU use low to stay unnoticed.

  • 20 February 2018

    RedLock's CSI team, tracing leaked AWS keys, discovers the intrusion. RedLock reports it to Tesla and publishes the post "Cryptojacking Runs Wild in the Cloud".

  • Within hours of the report

    Tesla fixes the exposed console and addresses the issue. RedLock receives a bug bounty of $3,133.70.

  • 20–21 February 2018

    Fortune, CNBC, and CyberScoop publish the story; Tesla confirms the incident publicly.

Detection point

Tesla did not detect this internally — an outside researcher did. The signals were all there: unusual compute spend, a pod running Stratum software, and traffic to CloudFlare-fronted pool endpoints on non-standard ports. This is exactly the RH-02/RH-03 combination from Section 5. A billing anomaly alert or a "new container image from unknown registry" rule would have caught it far earlier, without an outside researcher.

Containment and eradication

Containment meant closing the exposed console and stopping the mining pods. Eradication required removing attacker workloads and, critically, rotating the AWS credentials that had been exposed inside pod configuration — credentials in workloads are readable by anyone who controls the workload. Tesla stated the fix was applied within hours of the report.

Recovery and impact

Tesla said the impact was limited to internally used engineering test cars, with no indication that customer privacy or vehicle safety was affected. The financial cost of the mining itself was never published, but the reputational cost of a public disclosure was real. Recovery included hardening console access and reviewing credential placement.

Team response and communication

The response went well because of cooperation: RedLock reported responsibly, Tesla paid a bounty and fixed quickly, and communication was factual ("limited to engineering test cars"). The lesson for your IR (incident response) plan: when researchers or providers report a hijack, disclosure becomes public quickly. Prepare a statement template and an owner for cloud incidents.

Lessons learned

  • Admin consoles must never be internet-reachable without authentication — put them behind a VPN (virtual private network) or an identity-aware proxy.
  • Credentials inside pod definitions are exposed to the cluster; use secret managers with short-lived tokens.
  • Attackers throttled CPU and hid behind CloudFlare — CPU-only detection fails; join network, audit, and billing signals (Section 5).
  • A private mining pool does not help attackers if egress rules block unknown destinations by default.
  • External researchers found it before the SOC. Reward them, then close the gap so the next report is unnecessary.

Mitigation and Defense

ATT&CK's own mitigation note for this technique is honest: it "cannot be easily mitigated with preventive controls since it is based on the abuse of system features." The practical answer is layered defense: make entry hard, make hijacking easy to see, and make the bill stop fast.

Policy & people

  • Asset policy: no internet-reachable admin panels; exception process with expiry.
  • Cloud spend policy: budgets with alerts at 50/80/100% of forecast.
  • Developer training on secret hygiene (no keys in pods, repos, or build logs).

Identity

  • MFA on all cloud root and admin accounts — no exceptions.
  • Least-privilege IAM; separate roles for CI, humans, and workloads.
  • Short-lived credentials for workloads instead of static keys.

Endpoint

  • EDR with behavioral mining detection on all servers and endpoints.
  • Block binaries executing from temp paths; application allowlisting where possible.
  • Patch internet-facing applications within defined SLAs (service-level agreements), for example Oracle WebLogic or Atlassian Confluence.

Network

  • Default-deny egress; allowlists for required destinations only.
  • Block or alert on pool ports 3333/4444/5555/7777/14444 outbound.
  • DNS filtering for known pool, proxy, and miner-distribution domains.

Cloud & containers

  • CloudTrail/audit logging on in ALL regions, sent to an immutable store.
  • Kubernetes API behind VPN; RBAC least privilege; no anonymous access; pod security standards.
  • Quotas and instance-type restrictions on GPU families for human principals.

Logging & monitoring

  • Deploy the five Sigma rules from Section 5.5 with their listed log sources.
  • Billing anomaly alerts routed to the SOC, not just finance.
  • CPU/bandwidth baselines per host class; alert on plateaus above baseline.

Home and small-office users

You are a target too — mostly for bandwidth hijacking and miner payloads hidden in cracked software. Five practical steps: (1) never install cracked or "free" versions of paid software; (2) keep your router firmware and computers updated; (3) if a device becomes slow, hot, or uploads constantly, check Task Manager or top for unknown processes; (4) use the built-in malware protection and let it update; (5) on your router, block strange outbound ports if the interface allows it. If your ISP warns you about unusual traffic, take it seriously.

Response-ready habits

Keep an emergency runbook for "cloud bill spike" and "unknown process at 95% CPU": who to call, which keys to disable first, how to isolate a host from the network, and where logs are stored. Practice it once a quarter as a tabletop. The Tesla case shows the public clock starts the moment someone outside your team notices.

Common Mistakes and Best Practices

These ten mistakes come from real SOC reviews of hijacking detections. Each one lists the symptom you will notice, the root cause, the fix, and the habit that prevents it from returning.

1. Watching CPU only

  • Symptom: incidents found by users or bills, not alerts.
  • Root cause: detection logic stops at "high CPU", so throttled miners (like the Tesla case) pass.
  • Fix: join CPU signals with process and network signals (RH-01 + RH-02).
  • Prevention: require two data sources for every hijacking rule.

2. No cloud audit logging (or only one region)

  • Symptom: "impossible" bill spikes with no logs to investigate.
  • Root cause: CloudTrail/audit not enabled everywhere; attackers use unused regions on purpose.
  • Fix: enable all-region audit logging into an immutable store; alert on first-seen regions.
  • Prevention: cloud baseline check in onboarding for every new account.

3. Alerting on every pool port hit

  • Symptom: hundreds of low-value alerts, analysts auto-close them.
  • Root cause: one-packet port matches; no duration, volume, or allowlist context.
  • Fix: require session duration above 6 hours or repeated hits; tag sanctioned test hosts.
  • Prevention: every rule ships with its false-positive budget documented.

4. Forgetting DNS and SNI

  • Symptom: port rules never fire because pools run on 443.
  • Root cause: detection only at TCP layer; attackers hide behind TLS.
  • Fix: add DNS query and TLS SNI watchlists of pool/proxy domains.
  • Prevention: refresh watchlists monthly from your threat intel feeds (5.2).

5. Deleting the miner and closing the ticket

  • Symptom: the same host reappears with a new miner name next week.
  • Root cause: symptom-only response; the entry path and persistence stay.
  • Fix: mandatory persistence sweep (RH-05 rule) + entry-path review before closing.
  • Prevention: closure checklist in the ticket template.

6. Missing container and Linux telemetry

  • Symptom: strong Windows coverage, blind on clusters where miners actually live.
  • Root cause: no K8s audit log, no runtime sensor, no auditd.
  • Fix: enable K8s API audit + Falco/runtime sensors; ship auditd.
  • Prevention: coverage matrix per platform reviewed quarterly.

7. Untuned "temp folder" rules

  • Symptom: rule disabled after a week of noise from installers.
  • Root cause: no allowlist for legitimate temp-path software.
  • Fix: allowlist by signer plus parent process; require web-server parent for temp-path alerts.
  • Prevention: tune in "report-only" mode for two weeks before alerting.

8. No ownership of SMS/SaaS spend signals

  • Symptom: SMS pumping runs for weeks; finance notices, SOC never does.
  • Root cause: messaging dashboards are owned by product teams, invisible to security.
  • Fix: route provider fraud alerts (Twilio Fraud Guard, AWS anomaly detection) to the SOC.
  • Prevention: asset inventory includes messaging/SaaS senders with security contact.

9. Static thresholds forever

  • Symptom: floods of alerts after a legitimate campaign, or silence after infra growth.
  • Root cause: "90% CPU" thresholds written once, never re-baselined.
  • Fix: per-host-class baselines with automatic re-learning windows.
  • Prevention: quarterly threshold review tied to change calendar.

10. Rules never tested

  • Symptom: a rule "works" for years — because it has never matched anything, including real attacks.
  • Root cause: no validation pipeline; field names drifted after a TA upgrade.
  • Fix: replay lab events (Section 3 snippet) monthly; alert on rules with zero matches in 180 days for review.
  • Prevention: detection CI: every rule change runs a synthetic event test.
