T1590.001

Domain Properties

Every domain on the internet carries public records. They list the owner, the registrar, contacts, addresses and name servers. Attackers read these records first, because they are free, legal and full of clues. This guide shows what they collect, what they do with it, and how defenders can hear it happening.

01

Overview: What Is This Technique?

MITRE ATT&CK is a free, public knowledge base that describes how real attackers behave. It sorts attacker goals into tactics. It sorts the methods attackers use into techniques. Each technique has an ID, such as T1590. Many techniques have smaller parts, called sub-techniques, with a second number, such as T1590.001. Security teams use ATT&CK as a shared language. When a report or a detection rule says T1590.001, everyone knows exactly which attacker behavior is meant.

This page covers T1590.001: Domain Properties, a sub-technique of T1590 in the Reconnaissance tactic. It describes how attackers gather facts about the domains a victim owns. Some facts are administrative data, such as the owner name and the registrar (the company that sells and manages domains). Other facts are directly useful: contact email addresses, phone numbers, business addresses, and the name servers (the DNS servers that answer for a domain). Attackers collect these facts from public data such as WHOIS (a public directory that lists who owns a domain). Some also use Active Scanning (T1595) or Phishing for Information (T1598). Where the victim uses third-party cloud such as Microsoft 365, some domain properties sit behind public API endpoints. Two well-known examples are GetUserRealm and autodiscover. A single question to these endpoints can confirm that an organization uses Microsoft 365 and reveal its tenant name. The result helps the attacker in three ways. It shows places for more reconnaissance. It shows operational resources, such as mail systems and VPN gateways. And it shows possible paths for initial access, such as a lookalike domain built for phishing.

In this guide you will first watch a short simulation of one recon run, scene by scene. You will then read both sides of the story: how attackers work, and what defenders see in their logs. The detection deep dive gives realistic log samples, five Sigma rules and matching Splunk SPL queries. A real-world scenario, mitigation lists, common mistakes and a glossary close the page. By the end, you should be able to explain this sub-technique to your team and tune its detections at work.

Why should you care?

  • Domain recon comes before most outside attacks. If you can see the recon, you get an early warning of the attack that follows.
  • Public records expose forgotten hosts. Old subdomains and stale records are common first doors into a company.
  • Contacts, addresses and mail records feed social engineering and lookalike phishing. The recon makes the later attack feel real.
  • Detection here is cheap. DNS logs and public certificate feeds usually already exist in your environment.
  • A canary subdomain is a near zero-noise tripwire. Any team can plant one this week and alert on the first query.

Red Team View: How Attackers Do It

This section explains how attackers map a domain, so you can think one step ahead and build better defenses. It is written for learning and defense only. Collect data only about systems you own or have written permission to test, because probing other people's domains can break laws and provider terms.

When attackers use it

  • Attack planning. This is one of the first steps in outside reconnaissance, long before any intrusion. A domain map shows web portals, VPN gateways, mail systems and test hosts.
  • Phishing preparation. Knowing the real domain, its mail records and its naming style helps an attacker register a lookalike that feels trustworthy at first glance.
  • Finding forgotten systems. Old staging hosts and retired projects stay listed in certificates and DNS long after people stop caring for them. Attackers hunt exactly this kind of system.
  • Pre-positioning. While listing names, an attacker also notes which ones point at removed cloud services, because those can sometimes be claimed silently.

How it works, in order

  1. WHOIS the base domain. One lookup returns the registrar, creation and expiry dates, name servers and public contact data.
  2. Search certificate lists. A search for the domain returns every certificate that ever named it, and each certificate names its hosts.
  3. Run passive tools. Tools such as subfinder collect names from public sources without touching the victim.
  4. Guess names with a wordlist. The tool asks DNS for vpn., mail., staging., test. and thousands of similar names.
  5. Pull the records for each hit. A, MX, NS, TXT and CNAME records turn a name into an address, a mail path or a cloud service.
  6. Try one AXFR. A zone transfer asks a name server for a copy of the whole zone. Well-configured servers refuse.
  7. Check cloud endpoints. If mail hints at Microsoft 365, questions to autodiscover and GetUserRealm confirm the tenant.
  8. Plan the next step. The attacker ranks the findings: unlisted admin panels, old apps, and the shape of a good lookalike domain.

Where it happens

The work is fully external. Attackers run it from a home laptop, a cheap cloud host, or a rented VPN. In ATT&CK terms this is the PRE platform: the activity happens before the attacker has any access to the victim. Public DNS resolvers, WHOIS servers and certificate lists answer most questions. Only the wordlist phase touches victim systems directly, because each guessed name is a real query to the victim's public DNS servers. No exploit, no credentials and no malware are needed at this stage. That is why the attack chain starts so quietly.

Why they want it, and what they need

Each finding enables a next step. A found VPN name leads to password attacks on the login page. Public contacts feed convincing phishing mail. Mail records show the provider, and the provider shapes the spoofing plan. Tenant data opens the door to cloud-focused attacks. Prerequisites are almost none: no victim access, no special hardware, and no budget beyond time. Free tools cover the whole workflow. The needed skill is low, which is why this sub-technique appears in nearly every outside attack, from hobbyists to organized groups.

Safe lab example

The commands below are the classic starting point of domain recon. Run them against example.com, which is reserved for documentation, or against a domain you own. The output lines are fake but shaped like real answers. The victim addresses use the documentation range 192.0.2.0/24.

lab-domain-recon.sh — safe starter commands
# Lab only: run against a domain you own, or against example.com
$ whois example.com
Registrant Name:         EXAMPLE ORGANISATION
Registrant Contact Email: dns-admin@example.com
Registrant Phone:         +1.5550100
Registrar:                Example Registrar, Inc.
Creation Date:            2011-04-19T04:00:00Z
Name Server:              NS1.EXAMPLE.NET
Name Server:              NS2.EXAMPLE.NET

$ dig example.com A +noall +answer
example.com.        3600  IN  A     192.0.2.10

$ dig example.com MX +noall +answer
example.com.        3600  IN  MX    10 mail.example.com.

$ dig -x 192.0.2.15 +noall +answer
15.2.0.192.in-addr.arpa.  3600  IN  PTR   mail.example.com.

What the output means. The WHOIS block gives the owner, the registrar contact, a phone number and the two name servers. An attacker now knows who to imitate and where the zone lives. The A record maps example.com to 192.0.2.10, where its web server answers. The MX record says that mail for the domain goes to mail.example.com. The PTR record confirms that 192.0.2.15 really is the mail host. Each line is small on its own, but together they turn a name into a small map of the company.

Ethics warningRecon tools are dual use by design. Collecting data about domains you do not own can violate computer misuse laws, bug bounty scopes and provider terms. Aggressive DNS guessing can also load servers enough to cause real harm. Practice on example.com, on domains you own, or in a home lab, and keep permission in writing for anything else.

Blue Team View: How Defenders See It

From the defender side, domain recon is mostly silent but not invisible. The queries must cross your public DNS servers. New certificates must appear in public lists. Cloud probes must touch your mail flow or your web servers. Each step leaves records you can alert on today.

Traces the attacker leaves

  • Bursts of queries against your public DNS zone, often from one source address, spread over seconds or minutes.
  • Queries for random or wordlist names such as a8f3.example.com; most end in NXDOMAIN.
  • AXFR attempts in the DNS logs of your name servers. A safe server refuses them, and the refusal is logged.
  • Probes to cloud paths such as /autodiscover/autodiscover.xml on your mail-facing web servers, often with odd user agents.
  • New certificates near your brand in public certificate lists, including lookalike names you did not request.

Traces it does NOT leave

  • No malware or exploit. Nothing installs, nothing crashes, and endpoint tools stay quiet.
  • No failed logins. The attacker does not touch authentication, so your identity logs show nothing new.
  • Nothing from pure reading. WHOIS lookups and certificate searches happen on other people's servers. You cannot see them at all.
  • No direct alert. There is no agent, no EDR event and no firewall deny to raise a hand. The signal lives in ordinary traffic logs.

Where to look

SourceWhat to collectWatch for
Authoritative DNS server logsQuery name, client address and response code per query (BIND query log, Windows DNS analytic log, Zeek dns.log).Bursts from one source, NXDOMAIN storms, AXFR attempts, any hit on a canary name.

SIEMAll of the above, time-aligned in one place.The same source address appearing in DNS, web and mail logs close together.

Why early visibility matters

Domain recon precedes almost every outside attack. Phishing needs believable domains and real staff names. Initial access often starts at a forgotten system that recon uncovered. If you detect the recon, you gain time that nothing else in the chain gives you. You can close a door before anyone knocks on it. You can warn the teams that own the named systems. This is also one of the cheapest detections in security operations, because the logs already exist. The main work is turning them into a few good alerts.

How it fits the attack chain

In ATT&CK terms, T1590.001 feeds several later steps. The subdomain list feeds T1595 Active Scanning, which checks which doors are alive. The brand and mail knowledge feeds T1583.001 Acquire Infrastructure: Domains, where lookalike domains are registered. The contacts feed T1589 Gather Victim Identity Information. The lookalikes then carry T1566.002 Spearphishing Link mail, which aims at Initial Access. Detecting recon at T1590.001 cuts the chain at its quietest link, long before an exploit is written or a phishing mail is sent.

Defender mindsetAssume someone is listing your doors right now, from a laptop, for free. You cannot hide the list, because DNS, WHOIS and certificate records are public by design. What you can do is know the list better than the attacker. Remove everything that should not be on it, plant tripwires on it, and watch the logs while it is being read. That is exactly what the detection deep dive in the next section builds.

5.2Threat Intelligence

Threat intelligence tells you who does domain recon, how they do it, and what they do next. That helps you tune thresholds and brief management. Domain recon is common to nearly all outside actors. A few groups are known for doing it unusually well, or for unusual goals.

Sources worth following

SourceWhat you getHow to use it
OSINT news, blogs and researchFresh cases of lookalike domains, takeover abuse and phishing infrastructure.Turn each case into a pattern to hunt for in your own DNS and certificate feeds.
MITRE ATT&CK siteThe shared language for the behavior, including the T1590 family and procedure notes.Tag detections and reports with T1590.001 so the whole team means the same thing.
Vendor reports (Microsoft, Mandiant, CrowdStrike)Named groups, tooling details and campaign timelines.Extract registrar names, hosting choices and naming patterns the actors favor.
CISA / FBI advisoriesGovernment-confirmed cases with indicators and recommended actions.Check the advisories against your own zones and brand; alert on overlap.
Commercial feedsNew registrations near your brand, passive DNS history, WHOIS history.Feed lookalike names into mail filtering, DNS blocking and the rules in 5.5.

Intel workflow: collect, analyze, apply

  1. Collect. Stream new certificate entries for your brand. Watch your domains in public certificate search sites. Pull passive DNS history for your zone. Save WHOIS snapshots on a schedule.
  2. Analyze. Diff new certificates against your known inventory. Cluster lookalike domains by registrar and mail server. Score each finding by how close it sits to your brand.
  3. Apply. Feed confirmed names into the SIEM rules in 5.5. Open registrar abuse and takedown requests. Brief the SOC on active brand abuse with concrete examples.

Turn the reporting into detections. Each report on this list contains reusable facts: the registrars the actors liked, the naming patterns of their lookalike domains, the hosting providers they used, and the tooling they ran. Extract those facts into three lists: a lookalike pattern list for rule R5, a registration watch list for brand monitoring, and a set of expected-log notes for the rules in 5.5. Refresh the lists when a new report appears, and date every change so the SOC knows how current the patterns are.

If you have no intelligence team. Start small and stay regular. Read the official ATT&CK page for T1590.001 once, then skim vendor blogs and CISA advisories for the word "domain" in their infrastructure sections. One hour per week is enough to keep the pattern lists alive. Write every finding in the same three lines: what was seen, which of your domains it touches, and which rule should carry it. A small habit beats a big project that never starts.

5.4Logs and Patterns

Each log source below covers one or more threats from 5.3, and each one feeds a Sigma rule in 5.5. All values are fake and safe. Host and address roles: the attacker sits at 203.0.113.50 (network 198.51.100.0/24), the victim network is 192.0.2.0/24, and the victim zone is example.com.

The six sources see different moments of the same run. The authoritative DNS servers see the name guessing and the zone transfer try, because those questions must reach the owner of the zone. Zeek sees the same DNS traffic when it crosses the network, with cleaner fields for counting. The mail-facing web server sees the cloud probes. Endpoint logs see only the step that matters most: an internal machine resolving a lookalike name. The public certificate feed sees steps that happen on other people's servers, which is why it is the only source for the registration phase. Read them together and the run becomes one story with timestamps.

1. BIND query log — canary and wordlist hits (threat 2, rule R1)

/var/log/named/queries.log — BIND query log
12-Jan-2026 09:14:02.101 queries: info: client @0x7f8a2c 203.0.113.50#53412 (example.com): query: vpn.example.com IN A +E(0)K
12-Jan-2026 09:14:02.214 queries: info: client @0x7f8a2c 203.0.113.50#53413 (example.com): query: mail.example.com IN A +E(0)K
12-Jan-2026 09:14:02.327 queries: info: client @0x7f8a2c 203.0.113.50#53414 (example.com): query: staging.example.com IN A +E(0)K
12-Jan-2026 09:14:02.440 queries: info: client @0x7f8a2c 203.0.113.50#53415 (example.com): query: canary.example.com IN A +E(0)K
  • One client address asks for many different service names in under a second. That is the shape of an enumeration run.
  • The names follow wordlist order (vpn, mail, staging), not natural user behavior.
  • The canary name canary.example.com appears in no link, no mail and no certificate you own. Any hit is a tripwire.

3. BIND name server logs — zone transfer attempt (threat 3, rule R3)

queries.log + security log — AXFR denied
12-Jan-2026 09:14:40.812 queries: info: client @0x7f8a2c 203.0.113.50#49152 (example.com): query: example.com IN AXFR -E(0)K

  • Any AXFR attempt from outside your name server group is reconnaissance. Approvals belong only to your secondary servers.
  • The refusal line proves the control works. Keep logging it, and alert on it anyway.
  • Allowlist your real secondaries by address, so the rule stays quiet for them.

5.5Sigma Rules (Detection as Code)

The five rules below map one to one onto the top five threats of section 5.3: R1 covers threat 2 (canary and wordlist probing), R2 covers threat 5 (NXDOMAIN burst), R3 covers threat 3 (zone transfer), R4 covers threat 4 (cloud tenant enumeration), and R5 covers threat 1 (lookalike resolution). Rule 1 and rule 5 are near zero noise. Rules 2 and 4 need a threshold tuned to your own zone. Rule 3 should stay quiet once your secondaries are allowlisted. Each rule shows the Sigma YAML first, with the matching Splunk SPL directly after it.

R1 · DNS Wordlist and Canary Subdomain Probing

This rule catches a source that asks for common service names under your domain, or for your canary subdomain. It fires at high level because a canary hit is almost never a false positive. The main false positive is an approved scanner that probes the same names. Change the name list to fit your own zone.

sigma/r1-dns-wordlist-canary-probing.yml
title: DNS Wordlist and Canary Subdomain Probing
id: 8c3f1d62-94a7-4e25-b1c9-6f0d8a47e253
status: stable
description: Detects a source asking for common service names such as vpn, mail,
  staging or test under the victim domain, or any query for the canary subdomain.
  This covers threat 2 of section 5.3, hidden portal discovery. A canary hit alone
  is a strong recon signal with almost no noise. Adjust the name list to your zone.
references:
  - https://attack.mitre.org/techniques/T1590/001/
author: Detection Engineering Team
date: 2026/09/29
logsource:
  category: dns
  product: linux
  service: named
detection:
  selection_wordlist:
    qname|endswith: '.example.com'
    qname|contains:
      - 'vpn.'
      - 'mail.'
      - 'staging.'
      - 'test.'
  selection_canary:
    qname|startswith: 'canary.'
  condition: selection_wordlist or selection_canary | count() by src_ip > 10
falsepositives:
  - Approved vulnerability scanners that probe the same names
  - Monitoring tools that check VPN and mail names on a schedule
level: high
tags:
  - attack.reconnaissance
  - attack.t1590.001
Splunk SPL — same logic (R1)
index=dns sourcetype=bind:queries qname="*.example.com"
| regex qname="^(vpn|mail|staging|test)\.|^canary\."
| bin _time span=5m
| stats count as probe_queries dc(qname) as distinct_names by _time src_ip
| where probe_queries > 10
R2 · DNS NXDOMAIN Burst from One Source

This rule counts NXDOMAIN answers per external source in a five-minute window. Most guessed names do not exist, so a wordlist run produces a wave of misses. It fires at medium level. The main false positives are broken internal software and misconfigured mail servers, which the private-range filter removes.

sigma/r2-dns-nxdomain-burst.yml
title: DNS NXDOMAIN Burst from One Source
id: 51e7b9a4-2c6d-4f83-9a70-3d4e5c6b7a91
status: stable
description: Counts NXDOMAIN answers per external source in a five-minute window
  on Zeek dns.log data. A wave of misses from one address is the classic shape of
  a wordlist enumeration run. This covers threat 5 of section 5.3, bulk mapping.
  Tune the threshold of 40 to sit just above your measured normal noise.
references:
  - https://attack.mitre.org/techniques/T1590/001/
author: Detection Engineering Team
date: 2026/09/29
logsource:
  category: dns
  product: zeek

Deploying the five rules

Roll the rules out in three steps. First, run every rule in search-only mode for one week and collect the counts. Second, set each threshold just above your measured noise, and allowlist your approved scanners, your secondary name servers and your roaming mail clients. Third, switch on alerting: page on R1 and R5, which are near zero noise, and queue R2, R3 and R4 for normal triage. Test each rule against the matching log sample in 5.4 before it ships, and keep the YAML and the SPL in the same repository so they never drift apart. Review thresholds monthly, because your zone and your tools will change.

Real-World Scenario: Copy-cat names — the Ghostwriter lookalike domains

This scenario is based on public reporting by Mandiant and Google Threat Analysis Group about the Ghostwriter operation and the group Mandiant tracks as UNC1151, disclosed in January and February 2022. Details are simplified for learning. All host names, addresses and mail text in the examples are fake.

Background

Starting around 2017, an actor tracked by Mandiant as UNC1151 ran the Ghostwriter operation. Public reporting by Mandiant and Google TAG in 2022 described how the group targeted military and defense organizations in Poland, Latvia and Lithuania. The group registered lookalike copies of the targets' real domains. It used the copies for credential phishing, and public reporting links the stolen access to content changes that pushed false stories. Everything the group needed for the first step was public: the real domain names, their registration data, their certificates, and their naming style. Domain properties were the raw material of the whole campaign.

Attack and response timeline

Phase 1 · Target list

Picking the targets

The actors chose military and defense organizations in three countries. The targets differed in size and network, so a single exploit would not fit them all. But they all had one thing in common: their domain data was public and readable by anyone.

Phase 2 · Domain recon

Reading the public records

The actors read WHOIS records of the real domains and searched public certificate lists. They learned the naming style, the registrars in use, and the names of public contacts. This is T1590.001 in its plainest form: quiet reading, no intrusion.

Phase 3 · Lookalike domains

Registering the copies

The actors registered lookalike names. Public reporting describes small changes, such as swapped letters or added words, that read like the real domain at first glance. Privacy services hid who owned the new domains.

Phase 4 · Certificates

Getting HTTPS ready

The actors obtained TLS certificates for the lookalike names. Certificates must appear in public Certificate Transparency lists, so this step left a visible trace. Few organizations watched those lists at the time.

Phase 5 · Credential phishing

Fishing with trusted-looking names

The group sent mails that looked like internal messages. Links led to login pages on the lookalike domains. Public reporting describes targets receiving documents that looked like real organizational mail. Some recipients entered their credentials.

Phase 6 · Use of access

From passwords to influence

Stolen credentials gave the actors a hold inside target mail and content systems. Public reporting links Ghostwriter access to edited or published content that pushed false narratives. The phishing stage and the influence stage worked together.

Phase 7 · Detection and disclosure

Researchers connect the dots

Researchers clustered the lookalike registrations by registrar, privacy pattern and hosting choices. All three are domain properties. Mandiant tracked the group as UNC1151 and published its assessment in January 2022. Google TAG reported on the campaigns in the same period.

Phase 8 · Response

Takedowns and hardening

After disclosure, affected organizations and platform providers moved against the lookalike domains. Defenders blocked the names, reset exposed credentials and briefed staff. The case became a standard example of why brand and certificate monitoring matters.

How it was detected

Detection came from three sides, and none of them needed a malware alert. First, recipients and mail security saw sender domains that were close to, but not exactly, the real ones. Second, researchers watching public certificate lists noticed new certificates for names near the targeted brands. Third, analysts clustered the registrations themselves: same registrar habits, same privacy setup, same hosting pattern. The cluster was made of domain properties, which is the lesson of this page. The public reports from Mandiant and Google TAG in early 2022 turned those clusters into a named campaign.

Containment

  1. Block the confirmed lookalike domains in mail filtering, DNS filtering and web proxies.
  2. Reset credentials for accounts that entered data on a lookalike page, and revoke their sessions.
  3. Report the lookalike domains to the registrars and request takedown.
  4. Publish a short warning to staff with screenshots of the fake mails, so new reports can come in.

Recovery

  1. Review the affected accounts for new mail rules, forwarding addresses and app grants.
  2. Hunt for sign-ins from the attacker hosting ranges over the previous weeks.
  3. Add the confirmed lookalike patterns to certificate, DNS and mail monitoring, as in rules R1 to R5.
  4. Brief staff again, with a simple rule: check the sender domain letter by letter before entering credentials.

Impact and consequences

  • Business: staff credentials were exposed, and public reporting links the access to false content published under trusted names. Trust is the currency of defense organizations, and it took a direct hit.
  • Business: takedowns, monitoring contracts and staff time carried real cost, across several countries at once.
  • Technical: attackers held valid mail-style access for a time, which let them read threads and imitate internal tone.
  • Technical: the campaign forced monitoring changes: brand watch, certificate watch and lookalike DNS rules became standard asks.

Lessons learned

  • Your records are the input. The attackers built the whole campaign from public domain data. Treat your domain records as an attack surface, not as paperwork.
  • Certificates betray preparation. Lookalike phishing needs HTTPS, and HTTPS leaves a public trail. Watch certificate lists for your brand.
  • Patterns beat single names. One lookalike is easy to block. Clustering registrar, privacy and hosting patterns finds the whole campaign.
  • Privacy cuts both ways. The actors hid behind privacy services. Use privacy for your own domains, and expect it on hostile ones.
  • Recon detection buys time. The phishing mails were the loud step. The domain steps came weeks earlier and were watchable all along.
Team response and communicationIn a case like this, the SOC owns the watch: it adds the lookalike patterns to the rules and watches for internal lookups. IT owns DNS and mail changes. The security lead talks to leadership with three facts only: what was faked, who was exposed, and what changed. Staff hear a short, blame-free message with screenshots, because reports from staff are the fastest sensor in this scenario. Legal and communications own registrar abuse reports and any public statement. The tone stays factual and calm: the case is about preparation and process, not about blaming anyone for clicking.

Mitigation and Defense

No single control stops domain recon, because most sources are public by design. Layered defense works instead. Shrink what the public map shows, watch the map for changes, and be fast when something moves.

Enterprise defenses

  1. Keep a current domain inventory. List every domain, subdomain and certificate you own, with an owner per record. You cannot defend a list you do not have.
  2. Lock the registrar down. Turn on MFA and registry lock for every registrar account, and keep recovery codes offline.
  3. Turn on WHOIS privacy. Hide staff names, emails and phone numbers from the public record so they cannot feed social engineering.
  4. Deny AXFR to everyone. Allow zone transfers only to your approved secondary name servers, and log every refusal.
  5. Avoid wildcard DNS records. A *.example.com record makes every guessed name answer and removes your best signal.
  6. Plant canary subdomains. Add fake names to the zone and alert on the first query, as in rule R1.
  7. Watch certificates and brand names. Stream new certificate entries and watch new registrations near your brand.
  8. Log public DNS and mail-facing web hosts. Feed the logs into the five rules of section 5.5.
  9. Publish mail authentication. Set DMARC, SPF and DKIM so lookalike mail cannot easily spoof your real domain.
  10. Pre-register common lookalikes. Register the frequent typo and hyphen variants of your brand before someone else does, and keep a takedown runbook.

Home & small business defenses

Attackers run the same playbook against personal and small-business domains, just with less noise. If you own a domain, these habits cover most of the risk:

  • Turn on WHOIS privacy. Your registrar offers it, often free. Keep your home address and phone number out of the public record.
  • Keep renewals on. Expired domains get bought within minutes and often become phishing hosts with your old name on them.
  • Check yourself in certificate lists. Search your domain in a public certificate search site once in a while. Every name you find there should be one you know.
  • Do not leak subdomains. Staging names and admin URLs in public code or README files end up in attacker wordlists.
  • Remove old records. The blog you hosted years ago does not need its DNS record anymore. Delete what you no longer serve.
  • Use MFA everywhere. If a lookalike page does catch a password, MFA is what stops the login.

Layered defense, from quick wins to advanced

After that, every new domain joins the system on day one, and the layers just keep running.

Common Mistakes and Best Practices

This section is aimed at SOC analysts and detection engineers in daily work. Each mistake below is common, cheap to fix, and directly useful to an attacker who runs the playbook on this page.

Use the table as a review agenda, not as a wall poster. Pick two rows per month, check the current state, and fix what is broken. Most rows need one person for one afternoon. The order matters less than the habit: a team that checks two rows every month finishes the list twice a year, and the rows that failed last time are the ones to recheck first.

MistakeWhy it hurtsBetter way
Leaving AXFR open to the worldOne request hands the attacker your whole zone, including names you never published.Allow transfers only to approved secondaries and log every refusal.
Keeping wildcard DNS recordsEvery guessed name answers, so wordlist probing returns nothing to detect.List names explicitly and let wrong names return NXDOMAIN.
No certificate or brand monitoringLookalike certificates are the attacker's most public step, and you miss it.Stream certificate entries and alert on unexpected names near your brand.
Dismissing recon alerts as harmless noiseEnumeration is the earliest warning you will ever get, and ignoring it wastes the head start.Triage recon alerts with a short runbook: check the source, check the names, close the named doors.
Internal names on public certificatesPublic certificate lists leak your internal naming system to anyone who looks.Use split-horizon DNS and never request public certificates for internal-only names.
Stale records with no ownerEvery dead record is a door: a takeover target or a name worth imitating.Give records owners and expiry dates, and review the zone on a schedule.
Registrar account without MFAOne stolen password can move your name servers and take every service with it.Enable MFA and registry lock, and store recovery codes offline.
Watching only exploits, not preparationTools that look for malware see nothing here, so the earliest stage stays dark.Fund the cheap detections on this page; they cover the stage EDR cannot see.

Best practices checklist

  • Every domain, subdomain and DNS record has a named owner and a purpose written down.
  • AXFR is denied to everyone except approved secondaries, and refusals are logged.
  • The public zone has no wildcard record and no dangling CNAME to a removed service.
  • Internal names never appear in public certificates or public DNS answers.
  • A certificate monitor alerts on new entries for all company domains, including lookalikes.
  • At least one canary subdomain exists, and a query for it pages someone.
  • The five Sigma rules run in the SIEM and were tuned against real data.
  • Registrar accounts use MFA and registry lock, WHOIS privacy is on, and DMARC, SPF and DKIM are published.

Run the checklist as a quarterly audit with a named owner per line. Tick a box only with evidence: a screenshot of the registrar settings, a copy of the named.conf allowlist, or a link to the SIEM rule. Keep the evidence in one place, because it doubles as audit material for the frameworks in section 5.1. When a new domain or a new name server appears, the checklist is also the onboarding list for it.

Track the progress in one number your management understands: the count of open checklist lines. A falling number shows the program works, and a flat number starts the right conversation. Pair it with the alert counts from section 5.5, and you can show both sides in one slide: hygiene is improving, and the tripwires are still quiet.

Closing thoughtDomain recon wins because it is free, quiet, and ahead of every defense that only looks at exploits. Flip each part. Make your map small, make your changes loud, and make the reading visible in logs. A team that sees the recon can close doors before anyone knocks on them.

Glossary of Key Terms

Every technical term used in this guide, explained in simple words.

Domain
A named address on the internet, such as example.com. Companies use domains for websites, mail and remote access.
Subdomain
A name under a bigger domain, like vpn.example.com. Teams use subdomains for separate services.
Top-level domain (TLD)
The last part of a domain name, such as .com or .org. It sits at the top of the naming system.
Registrar
A company allowed to sell and manage domain names. The registrar records who owns a domain and renews it each year.
WHOIS
A public directory that answers questions like "who owns this domain?". It returns registrar, dates, name servers and sometimes contact data.
Name server
A DNS server that answers questions for a domain. The name servers are listed in the domain's public records.
DNS record
A single entry in DNS that stores one fact about a name, for example its address or where its mail goes.
A record
The DNS record that maps a name to an IPv4 address, like example.com to 192.0.2.10.
MX record
The DNS record that says which server receives mail for a domain, with a priority number for each server.
CNAME
A DNS record that points one name at another name, so the first name follows the second one.
NXDOMAIN
The DNS answer that means "this name does not exist". A long run of NXDOMAIN from one source is a sign of name guessing.
AXFR (zone transfer)
A DNS request that asks a name server for a copy of the whole zone. Safe servers refuse it for everyone except their own secondaries.
Canary subdomain
A fake name you plant in your zone and never publish. Any query for it is a strong signal, like a tripwire.
Certificate Transparency (CT) log
A public list where TLS certificates must be recorded. Searching it by domain reveals many host names, including hostile ones.
Lookalike domain (typosquat)
A domain registered to look like a real one, using small changes such as swapped letters. It is the base of many phishing campaigns.
Autodiscover and GetUserRealm
Public endpoints in Microsoft cloud mail that answer questions about a domain without a login. They can confirm cloud use and reveal tenant names.
Tenant
An organization's separate space in a cloud service, such as Microsoft 365. Knowing the tenant name helps an attacker aim cloud attacks.
