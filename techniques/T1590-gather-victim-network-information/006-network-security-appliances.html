T1590.006

Network Security Appliances

Security appliances are the guards of a network: firewalls, VPN gateways, proxies, and filters. Attackers study these guards from outside to find the weak door. This guide shows their tricks and the logs that expose them.

01

Overview: What Is This Technique?

MITRE ATT&CK is a free, public knowledge base about real attacker behavior. It lists the steps criminals take, one entry at a time, and gives each step an ID. This page covers one entry: T1590.006, Network Security Appliances. It belongs to the tactic Reconnaissance. That is the homework phase, when the attacker studies the target before any attack starts.

With this technique, an attacker gathers facts about the victim’s security appliances. The official MITRE description names the targets: firewalls, content filters, proxies and bastion hosts, and network intrusion detection systems (NIDS). A firewall filters traffic. A content filter blocks unwanted web or mail content. A proxy or bastion host is a controlled gateway into a network. A NIDS is a sensor that watches traffic and raises alarms. The attacker wants the brand, model, and software version of each guard. Why? Every version number maps to a list of known CVEs (public weakness IDs). Leaked or default credentials often match too. With that list, the attacker picks a key that fits instead of guessing for months.

The attacker collects these facts in three main ways. They use Active Scanning (T1595): they touch your edge systems directly and read what the systems say about themselves. They use Phishing for Information (T1598): they ask staff trick questions by email or chat. And they read victim-owned websites: office photos, job posts, and setup documents often name the vendor for free. This homework leads to more recon, to developing or obtaining exploit tools, and finally to initial access. A common entry point is an external remote service, such as a VPN. In this guide you will watch an animated simulation, then see both attacker and defender views. After that, a full detection deep dive gives you log examples, five Sigma rules, and Splunk SPL.

Why should you care?

  • Appliances sit at the network edge. They are the first systems the internet touches, so attackers study them first.
  • Many big breaches in recent years started at a VPN or firewall appliance, not at an office laptop.
  • Fingerprinting leaves logs. If those logs reach your SIEM (your central log store), you can catch the attacker weeks before an exploit.
  • A live appliance inventory lets you patch in days when a vendor publishes an urgent fix.
  • Detection engineers get cheap, high-value alerts from portal probes, banner grabs, and scan alerts.

Red Team View: How Attackers Do It

This section explains how attackers fingerprint security appliances, so you can understand the method and defend against it. It is for learning and defense only. Run these actions solely against systems you own or have written permission to test.

When attackers use this technique

Appliance fingerprinting happens early in the chain, while the platform is PRE. First, it guides target selection: a VPN appliance with a known bug is worth far more than a random web server. Second, it prepares exploitation (T1190) and phishing (T1598). Third, it tunes follow-up scanning, so scanners focus on the exact models found. The best version of this technique needs no victim contact at all, because public scan databases already store the answers.

How the fingerprint is built

  • Scan databases. Shodan and Censys scan the internet non-stop and store the banners that devices self-report. One product filter shows brand, model, and version without sending a single packet to the target.
  • Banner grabbing. Many services announce their software in the first bytes of an answer. An HTTP head request with curl, or a raw connection with nc, is often enough.
  • Admin-portal URL patterns. Vendors use fixed portal paths, so one request can name the vendor: /remote/login (FortiGate style), /dana-na (Pulse style), or /loginsso (Citrix style).
  • Version scanning with nmap. The -sV option probes open ports and guesses product and version from protocol replies. It is louder, but it works when the banner is short.
  • Certificate fields. The TLS certificate of a portal often names the vendor, the model, or an internal naming pattern. Tools like sslscan read it in seconds.
  • Open sources. Office photos with badges, job posts that name a vendor, and public setup documents give the brand away for free. Attackers also buy or trade leaked appliance details in criminal forums.

Where, why, and what is needed

Where: from anywhere on the internet. Attackers use their own infrastructure, a rented VPN, or a cheap cloud host. Passive database lookups come first; direct probes come second.

Why: each finding enables the next step. A version number maps to CVEs. A portal path names the vendor. A certificate hints at internal naming. A job post confirms the vendor estate. Together they pick the door for T1190.

Prerequisites: low skill and low cost. Free tools, a browser, and public databases cover most of it. If management ports are closed, banners hidden, and databases hold nothing, the attacker falls back to slow trial and error.

Simple step list

  1. Search scan databases for your own public addresses and see what an attacker sees for free.
  2. Grab banners with curl or nc for every exposed service.
  3. Request the common admin-portal paths and note which one answers 200.
  4. Read certificate fields with sslscan for extra vendor hints.
  5. Map every found version to vendor advisories and CVE feeds.
  6. Rank the doors by weakness, then hand the list to the exploit step (T1190).
04

Blue Team View: How Defenders See It

From the SOC side, appliance fingerprinting is one of the friendliest techniques to catch, because every active probe lands in some log. The hard part is that those logs often stay on the appliance itself and never reach the central log store.

Artifacts to look for

  • Admin-portal probes in appliance or web logs: requests to /remote/login, /dana-na, /global-protect/login.esp, or /loginsso from outside your office and VPN ranges.
  • Version-scan IDS alerts: signatures with names like ET SCAN, fired on appliance ports.
  • Bare TLS handshakes from one source: many short connections to 443, 8443, 22, or 23 that carry almost no data.
  • Your own appliances listed in scan databases with visible versions. Search Shodan and Censys for your public ranges on a schedule.

What traces it leaves — and what it does not

Active probes leave traces: web requests in appliance and front-proxy logs, connection records in network sensors, and IDS alerts. Passive collection leaves nothing on your network. When an attacker reads a scan database or buys leaked details in a forum, your side records no event at all. That is why you should also look outward: watch the scan databases yourself and keep the versions you publish as small as possible.

Where to look

Check four places. First, appliance local logs: VPN, firewall, and WAF events, shipped to the SIEM. Second, web or proxy logs in front of the portals. Third, network sensors: Zeek, IDS, and firewall connection logs. Fourth, external scan-database monitoring for your public addresses. If an appliance can only log to itself, install a syslog forwarder that copies events out. A guard that whispers to itself protects nobody.

Why early visibility matters

Between 2020 and 2024, mass exploitation of VPN appliances was one of the most common ways into companies. Public CISA directives and vendor advisories documented the wave, and attackers fingerprinted portals and versions before every exploit. If you do not watch appliance logs, you miss the cheapest and earliest warning you will ever get.

How it fits the attack chain

This technique is pure PRE homework. It feeds T1190, Exploit Public-Facing Application: the profile picks the door, the exploit opens it. It feeds T1595, Active Scanning, which sharpens the picture, and T1598, Phishing for Information, which fills gaps from staff. After access, attackers often keep using the stolen credentials or session tokens on the VPN. Blocking fingerprinting does not stop the whole chain, but it makes every later step slower, louder, and easier to catch.

Defender mindsetYour guard devices talk about you all day — listen to their logs. Ship every appliance log to the SIEM. Alert on portal probes. Treat a new scan-database entry for your addresses like an alarm, not as trivia.

5.2Threat Intelligence

Good appliance intelligence starts with free sources. Vendor advisories tell you which versions are weak. CISA and FBI advisories describe whole campaigns. ATT&CK tells you who does this and why. The table below shows where to look, what you get, and how to use it.

SourceWhat you getHow to use it
OSINT (news, blogs, forums)Early hints of new edge-appliance bug chatterWatch for your vendors; raise a patch ticket the same day
MITRE ATT&CK siteOfficial technique notes and procedure examplesAnchor detections and threat-profile reviews to T1590.006
Vendor reports (Microsoft, Mandiant, CrowdStrike)Actor tradecraft and tooling detailsTurn reported probe patterns into new detection logic
CISA / FBI advisoriesConfirmed exploited bugs and response stepsMatch KEV entries to your inventory; patch and hunt
Commercial feedsMachine-readable indicators and actor trackingFeed blocklists and enrich SIEM alerts with context

A simple loop keeps this useful. Collect weekly, analyze with one question, then apply in three moves.

Collect

  1. Keep a live inventory of every appliance with brand, model, version, and public exposure.
  2. Watch vendor advisories and the CISA KEV catalog for your exact versions.
  3. Monitor scan databases for your public ranges and alert on new or changed banners.

Analyze

  1. Ask one question for every new item: which of our appliances does this touch?
  2. Rate exposure: is the affected appliance internet-facing and unpatched?
  3. Note the probe patterns that precede the bug, from advisories and reports.

Apply

  1. Open a patch ticket the same day for anything internet-facing.
  2. Write or update a detection for the probe patterns you noted.
  3. Brief the SOC, so analysts recognize the exploit in logs, not in a news article.

5.5Sigma Rules (Detection as Code)

Sigma is an open format for writing a detection rule once and running it in many different SIEM products. Each rule below is complete and valid. Open a rule to read its YAML, and use the matching Splunk SPL right after it. Field names are written in a generic style, so map them to your own sources before rollout. All five rules target probing and preparation, not exploitation, which makes them safe high-signal alerts. Each rule maps to one of the top five threats in 5.3.

5 rules · 5 matching SPL queries
R1 - VPN admin portal probing

Catches one outside source that walks the admin-portal paths of several VPN vendors. Level: high. Main false positive: your own approved scanners.

Sigma YAML — R1
id: 3f6a9c2e-8b14-4d27-9a5f-6c0e12b7d401
title: VPN Admin Portal Probing from One External Source
status: stable
description: Detects one external source requesting many known VPN admin portal
  paths in a short window, a classic appliance fingerprinting step (T1590.006).
references:
  - https://attack.mitre.org/techniques/T1590/006/
author: Detection Engineering Team
date: 2026/09/29
logsource:
  category: webserver
  product: apache
  service: access
detection:
  sel_portal:
    c-uri|contains:
      - '/remote/login'
      - '/dana-na'
      - '/global-protect/login.esp'
      - '/loginsso'
      - '/admin'
  condition: sel_portal | count() by client_ip > 10
falsepositives:
  - Your own approved vulnerability scanners
  - Uptime monitors that check the login page
level: high
tags:
  - attack.reconnaissance
  - attack.t1590.006
Splunk SPL - same logic
index=web sourcetype=access_combined
  (uri_path="/remote/login*" OR uri_path="*/dana-na*" OR uri_path="/global-protect/login.esp*" OR uri_path="*/loginsso*" OR uri_path="/admin*")
| stats count AS portal_probes dc(uri_path) AS paths_tried BY clientip
| where portal_probes > 10
| sort - portal_probes

Catches banner and version probing: many TLS sessions that open but carry no client data. Level: medium. Main false positive: health checks and load balancer probes.

Real-World Scenario: Reading the guard’s badge — VPN appliance hunts

This is a realistic composite based on CISA Emergency Directive 19-01 and public vendor/CISA advisories (2020-2023); details simplified. It follows one company through three documented waves of edge appliance exploitation: Pulse Connect Secure (CVE-2019-11510), FortiOS credential leaks (CVE-2018-13379), and Citrix Bleed (CVE-2023-4966). All names, addresses, and log lines are fictional.

Background

Edge and VPN appliances were hit in three well-documented waves. In January 2020, CISA issued Emergency Directive 19-01 after attackers exploited Pulse Connect Secure with CVE-2019-11510. The bug let strangers read files through path traversal and collect credentials and session files. From 2020 to 2021, crews mass-scanned Fortinet FortiOS devices for a similar path-traversal bug, CVE-2018-13379, and downloaded login files with working passwords. In late 2023, CISA warned about Citrix Bleed, CVE-2023-4966. It steals live session tokens, so the attacker can log in without any password.

The story below follows the same recipe every time. The attacker fingerprints the appliance make, model, and version from banners and login pages. Then they match a known CVE. Then they exploit it, steal credentials or session tokens, and log in as users. The defenders in the story catch the pattern with the alerts from section 5.5.

Attack chain timeline

Day 0 · 09:14

Pick the building

The attacker queries a public scan database for the company’s address range. The database answers with banners: an EdgeVPN-style appliance at vpn.example.com, version 6.0.4, portal at /remote/login. The victim saw nothing, because no packet touched its network.

Day 0 · 15:40

Read the name tag

From a rented cloud host, the attacker grabs the banner again and walks the portal paths. One request to /remote/login returns a login page; the appliance web log records it as a single line from 203.0.113.50. The badge now names the vendor, the model, and the version.

Day 0 · 17:05

Match the key

The attacker checks CVE feeds for the exact version. A known path-traversal bug for this model leaks session files with usernames and passwords. Public advisories describe the trick in detail.

Day 2 · 03:10

Try the key

At night, the attacker probes the known paths, in the style of /remote/fgt_lang?lang=/../../... The first requests return 404. One crafted request returns 200, which means the leak may be live.

Day 2 · 03:26

Empty the pocket

The bug leaks session files. The attacker downloads a small dump: usernames, hashed and plain passwords, and session identifiers. In the Citrix Bleed wave, the same step stole live session tokens instead.

Day 3 · 01:44

Knock with stolen keys

The attacker tests the credentials on the VPN portal. The auth log records a burst of failed logins for admin, root, test, and several staff names, all from one source. One attempt succeeds.

Day 3 · 02:02

Walk in

The attacker logs in as two staff members over the VPN. With a stolen session token, no password is even needed. They move slowly and look for valuable data, exactly as the advisories describe.

Day 4 · 08:15

The alarm rings

The SOC gets an alert from rule R4: a failure burst from one external source. A review of the web log finds the R1 portal probes from the same address days earlier. The hunt for stolen sessions starts.

Day 4 · 09:00

Answer

The network team patches the appliance and rotates every session secret. The SOC kills all active sessions and forces re-login. Staff must re-enroll MFA. The hunt continues for weeks.

How it was detected

The SOC analyst on duty saw the R4 alert: more than five failed VPN logins from 203.0.113.50 within four minutes, many usernames tried. That alert came from the appliance auth log in the SIEM.

A back-check of the web log then showed the R1 portal walk and the R3 path probes. They came from the same source on Day 0 and Day 2. The probes were visible days before the login burst. Nobody had tuned those rules to page anyone, which became a lesson.

Containment

  1. Patch or upgrade the appliance to the fixed version at once.
  2. Rotate every session secret and invalidate all active sessions.
  3. Force a full re-login and re-enroll MFA for all VPN users.
  4. Block the source address and the rented host range at the edge.
  5. Preserve logs and the leaked file list as evidence.

Recovery

  1. Rebuild the appliance from a known-good configuration and keep banners hidden.
  2. Reset all VPN passwords and confirm MFA works for every account.
  3. Hunt for reused stolen sessions for several weeks; tokens can outlive the patch.
  4. Review internal logs for the two abused accounts, from first login to last action.
  5. Report the incident per policy and confirm closure with the security lead.

Impact and consequences

Business: one day of emergency work, locked-out staff during the reset, a customer notice, and an audit question about patch speed.

Technical: two staff accounts misused for about a day. Session tokens stayed valid until the rotation, which shows why rotation matters as much as patching.

Lessons learned

  • Fingerprint probes are the early warning. The R1 and R3 alerts fired two days before the break-in. Tune them to page.
  • Rotate, do not only patch. Patching closed the bug; rotating credentials and session secrets closed the stolen keys.
  • Session tokens are keys too. Token theft (Citrix Bleed style) works even on patched boxes until every secret rotates.
  • Ship appliance logs to the SIEM. The auth burst alert only existed because the logs left the box.
  • Own your badge. Hidden banners and closed management ports make the free intelligence useless.
  • Drill the wave. When an advisory lands, run the whole loop: inventory, patch, rotate, hunt.
Team response and communication

The SOC lead opened a priority-one case and kept one running timeline. The network team patched and rotated secrets the same morning. The SOC lead told leadership plain facts: what happened, what is fixed, and what is still open. No blame, no guesses.

IT told staff what to expect: forced re-login, MFA re-enrollment, and slower VPN access for a day. The comms team sent customers a short note: what was detected, what was patched, and what protection changed, citing the vendor advisory instead of rumors. One spokesperson, one fact sheet, one timeline.

Public sources: CISA Emergency Directive 19-01 (January 2020, Pulse Connect Secure CVE-2019-11510); CISA warnings and vendor advisories on Citrix Bleed (CVE-2023-4966), late 2023; vendor advisories on FortiOS CVE-2018-13379 and public reporting on mass scanning of VPN appliances (2020-2021); MITRE ATT&CK T1590.006 procedure examples. This scenario is a realistic composite; details are simplified for learning, and only ED 19-01 is cited by ID.

Mitigation and Defense

MITRE states plainly that this technique cannot be easily mitigated with preventive controls. The real defense is to minimize the amount and sensitivity of data available to external parties. Publish fewer banners. Close management doors. Watch the probes that remain. No single control does the job, so the stack below layers several.

Enterprise defenses

  1. Keep an asset inventory of every appliance with brand, model, version, and public exposure.
  2. Run an emergency patch lane for edge devices: edge CVEs get fixed in days, not months.
  3. Put management interfaces on a separate VLAN with an allowlist and MFA, and never publish them.
  4. Disable or hide version banners and verbose server headers where the vendor allows it.
  5. Replace end-of-life devices; a guard without patches is a wall without bricks.
  6. Ship central logs from every appliance to the SIEM, including auth and web events.
  7. Monitor scan databases for your own public addresses and alert on new entries.
  8. Scan your own edge benignly and on a schedule, before attackers do it for you.
  9. Rotate appliance credentials and session secrets after every vendor leak, and enforce MFA on VPN portals.
  10. Put a WAF or CDN in front of web portals to absorb low-effort scans.

Home & small business defenses

  • Update your router and modem firmware regularly; old routers are the home version of an unpatched edge.
  • Turn off WAN-side remote administration, so the management portal is not reachable from the internet.
  • Change every default password on day one; default credentials are the first thing attackers try.
  • Put smart devices on a separate guest network, away from work devices.
  • Check once a quarter what your router shows about itself from outside, using an online port checker.
  • If you run a small business VPN, patch it like an enterprise edge and check its logs monthly.

Common Mistakes and Best Practices

This closing section is aimed at SOC analysts and detection engineers in daily work. These are the mistakes we see most often around appliance security, each with a better way.

MistakeWhy it hurtsBetter way
Appliance logs never shipped to the SIEMThe cheapest early warnings stay unread on the box.Forward every appliance log and alert on portal probes.
Management portal public for convenienceAny attacker can probe and spray it all day, from anywhere.Separate VLAN, strict allowlist, MFA, never public.
Patching only internal systems, not the edgeThe edge faces the internet and gets hit first.Include appliances in the emergency patch lane.
Hiding the banner treated as patchingThe CVEs stay; only the name tag is gone.Hide banners and patch; never one instead of the other.
Rotation skipped after a vendor leakA patched box still honors the old key that leaked elsewhere.Rotate passwords and session secrets after every leak.
No appliance inventoryVendor alerts cannot be matched to your estate, so triage stalls.Keep a live list with brand, model, version, exposure.

Best practices checklist

  • Inventory all appliances with versions and public exposure.
  • Ship all appliance logs to the SIEM and keep them searchable.
  • Alert and page on admin-portal probes, bare TLS sweeps, and CVE path probes.
  • Maintain an emergency patch lane for edge devices.
  • Keep management interfaces on a separate VLAN with allowlist and MFA.
  • Hide banners where possible, but never instead of patching.
  • Monitor scan databases for your own public addresses.
  • Rotate appliance credentials and session secrets after every vendor leak.
Closing thoughtAppliance fingerprinting is reconnaissance, not attack — but it decides the attack. If your guards cannot be read, cannot be reached, cannot stay unpatched, and cannot be probed quietly, the attacker’s shopping list stays empty.

Glossary of Key Terms

Every technical term used in this guide, explained in simple words.

Security appliance
A dedicated box (or virtual box) that guards network traffic, such as a firewall or a VPN gateway.
Firewall
A guard that allows or blocks traffic between network zones according to rules.
VPN appliance
A remote door into a private network, used by staff who work from outside the office.
WAF (Web Application Firewall)
A web shield that filters requests to web applications and blocks common web attacks.
NIDS (Network Intrusion Detection System)
A traffic watchdog that raises an alarm when it sees something bad, but does not block it.
Content filter
A guard that blocks unwanted web or mail content before it reaches users.
Proxy / bastion host
A controlled gateway that stands between users and a protected network.
Banner grabbing
Reading the self-announced greeting of a service to learn its software name and version.
Fingerprinting
Collecting small details (banners, paths, certificates) to identify the exact brand and version of a system.
CVE
Common Vulnerabilities and Exposures: a public ID number for a known weakness in software.
Scan database
A public search engine, like Shodan or Censys, that indexes internet-facing devices and their banners.
Path traversal
A trick that uses sequences like ../.. in a URL to read files outside the intended folder.
Session token
A temporary digital pass that keeps you logged in; stealing it can mean access without a password.
Credential stuffing
Testing many leaked username and password pairs against a login page until one works.
MFA
Multi-factor authentication: a second proof of identity, such as a code from an app, beyond the password.
SIEM
Security Information and Event Management: the central store where logs are searched and alerts are raised.
PRE
The ATT&CK platform label for actions that happen before the attack touches the victim.
