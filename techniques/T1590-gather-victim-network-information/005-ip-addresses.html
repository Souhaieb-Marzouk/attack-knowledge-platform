T1590.005

IP Addresses

Public IP addresses are the doors of your network. Attackers collect whole address blocks from public databases, then walk those blocks door by door. This guide shows the method, the traces it leaves, and the detections that catch it.

01

Overview: What Is This Technique?

MITRE ATT&CK is a free, public catalog of attacker behavior. It sorts attacks into tactics and techniques. A tactic is the goal of an attack. A technique is the way an attacker reaches that goal. This guide covers one early step that comes before most attacks: learning about the victim. T1590.005 belongs to the Reconnaissance tactic. That tactic covers all information gathering that happens before the intrusion starts. ATT&CK marks this technique with the platform label PRE. The label means the preparation stage, before an attacker touches your systems.

T1590.005 is called Gather Victim Network Information: IP Addresses. Attackers gather the victim's IP addresses that they can use during targeting. Public IP addresses are often given to organizations as a block, or as a range of sequential addresses. The list of addresses can show which addresses are in use. It can also show the size of the organization, its locations, its Internet service provider, and where its public systems are hosted. Attackers read this data in RIR and WHOIS records (public directories that list who owns which addresses). They also collect it with active scanning.

This guide moves from seeing to defending. The simulation shows how one known address grows into a full block map. The red team view explains the attacker's steps. The blue team view shows which traces appear in your logs. The detection deep dive gives you a regulation map, threat intelligence, ranked threats, realistic log examples, five Sigma rules with matching Splunk SPL, and a real-world scenario. The guide ends with mitigations, common mistakes, and a glossary of every term. Every section uses safe, fake data, so you can copy the examples into your own lab.

Why should you care?

  • Your public addresses are your attack surface. Every address you announce on the internet is a door an attacker can knock on.
  • Address blocks are public by design. Anyone can read WHOIS records and see every range your organization owns.
  • The sweep has a clear shape. One external source touching many of your addresses in a short time is easy to detect with the right rules.
  • Forgotten addresses are the weakest doors. Old hosts inside old ranges rarely get patches or monitoring.
  • It feeds every later step. The address list powers active scanning (T1595) and, in the end, initial access.
How to read this guide

Watch the simulation first to build a picture in your mind. The red and blue team sections then explain the same steps from both sides. Section 5 is your work reference: use its tables, log samples and Sigma rules when you build or tune detections. Keep the glossary open for any new term.

03

Red Team View: How Attackers Do It

This section explains how attackers collect address data and why the data is so useful to them. It is written for learning and defense, so you can understand the method well enough to detect and reduce it. Only test systems you own or have written permission to test.

When attackers do this

Attackers collect addresses early, right after they pick a target. The trigger is usually one seed item: a single address from a mail header, or a domain name from an earlier step. Collection happens before active scanning (T1595) starts. Because everything is public, this work can happen days or weeks before any packet reaches the victim.

How they do it, step by step

  1. Start from one seed address or a domain name.
  2. Run whois on the address and write down the range, the CIDR and the owner.
  3. Search the RIR portals for every range with the same owner name or ID.
  4. Check a BGP looking glass for every prefix the organization announces.
  5. Confirm each range with a Team Cymru IP-to-ASN lookup.
  6. Check DNS history and scan databases for known live services.
  7. Record the full list of ranges as the scan scope.
  8. Then plan active scanning (T1595), slowly and with a clear purpose.

Where and why

Where

Everything here is external and public. The queries go to registries and route collectors, not to the victim. An attacker can run this from a laptop, a VPN exit, or a rented cloud host. The victim cannot see these queries, so there are no traces on the victim side. Collection costs nothing, so attackers repeat it before every campaign.

Why

  • Full ranges give full scan scope, so nothing is missed by guessing.
  • Forgotten ranges often have forgotten security.
  • Direct-to-origin addresses let attackers skip CDN protections.
  • Owner names and locations feed phishing and social engineering.

What is needed (prerequisites)

Very little is needed: one seed address, public data sources and patience. No malware and no victim contact are required. This low cost is why attackers of every skill level use this step. The noise level is also zero until the attacker chooses to start scanning, which leaves the defender one observable transition to catch.

Working quietly

Attackers keep this stage quiet on purpose. Public queries cost nothing, so there is no reason to rush. Many groups re-run the collection step before every campaign, because ranges change: new blocks appear and old blocks go away. A map that is six months old can send a scan at addresses that no longer exist, or miss a range that does. Fresh data is cheap, so the collection step never really stops.

Each finding opens a next step for the attacker. The block list defines the scan scope. The owner name and registration contacts feed phishing lists. Announced prefixes confirm which addresses are reachable today. A single quiet sweep then turns the scope into a list of live doors. The rules in section 5.5 are built to break exactly this chain: they make the sweep loud while it happens.

Ethics and legality

Reading public registry data is passive and generally legal, but scanning addresses you do not own is not allowed in most networks and laws. In a lab, use only documentation addresses such as 192.0.2.0/24 and 198.51.100.0/24, which are reserved for examples. At work, scan only your own ranges or systems where you have written permission.

04

Blue Team View: How Defenders See It

From the SOC side, the collection step is invisible, because the attacker reads public databases. It becomes visible the moment collection turns into scanning. The job of the SOC is to know its own address space completely and to catch that transition fast.

Artifacts to look for

  • Wide, slow sweeps. Many of your addresses touched by one external source within minutes or hours, mostly denied by the firewall.
  • Raw-IP web requests. Requests that arrive with an IP address in the Host field instead of a domain name.
  • PTR bursts. Many reverse DNS lookups for your address range from one external source.
  • Short banner connections. Connections to 21, 22, 23 or 3389 that open, take one answer and close at once.
  • Your assets in scan databases. Services from your ranges listed on Shodan-like services, sometimes days before any direct contact.

Where traces appear

Firewall / NetFlowDeny lines and flow records: one source, many distinct destination addresses in your public ranges
Web server logsRaw-IP Host fields, HEAD requests, odd methods, 404 and 400 bursts from one client
DNS server logsReverse lookup (PTR) bursts against your in-addr.arpa zone
Network telemetry (Zeek)Connections in state S0 or REJ for sweeps; state RSTO with tiny answers for banner grabs
External monitoringYour own EASM checks and scan-database watches showing new or forgotten services

What leaves no trace

Registry reads leave nothing on your systems. During the collection phase there are no endpoint artifacts, no mail logs and no DNS queries to your servers. Do not expect an alert that says someone read your WHOIS record. EASM scans from your own side are the only way to see what the registries show about you. The sweep is the first observable step, so the sweep is where your detections must live.

Why early visibility matters

Your IP footprint is your attack surface. An attacker with your full range list can test every door instead of guessing, so nothing you expose stays hidden by not being found. A forgotten range is worse than an open port: it is a row of doors that no guard watches. Early detection means the attacker's map stays incomplete and wrong, which makes every later step harder and louder for you to see. The reverse is also true: if you catch the sweep, you know the attacker's map has gaps, and you can change your exposure before they return.

What the SOC does with it

When a sweep alert fires, the SOC can act while the attacker is still mapping. Confirm that the source is unknown, then check what it touched. Addresses that answered deserve a patch and an exposure check the same day. The source goes to the block list and to a watch rule, because the same host often returns. If the source touched only one or two addresses, it is probably research. If it walked the whole block, the intent is different and the case goes to escalation. The alert also tells the asset team which addresses answered at all, because every answer is an asset that must be in the inventory.

How it fits the attack chain

This technique sits before Initial Access. The address list feeds active scanning (T1595) and vulnerability scanning (T1595.002). Together they point to exposed remote services, and access often comes through External Remote Services (T1133). The same list also guides host recon (T1592) and security-appliance recon (T1590.006). Stopping the map early degrades every step that follows.

Defender mindset

You cannot remove your addresses from the internet, but you can know exactly which addresses are yours and watch all of them. A current inventory of announced space plus flow data on every public segment turns quiet recon into a visible pattern.

Wide address reconnaissance itself is rarely a reportable event. The failures it exploits are. Auditors ask whether you know your own assets, whether you watch them, and whether you react to anomalies. Those questions appear in almost every framework that touches security operations. Intel workflow

  1. Collect: check your announced prefixes daily. Check your scan-database footprint weekly. Save every advisory that mentions range scanning.
  2. Analyze: compare every finding with your IP inventory. Each mismatch is a finding with an owner and a deadline. Look for the actor habits listed below.
  3. Apply: feed new exposed assets into patching and monitoring. Feed known scan sources into block and alert lists. Tune the rules in 5.5 to the reported port sets and rates.

Use the actor table when you tune. If reported actors scan ports 21, 23, 80, 443 and 3389, your probe-burst rule should include that port set. If a report gives timing, compare it with your thresholds. Intel that changes a rule is intel that pays for itself. Share the tuned thresholds with the SOC, so an alert never surprises the analyst who reads it.

5.4Logs and Patterns

The patterns below show what T1590.005 looks like the moment it leaves the public databases and touches your systems. Each block uses one log source with fake but realistic values, followed by the signals worth alerting on. All addresses come from the documentation ranges, so nothing here points at a real network. Field names match a common parsing pipeline; check the names in your own environment before you build rules. One habit helps: read each raw line once, slowly. The pfSense line puts the action before the ports. The Zeek line hides everything in JSON fields. The Apache line ends with the Host field. Once you can read each format by eye, tuning becomes a field-mapping exercise instead of guesswork. Every example uses the documentation ranges: 192.0.2.0/24 for the victim, and 203.0.113.0/24 plus 198.51.100.0/24 for the attacker side. Replace them with your own ranges when you test, and keep the fake ones out of production rules.

  • Sequential names: 44, 45, 46, which shows a scripted walk, not user behavior.
  • Your own DNS servers should never answer this pattern for outsiders, so the queries themselves are the signal.
  • PTR sweeps are rare for legitimate visitors, so a low threshold works.

Four sources cover all five rule-backed threats: firewall logs, Zeek conn.log, web logs and DNS logs. If you lack one source, the others still cover the pattern, because a real sweep touches all of them at once. If you collect Zeek or flow data, prefer the Zeek rules first: conn.log sees every attempt, even when the firewall allows it. The firewall rules catch the same sweep on the deny path. Between the two, a sweep must appear in at least one place.

5.5Sigma Rules (Detection as Code)

The five rules below are starting points, not finished products. They map one to one to the top five threats in section 5.3: R1 covers threat 1, R2 threat 2, R3 threat 3, R4 threat 4 and R5 threat 5. Each rule name, logsource and threshold matches the log examples in section 5.4. Tags use attack.reconnaissance and attack.t1590.005. Tune thresholds and field names to your environment, and start every rule in alert-only mode. Each rule body states in one sentence what the rule catches, its alert level and its main false positive. The rules follow the same skeleton: one selection, one timeframe and one aggregation. That shape keeps the cost low on large data and makes every rule easy to explain in a review. If a rule fires, the alert should carry the grouped source, the count and the timeframe, so the analyst sees the shape at once.

Test each rule on historical data before you trust it. Replay a documented scan exercise against a lab range, or replay a busy week of production logs with the rule in search-only mode. A good rule fires on the exercise, stays quiet on normal admin work, and keeps its runtime under a few seconds on your data volume.

Keep the rules in version control next to your IP inventory. When a new range goes live, update the inventory and review the thresholds the same week. Rules and inventory that drift apart produce either silence or noise, and both cost you trust.

Review the rule set twice a year. Remove rules that never fired and never will fire. Split rules that fire too often into a more specific version instead of raising the threshold into uselessness. Keep one changelog line per change, so the next engineer knows why a threshold moved.

Real-World Scenario: Half a million doors a day — the range scanners

This scenario is based on real public reporting: CISA alert TA18-106A, Russian State-Sponsored Cyber Actors Targeting Network Infrastructure Devices (2018). The alert describes the campaign pattern. The victim, the dates and the details below are a simplified reconstruction for learning.

Background

In 2018, CISA published alert TA18-106A about Russian state-sponsored cyber actors, linked to the GRU 85th Main Special Service Center. The actors scanned very large IP ranges. At peak times they covered more than 500,000 addresses per day. They looked for network infrastructure devices on ports such as 21, 23, 80, 443 and 3389. The results fed later attacks on routers and switches: credential attempts, device compromise, and interception of traffic. The alert is the single public source for this scenario.

Attack chain

Before day 1

The target list

The actors pick broad address ranges that belong to their target sectors. Public registry data narrows the list to ranges that are announced and alive. Nothing touches the victims yet, so nothing shows up in any log.

Day 1, continuous

The range scan

The sweep starts across the chosen ranges. At peaks it covers more than 500,000 addresses per day. The probes target ports 21, 23, 80, 443 and 3389, the usual doors of network device management and web interfaces.

Days 2 to 14

Device discovery

Devices that answer reveal banners with vendor and model names. The actors collect the answers into a device list. Routers and switches with web or telnet management stand out first.

Weeks 3 to 6

Credential attempts

The actors try default and weak credentials on the management interfaces they found. Many devices in the list were never reconfigured from the factory. One success is enough to continue.

Week 6

Device compromise

The actors log into the device. They change configurations to keep access and, in some cases, switch off logging or monitoring on the box. The device now belongs to their toolset.

After access

Traffic interception

From a compromised device on the path, the actors read the traffic that crosses it. They harvest more credentials and map the internal network. The device becomes a base for the next step of the campaign.

Detection day

The pattern surfaces

The SOC network team sees spikes of uniform probing in the firewall logs. Every probe has the same shape, the same ports and steady timing, which looks like one tool rather than many users. The team matches the pattern to the TA18-106A description.

Same week

Containment

The team closes management exposure from the internet. They add access control lists that limit which sources can reach management networks. Admin access moves to VPN only, with multi-factor authentication.

Weeks after

Recovery and hardening

The team rotates every device credential, installs firmware updates and re-images suspect boxes. Flow monitoring and canary addresses go live on every public segment, so the next sweep is loud instead of quiet.

How it was detected

Three signals came together. First, the SOC network team saw firewall spikes of uniform probing across the ranges: same ports, same timing, same shape. Second, an external surface review checked the organization's RIPE and ARIN records against the IP inventory and found ranges nobody managed. Third, an exposure check showed management ports reachable from the internet. The analyst who joined all three findings had the TA18-106A pattern in one case, not three loose events.

Containment

  • Close management exposure: no admin ports reachable from the internet.
  • Add ACLs that allow only known admin sources to reach management networks.
  • Move all admin access to VPN only, with multi-factor authentication.
  • Watch the affected ranges with canary addresses during the cleanup.

Recovery

  • Rotate every device credential, including local accounts and SNMP strings.
  • Install current firmware and re-image devices that show signs of access.
  • Restore and verify device configs from known-good backups.
  • Turn on flow monitoring and alerting for every public segment.

Impact and consequences

For the business, the main risk is quiet: attackers who read traffic and hold device access can wait, choose the moment and move deeper. Trust suffers most if customers learn that their traffic crossed a compromised device. For the technical teams, the costs are firmware work across the estate, credential rotation everywhere, and new monitoring that must stay on. Compared with a full breach, an early catch keeps the cost small; compared with doing nothing, the difference is the whole campaign.

Lessons learned

Volume does not equal stealth

Half a million addresses per day is loud. Uniform shape, not low volume, is what defenders must alert on.

Management doors decide

The campaign succeeded through ports 21, 23 and 3389. Closing management exposure removes the whole path.

Know your ranges

The review that compared RIPE and ARIN records with the inventory found the blind spots first.

Old devices fail first

Factory credentials and old firmware are the easy entry. A patch schedule for devices is a must, not a nice-to-have.

Shape beats thresholds

Threshold alerts missed the sweep because the rate was spread out. Grouping by source and shape caught it.

Watch after the fix

Canaries and flow monitoring turned the next sweep into an immediate alert instead of a weeks-long campaign.

Team response and communication notes

  • SOC: raise the uniform-probe spike as one case and attach the evidence chain, so leadership sees one story, not loose events.
  • Network team: close the management exposure, write the ACLs, and document what was reachable from where for the report.
  • Incident response: hunt for access on every device in the scanned ranges before closing the case.
  • Message to leadership: state what happened, what is closed now, and what remains open with dates. Avoid blame and unproven claims.
  • Tone: calm, factual and short. Update on a fixed schedule until the case closes.
Public sources

CISA, Russian State-Sponsored Cyber Actors Targeting Network Infrastructure Devices, CISA Alert TA18-106A (2018), cisa.gov/news-events/alerts/ta18-106a. This is the only source used for the scenario.

Mitigation and Defense

No single control stops address-space reconnaissance, because the data is public by design. Defense works in layers: shrink what is announced, close the doors the sweep probes, watch everything that remains, and make the transition from recon to scanning loud.

Start with the inventory, because every other layer depends on it. A rule that watches “all public addresses” silently watches only the addresses your tools happen to see. Once the inventory is right, closing doors becomes a checklist, and the detection rules in section 5.5 cover what is left. Two habits keep the layers honest. First, test from the outside: a scan of your own ranges shows what an attacker sees, and the result is a to-do list with hosts on it. Second, measure detection: count how many test sweeps your rules caught, and review the misses. Both habits cost little and find drift early.

Enterprise defenses

  • Keep an authoritative IP inventory. List every announced range, review it monthly and check it against BGP data.
  • Return or firewall unused ranges. Decommission systems without an owner.
  • Close management exposure. No admin ports reachable from the internet, with no exceptions.
  • Move admin access to VPN only, with multi-factor authentication for every account.
  • Add ACLs around management networks that allow only known admin sources.
  • Allowlist CDN addresses at web origins so direct-IP access fails.
  • Send flow and deny logs from every public segment to the SOC, not only from the main range.
  • Plant canary addresses in each range and alert on any touch.
  • Patch edge devices fast and track appliance banners as part of the inventory.
  • Run a quarterly external exposure review that compares scan-database results with the inventory.

Home & small business defenses

A home connection normally gets one dynamic address from the provider, so large-scale harvesting matters less. The same ideas still help, and they work for a small office too:

  • Switch off WAN ping answers on the router.
  • Remove port forwards you do not need.
  • Switch UPnP off, because it opens doors by itself.
  • Install router firmware updates on a schedule.
  • Use a strong, unique password for the router admin page.
  • Check your own address in scan databases once in a while.

Layered defense

LayerActionWhy it works
1 · Quick winWrite the authoritative list of all announced IP space and review it monthlyYou cannot defend addresses you do not know you own
2 · Quick winClose management ports from the internet and move admin access to VPN onlyThe sweep finds fewer doors, and found doors need stolen credentials
3 · Quick winReturn or decommission ranges and systems you do not needFewer announced addresses mean fewer doors to watch
4 · MonitoringSend NetFlow or firewall logs from every public segment to the SOCWide sweeps become visible as one-source-many-hosts patterns

Revisit the table every quarter. Quick wins age into routine work, and routine work drifts without an owner. Give each row an owner and a review date, and keep the table next to the IP inventory. When a new range appears, walk the table again for that range before it goes live. Total prevention is impossible, but a small, watched surface with loud detection is a poor target.

Common Mistakes and Best Practices

This section is aimed at SOC analysts and detection engineers in daily work. Each mistake below comes from real audit and incident findings, and each one maps directly to this technique. They are ordered by how often they appear in audits. The better way column gives the practical fix.

Most of these mistakes share one root cause: the address space is invisible in day-to-day operations. Firewalls, cloud consoles and DNS servers each hold a part of the truth, and nobody joins the parts. The fixes below therefore look boring on purpose. They build one shared picture and keep it current, which is exactly what this technique abuses when that picture is missing.

MistakeWhy it hurtsBetter way
No authoritative list of your own IP rangesNobody can say what is yours, so scans and canaries have blind spotsBuild an IP inventory and check it against BGP data monthly
Management ports reachable from the internetOne probe finds the door and one weak password opens itVPN-only admin, ACLs and no exceptions
Trusting that a small block stays invisibleRanges of every size are swept every day, including single /29sWatch every address, not only the main range
Dropping scans silently without loggingRecon repeats for weeks with no record and no pattern to correlateLog denies, keep flow data, alert on one-source-many-hosts
Answering every probe with a resetEach reset confirms the address is live and speeds up the mapDrop instead of reset where safe, and tarpit obvious sweeps
Ignoring raw-IP web requestsThey show that someone found the origin address and skipped DNSAlert on IP-shaped Host fields with rule R3 from section 5.5
Never checking PTR activityReverse sweeps map your names quietly, weeks before any direct attackAlert on PTR bursts against your in-addr.arpa zone with rule R5

Fix the first three rows before you tune anything else. An inventory, closed management ports and a smaller footprint remove most of the value of this technique. A weekend of work is often enough for the inventory, and one firewall change closes the management ports. The detection rows then work on a much smaller and quieter surface, which makes their alerts cleaner and their thresholds easier to set. They pay off on every future incident.

Use the checklist as a quarterly review, not as a one-time project. Tick an item only when you can show evidence: a report, an alert or a log query. Items that stay unticked for two quarters in a row belong in the backlog with a date, not in the meeting notes.

Best practices checklist

  • Keep one authoritative list of every announced range and update it monthly.
  • Compare BGP announcements with that list and investigate every difference.
  • Return or firewall ranges you do not use.
  • Close management ports from the internet and keep admin access behind VPN.
  • Collect flow and deny logs on every public segment.
  • Run the five Sigma rules from section 5.5 and tune them to your ranges.
  • Put canary addresses in each range and alert on any touch.
  • Check scan databases for your own ranges on a schedule.

Two mistakes deserve a second look. Silently dropped scans hide the problem and also destroy the evidence trail for later incidents. And resets sent to every probe actively help the attacker, because each reset confirms a live address. If you change only two things after reading this guide, change those two.

Closing thought

You cannot keep your addresses secret, and you do not need to. Attackers read public databases, so defenders should read them too, and more carefully. Make sure every address is known, needed and watched, and the quiet mapping step loses most of its value.

Glossary of Key Terms

Every technical term used in this guide, explained in simple words.

IP address
A number that identifies a device on an IP network, like a phone number for computers. Example: 192.0.2.10.
IP block (netblock)
A group of consecutive IP addresses owned or rented by one organization, for example 192.0.2.0/24.
CIDR notation
A short way to write the size of an IP block. The number after the slash counts the fixed bits: /24 means 256 addresses.
RIR
Regional Internet Registry. One of five public organizations that give out and register IP blocks, like land registries for IP space.
ARIN
The RIR for North America. Its public search shows who owns a range.
RIPE NCC
The RIR for Europe, the Middle East and parts of Asia.
WHOIS
A public query protocol and record system that shows who owns a domain name or an IP block.
BGP
Border Gateway Protocol, the routing protocol networks use to tell the rest of the internet which address ranges they can reach.
ASN
Autonomous System Number, the ID of one network under one control that speaks BGP, for example AS65001.
PTR record
A DNS record that maps an IP address back to a name. PTR lookups are also called reverse lookups.
Reverse sweep
Many PTR lookups in a row for one address range, usually scripted, to map addresses to hostnames.
Banner grab
A short connection that reads the welcome text a service sends, to learn its software and version without a real login.
Management port
A network port used to administer a device, such as SSH (22), telnet (23) or RDP (3389).
conn.log (Zeek)
The Zeek network monitor's connection record. It logs every connection attempt with a state code such as S0 or RSTO.
NetFlow
A network telemetry standard that summarizes connections, who talked to whom, on which ports and with how many bytes, without recording content.
ACL
Access control list. A firewall rule set that says which sources may reach which destinations.
VPN
Virtual private network. An encrypted tunnel that gives remote users safe access to an internal network.
