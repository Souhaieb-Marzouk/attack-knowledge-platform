Overview: What Is This Technique?

MITRE ATT&CK is a free, public catalog of attacker behavior. It is maintained by a non-profit organization. Every attacker behavior gets an ID, a name, and a place in the attack chain. Defenders use the catalog as a shared language. When a report says T1590.002, every analyst knows exactly which behavior is meant. This page is part 3 of a seven-page series about the T1590 family.

T1590.002 means that an attacker asks questions about the victim’s DNS before an attack. DNS (Domain Name System) is the phone book of the internet. It turns names like example.com into IP addresses that computers can use. Almost every system a company runs has an entry there: the website, the mail service, VPN gateways, and old test systems. Most of these entries are public by design. The attacker asks the public DNS servers small questions. Which address does this name use? Which servers accept mail? Which name servers manage the zone? And what do the TXT records say? The answers build a map of the victim’s internet presence. The map shows the attacker where the doors are and which doors look weak.

This guide shows the full picture in simple English. First, an animated simulation walks through a complete DNS interrogation in eight short scenes. Then you see both sides: what the attacker does, and what the defender can see in the logs. The largest part is a detection deep dive for SOC analysts and detection engineers. It ends with a real-world scenario, a defense checklist, common mistakes, and a glossary.

Why should you care?

  • Recon leaves records. Every question the attacker asks your DNS is written down somewhere. This is often the earliest signal a defender will ever see.
  • Public records are a map. MX records point to your mail servers, NS records to your DNS provider, and TXT records to your cloud vendors. Each answer plans the next step.
  • One setting can undo everything. A single wrong option, allow-transfer { any; }, lets one request copy your whole zone file to a stranger.
  • Subdomains expose doors. Names like vpn or staging reveal remote access points and test systems. Those are often the weakest doors.
  • Cheap detections exist. Counting queries and NXDOMAIN answers per source gives a SOC simple, high-value alerts at almost no cost.

Official ATT&CK description

“Adversaries may gather information about the victim’s DNS that can be used during targeting. DNS information may include a variety of details, including registered name servers as well as records that outline addressing for a target’s subdomains, mail servers, and other hosts. DNS MX, TXT, and SPF records may also reveal the use of third party cloud and SaaS providers, such as Office 365, G Suite, Salesforce, or Zendesk.”

Source: attack.mitre.org, technique T1590.002 (page last modified 2025-10-24)

In simple words: the attacker reads the victim’s public DNS records. Name server records show who runs the victim’s DNS. Address records show the subdomains, mail servers, and other hosts. Mail records (MX) and text records (TXT, SPF) often show which cloud and SaaS providers the company uses. The information can come from direct DNS queries or from Passive DNS (a service that records DNS answers seen on the internet). Open technical databases can also expose it. The result gives the attacker three things: next recon targets, useful resources, and paths to initial access. One example is External Remote Services, the remote login doors such as VPN.

“Adversaries may also use DNS zone transfer (DNS query type AXFR) to collect all records from a misconfigured DNS server.”

Source: official ATT&CK note on T1590.002

A zone transfer is one request for a full copy of the zone. A correctly configured server refuses it. The attempt itself is still written into the server log, and that log line is gold for defenders.

Red Team View: How Attackers Do It

This section explains how DNS recon works in practice, so you can recognize it and stop it. Treat it as defense knowledge. Only test systems you own or have written permission to test.

When would an attacker use this?

DNS recon happens very early. It sits in the Reconnaissance tactic, before any attack touches the victim’s servers. It needs no password and no exploit. Attackers run it while they choose targets and plan the intrusion. Because the platform is PRE, the victim often has no idea that it is happening at all.

Where does it run from?

From anywhere on the internet. Common launch points are the attacker’s own servers, rented cloud hosts, and VPN exit nodes. The queries land on the victim’s public authoritative name servers. Those servers are either provider-hosted or the company’s own BIND servers. If the company also exposes a resolver, the firewall in front of it sees probes too. Nothing has to touch an internal system.

What is needed (prerequisites)?

  • Record queries need nothing special. The phone book is public by design, and any DNS tool works.
  • A zone transfer succeeds only when a name server is misconfigured, for example with allow-transfer { any; }.
  • Subdomain brute force needs only time and a name list.
  • Basic command line skills are enough. Automated frameworks exist for attackers who want scale.

Why do attackers ask these questions?

  • MX records name the mail servers. They reveal the mail provider and the best phishing targets.
  • NS records name the name servers. They reveal the DNS provider and how DNS is operated. Attackers compare this with infrastructure they buy themselves under T1583.002.
  • TXT and SPF records often hold mail rules and cloud verification strings. They quietly list the SaaS vendors. That list feeds phishing and supply-chain targeting later.
  • Subdomains expose portals: vpn, mail, staging, dev, hr. Each name is a possible door, and test systems are usually the weakest ones.
  • AXFR would hand over every record at once, including names that were never meant to be public. One misconfiguration turns recon into a full dump.
  • PTR sweeps turn IP ranges into server names. That makes later scanning and targeting much more precise.

How is it done, step by step?

  1. Record lookups. Tools such as dig, nslookup, and host send single queries for A, AAAA, MX, NS, TXT, CNAME, and SOA records. Each answer is one fact. This step looks exactly like normal traffic, which is why it is so useful to log.
  2. Zone transfer attempts. The attacker asks each name server for a full zone copy with an AXFR request over TCP. Most servers refuse. Attackers still try variations: the other name servers, forgotten secondary servers, and tools that automate the whole check.
  3. Subdomain brute force. A wordlist of likely names is resolved one by one with tools like dnsrecon, fierce, sublist3r, massdns, or amass. A name either answers NXDOMAIN, which means it does not exist, or answers with records, which means it does. The rare hits are the interesting ones.
  4. Reverse lookups. PTR queries sweep the IP blocks that appear in the answers. Each address tells the attacker which name it carries.
  5. Write it down. The findings go into a target sheet: mail hosts, portals, providers, vendors, and who controls the registrar account.

Safe lab example

The commands below use documentation domains and reserved IP ranges, so they are safe to read and run as written. They show the most common question types: normal record lookups, one reverse lookup, and a zone transfer attempt against your own lab server.

dns-recon-lab.txt · safe values only
# 1. Which servers receive mail for the domain?
dig example.com MX +short
#    Answer lines such as "10 mail.example.com" name the mail
#    servers. An attacker reads this as a phishing target list.

# 2. Which name servers are authoritative for the zone?
dig example.com NS +short
#    Answer lines such as "ns1.example.com" name the servers
#    that must be asked (and tested) one by one.

# 3. What do the text records reveal?
dig example.com TXT +short
#    SPF rules and cloud verification strings often list
#    the company's SaaS vendors.

# 4. Which name does this address carry? (reverse lookup)
dig -x 192.0.2.10 +short
#    PTR answers turn bare IP numbers into server names.

# 5. Ask your own lab name server for a full zone transfer.
dig @ns1.example.com example.com AXFR
#    Expected output on a correctly configured server:
#    "transfer failed" or a status of REFUSED.
#    That refusal is the good, expected result.
Ethics note

example.com and the reserved ranges 192.0.2.x, 198.51.100.x, and 203.0.113.x exist for exactly this kind of practice. Against a real domain that you do not own, zone transfer attempts and wordlist brute forcing are noisy and may be illegal without written permission. Practice on your own lab zone, and keep a record of your authorization if you test at work.

Blue Team View: How Defenders See It

From the SOC side, DNS recon is one of the friendliest techniques to detect. The attacker must talk to your name servers, and name servers can keep diaries. If logging is on, the whole interrogation is written down.

What traces does it leave?

  • AXFR-denied lines in the DNS server log: a stranger asked for the whole zone.
  • Query bursts from one external IP with many different names under your zone.
  • NXDOMAIN floods: long runs of answers that say the name does not exist.
  • PTR sweeps: sequential reverse lookups walking an address block.
  • Port 53 scans and blocked probes at the firewall, especially over TCP.
  • IDS alerts for AXFR over TCP/53 and for unusually large DNS responses.

What traces does it NOT leave?

This is just as important for analysts. Pure record lookups of public names look exactly like normal traffic. A single query for example.com A or MX is invisible in a sea of normal queries. Passive DNS collection happens outside your network, so it leaves nothing on your systems at all. There is no malware, no login, and no packet to your web servers. The traces exist only where the questions are answered: your name servers, your resolver, and your firewall.

Where should you look?

  • BIND: the query log and the transfer log (query logging on, plus the xfer-in and xfer-out categories).
  • Windows DNS Server: the analytic and audit event logs, forwarded to a collector.
  • Network sensors: Zeek dns.log gives one JSON line per query and answer pair, with the answer code included.
  • Firewall: pfSense filterlog and similar, for port 53 probes and large TCP flows.
  • SIEM: all of the above should land in one place, for example index=dns and index=fw, where counts and thresholds become alerts.

Why does early visibility matter?

Recon always comes first. Every later step, from phishing to VPN attacks, is planned on top of the answers gathered here. DNS is often the only place where external recon physically touches your systems. The attacker may never send a packet to your web server, mail server, or firewalls. But they cannot avoid asking your name servers. That makes DNS telemetry an early-warning sensor for the whole organization. It is cheap to collect, and it stays small compared to web logs.

Where does this fit in the attack chain?

T1590.002 sits in the Reconnaissance tactic, before the intrusion. Its output feeds other techniques directly. MX and TXT answers feed phishing preparation. Subdomain answers feed initial access against VPN and portal logins, which ATT&CK calls External Remote Services (T1133). NS answers help the attacker pick or buy infrastructure (T1583.002). The same service is abused later for command and control over DNS (T1071.004) once something is inside. If you can see the recon, you can raise monitoring on the exact doors the attacker is likely to try next.

Defender mindset

Assume every public record is already in the attacker’s notebook. Your job is not to hide the phone book. Your job is to know who has been reading it. Turn DNS logging on before you need it, because the questions arrive weeks before the attack does.

5.4Logs and Patterns

Every detection starts with a log line. Below are the main log sources for this technique, one threat cluster at a time. Each source has a realistic fake example and a short list of what to look for. All values use the reserved documentation ranges, so nothing here is a real address.

1. BIND query log — zone enumeration (threat 4)

This is the workhorse source. With query logging on, every question the attacker asks is recorded with the client address. In Splunk we index it as index=dns sourcetype=bind:queries.

/var/log/named/queries.log · fake entry
29-Sep-2026 12:03:57.214 queries: info: client @0x7f9c1c048d40 203.0.113.50#41234 (mail.example.com): query: mail.example.com IN MX +E(0)K (192.0.2.53)
29-Sep-2026 12:03:58.902 queries: info: client @0x7f9c1c048d40 203.0.113.50#41235 (example.com): query: example.com IN TXT +E(0)K (192.0.2.53)
29-Sep-2026 12:04:01.117 queries: info: client @0x7f9c1c048d40 203.0.113.50#41236 (staging.example.com): query: staging.example.com IN A +E(0)K (192.0.2.53)
  • The same client IP (203.0.113.50) asking for many different names under your zone.
  • Short, regular gaps between queries, which means a machine and not a person.
  • Many record types in sequence (MX, TXT, SOA, A), which shows a systematic sweep.
  • Direct queries to your authoritative server from addresses that are not known resolvers.

2. BIND transfer log — AXFR attempts (threat 1)

Zone transfer events live in the xfer-in and xfer-out categories. Route them to their own file, for example xfer.log, indexed as index=dns sourcetype=bind:xfer.

/var/log/named/xfer.log · fake entry
29-Sep-2026 12:04:41.117 xfer-in: info: client 203.0.113.50#41901 (example.com): zone transfer (AXFR) denied
29-Sep-2026 12:06:18.530 xfer-in: info: client 203.0.113.50#42777 (example.com): zone transfer (AXFR) denied
  • The words AXFR or “zone transfer” together with “denied” or REFUSED.
  • Repeated attempts from one source with changing source ports.
  • Attempts against several zones, including reverse zones, which show a systematic survey.
  • The dangerous opposite: a transfer line without “denied”, followed by a very large response. Treat that as an incident, not an alert.

3. Zeek dns.log — NXDOMAIN storms (threat 2)

Zeek (an open network sensor) writes one JSON line per DNS query and answer pair. It includes the answer code, so it is perfect for NXDOMAIN counting. In Splunk we index it as index=dns sourcetype=zeek:dns.

dns.log (Zeek JSON) · fake event
{"ts":"2026-09-29T12:05:02.881420Z","uid":"CwK7fL1aBcD","id.orig_h":"203.0.113.50","id.resp_h":"192.0.2.53","id.resp_p":53,"proto":"udp","trans_id":4711,"query":"vpn1.example.com","qclass":1,"qclass_name":"C_INTERNET","qtype":1,"qtype_name":"A","rcode":3,"rcode_name":"NXDOMAIN"}
  • rcode_name values of NXDOMAIN in long runs from one id.orig_h.
  • Many different query values under your own zone from the same source.
  • Short, machine-like spacing between the queries.
  • A few NOERROR answers inside the storm — those are the attacker’s hits.

4. Zeek dns.log — PTR sweeps (threat 5)

dns.log (Zeek JSON) · fake event
{"ts":"2026-09-29T12:07:44.211006Z","uid":"CxT2gM9zEfH","id.orig_h":"203.0.113.50","id.resp_h":"192.0.2.53","id.resp_p":53,"proto":"udp","trans_id":5210,"query":"10.2.0.192.in-addr.arpa","qclass":1,"qclass_name":"C_INTERNET","qtype":12,"qtype_name":"PTR","rcode":0,"rcode_name":"NOERROR","answers":["web01.example.com"]}

  • query values that walk a reverse zone in order: .10, .11, .12, and so on.
  • NOERROR answers that turn bare addresses into server names.

5.5Sigma Rules (Detection as Code)

The five rules below turn the patterns above into portable YAML. Each rule maps 1:1 to one of the top five threats from 5.3, and each log source matches the examples in 5.4. Each rule block is followed directly by the matching Splunk SPL search. Field names such as query, rcode_name, and id.orig_h assume the log is parsed first; adjust them to your pipeline.

R1 — DNS Zone Transfer (AXFR) Attempt

Catches any AXFR request or refusal in the transfer log; level high; main false positive: an approved secondary name server on its regular schedule.

sigma/dns_zone_transfer_attempt.yml
title: DNS Zone Transfer (AXFR) Attempt
id: 4a9f2c31-6b7e-4d2a-9f41-8c3e5b7d1a02
status: stable
description: Detects attempts to perform a DNS zone transfer (AXFR) against an
    authoritative name server. A successful transfer hands the attacker the
    full list of records of the zone, so every attempt is worth an alert.
references:
    - https://attack.mitre.org/techniques/T1590/002/
author: Detection Engineering Team
date: 2026/09/29
logsource:
    category: dns
    product: bind
    service: xfer
detection:
    keywords:
        - 'AXFR'
        - 'zone transfer'
    condition: keywords
falsepositives:
    - Approved secondary name servers pulling the zone on schedule
    - DNS health monitors that test transfers on purpose
level: high
tags:
    - attack.reconnaissance
    - attack.t1590.002

Read every match. A “denied” line is a warning. A transfer line without “denied” is an incident.

Splunk SPL — same logic
index=dns sourcetype=bind:xfer ("AXFR" OR "zone transfer")
| bin _time span=5m
| stats count as axfr_attempts, dc(src_ip) as sources by _time
| where axfr_attempts > 0
| sort - _time
R2 — Subdomain Brute Force (NXDOMAIN Storm)

Catches one source with more than 60 NXDOMAIN answers for your zone in five minutes; level medium; main false positive: a busy recursive resolver. Scope the rule to your authoritative servers.

sigma/dns_subdomain_brute_force.yml
title: Subdomain Brute Force (NXDOMAIN Storm)
id: 7c2e8b54-1d93-4f6a-b2c7-5e9d0a4f83b1
status: stable
description: Detects a single source receiving many NXDOMAIN answers for names
    under one zone in a short window. Attackers brute forcing subdomains
    produce exactly this pattern, because most guessed names do not exist.
references:
    - https://attack.mitre.org/techniques/T1590/002/
author: Detection Engineering Team
date: 2026/09/29
logsource:
    category: dns
    product: zeek
    service: dns
detection:
    selection:
        rcode_name: 'NXDOMAIN'
        query|endswith: '.example.com'
    timeframe: 5m
    condition: selection | count() by id.orig_h > 60
falsepositives:
    - A recursive resolver serving many users at once
    - Monitoring probes that check many names on purpose
level: medium
tags:
    - attack.reconnaissance
    - attack.t1590.002

The NOERROR answers inside the storm are the hits. Sort the searched names by answer code to find the doors that really exist.

Splunk SPL — same logic
index=dns sourcetype=zeek:dns rcode_name=NXDOMAIN query=*.example.com
| bin _time span=5m
| stats count as nxdomain, dc(query) as unique_names by _time, id.orig_h
| where nxdomain > 60
| sort - nxdomain

Catches one source sending more than 30 PTR queries in ten minutes; level medium; main false positive: a mail server doing routine PTR checks.

R4 — Sensitive-Name Probing

Catches one external source probing several door names (vpn., mail., citrix., jira., staging.); level medium; main false positive: your own staff during normal work. Scope the rule to external sources.

sigma/dns_sensitive_name_probing.yml
title: Sensitive Subdomain Name Probing
id: 9b3e5c72-8a41-4d7f-a6c3-2d8e1b5f47a9
status: stable
description: Detects a single external source probing several short, sensitive
    names such as vpn., mail., citrix., jira., or staging. under the
    victim zone. The attacker is building a list of remote access doors.
references:
    - https://attack.mitre.org/techniques/T1590/002/
author: Detection Engineering Team
date: 2026/09/29
logsource:
    category: dns
    product: zeek
    service: dns
detection:
    selection:
        query|startswith:
            - 'vpn.'
            - 'mail.'
            - 'citrix.'
            - 'jira.'
            - 'staging.'
    timeframe: 10m
    condition: selection | count() by id.orig_h > 15
falsepositives:
    - Employees resolving the VPN or mail names during normal work
    - Monitoring probes that check these names on purpose
level: medium
tags:
    - attack.reconnaissance
    - attack.t1590.002

One probe is noise. A short burst of door names from one outside address is a plan.

Splunk SPL — same logic
index=dns sourcetype=zeek:dns (query=vpn.* OR query=mail.* OR query=citrix.* OR query=jira.* OR query=staging.*)
| bin _time span=10m
| stats count as probes, dc(query) as unique_names by _time, id.orig_h
| where probes > 15
| sort - probes
R5 — High-Volume Unique-Query Enumeration

Catches one source asking for more than 100 unique names under your zone in ten minutes; level low; main false positive: a busy resolver. Tune it to your own traffic.

title: High-Volume Unique-Query Enumeration of a Zone
id: 5d8a1f26-9e37-4b8c-bd54-7a2c6e9f31b8
status: stable
description: Detects a single source asking for an unusually high number of
    unique names under one zone in a short window. This is the pattern of
    broad record sweeps that map a zone and its cloud vendors.
references:
    - https://attack.mitre.org/techniques/T1590/002/
author: Detection Engineering Team
date: 2026/09/29
logsource:
    category: dns
    product: bind
    service: queries
detection:
    selection:
        query|endswith: '.example.com'
    timeframe: 10m

falsepositives:
    - A recursive resolver serving many users at once
    - Large mail providers doing bulk lookups
level: low
tags:
    - attack.reconnaissance
    - attack.t1590.002

This rule is the safety net. It fires even when the attacker spreads the sweep over many record types and avoids NXDOMAIN storms.

index=dns sourcetype=bind:queries query=*.example.com

Real-World Scenario: Before the hijack — studying the DNS roads

This scenario is based on real public reporting: CISA advisory AA19-080A (“DNS Infrastructure Hijacking Campaign”, March 2019). Cisco Talos tracks the same activity as “Sea Turtle”. Details are simplified for learning. The timeline shows the phase that matters for this guide: the reconnaissance that made the hijack possible.

Background

In early 2019, CISA and Cisco Talos described a campaign that hijacked the DNS of many organizations. The targets included telecom providers, internet service providers, government bodies, and NGOs, mostly in the Middle East and North Africa, and also in Europe. The attackers did not break into servers first. They studied each target’s DNS set-up. They asked which name servers answered for the zone and which registrar held the domain. They also listed the subdomains, the mail systems, and the accounts that could change all of it. Later, they stole registrar credentials and changed NS and MX records, which sent traffic and mail through machines they controlled. This scenario focuses on the quiet first phase: the mapping work that made the hijack possible.

Attack chain timeline

Weeks before · target selection

Picking the victims

The group chose organizations whose DNS mattered: providers and companies that many other people depend on. The attackers studied public information to learn which targets owned or managed large parts of DNS. One good target opened doors to many downstream victims.

Week 1 · name server mapping

Mapping the name servers

The attackers pulled NS records for each target domain. They learned which name servers were authoritative and whether the victim ran them itself or used a provider. Self-hosted BIND servers promised possible misconfigurations. Provider-hosted zones pointed the attackers toward the provider accounts instead.

Week 1 · registrar mapping

Finding the registrar behind each domain

WHOIS lookups (public directory entries that list who owns a domain) revealed the registrar for each target. The attackers now knew which company’s login portal held the keys to the NS records. They built a list of registrar accounts to study and, later, to phish.

Week 2 · subdomain and mail mapping

Drawing the door list

The attackers enumerated subdomains and read MX records. The mail records showed where mail flowed and which mail platforms the targets used. Names like vpn, webmail, and citrix marked remote access doors worth watching.

Week 2 · record sweeps

Sweeping TXT, SPF, and AXFR

TXT and SPF records named the cloud and SaaS vendors around each target. The group also tried zone transfers. Well-run servers refused, and the refusals cost the attackers nothing. Every refused answer still confirmed which servers were authoritative.

Week 3 · human mapping

Studying the people who control DNS

With the infrastructure mapped, the attackers prepared phishing pages that copied the login portals of the registrars and DNS providers. The recon told them exactly which portals the victim’s staff really used. Fake pages only work when they copy the right door.

Week 4 · the payoff (what the recon enabled)

Hijacking NS and MX records

Using stolen registrar and managed-DNS credentials, the group changed the NS and MX records of target domains. Mail and web traffic began to flow through attacker machines. There, the attackers could intercept mail and capture credentials before passing traffic on. This step is the hijack itself; this guide covers it because the recon phase made it possible.

After · discovery and response

The defenders catch up

Passive DNS watchers and alert victims noticed records that pointed to new name servers and mail hosts. CISA published AA19-080A with detection ideas and mitigations. Organizations were told to lock their registrar accounts, use multi-factor authentication, and audit their DNS records.

How it was detected

The clearest detection came from watching DNS data from the outside. Passive DNS services record the answers they see on the internet. When a well-known domain suddenly answered with new name servers and new mail hosts, the change stood out. The network security teams that watched their own records also noticed. A small set of controls made the difference:

  • DNS team: alerts on NS, MX, and SOA record changes for owned domains, including changes at the registrar.
  • SOC: denied AXFR lines and enumeration bursts in the name server logs, exactly like the Sigma rules in 5.5.
  • Mail team: mail flow that suddenly arrived through unknown relays, visible in mail gateway logs.

Containment steps

  1. Lock the registrar account and enable multi-factor authentication on it.
  2. Reset the credentials of every registrar and DNS provider account, and review recent logins.
  3. Correct the NS and MX records at the registrar, and lower the TTL first so fixes spread fast.
  4. Block the attacker infrastructure that received the redirected traffic and mail.

Recovery steps

  1. Audit the whole zone record by record, because the attackers changed records in other victims’ zones too.
  2. Reissue and revoke certificates that the attackers could have obtained during the interception window.
  3. Reset passwords and tokens for accounts that received mail through the attacker machines.
  4. Restore normal TTLs, keep monitoring record changes for a month, and report per CISA guidance.

Impact and consequences

For the victims, the technical impact was severe. Mail flowed through machines they did not control, and users typed passwords into real services through attacker relays. The business impact followed: incident response costs, weeks of cleanup, and hard questions from partners and customers. Trust suffered most, because DNS is invisible when it works. The attackers also collected a free map of every victim’s infrastructure, which kept its value long after the records were fixed.

Lessons learned

Lesson 1: protect the registrar account

The registrar account was the real target. Multi-factor authentication, a dedicated owner, and registrar lock would have stopped the hijack before it started.

Lesson 2: allow transfers only to validated servers

Zone transfer policies that permit transfers only to validated servers follow the official MITRE mitigation. They also remove the loudest recon prize.

Lesson 3: watch your own records

Alert on NS, MX, and SOA changes for your domains. The hijack was visible as a record change before anyone lost a password.

Lesson 4: log the questions

Denied AXFR lines and query bursts arrived weeks before the hijack. DNS logs turn the recon phase into early warning.

Lesson 5: inventory your providers

TXT, SPF, and NS records told the attackers which providers to target. The defenders should know that list better than the attackers do.

Team response and communication

In an incident like this, the SOC owns the timeline and the evidence: DNS logs, mail gateway logs, and registrar audit trails. The DNS and network teams own the record fixes, and IT security leadership owns communication. The message to leadership is short. Attackers studied our DNS, stole a provider account, and redirected our traffic. We have reverted the records, locked the accounts, and are now checking what they saw. Staff get one clear instruction, for example to change passwords and expect a short maintenance window. Partners and customers learn only confirmed facts, without speculation. Every action goes into one incident channel, twice a day, so the post-incident review has a clean record.

Mitigation and Defense

No single control stops DNS recon, because most of it uses normal questions that must be answered. The goal is a stack: make the big leaks impossible, remove the quiet leaks, and log everything that remains.

The official MITRE mitigation note

ATT&CK lists one main mitigation for this technique, and it is refreshingly concrete. Implement policies to permit zone transfers only to validated servers. In BIND this means allow-transfer with an explicit list of approved secondaries, or none. Verify the setting with a real AXFR request from an unknown host, and do not assume.

Enterprise defenses

  • Restrict zone transfers. Set allow-transfer to none, or to the exact list of approved secondaries, on every authoritative server.
  • Split-horizon DNS. Serve only public names externally. Keep internal names in an internal view that never answers outsiders.
  • Remove unnecessary records. Delete stale subdomains and TXT strings you no longer need, and document every string you keep.
  • Enable response rate limiting (RRL). It slows answer floods and blunts brute-force speed against your servers.
  • Use DNSSEC with NSEC3. It signs the zone and stops NSEC walking, because NSEC3 hashes names instead of listing them.
  • Ship DNS logs to the SIEM. Query logs and transfer logs from every authoritative server, sampled if volume is a worry.
  • Plant canary records. Fake hosts such as canary-gw1.example.com should never be queried. Alert the moment anyone asks.
  • Add IDS rules for AXFR. Alert on any AXFR over TCP/53 that does not come from an approved secondary.
  • Monitor NXDOMAIN rates. Keep a per-source baseline and alert on deviation (rule R2), and watch unique-query counts with rule R5.
  • Lock the registrar account. Enable registrar lock and multi-factor authentication, and alert on record changes (see the scenario).

Home & small business defenses

  • Use trusted, encrypted DNS (DoH or DoT) on your devices. It protects your users’ queries, even though it cannot hide your public records.
  • Keep router firmware updated. Home and small-office routers often run the network’s DNS, and old firmware is a common entry point.
  • If you run your own domain or lab zone, test your own AXFR with dig @your-ns your-domain AXFR and make sure the answer is refused.
  • Do not publish internal names publicly. Printer, NAS, and admin portal names belong in an internal view only.
  • Turn on query logging even at home. A day of logs will show you how chatty the internet really is.
  • Turn on multi-factor authentication at your registrar and DNS provider. It is the cheapest strong lock you will ever add.

Common Mistakes and Best Practices

This page is aimed at SOC analysts and detection engineers in daily work. The mistakes below are common in real environments, and each one has a short, concrete fix.

Best practices checklist

  • Zone transfer is refused from every public name server, and the test is documented, not assumed.
  • allow-transfer lists only approved secondaries on every authoritative server.
  • DNS query and transfer logs reach the SIEM with usable field names.
  • Rules R1 to R5 are deployed, and their thresholds fit your resolver load.
  • An NXDOMAIN baseline exists and is reviewed monthly.
  • No internal-only names appear in the public zone.
  • TXT records are minimal, documented, and reviewed quarterly.
  • Canary records are planted and wired to a high-priority alert.
Closing thought

DNS answers everyone, including attackers. You cannot stop the questions, but you can refuse the big one, shrink the small answers, and keep a diary of every question asked. That diary is often the first page of your incident report.

Glossary of Key Terms

Every technical term used in this guide, explained in simple words.

DNS
Domain Name System. The internet’s phone book: it turns names like example.com into IP addresses that computers can use.
DNS record
One entry in that phone book, for example one address, one mail rule, or one text note.
A record (and AAAA)
Says which IPv4 address a name points to, for example example.com at 192.0.2.10. AAAA is the same thing for IPv6.
MX record
Says which servers receive email for the domain. Attackers read it to pick phishing targets.
NS record
Says which name servers are authoritative for the zone and must answer its questions.
TXT record
A free-text entry. Used for mail rules and verification strings that often name cloud vendors.
SPF
Sender Policy Framework. A TXT rule that lists which servers may send mail for the domain; it often reveals vendors.
Canary record
A fake record planted on purpose. If anyone queries it or dumps it, that is a signal to investigate.
PTR record
The reverse of an A record: it maps an IP address back to a name.
Zone
The part of DNS that one organization controls, for example all names under example.com.
Zone transfer (AXFR)
A request to copy the whole zone file from a name server. Correctly configured servers refuse it for strangers.
NXDOMAIN
The DNS answer that means “this name does not exist”. In bursts, it is the signature of brute forcing.
Authoritative name server
The server that holds the official answers for a zone, instead of asking other servers.
Resolver
The service that accepts questions from computers and asks name servers on their behalf.
Passive DNS
A service that records DNS answers it sees on the internet. You can use it to look up what a domain looked like in the past.
Split-horizon DNS
Two answers for the same name: a public view for outsiders and an internal view for the company.
Registrar
The company where a domain is bought and renewed. Its account controls the name server records.
