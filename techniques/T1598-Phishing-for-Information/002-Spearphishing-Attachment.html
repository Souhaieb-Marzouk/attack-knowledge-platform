MITRE ATT&CK · RECONNAISSANCE

Spearphishing Attachment T1598.002

In this sub-technique the attacker sends a targeted email that carries a file — a PDF, a Word document, or an archive. Inside the file there is a questionnaire, an embedded form, or a written request to reply. The file is clean, the code is harmless, and the story inside is the weapon: every answer the reader types becomes reconnaissance data for the attacker.

Tactic · Reconnaissance Platforms · PRE (pre-attack; delivered through email platforms such as Office 365 and Google Workspace) Data sources · Email and attachment-gateway logs, Office 365 audit logs, endpoint file/process logs Parent · T1598

What it is

A targeted email with a clean document that asks the reader for sensitive information.

Where it fits

Reconnaissance — before Initial Access

Primary target

Employees who hold useful facts: HR, finance, IT, legal, and project staff.

Main risk

Staff and system details collected and reused for fraud, better lures, or intrusion.

Contents

    1

    Overview

    T1598.002 is the attachment variant of spearphishing for information. The attacker does not try to break a system; they try to get a person to fill in a document or send back the answers. This section explains the technique in plain words and shows where it sits in the ATT&CK model.

    What this technique is

    The adversary sends a spearphishing email — a targeted message written for one person or team — with an attachment. Inside the attachment there is a questionnaire, a fillable form, or a simple ask: reply with these details.

    The document holds no exploit (code that abuses a software flaw) and no malware (harmful software). It only asks questions. A PDF that requests team names is one shape. A Word file with form fields for an "access review" is another. An archive that must be opened and answered is a third. All are common shapes of this technique.

    Some actors also send an HTML file instead of a document. When opened, a trick called HTML smuggling (ATT&CK T1027.006) builds a fake login page from the file itself, so the reader types a password that goes straight to the attacker.

    Why it matters

    Clean files pass most security checks, because there is nothing technical to catch. The answers come back as an ordinary reply, and no endpoint alert fires at any point.

    The collected details feed later stages: better pretexts, fake portals, fraud, or a targeted intrusion. Detecting this technique means watching mail flow and human behavior, not just file code.

    Where it fits in the attack chain

    Reconnaissance→Initial Access→Execution→Exfiltration

    This technique lives fully in Reconnaissance. The attachment asks; nothing is installed. If the same actor later sends a file that runs code, that move is T1566.001 (Spearphishing Attachment, Initial Access), not this technique.

    Terms in this guide

    Spearphishing

    A targeted phishing message aimed at one person or team, written to fit their job, language, and current events.

    Elicitation

    Getting information from people through questions, forms, or chat, often without them noticing they gave it away.

    Pretext

    The fake story that gives the request a reason to exist: an audit, a survey, a court notice, a job interview.

    IdP (identity provider)

    The service that signs users in, such as Microsoft Entra ID or Okta. Details collected from staff can be used to target it.

    MFA (multi-factor authentication)

    A second proof of identity beyond the password. Some questionnaires fish for MFA reset details, backup codes, or phone numbers.

    DLP (data loss prevention)

    Controls that watch sensitive data leaving the organization, such as outbound mail that carries confidential text or filled files.

    3
    Red Team Perspective
    
      
    This section describes how adversaries plan and run attachment-based information elicitation. The details stay at planning level. Everything here is for defense planning and lab work — never for use against real people or real organizations.
    

      
    
        
    
          
    When and why attackers use it
    
          
    Asking is cheaper than breaking in. A questionnaire costs nothing to build, needs no exploit, and survives every patch cycle. It also slips past sandboxes (automated test systems that run files to see if they misbehave), because a document full of questions behaves exactly like a document full of questions.
    
          
    Attackers use this technique before an intrusion, when they want org charts, system names, VPN details, staff lists, or schedules. The answers shape better pretexts, better fake portals, and better-targeted follow-ups. Some actors blend it with malware delivery in one campaign. The elicitation part works even when the malware part fails.
    
        
    
        
    
          
    Preconditions
    
          
      
            
    • Basic target research: names, roles, and recent events from public sources.
      • 
            
    • Prior reconnaissance results: ATT&CK notes that lure details usually come from Search Open Websites/Domains (T1593) and Search Victim-Owned Websites (T1594).
      • 
            
    • A believable sender identity: a lookalike domain, a spoofed display name, or a hijacked thread.
      • 
            
    • Time and patience: replies arrive over days, and each one needs a human-quality answer.
      • 
            
    • A return path: a reply-to mailbox, a hosted form, or instructions to send the filled file back.
      • 
          
    
        
    
      
    

      
    How it is done
    
      
      
        
    1. Pick the story — choose a pretext that fits the target's job. Examples: a compliance audit for legal staff, a survey for HR, or a court notice for a company in litigation.
      2. 
        
    2. Design the ask — decide exactly which facts are wanted: staff lists, system names, VPN details, meeting schedules. Every question in the document maps to one of them.
      3. 
        
    3. Build the document — create a clean PDF with a questionnaire, or a Word file with form fields and content controls. No exploit code is added.
      4. 
        
    4. Set the return path — add a reply-to address on a lookalike domain, or instructions that ask the reader to email the completed file to a "processing office".
      5. 
        
    5. Prepare the sender — register or rent a domain that imitates a government body, partner, or internal team, and set display names that look official.
      6. 
        
    6. Send in small batches — personalize each message, keep volumes low, and sometimes split the attachment from the password to defeat scanning.
      7. 
        
    7. Collect and follow up — thank each reply, ask one more question, and record every answer in the target profile for the next stage.
      8. 
      
    

      
    Where it applies
    
      
    
        
    
          
    Government and legal impersonation
    
          
    Messages that imitate prosecutors, courts, or tax offices arrive with an attached "notification form". The target is told to fill it in and return it. This pattern was widely reported in campaigns against Colombian organizations.
    
        
    
        
    
          
    HR and recruitment
    
          
    Job applicants and new hires receive "candidate forms" or "onboarding questionnaires" that collect personal data, ID numbers, and sometimes credentials. Recruiters themselves are targeted with fake conference or candidate lists.
    
        
    
        
    
          
    Vendor and partner threads
    
          
    A "supplier compliance questionnaire" or a "project information request" uses a real business relationship. The ask sounds routine, so the form gets filled during a busy week.
    
        
    
        
    
          
    IT and security teams
    
          
    Fake "VPN audits", "access reviews", and "asset inventories" ask staff to list their systems, software, and remote-access details. That is exactly the data an intruder wants before choosing an entry path.
    
        
    
      
    

      
    
        Lab only
        
    In an isolated lab, you can stand up a local phishing-simulation range to study this technique safely. Run GoPhish (an open-source phishing-simulation tool) together with Mailpit (a local mail catcher) in Docker, on a private network, with test mailboxes only. Send only to your own lab addresses and inspect how the simulated attachment campaign looks in the mail log.
    
        
      
    

      
    Common variations
    
      
    
        
    
          
    Questionnaire PDF
    
          
    A plain PDF with numbered questions about staff, systems, or processes. The victim answers in the same file and emails it back. Zero code, total dependence on the story.
    
        
    
        
    
          
    Job application form (DOCX)
    
          
    A Word document with form fields, titled "job application" or "candidate details". Recruitment pretexts ask about employment history and references; some variants show empty pages until the fields are filled.
    
        
    
        
    
          
    Invoice-information request (protected archive)
    
          
    A supplier is asked to return billing and contact details in a password-protected RAR or ZIP. The password arrives in a second email or sits in the message body, which defeats automated detonation.
    
        
    
        
    
          
    Shared-document form request (.ics)
    
          
    An .ics calendar file carries a meeting that "needs confirmation of availability, team roster, or on-call rotation" by reply. It harvests operational details that fuel pretexting calls.
    
        
    
      
    

      
    
        Warning — mistakes attackers make that create noise
        
      
          
    • Reusing the same attachment across many mailboxes: one identical hash turns a single case into an enterprise-wide retro-hunt.
      • 
          
    • Sending in bursts at odd hours: delivery spikes at 03:00 local time stand out in mail-flow statistics.
      • 
          
    • Choosing lookalike domains that are days old: domain age is an easy, cheap signal for gateways to flag.
      • 
          
    • Following up in the same thread with the same subject: threading makes the whole chain visible in one search.
      • 
          
    • Putting the archive password in the subject line or sending it from the same domain: both leak the connection between the two emails.
      • 
        
    
      
    
    
    

    
    
      
    4
    Blue Team Perspective
    
      
    Defenders cannot rely on a malware verdict here, because there is no malware. What you can rely on is the trail of records: the delivery log, the document open, the outbound reply, and the user report. This section shows where each record lives and what to do in the first hour.
    

      
    Where defenders can see it
    
      
    
        
    
          
    SignalWhere you see itWhy it helps
    
          
            
    Message and attachment metadataEmail gateway and mail-flow logsSender, subject, and attachment hash are recorded at delivery, before anyone opens anything.
    
            
    Sandbox verdictGateway sandbox logs"Clean, no malware" is the expected result here. A clean verdict on a protected archive means "unknown", not "safe".
    
            
    Document process startEndpoint file/process logsWINWORD.EXE or Acrobat starting on an email attachment confirms a user actually opened the lure.
    
            
    Outbound reply with answersMail-flow and DLP logsSensitive text or a filled file leaving to the same external sender is the strongest exfiltration-shaped signal.
    
            
    User reportReporting mailbox or phishing buttonThe fastest, highest-quality signal you have. It anchors every other search.
    
              
        
    
      
    

      
    Artifacts this technique leaves behind
    
      
    
        
    
          
    The email itself
    
          
    Full headers, the thread, and the reply-to address. Stored in the gateway raw-mail sample store or in the user's mailbox export. Headers reveal the sending infrastructure and the return path.
    
        
    
        
    
          
    The attachment
    
          
    File name, hash (SHA-256), structure, and the questions inside. The gateway sandbox keeps the file object and its verdict. The questions list is your best content-based indicator.
    
        
    
        
    
          
    The reply
    
          
    Outbound mail that carries typed answers or the filled document. Found in outbound mail-flow and DLP logs, with the recipient, time, and any attachments listed.
    
        
    
        
    
          
    The pattern
    
          
    The same subject, sender, or hash across many mailboxes. Found with a SIEM (security information and event management) search over all mail telemetry. One pattern is worth more than ten single reports.
    
        
    
      
    

      
    
        Note — how this fits the attack chain
        
    Successful elicitation rarely stays alone. The answers usually feed T1589 (Gather Victim Identity Information) and sharper T1656 impersonation attempts. If the actor switches goal from answers to entry, the same lure shape becomes T1566.001 with a weaponized file. Treat every confirmed elicitation case as a rehearsal for a future intrusion, and brief the likely next targets.
    
      
    

      
    First-hour triage flow
    
      
      
        
    1. Collect the original — get the full email with headers and the attachment from the reporter. Do not forward it around; share the export, not the live message.
      2. 
        
    2. Search delivery records — query the gateway for the same sender, subject, and attachment hash across every mailbox. List all recipients as possible cases.
      3. 
        
    3. Inspect the file safely — open the attachment only in an isolated lab environment. Extract the questions and the return path; log both as indicators.
      4. 
        
    4. Check what left — search outbound mail and DLP logs for replies to the sender or for the filled file. If answers left, treat it as data exposure, not just spam.
      5. 
        
    5. Talk to the user — ask what they opened, what they typed, and whether they replied. Stay friendly; reporting is a behavior you want repeated.
      6. 
        
    6. Contain and decide — block the sender, domain, and hash; purge remaining copies. Then decide: pure elicitation, or a stage for malware delivery (T1566) — the document contents usually answer this.
      7. 
      
    

      
    
        Good — one quick win
        
    A retro-hunt by attachment hash across every mailbox takes minutes with a retained gateway log and finds all recipients, even the ones who never report. If you keep only one control from this page, make it twelve months of searchable gateway telemetry with hash fields.

    Confidence levels
    
          
    High means multiple credible vendors or direct telemetry agree — act on it: build rules and block infrastructure.     Turn each report into three things: indicators (hashes, domains, subjects), a behavior description (what the document asks), and a test question ("would my rules catch this?").       4.

      5.

    5.3 Threats Ranking and Categorization
    
      
    The five threats below cover the realistic attachment-based elicitation patterns for this technique. The order reflects a typical enterprise: documents that quietly harvest facts outrank exotic formats, and anything that defeats the sandbox ranks high because it blinds automated review.
    
      
    
        
    
          
    #ThreatPlatform focusDescription and preconditionsImpactWhy ranked here
    
          
            
    
              1
              Critical PDF/DOCX with embedded form eliciting staff or system details
              Windows, Email
              A clean PDF or Word file carries a questionnaire or fillable form and asks the reader to return staff lists, system names, or VPN details. Preconditions: a targeted user, a believable sender, and a return path.
              Structured internal facts leave the estate with no technical alert; they fuel fraud, better lures, and targeted intrusion.
              Highest volume and highest success rate in public reporting; the core shape of T1598.002.
            
    
            
    
              2
              High Macro-enabled or content-on-demand document requesting data before content unlocks
              Windows
              A .docm or templated file shows empty or locked pages until the reader types the requested data or enables content. Preconditions: the target opens the file on Windows with Office installed.
              Sits on the boundary of Reconnaissance and Initial Access; harvests data and can pivot to code execution.
              Dual-use risk: the same file can switch goal from elicitation to malware at any time.
            
    
            
    
              3
              High Password-protected archive attachment defeating gateway sandbox detonation
              Email, Network
              A RAR/ZIP/7Z or protected PDF arrives; automated sandboxing cannot open it, so the verdict stays unknown. The password arrives in a second email or the message body. Preconditions: gateway policy that still delivers protected archives.
              Removes the main automated control; both elicitation documents and payloads hide behind the same trick.
              Directly blinds detection tooling, which multiplies the impact of every other threat.
            
    
            
    
              4
              High OneNote/SVG/CHM lure documents with embedded questionnaires or links
              Windows
              Formats rarely sent by email (.one, .svg, .chm) carry questionnaire pages or links to fake forms. Preconditions: the format is still allowed to open on endpoints and passes gateway filters.
              Unusual formats bypass habit-based review; embedded links can shift the case toward credential harvesting.
              Repeatedly abused in recent campaigns precisely because filters and users both lag on these formats.
            
    
            
    
              5
              Medium Calendar invite (.ics) attachment harvesting availability and ops details
              SaaS, Email
              An .ics calendar file asks the reader to confirm availability, on-call rosters, or meeting attendees by reply. Preconditions: calendar files are delivered without attachment review.
              Operational rhythms and staffing details leak; these power convincing voice and email pretexts later.
              Lower volume and lower per-hit value, but almost never reviewed by security tooling.
            
    
              
        
    
      
    
      
    
        Note — re-rank for your environment
        
    This ranking is a starting point, not a verdict. A law firm that lives on court notifications should treat threat 3 as critical, because protected archives are its daily traffic. An organization that already blocks .one and .chm at the gateway can drop threat 4 two places and give the space to calendar lures.
    
      
    

      
    5.4 Logs and Patterns
    
      
    Each threat below gets its log sources, the fields that matter, what normal looks like, what suspicious looks like, and one realistic event example. Hostile indicators are defanged (dots shown as [.] ); internal values use the lab domain corp.example and documentation IP ranges, so nothing here points at a real target.
    

      
    Threat 1 — PDF/DOCX with embedded elicitation form
    
      
    
        
    Log sources
    Email gateway (Mimecast/Proofpoint class), Microsoft 365 audit (Exchange), mail-flow logs.
    
        
    Key fields
    sender, replyTo, subject, attachments.fileName, attachments.fileType, attachments.sha256, action.
    
        
    Normal behavior
    External PDFs and DOCX files arrive from known business senders with specific subjects, a few per user per day; reply-to matches the sending domain.
    
        
    Suspicious behavior
    New external sender plus generic-staff subjects ("survey", "questionnaire", "data update form") with a PDF/DOCX, especially when the reply-to domain differs from the sender domain.
    
        
    Detection logic
    Alert on external mail with pdf/docx attachments and elicitation keywords in the subject, weighted up when reply-to and sender domains do not match.
    
      
    
      

      
    Threat 2 — Macro-enabled or content-on-demand document
    
      
    
        
    Log sources
    Microsoft 365 audit (Exchange, MailItemsAccessed), endpoint process logs.
    
        
    Key fields
    AttachmentData.FileType, AttachmentData.FileName, AttachmentData.Sha256, Subject, SenderEmailAddress, RecipientAddress.
    
        
    Normal behavior
    Macro-enabled formats are rare in most inboxes; finance and legal templates come from known internal or partner senders.
    
        
    Suspicious behavior
    Any inbound .docm/.dotm/.rtf from a new external sender, or a document that renders blank pages until the requested data is entered.
    
        
    Detection logic
    Alert on inbound macro-enabled formats from external senders, then correlate with endpoint process logs to confirm who opened the file.
    
      
    
      

      
    Threat 3 — Password-protected archive defeating the sandbox
    
      
    
        
    Log sources
    Email gateway logs (Mimecast-class hold records), mail-flow logs.
    
        
    Key fields
    sender, recipient, subject, fileName, holdReason, action, sha256, geo.
    
        
    Normal behavior
    Genuine protected archives exist in finance, legal, and payroll traffic, usually announced by phone or a known contact.
    
        
    Suspicious behavior
    A protected archive from a new sender, a hold reason of "password protected", or a second email supplying the password in the same thread.
    
        
    Detection logic
    Alert on any hold for password-protected archives; correlate the archive email with the follow-up that delivers the password.
    
      
    
      

      
    Threat 4 — OneNote/SVG/CHM lure document
    
      
    
        
    Log sources
    Gateway attachment filters, endpoint process logs, Microsoft 365 audit.
    
        
    Key fields
    process.name, process.parent.name, file.path, file.hash.sha256, file.origin, user.name.
    
        
    Normal behavior
    In most organizations these formats almost never arrive by email and are not opened by end users.
    
        
    Suspicious behavior
    Any inbound .one/.onetoc2/.svg/.chm at the gateway; onenote.exe or hh.exe starting on a file that came from an email attachment.
    
        
    Detection logic
    Block these formats at the gateway; alert on their process starts at the endpoint and join the event with the delivery record by hash or message ID.
    
      
    
      

      
    Threat 5 — Calendar invite (.ics) harvesting availability
    
      
    
        
    Log sources
    Email gateway, Microsoft 365 audit, Google Workspace Gmail audit, SaaS calendar logs.
    
        
    Key fields
    AttachmentData.FileType (.ics), Subject, SenderEmailAddress/organizer, RecipientAddress, time sent.
    
        
    Normal behavior
    Internal invites and known external organizers with context in the body; the calendar entry is inline, not an attached file.
    
        
    Suspicious behavior
    An external .ics attachment whose subject asks to confirm availability, rosters, or on-call details, often sent before business hours.
    
        
    Detection logic
    Alert on external .ics attachments with roster or availability wording; correlate replies that carry schedules back to the same organizer.
    
      
    
      

      
    5.5 Sigma Rules and Splunk SPL
    
      
    Sigma is a YAML rule format that many SIEM products can compile into their own query language; SPL is Splunk's search language. Each rule below targets one threat from section 5.3 and states its severity. Each rule is followed by a matching SPL query, the field assumptions, real false positives, and one concrete tuning action. Domain indicators are defanged where they appear.
    

      
    Rule 1 — Questionnaire-style PDF/DOCX in Exchange Online
    
      
    Severity: Critical. This rule catches the core pattern of threat 1: external mail with a PDF or DOCX attachment and subject wording typical of elicitation, delivered through Exchange Online.
    
      
      
      
    
        
    
          
    AspectDetail
    
          
            
    Mapping and field assumptionsAssumes O365 audit events (ms:o365:audit) expose Subject, SenderEmailAddress, RecipientAddress, and AttachmentData.FileType/FileName. If you ingest message-trace data instead, map AttachmentData.FileType to the trace attachment field.
    
            
    False positivesLegitimate external survey platforms (HR tools) with matching subjects land here by design.
    
            
    TuningAllowlist the two or three approved survey-sender domains in filter_internal, and page only when the reply-to domain also mismatches the sender domain.
    
              
        
    
      
    

      
    Rule 2 — Macro-enabled document at the gateway
    
      
    Severity: High. This rule covers threat 2: inbound macro-enabled formats that power content-on-demand lures, seen at a Proofpoint-class gateway.
    
      
      
      
    
        
    
          
    AspectDetail
    
          
            
    Mapping and field assumptionsAssumes the Proofpoint PPS message log exposes attachment_extension, sender_domain, sender, recipient, and action fields; on Mimecast the same logic maps to the attachmentName field.
    
            
    False positivesPartner-supplied macro templates and legacy RTF report exports from known utilities.
    
            
    TuningKeep a per-team allowlist of partner domains that may send macro formats, and route everything else to a hold queue for human review.
    
              
        
    
      
    

      
    Rule 3 — Password-protected archive on hold
    
      
    Severity: High. This rule covers threat 3: any archive or PDF the gateway holds because it is password-protected or encrypted, the sandbox-evading pattern reported for APT-C-36.
    
      
      
      
    
        
    
          
    AspectDetail
    
          
            
    Mapping and field assumptionsAssumes Mimecast log fields holdReason, fileName, sender, recipient; on Proofpoint the equivalent lives in the PPS verdict/hold fields, and on M365 in Transport Rules with an encryption flag.
    
            
    False positivesEveryday protected payroll, legal, and finance traffic; expect a steady baseline volume.
    
            
    TuningBaseline the weekly volume per department, then alert only on new sender-and-recipient pairs or on volume spikes above twice the baseline.
    
              
        
    
      
    

      
    Rule 4 — OneNote, SVG, or CHM attachment
    
      
    Severity: High. This rule covers threat 4: attachment formats that almost never travel by email but keep showing up in lure campaigns.
    
      
      
      
    
        
    
          
    AspectDetail
    
          
            
    Mapping and field assumptionsAssumes AttachmentData.FileName is populated for every audited message; if your tenant only logs AttachmentCount, join the rule with gateway attachment logs on MessageTraceId.
    
            
    False positivesGenuine design-partner SVG exchanges and internal tooling that mails CHM help files.
    
            
    TuningFirst confirm with a one-week baseline that .one/.chm inbound volume is near zero, then keep the rule strict and move any real sender into the filter list.
    
              
        
    
      
    

      
    Rule 5 — Calendar file with availability ask
    
      
    Severity: Medium. This rule covers threat 5: external .ics calendar attachments whose wording asks the reader to confirm availability, rosters, or on-call details, seen in Google Workspace Gmail audit data.
    
      
      
      
    
        
    
          
    AspectDetail
    
          
            
    Mapping and field assumptionsAssumes Gmail audit events are exported to index=gws with sourcetype gws:gmail:audit and expose attachmentName, subject, and senderAddress; rename fields to match your Google Workspace SIEM export.
    
            
    False positivesReal recruiters and client coordinators who attach calendar files to scheduling mail.
    
            
    TuningRequire an external organizer with no prior thread history, and demote to informational when the same organizer has mailed the recipient in the last 30 days.
    
              
        
    
      
    
    
    

    
    
      
    6
    Real-World Case Study: APT-C-36
    
      
    This is an educational reconstruction based on public reporting of APT-C-36 campaigns in 2019, notably a widely shared vendor report. It is not an incident record from any named victim, and no real individual appears here. The reconstruction keeps the reported behavior: impersonated Colombian government entities, password-protected RAR/PDF attachments, questionnaire-style instructions, and blended implant delivery. The timeline is simplified for teaching.
    

      
    Case snapshot
    
      
    
        
    Victim sector
    Colombian government entities (prosecutors, courts, migration) and private companies.
    
        
    Year
    2019, with similar activity reported around it.
    
        
    Threat actor
    APT-C-36, a Spanish-speaking intrusion group tracked by several vendors.
    
        
    Technique used
    T1598.002-style spearphishing attachments for information elicitation, blended with implant delivery in the same lures.
    
        
    Outcome
    Repeated successful lures; sensitive documents and internal details exposed; follow-on access in reported cases.
    
      
    

      
    Timeline
    
      
    
        
    
          
    WhenWhat happenedDefender view
    
          
            
    Weeks before deliveryThe actor prepared lookalike government-style domains and wrote lures that imitated prosecutors and courts.Newly registered domains existed in Certificate Transparency logs; nobody was watching.
    
            
    Day 0, morningTargeted staff received emails that appeared to come from Colombian government bodies about a legal notification.Gateway logged the sender and subject; display-name impersonation, not domain spoofing.
    
            
    Day 0, same hourEach email carried a password-protected RAR or PDF. The sandbox could not open the file and returned an unknown or clean verdict.The hold reason "password protected" was the strongest automated signal available.
    
            
    Day 0, laterThe password arrived in the message body or a follow-up, with instructions to open the attachment and follow the steps inside.Thread correlation would have joined the two messages into one obvious chain.
    
            
    Day 0-2Victims who opened the file found questionnaire-style instructions asking for details; in many reported cases the file also attempted implant delivery.Endpoint logs showed the document opening; elicitation alone left no further trace.
    
            
    Days 1-14Data and, where implants ran, stolen material flowed back to actor infrastructure.Outbound replies to the impersonation domain were visible in mail-flow logs.
    
            
    After discoveryResponders blocked sender domains and hunted the attachment hash across mailboxes.Hash-based retro-hunt listed every recipient; the true patient zero was often a non-reporter.
    
            
    Weeks afterThe actor reused the same playbook with refreshed domains against new targets.Domain-pattern monitoring (name style, registrar, age) became the durable signal.
    
              
        
    
      
    

      
    
        
    
          
    Attack chain
    
          
    Research and impersonation come first. Then a targeted email with a protected archive, then the password and instructions. Finally, a document that asks questions — and, in the blended variant, delivers an implant. The elicitation and the delivery use the same trusted-looking story.
    
        
    
        
    
          
    Detection point
    
          
    The earliest reliable points were the protected-archive hold at the gateway and the outbound reply in mail-flow logs. The sandbox verdict was blind by design, and no endpoint alert existed for the pure-elicitation variant.
    
        
    
        
    
          
    Containment
    
          
    Block the sender, the lookalike domains, and the attachment hash; purge remaining copies from mailboxes; hold all future protected archives from unverified senders for manual review.
    
        
    
        
    
          
    Eradication
    
          
    For cases where an implant had run: isolate the endpoint, remove the access tool, reset credentials for the user, and review what the implant could reach. For pure-elicitation cases: confirm with the user exactly which answers left.
    
        
    
        
    
          
    Recovery
    
          
    Rebuild trust in the mail channel. Publish what happened in a short internal note. Refresh the "government impersonation" warning for likely targets, then resume normal operations with the new blocks in place.
    
        
    
        
    
          
    Impact and consequences
    
          
    Sensitive internal details and government correspondence left the environment, and in blended cases the actor gained a foothold. The operational cost was dominated by manual review of protected archives and repeated blocklist maintenance.
    
        
    
      
    

      
    
        
    Team response and communication
    
        
    The SOC told affected users what had been collected and asked them to list any details they had returned, without blame. Management received a one-page summary: what left, what it enables, and which blocks were now in place. The mail team and the national CERT-style contacts were notified so peer organizations could hunt the same sender pattern the same week.
    
      
    

      
    Lessons learned
    
      
      
        
    • A clean sandbox verdict on a protected archive means "unknown" — the human review step is the control, not the verdict.
      • 
        
    • Password delivery in a second message links two emails; correlate by thread before triaging either one alone.
      • 
        
    • Display-name impersonation of government bodies defeats SPF (sender policy framework) checks; train on the ask, not on authentication badges.
      • 
        
    • Hash-based retro-hunts find the quiet recipients who never report; run them by default.
      • 
        
    • Elicitation and delivery can share one lure; treat every attachment case as both until proven otherwise.
      • 
        
    • Domain-pattern monitoring (age, name style, registrar) outlasts individual blocklists.
      • 
      
    
    
    

    
    
      
    7
    Mitigation and Defense
    
      
    No single control stops a clean document that asks polite questions. The defense is layered: make the ask harder to answer, keep the records that reveal it, and rehearse the response. Each control below is written as an action you can assign and finish.
    

      
    
        
    
          
    Policy and people
    
          
      
            
    • Publish one plain rule: internal details never leave through documents sent by unverified parties.
      • 
            
    • Train staff to spot the ask, not the link: questionnaires, "fill before review" drafts, and reply-with-details requests.
      • 
            
    • Give every employee a one-click report path and thank reporters publicly.
      • 
            
    • Drill attachment lures in simulations at least twice a year, including government-impersonation pretexts.
      • 
          
    
        
    
        
    
          
    Identity
    
          
      
            
    • Enforce MFA (multi-factor authentication) on all accounts so collected credentials alone are not enough.
      • 
            
    • Verify unusual data requests by a second channel, ideally a phone number you already had.
      • 
            
    • Apply least privilege so a harvested org chart does not equal an access map.
      • 
            
    • Review IdP (identity provider) logs after every confirmed campaign for probing sign-ins.
      • 
          
    
        
    
        
    
          
    Endpoint
    
          
      
            
    • Keep process and file logging on so document opens are attributable to a user and time.
      • 
            
    • Block macros in files from the internet by default; require an approved exception path.
      • 
            
    • Restrict or remove unused handlers such as CHM viewers where the business does not need them.
      • 
            
    • Patch Office and PDF readers on schedule; blended lures still try old exploits.
      • 
          
    
        
    
        
    
          
    Network
    
          
      
            
    • Route all external mail through the security gateway; no direct MX exceptions for departments.
      • 
            
    • Hold password-protected archives from unverified senders for manual review.
      • 
            
    • Filter DNS (domain name system) against newly registered and lookalike domains.
      • 
            
    • Monitor egress for unexpected form posts or attachments to first-contact external domains.
      • 
          
    
        
    
        
    
          
    Cloud and SaaS
    
          
      
            
    • Enable Office 365 and Google Workspace audit logging on every tenant, including Exchange and Gmail.
      • 
            
    • Tag external senders in the client so "external" is visible at a glance.
      • 
            
    • Configure calendar policy so external invites and .ics files are quarantined or annotated.
      • 
            
    • Run DLP rules on outbound attachments and first-time external recipients.
      • 
          
    
        
    
        
    
          
    Logging
    
          
      
            
    • Retain gateway, mail-flow, and audit logs for at least 12 months, with 90 days hot.
      • 
            
    • Centralize logs into the SIEM with consistent field names for sender, hash, and verdict.
      • 
            
    • Keep raw mail samples of blocked and held messages for later indicator extraction.
      • 
            
    • Log document-open events on endpoints, not just executions.
      • 
          
    
        
    
        
    
          
    Monitoring
    
          
      
            
    • Deploy the five Sigma rules from section 5.5 and review hits weekly.
      • 
            
    • Hunt by attachment hash and subject across all mailboxes after every report.
      • 
            
    • Alert on outbound replies with attachments to first-contact external domains.
      • 
            
    • Track protected-archive volume; a spike is a campaign, not a coincidence.
      • 
          
    
        
    
        
    
          
    Backup and response
    
          
      
            
    • Maintain a phishing playbook that covers elicitation cases, not only malware.
      • 
            
    • Define who can purge mail across all mailboxes and rehearse that action quarterly.
      • 
            
    • Keep blocklist changes versioned and reversible.
      • 
            
    • Preserve the original email, attachment, and replies as evidence before cleanup.
      • 
          
    
        
    
      
    

      
    
        
    Home and small office
    
        
      
          
    • Be suspicious of any document that asks you to fill in personal or work details and send it back.
      • 
          
    • Never open password-protected attachments whose password arrived by email from someone you did not expect.
      • 
          
    • Check the sender address, not just the display name; government bodies rarely send forms by email.
      • 
          
    • Use your mail provider's report-phishing button instead of replying to test the sender.
      • 
          
    • Turn on two-factor authentication for your important accounts so leaked details are less useful.
      • 
        
    
      
    

      
    Prioritized actions
    
      
    
        
    
          
    PriorityActionEffortOwnerExpected risk reduction

    Cheat Sheet and Quick Reference
    
      
    The one-screen version of this guide: the facts, the five detections, the response checklist, and the official links worth bookmarking.
    

      
    
        
    
          
    Key facts
    
          
    
            
    ATT&CK ID
    T1598.002 (sub-technique of T1598)
    
            
    Tactic
    Reconnaissance (TA0043)
    
            
    Core idea
    A clean document asks; the answers are the payload
    
            
    Platforms
    PRE (pre-attack; delivered through email platforms such as Office 365 and Google Workspace)
    
            
    Core logs
    Email and attachment-gateway, Office 365 audit, endpoint file/process
    
            
    Best quick win
    12 months of searchable gateway telemetry with hash fields
    
          
    
        
    
        
    
          
    Top detections
    
          
      
            
    1. External PDF/DOCX with elicitation keywords and a reply-to mismatch.
      2. 
            
    2. Any inbound macro-enabled format (.docm/.dotm/.rtf) from a new external sender.
      3. 
            
    3. Gateway hold on password-protected archives, joined with the follow-up password email.
      4. 
            
    4. Rare formats by email: .one, .onetoc2, .svg, .chm from external senders.
      5. 
            
    5. External .ics attachments whose subject asks for availability, rosters, or on-call details.
      6. 
          
    
        
    
      
    

      
    
        
    Response checklist
    
        
      
          
    • Collect the original email with headers and the attachment from the reporter.
      • 
          
    • Search the gateway for the same sender, subject, and hash across every mailbox.
      • 
          
    • Inspect the file only in an isolated lab; extract the questions and the return path.
      • 
          
    • Search outbound mail and DLP logs for replies or filled files to the same sender.
      • 
          
    • Interview the user about what they opened and what they typed back.
      • 
          
    • Block the sender, domains, and hash; purge remaining copies from all mailboxes.
      • 
          
    • Decide whether the lure was pure elicitation or a delivery stage (T1566) and scope accordingly.
      • 
          
    • Write the case note and brief the likely next targets the same week.
