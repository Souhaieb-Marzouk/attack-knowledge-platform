T1588.003 Code Signing Certificates

A code signing certificate works like an identity card for software. When a program is signed, Windows, macOS, and security tools trust it more and show fewer warnings. Attackers know this, so they buy or steal these certificates and use them to sign malware. This guide explains the technique in plain language, shows an animated example, and gives defenders Sigma rules, Splunk queries, and a full detection playbook.

Overview

What code signing certificates are, why attackers want them, and where this sub-technique sits in the attack chain.

What it is

Code signing is the process of adding a digital signature to a program or script. The signature says two things: who published the file, and that nobody changed the file after signing. The signature is made with a secret key, the private key, which lives inside a code signing certificate issued by a certificate authority (CA), a company whose job is to check identities and hand out certificates.

T1588.003 covers attackers who buy or steal these certificates before an attack. They can buy them using a fake company that passes the CA checks, or steal them from a compromised software vendor. The malware they sign then carries a valid signature from a real certificate.

Why it matters

Operating systems and security products trust signed files more than unsigned ones. A signed program can skip warning dialogs, pass software allowlists, and look safe in a mail gateway. ATT&CK states it plainly: users and tools may trust signed code even when they do not know the signer.

For defenders, the signature is both a problem and a gift. It is a problem because the file looks legitimate. It is a gift because the signer identity is a stable marker: attackers can rebuild the malware to change its hash, but the certificate stays the same. Learn one abused certificate, and you can find every payload signed with it.

Where it fits

This sub-technique sits under T1588 Obtain Capabilities in the Resource Development tactic (TA0042), the phase before any contact with the target. It pairs naturally with T1588.001 (Malware), because the malware is the thing being signed, and with T1588.002 (Tool).

Two related techniques complete the picture: T1552.004 (Private Keys) describes how attackers steal signing keys from a victim company, and T1553.002 (Code Signing, under Defense Evasion) describes the abuse itself, when malware runs because of its valid signature. Signing is stronger than plain masquerading: it abuses real trust instead of just imitating it.

    The same story in words

    This written version covers exactly the same eight steps as the animation. Read it if you prefer text, use it with a screen reader, or quote it in a training session.

    Step 1

    The malware must look trusted

    A threat actor prepares a payload, for example a backdoor and a Windows kernel driver (a program that runs deep inside the operating system). The actor knows an unsigned file raises warnings, so the plan needs a valid code signing certificate. Nothing has touched the victim yet, so the defender sees nothing.

    Step 2

    Buying a stolen certificate

    The actor buys a code signing certificate on a criminal market. The seller stole it weeks earlier from a small software company. The actor now holds the private key and can sign any file so it looks like it came from that company. Intelligence teams sometimes notice this resale, and the certificate identity becomes a fixed marker.

    Step 3

    Signing the payload on the build box

    On a rented workstation, the actor signs the driver and the backdoor with the stolen certificate. Everything here happens on the attacker's own infrastructure. The defender still has nothing to see, which is the honest answer for this step.

    Step 4

    A test sample leaks to a sandbox

    Good practice for attackers is to test the payload first, but testing leaks data. The sample lands in an online sandbox, which records the file hash and, crucially, the signer identity. Malware repositories now know that "Example Software Ltd" signed this file. The first public trace exists.

    Step 5

    Threat intelligence reports the abuse

    A security vendor publishes a report naming the abused certificate: the subject name, the thumbprint (a short fingerprint hash of the certificate), and sample files. Your intelligence pipeline turns this into a hunt. From now on, the SOC can search its own estate for that signer.

    Step 6

    Delivery passes the signature check

    The actor sends phishing mail with the signed payload. The mail gateway checks the signature and finds it valid, so the message is not blocked by trust rules. Only weak signals remain: a low-reputation sender and an unusual attachment type. This is the moment a signature-based defense alone fails.

    Step 7

    The signed driver loads on the victim

    A user runs the installer. The driver loads, and endpoint logging records it: Sysmon Event ID 6 shows a valid signature from a signer nobody has seen before. On hosts that run application control in audit mode, CodeIntegrity event 3076 records that the same file would not meet policy; in enforced mode the driver would be blocked instead. The strong signal finally exists.

    Step 8

    The SOC pivots on the signer

    The SOC matches the signer against the intelligence report, confirms the abuse, and hunts the whole estate for that thumbprint. Affected hosts are isolated, the signer is blocked, and the team asks the vendor for revocation context. One stolen certificate turned into a complete detection chain.

    How to read the animation

    Red flows are attacker actions. Amber flows carry the capability or payload itself. Blue elements belong to the defender side.     What is realistic here

    This story is a composite of public reporting: groups such as Wizard Spider, OilRig, and APT41 all used stolen certificates, and MegaCortex used certificates issued to fake companies. Prices, forums, and timings are simplified for teaching. The shape is what matters: the purchase is invisible, the signer identity is the pivot, and the load event is where strong detection starts.

    Red Team / Hacker Perspective

    Why a valid signature is worth money to an attacker, how certificates are obtained in principle, and where the process leaks traces.

    ?Ethics and scope

    This section explains attacker behavior so defenders can detect it. It stays at the level of concepts and public reporting. It gives no operational instructions for obtaining or abusing certificates. Any hands-on practice belongs in an isolated lab you own, with fake data, and clearly labeled as lab-only.

    A signature changes how the world treats a file. Windows shows fewer warnings for signed programs. Mail gateways score signed attachments as safer. Software allowlists that check signatures let the file run. For an attacker, one valid certificate removes many warnings and checks, which is why stolen signing keys sell well on criminal markets.

    The trust chain makes this powerful. A certificate is issued by a certificate authority (CA), and operating systems ship with a list of CAs they already trust. A program signed with a certificate from a trusted CA inherits that trust automatically, even if nobody has ever heard of the signer. This is also why Authenticode, the Windows technology that checks these signatures on programs and drivers, treats a valid chain as a pass, and why a stolen certificate is far more useful to an attacker than a fake name.

    ATT&CK documents this technique across many actor types, from financially motivated ransomware crews to state-linked teams. That range tells you the technique is not exotic. It is a standard step in preparing a serious intrusion.

    How attackers obtain the certificates

    Buying with a front company

    The attacker registers a fake company and applies for a certificate like a normal business. The CA asks for company documents, and the attacker supplies stolen or forged ones. When validation succeeds, the attacker owns a fresh certificate that no victim can find in any stolen-data list. MegaCortex used certificates issued to fake companies this way.

    Stealing from a real vendor

    The attacker breaks into a software company and takes the signing material: the private key file, an export from a secrets vault, or a key held on a build server. OilRig, BlackTech, Kimsuky, Lazarus during Operation Dream Job, Threat Group-3390, and APT41 in the DUST campaign all used stolen certificates for their payloads.

    Abusing the issuing process

    Some certificates were issued wrongly in the first place: validation was tricked, or a CA cut corners. Groups that specialize in fraud sometimes combine this with the front-company path. Once issued, the certificate looks completely normal, and only the CA's own audit can unwind it.

    Reusing revoked or expired certificates

    Attackers sometimes sign with certificates that are already revoked (formally cancelled by the CA) or expired. This works when the victim does not check revocation status, which many older systems and drivers do not. Mustang Panda used revoked certificates, and FIN8 used an expired test certificate, so signatures that fail strict checks still pass on systems that do not check properly.

    Conditions and preparation

    Obtaining the certificate is only the start. The actor needs a signing tool that supports the platform format, for example Microsoft's Authenticode signing tools on Windows. The actor should keep the trust chain intact, which usually means adding a trusted timestamp to each signature so the signature survives certificate expiry. And the actor wants to test the signed payload on a clean machine before use, which is exactly the step that sometimes leaks the sample, and with it the signer identity, to researchers. Certificates also have value beyond one campaign: resellers rent or sell the same stolen certificate to several crews, so one identity can appear across unrelated incidents.

    iLab-only practice example

    A safe classroom exercise looks like this: on your own test machine, inspect the signature of any installed program with a read-only command such as PowerShell's Get-AuthenticodeSignature, and note the subject, issuer, and status. Then compare a Windows system file and a random unsigned tool. You are learning what defenders read from signatures, without touching any real certificate or target. Label the exercise and the lab clearly.

    Variations and common mistakes attackers make

    VariationWhat changesTrace it leaves
    Front-company purchaseFresh certificate, full control, cost and paperworkCA issuance records; a signer with a young certificate and no history
    Stolen from a vendorReal company identity, high trust, victim may revokeVendor-side intrusion logs; revocation notice; security firm reports
    Second-hand purchaseCheap and fast, but shared with other crewsThe same signer across many unrelated campaigns
    Revoked or expired reuseWorks only where revocation is not checkedSignature status fields; vendor advisories naming the certificate

    Mistakes that expose the abuse

    Resellers hand the same certificate to many buyers, so one signer identity links campaigns that believed they were separate. Test samples reach online sandboxes, and the sandbox records the signer. Some crews skip timestamps, so signatures break after expiry. Others reuse a revoked certificate and only find out when the target host refuses to load the file. Each mistake is a pivot for the defender.

    Blue Team / SOC Perspective

    What the technique looks like from the inside, which artifacts survive, and a short triage flow your team can follow.

    The purchase itself happens on servers you cannot see, so no alert fires when a stolen certificate changes hands. MITRE notes that most of this activity stays outside the visibility of the target organization. Good teams therefore work two layers. The first layer is intelligence: reports from security vendors name abused certificates, their subjects, and their thumbprints. The second layer is telemetry: your endpoints record every driver and image load together with its signature, and that is where the abuse becomes visible.

    The signer identity deserves special attention. File hashes change with every rebuild of the malware, so hash blocking becomes an endless chase. The certificate subject and thumbprint do not change. When a vendor report says "payloads signed with certificate CN=Example Software Ltd, thumbprint AB12…", that identity can match months of history and every future rebuild. This makes signer-based hunting the highest-value action on this page.

    There is a second, quieter role for the blue team: not becoming the source. The stolen certificate of the next campaign may be yours. Signing keys on build servers, exports of .pfx files (a password-protected container that holds a certificate and its private key), and unusual reads of signing secrets are all things you can detect on your own side, which is what threat TH-2 in section 5 covers.

    Artifacts the technique leaves behind

    Certificate artifacts

    Every signed file carries the subject, issuer, serial, and thumbprint of the certificate inside its signature metadata. Unlike website certificates, code signing certificates are not published in certificate transparency logs, so the identity is learned from samples, endpoint logs, and vendor reports instead.

    Endpoint artifacts

    Sysmon Event ID 6 records kernel driver loads and Event ID 7 records DLL and executable image loads, both with Signed, Signature, and SignatureStatus fields. Windows CodeIntegrity events 3076 and 3077 record files that failed application control policy. EDR products expose the same signature data in their process and module views.

    Cloud and build artifacts

    When the attacker goes for your keys, cloud audit logs show secret reads and key access, CI/CD runners show unexpected signing jobs, and file audit shows .pfx exports. On macOS, Gatekeeper decisions, quarantine attribute changes, and codesign activity show how signing trust is being tested or removed.

    Why this matters for the attack chain

    Stopping the signed payload at load time stops the intrusion at step one. A driver that never loads means no persistence, and a backdoor that never runs means no credential theft. That is why this pre-compromise technique has real detection value: it tells you exactly which markers to expect. Teams that keep a signer inventory and hunt abused identities see these campaigns earlier, and at lower cost, than teams that chase file hashes one by one.

    Short triage flow

    1. Receive or find the marker. A vendor report, a sandbox match, or your own endpoint log gives you a signer subject or thumbprint.
    2. Enrich it. Read the full report: which families used the certificate, when it was first and last seen, whether the CA revoked it, and which thumbprint is current.
    3. Check exposure. Search 90 days of Sysmon 6 and 7, EDR module loads, and mail gateway logs for the subject or thumbprint. One query per source, saved as a scheduled hunt.
    4. Validate hits. For each hit, decide whether the signer is legitimately used in your estate. Check the software vendor's own site, and note that a stolen certificate can still sign real products.
    5. Escalate and block. Real hits become an incident: isolate hosts, block the thumbprint in policy, and record the case. No hits become an intelligence note with an owner and the next review date.

    ✓Good practice

    Block by certificate thumbprint, not by file hash. A thumbprint block survives malware rebuilds, costs almost nothing to store, and works across every file the attacker signs with that certificate. Keep the blocklist next to your signer inventory so allow and deny stay in one place.

    iWhat ATT&CK officially says

    MITRE rates direct detection of this sub-technique as difficult and lists the mitigation Pre-compromise [M1056], because buying and stealing certificates happens outside your boundary. The official detection strategy is DET0875 — Detection of Code Signing Certificates. Its analytic AN2007 says: consider analyzing code signing certificates for features that may be associated with the adversary and/or their developers, such as the thumbprint, the algorithm used, the validity period, the common name, and the certificate authority. MITRE also points to the follow-on behavior it makes possible: detection efforts may focus on related activity such as Code Signing (T1553.002) or Install Root Certificate.

    Read the official T1588.003 page for the full strategy text. The rest of section 5 turns these official hints into concrete rules.

    5.1Regulation mapping

    A signing-focused threat matters to auditors because a stolen certificate defeats the controls that regulators assume exist: software integrity checks and trusted supply chains.     FrameworkControlWhy it appliesExpected evidence
    GDPR Art. 32 Requires technical measures against unlawful access. Signed malware is a common entry path, so signature enforcement and signer monitoring are part of those measures. Application control policy, signer inventory, incident tickets with containment timelines
    HIPAA Security Rule §164.308(a)(5)(ii)(B), §164.312(c)(1) Demands protection from malicious software and integrity controls. Code signing abuse breaks the integrity assumption that signed equals safe. Endpoint protection policy, CodeIntegrity monitoring records, audit log retention settings

    Every certificate identity you ingest needs a confidence level, or your alerts will argue with each other. Use three levels and write them into the detection metadata.

    LevelMeaningTypical source qualityHow you act

    2. Analyze each item: which subject and thumbprint, which malware families, which platforms, what confidence.
    3. Apply by turning identities into hunts and detections, then link each detection back to the intelligence item.
    4. Measure quarterly: which items produced detections, which detections fired, and which feeds never produced anything useful. Drop weak feeds, keep strong ones.

    5.3Threats ranking and categorization

    The six threats below are the realistic ways this technique turns into risk for an organization. They are ranked and categorized by platform. The same six threats are used in 5.4 and 5.5, so the section stays practical.

    ThreatRankCategoryOne-line summary
    TH-1CriticalEndpoint · WindowsBinary or kernel driver signed with a stolen or abused certificate executes or loads
    TH-2HighIdentity · CloudAccess to code-signing keys on build infrastructure, such as vault reads or .pfx exports
    TH-3MediumNetwork · IntelCertificate identity from TI reporting used to hunt stored telemetry for an abused signer
    TH-4HighEndpoint · macOSAd-hoc signed or unsigned payloads plus Gatekeeper bypass tooling around obtained signing material
    TH-5HighEndpoint · WindowsRevoked or watchlisted signer hits at image or driver load, or a Revoked or Expired signature status on a file that still loaded
    TH-6MediumEndpoint · WindowsValid signature from a publisher never seen before in the estate, found by signer rarity

    Critical TH-1 signed binary or driver loads

    Description. A malicious binary or kernel driver, signed with a stolen, bought, or otherwise abused certificate, executes or loads on a Windows host. Preconditions. The attacker already holds the certificate; a user runs the file or an installer stages it. Impact. Kernel-level persistence, credential theft, ransomware staging, and a free pass through signature-based checks. Justification. This is the direct end point of the technique, documented for many actors including Wizard Spider and OilRig. It is reliably detectable from Sysmon signature fields when you keep a publisher inventory, so it ranks Critical. TH-6 is the subtle first-seen variant; TH-1 is the broad rule that any valid signature outside your inventory is a reason to look.

    High TH-2 signing keys accessed on build infrastructure

    Description. An attacker with a foothold, or an insider, reads code-signing material from build infrastructure: CI/CD runner abuse, secrets vault reads, or an export of a .pfx key container. Preconditions. Access to build systems or leaked runner credentials. Impact. Your company certificate becomes the attacker's trust weapon, and revocation will embarrass you publicly. Justification. ATT&CK describes exactly this path: purchase using information stolen from a previously compromised entity. A single success poisons every downstream trust decision, so High.

    Medium TH-3 TI-reported abused signer hunted in stored telemetry

    Description. A vendor report names an abused certificate. You search your stored endpoint history and find that a host loaded a file signed by that identity. Preconditions. A working intelligence pipeline plus Sysmon 6/7 history. Impact. Confirms the payload reached you, often days before other signals. Justification. High value when it fires, but it depends fully on report quality and refresh, so a Medium rank with low false-positive volume. TH-5 is the automated, load-time version of the same idea.

    High TH-4 macOS ad-hoc signing and Gatekeeper bypass

    Description. Ad-hoc signed or unsigned binaries, plus Gatekeeper bypass tooling such as spctl, quarantine removal with xattr, and re-signing with codesign, tied to obtained signing tooling on Mac endpoints. Preconditions. User execution of an unnotarized app; local access. Impact. Malware that Gatekeeper would have blocked runs freely on macOS. Justification. Mac fleets are growing attack surface, the bypass leaves clear process evidence, and reporting on this pattern is rising, so High.

    High TH-5 revoked or watchlisted signer at load time

    Description. A driver or image loads while its signer sits on a watchlist of revoked or abused code signing certificates, or Sysmon itself records the signature status as Revoked or Expired although the file still loaded. Preconditions. The attacker reuses a certificate the CA cancelled or that intelligence has named; the host does not enforce revocation. Impact. The documented Mustang Panda and FIN8 patterns: payloads keep loading on hosts that do not check. Justification. A load-time control against an explicit list, with very low false-positive volume, so High.

    Medium TH-6 first-seen publisher in the estate

    Description. A file with a perfectly valid signature loads, but the publisher has never been seen in your estate before. A baseline lookup over your own image-load history provides the age of each signer. Preconditions. Stored Sysmon 7 history and an enrichment lookup; nothing else. Impact. Catches payloads signed with fresh certificates bought for one campaign, before any vendor report exists. Justification. NIMBUS MANTICORE obtained valid signatures through the public service SSL.com, per ATT&CK. The rule needs a baseline and tuning, so it ranks Medium and stays experimental.

    5.4Logs and patterns

    For each threat: where to look, which fields matter, what normal looks like, what suspicious looks like, and one realistic event-shaped example. Field names follow the most common logging formats; adjust them to your stack.

    TH-1 — signed binary or driver loads on Windows

    Log sources
    Sysmon Event ID 6 (driver load) and Event ID 7 (image load); Windows CodeIntegrity operational log; EDR module events
    Key fields
    EventID, UtcTime, Image, ImageLoaded, Signed, Signature, SignatureStatus, Hashes
    Normal behavior
    Drivers and DLLs from signers in your software inventory; SignatureStatus Valid for known vendors; loads from Program Files
    Suspicious behavior
    A Valid signature from a signer absent from your inventory, or named in a TI report; a driver loading from a user-writable path
    Detection logic
    Event 6 or 7 with Signed true and SignatureStatus Valid, where the signer is not on the expected publisher list; CodeIntegrity 3076 (audit) or 3077 (blocked) as independent confirmation

    The signer subject is synthetic, chosen for teaching. A driver under C:\Windows\System32\drivers signed by a publisher you have never shipped is the pattern worth waking up for.

    iCodeIntegrity 3076 and 3077

    On hosts that run Windows Defender Application Control (WDAC), the CodeIntegrity operational log writes event 3076 when a file does not meet the policy in audit mode, and event 3077 when the load is blocked in enforced mode. A driver that Sysmon shows as validly signed can still fail WDAC policy, so 3076 and 3077 are strong confirmations for TH-1. Collect them and treat them as high-signal, never as noise.

    TH-2 — signing keys accessed on build infrastructure

    Log sources
    AWS CloudTrail (secretsmanager.amazonaws.com); vault audit logs; CI/CD audit logs; Windows file audit on build hosts
    Key fields
    eventName, requestParameters.secretId, userIdentity.userName, sourceIPAddress, userAgent
    Normal behavior
    The dedicated signing principal reads signing secrets from known runner hosts during release windows
    Suspicious behavior
    GetSecretValue on signing secrets from a new principal or a hosting-provider IP; a .pfx file written to temp; signing jobs outside release windows
    Detection logic
    GetSecretValue where the secret name matches signing keywords and the caller is not the known signing principal

    The source address uses the reserved documentation range 198.51.100.0/24, which stands in for a hosting provider. The account name and secret name follow the pattern of the Sigma rule below; replace both with your own naming scheme.

    TH-3 — TI-reported abused signer matched in stored telemetry

    Log sources
    Sysmon Event ID 6 and 7 history across the estate; TI vendor reports; your signer inventory
    Key fields
    Signature, SignatureStatus, ImageLoaded, Hashes, plus subject and thumbprint from the TI report
    Normal behavior
    Signature subjects that match your inventory; no overlap with published abused-certificate lists
    Suspicious behavior
    A subject or thumbprint that matches a TI-reported abused certificate, on any host, even once
    Detection logic
    Endpoint signature history matched against the TI abused-signer list from one report; refresh the list monthly as vendors publish new abuse

    The subjects in this example, and in the matching Sigma rule later, are synthetic names chosen for teaching. Replace them with the real subjects from your threat intelligence list, and record the report and date next to each entry so you know when the list was last refreshed.

    TH-4 — macOS ad-hoc signing and Gatekeeper bypass

    Log sources
    macOS process telemetry (EDR or unified log); syspolicyd Gatekeeper decisions; MDM software inventory
    Key fields
    process path, command line, user, parent process, signing status, quarantine attribute changes
    Normal behavior
    IT and developer hosts use spctl and codesign during packaging; business users almost never touch them
    Suspicious behavior
    spctl --master-disable or --add from non-IT users; xattr -d com.apple.quarantine on downloaded apps; codesign -f -s with an unknown identity
    Detection logic
    Process creation for spctl, xattr, or codesign where the arguments show a Gatekeeper bypass or a re-signing operation

    Ad-hoc signing means the app carries a signature that proves nothing about the publisher; it is a self-made signature without an identity. Attackers use it to satisfy basic structure checks while avoiding any real identity, which is why a mix of ad-hoc files and bypass tooling on one host is a strong signal.

    TH-5 — revoked or watchlisted signer at image or driver load

    Log sources
    Sysmon Event ID 6 (driver load) and 7 (image load); a revoked or abused signer watchlist from TI, kept as a lookup; CA revocation status feeds
    Key fields
    EventID, UtcTime, ImageLoaded, Signed, Signature, SignatureStatus, Hashes
    Normal behavior
    Loaded files whose signers have a clean revocation record and no watchlist entry
    Suspicious behavior
    A load whose signer is named by TI as revoked or abused, or whose own SignatureStatus reads Revoked or Expired even though the file loaded
    Detection logic
    Event 6 or 7 with Signed true, and either the Signature on the revoked or abused watchlist or SignatureStatus in Revoked or Expired

    The signer subject is synthetic. The event shows the core pattern: the file loaded although its certificate is revoked, which happens on systems that do not enforce revocation. This is the documented Mustang Panda pattern, and the FIN8 expired-certificate case behaves the same way with an Expired status. On hosts where the status still reads Valid, only your TI watchlist reveals the abuse, which is the second branch of the rule.

    TH-6 — first-seen publisher in the estate

    Log sources
    Sysmon Event ID 7 (image load); a signer baseline lookup built from your own image-load history (SIEM or EDR export)
    Key fields
    UtcTime, Image, ImageLoaded, Signed, Signature, SignatureStatus, Hashes, plus the enrichment field signer_age_days
    Normal behavior
    Image loads from signers with months or years of history in the estate baseline
    Suspicious behavior
    A valid signature whose signer first appeared in the estate within the last 90 days, or has no baseline entry at all
    Detection logic
    Event 7 with Signed true and SignatureStatus Valid, joined to the baseline lookup: signer_age_days of 90 or less, where the enrichment writes 0 for signers the baseline does not know

    Nothing on the host is technically wrong here: the signature is valid. The anomaly is history. No file signed by this publisher has ever loaded in the estate before, and your enrichment lookup therefore returns an age of 0 days. The subject is synthetic. Once a vendor report names the signer, TH-3 and TH-5 take over with higher fidelity; until then, rarity is often the only local hint. Mark the rule experimental, review new publishers monthly, and promote legitimate ones into the baseline.

    5.5Sigma rules and Splunk SPL

    One Sigma rule and one matching Splunk query per threat. The Sigma logic and the SPL logic match by design. Replace index names, publisher lists, and watchlist contents with your own values before deploying, and record the mapping from rule to threat in your detection inventory.

    TH-1 — Sigma: validly signed driver or image from unexpected publisher

    SPL for TH-1. Maps to TH-1 (ATT&CK T1588.003, follow-on abuse as T1553.002). Assumes Sysmon data lands in index=sysmon with sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational; adjust to your environment. The selection matches the Sigma rule exactly: events 6 and 7, Signed true, status Valid, and the same five publisher substrings filtered out. The rex extracts a CN= form for readable output only.

    TH-2 — Sigma: vault access to code signing material

    SPL for TH-2. Maps to TH-2 (ATT&CK T1588.003 with T1552.004). Assumes CloudTrail in index=aws with sourcetype=aws:cloudtrail. The *... wildcard patterns mirror the Sigma |contains and |endswith modifiers one to one.

    TH-3 — Sigma: signer on the TI abused-certificate list

    SPL for TH-3. Maps to TH-3 (ATT&CK T1588.003). Assumes Sysmon in index=sysmon. The query uses the same three synthetic subjects as the Sigma rule, so the logic is identical; keep the two lists in sync or, better, move both to a shared lookup such as ti_abused_signers that carries the subject, the confidence, and the source report, and refresh it monthly.

    TH-4 — Sigma: macOS Gatekeeper bypass and re-signing

    SPL for TH-4. Maps to TH-4 (ATT&CK T1588.003). Assumes macOS process telemetry lands in index=macos with sourcetype=macos:process; if your EDR uses index=edr, swap the index and the field names (process_path, command_line) accordingly. The three bypass branches mirror the three Sigma selections one to one.

    TH-5 — Sigma: revoked or watchlisted signer at load time

    SPL for TH-5. Maps to TH-5 (ATT&CK T1588.003, follow-on abuse as T1553.002). Assumes Sysmon in index=sysmon. The selection is the Sigma logic written in SPL: events 6 and 7, Signed true, and the same two watchlist subjects or the same two status values. In production, replace the subject list with a lookup such as ti_revoked_signers that carries the subject, the revocation date, and the source report.

    TH-6 — Sigma: signature from a publisher never seen in the estate

    SPL for TH-6. Maps to TH-6 (ATT&CK T1588.003). Assumes Sysmon in index=sysmon plus a KV-store lookup signer_baseline with columns signer_cn and first_seen (date in YYYY-MM-DD form). The lookup enrichment and the coalesce to 0 mirror the Sigma signer_age_days|lte: 90 selection exactly, and the same four publishers are filtered out. rex again only normalizes the CN form for grouping.

    Tuning guidance

    Start every rule in search-only mode for two weeks and review hits with the data owner. For TH-1, grow the publisher list from your own signer inventory instead of adding suppressions one alert at a time. For TH-2, register every pipeline principal by name and review the list quarterly. For TH-3, refresh the subject list monthly and record the source report next to each entry. For TH-4, allowlist packaging hosts explicitly and keep the rule strict for everyone else. For TH-5, keep the revoked-signer list in a lookup with revocation dates, and check the Expired branch against your oldest deployed software. For TH-6, refresh the baseline monthly, promote legitimate new publishers, and exclude lab hosts.

    Validation in the lab

    Test each rule in a lab before production. For TH-4 you can remove the quarantine attribute from a file you downloaded yourself, confirm the rule fires with the right fields, and then delete the file. For TH-1, load a signed Microsoft driver and confirm the filter suppresses it. For TH-5 and TH-6, inject one synthetic Sysmon event into a test index and confirm both branches (watchlist and status, or age) fire as expected. Keep the test steps in the rule ticket so the next engineer can re-run them. All subjects and names in these rules are synthetic.

    Real-World Case Study

    Stuxnet (2007–2010) is the classic example of malware signed with stolen code signing certificates, and the reason the industry started treating signing keys as its most protected assets.

    Stuxnet is the clearest public case of T1588.003. The malware carried drivers signed with certificates that belonged to two real hardware companies, Realtek and JMicron. Public analyses agree that the attackers did not apply for those certificates. They stole the private keys from the companies and signed their own kernel drivers with them, so every system that trusted the signature chain loaded the drivers without complaint. All facts below come from public reporting by security vendors and press coverage; where something is an estimate or a reconstruction, the text says so.

    Context

    Stuxnet targeted industrial controllers, and public reporting links it to the Natanz uranium enrichment facility in Iran. It spread quietly between computers and jumped to isolated networks on USB removable media, which meant it reached machines that had never touched the internet. To install a kernel driver on a modern Windows system, the driver needs a valid signature. Stealing signing certificates solved that problem in one step. The certificates were issued to the real companies, by public CAs, so nothing about the signatures looked wrong.

    2005–2007 (estimated)

    Development of the earliest version

    Public vendor analyses date the first Stuxnet version to around this period. The exact start date is an estimate based on code timestamps and exploit choices; no group has publicly claimed authorship.

    June 2009 (public analyses)

    Earliest observed version in the wild

    Analysts later reconstructed versions of Stuxnet from 2009. This early build already showed the project's shape: propagation logic, exploit code, and the industrial control attack payload that made the worm famous.

    2009–2010 (estimated)

    Private keys stolen from Realtek and JMicron

    At some point before the signed builds appeared, the attackers obtained the private keys of two Taiwan-based hardware companies. Public reporting describes this as theft from the companies, not fraudulent issuance. The details of the theft were never publicly established, so treat this item as documented in effect but estimated in method.

    January 2010

    A build signed with the Realtek certificate

    A Stuxnet version appeared whose kernel driver was signed with a valid certificate belonging to Realtek. Because the certificate was real, current, and from a trusted chain, Windows loaded the driver without the warnings an unsigned driver would face.

    March–April 2010

    A build signed with the JMicron certificate

    A later version was signed with a certificate belonging to JMicron, a second, unrelated company. Using two different stolen identities showed the attackers' operational security: compromise of one certificate would not break the campaign.

    17 June 2010

    Discovery by VirusBlokAda

    The Belarus-based antivirus company VirusBlokAda publicly reported the worm on 17 June 2010, after it spread far beyond its intended targets on USB devices. Its unusual signed drivers and exploit chain drew immediate research attention.

    July 2010

    Global analysis confirms signed drivers

    Major vendors published deep analyses. Researchers highlighted that Stuxnet's drivers were signed with legitimate, unexpired certificates from Realtek and JMicron, and that the worm used several previously unknown Windows vulnerabilities. The signing abuse became the headline.

    July–August 2010

    Certificates revoked

    Within weeks of the first analyses, the certificate authorities revoked both abused certificates. Exact revocation dates differ between reports, so this entry is a period. Revocation stopped future trust for systems that check it, but it came years after the certificates were stolen, which is the gap attackers count on.

    Late 2010 – 2011

    Impact and lasting lessons

    Public estimates attribute the destruction or damage of roughly 1,000 IR-1 centrifuges at Natanz to the campaign; precise figures were never officially confirmed. Vendor analyses in 2011 documented the full version timeline. The incident permanently changed how the industry protects code signing keys.

    ?What is established and what is estimated

    Publicly established: the drivers were signed with real certificates from Realtek and JMicron; the certificates were revoked in the weeks after discovery (July to August 2010); VirusBlokAda reported the worm on 17 June 2010. Publicly estimated: the development start date, how the keys were stolen, the exact number of damaged centrifuges, and the attribution of the operation. This page keeps the two categories apart on purpose.

    Containment, eradication, and recovery

    Containment. For an organization hit by a Stuxnet-class worm, containment means cutting the spread paths first. Freeze or restrict removable media, segment network shares, isolate hosts that show the driver or injection anomalies, and hunt the whole estate for the file hashes and certificate subjects named in vendor reports. Blocking by signer subject and thumbprint catches every file signed with the stolen certificates, including rebuilds. Public reporting never described the victim's internal containment, so the specifics here are a reconstruction from the vendor guidance published at the time.

    Eradication. Eradication removes the worm and closes its doors. Run the removal tools vendors shipped; Microsoft added Stuxnet detection to the Malicious Software Removal Tool in 2010. Patch the exploited flaws (MS10-046, MS10-061, MS10-073), rebuild hosts where kernel components ran, and confirm the abused certificates stay revoked. Eradication also has an industry layer: certificate authorities, Microsoft, and antivirus vendors coordinated on revocation and cleanup, which took weeks.

    Recovery. Recovery means proving the door is closed. Restore systems from clean images where tampering is suspected, re-verify controller logic against its design, watch a clean telemetry window before reconnecting segments, and keep the signer blocks in place. The Stuxnet case adds one more recovery step for every organization: review whether your own signing keys could be next, and move them into hardware protection if they are not.

    Impact and consequences

    Beyond the physical damage, Stuxnet broke an assumption: that a valid signature chain proves a file is safe. Two companies spent years answering for abuse they did not commit, and every Windows release since has tightened driver signing rules. The worm also proved that signing trust, once stolen, multiplies across every target the attacker wants.

    Team collaboration, then and now

    The victim's team was never publicly documented, so these are the roles the industry learned from this case. CTI tracks the samples and names the abused certificates. The SOC monitors and hunts for the signer and the hashes. Incident response (IR) leads containment, eradication, and recovery. IT owns patching and removable-media policy. Legal assesses what the abuse means for the impersonated companies and for regulators. Comms prepares statements, because vendor reporting will name the certificates publicly anyway. Write these roles into your playbook before you need them, with one decision-maker per stage.

    Tools in the response

    The public response ran on known tools: antivirus engines and the Microsoft Malicious Software Removal Tool for detection and cleanup; reverse-engineering workstations used by vendor researchers to unpack the drivers; Microsoft patches MS10-046, MS10-061, and MS10-073 to close the exploited flaws; Siemens security advisories and customer guidance for industrial operators; and the certificate authorities' revocation process. A modern SOC adds Sysmon or equivalent logging, a signer watchlist, and a signer baseline, which are the controls this page builds.

    Lessons learned

    • Treat hardware-level and kernel-level trust assumptions as attack surface: a signed driver runs inside the operating system's most protected layer.
    • Code signing keys are the highest-value secrets a software organization owns. Store them in hardware protection, restrict access, and monitor their use.
    • Revocation is not instant protection. Systems that do not check revocation keep trusting a revoked certificate, so detection cannot rely on revocation alone.
    • One campaign can use several stolen identities. Hunt by report, not by one certificate.
    • Log signature fields everywhere. Organizations that kept signature metadata answer scope questions in hours, not weeks.
    • Share fast. Public vendor reporting in 2010 is what made revocation and cleanup possible at all.

    Mitigation and Defense

    You cannot stop a certificate from being bought or stolen elsewhere, but you can protect your own keys and make abused certificates fail. Enterprise controls, home advice, and a prioritized action list.

    ATT&CK is direct about this technique: the official mitigation is Pre-compromise [M1056], and its description says the technique cannot be easily mitigated with preventive controls, because it is based on behaviors performed outside the scope of enterprise defenses. Defense therefore has two goals. First, protect your own signing keys, so nobody can turn your company into the next stolen certificate. Second, reduce what an abused certificate can do once its payloads arrive: enforce policy, block known-abused signers, and monitor the events that expose them.

    !Common trap

    Do not allowlist software by signer name alone. A stolen certificate signs malware with a perfectly valid chain, under a name that looks like a real vendor. Combine the signature with path, inventory, and reputation checks so a valid-but-unknown signer still gets reviewed. And make sure revocation checks are actually enabled on the platforms you run, because a revoked certificate is only useless to attackers if somebody checks.

    Key facts

    T1588.003 — Code Signing Certificates (Resource Development, TA0042; parent T1588)
    Core idea
    Attackers buy or steal code signing certificates and use them to sign malware so it appears trusted
    How they get it
    Front-company purchase, theft from a compromised vendor, abused issuance, or second-hand, revoked, and expired certificates

    Response checklist

    • Confirm the report: subject, thumbprint, families, first and last seen, and revocation status of the abused certificate.
    • Check enforcement: whether your platforms honor revocation, and whether the TH-5 watchlist covers this signer yet.
    • Hunt the estate: search 90 days of Sysmon 6/7, EDR module loads, and mail gateway logs for the subject or thumbprint.
    • Check your own keys first: review vault reads, runner logins, and .pfx exports to rule out that your certificate is the abused one.
    • Contain: isolate hosts that loaded the payload, block the thumbprint in policy, and revoke sessions for affected users.
    • Eradicate: remove the signed payload and staged files, rotate any exposed credentials, and close the entry path.
    • Report and prevent: record the case, update the signer inventory, baseline, and blocklists, and share sanitized indicators with your ISAC.
