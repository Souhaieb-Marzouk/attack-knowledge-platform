T1588.006 Vulnerabilities

Before an attack, adversaries collect knowledge about software weaknesses. Some research the weaknesses themselves, some buy reports from vulnerability brokers, and some search public databases. 1

Overview

What this technique is, why knowledge of weaknesses is worth money, and where it sits in the attack chain.

What it is

T1588.006 covers attackers collecting knowledge about vulnerabilities before an attack. A vulnerability is a weakness in software or hardware that an attacker can misuse to make the system behave in unexpected ways. The knowledge is the asset here: testing data, a written report, or an exploit, which is a program that uses the weakness.

The attacker has three main ways to get this knowledge. They can research it in-house, buy it from a vulnerability broker, or collect it from public databases. A broker is a middleman who pays researchers for weakness reports and resells them, often to governments or criminal buyers.

Why it matters

Knowledge of a weakness is cheap to store and slow to expire. A zero-day is a weakness the vendor does not know about, so there are "zero days" to prepare a patch, which is the vendor's fix. An N-day is a weakness that is already public and has an official number, but many systems are still not patched.

For defenders this is a timing problem. The learning itself is invisible in your logs. What you can see is the wave that follows: scanning, machine-like requests against your web applications, and later a formal advisory. Learning to connect that wave to your own exposure is the core skill this page teaches.

Where it fits

This technique lives in the Resource Development tactic (TA0042), the phase before any contact with the target. Its sibling T1588.005 covers obtaining exploit code; T1588.006 is one step earlier and covers obtaining the knowledge of the weakness itself. Knowledge can then lead to buying or building an exploit.

After preparation, the knowledge flows into initial access, most often T1190 (Exploit Public-Facing Application). Detection engineers treat T1588.006 as an early-warning signal: it rarely fires an alert on its own, but it decides which request patterns your team should hunt for tomorrow.

Where the knowledge travels

A weakness follows a path from discovery to misuse, and defenders sit at several points along it. The table below is the map this page follows. Note how the attacker's options shrink as the knowledge becomes public: that is why disclosure timing is itself a defensive topic.

StageWhat happensWho can see it
DiscoveryA researcher or attacker finds a weakness in software that many organizations runNobody, if the finder stays quiet
MoneyKeep private, sell to a broker, or report to the vendor for a bountyVendors see reports; brokers stay quiet; intel teams map both
WeaponizationThe knowledge becomes a tested exploit, often in a private labNobody; this is the T1588.005 hand-off
ReconnaissanceMass scanning to find exposed instances of the weak softwareEvery defender that collects IDS alerts or web logs
UseAttack requests against vulnerable instances; data theftWebserver logs, DLP, database audit logs (if collected)
DisclosureVendor publishes a patch; CISA may add the CVE to the KEV catalogEveryone; the clock for emergency patching starts here

iKnowledge versus code

Keep the sibling split in mind. T1588.005 is about the attacker having working exploit code. T1588.006 is about the attacker knowing where software is weak, even without code yet. In real campaigns the knowledge comes first, the exploit follows, and the two techniques appear together in reports.

    The same story in words

    This written version covers exactly the same eight steps as the animation. Read it if you prefer text, use it with a screen reader, or quote it in a training session.

    Step 1

    Researching the target software

    A researcher working for the criminal side picks software that many organizations expose to the internet, such as a managed file transfer (MFT) product. They study documentation, download trial copies, and hunt for a weakness. No packet of yours is involved, so the defender sees nothing.

    Step 2

    The broker decision

    The finder now has three options: keep the weakness private, sell it to a vulnerability broker, or report it to the vendor for a bounty payment. In this story the finder sells to a broker, who resells the report to a criminal buyer. Vendors and intelligence teams try to map this trade, but your network still shows nothing.

    Step 3

    Building the exploit privately

    The criminal buyer turns the bought report into working exploit code and tests it against a trial copy in a private lab. This is the hand-off point to T1588.005, which covers obtaining the exploit itself. Again, nothing reaches the victim yet.

    Step 4

    Scanning for exposed targets

    The attacker scans wide parts of the internet for instances of the weak software. Intrusion detection systems (IDS), which watch network traffic and raise alerts, log scan signatures. Many organizations ignore this noise, but it is the first visible step of the whole story.

    Step 5

    Mass exploitation

    The attack requests begin: machine-like bursts of POST requests to unusual handler paths, sent by automated tools rather than browsers. Webserver logs at hundreds of organizations record the same patterns. Unpatched instances are entered.

    Step 6

    Data staged at one victim

    At one target organization, the attacker collects and stages files for later theft. The signals are faint: a large unusual export in database audit logs, or a data loss prevention (DLP) tool, which watches for data leaving, showing a spike. Nothing crashes, so nobody calls the SOC yet.

    Step 7

    Patch and KEV entry

    The vendor publishes a patch and an advisory. CISA adds the CVE, the public weakness number, to its Known Exploited Vulnerabilities (KEV) catalog, a list of weaknesses that attackers are actively using. From this moment every defender has both a deadline and a hunt task.

    Step 8

    The SOC responds

    The SOC checks its exposure list, applies the emergency patch, and hunts the documented request patterns over the last 90 days of web logs. One hit appears: the staged data from step 6. The response becomes a full incident with containment, notification, and reporting duties.

    Red flows are attacker actions. Amber flows carry the capability or the stolen data itself. Blue elements belong to the defender side. The products, prices, and timings are simplified for teaching. The important part is the shape: the knowledge phase is invisible, scanning is the first visible step, and the advisory turns the whole story into a deadline.

    3

    Red Team / Hacker Perspective

    Why weakness knowledge is traded like a commodity, which acquisition paths exist, and where the process leaks traces.

    ?Ethics and scope

    This section explains attacker behavior so defenders can detect it. It stays at the level of concepts and public reporting. It gives no vulnerability details and no exploitation steps. Any hands-on practice belongs in an isolated lab you own, with fake data, and clearly labeled as lab-only.

    Finding a weakness takes skilled people and time, so the result has market value. Legitimate buyers pay through coordinated disclosure, a process where the researcher reports the weakness to the vendor, waits for a patch, and receives a bounty and public credit. Criminal buyers pay more, ask fewer questions, and impose no rules. Reporting on the vulnerability market keeps showing the same gap: the illegal path is faster and often pays several times more than the bounty.

    ATT&CK documents how real groups did this. Sandworm Team conducted technical research into weaknesses of websites connected to Korean targets in 2017, which is in-house research. Volt Typhoon relied on publicly available exploit code for initial access, which starts with N-day knowledge. Leviathan weaponized publicly known weaknesses, and Storm-0501 obtained capabilities for N-day weaknesses in public-facing services. The pattern is the same at every skill level: knowledge first, weapon second.

    Acquisition channels

    In-house research

    Capable groups study popular software on their own: reading documentation, comparing versions, and testing trial copies in private labs. This costs months of work but produces exclusive knowledge. ATT&CK also notes a darker variant: targeting the systems of the researchers themselves to steal their findings.

    Vulnerability brokers

    Brokers pay researchers for weakness reports and resell them, most often to government clients and, in criminal markets, to any funded buyer. Prices rise with how widely the software is used and how quietly the weakness can be used. Buyers treat the report as a private asset, sometimes for years.

    Databases, public and closed

    Public databases list known weaknesses with numbers and descriptions, so N-day knowledge is free. Closed databases, leak sites, and stolen researcher notes trade for money. ATT&CK explicitly describes adversaries monitoring disclosures and taking data from closed sources, because there is usually a delay between discovery and publication.

    Watching the disclosure clock

    When a vendor publishes a patch, every unpatched customer becomes a target with a countdown attached. Groups stockpile N-day weaknesses before disclosure day and exploit in the window before customers finish patching. This is the most common path in real incidents, including the documented examples listed above.

    Conditions and preparation

    Knowledge alone is not an attack. The actor also needs a working exploit for that weakness (T1588.005), targets that still run the weak software, and a way to reach those targets from the internet. That is why mass exploitation campaigns always start with wide scanning: the attacker must know who still runs the weak version. Groups with strong research skills buy reports; groups with weaker skills wait for public N-days and reuse public exploit code. Both produce the same defender-visible wave: scanning, then requests.

    iLab-only practice example

    A safe classroom exercise looks like this: in an offline lab, run a vulnerability scanner against a deliberately weak test machine you own, then write a short report in the style a researcher would send to a vendor. Role-play the disclosure timeline on paper: discovery, vendor report, patch date, publication date. You are practicing the economics and the paper trail, without touching any real target. Label the exercise and the lab network clearly.

    Variations and common mistakes attackers make

    VariationWhat changesTrace it leaves
    Research in-houseExclusive knowledge, high cost, no deadlineQuiet until use; scanning starts the visible phase
    Buy from a brokerFast, expensive, report may be resold many timesBroker activity appears in vendor and intel reporting
    Collect N-daysFree knowledge, crowded, patch clock runningKEV and advisory listings; public exploit code
    Steal researchExclusive knowledge without the research costVictim breach disclosures; sudden shift in actor capability

    Mistakes that expose the acquisition

    Scanning for exposed targets is loud, and probe storms land in web logs even when IDS alerts are ignored. Automated tools leave machine-like request shapes: identical timing, unusual user-agent strings, and repeated calls to rare handler paths. Reusing the same handler paths across campaigns lets analysts link incidents the buyer believed were separate. And every public disclosure ends the quiet phase: the moment a CVE and a patch exist, defenders get a deadline and a hunt recipe at the same time.

    4

    Blue Team / SOC Perspective

    What the technique looks like from the inside, which artifacts survive, and a short triage flow your team can follow.

    First, the limits: reading documentation, buying a report, or testing an exploit happens on servers you cannot see, so no SIEM alert fires during the knowledge phase. Good teams therefore work on two layers. The first layer is intelligence: advisories, the CISA KEV catalog, and vendor bulletins tell you what is being used against everyone. The second layer is telemetry: webserver logs, IDS alerts, scanner exports, and cloud audit logs show the wave when it reaches you. The skill is joining the two layers quickly.

    Artifacts the technique leaves behind

    Scanning artifacts

    Mass scanning produces IDS alerts with scan signatures, bursts of connections to many ports, and web logs full of failed requests for paths that do not exist. One source asking for sixty different paths is a fingerprint, not a user.

    Web log artifacts

    Exploitation traffic looks machine-made: POST requests to rare handlers, automated user-agent strings, identical timing, and unusual response codes such as 302 redirects after data operations. Advisory writers often publish these request patterns for exactly this reason.

    Post-exploit artifacts

    After entry, the attacker's tools behave like any other: new cloud users and access keys, unexpected file writes on servers, and staged data waiting to leave. Database audit logs and DLP tools show the staging even when the web requests look normal.

    Where to look

    SourceWhat it showsWhy it helps
    CISA KEV catalogWeaknesses with confirmed active exploitationTurns patching into a dated, auditable obligation
    Vendor advisoriesPatch releases plus documented request patternsGives the exact hunt keys for your web logs
    NVD and CVE recordsNumbered weaknesses with scores and descriptionsThe shared index that joins intel to your inventory
    Webserver access logsProbe storms and machine-like request burstsShows both reconnaissance and exploitation attempts
    IDS alerts (Suricata or Zeek)Scan signatures and fingerprinting activityEarliest broad warning that a wave is moving
    Cloud audit logs (CloudTrail)New users, keys, and policy changes after entryReveals persistence added after a weakness was used
    Asset and exposure inventoryWhich systems run the weak software, and whereWithout this, every advisory question stays unanswerable

    Why this matters for the attack chain

    Catching the wave early collapses the rest of the chain. A probe storm noticed on day one becomes an exposure review instead of an incident. A documented request pattern hunted in 90 days of logs finds the victim before extortion starts. Teams with an exposure inventory answer the advisory question "are we affected?" in minutes; teams without one answer it after the attackers have already moved. That is why this pre-compromise technique has real detection value: it defines the exact patterns your downstream detections should expect.

    Short triage flow

    1. Get the trigger. A KEV addition, a vendor advisory, a client asking about a headline, or an IDS scan alert from your own edge.
    2. Map exposure. Search your asset inventory for the affected product and version, then mark which instances are internet-facing. No inventory means manual triage, so treat this gap as the finding.
    3. Hunt the patterns. Take the documented request patterns from the advisory and search 90 days of web logs for them, before patching, so you know whether you were already used.
    4. Check post-exploit behavior. New IAM users or access keys, unexpected server-side file writes, large exports in database audit logs, DLP spikes.
    5. Patch or virtual patch. Apply the vendor patch, or apply a web application firewall (WAF) rule, a filter in front of the application, while you test the patch.
    6. Escalate or document. Real hits become an incident with containment and notification duties. Clean hunts become an intelligence note with the next review date.

    ✓Good practice

    Treat every KEV addition as a four-step run: exposure check, pattern hunt, patch with a deadline, and a written result. Detection coverage for T1588.006 is built from many small, maintained hunts, not from one perfect rule.

    iWhat ATT&CK officially says

    MITRE gives T1588.006 one official detection strategy: DET0808 — Detection of Vulnerabilities. Its analytic AN1940 is honest about the limits: “Much of this activity will take place outside the visibility of the target organization, making detection of this behavior difficult.” The official advice is to focus on behaviors that show the knowledge is being used — the exploitation techniques: Exploit Public-Facing Application (T1190), Exploitation for Client Execution (T1203), Exploitation for Privilege Escalation (T1068), Exploitation for Stealth (T1211), Exploitation for Credential Access (T1212), Exploitation of Remote Services (T1210), and Application or System Exploitation (T1499.004). The official mitigation is Pre-compromise [M1056]: the learning and buying happen outside enterprise defenses, so no preventive control stops them.

    5.1Regulation mapping

    A weakness-focused threat matters to auditors because running known, unpatched weaknesses on sensitive systems is a textbook control failure. The table below maps the technique to common frameworks. Use it to justify detection engineering work in risk language, and to know which evidence an auditor may ask for.

    FrameworkControlWhy it appliesExpected evidence
    GDPR Art. 32 Requires security measures that match the risk. A known, unpatched weakness on an internet-facing system holding personal data is a common enforcement example. Patch SLA records, KEV response runbook, scan and exposure reports, incident tickets with timelines
    HIPAA Security Rule §164.308(a)(1)(ii)(A), §164.312(b) Demands risk analysis and audit controls. Unpatched weaknesses on systems that hold electronic health records are a recurring audit finding. Risk analysis updates, patch management policy, audit log review records

    PCI DSS 4.0 6.3.1, 11.3.1, 11.3.2 Cardholder environments must identify and manage critical vulnerabilities and run external scans through an approved scanner. Bi-weekly critical vulnerability records, quarterly external scan reports, exposure remediation notes
    NIST CSF 2.0 ID.RA-01, ID.RA-02, DE.CM-01 Links vulnerability identification and threat intelligence intake to network monitoring, which is the exact workflow of this page. Asset-vulnerability-risk mappings, intel intake records, monitoring coverage lists, detection backlog

    iAuditor-friendly framing

    When an auditor asks how you address a pre-compromise technique, answer with the downstream controls: exposure-based vulnerability management, a KEV-driven emergency patch SLA, documented request-pattern hunts, and an inventory you can query. Keep one page that lists which control touches which part of T1588.006. That page becomes your evidence pack.

    Every item you ingest needs a confidence level, or your alerts will argue with each other. Use three levels and write them into the detection metadata.

    LevelMeaningTypical source qualityHow you act

    2. Analyze each item: which product, which versions, is it in our inventory, is it internet-facing, what confidence.
    3. Apply by turning advisories into exposure checks, request-pattern hunts, and patch tasks, then link each task back to the intelligence item.
    4. Measure quarterly: which advisories produced hunts, which hunts found hits, how long patch SLAs took. Drop weak feeds, keep strong ones.

    5.3Threats ranking and categorization

    The six threats below are the realistic ways this technique turns into risk for an organization. They are ranked and categorized by platform. The same six threats are used in 5.4 and 5.5, so the section stays practical.

    ThreatRankCategoryOne-line summary
    TH-1CriticalNetwork · WebserverZero-day mass exploitation of an internet-facing application with machine-like request bursts
    TH-2HighNetworkPre-exploit probing and directory brute-forcing with 404 and 500 storms from one source
    TH-3HighCloud · IdentityN-day use against a cloud-edge service followed by suspicious IAM persistence
    TH-4MediumNetwork · IntelMass-scanning infrastructure fingerprinting exposed services before any exploit
    TH-5CriticalCloud · NetworkInternet-facing asset named in the CISA KEV catalog beyond its remediation SLA
    TH-6MediumNetworkBurst of vulnerability probing of one web application from one source

    Critical TH-1 zero-day exploitation of an internet-facing application

    Description. An attacker uses knowledge of an unreported weakness against an application exposed to the internet, such as a managed file transfer (MFT) server. The web logs fill with machine-like bursts: automated POST requests to rare handler paths with 200 or 302 answers. Preconditions. The attacker holds private knowledge and a working exploit; your instance is reachable and unpatched, which is inevitable for a zero-day. Impact. Server-side code execution, data staging, and extortion at scale, as the 2023 MOVEit campaign showed. Justification. Highest real-world damage in this family, affects hundreds of organizations at once, and the only defense at hour zero is behavioral detection, so Critical.

    High TH-2 probe storm before exploitation

    Description. One source asks for many different web paths in a short window, and most answers are 404 or 500. The source is mapping what exists on your server before trying a known weakness. Preconditions. A public-facing web application; the attacker holds an N-day weakness and needs targets. Impact. Reveals the reconnaissance stage; noisy attackers help you patch or block before real exploitation. Justification. Very common, cheap to detect, and a reliable early warning, so High even though the probing alone causes no damage.

    High TH-3 N-day use against cloud-edge services with IAM persistence

    Description. The attacker exploits an N-day weakness in a cloud-edge service, such as an identity proxy or file transfer appliance, and then adds persistence: a new cloud user, a new access key, or a new policy attachment within minutes. Preconditions. An unpatched public weakness in a service that fronts your cloud identity plane. Impact. Durable access to cloud resources and data, surviving the appliance patch. Justification. This mirrors the documented Storm-0501 pattern: N-day exploitation of public-facing services followed by cloud-side moves (Microsoft, 2024), and the cloud audit trail makes it reliably detectable, so High with good detection odds.

    Medium TH-4 mass-scanning infrastructure fingerprinting services

    Description. Scanner infrastructure sweeps wide address ranges and fingerprints exposed services, producing intrusion detection system (IDS) alerts with scan signatures and scanner user-agents. Preconditions. Nothing on your side; this happens to everyone with an internet presence. Impact. Low direct damage, but it marks the start of the wave and tells you what the attackers are looking for. Justification. High frequency, low single-event impact, and useful mostly as a trend signal, so Medium.

    Critical TH-5 KEV-listed weakness open past its remediation SLA

    Description. A vulnerability scanner finds a weakness on an internet-facing asset, and that weakness is named in the CISA Known Exploited Vulnerabilities (KEV) catalog, which lists flaws with confirmed active exploitation. The catalog entry carries a remediation due date, and the asset is still unpatched after it. Preconditions. Scanner coverage, a KEV feed, and an inventory that flags internet-facing assets. Impact. The exact precondition for mass exploitation (T1190): attackers hold the knowledge, use it in the wild, and your door is open past the deadline. Justification. A hit is a policy failure with active exploitation behind it, and the fix is known and tested, so Critical.

    Medium TH-6 vulnerability-probe burst against one web application

    Description. One source sends a burst of requests to well-known weakness probe paths, such as .env, .git, phpinfo, admin panels, and framework actuator endpoints, against one web application. This is a scanner testing your application against published N-day knowledge. Preconditions. A public-facing web application and public knowledge of its platform. Impact. Focused interest usually precedes exploitation attempts; the burst shows who is looking and at what. Justification. Common and easy to detect with an aggregation rule, but single bursts often end in nothing, so Medium.

    5.4Logs and patterns

    For each threat: where to look, which fields matter, what normal looks like, what suspicious looks like, and one realistic event-shaped example. Every example uses the real field names of its format (IIS W3C, Apache combined, CloudTrail JSON, Suricata EVE, Nessus CSV, nginx JSON), and the row values are synthetic teaching examples. The Sigma rules in 5.5 use the common webserver field names (c-uri, sc-status); the mapping note under each query shows how they translate to your extractions.

    TH-1 — zero-day exploitation of an internet-facing application

    Log sources
    Webserver access logs (IIS W3C, nginx, Apache); reverse proxy logs; WAF logs; server-side file audit for unusual writes
    Key fields
    date, time, s-ip, cs-method, cs-uri-stem, c-ip, cs(User-Agent), sc-status, sc-bytes, time-taken (IIS W3C)
    Normal behavior
    Users browse with browser user-agents, few POSTs per session, handlers match deployed application pages
    Suspicious behavior
    Automated client libraries POSTing to rare handler paths, 302 or 200 answers, little or no referer, bursts from few sources
    Detection logic
    POST plus machine-like user-agent plus success status, grouped per source per hour; alert on bursts rather than single calls. Tuning adds the handler-inventory rarity check (see 5.5)

    TH-2 — probe storm before exploitation

    Log sources
    Webserver access logs; reverse proxy logs; WAF rate reports
    Key fields
    client address, method, request path, status, user-agent (Apache combined format)
    Normal behavior
    A user requests a handful of paths per session; crawlers identify themselves and obey rate rules
    Suspicious behavior
    One source with 404 or 500 answers across 50 or more distinct paths within an hour, generic scanner user-agents
    Detection logic
    Count the distinct paths answered 404 or 500 per source per hour; alert when the count crosses the threshold

    TH-3 — N-day cloud-edge use with IAM persistence

    Log sources
    AWS CloudTrail; Azure and GCP audit logs; appliance admin logs from the exploited service
    Key fields
    eventName, sourceIPAddress, userIdentity.type, userAgent, requestParameters.userName
    Normal behavior
    Identity changes come from corporate ranges, known automation, or role-based sessions, and match change tickets
    Suspicious behavior
    CreateUser, CreateAccessKey, or AttachUserPolicy from a hosting network or unknown ASN, close in time to anomalous application logs
    Detection logic
    Identity-change events whose source network is outside approved ranges, scored higher when they follow anomalous web traffic

    TH-4 — mass scanning and fingerprinting

    Log sources
    Suricata or Zeek records at the network edge; firewall logs; passive DNS
    Key fields
    alert.signature, src_ip, dest_ip, dest_port, alert.category, severity
    Normal behavior
    Business traffic to documented services; occasional single scan hits from one-off sources
    Suspicious behavior
    Bursts of ET SCAN signature alerts from one source across many hosts or ports; scanner user-agents in related web logs
    Detection logic
    Group scan alerts per source and alert on volume, because single alerts are noise while bursts are the wave

    TH-5 — KEV-listed weakness open past its remediation SLA

    Log sources
    Vulnerability scanner exports (Tenable Nessus, Qualys, Microsoft Defender Vulnerability Management) normalized into the SIEM; CISA KEV catalog lookup; asset and exposure inventory
    Key fields
    Scanner: cve, plugin_id, host, port, risk_factor. Enrichment added by lookups: kev_listed, kev_due_date, internet_facing, days_past_due
    Normal behavior
    Findings get patched before their KEV due date; rescans show the fix; non-KEV findings follow the normal patch cycle
    Suspicious behavior
    A finding whose CVE is KEV-listed, on an asset flagged internet-facing, still present after the catalog due date
    Detection logic
    Join scanner findings to the KEV catalog by CVE, join the asset to the exposure inventory, and alert when the due date is past (days_past_due >= 1)

    The CVE in the row is real and KEV-listed, which ties this threat to the section 6 case study. The SIEM adds the enrichment columns with two lookups: a KEV lookup keyed on cve (carrying the official due date) and an inventory lookup keyed on host (carrying internet_facing). Keep both lookups refreshed daily, because the KEV catalog changes every week.

    TH-6 — vulnerability-probe burst against one web application

    Log sources
    Webserver access logs (nginx JSON shown here); WAF logs; reverse proxy logs
    Key fields
    time_iso8601, remote_addr, request_method, request_uri, status, http_user_agent (nginx JSON format)
    Normal behavior
    No requests to sensitive or framework-internal paths; one-off misses from links are rare and isolated
    Suspicious behavior
    One source requesting many known probe paths (.env, .git, phpinfo, wp-admin, phpmyadmin, actuator) in bursts, often with scanner user-agents
    Detection logic
    Count requests to probe paths per source per hour; alert on volume, because scanners fire bursts, not single requests

    The addresses in the examples use the reserved documentation ranges 203.0.113.0/24 and 198.51.100.0/24, which are safe for teaching material and must be replaced by your real watchlists in production. The user-agent string in the nginx example is the default of the public Nuclei scanner; your blocklists should expect a rotating set of such names.

    5.5Sigma rules and Splunk SPL

    One Sigma rule and one matching Splunk query per threat — six pairs in total. The Sigma logic and the SPL logic match by design, including the aggregation conditions: where a Sigma rule counts events or distinct values, the SPL twin uses stats count or stats dc() with the same threshold. Replace index names, network ranges, and thresholds with your own values before deploying, and record the mapping from rule to threat in your detection inventory.

    TH-1 — Sigma: machine-like POST bursts

    SPL for TH-1. The Sigma condition ends in the aggregation count() by src_ip >= 20: count() counts matching events per source, so the SPL twin groups with stats count and applies the same threshold of 20. The time window is the rule schedule, so run the Sigma rule hourly and keep the SPL bin at one hour. Assumes webserver access logs in index=web (for example sourcetype=iis for IIS W3C logs) with field extractions named cs_method, c_uri, sc_status, c_useragent, and src_ip; adjust to your environment.

    TH-2 — Sigma: directory probe storm from one source

    Aggregation mapping. In Sigma, count(field) counts the distinct values of the field, so count(c-uri) by src_ip > 50 means "more than 50 distinct request paths from one source". The SPL twin must therefore use dc(c_uri) (distinct count), not plain count, with the same threshold of 50. The window is the rule schedule: schedule the Sigma rule hourly and keep the SPL bin at one hour. SPL for TH-2. Assumes the same index=web extraction names as TH-1.

    TH-3 — Sigma: IAM persistence from an unfamiliar network

    The documentation ranges stand in for "unknown hosting network". In production, replace them with your own logic: an ASN lookup, a CIDR allowlist of approved networks, or a comparison against known corporate ranges. To express the time window of the story, raise the score when the same hour contains anomalous application logs, for example from the TH-1 rule. SPL for TH-3. The SPL implements the same three clauses 1:1: the same event names, the same source-range match, and the same exclusion. Assumes CloudTrail in index=aws with sourcetype=aws:cloudtrail.

    TH-4 — Sigma: IDS scan signature burst

    SPL for TH-4. The aggregation count() by src_ip >= 10 matches stats count with the same threshold; the filter_lab selection matches the src_ip!=10.0.* exclusion. Sigma has no built-in window here, so schedule both at the same interval (for example every 15 minutes) to keep the windows equal. Assumes Suricata EVE JSON in index=ids with sourcetype=suricata; adjust to your environment.

    TH-5 — Sigma: KEV-listed weakness past its remediation SLA

    Sigma has no standard log source for scanner exports. This guide uses category: vulnerability for normalized scanner findings, enriched with KEV and inventory columns; adapt the logsource line to your normalization. The fields kev_listed, internet_facing, and days_past_due are enrichment columns, like the domain-age pattern used for young-domain detections.

    SPL for TH-5. The numeric selection uses the Sigma modifier days_past_due|gte: 1, so the SPL twin evaluates the same integer comparison with >= 1. The SPL builds the enrichment columns exactly as the Sigma rule expects them: kev_listed from the KEV lookup, internet_facing from the inventory, and days_past_due from the official due date. Assumes normalized scanner findings in index=vuln (example sourcetype=tenable:sc:vuln), a KV-store lookup kev_catalog keyed on cve that carries the official due_date, and an asset inventory lookup asset_inventory keyed on host that carries internet_facing.

    TH-6 — Sigma: vulnerability-probe burst from one source

    Aggregation mapping. Here count() counts matching events (not distinct values), so the SPL twin uses stats count with the same threshold of 20; dc(request_uri) is an output column only. The Sigma webserver field names map to the nginx JSON fields like this: c-uri → request_uri, src_ip → remote_addr, sc-status → status. Schedule the Sigma rule hourly and keep the SPL bin at one hour. SPL for TH-6. Assumes nginx JSON access logs in index=web with sourcetype=nginx and the field names nginx writes (remote_addr, request_method, request_uri, status, http_user_agent).

    Tuning guidance

    Start every rule in search-only mode for two weeks and review hits with the data owner. For TH-1, build a handler inventory from 30 days of logs and add handler rarity as an enrichment field, because a per-request rule cannot join with a baseline. For TH-2, allowlist known crawlers by user-agent and reverse DNS. For TH-3, replace the documentation ranges with an ASN or CIDR allowlist. For TH-4, allowlist your authorized scanner ranges with expiry dates. For TH-5, refresh the kev_catalog and asset_inventory lookups daily and warn before due dates, not only after them. For TH-6, keep the probe-path list current with advisory and intelligence reporting and allowlist announced test windows.

    Validation in the lab

    Test each rule in a lab before production. Send twenty POSTs with a python-requests user-agent to a lab webserver you own to trigger TH-1, and request sixty random missing paths for TH-2. Replay a scanner finding with a test KEV row for TH-5, and send thirty probe-path requests from one source for TH-6. Confirm each rule fires with the right fields, and keep the test steps in the rule ticket so the next engineer can re-run them. All example addresses in this section are reserved documentation ranges.

    Real-World Case Study

    MOVEit Transfer and Cl0p (CVE-2023-34362, May–June 2023) shows weakness knowledge turned into the largest data theft extortion campaign of its year.

    The MOVEit campaign is the clearest public example of T1588.006 at industrial scale. The attackers held knowledge of a weakness in MOVEit Transfer, a managed file transfer (MFT) product used by thousands of organizations to move files with partners. Public reporting, including the CISA advisory AA23-158A and Microsoft reporting, describes how that knowledge became a working exploit and then a wave of attacks against hundreds of organizations in days. All facts below come from public reporting; where an actor link is attributed rather than proven, the text says so.

    Context

    MOVEit Transfer sits on the internet by design, because its job is receiving files from outside parties. That makes it crown-jewel attack surface (the small set of systems whose compromise hurts most): one weakness there touches every partner connection and every stored file. The actors publicly tracked as Cl0p, and attributed by Microsoft to the cluster Lace Tempest, are data theft extortionists: they steal data and demand payment for not publishing it, without encrypting systems. For this campaign they are believed to have prepared both the knowledge of the weakness and the exploit before the first attack, which is the exact T1588.006 pattern.

    Before May 2023

    Preparation, invisible to victims

    Public reporting indicates the exploit used in the campaign was developed and prepared in advance, with no public weakness number and no vendor patch existing yet. This is the zero-day knowledge phase of T1588.006: quiet, unobservable from the outside, and the reason the following wave moved so fast.

    On or about May 27, 2023

    Mass exploitation begins

    Per CISA and Microsoft reporting, exploitation of the weakness (CVE-2023-34362) in internet-facing MOVEit Transfer instances started around May 27, 2023. The attack traffic showed machine-generated patterns against the web application rather than human browsing, which later became the key detection point.

    May 31, 2023

    Vendor advisory and first patch

    The vendor published a security advisory and a patch. From this moment the weakness was an N-day, and every unpatched customer had a countdown attached. Organizations without an exposure inventory spent the following days answering one question: do we run this, and where?

    Early June 2023

    KEV listing sets the deadline

    CISA added CVE-2023-34362 to the Known Exploited Vulnerabilities (KEV) catalog, with a dated remediation deadline. For US federal agencies the catalog carries binding force; for everyone else it became the de facto emergency patching clock for this campaign.

    June 2, 2023

    Extortion without encryption

    The Cl0p leak site began listing victim organizations. The campaign's business model was data theft extortion: steal files, demand payment, publish refusers. No ransomware appeared, which caught many teams off guard, because their playbooks assumed encryption as the impact signal.

    June 5, 2023

    Microsoft attribution

    Microsoft Threat Intelligence attributed the mass exploitation to Lace Tempest, a Cl0p-related actor, and described the use of a web shell for data theft. Public reporting emphasized that the same crew had run similar campaigns against other large file transfer products in previous years, so the target choice matched a known strategy.

    June 7, 2023

    CISA advisory with request patterns

    CISA published advisory AA23-158A with detection guidance and indicators. It documented the machine-generated request patterns seen in exploitation, including calls to handler paths such as human.aspx and machine2.aspx, giving every defender concrete strings to hunt for in web logs.

    Mid-June 2023

    Follow-up patches

    Additional weaknesses in the same product (CVE-2023-35036 and CVE-2023-35708) were disclosed and patched within days, and CISA updated the advisory. The lesson repeated: one weakness became several, and response teams had to re-run exposure checks and hunts each time.

    June–July 2023

    Named victims across sectors

    Public reporting named government agencies, state motor vehicle agencies, energy organizations, and large companies among the affected, including organizations reached through their payroll suppliers. Data from tens of millions of individuals was reported stolen by trackers following the campaign.

    October 2023

    Scale confirmed

    Public trackers counted over 2,000 organizations and tens of millions of individuals affected, making it one of the largest mass exploitation campaigns measured. Almost all of it ran through one weakness, one product, and one prepared exploit, which is why the knowledge phase matters more than any single intrusion step.

    The attack chain in technique terms

    Chain stepWhat the attacker heldClosest technique

    WeaponizationA working exploit prepared in advance (public reporting)T1587.004 or T1588.005

    Containment, eradication, and recovery

    Detection. Detection in this campaign happened in web logs. Organizations that hunted the documented request patterns found their hits before the extortion mail arrived, which moved them from surprised to prepared.

    Containment. Containment meant taking the vulnerable instance offline or blocking the attack paths at a web application firewall, then assuming data theft had occurred, because the campaign's goal was theft, not damage.

    Eradication. Eradication required removing the web shell, applying the vendor patch, and rotating exposed credentials to the stored files and to connected systems.

    Recovery. Recovery focused on proof: clean logs, a patched build, and a written picture of exactly which files had been exposed, because notification duties depended on that answer.

    Impact and consequences

    Two thousand organizations and tens of millions of individuals, per public trackers, with no encryption anywhere. The campaign showed that data theft extortion scales through weakness knowledge, and that "we were not ransomed" is not the same as "we were not breached". It also set new expectations for how fast internet-facing file transfer software must be patched.

    Team roles in the response

    Threat intelligence (CTI) tracked Cl0p reporting, the advisory detail, and the leak sites. The SOC triaged web-log hunts and the KEV exposure checks. Incident response (IR) led containment, forensics on the web shell, and eradication. IT owned the patching race across fleets and re-scans. Legal assessed notification duties across jurisdictions, and communications (comms) handled partner, customer, and public statements.

    Tools involved

    MOVEit Transfer as the targeted product; a web shell (human2.aspx, per Microsoft reporting) as the post-exploitation tool; the Cl0p leak site as the extortion channel; CISA advisory AA23-158A and the KEV catalog as the defender's playbook; webserver, WAF, and DLP logs as the evidence base; vendor patches as the fix.

    Lessons learned

    • Internet-facing file transfer is crown-jewel surface, and deserves the same telemetry and patch SLA as a payment system.
    • A zero-day response playbook must work before any CVE exists: hunt behavior, not numbers.
    • Assume data theft even without ransomware, and let the file inventory, not the attackers, decide the notification scope.
    • Vendor disclosure speed saved customers: patch within the advisory window, not the quarterly cycle.
    • Documented request patterns are the fastest hunt key; collect web logs long enough to search history.

    Mitigation and Defense

    You cannot stop the research or the sale, but you can shrink the window in which weakness knowledge works against you. Enterprise controls, home advice, and a prioritized action list.

    ATT&CK is honest about this technique: the official mitigation is Pre-compromise [M1056], and its description says the technique cannot be easily mitigated with preventive controls, because the learning and buying happen outside enterprise defenses. Defense therefore has two goals. First, reduce how long knowledge stays useful: patch fast, shrink exposure, and buy time with virtual patches. Second, detect the behavior that knowledge produces: request patterns, identity changes, overdue KEV items, and staged data.

    Enterprise controls

    AreaControlWhat it stops
    Vulnerability managementExposure-based prioritization: internet-facing and exploited-in-the-wild first, not the highest score firstThe long windows in which N-day knowledge works (TH-2, TH-3, TH-5)
    Emergency patchingKEV-driven SLA with dated obligations for every catalog entry, and escalation for overdue itemsMass exploitation campaigns that ride the patch gap (TH-1, TH-5)
    Attack surfaceQueryable inventory of internet-facing applications; remove or restrict MFT and admin panels that do not need exposureFewer instances for one report to compromise (TH-1, TH-5)
    Virtual patchingWeb application firewall (WAF) rules per advisory while patches are testedBuys days against zero-day and N-day waves (TH-1, TH-2, TH-6)
    Behavior detectionThe six Sigma rules of section 5.5: request bursts, probe storms, IAM persistence, scan bursts, KEV overdue, probe pathsZero-days at hour zero and the wave before them (TH-1 to TH-6)
    Threat-informed huntingAdvisory request patterns hunted across 90 days of web logs on publication dayFinds already-exploited hosts that patching alone would miss (TH-1, TH-3)
    Scanner data pipelineFeed scanner findings by API into the SIEM and inventory, with daily KEV and exposure lookupsMakes the TH-5 overdue-exposure rule possible at all
    Disclosure intakesecurity.txt, a vulnerability disclosure policy, and a bug bounty programTurns researchers into reporters instead of sellers or brokers

    !Common trap

    Do not sort patch work by CVSS score alone. A score of 7 on an internet-facing file transfer server that is exploited in the wild matters more than a score of 9 on a laptop that never leaves the office. Sort by exposure first, exploitation evidence second, score third.

    Home and small office

    Mitigation M1056 is an enterprise statement, but the same logic works at home: weakness knowledge mostly attacks unpatched machines, so updates are the strongest habit. The table lists what to do and why it defeats a bought capability.

    Cheat Sheet and Quick Reference

    Everything important from this page on one screen: facts, top detections, a response checklist, and the links to go deeper.

    Key facts

    Technique
    T1588.006 — Vulnerabilities (sub-technique of T1588, Resource Development TA0042)
    Core idea
    Attackers collect knowledge of software weaknesses through research, brokers, or databases, then turn it into exploits
    Sibling split
    T1588.005 is obtaining the exploit code; T1588.006 is obtaining the knowledge of the weakness itself
    Official guidance
    Mitigation M1056 Pre-compromise; detection strategy DET0808 (Detection of Vulnerabilities) with analytic AN1940: much of the activity is invisible, so watch exploitation behaviors
    Where detection happens
    Scanning waves, machine-like web requests, IAM changes, KEV-overdue exposure, data staging, and the advisory stream
    Best early signal
    A KEV addition matched against your exposure inventory, plus the documented request patterns from advisories

    Response checklist

    • On a new KEV entry or advisory: identify the affected product and check the exposure inventory within hours.
    • Hunt the documented request patterns across 90 days of web, proxy, and WAF logs before declaring yourselves clean.
    • Run the TH-5 KEV-overdue search and clear every hit before its catalog due date; escalate what cannot be patched and add a virtual patch.
    • Check post-exploit behavior: new IAM users or keys, unexpected file writes on servers, large exports in audit logs.
    • Apply the vendor patch, or a WAF virtual patch first, and verify with a test that the rule blocks the documented pattern.
    • Assume data theft if any hit was found: scope the stored files, rotate exposed credentials, and start notification duties.
    • Write the result down: what fired, what was found, what was patched, and which detection was added so the next advisory is faster.
