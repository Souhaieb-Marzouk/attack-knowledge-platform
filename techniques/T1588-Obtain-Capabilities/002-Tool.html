T1588.002 Tool

Before an attack starts, attackers gather software tools. They buy commercial hacking frameworks, crack trial versions, steal licenses, or download free open-source tools such as password dumpers and remote access clients. This guide explains the technique in plain language, shows an animated example, and gives defenders practical detections, Sigma rules, and Splunk queries.

Overview

What this sub-technique is, why it matters to defenders, and how it differs from its neighbor techniques.

What it is

T1588.002 covers the way attackers obtain software tools before an attack. A tool is normal software. It was built for administrators, testers, or researchers, but it works just as well for an attacker. The official definition is wide: tools can be open or closed source, free or commercial, and the acquisition can include commercial licenses.

The three paths are simple. Attackers buy a tool or a license, steal one from a vendor or from another criminal, or download a free open-source project. A special case is cracking: taking a trial version of commercial software and removing its license checks. Cracked copies of one commercial attack framework, Cobalt Strike, became a criminal ecosystem of their own.

Why it matters

Tools do the hard work of an intrusion: command and control (the channel an attacker uses to control a victim machine), credential theft, and moving between computers. ATT&CK documents tool acquisition by many groups: Turla obtained and customized Mimikatz, Inception used the open-source LaZagne, BITTER obtained PuTTY, and FIN7 and DarkVishnya both used Impacket.

For defenders this means you rarely see the purchase, but you will meet the tool. Cracked and default tool builds are noisy: they keep default names, default certificates, and default network fingerprints. Learning those defaults is the core skill this page teaches.

Where it fits

This sub-technique lives under T1588 (Obtain Capabilities) in the Resource Development tactic (TA0042), the phase before any contact with the target. It is not the same as its neighbors: T1587 covers tools an actor builds, and T1588.001 covers malware, software written to be harmful. A tool, in contrast, has a normal purpose. ATT&CK gives PsExec as the example: a legitimate admin utility that attackers also love.

After acquisition, the tool flows into the attack chain: execution, credential access, lateral movement. Detection engineers treat tool acquisition as a pre-positioning signal (the attacker is getting ready before they touch you). It tells you which tool defaults your rules should watch for tomorrow.

    The same story in words

    This written version covers exactly the same eight steps as the animation. Read it if you prefer text, use it with a screen reader, or quote it in a training session.

    Step 1

    Planning the toolkit

    A threat actor lists what the operation needs: a command and control framework, credential theft tools, and utilities for moving between machines. Buying is faster than building, so the plan starts with a shopping list. Nothing has touched the target yet, so the defender sees nothing.

    Step 2

    Getting cracked tools

    The actor buys a cracked copy of a commercial attack framework on a criminal forum and downloads open-source tools like Mimikatz and LaZagne. Public reporting documents exactly this pattern: FIN7 and DarkVishnya used Impacket, and cracked Cobalt Strike builds power many intrusions. The cracked build keeps the framework’s default traits, which later become detection markers.

    Step 3

    Setting up the team server

    The actor uploads the toolkit to a rented server and starts the framework’s team server, the component that beacons connect to for orders. A TLS certificate is requested for the fresh domain. Certificate transparency logs publish it within minutes, which is the first public trace.

    Step 4

    Configuring the beacon

    The actor edits the malleable profile, the configuration file that controls how the beacon talks and looks. Skilled operators change everything; most buyers keep the defaults. Every default, from pipe names to the TLS certificate, is a marker defenders already know.

    Step 5

    Phishing delivers the loader

    A phishing mail carries a link to the staging server. The loader writes beacon.exe into a user folder and creates its first named pipe, the local channel the beacon uses to talk to other processes on the machine. Sysmon sees the file write and the pipe creation as two separate, matching events.

    Step 6

    Beacon check-in

    The beacon calls home over HTTPS. The cracked build uses its default TLS settings, so the network sensor flags a known client fingerprint, called a JA3 hash, and an IDS alert fires on the framework’s traffic pattern.

    Step 7

    Credential tools on the host

    With an active session, the actor runs credential dumping and remote execution tools. Process creation logging records the odd command lines and the process ancestry that leads back to the exploit chain. A workstation that should never run these tools just did.

    Step 8

    The SOC joins the dots

    The security operations center (SOC) correlates the pipe name, the network fingerprint, and the process lineage into one case. The host is isolated and sessions are revoked before ransomware can follow. The lesson: cracked tools fail because their defaults survive.

    How to read the animation

    Red flows are attacker actions. Amber flows carry the tool or the payload itself. Blue elements belong to the defender side. The panel on the right of the canvas lists what a security operations center (SOC) could see at that exact moment, including the steps where the honest answer is nothing.

    What is realistic here

    This story is a composite of public reporting on cracked commercial frameworks and on groups that obtained tools, such as FIN7 with Impacket and Inception with LaZagne. The forum names, prices, and timings are simplified for teaching. The important part is the shape: the tool is acquired early, configured lazily, and its defaults become the defender’s best markers.

    3

    Red Team / Hacker Perspective

    Why attackers prefer obtaining tools over building them, which acquisition channels exist, and where the process leaks traces.

    ?Ethics and scope

    This section explains attacker behavior so defenders can detect it. It stays at the level of concepts and public reporting. It gives no operational instructions for attacking real systems. Any hands-on practice belongs in an isolated lab you own, with fake data, and clearly labeled as lab-only.

    An attacker chooses the cheapest path to a working tool. Writing a reliable framework takes months. A cracked copy costs almost nothing and works the same evening. This is why obtained tools dominate real intrusions: ATT&CK documents tool acquisition across dozens of groups, from financially motivated crews to state-linked teams.

    Obtained tools also buy cover. When hundreds of crews run the same cracked framework, defenders and police cannot link one incident to one group by the tool alone. Even capable teams keep public tools in the mix for exactly this reason. The ATT&CK entry for T1588.002 lists Turla customizing Mimikatz and Magic Hound obtaining web attack tools like Havij, showing that skill level does not remove the shortcut.

    Tools also serve preparation, not just attack. Actors evaluate their malware against commercial endpoint security products, using obtained copies of those products or their trials. That means a purchased or cracked tool can be part of the attacker’s lab long before any victim is touched.

    Acquisition channels

    Cracked commercial frameworks

    Commercial attack tools like Cobalt Strike are sold for legitimate penetration testing. Attackers crack trial builds or buy leaked licenses. Public reporting describes a whole resale ecosystem around cracked Cobalt Strike builds, which is why the default traits of that one commercial product appear in intrusions everywhere.

    Free and open-source tools

    Projects like LaZagne, Impacket, and Metasploit can be downloaded by anyone. They are legitimate for their intended users, which also means they are rarely blocked by name alone. ATT&CK documents Inception obtaining LaZagne and FIN7 using Impacket for targeting efforts.

    Stolen and leaked toolkits

    Attackers steal tools from each other, from vendors, and sometimes from security companies. Leaked builders and shared archives move through forums. Once a toolkit leaks, thousands of low-skill actors can use it, which multiplies the detection problem for defenders.

    Licenses through front identities

    Some actors buy commercial software licenses using stolen or fake company identities. This gives them a genuine, supported build of the tool. The license paperwork is invisible to defenders, but the tool it activates is not: genuine builds still carry detectable defaults.

    Conditions and preparation

    Acquisition has its own prerequisites. Payment usually runs through cryptocurrency so money is hard to trace. The actor needs hosting to test what it bought and skill to wire the parts together: a cracked framework still needs servers, a profile, and a delivery method. Groups with less skill buy complete packages; capable groups assemble components. The attacker also needs operational security, and this is where many fail. Keeping a cracked build quiet means changing its loud defaults, and many buyers never bother.

    iLab-only practice example

    A safe classroom exercise looks like this: in an offline lab you own, download a well-known open-source security tool from its official repository, run it against a test machine you control, and record every artifact it creates: files, processes, pipes, and network traffic. You are replaying what a blue team sees after an obtained tool runs, without touching any real target. Label the exercise and the lab network clearly.

    Variations and common mistakes attackers make

    VariationWhat changesTrace it leaves
    Cracked trial buildFree, but often old and unchangedDefault pipes, default certificate, known JA3, license watermarks
    Genuine license, fake buyerFully featured, supported, quietInvoice trail exists somewhere; the tool itself looks normal
    Open-source downloadFree and public, needs skill to weaponizeKnown hashes, public detection content, repository download traffic
    Stolen or leaked toolkitFree for the takerShared hashes and family traits across unrelated groups
    Tool kept for lab testingPrepares evasion before the attackSandboxes and vendor evaluation copies see it first; nothing victim-side yet

    Mistakes that expose the acquisition

    Buyers keep the default license watermark, the ID stamped into every beacon, so researchers can link all their campaigns. They keep default pipe names and the default self-signed certificate, which sensors flag on day one. They share team servers across campaigns, so one discovery breaks many operations. And they download tools from public repositories over infrastructure they reuse elsewhere, linking a criminal identity to an otherwise anonymous purchase. Each mistake is a pivot for the defender.

    4

    Blue Team / SOC Perspective

    What the technique looks like from the inside, which artifacts survive, and a short triage flow your team can follow.

    The purchase happens on servers you cannot see, so no alert fires when money or files change hands there. MITRE is clear about this: most of the activity sits outside the visibility of the target organization. Good teams therefore work on two layers. The first is intelligence: know which tools are circulating and what their defaults look like. The second is telemetry: detect the tool the moment it touches an endpoint, a server, or the network.

    Artifacts the technique leaves behind

    Named pipe artifacts

    Frameworks like Cobalt Strike use named pipes (channels that let programs on one Windows machine talk to each other) for local and lateral work. Default builds create pipes with names like MSSE-1668-server or postex_ssh_8f21. Sysmon Event ID 17 records every pipe creation.

    File artifacts

    Obtained tools land on disk: beacon.exe and artifact.exe from default framework builds, laZagne.exe in a temp folder, archives staged for later use. Hashes of cracked builds accumulate in public malware repositories.

    Process artifacts

    Credential tools leave very specific command lines, such as sekurlsa::logonpasswords. Impacket remote execution shows a marker pattern of cmd.exe called by WmiPrvSE.exe. These strings often survive renaming, because the tool’s own output text stays the same.

    Network artifacts

    Default TLS certificates (the framework’s self-signed certificate with its published subject), known JA3 client fingerprints, and IDS signatures for framework traffic. Malleable profiles can hide these, but only if the buyer bothers to configure them.

    Linux artifacts

    Staged toolkits on Linux servers appear as executables in /tmp, /dev/shm, or /var/tmp, often freshly compiled with gcc and run by no scheduled service. The auditd subsystem can record every execution with its full path.

    Intelligence artifacts

    Cracked builds carry license watermarks, and samples end up in sandboxes. Vendors publish YARA rules (pattern searches for malware families) and hashes. This layer tells you what to hunt before you ever see it yourself.

    Where to look

    SourceWhat it showsWhy it helps

    Sysmon Event ID 1 and Windows 4688Process creation with command line and parentCatches tool command lines and process lineage

    Why defaults decide the outcome

    Obtained tools are a detection gift in disguise. A custom implant can be unique, but a cracked framework shared by hundreds of crews must stay compatible with itself, and that keeps its defaults alive. Teams that watch default pipes, default certificates, and default command lines get free coverage against a large share of real intrusions. Teams that only block tools by name miss every renamed copy.

    Short triage flow

    1. Receive or find the marker. An IDS alert, a pipe event, or an intelligence report names a tool family or one of its default traits.
    2. Enrich it. Check the hash in malware repositories, the watermark in vendor reporting, and the certificate subject in your proxy logs.
    3. Check exposure. Search 90 days of endpoint, network, and Linux telemetry for the trait, not just for one hash.
    4. Validate hits with context. Which host, which user, which process ancestry, and does that host have a legitimate reason to run this tool at all.
    5. Escalate or document. Real hits become incidents with containment steps. Empty results become an intelligence note with the next review date, so the hunt stays alive.

    ✓Good practice

    Write one rule per default trait, not per tool name. Pipe patterns and certificate subjects survive renames and rebuilds. Keep every rule linked to the intelligence report that motivated it, with an owner and a review date.

    iWhat ATT&CK officially says

    MITRE rates direct detection of T1588.002 as difficult and lists the mitigation Pre-compromise [M1056], because the buying happens outside your boundary. The official detection strategy DET0852 — Detection of Tool gives one main analytic, AN1984: “Monitor for contextual data about a malicious payload, such as compilation times, file hashes, as well as watermarks or other identifiable configuration information.” For tools this means license watermarks and default build traits. MITRE also says that much of the activity stays invisible, and that detection efforts may focus on post-compromise phases of the adversary lifecycle.

    Read the official T1588.002 page for the full strategy text. The rest of section 5 turns these official hints into concrete rules.

    iAuditor-friendly framing

    When an auditor asks how you address a pre-compromise technique, answer with the downstream controls: application control, credential protection, named pipe monitoring, IDS rule freshness, cloud audit review, and a documented intelligence process.     ATT&CK documents rich real-world usage for this exact sub-technique: Turla obtained and customized publicly available tools like Mimikatz; TEMP.Veles obtained tools such as Mimikatz and PsExec during the TRITON-related campaign C0032; Inception obtained and used open-source tools such as LaZagne; Magic Hound obtained tools like Havij; BITTER obtained tools such as PuTTY; FIN7 and DarkVishnya obtained and used Impacket; and MirrorFace deployed multiple publicly available tools during Operation AkaiRyū. Treat these entries as seed intelligence for hunts in your own environment.

    Confidence levels

    Every item you ingest needs a confidence level, or your alerts will argue with each other. Use three levels and write them into the detection metadata.

    LevelMeaningTypical source qualityHow you act
    HighMultiple independent reports, or observed in your own telemetryTwo vendors plus a repository sample of the cracked buildBuild a detection within days, treat hits as incidents
    MediumOne credible report or partial corroborationSingle vendor blog with technical detail on a tool buildSchedule a hunt, watch for corroboration
    LowRumor, unclear sourcing, or old dataForum chatter about a new crack, unverified screenshotsStore in the backlog, revisit on the next review date
    1. Collect from at least two source types above, on a fixed weekly rhythm, into one shared place.
    2. Analyze each item: which tool is affected, which defaults survive, which platforms, what confidence.
    3. Apply by turning traits (pipe names, JA3 hashes, certificate subjects, user agents, command lines) into hunts and detections, then link each detection back to the intelligence item.
    4. Measure quarterly: which intelligence items produced detections, which detections fired, and which feeds never produced anything useful. Drop weak feeds, keep strong ones.

    5.3Threats ranking and categorization

    The six threats below are the realistic ways this technique turns into risk for an organization. They are ranked and categorized by platform. The same six threats are used in 5.4 and 5.5, so the section stays practical.

    ThreatRankCategoryOne-line summary
    TH-1CriticalEndpoint · WindowsCracked commercial framework beacon with default named pipes and default files
    TH-2HighEndpoint · WindowsCredential dumping and remote execution tools run on non-admin hosts
    TH-3MediumNetworkKnown C2 framework fingerprints in IDS alerts, JA3 hashes, and certificates
    TH-4HighLinux serversOffensive toolkits staged and compiled in Linux temporary directories
    TH-5MediumCloud · IdentityScripted attack tooling driving cloud audit-log sessions and IAM enumeration
    TH-6HighEndpoint · Windows/LinuxTool staged from a code-sharing or paste site onto a server, then executed

    Critical TH-1 cracked framework beacon with default traits

    Description. A beacon from a cracked or carelessly configured commercial command and control framework runs on a workstation. Default named pipes such as MSSE-*, postex_*, and status_*, default executable names like beacon.exe and artifact.exe, and default TLS certificate traits all survive. Preconditions. The tool was obtained through cracking or lazy setup, and initial access already happened. Impact. Full interactive control of the endpoint and a staging point for ransomware. Justification. Cracked builds of one commercial framework power a huge share of real intrusions; the defaults give reliable, high-fidelity detections, and an uncaught beacon is one step from domain compromise, so the rank is Critical.

    High TH-2 offensive credential tools on non-admin hosts

    Description. Credential dumping and remote execution tools such as Mimikatz, LaZagne, Impacket’s wmiexec and secretsdump patterns, or misused ntdsutil run on hosts that have no business running them. Preconditions. The attacker has a session or valid credentials, and the tools were obtained and staged. Impact. Credential theft at scale and a path to full domain compromise. Justification. This is extremely common post-compromise behavior and ATT&CK lists many groups doing exactly this. Command-line evidence is strong, but only where command-line logging is enabled, so High rather than Critical.

    Medium TH-3 known C2 framework network fingerprints

    Description. Known fingerprints of command and control frameworks appear in network traffic: IDS signatures for framework traffic, default JA3 client fingerprints, and default self-signed certificates. Preconditions. A beacon is active and communicating, and the buyer kept the framework defaults. Impact. Confirms active compromise and gives clean pivots to find every other host using the same build. Justification. High fidelity when it fires, but malleable profiles can remove the fingerprint entirely, so coverage is partial and the rank is Medium.

    High TH-4 toolkits staged and compiled on Linux servers

    Description. Offensive or staging toolkits are compiled and run on Linux servers: executables produced by gcc or ld that run from /tmp, /var/tmp, or /dev/shm, busybox drops, and tar archives staged for transfer. Preconditions. The attacker has a foothold on a Linux host, often through a web shell or an exposed service. Impact. The toolkit becomes the base for attacking other internal systems. Justification. A common staging pattern on servers that few teams watch. Detection is cheap with auditd, but coverage is rare in practice, so the risk stays High.

    Medium TH-5 scripted attack tooling driving cloud sessions

    Description. A bought or stolen cloud credential is first used by a scripted offensive tool, not by a person. The cloud audit log cannot show the tool download, but it shows the session: generic script user agents, IAM enumeration calls, and bursts no documented process runs. Preconditions. A leaked access key, a bought session cookie, or a phished console session. Impact. The attacker maps accounts and roles, then prepares data theft or compute abuse in your subscription. Justification. Common in cloud-first estates and cheap to detect from audit logs, but a hit confirms access to one cloud identity rather than the whole estate, so Medium.

    High TH-6 tool staged from code-sharing sites, then executed

    Description. The actor downloads an obtained offensive tool, such as a tunnel or proxy binary, from a paste or code-sharing site straight onto a server, and then runs it from a temp path. Preconditions. A foothold or an unmanaged service account, plus outbound access to the sharing site. Impact. The staged tool becomes the base for lateral movement and remote access. Justification. ATT&CK documents actors obtaining tools from GitHub and similar sites, and the download-and-run pair is highly detectable, but tuning server and CI noise takes real work, so High.

    5.4Logs and patterns

    For each threat: where to look, which fields matter, what normal looks like, what suspicious looks like, and one realistic event-shaped example. Field names follow the most common logging formats; adjust them to your stack.

    TH-1 — cracked framework beacon with default traits

    Log sources
    Sysmon Event ID 17 (pipe created) and 18 (pipe connected); Sysmon Event ID 11 (file create); EDR process and file events
    Key fields
    PipeName, Image, TargetFilename, Hashes, User, ProcessGuid
    Normal behavior
    Pipes created by browsers, office software, and update agents with random or vendor-specific names; executables written from managed installers
    Suspicious behavior
    Pipes named MSSE-*, postex_*, or status_*; files named beacon.exe or artifact.exe in user-writable paths; the creating process is unsigned or sits in AppData
    Detection logic
    Pipe name pattern match on Sysmon 17/18, or default beacon file name written by any process, joined to the process image for context

    The pipe name MSSE-1668-server follows the default pattern of a well-known commercial framework. A random-looking name like this is exactly what a malleable profile would have changed, so its presence tells you the operator kept the defaults.

    TH-2 — offensive credential tools on non-admin hosts

    Log sources
    Sysmon Event ID 1 (process create); Windows Security Event ID 4688 with command-line auditing; EDR process events
    Key fields
    Image, CommandLine, ParentImage, User, Computer, Hashes
    Normal behavior
    Administrators run such tools only from dedicated admin workstations or on domain controllers for documented maintenance
    Suspicious behavior
    Tool names or command patterns like sekurlsa::logonpasswords, secretsdump.py, or wmiexec.py on a normal workstation; cmd.exe spawned by WmiPrvSE.exe; ntdsutil with create full on a member server
    Detection logic
    Command line or image name matches a known offensive tool pattern, minus an allowlist for documented admin hosts

    The command line shown is the classic marker of Impacket’s wmiexec: a quiet cmd.exe with redirected output, launched by WMI. The same threat also covers direct tool executions, for example laZagne.exe or mimikatz.exe appearing in a user’s Downloads folder.

    TH-3 — known C2 framework network fingerprints

    Log sources
    Suricata EVE JSON alerts; Zeek ssl.log and conn.log; firewall and proxy records
    Key fields
    alert.signature, ja3_hash, tls.sni, issuerdn, src_ip, dest_ip, dest_port
    Normal behavior
    Business TLS to known SaaS ranges; occasional IDS hits from old signatures that match legacy software
    Suspicious behavior
    An IDS signature naming a known command and control framework; a default framework JA3 hash; a self-signed certificate with the framework’s published default subject
    Detection logic
    IDS signature contains the framework name, or the JA3 hash matches a documented default fingerprint

    The destination address uses the reserved documentation range 203.0.113.0/24, which is safe for teaching material. The JA3 hash is the fingerprint of how the client speaks TLS; the certificate subject shown is the framework’s default, which a configured profile would replace. Depending on your Suricata version and SIEM add-on, the JA3 hash can appear as a top-level field or under tls.ja3_hash; pick the name your pipeline actually produces.

    TH-4 — toolkits staged and compiled on Linux servers

    Log sources
    Linux auditd (EXECVE and SYSCALL records for execve); file integrity monitoring; shell history where available
    Key fields
    type, a0 (binary path), exe, comm, ppid, uid, hostname
    Normal behavior
    Executables run from package paths, /usr/bin, /opt, and build servers that run from documented temporary workspaces
    Suspicious behavior
    Execution of freshly compiled binaries from /tmp, /var/tmp, or /dev/shm; busybox downloads or drops; tar.gz archives staged in those paths
    Detection logic
    EXECVE record where the executed binary path starts with a temporary directory, minus allowlisted build workspaces

    The record shows syscall 59, which is execve, running a binary that lives in a hidden directory under /tmp. The name imitates a system cache folder. A file integrity monitor would also show the binary appearing minutes earlier, which is the compile-and-run pattern of a staged toolkit.

    TH-5 — scripted attack tooling driving cloud sessions

    Log sources
    AWS CloudTrail (or Azure sign-in and audit logs); cloud SIEM; IAM access review reports
    Key fields
    eventSource, eventName, sourceIPAddress, userAgent, userIdentity.type, userIdentity.userName
    Normal behavior
    Console logins and SDK calls from corporate ranges; documented automation with known SDK user agents; MFA on interactive logins
    Suspicious behavior
    IAM enumeration such as ListUsers or ListRoles from a hosting-provider address with a generic script user agent like python-requests; a dormant key suddenly listing accounts and roles
    Detection logic
    IAM read calls whose user agent matches generic script or attack tooling, reviewed per account, source address, and business owner

    The source address is from the reserved documentation range 198.51.100.0/24 and stands in for a hosting provider. Nothing in this single event is malicious by itself; the signal is the combination: an enumeration call, a generic script user agent, and a service account whose documented automation never calls IAM.

    TH-6 — tool staged from a code-sharing site, then executed

    Log sources
    Sysmon Event ID 11 (file create) and Event ID 1 (process create); proxy logs for the site request; EDR
    Key fields
    UtcTime, Image, CommandLine, TargetFilename, Hashes, User, ParentImage
    Normal behavior
    Signed installers write to documented tool paths; CI fetches packages from approved repositories and package managers
    Suspicious behavior
    A script host such as PowerShell fetching from a paste or code-sharing site into temp, a new executable landing there, and that file running minutes later
    Detection logic
    A download command line naming a sharing site, a script-hosted temp file write of an executable type, or execution from a temp path — three signals, one rule

    The two events share one ProcessGuid, so the file write is linked to the PowerShell download. Moments later a second process-create event would show chisel.exe running from the temp folder. Those are exactly the three signals of the TH-6 rule: download command, staged file, and execution from temp. Proxy logs would show the same request leaving the server.

    5.5Sigma rules and Splunk SPL

    One Sigma rule and one matching Splunk query per threat. The Sigma logic and the SPL logic match by design. Replace index names, allowlist values, and lookup tables with your own values before deploying, and record the mapping from rule to threat in your detection inventory.

    TH-1 — Sigma: default framework pipes and beacon file names

    SPL for TH-1. Assumes Sysmon data lands in index=sysmon with sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational; adjust to your environment.

    TH-2 — Sigma: offensive tools on non-admin hosts

    SPL for TH-2. Assumes Sysmon data in index=sysmon as above. The .paw.corp.example suffix is an example for privileged access workstation naming; replace it with your own.

    TH-3 — Sigma: framework signatures and default JA3 fingerprints

    SPL for TH-3. Assumes Suricata EVE JSON lands in index=ids with sourcetype=suricata and the JA3 hash extracted into a field called ja3_hash (common with a Suricata add-on). Field names here use the dotted EVE form, so alert.signature is one field.

    TH-4 — Sigma: execution from Linux temporary directories

    SPL for TH-4. Assumes auditd records land in index=os with sourcetype=linux_audit and EXECVE records keep the a0 argument field (adjust to your auditbeat or add-on mapping).

    TH-5 — Sigma: attack tooling user agents in cloud audit logs

    SPL for TH-5. Assumes CloudTrail lands in index=aws with sourcetype=aws:cloudtrail. The userAgent field is the raw CloudTrail value; adjust if your add-on renames it. Keep an inventory of your documented automation so known script agents can be allowlisted the same way the Sigma filter would.

    TH-6 — Sigma: tool staged from a code-sharing site and executed

    SPL for TH-6. Assumes Sysmon data in index=sysmon as above. The three selections fire as separate events; the download and the file write usually share a ProcessGuid, so keep it in the output to join them.

    Tuning guidance

    Start every rule in search-only mode for two weeks and review hits with the data owner. TH-1 is near zero-noise and can go live early. TH-2 needs your real admin host naming in place of the example suffix. TH-3 needs your rule feed confirmed and JA3 extraction tested. TH-4 needs a per-host list of legitimate build workspaces. TH-5 needs an inventory of your automation so known script agents are allowlisted. TH-6 needs your CI and package-manager patterns allowlisted first. Track every rule in your detection inventory with the threat ID it covers.

    Validation in the lab

    Test each rule in a lab before production. For TH-1, create a local test pipe whose name matches the pattern on a lab host and confirm the Sysmon event and the rule fire. For TH-2, run an echo of a harmless string that contains a pattern token and check the search works. For TH-4, copy /bin/true into /tmp on a test VM, run it, and confirm the auditd record appears. For TH-5, replay a sample CloudTrail event into a lab index and confirm the search fires. For TH-6, copy a signed system tool such as notepad.exe into the temp folder of a lab host, run it once, and confirm the execution signal fires. Keep the test steps in the rule ticket so the next engineer can re-run them.

    Real-World Case Study

    The 2021 ransomware attack on Ireland’s Health Service Executive (HSE) shows what happens when obtained and shared tooling runs unnoticed for two months.

    In May 2021, the Health Service Executive, Ireland’s national health service, was hit by Conti ransomware. The facts below come from public reporting, from the independent post-incident report that the HSE itself published, and from the CISA advisory AA21-265A on the Conti playbook. The technique link is direct: the attack was carried out with obtained and shared tools, the pattern this page describes. The Conti operation distributed a playbook and a shared toolbox to its affiliates, and the HSE attack was executed by one of those affiliates.

    Context

    Conti was a ransomware group that ran a franchise-style model. A core team built the ransomware and shared tooling, guides, and infrastructure with affiliated crews, who then executed attacks. Public reporting and the 2022 leak of Conti’s internal chats describe a toolbox that included the Cobalt Strike framework, Mimikatz-style credential tools, remote access utilities like Plink, network scanners such as Advanced Port Scanner, and data staging utilities like Rclone. This is T1588.002 at organizational scale: the group did not need every operator to obtain tools separately, because the playbook shipped with them. Some details differ between reports; where sources disagree, this page follows the HSE post-incident report.

    2021-03-16

    Phishing reaches the HSE

    According to the public post-incident report, a phishing email with a malicious attachment was opened on an HSE workstation. The initial delivery did not use a zero-day exploit; it used ordinary office software and human trust. The HSE reported that antivirus alerts were raised but the response did not stop the intrusion at this point.

    2021-03-18

    First Cobalt Strike beacon

    Two days later, the attackers deployed Cobalt Strike beacons, giving them interactive control of the environment. The framework was an obtained tool, not something the crew wrote. From here the intrusion had a stable command channel, and the beacon’s presence became the pivot for everything that followed.

    2021-03 to 2021-05

    Two months of quiet tool use

    The public report describes weeks of lateral movement, credential theft, and privilege escalation using common offensive and administrative tools. Because the tools were familiar utilities and the beacons blended into normal traffic, none of this raised a decisive alarm at the time. This long silent phase is the core T1588.002 lesson: the tools were already known quantities with known defaults.

    2021-05-13

    Data staging before the strike

    In the days before the ransomware detonated, the attackers prepared the data theft. Public reporting describes large volumes of data gathered for exfiltration and later published under pressure, a pattern consistent with staging utilities such as Rclone. Staging is one of the last quiet steps, and it is one where volume anomalies are visible if anyone is watching.

    2021-05-14

    Conti ransomware detonates

    Early in the morning of 14 May 2021, the Conti payload executed across thousands of machines. Detection arrived here, at impact, not during the two months of tool use before it. The HSE took the precaution of shutting down its entire network, which stopped the spread but also stopped many clinical and business services.

    2021-05

    Immediate impact

    COVID-19 testing and contact tracing were disrupted, appointments and radiology services were canceled, and staff reverted to paper. Public reporting states that around 700 gigabytes of data was stolen and later published on the group’s leak site under pressure. Patient care was affected nationally, and the incident dominated Irish public life for weeks.

    2021-05 to 2021-06

    Containment and eradication

    The HSE worked with Ireland’s National Cyber Security Centre and external partners. Containment meant the full network shutdown; eradication meant checking and rebuilding servers and workstations, rotating credentials, and hunting for every beacon and staged tool before systems could come back.

    2021-06 onward

    Phased recovery

    Systems were restored in phases over weeks and months, with some services taking far longer. In public statements, HSE leadership pointed to remediation and restoration costs in the region of 100 million euro. The long recovery reflected the size of the estate and the need to rebuild trust in every restored system.

    2021-12 to 2022

    Public report and the Conti leaks

    The HSE published an independent post-incident report in late 2021. Its lessons included network segmentation, patching of legacy systems, better logging and monitoring visibility, and stronger privileged access controls. In February 2022, a leak of Conti’s internal chats confirmed how systematically the playbook and its shared toolbox moved between affiliates.

    Containment, eradication, and recovery

    Containment. The network shutdown stopped the encryption spreading further and froze the attackers’ interactive access. It was drastic, and the HSE chose it because patient safety data and unknown attacker access were both at stake. The lesson for less severe cases: isolate affected hosts and revoke sessions first, so containment does not have to be total.

    Eradication. Teams verified device by device, removed beacons and staged tools, and rebuilt anything that could not be trusted. Credentials were rotated, including privileged accounts, so the stolen secrets from the tool phase lost their value.

    Recovery. Systems came back in phases, with clinical priorities first, and clean logs had to prove that no beacon or staged tool remained. Teams with good logging visibility could answer the key question faster: which tools ran here, when, and with which credentials.

    Impact and consequences

    The attack disrupted a national health service at the worst possible time, during a pandemic. Beyond the direct damage, it changed how health systems worldwide treat segmentation, legacy systems, and logging. The 700 gigabytes of stolen patient and business data gave criminals leverage, and publication caused harm long after systems were restored. Remediation and restoration costs reached the region of 100 million euro, and the recovery consumed staff attention for the rest of the year.

    Team response and communication

    Every event needed a team, not a tool. Threat intelligence (CTI) tracked the Conti playbook and shared indicators. The security operations center (SOC) triaged alerts and supported the hunts. Incident response (IR) led containment, forensics, and eradication. IT operations rebuilt systems and managed the phased recovery. Legal handled the extortion contact, data protection duties, and law enforcement liaison. Communications ran public statements, patient guidance, and staff updates. Ireland’s National Cyber Security Centre coordinated technical support across all of these roles. Write the same roles into your playbook before you need them, with one decision-maker per stage.

    Lessons learned

    • Two months of tool use went unnoticed: monitor for known tool defaults, not only for the final payload.
    • Alerts that fire early are only alerts if routing and response follow them; make tool detections someone’s job.
    • Network segmentation limits how far an obtained tool can travel after one host falls.
    • Patch and retire legacy systems, because staged toolkits feed on old, unmonitored servers.
    • Logging and monitoring visibility is a patient-safety control, not a compliance checkbox.
    • Privileged access controls decide whether credential tools find anything worth stealing.
    • Share findings publicly: the HSE report, the CISA advisory, and the Conti leaks turned one attack into sector-wide defense.

    Mitigation and Defense

    You cannot stop the purchase of a tool, but you can make obtained tools fail. Enterprise controls, home advice, and a prioritized action list.

    ATT&CK is honest about this technique: the official mitigation is Pre-compromise [M1056], and its description says the technique cannot be easily mitigated with preventive controls because the behavior happens outside enterprise defenses. Defense therefore has two goals. First, reduce what an obtained tool can do once it arrives. Second, make sure that when the tool runs, its defaults hit detections you actually watch.

    Enterprise controls

    CredentialsLSA Protection and Credential Guard, plus privileged access workstations for adminsCredential dumping tools finding usable secrets (TH-2)
    Detection engineeringNamed pipe monitoring via Sysmon 17/18, YARA rules for framework defaults, decoy pipes on serversDefault framework beacons and lateral movement pipes (TH-1)

    !Common trap

    Do not defend by tool name alone. Renaming mimikatz.exe defeats a name blocklist in seconds, while the tool’s command lines, pipes, and traffic stay the same. Block and detect by behavior and default traits, and use names only as one weak signal among several.

    Home and small office

    Obtained tools reach homes too, mostly through phishing and bundled downloads. The habits below are short, but each one takes away the payoff of a bought capability. This is the same advice ATT&CK’s Pre-compromise mitigation points to in spirit: harden what the tool will touch.

    HabitWhy it defeats a bought capability
    Turn on automatic updates for the operating system and browserMost purchased exploits and loaders only work on unpatched machines, so updates close their entry door
    Leave the built-in antivirus or protection stack switched onCloud reputation checks catch stealer and loader families days after they first appear
    Keep a 3-2-1 backup: three copies, two media, one offlineRansomware that arrives through a staged toolkit loses its leverage when files survive it
    Use a password manager plus multi-factor authentication everywhereA credential dumping tool that grabs your password still cannot log in without the second factor
    Update the router and smart devices, and change default passwordsHome devices run the same edge software that off-the-shelf attack tools target
    Agree on a family code word for urgent voice or video requestsA cloned voice produced by an AI tool cannot answer a question only your family knows
    Treat urgent payment or identity requests as hostile until verified by a second channelMost purchased phishing kits and tool-driven scams depend on speed, not skill

    Cheat Sheet and Quick Reference

    Everything important from this page on one screen: facts, top detections, a response checklist, and the links to go deeper.

    Key facts

    Technique
    T1588.002 — Tool (Resource Development, TA0042; parent T1588)
    Core idea
    Attackers buy, steal, crack, or download normal software tools to use during attacks, including commercial licenses
    What counts
    Open or closed source, free or commercial; examples: Cobalt Strike, Mimikatz, Impacket, PsExec, PuTTY, LaZagne
    Not this technique
    Self-built tools are T1587; malware itself is T1588.001
    Official guidance
    Mitigation M1056 Pre-compromise; detection strategy DET0852 (Detection of Tool) with analytic AN1984 (monitor contextual payload data: compilation times, hashes, watermarks)
    Where detection happens
    Named pipes, process command lines, IDS and JA3 fingerprints, Linux temp directory execution, cloud audit user agents, paste-site staging, intelligence matches
    Best early signal
    Default traits: MSSE-*, postex_*, status_* pipes, default certificates, known command lines

    Response checklist

    • Pivot the marker (pipe name, JA3 hash, command line, hash, user agent) across 90 days of endpoint, network, Linux, and cloud telemetry.
    • Enrich: malware repositories for hashes, vendor reporting for watermarks and build details, your license inventory for legitimacy.
    • Confirm scope: which hosts ran the tool, which users, which process lineage, and whether credentials or cloud keys were exposed.
    • Contain: isolate affected hosts, revoke sessions, block the team server domains and IPs, reset exposed credentials, disable exposed cloud keys.
    • Eradicate: remove beacons and staged files, verify no default pipes remain, close the delivery path.
    • Recover: watch a clean telemetry window before reopening services in stages.
    • Report and prevent: record the case, turn the tool’s traits into new detections, share sanitized indicators with your ISAC.
