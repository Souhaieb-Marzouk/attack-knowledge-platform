Endpoint Denial of Service T1499

Attackers can knock a server offline without ever breaking into it. This guide explains how endpoint denial of service works, shows a safe lab animation, and gives defenders the logs and ready-made detection rules to catch it. Every command here is labeled for lab use only, on machines you own.

    1. Overview: what is endpoint denial of service?

    This section explains the technique in plain words, shows where it sits in an attack, and how it differs from network denial of service.

    Endpoint denial of service (DoS) is an attack that makes a computer, or the services running on it, unusable. The attacker sends traffic or requests that eat the resources the service needs: CPU time, memory, disk space, or the operating system's table of open connections. Some attacks crash software with a bug instead of flooding it. MITRE ATT&CK tracks this behavior as T1499. ATT&CK is a free public catalog of attacker techniques that defenders use to organize detection.

    The official ATT&CK description says that adversaries perform this technique to degrade or block the availability of services to users. Example services include websites, email services, DNS (the system that turns names into addresses), and web-based applications. The attack works in one of two ways: exhausting the system resources those services run on, or exploiting the system to cause a persistent crash condition. The official page lists four observed motives: political purposes, distraction (supporting other malicious activity), hacktivism, and extortion.

    ATT&CK draws one sharp line for this technique. An Endpoint DoS denies the availability of a service without saturating the network used to provide access to that service. If the attack instead floods the network pipes, ATT&CK tracks it as T1498 Network Denial of Service. The table below contrasts the two.

    The attack can come from one machine, or from many machines spread across the internet, which is called a distributed DoS (DDoS). Two aspects apply to most methods. The first is IP address spoofing: the attacker fakes the sender address of packets. This defeats source-address filtering and can enable reflection, which means other servers send the attack traffic. The second is botnets: hijacked devices controlled by the attacker, either built by the attacker or rented by the hour.

    In the worst DDoS cases, so many systems take part that each one only sends a small amount of traffic. The flood then blends in with legitimate clients and is very hard to tell apart. Botnets drove some of the most high-profile attacks, such as the 2012 series of incidents against major US banks. Traffic manipulation has also been used. In one historic case, censorship-grade network equipment injected JavaScript into client web traffic, and those clients then flooded the target web servers.

    Family 1: resource exhaustion

    The attacker floods a service with work: half-open TCP connections (connections opened but never completed), repeated expensive requests, or endless data. The service slows down, then stops answering. The machine itself may stay up while everything on it times out.

    Family 2: crash by exploitation

    The attacker sends a crafted request or packet that triggers a bug in an unpatched service. The program crashes and restarts, crashes and restarts, or stops for good. No flood is needed — one packet can be enough.

    Why it matters

    Availability is one of the three core security goals, next to confidentiality and integrity. When a shop, a hospital portal, or a factory system goes down, work stops and money is lost. Extortion groups use DoS to demand payment; some groups attack to distract defenders from an intrusion happening at the same time.

    No foothold needed

    A DoS attack needs no password and no malware inside the target. The attacker only needs a reachable service. This is why T1499 sits in the Impact tactic: it is the harm itself, not a step toward it.

    Where it fits in the attack chain

    The ATT&CK chain ends with Impact. A denial of service can be the final goal, or it can be cover for another attack. While responders fight a flood, the attacker may quietly try to break in somewhere else. Treat every DoS event as a possible distraction and check the rest of your telemetry. In this guide you will learn to recognize the technique. You will watch a safe simulation of it, find its signals in logs, write working Sigma and Splunk rules, and mitigate it.

    The layer model: what gets exhausted

    The official description explains that a service is a stack of layers. Each layer has its own bottleneck. Each bottleneck has its own sub-technique, so the layer you defend decides the control you need.

    Layer of the stackWhat the attacker exhaustsExampleSub-technique
    Operating system (OS)Kernel resources: connection tables, process table, memoryA SYN flood (a storm of connection-opening packets) fills the kernel's half-open connection tableT1499.001 OS Exhaustion Flood
    Server applications (web servers, DNS servers, databases)Service worker slots, sockets, and service memoryHalf-open HTTP requests keep every web-server worker busyT1499.002 Service Exhaustion Flood
    Application on top (typically web-based)Expensive features: search, export, report generationRepeated heavy queries burn CPU and database timeT1499.003 Application Exhaustion Flood
    Any layer, via a bugNothing is exhausted; a crafted input triggers a crashOne malformed packet crashes an unpatched serviceT1499.004 Application or System Exploitation
    Note

    ATT&CK words it this way: attacking each layer requires different techniques that take advantage of bottlenecks unique to the respective components. That is why this guide ranks threats by layer in section 5.3 and pairs each threat with the log source that actually sees it.

    The four sub-techniques

    IDNameOne-line summary
    T1499.001OS Exhaustion FloodFloods the operating system itself, for example a TCP SYN flood that fills the kernel connection table.
    T1499.002Service Exhaustion FloodExhausts one service, for example keeping many HTTP connections half-open so the web server runs out of slots.
    T1499.003Application Exhaustion FloodSends expensive requests, for example heavy search or report queries that burn CPU and database time.
    T1499.004Application or System ExploitationUses a software bug to crash a service or the whole system, without a flood.

    Both can hit at once. Many real campaigns mix network and endpoint vectors, which is why the simulation in the next section shows both the flood and the host gauges. ATT&CK lists Containers, IaaS, Linux, Windows, and macOS as the official platforms for this technique.

    This animation shows a small flood attack from both sides at once. You see the attacker's steps and, at the same time, what the SOC analyst sees — the SOC is the security operations center, the team that watches alerts. It is a drawing on a canvas, not real traffic.

    Step 1 of 8 — Recon probe: one normal-looking request to the web service.

    Defender hint: single requests are invisible to defenders. Traffic baselines start here.

    Tip: hover or tap a drawn node to read what it is.

    Note

    Text alternative for the animation, with the same eight steps. Each step names the attacker action and the defender view.

    1. Step 1 — Recon probe. The attacker sends one normal-looking HTTP GET request to the target web server. The server answers in a few milliseconds. The SOC traffic graph sits at its usual baseline — the normal measured level of traffic — and no alert fires.
    2. Step 2 — Botnet assembled. Three botnet nodes switch on. A botnet is a set of hijacked devices that an attacker controls remotely. Each node now holds a small attack script and waits for the command.
    3. Step 3 — Flood starts. The nodes stream TCP SYN packets and repeated HTTP requests at the server. The SOC traffic graph starts to climb above its baseline.
    4. Step 4 — Gauges go amber and red. The server's CPU, memory, and connection gauges rise. The kernel connection table fills with half-open connections that never complete.
    5. Step 5 — Legitimate user blocked. A real customer tries to open the site and gets timeouts, drawn as a red X. This is the moment of real impact: availability is lost.
    6. Step 6 — SOC alert fires. The SOC screen raises a traffic anomaly alert. The analyst compares the graph with the baseline and pulls flow records to find the top talkers.
    7. Step 7 — Mitigation. The edge firewall rate-limits new connections and blocks the botnet address ranges. Flood packets bounce off the filter line; the user's request gets through.
    8. Step 8 — Recovery. The gauges fall back to green, the block rules stay in place, and the user request succeeds with a green check. The incident moves to review.

    3. Red team perspective: how attackers use it

    This section describes how attackers choose and build this technique, so you understand what to look for. All commands are for a lab you own.

    When and why attackers pick it

    • Extortion: stop the flood in exchange for payment, often in cryptocurrency.
    • Protest (hacktivism): take a symbol offline to draw attention.
    • Distraction: keep responders busy while another intrusion runs.
    • Sabotage or rivalry: hurt a competitor's service during a critical window.
    • Red team testing: prove that availability controls work, inside your own organization.

    Prerequisites and conditions

    • A reachable, exposed service (web, DNS, mail, VPN — virtual private network — or game server).
    • Knowledge of the target stack: software, version, expensive endpoints.
    • Enough sources: one host, a rented botnet, or many cloud machines.
    • For T1499.004 only: a known, unpatched bug that crashes the service.
    • For stealth: patience, because a slow ramp stays under fixed thresholds.

    Conceptual flow

    The attacker does not need access to the target network. A typical flow looks like this:

    1. Choose a target service that must stay online.
    2. Probe it: which software, which version, which endpoints are expensive.
    3. Pick a vector: fill OS connection state (T1499.001), exhaust one service (T1499.002), send costly requests (T1499.003), or crash with a bug (T1499.004).
    4. Get sources: a single host, a rented botnet, or many cloud machines.
    5. Launch with a slow ramp so fixed thresholds stay quiet at first.
    6. Watch the effect, adjust the mix of vectors, repeat.
    7. Stop and disappear, or send the ransom demand.
    Danger — Lab only

    Run these commands only against your own test host in an isolated lab network. For example, use the VM (virtual machine) 10.0.0.10 (lab.local) running a test web server. Never aim them at systems you do not own — doing so is a crime in most countries. Stop immediately if any shared network element slows down. Keep the lab on a private virtual network.

    bash — lab only: attacker-side test tools
    # Lab only — target is your own VM 10.0.0.10 running a test web server

# Gentle, COUNTED SYN packets (not a flood) to test your monitoring
hping3 -c 500 -S -p 443 --syn 10.0.0.10

# Slow HTTP connection exhaustion test (Slowloris-style) against lab.local
slowhttptest -c 500 -H -i 10 -r 100 -t GET -u http://lab.local/ -p 5 -l 60

# Expensive request flood: 100 parallel heavy search queries for 30 seconds
wrk -t2 -c100 -d30s "http://10.0.0.10/search?q=generate+report"

# Simple load check with ApacheBench
ab -n 2000 -c 50 http://10.0.0.10/
    bash — lab only: watch the target while the test runs
    # Lab only — run these on the target VM (10.0.0.10) while the test runs
ss -s                # connection table summary (watch tcp counts climb)
vmstat 1             # CPU and memory pressure
sar -n TCP,ETCP 1    # TCP active opens and error counters
journalctl -k -f     # kernel messages, e.g. "possible SYN flooding"
    Good practice

    Turn every lab test into a defender exercise: run the test, then try to catch it with your own Sigma rule from section 5.5. A test you cannot detect is a test without a result.

    Common variations

    SYN and ACK floods

    Raw packets at the OS layer fill the connection table. Cross-reference T1499.001.

    Slowloris and slow read

    Open connections and send almost nothing, or read very slowly, until the web server runs out of worker slots. Cross-reference T1499.002.

    Expensive endpoint flood

    Repeat heavy URLs: big searches, exports, report generation. Each request costs the server far more than it costs the attacker. Cross-reference T1499.003.

    Crash exploits

    A crafted packet or request triggers a bug in an unpatched service and stops it. Cross-reference T1499.004.

    Multi-vector mixes

    Real campaigns combine vectors, for example SYN flood plus heavy requests, so that blocking one does not stop the attack.

    Common attacker mistakes

    • Single source: one attacking IP is trivial to block. Botnets exist to avoid this.
    • Fixed timing: packets at exact intervals stand out from human traffic patterns.
    • No baseline check: without measuring first, the attacker cannot tell whether the flood worked.
    • Loud reconnaissance: a noisy scan right before the flood gives defenders a warning and a head start.
    • Ignoring their own footprint: rented infrastructure leaves billing and network records that investigators can follow.

    4. Blue team perspective: how defenders see it

    Here is how defenders notice endpoint DoS: which signals exist, which logs carry them, and how to triage an event.

    Network view

    Firewall rate-drop messages, IDS alerts (an IDS is an intrusion detection system), and flow records (per-connection summaries) show packet storms, per-source rates, and half-open connection counts. They often fire before the host itself reports a problem.

    Host view

    CPU, memory, and connection-table metrics, plus kernel messages such as the Linux SYN-flooding warning, show the endpoint running out of room.

    Service view

    Web server error logs, 5xx waves, worker exhaustion messages, and restart events show the service failing under load or crashing.

    Human view

    Support tickets and external uptime monitors tell you what real users feel. If users fail while internal dashboards look calm, your monitoring has a blind spot.

    Artifacts this technique leaves

    • Linux kernel message: Possible SYN flooding on port 443. Sending cookies.
    • A sharp rise in half-open TCP connections and SYN cookies sent per second.
    • Firewall threat-detection messages, for example Cisco ASA 733100 with a SYN-flood drop reason.
    • Web server errors: worker_connections are not enough, upstream timeouts, 502/503 waves.
    • Repeated service crash events, for example Windows Event IDs 7031 and 7034.
    • Local disks filling with access logs during the flood.

    Where to look

    SignalSourceWhat it tells you
    Rate-drop messagesFirewall (Cisco ASA 733100, similar)Packets to one host exceeded a configured rate threshold.
    SYN backlog warningsLinux kernel syslogThe OS connection state is under pressure; SYN cookies (a defense that answers handshakes without storing state) activated.
    Per-source request ratesnginx access logs, CDN or WAF logsApplication-level flood sources and the URLs they abuse.
    5xx wavesWeb access logs, APM tools (APM — application performance monitoring)The service is failing under load, per source and per URL.
    Service crash eventsWindows System log (7031/7034)Possible crash exploitation (T1499.004) or a failing service.
    Uptime monitor errorsExternal synthetic checksReal user impact, measured from outside your network.
    Official ATT&CK detection strategy

    ATT&CK maps this technique to detection strategy DET0208, "Endpoint Resource Saturation and Crash Pattern Detection Across Platforms". Its analytics match the signals above. AN0584: processes or scripts launched by users that rapidly consume CPU and memory, or attempt malformed service interactions. AN0585: scripts or binaries that cause repeated kernel panics, OOM kills (the kernel terminating processes when memory runs out), or systemd restarts of services like nginx, httpd, and sshd. AN0586: malformed processes or app bundles that cause repeated application crashes and system slowdowns. AN0587 covers instances that turn degraded or unhealthy from abnormal process load. AN0588 covers container orchestrator logs that show crash-looping pods and exhausted cgroup limits (cgroups are the Linux mechanism that caps a container's resources). Quote these IDs when you write detections, so your rules map to the official objects.

    Warning

    Denial of service sits at the Impact stage, but it can also be a distraction. While the flood absorbs attention, the attacker may try to break in elsewhere. During and after every DoS event, check authentication logs, endpoint alerts, and IDS events (an IDS is an intrusion detection system) in the same time window. Treat the DoS as one signal, not the whole story.

    Triage flow

    1. Triage step 1Confirm it is real: compare traffic with the baseline and check external uptime monitors before declaring an incident.
    2. Triage step 2Classify the vector: volumetric flood (pure traffic volume), connection or service exhaustion, expensive requests, or crash exploitation. The class decides the control you need.
    3. Triage step 3Scope: list top talkers (the sources sending the most traffic) from flow records, affected services, and whether other hosts are hit too.
    4. Triage step 4Mitigate at the edge: enable rate limits and block the worst ranges. If the load stays high, engage your CDN (content delivery network) or provider scrubbing — the provider filters attack traffic upstream.
    5. Triage step 5Check host health: CPU, memory, connection table, and disk. Confirm services recovered after the pressure drops.
    6. Triage step 6Escalate when needed: your ISP (internet service provider), your hosting or CDN provider, and law enforcement if extortion is involved (for example the FBI's IC3 in the US).
    7. Triage step 7Document and review: write the timeline, preserve evidence, and turn every gap you hit into a runbook update.

    5.2 Threat intelligence

    Threat intelligence turns isolated alerts into context: who attacks services like yours, with which vectors, and what is normal for them. Use it to tune the rules in section 5.5 before an attack, not during one.

    Where to collect

    • MITRE ATT&CK groups and software pages for documented DoS actors.
    • CISA (the US Cybersecurity and Infrastructure Security Agency) and FBI alerts (for example the 2020 healthcare DDoS extortion warnings).
    • Vendor reports from network and cloud security companies.
    • OSINT (open-source intelligence, meaning public sources): news, researcher blogs, public blocklists.
    • Commercial feeds, if you subscribe.
    • ISACs (information sharing and analysis centers) for your sector: MS-ISAC (government), FS-ISAC (finance), H-ISAC (health).
    • Your own telemetry: top talkers, blocked ranges, repeated sources.

    How to apply it

    1. Collect: pull relevant reports weekly.
    2. Analyze: map each claim to your exposure — do you run the targeted stack?
    3. Apply: feed ranges and indicators into rate limits, blocklists, and rule tuning.
    4. Review: drop stale indicators, measure which ones ever fired, and re-check quarterly.

    Keep claims defensible

    Write down where every claim came from and how confident you are. Attribution is hard; say "reported by X" instead of "actor Y did it". Confidence ratings below follow that rule.

    5.3 Threats: ranking and categorization

    Seven realistic threats cover this technique across all major vectors. Each one gets a severity and a threat scope (the systems where it applies — broader than the official ATT&CK platform list above). The same seven threats drive the log examples in 5.4 and the rules in 5.5.

    Threat 1: Multi-vector botnet flood Critical NetworkEndpoint

    Description: a botnet sends SYN packets, incomplete HTTP requests, and heavy URLs at the same exposed service. Stopping one vector leaves the others running.

    Preconditions: a public service and a rented or owned botnet. No access to the target is needed.

    Impact: full service outage for real users; saturation of firewalls and upstream links.

    Why this rating: multi-vector floods defeat single-layer defenses and historically cause the longest outages, including extortion campaigns.

    Threat 2: TCP SYN flood High NetworkLinuxWindows

    Description: the attacker sends SYN packets — the first step of opening a TCP connection — but never finishes the handshake. Half-open connections fill the OS connection table.

    Preconditions: a reachable TCP service; spoofed or rotating source addresses help the attacker.

    Impact: new connections time out for everyone; established sessions may survive briefly.

    Why this rating: very common, easy to launch, but SYN cookies and edge rate limits reduce its power on tuned hosts.

    Threat 3: ACK flood and state-table pressure High NetworkLinux

    Description: the attacker sends TCP ACK packets (ACK is the packet that confirms receipt in a TCP conversation), or traffic that changes fast. Stateful devices and the OS then fill their connection-tracking tables with junk entries.

    Preconditions: a stateful firewall or a Linux host using connection tracking (conntrack) in the attack path; a reachable TCP service.

    Impact: the state table fills and new legitimate flows get dropped; the firewall or host drops packets for everyone, not only for the attacker.

    Why this rating: common in botnet toolkits and effective against every stateful middlebox, but well understood and measurable with conntrack and firewall counters.

    Threat 4: Slow HTTP exhaustion High Network

    Description: the attacker opens many connections and sends bytes extremely slowly (Slowloris-style), keeping worker slots busy with almost no bandwidth.

    Preconditions: a web server with per-connection worker limits and long timeouts.

    Impact: the server accepts no new users while looking "quiet" on bandwidth charts.

    Why this rating: cheap, hard to see on volume graphs, but easy to defeat with timeouts and connection caps per source.

    Threat 5: Expensive request flood High NetworkCloud

    Description: repeated requests to costly endpoints: big searches, exports, report generation. Each request burns far more server work than the attacker spends.

    Preconditions: exposed application endpoints without per-client rate limits or caching.

    Impact: database and CPU exhaustion, 5xx waves, slow pages for everyone, high cloud bills.

    Why this rating: common and costly, but WAF rate rules and caching contain it well once identified.

    Threat 6: Crash exploit Critical LinuxWindows

    Description: a crafted request triggers a bug in an unpatched service and stops it, or restarts it in a loop. One machine can do it; no flood needed.

    Preconditions: a vulnerable, unpatched service exposed to the network.

    Impact: persistent outage of the service until patched; repeated crash-restart cycles stress the host.

    Why this rating: a single actor can take down a critical service, and exploitation may also open the door to worse attacks.

    Threat 7: Local resource exhaustion Medium LinuxWindows

    Description: malware on the host itself exhausts resources. One example is a fork bomb: a small script that keeps starting copies of itself until the process table is full.

    Preconditions: attacker code already running on the endpoint (after phishing, a compromised account, or a supply chain problem).

    Impact: the machine freezes; local services fail; other tenants may suffer on shared hosts.

    Why this rating: needs prior access, so it is less likely than remote floods, but it can hit one critical host hard.

    5.4 Logs and patterns

    Each threat below lists the log sources, the fields that matter, what normal looks like, what suspicious looks like, the detection logic, and one realistic example log line. Field meanings follow each code block. These patterns are the page-level version of the official analytics in detection strategy DET0208, which section 4 quotes in full.

    Threat 1 — Multi-vector botnet flood

    Pattern

    • Sources: firewall logs (Cisco ASA threat detection), IDS (Suricata, with its EVE JSON event log — JSON is a structured text format), flow records (Zeek conn.log).
    • Key fields: source and destination IP and port, packets per second, TCP flags, alert signature, drop reason.
    • Normal: mixed sources, rates below thresholds, mostly completed handshakes and established flows.
    • Suspicious: dozens of new half-open flows per second toward one host; SYN without ACK; several flood signatures in the same minute.

    Detection logic

    • Alert on any firewall threat-detection drop message for SYN floods.
    • Flag sources with more than 50 new half-open flows in 10 seconds toward one host.
    • Correlate two or more signature families (SYN, HTTP, UDP) within one minute as a multi-vector indicator.
    log — Cisco ASA threat detection (733100)
    %ASA-4-733100: [0x8ed66b61, 0x0] drop Rate-1 (drop-exceed-rate) - TCP SYN-flood, 320 packets from outside:203.0.113.50/52113 to inside:10.0.0.10/443, current burst rate is 512 per second, max configured rate is 200

    Field notes: %ASA-4 is severity 4 (warning). 733100 is the threat-detection message ID. The drop reason says the configured rate was exceeded. The burst rate (512/s) versus the configured maximum (200/s) shows how far the traffic went over the line. Source 203.0.113.50 hit the inside host 10.0.0.10 on TCP/443.

    log — Zeek conn.log (flow record)
    #fields  ts  uid  id.orig_h  id.orig_p  id.resp_h  id.resp_p  proto  conn_state  orig_pkts  resp_pkts
1728705122.441123  CmZLkA2XV1pQ3rT8d  203.0.113.50  52113  10.0.0.10  443  tcp  SR  1  0

    Field notes: ts is the Unix timestamp. uid is a unique flow ID. id.orig_h is the source. conn_state SR means the originator sent SYN packets but the responder never replied — the classic half-open shape of a SYN flood.

    Threat 2 — TCP SYN flood (host view)

    Pattern

    • Sources: Linux kernel syslog; TCP counters from /proc or SNMP (a standard device-metrics protocol); connection-table monitors.
    • Key fields: host, port, SYN cookies sent, SYN-RCVD count, backlog size.
    • Normal: the kernel warning is absent; half-open counts stay low and steady.
    • Suspicious: the SYN-flooding warning appears; SYN cookies sent per second spike; SYN-RCVD connections pile up.

    Detection logic

    • Alert immediately on the kernel message below — it means the SYN backlog (the kernel's waiting queue for half-open connections) already overflowed.
    • Alert when the SYN-cookies-sent counter exceeds 100 per second for 60 seconds.
    • Pair with firewall data to name the sources pushing the backlog.
    log — Linux kernel (syslog)
    Oct 12 04:31:22 web01 kernel: [870221.441123] TCP: request_sock_TCP: Possible SYN flooding on port 443. Sending cookies.  Check SNMP counters.

    Field notes: web01 is the host. The bracketed number is kernel uptime in seconds. The message names the affected port (443) and says the kernel switched on SYN cookies, a defense that answers handshakes without storing state. Seeing this line means the OS was already under connection pressure.

    Threat 3 — ACK flood and connection-state table pressure

    Pattern

    • Sources: Linux kernel syslog (conntrack), firewall threat-detection logs, Zeek conn.log.
    • Key fields: host, conntrack table usage, drop counts, conn_state, packets per flow.
    • Normal: conntrack usage tracks active sessions and falls back after they close; Zeek sees a completed handshake on almost every flow.
    • Suspicious: "table full, dropping packet" kernel messages; many short flows with no handshake seen (conn_state OTH); per-source ACK counts far above the baseline.

    Detection logic

    • Alert at once on the kernel conntrack "table full" message — the state table is already exhausted.
    • Alert when conntrack usage stays above 80 percent of its maximum for 60 seconds.
    • Flag sources with many flows where no handshake was ever seen; Zeek marks those flows conn_state OTH.
    log — Linux kernel (conntrack table full)
    Oct 12 04:31:22 edge01 kernel: [771233.220418] nf_conntrack: nf_conntrack: table full, dropping packet

    Field notes: edge01 is the affected host. nf_conntrack is the Linux connection-tracking module; it records every flow that passes through the machine. This message means its table had no free entry, so the kernel dropped new packets. An ACK flood forces this by pushing thousands of junk flows into the table.

    log — Zeek conn.log (no-handshake flow)
    #fields  ts  uid  id.orig_h  id.orig_p  id.resp_h  id.resp_p  proto  conn_state  orig_pkts  resp_pkts
1728705123.990211  CJkTbM4Wq8vLnR2e1f  198.51.100.87  44902  10.0.0.10  443  tcp  OTH  184  0

    Field notes: conn_state OTH means Zeek recorded the flow without ever seeing a SYN, so no handshake happened. A burst of these flows from one source, with many originator packets and no reply, is the ACK-flood shape. Normal traffic almost never looks like this.

    Threat 4 — Slow HTTP connection exhaustion

    Pattern

    • Sources: web server error logs, WAF logs, server-status pages.
    • Key fields: active connections per client IP, connection age, bytes read per connection, worker usage.
    • Normal: requests finish in under a second; few concurrent connections per source.
    • Suspicious: many connections open longer than 30 seconds with tiny byte counts; worker exhaustion errors appear.

    Detection logic

    • Alert on the worker_connections are not enough error.
    • Count connections per client IP open longer than 30 seconds; alert at 30 or more.
    • Track average bytes read per active connection; a floor of near-zero readers is the slow-read signature.
    log — nginx error log
    2025/10/12 04:31:22 [alert] 8119#8119: *91234 worker_connections are not enough
2025/10/12 04:31:24 [error] 8119#8119: *91310 upstream timed out (110: Connection timed out) while reading response header from upstream, client: 203.0.113.77, server: lab.local, request: "GET /search?q=report HTTP/1.1", upstream: "http://127.0.0.1:8080/search?q=report"

    Field notes: the first line means every worker slot is taken — the direct sign of connection exhaustion. The second line shows the result: the backend (upstream) could not answer in time. client is the connecting IP, and the request line shows what was asked. Repeated pairs of these two lines during a quiet bandwidth period point to a slow-style flood.

    Threat 5 — Expensive application request flood

    Pattern

    • Sources: web access logs, WAF logs, application performance monitoring traces.
    • Key fields: client IP, URL, status code, request time, user agent, bytes.
    • Normal: heavy URLs are rare, return 200, and finish in bounded time.
    • Suspicious: the same expensive URL repeated per source; a wave of 5xx; bot-like user agents at high rates.

    Detection logic

    • Count 5xx responses per source per 5 minutes; alert above your tuned threshold.
    • Count requests to a known-expensive URL per source; alert on repeat bursts.
    • Watch average request time per URL; a jump combined with one client IP is the strongest pair.
    log — nginx access log
    203.0.113.77 - - [12/Oct/2025:04:31:22 +0000] "GET /search?q=annual+report HTTP/1.1" 502 559 "-" "python-requests/2.31.0" 29.998
203.0.113.77 - - [12/Oct/2025:04:31:22 +0000] "GET /export?format=csv HTTP/1.1" 503 0 "-" "python-requests/2.31.0" 29.999

    Field notes: read each line left to right: client IP, timestamp, request line, status (502, 503), response bytes, referrer (empty), user agent, and request time in seconds. The user agent is python-requests, a scripted client. Request times sit at about 30 seconds — the timeout ceiling. The same IP, scripted agent, heavy URLs, error statuses, and maxed-out request times together form the flood signature.

    Threat 6 — Crash exploit against an unpatched service

    Pattern

    • Sources: Windows System log (Service Control Manager), Linux journals and core dumps, restart monitors.
    • Key fields: service name, crash count, event ID, time between crashes.
    • Normal: rare single crashes after patching or config changes.
    • Suspicious: the same service crashing every few seconds; crash bursts right after a traffic burst from one source.

    Detection logic

    • Alert when one service logs more than 5 crash events in 5 minutes.
    • Correlate the crash window with per-source request spikes in the web or firewall logs.
    • Keep a list of patch levels; a crash on a known-vulnerable version is high confidence.
    log — Windows System event (Service Control Manager)
    Log Name:      System
Source:        Service Control Manager
Event ID:      7034
Level:         Error
Computer:      APP01.corp.example
Message:       The World Wide Web Publishing Service service terminated unexpectedly.
               It has done this 14 time(s). The following corrective action will be
               taken in 30000 milliseconds: Restart the service.

    Field notes: Event ID 7034 means a service exited without warning; 7031 is similar but names a crash loop with the restart action. The counter "14 time(s)" shows repetition — a handful of these in minutes is a crash storm, the host-side footprint of T1499.004 (or a genuinely broken update).

    Threat 7 — Local resource-exhaustion malware (fork bomb pattern)

    Pattern

    • Sources: process creation telemetry (Sysmon, including Sysmon for Linux, or auditd — the Linux audit daemon — with its execve process-start events) and EDR — endpoint detection and response software.
    • Key fields: parent image, child image, command line, user, host, creation rate.
    • Normal: compilers and build jobs spawn many children, but in bursts tied to release windows.
    • Suspicious: one shell spawning hundreds of identical children per minute, often looping on itself.

    Detection logic

    • Alert when one parent image creates more than 120 child processes in one minute on one host.
    • Add a child-image match (for example the same interpreter looping) to cut false positives.
    • Whitelist known build agents by host and account, and alert harder elsewhere.
    log — Sysmon process creation (EID 1 — event ID 1, Sysmon for Linux shape)
    {"EventTime":"2025-10-12T04:31:22.441Z","Computer":"web01","EventID":1,"Channel":"Linux-Sysmon/Operational","Image":"/bin/bash","ParentImage":"/bin/bash","CommandLine":"bash -c job_loop","User":"svc_web"}

    Field notes: Image is the new process, ParentImage its parent. Here bash keeps spawning bash — the self-replicating shape of a fork bomb. Hundreds of these records per minute, all with the same pair, fill the process table and freeze the host. The exact payload does not matter for detection: the rate and the shape do.

    5.5 Sigma rules and Splunk SPL

    Each threat below gets one Sigma rule and one matching Splunk SPL query. Sigma is an open YAML format (a human-readable configuration format) for detection rules that many SIEM tools — central log-search platforms — can translate. SPL is the Splunk search language. Both were written for the log shapes in 5.4. Every SPL query states its assumed index and sourcetype — rename those for your environment before use.

    Pair 1 — Firewall volumetric flood (Cisco ASA 733100)

    sigma — pair 1
    title: Cisco ASA Threat Detection Drop for TCP SYN Flood
id: 676f21cb-780a-472a-998e-3328c5d6a96f
status: stable
description: "Detects Cisco ASA threat-detection messages (733100) that report dropped
  packets because a rate threshold was exceeded, commonly a TCP SYN flood against one
  exposed host. Matches endpoint resource exhaustion floods."
references:
  - https://attack.mitre.org/techniques/T1499/
  - https://attack.mitre.org/techniques/T1499/001/
author: SOC Detection Engineering
date: 2025-09-12
logsource:
  product: cisco
  service: asa
detection:
  sel_asa:
    - '%ASA-4-733100'
  sel_syn:
    - 'SYN-flood'
  condition: sel_asa and sel_syn
fields:
  - src_ip
  - dst_ip
  - dst_port
  - action
falsepositives:
  - "Legitimate traffic bursts, such as a marketing event or a large download, that exceed the configured threat-detection rate."
  - "Internal load tests that traverse the firewall."
level: high
tags:
  - attack.impact
  - attack.t1499
    spl — pair 1 (assumes index=netfw, sourcetype=cisco:asa — rename for your environment)
    index=netfw sourcetype=cisco:asa "%ASA-4-733100" "SYN-flood"
| rex field=_raw "from (?\S+):(?\d{1,3}(?:\.\d{1,3}){3})/(?\d+) to (?\S+):(?\d{1,3}(?:\.\d{1,3}){3})/(?\d+)"
| stats count AS flood_drops, values(dst_ip) AS target_hosts by src_ip, dst_port
| where flood_drops > 5
| sort -flood_drops

    Mapping note: Sigma keyword matches (sel_asa, sel_syn) become the quoted search terms before the first pipe. The fields src_ip and dst_ip are produced by the rex command, which pulls them out of the ASA message text. Tuning: raise flood_drops if your firewall splits one attack across many messages; suppress during planned load tests.

    6. Real-world case study: healthcare DDoS extortion (2020)

    A documented campaign backdrop plus a representative timeline that shows how one attack unfolded hour by hour and what responders did.

    Documented backdrop

    In August 2020, CISA (the US Cybersecurity and Infrastructure Security Agency), the FBI, and the US Department of Health and Human Services issued a joint statement. It warned of an increased and imminent cybercrime threat to US hospitals and healthcare providers. During the same period, agencies and ISACs reported DDoS extortion campaigns against the health sector, with attackers demanding payment to stop attacks. The statement and the sector warnings are documented; this guide uses them as the backdrop.

    Scope note

    The timeline below is a representative scenario based on public incident reports, including the 2020 healthcare extortion warnings. The organization, dates, clock times, and numbers are illustrative composites, not a specific named victim.

    Representative timeline

    • Day 1 — Tue 11 Aug 2020, 03:40Recon: light probes hit the patient portal (an EHR — electronic health record — front end). Requests look normal; the SOC sees nothing unusual. The attacker is measuring timeouts and stack versions.
    • Day 1, 04:10Flood starts: hundreds of sources send SYN packets plus repeated heavy search requests — a multi-vector mix of T1499.001 and T1499.003.
    • Day 1, 04:25Impact: the portal returns 503 errors. The external uptime monitor pages the on-call engineer.
    • Day 1, 04:40Detection confirmed: the firewall logs 733100 SYN-flood drops, the portal host logs the kernel SYN-flooding warning, and a ransom email arrives demanding payment within 24 hours.
    • Day 1, 05:00Containment: the runbook activates. Provider scrubbing is enabled, WAF rate limits go on the heavy URLs, and the worst source ranges are blocked at the edge.
    • Day 1, 06:30Traffic drops by about 90 percent from the peak. The portal serves some users again; gauges fall from red to amber.
    • Day 1, 08:30Recovery: full service with the new rules in place. Evidence is preserved; the FBI's IC3 (Internet Crime Complaint Center) is notified because extortion is involved.
    • Day 2–8 — Wed 12 to Tue 18 AugEradication and hardening: edge devices patched, a capacity test scheduled, the runbook rewritten with the gaps found during the night, and a quarterly drill booked.

    Attack chain and detection point

    Chain: recon, vector selection, botnet flood, extortion demand. Detection came from three independent signals that agreed: the external uptime monitor (04:25), the firewall rate drops (04:31), and the kernel warning (04:33). Any one alone could have been a false alarm; three together justified declaring an incident.

    Impact and consequences

    About four hours of degraded service and roughly two hours of full outage. No data breach was found; a follow-up review found no unauthorized access, so no breach notification was required. Appointment scheduling slowed for the morning. Costs: response hours, emergency capacity upgrades, and reputational damage managed through the status page.

    Team response and communication

    An incident commander coordinated network, server, and communications staff. Staff posted updates to the public status page every 30 minutes and told employees to use documented downtime procedures instead of improvising. Legal advised against paying; the evidence went to law enforcement.

    Who did what — and with which tools

    • Incident commander (security lead): kept the decision log and ran 30-minute check-ins.
    • SOC analyst: ran the Splunk queries from section 5.5 (pairs 1 and 2) to confirm ASA 733100 drops and the kernel warning.
    • Network engineer: enabled provider scrubbing in the provider console and set edge rate limits on the firewall.
    • System administrator: watched host gauges with sar and vmstat, confirmed service recovery, and patched edge devices.
    • Communications lead: status page updates and the staff notice.
    • Legal and compliance: extortion decision, breach assessment, and the IC3 report.

    Lessons learned

    • Provider DDoS protection existed but was switched off — enable it before you need it.
    • The runbook had no phone contact for ISP escalation; that gap cost 20 minutes.
    • Local log disks nearly filled during the flood; remote log shipping was added.
    • No external baseline existed, so "how abnormal is this?" was a guess for the first hour.

    Controls that worked

    Three controls carried the response. The external uptime monitor caught the impact. The Sigma rules from section 5.5 fired on firewall and kernel logs. The pre-agreed runbook gave every role a step.

    Each control existed before the attack — that is the lesson to copy.

    7

    7. Mitigation and defense

    Concrete, verifiable controls across the whole stack. ATT&CK's own mitigation entry (M1037, Filter Network Traffic) points at CDN and DoS-mitigation providers and SYN cookies — both appear below.

    Policy

    • Write a DDoS runbook with named owners and steps.
    • Test it quarterly (tabletop plus live drill) and keep the records for audits.
    • Keep incident contacts for your ISP, provider, and law enforcement in one place.
    • Define the extortion decision path with legal before an attack happens.

    Network edge

    • Put public services behind a CDN or DDoS protection service.
    • Enable provider scrubbing now, so activation is one click later.
    • Rate-limit new connections and per-source flows at the edge firewall.
    • Know how to apply blackhole routing (dropping all traffic to one target so the rest of the network survives) as a last resort for the worst targets.

    Endpoint (Linux)

    • Enable SYN cookies: net.ipv4.tcp_syncookies=1.
    • Raise the SYN backlog: net.ipv4.tcp_max_syn_backlog=4096.
    • Trim connection-tracking limits so one host cannot exhaust shared state.
    • Cap service memory with systemd resource limits.

    Endpoint (services)

    • Keep web, DNS, and VPN software patched — this is the T1499.004 defense.
    • Set request and connection timeouts low; long timeouts feed slow floods.
    • Limit request body sizes and disable unused endpoints.
    • Restart crashed services with backoff, and alert on the restart storm.

    Cloud and application

    • Configure WAF rate rules per URL and per client.
    • Use autoscaling with a cost cap, and cache expensive responses.
    • Set load balancer idle timeouts to cut slow connections automatically.
    • Apply rate limits per API key (an API is the programmatic interface of a service), not only per IP.

    Identity

    • Rate-limit login and token endpoints; they are favorite flood targets.
    • Tune lockout thresholds so floods cannot lock out real users.
    • Add step-up checks (for example a challenge) when request rates look scripted.

    Logging

    • Ship security logs off-host in near real time — a flooded host cannot keep its own evidence.
    • Rotate and cap local log size so a flood cannot fill the disk.
    • Sync clocks with NTP (network time protocol) so evidence lines up across systems.

    Monitoring

    • Keep a traffic baseline per service and per hour of day.
    • Run external uptime checks; they catch what internal dashboards miss.
    • Alert on deviation from baseline, not only fixed thresholds.
    • Watch connection tables and kernel messages on every public host.

    Backup and response

    • Backups do not stop floods, but verified restore paths keep calm during chaos.
    • Define who talks to whom: status page, staff, customers, provider, police.
    • After every incident, convert each gap into a runbook line.

    Home and small-office advice

    • Update your router firmware regularly; many botnet nodes are old home routers.
    • Turn off remote administration from the internet.
    • Avoid hosting public services from home; use a provider with protection.
    • Ask your internet provider for their abuse contact and any protection they offer.
    • If a service you use is under attack, report it to the operator. Never "hit back" — counterattacks are illegal and usually hit innocent addresses.

    8. Common mistakes and best practices

    Twelve mistakes blue teams make around DoS detection, each with symptom, root cause, fix, and prevention. Then the daily, weekly, and monthly habits that keep them fixed.

    1. Treating every spike as an attack

    Symptom: every dashboard jump becomes an incident call.

    Root cause: no measured baseline to compare against.

    Fix: measure normal traffic per service and compare before escalating.

    Prevention: monthly baseline reviews, per service and per hour of day.

    2. Alert fatigue

    Symptom: the same flood alert fires hundreds of times; staff start muting it.

    Root cause: per-event alerts with no aggregation or dedupe.

    Fix: alert on aggregated counts in a time window, one alert per condition.

    Prevention: alert review each week; every alert must need a human decision.

    3. Missing host logs

    Symptom: kernel warnings exist on the server but never reach the SIEM.

    Root cause: only web logs were onboarded for shipping.

    Fix: ship syslog and kernel messages for every public host.

    Prevention: keep a log-source inventory with named owners per source.

    4. Log disk fills during the attack

    Symptom: logging stops at the worst possible moment.

    Root cause: local rotation caps plus a burst of access logs.

    Fix: ship remotely, raise rotation limits, sample very noisy sources.

    Prevention: disk usage alert at 70 percent on every log-producing host.

    5. No baseline

    Symptom: analysts argue whether traffic is abnormal instead of acting.

    Root cause: nobody records what normal looks like.

    Fix: keep a rolling four-week baseline per service.

    Prevention: baselines reviewed and re-published as part of change management.

    6. Ownership gap

    Symptom: during an attack, nobody knows who calls the ISP.

    Root cause: the runbook lists steps but not names and phone numbers.

    Fix: on-call contacts with a clear escalation order.

    Prevention: call the contacts during the quarterly drill, not during the outage.

    7. Threshold-only tuning

    Symptom: rules are either noisy or silent, nothing in between.

    Root cause: static thresholds ignore service context and time of day.

    Fix: per-service thresholds plus baseline-deviation alerts.

    Prevention: tune one rule after every incident and record what changed.

    8. Untested runbook

    Symptom: the first real test of the plan is a real attack.

    Root cause: the plan exists on paper only.

    Fix: quarterly tabletop plus one live drill against your own lab.

    Prevention: auditors and team leads ask for test evidence, not intentions.

    9. Blocking single IPs in a botnet flood

    Symptom: the blocklist grows all night and the outage continues.

    Root cause: wrong mental model — botnets rotate thousands of sources.

    Fix: mitigate upstream with the provider or CDN; rate-limit instead of enumerating.

    Prevention: classify the vector first, then choose the control that matches it.

    10. Host-side blindness

    Symptom: network charts look clean while the server burns CPU.

    Root cause: only network tooling was deployed.

    Fix: host metrics and kernel logs on every public host.

    Prevention: a golden monitoring profile applied to every new host at build time.

    11. Confusing T1498 with T1499

    Symptom: mitigation applied at the wrong layer; the ISP scrubs traffic while the host itself is exhausted.

    Root cause: the two techniques look identical from the outside.

    Fix: classify volumetric (T1498) versus endpoint exhaustion (T1499) in triage.

    Prevention: train the runbook on both classes with different playbooks.

    12. Missing the second intrusion

    Symptom: the outage is resolved, then an intrusion is found two days later.

    Root cause: the DoS was treated as a pure availability event.

    Fix: run intrusion checks (auth logs, EDR, IDS) during and after every DoS.

    Prevention: correlation step built into the runbook as a mandatory phase.

    Daily habits

    • Check external uptime and the top-talker dashboard.
    • Skim overnight alerts for repeat sources.
    • Confirm log shipping is green on all public hosts.

    Weekly habits

    • Review new kernel and service error trends.
    • Tune one noisy rule; delete one useless rule.
    • Read one current threat report and note exposures.

    Monthly habits

    • Run a DDoS tabletop or lab drill.
    • Test the log-disk alert and rotation caps.
    • Refresh baselines and review the intel list for stale entries.

    Response checklist

    • Confirm the outage against the baseline and external uptime monitors.
    • Classify the vector: volumetric, connection or service exhaustion, expensive requests, or crash exploit.
    • Identify top talkers from flow records and firewall drops.
    • Apply edge mitigations: rate limits, blocklists, provider scrubbing.
    • Verify host health: CPU, memory, connection table, disk, service state.
    • Check for a distraction: review auth logs, EDR (endpoint detection and response software), and IDS for the same window.
    • Escalate to ISP, provider, or law enforcement as the runbook requires.
    • Document the timeline and update the runbook with every gap you found.
