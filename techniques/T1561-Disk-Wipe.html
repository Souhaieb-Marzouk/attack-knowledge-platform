MITRE ATT&CK · TACTIC: IMPACT

T1561 Disk Wipe

Disk Wipe is a destructive technique: an attacker erases or corrupts the data stored on disks to destroy information and to make machines unusable. This page explains both wiping variants, walks through an animated attack story, and gives detection engineers the logs, Sigma rules, and Splunk queries they need.

Version: v2.0 Tactic: Impact Platforms: Linux, Windows, macOS Sub-techniques: T1561.001 · T1561.002 Typical privileges: Administrator / root

ATT&CK ID

T1561 · Impact

Added in ATT&CK v8 (Oct 2020), alongside its two sub-techniques.

Two variants

Content vs structure wipe

T1561.001 overwrites file content. T1561.002 corrupts disk structure such as the MBR.

Goal

Destroy data and availability

Remove evidence and block recovery. There is no ransom promise and no decryption key.

Main data sources

Process creation, file modification, raw disk access, and command execution telemetry.

Overview

What Disk Wipe is, how the two sub-techniques differ, and where it sits in an intrusion.

Disk Wipe (T1561) is a destructive technique in the Impact tactic. The attacker erases or damages the data on disk drives so that files, applications, or whole operating systems stop working. Unlike ransomware, a wiper usually offers nothing back: there is no ransom note and no way to buy the data back. The attacker wants the data gone, the machines down, or both.

ATT&CK splits the technique into two sub-techniques:

  • T1561.001 - Disk Content Wipe. The attacker overwrites the content of files, folders, or whole volumes. The file system structure stays mostly intact, but the data inside is replaced with zeros, random bytes, or repeating patterns. Files keep their names, but opening them shows empty or broken content.
  • T1561.002 - Disk Structure Wipe. The attacker corrupts the structure of the disk instead of (or in addition to) the files. This includes the MBR (Master Boot Record, the small boot program at the start of a disk), the GPT (GUID Partition Table, the modern list of where partitions live), and file system metadata such as the MFT (Master File Table, the index that tells Windows where every file is stored). When the structure is gone, the computer cannot boot or cannot even find its files.

Some wiping tools do both: they overwrite files and then destroy the boot records. The parent technique covers both behaviors at this overview level; the sub-technique pages go deeper into each variant.

Content wipe vs structure wipe

The two sub-techniques differ in what they destroy and what defenders see. Keep the two columns apart when you build detections.

Platform note (checked against the current MITRE page)

The current MITRE page for T1561 lists four platforms: Linux, Windows, macOS, and Network Devices. On routers and switches, wiping can mean erased configuration files through device CLI commands such as erase. Most enterprise telemetry for this page still comes from servers and workstations, so the detections below focus there.

Why attackers wipe disks

Public incident reports give four common motives:

  • Sabotage. Disrupt a company, a government, or a critical service such as power or transport.
  • Covering tracks. Wipe logs, tools, and staging areas after stealing data, so investigators find little. This overlaps with T1070 (Indicator Removal).
  • Extortion without decryption. Threaten destruction instead of promising restoration, sometimes mixed with data theft first.
  • Destroying recovery options. Wipe backups and shadow copies so the victim cannot simply restore. This is usually paired with T1490 (Inhibit System Recovery). Note that T1490 is a separate, related technique — not a sub-technique of T1561 — but the two appear together so often that defenders treat recovery deletion as the earliest disk-wipe warning.
Note

This is the parent technique page. It explains both wiping variants at a high level. For command details and per-platform detection logic, read the sibling guides: T1561.001 Disk Content Wipe (v2.0) and T1561.002 Disk Structure Wipe (v2.0).

Warning

Destructive events are rare, but they are not random. Wiping is usually the last step of a long intrusion. If you see it, the attacker already had privileged access for days or weeks, and your logs, backups, and recovery paths are probably targets too.

Words used on this page

  • Wiper: any program built to erase data or disk structure.
  • Shadow copies (VSS): Windows Volume Shadow Copy Service snapshots that let users and admins restore earlier versions of files.
  • Golden image: a trusted, pre-built copy of an operating system used to rebuild machines quickly.
  • Raw disk access: reading or writing the physical drive directly (for example \\.\PhysicalDrive0 on Windows), bypassing the normal file system.

Written story (text alternative)

The same eight steps in plain text, for screen readers, printing, and quick review:

  1. 1 · Phish. Attacker: sends an invoice-themed email with a malicious macro document; an employee enables macros and a small implant calls home. Defenders see: a single Office process spawning PowerShell on one workstation, often buried in normal noise.
  2. 2 · Move. Attacker: steals credentials from the workstation, then uses them with SMB and WMI-style remote administration to reach file servers and domain systems. Defenders see: remote execution events from one account touching many hosts within minutes, plus new logons at unusual hours.
  3. 3 · Stage. Attacker: copies the wiper binary to a trusted file share and pushes it out with scheduled tasks or group policy. Defenders see: a new executable appearing on a share and identical scheduled-task creations landing on dozens of hosts in a row.
  4. 4 · Prime. Attacker: attacks recovery first: deletes shadow copies, backup catalogs, and snapshots so nothing can be restored later. Defenders see: vssadmin delete shadows commands and failing backup jobs, which are strong early-warning signals.
  5. 5 · Ignite. Attacker: triggers the wiper fleet-wide; file contents are overwritten and disk areas are filled with zeros. Defenders see: a burst of mass file-modification events and raw disk writes across hundreds of hosts at the same moment.
  6. 6 · Crash. Attacker: lets machines restart into corrupted boot records; hundreds of systems cannot start. Defenders see: unexpected reboot events followed by boot failure errors and a fast-rising helpdesk queue.
  7. 7 · Alarm. Attacker: has finished; the damage is now visible everywhere. Defenders see: EDR mass-overwrite alerts, unbootable hosts reported from many sites, and the SOC declaring a major incident.
  8. 8 · Recover. Defenders: segment the network to stop any remaining spread, rebuild hosts from golden images, restore data from offline backups, and rotate every credential the attacker may have held. Lesson: offline, tested backups turn a catastrophe into a bad week.
Best practice

Notice the two minutes between step 4 (backup deletion) and step 5 (wipe). That gap is your best chance to stop a destructive attack. Alert on recovery-deletion commands with high priority.

Red Team Perspective

How operators think about disk wiping: when they would use it, what they need in place first, and where it usually goes wrong for them.

When and why an attacker wipes

From the attacker's seat, wiping is a decision about goals, not a step in a checklist. Public incidents show four situations where a destructive operator reaches for a wiper:

  • After exfiltration. The data is already copied out. Destroying the originals hides what was taken and hurts the victim at the same time.
  • Pure disruption. The objective is downtime itself, for example against a rival company or a government service.
  • Extortion without decryption. The attacker threatens deletion instead of leaking or locking data.
  • Covering tracks. Wiping logs and staging folders overlaps with T1070 (Indicator Removal). It makes forensics slow and expensive.

All four motives connect to T1485 (Data Destruction), the broader family of destructive behavior. T1561 is the disk-focused member of that family.

How a wipe is performed

A destructive operation usually follows the same shape, whatever the platform:

  1. Obtain admin or root. Raw disk writes and boot-record corruption need high privileges on every target host.
  2. Acquire or build a wiper. Operators either write custom code (like HermeticWiper, which abused legitimate driver libraries to corrupt disks) or use signed utilities such as Sysinternals sdelete or Unix shred and dd.
  3. Disable recovery first. Delete shadow copies, backup catalogs, and snapshots (T1490) so the wipe cannot be undone.
  4. Distribute. Push the payload remotely: PsExec, WMI, scheduled tasks, or group policy on Windows; SSH and automation tooling on Linux.
  5. Trigger. Fire the wipe everywhere at once, or at a chosen moment. Many real wipers activate at shutdown or reboot, so the corruption happens while operators are not watching.

Where the technique applies

  • Windows fleets. A domain admin account plus PsExec, WMI, or GPO can reach thousands of machines quickly. This is the pattern seen in Shamoon and NotPetya.
  • Linux servers. One stolen SSH key or service account is enough to run dd, shred, mkfs, or wipefs against database and file servers.
  • Cloud disks. Abusing provider APIs or consoles to detach, overwrite, or delete virtual disks and snapshots - the cloud-native version of a structure wipe.

Prerequisites

  • Administrator or root rights on the target hosts (or cloud IAM permissions that match).
  • A distribution path: network reachability, valid credentials, and a remote execution method.
  • Often a pre-staged payload sitting on a share or already dropped on hosts, waiting for a trigger time.
Danger · Lab only - never run against systems you do not own

Ethical practice of wiping in a lab means isolated throwaway systems and your own data only. Safe shapes of these exercises: run Sysinternals sdelete against a scratch folder on a disposable VM. Use Linux shred on one test file you created. Write zeros with dd to an old USB stick you own, never to /dev/sda. Documented malware behavior (Shamoon, NotPetya, HermeticWiper, CaddyWiper, WhisperGate) should be studied through vendor reports and reverse-engineering write-ups, not by executing samples.

Danger · Real-world case names (description only)

Shamoon (2012, 2016-2017) overwrote files and the MBR across thousands of corporate machines in the energy sector. NotPetya (2017) spread automatically and corrupted MBR and MFT structures worldwide. In 2022, WhisperGate, HermeticWiper, and CaddyWiper hit Ukrainian organizations with staged, multi-day destructive campaigns. These names are listed as case descriptions only.

Common attacker variations and mistakes

  • Wiping too early. If the wiper fires before lateral movement is complete, the operator destroys their own access and remaining objectives.
  • Triggering detection before maximum spread. Staging thousands of identical scheduled tasks in minutes is loud; careless operators are stopped mid-push.
  • Forgetting their own persistence. A wipe that destroys the implant, the staging share, and the logs also removes the operator's map of what happened.
  • Using noisy signed tools. Well-known utilities such as sdelete are easy to alert on, which is exactly why defenders should do so.

Blue Team Perspective

What a wipe looks like in telemetry, which artifacts survive, and how to triage a destructive event without losing the remaining evidence.

How defenders actually see a wipe

A well-run wipe is quiet until the moment it is not. Before ignition, the best signals are administrative: shadow copies deleted, backup agents stopped, catalogs removed. At ignition, the picture changes fast: file-overwrite telemetry spikes, raw disk handles open on many hosts, and within minutes helpdesk tickets arrive about machines that cannot boot. The worst clue of all is silence: when agents, log forwarders, and backup servers go dark at the same time, assume they were attacked first.

Artifacts left behind

  • Zero-filled or pattern-filled files. Sizes stay the same; content becomes zeros, random bytes, or repeating strings.
  • Corrupted MBR, GPT, or MFT. Machines stop with boot errors such as "Operating system not found".
  • Deleted shadow copies and backup catalogs. Often the earliest artifact, sometimes hours before ignition.
  • Leftover binaries and scheduled tasks. The wiper executable on a share, task XML on hosts, service creations in the System event log.
  • Destroyed local logs. Gaps in Windows event logs or /var/log, which is why centralized, off-site copies matter.

Warning

Assume the backup and recovery infrastructure is a target too. In several public destructive campaigns, backup servers were wiped before or with the fleet. Isolate and protect them first.

Why this matters

A wipe destroys two things at once: availability and evidence. The order of volatility (the principle that the most fragile evidence disappears first) forces you to make hard choices fast. Memory on surviving hosts, the network flows of the last hour, and any untouched logs are precious. Copy them before rebuilding anything, and pull a copy of the wiper binary for analysis.

Fit in the attack chain

Wiping is almost always the final Impact phase. When you confirm it, work backwards through earlier phases. How did they get in (phishing, exposed services)? Which credentials did they steal (T1003 OS Credential Dumping)? How did they move (T1021 Remote Services)? When did they attack recovery (T1490)? Answering those questions tells you whether other sites, domains, or clouds are also at risk.

5.2 Threat intelligence

Threat intelligence answers one question for this technique: who wipes disks in my sector right now, and what do their tools look like? Useful sources:

  • MITRE ATT&CK itself, via the STIX/TAXII feeds, for technique and software mappings (Shamoon S0140, NotPetya S0368, and others list T1561 usage).
  • Vendor research blogs such as ESET WeLiveSecurity, Microsoft Security, and Symantec/Broadcom threat reports, which publish the deepest destructive-malware analysis.
  • OSINT trackers and open indicator lists, useful for fast hashes and naming after a public campaign.
  • Commercial feeds, for finished reports and structured indicators tied to your sector.
  • ISACs, especially for energy and ICS: E-ISAC and SANS ICS communities share destructive-incident lessons fast.
  • Your own telemetry, the source teams forget: failed wipe attempts in your logs reveal tooling before public reporting does.

A simple intelligence workflow for destructive threats:

  1. Collect. Subscribe to the sources above and tag everything about Impact techniques (T1561, T1485, T1490, T1489).
  2. Analyze. For each report, extract: target sector, initial access, distribution method, wiper behavior (content vs structure), and recovery-attack behavior.
  3. Apply. Turn findings into detections (Section 5.5), tabletop scenarios, and backup/monitoring changes; record which intelligence triggered each change.

5.3 Threats ranking and categorization

The seven ranked threats below are the backbone of this page. Section 5.4 gives every threat its own log analysis. Section 5.5 gives one Sigma rule plus one Splunk query for each threat from TH-01 to TH-06. TH-07 is different: its main signal is deletion after exfiltration, so it is detected with the TH-04 rule plus the off-host correlation shown in 5.4.

TH-01 · Fleet-wide wiper pushed by remote execution

Critical Windows

A wiper binary is staged on a share and pushed to hundreds or thousands of Windows hosts with PsExec, WMI, GPO, or scheduled tasks, then triggered at one time. This is the Shamoon and NotPetya pattern.

Preconditions
Domain admin or equivalent privileges; network reachability to admin shares; staged payload.
Impact
Mass unbootable machines; fleet-wide data loss; days to weeks of restoration effort.
Why this rank
Documented repeatedly at scale (Shamoon, NotPetya); one action destroys a whole organization.

TH-02 · Raw disk writes corrupting boot records

Critical Windows

Code running with SYSTEM rights opens the physical drive directly and overwrites the MBR, GPT, or MFT - the structure-wipe lens of T1561.002. Hosts stop booting even though files may still exist.

Preconditions
SYSTEM-level code execution; raw disk write access; no allowlisting on the host.
Impact
Machines cannot boot; recovery requires rebuilds and, for content, specialist tools.
Why this rank
A single process can brick a machine in seconds; seen in HermeticWiper and NotPetya.

TH-03 · Wiping commands on Linux servers

High Linux

An attacker with SSH access or a stolen service account runs dd, shred, mkfs, or wipefs against data volumes on database or file servers.

Preconditions
Root or sudo on the server; a reachable SSH path; valid credentials.
Impact
Immediate destruction of databases and file stores on critical servers.
Why this rank
Less common than Windows fleets but devastating, quiet, and hard to distinguish from admin work without auditd.

TH-04 · Recovery infrastructure destroyed first

High Cloud · Windows

Before any wipe, the attacker deletes shadow copies, backup catalogs, cloud snapshots, and backup agents - the T1490 companion that turns a recoverable incident into permanent loss.

Preconditions
Admin rights on hosts or IAM rights in cloud; access to backup consoles or APIs.
Impact
Removes the safety net; even minor later damage becomes unrecoverable.
Why this rank
Standard modern destructive pattern (WhisperGate, CaddyWiper); loud if logged, catastrophic if not.

TH-05 · Rogue or compromised insider bulk-deletes with admin tooling

Medium Identity

A privileged user - malicious, compromised, or simply reckless - bulk-deletes data with legitimate administration tools instead of malware.

Preconditions
Existing privileged access; weak change control; no delete-rate monitoring.
Impact
Severe local loss, but usually scoped to the shares and systems the account controls.
Why this rank
Rarer than malware campaigns and often detectable through change-control gaps rather than endpoints.

TH-06 · Wiper disguised as ransomware

High Windows Linux

The attacker drops ransom-note files and a demand, but nothing is encrypted. Files are simply overwritten, extensions stay the same, and no decryption exists at any price. Vendor reporting has documented destructive operations that use this disguise, including the WhisperGate stage that showed a ransom demand while destroying boot records.

Preconditions
Admin rights on the host or file shares; a payload that overwrites files and writes note files.
Impact
Data is unrecoverable even if a victim pays; the disguise pushes responders toward a ransomware playbook and wastes the first hours.
Why this rank
High, not critical: the destructive footprint is often smaller than a fleet push, but the misclassification cost is real and documented (WhisperGate, NotPetya-style fake ransom screens).

TH-07 · Wipe to cover an espionage exit

Medium Windows Linux Cloud

After stealing data, some operators destroy the staging areas, jump hosts, and logs they used, then leave. The goal is not downtime; it is to remove traces of the theft and slow attribution. This pairs with T1070 (Indicator Removal), and it means the organization likely lost data weeks before the wipe.

Preconditions
Completed exfiltration; access to staging paths, jump hosts, and local log stores; often cloud or file-transfer credentials.
Impact
Less downtime than fleet wipes, but it destroys exactly the evidence responders need for scope and attribution.
Why this rank
Medium: the destructive footprint is usually narrow, so availability impact is limited; the damage concentrates on the investigation and on data already gone.

5.4 Logs and patterns

For each ranked threat, this section lists the log sources that reveal it, the fields that matter, what normal looks like, what suspicious looks like, and the detection logic behind the rules in 5.5.

TH-01 - Fleet-wide wiper pushed by remote execution

Log sources
Sysmon EID 1/3, Windows Security 4688/4698/7045, EDR process tree, file-share audit (Sysmon EID 11 on the staging share).
Key fields
Image, ParentImage, CommandLine, User, TargetFilename, ServiceName, source and destination host.
Normal
Software deployment tools push from a small set of management servers with stable names; admins use PsExec rarely and interactively.
Suspicious
One account creating the same service or task on dozens of hosts in minutes; PSEXESVC.exe appearing where no deployment tool lives; task names or binaries that differ from your software baseline.
Detection logic
Flag remote-execution parents (PsExec service, WMI process call create) or command lines referencing admin-share paths, then aggregate per user and per source host so a fleet push shows up as one high-count event instead of thousands of small ones.

TH-02 - Raw disk writes corrupting boot records

Log sources
Sysmon EID 9 (RawAccessRead), EID 1 for the writing process, EID 13 registry writes if the tool changes boot settings, EDR driver telemetry.
Key fields
EventID, Image, TargetObject (for EID 9, the device path), User, process signature status.
Normal
Backup, imaging, and defragmentation software reads raw disks; disk management tools do so briefly during maintenance windows.
Suspicious
An unsigned or unknown binary touching \\.\PhysicalDrive0; raw access combined with bcdedit or boot-related registry changes; raw access on hosts with no imaging tool installed.
Detection logic
Alert on EID 9 where TargetObject starts with \\.\PhysicalDrive and the process is not on an allowlist of known imaging tools. Treat writes (observed via EDR) as higher severity than reads.

TH-03 - Wiping commands on Linux servers

Log sources
auditd EXECVE and SYSCALL records, shell history forwarding, EDR for Linux, sudo logs (CMD records).
Key fields
a0 (program), a1/a2 (arguments), uid, exe, key (audit rule tag), tty.
Normal
Storage admins run wipefs or mkfs during planned provisioning; backup jobs may stream dd locally.
Suspicious
Any of these commands targeting /dev/sd*, /dev/nvme*, or /dev/vd* outside a change window, from an interactive SSH session, or by an account that never runs them.
Detection logic
Match EXECVE records where the program is a wipe utility and any argument names a block device; compare the account and time against change tickets; alert immediately for data-bearing devices.

TH-04 - Recovery infrastructure destroyed first

Log sources
Windows Security 4688 with command-line auditing, Sysmon EID 1, Microsoft-Windows-VSSaaS operational log, backup server application logs, cloud audit logs (snapshot and delete API calls).
Key fields
CommandLine, SubjectUserName, Computer, cloud eventName (for example DeleteSnapshot), principal, request source IP.
Normal
Backup software deletes its own oldest restore points on rotation; storage admins run cleanup scripts from management servers with tickets.
Suspicious
vssadmin delete shadows /all, wmic shadowcopy delete, wbadmin delete catalog, bcdedit /set recoveryenabled no, or mass snapshot deletions in cloud consoles - especially from hosts that are not backup servers and outside rotation windows.
Detection logic
Alert on the specific recovery-destruction command lines (near-zero false positives) and on deletion rate anomalies in cloud audit logs. Correlate with TH-01 staging signals.

TH-05 - Insider bulk-deletes with admin tooling

Log sources
Windows Security 4663 (file access with Delete), 4660 (object deleted), 4670 (permissions changed), file-server audit, cloud storage audit, Microsoft 365 / Google Workspace admin logs.
Key fields
SubjectUserName, ObjectName, AccessList, ObjectServer, cloud actor identity, item counts per window.
Normal
Users delete a handful of files per hour; retention jobs delete in bulk but from service accounts on schedule.
Suspicious
A human account deleting hundreds of documents in minutes; deletes concentrated in business shares rather than the user's own folders; deletes shortly after a permissions change (4660/4670 pairs).
Detection logic
Count 4663 Delete events per identity in a short window and compare against a baseline; require a minimum count to avoid noise from legitimate cleanup, and whitelist scheduled retention service accounts.

TH-06 - Wiper disguised as ransomware

Log sources
Sysmon EID 11 (file create) for note files, Windows Security 4663 for overwrite bursts, EDR ransomware analytics, FIM, backup job logs.
Key fields
TargetFilename (note names), Image, ProcessId, User, AccessList (WriteData), file-size deltas, extension-change counts.
Normal
Red-team drills and ransomware simulations create a handful of note files in one test share; restore tools write instruction files next to restored data.
Suspicious
One process creating note files across dozens of directories within minutes, together with 4663 WriteData bursts on the same paths, while no new file extensions appear and no known ransomware family signature fires.
Detection logic
Count note-file creations per host and process in a short window, then correlate with overwrite bursts. The "no new extensions" check is what separates a wiper from real ransomware: encryption renames files, a wipe does not.

TH-07 - Wipe to cover an espionage exit

Log sources
Centralized and off-host logs only (the endpoint copies are the target): cloud object-store audit logs, file-transfer and proxy logs, EDR, auditd, VPN logs.
Key fields
Identity, source IP, eventName (download vs delete), byte counts, object counts, staging paths, command lines such as sdelete or shred on transfer folders.
Normal
Retention jobs delete on schedule under service accounts; admins clean their own transfer folders with a change ticket.
Suspicious
A large download or archive pull followed within hours by targeted deletion of the same staging paths by the same identity; deletion of local log-forwarder configurations; selective event-log clearing limited to the hosts the actor touched.
Detection logic
Join egress volume and deletion events by identity and host, and alert when deletion follows a large transfer inside a short window. Never rely on on-host logs for this threat; the actor deletes them on the way out.

Example events (realistic shapes)

The next listings show what the important events look like in raw form. Use them to test your parsers.

  • Image - the process that opened the raw device. An unknown executable in a temp directory is the alarm, not the raw read itself.
  • TargetObject - the device path. \\.\PhysicalDrive0 is the whole first disk, which contains the boot records; shadow-copy paths suggest recovery data is being read or erased.
  • User - raw disk access usually requires SYSTEM or Administrator; combine with the process signature to decide severity.
  • UtcTime - two raw-access events from the same process within one second, sweeping devices, is typical wiper behavior.
  • a0="dd" - the executed program. Together with a1/a2 it shows input /dev/zero being written to /dev/sda, the entire first disk.
  • uid=0 / euid=0 - the command ran as root, which raw device writes require.
  • auid=10042 - the login audit ID of the human or service account behind the sudo call; this is the identity to investigate.
  • tty=pts2 - an interactive SSH session, not a scheduled job; compare with your change calendar.
  • USER_CMD - the sudo wrapper log linking the same timestamp to the sudo dd request.
  • CommandLine - vssadmin delete shadows /all /quiet removes every shadow copy silently. Outside a documented maintenance task this is a near-certain destructive signal.
  • SubjectUserName - jmalone, a regular finance user, deleting shadows should be impossible; this alone justifies a privilege investigation.
  • NewProcessName - a signed Windows binary, so reputation checks will not help; command-line auditing is what makes this visible.
  • ParentProcessName - spawned from cmd.exe; tracing the parent chain reveals how the command got there.
  • Image - PSEXESVC.exe appears on a host only when someone used PsExec against it; on servers with no deployment tooling this is already worth a look.
  • CommandLine - the payload path goes through an admin share (C$\tools$\wiper.exe), the classic distribution shape of a staged wiper.
  • SourceIp / SourceHostname - one source address driving the same pattern on many hosts is the aggregation signal the TH-01 rule counts.
  • User - a deployment service account at an unusual time, or an interactive admin account used for fleet-wide pushes, refines the severity decision.
  • TargetFilename - a ransom-note name written into a user folder. One file is noise; a storm from one process is the signal.
  • Image - the writer is an unknown binary in Temp using a fake svchost name, which no backup or restore tool should look like.
  • ProcessId - the join key for the storm count: dozens of note files sharing one ProcessId is the TH-06 rule's threshold.
  • Paired 4663 WriteData events - same-size overwrites with unchanged extensions point to a wipe, not to encryption.
  • eventName - a bulk download at 09:31 followed by a bulk delete of the same prefix at 09:47 from the same identity is the espionage-exit fingerprint.
  • sourceIPAddress - identical for both calls, so the pair correlates cleanly; compare it with known transfer-server addresses.
  • bytesTransferred / objectsDeleted - the volume fields that turn two normal-looking API calls into one high-severity incident.
  • This listing is an illustrative shape, not a real product log; map the field names to your cloud provider's audit stream.
Note

IP addresses in this page use the RFC 5737 documentation ranges (for example 192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24), and host names like WS-FIN-114 or FS-CORE-01 are fictional examples for testing detections.

5.5 Sigma rules and Splunk SPL

The six rules below cover TH-01 to TH-06: each threat gets one complete Sigma rule and one matching Splunk SPL query. TH-07 needs no new rule: its main signal is deletion after exfiltration, caught by the TH-04 rule plus the off-host correlation shown in 5.4. The Sigma rules follow the standard specification: valid YAML, spaces for indentation, one unique UUID per rule, and a detection block with selections and a condition. Adapt field names to your pipeline before deploying.

TH-01 · Fleet-wide wiper pushed by remote execution

  • Sigma to SPL mapping: Sigma's Image|endswith becomes process_path="*\\...", and the aggregation condition is expressed with stats plus where, which SPL needs for cross-host counting.
  • False positives: software deployment and IT administration from known management servers. Baseline them and add a filter for their specific parent images and accounts.
  • Tuning: adjust the count thresholds (hosts_touched >= 5, remote_execs >= 20) to your fleet size; in small estates, lower both. Consider a lookup table of approved remote-execution sources.
  • Severity: critical, matching the TH-01 rank. Any hit outside a change window deserves immediate review.

TH-02 · Raw disk writes corrupting boot records

  • Sigma to SPL mapping: TargetObject|startswith becomes a wildcard match; in SPL, each literal backslash must be escaped, so the device path is written with doubled backslashes inside the quoted string.
  • False positives: imaging and cloning tools (disk2vhd, physical dd) and block-level backup agents. Keep the allowlist short and reviewed.
  • Tuning: add your own imaging tools to both filters, and consider separating reads (EventID 9) from writes if your EDR provides write-level raw access events, raising severity for writes.
  • Severity: critical, matching TH-02; raw access by an unknown binary is rarely benign.

TH-03 · Wiping commands on Linux servers

  • Field assumptions: the linux:audit sourcetype extracts a0..a3 from the EXECVE record; if your parser stores arguments as argc_a0 or one concatenated cmd field, adapt the field names or add an rex step.
  • Sigma to SPL mapping: the two selection_dev_* variants mirror argument-position differences (dd uses a1/a2, mkfs usually a1); in SPL, coalesce collapses that variance.
  • False positives: planned provisioning and disk sanitization by storage teams. Correlate with change tickets and allowlist the responsible accounts.
  • Tuning: add a second rule for device paths of data volumes only if alerts are noisy; keep at least monitoring coverage for /dev/sda-style system disks.
  • Severity: high, matching TH-03.

TH-04 · Recovery infrastructure destroyed first

  • Field assumptions: command-line auditing (4688 with CommandLine) is enabled and the WinEventLog:Security sourcetype provides process_path, process_command_line, and parent_process_name fields; rename to your schema if you use CIM addons.
  • Sigma to SPL mapping: each selection is a direct field-value pair; the Sigma 1 of selection_* condition becomes the OR block.
  • False positives: legitimate rotation scripts on backup servers. Scope a suppression to the backup server group only, never fleet-wide.
  • Tuning: alert immediately at this level; add a companion correlation that raises severity when this fires within an hour of TH-01 staging signals.
  • Severity: high, matching TH-04 (the wipe that follows would be critical; the deletion itself is the earliest reliable alarm).

TH-05 · Insider bulk-deletes with admin tooling

  • Field assumptions: the sourcetype extracts user from the 4663 SubjectUserName field and keeps ObjectName intact; adjust for your add-on.
  • Sigma to SPL mapping: Sigma's aggregate condition (count(ObjectName) by SubjectUserName > 200 in a 5-minute timeframe) becomes bin + stats + where.
  • False positives: retention and migration jobs; the example excludes two service accounts, but you should drive this from a lookup of scheduled accounts.
  • Tuning: start with 200 files per 5 minutes, then calibrate against two weeks of baseline data; combine with 4660/4670 events for confirmation.
  • Severity: medium, matching TH-05.

TH-06 · Wiper disguised as ransomware

  • Field assumptions: the Sysmon add-on extracts EventCode, TargetFilename, Image, and user from Event ID 11 file-create events; rename to your schema if you use a CIM mapping.
  • Sigma to SPL mapping: the two note selections become one OR block; contains|all (both strings in one filename) becomes two adjacent wildcard filters, which SPL joins with AND; the aggregation becomes bin + stats + where; the program-files filter stays as a NOT clause.
  • False positives: ransomware drills and restore tools that write instruction files. Log your exercise windows and exclude them by host or time.
  • Tuning: raise the threshold on large terminal servers; add a companion check that counts 4663 WriteData bursts with no extension changes, which confirms the wipe story.
  • Severity: high, matching TH-06. Treat every true hit as a destructive-incident trigger, not a ransomware negotiation case.

Real-World Case Study

The Ukraine power-grid attack of 23 December 2015: a destructive intrusion that ended with wiped systems and a city-sized blackout.

Context

On 23 December 2015, three regional electricity distribution companies in Ukraine suffered simultaneous cyber attacks on a winter evening. The attackers opened breakers at about thirty substations. Roughly 225,000 to 230,000 customers lost power for one to six hours. These figures come from public reporting by ESET, SANS ICS, and the US ICS-CERT alert IR-ALERT-H-16-056-01 (later republished by CISA).

The incident is the clearest public example of disk wiping inside an OT (operational technology) network. OT means the systems that control physical equipment. After the disruption, the attackers destroyed systems to slow the response.

The intrusion had started much earlier. Public reporting describes spearphishing emails with macro-laden Microsoft Office documents sent to utility staff. The attachments delivered BlackEnergy3. The attackers then lived in the networks for months. They learned the environment, stole credentials, and prepared both the grid actions and the destructive finale.

In the same campaign wave, vendor reporting described KillDisk-based destructive attacks against Ukrainian news media organizations. ESET published this analysis in January 2016, so the wipe component reached more than one sector.

Public record vs. illustrative

Public record: the date, the three distribution companies, about thirty substations, and the outage of roughly 225,000 to 230,000 customers for one to six hours. Also public: BlackEnergy3 delivery by macro documents, KillDisk file and boot-record destruction, and the call-center phone denial-of-service. Illustrative: exact clock times, host names, and any internal ticket flow that public sources do not document; treat those as teaching reconstructions.

Timeline

  1. Early 2015 Utility staff receive spearphishing emails with malicious macro documents. According to public reporting, some users enabled macros and BlackEnergy3 was installed.
  2. Months before December The attackers harvest credentials with keyloggers and move laterally, mapping the corporate networks and the remote-access path into SCADA (Supervisory Control and Data Acquisition, the control systems for the grid).
  3. Days before Operators prepare: they study breaker-control workflows and stage destructive tooling, including KillDisk components.
  4. 23 December, about 15:00 local Using stolen VPN credentials and valid accounts, the attackers connect into the OT environment through external remote services.
  5. 23 December, about 15:15-15:30 Breakers open across roughly thirty substations. Customers begin losing power. Operators switch to manual control of the grid.
  6. Same afternoon KillDisk wipes systems: files are overwritten, boot records are corrupted, and logs are destroyed. Serial-to-Ethernet gateway devices are rendered unbootable through firmware attacks, per public reporting.
  7. Following hours Helpdesk calls spike; the utility also suffers a simultaneous telephone denial-of-service against its call center, delaying customer reports.
  8. Days after Power is fully restored by manual operation and repairs; the forensic picture is limited because the attackers had destroyed logs.
  9. January 2016 Vendor reporting describes KillDisk-based destructive attacks against Ukrainian news media organizations in the same wave.
  10. January-February 2016 ESET, SANS ICS, and ICS-CERT publish their analyses. Public reporting attributes the operation to the group tracked as Sandworm; several vendors and the targeted government have stated this attribution, and investigators continued to refine it.

Detection point

The destructive phase was visible: wiping and unbootable workstations were discovered during the attack itself. What defenders lacked was early detection. According to public reporting, the months of credential theft and lateral movement went unnoticed. The log destruction in the finale deliberately impaired the investigation. The lessons map directly to this page's detections: command-line auditing for vssadmin-style destruction (TH-04), mass remote-execution monitoring (TH-01), and logs kept safely outside the machines an attacker can wipe.

Containment, eradication, and recovery

  • Containment: operators disconnected remote-access paths and isolated affected segments to stop further actions.
  • Service restoration: the grid ran in manual mode while affected control systems were repaired; this manual operation is what kept the outage bounded.
  • Eradication and recovery: wiped workstations and servers were rebuilt, and serial-to-Ethernet gateways needed firmware reflashing because their software had been rendered unusable.
  • Team response and communication: per public reporting, the utilities coordinated with national CERTs and international investigators; the call-center denial-of-service forced them to set up alternative customer communication paths - a reminder that destructive attacks often come with distraction attacks.

Response team roles

Public after-action reporting does not name the individuals. The roles below are an illustrative reconstruction of how utilities and CERTs handled this class of incident. Use them as a staffing checklist for a destructive-incident drill.

  • Incident commander: declares the major incident, owns the decision log, and arbitrates between power-restoration and evidence-preservation choices.
  • OT and grid engineers: switch to manual operation, protect safety functions, and decide which control systems can be taken offline for rebuild.
  • IT and helpdesk leads: triage unbootable machines, manage the customer-communication fallback after the call-center flood.
  • National CERT and vendor liaisons: share samples and indicators, coordinate the public advisories that later documented the case.
  • Forensics and malware analysts: recover what the wiper left, analyze KillDisk and BlackEnergy3 artifacts from untouched copies.
  • Executive and regulatory communication: brief leadership and regulators; destructive outages in critical infrastructure carry reporting duties.

Impact and lessons learned

Roughly 225,000 to 230,000 customers lost electricity for one to six hours. There were no confirmed safety incidents, but the event proved that cyber intrusions can cause mass outages. For defenders, six lessons stand out:

  • Disable or tightly control Office macros. The intrusion began with one enabled macro.
  • MFA on every remote-access path. Stolen VPN credentials were the bridge into the OT network.
  • Segment IT and OT. A corporate foothold should never directly reach breaker controls.
  • Keep logs off-site. Wiping destroyed local evidence; centralized copies preserve the truth.
  • Practice manual operations. The grid survived because operators could work without SCADA.
  • Treat wiping as the end, not the whole story. A wipe means months of undetected access - assume broader compromise and hunt backwards through the chain.

Mitigation and Defense

The controls that make a fleet-wide wipe hard to stage, hard to miss, and possible to undo.

No single control stops a privileged destructive attack. The defense is a stack: make privilege rare, make recovery independent, and make destruction noisy. The groups below use MITRE ATT&CK mitigation names.

Policy

Implementation · Playbook

  • Maintain a destructive-incident playbook with clear decision authority.
  • Require change control for shadow-copy and backup-configuration changes.
  • Run destructive-scenario tabletop exercises twice a year.

Identity

Privileged Account Management

  • Tiered admin model: domain admins never log into workstations.
  • MFA on all remote access and admin consoles.
  • No shared credentials; per-admin accounts with just-in-time elevation.

Endpoint

Operating System Configuration

  • EDR with tamper protection and mass-overwrite analytics enabled.
  • Application allowlisting on servers where feasible.
  • Block or tightly control Office macros; block raw disk device access for standard users.

Network

Network Segmentation

  • Segment IT from OT and restrict admin shares (C$, ADMIN$) between workstations.
  • Limit SMB, RDP, WMI, and SSH to management servers only.
  • Rate-limit and monitor remote-execution patterns across segments.

Cloud

Remote Data Storage

  • Snapshot isolation: backups written by a separate identity the fleet cannot use.
  • Immutable or object-lock storage for critical datasets.
  • Alert on mass snapshot deletion in cloud audit logs.

Logging

Operating System Configuration

  • Centralize Sysmon, Security, auditd, and backup logs off-host.
  • Write-once or forward-immediately so wiping cannot destroy them.
  • Enable command-line auditing (4688) and auditd execve rules fleet-wide.

Monitoring

Operating System Configuration

  • Deploy the Section 5.5 rules: raw disk access, recovery deletion, remote-execution bursts.
  • Monitor backup job health and agent liveness as security signals.
  • Alert when multiple forwarders go silent together.

Backup

Data Backup

  • Follow the 3-2-1 rule: three copies, two media types, one offline.
  • Keep at least one copy immutable or physically offline.
  • Test restores quarterly and record the results as evidence.

Response

Incident Response Plan

  • Pre-approve isolation authority for on-call analysts.
  • Practice the six-step triage flow from Section 4.
  • Define rebuild and restore sequences before you need them.

Home and small office

  • Turn on automatic backups to an external drive that stays disconnected most of the time, plus one cloud backup service.
  • Keep system restore enabled and create a monthly restore point.
  • Use a standard (non-administrator) account for daily work; type the admin password only when installing or changing settings.

Common Mistakes and Best Practices

Twelve blue-team mistakes that turn a detectable wipe into a disaster, each with a fix and a prevention habit.

01 Alerting on every sdelete or dd

  • SymptomThe team stops trusting the rule after a week of noise.
  • Root causeNo baseline of which admins legitimately wipe decommissioned disks.
  • FixBuild an allowlist of accounts, hosts, and change windows; alert only outside it.
  • PreventionRe-review the allowlist quarterly with the infrastructure team.

02 Treating backup deletion as an IT ticket

  • Symptomvssadmin delete shadows arrives as a low-priority queue item.
  • Root causeRecovery-destroying commands are seen as operational, not security.
  • FixRoute TH-04 detections straight to security triage at high severity.
  • PreventionJoint SOC/IT runbook that names these commands as incident triggers.

03 Logging only on the endpoints

  • SymptomEvidence dies with the machines that were wiped.
  • Root causeLogs stay local; the wiper deletes them with everything else.
  • FixForward logs off-host in near real time to a place the fleet cannot write to.
  • PreventionTest: wipe a lab box and confirm its logs survive in the SIEM.

04 auditd disabled on Linux servers

  • SymptomNo EXECVE record exists for the dd that destroyed a database.
  • Root causeauditd seen as a performance cost; execve rules never added.
  • FixEnable auditd with execve, device, and identity rules on all servers.
  • PreventionServer build images ship with the audit policy preinstalled.

05 Backup health not monitored as security

  • SymptomBackup jobs failed for days; nobody noticed until restore time.
  • Root causeBackup telemetry lives in an ops tool, separate from SOC alerting.
  • FixStream backup job, agent, and catalog events into the SIEM with alerting.
  • PreventionWeekly review of restore-point coverage for critical systems.

06 One giant wipe alert with no context

  • SymptomAnalysts cannot tell a provisioning job from Shamoon-style staging.
  • Root causeRules fire without user, host, parent, and change-window context.
  • FixEnrich alerts with process tree, ticket data, and asset criticality.
  • PreventionUse the 5.5 rules, which were written to carry that context.

07 No owner for destructive detection content

  • SymptomRules break silently after a Sysmon or parser change.
  • Root causeNobody owns the rules; no regression tests exist.
  • FixAssign an owner, add the events in 5.4 as pipeline test cases.
  • PreventionCI job that replays test events against detections each week.

08 Assuming wipes are Windows-only

  • SymptomLinux servers have no coverage; a stolen key destroys a data tier.
  • Root causeThreat models built only from Windows ransomware incidents.
  • FixDeploy TH-03 and auditd coverage; add Unix wiping to threat models.
  • PreventionCoverage matrix by platform, reviewed per ATT&CK release.

09 Backups reachable from the domain admin account

  • SymptomAttacker with one stolen admin credential deletes every backup.
  • Root causeBackup consoles and shares trusted the whole domain.
  • FixIsolate backup infrastructure; separate credentials and MFA.
  • PreventionAccess review showing no production admin can reach backup stores.

10 Tuning by disabling, not by scoping

  • SymptomAfter false positives, the rule is switched off entirely.
  • Root causePressure to silence noise without analysis time.
  • FixScope suppressions to specific accounts, hosts, and windows only.
  • PreventionChange review requires an expiry date on every suppression.

11 Forgetting cloud and SaaS deletion paths

  • SymptomAttackers delete snapshots and mailboxes via API while endpoints look fine.
  • Root causeDetection scope stops at the network edge.
  • FixIngest cloud audit logs; alert on bulk snapshot and object deletions.
  • PreventionInclude cloud admins and APIs in the destructive threat model.

12 No practiced restore sequence

  • SymptomAfter a wipe, teams argue about what to rebuild first while downtime grows.
  • Root causeRestores were tested ad hoc, never sequenced under pressure.
  • FixDocument and rehearse rebuild order: identity, security tooling, core services, data.
  • PreventionAnnual destructive-scenario exercise with measured recovery time.

Operating habits

Daily

  • Review high-severity file-overwrite and raw-disk alerts within the hour.
  • Check backup job status as part of the morning SOC routine.
  • Glance at log-volume anomalies: sudden gaps can be a wipe in progress.

Weekly

  • Verify restore points exist for all critical systems.
  • Review new suppressions and expired change windows.
  • Tune the 5.5 rules against the week's false positives.

Monthly

  • Run one restore test from the offline copy and record the result.
  • Re-check detection coverage against updated ATT&CK data.
  • Confirm auditd, Sysmon, and command-line auditing are still enabled everywhere.

Incident response checklist

  1. Declare a major incident and open the destructive-incident playbook.

Short glossary

MBR / GPT
The Master Boot Record and GUID Partition Table: the small structures at the start of a disk that tell the machine how to boot and where partitions live.
MFT
Master File Table: the NTFS index that tells Windows where every file is stored.
VSS / shadow copies
Windows snapshots of files that allow restoring earlier versions; attackers delete them first.
EDR
Endpoint Detection and Response: agent software that records process, file, and disk activity and can isolate a host.
FIM
File Integrity Monitoring: a tool that alerts when files change, by comparing hashes.
auditd
The Linux audit daemon; it records system calls such as executed commands (EXECVE).
Sysmon
A Windows system monitor that writes detailed process, file, and raw-disk events to the event log.
SOC / SIEM
Security Operations Center and Security Information and Event Management: the team and the platform that collect and correlate logs.
