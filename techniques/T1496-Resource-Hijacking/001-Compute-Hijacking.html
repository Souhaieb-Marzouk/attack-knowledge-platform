T1496.001 Compute Hijacking

Compute hijacking is the core of cryptojacking (using stolen computers to mine cryptocurrency): an attacker uses your processors — the CPU (central processing unit, a computer's main chip) or the GPU (graphics processing unit, the chip that renders images and powers AI math) — to mine cryptocurrency, which is digital money. Your machines do the work, the electricity and cloud time are on your bill, and the coins land in the attacker's wallet. This sub-technique guide walks through the attack on servers, endpoints, containers, and cloud compute. It shows what the attack leaves in your logs, and it gives you detections you can adapt.

  • Tactic: Impact
  • Platforms: Containers, IaaS, Linux, Windows, macOS
  • Parent: T1496 Resource Hijacking
  • ATT&CK v20 · modified 15 Apr 2025
  • Detection strategy: DET0540
  • Guide version: 2.0

What it is

Your compute cycles, attacker profit

Malware or abuse of cloud APIs (application programming interfaces — ways for programs to request services) turns your machines into coin-mining workers.

Typical impact

Slow systems, big bills

CPU plateaus can stall apps; hijacked GPU fleets can cost thousands per day.

Where it strikes

Servers, containers, cloud compute

Exposed Kubernetes APIs and leaked cloud keys are the most common doors.

Why it is hard to catch

Load can look like real work

Miners throttle CPU, rename files, and hide pool traffic inside TLS (the encryption that protects normal web traffic).

Overview

In this sub-technique the attacker runs their work on your computers. After getting in, they use your processors to mine cryptocurrency (this abuse is called cryptojacking) — digital money such as Monero. Your machines pay in heat, noise, power, and cloud spend, while the coins go to the attacker. Compute hijacking is the most widely reported form of resource hijacking (the parent technique T1496).

What the sub-technique is

An attacker gains code execution or cloud access. Instead of stealing data or locking files, they install a miner, or they use your cloud provider's API to rent GPU machines on your card. ATT&CK (MITRE ATT&CK — the free public knowledge base of attacker techniques) describes the purpose plainly: validating cryptocurrency transactions, called mining, to earn virtual currency. The load can make machines unresponsive, so real work suffers.

Targets range from one laptop to whole clusters. Servers and cloud systems are preferred targets because they have many cores, stay online all the time, and few people watch them outside work hours. Container platforms are extra attractive because one exposed API can start dozens of miner pods in minutes.

Why it matters

First, money. A hijacked cloud account running GPU machines can add thousands of dollars per day. A mining fleet on your servers raises power and cooling costs and shortens hardware life. Second, availability. A miner that takes 95 percent of the CPU makes applications slow or unresponsive; on laptops, fans run at full speed and batteries drain early.

Third, and most important: a miner is a symptom. It proves an attacker got past your patching process, found an exposed API, or stole a key. If you only delete the miner, the same door stays open. Many crews, such as 8220 Gang, started with mining and later added data theft.

Where it fits in the attack chain

Compute Hijacking sits in the Impact tactic, the last stage of the ATT&CK chain. By the time you see it, the attacker finished earlier steps: exploiting a public application (T1190), abusing valid accounts (T1078), and adding persistence such as cron jobs (T1053.003). The hijacking itself is usually the only step the attacker wants to keep alive, so most of their hiding effort goes here: renamed binaries, throttled CPU, and pool traffic disguised as web traffic.

Written story of the simulation

The list below covers the same eight steps as the animation. Screen readers and printouts get the full content here.

  1. Step 1 — Finding the exposed dashboard. The attacker scans the internet for Kubernetes dashboards, which are web control panels for clusters. One dashboard answers without asking for a password. The firewall sees ordinary scan noise, so no alert fires.
  2. Step 2 — Creating a privileged pod. The attacker uses the dashboard to send API calls that create a pod with full host privileges. A pod is a group of containers that runs together. The audit log records the creation, and the caller is anonymous — the first strong signal.
  3. Step 3 — Pulling the miner image. The pod downloads a public miner image, a ready-made mining program packaged for containers. A service account with no history pulls a Monero miner at 2:41 a.m. The cluster now runs attacker code.
  4. Step 4 — Mining starts. The miner connects to a mining pool, a server that hands out hashing jobs, and starts hashing. CPU jumps to about 94 percent and stays there. The billing curve climbs in parallel.
  5. Step 5 — Scaling to more pods. The attacker copies the pod to every node, so all cores work for the same wallet. Twenty similar pod creations in forty minutes, all from one source IP, reveal the scale-out.
  6. Step 6 — Defender signals align. The SOC joins three weak signals: anonymous pod creation, the CPU plateau, and egress to a pool address. The correlation rule raises one critical alert with full context. This is the CH-04 plus CH-02 join from Section 5, with node CPU metrics adding the third signal.
  7. Step 7 — Containment. The SOC evicts the miner pods, moves the dashboard behind the VPN (virtual private network — a private remote-access path), and rotates exposed tokens. Pool sessions end and CPU returns to baseline within minutes.
  8. Step 8 — Hardening and lessons. The team disables anonymous API access, applies pod security rules, and adds audit-based alerts. The entry path is closed, not just the symptom.

Red Team / Hacker Perspective

Understanding why attackers like this sub-technique helps you predict where they will show up. This section describes attacker thinking at a conceptual level. All commands shown later are lab-only examples for your own test systems.

When and why attackers use it

Mining is attractive because it pays without talking to the victim. Ransomware needs a negotiation; a miner just needs uptime. Some coins are designed to be mined with ordinary CPUs, which makes every server a candidate. Attackers pick this technique when they have broad but weak access: a foothold in a container cluster, a leaked cloud key, or a web shell on one server. It scales well — the script that mines one server mines a thousand.

Cloud accounts change the math. There is no malware to hide; the attacker just rents GPU machines from your provider using your keys. GPU families are built for machine learning work, but they are also ideal for mining, so they are the first thing abusers launch.

How it is performed (concept)

The pattern is almost always the same four moves: get code execution, download a miner or call the compute API, point the miner at attacker infrastructure, and make it survive reboots and cleanup. Mining malware frequently kills competing miners it finds, so the strongest miner wins the CPU. That kill behavior helps defenders, because it appears in logs as one process terminating another.

On containers the moves shift one level up: create a privileged pod, mount the host, pull a public miner image, and let the scheduler spread it everywhere. On cloud accounts there may be no payload at all — only audit-log entries that show compute the attacker created.

Ethics and legality

Using these methods against systems you do not own is a crime in almost every country, even "just to see if it works". Mining on stolen compute is theft of services, and connecting to pools creates real traffic to real infrastructure. Everything in this guide is for defenders and for safe labs you control. Run examples only on isolated machines you own, never against production or third-party systems.

Common variations

  • Container fleet mining: one exposed API, dozens of miner pods (TeamTNT and Kinsing used this method in many well-known campaigns).
  • Cloud-native hijack: no malware at all — the attacker launches GPU or spot fleets with stolen keys.
  • GPU cluster abuse: job-submission panels of AI platforms hijacked for mining (ShadowRay, campaign C0045).
  • Kill-and-take-over: new miner kills the old one, so traces of several families pile up on one host.
  • Miner plus loader: the miner earns the coins, while a second stage steals data or delivers more malware (8220 Gang's later waves).

Mistakes attackers make

  • Shipping stock miner binaries, so name and hash rules fire on arrival.
  • Using public pool addresses on default ports (3333, 4444, 14444), which egress rules block easily.
  • Ramping CPU to 100 percent immediately, which trips simple baselines.
  • Skipping the throttle on cloud GPU fleets, which triggers the billing alarm within hours.
  • Reusing one wallet address across victims, letting defenders link incidents.
  • Killing rival miners loudly, leaving a process-terminates-process trail in EDR (endpoint detection and response — security software that records what programs do) logs.

Blue Team / SOC Perspective

Compute hijacking is one of the most visible sub-techniques — if you collect the right data. This section shows what it looks like from inside your estate and gives you a triage flow you can follow on a busy shift.

How defenders can see it

Four telemetry families catch almost every variant: process telemetry (what runs, from where, with which command line), performance telemetry (CPU and GPU use over time), network telemetry (sessions, volumes, destinations), and audit logs (Kubernetes API calls, cloud API calls). No single source is enough. The strong detections in Section 5 all join at least two sources.

Remember the scale trick: one throttled miner is quiet, but fleets are loud. Cluster and cloud attacks create volume patterns — many pods, many instances, many similar events — that single hosts cannot produce by accident.

Artifacts it leaves behind

  • Miner binary in a temp path with a generic or kernel-like name, often with pool strings inside.
  • Cron entries, systemd services, or scheduled tasks that relaunch the payload after reboot.
  • Very long outbound TCP sessions (hours to days) to a small set of destinations.
  • CPU or GPU graphs with flat plateaus instead of normal daily waves.
  • Kubernetes audit entries: anonymous or unknown callers creating privileged pods.
  • Cloud audit entries: GPU instance types, spot fleets, regions your teams never use.
  • Traces of miner-versus-miner fights: one process repeatedly killing others.

Triage flow: a compute hijack alert arrives

  1. Confirm scope. One host or a fleet? Search your estate for the same indicators: pool domain, image name, wallet string, instance type.
  2. Join two signals. Pair the resource signal (CPU, instance, pod) with a cause signal (process, API caller, source IP). One alone is often a false positive.
  3. Decide containment speed. Miner on one app server: isolate the host now. Cloud API hijack: disable the key and set a spend throttle first, investigate after — costs grow every hour.
  4. Preserve evidence. Snapshot the host or export the audit slice before cleanup. You need the binary, image, config, and entry path later.
  5. Remove cause, not just effect. Deleting the miner is symptom work. Close the entry path, rotate exposed keys, and sweep for persistence such as cron jobs or new deployments.
  6. Feed detection. Turn the indicators into new Sigma rules and add the missed log source to your pipeline. Record the case in your threat intel notes.

Why this matters beyond money

Treat every miner as proof that the outer defenses failed. The attacker passed through the same paths ransomware crews use — exposed APIs, unpatched apps, and leaked keys. Closing those paths after a cheap mining case also protects you from a costly ransomware case later.

5.1Regulation mapping

A miner is rarely a reporting obligation by itself, but it always breaks control requirements about malware protection, monitoring, and resource integrity. When it runs on systems that handle personal or cardholder data, it becomes audit-relevant evidence that controls failed. Some auditors now treat unauthorized use of computing resources as its own review topic.

Audit tip

Keep three artifacts ready for every hijack scenario: a baseline document that defines normal CPU per host class, an export of the alert that fired with its disposition, and the post-incident rule change. Auditors trust artifacts that link detection to response.

5.2Threat intelligence

Mining actors are well documented, which makes intelligence work here very practical. Keep four lists fresh: active groups, their tools, their infrastructure (pools, proxies, loaders), and their current entry vectors. Feed those lists into the detections in 5.5.

Source types and how to use them

  • MITRE ATT&CK — the technique page lists active groups and software for T1496.001 (see the table below). Start here; it is free and vendor-neutral.
  • Vendor reporting — Trend Micro, Palo Alto Unit 42, Cado Security, and Sysdig's Threat Research team publish campaign write-ups with indicators and full kill chains.
  • OSINT feeds — abuse.ch MalwareBazaar has an xmrig tag for miner samples; URLhaus tracks distribution URLs; GitHub trackers follow pool infrastructure.
  • Commercial feeds — paid feeds add attribution and infrastructure age, useful for confidence scoring.
  • ISACs and abuse-working groups — sector warnings from ISACs (information sharing and analysis centers) such as MS-ISAC, and from M3AAWG (the Messaging, Malware and Mobile Anti-Abuse Working Group), about mining waves hitting municipalities, schools, and hospitals.
  • Internal telemetry — your own egress logs and DNS history are the best intel for your environment; every incident adds a permanent detection.

Confidence levels, in plain words

High means multiple independent sources agree and your own telemetry confirms it. Use it for blocking and alerting. Medium means the report is credible but you have not seen it locally — use it for hunts. Low means a single unverified claim — use it for awareness only. Re-score every quarter, because mining infrastructure rotates fast.

Apply intel in three steps: (1) enrich — tag pool, loader, and wallet indicators into your SIEM (a central system that collects and connects security logs); (2) hunt — search 90 days of history for each new actor's tools; (3) detect — write or tune a Sigma rule per tool family, then retire rules when a campaign dies.

5.5Sigma rules and Splunk SPL

Each threat gets one Sigma rule and one Splunk query in SPL (Search Processing Language — Splunk's search syntax) that implement the same logic. Index and sourcetype names are common defaults; adjust them to your environment. All queries assume fields are extracted at ingest time.

CH-01 Cryptominer execution — Sigma (process_creation, Linux) + SPL

Mapping note: implements analytic AN1490 (long-running high-CPU processes and miner launches) on the endpoint side of DET0540. Severity: critical.

Splunk SPL equivalent (assumes your Linux EDR forwards normalized process events to index=edr, sourcetype=linux:process, with fields image, command_line, parent_image, user; rename to match your TA):

False positives and tuning: pin your build tools' temp paths in an allowlist lookup; exclude CI runners by hostname tag; require the web-server parent clause on shared web hosts to cut installer noise. Re-test after every EDR agent upgrade, because field names drift.

CH-02 Mining-pool connections — Sigma (network_connection) + Zeek SPL

Real-World Case Study: 8220 Gang vs Oracle WebLogic

Public reporting describes the "8220 Gang" as a Chinese-speaking criminal crew tracked since 2019; newer tracking also uses the name "Water Sigbin". Its signature move: scan the internet for Oracle WebLogic servers, exploit a known flaw, and turn the host into a Monero miner. Unit 42 reported the first waves in May 2019; Trend Micro documented evolved tactics in May 2023, with follow-up reports in December 2023 and June 2024. The case is a clear teaching example because every detection from Section 5 applies to it.

Context

Oracle WebLogic is a Java application server that many companies run on the internet. It has had several serious flaws that allow remote code execution without credentials. A flaw that lets attackers run code without a password is very valuable to them. The 8220 Gang built an automated pipeline around those flaws: scan, exploit, download, mine, repeat. The name comes from the port 8220 used in early campaigns.

Public reporting includes Unit 42 (May 2019, first WebLogic XMRig waves), Trend Micro (May 2023, "8220 Gang Evolves With New Strategies"), Help Net Security (December 2023), and The Hacker News (June 2024). Later public reporting also links the crew to attempts against Atlassian Confluence, Log4Shell, RocketMQ (CVE-2023-33246), and misconfigured Docker servers. Over the years the crew widened targeting to Linux cloud hosts and added information stealers to the payload mix.

Attack chain

  1. Scan the internet for Oracle WebLogic servers on default ports.
  2. Exploit known deserialization or authentication-bypass flaws — a CVE (a public ID for a known software flaw) is one such flaw. Examples: CVE-2020-14882, CVE-2020-14883, and later attempts against CVE-2023-21839.
  3. Use the server's own download tools (curl, wget, PowerShell) to fetch a loader and the XMRig miner.
  4. Kill competing miners found on the host, so their process keeps the CPU.
  5. Connect to Monero mining pools, hiding pool traffic behind CDNs and ordinary-looking ports.
  6. In later waves: steal cloud credentials with an information stealer, opening the door to CH-03 cloud compute hijack as well.

Timeline (from public reporting)

  • May 2019

    Unit 42 documents the first 8220 Gang campaigns exploiting Oracle WebLogic servers to run the XMRig miner. The group name comes from the port 8220 the crew used.

  • 2019 to 2022

    The crew automates scanning and exploitation, adds Linux targets, and rotates loader domains and pool addresses to survive blocking.

  • November 2022 onward

    Attack intensity grows. Trend Micro later links this period to expanded tooling, CDN-fronted pool traffic, and information-stealer payloads.

  • May 2023

    Trend Micro publishes "8220 Gang Evolves With New Strategies" (16 May 2023), documenting attempts against the WebLogic flaw CVE-2023-21839 and new evasion behavior.

  • December 2023

    Public reporting (Help Net Security and other outlets) reports continued mining waves against unpatched servers worldwide.

  • June 2024

    Public reporting (The Hacker News) says the crew is still active, now mixing miners with information stealers on both Linux and Windows hosts.

Detection point

This attack chain is easy to see if you log process parents: a Java application server should never spawn curl, wget, or a miner. The moment WebLogic's java process becomes a parent to download tools or unknown binaries, you have a high-confidence alert (the CH-01 web-parent clause). Minutes later, the host shows a CPU plateau and a long stratum session (CH-02). Organizations that watched process lineage caught this campaign at step 3 of 6 — before serious cost accrued.

Containment and eradication

Containment: isolate the server, kill the miner tree, and block the loader and pool addresses at the firewall. Eradication: patch WebLogic (the CVE-2020-14882 class is fixed by Oracle's critical patch updates), remove loader artifacts and cron or systemd persistence, rotate any credentials the host held, and check for the information-stealer payload in later waves. The kill-competitor behavior makes eradication checkable: if your CH-05 rule stays quiet for a week, the rivalry cycle is gone.

Recovery and impact

Recovery is usually quick for this crew's mining-only waves: return the host to service with egress rules in place and monitor for one week. Impact adds up quietly: days of full CPU on an application server, higher power costs, degraded response times for real users, and — in the later waves — the risk that stolen credentials led to deeper access. The cost of the Monero mined was modest per host; the cost of the exposure was not.

Team response and communication

Responders who wrote up these incidents emphasize one communication point: a miner is a perimeter failure, so the report should go to the application owner and the platform team, not only to security. Frame it as "an unpatched internet-facing service was weaponized", not "we had a virus". That framing helped security teams get patching budgets and exposure reviews approved in the documented cases.

Lessons learned

  • Internet-facing application servers need a patch SLA measured in days — WebLogic flaws were exploited within days of disclosure.
  • Process lineage is the cheapest strong detection: java spawning curl or a miner should be a critical alert on every platform.
  • Egress control starves the attack: default-deny outbound makes pool connections and loader downloads fail loudly.
  • The kill-competitor pattern is easy to detect — watch for one process repeatedly terminating miner-named processes.
  • Assume credential theft in later waves: rotate host-held secrets even when the payload "only" mined.
  • Report the entry path, not the symptom, so the organization fixes the door, not just the payload.

Mitigation and Defense

ATT&CK's own mitigation note for this sub-technique is honest: it "cannot be easily mitigated with preventive controls since it is based on the abuse of system features." Mining uses the same CPU instructions your applications use. The practical answer is layered defense: make entry hard, make hijacking loud, and make the bill stop fast.

Policy & people

  • Asset policy: no internet-reachable admin panels or cluster APIs; exception process with expiry dates.
  • Cloud spend policy: budgets with alerts at 50, 80, and 100 percent of forecast, routed to security too.
  • Training on secret hygiene: no keys in pods, repositories, or build logs.

Identity

  • MFA on all cloud root and admin accounts — no exceptions.
  • Least privilege in IAM (identity and access management); separate roles for CI, humans, and workloads; no wildcard compute permissions for human users.
  • Short-lived credentials for workloads instead of static keys.

Endpoint

  • EDR with behavioral mining detection on all servers and endpoints.
  • Block binaries executing from temp paths; application allowlisting where possible.
  • Patch internet-facing applications within days: WebLogic, Confluence, and peers are proven miner doors.

Network

  • Default-deny egress; allowlists for required destinations only.
  • Block or alert on pool ports 3333, 4444, 5555, 7777, and 14444 outbound.
  • DNS filtering for known pool, loader, and proxy domains, refreshed monthly.

Cloud & containers

  • Kubernetes API and dashboard behind VPN or identity proxy; anonymous auth off; RBAC least privilege.
  • Pod security standards: no privileged pods by default; scan images for miners before they enter the registry.
  • Quotas and instance-type restrictions on GPU families; spot-fleet requests need approval.

Logging & monitoring

  • Deploy the five Sigma rules from Section 5.5 with their listed log sources.
  • CPU and GPU baselines per host class; alert on plateaus above baseline.
  • Kubernetes and cloud audit logs to an immutable store; billing alerts reach the SOC, not just finance.

Home and small-office users

You are a target too — mostly through cracked software and fake installers that carry miners. Five practical steps help:

  1. Never install cracked or "free" versions of paid software.
  2. Keep your operating system and router updated.
  3. If a computer gets slow, hot, or noisy for no reason, open Task Manager or top and look for unknown processes using most of the CPU.
  4. Use the built-in malware protection and let it update.
  5. Do not trust browser extensions that promise free content.

If your computer is loud while you sleep, investigate.

Response-ready habits

Keep an emergency runbook for the two classic pages: "unknown process at 95 percent CPU" and "cloud bill spike". It should name who to call, which keys to disable first, how to isolate a host, and where the audit logs live. Practice it once a quarter as a tabletop. The 8220 Gang case shows why speed matters: their pipeline exploits new targets within days, so your patch SLA and your egress rules are the real defense.

Common Mistakes and Best Practices

These ten mistakes come from real SOC reviews of cryptojacking detections. Each one lists the symptom you will notice, the root cause, the fix, and the habit that prevents it from returning.

1. Watching CPU only

  • Symptom: incidents found by users (loud fans) or by bills, not by alerts.
  • Root cause: detection logic stops at "high CPU", so throttled miners that cap at 80 to 90 percent pass.
  • Fix: join CPU signals with process and network signals (CH-01 plus CH-02).
  • Prevention: require two data sources for every hijacking rule.

2. Trusting antivirus names

  • Symptom: "no malware found" verdicts on hosts that are clearly mining.
  • Root cause: miners arrive renamed (kswapd0, kdevtmpfsi look-alikes), so name-based antivirus misses them.
  • Fix: detect behavior and context — temp paths, pool strings, web-server parents — not just names.
  • Prevention: keep the CH-01 rule in the SIEM, not only in the antivirus console.

3. Ignoring Linux servers

  • Symptom: strong Windows coverage, yet miners live on Linux web hosts.
  • Root cause: no auditd or EDR agent on Linux; "it is just a web server" thinking.
  • Fix: ship auditd plus EDR to every Linux host; deploy CH-01 and CH-05 for Linux.
  • Prevention: coverage matrix per platform, reviewed quarterly.

4. Leaving cluster APIs open

  • Symptom: miner pods appear with names and images nobody in the team knows.
  • Root cause: dashboard or API reachable from the internet, anonymous access on, RBAC wide open.
  • Fix: move the API behind VPN, disable anonymous auth, enforce RBAC and pod security standards.
  • Prevention: cloud baseline check at onboarding for every new cluster.

5. Deleting the miner and closing the ticket

  • Symptom: the same host reappears with a new miner name next week.
  • Root cause: symptom-only response; the entry path and persistence stay.
  • Fix: mandatory persistence sweep (CH-05) plus entry-path review before closing.
  • Prevention: closure checklist in the ticket template.

6. Egress allow-all

  • Symptom: weeks of mining before anyone notices; loaders update freely.
  • Root cause: servers can reach any address on any port, including pools on 443.
  • Fix: default-deny egress; allowlists; DNS filtering for pool domains.
  • Prevention: treat new outbound destinations as change requests.

7. Alerting on single pool-port packets

  • Symptom: hundreds of low-value alerts; analysts auto-close them.
  • Root cause: one-packet port matches with no duration, volume, or allowlist context.
  • Fix: require 6-hour-plus sessions, repeat hits, or upload volume (the CH-02 SPL does this).
  • Prevention: every rule ships with its false-positive budget documented.

8. Billing alerts never reach the SOC

  • Symptom: finance reports a bill over 10,000 dollars days after the fact.
  • Root cause: cost alerts route to finance only; security has no visibility of spend.
  • Fix: route budget and anomaly alerts to the SOC channel; add CH-03 as a saved search.
  • Prevention: asset inventory includes every cloud account with a security contact.

9. Static thresholds forever

  • Symptom: alert floods after a legitimate batch job, or silence after infrastructure growth.
  • Root cause: "90 percent CPU" thresholds written once, never re-baselined.
  • Fix: per-host-class baselines with scheduled re-learning windows.
  • Prevention: quarterly threshold review tied to the change calendar.

10. Rules never tested

  • Symptom: a rule "works" for years — because it has never matched anything, including real attacks.
  • Root cause: no validation pipeline; field names drifted after an agent upgrade.
  • Fix: replay the Section 3 lab events monthly; review rules with zero matches in 180 days.
  • Prevention: detection CI: every rule change runs a synthetic event test.
