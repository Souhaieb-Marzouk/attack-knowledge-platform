T1584.007Serverless

Serverless functions are small pieces of cloud code that run only when someone calls them. In T1584.007, an attacker breaks into a cloud account and turns that on-demand computing power into free, auto-scaling attack infrastructure — a redirector, a proxy, or a command relay that hides behind a trusted vendor domain.

Overview

This section explains the technique in plain words: what serverless computing is, why attackers want it, and where it sits in an attack. It also shows the difference between compromising someone’s cloud functions and simply signing up for a free account.

What serverless means

Serverless is a cloud offer where you upload small pieces of code, and the provider runs them only when someone calls them. You never see or manage a server. The main products are AWS Lambda (Amazon’s serverless service), Azure Functions, Google Cloud Functions and Cloud Run, and Cloudflare Workers.

T1584.007 Serverless means an attacker compromises serverless resources — usually by stealing cloud account access or abusing deploy permissions — and then uses those functions as command-and-control (C2) redirectors, proxies, or task runners for an attack.

Why attackers want it

  • Auto-scaling: the vendor adds capacity automatically, so one beacon and one million beacons look the same to the platform.
  • Hard to block: endpoints live on vendor domains like amazonaws.com or workers.dev, which normal business apps also use; blocking the whole domain breaks your own tools.
  • Ephemeral endpoints: a function can be deleted and redeployed with a fresh address in minutes, so URL blocklists age fast.
  • Cheap: free tiers and pay-per-use pricing make thousands of requests cost almost nothing.

Where it fits in the attack chain

ATT&CK calls this stage Resource Development. It happens before the victim is involved. A deployed function then supports the intrusion steps that follow:

  1. T1584.007 Serverless
  2. T1568 Dynamic Resolution (redirector front)
  3. T1090 Proxy (traffic relay)
  4. T1071 Application Layer Protocol (C2 channel)

The function never runs the malware’s heavy work itself — its job is to hide where the malware really talks. One function can serve many implants at once, and the extra regions cost the attacker pocket change.

Compromise (T1584.007) vs. acquire and free-tier abuse (T1583.007)

ATT&CK splits the idea in two. T1584.007 (this page) is compromise: the attacker takes over serverless resources that belong to someone else, often the whole cloud account behind them.

T1583.007 (Acquire Infrastructure: Serverless) is acquiring: the attacker signs up for a new account and abuses the free tier. No victim account exists yet, so the main defenses are provider-side abuse controls and your own egress visibility.

Attackers still prefer compromise when they can get it: a hijacked company account has real billing history, higher service limits, and access to data that is already inside.

    The same story in words

    1. Steal a way into the cloud. The attacker uses access keys stolen by an info-stealer, or hijacked CI/CD credentials, to reach a cloud account they do not own. SOC view: a dormant access key wakes up from a new network and country.
    2. Deploy a forwarding function. A small function is created whose only job is to receive requests and forward them onward. SOC view: a CreateFunction event from a principal that never appears in normal releases.
    3. Get a trusted HTTPS endpoint. The cloud hands the function a public HTTPS address with a valid vendor TLS certificate included. SOC view: a new endpoint under a vendor domain, easy to miss in an ungoverned account.
    4. Implant beacons out. Malware on an infected workstation starts calling the serverless endpoint over normal HTTPS. SOC view: fixed-interval POSTs to a serverless URL from an unknown process.
    5. Function forwards to the attacker. The beacon is forwarded to the attacker backend, hiding the true destination. SOC view: small payloads on a steady clock.
    6. Commands ride back. The backend answers and the function passes commands to the implant. The C2 channel is complete. SOC view: request and answer pairs repeat in a loop.
    7. Scale and rotate. As blocks arrive, the same function is deployed in other regions and new endpoints appear in minutes. SOC view: single-URL blocking loses; the pattern keeps coming back.
    8. SOC responds. Analysts correlate the alerts, block the vendor endpoint paths, report abuse to the provider, and rotate the keys. SOC view: the attacker’s route is cut off.

    Red team / hacker perspective

    This section explains how attackers think when they abuse serverless platforms. Everything here is described for education and defense only. Practice these ideas exclusively in your own sandbox account.

    Why attackers choose serverless

    • IP rotation: functions run on cloud address ranges that change constantly, and endpoints can be redeployed in other regions in minutes.
    • TLS from the vendor: every endpoint arrives with a valid certificate owned by Amazon, Microsoft, Google, or Cloudflare, so certificate checks pass.
    • Pay-per-use: nothing to buy up front; free tiers give generous monthly limits, and beacon-scale traffic costs pennies.
    • No server ops: no patching, no hosting bills, no VPN to manage — the provider runs and scales the code.

    How the takeover happens (conceptual)

    • Stolen long-lived access keys: info-stealer malware and leaked repositories expose static cloud keys that often keep working for months.
    • Compromised CI/CD: the attacker steals the pipeline’s tokens and uses the pipeline’s own deploy permissions.
    • Over-privileged deploy roles: a role that may create any function in any region becomes free hosting for the attacker.
    • Secrets in code: keys pushed to public code hosts are found by automated scanners within minutes.

    Where it applies and what it needs

    Attacker goalWhat the function doesPreconditions
    C2 redirectorReceives implant beacons, forwards them to the real backend, and returns the answersStolen cloud keys or a compromised deploy pipeline
    Proxy / relayChains traffic through several functions and regions to hide the true originAccess to several accounts or free tiers
    Scanning / staging runnerRuns scans or stages tools from cloud addresses that look harmlessFunction with broad network permissions
    Credential-stuffing frontForwards login attempts so targets see many vendor cloud addressesA list of stolen passwords and a simple request loop

    Lab practice that stays legal

    You can safely feel how this works with an echo function — a function that answers each request with a fixed string — in your own sandbox. Typical lab steps:

    1. Create a personal sandbox account on the free tier that shares nothing with your employer or clients.
    2. Deploy a tiny echo function and note its public HTTPS address.
    3. Call it with curl, then read the function logs and the endpoint access logs.
    4. Add a second function that forwards to the first, and watch how a forwarding chain looks in logs.
    5. Delete everything when done, and set a billing alarm while you practice.
    Danger. Never deploy functions into someone else’s account, never use functions you do not own as relays, and never test systems you have no written permission to test. Free-tier abuse breaks provider terms and can be a crime.

    Common variations and attacker mistakes

    • Variation — relay chains: several functions across providers; blocking one changes nothing.
    • Variation — lookalike naming: function names copy the victim’s own style, such as billing-sync-prod, so they blend in.
    • Mistake — free-tier burning: heavy use triggers billing alarms and provider bans, which invites abuse-team attention.
    • Mistake — name leftovers: functions called c2-forward or stage1 tell responders exactly what happened.
    • Mistake — static configs: a hardcoded backend address lets defenders sinkhole it and watch who still calls.

    Blue team / SOC perspective

    Defenders cannot see inside the cloud provider’s platform, but they can see both ends: who changes what in the cloud account, and what your own devices and servers actually connect to. This section shows where function abuse becomes visible and how to triage it.

    How defenders can see it

    Function abuse produces two kinds of visibility. Cloud-side signals come from audit logs: AWS CloudTrail, the Azure Activity Log, and Google Cloud Audit Logs record who created or changed every function. Network-side signals come from your own perimeter: the egress proxy shows which vendor endpoints your devices really call, and an EDR (endpoint detection and response) tool shows which process made each connection. A WAF (web application firewall) adds visibility for public endpoints you own, and billing alerts expose sudden usage spikes.

    If you ingest only one of the two sides, you will miss half the picture. Correlating them is where the confidence comes from: an odd deployment plus a beacon is a case, not a coincidence.

    Artifacts it leaves and where to look

    ArtifactWhere to lookExample signal
    Function created or updated by an odd principalCloudTrail / Azure Activity / GCP audit logs in the SIEMCreateFunction20150331 from a human user at 02:00 from a new country
    Beacons to serverless vendor endpointsEgress proxy logs, EDR network eventsFixed-cadence POSTs to *.execute-api.amazonaws.com or *.workers.dev
    Sudden cost spikes on function servicesBilling and cost anomaly alertsAPI Gateway spend multiplies overnight with no release
    New log groups or unusual runtimesCloudWatch / Azure MonitorNew log group with a steady, non-business request rate
    New roles or keys around deploymentIAM and key management logsAccess key created and used within minutes

    Why this matters for your organization

    Serverless abuse hits you in two directions. As the victim account owner: attacker code runs under your name, on your bill, next to your data — and may read secrets if its role allows. As the target: implants hiding behind vendor HTTPS defeat user training ("check the lock icon!") and most IP blocklists alike. Fast detection on either side shortens every later attack stage.

    Short triage flow

    1. Validate the deployment: change ticket, owner, pipeline job name.
    2. Enrich: who used the key, from which ASN (the network operator behind an IP) and country, and what else changed in the account.
    3. Scope: search proxy, EDR, and DNS logs for the endpoint for the last 90 days.
    4. Contain: rotate or disable the keys, remove or disable the function, block the endpoint path.
    5. Report abuse to the cloud provider and notify your account team.
    6. Hunt for other functions, roles, and log groups the same principal touched.
    Good practice. Build a small "cloud change" alert list: new functions, new access keys, first-time use of old keys, and new public endpoints. These four cheap alerts catch most serverless abuse before the first beacon completes.

    5.2 · Threat intelligence

    Serverless abuse moves with the cloud market, so intelligence keeps your detections current. A simple pipeline works: collect raw signals, analyze them against your assets, apply the result to detections and blocks, then review what worked.

    Sources worth wiring up

    • Cloud vendor security blogs: AWS, Microsoft, and Google publish abuse patterns and new protections first.
    • Research teams: Microsoft MSTIC, Unit 42, Lacework (now part of Fortinet), and Intezer — reports such as Denonia.
    • CISA advisories: cloud misuse warnings and key-hygiene guidance for operators.
    • Cloud-native telemetry vendors: serverless and workload threat reports from CNAPP/CSPM tool makers.
    • Internal telemetry: your own CloudTrail and proxy logs — the highest-signal source you own.

    Confidence levels that work

    Tag every indicator with a confidence level and keep the meaning strict:

    • High: confirmed by two independent sources or direct observation (your logs plus a vendor report).
    • Medium: one reliable source, no second confirmation yet — good for detection, not for blocking.
    • Low: rumor, paste-site claim, or machine-only correlation — good for hunting lists only.

    Write the level into the indicator record so the analyst who meets it at 03:00 knows how much to trust it.

    5.5 · Sigma rules and Splunk SPL

    The four rules below cover the highest-value threats (TH-01, TH-02, and TH-05). Sigma is an open format for detection rules that most SIEM tools can translate; SPL is the search language of Splunk. Each rule is valid YAML and is followed by a matching query, a mapping note, and tuning advice. Replace index and sourcetype names with your local naming — the field assumptions are stated under each query.

    SIG-001 · Function created or updated outside the deploy pipeline (TH-01)

    Mapping note: assumes CloudTrail normalized into the CIM with user_arn for userIdentity.arn — if your fields keep the raw JSON names, run spath first. False positives: ungoverned sandbox accounts share the trail; scope by account ID. Tuning: after GeoIP enrichment, add a source-country filter so a pipeline identity deploying from a new country still alerts. Treat every hit as a possible stolen key until the owner confirms it.

    SIG-002 · Fixed-cadence egress to serverless vendor endpoints (TH-02)

    Mapping note: the query flags users that called a serverless endpoint in at least four consecutive 5-minute buckets — a cheap stand-in for "fixed cadence". False positives: dashboards that poll a serverless API. Tuning: allowlist known product backends by domain and user, and check byte patterns — C2 payloads are small and regular, page loads are not.

    SIG-003 · Long-lived access key used from a new network operator (identity)

    Mapping note: an ASN (autonomous system number) identifies the network operator behind an IP address. Build corp_asn_lookup from a free GeoIP/ASN feed and refresh it monthly; the two filtered values cover CI runners inside Amazon. False positives: travel and new integrations. Tuning: add your office and VPN provider ASNs, and page only when the key has been dormant for 90 days or the event list includes function or policy changes.

    SIG-004 · Non-browser process reaches a serverless vendor endpoint (TH-02)

    Mapping note: uses Sysmon Event ID 3 (network connection) with hostname logging enabled — turn on DNS query logging if your endpoints do not record hostnames. False positives: developers and approved tools. Tuning: keep the process allowlist per department, and combine with SIG-002 — a process hit plus proxy cadence on the same host is a confirmed C2 case, not a guess.

    Warning. Validate every rule in a test index before production, and record the validation result in the rule’s comments. A rule that has never fired in a test is a guess, not a detection.

    Real-world case study — Denonia (AWS Lambda)

    In 2022, researchers documented the first malware built specifically to run inside AWS Lambda. The case, named Denonia, is the cleanest public example of T1584.007: stolen cloud credentials, a deployed serverless function, and command-and-control hidden from cloud monitoring.

    Context

    Denonia is a small malware sample written in the Go language and packaged as a custom Lambda runtime. It was found running in cloud accounts whose owners did not deploy it. The attacker needed only one thing: valid AWS credentials for the account. How those credentials were obtained was never confirmed publicly — candidates include scanning for exposed keys, leaks, and info-stealer logs.

    Attack chain in short

    1. Attacker obtains AWS access keys for a victim account.
    2. Attacker deploys a Lambda function with a custom runtime carrying the Denonia binary.
    3. Malware resolves its C2 using DNS-over-HTTPS (DoH) — DNS lookups hidden inside normal HTTPS — to a domain the report calls Kyew, dodging cloud DNS monitoring.
    4. The payload runs inside the account and mines cryptocurrency on the victim’s budget.

    Timeline

    1. Early 2022
      Discovery. Lacework researchers spot unusual Lambda functions deployed in cloud accounts using compromised credentials. The binary inside is written in Go and carries the name Denonia.
    2. April 2022
      Analysis. Lacework publishes the findings: the first documented malware designed to run inside AWS Lambda, with C2 hidden in DNS-over-HTTPS queries to the Kyew domain so GuardDuty’s DNS monitoring sees nothing.
    3. April 2022
      Payload confirmed. The visible payload is cryptojacking — the function mines cryptocurrency using the victim account’s compute budget.
    4. Through 2022
      Industry response. Cloud security vendors add serverless runtime detections, providers repeat credential-hygiene guidance, and the case becomes the standard teaching example for T1584.007.

    Detection point

    Two signals together gave the case away. First, an unusual Lambda deployment: functions appeared in accounts with no history of serverless use, deployed by principals with no release activity. Second, DoH traffic from the serverless environment: the malware fetched DNS answers inside HTTPS, so the cloud’s DNS threat detection (GuardDuty) never saw the C2 domain. The lesson: monitor the deployment event itself, because the network part can be hidden.

    Response arc

    • Containment: rotate or disable the compromised credentials and delete the function, which cuts the C2 path at once.
    • Eradication: audit every key, role, and function the compromised principal could reach, and remove anything it created.
    • Recovery: check billing for abuse-driven costs and watch for redeployment from the same key material.
    • Impact: limited in this case — mining costs, no data theft reported — but a full proof of concept for serverless abuse.

    Impact and team response

    The direct financial impact was small, but the case exposed a monitoring gap: endpoint tools do not run inside Lambda, so nobody was watching the runtime. Response needed the cloud platform team, not only the SOC — someone who could rotate keys, delete functions, and read the audit trail. Teams that already sent cloud audit logs to the SIEM could answer "what else did this principal touch?" in minutes; teams without them had to reconstruct history from memory.

    Lessons learned

    • Serverless runtimes were a monitoring gap — treat functions as production infrastructure from day one.
    • Credential hygiene is the front door: long-lived keys without alerts are an open invitation.
    • Cloud-native detection is needed: audit log alerts plus cost alerts, not adapted endpoint tooling.
    • DNS-over-HTTPS defeats DNS monitoring — egress visibility must cover the HTTPS path too.

    Mitigation and defense

    ATT&CK lists only M1056 Pre-compromise for this technique, which honestly says: you cannot fully stop the abuse from inside your network. What you can do is make account takeover hard, see function changes fast, and limit what a malicious function can reach.

    Enterprise controls by layer

    Identity & keys

    • No long-lived keys: use OIDC federation — the pipeline logs in with short-lived tokens instead of stored keys — and short console sessions for people.
    • MFA on every cloud account; hardware keys for administrators.
    • Quarterly key review: find, rotate, or delete any static key still alive.

    Deploy pipeline & guardrails

    • Least-privilege deploy roles: scoped to named functions and regions, with PassRole denied.
    • CI/CD hardening: protected branches, signed commits, no secrets in build logs.
    • Guardrails — automatic rules an account must obey — enforced through service control policies and CSPM checks (CSPM tools audit cloud settings against policy).

    Monitoring & egress

    • Cloud audit alerts on function create and code update outside deploy roles.
    • Egress policy that also covers serverless vendor endpoints for servers and non-browser processes.
    • Cost anomaly alerts on Lambda and API Gateway spend.

    Response readiness

    • Function inventory with owners, tags, and expected traffic shape.
    • Saved abuse-report contacts for AWS, Microsoft, Google, and Cloudflare.
    • Practiced runbook: rotate keys → disable function → review logs → report.

    Home and small office

    • Turn on MFA for your cloud account, and never share one account between people — one account per person.
    • Do not keep long-lived access keys on laptops or in code folders; use short sessions from the console instead.
    • Set a billing alarm — a strange bill is often the first sign of abuse.
    • If you get an abuse notice from the provider, answer it quickly: your account may already be used against others.

    Response checklist — suspected serverless abuse

    • Rotate or disable the stolen access keys and revoke active sessions.
    • Delete or disable the malicious function and its public endpoint.
    • Review logs: who deployed, what else the principal touched, 90 days back.
    • Report the abuse to the cloud provider’s abuse team with evidence attached.
    • Check data access: what could the function’s role read — secrets, buckets, databases?
    • Hunt for beacons to the endpoint in proxy and EDR history; add indicators with confidence levels.
    • Confirm cost anomaly alerts are on, and file the incident record with the timeline.
