T1584.003Virtual Private Server

Attackers rarely pay for their own servers. With this technique they take over a Virtual Private Server that already exists — usually by stealing the cloud account that rents it — and then use that machine for staging, phishing, and command and control. This guide walks through the whole story and shows what defenders can see at every step.

Overview

This section explains the technique in plain words. It shows what a VPS is, why attackers steal one instead of renting one, and where the hijacked machine sits in an attack chain.

What the technique is

T1584.003 Virtual Private Server is a sub-technique of T1584 Compromise Infrastructure. A Virtual Private Server (VPS) is a virtual machine that a customer rents inside a provider data center. The renter gets a full server, a public IP address, and administrator access, usually for a few dollars per month.

This page covers the compromise angle. The attacker does not rent a fresh VPS with their own payment card. Instead, they take over a VPS that already exists. Most often this means stealing the cloud account that owns the machine — with phished passwords, stolen session cookies, or an access key bought from a criminal market. Once inside the account, the attacker can create new VMs, repoint the old ones, or quietly wait on a machine the real owner forgot about.

Why attackers like a hijacked VPS

  • Anonymity. The bill goes to the victim, not to the attacker. Payment trails lead nowhere.
  • Cheap. A stolen account is free. Even a paid VPS costs less than a coffee per month.
  • Fast spin-up. Cloud APIs create a ready VM in about one minute, in any region the account can reach.
  • Existing reputation. The IP address of a small business server is usually not on blocklists, so mail and C2 traffic blend in.

Where it fits in the attack chain

ATT&CK calls this stage Resource Development. It happens before the victim is involved. The hijacked VPS then supports many later steps:

  1. T1584.003 Compromise VPS
  2. Staging — host malware and phishing pages
  3. T1568 Dynamic Resolution — redirectors
  4. T1071 Application Layer Protocol — C2 beacons
  5. T1090 Proxy — SOCKS relay for intrusion traffic

One hijacked VPS can play several roles at once: malware host, command-and-control (C2) relay, proxy hop, and data drop location. That is why a single abused machine can serve a whole campaign from start to finish.

Compromise vs. rent (T1583.003)

Do not confuse this technique with T1583.003 Acquire Infrastructure: Virtual Private Server. In T1583.003 the attacker rents a VPS in their own name, or with a stolen card. In T1584.003 the attacker hijacks a VPS that already belongs to someone else — the account takeover is the defining step.

For defenders the difference matters little at detection time: both leave a server in a known provider range. But the response differs. A rented VPS is shut down by the attacker's own provider. A hijacked VPS has a real victim who must be told that their server, or their whole cloud account, was abused.

    The same story in words

    1. Steal a cloud account. The attacker phishes a small hosting customer and harvests the password or session cookie for their cloud account. SOC view: a phishing report arrives, and soon a login from a strange country shows up in cloud audit logs.
    2. Log into the hijacked account. The attacker signs in with the stolen credentials. No MFA stands in the way. SOC view: the audit log shows a login from a new country and a new network provider.
    3. Spin up the attack VM. With one API call the attacker creates a fresh virtual machine — the hijacked VPS — in a region the customer never uses. SOC view: a RunInstances event appears from an unknown IP address.
    4. Scan the target from the VPS. The new machine sweeps the target organization's servers for open ports and weak services. SOC view: a scan burst arrives from a known VPS provider range.
    5. Serve the lure. The VPS now hosts a malware file and a fake login page. A target employee clicks a link and connects. SOC view: the proxy log shows a user visiting a raw VPS IP address.
    6. Malware calls home. The downloaded implant beacons back to the VPS on a fixed schedule. SOC view: one endpoint connects to one external IP every 60 seconds, small and regular.
    7. Hands on keyboard. The attacker drives the implant through the VPS relay, so the operator's real location stays hidden. SOC view: a long, chatty TCP session to a VPS port appears in flow records.
    8. SOC shuts it down. Analysts flag the VPS range, block the IP, report abuse to the provider, and the provider suspends the VM. SOC view: the beacon goes dark, and the cloud tenant is locked down.

    Red team / hacker perspective

    This section explains how attackers and authorized red teamers look at VPS abuse. Everything here is described for education and defense only. Practice these ideas exclusively in your own isolated lab.

    Why a VPS works so well

    • Disposable. Burned infrastructure costs one API call to replace. Nothing is rebuilt by hand.
    • Re-deployable. Setup scripts and saved images turn a fresh VM into a live C2 node in minutes.
    • Geolocation choice. Attackers pick a region close to the target, so latency looks local and normal.
    • Reverse shells. A reverse shell is a connection from the victim machine back to the attacker. It needs a reachable public IP, and a VPS provides one on demand.

    How the takeover happens (conceptual)

    • Phishing the hosting customer. A fake provider login page steals the password or session cookie of a real cloud account.
    • Credential stuffing. Attackers replay username and password pairs from old breaches against hosting portals.
    • Misused free trials. New accounts burn trial credits; some providers ask for nothing more than an email address.
    • Stolen payment cards. Buying VPS with card data adds a fraud problem on top of the attack.

    All of these routes end the same way: an account that can create and control VMs, but does not belong to the attacker.

    Where the VPS is used

    • C2 relay. Implants beacon to the VPS, and the VPS forwards traffic to the operator.
    • Proxy. The VPS becomes a SOCKS or web proxy, so hands-on intrusion traffic comes from a clean address.
    • Staging. Tooling, malware, and phishing pages sit on the VPS until the campaign starts.
    • Bulletproof hosting. Some providers ignore abuse reports on purpose; attackers pay extra for that service.

    Prerequisites an operator needs

    • Stolen or created account credentials with compute permissions.
    • A region choice close to the target network.
    • Tooling staged as scripts or container images for fast setup.
    • A reputation check — is this IP already on blocklists?

    Skip the reputation check and the campaign can fail before it starts, because the fresh VM may already sit on a dozen blocklists.

    Lab only. Never point VPS-style tooling at systems you do not own. A safe practice setup is a local virtual machine that plays the "fake VPS", plus a firewall and Zeek logging on your own lab network. You get the same telemetry — flow records, beacon patterns, proxy hits — with zero legal risk.

    Variations and operator mistakes

    • IP reuse across campaigns. The same VPS IP in two campaigns lets defenders merge both cases into one.
    • Provider reputation lists. Cheap VPS ranges are heavily pre-flagged; some threat feeds list whole provider networks.
    • Missing log cleanup. Login history, session records, and billing alerts keep firing on a hijacked account — the attacker cannot remove them all.

    Every one of these mistakes is a gift to the defender. Watch for them in your own data.

    Blue team / SOC perspective

    Defenders cannot stop every stolen account on the internet, but VPS abuse leaves clear traces. This section shows where to look, which artifacts matter, and how to triage a hit.

    What gives you visibility

    • NetFlow and Zeek conn logs. Flow records show who talked to which external IP, when, and how much data moved. (A Zeek conn.log is a standard network connection log.)
    • Threat intel IP reputation. Feeds flag known VPS and bulletproof ranges, so one lookup enriches every alert.
    • Cloud audit logs. If your own accounts are the target, services like AWS CloudTrail record every login, VM, and API key.
    • Proxy logs. They show users or servers reaching raw VPS IP addresses instead of normal domains.

    Why it matters

    A hijacked VPS is the quiet part of most intrusions. It hosts the lure, receives the beacon, and relays the operator. If you watch egress traffic and cloud audit logs, you can catch the attack before it lands — or at least cut the relay when it does.

    Every blocked VPS IP and every suspended VM makes the next campaign slower and noisier for the attacker. Sharing what you find with the provider also protects everyone else using that network.

    Where to look first

    • Egress flow records toward external hosting networks.
    • Cloud audit events: RunInstances, CreateAccessKey, new console logins.
    • Proxy logs for raw-IP browsing from user subnets.
    • SIEM enrichment: map every external IP to its ASN before alerting.

    Fast triage checklist

    1. Check the destination IP against current reputation and ASN context.
    2. Identify the internal source: workstation, server, or cloud identity.
    3. Pull the session history — fixed intervals mean beaconing.
    4. Block with a tagged, expiring rule, then report to the provider.

    5.2 · Threat intelligence

    Good intel makes a VPS alert trustworthy. The sources below are ordered from free and automatic to slow and human. Wire at least the first three into the SIEM.

    Sources worth wiring in

    • IP reputation feeds. Daily lists of addresses seen in spam, malware, and C2 roles.
    • ASN intelligence. Context on provider networks — an ASN is one provider's block of IP space — so you can tell hosting from business or residential use.
    • abuse.ch Feodo Tracker and URLhaus. Free, fast lists of current malware C2 and payload addresses.
    • Vendor reports. Campaign write-ups often name the VPS ranges an actor uses.
    • CISA and national CERT advisories. Free and authoritative — the Volt Typhoon advisories (AA23-144A, AA24-038A) describe compromised VPS relay chains end to end.
    • Internal telemetry. Your own beacon and proxy history is the best labeled data you own.

    Confidence levels and how to act

    • High — several independent feeds or a vendor confirm it. Act quickly: block and hunt.
    • Medium — one feed or limited corroboration. Alert and investigate first.
    • Low — a single unverified sighting. Store it as context; do not block on it.

    Tag every block with the feed name and date, and give it an expiry. Intel that never expires turns into noise.

    5.5 · Sigma rules and Splunk SPL

    Four rules cover the top threats. The IP ranges shown are documentation ranges — swap them for the VPS and bulletproof ranges from your own intel feed. Each card has the Sigma rule, a matching Splunk query, and tuning notes.

    SIG-001 · AWS VM launched from an unusual country or IP (TH-01/TH-05)

    Mapping note: CloudTrail records every control-plane action, so the rule needs no agents. False positives: traveling admins and new regional offices. Tuning: keep the home-country allowlist in a lookup table, add a first-time-in-this-region condition, and page only when the caller is a human identity rather than an automation role.

    SIG-002 · Endpoint connects to a known VPS or bulletproof range (TH-02/TH-06)

    Mapping note: Sysmon Event ID 3 logs outbound connections, which pairs well with the blocklist lookup. False positives: approved services hosted in these ranges. Tuning: store the VPS and bulletproof ranges in a threat-intel lookup with an expiry date, suppress known-good destinations, and escalate any hit from a server identity immediately.

    SIG-003 · Beacon-like cadence to a single external IP (TH-02)

    Mapping note: the Sigma aggregation counts hits per client, while the SPL version adds bucket counts, which is the stronger rhythm signal. False positives: backups, update mirrors, and scheduled syncs. Tuning: require at least six buckets within one hour, keep the destination restricted to VPS ranges from your feed, and allowlist scheduled jobs by user agent.

    SIG-004 · New access key followed by unusual region use (TH-01)

    Mapping note: both halves of the pattern live in the same CloudTrail log, so one rule covers them and the SPL query joins the events per user. False positives: planned global rollouts. Tuning: list only the regions your teams never use, alert on CreateAccessKey for human accounts only, and check whether the new key is used within 24 hours.

    Warning. Validate every rule in a test index before production, and record the validation result in the rule's comments. A rule that has never fired in a test is a guess, not a detection.

    Real-world case study — Volt Typhoon's compromised VPS relay chain

    Volt Typhoon is a state-sponsored group that ATT&CK lists directly under T1584.003: "Volt Typhoon has compromised Virtual Private Servers (VPS) to proxy C2 traffic." CISA's advisories (AA23-144A, June 2023, updated AA24-038A, February 2024) describe how the group chained compromised SOHO routers and VPS machines between its operators and target networks in critical infrastructure — communications, energy, water, and transport.

    What happened, step by step

    Volt Typhoon's goal was pre-positioning: quiet access into networks that run critical services, held ready for later use. To reach targets without revealing a home base, the group rented nothing under its own name. It took over other people's infrastructure — home routers and VPS machines — and used them as relay hops, one after another, until the trail went cold.

    • 2021 onward — targeting

      Activity begins against communications, energy, water, and transport organizations, mostly in the United States and its territories (per CISA).

    • Infrastructure building

      The group compromises edge devices and VPS accounts and chains them into proxy networks. Public reporting (June 2023) documents a botnet of small-office routers used purely as operational infrastructure — the official T1584.008 and T1584.003 patterns working together.

    • June 2023 — CISA advisory

      CISA publishes AA23-144A with detection guidance after the router botnet is discovered.

    • February 2024 — updated advisory

      AA24-038A confirms the group also uses compromised VPS to proxy C2, and documents the KV Botnet implant on end-of-life Cisco and NETGEAR routers.

    • Throughout — hands-on access

      Inside targets, operators use built-in administration tools instead of malware, so endpoint antivirus sees almost nothing. The visible trail is in network flows and odd use of normal tools.

    The attack chain

    1. Edge device or VPS account compromised
    2. Relay chain built (VPS + SOHO routers) (T1584.003 / T1584.008)
    3. C2 traffic proxied through the chain
    4. Initial access into the target network
    5. Built-in admin tools used for hands-on activity
    6. Access held quietly for later use

    Note the division of labor: the VPS and routers are Resource Development — attack infrastructure assembled before the intrusion — while the hands-on activity lands in later tactics. Watching the infrastructure layer catches the attack before the target's name appears in it.

    Detection point

    Because the implants keep to living-off-the-land tradecraft, the strongest signals are in egress and device logs: servers or edge devices reaching VPS and hosting ranges they never touched before, admin tools used at unusual hours or from unusual hosts, and management logins on routers from unexpected addresses. CISA's guidance also points to small, periodic relay sessions and certificate or fingerprint oddities on otherwise normal-looking traffic.

    Response arc

    • Containment: block the VPS and router indicators at the egress firewall, isolate affected edge devices, and preserve flow records before anything changes.
    • Eradication: hunt for built-in-tool abuse (unusual admin-tool chains, odd account use), rotate all edge and administrative credentials, and reflash or replace compromised devices — reboots do not remove firmware-level implants.
    • Recovery: deploy egress allowlists for servers and edge devices, raise logging on management planes, and share indicators with CISA and your ISAC so peers can hunt the same chain.

    Impact and communication

    No single victim saw data destroyed or encrypted. The impact was strategic: a capable adversary holding quiet access inside critical infrastructure, with the groundwork for future disruption. For the owners of the hijacked VPS and routers, the impact was being turned into unwitting accomplices — their addresses appeared in federal advisories and their resources ran attacker traffic. Communication flowed through CISA advisories and sector ISACs rather than per-victim disclosures, because the shared lesson mattered more than any single incident.

    Lessons learned

    • Watch where traffic goes, not just where it comes from. The relay chain is visible in egress flows to hosting ranges you never use.
    • Baseline normal admin-tool use. Living-off-the-land tradecraft hides from antivirus but not from a good baseline.
    • End-of-life devices are soft infrastructure. Retire or segment them before someone chains them into a proxy network.
    • Share and consume advisories. CISA and ISAC reporting named the exact ranges and behaviors that made hunting possible.
    • Reboots are not cleanup. Firmware-level implants survive restarts — reflash or replace.

    Mitigation and defense

    You cannot stop an attacker from renting or stealing a VPS elsewhere on the internet. You can make the abuse fail against you: protect the accounts that own cloud machines, control what leaves your network, and know who to call.

    Protect cloud accounts

    Put MFA on every console identity — phishing-resistant methods are best — and give each person only the permissions they need. Most T1584.003 chains die at the stolen login.

    Alert on cloud changes

    Audit new VMs (RunInstances), new access keys, logins from new countries, and unused regions. These are low-noise alerts in a small tenant, with high value.

    Control egress

    Use allowlists on servers, block raw-IP browsing from user subnets, and force updates through a proxy. A beacon needs an open door out of your network.

    Enrich with IP reputation and ASN data

    Map every external IP in the SIEM to its provider network. Alerts like "server talks to a hosting ASN" fall out of one lookup table.

    Watch geo anomalies

    Logins from countries you never do business with, and regions your teams never deploy into, deserve a fast look. Cheap signal, early catch.

    Prepare the response runbook

    Keep provider abuse contacts, evidence templates, and pre-approved blocking steps ready. A clean report with timestamps gets a VM suspended within hours.

    Home and small office. Turn on MFA for your hosting and cloud accounts today. Watch billing alerts for machines you did not create, and report anything strange to your provider — good providers act fast on abuse reports. A low-cost DNS filter also blocks most VPS-hosted phishing before anyone clicks.

    Habit cadence for the team

    Daily

    • Review cloud control-plane alerts: new regions, new keys, new VMs or functions.
    • Triage egress anomalies from servers and edge devices.

    Close the whole loop: endpoint, cloud account, and network belong to one case.

    Weekly

    • Refresh intel-driven blocks; every block carries a source, a date, and an expiry.
    • Check that ASN, country, and reputation enrichment still lands inside alerts.

    Enrichment must be automatic — manual lookups never happen at 03:00.

    Monthly

    • Rotate stale keys and review IAM for over-privileged identities.
    • Expire or re-own old blocks so they never become silent breakage.
    • Run one hijack-chain tabletop: account → VPS → C2 → cleanup.
    9

    Cheat sheet and quick reference

    One screen for the 03:00 analyst: key facts, the alerts that matter most, a response checklist, and the links to keep in the runbook.

    Key facts

    • T1584.003 means hijacking an existing VPS or its cloud account — not renting one (that is T1583.003).
    • Main routes: phished hosting customer, credential stuffing, stolen sessions, free-trial abuse.
    • Roles on the box: staging, C2 relay (T1071, T1568), SOCKS proxy, phishing host.
    • Best signals: cloud audit events, egress beaconing, ASN reputation.

    Top detections

    • SIG-001 — VM launched from an unusual country or IP (critical).
    • SIG-002 — endpoint connects to a known VPS or bulletproof range (high).
    • SIG-003 — beacon-like cadence to one external IP (medium).
    • SIG-004 — new access key plus unusual region use (high).

    Response checklist

    • Confirm the external IP against current reputation and ASN context.
    • Block the IP at egress points with a tagged, expiring rule.
    • If the hijacked account is yours: revoke sessions, rotate keys, review IAM.
    • If the VM is yours: snapshot for evidence, then stop it.
    • Report abuse to the provider with timestamps, IPs, and samples.
    • Hunt the whole VPS range, not just the one address.
    • Search proxy, flow, and EDR logs for past beacons to that IP.
    • Record the case: feed source, dates, actions, provider ticket ID.
