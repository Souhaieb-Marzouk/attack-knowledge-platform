T1584.002DNS Server

Every visit to a website starts with a question: which server is behind this name? DNS servers answer that question, and this guide covers what happens when an attacker takes one over. A single wrong answer can silently send every user of that server to a fake website — no email, no malware, and no obvious warning.

Overview

This section explains DNS server compromise in plain words, why it is dangerous even though nothing looks broken, where it sits in an attack, and how it differs from hijacking a domain (T1584.001).

What this technique is

DNS (Domain Name System) is the address book of the internet: it turns names like example.com into the IP addresses that computers really contact. T1584.002 DNS Server means an attacker takes control of a machine that answers those questions and changes what it says.

Two kinds of servers matter. A recursive resolver looks up answers on behalf of users — companies and internet providers run them. An authoritative name server holds the official records for one domain. Whoever controls either kind decides where users really go.

Why it matters to defenders

The redirection is silent. The user types the correct address, the browser still shows the correct name, and only the underlying IP address is wrong. There is no email to catch and no file to scan.

The blast radius is also large. One compromised corporate resolver feeds answers to thousands of laptops. One poisoned authoritative server spreads further, because other resolvers remember (cache) the false answer for its whole lifetime. So detection must compare answers, not only watch queries.

Where it fits in the attack chain

ATT&CK places this technique in Resource Development, the stage before the victim is involved. The hijacked DNS server then quietly supports the next steps:

  1. T1584.002 DNS Server hijack
  2. T1566 Phishing (fake site is ready)
  3. T1557 Adversary-in-the-Middle (harvest logins)
  4. T1568 Dynamic Resolution (fast-changing answers)
  5. T1071.004 DNS (C2 over DNS)

A hijacked resolver can also hide the true location of command-and-control (C2) servers: the malware asks the trusted resolver for a name and receives the address the attacker wants, and the attacker can change that address at any moment.

DNS server vs. domain — the T1584.001 difference

Keep the two sibling techniques apart, because their evidence and fixes differ. T1584.001 Domains is about owning or hijacking the name itself — for example by stealing a registrar account or changing the nameserver records that say where a domain is hosted. T1584.002 DNS Server is about attacking the machine that answers the lookups.

Both end in false answers for users. But the domain version leaves changes at the registrar and in nameserver records, while the server version leaves changes on the DNS server itself — in zone files, resolver configuration, and answer logs. You defend the domain with registrar security; you defend the server with patching, admin lockdown, and answer monitoring.

    The same story in words

    1. Find a weak DNS server. The attacker scans the internet for an exposed DNS admin panel or an old, unpatched resolver. SOC view: scanning of port 53 and admin pages from an unknown network.
    2. Abuse weak admin credentials. A default or reused password, or an old bug, hands the DNS server to the attacker. SOC view: an admin login from a new device or country.
    3. Rewrite the zone record. The A record of the brand domain now points to an attacker-controlled IP address. SOC view: a zone serial change with no matching change ticket.
    4. The laptop asks for the domain. An employee opens the bank or vendor site, and the laptop sends a normal DNS query to the corporate resolver. SOC view: nothing unusual — the question looks perfectly normal.
    5. A false answer comes back. The compromised server replies with the attacker's IP address instead of the real one. SOC view: the answer differs from a trusted public DoH resolver.
    6. The user lands on the fake site. A certificate warning appears, or a perfect copy of the site asks for login details. SOC view: certificate mismatch reports and user complaints.
    7. Harvest and continue. The attacker saves the submitted passwords and can now log in as the victim. SOC view: impossible-travel logins right after the DNS anomaly.
    8. SOC detects and restores. The team cross-checks with a secondary DoH resolver, blocks the attacker address, and restores the correct records. SOC view: the false answers stop and the case opens.

    Red team / hacker perspective

    This section explains how attackers think when they target DNS servers. Everything here is described for education and defense only — no exploit steps, no code. Practice these ideas exclusively against servers inside your own isolated lab.

    Why attackers target DNS servers

    Scale first. One company resolver answers for every laptop and server on the network. One authoritative server answers for a whole brand. Change one record once, and the attacker reaches thousands of users without sending a single phishing email.

    Stealth second. DNS answers are trusted by default. The browser address bar still shows the real name, so victims see nothing wrong. There is no attachment for a mail filter to catch. For the attacker, a hijacked resolver is also a stable asset: it stays in place inside the target's network, while rented servers get blocked and replaced.

    How takeover happens (conceptual)

    • Exposed admin panels: management web pages or control channels left reachable from the public internet.
    • Weak or default credentials: shared passwords, vendor defaults, or passwords reused from old leaks.
    • Vulnerable versions: resolvers with known, unpatched security bugs in the service itself.
    • Unpatched or forgotten resolvers: appliances and VMs that nobody owns and nobody updates.
    • Weaker upstream hops: forwarders and hosted provider accounts that inherit the attacker's control.

    Where the technique applies

    • Corporate resolvers: the internal DNS servers every workstation uses. Highest value inside a company.
    • ISP resolvers: the default resolvers of an internet provider. One change hits many homes at once.
    • Authoritative servers for brands: where a company's public records live, often at a hosted provider. Attackers target both the provider's panel and the servers themselves.

    The common thread is position: the attacker does not need your password or your laptop. Sitting on the path between users and the internet is enough.

    Prerequisites an attacker needs

    • Network reachability to the admin interface or the vulnerable service.
    • Valid credentials or a working exploit for the DNS software.
    • Knowledge of which zones and records matter (names of the victim brand's domains).
    • A place to send users — a server that imitates the real site or accepts the redirected traffic.
    • A quiet window: no alerting on zone changes, no cross-checking of answers.

    Notice that four of the five prerequisites are defensive failures — reachability, credentials, patching, and monitoring. Remove one and the technique usually fails.

    LAB ONLY — never touch DNS you do not own. Redirecting real users or real domains is illegal in most countries and can turn into a mass incident, because DNS changes spread to caches. Do all DNS exercises inside an isolated virtual network with fake domain names, and never point lab resolvers at production records.

    A safe lab exercise

    • Set up an isolated lab VM and install a resolver such as Unbound or BIND on it.
    • Create a private test zone (for example lab.example) with one A record.
    • Query it from a second lab VM and confirm the answer.
    • Change the record through the admin tool, then observe the query log and the zone serial number increasing.
    • Try a zone transfer request against the lab server and watch how the log records it.
    • Now enable logging of every change and every transfer — this is exactly the telemetry your SOC needs.

    The goal is not the trick itself. The goal is to learn which logs fire when a record changes, so you can build alerts on them.

    Variations attackers use

    • Zone poisoning: editing the zone file or record set directly on the server, as in the simulation.
    • Forwarder abuse: changing the resolver's upstream forwarder to an attacker-controlled resolver, so every unknown name goes through the attacker.
    • Cache-only poisoning: using old software bugs to insert false answers into the cache without touching config.
    • Open-resolver abuse: using someone else's open resolver to answer victims' queries with chosen data.

    Mistakes in exercises

    • Leaving a lab admin interface reachable after the test ends.
    • Changing records without a ticket, then losing track of what was touched.
    • Forgetting to restore the original zone or to lower the cache time (TTL) afterwards.
    • Not writing down the test window, so the SOC investigates a ghost.

    Blue team / SOC perspective

    Defenders cannot stop every hijack on the internet, but a poisoned DNS server leaves surprisingly clear marks. This section shows where the visibility comes from, which artifacts to hunt for, where to look first, and a short triage flow.

    Where visibility comes from

    • DNS server logs: BIND query and zone logs, Windows DNS Server audit/analytical logs, Unbound logs. They show changes, transfers, and unusual answer patterns at the source.
    • Zeek dns.log on the wire: a passive sensor records every question and every answer on the network — the answer field is the important one here.
    • Resolver query logs: cloud and hosted DNS providers (and managed resolvers) can stream per-query logs with answers.
    • Passive DNS cross-check: passive DNS databases keep the long-term history of which answers a domain normally returns, so a sudden change stands out.
    • Certificate signals: browsers, pinning plugins, and users report certificate mismatch warnings — often the first human-seen sign of redirection.

    Artifacts a DNS hijack leaves behind

    ArtifactWhat it looks likeWhy it matters
    Unexpected A-record answersA known domain now resolves to an IP outside the owner's networks, often with a short TTLThe core signature of the technique; nothing else needs to happen for harm to start
    New zone transfer (AXFR) requestTCP connection to port 53 asking for the whole zone, from an unknown sourceReconnaissance — the attacker is mapping your records, often right before a change
    Config or zone change without a ticketZone serial number jumps, new records appear, no change record existsDirect evidence of tampering on the server itself
    Certificate mismatchBrowser or pinning reports a wrong certificate on a brand domainThe fake site almost never has the real certificate; this is the human-scale alarm
    Resolver config editsForwarders, allowlists, or logging settings change outside maintenance windowsAttackers redirect upstream paths or blind the logging first

    Where to look first

    • Pull the zone-change history of your brand domains for the last 30 days and match each change to a ticket.
    • Compare answers from your resolver with a trusted second resolver (a DoH service works well) for your top 500 domains.
    • Search Zeek dns.log for answers that fall outside the owner's known networks.
    • Check AXFR/IXFR attempts against your authoritative and internal servers.
    • Review admin logins on the DNS servers themselves for new devices, countries, or hours.

    Why this matters to the SOC

    A DNS hijack is one of the few attacks where the victim's own endpoint logs stay completely clean. The laptop did nothing wrong; it just believed its resolver. That is why queries-only dashboards miss the whole technique.

    It also multiplies every other threat. Fake sites make phishing more convincing, and hijacked answers can hide C2. When your brand domain redirects wrongly, your customers are the victims, so the incident may belong to you even though the hijacked server belonged to someone else.

    Short triage checklist — suspected DNS redirection

    • Confirm the anomaly: query the same domain from your resolver and from an independent DoH resolver.
    • Record the false answer (IP, TTL, timestamp) before caches change; capture the Zeek record if available.
    • Identify the path: is your resolver poisoned, or is the authoritative side serving false answers?
    • Check zone-change and admin-login logs on the affected servers for the last change window.
    • If your server is compromised: block attacker ranges, restore records from a known-good copy, and rotate admin credentials.
    • If another party's server is poisoned: notify the owner and the registrar, and protect your users by pinning or blocking the fake address.
    • Open the incident record and warn users to treat certificate warnings on the brand domain as real.

    5.2 · Threat intelligence

    Much of this technique happens outside your network, so external intelligence does real work here. A simple pipeline: collect signals, analyze them against your domains and resolvers, apply the result to detections and blocks, then review what helped.

    Sources worth wiring up

    • MITRE ATT&CK: the T1584.002 page and its citations describe documented DNS server abuse.
    • Passive DNS + DoH cross-validation: passive DNS history shows normal answers; querying a trusted DoH resolver shows what the world sees right now. Comparing both catches poisoned paths.
    • Vendor reporting: Cisco Talos, ESET, Microsoft, Mandiant and CERT blogs publish DNS hijack campaigns and indicators.
    • OSINT scanning: Shodan and Censys expose resolvers with open admin panels; urlscan.io and crt.sh show where brand names really resolve.
    • ISACs: sector sharing groups push fast alerts when members see hijacks targeting your industry.
    • Internal telemetry: your own DNS server audit logs and answer comparisons — the highest-signal source you own.

    Confidence levels that work

    Tag every indicator with a confidence level and keep the meaning strict:

    • High: confirmed by two independent sources or by direct observation in your own logs.
    • Medium: one reliable source, no second confirmation yet — good for detection and hunting, not for blocking.
    • Low: rumor, paste-site claim, or machine-only correlation — hunt lists only.

    Write the level into the indicator record so the analyst who meets it at 03:00 knows how much to trust it — and whether they may block it.

    5.5 · Sigma rules and Splunk SPL

    The four rules below cover the highest-value threats (TH-01, TH-02, TH-05 and the tunnel/exfil pair TH-03/TH-04). Each Sigma rule is valid YAML and is followed by a matching Splunk query, a mapping note, and tuning advice. Replace index and sourcetype names with your local naming — the field assumptions are stated under each query.

    SIG-001 · Brand domain resolves outside expected networks (TH-01, TH-02)

    Mapping note: the logsource is Zeek dns.log shipped as JSON; answers is a multi-value field, so the SPL takes the first answer and cidrmatch checks the expected ranges. False positives: planned migrations and CDN changes — update the range list through the same change process as the DNS records themselves. Tuning: keep the domain list in a lookup table, and raise the answer list from passive DNS history so new attacker networks never pass by default.

    SIG-002 · NXDOMAIN flood or DGA-like names from one client (TH-03, TH-04)

    Mapping note: Sigma's aggregation counts matching events per client (id.orig_h); the SPL mirrors it with stats by plus a threshold. False positives: buggy retry loops and monitoring agents. Tuning: baseline one normal week, set the count a little above the busiest benign client, and exclude the resolver's own health-check names.

    SIG-003 · Zone transfer attempt or admin path to port 53 (TH-05)

    Mapping note: the logsource is Zeek conn.log (network connections); normal UDP lookups never match because the rule requires network_transport: tcp. False positives: monitoring probes and forgotten secondary resolvers — add them to the admin CIDR list. Tuning: pair this with the DNS server's own security log; an allowed transfer from a rogue source is worse than a denied one, so alert on successful transfers from outside the secondary list as critical.

    SIG-004 · Client bypassing the internal resolver (TH-02 follow-up)

    Mapping note: the logsource is the perimeter firewall; the count threshold keeps one-off bursts quiet and surfaces repeat offenders. False positives: devices with a policy exception — keep the exception list next to the rule. Tuning: also alert on denied attempts separately, because a deny followed by silence often means malware moved on to DoH; combine with proxy logs for that case.

    Real-world case study — Sea Turtle (2019–2021)

    Sea Turtle is the name Cisco Talos gave a group that ran DNS hijacking at registrar scale against government and infrastructure organizations. ATT&CK's official procedure for T1584.002 is exactly what Talos described: Sea Turtle "modified Name Server (NS) items to refer to Sea Turtle-controlled DNS servers to provide responses for all DNS lookups." Talos reported roughly 40 affected organizations across about a dozen countries — national security agencies, ministries, energy organizations, and internet providers.

    What happened, step by step

    The attackers did not hack the victims' servers. They hacked the path: registrar and DNS-provider accounts. With those accounts they rewrote Name Server records, so every resolver on the internet asked the attacker's servers for answers. Valid TLS certificates then made the redirection invisible.

    • 2016–2018 — quiet build-up

      Later reporting pushed Sea Turtle activity back to at least 2016. The group studied how target organizations ran their domains, registrars, and DNS providers.

    • Early 2019 — registrar access

      Phishing and stolen credentials gave the group control of accounts at registrars and DNS providers used by the targets.

    • Spring–Summer 2019 — NS rewrite

      Name Server records for victim domains were changed to Sea Turtle-controlled DNS servers. From that moment, every lookup for those names went to the attacker first — the official T1584.002 pattern.

    • Days later — valid certificates

      Because the attacker now answered the domain-control checks, certificate authorities issued valid TLS certificates for the hijacked names. Browsers showed padlocks, not warnings.

    • Following weeks — silent interception

      Web and mail traffic was copied on the way through. Users "logged in normally" to perfect copies; the group harvested credentials and session cookies. The goal was intelligence collection, not money, and most victims noticed nothing.

    • October 2019 — disclosure

      Talos published the "Sea Turtle" report. CISA later released a malware analysis report (April 2020) covering the group's tooling.

    • 2020–2021 — return

      Researchers documented renewed activity ("Teal Kurma", PwC, July 2021) using similar registrar-first tradecraft against a similar audience.

    The attack chain

    1. Registrar / DNS provider account takeover
    2. NS records rewritten to attacker DNS (T1584.002)
    3. Domain-control checks answered by attacker DNS
    4. Valid TLS certificates issued for hijacked names
    5. Web and mail traffic intercepted with valid encryption (T1557)
    6. Credentials and session cookies collected

    This is a full adversary-in-the-middle supply chain, and every stage lives in Resource Development except the final collection. That is why a change at one registrar account can silently affect an entire organization.

    Detection point

    The highest-value signals were all external to the victim: an NS change at the registrar, a new certificate for a corporate domain in Certificate Transparency, and a certificate issued by an unusual authority. Inside the network, TLS inspection or pinning catches a proxy that holds a cert the client never saw before, and DNSSEC-aware resolvers reject the false answers. The victims who detected Sea Turtle fastest were the ones watching their own name's certificate and NS history, not just their own networks.

    Response arc

    • Containment: restore the correct NS records through the registrar, lock the compromised registrar accounts, and revoke the fraudulent certificates through the issuing CAs.
    • Eradication: audit every DNS record for hidden edits (MX, TXT, subdomains), remove attacker mail forwarding, reset all registrar and DNS-provider credentials, and invalidate sessions that may have been captured.
    • Recovery: add registry lock and CAA records, enforce hardware MFA on registrar accounts, consider DNSSEC, and re-issue certificates with tighter validation; users re-authenticate everywhere because session cookies must be assumed stolen.

    Impact and communication

    Impact was espionage-grade: credentials, mail content, and session access across government and critical-infrastructure organizations — with no malware on any victim server and no downtime to alert anyone. Affected organizations worked through national CERTs and the CAs to unwind the hijack quietly. Communication was deliberately low-key; the priority was restoring the true DNS path before attackers re-registered the access they had lost.

    Lessons learned

    • Your DNS is a supply chain. The registrar, the DNS provider, and the CA are all part of your attack surface.
    • Watch answers and certificates, not only queries. Monitors on NS changes, CT logs, and issuing CAs catch this class early.
    • Registry lock and CAA records are cheap insurance. They block exactly the two moves Sea Turtle relied on.
    • Assume sessions are stolen after any on-path event. Short session lifetimes and phishing-resistant MFA limit the reuse of harvested cookies.
    • Certificate warnings matter, but padlocks can lie. A valid certificate on a hijacked path is worse than an obvious warning — monitor issuance, not just browser signals.

    Mitigation and defense

    ATT&CK lists only M1056 Pre-compromise for this technique, which honestly says: you cannot fully prevent DNS hijacking from inside your network. What you can do is make the takeover hard, make the false answers visible, and limit what a hijacked resolver can do.

    Enterprise controls by layer

    Registry, registrar & admin path

    • Registry lock on brand domains, and hardware MFA on the registrar and hosted-DNS accounts that manage them.
    • Restrict DNS administration: management interfaces only from a VPN or bastion, never from the internet.
    • Named owners for every DNS server and zone; every change needs a ticket and dual approval.

    Resolver hardening

    • Patch resolvers (BIND, Unbound, Windows DNS, appliances) on a fixed clock — they are internet-facing services too.
    • Enable DNSSEC validation where possible, and sign your own authoritative zones.
    • Disable recursion toward the internet and refuse AXFR to everyone except listed secondaries.

    Trusted resolution paths

    • Point clients at known internal resolvers, and use DoT/DoH to trusted upstream resolvers so answers are authenticated in transit.
    • Run a secondary DoH resolver and cross-check answers for critical domains on a schedule.
    • Keep a known-good copy of your zones so records can be restored in minutes.

    Network & monitoring controls

    • Egress control: allow outbound port 53 only to your resolvers (SIG-004), which also kills DNS tunnels to arbitrary servers.
    • Ship DNS server audit logs, query logs, and Zeek dns.log into the SIEM; run the Section 5.5 rules.
    • Alert on zone serial changes, AXFR attempts, and certificate mismatch reports for brand domains.

    Home and small office

    • Change the default password on your router — attackers have hijacked home routers just to change their DNS settings.
    • Review the router's DNS settings: set them to trusted resolvers (or "automatic" from a provider you trust) instead of unknown values.
    • Turn off remote administration of the router unless you truly need it, and enable firmware updates.
    • Never click through a certificate warning on a banking or wallet site. Close the tab and investigate.

    Response checklist — suspected DNS server compromise

    • Confirm with two resolvers: your own and an independent DoH service; record both answers with TTLs.
    • Freeze evidence: Zeek records, zone-change logs, admin-login logs, screenshots of the fake site.
    • Identify the path — your resolver poisoned, your authoritative server, or an upstream provider.
    • If your server: block attacker ranges, restore records from the known-good copy, rotate admin credentials, flush caches.
    • If upstream: notify the owner and provider, and pin or block the false address for your users meanwhile.
    • Scope: search 90 days of logs for the false IP and the affected domains; look for credential reuse from the fake site.
    • Warn users: certificate warnings on the brand domain are real until this case closes.
    • File the incident record with the timeline and evidence links.
