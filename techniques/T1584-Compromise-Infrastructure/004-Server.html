T1584.004Server

Attackers love free infrastructure. Instead of renting a server, they break into one that already belongs to somebody else — a small company website, a mail server, or a forgotten admin panel — and quietly repurpose it. The stolen server hosts phishing pages, passes out malware, and relays attacker traffic, all while wearing its innocent owner's name. This guide explains the whole technique in plain words and shows the detections that catch it.

Overview

This section explains technique T1584.004 in plain words: what a "compromised server" is, why attackers want one, and how it connects to the rest of an attack.

What the technique is

T1584.004 Server means an attacker takes over a server that belongs to somebody else and uses it to prepare an attack. The victim of the takeover is usually a real organization: a small business website, a community forum, a mail server, or an old server used to stage VPN access.

After the takeover, one hijacked server can play several roles at the same time:

  • Phishing host — it serves fake login pages that look trustworthy.
  • Malware drop — it stores the malicious files that victims are tricked into downloading.
  • C2 relay — "C2" means command and control. The server passes traffic between infected computers and the attacker, hiding where the attacker really is.
  • Staging area — it holds tools and stolen data between attack steps.

Why attackers hijack servers

Why not simply rent a cheap server? Three reasons:

  • Reputation inheritance. A server that has hosted a real website for years has a clean history. Spam filters, web filters, and security tools judge it by its past, so malicious content on it gets a free pass.
  • Cost. A hijacked server is free. The real owner pays for the hosting, the bandwidth, and even the TLS certificate that keeps the padlock icon green.
  • Takedown resistance. When defenders report a rented server, the hosting provider shuts it down quickly. When the same content sits on an innocent school's server, removal is slow and the attacker has already moved on.

Where it fits in the attack chain

ATT&CK places this technique in the Resource Development tactic. It happens before the attacker touches the final target. The compromised server then supports the later steps:

  1. T1584.004 Server (hijack and repurpose)
  2. T1566 Phishing (the server hosts the lure)
  3. T1505.003 Web Shell (the server keeps access open)
  4. T1071 Application Layer Protocol (the server relays C2)
  5. T1041 Exfiltration Over C2 Channel (data leaves through it)

A web shell is a hidden page on a web server that gives the attacker a command console inside the browser. It is both the most common way to keep a hijacked server and a strong detection signal on its own.

Server (T1584.004) vs VPS (T1584.003)

These two sub-techniques look similar but are different:

  • T1584.003 Virtual Private Server (VPS): the attacker takes over a cloud account or reseller account and uses it to spin up servers the attacker controls from the start. The servers are new and belong to the attacker's stolen identity.
  • T1584.004 Server: the attacker breaks into a server that is already running for a real owner. The server keeps its domain, its certificate, its mail history, and its place in other people's trust lists.

The practical difference for defenders: a hijacked VPS is a new malicious asset, while a hijacked server is a trusted asset that turned bad. Trusted assets need different detections — you must notice behavior change, not just newness.

    The same story in words

    1. Scan for an outdated web app. The attacker scans the internet for a web server running an old CMS or an outdated plugin. SOC view: probe requests hit /wp-admin and version files from an unknown address.
    2. Exploit the plugin. A file-upload flaw in the plugin is abused and a web shell lands on the server. The server is now compromised. SOC view: the WAF logs the exploit and a new file appears in the web root.
    3. Stage phishing and malware. The attacker uploads a fake login page and malware downloads to the trusted server. SOC view: FIM flags new files; EDR sees the worker process writing them.
    4. Point the domain, send the emails. A domain the attacker controls is pointed at the server, and phishing emails carry links to it. SOC view: a fresh TLS certificate shows up in CT logs for that domain.
    5. Employee opens the lure. A target employee clicks the link and sees a convincing fake login page on a trusted-looking site. SOC view: the mail gateway quarantines a copy and flags the link.
    6. Credentials harvested. The employee submits the form; the POST goes to the web shell domain and the password is saved. SOC view: a failed real login follows soon after.
    7. Relay through the server. Stolen data and malware beacons pass through the hijacked server toward the attacker. SOC view: the server sends small uploads to a network it never used before.
    8. SOC responds. Analysts connect the web shell POST and the worker-process alert, block the attacker domain, remove the shell, and patch the plugin. SOC view: the route is cut and the server is cleaned.

    Red team / hacker perspective

    This section explains how attackers think when they hunt for and reuse other people's servers. Everything here is described for education and defense only. Practice these ideas exclusively in your own isolated lab.

    Why a stolen server beats a rented one

    A red team picks a hijacked server when trust matters more than control:

    • Trusted IP address. The server sits in the address range of a real company or hosting brand. Firewalls and reputation lists have no reason to distrust it, unlike the crowded ranges of known "bulletproof" hosts.
    • Existing TLS certificate. The site already has a valid certificate, so the browser padlock stays green. An attacker can also issue a free new certificate for a domain they control, pointed at the same server.
    • Mail reputation. A mail server that sent normal mail for years passes spam filters more easily than a fresh one. This is why hijacked mail servers are prized for phishing.
    • Content history. The domain has real pages, backlinks, and age — all things that security scoring treats as "good".

    How the takeover happens (conceptual)

    • Unpatched web apps: old CMS versions and vulnerable plugins — especially file-upload and file-manager plugins — are the classic way in.
    • Weak admin panels: default or reused passwords on hosting panels, routers, and admin portals.
    • Abandoned servers: machines nobody maintains or pays attention to still serve traffic. Nobody patches them and nobody reads their logs.
    • Plugin supply chain: a tainted plugin or theme update installs the attacker's code on many servers at once — the owner essentially delivers the web shell.
    • Stolen credentials: reused passwords or leaked keys for SSH, FTP, or panel logins.

    Where it applies and what it needs

    Lab practice that stays legal

    You can safely experience both sides of this technique in an offline lab:

    1. Deploy a training virtual machine with a deliberately vulnerable web app, such as a DVWA-style image. DVWA ("Damn Vulnerable Web Application") is a learning app built to be broken.
    2. Run nginx or IIS in a second lab VM as your "production" server.
    3. Practice the file-upload exploit on the training VM only, then replay the same request patterns against the lab server to study the logging.
    4. Watch the nginx/IIS access logs, Windows audit logs, and file changes while you repeat each step. Compare what the WAF would see with what plain logs show.
    Lab only. Never scan, exploit, or log into systems you do not own. Testing a technique against a real third-party server is illegal in most countries, even as a "good deed".

    Variations and attacker mistakes

    • Variation — long-dwell relay: the attacker keeps the server quiet for months and uses it only briefly per campaign, sending small, periodic traffic to stay under thresholds.
    • Variation — quick staging: the opposite style — upload phishing kits and tooling fast, burn the server in days, and move to the next one.
    • Mistake — loud staging: mass downloads and tool installations on the server trigger EDR and admin alerts within hours.
    • Mistake — IP reuse: using one hijacked server across campaigns lets defenders link them all into one tracking cluster.
    • Mistake — forgetting certificates: a phishing page served without a valid certificate scares victims away and gets flagged by scanners.

    Blue team / SOC perspective

    A hijacked server leaves fingerprints on the server itself, on the network around it, and sometimes in other people's abuse reports. This section shows where to get visibility, which artifacts to hunt for, and a short triage flow for analysts.

    Where visibility comes from

    Five sources cover almost every useful signal for this technique:

    • Web access logs (IIS, Apache, nginx): every request to the server, with method, path, status code, and source IP. This is where web shell traffic shows first.
    • WAF (Web Application Firewall — a filter that inspects HTTP requests to your apps): exploit attempts, shell-like requests, and unusual upload sizes.
    • EDR on servers (endpoint detection and response — software that records process, file, and network events): a web worker process starting a command shell is the loudest possible alarm.
    • File integrity monitoring (FIM): alerts when files in protected folders, such as the web root, are created or changed.
    • Egress netflow: records of connections that leave your network. A server talking to a network it never used before is a classic relay signal.

    Artifacts it leaves and where to look

    Server attacking othersAbuse reports, provider blacklist monitors"Your IP is scanning us" complaints in the abuse mailbox
    Server sending spam or phishingMail logs, blocklist feedsYour mail domain lands on a spam blocklist overnight

    Why this matters for your organization

    Server compromise cuts in two directions. Outward: your server can attack others. You will learn about it from abuse reports, blocklist entries, and angry partners — often before you learn about it from your own tools. Every day it stays dirty costs reputation and can end in legal questions. Inward: a hijacked server is often the first real foothold inside your network. From the web root, attackers pivot to internal systems, steal service credentials, and wait. Fast detection on the server shortens every later stage of the attack.

    Short triage checklist

    1. Confirm the alert: check the file exists, replay the request pattern, rule out a legitimate deploy.
    2. Isolate the server from the inside network, but keep logging alive.
    3. Preserve evidence: copy access logs, the shell file, and process history before any cleanup.
    4. Find the entry point: which app, plugin, or panel was the way in?
    5. Remove the shell and rebuild the server if the platform allows.
    6. Rotate secrets that lived on the server: database passwords, API keys, certificates.
    7. Scan neighbors for the same shell family — attackers rarely stop at one server.
    8. Report: answer abuse mail, notify partners if your server attacked them, file the incident record.
    Good practice. Treat the abuse@ mailbox as a detection source, not a nuisance. Feed abuse reports into the SIEM and triage them like any other alert. External eyes often see your hijacked server before your own tools do.

    5.2 · Threat intelligence

    Hijacked servers are shared infrastructure: the same URL may serve a phishing page one week and a malware drop the next. External intelligence helps you recognize them early. A simple pipeline works: collect signals, analyze them against your assets, apply the result to detections, then review what worked.

    Sources worth wiring up

    • URLhaus and abuse.ch feeds: community lists of malware distribution URLs and botnet C2 hosts, updated by the minute.
    • urlscan.io: public scans of web pages; search for your brand, your IP ranges, or lookalike names to find hosted phishing.
    • Vendor blogs: ESET, Proofpoint, Cisco Talos, and Mandiant reports name the servers and shells used in real campaigns.
    • WAF vendor intel: your WAF provider sees exploit waves across all customers and pushes rules for new plugin vulnerabilities.
    • Internal web logs: your own IIS/Apache logs are the highest-signal source you own. Search them weekly for the patterns below.

    Confidence levels that work

    Tag every indicator with a confidence level and keep the meaning strict:

    • High: confirmed by two independent sources or direct observation (your own logs plus a vendor report).
    • Medium: one reliable source, no second confirmation — good for detection, not for blocking.
    • Low: rumor or machine-only correlation — good for hunting lists only.

    Write the level into the indicator record, so the analyst who meets it at 03:00 knows how much to trust it. Blocking on a Medium indicator can cut off an innocent partner, because many hijacked servers still run real business.

    5.4 · Logs and patterns

    Each threat needs the right log source with the right fields. "Normal" and "suspicious" below describe the same fields — that contrast is exactly what makes the detection logic possible.

    TH-01 / TH-02 — Web shell and phishing-host signals

    Log sourceKey fieldsNormalSuspicious
    Web access log (IIS/Apache/nginx)method, uri_stem, status, c_ip, user_agent, time_taken, bytesGETs on real pages; POSTs only to known forms and APIsPOST to a rare path with shell/cmd/eval in the name, status 200, small and repeatable
    WAF logrule_id, action, uri, body_len, client_ipMostly allowed requests, known scanner noiseBlocked or flagged upload to the web root; shell keywords in a body
    FIM / EDR file eventspath, file_name, hash, actor_process, timeChanges only during deploy windows from CI identitiesNew .aspx/.php file at 02:40 written by the app pool itself

    Detection logic: (method = POST) AND (path looks shell-like OR is a rarely-seen upload path) AND (status = 200) AND path not on the business allowlist. Correlate in the same hour: a new file in the web root plus a worker process running a command.

    Read the line like this: at 02:44, a client from 198.51.100.77 sent a POST to /uploads/shell.aspx, and the server answered 200. Two POSTs in twelve seconds to a file nobody deployed is a web shell conversation, not a user.

    5.5 · Sigma rules and Splunk SPL

    The four rules below cover the highest-value threats (TH-01, TH-03, TH-04, TH-05). Each Sigma rule is valid YAML and is followed by a matching Splunk query, a mapping note, false positives, and tuning advice. Replace index and sourcetype names with your local naming — the field assumptions are stated under each query.

    SIG-001 · POST to shell-like path returns 200 (TH-01)

    Mapping note: assumes Splunk's IIS field extractions (cs_method, cs_uri_stem, sc_status, c_ip). False positives: CMS file managers and legacy admin pages. Tuning: replace the generic keyword regex with your own baseline of rarely-seen paths (build it with tstats over 30 days) and keep filter_known_paths in sync with the apps you actually run.

    SIG-002 · Web worker spawns command interpreter (TH-01/TH-03)

    Mapping note: uses Sysmon Event ID 1 (process creation) forwarded to the edr index. False positives: planned maintenance jobs running under service identities. Tuning: allowlist known maintenance scripts by hash or command-line prefix, and page on this rule — it usually means someone is typing commands on your server right now.

    SIG-003 · Executable file written to the web root (TH-04)

    Mapping note: uses Sysmon Event ID 11 (file create) with the writing process in Image — a file written by the app pool itself is far more interesting than one written by a deploy account. False positives: CMS updates and plugin installers. Tuning: add a deploy-window filter (allow CI identities and change windows), and for mostly static sites add more extensions such as .phtml or .war.

    SIG-004 · Server initiates outbound to rare port or network (TH-03/TH-05)

    Mapping note: uses Sysmon Event ID 3 (network connection). Sysmon does not carry ASN data, so add the "rare ASN" part in the SIEM: join DestinationIp against your ASN enrichment lookup and alert on first-seen autonomous systems for that server. False positives: approved partner APIs on custom ports. Tuning: keep a per-server allowlist of destination networks and ports, and treat any repeat on a fixed schedule (the relay pattern) as a finding even when the port looks harmless.

    Warning. Validate every rule in a test index before production, and record the validation result with the rule. A rule that has never fired in a test is a guess, not a detection.

    Real-world case study — Operation Ghost (Turla)

    Between roughly 2013 and 2019, the Turla group ran one of the longest documented infrastructure operations on record. ESET researchers named it Operation Ghost and published the full story in October 2021. It is the perfect teaching case for T1584.004: hijacked servers, not rented ones, carried an entire espionage platform for years.

    Context

    Turla is a well-known espionage group linked by many investigators to Russian state interests. Instead of renting new servers for each campaign, they compromised ordinary internet-facing servers — small business sites, community portals, hosting boxes with old web apps — around the world. Each stolen server became one hop in a relay chain.

    The chain looked like this: victim computer → hijacked server 1 → hijacked server 2 → attacker. Commands and stolen files passed through the hops. No single server ever revealed the attacker's true location, and no victim connection pointed at anything obviously hostile.

    Attack chain in short

    1. Compromise internet-facing servers with old CMS apps and weak panels.
    2. Install quiet relay software that forwards traffic to the next hop.
    3. Chain several relays across different countries and hosting companies.
    4. Point dormant malware inside victim networks at the relay chain.
    5. Send commands through the chain; store files on the hijacked hosts.

    Timeline

    1. ~2013
      Infrastructure build-out. Turla compromises the first servers and connects them into relay chains. Some chains stay alive for more than six years.
    2. 2017
      Discovery lead. Investigators following a separate Turla case notice C2 traffic disappearing into servers that look like ordinary small-business websites.
    3. 2019
      Multi-country investigation. Swiss authorities, coordinated with other countries and ESET, map the relay chains and collect enough evidence for legal action.
    4. October 2019
      Server seizures. Police seize the compromised servers in coordinated raids. The relay chains go dark at once.
    5. October 2021
      Public report. ESET publishes "Operation Ghost", documenting the hijacked-server technique end to end.

    Detection point

    The break came from hypothesis-driven correlation. Analysts saw small, periodic egress from victim machines to servers with no logical relationship to the victim. The hijacked servers shared three traits: old unpatched web apps, unusually stable uptime for "neglected" machines, and outbound traffic at fixed intervals. Each trait alone was noise. Together, they were the relay chain. The lesson for defenders: watch for low-volume, periodic connections from servers, not only for big, loud events.

    Response arc

    • Containment: law enforcement physically seized the relay servers, cutting the C2 path in one stroke.
    • Eradication: the hard part — implants in victim networks sat dormant and had to be found by hunting, not by waiting for beacons.
    • Recovery: victims re-audited their egress paths and rebuilt trust; Turla partly rebuilt chains on new hijacked servers, proving the method persists.

    Impact and team response

    The operation shows the true cost of server compromise: decade-scale dwell time and intelligence loss that no single victim could see from inside. Response needed rare cooperation — law enforcement from several countries, hosting providers, researchers, and victims' security teams sharing indicators quietly. Communication followed a strict need-to-know pattern until seizure day, because any leak would have let Turla abandon the servers early.

    Lessons learned

    • Relay servers look boring — patch hygiene on other people's servers matters as much as on your own.
    • Periodic, low-volume egress from servers is a first-class detection target.
    • Takedowns work but take years; detection must not depend on them.
    • After cutting any C2 path, hunt for the dormant implants it served.

    Mitigation and defense

    ATT&CK lists only M1056 Pre-compromise for this technique, which honestly says: you cannot fully prevent hijack attempts from inside your network. What you can do is make your servers hard to hijack, see a hijack fast, and limit what a hijacked server can do.

    Enterprise controls by layer

    Patch and harden

    • Patch internet-facing applications on a fast clock (14 days or less) — they are the raw material for T1584.004.
    • Apply a server hardening baseline (for example CIS benchmarks): no unused services, panels locked down, admin ports behind a VPN.
    • Retire abandoned servers and remove unused plugins, themes, and apps — every leftover is a door.

    Monitor and detect

    • File integrity monitoring (FIM) on web roots; alert on new scripts and executables.
    • WAF in front of internet-facing apps, with managed rules and virtual patching for slow patch cycles.
    • EDR on servers, not only on laptops; forward Sysmon and web logs to the SIEM.

    Limit the blast radius

    • Egress allowlists: a web server rarely needs broad outbound internet access.
    • Least-privilege service accounts: the app pool identity cannot write outside the web root, run commands, or read other users' data.
    • Segment the web tier from the internal network, so a web shell is not a highway inward.

    Prepare to respond

    • Maintain a server-compromise runbook: isolate, preserve logs, remove the shell, rotate secrets, scan neighbors.
    • Include abuse-report handling in the runbook: who reads abuse@, how to verify a report, how to answer blocklist operators.
    • Test the runbook twice a year with a purple-team exercise, and keep the contact list for partners and providers current.

    Home and small office

    • Keep your CMS, plugins, and themes updated — old plugins are the number one way small sites get hijacked.
    • Delete plugins and themes you do not use; use strong, unique passwords for admin logins and enable two-factor authentication.
    • Choose shared hosting that isolates accounts from each other and scans files automatically.
    • If your site is abused: restore from a clean backup, change every password, ask the host to check neighboring sites, and answer abuse mail quickly.

    Response checklist — suspected server compromise

    • Isolate the server from the internal network, but keep logging and evidence collection alive.
    • Preserve logs: copy access logs, WAF logs, the shell file itself, and process history before cleanup.
    • Remove the shell and any other planted files; rebuild the server if the platform allows it.
    • Rotate secrets that lived on the server: database passwords, API keys, certificates, SSH keys.
    • Scan neighbors: search other web servers for the same shell family and the same source IPs.
    • Find and patch the entry point: the vulnerable app or plugin that let the attacker in.
    • Report: answer abuse mail, notify affected partners, add indicators to intel with a confidence level.
