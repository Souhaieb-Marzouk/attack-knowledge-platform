T1055.003 Thread Execution Hijacking

A thread is the part of a program that actually runs instructions. Thread execution hijacking pauses an existing thread inside a trusted process, points it at attacker code instead, and resumes it. No new thread is created, which makes it quieter than classic injection. ATT&CK lists this technique under the tactics Stealth (TA0005) and Privilege Escalation (TA0004). TA0005 was named Defense Evasion before ATT&CK v20.

What it is

An existing thread's next instruction is redirected to attacker code that was written into the process memory. The thread never leaves its original process.

Why attackers use it

No remote thread is created and no new process appears, so there are fewer obvious events for defenders to see than with classic injection.

Main risks

Quiet implants that run inside trusted processes such as browsers, with full access to that process's data, cookies, and network session.

Detection focus

Thread-context writes across processes, suspend and resume handle patterns, and code in memory that has no file behind it.

Contents

1Overview

Thread Execution Hijacking is a quiet way to run attacker code inside a process you already trust. This section explains the idea in plain words and shows where it fits in an attack.

Threads and the instruction pointer

A program is a list of instructions stored in memory. A thread is the worker that runs those instructions, one after the other. The CPU keeps a small register called the instruction pointer (named EIP on 32-bit x86 CPUs and RIP on 64-bit x64 CPUs). It always holds the address of the next instruction to run.

Whoever controls the instruction pointer controls what the thread does next. That is the whole idea of this technique.

How the hijack works

The attacker code does five things to one thread inside the target process. OpenThread gets a handle to the chosen thread. SuspendThread pauses the thread. VirtualAllocEx and WriteProcessMemory place the payload into the process memory. GetThreadContext and SetThreadContext read and change the saved CPU registers, so the instruction pointer (EIP on x86, RIP on x64) points at the payload. Finally ResumeThread starts the thread again — and it now runs the attacker code.

Why it evades detection

Classic injection creates a new remote thread with CreateRemoteThread, and Windows logs that event (Sysmon Event ID 8). Here no new thread is created. The attacker reuses a thread that already exists, so that event never appears. Tools that only watch for remote-thread events see nothing.

Main risks

The payload runs inside a trusted process such as a browser. It can read that process's data, reuse its network session, and stay hidden for a long time. If the implant picks a busy thread carelessly, the trusted process can also crash — which becomes a visible side effect for the user.

Where it fits in the attack chain

This is a post-execution Stealth (TA0005) step: the implant is already on the host and just needs a safe place to run. After the hijack succeeds, the attacker uses the hidden code for Command and Control (C2 — the attacker's remote channel) and later for Credential Access. The hijack itself is staging: it turns a fragile implant file on disk into durable code inside a trusted process.

What you will learn in this guide

You will see the full attack story step by step, what an attacker must prepare, which traces the technique leaves on Windows, which events and fields matter (Sysmon Event ID 10 with thread-context rights), five ready-to-adapt Sigma rules with matching Splunk queries, and a complete response checklist.

Note — how T1055.003 differs from its neighbors

T1055.004 (Asynchronous Procedure Call) queues code through the APC queue instead of changing the instruction pointer. T1055.005 (Thread Local Storage) abuses TLS callbacks, which run before a program's entry point. T1055.003 is the direct approach: suspend a live thread and overwrite its instruction pointer.

Note — quiet does not mean invisible

The technique avoids one loud event, but it must still write into another process's memory and change a thread context. Those actions leave traces in Sysmon Event ID 10, EDR thread telemetry, and memory scans. Good detection coverage is realistic and achievable.

  4. Step 4 — Write shellcode. The implant copies its payload into a read-write-execute memory region inside the browser process. Defender view: EDR memory scanning flags code in a region that has no file on disk behind it.

3Red team perspective

Understanding how attackers think about thread hijacking helps you write better detections. This section describes the technique conceptually, for defense and lab learning only.

Why attackers choose it

The main reason is stealth. Hijacking reuses a thread that already exists, so there is no remote-thread event to catch. The attacker also inherits everything the thread already has: the memory of the trusted process, its security context, and its network identity. From the outside, traffic from the implant looks like traffic from the browser or from another legitimate program.

A second reason is stability of access. Code inside a long-running process survives longer than a short-lived loader file on disk, which antivirus can delete.

Where it is used in the wild

Thread and context manipulation appears in three families of tooling. Old loaders and RATs (remote access trojans) used it for years, and many families keep it as a fallback. Modern custom implants and red-team frameworks still offer it as a code-execution option, often together with APC injection, because it defeats naive remote-thread detections. The official ATT&CK page for T1055.003 documents this behavior for Gazer, Trojan.Karagany, Waterbear, Pikabot, and Vidar.

Danger — Lab only

The sequence below is a conceptual map for building detections, not instructions to run. Never execute injection techniques against systems you do not own. In a legal lab, the primitive chain is: find a target thread → OpenThread → SuspendThread → VirtualAllocEx + WriteProcessMemory → GetThreadContext → SetThreadContext (move the instruction pointer, EIP/RIP) → ResumeThread. Every step in that chain is a detection opportunity described in Section 5.

Prerequisites an attacker needs

  • A process handle with the right access. Writing memory and setting a thread context needs PROCESS_VM_WRITE, PROCESS_VM_OPERATION, and THREAD_SET_CONTEXT rights.
  • Matching architecture. A 64-bit implant cannot set the context of a 32-bit process in a meaningful way; the bitness must match.
  • An idle thread. Hijacking a thread that is mid-task corrupts the program. Attackers pick threads that are waiting, so the application survives.
  • User-level rights. The technique works without administrator privileges, which is why it is common in ordinary malware.

Common variations

  • Early-bird style. The process is created suspended, the payload is staged, and the main thread is hijacked before its own code runs. ATT&CK tracks this suspended-process pattern mainly under T1055.004 (Asynchronous Procedure Call). For thread execution hijacking proper, the thread is suspended, not the process.
  • APC queue alternative. T1055.004 uses the APC queue instead of the instruction pointer: the implant queues code to run at the next alertable wait.
  • Fiber hijacking. Windows fibers are lighter than threads; an implant can switch execution to a fiber it controls with the same evasion goal.

Mistakes the technique makes (useful for defenders)

Implants get hijacking wrong in predictable ways, and each failure leaves a trace. Hijacking a busy thread crashes the trusted process, which produces error reports. Forgetting the CONTEXT_CONTROL flag in the context request fails silently, so the implant retries and repeats the same handle events. Leaving the payload region as RWX (read-write-execute) memory makes it visible to memory scanners. Wrong stack alignment makes the payload crash shortly after the resume, and the crash points at a thread whose start address belongs to no module.

4Blue team perspective

The technique hides one event but creates others. Here is what defenders can actually see, where to look, and how to triage an alert quickly.

Your visibility options

Sysmon Event ID 10 (ProcessAccess) is the workhorse. With the right configuration it logs cross-process handle access, including the rights requested and the call stack of the requesting thread. One limit matters: Event ID 10 records handles to processes. The context change happens on a handle to a thread, so Sysmon does not log it as a separate event — you infer it from the Event ID 10 record and from EDR thread telemetry. EDR agents close that gap: they raise context-modification alerts directly, with thread start addresses and memory region protection. ETW (Event Tracing for Windows) provides the raw stream that both tools build on.

Artifacts to collect

  • Handle access to a process with write-class rights such as 0x143A (PROCESS_VM_WRITE + PROCESS_VM_OPERATION + query rights), or full access 0x1FFFFF.
  • Handle access to a thread with THREAD_SET_CONTEXT (0x0010) and THREAD_SUSPEND_RESUME (0x0002). Sysmon Event ID 10 records process handles only, so these thread rights appear mainly in EDR telemetry.
  • On process handles, PROCESS_SUSPEND_RESUME (0x0800) when a tool suspends every thread of a process.
  • An RWX memory region in the target with no file on disk behind it (unbacked memory).
  • A thread whose stack shows UNKNOWN(...) frames — code running outside any loaded module.
Warning — Sysmon Event ID 8 will not fire

Event ID 8 logs CreateRemoteThread. Thread hijacking never calls that API, so a detection stack built on Event ID 8 alone is blind to this technique. You need Event ID 10 with thread-context rights, or EDR thread telemetry.

Where to look

In your EDR console, open the process and thread view for the target process and sort threads by start address; unbacked start addresses stand out. In Sysmon Event ID 10 logs, group by source image and granted access. In Windows Security Event ID 4688 (process creation), anchor the timeline: it shows the loader and its parent, but it cannot see the hijack itself. Microsoft Defender for Endpoint alerts (IDs 1116 and 1117) can confirm malware on the host. In memory forensics, list thread start addresses and look for regions that no module maps.

Why it matters and how it fits the chain

This technique specifically defeats naive remote-thread detections, so its presence tells you the attacker invests in evasion. It usually sits between initial access and C2. When you confirm it, assume the implant had time to collect credentials from the hijacked process, and scope the incident wider than one host.

Six-step triage flow

  1. Step 1Validate. Confirm the alert is real: check that the source image, target image, and granted access in the event match, and that the source is not a known tool on your allowlist.
  2. Step 2Identify. Name the source process, target process, and source thread ID. Pull the command line and file hash of the source.
  3. Step 3Capture memory. Take an EDR-triggered memory dump of the target process before killing anything, so the payload region is preserved.
  4. Step 4Check thread starts. List thread start addresses and call stacks in the target. UNKNOWN frames or start addresses outside any module confirm injected code.
  5. Step 5Isolate. If unbacked code is confirmed, remove the host from the network and block the source process hash.
  6. Step 6Hunt fleet-wide. Search all endpoints for the same source hash, the same handle pattern, and the same parent chain, then open an incident if more hosts match.

5.3Threats ranking and categorization

Five concrete threats built from this technique, ranked by detection priority on Windows. Severity reflects how likely the pattern is malicious and how much damage it enables.

Critical Windows T1 — Cross-process thread-context write (SetThreadContext)

Description. A process outside the target changes the instruction pointer of a thread inside it. This is the core primitive of the sub-technique. Preconditions. A process handle with write rights plus a thread handle with set-context rights; user-level privileges are enough. Impact. Arbitrary code runs inside a trusted process with no new thread. Justification. Legitimate cross-process context writes are rare and short-lived. With the tool filter in place, noise is workable, and this is the direct signature of the technique, so it earns a critical rule.

Medium Windows T2 — Remote thread suspend/resume manipulation

Description. Suspend and resume rights requested on another process, the preparation pattern of a hijack even when the context write is not yet visible. Preconditions. Same handle chain as T1. Impact. A frozen thread or a completed hijack that started quietly. Justification. Some administration and debugging tools suspend processes, so this is a hunt signal more than an automatic alert.

High Windows T3 — Process created suspended, then staged

Description. A script host or Office parent creates a child with the CREATE_SUSPENDED flag, so the child's main thread can be hijacked before its own code runs. ATT&CK tracks this suspended-process pattern mainly under T1055.004 (Early Bird APC), but loaders that MITRE associates with T1055.003, such as Pikabot and Vidar, use it too. For thread execution hijacking proper, the thread is suspended, not the process, so treat this as a staging signal rather than proof. Preconditions. A document, script, or dropper that starts the child. Impact. The "hijack before start" variant evades process-creation scanning entirely. Justification. The parent-child combination (wscript, winword, excel) with a suspended child is unusual in normal work.

Low Windows T4 — Unknown-module thread activity in a browser process

Description. Call stacks containing UNKNOWN frames — code with no module on disk behind it — appearing in events that touch browser processes. Preconditions. Code already running unbacked somewhere in the estate. Impact. Marks an active implant stage rather than preparation. Justification. JIT engines and .NET runtimes also produce UNKNOWN frames, so this is a hunt-first signal: run it as a low-severity query and escalate only when it correlates with T1 or T5.

High Windows T5 — Script host reads or writes another process's thread context

Description. PowerShell, wscript, cscript, or mshta opening another process with write or context rights. Script hosts almost never inject code legitimately. Preconditions. A malicious script executed by user action, macro, or scheduled task. Impact. The whole chain runs from a signed, trusted binary, which defeats application allowlisting based on image names. Justification. The source image alone makes this high-value: legitimate context writes from script hosts are rare enough to tune by allowlist.

Note — who legitimately uses these rights

The same access rights appear in honest work. Debuggers attach to processes with full access. Profilers and some application monitoring agents read and write process memory. Antivirus and EDR agents do it constantly. Build your baseline around these three groups first, then treat everything else with write-class masks as a candidate signal.

5.5Sigma rules and Splunk SPL

Five rules, one per ranked threat. Each rule has a matching Splunk query and a mapping note. Tune the filter lists against your own tooling before you enable them.

R1 — Cross-process context write (covers T1, level critical)

Mapping note. Field names follow the common Splunk Sysmon add-on naming: EventCode=10 is the normalized Event ID, and GrantedAccess is kept as the exact string Sysmon recorded. Adjust the index name to your environment. The SourceImage filters mirror the Sigma filter_tools list. The | search TargetImage!=SourceImage line is an SPL-only refinement: basic Sigma cannot compare two fields to each other, so the rule description documents it for anyone porting the rule.

R2 — Remote suspend/resume rights (covers T2, level medium)

Mapping note. The mask list is a practical compromise: it covers full access, the common combinations that include 0x0800, and the pure 0x0800 request. The SourceImage filters mirror the Sigma filter list. If your EDR records thread-level suspend events (thread handles with 0x0002, THREAD_SUSPEND_RESUME), prefer those as the primary signal and use this rule as the corroboration layer. Expect more noise than R1, which is why the query requires at least two events.

R3 — Suspended process staging (covers T3, level high)

Mapping note. The SPL reproduces the same loose contains-style match as the Sigma rule: like(CreationFlags, "%4%"). Both are approximations: CREATE_SUSPENDED combined with other flags produces a different decimal value. Validate each hit by checking whether the child ever ran its own code, and cross-check with EDR process data as the tuning note in the rule says.

R4 — Unknown-module call stacks touching a browser (covers T4, level low)

Mapping note. The wildcard in the base search keeps the expensive string match off the where stage. Tune by allowlisting your known dynamic-code tooling (browser update agents, .NET profilers, monitoring DLLs) and by ranking sources whose path is user-writable.

R5 — Script host with write or context rights (covers T5, level high)

Mapping note. The source-image match is case-insensitive by design, because script hosts can be launched from unusual capitalizations. If you run an incident-response toolkit that uses PowerShell for memory collection, allowlist its exact signed path first, then deploy the rule.

6Real-world case study

A loader with tools and behaviors similar to those reported for TrickBot, reconstructed for training. In the public incidents this chain ended in ransomware; here the detection lands in time to stop it.

Warning — educational reconstruction

This case study is an educational reconstruction based on public reporting (2019–2021 DFIR and vendor reports). The tools and behaviors are similar to those reported for TrickBot and follow-on ransomware intrusions, but the incident as told here is illustrative. Hosts, users, times, and identifiers are invented. It is written for defense training only.

Context

A mid-size company with roughly 800 Windows workstations ran antivirus and central log collection, but had no tuned Sysmon configuration and no thread-context rules. TrickBot is a banking trojan, and public reporting describes loaders similar to it: they inject into trusted processes and hijack their threads. After the loader settles, it can hand control to a post-exploitation framework such as Cobalt Strike. The same intrusions often ended in ransomware deployment a few days later.

Timeline

  1. Day 0 · 09:12A lure email continues an existing message thread and carries a malicious attachment. Because it rides a real conversation, the user opens it. This is email thread hijacking — a different use of the word "thread", on the attacker's delivery side.
  2. Day 0 · 09:31The user opens the attachment. The loader runs, and its behavior matches TrickBot reporting: it injects into and hijacks threads in trusted processes, then survives on the host without an obvious second process.
  3. Day 0 · 14:05The implant collects browser data and stored credentials from the hijacked processes. Nothing alerts.
  4. Day 1 · 08:40Detection point. The new Sysmon Event ID 10 rule fires: rundll32, started by wscript, opened msedge.exe with full access and an UNKNOWN call-stack frame. An EDR memory alert confirms an unbacked RWX region.
  5. Day 1 · 09:20The analyst validates the alert, captures memory, and isolates the host. The loader hash is blocked fleet-wide.
  6. Day 2 · 10:00Correlation finds the Cobalt Strike beacon attempt in proxy logs and a second host with the same loader hash. Both are isolated; lateral movement was attempted but blocked.
  7. Day 3–5Eradication and recovery complete. The ransomware stage was never reached because the Day 1 alert interrupted the chain.

Detection point

Sysmon Event ID 10 with write-class rights and an UNKNOWN call frame, correlated with the EDR memory alert for an unbacked RWX region. One event alone was suggestive; the pair was conclusive.

Containment

Host isolation through the EDR console, loader hash blocked fleet-wide, and the compromised mailbox credentials reset within the hour.

Eradication

Loader files removed, persistence tasks deleted, and the memory payload confirmed gone by a follow-up offline scan of the isolated host.

Recovery

Hosts returned to the network after verification. Passwords and browser sessions on the affected hosts were treated as compromised and rotated.

Impact

Two hosts, about six hours of analyst work, one user's mailbox reset, and under a day of downtime. No encryption event, no data extortion note. In the public cases without an early context-write alert, the same chain reached ransomware.

Team response and communication

The SOC used a single channel, updated leadership twice daily, and notified the email team, who purged the lure message from all mailboxes — a step that prevented at least one more open attempt.

Good practice — lessons learned

First, do not rely on Sysmon Event ID 8 alone: it never fires for thread hijacking, and this intrusion was invisible until Event ID 10 rules arrived. Second, deploy thread-context write rules — they were the single highest-value detection in this case. Third, email controls that spot replies in hijacked external threads stop the chain before it reaches the endpoint.

Home and small office

Keep Windows and the browser updated — modern Edge and Chrome raise the bar against memory attacks. Leave the built-in Windows security features on, including memory integrity where the hardware supports it. Do not run scripts or documents from unexpected emails. Back up important files offline and test that you can restore them. If something feels wrong — the browser crashing in a repeating pattern, unexplained pop-ups — disconnect from the network and get help rather than debugging alone.

Daily habits

Review new high-severity injection alerts with the triage flow from Section 4. Check that Sysmon and EDR agents are reporting on all expected hosts. Note any repeat offender in the false-positive register.

Weekly habits

Compare alert volumes against the baseline and investigate sudden changes. Verify rule-to-owner assignments are current. Spot-check one rule end to end, from event to closure.

Monthly habits

Review exclusions and expire what is unused. Re-read vendor reporting for new injection primitives and update the mask lists. Run one purple-team validation of the full chain against a lab host.

9Cheat sheet and quick reference

Everything from this page in one place: facts, the five detections, the response checklist, and the links worth keeping.

Key facts

Technique
T1055.003 — Thread Execution Hijacking
Parent
T1055 — Process Injection
Tactics
Stealth / Privilege Escalation (TA0005 / TA0004)
Platform
Windows (user-level rights)
Core primitive
OpenThread → SuspendThread → memory write → SetThreadContext (EIP/RIP) → ResumeThread
Key telemetry
Sysmon Event ID 10 (context/suspend masks, CallTrace), Event ID 1 (CreationFlags), Windows Security 4688, Defender 1116/1117
Will not fire
Sysmon Event ID 8 (no remote thread is created)

Top five detections

  1. R1 — Cross-process handle access with write and context rights (Sigma and SPL).
  2. R2 — Remote handle with suspend/resume rights (Sigma and SPL).
  3. R3 — Suspended child created by a script host or Office parent (Sigma and SPL).
  4. R4 — UNKNOWN call-stack frames touching a browser process (Sigma and SPL).
  5. R5 — Script host opening a process with write rights (Sigma and SPL).

Pair any single hit with a memory scan before you declare an incident. Two hits on one host within an hour is a strong signal.

Response checklist — first 30 minutes

  • Validate the alert: source image, target image, granted access, call stack.
  • Exclude known tooling from the allowlist before escalating.
  • Pull the source process command line and file hash.
  • Capture memory of the target process through the EDR.
  • Check thread start addresses in the target for unbacked regions.
  • Isolate the host if unbacked code is confirmed.

Response checklist — first 24 hours

  • Hunt the source hash and handle pattern across all endpoints.
  • Review proxy and DNS logs for beaconing from the affected host.
  • Reset credentials and sessions used on the host.
  • Purge lure emails from all mailboxes if delivery was by message.
  • Block the loader hash and parent chain in prevention mode.
  • Write the incident record and update rule false-positive notes.
