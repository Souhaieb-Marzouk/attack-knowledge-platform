T1055.004 Asynchronous Procedure Call

An asynchronous procedure call (APC) is a Windows feature that lets a program queue a function to run later, when a thread is ready — a state called an alertable wait. Attackers abuse this by queueing their own code, so a trusted Windows thread runs it as part of its normal work. This guide explains the trick in simple words and gives defenders concrete ways to detect, triage, and stop it.

What it is

Attacker code is queued onto a thread's APC list and runs when the thread becomes alertable, so the host process executes it as part of its normal work.

Why attackers use it

No remote thread is needed, and the payload blends with the normal scheduling of a trusted process instead of standing out.

Main risks

Quiet execution inside fresh, trusted processes — code can run before the program's real logic and before some monitoring attaches.

Detection focus

Suspended process creation, thread-context handles on new processes, and behavioral alerts from EDR tools (EDR means endpoint detection and response).

Contents

1Overview

What an asynchronous procedure call is, how the "Early Bird" trick abuses it, and why loaders and droppers like it so much.

APC in plain words

Windows runs every program as one or more threads. A thread is the part of the program that actually executes code, one instruction after another.

An asynchronous procedure call (APC) is a small package of work that code can attach to a thread. The thread does not run the package right away. It runs it only when it reaches an alertable wait.

An alertable wait is a rest state in which the thread tells Windows: "I am pausing now — hand me any queued work." Calls such as SleepEx and WaitForSingleObjectEx create this state. Think of it as a door sign that reads "pending callbacks welcome here".

The classic abuse pattern: Early Bird

The best-known abuse is called Early Bird injection. It works in four moves:

  1. Create a real Windows process in a suspended state (CREATE_SUSPENDED), so its main thread is frozen before any program logic runs.
  2. Write shellcode — small raw machine code — into that new process.
  3. Call QueueUserAPC to attach the shellcode to the frozen main thread.
  4. Resume the thread. The APC fires before the program's real main() runs.

A common variant queues LoadLibraryA instead of raw shellcode. That call makes the new process load an attacker's DLL file, so the payload arrives as a library.

Why it is effective

The injected process is a genuine, signed system binary. Image checks and signature checks pass, because the file on disk was never changed.

There is no remote thread. Classic detections look for CreateRemoteThread or unusual new threads in another process; APC injection needs neither. Execution is scheduled by Windows itself, inside the trusted process, as part of its normal work.

This also separates T1055.004 from its sibling T1055.003 (Thread Execution Hijacking). That technique rewrites the instruction pointer — the marker that says which instruction a thread runs next — of an existing thread. T1055.004 instead queues new work and lets the thread pick it up.

The code also runs very early — often before user-mode monitoring hooks are attached to the new process.

Where it fits in the attack chain

T1055.004 belongs to the Stealth and Privilege Escalation tactics (TA0005 / TA0004). TA0005 was named Defense Evasion before ATT&CK v20. In practice it is mostly an execution-staging move: a dropper or loader gets its implant running inside a clean process before the attack continues.

Typical order: initial access (phishing, lure script) → APC injection → command-and-control (C2) → discovery and follow-up actions. Catching this step usually means catching the attack before persistence.

Note — key terms

Alertable: a thread state in which the thread accepts queued APCs while it waits. Shellcode: a small block of raw machine code that an implant uses as its first stage. Dropper: a small program whose only job is to deliver and start the next stage.

  4. Step 4 — Queue APC. QueueUserAPC (or the native NtQueueApcThread) attaches the shellcode to the new process's main thread (APC queued). Defender view: thread-context access on a brand-new process; Sysmon EID 10 with broad GrantedAccess rights.
  5. Step 5 — Resume. The thread starts and becomes alertable almost immediately, so it picks up the queued APC. Defender view: the process is running before its own main logic ever executed; an EDR behavioral anomaly.
  6. Step 6 — APC fires early. The shellcode runs before the legitimate main() — the classic Early Bird signature. The implant initializes inside the trusted process. Defender view: an EDR behavioral injection alert names the pattern.
  7. Step 7 — Hidden activity. The implant beacons (sends regular check-in messages) to its C2 server. On paper the parent-child chain looks clean: script host to a real system binary. Defender view: a network flow from a freshly spawned process is the visible trace.
  8. Step 8 — SOC triage. The analyst chains Sysmon EID 1 (suspended), EID 10, and the EDR alert into one timeline, then isolates the host. Defender view: three weak signals become one strong case.

3Red team perspective

Why attackers pick APC injection, how the sequence looks conceptually, which variants exist, and the mistakes that make lab work fail. Everything hands-on belongs in a lab you own.

Why attackers use it

It runs early. Code queued with an APC fires during process startup, before many hooking and monitoring mechanisms attach to the new process.

No remote thread. Detections built around thread creation in another process never fire, because the thread already belongs to the new process.

Clean lineage. The payload ends up inside a real signed binary. The parent-child chain — script host to system binary — looks ordinary in a process tree view.

Where it applies

APC injection shows up most often in:

  • Loaders and droppers that need their stager running fast and quietly.
  • Packers that unpack the real payload inside a fresh process.
  • Red-team initial access toolkits used right after a phishing foothold.

It is an execution-staging primitive: it does not persist by itself, but it gives the next stage a trusted place to live.

Danger — Lab only

Conceptual sequence, useful for building detections and for safe lab exercises on systems you own: CreateProcess with CREATE_SUSPENDED → VirtualAllocEx + WriteProcessMemory → QueueUserAPC → ResumeThread. This is an API ordering — API means a named Windows function a program can call — not a working exploit. Never run injection code against systems you do not own.

Prerequisites

The attacker needs one of two starting points: the ability to create a process (the Early Bird route), or an open handle to a thread in a target process (the remote route). A handle is an internal reference a program holds to a system object such as a process or a thread.

The hard part is the alertable condition. A queued APC runs only when the thread waits alertably. In simple words: the thread must pause in a special "interruptible" wait. Common ways to reach that state are SleepEx, WaitForSingleObjectEx, MsgWaitForMultipleObjectsEx, and message loops built on GetMessage; plain Sleep becomes alertable only when it is called with bAlertable = true. A thread that never waits alertably will never run the queued code. That is why a suspended fresh process works so well: its first thread waits alertably during startup by design.

Common variations

  • Self-APC: the malware queues code on a thread of its own process — no cross-process access needed.
  • Remote APC: the attacker injects into an existing alertable thread of another process, such as a browser or chat client.
  • Special user APC: queueing through NtQueueApcThreadEx or its Win32 wrapper QueueUserAPC2 — a newer variant seen rarely, with little native telemetry.
  • AtomBombing: writes code into the global atom table, then uses APCs to make the target process copy and run it.
  • Early Bird vs Early Cascade: Early Bird queues on the suspended process's first thread; Early Cascade stages a small loader that fires as each new child process starts.

Mistakes attackers and testers make

  • Target thread never alertable: the payload is queued but never runs. The implant silently does nothing.
  • Architecture mismatch: 32-bit shellcode queued into a 64-bit process fails at the first call.
  • Killing the suspended process before resume: if the parent cleans up too early, the payload never gets its slot.
  • Choosing heavily monitored parents: spawning from a script host or Office app attracts more scrutiny than a common utility.
Warning — Test your detections, not your neighbors

Validate the rules in Section 5 against a controlled lab VM (a virtual machine used for safe testing). On production systems run only the detection side, and get written permission from system owners before any active testing.

4Blue team perspective

What defenders actually see when APC injection happens, which artifacts survive, and a six-step triage flow that turns weak signals into a decision.

Visibility

Sysmon EID 1 with CreationFlags shows suspended process creation — the setup move.

Sysmon EID 10 shows cross-process access, including the broad rights (0x1FFFFF, 0x143A) that thread-context manipulation needs.

EDR behavioral engines are the most reliable signal here. They watch API sequences and memory state instead of single events, and they catch Early Bird patterns well.

Windows Security event 4688 records process creation too, but without CreationFlags, so it is a fallback source rather than the primary one. Sysmon EID 8 (CreateRemoteThread) cannot see APC queueing, but it still catches sibling injection routes — keep collecting it.

Honest limit: Windows emits no generic "APC queued" event. Native APC-queue telemetry is sparse, so behavior-based detection carries most of the weight.

Artifacts

  • A process created suspended, followed almost immediately by cross-process access to it.
  • A process that is alive, talking on the network, or loading modules before its main logic ran.
  • Unbacked memory — private memory regions not backed by any file on disk — inside a signed process.
  • A thread whose start address points outside the process's own image.

Where to look

  • EDR console: behavioral injection verdicts, unbacked-memory findings, and process lineage views.
  • Sysmon pipeline: join EID 1 and EID 10 by process GUID (a unique ID that Windows gives each process) to find suspended creations touched by another process.
  • Process lineage: script hosts (wscript, cscript, mshta, Office apps) with unusual children are the classic dropper tree.

Why it matters and where it fits

Catching APC injection usually means catching the attack before persistence, credential theft, and lateral movement. The detection point sits early in the chain: initial access → this technique → command-and-control.

Each signal alone is weak: a suspended process, a handle, one alert. Together they are strong, because legitimate software rarely does all three within seconds.

Good practice — Correlate, then decide

The strongest SOC habit here is correlation: suspend flag + cross-process handle + behavioral verdict, tied to the same process GUID. Build that join once, and most APC cases become clear on their own.

Triage flow (six steps)

  1. Validate the alert: confirm the rule is meaningful and the finding is not a known benign pattern.
  2. Confirm suspended-creation lineage: pull Sysmon EID 1 for the process; check CreationFlags and the parent process.
  3. Check cross-process handles: find EID 10 events targeting the same process; note the source image and GrantedAccess.
  4. Capture memory: take an EDR memory dump or use a memory triage tool; look for unbacked executable regions.
  5. Isolate the host: if the picture is confirmed, cut network access while keeping the sensor online.
  6. Hunt fleet-wide: search every endpoint for the dropper name, payload hashes, and the same behavioral pattern.

5.3Threats ranking and categorization

Five realistic threat scenarios for this technique, ranked for a typical Windows enterprise. Severity reflects how urgent the signal is and how reliable the detection is.

Critical Windows T1 — Early Bird: suspended process created by script or Office host, then injected

Description: the signature initial-access tradecraft of this technique — a wscript, cscript, mshta, or Office parent creates a system-binary child with the suspended flag and injects into it.

Preconditions: a dropper running as the user; no admin rights needed.

Impact: an implant runs inside a clean process before its main logic and before most inspection starts.

Justification: matches documented campaigns; user-level execution of a suspended system binary from an interpreter parent is a near-certain attack pattern.

High Windows T2 — Cross-process SET_CONTEXT-class handle on a fresh process

Description: one process opens another with thread-context rights — the queueing primitive used from another process (the remote APC route).

Preconditions: user-level code execution; an open process handle.

Impact: code can be queued into an existing trusted process without creating anything new.

Justification: a strong signal, but security tools themselves open handles, so tuning is required before it can rank critical.

Medium Windows T3 — EDR behavioral self-APC detection

Description: the EDR names in-process APC execution behavior (self-APC) on a single process — an injection verdict without cross-process context.

Preconditions: EDR behavioral engine enabled.

Impact: confirms injection behavior, usually at the last stage of the chain.

Justification: highly actionable, but it often fires alone and needs memory triage to confirm scope; medium until correlated with lineage.

High Windows T4 — Dropper tree staging injection

Description: a wscript/cscript → rundll32/regsvr32 chain shows classic loader staging that typically precedes APC injection.

Preconditions: a lure executed by the user.

Impact: an early warning of the injection setup, sometimes seconds before the APC fires.

Justification: rare lineage in enterprise traffic; a few admin scripts create similar shapes, so high rather than critical.

Low Windows T5 — Special user APC usage (NtQueueApcThreadEx)

Description: a rare variant that queues special user-mode APCs through NtQueueApcThreadEx / QueueUserAPC2 instead of the classic call.

Preconditions: attacker with code execution; a modern Windows build.

Impact: the same as standard APC injection, but harder to see.

Justification: low because of visibility gaps, not because it is harmless: native telemetry rarely confirms it, so detection rests on EDR verdicts alone. Standalone low-confidence alerts should start hunts rather than pages — the low rank reflects detection confidence, not attacker intent.

Some installers, backup agents, and update tools suspend their own child processes for staging. A suspended creation alone is not proof of anything. Always pair the flag with lineage and cross-process access before you escalate.

Warning — Tuning notes that matter

CreationFlags brittleness: the flag is a bitmask reported as a string. Substring matching for "4" also matches composite masks that merely include the suspended bit. Prefer the bitwise check in the R1 SPL, or compare the exact value.

svchost children: real svchost.exe processes are children of services.exe. Any other parent is worth review on its own.

Rule R2: expect noise from security tools and debuggers; keep the expected-source filter current.

Validation: replay a test EID 1 and EID 10 pair against each rule after every Sysmon upgrade.

6Real-world case study

APT32 "Early Bird" APC injection — an educational reconstruction based on Cybereason's public research (2018). Hosts, users, and times are illustrative.

Note — sourcing

This case study is an educational reconstruction based on public reporting by Cybereason (2018) and on MITRE ATT&CK procedure examples. Details are simplified and illustrative; the detection lessons are real.

Context

A company with operations facing Southeast Asia becomes a target of APT32 (OceanLotus), a group with espionage goals. The attackers want a quiet foothold inside the corporate network, not quick money. They prepare a spearphishing attachment that carries a dropper built around Early Bird APC injection.

Attack chain at a glance

Spearphishing attachment → dropper with embedded CAB archive or script → suspended legitimate process → APC queue injection → C2 implant → credential harvesting → network discovery → exfiltration attempt caught on egress review.

Timeline

  1. Day 0 · 09:14 A finance user opens the spearphishing attachment. The embedded dropper starts under the Windows script host. No macro warning appears — the lure is macro-free.
  2. Day 0 · 09:15 The dropper creates a suspended legitimate process, writes the payload into it, and queues it on the main thread with QueueUserAPC. The thread resumes, and the implant starts before the real program. No alert fires yet.
  3. Day 1 The implant beacons to attacker infrastructure over HTTPS. The traffic blends into normal web flows.
  4. Day 2 · 11:03 DETECTION POINT: the EDR raises a behavioral injection alert on the process. A busy analyst triages it as low — the process is a known system binary, and no other alert exists yet.
  5. Day 3 The implant harvests credentials from memory and runs discovery commands. The suspended-creation Sysmon events exist in the pipeline, but nobody has correlated them with the Day 2 alert.
  6. Day 5 An egress review (a check of outbound network traffic) flags an unusual upload to a rare domain. The security team reopens the Day 2 alert and pulls the Sysmon events around it.
  7. Day 6 Incident response isolates the workstation, blocks the C2 domains, and starts a fleet-wide hunt for the dropper hash.

Detection point

The EDR behavioral injection alert on Day 2. It was correct but triaged low: a single behavioral verdict on a trusted binary, with no lineage context attached. The lesson is not "the tool failed" — the process around the alert failed.

Containment

Isolate the workstation the same hour. Block the C2 domains and addresses at the proxy and firewall. Reset credentials for the affected user, because the implant had access to memory for days.

Eradication

Remove the dropper and implant artifacts, reimage the host, and close the delivery path: restrict script hosts for standard users and apply attack-surface-reduction rules for Office and script child processes.

Recovery

Restore the host from a clean image, return it to the network after a 72-hour watch, and run retro-hunts across 90 days of telemetry for the same hashes and behavioral pattern.

Impact

Espionage goals mean the damage is quiet: exposed documents, harvested credentials, and a mapped network. Early detection on Day 2 — once escalated — kept the intruder contained to one host.

Team response and communication

A named incident lead, a daily bridge, and short written updates to management. The analyst who triaged the alert low joined the review without blame; the fix was process, not punishment.

Lessons learned

  • Behavioral alerts need a triage SLA (a promised response time). A 30-minute first-look target for injection verdicts would have surfaced this on Day 2 instead of Day 5.
  • Script-host controls pay off twice: they prevent many droppers and make the ones that run far more visible.
  • Hunt for suspended creations. The Sysmon CreationFlags data was collected but never queried. A weekly hunt would have shown the pattern on Day 1.

Home and small office

Keep Microsoft Defender (or your antivirus) fully enabled — do not switch off behavioral features for speed. Install updates on time. Do not run scripts or attachments you did not expect, even from people you know. Keep at least one offline backup. If your antivirus shows an injection warning, take it seriously and let the tool quarantine or remove the file.

8Common mistakes and best practices

Twelve concrete blue-team mistakes around APC detection, each with symptom, root cause, fix, and prevention — plus the habits that keep them fixed.

1. CreationFlags not collected or misparsed

Symptom: rules never fire; the field is empty in the SIEM.
Root cause: an old Sysmon config, or a parser that drops the field.
Fix: enable the field in the config and validate end to end with a test event.
Prevention: treat the config as code and test the parser monthly.

2. Excluding script hosts broadly

Symptom: no visibility into dropper trees at all.
Root cause: early false positives led to a blanket filter on wscript and cscript.
Fix: remove the blanket exclusion; correlate flags and lineage instead.
Prevention: review exclusions quarterly and record why each one exists.

3. Treating suspended creations as installer noise

Symptom: alerts auto-closed without lineage checks.
Root cause: the assumption that only installers suspend child processes.
Fix: verify lineage and cross-process access before closing.
Prevention: document which installers legitimately suspend, and challenge anything else.

4. Only alerting on remote threads

Symptom: APC injection is missed completely.
Root cause: rules built for the CreateRemoteThread era.
Fix: add behavioral and EID 10 cross-process rules from Section 5.5.
Prevention: keep a coverage map per injection sub-technique.

5. EDR behavioral engine toggled off for performance

Symptom: no injection verdicts arrive at all.
Root cause: performance complaints led to silent configuration changes.
Fix: re-enable the engine and fix real performance issues with targeted exclusions.
Prevention: put sensor settings under change control.

6. No lineage-based correlation

Symptom: single events look harmless and get dismissed.
Root cause: EID 1 and EID 10 are stored but never joined.
Fix: join events by process GUID; alert on the combined pattern.
Prevention: build and test one correlation search per injection pattern.

7. Allowlisting by parent process name only

Symptom: spoofed parent names pass every check.
Root cause: parent names are easy to fake (PPID spoofing — faking the parent process ID).
Fix: require multiple signals — flags, access rights, memory — before trusting anything.
Prevention: never allowlist on a single field.

8. Logs stay on the endpoint

Symptom: no fleet-wide hunt is possible; evidence dies with the host.
Root cause: Sysmon and Defender logs never forwarded.
Fix: forward both channels to the SIEM with sane retention.
Prevention: monitor collection coverage as a service-level metric.

9. No memory triage capability

Symptom: the team cannot confirm or rule out injection.
Root cause: no tooling, no training, no playbook.
Fix: add memory capture to the triage flow and practice it.
Prevention: run a quarterly injection-triage exercise.

10. Orphaned detection rules

Symptom: rules fire but nobody owns them or reads the output.
Root cause: rules deployed without owners or queues.
Fix: assign an owner and a destination queue to every rule.
Prevention: keep a rule registry with owner, purpose, and review date.

11. Untested rules

Symptom: rules silently break after a Sysmon or Windows update.
Root cause: no validation pipeline with test events.
Fix: replay recorded test events after every upgrade.
Prevention: automate rule tests in the deployment pipeline.

12. Undocumented false positives

Symptom: the same benign pattern gets triaged again and again.
Root cause: FP knowledge lives in one analyst's head.
Fix: document known FPs in the rule repo and suppress narrowly.
Prevention: require an FP journal entry for every suppression.

Working habits that keep the above fixed

Daily

Review injection and suspended-creation alerts within the SLA. Check the EDR console before other queues. Write down anything odd, even if you close it.

Weekly

Hunt for suspended creations fleet-wide. Tune the noisiest rule. Read one new vendor report on loaders and note any new behavioral detail.

Monthly

Validate the Sysmon config and parser. Re-run detection tests. Review rule ownership and exclusion lists. Map coverage against the T1055 family.

9Cheat sheet and quick reference

One screen: the facts, the five detections, the first response steps, and the links worth keeping.

ID
T1055.004 — Asynchronous Procedure Call (sub-technique of T1055 Process Injection)
Tactics
Stealth / Privilege Escalation (TA0005 / TA0004) — TA0005 was named Defense Evasion before ATT&CK v20
Platform / permissions
Windows · User
Core trick
Queue code on a thread's APC list; it runs when the thread is alertable. Classic form: suspended process + QueueUserAPC + resume ("Early Bird").
Best signals
EDR behavioral injection verdicts · Sysmon EID 1 CreationFlags = 4 · Sysmon EID 10 with broad cross-process access
Data sources
Process creation, Process access, OS API execution

Top five detections

  1. Critical early-bird-suspended-child — suspended child of a script or Office host
  2. High cross-process-setcontext-fresh-process — thread-context handle on a fresh process
  3. High dropper-tree-staging — script host staging rundll32/regsvr32
  4. Medium defender-self-apc-behavior — Defender behavioral APC or injection verdict
  5. Low special-apc-edr-only — EDR-only verdict for rare special APC usage

Full rules, SPL, and tuning notes: Section 5.5.

Response checklist — first 30 minutes

  • Validate the alert and open a case ticket.
  • Pull Sysmon EID 1 for the process: check CreationFlags and the parent.
  • Pull Sysmon EID 10 events targeting the process: note the source and GrantedAccess.
  • If the picture matches the pattern, isolate the host (keep the sensor online).
  • Notify the incident lead.

Response checklist — within 24 hours

  • Capture and triage memory from the affected host.
  • Hunt dropper names and payload hashes fleet-wide.
  • Block C2 domains at the proxy and firewall.
  • Reset credentials of affected users.
  • Add retrospective detection rules and review 90 days of history.
