T1055.002 Portable Executable Injection

A portable executable (PE) is the standard Windows file format for programs and libraries. PE injection copies a complete PE image into the memory of another process and starts it there, so a whole program can run without ever existing on disk in the target. ATT&CK lists this technique under two tactics: Stealth (TA0005) and Privilege Escalation (TA0004). TA0005 was named Defense Evasion before ATT&CK v20.

What it is

A full PE image — headers, sections, and entry point — is written into another process's memory and executed there with a remote thread.

Why attackers use it

Fileless execution inside a trusted process. The payload never lands on disk, so file-scanning antivirus has nothing to find.

Main risks

Memory-only implants, hidden command-and-control channels, and a quiet staging point for credential theft and bigger attacks.

Detection focus

Unbacked executable memory, remote threads from odd addresses, and script hosts that write into other processes.

Contents

1Overview

Portable executable (PE) injection moves a complete program into the memory of another Windows process and runs it there. This section explains the idea in plain words, compares it with DLL injection, and shows where it sits in an attack chain.

The PE format in one minute

Windows programs and libraries use a file format called the portable executable (PE) format. A PE file has three main parts:

Headers. A table at the start of the file describes the file, the CPU it is built for, and where execution begins. The header block starts with the two letters MZ.

Sections. These are the blocks with real content: .text holds code, .data holds variables, and .rsrc holds resources such as icons and dialogs.

Entry point. The exact address of the first instruction the CPU should run.

PE injection copies this whole structure — headers, sections, and entry point — into the memory of a process that is already running.

How it differs from DLL injection

In classic DLL injection (T1055.001), the attacker makes the target process call LoadLibrary. The Windows loader itself then loads a DLL file from disk and runs it.

PE injection skips the loader. The attacker copies a complete, standalone PE image straight into the target's memory and starts it with a remote thread. Because the loader never runs, the attacker must handle relocation manually. Relocation simply means fixing the absolute memory addresses inside the image so they match the base address where the image actually landed in the target.

The reward: the payload never needs a file on disk, so file-based antivirus has nothing to scan.

Self-injection vs remote injection

Self-injection writes and runs the PE inside the attacker's own process, such as a script host or the dropper itself. There are no cross-process events, so thread and process-access logs stay quiet.

Remote injection writes into a different process, usually a trusted one such as explorer.exe or svchost.exe. This hides the implant behind the trusted process, but it produces loud cross-process events that defenders can detect.

Where it fits in the attack chain

PE injection usually appears after delivery, when a dropper already runs on the host. It serves two goals at once: stealth, because no payload file lands on disk, and privilege escalation, when the target process runs with more rights than the dropper.

From this hidden position, attackers stage the next steps: credential access, command-and-control (C2) — the channel back to the attacker — and data collection.

Note — memory becomes the file

Once the PE image runs, only the memory of the target process holds the implant. A reboot destroys it, and a disk scan finds nothing. That is why memory visibility, not file scanning, is the core detection idea for this technique.

Step 1 of 8

SOC view

Written story (text alternative)

  1. Step 1 — Foothold. A user opens a fake installer from a phishing email. The packed dropper starts, shows a normal setup screen, and quietly prepares its hidden payload. Defender view: Sysmon EID 1 logs a new process in a user-writable folder with an unusual parent chain; a fresh or missing signature is another hint.
  2. Step 2 — Read payload. The dropper decrypts its own resources and unpacks a complete hidden PE image into a private memory buffer. Defender view: EDR (endpoint detection and response) sees unusual section activity — large executable-looking regions appear inside the dropper before it touches other processes.
  3. Step 3 — Open + allocate. The dropper opens the trusted explorer.exe with OpenProcess and reserves fresh read-write (RW) memory inside it with VirtualAllocEx. Defender view: Sysmon EID 10 records cross-process access with sensitive rights, and an EDR rule flags the new writable region in a trusted process.
  4. Step 4 — Write full PE image. WriteProcessMemory copies the PE headers and all sections into the new region, relocation fixups adjust the image for its new base address, and VirtualProtectEx raises the memory protection to executable. Defender view: the region now holds image-like bytes that start with an MZ header and run executable, but no file backs them — an unbacked image region.
  5. Step 5 — Start execution. CreateRemoteThread starts a new thread in the target at the PE entry offset. No LoadLibrary call happens at any point. Defender view: Sysmon EID 8 shows a remote thread whose StartModule and StartFunction are empty, because the start address belongs to no module.
  6. Step 6 — Implant runs. The implant finishes initializing inside explorer.exe. It is now a complete, memory-only program living inside a trusted process. Defender view: EDR memory scanning finds unsigned executable code running inside a signed, trusted process.
  7. Step 7 — Hidden activity. From inside the trusted process, the implant polls the C2 server over HTTPS and waits for tasks. Defender view: network monitoring sees a periodic beacon flow from a process that never spoke like this before; egress baselines make it stand out.
  8. Step 8 — SOC triage. The SOC analyst captures triage memory. Scanners reveal the in-memory PE, and the host is isolated from the network. Defender view: the alert chain lines up — new process, cross-process write, unbacked thread, beacon flow — and memory forensics confirms a full PE image.

3Red team perspective

This section explains, at a conceptual level only, why attackers choose PE injection and which building blocks the technique is made of. It describes the purpose of each step — never working code.

Danger — Lab only

Everything in this guide is educational. Process injection code can damage systems and is illegal to run on machines you do not own. Practice only inside an isolated lab you control, and never against production or other people's systems. This page describes the purpose of each API step, not a recipe that can be copied.

Why attackers pick PE injection

  • Whole implant in memory. The complete program lives and runs inside the target's memory space.
  • Nothing on disk after start. A dropper can delete itself, and the implant never had a file at all.
  • Works with packed payloads. Crypters and packers can wrap the PE so static analysis sees nothing useful.
  • Trusted cover. The implant runs inside a signed process, so simple process trust checks pass.

Where it applies in practice

  • Crypter services sold in criminal markets wrap a payload so it unpacks and injects at run time.
  • Custom loaders of espionage toolsets stage second-stage implants this way.
  • Commercial implants use in-memory PE execution to keep their tooling off disk.

Conceptual sequence (purpose of each step)

Each step below states what the step achieves. Real tooling wraps these calls in error handling, obfuscation, and API hashing — details a defensive guide does not need.

StepPurposeWhat defenders can see
Read payloadDecrypt and unpack the PE image from the dropper's resources into a private buffer.Large executable-looking regions form inside a newly started process.
OpenProcessAsk Windows for a handle to the target process — a handle is a permission ticket for one open object — with write and thread-creation rights.Sysmon EID 10 logs the access request with its GrantedAccess mask.
VirtualAllocExReserve fresh read-write (PAGE_READWRITE) memory inside the target.A new writable private region appears in a process that normally needs none.
WriteProcessMemory + relocationsCopy the headers and section data, then process the relocation table so absolute addresses match the base address where the image actually landed — it is not the preferred ImageBase the file was built for.Image-like bytes with an MZ header appear in memory that no file backs.
VirtualProtectExRaise the memory protection of the copied image to executable, for example PAGE_EXECUTE_READ on the code section.A private region that was only writable turns executable — a classic EDR memory alert.
CreateRemoteThreadStart a thread at the PE entry offset. No LoadLibrary is used.Sysmon EID 8 shows a thread whose start address belongs to no module.

Prerequisites

  • Handle rights. The injector needs a handle with memory-write, memory-operation, and thread-creation access to the target.
  • Architecture match. A 32-bit payload cannot simply run inside a 64-bit process; the bitness must line up.
  • Base address handling. The payload must be relocated to the base address it actually gets, or be position-independent.

Common mistakes attackers make

  • Skipping relocations — the implant crashes the target process at once.
  • Hard-coding a base address that collides with address space layout randomization (ASLR), the Windows feature that randomizes memory positions.
  • Leaving the dropper on disk, which gives defenders a file to analyze.
  • Targeting protected processes, where Windows blocks these access rights entirely.

Variations defenders should know

VariationHow it differsWhy it matters for detection
Self-injectionThe payload is written into the injector's own process instead of a remote one.No cross-process thread or access events fire, so EID 8 and EID 10 stay quiet; memory scanning becomes the main signal.
Manual section mappingEach PE section is written at its correct offset instead of one flat copy.The memory layout looks more like a real loaded module, but scanners still find the unbacked image.
Reflective loading (T1620)A small loader is written first; it then loads the PE inside the target itself.The write is smaller, but the loader and image are both unbacked code.
Process hollowing (T1055.012)The image of an existing process is replaced rather than a new image being added.Hollowing swaps the real image; PE injection adds a new image next to it. Scanners flag both, but the process lineage differs.

4Blue team perspective

Defenders cannot scan what is not on disk, so the blue-team view centers on memory and behavior. This section covers the telemetry sources, the artifacts that give the technique away, and a short triage flow.

Visibility sources

EDR memory scanning (endpoint detection and response) inspects process memory on a schedule and on demand.

ETW-TI is the Windows threat-intelligence event stream; it exposes sensitive API use to security products.

Sysmon events 8 and 10 record remote thread creation and cross-process access.

Microsoft Defender raises behavioral verdicts for injection patterns.

Artifacts that reveal the injection

RWX private regions that contain PE headers (MZ) but are backed by no file on disk.

Thread start outside any module — Sysmon EID 8 with an empty StartModule field.

Ghost image — image-shaped memory whose contents match no signed file in the operating system.

Where to look first

Start with EDR memory scan results, then triage captures scanned with malfind-style tools that list unbacked executable regions.

Correlate with Sysmon EID 8 and EID 10 to find the source process that injected.

Why it matters

Fileless implants escape antivirus that only scans files. If your controls stop at the disk, a whole class of attacks is invisible to you. Memory telemetry closes that gap.

It also matters for scope: one host with an in-memory implant usually means the campaign touched more hosts, so the finding should drive a fleet-wide hunt.

Fit in the attack chain

PE injection is the pivot between "attacker has code running" and "attacker has a durable, hidden foothold". After injection comes C2, credential access, and collection.

Detecting the injection step cuts the chain before the expensive stages start.

Good practice — treat memory verdicts as high signal

EDR memory scans and empty StartModule events are noisy but rare. A behavioral memory verdict on a signed, trusted process deserves human review within minutes, not days. Build the habit before the real incident arrives.

5.2Threat intelligence

Where to collect

  • MITRE ATT&CK — the technique page and its parent T1055 give the baseline behavior and data sources.
  • Vendor reporting — Kaspersky, ESET, Microsoft, and Check Point regularly document loaders that run PEs in memory.
  • OSINT — Malpedia tracks families with injection behavior; MalwareBazaar hosts samples; public YARA rulesets flag loader traits.
  • ISACs — sector groups share indicators that fit your industry.
  • Internal telemetry — your own EID 8 and EID 10 history is the best baseline for what is normal in your estate.

How to apply it

Collect loader names and injection traits from reporting, then analyze which traits your sensors can see — usually the empty StartModule event and RWX regions.

Apply the traits as detection content: Sigma rules, EDR custom indicators, and hunt queries. Track each family with the confidence notes below so triage knows what a hit likely means.

Refresh the mapping when vendors publish new loader reports; tooling changes fast in this space.

5.3Threats ranking

The five realistic threats below are ranked by detection value for this technique, all on the Windows platform. "Preconditions" lists what must already be true; "justification" explains the rating.

T1 · Remote thread started at an unbacked address High Windows

Description. A new thread begins running at an address in memory that no file backs. This is the moment an injected PE image, or shellcode (a small piece of raw code without a full PE header), starts to run inside the target process.

Preconditions. Attacker code already runs somewhere on the host; Sysmon EID 8 is collected.

Impact. Hidden execution of a complete implant inside a trusted process.

Justification. Rated high because it is the core execution signal of T1055.002 and is almost always malicious when the target is a system process.

T2 · EDR behavioral verdict: self or remote injection High Windows

Description. Defender-class engines watch for the injection pattern itself and raise a behavioral verdict such as Behavior:Win32/ProcessInject.* when a process allocates memory in another process, writes code into it, and makes that memory executable.

Preconditions. An EDR or antivirus product with a behavioral engine is deployed and enabled.

Impact. A direct, high-confidence verdict that names the injecting process.

Justification. Rated high because the engine observed the injection pattern directly, not just a side effect.

T3 · Script host writes to another process's memory High Windows

Description. PowerShell, wscript, cscript, or mshta opens a second process with memory-write rights — the classic shape of a script-based loader preparing PE injection without dropping a binary.

Preconditions. Script hosts can run on the endpoint; Sysmon EID 10 is collected.

Impact. Fileless staging: the loader leaves no payload file for defenders to analyze.

Justification. Rated high because script hosts almost never have a legitimate reason to write into other processes.

T4 · Dropper chain staging injection Medium Windows

Description. Office or script parents spawn rundll32, regsvr32, or mshta with uncommon command lines. The chain often ends in a loader that performs PE injection.

Preconditions. A user opens a malicious document or script; Sysmon EID 1 is collected.

Impact. Early warning before the implant runs — the cheapest moment to stop the attack.

Justification. Rated medium because the chain can also deliver other techniques and needs the uncommon-command filter to stay precise.

T5 · Unsigned code region executing in a trusted process Medium Windows

Description. CallTrace shows unknown module frames, or a memory scan finds unsigned executable code, inside explorer.exe or svchost.exe. This confirms that injected code actually runs, not only that memory changed.

Preconditions. CallTrace is collected with EID 10, or periodic memory scans are configured.

Impact. Confirms active implant execution and anchors deeper response.

Justification. Rated medium because generated code and software protection layers can mimic it; the rule needs a baseline.

5.5Sigma rules and Splunk SPL

Five rules map one-to-one to the ranked threats. Levels follow the ranking: high, high, high, medium, medium. Each rule ships with a matching Splunk query and a mapping note.

R1 — remote-thread-unbacked-start High

Catches T1: a remote thread whose start address no module backs.

Mapping note. Assumes Sysmon XML through a universal forwarder with standard field names, and the same OR logic as the Sigma rule (empty StartModule or empty StartFunction). An empty value can arrive as - or as a missing field; add | fillnull value="-" StartModule, StartFunction if your forwarder drops empty fields. The stats line only groups results for review — remove nothing else to keep the logic one-to-one. Tune .NET-heavy hosts by allowing known JIT paths.

R2 — defender-behavioral-process-injection High

Catches T2: the Defender behavioral verdict for injection activity.

Mapping note. The Defender channel is Microsoft-Windows-Windows Defender/Operational; note the doubled "Windows". Field names vary by add-on: some normalize to detection_name and event_id. Validate with | fieldsummary before tuning.

R3 — script-host-cross-process-write High

Catches T3: a script host opening another process with full memory rights.

Mapping note. Sigma cannot compare two fields directly, so the rule filters script-host targets to approximate "target is not the source"; in SPL the comparison is exact with | where TargetImage != SourceImage. The GrantedAccess values all combine at least memory write (0x20), memory operation (0x8), and thread creation (0x2); 0x1FFFFF is the full-rights mask. Extend the list with your EDR agent's known access patterns if needed.

R4 — dropper-chain-staging Medium

Catches T4: Office or script parents spawning loader binaries with uncommon command lines.

Mapping note. The uncommon-command selection uses common staging markers. Adjust the list to your environment, and add your software build paths to falsepositives if developers test scripts with these loaders.

R5 — unsigned-region-trusted-process Medium

Catches T5: unknown call-stack frames inside explorer or svchost.

Mapping note. CallTrace joins frames with a pipe as module!function+0xoffset; unknown frames appear as UNKNOWN(0x...). The Splunk wildcard form CallTrace="*|UNKNOWN(*" is case-insensitive by default, which matches Sigma's contains modifier.

Warning — tune R1 before you trust it

Just-in-time compiled .NET applications and some profiling tools create threads whose module resolution is briefly empty. Run R1 in search-only mode for two weeks, list the source images that appear, and allow-list confirmed runtimes before the rule pages anyone.

6Real-world case study

An espionage intrusion rebuilt for teaching, using tools and behaviors similar to those reported for Lazarus/DTrack. Every host, user, and timestamp is illustrative.

Note — source and limits of this case study

Educational reconstruction. The tools and behaviors are similar to those reported for Lazarus/DTrack in public vendor reporting (Kaspersky, 2018–2020). Hosts, users, addresses, and times are invented. The goal is to show how the detection content in this page would play out, not to document one specific incident.

Context

Victim. A mid-size research and engineering organization with valuable intellectual property: design documents and source code.

Attacker. An espionage team using tooling similar to DTrack, as reported by vendors. The goal is intellectual property theft over weeks, not fast extortion.

Environment. Windows 10 workstations, file-based antivirus, EDR deployed but with memory-scan reviews handled lightly.

Attack chain at a glance

Spearphishing email with a fake conference-registration installer. The installer drops a signed-looking downloader, which unpacks a DTrack-style PE and injects it into explorer.exe. The memory-only implant keys logs, collects documents, and exfiltrates archives over HTTPS.

Every stage after the installer is either packed or memory-only, so file scanning stays quiet until the memory scan fires.

Timeline

  1. Day 0 · 09:14 An engineer opens the spearphish and runs the fake conference installer. The dropper starts and shows a plausible setup wizard.
  2. Day 1 · 11:02 The signed-looking downloader fetches the packed payload. Antivirus file scans see nothing suspicious on disk.
  3. Day 2 · 03:47 The dropper injects the full PE image into explorer.exe and starts it with a remote thread. The implant is now memory-only.
  4. Day 3 · 10:15 Detection point. An EDR memory scan flags a PE image inside explorer.exe. The alert is initially triaged as a false positive because the process is signed and the ticket notes "explorer is trusted".
  5. Day 4–5 The implant keylogs and collects design documents, staging them into archives inside user temp folders.
  6. Day 6 · 22:40 Exfiltration over HTTPS blends with normal browser egress; no allow-list blocks the destination.
  7. Day 7 · 14:30 A weekly threat hunt revisits the Day 3 alert, pulls Sysmon EID 8, finds the empty StartModule event from Day 2, and escalates to an incident.

Detection point

The EDR memory scan on Day 3 — a PE image with an MZ header inside explorer.exe, backed by no file. The missed follow-up, not the sensor, was the gap.

Containment

The host was isolated at the network level within 40 minutes of escalation. Memory was captured before any reboot, preserving the implant for analysis.

Eradication

The dropper file was removed, run keys were cleaned, and the workstation was rebuilt. Password resets covered accounts used on the host.

Recovery

The rebuilt host returned to service the next day. Egress allow-listing and a memory-alert review procedure went live the same week.

Impact

Later review confirmed several research documents left the network, so intellectual property loss was assumed. Regulatory reporting followed, since customer data was also reachable from the host.

Team response and communication

The SOC, IT, and legal leads joined one bridge. Status updates went out every four hours; the false-positive triage on Day 3 was reviewed openly, without blame, and the process changed.

Lessons learned

Memory-scan alerts deserve review — "explorer is signed" is not an explanation; capture memory first. Egress allow-listing would have made the Day 6 exfiltration visible immediately. Hunt cadence — the weekly hunt caught what the triage process missed, and a daily review would have caught it three days earlier.

8Common mistakes and best practices

Twelve concrete blue-team mistakes that keep showing up around memory-only threats. Each one lists the symptom you will notice, the root cause, the fix, and the prevention that stops it from returning.

1. Trusting file-based antivirus only

Symptom. Scans stay clean while an implant already runs.

Root cause. Fileless execution leaves no file to scan.

Fix. Turn on EDR memory scanning and behavioral verdicts.

Prevention. Test defenses with fileless scenarios, not only sample files.

2. Memory-scan verdicts auto-closed as false positives

Symptom. Behavioral memory verdicts closed in minutes with no capture.

Root cause. "The process is signed" treated as an explanation.

Fix. Reopen such tickets, capture triage memory, and re-verify.

Prevention. Forbid auto-close rules on behavioral memory verdicts.

3. No baseline of legitimate RWX regions

Symptom. Every RWX finding is treated as noise, or all findings are ignored.

Root cause. JIT compilation and .NET create RWX memory by design.

Fix. Build per-application baselines of known runtimes.

Prevention. Keep the baseline list reviewed like any other asset data.

4. Sysmon EID 8 and 10 not collected

Symptom. No StartModule or CallTrace data during hunts.

Root cause. Default audit policies never install a Sysmon configuration.

Fix. Deploy a config with thread and process-access events.

Prevention. Run coverage checks that verify the events actually arrive.

5. PowerShell logging switched off

Symptom. Loader scripts are invisible in investigations.

Root cause. Script block logging never enabled by policy.

Fix. Enable script and transcript logging and forward the logs.

Prevention. Check the policy in the monthly configuration baseline.

6. Dropper allowed to run because "the user needed it"

Symptom. Exceptions open for unsigned tools on demand.

Root cause. No application control policy or exception workflow.

Fix. Remove the exception; approve and sign the tool properly.

Prevention. Route every exception through a security review.

7. No triage memory capture process

Symptom. Evidence is lost after a reboot or reinstall.

Root cause. No runbook for memory-only threats.

Fix. Add capture steps with named tooling to the runbook.

Prevention. Practice the capture quarterly on a lab host.

8. Hash-only hunting

Symptom. Hunts find nothing because each payload rebuild is unique.

Root cause. Reliance on file hashes as the only indicator.

Fix. Hunt behavior: EID 8/10 patterns and memory traits.

Prevention. Add at least one behavioral hunt to the monthly plan.

9. No egress allow-listing, so C2 blends in

Symptom. Beacon traffic looks like every other HTTPS flow.

Root cause. Open outbound internet from workstations.

Fix. Route egress through categories, allow-lists, and logs.

Prevention. Review the egress baseline each quarter.

10. Orphaned detection rules

Symptom. Rules silently break after log source changes.

Root cause. No owner assigned to any rule.

Fix. Assign owners and monitor rule health and drift.

Prevention. Keep a rule inventory with review dates.

11. Untested rules

Symptom. A rule misses a real event or floods false positives during an incident.

Root cause. Rules never validated against sample data.

Fix. Replay captured events through the rule set.

Prevention. Purple-team validation and automated tests for rules.

12. Undocumented false positive rationale

Symptom. The same benign pattern escalates repeatedly; analysts distrust the rules.

Root cause. Tuning decisions live in chat threads and memories.

Fix. Record every false positive and its reason in the rule notes.

Prevention. Review the tuning log in the monthly detection meeting.

Warning — alert fatigue is the main risk

Most of the mistakes above combine into one failure: noisy rules train analysts to ignore memory verdicts. Tuning for precision is not optional; it is what keeps the high-value verdicts trusted when they matter.

Daily habits

  • Review memory-scan and injection verdicts within minutes.
  • Check overnight beacon anomalies against the egress baseline.
  • Confirm log pipelines are green for Sysmon and Defender.

Weekly habits

  • Review new unbacked-thread events and tune noisy rules.
  • Verify agent health and Sysmon coverage on new hosts.
  • Walk one detection rule end to end, source to response.

Monthly habits

  • Run a purple-team injection test in the lab.
  • Review false positive documentation and rule drift.
  • Verify the egress baseline and backup restore paths.
