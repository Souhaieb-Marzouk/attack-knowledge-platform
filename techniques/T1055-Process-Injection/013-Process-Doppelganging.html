T1055.013 Process Doppelgänging

Process Doppelgänging uses transactions in NTFS, the Windows file system, to launch a program from a file that never exists on disk. The attacker writes a malicious program into a pending transaction, loads it into memory, and rolls the transaction back. This guide explains the attack, shows it step by step, and teaches defenders how to catch it.

1Overview

This section explains the technique in plain language, shows where it fits in an attack chain, and lists the key facts used again in later sections.

What it is

Process Doppelgänging is a Windows process-injection method. It abuses TxF (Transactional NTFS), a Windows feature that groups file operations into a transaction. A transaction can be committed, which makes changes real, or rolled back, which undoes them. The attacker writes a malicious PE (portable executable, the standard Windows program file format) into a pending transaction. The kernel loads that pending file as a program image in memory. The attacker then rolls the transaction back.

The file never becomes a real file on disk, but the in-memory image stays valid and runs. Windows ends up executing a program that, from the file system's point of view, does not exist. There is no file for antivirus to scan, no file hash to match, and no file-integrity event to review.

ATT&CK describes the method in four official steps: Transact, Load, Rollback, and Animate. The chain also avoids the highly monitored functions NtUnmapViewOfSection, VirtualProtectEx, and SetThreadContext, so sensors that watch those Process Hollowing (T1055.012) APIs see nothing. Section 3 compares the two techniques in detail.

Naming note: in 2025, ATT&CK version 17 renamed the Defense Evasion tactic to Stealth. This guide writes "Stealth (formerly Defense Evasion)" at first mention and "Stealth" afterwards.

Why it matters

Many endpoint defenses lean on files. They scan files when they are written, match hashes, and check digital signatures. Process Doppelgänging removes that evidence on purpose. Defenders must switch to behavioral signals: a process whose image path no longer resolves on disk, memory sections with no file behind them, and payload behavior such as ransomware actions.

Researchers at enSilo published the technique in late 2017. Public vendor reporting from 2018 links it to FIN7 activity that deployed SynAck ransomware. Microsoft has deprecated TxF, but the feature still works on many Windows builds, so the technique stays relevant for defenders.

Where it fits in the attack chain

Process Doppelgänging is a sub-technique of T1055 Process Injection. A typical chain looks like this:

  1. Initial access. A malspam email carries a link or attachment. The user downloads and runs the loader.
  2. Execution. The loader starts and performs the transaction trick described in this guide.
  3. Stealth. The payload runs with no file on disk, so file-based tools miss it. This is the core of T1055.013.
  4. Privilege escalation. ATT&CK lists this tactic too, but the injected process inherits the security context of the injecting process. A privilege gain is therefore unlikely. The step matters only when the loader already runs with high rights.
  5. Payload stage. The implant or ransomware acts: it steals data, encrypts files, or spreads further.

  • TxF (Transactional NTFS): a Windows feature for transactional file operations.
  • PE (portable executable): the standard Windows program file format.
  • EDR (Endpoint Detection and Response): endpoint tooling that records process, file, and memory events.
  • SOC (Security Operations Center): the team that watches alerts and responds to incidents.
  • ETW (Event Tracing for Windows): a Windows logging framework used by many sensors.
  • FIM (file integrity monitoring): tooling that records changes to files on disk.

The same story in text

  1. Delivery. The attacker sends a malspam email with a link. The user downloads the loader. The loader is a normal file on disk at this point. Defender hint: a file-creation alert for a new executable in a user folder is the first and only file artifact.
  2. Transaction opens. The loader calls NtCreateTransaction and gets a handle to a transacted file. Windows holds every write to this file in a pending state. Defender hint: almost no telemetry exists for this step in default logging.
  3. Malicious PE is written. The loader writes the payload PE (portable executable) into the transacted file. The bytes exist only inside the pending transaction. Defender hint: antivirus file scans and FIM (file integrity monitoring) see nothing, because no persisted file appears.
  4. Image section is created. The loader calls NtCreateSection with the SEC_IMAGE flag on the transacted file. The kernel maps it as a program image in memory. Defender hint: coverage is sparse; some EDR kernel sensors or ETW (Event Tracing for Windows) providers may log an image load from a temporary path.
  5. Rollback. The loader calls NtRollbackTransaction. The transacted file vanishes from the file system. The in-memory section stays valid. Defender hint: file monitors report no deletion, because the file never persisted. This is the core evasion trick.
  6. Process and thread start. The loader calls NtCreateProcessEx with the section and then NtCreateThreadEx at the entry point. The malicious image runs as a process with no file behind it. Defender hint: the EDR flags a process whose reported image path no longer resolves on disk. This is the strongest native signal.
  7. Payload stage runs. The payload executes its task. In the 2018 FIN7 reporting the payload was SynAck ransomware; here it behaves like an implant or ransomware stage. Defender hint: a behavioral detection fires on the malicious actions, not on a file.
  8. Defender response. The SOC isolates the host, captures memory, and scans for orphaned image sections. Behavioral evidence, not file evidence, drives the case. Defender hint: containment works even when the disk holds no payload, because the process is still alive in memory.
Good practice

Watch step 5 and step 6 together. The file disappears and the process appears at almost the same time. If your tools can join those two signals in one view, analysts will understand the case much faster.

3Red Team / Hacker Perspective

This section explains how attackers use the technique and why they pick it. The goal is defensive understanding: if you know what the attacker needs, you know what to log and block.

Authorized use only

Everything on this page is for defense and lab practice. Only test techniques like this inside an isolated lab that you own, with written approval. Running these methods against systems you do not own is illegal and harmful. This guide gives conceptual API listings, not working attack code.

Why an attacker picks this method

  • No payload file on disk. File scans, hash matching, and signature checks have nothing to inspect.
  • Simple user-mode chain. The trick needs only a handful of native API calls and no kernel driver.
  • Low local footprint. Apart from the loader itself, the endpoint shows no dropped payload.
  • Works with any PE. The same chain loads an implant, a ransomware locker, or a post-exploitation agent.
  • Surprise factor. Many older tool sets assume every process has a backing file and misreport the case.

Prerequisites and conditions

  • A Windows endpoint that uses the NTFS file system, because TxF is an NTFS feature.
  • A Windows build where TxF is still enabled. Microsoft kept the deprecated API enabled through Windows 10, so older builds are the main exposure.
  • Enough rights to run a process in the user's session. Local administrator rights are not required for the basic chain.
  • A payload PE and a loader that can make the calls listed below.
  • An initial access path, usually malspam, to get the loader onto the host.

How the attack chain works, step by step

  1. Build or obtain a loader. The loader is a small program whose only job is to run the transaction chain. It may arrive as an email attachment, a dropped file, or a staged download.
  2. Open a transaction. The loader calls NtCreateTransaction and creates a transacted file handle. The file exists in a pending state that normal tools barely notice.
  3. Write the payload. The loader writes the malicious PE into the transacted file. The bytes are visible only inside the transaction.
  4. Map it as an image. The loader calls NtCreateSection with the SEC_IMAGE flag on the transacted file. The kernel parses the PE and prepares a program image in memory.
  5. Roll back. The loader calls NtRollbackTransaction. The pending file is discarded. The section, which the kernel already materialized in memory, stays valid.
  6. Create the process. The loader calls NtCreateProcessEx with the orphaned section. Windows builds a process whose image has no on-disk source.
  7. Start execution. The loader calls NtCreateThreadEx to begin running at the payload entry point. The payload stage now runs.

Common variations

  • Different payload types. The same chain loads DLL (dynamic-link library) style payloads or full EXE (executable) images; the SEC_IMAGE flag does the parsing work.
  • Second-process mapping. The transaction and section can be split across steps to reduce the chance that one callback sees the whole chain.
  • Chained evasion. Attackers pair the technique with masquerading file names or scheduled execution so the loader itself also looks benign.
  • Older transaction abuse. Some families used TxF purely for self-deleting drops, without full process injection.

Mistakes attackers make

  • Leaving the loader executable on disk in an easy-to-flag folder such as a temp path.
  • Reusing the same loader binary, so one hash match burns every campaign.
  • Letting the payload write files anyway, which hands defenders the behavioral evidence the trick tried to avoid.
  • Forgetting that a process with a missing image path is itself a loud EDR signal.
  • Testing only on the newest Windows builds and missing build-specific failures.

How it compares with Process Hollowing (T1055.012)

Both techniques end with a process that lies about its image. The details differ, and those differences change detection.

4Blue Team / SOC Perspective

This section shows what defenders can see when Process Doppelgänging runs. The short version: file evidence is gone, so behavioral and memory signals carry the case.

How defenders see it

The payload file never persists, so the usual first questions — which file, what hash, what signature — have no answer. Defenders see the technique through side effects instead:

  • A process whose reported image path no longer resolves on disk.
  • A loader that starts from a user-writable path and then spawns an unusual child.
  • Payload behavior: ransomware-style file changes, shadow copy deletion, or implant network calls.
  • Memory contents: an image section with no file behind it.

Native logging is thin. Sysmon (System Monitor) and ETW cover a few edges of the chain, and coverage differs between Windows builds. Treat missing telemetry as expected, not as proof that nothing happened.

Why it matters for the SOC

A fileless payload breaks the habit of confirming every alert with a hash lookup. Analysts must be ready to trust process context and memory. If the SOC waits for a file to triage, the ransomware stage finishes first.

The technique also changes the evidence plan. Volatile evidence, especially memory, must be captured before the host is rebooted. A reboot removes the payload entirely, and with it the strongest proof of what ran.

Finally, the detection history matters: public reporting from 2018 shows that behavioral endpoint protection was the control that caught real-world use. File-based controls alone missed it.

Endpoint logs

Collect Sysmon Event ID 1 (process creation) and Event ID 7 (image load), plus the Windows Defender operational log. Enrich process events with a check that the image path still exists on disk.

Memory

Memory scanning tools in the pe-sieve and moneta style list image sections that have no file on disk. An orphaned section is close to proof that a fileless launch happened.

Process tree context

Look at the parent chain. A loader that starts from Outlook or Word and spawns from a temp path is suspicious even before the payload does anything.

Network

The payload still needs command-and-control traffic. Proxy, DNS (Domain Name System), and firewall logs show beacons even when endpoint file evidence is absent. Watch for new processes opening outbound connections shortly after a suspicious launch.

Short triage flow

  1. Confirm the alert. Read the full process record: image path, command line, parent, user.
  2. Check the image on disk. Verify whether the reported image path still resolves. A missing path is the signature tell.
  3. Capture memory first. Take a memory image or run a scanning tool before any reboot or re-image.
  4. Isolate the host. Cut network access but keep the machine powered on so volatile evidence stays.
  5. Pull the parent chain. Find how the loader arrived: email, download, or another stage.
  6. Hunt across the fleet. Search other hosts for the same loader path, parent pattern, or missing-image condition.
Warning

Not every process with a missing image path is an attack. Patched applications, uninstalled software, and portable tools all leave deleted-but-running binaries behind. Triage these events, but tune with a known-good list before you page anyone at night.

The four samples below come from one fictional but realistic incident timeline on host FIN-WKS-114. Read them in order: loader spawns payload, payload loads images, endpoint protection reacts, ransomware staging appears.

  • Image — the path Windows reports for the new process. During Process Doppelgänging this path stops resolving on disk, because the transaction rolled back.
  • ParentImage — the loader. A temp-path parent for a payload-style child is already suspicious.
  • IntegrityLevel — Medium here; the technique does not need administrator rights for the basic chain.
  • Hashes — the hash of the loader, not of a payload file; there is no payload file to hash.
  • ImageLoaded — the file the kernel mapped. Coverage for the transacted-file load varies by sensor and build; treat its absence as normal and its presence as a gift.
  • Signed / SignatureStatus — the loader is unsigned and carries no product metadata, which fits a throwaway tool.
  • EventTime — a few seconds before the rollback. A short file-then-vanish window is the pattern to hunt.
  • DetectionCategory "Behavior" — the engine flagged actions, not a file. This is the class of detection that caught documented real-world use.
  • ProcessName — matches the orphaned process from Sample 1, which links the two records.
  • SeverityID 5 (Severe) — behavior-based ransomware alerts deserve the SOC's fast lane.
  • CommandLine — deleting shadow copies is classic ransomware staging, because it removes easy recovery.
  • ParentImage — the orphaned payload process from Sample 1 is the parent, which ties the fileless launch to destructive behavior.
  • IntegrityLevel High — vssadmin runs with the administrator user's elevated token here. The technique itself inherits the security context of the injecting process, so it grants no extra rights; this user already had them.
  • ParentImage — Word spawning an executable is the delivery-stage pattern that Sigma Rule 5 catches. This is the easiest moment to stop the whole chain.
  • Image — the loader, unsigned, in a temp path with a fake document-scan name. Both traits feed the transient-location rule.
  • ParentCommandLine — the macro-enabled document name is visible, which points the analyst to the exact email attachment.
  • Timeline value — this event is the parent record for Samples 1 and 2, so the full chain links: Word, loader, transacted file, orphaned process, staging.

One enrichment pattern ties the samples together: join process events against a software inventory, then look for creations whose image is unknown or missing. The Splunk query below shows the idea; it needs a lookup table named software_inventory with host and path fields.

Field assumptions: software_inventory maps host names to installed paths; Computer carries the host name. Adjust index, sourcetype, and lookup names to your environment. The same idea works with any asset database, not only Splunk lookups.

5.5Sigma Rules and Splunk SPL

Each rule below targets one threat from section 5.3. Every rule is followed by a matching Splunk SPL query. A mapping note connects Sigma fields to SPL fields. Each rule also lists the expected false positives, tuning guidance, and the severity used by the SOC queue. Indexes and sourcetypes are realistic defaults; adjust them to your environment.

Tag note: the Sigma tags keep attack.defense_evasion even though ATT&CK renamed the tactic to Stealth. The Sigma tag vocabulary predates that 2025 rename.

Rule 1 — Process created from a transient location

  • Mapping note Sigma Image|endswith becomes SPL wildcard matching on Image; the quoted \\ sequences match one literal backslash. EventCode: 1 maps directly to EventCode=1.
  • False positives Installers, updaters, and portable tools that run from temp or Public folders.
  • Tuning Add an existence check: enrich each hit with a lookup of known-good software paths, and alert only when the image is absent or unknown. Keep the filter list short and reviewed.
  • Severity High

Rule 2 — Image loaded from a transient or missing file

  • Mapping note ImageLoaded|contains becomes SPL substring matching with leading and trailing wildcards; Signed: 'true' becomes the NOT Signed="true" exclusion.
  • False positives Unsigned helper libraries from legitimate installers; developer and build tooling.
  • Tuning Correlate with a follow-up file-existence check on ImageLoaded; the doppelgänging case is the one where the path no longer exists seconds later. Drop known build-machine hosts from the alert path.
  • Severity High

Rule 3 — Windows Defender behavioral alert

  • Mapping note Sigma EventID maps to EventID in the Defender operational channel; DetectionName|contains becomes SPL wildcard matching on DetectionName.
  • False positives Deliberate security tests and malware sample collections on analyst workstations.
  • Tuning Exclude dedicated lab and sample-analysis hosts from paging, but keep them searchable. Join ProcessName against process events to enrich with the parent chain.
  • Severity Critical

Rule 4 — Shadow copy deletion as ransomware staging

  • Mapping note CommandLine|contains|all becomes two quoted SPL terms, which AND together; the Sigma filter_backup list becomes a single NOT clause on ParentImage.
  • False positives Scheduled backup jobs and storage maintenance tasks.
  • Tuning Keep a per-host allowlist of backup parent processes. When the parent image also lacks an on-disk file, treat the event as a confirmed destructive attack.
  • Severity Critical

Rule 5 — Office application spawning an executable in a user-writable path

  • Mapping note Both Sigma selections become parenthesized wildcard groups; SPL ANDs the two groups, which matches the Sigma condition.
  • False positives Business add-ins that launch local helpers from user folders.
  • Tuning Combine with attack surface reduction rules that block Office child processes; use this rule to find hosts where the policy has not landed yet.
  • Severity High

Rollout checklist for the five rules

  • Deploy each rule to your pipeline and confirm it parses, fires on the matching sample event, and routes to the right queue.
  • Attach the right severity and runbook link to every alert, so analysts know the first three steps without searching.
  • Build one dashboard that shows all five rules over 30 days, with host and user breakdowns for context.
  • Set review dates: rule owners re-read false positives and tuning notes every month.
  • Track the rules in version control like code, with a short change note for every edit.
  • Re-test the full set after any Sysmon config, collector, or index change.
Good practice

Ship these five rules as one change set, then test them in the same week with a safe lab replay of the eight simulation steps. Rules that have never fired on a test event are guesses, not detections.

6Real-World Case Study

This case study follows the best-documented public use of the technique: the 2018 reporting on FIN7-linked deployment of SynAck ransomware. Attack facts come from public vendor reporting. The response phases are a realistic reconstruction for teaching.

Source note

The attack facts here come from public vendor reporting, chiefly Kaspersky Securelist coverage from 2018 that described attackers using Process Doppelgänging to load SynAck ransomware, in activity attributed to FIN7. Where public reporting ends, this study clearly marks reconstruction. No invented detail is presented as verified fact.

Context

FIN7 is a financially motivated actor group, often linked by researchers to the Carbanak cluster of actors. The group is known for targeting businesses through employees and payment systems. In 2018, public vendor reporting described the group using Process Doppelgänging to load SynAck ransomware. The choice fits the group's goals: the fileless launch reduced the chance that file-based defenses would flag the locker before encryption started.

Timeline

  • Late 2017Researchers at enSilo publish Process Doppelgänging, describing the transaction, section, rollback, and process creation chain in public detail.
  • 2017 to 2018Microsoft documentation already lists TxF as incomplete and deprecated; the feature remains functional on Windows 8 and Windows 10 era builds.
  • 2018Public vendor reporting (Kaspersky Securelist) describes attacks using the technique to load SynAck ransomware, attributed to FIN7-linked actors.
  • 2018 onwardEndpoint vendors add behavioral detections for the pattern; defenders document the missing-image-path tell and memory-based checks.
  • TodayTxF stays deprecated but functional on many builds, so the technique remains a live detection topic for legacy estates.

Attack chain, as reported

  1. Initial access through the group's known lure patterns, with an employee opening the path that delivered the loader.
  2. A loader executable lands on disk; it is the only persistent file in the chain.
  3. The loader performs the doppelgänging chain: transaction, PE write, SEC_IMAGE section, rollback, process creation, thread start.
  4. SynAck ransomware runs from memory, with no locker file on disk to scan, and begins its destructive stage.

Detection point

Public reporting credits vendor behavioral detection: endpoint protection flagged the malicious behavior rather than a file. In SOC terms, the fired signals are the ones this guide builds rules for. They are: a process whose image path does not resolve, behavior-based Defender-style alerts, and ransomware staging such as shadow copy deletion. No file hash existed for the payload, so hash-based blocking alone would have failed.

Containment

Reconstruction. A realistic containment set: isolate the host from the network while keeping it powered on. Block the loader hash at mail and proxy controls. Reset credentials used on the host. Check peers for the same loader path. Memory capture happens before any reboot, because the payload exists only while the process lives.

Eradication

Reconstruction. Remove the loader file, clear any persistence the operator added around it, re-image or clean the host, and verify with a full memory scan for orphaned image sections. Because the payload never persisted, eradication focuses on the loader and on operator access, not on a payload file hunt.

Recovery

Reconstruction. Where encryption succeeded, recovery came from offline or immutable backups after the shadow copy deletion attempt. Where behavioral detection stopped the stage early, recovery was a cleanup and a monitoring period. Either way, restore from media that the attacker could not reach.

Impact and consequences

The impact pattern matches ransomware incidents of that period: encrypted files, operational downtime, and recovery costs. The security consequence worth recording is different: a technique published publicly in late 2017 was in criminal use months later. The window between public disclosure and criminal adoption was short, which argues for treating fresh research disclosures as detection backlog items, not curiosities.

Team response and communication

Reconstruction. A good response pattern for this case: the SOC pages the incident channel on the behavioral alert. The endpoint team isolates the host within minutes. The analyst records the process tree and memory evidence. Leadership receives a short written summary with impact, containment status, and next steps. One communicator holds the message, so email, chat, and phone stay consistent.

Lessons learned

  • Behavioral detection beat file-based detection in documented real-world use.
  • EDR memory inspection and image-path checks are the durable tells for fileless launches.
  • Deprecation is not removal: TxF was already deprecated, and attacks still worked.
  • Public research disclosures are attack roadmaps; detection teams should triage them fast.
  • Backups that the attacker cannot delete are what make ransomware survivable.

No single control stops a fileless launch. Defense works in layers: make delivery harder, make execution harder, and make detection certain. The table below lists controls in a practical order.

ATT&CK mitigation and detection strategy mapping

ATT&CK maps one official mitigation to this technique: M1040 Behavior Prevention on Endpoint. Some endpoint security products can block common behavior sequences that appear during process injection. The EDR rows in the controls table above are the practical implementation of that mitigation on a Windows estate.

ATT&CK also publishes a detection strategy for Process Doppelgänging on Windows, tracked as DET0544. Treat it as the canonical starting point, and pair it with the rules in section 5.5.

Home and small-office advice

Keep protection current

Use the built-in Windows protection with cloud-delivered protection turned on. Install updates quickly. Old, unpatched Windows builds are exactly where this technique works best.

Be careful with email

Do not open attachments you did not expect, even from real contacts. When an invoice or delivery note appears without warning, confirm through another channel first.

Back up offline

Keep one backup that is disconnected from the computer, such as an external drive that stays unplugged. Ransomware cannot delete what it cannot reach.

Do these first

  • Turn on EDR memory inspection and test the orphaned-image-section alert in a lab.
  • Deploy the five Sigma rules from section 5.5 and confirm each one fires on a test event.
  • Enrich process events with a file-existence or inventory check for the image path.
  • Block Office applications from spawning executables, and watch the exceptions.
  • Restore one backup end to end, on purpose, this quarter.
  • Train the SOC on the missing-image-path triage flow from section 4.
Good practice

Defensive priorities for this technique are unusual: file controls matter less, and behavioral plus memory controls matter more. When you plan coverage, spend the budget on EDR quality and response speed rather than on more file scanning.

Response checklist

  • Confirm the alert: read image path, command line, parent, and user.
  • Verify whether the image path still resolves on disk.
  • Isolate the host from the network, but keep it powered on.
  • Capture memory before any reboot or re-image.
  • Scan memory for image sections without backing files.
  • Pull the parent chain to find the delivery path.
  • Block the loader hash at mail and proxy controls.
  • Hunt the fleet for the same loader path and parent pattern.
  • Reset credentials used on the host during the window.
  • Write the incident summary with impact, containment, and next steps.
