T1055.015 ListPlanting

ListPlanting is a Windows process-injection method. It hides attacker code inside a trusted GUI (Graphical User Interface) process, such as File Explorer. In the best-known variation, the attacker never calls WriteProcessMemory. Ordinary-looking list-view window messages carry the code, piece by piece, into the target. This page explains the method, shows an animated lab simulation, and gives SOC (Security Operations Center) and detection engineering teams ready-to-adapt detections.

1Overview

A plain-language look at how ListPlanting plants code in a trusted Windows list-view control, why attackers like it, and what this page teaches.

ListPlanting is a process-injection technique for Windows. Process injection means an attacker places code inside a process that is already running, and then makes that process run the code. The injected code inherits the identity and the trust level of the host process. Security tools often trust that process, so the code hides well.

ListPlanting targets a special screen element: a list-view control. A list-view control draws a list of items, such as files and folders. Windows identifies it by the window class name SysListView32. A window class is a template that tells Windows how a kind of window behaves. The Windows desktop and File Explorer (explorer.exe) host such a control, and many other applications do too.

The attack moves in three stages. First, the attacker copies code into the virtual address space of a process that owns a list-view control. The attacker can get a handle to the SysListView32 child window with Windows API calls such as FindWindow or EnumWindows, or can copy the code with another Process Injection method. Second, the payload is written. In the best-known variation the attacker sends LVM_SETITEMPOSITION and LVM_GETITEMPOSITION messages - LVM is the list-view message family - with PostMessage or SendMessage. Each message copies 2 bytes of the payload into the control memory. The shellcode - a small piece of machine code that runs from memory, with no file on disk - builds up message by message. No call to the highly monitored WriteProcessMemory is needed. Third, the attacker sends LVM_SORTITEMS to the control. The control runs its sort routine and executes the payload as the ListView_SortItems callback, so the shellcode runs inside the trusted GUI process.

ATT&CK classifies ListPlanting as a form of message-passing "shatter attack": abuse of window messages between processes that share one desktop.

Why it evades

Data moves as normal-looking GUI chatter. The best-known variation uses no WriteProcessMemory and no CreateRemoteThread. Execution happens inside a signed, trusted process. MITRE ATT&CK (Adversarial Tactics, Techniques, and Common Knowledge) classifies this method as sub-technique T1055.015 under the parent technique T1055 (Process Injection).

Why it matters to attackers

  • Trusted execution. The code runs inside a signed process, not a suspicious new one.
  • Quiet data path. Window messages look like everyday GUI traffic.
  • Weak native logging. Windows event logs do not record window messages at all.
  • Common target. explorer.exe runs on nearly every Windows desktop.

What you will learn here

  • How the technique works, step by step, from both sides.
  • Which telemetry it leaves and which gaps it hides in.
  • Six Sigma (a detection-rule format) rules with matching Splunk SPL (Search Processing Language) queries.
  • A composite case study from purple-team testing.
  • Practical mitigations and triage habits.

Where it fits in the attack chain: ListPlanting sits in the Stealth (formerly Defense Evasion) and Privilege Escalation tactics. ATT&CK renamed the Defense Evasion tactic to Stealth in 2025, so some older tools and rule tags still use the old name. ATT&CK added this sub-technique in November 2021, which makes it newer and less reported than most injection methods. An attacker needs a foothold first, usually from a loader or a phishing attachment. After the injection, the implant can keep access, steal data, or move further inside the network. Privilege Escalation happens when the target control lives in a higher-integrity process; otherwise the gain is mostly evasion.

Written story of the eight steps

  1. Step 1 - Foothold. The operator lands on the Windows endpoint through a lab loader. It runs as an unsigned svchost.exe copy in a user Temp folder. SOC view: suspicious process creation from Temp; native logs show the loader start but nothing about injection yet.
  2. Step 2 - Window discovery. The loader enumerates windows in the session and looks for the window class SysListView32. It finds one hosted by explorer.exe. SOC view: sparse native telemetry. Windows event logs do not record window classes or window messages; only EDR (Endpoint Detection and Response) or ETW (Event Tracing for Windows) data can show this scan.
  3. Step 3 - Copy by messages. The loader sends many LVM_SETITEMPOSITION messages. Each message plants 2 bytes of the shellcode into the control memory, so no cross-process memory API is needed. SOC view: the EDR message-storm heuristic fires - thousands of LVM messages per second to a remote list-view window.
  4. Step 4 - Read-back check. The loader reads item positions back with LVM_GETITEMPOSITION messages. This confirms the payload landed in the right memory layout. SOC view: the LVM chatter continues, now with read messages. The pattern is odd for a user session and raises the risk score.
  5. Step 5 - Sort-callback trigger. The loader sends LVM_SORTITEMS to the control. The message passes the planted buffer as the ListView_SortItems callback. SOC view: the LVM stream now contains a sort message aimed at a remote list-view window. Window-message telemetry can catch it.
  6. Step 6 - Execute. The control runs its sort routine and calls the callback in the planted buffer. The shellcode now runs inside explorer.exe. SOC view: unbacked RWX (Readable, Writable, and Executable) memory executes in explorer.exe. Memory scanning flags a region with no file on disk behind it.
  7. Step 7 - Beacon. The implant now runs in a trusted, signed process. It beacons to its C2 (Command and Control) server over HTTPS (encrypted web traffic) from explorer.exe. SOC view: unusual outbound HTTPS from explorer.exe. Network telemetry ties the flow to the alerting process ID.
  8. Step 8 - Response. The SOC isolates the endpoint, captures memory, and scans GUI processes for unbacked RWX regions. Analysts tune the EDR rules that caught the message storm. SOC view: containment confirmed. The implant died with the isolate action. The memory image confirms the injected region.

3Red Team / Hacker Perspective

How an attacker thinks about ListPlanting: when it is worth the effort, what it needs, and where it breaks. Everything here is for defense work and lab practice.

Lab use only

This page exists so defenders can detect the technique. Do not run these methods on systems you do not own. Practice only inside an isolated lab virtual machine (VM), with written approval from your organization. Injecting code into real user machines is illegal in most places and will break trust.

When an attacker picks ListPlanting

  • When EDR (Endpoint Detection and Response) rules watch classic injection calls, such as WriteProcessMemory and CreateRemoteThread.
  • When the goal is a quiet implant inside a signed, trusted process.
  • When the operator already has code running in the user session, so no new privilege is needed.
  • When the target machine runs a desktop session with File Explorer open - which is nearly always.

Prerequisites an attacker needs

  • Code execution in the same user session and desktop as the target control.
  • A reachable SysListView32 window handle (a handle is an ID that points to a window).
  • An integrity level equal to or above the target process. UIPI (User Interface Privilege Isolation) blocks messages from lower-integrity senders to higher-integrity windows.
  • Position-independent shellcode (PIC): code that runs at any address because it uses no fixed addresses.
  • Knowledge of how the control lays out item text in memory.

How the attack is done, step by step

  1. Foothold. A loader runs in the user session, for example from a phishing attachment or an exposed service.
  2. Window discovery. The loader enumerates windows with calls such as EnumWindows and FindWindowEx, then reads class names with GetClassName until it finds SysListView32.
  3. Target choice. It picks a control hosted by a trusted process, classically the desktop list inside explorer.exe.
  4. Staging. It prepares small chunks of position-independent shellcode.
  5. The write. It sends LVM_SETITEMPOSITION messages with PostMessage or SendMessage. Each message plants 2 bytes of attacker data at a chosen item position. No cross-process memory API is called.
  6. Verification. It reads item positions back with LVM_GETITEMPOSITION messages to confirm the payload landed in the right memory layout.
  7. The trigger. It sends LVM_SORTITEMS to the control. The control passes the planted buffer to its sort routine as the ListView_SortItems callback, and the shellcode runs inside the trusted GUI process.

Common variations

  • Target any SysListView32 host: the desktop list, file dialogs, or third-party file managers.
  • Use SendMessage instead of PostMessage for a synchronous message flow.
  • Allocate memory in the target process with another Process Injection method first, then copy the payload into it 2 bytes per message.
  • Skip the messages entirely and plant the payload with the other injection method alone, then send only the LVM_SORTITEMS trigger.
  • Stage a small loader first, then pull the main implant from C2 (Command and Control).

Where the technique breaks

  • Non-position-independent shellcode crashes the control.
  • Shellcode that is not a valid callback crashes the control as soon as sorting runs.
  • Messages sent from a lower-integrity process fail silently under UIPI.
  • Corrupted list data confuses the user, and the control may repaint oddly or stop responding.
  • Message storms are visible to EDR heuristics even when single calls are not.
Honest context

The ATT&CK page documents one real malware example: InvisiMole [S0260]. ESET, a cited ATT&CK contributor for this technique, described it in June 2020. Beyond that example, public reporting on ListPlanting is thin. The technique is well documented in process-injection research talks and public PoC collections, and red teams use it in adversary emulation. Treat it as a real, testable method with rare confirmed in-the-wild use - and test your detections against it anyway, because the underlying primitive is simple to rebuild.

4Blue Team / SOC Perspective

What defenders actually see when ListPlanting runs: indirect artifacts, log gaps, and a triage path that starts with the strongest signal.

The hard truth first: native Windows event logs give you almost nothing here. Windows does not write an event when a window message crosses processes or when a window procedure changes. Detection therefore leans on EDR (Endpoint Detection and Response) sensors, Sysmon (a Sysinternals tool that logs rich endpoint events), memory scanning, and network telemetry. If your stack has none of those, ListPlanting is close to invisible.

Key teaching point

A storm of LVM_* window messages is visible in some ETW (Event Tracing for Windows) sessions and in EDR telemetry, but never in the Windows event log itself. Teams that only collect native logs have a blind spot exactly where this technique lives. Plan your logging around that fact.

Logs

Ship the Sysmon operational channel and EDR sensor data to your SIEM (Security Information and Event Management). Baseline which processes normally open handles to explorer.exe. Keep EDR raw events long enough for retro-hunts.

Memory

Enable scheduled and on-demand memory scans for unbacked RWX regions. For triage, capture explorer.exe memory before reboot; the injected region disappears with the process.

Network

Alert on connections from GUI processes such as explorer.exe to new external hosts. Proxy and DNS logs (DNS translates names to addresses) add the host name and reputation context.

Why it matters: ListPlanting turns your most trusted desktop process into an attack platform. Everything the implant does then carries the reputation of explorer.exe. In the attack chain it usually follows initial access and precedes persistence, credential theft, or lateral movement. Treating the explorer process as a first-class detection surface closes a real gap.

Short triage flow

  1. Validate the alert: which source process opened a handle to which target, and with which access rights.
  2. Check the call trace for unbacked frames, and check the access rights on the handle.
  3. Run or schedule a memory scan of the GUI process; look for unbacked RWX regions.
  4. Correlate: child processes from that PID, network connections from that PID, recent LVM message telemetry.
  5. If confirmed, isolate the endpoint through EDR - this kills the implant with the session.
  6. Capture memory and key artifacts before any reboot or cleanup.
  7. Record the case, tune the rules that fired (and the ones that did not), and brief the team.

5.2Threat Intelligence

Threat intelligence tells you who might use ListPlanting, how they use it, and how much you should trust each claim. Collect from several source types, analyze against your own telemetry, and apply the result to rule backlogs and test plans.

MITRE ATT&CK

The ATT&CK page for T1055.015 gives the official behavior description, tactics, and data sources. ATT&CK also publishes a detection strategy for this technique, DET0331 "Detection Strategy for ListPlanting Injection on Windows"; this page does not quote its internal details. Use ATT&CK Navigator to track detection coverage. This is your baseline source - high confidence.

Vendor reporting

EDR and antivirus vendor blogs describe injection tradecraft and occasionally window-message abuse. Treat single-vendor claims as medium confidence until a second source confirms them.

OSINT and PoC collections

OSINT (Open-Source Intelligence) includes research blogs, conference talks, and public PoC (Proof of Concept) repositories. ListPlanting is documented this way. PoC existence proves feasibility, not criminal use.

Commercial feeds

Commercial TTP (Tactics, Techniques, and Procedures) feeds tag injection behaviors across many families. Cross-check whether they name window-message methods specifically, not just "process injection" in general.

ISACs

An ISAC (Information Sharing and Analysis Center) shares sector-specific sightings. Ask peers whether their EDRs flagged message storms or unbacked call-trace frames in GUI processes - shared sightings raise confidence fast.

Internal telemetry

Your own baselines and purple-team tests are the most actionable intel. They tell you exactly what the technique looks like on your endpoints with your tooling.

Attribution honesty matters for this technique. ATT&CK documents exactly one procedure example, and public reporting beyond it is scarce. Most commodity loaders prefer other T1055 sub-techniques. Key fields to collect

Sysmon Event ID 10 (ProcessAccess)

  • SourceImage, TargetImage - who touches whom.
  • SourceProcessId, TargetProcessId - the PIDs (Process Identifiers) to correlate.
  • GrantedAccess - the requested handle rights; full-rights values matter.
  • CallTrace - the call stack; look for unbacked frames, shown as UNKNOWN(address) entries.
  • SourceUser, TargetUser - session context.

EDR window-message telemetry

  • event_type - vendor event class, for example a message-burst summary.
  • sender_pid, target_pid - message sender and receiver.
  • target_window_class - should read SysListView32 for this technique.
  • messages_per_second and top_messages - the storm shape.
  • is_remote_window - cross-process flag, the heart of the heuristic.

Event-shaped samples

The samples below come from lab exercises. Field values are illustrative; shapes match real output.

  • SourceImage - an unsigned lookalike in Temp; the classic loader shape.
  • GrantedAccess - 0x1FFFFF means near-full handle rights, enough to read and write the target.
  • CallTrace - the stack ends in UNKNOWN(1858133186), a frame with no module on disk - the signature of unbacked code.
  • TargetImage - explorer.exe, the trusted GUI process hosting the list control.
  • messages_per_second - thousands per second; human-scale list updates are far slower.
  • top_messages - position writes, position reads, then a sort message: exactly the plant-then-trigger pattern of ListPlanting.
  • is_remote_window - true means sender and receiver are different processes.
  • heuristic and risk_score - vendor scoring fields; useful for threshold tuning.
  • ParentImage - explorer.exe spawning a script host is rare and links to the injection timeline.
  • CommandLine - a DLL (Dynamic-Link Library) from a user-writable folder passed to rundll32.exe.
  • IntegrityLevel - Medium: the injected code inherits the user context, not elevated rights.
  • Hashes - forward to sandbox or reputation lookups for the follow-up report.
  • Image - the connection belongs to explorer.exe itself, not a child - a strong beacon signal.
  • DestinationIp - a documentation-range address stands in for the lab C2 (Command and Control) server.
  • DestinationPort - 443 blends with normal web traffic, so host-based context does the work.
  • Initiated - true means the GUI process started the connection.
  • memory_origin - unbacked means no file on disk owns this memory: injected code territory.
  • region_protection - RWX (Readable, Writable, and Executable) is legal for JIT (Just-In-Time) compilers but rare in GUI processes.
  • entropy - above 7 bits per byte suggests packed or encrypted content.
  • related_alerts - chain the ProcessAccess and message-storm events into one incident.

5.5Sigma Rules and Splunk SPL

Six Sigma rules follow, one per major threat. Each rule comes with a matching Splunk SPL query, a field-mapping note, false positives, tuning guidance, and severity. Sigma is an open detection-rule format; Splunk SPL (Search Processing Language) is the query language of the Splunk platform. The rule tags below use attack.defense_evasion: the Sigma tag vocabulary predates the ATT&CK tactic rename to Stealth, so the old tag value stays. Adjust index, sourcetype, and field names to your environment before you deploy anything.

  • Mapping note. The vendor schema in this example uses lowercase fields; the SPL assumes the index edr with sourcetype edr:memory_scans - rename both to your forwarding setup. The |endswith modifier becomes the trailing-wildcard "*\\explorer.exe".
  • False positives. Legitimate JIT (Just-In-Time) compiler regions in GUI-adjacent processes; vendor test harnesses.
  • Tuning guidance. Keep memory_origin: unbacked mandatory - that field removes mapped-module noise. Add a minimum region size or an entropy floor once your baseline is known.
  • Severity. Critical - unbacked executable memory in the desktop process is almost always injected code.
  • Mapping note. The Sigma list under GrantedAccess|contains becomes an OR group; the filter_known_tools selection becomes a NOT group of the same shapes.
  • False positives. EDR, backup, and RMM agents that inventory windows; app-compat shims; remote-support tooling.
  • Tuning guidance. Baseline for two weeks, then allowlist the top legitimate sources by image path and signing name; prefer alerting on sources that are unsigned or user-writable paths.
  • Severity. Medium - broad signal, high value after allowlisting.
  • Mapping note. Vendor schema in this example uses lowercase fields; the SPL assumes the index edr with sourcetype edr:window_messages - rename both to your forwarding setup. The |gte modifier becomes >=.
  • False positives. Test automation in build agents; accessibility tooling; heavy file-manager refreshes after mass file operations.
  • Tuning guidance. Learn a per-host baseline of list updates; raise the threshold until daily volume is near zero; keep is_remote_window mandatory - that flag removes most benign chatter.
  • Severity. Medium - heuristic, but paired with rule 1 it becomes near-certain.
  • Mapping note. Sigma Image|endswith list maps to an OR group of trailing-wildcard matches; EventID: 1 maps to EventCode=1.
  • False positives. Legitimate user workflows that open scripts from folders; IT self-service tools; developer machines where this is common.
  • Tuning guidance. On developer or admin workstations, require correlation with an injection signal from rules 1 to 3 within 30 minutes; elsewhere alert standalone. Add ParentCommandLine to the review pane.
  • Severity. High - standalone on office endpoints; correlated everywhere.
  • Mapping note. The private-range filter becomes a NOT group of CIDR (Classless Inter-Domain Routing) matches; Splunk handles CIDR equality in DestinationIp="10.0.0.0/8" form.
  • False positives. Shell-integrated sync clients; shell extensions with web features; token refreshes for cloud storage icons.
  • Tuning guidance. Allowlist known sync-client destination hostnames; add a newness check so only first-seen hostnames alert; join with proxy logs for the full URL (Uniform Resource Locator).
  • Severity. High - explorer calling home is rare enough to warrant fast review.
  • Mapping note. The Sigma condition not 1 of filter_* becomes explicit NOT groups in SPL; all other fields map one to one.
  • False positives. Shell extensions and preview handlers touching other applications; shell-hosted automation.
  • Tuning guidance. Start in test status; collect two weeks of counts; then allowlist the top five legitimate targets per estate and move the rest to alerting.
  • Severity. Medium - a pivot indicator that pairs well with the memory-scan alert.
Before you deploy

Every rule above needs three things: an environment fit (index and field names), a false-positive baseline (usually two weeks), and one purple-team validation run in a lab. Keep the Sigma YAML in version control and record the date and result of each test next to the rule.

6Real-World Case Study

A walkthrough of one incident from start to finish: what happened, where detection caught it, and what the team changed afterwards.

Composite scenario

This case study is a COMPOSITE. It merges events from purple-team lab exercises and public process-injection research into one teaching timeline. It does not describe a single real, named intrusion, it names no real victim, and no detail here should be quoted as verified fact about any real attack. For a documented real-world precedent, see the ATT&CK entry for InvisiMole [S0260], which ESET described in June 2020.

Context

A financial-services company runs a purple-team exercise. The goal: measure EDR (Endpoint Detection and Response) coverage against message-based injection on Windows 11 endpoints. The operator uses a lab loader that performs ListPlanting against the desktop list-view control hosted by explorer.exe. A benign implant then beacons only to a lab C2 (Command and Control) server. The exercise runs inside the corporate VPN with full SOC visibility and a pre-agreed abort phrase.

Timeline

  • 09:14The loader starts after the user opens a simulated phishing attachment. EDR logs the process creation as low severity; the SOC ticket sits unread at first.
  • 09:16The loader enumerates windows in the session and finds a SysListView32 control hosted by explorer.exe.
  • 09:19The write phase begins: a burst of roughly 4,800 LVM messages per second for about 40 seconds copies shellcode chunks into the control.
  • 09:20Read-back checks with LVM_GETITEMPOSITION style messages confirm the memory layout.
  • 09:21The loader sends LVM_SORTITEMS across the process boundary. The EDR window-message heuristic flags the sort message to a remote list-view control at medium severity.
  • 09:22The sort routine calls the planted callback and the shellcode runs. The EDR memory scanner flags an unbacked RWX (Readable, Writable, and Executable) region in explorer.exe at critical severity. This is the detection point that would have mattered in a real intrusion.
  • 09:22The implant beacons to the lab C2 over HTTPS (encrypted web traffic) from explorer.exe. Proxy telemetry records a first-seen destination.
  • 09:35A SOC (Security Operations Center) analyst correlates three signals on one host and PID (Process Identifier). The signals: the ProcessAccess event with unbacked frames, the message-storm heuristic, and unbacked-memory execution.
  • 09:44The analyst isolates the endpoint through EDR. The beacon stops within seconds, because the implant lives inside the isolated session.
  • 09:58Memory is captured before reboot. The unbacked region is confirmed and the benign shellcode is extracted for signatures.
  • 10:40Eradication: the lab loader is removed, a fake persistence value is deleted, and the test account password is reset as a precaution.
  • Next dayRecovery and tuning: the endpoint is rebuilt from a clean image, two rules get new allowlist entries, and a repeat test is scheduled for the next quarter.

Detection point - what fired and why

The critical alert came from the EDR memory scan: executable code in explorer.exe with no file on disk behind it. Two earlier signals built the story: Sysmon Event ID 10 showed a cross-process handle with unbacked frames in the call trace, and the window-message heuristic caught the LVM burst. Signature-based antivirus played no role - behavior, not signatures, carried the detection.

Attack chain in short

  1. Simulated phishing attachment runs the loader.
  2. Loader finds the list-view control in explorer.exe.
  3. LVM messages copy shellcode; read-back verifies it.
  4. LVM_SORTITEMS passes the planted buffer as the sort callback.
  5. The callback runs the implant inside explorer.exe; it beacons.
  6. SOC correlates, isolates, captures, eradicates.

Containment

Network isolation through EDR cut the beacon immediately. The analyst resisted the urge to reboot first, because reboot destroys the memory evidence.

Eradication

The loader binary and its persistence value were removed on the isolated host, and the extracted shellcode became a local IOC (Indicator of Compromise) for a retro-hunt across 30 days of telemetry.

Recovery

The endpoint was rebuilt from image, the user kept working the same day, and the exercise resumed with the improved rules for a second validation round.

Impact and consequences. Real impact stayed inside the lab: one hour of analyst time and one rebuild. In a real intrusion the same chain would have granted an attacker a quiet foothold in the most trusted desktop process, with credential theft and lateral movement as likely next steps.

Team response and communication. The SOC opened a bridge, invited the detection engineering owner, and kept one shared timeline document. The exercise lead gave the abort phrase only once containment was confirmed, so the response ran against a live-feeling incident.

Lessons learned

  • Native Windows logs never showed the injection; EDR and memory telemetry carried the whole case.
  • The message-storm rule fired first and early - keep it tuned.
  • Message-storm heuristics need per-host baselines, or busy file managers drown them.
  • Isolation before reboot preserved memory evidence that sealed the analysis.
  • Correlation by host plus PID turned three medium signals into one clear incident.
  • The team now tests this technique every quarter instead of assuming coverage.

Home and small-office advice

Keep built-in protection on

Use the built-in antivirus with real-time protection and cloud-delivered protection enabled. It ships behavior and memory rules that catch most injection attempts.

Update everything

Turn on automatic updates for Windows and your browser. Old systems lack the integrity boundaries that make message-based attacks harder.

Stay a standard user

Work in a standard (non-admin) account and enter admin passwords only when a trusted installer asks. Attackers that stay low-privilege can reach far fewer targets.

Do these first

  • Confirm EDR coverage on every Windows endpoint, with memory scanning enabled.
  • Deploy a Sysmon baseline configuration and forward it to the SIEM (Security Information and Event Management).
  • Move daily users to standard accounts; reserve admin rights for separate accounts.
  • Turn on application control for known loader locations such as user Temp folders.
  • Write the triage runbook for suspicious ProcessAccess alerts against GUI processes.
  • Add a network alert for outbound connections from explorer.exe.
  • Schedule the first purple-team test of these rules within 90 days.

Response checklist

  • Confirm the alerting process image and PID (Process Identifier) on the host.
  • Check the call trace for unbacked frames and full-rights handle access.
  • Run a memory scan of the GUI process for unbacked RWX regions.
  • Pull child processes and network connections for the same PID and time window.
  • Isolate the endpoint if two or more signals agree - do not reboot first.
  • Capture memory and export key artifacts before remediation.
  • Hunt retroactively for the same source image and window-class pattern.
  • File the case, tune the rules, and brief the wider team.
