T1055.014 VDSO Hijacking

VDSO hijacking is a Linux process injection method. The attacker overwrites a small, kernel-mapped code page called the vDSO (virtual dynamic shared object) inside a running process. When that process next asks for the time, the attacker's code runs inside it. This page explains the attack, the evidence it leaves behind, and how to detect, contain, and prevent it.

1Overview

A short, plain-language tour of vDSO hijacking: what the vDSO is, why attackers patch it, and what you will learn on this page.

The vDSO (virtual dynamic shared object) is a tiny shared library that the Linux kernel maps into every process. Programs use it to answer time questions such as clock_gettime, gettimeofday, and time. Because the kernel maps this code directly into process memory, the C standard library (libc) can read the clock without a syscall (system call), which is a slow switch into kernel mode. Almost every program calls these time functions constantly, often many times per second.

VDSO hijacking turns this convenience into an attack path. An attacker who can already write memory in a victim process finds the [vdso] mapping in /proc/<pid>/maps. The attacker then overwrites the vDSO code, usually the clock_gettime function, with small bootstrap code (shellcode). The next time the process asks for the time, the shellcode runs inside the victim. The attacker never creates a new process or thread, so there is no new PID (process identifier) to notice.

ATT&CK also notes why attackers pick this route. Memory protections may block the direct path: writing executable code into a process through ptrace (see T1055.008 Ptrace System Calls). The patched vDSO stub does not need that direct write. The stub can run syscall instructions itself, so it can open and map a malicious shared object into the process. Attackers can then steer the process to that code by patching GOT (Global Offset Table) entries. The GOT is the table that holds the absolute addresses of the library functions a process has mapped.

Skilled attackers go one step further. After the bootstrap code downloads and starts the real payload, the attacker restores the original vDSO bytes. A memory scanner that hashes (fingerprint) the vDSO will now see a clean page. This trick is called a self-healing hook, and it is the main reason this technique is hard to detect after the fact.

Why attackers like it

The vDSO is called automatically and often, so the payload runs quickly and reliably. Execution needs no thread creation and no new process. The code runs inside a trusted, long-lived daemon. Restoring the original bytes defeats naive memory hashing. The price is that the attacker needs a memory-write primitive first, which normally comes from ptrace (the Linux debugging interface) or from a write to /proc/<pid>/mem.

Good to know

The vDSO is not a normal file on disk. The kernel builds it at boot and maps it into each process, so there is no file hash to check. Integrity checks must compare the bytes mapped in memory against a clean copy saved for the same kernel version.

The same attack in text form

  1. Step 1 — Foothold. The attacker reaches a Linux server through an exposed management service and gets a shell as a service account. Nothing unusual is visible yet, because the login looks like normal automation. SOC view: a new execve by a service account that never logs in interactively is the first weak signal.
  2. Step 2 — Write primitive. The attacker picks a daemon that runs for months and will not restart. Using ptrace, the Linux debugging interface, they attach to the process and gain the ability to read and write its memory. SOC view: auditd records a successful ptrace attach. Long-running daemons are almost never debugged in production.
  3. Step 3 — Locate the vDSO. The attacker reads /proc/2041/maps. This file lists every memory mapping of the process, including the line marked [vdso] with its exact address range. SOC view: an unusual process opened another process's memory map. This is rare outside debuggers and performance tools.
  4. Step 4 — Patch the time function. The attacker writes small bootstrap shellcode over the clock_gettime function inside the [vdso] page. The daemon calls this function many times per second, so the trap will trigger at once. SOC view: the eBPF sensor fires the critical alert, a memory write landed inside the [vdso] mapping.
  5. Step 5 — Trigger. The daemon asks for the time. The patched function runs the bootstrap code inside the trusted daemon. No new process or thread was created, so process-list based tools see nothing new. SOC view: execution from the vDSO region is flagged and pairs with the write alert from the previous step.
  6. Step 6 — Payload and cleanup. The bootstrap code downloads the real payload, starts it inside or beside the daemon, and then restores the original vDSO bytes. A memory scanner now sees a clean page. This is the self-healing hook. SOC view: the integrity scanner reports a matching hash. Do not close the case; correlate with the earlier write alert.
  7. Step 7 — Beacon and load. The payload beacons to attacker infrastructure and starts mining or staging. The daemon's CPU time climbs, and new outbound traffic leaves the server. SOC view: netflow beaconing plus CPU saturation give two independent anomalies that agree.
  8. Step 8 — Response. Defenders isolate the host, hash the vDSO against a clean baseline saved for the same kernel version, harden ptrace settings, and hunt every server for the same pattern. SOC view: containment and a fleet-wide hunt turn one alert into a full scope check.

3Red Team / Hacker Perspective

How an attacker thinks about vDSO hijacking, when the technique makes sense, and where it usually fails. Everything here is described for defense and lab practice only.

Ethics and scope

This page is educational and defensive. Perform injection experiments only on lab machines you own, with written permission. Running these techniques on systems you do not own is illegal in most jurisdictions. No weaponized code is provided here; the steps below describe behavior so defenders can recognize it.

When and why attackers use it

An attacker chooses vDSO hijacking when they already have code execution on a Linux host but want their payload to run inside a trusted, long-lived process. A daemon that has run for months has no suspicious parent process, no new binary on disk, and no new entry in the process table. Injecting through the vDSO adds: automatic and frequent triggering (time queries happen constantly), no thread or process creation, and a clean memory story after the bytes are restored. The trade is that the technique is harder to spot but more fragile. It depends on exact vDSO offsets, and those change with kernel and libc versions.

How it is performed, step by step

  1. Gain a foothold. The attacker gets a shell as a service account or user on the Linux host, often through an exposed service or stolen credentials.
  2. Confirm write access. The attacker checks yama.ptrace_scope, group membership, and capabilities to see which local processes they can attach to or write via /proc/<pid>/mem.
  3. Pick a resident victim. A good target is a daemon with a long uptime, steady network role, and no restarts planned: web servers, monitoring agents, or helper daemons.
  4. Read the memory map. The attacker parses /proc/<pid>/maps and finds the line ending in [vdso]. The vDSO is an ELF (Executable and Linkable Format) image, so its symbol table reveals where clock_gettime lives; advanced attackers cache these offsets per kernel build.
  5. Patch the time function. The attacker writes small bootstrap shellcode over the function entry. The code must be position-independent because the vDSO address changes with ASLR (Address Space Layout Randomization, which moves code in memory on every boot).
  6. Wait for the trigger. On the next time query, the bootstrap runs inside the victim. The injected stub can also execute syscall instructions directly, so it can open and map a malicious shared object without calling the library functions the process normally uses.
  7. Redirect execution through the GOT. Some attackers patch GOT (Global Offset Table) entries instead of relying on the patched time function alone. The GOT stores the absolute addresses of mapped library functions, so a patched entry sends the next library call to the injected code.
  8. Restore and clean. The bootstrap copies the original vDSO bytes back so memory-integrity scanners see a clean page, then keeps the payload running elsewhere in the process or as injected memory regions.

Prerequisites and conditions

  • A memory-write primitive in the target process (ptrace attach, process_vm_writev, or /proc/<pid>/mem access).
  • Permission context: same user, root, permissive Yama scope, or CAP_SYS_PTRACE.
  • Knowledge of vDSO layout: parse ELF symbols at runtime or use offsets cached per kernel version.
  • A victim that calls time functions often, which is nearly every daemon.

Common variations

  • Write the shellcode through /proc/<pid>/mem instead of ptrace, which avoids some attach telemetry.
  • Hook gettimeofday or time instead of clock_gettime if the target calls those more often.
  • Restore the vDSO bytes immediately after the first trigger instead of after payload start.
  • Use a saved clean vDSO copy to restore byte-perfect, defeating strict baselines.
  • Redirect execution by patching GOT entries only, leaving the vDSO bytes clean so a vDSO hash check alone passes.

Where the technique fails

  • Hardened Yama settings (ptrace_scope=2 or 3) and dropped capabilities remove the write primitive.
  • eBPF sensors see the write into the [vdso] region even after the bytes are restored.
  • Offsets drift after kernel updates, so stale offsets crash the victim and create noise.
  • Strict per-kernel baselines catch even a short-lived patch window.

4Blue Team / SOC Perspective

What defenders see when vDSO hijacking happens, which artifacts matter, and a short triage flow for the moment an alert fires.

The defining event is simple: something wrote into a kernel-mapped code page. On a healthy server, nothing but the kernel ever places the vDSO, and nothing in user space should ever modify it after boot. So a write into the [vdso] region is a very high-signal alert, even though the attacker later restores the bytes. Everything else in the attack chain is supporting evidence: the write primitive before the patch, and resource or network anomalies after the payload starts.

Where to look

Telemetry sources

  • auditd: SYSCALL records for ptrace, process_vm_writev, and access to /proc/*/maps and /proc/*/mem.
  • eBPF sensors: Falco, Tracee, or Tetragon rules for writes into vDSO, vvar, or other kernel-mapped regions.
  • SIEM (Security Information and Event Management): join auditd and eBPF events with asset lists so daemon targets stand out.
  • Metrics and netflow: per-process CPU from node agents, plus flow records for beacon timing.

Host memory checks during response

  • Dump the [vdso] range from a suspect process and compare it to a clean copy for the same kernel version.
  • Look for anonymous executable regions that appeared recently inside the daemon.
  • Check /proc/<pid>/maps for unexpected writable-plus-executable pages.
  • Remember: a matching hash alone does not clear the host, because of the self-healing hook.

Why it matters and where it sits in the attack chain

VDSO hijacking maps to two tactics. As Privilege Escalation, code written into a more privileged or more trusted process runs with that process's context. As Stealth, the payload hides inside a legitimate process and the restored vDSO defeats memory checks. The write primitive usually comes from T1055.008 Ptrace System Calls or T1055.009 Proc Memory, and the initial access is typically an exposed service or stolen credentials, not the injection itself.

Triage flow when the vDSO-write alert fires

  1. Confirm the alert fields: source process, target PID, address range, and host.
  2. Check auditd for the preceding ptrace or process_vm_writev record and the maps read.
  3. Pull per-process CPU and netflow for the target daemon over the last 24 hours.
  4. Run the vDSO integrity check against the clean baseline for that kernel version; a match does not clear the host.
  5. Isolate the host if two or more signals agree; capture memory before reboot if possible.
  6. Open a fleet hunt with the SPL queries in section 5.5 to find the same pattern elsewhere.

5Detection Engineering Deep Dive

The core of this guide: control mappings, threat intelligence with honest confidence labels, a ranked threat model, real event shapes, and six Sigma rules with matching Splunk SPL. Everything is written so you can adapt it to your own SIEM (Security Information and Event Management) in an afternoon.

Detecting vDSO hijacking is a timing problem. The strongest event, the write into the [vdso] region, exists for seconds or minutes before the attacker restores the bytes. Your detection stack must therefore watch the write itself (eBPF sensors), the write primitive that enabled it (auditd), and the aftermath (resource and network telemetry). No single source is enough. The subsections below build the full picture: why the controls exist, who abuses this technique, what to prioritize, what the events actually look like, and ready-made rules.

5.2Threat Intelligence

Threat intelligence for this technique is thin, and honest teams should say so. The official ATT&CK page lists no procedure examples for this technique. That absence is notable, and it is not an omission in this guide. Public reporting describes the mechanics well, but confirmed in-the-wild use by named groups is rare. Treat the technique as a realistic Linux threat driven mostly by commodity toolkits, and keep every attribution claim labeled with its confidence level.

Sources and collection

  • MITRE ATT&CK: the free technique definition, data sources, and detection notes for T1055.014 are the baseline.
  • Vendor reporting: endpoint and cloud security vendors publish Linux injection tradecraft; collect the ones that touch ptrace, proc-mem, and vDSO behavior.
  • OSINT (open source intelligence): research blogs and public proof-of-concept repositories show the technique is implementable, which raises real-world likelihood.
  • Commercial feeds: useful for infrastructure indicators, rarely for technique-level detail on Linux injection.
  • ISACs (Information Sharing and Analysis Centers): sector peers may share sightings of resident-process injection on shared platforms.
  • Internal telemetry: your own auditd and eBPF data is the highest-value source; it tells you prevalence in your fleet.

Analysis and application

  • Analysis: score the technique on relevance (Linux servers present?), feasibility (write primitive obtainable?), and observability (can you see it?).
  • Application: feed the ranked threats in 5.3 into backlog priority, tune the rules in 5.5 with your asset lists, and report coverage gaps to the platform team.
  • Feedback loop: every true or false positive updates the tuning notes in 5.5, so the rules get cheaper to run each quarter.

Detection logic in one line each:

  • Alert when a write lands in the [vdso] region.
  • Alert when a successful cross-process memory write targets a resident daemon.
  • Alert when a non-debug tool reads another process's maps.
  • Alert when a daemon executes a binary from an ephemeral directory.
  • Treat a clean vDSO hash with no earlier write alert as normal.
  • Treat a clean hash right after a write alert as the self-healing hook, not as an all-clear.

Sample event 1: auditd record of the ptrace attach

  • syscall and exit: the call was ptrace and it succeeded, so the attacker now holds a write primitive.
  • auid (audit user ID): 4294967295 means the loginuid is unset, typical for a service account shell rather than a logged-in engineer.
  • uid: 48 is the Apache service user, confirming a daemon context is doing the attaching.
  • proc: the acting process is a plain python3 interpreter, not gdb or strace, which is the anomaly.
  • a0 and a1: request 10 is PTRACE_ATTACH and 2041 is the target daemon PID.
  • key: auditd rule tag added by the detection engineering team for fast filtering.

Sample event 2: auditd record of the maps read

  • name: the file argument shows the attacker enumerating the target's memory map to find the [vdso] line.
  • exit: a file descriptor number, so the open succeeded and the contents were readable.
  • Same pid and auid as sample 1: the two records chain into one attacker story, two minutes apart.

Sample event 3: eBPF sensor alert for the vDSO write

  • rule: a custom sensor rule name; keep the word vdso in your own rule names so the Sigma rule in 5.5 matches.
  • evt.type: the kernel call that delivered the write, here process_vm_writev.
  • target.region: the address range and its kernel label, proving the write landed inside the vDSO page and not nearby heap.
  • priority: Critical, because on a healthy host nothing ever writes into this region.

Sample event 4: aftermath, payload execution from an ephemeral directory

  • exe: the payload path hides in /dev/shm (a memory-backed scratch filesystem) under a fake kernel-worker name.
  • proc.ppid: 2041 is the daemon, so the daemon itself spawned the payload after the vDSO trigger.
  • exit: -13 (permission denied) here would still be worth triage; repeated attempts show persistence, and one success shows compromise.

5.5Sigma Rules and Splunk SPL

Six rules cover the technique end to end: the write primitive, the maps reconnaissance, the vDSO write itself, service-account abuse, payload staging, and ptrace scope tampering. Each rule is followed by a matching Splunk SPL query, a mapping note, false positives, tuning guidance, and severity. All queries assume a flat Auditbeat-style schema in index=linux_audit sourcetype="linux_audit" and Falco events in index=ebpf_sensors sourcetype="falco". Adjust index and sourcetype names to your environment. The Sigma tags below keep attack.defense_evasion, because the Sigma tag vocabulary predates ATT&CK's rename of Defense Evasion to Stealth.

Sigma 1 — Ptrace Attach or Cross-Process Memory Write to a Resident Daemon

Mapping note, false positives, tuning

  • Mapping: Sigma syscall, exe, and exit map one to one to SPL fields. Sigma's not filter_debug_tools becomes the SPL search NOT exe IN (...) with wildcards. The "resident daemon" intent is enforced in SPL by the daemon_assets lookup, which Sigma cannot express.
  • False positives: performance agents, crash collectors, and engineers debugging during incidents.
  • Tuning: maintain the debug-tool list and the asset roles lookup quarterly; add an allow-list keyed on change tickets for known profiling windows; keep earliest=-7d for hunting, run live at earliest=-15m.
  • Severity: high. A successful cross-process memory write on a server is rarely legitimate.

Sigma 2 — Memory Map Enumeration by a Non-Debug Tool

Mapping note, false positives, tuning

  • Mapping: Sigma name|startswith and |endswith collapse into the SPL wildcard name="/proc/*/maps"; the filter list matches exactly on both sides.
  • False positives: support tools, node agents, and runtimes that inspect workloads; add them to the filter with a comment and an owner.
  • Tuning: raise the map_reads threshold only after measuring a week of baseline noise; alert faster when the reader runs under an unset loginuid.
  • Severity: medium. Reconnaissance alone, but it chains directly into rule 1 and rule 3.

Sigma 3 — Write into the vDSO Mapping (eBPF sensor)

Mapping note, false positives, tuning

  • Mapping: Sigma rule|contains: vdso becomes the SPL wildcard rule="*vdso*"; evt.type maps directly; the custom sensor rule on your side must contain "vdso" in its name, which is the convention this pack assumes.
  • False positives: your own lab rules; kernel live-patching tools that touch mapped pages on exotic setups.
  • Tuning: route this rule straight to page severity with a 15-minute triage SLA; never auto-close on a later clean hash, because restored bytes are the self-healing hook, not an all-clear.
  • Severity: critical. On a healthy host this event has no legitimate source.

Sigma 4 — Ptrace from a Service Account with Unset Loginuid

Mapping note, false positives, tuning

  • Mapping: Sigma string auid: '4294967295' matches auditd's textual field; in SPL the same value is searched numerically; everything else maps directly.
  • False positives: crash handlers; some container health probes on hardened images.
  • Tuning: add known crash handlers per distro; if your estate runs monitoring agents that ptrace, move them to a dedicated auid so this rule stays clean.
  • Severity: high. A daemon context doing ptrace is the exact scenario this technique needs.

Sigma 5 — Payload Executed from an Ephemeral Directory

Mapping note, false positives, tuning

  • Mapping: Sigma exe|startswith list becomes three ORed SPL wildcards; proc.ppid in Sigma matches the flat proc.ppid field shipped by the agent.
  • False positives: CI (continuous integration) runners and build tooling; scope the rule per asset class to keep it sharp.
  • Tuning: on build servers demote to informational; on production daemons keep high; join with rule 3 by host within 10 minutes for automatic case creation.
  • Severity: high, with the highest value when the parent PID belongs to a long-running daemon.

Sigma 6 — Access to the Yama ptrace_scope Control

Mapping note, false positives, tuning

  • Mapping: exact field match on name on both sides; the filter list matches the configuration management agents your estate actually uses.
  • False positives: hardening scripts and health checks during maintenance windows.
  • Tuning: suppress during the patching window per host group; a write to this path (compare file content before and after) deserves escalation, because it directly weakens the control that blocks this technique.
  • Severity: medium; pairs with the mitigation work in section 7.

6Real-World Case Study

A complete incident walkthrough for training: timeline, detection point, containment, eradication, recovery, impact, communications, and lessons learned.

Composite scenario

This case study is a labeled composite. It blends public research on vDSO abuse with common patterns from Linux miner campaigns. Hostnames, times, and numbers are invented for teaching. Do not quote it as a real incident, and do not treat any detail as verified fact.

Context

A mid-size software company runs a small Linux estate: web servers, build runners, and internal tooling on cloud virtual machines. The platform team is three engineers. Detection coverage was auditd shipped to a SIEM, plus one eBPF sensor (Falco) piloted on 20 percent of hosts. A config-management breach started the story: a deployment key was copied off a build runner after a toolchain compromise, and the key allowed shell access to app servers as a service account.

Timeline

  • Day 0, 09:10Config-management breach. An attacker extracts a deployment key from a build runner through a dependency-script weakness. No security control fires, because the runner is outside the sensor pilot.
  • Day 1, 23:02Foothold. The key is used from a new network to reach an internal management endpoint on app-web-04 that should not have been reachable. The service account gets a shell. Auditd logs the unusual execve, but the alert waits in the queue.
  • Day 2, 02:41Write primitive. The attacker enumerates processes and attaches to PID 2041, a resident web daemon (httpd) that has run for 91 days, using ptrace. Auditd records the syscall with an unset loginuid.
  • Day 2, 02:43Recon in memory. The attacker opens /proc/2041/maps and locates the [vdso] mapping, then confirms the clock_gettime offset for that kernel build.
  • Day 2, 02:44The detection point. app-web-04 is in the eBPF pilot. The sensor fires the critical rule: a process_vm_writev landed inside the [vdso] region. The alert pages the on-call analyst.
  • Day 2, 02:46Payload start and cleanup. The patched time function runs bootstrap code, which downloads a miner from 203.0.113.10 and starts it from /dev/shm under a fake kernel-worker name. The bootstrap then restores the original vDSO bytes.
  • Day 2, 02:52Triage. The analyst correlates three records: the ptrace attach, the vDSO write, and a new execve from /dev/shm. The host is isolated through the management plane within eleven minutes of the first page.
  • Day 2, 04:30Scope check. A fleet-wide SPL hunt over linux_audit finds the same ptrace-plus-maps pattern on one more host, a stale test server. It is isolated too.
  • Day 3 to 5Eradication and recovery. Both hosts are rebuilt, the deployment key family is rotated, Yama scope is enforced fleet-wide, and the eBPF rollout is accelerated to 100 percent.

Detection point, response, and impact

Detection point

The eBPF vDSO-write alert was the single event that converted a quiet incident into an active response. The auditd records alone (ptrace, maps read) looked like noise until joined with the sensor alert by host and PID. This is the key lesson of the composite: the strongest signal exists only for a short window, so it must page a human, not wait for a daily review.

Containment

Containment came first, forensics second. The management plane quarantined the host and cut its egress to the management network only. The analyst captured memory of PID 2041 before shutdown, which preserved the injected payload region and the beacon configuration.

Eradication and recovery

Eradication was rebuild-from-image rather than clean-in-place: both hosts were reprovisioned, the key family rotated, and the exposed endpoint removed. Recovery returned service in four hours. The vDSO integrity check on neighboring hosts matched clean per-kernel baselines, which supported the two-host scope conclusion.

Impact and communications

Impact was limited to compute theft: roughly three days of CPU saturation on one host before detection, an estimated low hundreds of dollars of wasted compute, and no evidence of data theft. Communications stayed internal. Engineering leadership received a plain-language update within two hours. The service owner was notified with the isolation rationale. A customer-facing status note was judged unnecessary, because no customer data was in scope.

Lessons learned

vDSO baselining

Save a clean vDSO image per kernel version at boot from a trusted reference host. Check baselines on a schedule and after every kernel update, and never treat a single clean hash as an all-clear.

eBPF rollout

The pilot found what auditd could not. Region-level memory telemetry pays for itself; expand it to every internet-reachable Linux host first, then everywhere.

ptrace hardening

Setting yama.ptrace_scope=2 and dropping CAP_SYS_PTRACE from service units would have broken the attack chain before the injection step. Hardening beat detection on cost and speed.

7Mitigation and Defense

Controls that break the vDSO hijacking chain, ordered by what they actually prevent. The cheapest wins are configuration, not purchases.

The attack chain has three doors: the foothold, the write primitive, and the patch itself. Close the write primitive first. A host with yama.ptrace_scope=2 and daemons that run without CAP_SYS_PTRACE is a poor target, whatever the attacker's initial access was. Detection then covers the residual risk: eBPF sensors for the patch event, auditd for the primitive, and integrity baselines for verification.

ATT&CK mitigation mapping

  • M1040 Behavior Prevention on Endpoint (https://attack.mitre.org/mitigations/M1040/) is the official ATT&CK mitigation for this technique. Some endpoint security tools can block process injection by recognizing common behavior sequences during the injection process. On Linux this maps to the endpoint rows above. It covers SELinux or AppArmor confinement for daemons. It also covers eBPF-based runtime sensors that alert or block on the write into the [vdso] region. Capability removal that denies the write primitive belongs to the same mapping.

ATT&CK also publishes a detection strategy for this technique, DET0448 (Detection Strategy for VDSO Hijacking on Linux). This page does not restate its contents; the analytics in section 5 are a practical starting point.

Home and small office

Turn on automatic updates so kernel fixes land quickly. Run only services you need, and close management ports to the internet. A single Raspberry Pi or home server with default Yama settings and updated packages is already a hard target for this technique.

Small team without a SOC

Install one eBPF sensor with the vDSO rule, ship auditd to a free log service, and set a daily review habit. Enable MFA on every admin surface. Two hours of setup covers most of the detection value described on this page.

Cloud-only estate

Prefer managed runtimes where you cannot ptrace at all, use the provider's host-level threat detection, and treat any write into kernel-mapped memory as a page. Keep host login restricted to a brokered, logged path.

Do these first

  • Set kernel.yama.ptrace_scope=2 across the fleet and verify with configuration management drift checks.
  • Remove CAP_SYS_PTRACE from every service unit that does not provably need it.
  • Deploy the six auditd rules from section 5.5 and confirm records arrive in your SIEM.
  • Stand up one eBPF sensor rule for writes into the [vdso] region with paging severity.
  • Build the per-kernel vDSO baseline store and a scheduled check job.
  • Write the one-page triage runbook that joins ptrace, maps, and vDSO alerts by host and PID.

Daily habits

  • Review every critical eBPF alert within the SLA, including vDSO-region events.
  • Check new execve records from /tmp, /dev/shm, and /var/tmp on production hosts.
  • Skim ptrace and process_vm_writev records against the daemon asset list.

Weekly habits

  • Verify eBPF sensor health fleet-wide; a silent sensor is a detection gap.
  • Review the debug-tool and crash-handler filter lists for drift.
  • Run one hunt from section 5.5 and record the result, even when empty.

Monthly habits

  • Refresh vDSO baselines for every new kernel version in the fleet.
  • Purple-team one injection technique and file the detection gaps.
  • Review the daemon asset lookup table and the control coverage matrix.

Response checklist

  • Confirm the alert fields: source process, target PID, address range, host.
  • Join auditd ptrace, maps read, and eBPF write events by host and PID.
  • Isolate the host at the network layer; capture memory before reboot.
  • Hash the vDSO against the clean baseline for that exact kernel version.
  • Run the 5.5 SPL hunts fleet-wide and list every host with the pattern.
  • Rotate credentials reachable from the affected hosts, including deployment keys.
  • Verify yama.ptrace_scope and capability settings fleet-wide before recovery.
  • Write the incident note: timeline, detection point, impact, and fixes shipped.
