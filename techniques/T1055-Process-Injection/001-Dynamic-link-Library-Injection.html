T1055.001 Dynamic-link Library Injection

A dynamic-link library (DLL) is a Windows code file that programs load to reuse functions. DLL injection forces a legitimate process to load an attacker's DLL. The malicious code then runs inside trusted software, borrowing that program's rights, memory, and appearance.

What it is

The target process is tricked into calling LoadLibrary on an attacker's DLL, so the Windows loader runs that file inside the trusted process.

Why attackers use it

Code runs inside a trusted process with its rights and look, so process lists and users see a normal program name instead of the attacker's tool.

Main risks

A backdoor running inside trusted software, credential theft from process memory, and banking fraud driven from inside everyday software.

Detection focus

Remote threads that start at LoadLibrary, and DLL image loads from user-writable paths into system processes.

Contents

1Overview

This section explains dynamic-link library injection in plain words. You will learn what a DLL is, how an attacker forces a trusted program to load one, and where this trick sits in a full attack chain.

What a DLL is, in plain words

A dynamic-link library (DLL) is a Windows code file. Programs load DLLs to reuse functions instead of shipping the same code again and again. When a program wants a function from a DLL, it calls a Windows function named LoadLibrary. The Windows loader then maps the DLL file into the program's memory, connects its code and data, and makes it live.

The loader is the part of Windows that prepares code files for execution. Because the loader runs inside the target process, anything it loads becomes a real part of that process.

How classic DLL injection works

The attacker's program does not start a new process. It borrows an existing one, in five moves:

1. Pick a trusted target, for example explorer.exe. 2. Open a handle (a permission ticket) to that process. 3. Reserve memory inside the target and write the DLL's file path there. 4. Start a remote thread (a thread created in another process) whose start address is LoadLibraryA, with the path as its argument. 5. The Windows loader inside the target loads the DLL, and its DllMain entry function runs the implant.

This page describes the idea only — it is not a how-to guide.

Where it fits in the attack chain

ATT&CK lists T1055.001 under two tactics: Stealth / Privilege Escalation (TA0005 / TA0004). TA0005 was named Defense Evasion before ATT&CK v20. As stealth, the malicious code hides inside a trusted process, so process lists look normal. As privilege escalation, the code inherits the rights of the host process, which can be higher than the attacker had.

The injection itself lasts only as long as the host process. To come back after a reboot, an attacker must run the injector again — for example from a scheduled task or registry autorun. Those repeat runs are separate persistence techniques, and each one is a fresh chance for you to detect the chain.

Step 1 of 8

SOC view

Written version of the animation

  1. Step 1 — Foothold. A user opens a malicious installer from an email. The installer drops a small dropper program that runs in the user's session. Defender view: Sysmon (Microsoft's free system monitor that records detailed Windows event logs) event 1 records a suspicious new process tree starting from a temp folder.
  2. Step 2 — Stage DLL. The dropper writes malicious.dll to C:\Users\Public, a folder every user can write to. Defender view: Sysmon event 11 records a DLL appearing in a user-writable path.
  3. Step 3 — Open target. The dropper asks Windows for a handle to explorer.exe with rights to write memory and create threads. Defender view: Sysmon event 10 shows cross-process access from a temp binary.
  4. Step 4 — Write DLL path. The dropper reserves memory in the target with VirtualAllocEx and copies the DLL path string with WriteProcessMemory. Defender view: the EDR (endpoint detection and response — security software that records and blocks process behavior on the host) raises a memory-write-into-another-process alert.
  5. Step 5 — Remote thread at LoadLibraryA. CreateRemoteThread makes explorer.exe call LoadLibraryA on that path. Defender view: Sysmon event 8 shows a remote thread starting in kernel32!LoadLibraryA.
  6. Step 6 — DllMain runs. The Windows loader executes the DLL inside explorer.exe. The implant initializes. Defender view: Sysmon event 7 shows an unexpected DLL image load in a trusted process.
  7. Step 7 — Hidden activity. The implant beacons to the attacker's C2 server (command and control — the server the attacker uses to send commands) from inside explorer.exe. The user sees nothing. Defender view: a network flow with an unusual process context stands out.
  8. Step 8 — SOC triage. The analyst links the event 8, event 7, and event 10 chain, confirms the DLL, and isolates the host. Defender view: a correlated alert joins the three events and ends with host isolation.
Good practice — the chain is the detection

Each single event can be explained away. A file write, a handle, a thread — one at a time they look like noise. Linked together on one host within minutes, they are a strong DLL injection signal. Correlation is the core skill of this page.

3Red team perspective

This section explains why attackers like DLL injection, where it is used, and which parts of the classic recipe fail in practice. All details are conceptual and for defense work only.

Danger — lab only

Everything here describes published, well-documented behavior so that defenders can recognize it. Never run injection tooling on systems you do not own or do not have written permission to test. No working code is provided anywhere on this page.

Why attackers choose it

Reuse the loader. Writing shellcode (a small piece of raw machine code) by hand means fixing imports, relocations, and thread setup yourself. LoadLibrary hands all of that work to Windows for free.

Hide in a trusted host. A thread inside explorer.exe or svchost.exe inherits the host's name, rights, and network context. Analysts skim past familiar names.

Live as a module. A loaded DLL can stay small, unload when someone looks too closely, and reload later from the same file on disk.

Where it applies

Initial-access loaders use it to move their payload out of the dropper and into memory. Information stealers inject into browsers or explorer.exe to reach data quietly. Red-team implants carry "migrate"-style features that inject into a longer-lived process before a reboot. Banking trojans inject into processes that display web content.

Conceptual sequence

The classic recipe has five steps. Each step needs a specific handle right, and each step leaves its own telemetry:

OpenProcess (get a handle to the target) → VirtualAllocEx (reserve memory in the target) → WriteProcessMemory (copy the DLL path string into it) → CreateRemoteThread at LoadLibraryA → the loader runs DllMain.

The OpenProcess request needs three access rights: create thread (0x0002), VM operation (0x0008), and VM write (0x0020). Many tools simply ask for 0x1FFFFF — full control — which makes the event 10 access mask even more recognizable. Note the A in LoadLibraryA: it takes an ASCII (narrow) path string, so WriteProcessMemory must write exactly that kind of string into the target.

Step four is the quiet one, step five is the loud one: a thread born in another process that starts inside kernel32 is rare in a healthy estate.

Prerequisites

A readable path. The attacker needs write access to a folder the target can read, such as C:\Users\Public or C:\ProgramData.

Matching architecture. An x64 process cannot load an x86 DLL through LoadLibrary. Mixing this up is the most common lab failure.

Enough handle rights. The recipe needs process-access rights for memory writing and thread creation. Injecting into a higher-integrity process needs equal or higher privilege, or the SeDebugPrivilege right. Protected processes and hardened hosts refuse these requests.

Common variations

NtCreateThreadEx instead of CreateRemoteThread — the same result through a lower-level API. LdrLoadDll — the loader function inside ntdll that LoadLibrary itself calls, used to skip the usual API layer. SetWindowsHookEx — a window hook makes the target load the DLL for you. AppInit_DLLs registry values — the loader loads a DLL into GUI programs automatically, tracked separately as T1546.010 (AppInit DLLs). Reflective loading — the DLL maps itself and never calls the loader, tracked as T1620 and much quieter.

Warning — mistakes that break the injection

Four failures are classic. Wrong architecture: an x86 DLL into an x64 process fails silently, because a 64-bit target can only load a 64-bit DLL. A DLL left on disk: a free forensic artifact for responders. A protected target: Windows refuses the handle, so the recipe dies at step one. And ignoring loader-lock rules inside DllMain, which makes the implant crash inside the host and destroys the access.

4Blue team perspective

Defenders never see "DLL injection" as one event. They see a short chain of ordinary-looking events. This section maps each artifact to the log that carries it.

Visibility you need

Sysmon event 7 — every image load (an image is any file Windows loads to run, an EXE or a DLL), with signer status and path. Sysmon event 8 — remote thread creation, with the start module and function. Sysmon event 10 — one process opening another, with the access mask. Sysmon event 11 — file creation, which catches the DLL landing on disk. An EDR gives the same four views through its module-load and thread telemetry.

Key artifacts

An unknown DLL mapped into a trusted process from a user-writable path. A remote thread whose start function is LoadLibraryA or LoadLibraryW. A small unsigned file left in C:\Users\Public or C:\ProgramData. Any one of these alone is weak; together they are a signature.

Where to look

Start in the EDR: open the target process and list its loaded modules, sorted by path and signer. Then pull the Sysmon pipeline around the alert time: events 10, 8, and 7, in that order. Finish on disk: collect the DLL, check its signer and hash, and use prefetch and file timestamps to work out when it first appeared.

Why it matters and how it fits the chain

DLL injection usually sits between initial access and the attacker's real goal — credential access, discovery, or command and control. Catching step two (the file write) or step three (the handle) stops the chain before a beacon starts. Catching only step six means the implant is already live inside a trusted process.

Triage flow — six steps

  1. Validate the alert: is the event 8 thread real, and does event 7 confirm the load?
  2. Identify the source process and the exact DLL path from the event data.
  3. Confirm the DLL's hash and reputation against threat intelligence sources.
  4. Collect the DLL file itself for analysis before remediation deletes it.
  5. Isolate the host from the network while you work.
  6. Hunt the hash fleet-wide to find every other host that loaded the same file.
Good practice — collect before you clean

Isolation stops the attacker's current access, but the DLL file and its hash are your best hunting clues. Copy them somewhere safe before any antivirus quarantine or reimaging destroys the evidence.

5.2Threat intelligence

Threat intelligence turns a generic rule into a prioritized one. Use it to answer two questions: who uses DLL injection against estates like yours, and what does their tradecraft look like this year?

Sources

The official ATT&CK page for T1055.001 and its listed data sources; vendor reporting from Microsoft, ESET, and Cisco Talos; OSINT trackers such as Malpedia, abuse.ch, and ThreatFox.

Collection and analysis

Commercial feeds and sector ISACs add early warning. Internal EDR telemetry is the most valuable source of all: your own hosts show which loader families actually reach you.

Map each reported family to the five Sigma rules in section 5.5. Families that load their DLL from disk light up rules R1 and R2. Reflective loaders never touch the loader from disk, so keep R3 and R4 access monitoring on and add EDR memory scanning to the plan.

5.3Threats ranking

Five realistic threats, ranked by how often they appear and how much damage they do. Each one maps to a Sigma rule in section 5.5 and a log pattern in section 5.4.

T1 — Classic remote thread at LoadLibraryA/W High Windows

An attacker DLL path is written into a target process, then a remote thread forces the target to load it. The textbook T1055.001 move, seen in commodity loaders every week.

Preconditions
Unhardened endpoint, user-level access, no rule on Sysmon event 8.
Impact
A full implant inside a trusted process; C2 traffic under a familiar name.
Justification
Most common injection variant; the event 8 signature is precise and high-value.

T2 — Unsigned DLL from user-writable path into a system process High Windows

The Sysmon event 7 view of the same tradecraft: an unsigned DLL from a user-writable path lands inside svchost.exe, explorer.exe, or another system process.

Preconditions
Event 7 logging with signature checks enabled.
Impact
The implant lives in the host even when event 8 was missed or tuned away.
Justification
Catches injection families that skip the remote-thread step entirely.

T3 — Cross-process VM-write handle precursor Medium Windows

A process opens another process with a write-capable access mask — the setup step that makes the DLL path write possible. A precursor, not a compromise by itself.

Preconditions
None beyond event 10 logging.
Impact
Early warning; enables correlation before the injection completes.
Justification
Medium because legitimate update and backup agents trip it; strongest as a correlation signal.

T4 — LSASS access from an unusual source plus odd image loads High Windows

An unusual process opens LSASS with credential-read masks, and strange DLL loads follow. This is credential-theft staging that also uses DLL loading for its tooling.

Preconditions
Event 10 coverage of lsass.exe plus an allowlist of known agents.
Impact
Credential dumping leads to lateral movement and account takeover.
Justification
High because of the direct account-compromise risk that follows.

T5 — Signed binary side-loads an unsigned DLL from ProgramData/Public Medium Windows

A signed, trusted binary loads an unsigned DLL from a user-writable folder — the side-loading pivot that reuses the same loader logic as DLL injection (related to T1574.002).

Preconditions
Event 7 logging; knowledge of which signed binaries are abused in your estate.
Impact
Attacker code runs under a vendor name, defeating trust-based decisions.
Justification
Medium; needs path plus signer correlation to stay quiet enough to be useful.

5.5Sigma rules and Splunk SPL

One Sigma rule per threat, each with a matching Splunk SPL query and a mapping note. Rules assume Sysmon data; every allowlist needs review against your own software inventory before production.

Mapping note — the Splunk Add-on for Windows exposes Sysmon XML as EventCode; if your TA keeps the raw EventID name, swap it. The where clause keeps results seen more than twice to cut one-off debugger noise; drop it for alerting and keep it for hunting. Adapt index and sourcetype to your onboarding.

Mapping note — Sysmon event 7 natively names the loading process Image and the loaded file ImageLoaded; the Sigma rule and the SPL both use those native field names, so no renaming is needed. Sysmon writes the Signed value as the lowercase string false, which both rules match. Backslashes are doubled inside Splunk quoted wildcards.

Mapping note — GrantedAccess arrives as a hexadecimal string; keep it quoted. 0x2A is the minimal injection trio (create thread 0x0002 + VM operation 0x0008 + VM write 0x0020), and 0x1FFFFF means full control. The NOT clause mirrors filter_legit. Expect a medium alert rate; the value of this rule is correlation with R1 and R2 on the same host within minutes.

Mapping note — replace the two allowlist entries with the agents that legitimately touch LSASS in your estate; ask the owning team before adding each one. Correlate hits with event 7 image loads from the same SourceImage within ten minutes to see the DLL-loading behavior this threat describes.

Mapping note — Sysmon writes the Signed value as the lowercase string true or false; some TAs cast it to boolean, so verify with eval lower(Signed) if you get zero results. Replace the signed-name list with the updaters that actually exist in your estate, and prune names for software you have uninstalled.

Good practice — validate the rules in a lab

Load a harmless test DLL into a sandbox host with a lab-only injection simulator once a year and confirm that R1, R2, and R3 all fire on the same run. A rule that has never fired in a controlled test is an untested rule.

6Real-world case study

A hospitality-industry intrusion in the style reported for FIN7 / Carbanak, rebuilt as an educational reconstruction from public vendor reporting. Hosts, users, and times below are illustrative, and no detail here is operational.

Warning — educational reconstruction

This case study is based on public reporting and simplified for teaching. It does not describe one specific victim, and no detail here is operational.

Context

The victim ran hotels and restaurants. Groups reported as FIN7 / Carbanak operators targeted exactly this data: payment-card numbers live briefly in point-of-sale (POS) terminal memory, and their tools scraped that memory. The intrusion team phished office staff first, then moved toward the POS network. DLL injection was the bridge. Office-side tooling injected a DLL into svchost.exe on a shared server. From there the implant lived on a machine nobody suspected and reached systems the office network could touch.

Timeline

  1. Day 0 · 09:14 A finance employee opens a phishing email with a malicious .lnk shortcut. One click runs a command that downloads the first-stage dropper.
  2. Day 0 · 10:02 The dropper stages payment_utils.dll into a user-writable folder on a file server it reached through the stolen session.
  3. Day 0 · 10:05 The dropper injects the DLL into svchost.exe on that server using a remote thread at LoadLibraryA.
  4. Day 1 · 14:20 The implant loads a POS memory-scraping module from the attacker's staging server and starts collecting card data from reachable terminals.
  5. Day 2 · 22:47 Staged card data is packed and queued on the staging server.
  6. Day 3 · 03:10 Data is exfiltrated. The same pattern repeats against two more sites over the following weeks.
Danger — the detection point that was missed

The injection at Day 0 · 10:05 produced a Sysmon event 8: a remote thread starting in LoadLibraryA inside svchost.exe. A rule existed and it fired. The alert then sat in an unowned queue for weeks. The chain — event 10, then 8, then 7, within three minutes on one server — would have been a simple, certain positive.

Detection point

The strongest signal was the event 8 plus event 7 pair on a server that never loads user DLLs. A secondary signal was svchost.exe opening outbound connections to a hosting provider it had never contacted before.

Containment

Once found, the team isolated the affected server and the POS segment, blocked the staging domain at the web proxy, and disabled the phished account. Injection stops the moment the host process is cut off from its operators.

Eradication

Analysts pulled the DLL and the scraping module, removed the scheduled tasks the group had added, rebuilt the two affected servers, and reimaged POS terminals out of caution rather than wait for proof on each one.

Recovery

Services returned segment by segment with egress filtering in front. The team ran a two-week enhanced-monitoring window and replayed historic logs against the new event 8 plus event 7 correlation to prove the estate was clean.

Impact

Payment-card fraud followed within weeks. The company faced a forensic investigation, card-brand fines, mandatory monitoring periods, and — hardest to rebuild — the trust of guests and partners.

Team response and communication

Security, IT, legal, and payments ran a daily joint bridge. Updates went to executives twice a day in plain language: what is contained, what is unknown, what happens next. The POS vendor and the acquiring bank were told early, which reduced friction later.

Lessons learned

Segment POS. Cardholder systems must not share a network path with office systems; this intrusion crossed in hours. Correlate EID 8 with EID 7. One event is arguable; the pair on one host within a minute is not. Filter egress. Only a handful of destinations were needed to stage and steal data; allowing only those destinations would have cut the operation off early.

Home and small office

Keep the built-in antivirus turned on and updated. Install operating-system updates within days, not months. Avoid pirated software and cracked installers — they are the most common carriers of injection loaders. Keep one offline backup of important files and test restoring it twice a year.

Good practice — measure the layers

Once a quarter, run a benign lab DLL-load test on a sandbox host and check that the event 8 alert, the event 7 view, and the egress log all fired. A control you cannot demo is a control you do not have.

Warning — alert fatigue is the real adversary

Seven of these twelve mistakes end the same way: a real alert exists, but nobody trusts or reads it anymore. Every tuning change should make the next true positive easier to see, not just make the queue shorter.

Daily habits

Review new event 8 alerts against the allowlist. Check that Sysmon forwarders are alive. Skim per-process egress for system processes that rarely talk.

Weekly habits

Track false-positive counts per rule and tune the top offender. Read one loader family report and map it to your rules. Spot-check one host's loaded modules by path and signer.

Monthly habits

Refresh allowlists against the software inventory. Test the isolation step of the runbook. Report detection coverage for T1055.001 to stakeholders.

9Cheat sheet and quick reference

One screen for the wall: the key facts, the five rules, the first thirty minutes of a response, and where to read more.

Key facts

ID
T1055.001 — Dynamic-link Library Injection
Parent
T1055 Process Injection
Tactics
Stealth / Privilege Escalation (TA0005 / TA0004)
Platform
Windows
Permissions
User
Core signal
Remote thread at LoadLibrary plus a DLL load from a user-writable path

Top 5 detections

  1. R1 — remote thread at LoadLibrary (event 8)
  2. R2 — unsigned DLL from user path into a system process (event 7)
  3. R3 — cross-process VM-write handle (event 10)
  4. R4 — LSASS access from an unusual source (event 10)
  5. R5 — signed updater side-loads an unsigned DLL (event 7)

Response checklist — first 30 minutes

  • Validate the event 8 plus event 7 chain on the alerting host.
  • Isolate the host from the network.
  • Recover the DLL file and its hash before cleanup tools run.

Response checklist — first 24 hours

  • Hunt the DLL hash fleet-wide in the EDR and the SIEM.
  • Review egress logs from the host for the beacon period.
  • Rotate credentials exposed on the host, starting with the logged-on user.
