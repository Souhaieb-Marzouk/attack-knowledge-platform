T1055.008 Ptrace System Calls

Ptrace System Calls is a Linux way to inject code into a running process. One process attaches to another, stops it, changes its memory and CPU registers, and lets it run again. Attackers use this to hide their code inside a trusted program, so no new file ever appears on disk.

1Overview

What this technique is, why attackers like it, and what you will learn on this page.

ptrace means "process trace". It is the Linux debugging API (Application Programming Interface) - the set of functions a debugger uses to watch another program. One process, the tracer, attaches to another process, the target. While attached, the tracer can stop the target, read and write its memory, and read and write its CPU registers. The kernel provides all of this through the ptrace system call (a system call, or syscall, is how a program asks the kernel to do work for it).

Attackers use those same normal-looking calls for a harmful goal. First they stop a trusted, long-running process. Then they write a small payload into its memory. A payload of this kind is called shellcode: machine code that can run from almost any memory address. Next they point the instruction pointer at the payload. RIP is the CPU register that holds the address of the next instruction. Finally they let the process continue. The payload now runs inside the trusted process. The process name, the file on disk, and the open network ports all still look normal. This is why the technique belongs to Process Injection (T1055). It serves the Stealth tactic (formerly Defense Evasion) and the Privilege Escalation tactic. In 2025, ATT&CK version 17 renamed the Defense Evasion tactic to Stealth. This page uses the new name, and older tools and Sigma tags still carry the old one.

Why attackers like it

  • The payload runs inside a process that defenders already trust.
  • No new file is written to disk, so file-based antivirus sees nothing.
  • Linux has no loud CreateRemoteThread equivalent, so classic Windows-style injection alerts do not exist here.
  • It pairs well with sibling sub-techniques: writing to /proc/pid/mem (T1055.009) and vDSO (virtual Dynamic Shared Object) hijacking (T1055.014) use similar memory-write steps.

What you will learn here

Where it fits in the attack chain

Attackers usually get the first foothold with valid accounts, for example a stolen SSH (Secure Shell) key. Ptrace injection then gives them a hiding place inside a trusted process. After that they steal data or reach a command and control (C2) server. The SOC (Security Operations Center) often sees the first and last steps but misses the middle one - this page fixes that.

Written story - the same 8 steps

  1. Step 1 - Login with a stolen key. The attacker logs in to the build server with a stolen SSH key that belongs to the ci-deploy service account. SOC view: a service account logs in from an unusual IP address, outside the build window.
  2. Step 2 - Process discovery. The attacker lists processes and reads /proc to find a daemon that stays up for weeks. SOC view: a burst of process-listing commands from a service account looks like discovery.
  3. Step 3 - PTRACE_ATTACH. The attacker calls ptrace with PTRACE_ATTACH. The kernel stops the daemon and names the attacker as its tracer. SOC view: auditd records a ptrace system call from an unexpected binary.
  4. Step 4 - Register reads. With PTRACE_GETREGSET the attacker reads the registers, including RIP, the next-instruction address, to plan where the new code can live. SOC view: a tight attach-wait-read chain does not match normal debugging.
  5. Step 5 - Shellcode write. The attacker writes shellcode into daemon memory with PTRACE_POKEDATA or process_vm_writev. No file touches the disk. SOC view: the eBPF sensor reports a cross-process memory write into the daemon.
  6. Step 6 - Redirect and release. The attacker points RIP at the shellcode and detaches. The daemon resumes and now runs attacker code inside a trusted process. SOC view: EDR (Endpoint Detection and Response) flags execution from a memory region that no file backs.
  7. Step 7 - Beacon. The injected code calls out to the attacker C2 server while wearing the good name of the trusted daemon. SOC view: a rare outbound connection to a new IP address.
  8. Step 8 - Response. Defenders verify kernel.yama.ptrace_scope, hunt older auditd events, isolate the host, stop the daemon, and rotate the exposed keys. SOC view: containment in order - isolate, collect, clean, recover, rotate.

3Red Team / Hacker Perspective

How attackers use ptrace injection, and how defenders can rehearse the same steps safely in a lab.

Defense and lab use only

Everything in this section exists for defenders and students. Run commands only against test machines that you own, inside an isolated lab network. Using these steps against systems you do not own is illegal in most countries. The code samples are incomplete on purpose: they teach the concept, they are not a working attack tool.

When and why an attacker picks this technique

Ptrace injection becomes attractive after an attacker already has a shell on a Linux host - for example through a stolen SSH key, a webshell, or a weak service. Instead of dropping a new binary on disk (a step that file scanners see), the attacker moves into a process that is already allowed to run. That process is also already allowed to talk to the network. On servers that run for months, a daemon is a quiet and stable home.

It also helps with privilege goals. Sometimes the attacker's account runs as the same UID (user identifier) as a more privileged service. Sometimes the attacker holds CAP_SYS_PTRACE. In both cases the injection hands over the service's view of the world: its open files, its credentials in memory, and its network position.

Preconditions an attacker needs

Access conditions

  • Code execution on the host: a shell, a webshell, or compromised automation.
  • The same UID as the target process, or root.
  • A permissive kernel.yama.ptrace_scope: 0 allows any same-UID attach, 1 (the common default) allows only child processes, 2 needs CAP_SYS_PTRACE, 3 blocks ptrace for everyone.
  • CAP_SYS_PTRACE overrides the scope=1 limit and is the only way to attach at scope=2. Only scope=3 blocks attach for everyone. Containers that leak this power by mistake are a common finding.

Good target choices (from the attacker's view)

  • Long-running daemons: web servers, CI (Continuous Integration) agents, database processes.
  • Processes with network access, so injected code can beacon without strange new sockets.
  • Processes nobody restarts often, because the injection dies with the process.

The attack flow, step by step

  1. Get a foothold. Log in with a stolen key or abuse a vulnerable service.
  2. Enumerate. List processes with ps or by reading /proc; pick a daemon that is old, chatty, and trusted.
  3. Attach. Call ptrace(PTRACE_ATTACH, pid) or use PTRACE_SEIZE. The kernel stops the target and records the attacker as its tracer.
  4. Read the layout. Use PTRACE_GETREGSET or PTRACE_GETREGS to read RIP and the other registers; read /proc/pid/maps to find a code cave - an unused memory region big enough for the payload.
  5. Write the payload. Copy position-independent shellcode into the cave with PTRACE_POKEDATA, process_vm_writev, or a write to /proc/pid/mem (that variant is T1055.009).
  6. Redirect execution. Set RIP to the payload address with PTRACE_SETREGS or PTRACE_SETREGSET.
  7. Release. Call PTRACE_DETACH or PTRACE_CONT. The daemon resumes - now running attacker code inside itself.
  8. Hold on. The payload beacons out and hides behind the daemon's good name until the process restarts.

Lab-only examples

The snippets below show the shape of the technique. They stop early on purpose and only work inside a lab VM (virtual machine) where kernel.yama.ptrace_scope is 0 and you own every process.

Common variations

PTRACE_SEIZE instead of ATTACH

SEIZE takes control more gently and supports live tracing without a hard stop. The detection picture stays the same: it is still a ptrace call with a distinctive first argument.

process_vm_writev as the writer

The same payload placement without a full attach. Some injectors also read memory with process_vm_readv instead of PTRACE_GETREGS. Writing through /proc/pid/mem is the sibling sub-technique T1055.009.

vDSO hijacking

T1055.014 patches the small shared code page the kernel maps into every process. It uses ptrace or process_vm_writev as its write primitive, so the same telemetry can catch both.

Injection from inside containers

A container that gets CAP_SYS_PTRACE can reach processes beyond its own boundary. This turns one weak container into a host-wide problem, which is common on shared build machines.

Mistakes attackers make (and detectors should watch for)

  • Forgetting waitpid after attach: the injector touches registers too early and fails.
  • Choosing a target that crashes under modification - a dead daemon is a loud detector.
  • Leaving the tracer attached: TracerPid in /proc/pid/status then names them.
  • Running the injector from /tmp under a random name - a gift for auditd rules.
  • Ignoring Yama: the blocked attempt still shows up as a failed ptrace call, which is evidence too.

4Blue Team / SOC Perspective

What defenders see, which artifacts the technique leaves behind, and a short triage flow for the first hour.

The SOC (Security Operations Center) rarely sees the injection moment directly. It sees the edges: a strange login before it, and a strange connection after it. The middle - the ptrace calls themselves - shows up only if the host logs syscalls with auditd or an eBPF sensor. That is why this technique is hard: the pages before and after the crime are logged by default, but the crime itself needs extra sensors.

Where to look

Logs

auditd for ptrace and process_vm_writev syscalls; sshd auth logs for the entry point; SIEM dashboards that join them by host and time.

Memory

Live response: check TracerPid, then capture the daemon's memory if your process allows it. EDR memory scans find code without a file backing.

Network

Netflow and proxy logs: a new destination IP from a server VLAN is rare and worth a look, especially port 443 from a daemon that had no egress before.

Quick win

On any Linux host you can answer "is this process being traced?" with one command: grep TracerPid /proc/2147/status. A non-zero result means someone is attached. Put this in your live-response runbook.

Field to know: auid

auid is the audit user ID: the user who logged in and started the process chain. It survives UID switches and sudo. A ptrace call with auid=4294967295 means "no login session at all" - typical for cron jobs, or for a compromised daemon doing the injecting.

First-hour triage flow

  1. Validate the alert: host, caller binary, target process, and exact time.
  2. On the host, check TracerPid for the target and read /proc/<pid>/maps for odd regions.
  3. Pull auditd records for that host in a 30-minute window around the event.
  4. Check kernel.yama.ptrace_scope - a value of 0 tells you the host was open to this attack.
  5. If confirmed: isolate the host, capture memory, and stop the daemon.
  6. Rotate the exposed keys, then rebuild the host from a trusted image.

5.1Regulation Mapping

Ptrace injection hides malicious code inside trusted processes on systems that hold customer, patient, cardholder, or company data. Auditors do not test for ptrace directly. They test whether you log, monitor, and harden the systems that could face it. The controls below map that duty onto this technique.

Turning these controls into evidence is simple once you see the pattern. Each control maps to a check. Configuration management exports the yama.ptrace_scope value for every host. The SIEM shows that the ptrace rules are deployed and firing. The ticket system shows that a person reviewed the alerts. Collect those three artifacts per host class and you can answer an auditor for GDPR, HIPAA, ISO, SOC 2, PCI DSS, and NIST at the same time. Review the mapping twice a year, because sensor and control names change.

5.2Threat Intelligence

Good threat intelligence for this technique answers two questions: who injects code on Linux hosts, and what does that behavior look like in logs. Names change; the syscall pattern does not. Build your picture from the four source families below, then check them against your own telemetry.

MITRE ATT&CK and vendor reporting

Start with the official ATT&CK entry for T1055.008, then read vendor reports about Linux malware. Vendor blogs often describe loader behavior without naming the syscall - read for the pattern, not the brand name.

OSINT and public code

OSINT (open-source intelligence) includes research blogs and public proof-of-concept (PoC) repositories. Small ptrace injectors are public, and reading them shows which syscalls real code touches - perfect input for detection logic. Never deploy them outside a lab.

Commercial feeds and ISACs

Commercial threat feeds add observed infrastructure and sample hashes. An ISAC (Information Sharing and Analysis Center) shares what peer companies see. Filter both to Linux endpoint telemetry so the signal stays relevant to this technique.

Internal telemetry

Your own auditd and eBPF data is the best source you have. It defines the normal debugging baseline per host class - and that baseline is exactly what your detection rules need for tuning.

Honest note on attribution

ATT&CK documents exactly one procedure example for this sub-technique: the PACEMAKER malware, listed first below. Beyond it, public reporting that names ptrace specifically is thin. Few sources confirm which groups used this exact sub-technique, and memory-injection stories often blur ptrace with /proc/pid/mem writes. The table below shows confidence levels on purpose. Where evidence is weak, we say so - do not copy these claims into your own reports without the same care.

Use this intelligence the practical way. Turn each reported pattern into a detection idea (section 5.5 has six), then test the idea against your own baseline before you deploy it. Analysis means pulling the exact syscalls and preconditions out of each report. Application means turning them into rules or hardening checks. Track actor names in your threat register, but let the syscall-level behavior drive the rules - behavior survives rebranding, group names do not.

How to use this ranking

Build detections for the top three rows first, because they share one telemetry set: auditd records for ptrace and process_vm_writev. The bottom row then tells you what to allowlist so those detections stay quiet and useful.

Turn the logging on with two auditd rules. The commands below are for a lab host first, then roll them out with your configuration management. On production, prefer persistent files under /etc/audit/rules.d/.

Event example 1 - ptrace attach from an unknown binary

This is the record you want to alert on. The caller is a strange binary in /tmp, the caller has no login session, and the target is a long-running daemon.

  • syscall: "ptrace" with a0: "0x10" - an attach request (PTRACE_ATTACH), not a read.
  • exe: "/tmp/.cache-loader" - the caller is not a debugger and hides in a world-writable directory.
  • auid: 4294967295 - no login session behind the caller, so a shell user did not start it.
  • exit: "0" - the attach succeeded; the daemon is now stopped and traced.
  • target.pid: 2147 - the victim process, which enrichment will name as the ci-runner daemon.

Event example 2 - eBPF sensor flags the injection

An eBPF sensor such as Falco evaluates kernel events directly. Its output is a ready-made alert with the fields your incident ticket needs.

  • rule - the sensor policy that matched; keep the wording stable so SIEM rules stay simple.
  • priority: "Critical" - the sensor already ranked it; your Sigma rule can filter on it.
  • output - a human-readable sentence with caller, user, and target; copy it into the ticket.
  • tags - includes the ATT&CK mapping, which makes dashboards trivial.

Event example 3 - EDR sees code running from unbacked memory

After the detach, the daemon executes the payload. EDR (Endpoint Detection and Response) memory scanning sees code that no file on disk backs, and the same alert often shows the new network destination.

  • process.name: "ci-runner" - the trusted daemon is now the one running the code; that inversion is the story of this technique.
  • threat.technique.id: "T1055.008" - the vendor already maps the alert; use it for ATT&CK coverage reports.
  • network.destination.ip - joins the endpoint story to the network story in one record.
  • event.severity: 88 - tune thresholds so this outranks everyday policy noise.

Event example 4 - a blocked ptrace attempt

On a hardened host the kernel refuses the attach. The attempt failed, but the record still proves someone tried - keep it and hunt it.

  • exit: "-1" - the kernel said no; Yama or seccomp did its job.
  • target.pid: 771 - a process the updater has no business touching.
  • exe points to a signed vendor path - a good example of a false positive to allowlist after review.
  • Compare across hosts: the same attempt succeeding somewhere means that host lost its hardening.

Detection logic in one sentence per threat

  • Hidden implant: alert when a ptrace attach arrives from any binary that is not on the host class debugger allowlist.
  • Miner loader in CI: alert when a build daemon itself calls ptrace or process_vm_writev.
  • Open scope: alert on configuration drift when kernel.yama.ptrace_scope drops below the approved value.
  • Insider misuse: alert when a user account attaches to a daemon owned by a different account.
  • Benign lookalikes: allowlist gdb, strace, crash handlers, and APM (Application Performance Monitoring) agents by host class, then alert on everything else.

5.5Sigma Rules and Splunk SPL

Six Sigma rules cover the threats from section 5.3. Each rule is followed by a matching Splunk SPL query, a mapping note, false positives, tuning guidance, and a severity. The log source for rules 1 to 5 is auditd in Auditbeat-style output; rule 6 reads Falco eBPF findings. The Sigma tags keep attack.defense_evasion, because the Sigma taxonomy predates the ATT&CK v17 rename to Stealth.

Field names follow Auditbeat-style auditd output. Adjust index and sourcetype names to your environment.

Mapping note
Sigma fields keep their names in SPL: syscall, a0, proc.name, exe, auid, uid, target.pid. The Sigma condition becomes the NOT proc.name IN (...) filter.
False positives
Debugger use by developers and support engineers; APM agents, crash handlers, and profilers that attach to processes by design.
Tuning guidance
Scope the rule to server host classes first. On auditd setups that log decimal arguments, match a0=16 instead of 0x10. Add your profiling agents to the filter list after a two-week baseline.
Severity

6Real-World Case Study

A composite incident that puts every detection from section 5 into one story, from the stolen key to the lessons learned.

Composite scenario

This case study is a composite: it merges patterns that appear in public vendor reporting about Linux miners with common incident response experience. It does not describe one confirmed intrusion, and it names no real company. Times, host names, and IP addresses are examples in the reserved documentation ranges (for example 203.0.113.x). For one documented real-world use of ptrace against a victim process, see the PACEMAKER example in section 5.2. The story below stays composite.

Context

A software company runs a build farm of twelve Linux servers. Each server runs a CI (Continuous Integration) agent called ci-runner that stays up for months. A developer laptop was stolen. The laptop held an SSH (Secure Shell) private key named deploy-2024 that could log in to the build farm as the ci-deploy service account. The build hosts had kernel.yama.ptrace_scope=0 because an old debugging tool needed it years ago. Nobody had auditd rules for ptrace until after this incident.

Timeline

  • 02:38Build server build-srv-04 accepts an SSH login for ci-deploy from an IP in a country the team never works from. The auth log shows public-key auth with key deploy-2024.
  • 02:41The session runs a burst of ps and /proc reads and settles on ci-runner, a daemon that has been up for 71 days.
  • 02:43An unknown binary at /tmp/.cache-loader calls ptrace(PTRACE_ATTACH) on the daemon. The new auditd ptrace rule fires here - this is the detection point.
  • 02:44Register reads, a memory write into the daemon, register redirect, detach. The eBPF sensor logs a cross-process write; no memory-scanning EDR rule exists yet.
  • 02:45The daemon opens a TLS (Transport Layer Security) connection to 203.0.113.77 - a destination no process on the host has contacted before. Netflow stores it; no alert exists for it.
  • 09:15The morning SOC analyst reviews the auditd alert, sees the /tmp caller and the daemon target, and opens a priority 1 (P1) incident. The host is isolated at the network switch.
  • 11:30The daemon is stopped after its memory is captured. The stolen key deploy-2024 is revoked, and two more keys on the same laptop are rotated as a precaution.
  • Next dayThe host is rebuilt from the golden image with kernel.yama.ptrace_scope=2, and the Sigma rules from section 5.5 ship to the whole build fleet.

Attack chain

Stolen key (valid accounts) to service login, process discovery, ptrace attach, register read, memory write, execution redirect, and a beacon from inside the trusted daemon. Each step except the login left a syscall or network record.

Detection point

The auditd rule for ptrace fired on the attach at 02:43: caller exe=/tmp/.cache-loader, auid=4294967295, target ci-runner. Two independent confirmations followed: the eBPF cross-process write, and the rare outbound destination.

Containment

Isolate first: the switch port for build-srv-04 was disabled within 20 minutes of the ticket. Capture second: the daemon's memory was snapshotted before anyone stopped the process.

Eradication

The injected code lived only in daemon memory, so stopping the daemon removed it. Responders searched the other eleven build hosts for the same caller path and ptrace pattern; two more hosts showed the blocked-attach signature and were rebuilt too.

Recovery

The host was rebuilt from the golden image, ptrace_scope=2 became the fleet standard, and the revoked key was replaced with a short-lived certificate. Builds resumed the same afternoon.

Impact

No customer data left through this path. The attacker burned a stolen key, lost the foothold in under seven hours, and got no builds out of it. Engineering time was the main cost: about 30 person-hours across SOC, platform, and identity teams.

Team response and communication

One incident channel, one scribe, updates every 30 minutes. Leadership got a plain-language summary: what happened, what we do not yet know, and the two decisions needed (isolate the farm, rotate all deploy keys). Support teams got a short note so they would not answer customer questions with guesses.

What nearly went wrong

The on-call almost restarted the daemon before the memory capture. The runbook now says it in bold: capture memory first, then stop the process. The stolen laptop was also still trusted in the VPN - a second key rotation closed that gap.

Lessons learned

Yama hardening

The old ptrace_scope=0 setting from a forgotten debugging tool made the whole fleet injectable. Fix the debugging workflow instead of opening the kernel knob, and enforce the value with configuration management.

auditd coverage

Two auditd rules found in seconds what file scanning would have missed for weeks. Add ptrace and process_vm_writev rules to the baseline image, not to individual hosts.

eBPF sensor rollout

The eBPF sensor logged the cross-process write but nobody watched its output. A sensor without a routing plan is a hard drive with evidence on it. Give every sensor an owner and a queue.

Check and set the Yama policy (lab first, then fleet)

If you run a small office or a home lab

Harden what you have

Set ptrace_scope to 2 on your Linux machines, update the system weekly, and do not run random binaries as root. That alone stops most of this technique.

Watch your keys

Keep one SSH key per device, use a passphrase, and remove old keys from servers you no longer log in to. A stolen key is how this story starts.

Back up and isolate

Keep offline backups of anything important, and keep lab machines off your main network. If a box acts strange, pull its cable first and ask questions after.

Do these first

  • Measure kernel.yama.ptrace_scope across every Linux host today; you cannot fix what you have not counted.
  • Deploy the two auditd rules from section 5.4 in the golden image.
  • List every container and service unit that holds CAP_SYS_PTRACE and remove it where you can.
  • Inventory service accounts with valid SSH keys and set a rotation date.
  • Ship Sigma rules 1 to 4 from section 5.5 to your SIEM and silence the known debugger allowlist.
  • Add "capture memory before stopping the process" to your Linux response runbook.

Know your normal first: a two-week baseline of who calls ptrace per host class turns a noisy rule into your best Linux injection detector.

Habits that keep the detections honest

Daily

  • Review high-severity ptrace alerts and close them with a reason.
  • Check log source heartbeats: auditd and sensors must be shipping.
  • Skim new outbound destinations from server VLANs.

Weekly

  • Compare yama values across the fleet against the standard.
  • Tune the noisiest rule and record why.
  • Read one vendor report on Linux threats and extract one detection idea.

Monthly

  • Purple-team one injection step in the lab and measure the gap.
  • Review the allowlist: remove entries nobody owns.
  • Rotate service keys and export the compliance evidence from 5.1.

Response checklist

  • Confirm the alert: host, caller binary, target process, exact time.
  • Run grep TracerPid /proc/<pid>/status on the host.
  • Pull auditd events for the host in a 30-minute window around the alert.
  • Check kernel.yama.ptrace_scope on that host.
  • Isolate the host if the injection is confirmed.
  • Capture the daemon's memory, then stop the daemon.
  • Rotate the exposed SSH keys and tokens.
  • Rebuild from a trusted image before returning the host to service.
