T1055.005 Thread Local Storage

Thread local storage (TLS) is a Windows feature that gives each thread its own private data slots. Every program can also register TLS callback functions, and the Windows loader runs them before the program's main entry point. Attackers abuse these callbacks so their code executes very early — before most security tools attach — or to inject code into other processes.

What it is

Malicious code placed in a program's TLS directory runs before the program's main function. The visible program logic looks untouched, yet the attacker's code executes first.

Why attackers use it

Early execution, anti-analysis, and quiet staging. Code that runs before monitoring starts can hide itself, check for research tools, or prepare a payload in peace.

Main risks

Loaders that start before monitoring; hidden staging inside files that look normal; a modified executable sitting on disk that nobody notices.

Detection focus

Static PE inspection, antivirus (AV) and EDR (endpoint detection and response) verdicts, and memory scanning. Native Windows logs are sparse — they do not show callback execution directly.

Contents

1Overview

Windows gives every thread private data slots called thread local storage (TLS). A program file can also list small functions — TLS callbacks — that the Windows loader runs before the program's main entry point. This section explains that mechanism in plain language and shows the two main ways attackers abuse it.

TLS and TLS callbacks in plain language

A Windows program is made of threads, and each thread needs its own private scratch space. Thread local storage (TLS) provides that space: a set of data slots that only one thread can see. That part is normal and harmless.

The interesting part is in the file format. Every executable or DLL on Windows is a PE file (Portable Executable). A PE file can carry a small table in its header called the TLS directory. This table lists the addresses of callback functions. When Windows loads the file, its loader (the ntdll library) maps the image — the file laid out in memory — reads the headers, and finds the TLS directory. It then calls every listed callback before the program's main entry point. That means the callbacks run before main() and before the first line of normal code. The loader calls them on process start and again on every new thread attaching or detaching, with a reason code such as DLL_PROCESS_ATTACH or DLL_THREAD_ATTACH.

Think of it as a "before main()" hook that the loader always honors. Legitimate software uses it for setup work. Attackers use it because whatever they put there runs first — automatically, on every launch, without touching the visible program logic.

Abuse angle 1 — the trojanized executable

The attacker takes a normal, working installer or utility and adds — or redirects — a TLS callback entry in its header. The callback points at code the attacker hid in an extra section of the file.

When anyone runs the file, the attacker's code runs first. It can stage an implant, unpack a payload, or run anti-analysis checks. Then the real installer continues on top, so the user sees a program that works and suspects nothing. Security tools that attach to a process later arrive after the callback has already finished.

Abuse angle 2 — hijacking execution through the callback table

The TLS callback table is also an execution hook that can be modified. An attacker who can change a PE's header — on disk or in memory — can point a callback at new code, redirect an existing callback, or add extra entries.

Used against another process, this becomes an injection method: the attacker's code gets a guaranteed, early execution slot inside a process they did not start. This is why ATT&CK places T1055.005 under Process Injection (T1055), alongside Stealth and Privilege Escalation. TA0005 was named Defense Evasion before ATT&CK v20.

Note — why some sandboxes and AV missed TLS-first code historically

Older sandboxes ran a program and waited for "interesting" behavior from the main code path. Older AV engines sometimes attached their hooks after startup had finished. A payload hidden in a TLS callback finished its work before either tool looked. Modern EDR hooks earlier, scans memory continuously, and inspects file headers statically — which is exactly where this guide's detections focus.

Where it fits in the attack chain

T1055.005 is mainly a stealth and execution staging technique. Its official goal is to evade process-based defenses — tools that watch what a process does — and possibly elevate privileges. It gives attacker code an early, quiet ride inside a trusted-looking file. It becomes persistence when the trojanized binary is a legitimate program that auto-starts with Windows — then the callback runs again at every boot. It becomes privilege escalation when the callback-based injection lands inside a process with higher rights.

How it differs from its sibling sub-techniques: T1055.003 (Thread Execution Hijacking) takes over the instruction pointer of an existing thread. T1055.004 (Asynchronous Procedure Call) queues a function to run when a thread becomes available. T1055.005 instead uses the loader's own TLS callback list, so the code runs before the entry point.

On an isolated lab VM, the attacker patches a benign installer: they add a TLS directory entry that points at their own callback function and hide the payload in an extra section. The file still installs normally. Defender view: nothing has fired yet — only static PE analysis or YARA on the file would flag the unusual TLS directory.

  3. Step 3 — Execute. The user double-clicks the installer. Windows creates the process from the Downloads folder. Defender view: Sysmon EID 1 records the new process and its path — a weak signal alone, but valuable context later.
  4. Step 4 — Loader reads TLS directory. The Windows loader (ntdll) maps the image, walks the PE headers, finds the TLS directory, and collects the callback addresses. Defender view: this activity is invisible in native logs; no event fires for header parsing.
  5. Step 5 — Callback runs before main. The loader calls the malicious callback before the program's entry point. The callback stages an implant and runs quick anti-analysis checks. Defender view: EDR early-behavior hooks or the AV engine may raise a verdict; Windows Defender can log event 1116.
  6. Step 6 — Implant continues. The real installer keeps running normally on top, so the user sees a working program. The implant now operates from unsigned memory inside the installer process. Defender view: EDR memory scanning finds an unsigned, unrecognized region inside the process.
  7. Step 7 — Optional injection. The callback-based loader injects its payload into another process, such as the file manager, to move the work away from the original program. Defender view: cross-process access with write and execute rights raises an EDR alert; Sysmon EID 10 records the access.
  8. Step 8 — SOC triage. The analyst pulls the file from the host and runs a static YARA check, which confirms a suspicious TLS callback table. The host is isolated and the file is removed. Defender view: YARA match confirmed, host isolated in the EDR console, file hash pushed to the blocklist.

3Red team perspective

This section explains, at a structural and educational level, why attackers pick TLS callbacks, what conditions the trick needs, and where it shows up in real tooling. Everything here is descriptive — no working patcher or payload is provided, and any research belongs on isolated lab machines.

Why attackers use TLS callbacks

They run before user-mode sensors hook in. Many monitoring tools attach to a process after it has started. A TLS callback has already finished by then, so its setup work — mapping payloads, decrypting config, checking for research tools — leaves few live traces.

They historically bypassed some sandboxes. Automated analysis systems that waited for "main program" behavior saw a quiet installer, because the malicious part never touched the main code path.

They pair naturally with packing. A callback can unpack the real payload into memory and hand control over later, which adds an obfuscation layer (see T1027) on top of the early-execution advantage.

Danger — Lab only. Structural description, not a build guide.

Structurally, a PE's TLS directory is a header table that lists the virtual addresses of callback functions. A trojanized build adds a new entry — or redirects an existing one — so that attacker code placed in an extra section of the file runs when the loader honors the table. That is the whole concept; no patcher steps, offsets, or code are given here, and none are needed for defense.

Studying this technique is legitimate only on isolated research VMs, with self-made unsigned test binaries, no real user data, and written approval. Modifying and redistributing software you do not own is illegal in most jurisdictions.

Where it applies in real tooling

TLS callbacks are not exotic. Public reporting ties them to several common places:

Commodity loaders Protectors and packers Anti-analysis packers Staged droppers

Commercial protectors ship TLS callbacks as a standard feature, which means many packed files — benign or malicious — carry them. That is exactly why static detection needs prevalence and context, not just "has a callback".

Prerequisites and constraints

The attacker must be able to modify and distribute a PE file, which means this technique usually starts with phishing, malvertising, or a supply-chain position. The callback code must also survive loader constraints: it runs while the loader lock may be held, so only a safe subset of API calls works reliably, and anything heavy risks deadlock or a crash on newer Windows builds.

4Blue team perspective

Defenders rarely see the callback itself. They see the file it lives in, the verdict their AV or EDR raises, the memory it occupies, and the injection behavior that sometimes follows. This section maps that visibility and gives a six-step triage flow.

Visibility — static

Static analysis is your strongest ground here. A YARA rule (or any PE parser) can read the TLS directory of a file at rest: how many callbacks it lists, and where they point. Callback addresses that fall outside the file's normal sections, or a brand-new TLS directory in a previously clean file, are concrete, reproducible evidence.

Mail and web gateways can run these checks on arrival, before any user is involved.

Visibility — runtime

At runtime, rely on verdicts and memory, not on a "callback ran" event. AV and EDR engines raise verdicts when the early code behaves badly (T1055.005-aligned signatures like loader or injection detections). EDR memory scanning finds unsigned, unrecognized regions inside otherwise normal processes. Cross-process access alerts (Sysmon EID 10) catch the injection follow-up. MITRE's own detection strategy for this technique (DET0467) works the same way: it watches memory changes to PE headers and TLS directory structures, followed by anomalous thread behavior before the main entry point runs.

Warning — the logging gap you must plan around

Sysmon and standard Windows event logs do not show TLS callback execution. There is no event that says "callback ran". You will see the file being created (Sysmon EID 11), the process starting (EID 1), AV/EDR verdicts, and memory scan results — but the loader's header parsing and the callback call itself happen inside the loader, unlogged. Build your detections around files, verdicts, and memory, and document this gap explicitly for your auditors and analysts.

Artifacts to collect

The modified PE itself — look for an unusual TLS directory, an unexpected extra section, or unsigned regions inside an otherwise normal file. The quarantine copy your AV already saved. A memory capture from the affected process, if timing allows. If injection followed, the cross-process access records (Sysmon EID 10) naming source and target process.

Where to look

Mail and web gateway logs plus YARA verdicts (delivery trail); the EDR verdict queue and AV operational log (Windows Defender events 1116 and 1121); EDR memory scan results; and, for the injection angle, process access events. A hash lookup against your gateway and endpoint history tells you whether the file arrived anywhere else.

Why it matters

Because the technique defeats timing assumptions. If your playbooks assume "monitoring starts when the process does", TLS-first code breaks that assumption silently. Knowing the gap lets you close it with static inspection and memory scanning instead of waiting for a log that will never arrive.

Fit in the attack chain

Expect T1055.005 early in the chain — right after delivery, before or alongside the first implant actions. It pairs with T1574 (Hijack Execution Flow) and T1027 (Obfuscated Files or Information). Detections here cut the chain before credential theft or movement happens.

5.2Threat intelligence

TLS-callback abuse is well documented in loader and protector research. These are the sources worth tracking, how to use them, and what public reporting currently says about the actors behind the tooling.

MITRE ATT&CK

The official T1055.005 page defines scope and terminology. The parent page T1055 gives the injection context. Start every new detection here so names and IDs stay consistent in your documentation.

Vendor reporting

Microsoft, ESET, Check Point, and Fortinet regularly publish loader-family write-ups. Their reports describe staging quirks — including TLS-callback use — and often release YARA rules and hashes you can adapt.

OSINT repositories

Malpedia indexes loader families with references. MalwareBazaar offers samples and community YARA. Yara-Rules and ReversingLabs feeds provide ready static rules. VirusTotal gives prevalence and verdict context for any hash.

ISACs

Sector ISACs share indicators that already passed relevance filtering for your industry. A loader hash shared by your ISAC often deserves instant blocklisting without full re-analysis.

Commercial feeds

ReversingLabs and similar feeds classify files at scale, including header anomalies. They are useful for the supply-chain watch in threat T4 below: is this signed binary supposed to have a TLS directory?

Internal telemetry

Your own verdict history, hash cache, and gateway logs are the best baselines. Track first-seen dates for hashes in your environment; a "first seen this week" verdict is far more interesting than a year-old one.

Collection → analysis → application: pull new verdicts and hashes weekly from gateway and EDR queues; analyze whether detections map to T1055.005 by checking the file's TLS directory once; apply by pushing hashes to blocklists, feeding rules back to the gateway, and tuning Sigma rules with the prevalence you observe.

5.3Threats ranking and categorization

Five realistic threats built on T1055.005, ranked for a typical Windows enterprise. Severity reflects likely impact combined with how hard the threat is to see with native logging. All five run on Windows only; the summary table at the end lists them in severity order.

T1 — Trojanized executable with malicious TLS callback Critical Windows

Description: an attacker patches a benign-looking installer or utility so its TLS directory points at attacker code that stages an implant before the program starts. Preconditions: ability to deliver a file users will run (phishing, malvertising, fake updates). Impact: full foothold before most tools look; credential theft and further injection. Justification: this is the most common, best-documented abuse (documented for the Ursnif banking trojan), it defeats timing-based monitoring, and it needs no prior access to the target. Primary detection signal: AV/static verdict on the delivered file.

T2 — TLS callback used for anti-analysis or sandbox evasion Medium Windows

Description: the callback checks for research tools and changes behavior — staying quiet in sandboxes, active on real hosts. Preconditions: attacker-controlled code in the callback window. Impact: delayed or missed detections; analysis results that lie. Justification: raises evasion quality of any chain using it, but depends on another technique for delivery. Primary detection signal: behavior verdicts on execution.

T3 — Remote TLS-callback injection into another process High Windows

Description: an implant with existing access modifies or injects through a TLS callback mechanism into a second process, gaining an early execution slot there. Preconditions: prior foothold and write access to a target process or its image. Impact: stealthy persistence inside trusted processes; hard-to-attribute execution. Justification: rare but high impact and it typically indicates an established intrusion. Primary detection signal: EDR behavioral verdicts (cross-process access plus injection).

T4 — Unexpected TLS directory in a signed or expected binary Medium Windows

Description: a software update or internally expected binary suddenly carries a TLS directory it never had — a sign of tampering or a compromised build pipeline. Preconditions: supply-chain compromise or insider modification. Impact: signed malware that walks past allow-listing. Justification: low frequency, very high trust impact. Primary detection signal: static comparison against a known-good baseline.

T5 — Packed loader executing before the entry point Medium Windows

Description: a packed payload whose protector unpacks and launches code through TLS callbacks, before any normal program logic. Preconditions: delivered packed file; often combined with T1. Impact: static signatures miss the real payload; behavior appears only in memory. Justification: common in commodity chains but usually caught downstream by memory scanning. Primary detection signal: memory-scan verdicts on the host.

5.4Logs and patterns

Remember the core gap: nothing in native Windows logging records the callback itself. Every detection below rides on the file, the verdict, or the memory around it. Use this section to connect the threats from 5.3 to concrete log sources, fields, and example events.

Log sources that matter

Windows Defender operational log — events 1116 (detection), 1117 (remediation action succeeded), and 1121 (behavior blocked) carry verdict names you can route on. EDR product logs — verdicts, memory-scan findings, cross-process access. Sysmon events 1, 7, and 11 — process start, image load, and file create; supporting context, not the technique itself. Static YARA reports — gateway and endpoint scan outputs that describe PE header anomalies. Pure TLS callback execution leaves few direct event traces, so memory scanning and EDR behavioral telemetry carry the real weight here.

Fields worth routing on

EventID — which event fired. DetectionName — the verdict; its keywords drive routing. ProcessName / PathName — who did it and from where. FileHash — the pivot and block key (some Defender builds expose it only in the quarantine record or MPLog — enrich there). ImageLoaded (Sysmon 7) — modules loaded. TargetFilename (Sysmon 11) — where files land. User — account context.

Note — legitimate TLS callbacks exist in many applications

Compilers and frameworks emit TLS callbacks for honest reasons, and commercial protectors add them to benign software. A TLS directory is therefore context, not a verdict by itself. 5.5Sigma rules and Splunk SPL

Five rules, one per detection lane, each with a matching Splunk SPL query. Field names for Defender events vary slightly between platform versions — validate FileName, PathName, and FileHash against your own event stream and adjust the SPL field list.

R1 — Defender Trojan verdict on executable in Downloads or Temp (high)

Mapping note: XML event rendering exposes Defender fields as EventCode, DetectionName, FileName, PathName; the doubled backslash is SPL escaping for a literal one. Adapt index and sourcetype to your environment. False positives: user-initiated downloads of legitimately flagged tools. Tuning: add a prevalence lookup on FileHash; suppress known signed publishers; pair every hit with a static YARA confirmation.

R2 — Defender behavior block with loader or injection keywords (medium)

Mapping note: the eval turns spread into priority — the same verdict on many hosts at once is rarely one user's mistake. False positives: self-unpacking installers. Tuning: correlate with Defender 1116 on the same host and hash; add file-path context from Sysmon EID 11.

R3 — Defender or EDR remote process injection verdict (high)

Mapping note: in EDR products that do not mirror verdicts into Defender events, run the same logic against the EDR product log index and its detection-name field. False positives: developer hosts with debuggers. Tuning: allow-list developer subnets, require Sysmon EID 10 corroboration, escalate every hit outside known developer machines.

R4 — Executable file created in a user Downloads folder (medium)

Mapping note: this rule is context, not verdict — its job is to give R1/R3 hits a delivery trail. False positives: any user downloading software on purpose; expect volume. Tuning: keep it at informational routing, feed Hashes into the prevalence cache, and only page when it joins with a Defender verdict within 15 minutes.

R5 — Process execution from a user Downloads folder (medium)

Mapping note: execution from Downloads is weak alone; the eval reminder documents the join that makes it strong. False positives: ordinary installer runs. Tuning: never run this as a stand-alone page; use it inside a correlation with Defender verdicts or gateway YARA hits, and drive hash blocking from the joined result.

Warning — tune before you trust

Rules R4 and R5 will be noisy on day one. That is expected: they are context rules. Deploy them with correlation to R1–R3, watch two weeks of data, add your legitimate-software allow-list, and record every false positive in the rule notes so the next engineer inherits your tuning, not your noise.

6Real-world case study

A complete incident told in incident-response order, from first download to lessons learned. Use it as a walkthrough of the triage flow from section 4 under time pressure.

Note — educational reconstruction

This case study is an educational reconstruction based on public reporting of TLS-callback-using loader families (2019–2024). The company, users, hosts, and timestamps are illustrative. No real incident is described.

Context

A mid-size company, roughly 1,200 staff, mostly Windows 11 workstations with an EDR agent deployed fleet-wide and a mail/web gateway that does not yet run static YARA. An employee searching for a free PDF tool clicks a sponsored search result. The site serves a polished installer: a real, working PDF utility with a malicious TLS callback added by the attacker. The callback stages an info-stealer before the real program's first line runs.

Timeline

  1. Day 0 · 09:14 The user downloads the "PDF tool" installer from the malvertising link to the Downloads folder.
  2. Day 0 · 09:16 The user runs it. The Windows loader honors the TLS directory; the malicious callback executes before main and stages the loader component in memory.
  3. Day 0 · 09:17 The loader injects the info-stealer into the running browser process via cross-process access.
  4. Day 0 · 09:40 Browser credential theft begins: saved passwords and live session cookies are collected and staged.
  5. Day 1 · 11:05 DETECTION POINT. The EDR raises a behavioral verdict: unsigned memory region inside the installer process plus cross-process access to the browser. Windows Defender records a related verdict in the operational log.
  6. Day 1 · 11:40 The analyst validates the verdict, retrieves the file, and runs the static YARA check — the TLS callback table confirms the anomaly. The host is isolated.
  7. Day 1 · 14:00 Response continues: exposed credentials are reset, session cookies are revoked, and the file hash is blocked at the mail and web proxies.
  8. Day 2 · 09:00 The workstation is rebuilt from a clean image. Eradication checks: no further cross-process access, no leftover files, no recurring verdicts.
  9. Day 2 · 15:00 Recovery is verified with the user; monitoring stays elevated for 30 days; the lessons-learned review is scheduled.

Detection point

EDR behavioral verdict on day 1 — roughly 26 hours after execution. The TLS callback itself never produced a log line; the unsigned memory region and the cross-process access did. This is the expected detection shape for T1055.005.

Containment

Host isolation within 35 minutes of the verdict. Blocking the hash at the proxies stopped three re-delivery attempts on other hosts later the same day.

Eradication

Rebuild instead of cleaning: the implant staged from memory and the artifact chain was simple, but a rebuild removed all doubt. The quarantine copy was kept as evidence.

Recovery

Clean image, restored user data from backup, monitoring elevated for 30 days, and a fleet-wide hunt for the hash and delivery URL across gateway and endpoint history — which found no other affected hosts.

Impact

Stolen session cookies and saved browser passwords; one attempted fraudulent payment from a reused corporate card credential, blocked by the bank. No data-store breach; no lateral movement.

Team response and communication

The SOC led; IT handled the rebuild; identity team reset credentials; leadership got a plain-language note the same afternoon. Users received a short malvertising warning — without naming or blaming the affected employee.

LessonWhat changed

Home and small-office advice

Keep the built-in antivirus on — modern Microsoft Defender already inspects PE headers and scores behavior. Download software from the vendor's own site, not from search-engine ads. Install updates quickly. Use a standard (non-admin) account for daily work. Keep an offline or cloud backup of important files. If a download "installs" but the antivirus complains, trust the antivirus and delete the file.

Daily habits

Review the verdict queue with prevalence context. Check EDR cross-process access events on hosts that got a file verdict. Confirm any new exclusion requests have a scope and an expiry.

Weekly habits

Check first-seen dates for new hashes. Push confirmed hashes to proxy and EDR blocklists and verify one block actually works. Skim vendor and ISAC reporting for loader-family updates.

Monthly habits

Test gateway YARA against the sample corpus. Review exclusions and expiry dates. Retire or repair orphaned rules. Audit the downloads policy against actual delivery-channel data.

Good practice — make the gap explicit

The single highest-leverage habit for this technique: write down, in your detection documentation, that TLS callback execution is invisible to native logs, and list what replaces it — verdicts, memory scanning, static inspection. Teams that document the gap stop waiting for events that never come, and start tuning the signals that do.

Top five detections

All five rules live in section 5.5:

  1. R1 — Defender Trojan verdict on executable in Downloads/Temp (high)
  2. R2 — Defender behavior block with loader or injection keywords (medium)
  3. R3 — Defender/EDR remote process injection verdict (high)
  4. R4 — Executable file created in Downloads (Sysmon 11, context)
  5. R5 — Process execution from Downloads (Sysmon 1, context)

Correlate R4/R5 with R1–R3 by host within 15 minutes before paging anyone.

Response checklist — first 30 minutes

  1. Validate the verdict: real behavior or known-benign installer?
  2. Isolate the host in the EDR console if the verdict or the static check is positive.
  3. Retrieve the file: quarantine copy, SHA256 hash, full path.
  4. Run the static YARA / TLS-directory check on the sample.
  5. Check Sysmon EID 10 for cross-process access on the same host.

Response checklist — first 24 hours

  1. Block the hash at EDR, mail proxy, and web proxy; verify the block.
  2. Hunt hash, file name, and delivery URL across gateway and fleet history.
  3. Reset exposed credentials and revoke live sessions for affected users.
  4. Clean or rebuild the workstation; confirm no recurring verdicts.
  5. Record the incident, notify stakeholders, and schedule lessons learned.
