T1055.009 Proc Memory

Proc Memory is a Linux process injection method. An attacker opens the memory of a running process as a file (/proc/<pid>/mem), writes small attacker code into it, and makes the process run that code. This page explains the attack, shows it step by step, and gives your SOC (Security Operations Center) ready-to-use detections.

1Overview

What Proc Memory injection is, why attackers use it, and what you will learn on this page.

On Linux, the /proc directory is a special file system called procfs (the "process file system"). It shows kernel data as normal files. Every running process has a folder named /proc/<pid>, where pid is the process identifier, a number the kernel gives each process. Inside that folder, the file /proc/<pid>/mem shows the memory of that process as one plain file.

Normal software almost never opens this file. An attacker does. With the right permissions, they open it with O_RDWR (a flag that asks for read and write access). They then move the file position to a chosen memory address and write a small piece of code, called shellcode, straight into the running process. To make the process run that code, they usually patch a function pointer (a variable that stores the address of a function). Some attackers instead pair the write with ptrace, the Linux debugging interface, and point the instruction register (RIP, the CPU register that says which instruction runs next) at the new code.

The official ATT&CK description adds more mechanics. An attacker first enumerates the memory of the target through /proc/<pid> and reads /proc/<pid>/maps. That map shows the real addresses, so it defeats ASLR (address space layout randomization), the kernel feature that shuffles memory locations to break hard-coded addresses. The map also reveals gadgets: short instruction sequences already inside the process, which can be chained into a ROP (return-oriented programming) payload. Public research also shows attackers overwriting memory with dd, using offsets read from the map. Like Process Hollowing (T1055.012), this technique can target child processes, for example a backgrounded copy of the sleep program.

What the attacker does

  • Gets code execution on a Linux host, often through a web shell.
  • Reads /proc/<pid>/maps to find a writable memory region in a long-running daemon (a background service).
  • Opens /proc/<pid>/mem with O_RDWR and writes shellcode with lseek or pwrite.
  • Triggers execution inside the trusted process.

Why defenders care

  • No file lands on disk, so file scans see nothing. This is called a fileless attack.
  • The payload runs inside a legitimate process, so process allowlists still pass.
  • The write goes through the file layer, so tools that only watch ptrace syscalls can miss it.
  • The kernel permission checks are weak when services share one user ID.

Where it fits in the attack chain. Proc Memory injection is a mid-chain technique. It comes after the attacker already has code execution on the host. ATT&CK lists it under two tactics. The first is Stealth (formerly Defense Evasion): the payload hides inside a trusted process. The second is Privilege Escalation: if the attacker can inject into a process owned by another user, such as root, they gain that user's rights. A note on the name: ATT&CK v17 (2025) renamed the Defense Evasion tactic to Stealth, and this guide uses the new name. A typical chain looks like this:

  1. Initial access: exploit a web app, drop a web shell.
  2. Discovery: list /proc to find a good target daemon.
  3. Stealth / Privilege Escalation: Proc Memory injection (this page).
  4. Command and Control: the injected code talks to attacker infrastructure.

What you will learn here:

  • How the attack works, step by step, with an animated simulation.

  • How to write auditd and eBPF detections, plus five complete Sigma rules with matching Splunk SPL.
  • How to harden Linux so the attack fails: Yama ptrace scope, capabilities, and user separation.
  • How to respond when an alert fires.
Note

ATT&CK lists only Linux for T1055.009. That matches the kernel design: the /proc filesystem is a Linux feature, so /proc/<pid>/mem does not exist on other systems such as macOS. Keep your coverage for this technique scoped to Linux hosts.

2Animated Simulation

Watch the attack unfold in eight steps. The attacker sits on the left, the Linux victim host sits in the middle, and the SOC (Security Operations Center) evidence panel on the right fills up as the steps leave traces. Hover or tap any box for details.

Step 1 of 8. The attacker gets a first foothold on the Linux server through a web shell. A web shell is a small hidden script on a website that lets a remote person run commands from a browser.

SOC view: The EDR (Endpoint Detection and Response) tool sees a suspicious child process under the web service process tree.

The same story in text form

  1. Step 1 — Foothold. The attacker exploits a web application and lands on the Linux server through a web shell. A web shell is a hidden script that turns a browser into a command prompt. SOC view: a suspicious child process appears under the web service process tree, away from normal deployment jobs.
  2. Step 2 — Target selection. The attacker lists processes under /proc, the Linux process file system, and picks a long-running daemon called metrics-agent, PID 812. A daemon is a background service, and a PID is a process identifier. SOC view: a short-lived shell reads many process status files in a row.
  3. Step 3 — Memory map. The attacker reads /proc/812/maps. This file lists the memory ranges of the daemon, so the attacker can choose a writable address, such as an unused gap, for the new code. SOC view: a web-spawned shell reads the memory map of an unrelated service. That is a strong reconnaissance signal.
  4. Step 4 — Open the memory file. The attacker opens /proc/812/mem with read and write access, the O_RDWR flag. The kernel allows it because both processes run under the same user ID. SOC view: auditd records an openat on /proc/812/mem with write flags and a success result.
  5. Step 5 — Write the code. The attacker moves the file position with lseek to the chosen address and writes a small piece of position-independent code, which runs at any address. SOC view: a write syscall succeeds on the /proc/812/mem file descriptor. Live memory of a trusted daemon just changed.
  6. Step 6 — Trigger. The attacker patches a function pointer inside the daemon and uses a short ptrace nudge to point the instruction register (RIP) at the new code. The daemon now runs attacker code. SOC view: the eBPF sensor flags code executing from an unusual memory region.
  7. Step 7 — Beacon. The injected code connects out to attacker command-and-control (C2) infrastructure. The traffic leaves from a trusted daemon, so it blends in at first. SOC view: netflow shows a rare outbound destination never seen before on this host.
  8. Step 8 — Response. Defenders isolate the host, stop the daemon, hunt the whole fleet for proc-mem opens, and tighten the Yama ptrace scope setting. SOC view: the host is isolated, and hunt and hardening tasks are opened.

3Red Team / Hacker Perspective

How attackers use the procfs memory interface, and what conditions they need. Everything here is described for lab work and defense only.

Warning — Defense and lab practice only

Injecting code into processes you do not own is illegal in almost every country and will break real systems. Use the ideas on this page only inside a lab you own, for example a throwaway virtual machine or container, to build and test detections. Nothing here is operational attack tooling, and we keep it that way on purpose.

When and why an attacker picks this technique

Proc Memory injection is attractive after an attacker already has shell access on a Linux host. Three reasons drive the choice:

  • It is fileless. The payload lives in memory. No new file on disk means no antivirus scan, no file-integrity alert.
  • It hides the parent. The code runs inside a trusted daemon, so "who started this?" points at a legitimate service.
  • It bypasses narrow monitoring. The write flows through the file layer (open, lseek, write), not the ptrace syscall path. Sensors that only watch ptrace see nothing.

Preconditions

Permission to open

The kernel runs ptrace-style checks when a process opens /proc/<pid>/mem. The attacker needs the same user ID as the target, root, or the CAP_SYS_PTRACE capability.

Weak Yama scope

kernel.yama.ptrace_scope=0 allows broad access. A scope of 1 still lets a parent process trace its own children. An attacker can spawn a child, such as a backgrounded copy of the sleep program, and inject into it. Scope 2 blocks both paths.

A steady target

The attacker wants a long-lived process, so the injected code keeps running. Web workers, agents, and monitoring daemons are common picks in labs.

How the attack works, step by step

  1. Foothold. Exploit a web app or weak service and get command execution. In the lab, this is just a shell in a container.
  2. Enumerate /proc. Walk /proc/<pid> folders and read status files to find a stable daemon running under your user ID.
  3. Read the map. Read /proc/<pid>/maps to list memory regions. Look for a writable region, an unused gap (sometimes called a code cave), or a function that runs often.
  4. Open the memory file. Call open("/proc/<pid>/mem", O_RDWR). If this fails with a permission error, the Yama scope or user IDs are against you, and the lab test ends here.
  5. Seek and write. Use lseek on the file to an absolute virtual address, then write the shellcode. Or use pwrite to seek and write in one call.
  6. Trigger execution. Patch a function pointer that the daemon calls later, or pair the write with ptrace: attach, stop the process, set the RIP register to the shellcode, then resume it.
  7. Run the payload. The daemon executes the shellcode. In a lab, the payload might just print a line. In a real intrusion, it usually connects out to C2 (command and control).

A small lab demo (harmless)

The shortest honest demo writes into the process's own memory through /proc/self/mem. It harms nobody and shows the core idea: seek to an address, write bytes, and the process memory changes. Run it only on a machine you own.

Note what this proves: a file descriptor on procfs memory behaves like a file. You can seek to any address that the map shows and write bytes there. Real injections use the same calls against another process, which is exactly what the detections in section 5 look for.

Common variations seen in labs

  • Write into a gap, then hijack control flow. Safer for stability than overwriting live code.
  • Patch a called function directly. Faster trigger, but a crash-prone mistake if the process is busy.
  • Pair with ptrace. Attach, stop, set RIP to the shellcode, detach. More traces left behind, so it is a trade-off.
  • Write with dd instead of a custom tool. Public research shows a dd one-liner that seeks to an address taken from /proc/<pid>/maps and writes payload bytes to /proc/<pid>/mem. Same file layer, same evidence.
  • Grow the gadget pool first. ATT&CK notes that Dynamic Linker Hijacking (T1574.006) can populate a target process with more usable gadgets for a ROP chain.
  • Load a shared object instead. Some loaders write a path string into memory and patch a call to dlopen-like behavior. Same file layer, same evidence.

Mistakes lab testers make

  • Writing to a read-only region. The write fails or the kernel kills the target.
  • Forgetting that maps addresses change between runs. Parse maps every time.
  • Picking a target owned by another user without root or CAP_SYS_PTRACE. The open fails.
  • Testing only with ptrace_scope=0, then claiming the technique works everywhere. It does not.
  • Leaving the lab injector on disk. The detection exercise then finds the boring part, not the injection.

4Blue Team / SOC Perspective

What the defense sees when Proc Memory injection happens, which artifacts it leaves, and a triage flow your team can follow.

The good news: this technique is not invisible. The write path is a normal file operation on a very unusual file. Almost nothing on a healthy Linux server opens /proc/<pid>/mem for writing, so a simple "open with write flags" alert is both rare and precise. The bad news: you only see it if you log it. A default Linux host records nothing about these opens.

Artifacts the technique leaves behind

Where to look

Log layer

auditd rules for /proc/*/mem opens and writes, shipped to your SIEM (Security Information and Event Management) platform. This is the cheapest reliable coverage.

Kernel layer

eBPF sensors such as Falco, Tracee, or Tetragon. They resolve file descriptors to paths directly and can flag execution from fresh memory regions.

Memory and network

On alert, capture memory for forensics and diff /proc/<pid>/maps against a known-good copy. Check netflow for new destinations from the daemon.

Why it matters and where it sits in the chain

Proc Memory injection usually appears after initial access, so the surrounding story is: how did the attacker get a shell, and what did the injected code do next? The detection value comes from the tight chain in section 5.4: maps read, then open, then write, then odd execution, then beacon. Each link is weak alone; the chain is convincing. Miss the early links and you still catch the beacon, but you lose hours.

Short triage flow

  1. Confirm the event shape. Check the syscall, the file path, the open flags, and that exit was success. Read-only opens by debuggers go to the allowlist queue.
  2. Identify the opener. Which process opened the memory file? Who is its parent? Was it spawned by a web service?
  3. Identify the target. Which daemon owns the memory? Is it internet-facing, privileged, or holding secrets?
  4. Look for the chain. Maps read before the open? Write after it? Execution from a fresh region after that?
  5. Contain. Isolate the host at the network level, stop the daemon, preserve memory and logs before restarting.
  6. Hunt the fleet. Run the hunt queries from section 9 across all Linux hosts for the last 30 days.
Good practice

Build the allowlist before the alert fires. Know which hosts run debuggers, which agents open process memory for profiling, and who owns them. An alert without an allowlist turns into noise within a week.

5.2Threat Intelligence

Threat intelligence for this technique is honest and a bit thin. ATT&CK documents one campaign example, which we list below. Public reporting that ties the technique to one named group is still rare, so build your picture from several source types instead of one vendor claim.

Sources worth your time

  • MITRE ATT&CK — the free baseline: technique definition, data sources, detection notes.
  • Vendor reporting — endpoint and cloud vendors publish Linux malware analyses, often with sandbox traces that show the proc-mem syscall chain.
  • OSINT (open-source intelligence) — research blogs and public proof-of-concept repositories show the exact open/lseek/write pattern and its kernel gates.
  • Commercial feeds — useful for hashes and infrastructure, less useful for fileless behavior. Ask how a feed detected this technique without disk artifacts.
  • ISACs (Information Sharing and Analysis Centers) — sector peers share Linux intrusion patterns under trusted terms.
  • Internal telemetry — your own auditd and eBPF data is the most honest source. Mine it for near-misses and noise.

Collection and analysis tips

  • Tag internal events with the ATT&CK sub-technique ID, so trends group by behavior, not by tool name.
  • Prefer behavioral reporting (syscalls, file paths, regions) over hash-based reporting for fileless tradecraft.
  • Track the kernel version and Yama scope of hosts in intel summaries; both change what is possible.
  • Keep a lab VM that reproduces each reported pattern once, so rules are written against real event shapes.

Event-shaped examples

All examples come from the composite lab scenario used across this page. The host is app-prod-03. The target is the metrics-agent daemon, PID 812, running as user ID 1001, with a web shell under the same user ID.

Example 1 — the open. An auditd record (shipped by Auditbeat) shows a php-fpm worker opening the daemon memory file with flag 2, which is O_RDWR.

  • file.path — the target: the memory file of PID 812.
  • auditd.data.a1 — the open flags in hex-ish form; 2 means O_RDWR, the write access that matters.
  • auditd.data.exit — 0 means the open succeeded, so the attacker holds a working handle.
  • user.auid — 4294967295 is the "unset" value. It means no login session owns this process, typical for a web shell working through a service worker.
  • process.name — the opener is a web worker, not a debugger. That single fact carries most of the alert value.

Example 2 — the write. Two seconds later, the same worker writes 214 bytes at a fixed offset inside the daemon memory.

  • event.action — pwrite64, a combined seek-and-write. write and writev belong to the same family.
  • auditd.data.a0 — the file descriptor number (6 here). Match it to the open in example 1 to tie the chain together.
  • auditd.data.a2 — byte count in hex; d6 is 214 bytes written.
  • auditd.data.exit — equals the byte count, so the write fully succeeded.
  • file.path — note that raw auditd logs the descriptor, not the path; the shipper or an eBPF sensor fills the path. State this mapping in your runbook.

Example 3 — the eBPF view. A Falco rule fires on the same write, with the path resolved in kernel.

  • rule — the Falco rule name; keep names stable, your Sigma rule for Falco keys on it.
  • fd.name — path resolved in kernel, no shipper guessing needed.
  • proc.cmdline — shows the worker role, which helps the allowlist decision.
  • output_fields — fields often arrive nested under this object in the JSON feed; flatten or spath them in Splunk.

Example 4 — the opener profile. Sysmon for Linux process creation shows the lab injector being spawned by the web worker, with the proc paths right in its command line.

  • Image — a hidden file in /tmp, a classic staging spot. Alone it is weak; with the command line it is strong.
  • CommandLine — names both /proc/812/maps and /proc/812/mem. This is the target selection step in writing.
  • ParentImage — the web worker. Process-tree context turns this from odd to alarming.
  • Hashes — a fixed fake SHA-256 for the lab. Real files give you a fleet hunt key.

Example 5 — the recon that preceded it. The maps read lands one second before the open, which is the ordering that raises confidence.

  • file.path — /proc/812/maps, the memory map read.
  • auditd.data.a1 — 0 means O_RDONLY, so this alone is not an alert; it is context for the next events.
  • process.name — a bare shell reading another service's map. Admins do this rarely and from sessions with a real auid.
  • Ordering — maps read, then open with write flags, then write, then odd execution. Time-ordered, it is the whole attack in four lines.

5.5Sigma Rules and Splunk SPL

Sigma is an open signature format for detections: you write a rule once in YAML (a readable configuration format) and convert it to your SIEM's query language. Each rule below is complete, followed by a matching Splunk SPL query, a field mapping note, false positives, tuning guidance, and severity. All rules assume the Auditbeat-style field names from section 5.4. Adjust index and sourcetype names to your environment. One tag note: the rules keep attack.defense_evasion because the Sigma tag set predates the ATT&CK v17 rename of that tactic to Stealth.

Rule 1 — Open of process memory with write access

Mapping note
Sigma file.path maps to the ECS file.path filled by Auditbeat. With raw auditd, the path comes from the PATHNAME record (name field); match the SYSCALL and PATHNAME records by event time and serial. Keep the "adjust to your environment" rule in mind for index and sourcetype names.
False positives
Debuggers on development hosts, memory forensics during an active case, and profiling agents. The two filters cover the common ones; extend them with your own inventory.
Tuning guidance
Track the filter list in version control. Add per-host-group exceptions (build fleet only) rather than removing conditions. If noise persists, require the maps-read context from Rule 4 as a correlated condition.
Severity
High. A successful write-flags open is one step before live memory change; on production servers it almost always deserves a page.

Rule 2 — Successful write to process memory

Mapping note
Sigma event.action holds the syscall name after Auditbeat mapping; raw auditd logs it in syscall. auditd.data.exit maps to the exit field (bytes written). Event.outcome success equals exit greater than zero.
False positives
Deliberate memory forensics during response. That is why this rule keeps no broad debugger filter: a debugger writing to another process memory is itself worth seeing.
Tuning guidance
This rule should stay nearly silent. If it fires often, first fix the environment (who writes memory at all?), then add narrow, documented exceptions. Correlate with the open from Rule 1 within five minutes for a stronger alert.
Severity
Critical. Live memory of another process changed. Treat every instance as a potential intrusion until proven otherwise.

Rule 3 — eBPF sensor flags proc memory write

Mapping note
Many Falco-to-Splunk shippers nest values under an output_fields object. If the fields above come back empty, add: | spath output_fields | rename output_fields.* AS *. Then the rest of the query works unchanged. The Sigma evt.type maps to the same name in the flattened view.
False positives
Observability agents with documented memory access; debuggers during supported work. Keep the list short and host-scoped.
Tuning guidance
Pair this rule with a Falco rule for execution from unusual regions to cover the trigger step. Alert on the pair, not just one event, to cut noise on busy nodes.
Severity
High. Kernel-resolved path evidence for proc memory access.

Rule 4 — Command line references proc memory paths

Mapping note
Sigma uses two contains conditions with all semantics; the SPL wildcard pattern "*proc*mem*" is the equivalent shorthand. Auditbeat maps the auditd proctitle record to process.command_line. Raw auditd shows the same data hex-encoded in proctitle, so decode before matching.
False positives
The word mem appears in paths like /proc/meminfo and in tools named mem. The filter list handles the common readers; review anything new by hand.
Tuning guidance
Add a second condition for the exact pair of strings maps and mem in one command line when noise grows. Exclude known maintenance scripts by host group, not globally.
Severity
Medium. Context-rich but indirect; strongest when it appears shortly before a Rule 1 or Rule 2 event.

Rule 5 — Yama ptrace scope change

Mapping note
file.path matches the sysctl pseudo-file after Auditbeat mapping. Raw auditd sees it in the PATHNAME record like any other file. The sysctl command writes through /proc/sys, so it lands in the same rule.
False positives
Configuration management runs. Filter by the tool's known binary name and by change-window hours, and document the baseline value per host group.
Tuning guidance
Also audit the file with an auditd watch (-w path -p wa) so reads of the value are available during hunts. Alert on value 0 appearing in any production host group.
Severity
High. A weakened Yama scope silently widens the attack surface for every process on the host.
Good practice

Convert all five rules with a Sigma converter in your CI (continuous integration) pipeline, and store both the YAML and the generated queries in one repository. When a field name changes in your pipeline, a single test run shows which rules need a mapping update.

6Real-World Case Study

A worked incident, from first foothold to lessons learned.

Composite scenario

This case study is a composite. It blends patterns that are common in public Linux intrusion reporting and in lab telemetry. It is not a real named incident, no attribution is claimed, and all host names, addresses, and times are fictional. The detection and response steps are the point. For a documented real-world use of this technique, see the KV Botnet Activity campaign in section 5.2.

Context

A mid-size SaaS (Software as a Service) company runs an internet-facing Linux application host, app-prod-03, behind a load balancer. The host runs a PHP web app and a resident metrics-agent daemon (PID 812) that has been up for 119 days. Both run under the same service user ID 1001. Linux Audit (auditd) ships events to the SIEM through Auditbeat, an eBPF sensor (Falco) covers a few high-value rules, and netflow lands in the same index. kernel.yama.ptrace_scope is still 0 on this host, a leftover from an old base image.

Timeline

  • Day 1, 09:12A file-upload flaw in the web app lets the attacker write a hidden script under the web root. The script works as a web shell: commands arrive inside normal HTTP requests.
  • Day 1, 09:18The EDR (Endpoint Detection and Response) connector logs a suspicious child process under the web worker. The alert sits in a low-priority queue, because web apps spawn shells during deployments too.
  • Day 1, 09:20:59A shell spawned by the web worker reads /proc/812/maps and lists the daemon memory regions. It picks a writable gap next to a function that runs on every metrics cycle.
  • Day 1, 09:21:07The worker opens /proc/812/mem with O_RDWR. The kernel allows it: same user ID, Yama scope 0. auditd records the openat with success.
  • Day 1, 09:21:09A pwrite64 writes 214 bytes of position-independent code into the gap. Two events land in the SIEM: the auditd write record and a Falco alert for the proc-mem write.
  • Day 1, 09:22:14The attacker patches a function pointer and gives the daemon a short ptrace nudge. The daemon runs the payload. Falco flags execution from an unusual memory region and auto-raises the case to high priority.
  • Day 1, 09:41Netflow shows a first-seen outbound connection from the daemon host to a raw IP on port 8443. The SOC (Security Operations Center) analyst links it to the earlier alerts and declares a suspected intrusion.
  • Day 1, 09:58Containment: the network team isolates app-prod-03 at the switch, the daemon is stopped, and memory plus /proc/812/maps are captured for forensics before restart.
  • Day 2Eradication: the web shell is removed, the upload flaw is patched, and the daemon is restarted from a known-good image. The team also rotates the credentials used by the web app and sets kernel.yama.ptrace_scope=2 in the base image.
  • Day 3Recovery: the host returns to service behind extra monitoring. Fleet hunts for proc-mem opens over 30 days find no other host affected.
  • Week 2The team writes the lessons learned list below and schedules a purple-team replay to test the new rules end to end.

Attack chain summary

  1. Initial access: file-upload flaw leads to a web shell.
  2. Discovery: /proc walk and maps read to pick the daemon.
  3. Stealth / Privilege Escalation: Proc Memory injection (T1055.009) into the trusted daemon.
  4. Command and Control: injected code beacons out from the trusted process.

Detection point

Two independent detections fired within seconds of each other, which is why the case moved fast:

  • auditd proc-mem rule (section 5.5, Rules 1 and 2). The open with write flags and the successful pwrite64 to /proc/812/mem. The opener process name, a web worker, made the false-positive discussion short.
  • Falco eBPF alerts. First the proc-mem write, then execution from an unusual region. The kernel-resolved path removed all doubt about which file descriptor was involved.

The netflow first-seen destination was the third signal, twelve minutes later. It confirmed the payload worked but was not needed to start the response.

Containment, eradication, recovery

Containment

Isolate at the network layer, stop the daemon, capture memory and maps before restarting anything. Keep the web shell in place but unreachable until forensics has a copy.

Eradication

Remove the shell, patch the flaw, rotate credentials, rebuild the daemon from a known-good image, and fix the weak Yama scope in the base image so every rebuild inherits the fix.

Recovery

Return the host with extra monitoring, run the fleet hunt from section 9, and keep the case open until a full 30-day hunt is clean.

Impact and consequences

The injected code was a miner loader in the lab pattern. Before containment it used roughly 80 percent of one core, added latency to the metrics pipeline, and would have raised cloud cost if left for a month. No evidence of data access appeared in the 30-day hunt, so no customer notification was required. The main cost was response time and a short maintenance window.

Team response and communication

The SOC opened a severity-2 ticket, paged the platform owner of the host, and posted updates every 30 minutes in the incident channel. Legal and leadership received a plain-language summary the same morning: what happened, what data was (and was not) touched, and the next milestones. The cloud provider received a courtesy case for the destination IP.

Lessons learned

  • auditd coverage for procfs paid off. Two rules found the event in seconds. Extend the same coverage to every Linux fleet tier.
  • The eBPF sensor closed the fd-to-path gap that raw auditd leaves. Keep both layers; they answer different questions.
  • Yama scope 0 was the enabler. One sysctl in the base image would have made the open fail. Hardening beats detection on cost.
  • Fileless-load detection needs a chain view. Maps read, open, write, odd execution, and beacon made sense together; no single event was conclusive.
  • Shared user IDs blurred attribution. Separate service users per function, so "who could have done this" has one answer.

7Mitigation and Defense

Controls that stop Proc Memory injection or shrink its blast radius, ordered by how much risk they remove per hour of work.

The strongest controls here are not detection products. They are two lines of kernel configuration and one line of deployment policy. Detection still matters, because misconfiguration happens, so the table mixes both.

ATT&CK mitigation mapping

ATT&CK lists two official mitigations for this technique:

  • M1040 — Behavior Prevention on Endpoint: some endpoint security products can block common behavior sequences that occur during process injection.
  • M1022 — Restrict File and Directory Permissions: restrict permissions on sensitive files such as /proc/[pid]/maps and /proc/[pid]/mem, so unprivileged users cannot read another process's memory layout or memory.

Home and small-office advice

Keep the system current

Enable automatic security updates on home Linux machines and small servers. Most chains that end in proc-mem injection start with an old, known flaw.

Run as a normal user

Do daily work as a non-root user. Modern distributions already set a safe Yama scope, so leave sysctl values alone unless a guide explains the trade-off.

Limit what faces the internet

Expose only what you must. A home server that runs one service is far harder to turn into an injection target than one that runs five.

Do these first

  1. Count how many production Linux hosts have kernel.yama.ptrace_scope other than 2, and fix them.
  2. List every container and service unit that holds CAP_SYS_PTRACE, and remove it unless a written exception exists.
  3. Ship the two auditd rules from section 7 of your runbook (opens and writes on /proc/*/mem) to every Linux fleet tier.
  4. Stand up one eBPF sensor on the most internet-facing host group and wire it into the SIEM.
  5. Split web-service and daemon user IDs on the five busiest hosts.
  6. Run the purple-team replay from section 9 and record the results as compliance evidence.

These rules are deliberately broad for a lab. In production, pre-filter the dir=/proc results in the SIEM (as the Sigma rules in section 5.5 do) rather than narrowing on the endpoint, so you keep the full picture for hunts.

8Common Mistakes and Best Practices

Ten concrete blue-team mistakes around this technique, each with the symptom you will notice, the root cause, the fix, and the prevention that keeps it away.

#MistakeSymptomRoot causeFixPrevention
1 Watching only ptrace syscalls Lab replay of proc-mem injection produces no alert at all. The write path uses open/lseek/write, not ptrace. Add the auditd and eBPF rules from section 5.5. Test every T1055 sub-technique rule against its own replay, not ptrace only.
2 No procfs audit coverage The SIEM shows zero events for /proc/*/mem, ever. No audit rules shipped; auditd absent from the base image. Deploy the lab rules from section 7, tuned per fleet tier. Put auditd coverage in the server build checklist, verified by config tests.
3 No allowlist for debuggers Developers get paged for routine debugging sessions. Rules fire on all proc-mem opens; known tooling was never inventoried. Inventory profiler and debugger use; add scoped filters with owners. Review the allowlist monthly; every entry needs a named owner.
4 Alert fatigue from read-only opens Hundreds of low-value alerts per week about maps or mem reads. Rules without flag or outcome checks treat reads and writes the same. Require write flags and success for page-worthy rules; route reads to hunt dashboards. Split rules by event shape: open-write, write, read-context.
5 Shared service user IDs Kernel permission checks pass for the web worker; alerts are the last line of defense. One account runs web app and daemons for convenience. Split user IDs per service on top hosts first. Make per-service users a platform standard with a lint check in deployment.
6 Containers with CAP_SYS_PTRACE Any container on a node can read and write neighbors' memory. Capability left in for a debug tool years ago. Drop the capability; grant per-pod exceptions in writing. Admission policy (cluster-side rule) rejects images requesting it.
7 Yama scope left at 0 Old hosts accept every injection attempt in the lab. Legacy base image; nobody owns sysctl security keys. Set scope 2 in the image; add drift alerts on the key. Assign sysctl security keys to the platform team with quarterly review.
8 No eBPF sensor on Linux fd-to-path gaps leave hunts with "descriptor 6" and no path. Endpoint spend went to Windows; Linux treated as second class. Deploy Falco, Tracee, or Tetragon on internet-facing hosts first. Include Linux coverage targets in the annual detection plan.
9 Alerts without an owner Proc-mem alerts age out untriaged. Rule deployed without escalation path or runbook. Attach a runbook and an owning team to every rule ID. Rule register with owner, runbook link, and last-test date per rule.
10 Detections never tested Rules pass review but fail silently after a pipeline change. No purple-team replay after deployments and field renames. Run the replay from section 9 after every pipeline change. Quarterly replay calendar with recorded evidence per technique.

Habits that keep the coverage honest

Daily

  • Review new proc-mem alerts with the allowlist open.
  • Check that auditd and sensor agents are reporting (agent health beats new rules).
  • Skim first-seen outbound connections from daemon hosts.

Weekly

  • Tune the noisiest rule; move one filter into version control.
  • Replay one technique in the lab, this week T1055.009.
  • Review the filter list diff with a second engineer.

Monthly

  • Full purple-team replay with recorded evidence.
  • Drift check on Yama scope and capabilities across the fleet.
  • Access review: who still shares a service user ID with a daemon?

Quick hunt query

Expect debugger and monitoring binaries on build hosts. Anything else, or any spike on a production tier, goes to triage. Adjust index and sourcetype names to your environment.

Response checklist

  • Confirm the event: syscall, path, write flags, success result.
  • Identify the opener process, its parent, and its user ID.
  • Identify the target daemon and what it serves.
  • Check for the chain: maps read before, write after, odd execution later.
  • Isolate the host at the network layer; preserve memory and logs first.
  • Stop the daemon only after the memory capture.
  • Run the fleet hunt query over 30 days.
  • Verify Yama scope and capabilities on the affected host group; fix drift.
  • Write the incident record with timeline, detection point, and lessons.
