T1055.012 Process Hollowing

Process hollowing is a Windows technique that hides attacker code inside a trusted program. The attacker starts a real system binary in a suspended state, replaces its code in memory, and lets it run. The file on disk stays clean, so only memory checks and process telemetry reveal the truth.

  • Tactic: Stealth (formerly Defense Evasion)

1Overview

This section explains process hollowing in plain words, shows why attackers like it, and tells you what this guide teaches.

A process is a program that is running in memory. Hollowing means the attacker removes the real code of a legitimate program from that memory and puts their own code in its place. The program name stays the same. The file on disk stays clean. Only the memory content changes.

The attacker usually targets svchost.exe, RuntimeBroker.exe, or another trusted Windows binary. First they start the binary in a suspended state, so its main thread never runs. Then they unmap the real image with ZwUnmapViewOfSection or NtUnmapViewOfSection. They reserve fresh memory with VirtualAllocEx and write their own PE (Portable Executable) image with WriteProcessMemory. Next, SetThreadContext points the frozen thread at the new entry point. A final ResumeThread call starts the code. From that moment, Windows schedules a process that looks normal but runs attacker code.

This matters because many detection systems trust process names and disk files. Task managers show a normal svchost.exe. File scans find nothing bad. Only memory checks, parent-child checks, and API (Application Programming Interface) telemetry expose the trick. Attackers also like it because mature malware frameworks support it, so it costs them little effort.

ATT&CK lists this behavior under two tactics: Stealth (formerly Defense Evasion) and Privilege Escalation. The tactic was called Defense Evasion until ATT&CK v17 renamed it to Stealth in 2025. Older rule tags and reports still use the old name, so you will see both in the wild. The injected process inherits the security context of the process that spawned it, so hollowing rarely grants more rights by itself. Its real value is hiding, because execution looks like a trusted program. ATT&CK also notes that hollowing is very similar to Thread Local Storage (T1055.005). The difference is that hollowing creates a new process, while T1055.005 targets an existing one.

Note

Process hollowing is old but still alive. Public vendor reporting keeps describing loaders that hollow svchost.exe, so detections for this pattern still pay off in 2025.

Where it fits in the attack chain

  • After initial access: a phishing attachment or dropper lands the loader.
  • Loader stage: the loader hollows a trusted process to hide itself.
  • Command and control: the hollowed process beacons to attacker servers.
  • Stealth: the clean disk file defeats name-based and file-based checks.
  • Privilege escalation: ATT&CK lists this tactic, but the injected process inherits the spawning process's rights, so privilege gain is unlikely.

What you will learn in this guide

  • What process hollowing is and which Windows APIs it uses.
  • How the eight-step attack scene plays out on a real host.
  • Which log events (Sysmon Event ID 1, 8, and 10) expose the technique.

Written story — the same eight steps in text

  1. Step 1 — Phishing payload lands. The attacker sends an email with a document attachment. The user opens it, and a hidden loader program starts on the Windows host WORKSTATION-42. Evidence: suspicious file created SOC view: a suspicious file was created and a new unknown process started. File and process creation events are the first hints.
  2. Step 2 — Loader creates svchost.exe suspended. The loader calls CreateProcessW to start svchost.exe with the CREATE_SUSPENDED flag. The real service host program never runs its own code; its main thread is frozen at the start. Evidence: Sysmon E1 — wrong parent SOC view: Sysmon Event ID 1 shows svchost.exe starting from a non-services parent. This is a top hollowing signal.
  3. Step 3 — Loader unmaps the real image. The loader calls NtUnmapViewOfSection. This removes the real svchost program image from the memory of the new process, leaving space for the payload. Evidence: EDR image unmap hook SOC view: EDR (Endpoint Detection and Response) hooks and the ETW (Event Tracing for Windows) Threat Intelligence provider report an image unmap inside a fresh process.
  4. Step 4 — Loader writes the malicious PE. The loader uses WriteProcessMemory to copy its own PE (Portable Executable) image into the process: headers first, then sections, with relocations fixed for the new base address. Evidence: Sysmon E10 — VM write 0x1F0FFF SOC view: Sysmon Event ID 10 logs PROCESS_VM_WRITE (the 0x20 right inside the broad 0x1F0FFF mask) from the temp-folder loader into svchost.exe.
  5. Step 5 — Entry point set, thread resumed. The loader calls SetThreadContext to point the frozen main thread at the payload entry point, then calls ResumeThread. The trusted binary now runs attacker code. Evidence: EDR context rewrite + resume SOC view: the EDR flags a thread context rewrite and a resume call on a suspended system binary, plus a memory image mismatch.
  6. Step 6 — Attacker code runs from unbacked memory. The hollowed svchost.exe executes the payload from unbacked memory, that is, memory regions with no file on disk behind them. The disk file of svchost.exe is still perfectly clean. Evidence: scan — unbacked RWX region SOC view: a memory scan finds executable RWX (read-write-execute) regions with no file backing inside a signed process. Image path and mapped section do not match.
  7. Step 7 — Beacon to command and control. The hollowed process beacons to the C2 (command and control) server. On the network it looks like traffic from svchost.exe, but the service group flag is missing and the destination is rare. Evidence: netflow — svchost to C2 (no -k) SOC view: svchost.exe without a -k service group argument makes a rare outbound connection. Proxy and EDR network events agree.
  8. Step 8 — Defender response. The defender isolates the host, captures memory, runs a pe-sieve style scan, blocks the parent-child lineage for every endpoint, and deploys mitigation policies such as dynamic code prohibition. Evidence: host isolated, memory captured SOC view: containment confirmed. The host is isolated, memory is captured for forensics, and the loader lineage is blocked everywhere else.

3Red Team / Hacker Perspective

This section explains how attackers perform process hollowing and why they pick it. It is written for defenders and authorized red teams. Everything here is for lab practice on systems you own.

Lab use only

The steps below describe a real attack pattern. Use this knowledge only to build detections and to test them in an isolated lab. Do not run hollowing tools on systems you do not own, and never on production or managed networks. Unauthorized access to computer systems is a crime in most countries.

Why attackers choose hollowing

  • The disk file of the hollowed process is clean, so file scans find nothing.
  • The process name is trusted. Task managers and simple log checks show a normal svchost.exe.
  • Firewall rules often allow svchost.exe to talk to the network, so beacons blend in.
  • Mature malware frameworks ship hollowing loaders, so the cost is low.
  • The payload exists only in memory. A disk-only response wipes nothing.

Preconditions for the technique

  • Code execution on the Windows host, usually from a phishing attachment or dropper.
  • Permission to create processes in the same session (normal user rights are enough).
  • A PE (Portable Executable) payload that matches the architecture of the host binary.
  • Knowledge of the PE layout: headers, sections, and the relocation table.
  • No mitigation policy in place that blocks dynamic code or unbacked memory.

The eight steps, in plain language

  1. Choose the host binary. Attackers pick a trusted, common binary such as svchost.exe or RuntimeBroker.exe. svchost.exe is popular because its network traffic blends in.
  2. Create the process suspended. The loader calls CreateProcessW with the CREATE_SUSPENDED flag. The main thread is frozen before the first instruction runs.
  3. Unmap the real image. The loader calls ZwUnmapViewOfSection or NtUnmapViewOfSection to remove the legitimate image from memory. Some variants skip this step and map over the image with section APIs instead.
  4. Write the payload image. The loader uses VirtualAllocEx to reserve space in the target, then WriteProcessMemory to copy its PE headers and sections. It fixes relocations so the code works at the new base address.
  5. Point the thread at the payload. The loader uses SetThreadContext to set the entry point in the frozen thread. Variants patch the PEB (Process Environment Block) image base delta instead, so the Windows loader resolves imports correctly.
  6. Resume the thread. A call to ResumeThread starts execution. The trusted binary now runs attacker code.
  7. Establish command and control. The payload beacons out from inside the trusted process name.
  8. Clean up. The loader process may delete itself. The only live artifact is the hollowed process.

Common variations

  • Section mapping: the loader maps the payload with NtCreateSection and NtMapViewOfSection instead of unmapping first.
  • Text-section overwrite: only the .text (code) section of the real image is replaced. The rest of the image stays intact, which defeats simple unmap checks.
  • Transacted loading: the payload is loaded from a memory-backed transaction. This is close to T1055.013 Process Doppelgänging.
  • PEB patching: instead of entry-point tricks, the loader patches the PEB image base delta so the Windows loader resolves imports against the payload.
  • RunPE-style loaders: open-source lab tools implement the classic unmap-and-write flow and are widely studied.

Mistakes hollowing builders make

  • Architecture mismatch: writing a 32-bit payload into a 64-bit host process crashes it.
  • Missing relocation fixes: the payload crashes or misbehaves at the new base address.
  • Import resolution skipped: the payload runs until the first API call, then dies.
  • Wrong entry point: the thread resumes into empty memory and the process faults, which creates a Windows Error Reporting event defenders can see.
  • Loud parents: spawning svchost.exe from a temp folder is exactly what the best detections watch for.

For lab study, the public proof of concept by John Leitch (2011) and open-source education projects show the full flow. Run them only inside an isolated virtual machine with no network access to your organization. A safer exercise is to run a published red-team framework that supports this technique and to watch which of your rules fire.

4Blue Team / SOC Perspective

This section shows what defenders see when hollowing happens, which artifacts it leaves, and a simple triage flow for the first hour.

Defenders rarely see hollowing directly. They see small wrong details around a normal-looking process. Common examples: a service host with the wrong parent, a process access event with write rights, unbacked executable memory, or a strange network connection from a trusted process. Each detail alone can look harmless. Together they tell one story.

Artifacts hollowing leaves behind

ArtifactWhere it appearsWhy it matters
svchost.exe with a non-services parentSysmon Event ID 1, Security 4688A real service host is started by the service control manager. Any other parent is a strong hollowing or masquerading signal.
Command line without the -k flagSysmon Event ID 1, command-line auditingWindows always starts svchost.exe with a -k service group. A missing flag means the process is fake or hollowed.
Cross-process memory writeSysmon Event ID 10 (ProcessAccess)GrantedAccess masks such as 0x1F0FFF include PROCESS_VM_WRITE. A user-mode loader writing into another process is the hollowing moment.
Remote thread into a system binarySysmon Event ID 8 (CreateRemoteThread)Some variants use remote threads instead of resume tricks. Source from a temp path is very suspicious.
Unbacked executable memoryEDR memory inspection, pe-sieve and moneta style scannersExecutable regions with no file on disk behind them mean injected or hollowed code is running.
Image path mismatchMemory scanners, EDR inspectionThe PEB (Process Environment Block) image path does not match the mapped section, which is a hollowing fingerprint.
Rare outbound connection from a service hostProxy logs, NetFlow, firewall, Zeeksvchost.exe traffic is normally limited to known service groups. A rare destination is worth review.

Look in the logs

Sysmon Event IDs 1, 8, and 10 are the core sources. Security event 4688 with command-line auditing is the backup. Forward both to your SIEM (Security Information and Event Management) platform and keep the fields listed in section 5.4.

Look in memory

Run an EDR memory inspection or a pe-sieve style scan on any suspect process. Hollowing shows up as unbacked executable memory and as an image path that does not match the mapped section. Dump the region for analysis.

Look at the network

Join process names with connection logs. A svchost.exe that never talks out suddenly connecting to a rare IP address, or without a matching -k group, deserves a close look.

Watch out for false positives

Legitimate installers, debuggers, software updaters, some anti-cheat tools, and DRM (Digital Rights Management) software also read and write other process memory. Tune with parent-path allowlists and signed-publisher filters before you alert.

First-hour triage flow

  1. Confirm the parent-child anomaly. Pull the Sysmon Event ID 1 record. Check parent image, command line, user, and the hash of the parent.
  2. Check the process access chain. Find Event ID 10 records where the source is the same parent and the target is the suspect process.
  3. Scan memory. Ask the endpoint team for a memory inspection of the suspect process. Look for unbacked executable regions.
  4. Join network context. List connections made by the suspect process in the last 24 hours. Note rare destinations.
  5. Decide the scope. Search all endpoints for the same parent hash, the same command line, and the same lineage.
  6. Contain. Isolate affected hosts, capture memory, and block the loader hash and lineage.
  7. Eradicate and report. Remove persistence, rebuild if needed, and record the case with the evidence list.

5.2Threat Intelligence

Threat intelligence makes your detections sharper. It tells you which families actually use this technique, which binaries they hollow, and which artifacts are worth alerting on. Use the sources below and keep the confidence levels honest.

MITRE ATT&CK

The official T1055.012 page documents 44 procedure examples at the time of writing. It names the malware families and groups and states the exact behavior each one showed. Start here, then pivot to the parent T1055 page. ATT&CK is free and structured, which makes it easy to turn into detection work.

Vendor reporting

Endpoint and antivirus vendors publish campaign reports. Public reporting over many years consistently describes PlugX-family implants starting and hollowing svchost.exe. That pattern is documented in vendor reporting, but PlugX is not currently listed on the ATT&CK page for this sub-technique. Treat each report as one data point and note the publication date.

OSINT (open-source intelligence)

Research blogs, conference talks, and public proof-of-concept repositories document the technique in depth. The 2011 proof of concept by John Leitch is the classic public reference for the unmap-and-write pattern. Malware sandbox reports also show hollowing behavior for specific samples.

Commercial feeds and ISACs

Commercial intelligence feeds add machine-readable indicators, and sector ISACs (Information Sharing and Analysis Centers) share what member organizations actually saw. Filter both by your platform (Windows) and by technique to keep the signal rate high.

Internal telemetry

Your own incident history is the best intelligence. Keep a record of every hollowing-related case: which binary was hollowed, which parent started it, and which rule caught it. This drives tuning better than any external feed.

Collection and analysis tips

Collect with structure: map every report to ATT&CK technique IDs and store the sample hashes. Analyze with care: prefer reports that show the API sequence, not just the outcome. Apply by turning each confirmed pattern into a rule test, then into a Sigma rule like the ones in section 5.5.

Detection logic in one sentence each:

  • Alert when svchost.exe starts with a parent that is not the service control manager chain.
  • Alert when svchost.exe runs without the -k flag in its command line.
  • Alert when a process asks for broad access with memory write rights on another process and the source is not a known security tool.
  • Alert when a remote thread is created in a system binary by a user-path process.
  • Alert when a memory scanner reports unbacked executable memory or an image path mismatch in a signed process.
  • Alert when the antivirus engine itself reports hollowing-style behavior — that is free corroboration.

Sample event 1 — Sysmon Event ID 1: svchost.exe with wrong parent

  • Image: the started binary is the trusted service host — the hollowing target.
  • CommandLine: only the file name, with no -k group flag. Real launches always carry it.
  • ParentImage: a temp-folder program, not services.exe. This alone makes the event notable.
  • ProcessGuid: join key for the later access and thread events from the same process pair.
  • Hashes: the hash of the target binary; useful to confirm it is the genuine Windows file.

Sample event 2 — Sysmon Event ID 10: cross-process memory write

  • GrantedAccess: 0x1F0FFF is a full-access mask. It includes PROCESS_VM_WRITE (0x0020) and PROCESS_VM_OPERATION (0x0008), which hollowing needs.
  • SourceImage: the temp-folder loader from sample 1 — the same ParentImage, now acting on the target.
  • TargetProcessGuid: matches the created svchost.exe, so this is the hollowing write, not random access.
  • CallTrace: the last frame points into the loader binary, which shows user-mode code drove the access.

Sample event 3 — Sysmon Event ID 8: remote thread variant

  • StartModule of Unmapped: the new thread starts in memory that belongs to no loaded module — a classic injected-code fingerprint.
  • StartAddress: not inside any known image range, which supports the injection read.
  • Same source and target as sample 2, so both events describe one hollowing operation.

Sample event 4 — EDR memory scan: unbacked executable memory

  • protection of RWX (read, write, execute): self-modifying or injected code almost always needs this mix.
  • unbacked_executable_memory: the decisive hollowing artifact — code running with no disk file behind it.
  • image_path_mismatch: the PEB (Process Environment Block) claims one image, the memory manager holds another.
  • verdict: scanner-level conclusion; treat it as a strong lead, then confirm with the process lineage.

5.5Sigma Rules and Splunk SPL

Sigma (a free rule format for log detections) rules below cover the six detection ideas from section 5.4. Each rule is followed by a matching Splunk SPL (Search Processing Language) query, a mapping note, false positives, tuning guidance, and a severity. All rules are for a Splunk deployment that ingests Sysmon XML events into index=sysmon and Windows Security events into index=wineventlog. Adjust index and sourcetype names to your environment. The Sigma tags keep attack.defense_evasion because that tag predates the ATT&CK v17 rename of the tactic to Stealth.

Rule 1 — Suspicious svchost.exe parent process Severity: high

The single best early signal for hollowing: the service host starting from anything other than the service control manager chain.

Mapping note: Sigma Image|endswith becomes the Splunk wildcard Image="*\\svchost.exe"; the double backslash in SPL yields the literal single backslash of the Windows path. The Sigma field EventID is EventCode in this sourcetype.

False positives: custom service-host style agents, installer bootstraps, and some backup tools that start service processes.

Tuning: add your known agent parents to filter_known_parents by endswith value, and prefer parent-hash allowlists over name lists where you can.

Rule 2 — svchost.exe command line missing the service group flag Severity: high

Windows always starts the real service host with a -k group argument. A missing flag means the process is fake or hollowed.

Mapping note: Sigma CommandLine|contains becomes the Splunk like() test with % wildcards; the negation moves into the where clause, which matches the Sigma condition.

False positives: monitoring agents that strip or truncate command lines; very old custom services named svchost.

Tuning: if your fleet reports truncation, join with the process hash: genuine svchost.exe hashes are stable per build, so hash context removes nearly all noise.

Rule 3 — Cross-process memory write from a user-mode loader Severity: high

The hollowing moment itself: a process asks for full access with memory write rights on another process.

Mapping note: Sigma endswith on the hex mask becomes a regex match anchored to the end after lowering the case. The self-access filter compares the two image fields directly in SPL, which classic Sigma expresses as a filter selection.

False positives: every security tool that scans process memory; developer debuggers on engineering hosts.

Tuning: maintain the security-tool list as a lookup table keyed by signed publisher, and scope the rule out on build servers where debugging is normal. Combine with Rule 1 or Rule 2 for the strongest story.

Rule 4 — Remote thread into a system binary Severity: medium

Covers hollowing variants that use remote threads instead of resume tricks. Noisier than the first three rules, so severity stays medium.

Mapping note: Sigma SourceImage|startswith becomes the Splunk like() pattern C:\Windows\%; both versions keep the same scope and filter out system-component sources the same way.

False positives: installers, updaters, and developer tooling that create threads in helper processes.

Tuning: raise the value by requiring StartModule of Unmapped or a target that is a system binary; both fields are already in the event.

Rule 5 — Antivirus behavioral hollowing alert Severity: high

When the built-in antivirus engine reports hollowing-style behavior, that is free corroboration. Forward it and alert on it.

Mapping note: the Defender operational log lands in the Windows event channel; Sigma EventID maps to EventCode in this sourcetype, and ThreatName|contains maps to the like() test.

False positives: rare. The engine names the behavior family, so noise is low.

Tuning: if your engine uses different behavior names, widen the match to hollow and review what comes back; keep tamper protection on so the engine itself cannot be disabled.

Rule 6 — svchost.exe with unusual parent via Security 4688 Severity: high

The backup rule for hosts without Sysmon. Windows Security event 4688 carries parent and child names when process auditing is on.

Mapping note: Sigma fields NewProcessName and ParentProcessName exist in the Security 4688 XML record; the plain WinEventLog:Security sourcetype exposes them after field extraction.

False positives: management agents and installers, as with Rule 1.

Tuning: enable command-line auditing (Audit Process Creation with the command-line policy) so ProcessCommandLine fills; then the Rule 2 idea can also run on this source. Adjust index and sourcetype names to your environment.

Good practice

Test every rule before you alert on it. Run an authorized hollowing simulation in a lab, confirm each rule fires, and record the test date next to the rule. A rule that never fired is a guess, not a control.

6Real-World Case Study

A composite espionage-style intrusion, informed by public vendor reporting on PlugX-style svchost.exe hollowing. Names, hosts, and times are illustrative. The detection logic and response actions match what the reporting describes.

Composite scenario

Public vendor reporting from 2018 through 2024 repeatedly describes PlugX-family loaders that start svchost.exe in a suspended state and hollow it. No single vendor report matches every detail below, so treat this as a teaching scenario built from consistent public patterns, not as a verified incident record.

Context

A regional engineering firm with about 800 Windows endpoints faced a targeted email campaign. The attackers wanted long-term access to project documents. Their loader used process hollowing against svchost.exe so that every stage after delivery looked like a normal Windows service host. The organization ran Sysmon on most endpoints with a central SIEM, plus antivirus with behavioral detections. No EDR memory scanning was configured at the time.

Timeline

  • Day 0, 09:14A finance employee opens an archive attached to a spoofed supplier email. A loader executable drops into the user temp folder and starts.
  • Day 0, 09:15The loader calls CreateProcessW on svchost.exe with CREATE_SUSPENDED. Sysmon records Event ID 1: service host, temp-folder parent.
  • Day 0, 09:15The loader unmaps the real image and writes its own PE image with relocations fixed. Sysmon records Event ID 10 with GrantedAccess 0x1F0FFF.
  • Day 0, 09:16The loader sets the entry point and resumes the thread. The implant starts inside the hollowed svchost.exe.
  • Day 0, 09:19The hollowed process beacons to a rare external IP address. No -k service group exists on its command line.
  • Day 0 to Day 6The implant collects documents and waits. Parent-child rules existed but pointed to a generic channel that nobody owned, so the alert sat unreviewed.
  • Day 6, 11:02Detection point: a detection engineer on routine rule health work notices the parent-child alert queue. It correlates with a ProcessAccess write event from the same loader hash. The engineer opens a case.
  • Day 6, 12:40The SOC isolates the host, captures memory, and runs a pe-sieve style scan: unbacked executable memory confirmed inside svchost.exe.
  • Day 7 to Day 8Eradication: the loader hash and lineage are blocked, the Run key persistence is removed, and two more hosts with the same lineage are rebuilt.
  • Day 12Recovery: hosts are returned to production with EDR memory scanning enabled and the tuned rules deployed.

Attack chain summary

  1. Initial access: phishing attachment with a loader inside an archive.
  2. Execution: the loader runs from the user temp folder with normal user rights.
  3. Stealth: hollowing a suspended svchost.exe — the core technique on this page.
  4. Command and control: beaconing from inside the trusted process name.
  5. Collection: staged documents waiting in the hollowed process working directory.

Detection point

Two signals decided the case. First, Sysmon Event ID 1 showed svchost.exe with a temp-folder parent and no -k flag. Second, Event ID 10 showed the same loader hash asking for 0x1F0FFF access on the new process. Memory scanning later confirmed unbacked executable memory, but the case was opened from the log pair alone.

Team response and communication

The SOC lead informed the security manager within one hour of the case opening, since a targeted campaign was suspected. The IT service desk sent a company notice about the phishing email. The detection engineer filed the tuned rules and the incident commander kept a single timeline document so every team worked from the same facts.

Impact and consequences

Three hosts were compromised. The implant stayed about six days on the first host. Forensics found staged project documents but no confirmed exfiltration to the C2 server beyond beacons. The main business cost was response time, two rebuilt workstations, and a delayed project review while access was reset.

Lessons learned

  • Parent-child rules need an owner. An unreviewed alert queue turned a day-zero detection into a day-six discovery.
  • Command-line telemetry was worth the extra logging cost: the missing -k flag removed all doubt during triage.
  • Memory scanning closed the case with confidence that logs alone could not provide.
  • Blocking the loader hash stopped the campaign only after lineage blocking covered the whole chain.
  • A one-page incident timeline kept communication simple across teams.
  • The same public reporting that describes this technique also described its detections — reading it cut rule work from days to hours.

ATT&CK mitigation and detection strategy mapping

ATT&CK lists one official mitigation for this technique: M1040 Behavior Prevention on Endpoint. Its idea is that some endpoint security solutions can block common behavior sequences that appear during injection. The EDR behavior-blocking and mitigation-policy rows above are that mitigation in practice.

ATT&CK also publishes a detection strategy for this technique: DET0382 — Process Hollowing on Windows. Its core idea follows the exact API chain: a suspended process creation (CREATE_SUSPENDED), then NtUnmapViewOfSection, then VirtualAllocEx and WriteProcessMemory, then SetThreadContext, then ResumeThread. The Sigma rules in section 5.5 watch the same chain from the log side.

Good practice

Enable dynamic code prohibition first on servers that never run user software. Those machines gain the most protection and produce almost no false positives, which makes the rollout conversation easy.

Home and small office

Keep the built-in antivirus on with tamper protection enabled, and let updates install automatically. Modern consumer engines already include behavioral checks that flag hollowing-style activity.

Attachments and downloads

Treat unexpected attachments as hostile, especially archives. When in doubt, open them on a non-work device or upload them to a scanner service first. Most hollowing incidents start with one double-click.

Backups

Keep one backup copy offline or immutable. If a hollowed process is only the first step of a ransomware attack, backups decide whether the week is an inconvenience or a disaster.

Do these first

  1. Confirm Sysmon or equivalent telemetry is on every Windows endpoint and forwarded centrally.
  2. Deploy the six rules in section 5.5 and test each one with a lab simulation.
  3. Turn on EDR memory scanning for servers first, then workstations.
  4. Remove standing local admin rights from standard users.
  5. Enable command-line auditing so the -k check works everywhere.
  6. Write the one-page response runbook: isolate, capture memory, scan, block lineage, rebuild.

Daily habits

  • Review the wrong-parent and missing--k queues.
  • Check that Sysmon and EDR agents are reporting everywhere.
  • Note any svchost.exe making first-time outbound connections.

Weekly habits

  • Review rule volumes and tune the top three noisy rules.
  • Reconcile exclusions against the allowlist policy.
  • Read one new vendor report and map it to a rule or dismiss it.

  • Audit log-source coverage per site and per host group.

Start a trusted binary suspended, replace its image in memory, resume it: clean file on disk, attacker code in memory.

Response checklist

  • Pull the Sysmon E1 record: parent image, parent hash, command line, user.
  • Join the E10 record with the same process GUID pair and note GrantedAccess.
  • Check for an E8 record if the variant uses remote threads.
  • Isolate the host from the network; keep it powered on.
  • Capture memory of the suspect process and the full machine.
  • Run a pe-sieve style scan; save the findings JSON with the case.
  • Search all endpoints for the same loader hash, parent path, and lineage.
  • Block the loader hash and the whole parent-child lineage.
  • Remove persistence, rebuild affected hosts, and reset exposed credentials.
  • File the incident record with the timeline, evidence, and rule test results.
