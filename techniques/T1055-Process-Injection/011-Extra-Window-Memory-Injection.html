T1055.011 Extra Window Memory Injection

Windows lets every window class reserve a small block of spare bytes, called extra window memory (EWM). Attackers can fill those bytes with shellcode (small, position-independent machine code) and then point the window procedure at it. When any message arrives, the trusted GUI (Graphical User Interface) process runs the shellcode itself. Classic injection APIs never appear, so many security tools miss it.

1Overview

A plain-language look at what Extra Window Memory Injection is, why attackers pick it, and what you will learn on this page.

What the technique is

When a Windows program registers a window class, it can ask for extra window memory: spare bytes attached to every window of that class. The program sets the size with the cbWndExtra field at class registration. A class may request up to 40 bytes of this spare memory; Windows caps the request there. Many classes reserve 8 bytes or more, because a pointer needs 8 bytes on 64-bit Windows.

Attack code running in the same session finds such a window in another process with FindWindow or EnumWindows. It writes shellcode into the spare bytes in small pieces with SetWindowLongPtr, using a new offset for every write. Then it calls SetWindowLongPtr again with GWLP_WNDPROC and swaps the window procedure (the function that handles messages for a window) so it points at the shellcode. A final SendMessage makes the system call the new procedure, and the shellcode runs inside the victim process.

Why it matters

This trick avoids the classic signs of code injection. It uses no WriteProcessMemory, no CreateRemoteThread, and no section APIs. Many older EDR (Endpoint Detection and Response) hooks and simple detection rules never look at window APIs, so the writes pass silently.

Execution also happens inside a legitimate, often signed GUI (Graphical User Interface) process. A shell command or a network connection from mspaint.exe or a similar trusted binary looks wrong only if you compare behavior against a baseline. That is why this technique needs behavioral and memory-based detection, not just name checks.

Where it fits in the attack chain

Extra Window Memory Injection sits in the Stealth (formerly Defense Evasion) and Privilege Escalation tactics of MITRE ATT&CK, as sub-technique T1055.011 of T1055 Process Injection. An attacker first gains code execution in a user session, for example with a phishing loader. The injection then moves the real payload into a trusted process. From there the payload can persist, reach Command and Control (C2), and act under the cover of a benign program. ATT&CK renamed the Defense Evasion tactic to Stealth in 2025, in ATT&CK v17. Older reports and some tool tags still carry the old name.

It is a user-mode technique on Windows. It needs the same window station and desktop, and an integrity level that matches or exceeds the target. UIPI (User Interface Privilege Isolation) blocks window messages from a lower integrity process to a higher one, so a Medium integrity process cannot trigger a High integrity target this way.

Key terms in plain words

Window class: a template that describes a type of window (for example a button or an editor pane). Window procedure (WndProc): the function that receives and handles messages for a window. Shellcode: a small piece of machine code that runs wherever it is placed. Unbacked memory: memory that no file on disk backs, so a scanner cannot match it to a known program.

Written story (the same eight steps)

  1. Step 1 · Foothold The operator lands on a Windows workstation through a phishing attachment. A small loader process starts with normal user rights inside the user session. SOC view: EDR shows a suspicious new process under the user session, started from the Downloads folder.
  2. Step 2 · Window hunt The loader enumerates windows and window classes. It looks for a window whose class reserves enough spare bytes: cbWndExtra of 8 bytes or more on 64-bit Windows. SOC view: window enumeration is quiet. Native logs show almost nothing, so this stage often has no direct evidence.
  3. Step 3 · Chunked writes The loader writes position-independent shellcode into the spare bytes, chunk by chunk, using SetWindowLongPtr with a new offset for every write. SOC view: an EDR user-mode hook, or Sysmon Event 10 (ProcessAccess), can record the cross-process writes against the GUI process.
  4. Step 4 · Procedure swap SetWindowLongPtr with GWLP_WNDPROC swaps the window procedure pointer. The window now points at the shellcode inside the extra window memory. SOC view: an EDR cross-process window-procedure change alert fires. This is the strongest early signal of Extra Window Memory Injection.
  5. Step 5 · Trigger and execution The loader sends any message to the window with SendMessage. The system calls the new window procedure, and the shellcode runs inside the trusted GUI process. SOC view: an unbacked-memory execution alert fires. The call stack of the API call has no image path on disk.
  6. Step 6 · Memory-only staging The payload stages a second implant in memory only. It never writes a new file to disk, so file-based antivirus has nothing to scan. SOC view: a memory scan finds an unbacked read-write-execute (RWX) region inside the signed GUI process.
  7. Step 7 · Beacon The implant beacons to its Command and Control (C2) server from the trusted GUI process. The traffic looks like it comes from a benign application. SOC view: the network team sees a rare outbound connection from a GUI app. Proxy or firewall logs confirm the beacon pattern.
  8. Step 8 · Defender response Defenders respond: they isolate the endpoint, capture memory, scan for unbacked RWX regions, and block the loader lineage across the estate. SOC view: containment. The host is isolated, volatile evidence is preserved, and the loader hash and parents are blocked.

3Red Team / Hacker Perspective

Why an attacker would choose this technique, how the flow works at a high level, and which mistakes ruin it. Everything here is described for lab practice and defense.

Lab and defense use only

Use this material only in an isolated lab or in an authorized engagement with written permission. Running injection code on systems you do not own is illegal in most places. The snippets below are read-only or pseudo-code sketches; they are not working attack tools.

When attackers use it

Attackers pick Extra Window Memory Injection when they want to move code out of their own process without tripping the usual tripwires. It suits a loader that already runs in the user session and wants to blend in fast. This is not only a research pattern. ATT&CK documents the malware families Epic (S0091) and Power Loader (S0177) using it against Explorer. Public proof-of-concept code exists too, so copying the pattern is easy.

Red teams also use it on purpose: injecting into a signed GUI application is a clean way to test whether an EDR catches window-API abuse and unbacked execution.

Why they like it

  • No WriteProcessMemory, no CreateRemoteThread, no section APIs, so classic hooks see little.
  • The writes use a common GUI API, SetWindowLongPtr, that normal apps call every day.
  • Code ends up inside a signed, trusted process with a real window.
  • The trigger is an ordinary window message, which almost no log records.
  • It needs only user rights in the same session; no admin token required.

How it is performed (high-level flow)

  1. Foothold. Loader code runs in the user session after phishing or a drive-by stage. It needs the same window station and desktop as the target.
  2. Window hunt. The loader calls EnumWindows or FindWindow, maps handles to process IDs with GetWindowThreadProcessId, and reads each class with GetClassLong to check cbWndExtra. Classes that reserve 8 bytes or more qualify on 64-bit Windows.
  3. Chunked writes. The loader writes position-independent shellcode into the spare bytes. Each SetWindowLongPtr call writes 8 bytes at one offset, so the payload must be small or split across many calls.
  4. Procedure swap. One more SetWindowLongPtr call with GWLP_WNDPROC points the window procedure at the shellcode inside the extra memory.
  5. Trigger. SendMessage, PostMessage, or SendMessageTimeout delivers any message. The system dispatches it to the swapped procedure, and the shellcode runs in the victim process.
  6. Stage and act. From inside the trusted process, the payload unpacks more code, connects out, and continues the operation.
Precondition 1
Attacker code runs in the same window station and desktop (the same interactive session) as the target window.
Precondition 2
Integrity level matches or exceeds the target. UIPI blocks the trigger message from lower to higher integrity processes.
Precondition 3
A target window class with cbWndExtra of 8 bytes or more, owned by a process the attacker can reach.
Precondition 4
Payload must be position-independent and small, because spare bytes are tiny and addresses are not known in advance.

Common variations

  • 32-bit vs 64-bit. On 32-bit builds the same flow uses SetWindowLong with 4-byte writes; mixing bitness between loader and target fails.
  • Shared-section variant. Some malware writes the payload into a shared section of the target's memory and stores only a pointer in the extra window memory. The 40-byte cap then stops mattering.
  • DEP-aware variant. Power Loader-style code chains window procedures with NTDLL functions to copy the payload into an executable region, which defeats Data Execution Prevention (DEP).
  • Choosing targets. Attackers prefer long-lived, low-attention processes with big spare fields, such as apps that subclass windows.
  • Sibling technique. T1055.015 ListPlanting abuses a list-control memory area and is triggered the same way, with a message to the control.
  • Trigger choice. SendMessage is synchronous and stable; PostMessage is fire-and-forget but can race.

Mistakes that break the technique

  • Targeting a window in a higher integrity session; UIPI silently swallows the trigger.
  • Using non-position-independent shellcode, which crashes the host process and burns the foothold.
  • Forgetting WOW64 (32-bit on 64-bit) thunking, so offsets and pointer sizes do not match.
  • Writing past cbWndExtra, which corrupts the window object and crashes quickly.
  • Picking a process that dies quickly, so the injected code never runs.

4Blue Team / SOC Perspective

How this technique looks from the defender side: the artifacts it leaves, the places to look, and a short triage flow your analysts can follow.

Extra Window Memory Injection is quiet, but not invisible. The attacker touches another process from the outside, and modern sensors notice that touch. The strongest signals are a cross-process handle with wide rights, a window-procedure change alert from EDR, and code that executes from memory no file backs. Each signal alone can be a false positive; together they are a strong case.

Logs

Turn on Sysmon with Event 10 (ProcessAccess) and keep CallTrace. Add Event 1 (process creation) and Event 3 (network connection). On newer builds, collect the ETW Win32k providers through your pipeline. EDR consoles often already record window-API behavior; make sure those events reach your SIEM (Security Information and Event Management) platform.

Memory

Scan long-running GUI processes for unbacked RWX (read-write-execute) regions. If you suspect a host, capture a full memory image before killing anything, because the payload exists only in memory. Call-stack inspection on the suspect thread shows the window-memory region instead of a mapped image.

Network

Baseline which processes normally talk out. GUI utilities almost never do. A periodic connection from one to a rare external IP, over 443 or 8443, is worth a look in proxy logs. Match the time window against EDR process access and memory alerts.

Why it matters to the SOC

A successful EWM injection gives the attacker a trusted home base. Alerts that name a benign process are easy to dismiss, so this technique buys time. Teams that only alert on CreateRemoteThread will see nothing at all. The fix is behavioral coverage: process access with call traces, window-API telemetry, and memory scanning.

Fit in the attack chain

Expect this technique after initial access and before C2. The loader that performs it is the pivot: block or alert on that lineage and you catch the whole chain. If you see the injection alerts, hunt backwards for the loader and forwards for staging and beaconing.

Triage flow when an EWM-style alert fires

  1. Confirm the pattern. Check the process access event: source process, target process, granted rights, and call trace. Look for an unbacked frame.
  2. Check the source. Did the source process start from a user-writable path? Pull its Sysmon Event 1 record and hash.
  3. Correlate. Search the same host for window-API alerts, memory scan findings, and new network connections in a plus or minus 30 minute window.
  4. Decide. If two or more signals line up, treat it as active intrusion activity, not noise.
  5. Contain. Isolate the host with the EDR containment action. Capture memory first or simultaneously, never after.
  6. Sweep. Search the estate for the loader hash, its parents, and the C2 domain or IP. Report per your incident process.
False positives to expect

UI automation frameworks (UIA), remote monitoring and management (RMM) tools, and input remappers all touch foreign window handles. IME (Input Method Editor) software and apps that legitimately subclass windows call window APIs too. Baseline them, then tune by source path and signature, never by process name alone.

5.2Threat Intelligence

Good intelligence for this technique mixes public research, vendor reporting, and your own telemetry. Be honest in reports: group-level attribution is thin, so label confidence levels clearly and mark composite scenarios as composite.

MITRE ATT&CK and vendor research

The ATT&CK page for T1055.011 gives the canonical description and procedure examples, and it publishes a detection strategy for this technique (DET0217, Extra Window Memory Injection on Windows). Vendor detection guides, especially public detection engineering write-ups from EDR vendors, describe how sensors see SetWindowLongPtr abuse. Use both as the base vocabulary for your rules and reports.

OSINT: research blogs and PoC repositories

Public Windows injection research collections on code-hosting sites include extra-window-memory proof-of-concept code, and conference talks walk through the mechanics. Track new commits in those repositories; a fresh PoC often precedes tool adoption in the wild by months.

Commercial feeds and ISACs

Commercial threat feeds rarely name this sub-technique, but they do report loader families that rotate injection methods. ISAC (Information Sharing and Analysis Center) bulletins help you learn when peers see similar loader behavior in your sector.

Internal telemetry

Your own environment is the richest source. Baseline which processes legitimately open cross-process handles, which call window APIs from unusual stacks, and which GUI binaries ever speak to the network. Feed those baselines back into rule tuning (section 5.5).

Detection logic in one sentence each:

  • Alert when a non-system source process opens a wide-rights handle to a benign GUI process.
  • Alert when the source process path is user-writable and the call trace contains an unbacked frame.
  • Alert when a scripting host command line names window-long APIs or GWLP_WNDPROC.
  • Alert when a quiet GUI application opens an external connection.
  • Alert when an EDR memory scan finds an unbacked RWX region in any long-running GUI process.

Event sample 1: Sysmon Event 10, ProcessAccess (the core signal)

  • SourceImage: the process asking for the handle. Here it sits in a user-writable path, which is the first red flag.
  • TargetImage: the victim. A benign, signed GUI binary that rarely gets opened cross-process.
  • GrantedAccess: 0x1F0FFF means near-full rights, enough for any window operation the attacker needs.
  • CallTrace: the caller stack. The last frame resolves to no module on disk, which points at memory-resident code.
  • SourceUser / TargetUser: same user here; the injection stays inside one session, which matches this technique.

Event sample 2: Sysmon Event 1, Process Creation (loader lineage)

  • Image and CurrentDirectory: the loader runs from a user-writable folder, a classic phishing-loader trait.
  • ParentImage: the shell opened the file, so the chain starts at user interaction.
  • IntegrityLevel: Medium, which tells you which window targets are reachable under UIPI.
  • Hashes: the SHA-256 anchor for containment blocks and estate-wide sweeps.

Event sample 3: Sysmon Event 3, Network Connection (beacon from a GUI app)

  • Image: a paint program is connecting out. On a healthy baseline this binary never opens sockets, so the record is a signal by itself.
  • Initiated: true means the process started the connection, not an inbound accept.
  • DestinationIp: 203.0.113.77 belongs to a documentation range reserved for examples, used here on purpose; in a real event it would be the C2 address.
  • DestinationPort: 443 hides the beacon in normal-looking TLS; the proxy log, not the port, tells the truth.

Event sample 4: EDR sensor memory finding (unbacked RWX region)

  • event_type: a scheduled or on-demand scan found the region; this is the fileless artifact the payload hoped to hide.
  • protection: RWX (read-write-execute) is rare in normal user processes and is the classic shellcode home.
  • backed_by_image: false means no file on disk maps to this region, so hash-based tools see nothing.
  • first_seen: compare with the ProcessAccess burst a few minutes earlier to build the timeline.
  • verdict and confidence: route anything above 70 for this process class straight to triage.

Event sample 5: Windows Security 4688 (fallback lineage)

  • EventID: 4688 fires on process creation when the audit policy enables it; it is the fallback when Sysmon is missing.
  • NewProcessName and ParentProcessName: enough to rebuild a thin lineage and match it to the Sysmon record.
  • MandatoryLabel: Medium integrity again, confirming which window targets UIPI puts out of reach.
  • TokenElevationType: %%1938 means a limited token; the loader never needed admin rights for this technique.

5.5Sigma Rules and Splunk SPL

Six Sigma rules cover the ranked threats from section 5.3. Each rule lists the matching Splunk SPL query, a mapping note, false positives, tuning guidance, and severity. The rules assume a Sysmon feed in the SIEM; adjust index and sourcetype names to your environment. All rules are experimental or test: deploy in monitor mode first, tune for two weeks, then raise severity. The rules keep the Sigma tag attack.defense_evasion, which predates the ATT&CK v17 rename of that tactic to Stealth.

Sigma rule 1: cross-process handle to a GUI process with full rights

Catches the moment the loader opens the victim process. Mapping note: Sigma EventID maps to SPL EventCode; the Sysmon XML sourcetype keeps SourceImage, TargetImage, GrantedAccess, and CallTrace as extracted fields with the same names. Severity: high.

Field assumptions: Sysmon XML fields are auto-extracted with the names shown. False positives come from management and automation tooling; tune by adding signed agent paths to a filter, never by dropping the rule. If your EDR also exports process access events, mirror this rule against that index.

Sigma rule 2: process access from a user-writable path

Tightens rule 1 by asking where the source process lives. Mapping note: Sigma startswith and contains map to SPL wildcards inside the same quoted match; the not 1 of filter_* condition becomes a chained NOT ... IN search. Severity: high.

Tune the productivity filter to your actual per-user application estate. Keep the target list short; a long list invites alert noise from OS utilities.

Sigma rule 3: unbacked frame in a process access call trace

Catches the execution stage, when injected code calls into APIs from memory no image file backs. Mapping note: the Sigma contains modifier maps to a Splunk wildcard string; the pipe character inside CallTrace values is safe in both. Severity: high.

Validate the exact unknown-frame text on one host before rolling out; some Sysmon versions format unknown frames differently. The count > 2 filter keeps one-off parsing quirks quiet while keeping real repeats visible.

Sigma rule 4: window-long API names on a scripting host command line

Catches tooling that shells out to a scripting host with inline window API code. Mapping note: Sigma Image|endswith and CommandLine|contains map to SPL wildcard matches; the two Sigma selections become a parenthesized AND group in SPL. Severity: medium.

This rule watches the technique's tooling, not the technique itself, so treat it as a medium-severity lead. Correlate a hit with rule 1 or rule 3 events on the same host before escalating.

Sigma rule 5: outbound connection from a quiet GUI application

Catches the beacon stage, where the implant lives inside a process that never talks out on a healthy network. Mapping note: Sigma Image|endswith maps to SPL wildcard matches; the Sigma cidr filter maps to Splunk CIDR-style matches on DestinationIp. Severity: medium.

Join this with proxy logs to separate add-in noise from real beacons: a real beacon repeats on a schedule to one destination. If your estate uses virtual desktop infrastructure (VDI) images, exclude those hosts or accept this rule as hunt-only.

Sigma rule 6: combined EWM pattern on a single event

The high-precision rule: a user-writable source, a GUI target with full rights, and an unbacked frame in one record. One event with all three traits is a strong signal and should trigger memory capture. Mapping note: all Sigma selection keys AND together, so the SPL keeps every term in the base search; no stats logic is needed. Severity: critical.

Because every term must match at once, this rule is quiet by construction. Any hit deserves a same-day look, a memory capture, and a check of rule 2 and rule 3 history for the same host.

6Real-World Case Study

A worked example you can learn from, with the detection point, containment, and lessons learned spelled out.

Composite scenario, clearly labeled

This case study is a composite. It is assembled from public proof-of-concept tooling, published red-team exercise patterns, and common incident-response practice. The attack pattern itself matches documented malware behavior. Epic overwrote the function pointer in the extra window memory of Explorer's Shell_TrayWnd (ESET reporting). Power Loader abused the same window class to reach an NTDLL gadget and a ROP chain (MalwareTech, August 2013; WeLiveSecurity, March 2013). The incident story, the company, and the timeline stay fictional. No real-world attribution is claimed.

Context

A financial-services company ran an authorized purple-team exercise. The red team's goal was to measure EDR coverage of injection tradecraft on Windows workstations. The blue team knew an exercise was running but not when or how. The scenario used an EWM injection loader into a signed GUI application, followed by a memory-only second stage and a short beacon window.

  • Day 1, 09:41 Foothold. An approved phishing simulation delivers a loader to a test user. Sysmon Event 1 records the process starting from the user's Downloads folder. The EDR raises a low-severity process alert, which lands in the exercise queue.
  • Day 1, 09:42 Window hunt and writes. The loader enumerates windows, picks a class with cbWndExtra of 8 bytes, and writes shellcode chunk by chunk. Sysmon Event 10 records wide-rights process access to the GUI process from the loader path.
  • Day 1, 09:43 Detection point. The EDR cross-process window-procedure change alert fires, severity high. The linked telemetry shows the GWLP_WNDPROC swap against a foreign window and a call trace with an unbacked frame. This is the alert that decides the case.
  • Day 1, 09:52 Containment. The on-call analyst confirms the pattern in under ten minutes, isolates the host with the EDR containment action, and captures memory while the implant is still resident.
  • Day 1, 11:10 Memory analysis. Forensics finds the unbacked RWX region with the second-stage implant. No new file ever touched disk, which is why file-based antivirus stayed quiet the whole time.
  • Day 1, 14:00 Sweep. The SOC searches the estate for the loader hash, its parent path, and the exercise C2 domain. One more lab host shows the same lineage and is isolated as a precaution.
  • Day 2 Recovery and tuning. Hosts are rebuilt from known-good images, the exercise C2 domain is blocklisted, and rule 2 from section 5.5 is tuned from the findings. The exercise report goes to the detection engineering backlog.

What worked

  • The window-procedure change alert carried enough context (source path, target, call trace) for a fast decision.
  • Sysmon Event 10 with call traces was already flowing to the SIEM, so the EDR alert could be corroborated in seconds.
  • Containment preserved volatile memory before any cleanup, which made the analysis conclusive.
  • The exercise scope was written down, so the blue team escalated without fear of misjudging a real attack.

What hurt

  • The first process-creation alert was low severity and sat unread for two hours; lineage would have cut the timeline.
  • Window-API telemetry existed only in the EDR console, not the SIEM, so the first analyst had to switch tools.
  • No baseline existed for which processes legitimately open foreign window handles, so triage leaned on the vendor's verdict.
  • The runbook had no memory-capture step for unbacked-execution alerts; analysts improvised one on the spot.

Impact, communication, and lessons learned

Impact was limited to exercise hosts by design, and the beacon window lasted minutes. Communication followed the exercise protocol: the red team disclosed its actions at the containment point, and the blue team validated each detection rather than assuming coverage. Lessons learned, in priority order: route window-API and memory alerts to the SIEM with full context. Add a memory-capture step to the unbacked-execution runbook. Baseline benign window-handle usage per estate. Treat any combined-pattern rule hit (rule 6) as same-day. The team filed four detection backlog items and scheduled a quarterly purple-team repeat with a different injection sub-technique each time.

Home and small office

Keep Windows Update on, and use the built-in antivirus with cloud protection enabled. Most home users never need to run unknown installers from email or download sites, and that single habit stops the loader stage that feeds this technique.

Use a standard account

Work day to day as a standard user, not an administrator. Admin rights widen the set of windows a malicious process can reach and remove the UIPI safety margin between your session and system processes.

Watch for the strange

If a paint utility, a text editor, or a calculator suddenly wants firewall access, deny it and investigate. On a healthy Windows install, simple GUI apps do not need the network.

Do these first

  1. Verify Sysmon Event 10 with call traces is collected on every workstation and reaches the SIEM.
  2. Deploy the six Sigma rules from section 5.5 in monitor mode on a lab scope.
  3. Confirm the EDR raises a distinct alert on cross-process window-procedure changes; if not, ask the vendor how to enable it.
  4. Add a memory-capture step to the alert runbook for unbacked execution.
  5. Baseline the top twenty processes that legitimately open foreign window handles, and write them into the tuning notes.
  6. Book a quarterly purple-team test that exercises one injection sub-technique and files the evidence.

Technique
T1055.011 Extra Window Memory Injection, parent T1055 Process Injection, Windows only.
Core idea
Shellcode lives in the spare bytes of a window (cbWndExtra); the window procedure pointer is swapped with SetWindowLongPtr(GWLP_WNDPROC); a message triggers execution.
What is absent
No WriteProcessMemory, no CreateRemoteThread, no section APIs, nothing new on disk.
Access needs
Same session and desktop, matching or higher integrity, user rights only.
Best signals
Wide-rights cross-process process access with an unbacked call frame, EDR window-procedure change alert, unbacked RWX region, network from a quiet GUI app.
Weakest stage
Window enumeration leaves almost no native telemetry; pair it with the later stages.
Main false positives
UIA automation, RMM agents, IME software, input remappers, window-subclassing apps.
First response
Isolate host, capture memory, then sweep the estate for the loader lineage.

Response checklist for a suspected EWM injection

  • Confirm the process access pattern: source path, target GUI process, granted rights, unbacked frame.
  • Pull the loader lineage from Sysmon Event 1 or Security 4688 and record the hash.
  • Isolate the endpoint with the EDR containment action.
  • Capture a full memory image before any cleanup or reboot.
  • Scan the image for unbacked RWX regions and extract implant configuration.
  • Block the loader hash, parent path, and C2 indicators estate-wide.
  • Sweep all hosts for the same lineage and beacon destinations.
  • File the timeline, tune the rules, and schedule the next purple-team validation.
