01

Overview

What "valid accounts" means, why attackers love it, and what this guide teaches you.

A valid account is a real username with a working password, key, or token. The attacker does not need a software bug or a special exploit. They simply log in as someone the system already trusts. From the network's point of view, their traffic looks ordinary. It is ordinary employee traffic — just sent by the wrong person.

This is why T1078 matters so much. Almost every security control trusts identity. A firewall may block a random scanner, but it welcomes a real user. An email gateway may stop malware, but it happily delivers the mailbox of a paid account. That is why valid account use appears in almost every real intrusion, from simple password attacks to ransomware and cloud data theft.

The same technique, four different jobs

Valid Accounts is unusual: it is listed under four tactics, because the same stolen login does different work at different stages of an attack. One tactic has a new name. It is now called Stealth, formerly Defense Evasion. This page writes "Stealth (formerly Defense Evasion)" at first mention so older reports stay easy to match.

Initial Access

The attacker buys or phishes credentials and uses them to get their first way in. The door is often a VPN, an SSO portal, or a webmail login. No exploit touches the target; the front door simply opens.

Persistence

A login that keeps working is a way back in that survives reboots and password scans. Attackers keep using (or quietly refresh) the account, especially if it is dormant, shared, or rarely reviewed.

Privilege Escalation

The attacker switches to a stronger account: a local admin, a domain admin, or a cloud admin. The extra power often comes from reused passwords or credentials dumped from memory.

Stealth (formerly Defense Evasion)

Malicious actions carried out by a legitimate user account blend into normal work. Many detections ignore "known users", which is exactly what the attacker hopes for. Older ATT&CK versions and most reports from 2024 and earlier use the former tactic name.

The four sub-techniques in one line each

Attacker side Company asset Identity Defender / SOC Data flow Evidence chip

The story, step by step

  1. Buying access. The attacker visits a criminal market and buys the VPN credentials of an employee, "j.wilson". The seller stole them in an earlier phishing campaign. This trade happens on an outside forum, so your network sees nothing yet.
  2. Credential test. The attacker opens the company VPN portal from their own laptop and tries the password. It works on the first try. The VPN log records a new country and a new device fingerprint for this user — the first weak signal.
  3. Valid login accepted. The VPN grants access because this account has no MFA on remote access. A successful VPN authentication now appears from an unusual network provider. A GeoIP and new-device check would flag this login.
  4. Quiet look around. Inside the session, the attacker runs simple discovery commands such as whoami and net view to map shares and permissions. The EDR agent sees rare commands running in a normal user session — another soft signal.
  5. Reaching the file server. Using the same valid account, the attacker opens a file share and copies a small folder of documents. File server audit logs show unusual mass reads for a user who normally opens two folders a day.
  6. Lateral use. The attacker tries the same password on a second server, and it works, because the employee reused the password. The same source IP has now logged into two hosts within minutes — a strong correlation signal.
  7. SOC alert. An anomaly rule fires: first VPN login from this country for this user. The analyst opens the session timeline and links the VPN record, the EDR process events, and the file audit line into one incident.
  8. Response. The analyst disables the account, resets the password, and kills the live VPN session. The attacker loses access within minutes of the alert, before any real damage is done.

Evidence chips drawn in the animation: VPN auth log line, Windows 4624, EDR process event, file audit line. In real incidents each chip stands for a log record you can pull, store, and query.

03

Red Team / Hacker Perspective

How attackers think about valid accounts — written for defenders, so you can predict and detect the behavior.

Why attackers choose a login over an exploit

  • No exploit crash, no malware sample, no unusual process tree.
  • Encryption and zero-trust tunnels work for the attacker once they are inside them.
  • A phished session token or a pushed MFA approval defeats second factors.
  • Remote access portals are, by design, reachable from anywhere.

Where the technique applies

  • VPN and SSO portals — the classic first way in.
  • Cloud consoles and APIs — broad reach from one login.
  • RDP, SSH, and SMB inside the network for lateral movement — attacker shorthand for spreading from one machine to the next with the same credentials.
  • Email and SaaS — mailbox rules, OAuth grants, data theft.

Prerequisites an attacker needs

  • A working credential for an enabled account — password, SSH key, or session token.
  • A network path to the login surface (public VPN portal, exposed RDP, cloud console).
  • No MFA on that path, or a second factor the attacker can phish, push, or reuse.
  • Some knowledge of usernames — from LinkedIn, leaked lists, or easy naming patterns.
  • Patience: testing credentials slowly to avoid lockouts and rate limits.

Common ways credentials become "valid"

Bought from a broker

Initial access brokers sell working VPN and SSO logins. This is the fastest path and the one shown in the simulation.

Stuffed or sprayed

Password lists from old breaches are replayed against portals. This guessing method is called credential stuffing or password spraying. Reused passwords make it work far too often.

Phished directly

Fake login pages and MFA relay kits capture passwords, one-time codes, and sometimes whole sessions.

Dumped from a host

After one working login, credentials stored in memory or files give access to more systems (see T1003, OS Credential Dumping).

Left behind

Dormant accounts, ex-employee logins, shared team passwords, and vendor default accounts never removed.

Asked for politely

Social engineering of IT help desks — pretending to be a locked-out employee — produces fresh, fully working credentials.

Generating safe test telemetry (lab only)

Detections are only real if you have replayed them. In a lab you own, you can produce the exact log events used in Section 5.4 without touching any real target.

Ethics and legality

Never test credentials against systems you do not own, and never use accounts that are not yours — even "just to see if it works". That is unauthorized access in most jurisdictions. All examples here use placeholders like <lab-host> inside an isolated lab.

Common variations and attacker mistakes

Variations you will meet

  • Low and slow: one login, tiny data volume, long gaps — built to stay under thresholds.
  • Only built-in tools: the attacker runs commands a normal user could plausibly run, so nothing unusual is installed.
  • Session hijack: stealing the cookie or token instead of the password (relates to T1550).
  • Help-desk social engineering: turning humans into a credential factory (see the case study).

Mistakes attackers still make

  • Wrong time zone — logins at 03:00 local time for a day-shift employee.
  • New device and user agent with zero history for that user.
  • Password spray noise — bursts of 4625 / failed events before a success.
  • Password reuse — the same source IP logging into many hosts in minutes.
  • Forgetting the geo — a "new country" for a user who never travels.
04

Blue Team / SOC Perspective

A valid login is not invisible — it is everywhere. Here is where to look, what it leaves behind, and how to triage it fast.

Defenders cannot stop a login from looking "normal" by itself, but a login is one of the most logged actions in IT. Every successful use of a valid account creates session records. The VPN or identity provider logs the entry. So do the hosts it touched and the cloud services it reached. The defender's job is to join those records into a timeline and compare it with what that user normally does.

Where defenders can see it

Windows Security log

4624 (logon success), 4625 (failure), 4648 (explicit credentials), 4672 (admin logon rights), 4768–4771 (Kerberos tickets). Logon type 3 = network, type 10 = RDP.

Identity provider sign-ins

Entra ID and Okta record every portal login with source IP, device, MFA method, and result. Best single source for cloud and SSO sessions.

VPN concentrator logs

Authentication results, source IP, geo, and device posture. The entry door for most remote attacks with bought credentials.

EDR telemetry

Process events inside a valid session: whoami, net view, archive tools, or first-time commands for that user.

File and share audit

Events 4663 / 5140 / 5145 show which shares were touched and how much was read. Mass reads from a quiet user stand out.

Cloud audit logs

AWS CloudTrail ConsoleLogin (MFAUsed field), Office 365 unified audit log, Google Workspace login events.

Why this matters for the whole chain

A valid-account session is rarely the goal — it is the vehicle. It carries the attacker from initial access through discovery, collection, and, in the worst cases, ransomware staging. If you detect the session early, you break the chain before payload deployment. If you only detect the payload, you are already late. This is why identity telemetry has some of the highest return on investment in a SOC.

Six-step triage flow for a suspicious valid login

  1. Step 1 — Identify Confirm the account owner, their team, and their expected location, devices, and working hours. A "suspicious" login for a frequent traveler may be routine.
  2. Step 2 — Pull the session record Get time, source IP, geo, device ID, user agent, and MFA method from the VPN or IdP log. Note whether MFA was satisfied, pushed, or skipped.
  3. Step 3 — Correlate Join the session with EDR process events, file audit records, and any other logins from the same source IP in the last 24 hours. One timeline, all sources.
  4. Step 4 — Check how far it reached Was the account privileged? Did it touch other hosts? Any new group memberships, mailbox rules, or OAuth grants (app permissions a user hands to an application) created during the session?
  5. Step 5 — Score and decide Privileged + new geo + mass reads = likely intrusion. Low-privilege + home country + normal apps = likely safe. Document the reasoning either way.
  6. Step 6 — Contain and preserve Before disabling: snapshot the evidence (logs, session records). Then disable or reset the account, revoke sessions and tokens, and notify the user through a known-good channel.

Worked example: one session, three sources

The same j.wilson incident from the simulation, assembled as an analyst would see it after correlation.

  1. 02:16:31 UTC · VPN concentrator user=j.wilson src_ip=198.51.100.87 geo="Lagos, NG" result=success mfa=none — successful VPN login, no second factor, first-ever session from this country and device. Signal: unusual entry.
  2. 02:18–02:26 UTC · EDR on VPN-assigned workstation whoami, net view \\corp\projects, net use — first-time commands for this user account; nothing malicious by signature, everything unusual by baseline. Signal: discovery in a valid session.
  3. 02:27–02:34 UTC · File server audit on fs-01 Event 4663, 214 read operations against \\fs-01\projects\ — versus a 30-day average of 6 per day for this account. Signal: collection.
  4. 02:31 UTC · Windows 4624 on srv-02 LogonType 3 from 10.20.4.51 (fs-01's internal address) — the same external session has now touched two hosts within 15 minutes. Signal: lateral movement with reused credentials.
  5. 02:41 UTC · SOC decision Four weak signals, one account, one source chain. Verdict: probable account compromise. Disable, reset, revoke; call the employee on their registered number. Total time from entry: 25 minutes.

5.3 Threats Ranking and Categorization

Not all valid-account threats are equal. This ranking assumes a typical mid-size enterprise. Picture a few thousand users, VPN or SSO remote access, mostly Windows endpoints with some Linux servers, at least one cloud platform, and partial MFA coverage. Ranks shift with your reality — a cloud-only company would push Threat 5 up; a company with strict PAM would push Threat 1 down.

Critical
T1		 Privileged account compromise (admin or service account used on VPN / SSO) Identity Windows An attacker logs in with a privileged identity — domain admin, cloud admin, or a powerful service account — and moves straight to domain or tenant takeover. Working credentials for a privileged account; MFA missing or phishable on that path; no just-in-time elevation. Domain or cloud takeover; ransomware-scale damage across the whole estate. One login gives broad access, and attackers go where the power is. No other threat on this page causes more damage from a single event.
High
T2		 Credential stuffing against VPN / SSO portals Network Identity Breached password lists are replayed against the remote-access portal until a reused password matches, then the attacker logs in as a real user. Breached password lists; no MFA or rate limiting on the portal; users reuse passwords. A quiet way in as a legitimate user — initial access completed without any exploit. The most common real-world initial access path we see; attempts are constant, and one hit is enough.
High
T3		 Valid account used for lateral movement (RDP / SSH / WMI / SMB) Windows Linux From the first valid login, the attacker reuses valid credentials to open network logons on many internal hosts, mapping the network and seeking privilege. Valid credentials (often dumped or reused); network reach between hosts; shared local admin passwords. Spread across servers, privilege discovery, staging for encryption or exfiltration. Severity legend

Critical — direct path to estate-wide takeover. High — likely intrusion step with major impact. Medium — serious hygiene and visibility problem with limited reach. Low — nuisance or edge case in most environments. Numbers T1–T5 are used consistently in 5.4 and 5.5 below.

5.4 Logs and Patterns

For each ranked threat, this part lists the log sources and key fields. It shows what normal looks like, what suspicious looks like, and the detection logic in one sentence. Then a realistic event example follows, with a field-by-field explanation.

Threat 1 — Privileged account compromise

Log sources and key fields

  • Sources: Windows Security (4624 / 4672 / 4648), Entra ID sign-in logs, AWS CloudTrail ConsoleLogin, VPN logs.
  • Key fields: TargetUserName, LogonType, IpAddress, WorkstationName, TargetSid, MFAUsed.

Normal vs suspicious

  • Normal: privileged logons from jump hosts or bastions, during business hours, from known admin networks.
  • Suspicious: privileged logon over VPN or RDP from an external or unknown network, at night, from a device with no history.
  • Detection logic: alert when a member of a privileged group authenticates remotely from outside the approved admin path.

Threat 2 — Credential stuffing against VPN / SSO

Log sources and key fields

  • Sources: VPN concentrator auth logs, identity provider sign-in logs, portal logs. Watch for 4625 bursts followed by a 4624 success.
  • Key fields: src_ip, user, result, reason, geo.country, device_id, attempts.

  • Normal: one or two failures per user, then success from the usual device and country.
  • Suspicious: 10+ failures across many usernames from one source IP, then a success from that same IP.
  • Detection logic: correlate authentication failures and the next success by source IP within a short window.

5.5 Sigma Rules and Splunk SPL

Each ranked threat gets one Sigma rule and one matching Splunk query — five pairs in all. After them you get one extra cross-check query that has no paired Sigma rule. Field names are realistic but you must adapt them to your own schema — mapping assumptions are noted under each pair. Validate every rule by replaying the log examples from 5.4 before you turn on alerting.

Detection 1 — Privileged account logs in remotely (Threat 1, severity: critical)

Mapping assumptions: the enrichment key IsPrivilegedAccount is added by your SIEM (assumption: a daily lookup of Domain Admins, Enterprise Admins, and sensitive service accounts). Splunk maps TargetUserName and LogonType via the Splunk Add-on for Windows; group membership can also come from a lookup join instead of a field.

Field assumptions: the lookup subsearch emulates the Sigma selection_suffix or selection_enriched logic. So privileged_accounts.csv must list every privileged account: both the -adm/_admin suffixed names and the accounts your enrichment marks as privileged. No extra threshold filter is applied, exactly like the Sigma rule. The Splunk Add-on for Windows maps Sigma's EventID to EventCode and provides TargetUserName, LogonType, and Computer; join on SID instead if your accounts are renamed.

Detection 2 — Stuffing burst then success on VPN (Threat 2, severity: high)

Mapping assumptions: fields assume VPN logs normalized to action (failed/success), src_ip, user, and geo.country. The near operator needs event timestamps. On platforms without it, use a fail-count-plus-success aggregation as in the SPL. That query counts failures per src_ip per 15-minute block and needs failures >= 10 plus one success.

Field assumptions: Palo Alto GlobalProtect Add-on fields action, src_ip, user; rename for other VPN vendors (for example FortiGate or Cisco AnyConnect).

Detection 3 — One source, many hosts (Threat 3, severity: high)

Mapping assumptions: Sigma cannot count unique values natively on every backend; the aggregation count(Computer) by IpAddress is a common SIEM translation and mirrors the SPL below. IpAddress|contains: '.' keeps IPv4 sources only — tune to your environment and add scanner exclusions.

Field assumptions: Source_Network_Address is the Splunk Add-on name for the 4624 source IP; add a lookup to exclude known jump hosts and scanners.

Detection 4 — Dormant account signs in (Threat 4, severity: high)

Mapping assumptions: user_dormant_90d is an enrichment field (assumption: your pipeline joins SignInLogs with a last-sign-in lookup and flags 90+ quiet days). Entra field paths use the properties.* structure of azure:aad:signinlogs; adjust to your normalizer (for example Identity vs UPN).

Field assumptions: user_dormant_90d is the same enrichment field the Sigma rule expects. Your pipeline must add it — a daily job that joins SignInLogs with last-sign-in data and flags 90+ quiet days. Without that field, filter with a lookup subsearch instead: [| inputlookup dormant_accounts_90d.csv | fields userPrincipalName | rename userPrincipalName as properties.userPrincipalName]. Keep the list fresh, or the alert will fire for accounts that were cleaned up last week.

Detection 5 — Guest activation or shared login from a new device (Threat 5, severity: medium)

Mapping assumptions: operation names follow Office 365 management activity strings; device_new_for_user is an enrichment flag from a first-seen device baseline (assumption: built per UserId + ClientInfoString). Suppress with a business-approved guest list.

Field assumptions: o365:management:activity provides Operation, UserId, ClientIP, UserAgent; device_new_for_user comes from your enrichment pipeline, not from Microsoft.

Extra cross-check query — Cloud console login without MFA (Threats 1 and 5)

This is a bonus hunt, not one of the five pairs: it has no paired Sigma rule above. A Sigma twin would use category: cloud, product: aws, service: cloudtrail and the same two field conditions.

Field assumptions: CloudTrail JSON is parsed by aws:cloudtrail sourcetype. Add an exception list for documented break-glass accounts that log in without MFA during incidents.

Tuning guidance

Deploy each rule in search-only mode first for one to two weeks. Expect most false positives from: patching and deployment tools (rule 3), users who mistype new passwords (rule 2), and seasonal staff (rule 4). Suppress by identity and system, never by disabling the rule. Re-validate after every log-source change, and record the validation date in the rule's ticket.

Real-World Case Study

MGM Resorts, September 2023 — how one help-desk call turned valid credentials into a multi-day outage.

Sources and caution

This case study uses publicly reported facts only: MGM's own 8-K filing to the U.S. SEC (October 2023), statements from the ALPHV/BlackCat ransomware group, and reporting by major security news outlets. Some details were never officially confirmed, so the wording below stays cautious ("publicly reported", "widely reported").

Context

MGM Resorts International runs hotels and casinos in Las Vegas and elsewhere. In September 2023, attackers gained access to MGM's environment. Researchers later tracked them as Scattered Spider (also UNC3944), working with the ALPHV/BlackCat ransomware operation. Public reporting says they did not break in through software. They called the IT help desk, pretended to be an employee, and talked their way into valid credentials and an MFA reset. Widely reported accounts describe that vishing call as lasting roughly ten minutes. That is T1078 in its purest form: the "hack" was a phone call that produced a working account.

Timeline (publicly reported)

  1. Before 8 Sep 2023Reconnaissance: public reporting describes research on employees and the organization's structure, gathering names and details needed to sound convincing.
  2. ~8 Sep 2023The help-desk call, widely reported as about ten minutes: an attacker posing as an employee obtained valid credentials and, reportedly, passed a further identity check. The account now worked like any real employee account.
  3. 8–10 Sep 2023Valid access was used to reach identity infrastructure, and the activity escalated to privileged cloud identity access. Public reporting names misuse of Okta and Microsoft Entra ID (Azure AD).
  4. ~10 Sep 2023ALPHV/BlackCat ransomware was deployed, reportedly on ESXi virtualization hosts. Major hotel and casino systems were taken offline; some operations moved to pen and paper.
  5. 10–14 Sep 2023Disruption continued for days: room keys, casino floors, reservations, and payment systems were widely reported as affected. MGM published customer notices.
  6. Following weeksPhased restoration of systems; MGM's 8-K later estimated an approximately 100-million-dollar negative impact on quarterly results, plus legal and security-hardening costs.

Attack chain (as reconstructed from public reporting)

  1. Research — identify the organization's help-desk process and a suitable employee identity to impersonate.
  2. Social engineering — call the help desk, pass basic identity checks, and obtain working credentials plus an MFA reset. The credential abuse itself maps to T1078.002 and T1078.004.
  3. Identity access — use the valid account to reach SSO and identity administration surfaces.
  4. Privilege escalation — reportedly gain access to privileged identity roles and infrastructure management.
  5. Impact — deploy ransomware on ESXi hosts and trigger mass shutdowns.
The detection point that mattered

Public post-incident discussion highlighted anomalous identity activity and unusual admin actions in the hours before encryption. The practical lesson for a SOC: watch the identity plane (new-session anomalies, MFA resets, privileged role changes) with the same care as endpoint telemetry. A valid-account session with unusual admin actions was the intrusion.

Containment

Reported response steps included disabling compromised accounts, shutting down remote access, and isolating affected systems to stop the spread.

Eradication

Domain-wide credential resets and system rebuilds were needed to remove attacker access, because valid credentials had touched many systems.

Recovery

Systems were restored in phases over days to weeks, with manual workarounds in hotels while core services came back.

Impact, team response, and communication

The widely reported financial impact was about 100 million US dollars against the quarter, plus legal exposure and hardening costs. The compromise began with identity, not malware, and that shaped the whole response.

Team response (as public reporting describes it): response steps included disabling compromised accounts, shutting down remote access, and isolating affected systems. Identity work came first, because stolen-but-valid credentials kept working until every session and token was revoked. Site staff ran hotels with manual workarounds while security teams cleared systems one by one.

Communication: MGM published customer notices about which services were affected, dealt with sustained media coverage, and filed an 8-K with the U.S. SEC in October 2023 describing the estimated impact. Public communication stayed active for weeks. The visible lesson: identity incidents need a communication plan for guests, staff, and regulators from day one.

Reported team roles and exact timings vary between sources. The steps above are the pattern worth copying, not a verified minute-by-minute record.

Lessons learned

  1. Verify callers out of band. Help desks need strong, rehearsed identity verification for resets — never the data an attacker can find online.
  2. Use phishing-resistant MFA. Push approvals and one-time codes can be socially engineered; FIDO2 keys and number matching raise the bar sharply.
  3. Guard privileged access. Admin roles should sit behind PAM, just-in-time elevation, and step-up verification — not behind a reset phone call.
  4. Detect on identity anomalies. New-device admin actions, unusual MFA activity, and rare sign-ins deserve the same alerting budget as endpoint events.
  5. Rehearse the playbook. Account disable, session revocation, and credential-reset drills must be tested before the day you need them at domain scale.

Home and small-office advice

If you run a small network or your family's accounts, the same ideas shrink to six habits.

One password per site

Use a password manager so a leak at one site cannot open your other accounts.

MFA on everything

Turn on multi-factor authentication for email, banking, and social accounts. App-based codes are fine; hardware keys are better.

Disable guest accounts

Turn off the built-in guest account on your computers, and remove accounts of people who moved out or left the company.

Change router defaults

Default router passwords are public knowledge. Set a unique admin password and firmware updates on.

Spot the phish

Fake login pages create most "valid accounts". Check the address bar before typing a password, and never approve an MFA prompt you did not start.

Watch for surprises

If you get a "new login" email you cannot explain, change that password first and check active sessions in the account settings.

Common Mistakes and Best Practices

Twelve concrete blue-team mistakes around valid-account detection — each with symptom, root cause, fix, and prevention.

1. Collecting 4624 without 4625

Symptom: no visibility into guessing; stuffing attacks look like a single clean login.
Root cause: the failure event (4625) was never enabled in the audit policy or forwarder.
Fix: enable failure auditing and forward 4625, 4771, and VPN failures today.
Prevention: a coverage matrix listing every identity log source and its enabled event IDs, checked quarterly.

2. Ignoring VPN and IdP logs

Symptom: the SOC sees the internal spread but never the entry door.
Root cause: remote-access appliances are owned by the network team, not the SOC.
Fix: route VPN and IdP auth logs into the SIEM and give the SOC read access.
Prevention: onboarding checklist requires an authentication log source for every external-facing service.

3. Trusting "known user" means safe

Symptom: analysts dismiss alerts because the account belongs to a real employee.
Root cause: identity is treated as proof of legitimacy rather than as the thing being attacked.
Fix: retrain triage to score sessions on context: device, geo, time, and behavior.
Prevention: triage runbooks list "valid user" as a non-factor; context fields are mandatory in the alert view.

4. No per-user baseline

Symptom: a login from another country is only "suspicious" if a rule author thought of it.
Root cause: thresholds are global, not per identity; quiet users hide inside noisy averages.
Fix: build per-user profiles (usual countries, devices, hours) and compare sessions to them.
Prevention: UEBA or a scheduled SPL baseline job is part of the detection backlog, not an optional extra.

5. Single-event alerts with no context (alert fatigue)

Symptom: analysts auto-close hundreds of identical 4624 alerts a day.
Root cause: one event per alert; no correlation, no context panel, no grouping.
Fix: correlate into behavior-level alerts (source + user + activity) and add context enrichment.
Prevention: a rule cannot go to production unless it includes context fields and a documented response action.

6. No dormant-account tracking

Symptom: ex-employee and service accounts wake up with nobody noticing (Threat 4).
Root cause: nobody owns "accounts nobody uses"; offboarding only covers current staff.
Fix: generate a daily dormant-account list (90+ days) and alert on any sign-in from it.
Prevention: monthly sweep job plus disable-without-delay policy for departures.

7. MFA gaps on legacy protocols

Symptom: attackers log in via IMAP, SMTP AUTH, or old VPN clients and skip MFA entirely.
Root cause: MFA is enforced on the modern portal but legacy paths bypass conditional access.
Fix: inventory legacy auth, migrate or block it, and monitor remaining exceptions.
Prevention: quarterly report of authentications by protocol; alerts on legacy-protocol successes.

8. Shared accounts breaking attribution

Symptom: during an incident, nobody can say who did what on the shared admin account.
Root cause: convenience won over individual accountability years ago.
Fix: replace shared logins with named accounts plus PAM check-out; audit remaining ones.
Prevention: policy bans new shared accounts; exceptions need CISO approval and expiry dates.

9. Detections never validated with replayed logs

Symptom: rules "work" in theory but silently match nothing (or everything) in production.
Root cause: field names and formats differ between the rule author's notes and your real pipeline.
Fix: replay the 5.4-style event samples through the rule; fix the mappings before enabling alerts.
Prevention: a small test-event set per rule, run in CI or manually after every source change.

10. No owner for identity detections

Symptom: stale thresholds, old lookups, and rules nobody has tuned since 2023.
Root cause: detections have projects but no ongoing owner.
Fix: assign each rule an owner, a review cadence, and a ticket for tuning history.
Prevention: detection-as-code reviews; ownership is a field on every rule, checked monthly.

11. Weak tuning driven by noise

Symptom: a rule that fired once too often gets its threshold raised until it detects nothing.
Root cause: tuning is done by threshold alone, without scoping by identity or system.
Fix: suppress by specific jump hosts, scanners, and approved accounts — never by raising global limits.
Prevention: every suppression is time-boxed, documented, and re-reviewed each quarter.

12. False positives treated as failure

Symptom: teams chase a zero-alert state and quietly disarm useful but noisy rules.
Root cause: false positives are part of detection on normal networks; the goal is triage efficiency, not silence.
Fix: measure precision and analyst time saved; keep rules that surface one true positive among ten benign ones when that true positive matters.
Prevention: monthly tuning reviews discuss trade-offs instead of demanding zero noise.

Habits for a detection engineer

Daily

  • Review privileged logons (4672, type 3/10) from the last 24 hours.
  • Check VPN and IdP alerts for failure-then-success patterns.
  • Skim new alerts for context quality — can you triage from the alert alone?

Weekly

  • Tuning review: pick the noisiest rule and fix its root cause, not its threshold.
  • Verify all identity log sources are fresh (no silent forwarder failures).
  • Run one hunt query against a hypothesis (for example, new-device RDP).

Quarterly

  • Dormant-account sweep with the IAM team; disable what has no owner.
  • Rule validation: replay the test-event set through every identity rule.
  • Access review of service, guest, and shared accounts; run one revocation drill.

Response checklist for a confirmed valid-account intrusion

  • Preserve evidence first: export the session records, EDR events, and audit logs you based the decision on.
  • Disable or reset the compromised account; if it is privileged, do the same for paired or delegated accounts.
  • Revoke sessions, refresh tokens, OAuth grants, and active VPN tunnels for that identity.
  • Sweep for what the session touched: hosts, shares, mailboxes, cloud resources, and any persistence created.
  • Check for sibling compromise: same password or same source IP used by other accounts.
  • Reset credentials for exposed systems, starting with privileged and service accounts.
  • Notify the account owner through a known-good channel (in person or via their manager, not the possibly-forwarded mailbox).
  • Write the timeline, update the detections that should have caught it earlier, and schedule the drill.
