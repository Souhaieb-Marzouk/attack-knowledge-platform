DETECTION GUIDE · T1090

T1090 · Proxy

A proxy is a middle system that passes traffic between two other systems. Attackers put proxies between their malware and their servers. This hides the real source of command-and-control (C2) traffic. This guide explains how that works and how to detect it.

Guide v2.0 · audited against ATT&CK v20.0
  • Tactic: Command and Control
  • Platforms: ESXi, Linux, macOS, Network Devices, Windows
  • Sub-techniques: 4
  • MITRE mitigations: M1037 · M1031 · M1021

What it is

Malware talks to a relay system instead of the attacker's server. The relay forwards the traffic, so the true C2 address never appears in victim logs.

Official tooling

MITRE names HTRAN (S0040), ZXProxy, and ZXPortMap. Attackers also rent VPS hosts and use ngrok, FRP, or reGeorg-style tunnels.

Why it matters

IP blocklists stop working. The visible address belongs to a rented server, a home connection, or a CDN. Attribution and blocking both get harder.

How to catch it

Enrich egress logs with ASN and reputation data. Detect behavior such as steady beacon timing, not single IP addresses.

What the technique is

A proxy is a middle system. It receives traffic from one computer and sends it onward from itself. Replies travel back the same way. The computer at the far end only sees the proxy, never the original sender.

MITRE describes T1090 like this: attackers use a connection proxy to direct traffic between systems, or as an intermediary for C2 communications, to avoid direct connections to their infrastructure. Common tools are HTRAN (S0040), ZXProxy, and ZXPortMap.

MITRE lists four purposes: manage C2 communications, reduce the number of simultaneous outbound connections, keep C2 alive after connection loss, and ride over trusted paths between victims. Attackers also chain several proxies to hide the source, and abuse CDN routing schemes to carry C2 traffic.

Here is the same idea in plain words. Malware on a victim machine needs to talk to a C2 server (the attacker's control server). If it connects directly, your firewall log shows the attacker's own address. One block rule can then stop the whole operation.

So the attacker rents or hijacks a relay and points the malware at it. The malware now talks only to the relay. Your logs show the relay. The real C2 server sits one or more hops away, outside your view.

Each sub-technique puts the relay in a different place: inside the network (001), outside on the internet (002), several hops deep (003), or hidden behind a CDN domain name (004). The parent T1090 covers the shared idea.

Key words in this guide

C2 — command and control; the channel that carries attacker commands to malware and results back. · Proxy — a middle system that forwards traffic for others. · Beacon — a small, regular check-in a compromised host sends to its C2. · Implant — the malware program that beacons and runs commands. · Egress — traffic leaving your network. · VPS — virtual private server; a cheap rented machine in a data center. · ASN — Autonomous System Number; the registered ID of the network that owns an IP address. · CDN — content delivery network; a company such as Cloudflare or Akamai that serves web content from many shared addresses.

Where it fits in the attack chain

T1090 belongs to the Command and Control tactic. It starts after the attacker already has a foothold. A typical chain looks like this: initial access (for example phishing) → execution → the implant beacons → commands and data flow. The proxy sits on that last link. It shields every later step, including operator logins and data theft.

What comes before: delivery and execution techniques such as T1566 Phishing or a web shell (T1505.003). What comes after: lateral movement, collection, and exfiltration, all carried over the hidden channel. Related techniques: T1572 Protocol Tunneling, T1573 Encrypted Channel, and T1071.001 Web Protocols.

Why detection is hard, and why it still matters

Why it is hard

Three things work against the defender. First, the visible address is disposable. The attacker pays a few dollars and rotates it. Second, the relay often shares addresses with normal business traffic, such as a CDN or a home internet line. Third, the traffic content is usually encrypted, so a firewall log shows little more than "IP, port, bytes, time".

Why it still matters

The relay must still be reachable, and reachability leaves traces. ASNs, TLS certificates, DNS names, timing, and volume all leak information. Teams that enrich egress logs and detect behavior catch relayed C2 routinely. The cost of detection is a lookup file and a few tuned rules, which is far below the cost of one missed intrusion.

Written story: the same eight steps in words

This text tells the same story as the animation. It is the accessible alternative to the canvas.

  1. Step 1 — Implant beacon start. An implant on Victim A starts its beacon. It connects outward to one address: a rented port-redirector proxy. The implant's configuration does not contain the real C2 address. Defender view: the firewall records a new egress flow from one workstation.
  2. Step 2 — Packet to proxy. The company firewall forwards the packet to the proxy on the internet. The log line shows the source host and the proxy's IP address and port. No attacker-owned address appears anywhere yet. Defender view: the destination is a hosting-provider IP you have never seen before.
  3. Step 3 — Proxy forwards to C2. The port redirector accepts the connection and opens a second one to the real C2 server. This leg happens on the internet, outside your logging. Your team cannot see it at all. Defender view: your visibility ends at the proxy IP — that is the design goal of the attacker.
  4. Step 4 — C2 reply through proxy. The C2 server answers. The reply travels back along the same path: C2 → proxy → firewall → Victim A. The implant receives its first command. Defender view: the reply content stays invisible without TLS inspection; the flow shape is what you can still measure.
  5. Step 5 — Defender view: the proxy hides the C2. The SOC reviews the flow. The destination is unknown but ordinary-looking, and no blocklist matches. The channel looks clean even though it carries attacker commands. Defender view: judge the behavior — steady timing, first-seen ASN — not the IP alone.
  6. Step 6 — Second victim added. The attacker spreads to Victim B, perhaps with a phishing reply or a stolen credential. The new implant uses the same proxy hop. Now two hosts beacon to one destination. Defender view: a second host to the same first-seen IP is a strong scope signal.
  7. Step 7 — Log trail on the firewall. The firewall log now shows a clean trail: two sources, one destination, steady intervals. The proxy IP is the one constant across both victims. The C2 behind it stays hidden. Defender view: the proxy IP is your pivot — everything else in the case hangs from it.
  8. Step 8 — SOC pivot. The analyst pivots on the proxy IP across 30 days of logs, finds both victims, blocks the address, and reports the case. The attacker may rotate the proxy, but the behavioral rules keep firing. Defender view: hunt the pattern, not the address — rotation does not defeat timing and ASN rules.

Red team perspective

How attackers and red teams use proxies, told for defenders. The goal is to know the pattern so the detections in Section 5 can be built and tested.

Four questions about the technique

Why do attackers use proxies?

A direct connection gives the defender the attacker's own address. One block rule, one provider abuse report, and the operation may be over. A proxy hides the origin, defeats IP blocklists, and makes attribution harder. It also protects the operator's own access, which often rides the same relay path.

When do they use it?

From the first beacon onward. Malware checks in through the relay from day one. Operators then reuse the relay for interactive logins, tool staging, scanning, and data theft. Some groups keep a relay alive for months; others rotate exits every few hours.

How do they set one up?

Three common ways. They rent a VPS and run a port redirector such as HTRAN or an iptables/netsh forwarder. They abuse a tunnel service such as ngrok or FRP. Or they compromise a server, plant a web shell, and tunnel through it with reGeorg or Neo-reGeorg.

Where does it appear in the chain?

In Command and Control, right after execution. The implant config holds the relay address. Later stages — lateral movement, collection, exfiltration — all flow through the same channel, which is why one relay discovery can scope the whole incident.

Typical setup and variations

A relay chain needs three parts. First, reachable infrastructure: something rented (a VPS) or borrowed (a compromised web server). Second, a listener on that system that forwards traffic — a port redirector, a SOCKS proxy (a generic proxy protocol for TCP traffic), or a reverse tunnel. Third, an implant configured with the hop address only. If one victim is captured, the real C2 address still stays hidden.

The sub-techniques differ by where the hop lives. Internal (001) means a device inside the victim network, used to pivot — that is, to move through the network from one machine to another. External (002) is a single system on the internet. Multi-hop (003) chains several relays, sometimes with Tor. Domain fronting (004) hides the destination behind a shared CDN domain.

Danger — Lab only

All commands below are Lab only — use only on systems you own. They demonstrate relaying mechanics between lab machines. Never point them at systems you do not own.

Variations and attacker mistakes

Common variations

  • Static single hop: one rented VPS with a forwarder. Cheap, fast to deploy, easy to burn.
  • Multi-hop chain: two or more relays, sometimes with Tor at the end, so one burned hop does not stop the operation.
  • Tunnel service abuse: ngrok, FRP, or similar tools give a stable name instead of an IP, which survives some blocking.
  • Compromised relay: a hijacked web server runs the forwarder, so the visible "attacker IP" belongs to a real company.

Mistakes that create detections

  • Reusing one exit IP across victims: the same address appears in unrelated incidents — a strong pivot for threat hunting.
  • Fixed beacon intervals: perfectly steady check-in times look machine-made and stand out in statistics.
  • Hardcoded hop addresses: strings recovered from malware expose the whole chain.
  • Wide-open relay ports: a public listener on 1080 or 8080 on a web server is rare and loud.
Ethics

This section exists to help defenders practice. Use these ideas only in a lab you own. Red teams should document every relay, use owned IP space, and tell the SOC the test window. If the Section 5 detections do not fire during a purple-team exercise, fix them before a real attacker tests them.

Blue team perspective

Where relayed C2 shows up first, what normal looks like, and a triage checklist your team can follow step by step.

Where to look first

ATT&CK data sourceTypical log productWhat it shows you
Network Connection CreationSysmon EID 3, EDR network events, host firewallsWhich process opened the connection — the key field most teams are missing.
Network Traffic ContentZeek conn/http/ssl/dns, TLS inspection or web proxy logsDomains, SNI (the server name a client claims in TLS), user agents, URI paths.
Network Traffic FlowNetFlow / IPFIX, firewall traffic logs, VPC flow logsWho talked to whom, when, on which port, and how many bytes — even when encrypted.

Normal versus suspicious

Normal egress

  • Workstations talk to known SaaS and CDN ranges, mostly 443, resolved by DNS first.
  • Browser and office-suite user agents dominate; ASN history is stable week to week.
  • Server subnets speak to a short, documented list of external endpoints.

Suspicious egress

  • A first-seen hosting or residential ASN contacted by a workstation, at a steady interval.
  • TLS straight to a bare IP with no matching DNS lookup in your logs.
  • A web server process opening connections to internal SMB or RDP ports.
  • One host that touches several different proxy-like exits in a single hour.

Triage checklist — seven steps

  1. Enrich the destination. Add ASN, network owner, country, and category to the alert. Verdict question: is the ASN in an approved list for this subnet?
  2. Check the history. Query 90 days for the same (source subnet, destination ASN) pair. Threshold: first-seen means no prior flow at all.
  3. Identify the process. Pull Sysmon EID 3 or EDR events for the source host. Fields: Image, DestinationIp, DestinationPort, User. A browser is explainable; rundll32.exe is not.
  4. Measure the timing. Collect timestamps for the last 24 hours. Threshold: a gap standard deviation under 90 seconds over 20 or more connections looks machine-made.
  5. Scope the pattern. Search all log sources for the destination IP and its ASN. List every internal host and user involved. Verdict question: one host, or a family of hosts?
  6. Decide and contain. If enrichment plus timing point to a relay, block the IP or ASN at the firewall, isolate the hosts, and preserve the process evidence before rebooting anything.
  7. Report and hunt. Record indicators, assets, and timeline. Then hunt 30 days back for the same ASN and the same timing pattern from other hosts.

When to escalate, and quick wins

Escalation criteria — call IR when

  • Two or more hosts beacon to the same first-seen relay address.
  • The beaconing host holds privileged data or domain-admin credentials.
  • The relay was reached by a web server process (a web shell is likely present).
  • Enrichment marks the destination as a known anonymizer or bulletproof network.

Quick wins this week

  • Turn on Sysmon EID 3 (network connection) on a pilot group of hosts.
  • Build a small asn_categories.csv lookup with hosting, residential, and anonymizer rows.
  • Run the never-seen-ASN query from 5.5 as a weekly hunt, before promoting it to an alert.
  • Add ASN enrichment fields to your top three egress alerts.

Six-step intel workflow

  1. Collect. Pull the sources above on a schedule into one place, such as a MISP instance.
  2. Process. Normalize, deduplicate, and age items. Tag hosting, residential, and anonymizer networks.
  3. Analyze. Score each item by how often it appears in reporting that matches your sector.
  4. Apply. Ship scored data as SIEM lookups (for example asn_categories.csv, tor_relay_list.csv) that the 5.5 rules join against.
  5. Review. Monthly, check rule hits against entry age. Retire stale rows; refresh fast-moving ones daily.
  6. Feed back. Send confirmed hits and false positives to the intel team and, where possible, back to the community.

How to turn intel into hunts

Hypothesis 1 — Tunnel-service names

Attackers abuse ngrok, FRP, and similar services for stable relays. Hunt DNS and proxy logs for tunnel-provider domains from workstation subnets. If it fires, treat the host as compromised until proven otherwise.

Hypothesis 2 — One relay, many victims

Actors reuse a good relay across campaigns. Take each first-seen hosting ASN from the last 30 days and count internal sources. Two or more sources to the same new relay is a campaign signal.

Hypothesis 3 — Known actor relay ranges

Advisories for groups such as Volt Typhoon include relay infrastructure ranges. Run those ranges over 90 days of flow logs. Any internal hit should start a scoping case.

Ranking logic. Rank 1 and 2 sit highest because they hide C2 completely and appear in both criminal and state-sponsored reporting. 5.4 Logs and patterns

For each ranked threat: the log sources to collect, what the pattern looks like, one synthetic example event, and tuning notes. Every example below is clearly marked as synthetic.

Threat 1 — C2 relayed through an external port-redirector proxy

Log sources: firewall / NGFW traffic logs, NetFlow or IPFIX, EDR network events (Sysmon EID 3), DNS logs for tunnel-provider names.

Pattern: a workstation opens a long-lived TLS session to a first-seen hosting ASN, repeats it at a steady interval, and resolves no new DNS name for it. The destination port is often 443, but the ASN category, not the port, is the signal.

Tuning: require both a first-seen ASN and at least 12 repetitions before alerting. Keep an approved-hosting allowlist per subnet to absorb developer tooling.

Threat 2 — Web-shell reverse proxy tunnel (reGeorg / Neo-reGeorg)

Log sources: Sysmon EID 3 network connections plus EID 1 process creation on web servers, web server access logs, Linux auditd for nginx/httpd children, Zeek conn logs.

Pattern: the web server process itself starts network connections to internal SMB, RDP, or WinRM ports. A normal application tier rarely does this, so process-to-network correlation on the server is the core artifact.

Tuning: scope the rule to ports 445, 3389, 5985, 5986, and 22 from web-server processes. Expect some hits from legitimate app-tier designs; document them as exceptions per host pair.

Threat 3 — LOLBin port forwarding (netsh portproxy, ssh -R, plink)

Log sources: Sysmon EID 1 process creation, Windows Security 4688 with command-line auditing, Linux auditd execve, EDR process events.

Pattern: a command line that adds a portproxy rule or starts an ssh or plink client with a remote forward (-R). The host keeps nothing behind after the process exits, so capture the command line and the parent process.

Tuning: allowlist documented administrative portproxy use by change ticket. Alert immediately on any other occurrence; the true-positive rate on this rule is high.

Threat 4 — Malware families routing C2 through proxies (NETWIRE, Dridex, Ursnif, QuasarRAT)

Log sources: Sysmon EID 3 with process context, EDR network and process events, Zeek ssl and http logs, TLS-inspection proxy logs.

Pattern: a script host or system binary (rundll32.exe, regsvr32.exe, mshta.exe) opens direct TLS to external addresses on proxy-friendly ports. The binary choice, not the destination, is what separates this from a browser.

Tuning: expect moderate volume from software updaters; keep a process-plus-destination allowlist. Promote to high severity when the source process also spawned from an office document path.

Threat 5 — Chained / CDN-fronted proxying that blends with business traffic

Log sources: web proxy logs (CONNECT method), TLS-inspection gateway logs comparing SNI with the HTTP Host header, Zeek ssl and http logs, DNS logs.

Pattern: CONNECT requests to shared CDN hosts on non-standard ports, or SNI and Host values that disagree once TLS is unwrapped. Without inspection, only the CONNECT-to-odd-port half is visible.

Tuning: treat CONNECT to 443 as normal; alert on CONNECT to other ports with browser-like user agents. With TLS inspection enabled, add an SNI-versus-Host mismatch check per request.

Threat 6 — Resilient proxy rotation (multiple endpoints, quick failover)

Log sources: firewall traffic logs and NetFlow aggregated over time, EDR network events, proxy logs for the HTTP half.

Pattern: one host contacts five or more distinct relay-like destinations within an hour. Each single flow looks unremarkable; only the count of distinct exits per host per hour exposes the rotation.

Tuning: start with a threshold of five distinct exits per hour and review a week of results before alerting. Exclude load balancers and SaaS gateways by asset role.

Refresh the first file monthly from threat intel.

Rule 1 — C2 relayed through an external port-redirector proxy

Mapping and tuning. Sigma src_role ↔ SPL role (from asset_roles.csv); Sigma dest_asn_category ↔ SPL category (from asn_categories.csv); the tunnel-name list matches one to one. Expected false positives: a handful per week from developer tunnels until the allowlist settles.

Rule 2 — Web-shell reverse proxy tunnel (reGeorg / Neo-reGeorg)

Mapping and tuning. Sigma Image|endswith ↔ SPL match(Image, ...); the port and CIDR lists match exactly. Expected false positives: low once your three-tier exceptions are documented; review new host pairs with the IT owner before exempting them.

Rule 3 — LOLBin port forwarding to adversary infrastructure

Mapping and tuning. Sigma CommandLine|contains|all ↔ two SPL match() conditions joined by AND; Image|endswith ↔ match(process_path,...). The allowlist join is an SPL-side extra; Sigma expresses it in tuning. Expected false positives: near zero after change-ticket entries are loaded.

Rule 4 — Malware families routing C2 through proxies (NETWIRE, Dridex, Ursnif, QuasarRAT)

Mapping and tuning. Sigma Image|endswith ↔ SPL match(process_path,...); Initiated and the port and CIDR lists match one to one. Expected false positives: moderate at first; the allowlist usually settles it within two weeks.

Rule 5 — Chained / CDN-fronted proxying through the corporate proxy

Mapping and tuning. Sigma method/port/user_agent ↔ the same SPL fields; the exclusion lists match exactly. Expected false positives: low. With TLS inspection deployed, add an SNI-versus-Host mismatch check as a second rule rather than widening this one.

Rule 6 — Resilient proxy rotation (multiple endpoints, quick failover)

Mapping and tuning. Sigma aggregation count(dest_ip) by src_ip > 4 ↔ SPL dc(dest_ip) ... where distinct_exits > 4; identical threshold and scope. Expected false positives: a few multi-tunnel developer hosts per month; exclude them by asset owner, not by IP.

Real-world case study — The Rented Front Door

Composite case

This case study is a realistic composite, clearly labeled as such. The company and people are fictional. The behaviors combine patterns documented across many public incidents. It does not describe one specific named intrusion.

Context

A regional finance company with about 900 staff. The SOC is managed by a partner; two internal detection engineers own the rules. Most staff reach internal systems through VPN, and multi-factor approval uses simple push prompts.

A ransomware affiliate needs quiet access. Instead of attacking from their own machines, they rent VPS relays so every login and beacon arrives from ordinary hosting space shared with real businesses.

Detection point, containment, eradication, recovery

How detection happened

Two rules from 5.5 did the work. Rule 1 (first-seen hosting ASN with steady beaconing) surfaced the two victims during the weekly hunt. Rule 6 (many distinct exits per hour) confirmed rotation after the second relay appeared. The firewall had logged every beacon from day one; only enrichment and aggregation turned those lines into a case.

Containment, eradication, recovery

Containment: block the relay IPs and their ASNs at the firewall, isolate both hosts, reset the stolen credentials, and revoke VPN sessions — in that order, so the operator cannot react mid-change. Eradication: rebuild both workstations, remove the run-key persistence, and verify no other host contacted the relay list. Recovery: one day, because ransomware was never deployed; the MFA change and rule tuning closed the gaps that let it start.

Impact and business consequences

  • Operational: two workstations offline for a day; no business systems touched.
  • Data: no confirmed exfiltration; staging was interrupted in time.
  • Cost: about 140 staff-hours across SOC, IR, and IT, plus one managed-SOC surcharge.
  • Business: a near-miss ransomware event; the board asked for the MFA upgrade, which was funded the same week.

Team response

  • SOC T1 triaged the hunt output and opened the case.
  • SOC T2 pulled EDR process history and mapped the chain.
  • IR lead ran containment and the evidence log.
  • Network engineer applied the ASN blocks within 40 minutes.
  • IT owner rebuilt both workstations and reset accounts.
  • Management and comms sent three updates: declaration, containment, closure.

Tools used

  • Attacker: macro loader, run-key persistence, rented VPS relays, RDP with stolen credentials, staged ransomware.
  • Defender: EDR, firewall logs with ASN enrichment, SIEM lookups, Sigma rules 1 and 6, number-matching MFA.

Lessons learned

1. Enrichment turns logs into evidence

The beacon was logged for eight days before anyone could read it. One ASN category field made the same lines speak. Build enrichment before you need the case.

2. Hunt weekly, alert always

The case started as a hunt, not an alert. Run new rules as weekly hunts first, then promote them once the noise level is known.

3. Rotation is itself a signal

Blocking one relay would have missed the second. The distinct-exits rule caught the rotation pattern, which survived the failover by design.

4. Identity and network must meet

The VPN login and the beacon shared one relay. A joint view of identity and egress would have linked them two days earlier.

5. Close the door behind the fix

Number-matching MFA and the new relay rules both shipped before case closure. Lessons that do not become controls are just documents.

6. Practice the playbook

Containment took 40 minutes because the block-and-isolate steps were rehearsed in a purple-team exercise a month earlier.

Mitigation and defense

You cannot patch someone else's rented relay. Defense is layered controls plus monitoring that assumes relays are already in use.

Official MITRE mitigations

ATT&CK lists three mitigations for T1090: M1037 Filter Network Traffic, M1031 Network Intrusion Prevention, and M1021 SSL/TLS Inspection. Everything below builds on those three ideas.

Prevention by layer

LayerControlHow it helps
NetworkSegmentationStops a relay on one segment from quietly forwarding traffic for another segment.

NetworkDNS filteringBreaks implants that resolve tunnel-provider or relay domains before they connect.

NetworkNetwork intrusion prevention (M1031)Signature and anomaly engines block known relay tools and C2 patterns in line (M1037 filtering complements it).

Detective controls

Log pipeline

Ship firewall, proxy, DNS, VPN, and EDR network events into the SIEM with NTP-synced clocks and 90-day retention. Add ASN and role enrichment as a first-class pipeline step, not an afterthought.

Sigma deployment

Deploy the six rules in 5.5 through version control with owners. Start noisy rules in observe mode, measure false positives for a week, then enable alerting.

Alert triage

Attach enrichment to every egress alert so triage starts from context. Track time-to-triage and false-positive rate as program metrics leadership sees.

Enterprise actions

  • Make anonymizer and tunnel-provider use an explicit policy violation, so detection has teeth.
  • Require change tickets for new external destinations on server segments.
  • Alert on new device plus new ASN combinations for remote-access logins.
  • Block proxy tooling (plink, frpc, chisel) by default at the endpoint, with a documented exception path.
  • Keep a tested playbook for suspected relayed C2: block ASN, isolate hosts, pull implant config, hunt the range.

Home and remote workers

Residential-proxy pools are built largely from infected home computers. If your home machine joins one, your address relays other people's attacks. Keep the router firmware current, turn off remote administration, and never port-forward into your home network.

Use a reputable VPN and antivirus product, enable a filtering DNS service, and keep work tasks in a separate user profile from personal browsing. A patched, boring home setup almost never ends up in a relay pool.

Report checklist for remote staff

  • A proxy or VPN app appeared that you did not install — report it.
  • Your internet feels slow in a steady, rhythmic way at night — report it.
  • Your browser shows certificates warnings on sites you trust — report it.
  • Your device was reset or had settings changed without your action — report it.

Response checklist

  • Enrich the destination IP: ASN, category, reputation.
  • Confirm the (subnet, ASN) pair is first-seen in 90 days.
  • Identify the process and user behind the flow.
  • Measure timing: count intervals and their spread.
  • Scope: search all sources for the relay IP and ASN.
  • Block the ASN or IP; isolate the affected hosts.
  • Hunt 30 days back for the ASN and timing pattern.
  • Report, tune the rules, and feed intel back.

If you only remember one thing

Never trust a single IP address as the story. Enrich every egress log with the owning network, watch the timing and the count of destinations, and let behavior — not blocklists — decide the verdict. The relay hides one address; it cannot hide a pattern.
