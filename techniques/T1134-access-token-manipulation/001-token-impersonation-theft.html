Overview: what this technique is

This guide explains Access Token Manipulation: Token Impersonation/Theft, MITRE ATT&CK technique T1134.001 (official ATT&CK page). You will see how attackers steal Windows logon tokens, what defenders can see, and how to build the detections yourself.

What is an access token?

When you sign in to Windows, the system creates an access token for your session. A token is a small data object that says who you are, which groups you belong to, and which rights you hold. Every program you start carries a copy of your token, and Windows checks that token before the program may open a file or a service.

Token impersonation means a program briefly uses somebody else's identity. Token theft means a program copies another user's token and attaches it to a new process. In both cases the attacker does not need your password. The stolen token does the talking for them. On a shared server, such as a terminal server or an admin jump host, one stolen admin token can unlock a whole company.

3

Red team view: how attackers use it

This part explains the attacker's side. Knowing their steps helps you predict what your logs should show. Everything here is written for defense work and for tests you run with written permission only.

When and why attackers use it

Attackers pick token impersonation when they are already inside one machine and want more. It solves three jobs in one move. First, privilege escalation: a stolen admin token lifts them from a normal user to an administrator without touching UAC or the password store. Second, defense evasion: their actions now look like they came from a trusted admin account, so guards that watch for new and strange accounts stay quiet. Third, lateral movement: on servers where many users share one box, they can ride an existing admin session to other systems.

Attackers also like this technique because it leaves no password trail. Password attacks fill logs with failures. Token theft succeeds on the first try, so there are far fewer events to raise alarms.

What an attacker needs first

Administrator rights on one machine
Or a malware process running as SYSTEM. Reading another user's token needs high rights.
A target process on the same machine
It must run as a more powerful user. A terminal server with many users on it is a rich target.
A tool that can do the theft
Several public test frameworks include token theft, so attackers do not need to write code themselves.

How it is done, step by step

These are the three most common patterns you will meet. They are shown here so you can hunt for their fingerprints, not so you can attack anyone. Use them only in labs or in tests with written permission.

Listing tokens and stealing one with a common test framework:

meterpreter > use incognito
meterpreter > list_tokens -u
meterpreter > steal_token 5124
meterpreter > getuid
Server username: CORP\adm-rmorales

Starting a session as another user with a normal Windows tool. The /netonly switch makes Windows record the session as logon type 9:

runas /netonly /user:CORP\adm-rmorales cmd.exe

Impersonating a user with a public PowerShell module:

powershell -c "Invoke-TokenManipulation -ImpersonateUser -Username 'CORP\adm-rmorales'"

Reminder. Using these commands against systems you do not own, or without written permission, is a crime in most countries. Honest testers use them in lab ranges and during agreed engagements, and they tell the blue team what they did.

4

Blue team view: what defenders see

Token theft is quiet, but it is not invisible. Windows writes events for the steps the technique must take, and the endpoint agent sees the memory access it needs. This part shows where to look.

What the technique leaves behind

Sysmon Event ID 10 (ProcessAccess)
The clearest sign: a strange process opens lsass.exe (the Windows process that keeps logon details) or another user's process with memory-read rights such as 0x1010.
Security Event ID 4672
Special privileges such as SeDebugPrivilege appear for accounts or machines where they make no sense.
Security Event ID 4624, logon type 9
The runas /netonly pattern creates a NewCredentials logon. Normal users almost never produce it.
Security Event ID 4700
A token right was adjusted. Watch for SeDebugPrivilege being switched on by unknown tools.
Unusual parent-child process chains
For example, services.exe (the service manager) starting a script host as SYSTEM.
Endpoint agent telemetry
Many endpoint tools report raw handle access to sensitive processes, even before a dump is written to disk.

Where it sits in the attack chain

ATT&CK files this technique under two tactics, and in most incidents it does both jobs at once: the attacker needs more power (privilege escalation) and wants to stay hidden inside a trusted identity (defense evasion). Later in an intrusion, the same trick supports moving between systems.

TacticWhat the attacker is doingWhat you may see in logs
Privilege EscalationStealing an admin token to skip permission wallsProcess access to lsass.exe; privilege spikes in Event 4672
Defense EvasionActing inside a trusted admin identity instead of a new noisy oneLogon type 9; new processes under services.exe
Lateral MovementCarrying the stolen identity to other hostsThe same admin signing in from many hosts in minutes
Credential AccessReading memory to collect even more credentialsMemory-access alerts from the endpoint agent

Why this matters to defenders

Treat token theft as an identity problem, not only a malware problem. If you clean the malware but leave the stolen session alive, the attacker walks back in. That is why response playbooks for this technique always include disabling the affected accounts and forcing new logons, not just removing the program that stole the token.

Detection engineer deep dive

This part turns the attacker story into working detections: rules and obligations, threat ranking, log sources, Sigma rules, and Splunk queries. Each threat card carries its own log samples and queries, loaded only when you open it, so the page stays light.

Regulation mapping

Token theft is, at its core, a failure of access control and monitoring. Several well-known rules ask companies to prevent it, or at least to detect and report it. These are the ones customers and auditors mention most often.

GDPR
Article 32 asks for security measures that fit the risk. A stolen admin token that exposes personal data is exactly that kind of risk, so detection and response must exist and be provable.
HIPAA
The Security Rule (45 CFR §164.312(b)) asks for audit controls that record and examine activity in systems that hold health data.
ISO/IEC 27001:2022
Control A.8.2 covers privileged access rights, A.8.15 covers logging, and A.8.16 covers monitoring activities.
SOC 2
Trust services criteria CC6.1 and CC6.2 cover logical access, and CC7.2 asks for monitoring that spots anomalies.
PCI DSS v4.0
Requirement 7 asks for least privilege, and Requirement 10 asks for logging and monitoring of all access to cardholder data.
NIST SP 800-53 Rev. 5
AC-6 (least privilege), AU-6 (audit record review), and SI-4 (system monitoring) all apply.

Threat intelligence

Threat intelligence work has four steps. Collect: pull reports from sources such as the MITRE ATT&CK knowledge base, CISA advisories, vendor blogs, and your industry's sharing group. Process: tag each report with the techniques it mentions, so reports about token theft land in one place. Analyze: compare what those attackers did with what your current logs can see, and write the gaps down. Apply: turn the findings into the kind of rules you see on this page, then check them again after each major report.

Which attackers use this technique? Public reporting, including the group list that MITRE keeps on the ATT&CK page, links token manipulation to several state-aligned and criminal groups. Names change as research moves on, so treat this as a starting point and verify it on the official page: APT29, APT32, APT41, Charming Kitten, Cobalt Group, HAFNIUM, and Lapsus$ have all been reported using token manipulation or closely related access-token tricks at some point.

For your own tracking, keep one line per group: where they use the technique in their chain, which tools carry it, and which of your log sources would catch it. Review that table every quarter, because both the groups and the tools change.

How to read and tune the detections

Each card follows the same shape. The log samples show real event fields; the Sigma rule is the portable detection logic; the Splunk query is the same logic written in the Splunk search language. Copy the Sigma YAML into your rule store, and edit the Splunk index and field names so they match your own setup, because every environment names them a little differently. Token impersonation is a Windows technique, so the cards use Windows and Entra ID logs; there is no Linux auditd or firewall trail for it.

Tune before you alert loudly. Run each rule in search-only mode for two weeks, note what fires, and add filters for your real admin activity. A rule that fires once a month with a true positive is worth more than ten rules that fire every hour with noise.

Real-world style incident walkthrough

This walkthrough is a realistic composite built from patterns that appear again and again in public incident reports. It does not describe one specific company or one named real event.

The attack chain, step by step

Day 1, 08:40
A finance employee opens a fake invoice attachment. The malware lands and runs with her normal user rights.
Day 1, 09:05
The malware quietly lists running processes. The employee also uses a company terminal server, and on that box an IT administrator is signed in.
Day 1, 09:12
The malware opens the administrator's process and copies the admin access token. No password is typed anywhere.
Day 1, 09:14
A new process starts under the admin identity. The attacker reads file shares and copies data.
Day 1, 09:30
Using the same rights, the attacker reaches a second server and collects more tokens and passwords.
Day 2, 07:55
The endpoint tool raises one clear alert: an unsigned program in a user folder opened lsass.exe on the terminal server (Sysmon Event 10, access mask 0x1010).
Day 2, 08:05
A first-line analyst checks the alert, sees the strange parent process, and escalates within ten minutes, exactly as the runbook says.
Day 2, 09:00
The response team isolates the terminal server, disables the affected admin account, and forces new logons for every account that was active on that box. The stolen tokens stop working.
Day 3 to 5
The team resets passwords, rebuilds the two affected servers, and watches the network for repeats. Nothing returns.
Week 2
The team writes the report, fixes the phishing gap, and adds the Sigma rules from this guide to permanent monitoring.

How the team responded

The company had an endpoint agent on every server, Sysmon shipping into the log platform, and a simple on-call rota. Those three things decided the outcome. The team also ran a short daily call with department heads during the first week, which kept rumours out of the staff chat and gave everyone one source of truth.

First-line analyst
Checked the alert, confirmed the strange process chain, escalated within ten minutes.
Second-line responder
Pulled the related events, mapped the chain to T1134.001, and scoped every host the admin account had touched.
Incident lead
Decided to isolate and rebuild, kept the timeline, and owned the final report.
IT operations
Isolated hosts, reset passwords, rebuilt servers from clean images. Tools used: endpoint agent, log platform with Sysmon, email gateway logs, backup system.
Leadership and comms
Approved the downtime, informed staff, and filed the required regulator notice because staged employee data was involved.

Impact and lessons learned

The ticket system and some file services were down for about two days. No ransomware went off, because the alert fired before the attacker was ready. The costs were downtime, overtime, a rebuild of two servers, and the regulator report. The trust damage with customers was harder to measure but real.

Coverage beats volume
A single, well-configured log source (Sysmon Event 10) caught the whole chain early.
Passwords were never needed
The attacker stole sessions, not passwords. Password-only thinking would have missed this.
Shared servers spread one token wide
Keep admin work off boxes that many users share.
The ten-minute escalation saved the company
Runbooks only work when people practise them.
Tokens are live sessions
Forcing new logons mattered as much as removing the malware. Kill the sessions.

Mitigation and defense

No single control stops token theft. The wins come from layers: fewer powerful sessions, harder targets, and fast detection when something slips through.

For an enterprise

Shrink the admin surface
Use separate admin accounts, keep domain admin rights off workstations, and tier your admin model so one stolen token cannot reach everything.
Protect LSASS
Turn on LSA protection (RunAsPPL) and, where licences allow, Credential Guard on Windows 10/11 and Windows Server. Both raise the bar for reading logon secrets.
Harden remote sessions
Use Restricted Admin mode for RDP, require network level authentication, and remove clipboard and drive redirection where they are not needed.
Watch the signals
Ship Sysmon and Windows Security logs to your log platform, then run the Sigma rules in this guide and test them with purple-team exercises.
Control what can run
Application control (such as AppLocker or WDAC) and Office attack-surface rules stop the first stage that often leads to token theft.
Segment the network
Keep admin jump hosts in their own zone, so a stolen token on a user LAN has nowhere to go.
Make admin rights temporary
Just-in-time elevation and MFA for admin access cut the window in which a stolen token is useful.
Rehearse the response
Practise isolating a host and forcing new logons, because stolen tokens are live sessions that must be ended, not just files to delete.

For a home user

Use a standard account
Work day to day without admin rights, and only type an admin password when you really need to install or change something.
Keep Windows Update and Microsoft Defender on
Leave tamper protection enabled so malware cannot switch your protections off.
Skip free cracks, keygens, and cheat tools
Most home token theft starts with a program like that.
Use a password manager
Turn on two-step sign-in for your important accounts, so one stolen session is not game over.
Check Defender's protection history
Look at it now and then, and take every LSASS-related block seriously.

Common mistakes and best practices

Common mistakes

Collecting logs nobody reads
Logs only help when someone gets an alert. Start with the eight cards in this guide and grow from there.
Trusting antivirus alone
Token theft often uses normal admin tools, so antivirus stays silent. You need the Windows and Sysmon events listed here.
Running Sysmon with a default config
The default config misses the useful Event ID 10 detail. Use a maintained config that logs ProcessAccess for LSASS.
Ignoring logon type 9
Type 9 is rare and cheap to alert on. Many teams never look at it.
Alerting on every admin action
Event 4672 fires all day for real admins. Use bursts and context, or your team will mute the alert.
Tuning without a baseline
Watch two weeks of admin activity first. Then decide what strange means for your company.
Assuming the agent sees everything
Offline laptops, tampered agents, and cloud assets need their own coverage plans.
Never testing detections
A rule that has never fired may be broken. Test rules with safe purple-team drills.

Best practices that work day to day

Stack your signals
One event is a hint; process plus privilege plus network context together is a case.
Treat detections as code
Keep Sigma rules in version control, review changes, and test before you deploy.
Map every alert to a technique
ATT&CK labels keep reports, metrics, and handovers clear.
Write a short runbook per alert
Say what to check first, who to call, and when to isolate.
Measure your coverage
For each card in this guide, ask: could our current logs actually catch this today?
Review admin accounts every quarter
Remove rights that nobody uses any more.
Run tabletop exercises twice a year
Use the exact scenario in this guide.
Feed lessons back into rules
After each incident or drill, tune the false positives and write down why.
