Dynamic Resolution T1568

Attackers keep their command and control (C2) channel alive by constantly changing the domain names and IP addresses their malware calls home to. This guide explains the three main tricks — fast flux, DGA domains, and DNS calculation — and shows how to catch each one with DNS logs, Sigma rules, and Splunk searches.

Overview

This section explains the technique in plain words, shows where it sits in an attack, and lists what this page will teach you.

What is dynamic resolution?

Malware needs an address to talk to. Most malware reaches out to a command and control (C2) server. C2 is the channel that carries attacker orders to the malware and carries stolen data back. If that address is a fixed domain or IP, defenders can block it once — and the attack is over.

Dynamic resolution removes that weakness for the attacker. Before or during an attack, the adversary buys, computes, or rotates the domain names and IP addresses that the malware uses. The calculations can change the domain name, the IP address, or even the port number the malware calls. ATT&CK also notes that malware often uses dynamic resolution as a fallback channel — a backup way to reconnect when the primary C2 server is lost. The malware almost always finds a live C2 server, while old addresses go dark. Blocking one address is not enough, because a new one appears within minutes.

Think of a spy who changes safe houses every night and leaves a small note about the next address. Dynamic resolution is that note system, built on top of DNS — the internet's phone book, which turns names like example.com into IP addresses.

Note

ATT&CK lists three children under T1568. This page is the parent guide. It explains all three children, shows how attackers combine them, and gives detections that cover the whole family. Each child also has its own deep-dive page.

Fast Flux DNS · .001

One name, many changing IPs. A domain points to a rotating list of hosts, and a very short TTL (time to live — how long a DNS answer may be cached) forces every computer to ask again within seconds or minutes.

ATT&CK page for T1568.001

Domain Generation Algorithms · .002

DGAs are small formulas inside malware. Each day they compute a list of fake-looking domain names, such as qhxvbmzsrt.com. The attacker registers only one or two of them, so the malware keeps trying names until one answers.

ATT&CK page for T1568.002

DNS Calculation · .003

Data hides inside the query itself. The malware packs its ID or a command into the domain name it asks about, for example a1f3c9.task.c2tld[.]com. The attacker's name server reads the request, decodes it, and answers — often with a TXT record (a DNS record that carries plain text).

ATT&CK page for T1568.003

Why it matters to defenders

  • Blocklists alone cannot keep up. A DGA can generate thousands of fresh names per day.
  • The C2 channel protects the attacker's whole operation. Cut it, and commands, updates, and data theft all stop.
  • DNS is one of the best places to watch. Almost every malware needs it, and it usually happens before any encryption hides the traffic.
  • Fast flux and DGA noise also appear in cheap adware. Telling the two apart saves hours of false alarms.

Small glossary before we start

Core DNS terms

  • DNS resolver (recursive resolver) — the server inside your company that answers name lookups for all devices.
  • Authoritative name server — the server that holds the official answer for a domain. Attackers love to run their own.
  • TTL — time to live. It says how long a DNS answer may be stored. Normal websites use hours or days.
  • NXDOMAIN — the DNS answer for "this name does not exist".

Detection terms

  • Passive DNS — a database that records which domains pointed to which IPs in the past, collected from many networks.
  • Beacon — a small, regular check-in from malware to C2, for example every 60 seconds.
  • Sinkhole — a server that takes over a malicious domain so malware talks to the defender instead of the attacker.
  • ASN — autonomous system number. It groups IP addresses under one network owner. Many ASNs in one domain's answers is a red flag.

Written story (screen-reader and no-JS version)

  1. Step 1 — Register a throwaway domain. The attacker registers a cheap, short-lived domain and points its name server records at a server they control. The plan is simple: the name may live only a few days, so defenders have little time to react, and the registration itself leaves the first clue in registrar and passive DNS data.
  2. Step 2 — DGA makes candidate names. Malware on the victim laptop runs a domain generation algorithm. It computes a list of fake-looking names for today and starts asking the company resolver about them. Most names do not exist yet, so the resolver answers NXDOMAIN again and again. The resolver log now shows one host with many random labels — a strong early signal.
  3. Step 3 — Resolver forwards upstream. The company resolver has no answer for these names, so it does its job and asks the authoritative name server on the internet. That server belongs to the attacker. The resolver's outbound lookups and its log entries connect the victim to the attacker's infrastructure.
  4. Step 4 — Fast-flux answer, TTL 30. One of the DGA names is actually registered today. The attacker's name server answers with an IP that changes at every query, and a TTL of 30 seconds keeps caches small. Within two minutes the same name has returned several different IPs, often in different networks. This IP churn is the fast-flux layer in action.
  5. Step 5 — DNS calculation channel. The malware hides data inside the query itself. It packs its host ID and the next request into a long label such as a1f3..9c.task.c2tld[.]com. The attacker's name server decodes the label and learns which machine is calling and what it needs. The company sees only ordinary-looking DNS questions, but their labels are far longer than any human name.
  6. Step 6 — Beacon to the real C2. The name server answers with the real C2 IP inside the A record. The malware now beacons to the C2 server over HTTPS every 60 seconds. On the network this looks like small, regular, boring sessions — to a brand-new domain and IP that nobody has seen before.
  7. Step 7 — SOC correlation fires. The SOC dashboard links the pieces: a high NXDOMAIN ratio, very low TTLs, IP churn, and a beacon to a first-seen domain, all from one host. A correlation alert goes to the analyst with the host name and a risk score. This is the detection moment — four weak signals become one strong case.
  8. Step 8 — Block, sinkhole, and hunt. The analyst blocks the domain at the resolver with a response policy and blocks the C2 IPs at the firewall. Then they use passive DNS to hunt backwards and find three more hosts that talked to the same infrastructure earlier. The attack channel is dead, and the wider campaign is now visible.

Three layers, one channel

The animation shows why the parent technique is an umbrella. Fast flux answers where to connect. The DGA decides which name to use today. DNS calculation hides who is asking. An attacker can use one layer, or all three at once. That is why your detections should watch different DNS features, not just one.

What to remember from the sim

  • The NXDOMAIN burst in step 2 happens minutes before any real C2 traffic. It is your earliest cheap alert.
  • Step 4 and step 5 both need per-client views. Single-line rules miss both.
  • Step 7 is correlation, not magic. Every input came from logs you can already collect.
  • Step 8 works only if you can act fast: resolver response policy zones (RPZ) and firewall blocks, then a retro-hunt.
3

Red team / hacker perspective

This section explains why attackers rotate their infrastructure, how the rotation works in practice, and which mistakes they often make. It is written for defenders: understanding the attacker's choices tells you exactly where to look.

Lab only

Every command in this section is safe and runs only inside a private lab you own — for example a virtual machine on your own computer. Never register lookalike domains of real brands, never point anything at systems you do not own, and never run these tests on a work network. Testing against third-party systems without written permission is a crime in most countries. Use the reserved .test name and documentation IP ranges such as 203.0.113.0/24, which exist exactly for this purpose.

Why attackers drop static C2

A fixed C2 address is a gift to defenders. One blocklist update kills it, one threat-intel report names it, and the whole botnet goes quiet. Public reporting on botnet takedowns shows the same lesson again and again: when the channel dies, the operation dies. Dynamic rotation answers three attacker problems:

  • Survival. Blocked or seized addresses are replaced automatically within minutes.
  • Cheapness. A throwaway domain costs a few dollars, and some top-level domains cost less than a coffee.
  • Attribution blur. Shared name servers, rented hosts, and fast-changing IPs make investigation slower.

How the rotation works, step by step

  1. Buy short-lived domains in bulk from cheap registrars, often under privacy protection, sometimes across several registrars to slow any single seizure.
  2. Point every domain at their own name server. One server can answer for thousands of names, which makes rotation cheap.
  3. Run a DGA inside the malware so the names of the day are computed on the victim, not written in a config file that defenders can read.
  4. Set very low TTLs (30 to 300 seconds) so caches never pin an old answer and flux works.
  5. Mix the layers: flux for the IPs, DGA for the names, DNS calculation for hidden commands. Each layer covers another's weakness.

What an attacker needs first

  • A registrar account and a payment method — a few dollars per domain.
  • A rented server (VPS) to run an authoritative name server and the C2 service.
  • Malware with a DGA or a hardcoded seed, plus a beacon loop.
  • Patience with trial and error: name must look random, TTL must be low, zones must stay small.

Where this technique applies

  • Ransomware groups keep DGA failover channels in case their main C2 is blocked.
  • Botnets use fast flux to rent out hidden hosting to other criminals.
  • Adware and PUP (potentially unwanted programs) use DGAs for noisy but low-value traffic.
  • Information theft tools tunnel stolen data out through DNS calculation when web traffic is watched.

Safe lab exercise: build a toy flux-and-calculation zone

Goal: see the same log shapes the SOC sees, without touching any real infrastructure. Run these commands in a lab virtual machine with Linux installed. The dig tool is a DNS lookup command that comes with most distributions.

Bash · dnsmasq lab zone (lab VM only)
# 1. Install a tiny DNS server inside the lab VM
sudo apt-get install -y dnsmasq

# 2. Point the toy domain at a documentation IP and use a 30 second TTL
#    (add these two lines to /etc/dnsmasq.conf)
#    address=/c2tld.test/203.0.113.10
#    local-ttl=30

# 3. Restart the service
sudo systemctl restart dnsmasq

This note explains the block: dnsmasq is a small, well-known DNS server. The two config lines make it answer for one fake .test name with a short TTL, which mimics fast-flux behavior in a harmless way.

Bash · query the lab zone
# Ask the lab server twice and compare the TTL in the answers
dig @127.0.0.1 beacon01.c2tld.test A +noall +answer
dig @127.0.0.1 beacon01.c2tld.test A +noall +answer

# Send a calculation-style query: a long label that carries fake "data"
dig @127.0.0.1 a1f3c9d2e5b7.task.c2tld.test TXT +noall +answer

This note explains the block: the two A queries show the 30-second TTL counting down, and the long-label TXT query shows what a DNS calculation channel looks like from the outside. Nothing leaves the lab.

Python · print DGA-style names (no registration)
# Prints candidate names only. It registers nothing and contacts nothing.
python3 - <<'PY'
import random, string
random.seed(7)  # fixed seed = same names each run, like a simple DGA
for _ in range(5):
    label = "".join(random.choice(string.ascii_lowercase) for _ in range(16))
    print(label + ".c2tld.test")
PY

This note explains the block: the script prints five random 16-character labels with a fixed starting value, so you always get the same list. Real DGA detection is exactly this problem reversed — telling such labels from normal ones.

Common variations an attacker picks from

Infrastructure variations

  • All three layers at once: DGA names, fluxed IPs, and calculation labels in the same channel.
  • Many top-level domains in rotation, so a block on one list barely hurts.
  • One subdomain per victim, which lets the attacker track each machine separately.
  • Borrowed reputation: some tools place C2 behind large shared hosting or CDN hostnames. The idea is to blend in with trusted traffic; defenders respond by checking that the requested name and the certificate really match the service.

Ethics reminder

Studying this technique is legitimate. Using it against systems you do not own is not. If your team runs attack simulations, keep them in the lab, get written approval, and use only fake or reserved domains and documentation IPs.

Blue team / SOC perspective

This section shows how dynamic resolution looks from the security operations center (SOC), which artifacts it leaves behind, and a simple triage flow you can follow on a busy day.

How defenders actually see it

Nobody in the SOC sees "dynamic resolution" directly. You see its side effects in DNS data. A malware sample asks for names that do not exist. One domain returns five IP addresses in ten minutes. A laptop sends TXT queries with 40-character labels. Each event alone looks boring. Together, they form a shape that normal business traffic does not have.

Your job is to make that shape visible: log every DNS query, keep the logs long enough, and count the right things per client. Section 5 turns this idea into concrete rules.

Where to look — network side

  • Zeek dns.log — one line per query with rcode, TTLs, and answers. The workhorse for all rules in section 5.
  • Suricata EVE (dns) — the same story from an intrusion-detection view, useful for cross-checking.
  • Resolver query logs — from BIND, Unbound, Windows DNS, or a cloud resolver. Covers clients Zeek cannot see, like remote offices.
  • Passive DNS — history for any domain or IP. Perfect for retro-hunts after you block something.
  • Flow logs / firewall — confirms the beacon actually connected after the lookup.

Where to look — endpoint side

  • Sysmon EID 22 (DNS query) — logs the process behind every lookup on Windows. It is the fastest way to move from a domain to a malware sample.
  • EDR DNS events — most endpoint tools (EDR — endpoint detection and response) can show DNS per process; enable it.
  • Proxy and TLS logs — show the beacon after resolution; check that the visited name matches the lookup.
  • Host timeline — did the NXDOMAIN burst start right after a phishing email or a new install?

Why it matters for the whole attack chain

Dynamic resolution sits in the Command and Control tactic, between the initial break-in and the final damage. That position makes it a choke point. If you cut the channel, you stop command delivery, tool downloads, and data theft at once — often before the attacker finishes their goal. It also works in reverse: when you find one C2 domain, passive DNS usually leads you to earlier infections you did not know about.

A simple triage flow

  1. Confirm the event is real. Pull the raw DNS lines. Bots and broken scripts can also make noise.
  2. Check the client. Is it a known server, a scanner, or an office laptop? Known noisy tools go to an allowlist with an owner and a review date.
  3. Read the names. Long random labels? Odd top-level domains? Subdomains that look like data?
  4. Read the answers. How many IPs came back, what TTL, how many different networks (ASNs)?
  5. Attribute on the endpoint. Which process asked? Sysmon EID 22 or EDR data answers in minutes.
  6. Decide and act. Block the domain at the resolver and the IPs at the firewall. Isolate the host if a beacon is confirmed.
  7. Hunt backwards. Query passive DNS for the same name server and IP set. Find other hosts from earlier days.
  8. Write it down. Save indicators, share them internally, and note which rule caught it so tuning has evidence.
Win condition

You do not need to catch the malware file. If you can see the NXDOMAIN burst, block the rotating channel, and attribute the host, the attacker loses their foothold even if you never find the original email.

5.2 Threat intelligence

Threat intelligence (CTI) is outside knowledge about attackers: which groups use which tools, which domains are known bad, and which campaigns are active. For dynamic resolution, CTI helps in three ways: it gives you indicators to block, it gives you context to judge an alert, and it warns you early when a new DGA family appears.

A simple way to work with it

  1. Collect from the sources in the table below. Start with ATT&CK and one passive DNS source.
  2. Enrich. For every DNS alert, attach: first-seen date of the domain, its name server history, and any known actor use.
  3. Apply. Feed high-confidence indicators into the resolver blocklist. Feed campaign context into alert notes so analysts decide faster.

Public reporting links this technique to several large campaigns. Treat the details below as context, not as confirmed facts about any specific network.

Avalanche network (taken down November 2016)

Public reporting by international law enforcement and research partners describes the Avalanche network as hosting infrastructure shared by many malware families. It relied on fast-changing domains and name servers. The November 2016 action seized servers and redirected thousands of domains to sinkholes, which let researchers count infected machines.

Gameover Zeus (disrupted 2014)

Public reporting describes a banking theft botnet that combined peer-to-peer communication with rotated domains, which made blocking harder. Its disruption in 2014 is widely cited as an example of coordinated sinkholing plus endpoint cleanup.

Necurs (disrupted 2020)

Public reporting describes the Necurs botnet as a major spam distributor whose messages carried other malware. Researchers documented its DGA-generated domains, and public reports say the domains could be predicted in advance, which enabled pre-emptive blocking before the 2020 disruption.

Note on hedging

Campaign details change as new reporting appears. When you copy context into an alert or a report, name the source and its date, and prefer "public reporting describes" over firm claims.

Threat 1 — Ransomware DGA failover channel Critical Windows

Description. Modern ransomware keeps a backup command channel. If the main C2 is blocked, the malware switches to DGA names and tries many per day until one answers. Public reporting on several ransomware families describes exactly this pattern.

Preconditions. Malware already runs on a Windows host, the main C2 was blocked or unreachable, and the client can still send DNS out.

Impact. The attacker regains control, pushes the encryption stage, and can also delete backups over the same channel.

Why this rank. Business-stopping damage plus high probability in the current threat landscape. The failover moment is your last cheap chance to stop the attack.

Key signals: NXDOMAIN burst (rule 1), unique-domain spike (rule 4), first-seen beacon (rule 5), endpoint process via Sysmon EID 22 (rule 3).

Threat 2 — Botnet fast-flux C2 hosting High Network Windows

Description. A botnet hides its C2 or rented hosting behind many quickly changing IPs, often machines of other victims. The name stays, the addresses move.

Preconditions. Any client that resolves the fluxed name; no malware needed on your side to be a relay target.

Impact. Steady C2 for the operator, and your network may relay traffic for other victims, which damages reputation and invites blocklisting.

Why this rank. Less sudden than ransomware, but it supports many campaigns at once and is easy to detect — so leaving it undetected is pure loss.

Key signals: TTL at or below 300 seconds with changing answers (rule 2), many unique domains per client (rule 4).

Threat 3 — DNS-tunnel exfiltration via DNS calculation High Network

Description. An attacker encodes stolen data into the labels of DNS queries. TXT answers carry the reply. Because DNS traffic is almost always allowed, the stolen data can leave the network without being noticed.

Preconditions. A compromised host, data worth stealing, and DNS traffic to the internet that is not restricted.

Impact. Quiet, steady data loss that may run for months and evade web-focused controls.

Why this rank. Lower probability than ransomware but very high cost when it happens, because the loss is long and silent.

Key signals: TXT burst with long labels (rule 6), long-label queries (rule 3), unusual query volume per client.

Threat 4 — Cloud-resolver shadow IT hiding C2 Medium Cloud / Identity

Description. Staff or malware switch devices to a public resolver or encrypted DNS service, so company DNS logs see nothing. Malware loves this blind spot.

Preconditions. Clients can reach the internet directly on port 53 or via known encrypted-DNS endpoints.

Impact. Loss of the main detection source; C2 that your rules never see.

Why this rank. Medium probability, medium impact — but it silently weakens every other rule on this page, so treat it as a control-health issue.

Key signals: firewall or flow logs showing direct DNS to external resolvers; check the coverage gap weekly.

Threat 5 — macOS backdoor with attacker resolver setup Medium macOS

Description. Public reporting on macOS backdoors describes malware that points the system resolver at attacker infrastructure and checks in on a schedule. The DNS side looks like threat 2 or 3, just from Macs.

Preconditions. A user installs a trojanized app; DNS egress is open.

Impact. Persistent access to a platform that many SOCs monitor less.

Why this rank. Medium probability and medium impact; the detection logic is identical to Windows cases, so it costs little to cover.

Key signals: low-TTL churn (rule 2), first-seen beacon (rule 5), endpoint DNS events from your Mac security tool — or the network rules above, which see Mac traffic too.

Threat 6 — Adware and PUP DGA noise Low Windows

Description. Cheap adware and Potentially Unwanted Programs also use DGAs, usually to fetch ads or reinstall themselves. The pattern mimics serious malware, so it burns analyst time.

Preconditions. A user installed bundled free software.

Impact. Mostly noise, plus mild risk and slow machines. Its real cost is alert fatigue.

Why this rank. High visibility, low harm. Handle it with a fast triage note, not a heavy investigation.

Key signals: same rules fire, but answers land on advertising or analytics networks; document the family and lower the rule score for that pattern.

5.5 Sigma rules and Splunk SPL

Sigma is a free, text-based format for detection rules. You write the logic once, and converters turn it into searches for Splunk, Elastic, and other tools. Each rule below is complete and valid YAML. Under every rule you get a matching Splunk SPL query (Splunk's search language), plus mapping notes, false positives, and tuning advice. The seven rules below cover the six threats from section 5.3: rules 1, 2, 3, 5 and 6 map to threats 1, 2, 3, 5 and 6, and rule 7 covers threat 4 — clients that bypass your resolver and leave every DNS rule blind. One assumption applies to every rule: your Zeek add-on maps id.orig_h to src_ip; if it does not, use id.orig_h wherever a rule says src_ip. Finally, a rule's level (how loud the alert is) and a threat's severity (how much damage it can do) measure different things — a Critical threat can have a Medium-level rule when the rule only sees part of the picture.

Before you paste

Field names depend on how your logs arrive. The queries assume a Zeek sensor feeding index=dns sourcetype=zeek:dns through a common Splunk add-on, and Sysmon feeding index=ep_sysmon sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational. Each mapping note lists the assumptions again, so you can swap in your own index and field names in minutes.

Detection 1 — NXDOMAIN burst from one client High Network Threat 1 · Threat 6

Sigma rule below: paste it into a .yml file in your rules folder, or test it in any Sigma converter. It fires when one client collects 40 or more NXDOMAIN answers with random-looking external names in five minutes.

YAML · Sigma
title: 'High NXDOMAIN burst from one client'
id: '3f7c2a91-6b4d-4e08-9a52-1c7d84e6f3b0'
status: stable
description: 'Detects a client that receives many NXDOMAIN answers for random-looking
  external names within five minutes. This fits a domain generation algorithm trying
  many candidate C2 names, for example ransomware searching for a live failover channel.'
references:
  - 'https://attack.mitre.org/techniques/T1568/'
  - 'https://attack.mitre.org/techniques/T1568/002/'
  - 'Practice reference: DNS analytics guides recommend watching NXDOMAIN ratios per client'
author: 'Beginner detection guide series'
date: '2026-09-14'
logsource:
  category: dns
  product: zeek
detection:
  selection:
    rcode_name: 'NXDOMAIN'
    query|re: '(?i)([a-z0-9]{8,})\.(com|net|org|info|biz|top|xyz)$'
  filter_internal:
    query|endswith:
      - '.internal'
      - '.corp'
      - '.local'
      - '.in-addr.arpa'
  condition: 'selection and not filter_internal | count() by src_ip >= 40'
  timeframe: 5m
fields:
  - 'src_ip'
  - 'query'
  - 'rcode_name'
falsepositives:
  - 'A browser or security tool that pre-fetches many dead names'
  - 'A misconfigured application that looks up a rotating list of removed hosts'
level: high
tags:
  - attack.t1568
  - attack.t1568.002
  - attack.tactic.command_and_control

Splunk search below: run it over the last 15 minutes as a scheduled search. It keeps only NXDOMAIN answers with random-looking labels, groups them in 5-minute buckets per client, and keeps the buckets with 40 or more hits.

Splunk SPL
index=dns sourcetype=zeek:dns rcode_name=NXDOMAIN
| regex query="(?i)[a-z0-9]{8,}\.(com|net|org|info|biz|top|xyz)$"
| bucket _time span=5m
| stats count AS nxdomain_hits dc(query) AS unique_names BY _time src_ip
| where nxdomain_hits >= 40
| sort -_time

Mapping and tuning. The Sigma selection becomes the two base filters (rcode_name=NXDOMAIN plus the label regex), the aggregation becomes stats ... BY _time src_ip, and where applies the threshold. Assumptions: index=dns holds Zeek DNS events; the add-on maps Zeek's id.orig_h to src_ip — if yours does not, replace src_ip with id.orig_h. False positives usually come from a single broken application; confirm on the endpoint with Sysmon EID 22 before you isolate anything. Tune by raising the threshold after a week of data — busy networks often sit at 15–25.

Detection 2 — Low-TTL answers with changing IPs High Network Threat 2 · Threat 5

Sigma rule below: it fires when one client resolves the same external domain 12 or more times in 30 minutes while every answer TTL stays at or below 300 seconds — the fast-flux shape.

YAML · Sigma
title: 'External domain answered with very low TTL and changing IPs'
id: '8e51d4c7-2f3a-4b19-b6e7-5a90c1d2e8f4'
status: stable
description: 'Detects fast-flux style answers. The same client resolves the same
  external domain many times in half an hour, the answer TTL stays at or below 300
  seconds, and the returned IP set keeps changing. This fits botnet C2 hidden behind
  fast flux.'
references:
  - 'https://attack.mitre.org/techniques/T1568/'
  - 'https://attack.mitre.org/techniques/T1568/001/'
  - 'Practice reference: passive DNS vendors flag low TTL with high IP diversity as flux'
author: 'Beginner detection guide series'
date: '2026-09-15'
logsource:
  category: dns
  product: zeek
detection:
  selection:
    qtype_name: 'A'
    rcode_name: 'NOERROR'
    TTLs|lt: 301
  filter_internal:
    query|endswith:
      - '.internal'
      - '.corp'
      - '.local'
  condition: 'selection and not filter_internal | count() by src_ip,query >= 12'
  timeframe: 30m
fields:
  - 'src_ip'
  - 'query'
  - 'TTLs'
  - 'answers'
falsepositives:
  - 'Round-robin load balancers of large websites with short TTLs'
  - 'Content delivery networks that rotate addresses often, such as video or update services'
level: high
tags:
  - attack.t1568
  - attack.t1568.001
  - attack.tactic.command_and_control

Splunk search below: same logic, plus an IP-diversity check. It needs at least three different answer addresses in the window, which removes most honest load balancers.

Splunk SPL
index=dns sourcetype=zeek:dns qtype_name=A rcode_name=NOERROR
| eval answer_ttl=mvindex(TTLs, 0)
| where answer_ttl <= 300
| bucket _time span=30m
| stats count AS lookups dc(answers) AS unique_ips min(answer_ttl) AS min_ttl BY _time src_ip query
| where lookups >= 12 AND unique_ips >= 3
| sort -_time

Mapping and tuning. TTLs|lt: 301 becomes eval answer_ttl=mvindex(TTLs, 0) and where answer_ttl <= 300: Zeek stores TTLs as a list, one value per answer record, and the add-on usually keeps it as a multivalue field — if your data has a flat TTL field instead, drop the mvindex. The Sigma aggregation by src_ip,query becomes the two-field stats. One note: the Sigma side cannot express "the IP set keeps changing" — it checks TTL and repeat count only, while the SPL adds the IP-diversity check; use the SPL version for alerting where you can. Tuning: large CDNs rarely trigger because their TTLs sit above 300; if a video service still fires, add its domain suffix to a filter block, exactly like filter_internal.

Detection 3 — Long random label from a Windows process High Windows Threat 1 · Threat 3

Sigma rule below: it uses Sysmon event 22 on Windows hosts and matches queries where a random-looking label of 16 or more characters is followed by at least one more label, for example tqs7zbmk1xoa4vh8.c2tld.com. Human names almost never look like this.

YAML · Sigma
title: 'Long random DNS label from a Windows process'
id: 'c2a9f613-7d84-4e5b-8a1d-9b3e6f2c7051'
status: stable
description: 'Detects a Windows process that issues DNS queries with very long,
  random-looking labels — at least one label of 16 or more characters followed by
  further labels, such as a generated subdomain under an attacker zone. This fits
  a domain generation algorithm or an attacker DNS zone. Event 22 also names the
  process, which speeds triage.'
references:
  - 'https://attack.mitre.org/techniques/T1568/'
  - 'https://attack.mitre.org/techniques/T1568/002/'
  - 'https://attack.mitre.org/techniques/T1568/003/'
  - 'Practice reference: Sysmon event 22 gives the process behind each DNS query'
author: 'Beginner detection guide series'
date: '2026-09-16'
logsource:
  category: dns_query
  product: windows
  service: sysmon
detection:
  selection:
    EventID: 22
    QueryName|re: '(?i)[a-z0-9]{16,}\.[a-z0-9-]{2,}\.'
  filter_known:
    QueryName|endswith:
      - '.windowsupdate.com'
      - '.azureedge.net'
      - '.akamaihd.net'
      - '.cloudfront.net'
  condition: 'selection and not filter_known'
fields:
  - 'QueryName'
  - 'QueryResults'
  - 'Image'
  - 'ProcessGuid'
falsepositives:
  - 'Content delivery networks and update services that use long cache-buster labels'
  - 'Backup or monitoring tools that encode job data inside names'
level: high
tags:
  - attack.t1568
  - attack.t1568.002
  - attack.t1568.003
  - attack.tactic.command_and_control

Splunk search below: same filter on the Sysmon index, then a per-host summary so you see repeat offenders and the exact process paths in one screen.

Splunk SPL
index=ep_sysmon sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=22
| regex QueryName="(?i)[a-z0-9]{16,}\.[a-z0-9-]{2,}\."
| search NOT QueryName IN ("*.windowsupdate.com", "*.azureedge.net", "*.akamaihd.net", "*.cloudfront.net")
| stats count AS hits dc(QueryName) AS unique_names values(Image) AS processes BY host
| where hits >= 5
| sort -hits

Mapping and tuning. The base filter (EventCode=22 plus the same regex on QueryName) matches the Sigma selection; the stats adds triage value on top. Assumptions: Sysmon arrives as XML into index=ep_sysmon, so fields keep their XML names — QueryName, QueryResults, Image, host — and EventCode=22 marks DNS query events. In Sigma the event number is EventID: 22; converters handle the rename. Tuning: watch the processes column — browser hits are noise, anything from AppData or a temp folder is urgent. Note that the Sigma rule fires on single events, while the SPL adds a per-host summary on top — keep both, they answer different questions.

Detection 4 — Unusual number of unique domains per hour Medium Network Threat 2 · Threat 6

Splunk search below: identical counting logic, sorted so the loudest client sits on top. Schedule it hourly and compare against your baseline before raising or lowering the threshold.

Splunk SPL
index=dns sourcetype=zeek:dns
| regex query="(?i)\.(com|net|org|info|biz|top|xyz)$"
| search rcode_name IN ("NOERROR", "NXDOMAIN")

Mapping and tuning. Sigma's two-value rcode_name list becomes the IN filter, and count(query) by src_ip becomes dc(query) ... Detection 7 — Client bypassing the internal resolver Medium Threat 4

status: stable

  every DNS rule. Treat hits as a control-health problem first and a compromise
  indicator second.'
references:
  - 'https://attack.mitre.org/techniques/T1568/'
author: 'Beginner detection guide series'
date: '2026-09-19'
logsource:
  category: network_connection
  product: zeek
  service: conn
detection:
  selection:
    id.resp_p: 53
    proto: 'udp'
  filter_resolvers:
    id.resp_h:
      - '10.20.1.10'
      - '10.20.1.11'
  condition: 'selection and not filter_resolvers'
fields:

Mapping and tuning. The Sigma selection is a single condition (destination port 53 over UDP) and the filter is the allowlist of your two internal resolvers; the SPL mirrors both and adds a per-client summary. Assumptions: Zeek connection logs land in index=network sourcetype=zeek:conn; change the index and the resolver list to match your site. Tuning: expect one burst of findings in the first week as you discover legitimate direct-resolver users — move each one into the allowlist with an owner and a reason, or block it.

Validation habit

Replay the lab queries from section 3 against your search head before going live: a five-minute test with fake data proves the fields, the regex, and the thresholds faster than any document. Re-test after every add-on upgrade, because field names quietly change.

6

Real-world case study

The best-known example of dynamic resolution at scale is the Avalanche network, taken down in November 2016. Everything below follows public reporting from law enforcement and research partners, so treat exact numbers as approximate.

Background

Public reporting describes Avalanche as a rented hosting and naming platform shared by many criminal groups. It gave them two services: fast-changing domains (fast flux) and name servers that moved often. Malware families that used it included banking theft tools and ransomware. Because the platform was shared, one takedown touched many campaigns at once — and because it rotated domains constantly, simple blocklists had little effect for years.

Timeline as public reporting describes it

  1. 2009 onward

    The platform grows. Researchers notice that many unrelated malware families resolve their C2 names through the same small set of name servers — the first structural clue.

  2. 2014–2016

    Researchers, registrars, and law enforcement map the network quietly. They document thousands of fluxed domains and plan a coordinated response, including sinkhole access for several malware families.

  3. November 2016

    Coordinated action across roughly 40 countries seizes servers and redirects large numbers of domains to defender-controlled sinkholes. Public reporting describes hundreds of servers taken and many hundreds of thousands of domains affected.

  4. Weeks after

    Sinkhole logs show millions of still-infected machines calling in worldwide. Security vendors push updated detections, and enterprises use the sinkhole data to find their own victims.

  5. 2017 and later

    Remaining botnets decline as their DGA names expire and cleanup finishes. The case becomes a textbook example of why shared infrastructure is both a strength and a weakness for attackers.

Attack chain in one view

  • In: spam and exploit kits deliver the malware to victims.
  • Resolve: each sample computes or fetches a rotating C2 name and resolves it — DGA plus flux together.
  • Connect: the malware beacons to whatever IP the answer gave, on shared fluxed hosting.
  • Act: the operator pushes commands — steal banking data, or drop the ransomware stage.

Detection point

For researchers, the detection point was structural: many families, one naming pattern. For an enterprise, the same campaign shows up exactly where this page says — NXDOMAIN bursts, low TTLs, and beacons to first-seen domains. After the takedown, sinkhole contact lists became a free victim-finding tool: if your resolver had asked those domains, you had an infected machine.

Containment and eradication

Containment was network-wide: domains were sinkholed, so malware talked to defenders instead of criminals. For individual organizations, eradication meant using sinkhole and vendor data to list infected hosts, then cleaning or reimaging them and resetting credentials the malware could have stolen.

Recovery and impact

Recovery meant watching for leftovers for months, because not every sample accepted the sinkhole answer. Public reporting says the platform infected millions of machines in many countries. The takedown reduced theft and spam for months. But the criminal groups later rebuilt their networks on new infrastructure.

How the response teams worked

The operation needed years of quiet coordination: researchers shared data, registrars suspended domains, courts in several countries approved seizures, and vendors prepared sinkhole coverage. Enterprises received indicator lists and cleanup guidance within days. The lesson for your SOC is communication speed — when a shared takedown happens, you want a person who reads the bulletins and turns them into searches that day.

Lessons learned

  • Shared infrastructure cuts both ways. One pattern exposed many campaigns at once.
  • Sinkholes do double duty — they stop the attack and count the victims.
  • DNS analytics matter more than blocklists for the next cycle, because the groups rebuilt.
  • Takedowns buy time. Endpoint hygiene and monitoring decide whether time becomes safety.
7

Mitigation and defense

You cannot stop malware from computing domain names — the fix is to make the network boring and observable, so rotation has nothing to hide behind. The controls below are grouped by area, then by budget.

Policy

  • Written rule: all clients use company resolvers only.
  • Domain allowlist process with an owner and review dates.
  • Turn on multi-factor authentication (MFA) and a registrar lock for the accounts that hold your own domains.

Network

  • Block direct outbound port 53 except from resolvers — this matches ATT&CK mitigation M1021 (Restrict Web-Based Content: a local DNS sinkhole).
  • Run a response policy zone (RPZ) or sinkhole for known-bad names.
  • Use network intrusion prevention on known malware channels — ATT&CK mitigation M1031 (Network Intrusion Prevention).
  • Alert on traffic to first-seen domains from section 5.5 rules.

Endpoint

  • Enable Sysmon event 22 (or EDR DNS events) on every Windows host.
  • Deploy EDR on Macs too — threat 5 is easy to miss.
  • Keep office software updated; most DGA malware still needs an old bug to land.

Cloud and identity

  • Turn on DNS query logging in each cloud account and send the logs to your SIEM — the central system that stores and searches security logs.
  • Least-privilege accounts, so a stolen login cannot change resolver settings.
  • Watch for new encrypted-DNS usage from servers, which should never need it.

Logging and monitoring

  • Retain DNS logs 90–180 days for retro-hunts.
  • Dashboards: NXDOMAIN ratio, low-TTL share, unique domains per client.
  • Integrate one passive DNS source for enrichment.

Backup and response

  • Offline or immutable backups — ransomware with a DGA failover channel still tries to delete them.
  • Runbook: block, isolate, retro-hunt, report (section 4 triage flow).
  • Practice the DGA alert once per quarter, end to end.
Home and small office

You can do this without an SOC. Point your router's DNS at a filtering resolver, keep router firmware updated, put smart devices on a guest network, and turn on DNS query logging if your router offers it. One habit matters most: keep one offline backup. Most home-relevant attacks using this technique are ransomware, and a backup turns a disaster into an inconvenience.

Daily habits

  • Check the DNS dashboards before the queue: NXDOMAIN ratio, unique-domain leaders.
  • Read one fired rule end to end — raw log to host — even for five minutes.
  • Note any new noisy client and route it to the allowlist process.

Weekly habits

  • Compare resolver coverage: what share of clients still uses it?
  • Tune the one rule with the worst true-positive rate.
  • Skim new CTI reports for DGA or flux keywords and save seeds if shared.

Monthly habits

  • Replay the section 3 lab data against every DNS rule.
  • Review the allowlist and remove expired entries.
  • Re-read the threat ranking (5.3) and adjust priorities with your team.
Watch out

The fastest way to lose this capability is a noisy first month. If a rule fires more than a handful of times per day without a true positive, stop and tune it that week. Analysts learn quickly to ignore an alert name — and un-learning is much harder than fixing.

Response checklist

  • Pull the raw DNS lines for the suspect client and time window.
  • Confirm the shape: burst, low TTL, long labels, or repetition.
  • Attribute the process with Sysmon EID 22 or EDR.
  • Block the domain at the resolver (RPZ) and the IPs at the firewall.
  • Isolate the host if a beacon is confirmed.
  • Retro-hunt the name server and IP set in passive DNS.
  • List other clients that touched the same infrastructure.
  • Save indicators with dates; note which rule fired.
  • Notify the data owner if exfiltration is possible.
  • Schedule the follow-up hunt for one week later.
