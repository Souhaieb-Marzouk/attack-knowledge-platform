Fast Flux DNS T1568.001

One domain, hundreds of changing IP addresses. Criminals use fast flux DNS to keep phishing pages and command-and-control servers online even when defenders take hosts down. The good news: the constant record churn itself leaves clear traces. This guide shows how to see them, step by step.

1

Overview

Fast flux is a way to hide a server behind a cloud of fast-changing IP addresses. This section explains the idea in plain words, introduces the few terms you need, and shows why detection teams treat fast flux as a high-value signal.

What is fast flux?

DNS (Domain Name System) is the phone book of the internet. It turns a name such as portal.example into an IP address, which is the number a computer really connects to. The link between a name and an address is stored in a DNS record, and every record carries a TTL (time to live). The TTL says how long the answer may be reused before the computer must ask again.

With fast flux, the attacker controls the authoritative name server — the server that gives the final answer for their domain. They set a very short TTL (often 30 to 300 seconds or lower) and change the A record (the name-to-address link) every few minutes. The answer always points to one of many flux proxy nodes: hundreds of hacked home computers and small servers spread across the world. Each node forwards traffic to the hidden real server. If one node is cleaned or blocked, the next query simply returns a different node. The domain survives; the hidden server is never exposed. ATT&CK describes two variants: single flux rotates the A-record addresses, which have a five-minute average lifespan, and double flux also rotates the name-server records of the whole zone, adding proxy hosts that insulate the real C2 server.

Public reporting describes fast flux as a standard part of large botnets since the Storm worm era in 2007. It is still common in phishing kits and malware families today.

Single flux

Only the A records (and sometimes AAAA records for IPv6) rotate. The name moves between many relay addresses. The name server itself stays in one place. This is the common form and is already hard to block by IP alone.

Double flux

The NS records rotate too. NS records say which name servers answer for a domain. In double flux, both the DNS layer and the traffic layer sit on moving hosts. This makes takedowns much harder, because defenders must chase the name servers as well as the relays.

Why it matters

Blocking one IP address does almost nothing against fast flux: the domain simply returns the next address. Teams that only chase IPs waste days in a loop that never ends. Teams that watch the name and its record churn get a stable, high-confidence signal that works across the whole botnet.

Where it fits in the attack chain

T1568.001 lives in the Command and Control tactic: malware on a victim talks to its operators through the fluxed domain. The same infrastructure often serves earlier stages too — phishing landing pages that steal passwords, and pages that hand out malware. The parent technique T1568 · Dynamic Resolution groups related ways to change DNS answers on demand.

Defender view

Attacker operator Victim PC Flux infrastructure SOC analyst Relay traffic to hidden C2

Written story (screen-reader and no-JS version)

  1. Step 1 — Building the flux network. The attacker infects many home PCs and small servers and installs proxy software on them. Each infected machine becomes a flux node that quietly forwards traffic for the attacker.
  2. Step 2 — Domain set to flux. The attacker registers a young domain, points its NS records at an attacker-run name server, and sets the record TTL to only 30 seconds.
  3. Step 3 — Victim resolves the domain. The victim PC asks for the domain and receives the IP address of flux node A in the answer.
  4. Step 4 — Relay to hidden C2. The victim connects to flux node A, which forwards the traffic to the hidden command-and-control server. The real server address never appears in the victim's logs.
  5. Step 5 — Records rotate. The 30-second TTL expires. The next lookup returns flux node B in another country and on a different network operator (ASN). In the double-flux variant, the zone's name-server set rotates too, so even blocking the name servers is not enough.
  6. Step 6 — Sinkhole hits node A. Defenders take over flux node A, but the botnet does not stop. The domain simply hands out flux node C instead, so the attacker sees no outage.
  7. Step 7 — SOC sees the pattern. The SOC analyst reviews passive DNS data and finds one name that mapped to 42 addresses in the last 24 hours — with bursts of more than 20 within a single hour — across 12 autonomous systems, all with a TTL of 30 seconds.
  8. Step 8 — Domain blocked and reported. The team blocks the domain at the recursive resolver, hunts for past connections to it, and reports the name to the registrar and threat intelligence partners.

The lesson of the animation is simple. The name stays the same; the answers keep changing. IP-based blocking plays catch-up forever, while name-based blocking plus record-churn analytics catches the whole network at once. The next sections turn that lesson into concrete log sources, rules, and queries.

3

Red team / hacker perspective

This section explains how attackers build and run a fast flux network. Understanding the attacker's requirements and their usual mistakes is what makes the detections in section 5 possible. The goal here is understanding, not a recipe.

Lab only

Everything below runs only inside a closed test network that you own — for example two virtual machines on an isolated host-only network. Running a real flux network, or pointing DNS at systems you do not own, is illegal in most countries and breaks every responsible-use policy. Use reserved example names (RFC 2606, like flux-lab.example) and documentation IP ranges (RFC 5737, like 203.0.113.0/24) so lab traffic can never leak to the internet.

Why attackers use it

Fast flux buys three things at once: uptime (takedowns of single hosts change nothing), anonymity (the real server never touches victims), and scale (stolen bandwidth and residential IPs are nearly free). A phishing page or C2 channel that survives IP blocks is worth the setup effort.

Where it shows up

Public reporting ties fast flux to spam campaigns, phishing kits, ransomware families, and long-lived botnets. The same pattern also appears behind fake shops, fake login pages, and "guaranteed profit" sites — anywhere the operator expects the infrastructure to get reported quickly.

What it costs them

Flux needs many stable bots, an attacker-run name server, and constant record updates. Each of those is a target for defenders: cleaning bots shrinks the pool, sinkholing a name server hurts the whole network, and passive DNS makes the churn visible.

How a flux network is built (concept)

Attackers assemble the same five pieces in almost every known campaign. Public research papers and takedown reports describe the flow like this:

  1. Collect hosts. Malware turns many victim machines into "flux agents" — small proxy programs that accept connections and forward them onward.
  2. Register a domain. Often a fresh, cheap name that resembles a trusted brand. The registration is usually short-term.
  3. Point NS at their own server. The attacker's authoritative name server now decides every answer for the domain.
  4. Set a low TTL and publish bot IPs. The zone answers with a handful of live flux agents and a TTL of 30–300 seconds or less.
  5. Rotate. A scheduler updates the zone every few minutes and drops dead agents from the answer set.

A safe lab look-alike with dnsmasq

You can recreate the observable part of fast flux — round-robin answers with a tiny TTL — without any malware. The lab below uses dnsmasq, a small open-source DNS server, on an Ubuntu VM. It serves three documentation IPs in turn with a five-second TTL, which behaves like a miniature flux zone for testing your rules.

Note: this config makes one lab VM hand out three rotating addresses for one example name. It never contacts the internet.

dnsmasq · lab zone
# /etc/dnsmasq.d/flux-lab.conf  — LAB ONLY, isolated host-only network
domain=flux-lab.example
local=/flux-lab.example/
address=/flux-lab.example/10.20.0.11
address=/flux-lab.example/10.20.0.12
address=/flux-lab.example/10.20.0.13
local-ttl=5
max-ttl=5
no-resolv
no-hosts
log-queries

Start the service with sudo systemctl restart dnsmasq, then probe it from the second lab VM with dig, the standard DNS test tool. Repeating the same query returns the addresses in turn, and the answer shows the five-second TTL — exactly the pattern the detection rules hunt for.

shell · dig checks
# From the second lab VM, same isolated network — LAB ONLY
dig +short flux-lab.example @10.20.0.5     # first answer, e.g. 10.20.0.11
dig +short flux-lab.example @10.20.0.5     # next answer, e.g. 10.20.0.12
dig flux-lab.example @10.20.0.5            # full answer shows TTL 5
dig NS  flux-lab.example @10.20.0.5        # NS answer for NS-churn tests

Point your Zeek sensor or resolver logs at this lab traffic and the six rules in section 5.5 will fire on it. That gives you a reproducible test bench for tuning thresholds before you trust them on production data.

Variations you will meet

Single flux

Only the A/AAAA records rotate. Easiest to run, easiest to spot. Most consumer-grade phishing kits use this form.

Double flux

NS records rotate as well, often on the same bot pool. The DNS layer itself becomes a moving target. Expect long answer sets and visible NS churn.

CDN-abuse look-alikes

Attackers either hide behind trial accounts on legitimate CDNs or imitate their look: many IPs, short TTL. The difference is the ASN spread pattern and the reputation of the networks involved.

Mistakes attackers make (and you can detect)

  • Reusing relay IPs across campaigns and families — passive DNS links the networks together.
  • TTL too high because a template zone was left unchanged — the rotation stalls and blocks start to work.
  • Too few ASNs — a handful of cheap VPS providers makes the footprint obvious in an ASN histogram.
  • Name server and web server on the same host — one takedown removes both layers.
  • Careful registration data left over — reused registrant details cluster domains for threat intel teams.

Each mistake is a clue to more findings. Attacker shortcuts often show you related domains.

4

Blue team / SOC perspective

Defenders rarely see the hidden server — they see its shadow: short TTLs, changing answers, and clients that keep asking for the same name. This section maps the shadow to the artifacts you already collect.

What defenders actually see

A fast flux domain does not look dangerous in a single event. One DNS query with one answer is boring. The danger appears only across time: the same name returns a different address every time you look, from networks all over the world. That is why passive DNS — a stored history of DNS answers — is the single most valuable source for this technique.

Passive DNS services

Commercial and open passive DNS feeds store every name-to-address pair their sensors see. Ask one question: how many addresses has this name used this week? Dozens across many ASNs is a strong flux signal.

Your own resolver logs

If you run your own recursive resolvers (you should), their query logs show which internal clients asked for the fluxed name and how often. Store them long enough to hunt retroactively — 90 days is a common minimum.

Network sensors

Zeek produces a dns.log with queries, answer sets, and TTLs. Suricata writes the same facts into its dns EVE records. Both are perfect inputs for the rules in section 5.5.

Registration data

RDAP and commercial registration feeds reveal domain age and registrant behavior. Flux domains are usually hours or days old when they start resolving.

Threat intelligence

Vendor feeds, ISAC bulletins, and your own incident history mark names already known for flux. Section 5.2 sorts these sources by confidence.

Proxy and firewall logs

Web proxies and firewalls show the second half: clients connecting to the rotating addresses on odd ports, or through the relays when a user opens the phishing page.

Why it matters for the SOC

Fast flux is rarely the attack itself — it is the delivery and command layer for something worse. A confirmed flux domain in your logs means one of three things is happening: someone clicked a phishing link, malware is beaconing, or spam is flowing through your mail gateway. Each one deserves a different follow-up, which is why the triage flow below starts with the domain, not with the hosts.

Five-step triage flow

  1. Confirm the name. Collect the exact domain from the alert or log line, and check it is not one of your own zones or a known partner.
  2. Pull passive DNS history. Count distinct answers, ASNs, and countries over 24 hours. Look at the TTL distribution.
  3. Check the registration. Domain age, registrar, and privacy-redacted registrant. A young domain that also shows flux is a strong warning sign.
  4. Measure the ASN spread. More than a handful of unrelated networks in an hour is rarely a legitimate CDN pattern.
  5. Block and hunt. Block the domain (not the IPs) at the resolver, then hunt backwards for every client that resolved it in the last 30–90 days, and report the name to your registrar contact and intel partners.
Good to know

You do not need to see the malware to catch fast flux. The DNS layer gives you a clean, durable signal that survives even when the attacker rotates every relay address. Keep the domain, keep the evidence.

Known campaigns (public reporting)

  • Storm botnet (2007–2008). Public reporting describes Storm as the campaign that made fast flux famous: spam waves pointed to fluxed domains, and researchers estimated the infected host count in the hundreds of thousands or more.
  • Avalanche (takedown announced 2016). An international action against a hosting and malware distribution platform that, per public reporting, relied on fast-flux-style infrastructure for many affiliated campaigns.
  • Kelihos. A spam and malware botnet whose reported infrastructure used fast-flux behavior; it was disrupted after years of operation.
  • Phishing kits with fluxed domains. Vendor reporting regularly describes kit operators rotating domains through many addresses to outlast URL blocklists.

ATT&CK's own detection strategy (DET0485)

The official page groups its detection advice as analytics AN1331–AN1334: flag repeated resolutions where one name returns many IPs in short succession, combined with low TTL values and high query volume from unusual processes (AN1331); watch resolver logs and Linux auditd for domains that rotate addresses inside very short TTL windows (AN1332); on macOS, use the unified log to catch processes whose resolved addresses keep changing (AN1333); on ESXi, alert on frequent domain-to-IP changes and unauthorized DNS settings from management agents (AN1334). The rules in section 5.5 implement the network side of this advice.

How to apply the intel

  1. Collect: subscribe to one passive DNS feed, one registration feed, and your sector ISAC.
  2. Analyze: tag every flux-confirmed domain with the artifacts you saw (TTL, ASN count, age).
  3. Apply: feed confirmed names into resolvers (block), rules (test), and hunts (retro match).
  4. Share: report confirmed names to your registrar and ISAC so other defenders benefit.

Spotlight: threat 1

Botnet C2 through flux relays is ranked critical because it removes every traditional lever: IP blocks fail, the hidden server stays hidden, and the malware keeps working for weeks. The DNS churn rules in 5.5 are the reliable way to stop it.

Spotlight: threat 2

Phishing pages behind flux stay alive exactly as long as the campaign needs. Treat any confirmed fluxed domain in user mail as an identity incident: force password resets for everyone who clicked, and check for new inbox rules.

Spotlight: threat 3

Double-flux hosting is the supplier behind threats 1, 2, and 4. Reporting the name server infrastructure to the registrar has a bigger effect than reporting any single relay IP — one report can take a whole campaign family offline.

5.4 Logs and patterns

Fast flux leaves its traces in three kinds of records: the DNS answers your sensors see, the passive DNS history built from them, and the connection logs that follow. The examples below use documentation IP ranges (RFC 5737) and example domains, so every line is safe to copy into training material.

Example 1 — Zeek dns.log. Zeek is an open-source network sensor. Its DNS log records each exchange with the full answer set and the TTL values. A flux answer looks innocent in one line and suspicious only when you compare lines over time.

JSON · Zeek dns.log
{"ts":"2025-11-03T09:41:22.410Z","uid":"Czw8Xj3aQpLk9mR2d","id.orig_h":"10.14.6.31","id.resp_h":"10.14.2.10","proto":"udp","trans_id":51234,"rtt":0.031,"query":"secure-login.example.com","qclass":1,"qclass_name":"C_INTERNET","qtype":1,"qtype_name":"A","rcode":0,"rcode_name":"NOERROR","AA":false,"TC":false,"RD":true,"RA":true,"Z":0,"answers":["203.0.113.7","198.51.100.23","203.0.113.99"],"TTLs":[30.0,30.0,30.0],"rejected":false}

Note: one Zeek event per DNS exchange. Here an internal client (10.14.6.31) asked the corporate resolver (10.14.2.10) for an A record and received three addresses, each with a 30-second TTL.

Example 2 — passive DNS record. Passive DNS services and open collectors summarize what they saw over time. This shape (common to several providers) is what answers the churn question in one object.

{"record_type":"passive_dns","domain":"secure-login.example.com","query_type":"A","first_seen":"2025-10-29T04:12:00Z","last_seen":"2025-11-03T09:40:00Z","ip_count":42,"asn_count":12,"country_count":9,"ttl_min":30,"ttl_max":300,"ns_set":["ns1.flux-ns.example.net","ns2.flux-ns.example.net"],"sources":["sensor-eu-1","sensor-us-2"]}

Note: 42 addresses across 12 autonomous systems and 9 countries within the last 24 hours, with a minimum TTL of 30 seconds — a typical fast flux footprint.

5.5 Sigma rules and Splunk SPL

Sigma is an open rule format for describing detections in vendor-neutral YAML; a converter turns each rule into the query language of your SIEM. Below are six rules for the ranked threats, each followed by a Splunk SPL (Search Processing Language) query with the same logic. Thresholds are starting points — tune them on a week of your own data before enabling alerts. Two notes before you start: a rule's level (how loud the alert is) and a threat's severity (how much damage it can do) measure different things — a Critical threat can have a Medium-level rule when the rule only sees part of the picture; and the assumptions under each rule trace back to ATT&CK's official detection strategy DET0485 (see section 5.2).

Rule 1 — answer churn. Matches threats 1–4: one name returning more than 20 distinct addresses within an hour is the defining fast flux behavior.

YAML · Sigma
title: DNS Name Resolved to Many Distinct IPs in One Hour (Fast Flux)
id: 9c1f7a2e-3d54-4b8a-9f6e-1c2d3e4f5a6b
status: experimental
description: >-
    Detects a single DNS name that returned more than 20 different IP addresses
    within one hour. Fast flux domains rotate A records very fast so that one
    name always points to a live relay. Content delivery networks behave in a
    similar way, so keep an allow list of known CDN names and network owners.
references:
    - https://attack.mitre.org/techniques/T1568/001/
    - The Honeynet Project research paper on Fast-Flux Service Networks
author: SOC Detection Engineering
date: 2025-11-04
logsource:
    category: dns
    product: zeek
detection:
    selection_ok:
        rcode_name: 'NOERROR'
    condition: selection_ok | count(distinct answers) by query > 20
    timeframe: 1h
fields:
    - id.orig_h
    - query
    - answers
    - TTLs
falsepositives:
    - Large content delivery networks and round-robin load balancers
    - Big mail providers with many A and MX records
level: high
tags:
    - attack.t1568.001
    - attack.tactic.command_and_control

The SPL uses the same count over the same window. It also reports how many clients asked, which turns the alert into a ready-made scope list.

Splunk SPL
index=dns sourcetype=zeek:dns rcode_name="NOERROR"
| bin _time span=1h
| mvexpand answers
| stats dc(answers) AS distinct_ips dc(id.orig_h) AS asking_clients values(TTLs) AS sample_ttls by _time, query
| where distinct_ips > 20
| sort - distinct_ips

Assumptions: Zeek DNS logs land in index=dns with sourcetype=zeek:dns, one event per exchange. answers and TTLs are multivalue fields, so mvexpand creates one row per answer before counting. Rename the index to match your environment, and add a filter that excludes names you own.

Rule 2 — short TTL on external names. A context rule for threats 1–5: legitimate CDNs also use short TTLs, so this signal wants a companion (churn or ASN spread) before you escalate.

YAML · Sigma
title: External DNS Answer with Very Short TTL
id: 5e8d2c41-9a7b-4f3c-8d1e-7f6a5b4c3d2e
status: experimental
description: >-
    Flags successful DNS answers with a time-to-live of 60 seconds or less for
    names outside your own zones. Fast flux operators keep the TTL low so that
    record changes reach victims quickly. Some CDNs and dynamic DNS services
    also use short TTLs by design, so treat this as a context signal and
    combine it with answer churn or ASN spread before escalating.
references:
    - https://attack.mitre.org/techniques/T1568/001/
    - Public passive DNS research describing fast flux TTL patterns
author: SOC Detection Engineering
date: 2025-11-06
logsource:
    category: dns
    product: zeek
detection:
    selection:
        rcode_name: 'NOERROR'
        TTLs|lte: 60
    filter_internal:
        query|endswith: '.corp.example'
    filter_reverse:
        query|endswith: '.in-addr.arpa'
    condition: selection and not 1 of filter_*
fields:
    - id.orig_h
    - query
    - TTLs
    - answers
falsepositives:
    - Content delivery networks that use short TTL by design
    - Dynamic DNS services used by remote workers
    - Anti-spam and time sync services with short-lived records
level: medium
tags:
    - attack.t1568.001
    - attack.tactic.command_and_control

Replace .corp.example with your own zones. The SPL keeps the filter explicit so reviewers can see the exclusions at a glance.

Splunk SPL
index=dns sourcetype=zeek:dns rcode_name="NOERROR"
| eval answer_ttl=mvmin(TTLs)
| where answer_ttl <= 60
| search NOT query="*.corp.example" NOT query="*.in-addr.arpa"
| stats count AS low_ttl_answers avg(answer_ttl) AS avg_ttl dc(answers) AS distinct_answers by query
| sort - low_ttl_answers

Assumptions: same index and sourcetype as rule 1. Zeek stores per-answer TTLs as a list in the TTLs field (see the examples above); mvmin(TTLs) takes the smallest value so one long-lived record cannot hide the short ones. If your add-on flattens the list into a numeric TTL field, replace mvmin(TTLs) with TTL. Edit .corp.example to your internal domain suffix.

Rule 3 — client-side beaconing on low TTL. Matches threat 1: malware that follows rotating records re-resolves constantly, so one client accumulates dozens of short-TTL answers in minutes.

YAML · Sigma
title: Client Collects an Unusual Number of Low TTL Answers (Flux Beaconing)
id: c3a95f17-6b28-4e7d-a1c4-2f9e8d7c6b5a
status: experimental
description: >-
    Counts low TTL answers per internal client in a ten minute window. Malware
    that uses a fast flux domain re-resolves the name many times per hour to
    follow the rotating records. A client that collects more than 100 short TTL
    answers in ten minutes is likely re-resolving a fluxed name or a very
    chatty legitimate service. Check the client for the queried names before
    you escalate.
references:
    - https://attack.mitre.org/techniques/T1568/001/
    - Botnet behavior studies on fast flux re-resolution patterns
author: SOC Detection Engineering
date: 2025-11-10
logsource:
    category: dns
    product: zeek
detection:
    selection:
        rcode_name: 'NOERROR'
        TTLs|lte: 60
    condition: selection | count() by id.orig_h > 100
    timeframe: 10m
fields:
    - id.orig_h
    - query
    - TTLs
falsepositives:
    - Workstations that sync time or fetch mail from short-TTL services
    - Build servers and CI runners with high DNS activity
level: medium
tags:
    - attack.t1568.001
    - attack.tactic.command_and_control

The SPL groups by ten-minute buckets, matching the rule's window, and adds the number of distinct names so you can tell one fluxed name from general noise.

Splunk SPL
index=dns sourcetype=zeek:dns rcode_name="NOERROR"
| eval answer_ttl=mvmin(TTLs)
| where answer_ttl <= 60
| bin _time span=10m
| stats count AS low_ttl_hits dc(query) AS distinct_names min(answer_ttl) AS min_ttl by _time, id.orig_h
| where low_ttl_hits > 100
| sort - low_ttl_hits

Assumptions: Zeek DNS logs in index=dns with the list field TTLs; mvmin(TTLs) picks the shortest TTL of each answer. If your pipeline exposes a flat numeric TTL, use it directly in both where lines.

Rule 4 — NS record churn. Matches threat 3 (double flux): the name-server set for one domain changes over and over, which legitimate zones almost never do.

YAML · Sigma
title: Changing NS Record Set for a Single Domain (NS Churn)
id: 7b4e1d92-8c35-4a6f-b2d8-3e5f7a9c1d0b
status: experimental
description: >-
    Detects name server (NS) answers for one domain that change too often. In
    double flux the attacker rotates NS records together with A records, so
    even the DNS layer sits on moving hosts. A name whose NS answer set shows
    more than two distinct values within the window deserves a closer look,
    especially when the domain is young.
references:
    - https://attack.mitre.org/techniques/T1568/001/
    - Public analyses of double flux botnet infrastructures
author: SOC Detection Engineering
date: 2025-11-12
logsource:
    category: dns
    product: zeek
detection:
    selection_ns:
        qtype_name: 'NS'
        rcode_name: 'NOERROR'
    condition: selection_ns | count(distinct answers) by query > 2
    timeframe: 1h
fields:
    - id.orig_h
    - query
    - answers
falsepositives:
    - Managed DNS providers during planned zone migrations
    - Registrars that answer NS queries from rotating anycast nodes
level: medium
tags:
    - attack.t1568.001
    - attack.tactic.command_and_control

The SPL mirrors the rule on your Zeek data. To watch NS churn over days rather than one search window, run it on a scheduled basis and compare to the previous run.

Splunk SPL
index=dns sourcetype=zeek:dns qtype_name="NS" rcode_name="NOERROR"
| mvexpand answers
| stats dc(answers) AS distinct_ns values(answers) AS ns_seen dc(id.orig_h) AS asking_clients by query
| where distinct_ns > 2
| sort - distinct_ns

Assumptions: Zeek DNS logs in index=dns with sourcetype=zeek:dns; for NS queries the answers field holds the name-server hostnames, so mvexpand plus dc(answers) counts the distinct NS values seen per name.

Rule 5 — retries against a blocked or dead domain. Dwell detection for threat 1: after a takedown or a resolver block, infected hosts keep asking. Their failed answers pile up per client.

YAML · Sigma
title: Client Keeps Querying a Blocked or Dead Flux Domain
id: e2d7a8b3-1f46-4c59-9e3a-8d2b6c4f7a1c
status: experimental
description: >-
    After a takedown or a resolver block, infected hosts keep trying to reach
    the same name. Those retries come back as REFUSED or NXDOMAIN answers. A
    client that collects more than 20 such answers within one hour asked for
    the name before it died and is probably still running the malware. Review
    the queried names on the client and hunt for the same name in older logs.
references:
    - https://attack.mitre.org/techniques/T1568/001/
    - Takedown case studies describing post-sinkhole retry behavior
author: SOC Detection Engineering
date: 2025-11-18
logsource:
    category: dns
    product: zeek
detection:
    selection_refused:
        rcode_name: 'REFUSED'
    selection_nx:
        rcode_name: 'NXDOMAIN'
    condition: 1 of selection_* | count() by id.orig_h > 20
fields:
    - id.orig_h
    - query
    - rcode_name
falsepositives:
    - Typos and retired internal names queried by scripts
    - Software that retries expired vendor domains in a loop
level: medium
tags:
    - attack.t1568.001
    - attack.tactic.command_and_control

The SPL adds the distinct-name count on purpose: a client failing on 40 different names is a typo machine; a client failing on one name 40 times is a beacon.

Splunk SPL
index=dns sourcetype=zeek:dns (rcode_name="REFUSED" OR rcode_name="NXDOMAIN")
| bin _time span=1h
| stats count AS failed_answers dc(query) AS distinct_names values(query) AS example_names by _time, id.orig_h
| where failed_answers > 20
| sort - failed_answers

Assumptions: Zeek DNS logs in index=dns with sourcetype=zeek:dns. Some resolvers answer blocked names with a sinkhole address instead of REFUSED — if yours does, add a filter for your sinkhole IP in the first line.

Rule 6 — answers spanning many ASNs (enriched). The strongest single signal for threats 1–4. It needs one enrichment step: a lookup that maps each answer IP to its ASN and network owner, refreshed weekly from a free or commercial IP-to-ASN source.

YAML · Sigma
title: DNS Answer Set Spans Many Autonomous Systems (Fast Flux Enriched)
id: b6f3c259-4d71-4e8a-a57d-1c9b8e2f3a6d
status: experimental
description: >-
    Requires an enrichment step. A lookup table maps each answer IP to its
    autonomous system number (ASN) and network owner before the rule runs. The
    rule then fires when one DNS name returns addresses from more than four
    different ASNs within one hour. This is one of the strongest fast flux
    signals and separates flux from most single-provider content delivery
    networks. Fields answer_asn and answer_asn_org are produced by the lookup.
references:
    - https://attack.mitre.org/techniques/T1568/001/
    - Fast flux detection studies based on ASN dispersion
author: SOC Detection Engineering
date: 2025-11-20
logsource:
    category: dns
    product: zeek
detection:
    selection:
        rcode_name: 'NOERROR'
    condition: selection | count(distinct answer_asn) by query > 4
    timeframe: 1h
fields:
    - query
    - answers
    - answer_asn
    - answer_asn_org
falsepositives:
    - Multi-cloud load balancers that publish answers from several providers
level: high
tags:
    - attack.t1568.001
    - attack.tactic.command_and_control

The SPL performs the enrichment inline with a lookup, so the rule logic and the join live in one place.

Splunk SPL
index=dns sourcetype=zeek:dns rcode_name="NOERROR"
| mvexpand answers
| lookup asn_lookup ip AS answers OUTPUT asn AS answer_asn, org AS answer_asn_org
| bin _time span=1h
| stats dc(answer_asn) AS distinct_asns values(answer_asn_org) AS network_owners by _time, query
| where distinct_asns > 4
| sort - distinct_asns

Assumptions: Zeek DNS logs in index=dns with sourcetype=zeek:dns. The lookup table file has the columns ip, asn, org and is published in Splunk as asn_lookup. Build it from a free IP-to-ASN feed (for example route data published by regional registries) and refresh it weekly. Tune the threshold of five ASNs after a week of observation.

Tuning tip

Rules 1 and 6 fire together on real flux and rarely on the same CDN. If rule 1 alone is noisy, require both: keep rule 1 as a hunting query and alert only on the enriched pair. Re-check the rules after every change to your resolver or sensor.

Real-world case study

The Storm botnet is the classic fast flux case. Everything below follows public reporting; estimates differ between sources, so treat the numbers as rough sizes, not exact facts. The final part translates the story into what it would mean for one enterprise today.

Storm botnet (2007–2008), as publicly reported

  1. January 2007

    Massive spam waves carry links to fluxed domains. Recipients who click pull the Storm loader from infrastructure that public reporting describes as rotating across many compromised hosts.

  2. Mid 2007

    Researchers watching passive DNS notice single names mapping to dozens of addresses across many networks — the first wide public documentation of fast flux at scale. Estimates of the infected host count range widely, from hundreds of thousands to millions.

  3. September 2007

    After researchers publish analyses, the botnet attacks several research organizations and security vendors — a public example of the cost of attracting operator attention.

  4. 2007–2008

    Defenders and providers map the flux infrastructure, sinkhole individual hosts, and pressure registrars and upstream hosters. Each action dents the botnet; none stops it, because records keep rotating. This is the core lesson: the name kept working after every IP-based response failed.

  5. 2008 onward

    Storm fades after sustained pressure and internal changes, but the playbook survives: later botnets such as Kelihos reuse fast flux behavior, and the 2016 Avalanche action shows the same takedown problems at larger scale.

Attack chain (as reported)

  1. Spam delivers the lure link to a fluxed domain.
  2. DNS hands out a live relay IP with a short TTL.
  3. The relay serves the loader; the payload installs.
  4. The infected host joins the relay pool and the cycle grows.

Detection point (what would catch it today)

The passive DNS view — one name, many addresses, low TTL — was visible from day one. Rules 1 and 6 in section 5.5 fire on exactly that pattern, weeks before any host-based tool sees the malware.

If a Storm-style campaign hit one enterprise today

  • Containment. Block the domain at the recursive resolver (not the IPs), force the resolver path so endpoints cannot bypass it, and isolate hosts that already resolved and connected.
  • Eradication. Reimage beaconing endpoints from the retro hunt list, revoke credentials typed into phishing pages, and sweep for the loader family.
  • Recovery. Restore isolated hosts from known-good images, unblock the domain only after the takedown is confirmed, and keep a watch rule on the name for six months.
  • Communication. Tell the helpdesk what users will see, brief leadership with the dwell-time estimate, and report the domain to the registrar and your ISAC.

Impact and consequences (as reported)

Public estimates put Storm's infected host count in the hundreds of thousands or higher, and the botnet's output — spam, phishing, and rented attack capacity — ran for almost two years. The direct consequences for victims included stolen credentials from flux-hosted phishing pages, malware installs served from the same relays, and reputational damage for networks that unknowingly hosted relays. The lasting consequence for defenders was strategic: the campaign proved that name-based blocking and coordinated registrar action beat address-based blocking, which shaped how flux is handled today.

Lesson 1

Passive DNS was the decisive dataset in 2007 and still is. Fund it before you need it.

Lesson 2

Taking down IP addresses alone does not work against flux. Coordinate with registrars and upstream providers — that is what finally worked.

Lesson 3

Public analysis provoked retaliation in 2007. Plan communications and monitoring posture before publishing anything about "your" botnet.

7

Mitigation and defense

You cannot patch DNS abuse away, but you can remove the easy paths and make the churn visible. The controls below are grouped by area; the table at the end sorts them by effort and payoff.

Policy

Write one page that says: all endpoints use corporate resolvers, DNS logging is retained for at least 90 days, and confirmed flux domains are blocked by name with a documented exception path. Policy turns the technical steps into an obligation someone owns.

Endpoint

Run EDR (endpoint detection and response) on every client and server. Flux nodes are ordinary machines running proxy malware — EDR rules for unexpected proxy or listening services shrink the bot pool your users would otherwise feed.

Network

Force all outbound DNS through your resolvers: block UDP/TCP 53 and DoT/DoH endpoints except approved ones. Without egress control, malware picks any public resolver and your visibility dies.

DNS service

Run your own recursive resolvers. Enable response policy zones (RPZ — a feed format that returns a "blocked" answer for listed names) with a reputable flux/malware feed. Validate with DNSSEC where the zone supports it, and log every query and answer, including TTLs.

Logging and monitoring

Ship Zeek or Suricata DNS records into your SIEM, keep raw logs searchable for 90 days, and deploy the six rules from section 5.5. Add a passive DNS subscription or run an open collector at your egress — stored DNS history is the most important tool here.

Backup and recovery

Keep offline, tested backups. Flux-delivered ransomware often stages its encryption step over the same resilient channel, so a clean backup is the one lever that survives a missed detection.

Response

Prepare the playbook now: block by name, retro hunt 90 days, isolate beaconing hosts, revoke exposed credentials, report to registrar and ISAC. Rehearse it once a year with the dns.log example from section 5.4 as the exercise input.

Cloud and mail

Apply the same resolver policy to cloud workloads and VPCs — fluxed domains reach servers too. On the mail side, use gateway URL rewriting and detonation so links to fluxed domains are checked at click time, not only at delivery time.

Identity

Because flux serves phishing, phishing-resistant multi-factor authentication (a hardware key or passkey) and number matching in approval prompts greatly reduce the chance that a stolen password alone is enough to break in.

Home and small office

  • Switch your router's DNS to a reputable filtering resolver that blocks malware and phishing domains.
  • Keep router firmware and device systems updated — flux bot pools are built from unpatched home devices.
  • Be suspicious of urgent links in mail and messages, even when the page looks perfect; check the domain name character by character.
  • If a site you use suddenly behaves oddly, search the exact domain name plus the word "scam" — fluxed phishing domains get reported quickly.

Response checklist

  • Capture the exact domain and the alert context (rule, client, time).
  • Confirm it is not your own zone, a partner, or a known CDN.
  • Pull passive DNS history: distinct IPs, ASNs, countries, TTL range, first seen.
  • Check RDAP/WHOIS: creation date, registrar, registrant country.
  • Decide: flux confirmed or not — write the one-line justification.
  • Block the domain at the resolver via RPZ or blocklist; record the change ticket.
  • Retro hunt 90 days: every client that resolved or connected to the name.
  • Isolate and reimage hosts that show beacon patterns; reset exposed credentials.
  • Report the domain to the registrar, upstream provider, and your ISAC.
  • Schedule a 30/90-day re-check of the blocked name and close with lessons learned.
