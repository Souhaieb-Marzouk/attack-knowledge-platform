DNS Calculation T1568.003

Some malware hides its command-and-control instructions inside ordinary DNS answers. The answer looks harmless, but the malware uses it as a recipe: the numbers inside the answer tell it which IP address and — crucially — which port to call next. This guide explains the trick in plain language and shows you how to detect it.

Overview

DNS Calculation is a stealth trick that turns harmless-looking DNS answers into instructions. This section explains what that means, why it is hard to block, and what you will learn on this page.

What is DNS Calculation, in plain language?

DNS is the internet’s phone book. When a computer wants to reach a website, it asks a DNS resolver (a helper server) to look up a name such as example.com. The resolver asks the authoritative name server — the server that owns that name — and returns the answer.

With this technique (MITRE ATT&CK T1568.003, part of parent technique T1568 Dynamic Resolution), malware does math on the address inside a DNS answer. The attacker owns a domain; whenever the malware asks for it, the answer contains an IP address the attacker chose. The malware does not simply connect to that address on a normal port. It uses the numbers inside the answer — the four octets (the number groups an IP address is made of) — to calculate the port for the command-and-control channel. MITRE's recorded example, the APT12 actor, multiplied the first two octets and added the third to get the port.

Worked example: the DNS answer says 45.77.12.88. The malware computes 45 × 77 + 12 = 3477 and connects to 45.77.12.88:3477. The DNS answer itself looks boring; the real channel hides in the port number that only the malware knows how to compute.

Why it matters to defenders

Most networks control outbound traffic with egress filtering — rules that say which destination ports a client may use. Attackers evade those rules with this technique:

  • The port is never fixed. A blocklist of known C2 ports is useless when the port changes with every DNS answer.
  • The port can look harmless — a high, random port that rules allow because it is “just a reply port”.
  • The DNS answer itself looks boring, so DNS-only monitoring sees nothing wrong.
  • ATT&CK notes the calculation can change the IP address as well as the port, and that malware often uses it as a fallback channel when the main C2 dies.

The defense is a join: pair each DNS answer with the connection that follows it. If the connection's port is a function of the answer's octets, you have found the technique. The rules in section 5.5 do exactly that.

Where it sits in the attack chain

Attackers need a foothold first. After malware lands (initial access, execution, persistence), the implant must talk to its operator. DNS Calculation builds that link even when egress rules block every known C2 port:

Written story (screen-reader and no-JS version)

  1. Step 1 — The implant needs orders. Malware on the victim laptop wakes up. Its main command-and-control address is blocked by the company’s egress firewall, so it falls back to a hardcoded attacker domain, update-svc.c2tld[.]com. Nothing has crossed the network yet.
  2. Step 2 — The DNS question leaves the host. The implant asks the company resolver for the A record of that domain. The query looks completely ordinary — a normal name, a normal record type. The resolver logs it and forwards it, because the name is unknown.
  3. Step 3 — The attacker’s name server answers. The attacker owns the domain and answers with a crafted IP address, 45.77.12.88, and a TTL of 300 seconds. The answer looks like a boring hosting address. It is not: the attacker chose those numbers on purpose.
  4. Step 4 — The implant computes the port. The malware takes the first three octets of the answer — 45, 77 and 12 — and computes 45 × 77 + 12 = 3477, the APT12-style formula from MITRE’s example. Nothing is on the wire yet; the port exists only inside the implant.
  5. Step 5 — Connect on the derived port. The implant connects to 45.77.12.88 on port 3477. The egress firewall allows it, because high ports are “just reply traffic”. The command-and-control session opens.
  6. Step 6 — Tasking over the hidden channel. The implant fetches orders and reports results over the derived-port session. Small, regular transfers — exactly like any quiet management channel, and invisible to port-based blocking.
  7. Step 7 — The port keeps changing. On the next check-in the attacker changes the answer to 91.204.16.5, so the new port is 91 × 204 + 16 = 18580. No static blocklist can keep up: the port is different after every answer.
  8. Step 8 — The SOC correlates DNS and connections. The SOC joins Sysmon Event 22 (DNS query) with Event 3 (network connection) per process and finds the pattern: each connection’s port equals a function of the answer’s octets. The team blocks the domain and hunts every host that shows the same pair.

Why the port math is clever

An IP address is four numbers, and every number is a free input for the formula. The attacker picks the answer, so they control the port: change one octet and the port moves. Port-based egress rules — “block 4444, block 6667” — can never catch up, because the next port is not configured anywhere until the DNS answer arrives. The channel also survives cache expiry: a fresh answer means a fresh port.

What the simulation leaves out

Real implementations vary the formula (subtract, XOR, or use different octets), sometimes derive the IP address too, and may split big numbers across several answers. Older ATT&CK text and vendor reports describe related variants where the server IP itself is encoded into queried subdomains — treat those as vendor-reported variants, not the MITRE definition. The detection idea in section 5.5 works for any formula: pair the DNS answer with the connection that follows and test the arithmetic.

3

Red team / hacker perspective

Understanding why attackers pick this technique — and where they get it wrong — is the fastest route to good detections. This section explains the mechanics, shows tiny lab-safe examples, and lists the mistakes that make the derived port visible. Everything here is for authorized defense testing in your own lab.

Ethics first

DNS Calculation knowledge is dual-use. Building a derived-port channel against a network you do not own is illegal in most countries and against every professional code of conduct. Use the examples below only inside an isolated lab (for example, two virtual machines on a private network with no internet access), and only to build and test detections for your own organization.

When attackers choose DNS Calculation

  • Egress filtering. The firewall blocks every known C2 port. A port that is computed at run time is not on any blocklist.
  • Port-flexible networks. Many firewalls allow all high outbound ports and inspect only web traffic. The derived port rides that gap.
  • Long dwell time. A quiet session on an unremarkable port can hide for months when nobody joins DNS logs with connection logs.
  • Backup channel. Malware tries HTTPS C2 first and falls back to a calculated port when the primary line is cut — MITRE explicitly notes this fallback use.

What the attacker needs

  • A domain they control. Registered (cheap, often stolen or abused) with an authoritative name server set to the attacker’s host. ATT&CK tracks that setup step as T1584.002 Compromise Infrastructure: Domain.
  • An implant on one host. It must parse the DNS answer, run the port math, and open an arbitrary outbound connection — no admin rights needed.
  • Outbound port freedom. The egress rules must allow the computed port — which is precisely why high, “random-looking” ports are chosen.
  • A listener ready on that port. The C2 server must open the matching port before the implant calls, or the session fails and the implant retries with a fresh answer.

How the port is actually calculated

An IPv4 answer gives the implant four numbers to work with, and each one is between 0 and 255. The formula can be anything the implant and the name server agree on — MITRE’s recorded example (APT12) multiplies the first two octets and adds the third:

  • APT12-style: port = octet1 × octet2 + octet3. For 45.77.12.88 that is 45 × 77 + 12 = 3477.
  • Other shapes: subtraction, XOR of octets, or octet3 × 256 + octet4 to map two octets directly onto the 0–65535 port range.
  • IP derived too: ATT&CK notes the calculation can pick the address as well as the port, for example by combining octets from several answers.

The attacker also chooses the answer TTL. A long TTL keeps one port stable per host (quiet, cache-friendly); a short TTL rotates ports quickly (harder to block). Either way, the pair “this DNS answer → this connection” is what the defender finally sees.

Lab only

The commands below are safe, tiny demos for an isolated lab network. They compute ports from fake answers and query a name server that you own on a private address. They never touch a real domain and never communicate with any real attacker infrastructure.

Python · port-derivation demo
# Lab only: show how answer octets become a C2 port (APT12 formula)
answer = "45.77.12.88"
o1, o2, o3, _ = [int(x) for x in answer.split(".")]
print(o1 * o2 + o3)          # 3477

answer2 = "91.204.16.5"
o1, o2, o3, _ = [int(x) for x in answer2.split(".")]
print(o1 * o2 + o3)          # 18580

What this shows: the same formula turns two different answers into two different ports. A defender who suspects this technique runs exactly this arithmetic offline, comparing each DNS answer with the connection that followed it.

Config · dnsmasq lab server
# Lab only - dnsmasq on an isolated VM network (10.10.10.0/24).
# It answers one fixed lab address so you can study the answer-to-connection pair.
address=/lab.c2tld.test/10.10.10.10
host-record=ns1.c2tld.test,10.10.10.53
log-queries

What this shows: a name server that always answers with the same crafted address stands in for the attacker. Change the address in the config and the “derived port” changes with it — that coupling is the whole technique.

Shell · lab queries
# Lab only - ask your own lab name server, then check what a sensor would see
answer=$(dig +short @10.10.10.53 -p 5353 A lab.c2tld.test)
echo "answer: $Dig"
tcpdump -ni eth0 -l 'port 53 or host 10.10.10.10' | head -20

What this shows: the DNS exchange is plaintext, so the sensor records both the question and the answer. Pairing that answer with the next connection record is the detection idea behind every rule in section 5.5.

Mistakes derived-port operators make (and the signal each one leaves)

  • Reusing one answer too long. A stable answer means a stable port — one blocklist entry kills the channel. Rotation creates the many-ports-one-process signal used in detection 3 below.
  • A predictable formula. Once defenders recover one answer-to-port pair, they can test every future pair offline. Weak formulas repeat across campaigns and end up in vendor tools.
  • Forgetting the listener. If the C2 server is not listening on the computed port, the implant retries loudly — connection attempts in bursts to sequential or repeated odd ports.
  • Port collisions. The computed port may land on a legitimate service on the target host, breaking the session. That failure pattern itself is visible.
  • Testing via big public resolvers. Queries to large public resolvers are logged heavily and feed passive-DNS datasets, which is how researchers notice the attacker domain in the first place.
4

Blue team / SOC perspective

Defenders cannot stop DNS — but they can pair it with everything else. This section shows the artifacts the technique leaves, the exact log sources that record them, why the technique is worth your time, and a practical triage flow you can follow when an alert fires.

Artifact: the answer→connection pair

The defining trace: a DNS answer for an attacker-owned domain, followed within seconds by a connection to that answer’s IP. Either event alone is boring; the pair is the technique.

Artifact: odd derived port

The connection lands on a port that is not in the known-good list for that process — often a high port such as 3477 or 18580. Process context (Sysmon Event 3) makes this checkable.

Artifact: ports that change

Same process, same domain, different ports after every answer. That rotation is impossible for honest software, which uses fixed service ports, and it defeats static port blocklists.

Artifact: beacon rhythm

The implant checks in on a schedule — resolve, compute, connect. Look for a host where a query to one domain is followed by a connection, over and over at steady intervals.

Artifact: odd answers

A records that point to hosting ranges your business never talks to, served by one young, attacker-controlled name server. Answers are the attacker’s only lever, so they stand out.

Artifact: NXDOMAIN storms

After you block the domain, the implant keeps asking. A burst of failed answers for one name from one host tells you exactly where the implant lives.

Why it matters so much

A working derived-port channel means an attacker has interactive control of a host through a path your egress rules were never built to catch. You can block every known C2 port and still miss it, because the port is computed after the DNS answer arrives. The pair-based detection in section 5.5 closes that gap with logs you already collect.

Attack-chain context

Expect DNS Calculation after execution and persistence, not before. The implant already runs; it is choosing a way home. Pair this technique with its neighbors:

  • T1071.004 — DNS used as an application protocol (plain beacons).
  • T1568 — dynamic resolution (fast flux, DGAs, DNS calculation).
  • T1048.003 — the same channel used to send data out.
  • T1584.002 — how the attacker prepared the domain and name server.

Triage flow when the pattern appears

  1. Confirm the source. Map the client IP to a hostname and user. One host is an incident; many hosts at once is more likely a tool or a false positive.
  2. Pull the full session. Export every query and answer for that host and domain for the last 7–30 days. Note volume, record types, and timing.
  3. Score the domain. Check registration date, name server, and passive-DNS history. A domain registered days ago with a single name server is a strong sign.
  4. Try the arithmetic (offline). Take each answer and the connection that followed it, and test the common formulas: o1 × o2 + o3, subtraction, XOR, o3 × 256 + o4. A match confirms the technique; vendor reports for similar families help you pick candidate formulas first.
  5. Identify the process. Ask your EDR which process made the queries (Sysmon EID 22 gives the image path on Windows).
  6. Contain. Isolate the host from the network; keep the process evidence alive if you can do it safely.
  7. Block at the resolver. Sinkhole or NXDOMAIN the domain. Watch which other clients keep asking — they are siblings worth investigating.
  8. Report and tune. Save the Sigma/SPL hit, the decoded payload, and the host list. Add the domain to your blocklist feeds and tighten thresholds that caused noise.
Good news

The technique must pair a DNS answer with a connection that follows it — that is the only way the implant learns the port. Pairs are easy to compute from logs you already collect, and the arithmetic turns “suspicious” into “proven” in one offline check.

5.2 Threat intelligence

Threat intelligence turns your detection from a guess into a ranked decision. For DNS Calculation, three layers matter: authoritative technique data (MITRE ATT&CK), vendor and researcher reporting about real malware families, and your own telemetry, which beats every external source for what is normal in your network.

What public reporting says (hedged)

  • APT12 is the official example. MITRE's T1568.003 page records that APT12 used multiple variants of DNS Calculation, including multiplying the first two octets of a DNS answer IP and adding the third octet to get the resulting command-and-control port. This is the anchor fact for the technique.
  • Vendor reporting from 2018 described the FlawedAmmyy and FlawedGrace families using DNS in a related way, with parts of server addresses worked into the DNS traffic. Treat those as vendor-reported variants of dynamic resolution — not the MITRE definition of this sub-technique.
  • Cobalt Strike, a commercial penetration-testing framework frequently abused by intrusion crews, ships DNS and DNS6 beaconing as a built-in capability. That is tunneling-style C2 (related technique T1071.004), but its traffic also exercises the same DNS-to-connection pairing this page detects.
  • Open-source tunneling tools such as dnscat2 and iodine are standard in authorized red-team kits; their lab traffic is a useful false-positive baseline for your rules.

Public reporting changes over time. Treat each item as a lead to verify against the original source, not as a settled fact.

How to use each intelligence layer

  • ATT&CK (T1568.003): defines the technique scope and its detection strategy (DET0262) — use it to design coverage, not to chase specific attackers.
  • Vendor reporting: gives you real formulas, families, and domains to build retro-hunts with.
  • Commercial feeds: supply daily lists of newly observed domains and name servers to intersect with your resolver logs.
  • ISACs: sector peers share attacker domains and answer-IP ranges that hit you both.
  • Internal telemetry: your own baseline of DNS-answer-to-connection pairs decides where thresholds belong. No external feed can do that.

ATT&CK's own detection strategy (DET0262)

The official page groups its detection advice as analytics AN0728–AN0731: monitor DNS query results where subsequent connections use derived or unusual port numbers not explicitly resolved, and correlate Sysmon Event ID 22 with process creation and socket activity (AN0728); inspect resolver and Linux audit logs for processes initiating connections to ports calculated from DNS response IPs, watching for abnormal ephemeral-port usage shortly after DNS queries (AN0729); on macOS, use unified logs to detect unusual DNS responses correlated with subsequent connections to calculated or non-standard ports (AN0730); on ESXi, analyze syslogs for management agents or VMs making outbound connections to dynamically calculated ports derived from DNS responses (AN0731). The Sigma rules in section 5.5 implement this correlation.

1 · Ransomware fallback channel Critical

Justification: Modern ransomware keeps backup command channels for the moment defenders cut the main line. A calculated port is exactly the kind of fallback public reporting describes, because it defeats the port blocklists most victims install first. Consequence plus likelihood puts it at the top.

2 · Management-plane C2 High

Justification: ESXi hosts and management agents are allowed broad outbound access and are rarely monitored with DNS-to-connection correlation. ATT&CK's own ESXi analytic (AN0731) exists because this is a real gap; control of the hypervisor outweighs most endpoint losses.

3 · Linux server reconnection High

Justification: Servers hold credentials, keys, and data, and often lack endpoint agents. A backdoor that re-resolves and reconnects on a computed port survives cleanup attempts that only block fixed ports.

4 · macOS check-ins Medium

Justification: macOS fleets often lack DNS process attribution, so the pair survives longer. Impact is limited by what the implant does, but dwell time pushes it above pure noise.

5 · Unmanaged devices on the wire Medium

Justification: IoT cannot run agents, so network detection is the only detection. Individually low value, but an attacker who controls a camera can reach other systems on the same network.

6 · Benign tests and tools Low

Justification: Security scanners, sanctioned pen tests, and proof-of-concept tools generate real derived-port traffic. Harm is indirect — noise and fatigue — but ignoring it wastes the value of detections 1–5.

{"ts":1768384364.108,"uid":"Cwr7vX2abCdEEF5h3","id.orig_h":"10.20.4.31","id.orig_p":53411,"id.resp_h":"10.20.0.10","id.resp_p":53,"proto":"udp","trans_id":41002,"rtt":0.043,"query":"update-svc.c2tld.com","qclass":1,"qclass_name":"C_INTERNET","qtype":1,"qtype_name":"A","rcode":0,"rcode_name":"NOERROR","AA":true,"answers":["45.77.12.88"],"TTLs":[300.0],"Z":1}

Reading it: the name looks boring, the record type is a plain A, and the TTL of 300 seconds is polite. Nothing in this line alone says “attack”. The evidence only appears when you pair the answer with what the client does next.

Zeek conn.log — the connection that followed, nine seconds later. This is the other half of the pair, and the port is the giveaway:

JSON · Zeek conn.log
{"ts":1768384373.552,"uid":"Cwr7vX2abCdEEF5h4","id.orig_h":"10.20.4.31","id.orig_p":49812,"id.resp_h":"45.77.12.88","id.resp_p":3477,"proto":"tcp","service":"-","duration":0.812,"orig_bytes":512,"resp_bytes":1280,"conn_state":"SF","local_orig":false,"local_resp":false}

Reading it: the destination IP equals the DNS answer, and the destination port is 3477 — exactly 45 × 77 + 12. The service field is empty ("-"), meaning the sensor cannot name the protocol — typical for a custom C2 listener. Neither file alone proves anything; together they are conclusive.

Sysmon Event ID 22 + Event ID 3 (Windows) — the endpoint view. Event 22 names the process that asked; Event 3 names the process that connected, and the shared ProcessGuid joins them:

JSON · Sysmon EID 22 + EID 3
{"@timestamp":"2026-01-14T09:12:44.180Z","event":{"code":22,"provider":"Microsoft-Windows-Sysmon"},"host":{"hostname":"FIN-WS-31"},"process":{"pid":6812,"executable":"C:\\Users\\jsmith\\AppData\\Roaming\\msvcrt\\msvcrt.exe","guid":"{A4B2C1D0-1111-2222-3333-444455556666}"},"dns":{"question":{"name":"update-svc.c2tld.com","type":"A"},"results":"type:  5 update-svc.c2tld.com; ::ffff:45.77.12.88;","status":"NOERROR"}}
{"@timestamp":"2026-01-14T09:12:53.552Z","event":{"code":3,"provider":"Microsoft-Windows-Sysmon"},"host":{"hostname":"FIN-WS-31"},"process":{"pid":6812,"executable":"C:\\Users\\jsmith\\AppData\\Roaming\\msvcrt\\msvcrt.exe","guid":"{A4B2C1D0-1111-2222-3333-444455556666}"},"network":{"destination":"45.77.12.88","destination_port":3477,"protocol":"tcp","initiated":"true"}}

Key fields: the same process.guid appears in both events, and Event 3 carries destination_port: 3477 — the arithmetic match that turns two boring events into one strong alert. Note type: 5 in the DNS results means a CNAME was followed before the address; take the last address in the string.

Resolver query log — BIND-style text line, the format many enterprises already ship to their SIEM. It gives you the answer IP when you have no Zeek sensor.

Text · BIND query log
14-Jan-2026 09:12:44.312 queries: info: client @0x7f2a4c015c40 10.20.4.31#53411 (update-svc.c2tld.com): query: update-svc.c2tld.com IN A +E(0)K (10.20.0.10)

The repeating pattern (client, name, record type, resolver) parses with one regex. The +E(0)K marker simply means EDNS was used; ignore it in detections. Note that this line shows only the question — pair it with connection logs or enable answer logging on the resolver.

Detection logic summary

Detections 1 and 2 do the join (DNS answer → connection, then test the port math on Sysmon and Zeek data). Detection 3 catches port rotation (one process, many ports). Detection 4 watches the management plane (ESXi analytics AN0731). Detection 5 catches rhythm (resolve-then-connect cycles). Detection 6 is the content guard for vendor-reported variants that also shape the queried names. Run them all; each covers the others’ blind spots.

5.5 Sigma rules and Splunk SPL

Six complete rules follow, one per detection idea from 5.4. Each rule is given twice: as a Sigma rule (portable YAML that converts to most SIEM query languages) and as a ready-to-run Splunk SPL query that matches the same logic. Detections 1 and 2 are per-event precursors whose Sigma side cannot express the correlation — the SPL carries the full join, exactly as ATT&CK's analytic AN0728 describes; some rules also use numeric value modifiers (|gte, |lte) that pySigma-capable pipelines accept (otherwise filter in SPL as shown). Adjust index names, sourcetypes, and field spellings to your own data before deploying.

Detection 1 — Windows process connects on the port computed from a DNS answer (endpoint join)

YAML · Sigma
title: Windows Process Connects on a High Port to a Fresh DNS Answer IP
id: e3a1c8f2-4b7d-4c95-9a2e-6f1d8b3c5a70
status: stable
description: 'Detects a Windows process opening an outbound TCP connection to a high,
    non-standard destination port. This is the per-event precursor for DNS Calculation
    (T1568.003): the full detection joins Sysmon Event ID 22 (DNS query) with Event
    ID 3 (network connection) on ProcessGuid and tests whether the connection port
    equals a calculation on the answer octets, exactly as the matching SPL below
    implements per the official analytic AN0728.'
references:
    - https://attack.mitre.org/techniques/T1568/003/
author: Detection Engineering Team
date: 2026-09-14
logsource:
    product: windows
    service: sysmon
detection:
    selection:
        EventID: 3
        DestinationPort|gte: 1024
    filter_common:
        DestinationPort:
            - 3389
            - 5985
            - 5986
            - 8530
            - 8531
    filter_private:
        DestinationIp|startswith:
            - '10.'
            - '192.168.'
            - '172.16.'
            - '172.17.'
            - '172.18.'
    condition: selection and not 1 of filter_*
fields:
    - Image
    - DestinationIp
    - DestinationPort
    - ProcessGuid
falsepositives:
    - Software with its own update channel on a custom port
    - Developer tools and authorized red-team tunnels
level: medium
tags:
    - attack.t1568.003
    - attack.tactic.command_and_control

Sigma note: the numeric modifier |gte works in pySigma-capable pipelines; if your converter rejects it, filter the port range in SPL as shown. The Sigma side fires per event; the SPL below adds the arithmetic join that makes the detection conclusive.

Splunk SPL
index=ep_sysmon sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational (EventCode=22 OR EventCode=3)
| eval guid=coalesce(ProcessGuid, process_guid)
| rex field=QueryResults "(?<answer_ip>(?:\d{1,3}\.){3}\d{1,3})(?:;)?$"
| eval octets=split(answer_ip, ".")
| eval calc_port=tonumber(mvindex(octets,0))*tonumber(mvindex(octets,1))+tonumber(mvindex(octets,2))
| sort 0 _time
| streamstats current=f window=1 global=f values(answer_ip) AS prev_answer, values(calc_port) AS prev_port, values(QueryName) AS prev_query BY host, guid
| where EventCode=3 AND DestinationIp=prev_answer AND DestinationPort=prev_port
| stats count AS hits, values(prev_query) AS resolved_names BY host, Image, prev_answer, prev_port
| where hits >= 2

Assumptions: Sysmon arrives as XML in index=ep_sysmon, so fields keep their XML names (QueryResults, DestinationIp, DestinationPort, ProcessGuid). The rex takes the last IPv4 in the answer string, which survives CNAME chains (type: 5 records). The formula shown is the APT12-style o1 × o2 + o3; swap in other candidate formulas as a second search when hunting. The streamstats window=1 pairs each connection with the previous DNS event of the same host and process.

Detection 2 — network join: connection to the answer IP on the octet-derived port

YAML · Sigma
title: Outbound TCP to High Port Outside Private Ranges (Network Precursor)
id: b7d94e21-5c68-4f0a-8d3e-2a9c7f46b1e8
status: stable
description: 'Detects outbound TCP connections to destination ports of 1024 or higher
    that are not aimed at private address space. This is the per-event precursor for
    the network-side DNS Calculation join (T1568.003): the SPL below pairs Zeek
    connection records with the preceding DNS answer and keeps only pairs where the
    destination port equals a calculation on the answer octets, per analytic AN0728.'
references:
    - https://attack.mitre.org/techniques/T1568/003/
author: Detection Engineering Team
date: 2026-09-15
logsource:
    category: network_connection
    product: zeek
    service: conn
detection:
    selection:
        proto: 'tcp'
        id.resp_p|gte: 1024
    filter_private:
        id.resp_h|startswith:
            - '10.'
            - '192.168.'
            - '172.16.'
            - '172.17.'
            - '172.18.'
    condition: selection and not filter_private
fields:
    - id.orig_h
    - id.resp_h
    - id.resp_p
    - service
falsepositives:
    - Business applications on custom high ports (add an allowlist)
    - Cloud agents and backup tools with dynamic endpoints
level: medium
tags:
    - attack.t1568.003
    - attack.tactic.command_and_control

Sigma note: keep the private-range filter in sync with your real address plan. The Sigma side is a high-value precursor; the SPL below carries the proof.

Splunk SPL
index=network sourcetype=zeek:conn id.resp_p>=1024 proto=tcp
| join id.orig_h type=inner
    [ search index=dns sourcetype=zeek:dns qtype_name=A rcode_name=NOERROR earliest=-10m
      | eval answer_ip=mvindex(answers, 0)
      | eval octets=split(answer_ip, ".")
      | eval calc_port=tonumber(mvindex(octets,0))*tonumber(mvindex(octets,1))+tonumber(mvindex(octets,2))
      | fields id.orig_h, answer_ip, calc_port, query ]
| where id.resp_h=answer_ip AND id.resp_p=calc_port
| stats count AS pairs, values(query) AS resolved_names BY id.orig_h, id.resp_h, id.resp_p
| sort - pairs

Assumptions: DNS and connection data share the Zeek field names and the same ten-minute window (earliest=-10m on the subsearch limits the join to fresh answers). The mvindex(answers, 0) takes the first answer — if your data can put a CNAME first, filter for IPv4 answers as in detection 1. Change the formula to hunt other variants.

Detection 3 — one process, one target, many ports (rotation)

YAML · Sigma
title: One Process Connects to the Same IP on Many Different Ports
id: 9c2f6b84-1e37-4d5a-a8c9-7b0e3d5f2c41
status: stable
description: 'Detects a single process that opens outbound connections to one
    destination IP on four or more different destination ports within one hour.
    Honest software uses a small, fixed set of service ports; a derived-port C2
    channel changes its port with every fresh DNS answer (T1568.003).'
references:
    - https://attack.mitre.org/techniques/T1568/003/
author: Detection Engineering Team
date: 2026-09-16
logsource:
    product: windows
    service: sysmon
detection:
    selection:
        EventID: 3
    filter_common:
        DestinationPort:
            - 53
            - 80
            - 123
            - 443
            - 3389
            - 5985
            - 5986
            - 8530
            - 8531
    filter_private:
        DestinationIp|startswith:
            - '10.'
            - '192.168.'
    condition: selection and not 1 of filter_common and not filter_private | count(distinct DestinationPort) by host,Image,DestinationIp >= 4
    timeframe: 1h
fields:
    - Image
    - DestinationIp
    - DestinationPort
falsepositives:
    - Load-tested services and proxy agents that reuse one target on many ports
    - Backup software talking to one storage node over dynamic ports
level: high
tags:
    - attack.t1568.003
    - attack.tactic.command_and_control

Sigma note: the aggregation in the condition needs a Sigma converter that supports count(distinct ...); the SPL below is the safe path.

Splunk SPL
index=ep_sysmon sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=3
| search NOT DestinationIp IN ("10.*", "192.168.*")
| search NOT DestinationPort IN (53, 80, 123, 443, 3389, 5985, 5986, 8530, 8531)
| bucket _time span=1h
| stats dc(DestinationPort) AS distinct_ports, values(DestinationPort) AS ports BY _time, host, Image, DestinationIp
| where distinct_ports >= 4
| sort - distinct_ports

Assumptions: Sysmon XML fields as in detection 1. Extend the common-port list with your own baseline (add one entry per legitimate custom service, with an owner in the comment of your scheduler).

| join id.orig_h type=inner

Assumptions: both sources share the Zeek field names and the same one-hour buckets. A true derived-port channel shows many connections and several ports against one freshly resolved name — the distinct_ports column tells you how fast the port rotates.

Detection 6 — long encoded first label (content guard for vendor-reported variants)

YAML · Sigma
title: Long Encoded First Label in DNS Query (Variant Guard)
id: 349c5305-e96a-4734-8b0b-1812f0186000
status: stable
description: 'Detects DNS queries whose first label is 40 or more Base32, Base64 or
    hex characters. Vendor-reported dynamic-resolution variants (for example the

Real-world case study

The case below is a teaching composite built from public vendor research reporting on commodity banking trojans that used DNS-based command channels (for example, analyses of the ISFB / Ursnif / Gozi family). Host names, timings, and numbers are fictional; the shape of the incident — quiet DNS C2 discovered only after outside research surfaced — matches patterns that researchers have described repeatedly.

Victim

A regional financial-services firm, about 900 staff, with a card-processing segment and a strict egress firewall policy: web proxy plus DNS out, everything else denied.

Attacker

A financially motivated crew distributing a commodity loader with a DNS-based fallback channel, per vendor research reporting on the family.

Dwell time

Nine days from first DNS beacon to containment — and the logs show the channel was fully visible from hour one.

Timeline

  1. Day 0 · 08:41

    A finance-team member opens a résumé-themed document from an external sender and enables macros. The loader runs, copies itself into a user-writable folder, and establishes HTTPS command-and-control over a proxy.

  2. Day 0 · 13:05

    A scheduled egress-policy update blocks the C2 domain. Instead of dying, the implant switches to its built-in fallback: DNS Calculation. It resolves the fallback domain, reads the crafted answer, and reconnects on a port computed from the answer’s octets.

  3. Days 1–9 · continuous

    The channel runs steady resolve-then-connect cycles from three hosts. Each fresh answer brings a different port, so the connection never sits on one blocklisted value. The resolver and firewall logs record everything; the SIEM ingests the logs; nobody joins the two sources, so nobody sees the pair.

  4. Day 9 · 16:20

    Vendor research describing the family’s DNS-based fallback is published, and a sector ISAC shares the fallback domains. The firm’s threat-intel analyst requests a retro-hunt against 30 days of DNS and connection logs.

  5. Day 9 · 18:47

    The retro-hunt joins Sysmon Event 22 with Event 3 per process and tests the arithmetic: three hosts show connections whose port equals o1 × o2 + o3 of the preceding answer — including the card-processing jump host.

  6. Day 10 · 09:00

    Containment: the two workstation hosts are isolated by EDR; the jump host is powered off pending imaging. The resolver starts answering the domain with NXDOMAIN. The implant on one host keeps asking for six more hours — proof of scope.

  7. Day 11

    Eradication: all three hosts are reimaged; credentials used on them are rotated, including the service account the jump host held; the domain and name server are reported for sinkholing.

  8. Day 12–15

    Recovery and verification: restored hosts, re-run of the retro-hunt (zero hits), and deployment of the six detections from section 5 — the same rules that would have caught this on day zero.

Detection point — where it should have happened

The channel produced its defining pair from day zero: a DNS answer followed by a connection whose port matched the answer’s octet arithmetic. Detections 1, 2, or 3 in section 5 fire within the first hour. The gap was not visibility — the logs existed — it was no rule joining DNS answers with connection ports. This is the most common failure mode for this technique.

Impact and consequences

Attackers read cached browser passwords and one shared service account; no confirmed movement into the cardholder segment, though the jump host held access. Costs: 3 reimaged hosts, roughly 120 analyst hours, a 72-hour regulatory notification review (no notification required in the end), and an audit finding for missing covert-channel monitoring — later closed using the mapping in section 5.1.

How the team worked together

  • Intel turned a public write-up into a retro-hunt within two hours.
  • Network forensics reconstructed the full session from resolver and Zeek logs, including the blocked-domain switch-over moment.
  • Endpoint mapped each query and each derived-port connection to the implant binary via Sysmon EID 22 and EID 3.
  • Management gave a single war-room owner and daily updates to legal and communications, which helped the team meet the 72-hour notification deadline correctly.

Lessons learned (as written in the post-incident review)

  • “Allowed” is not the same as “safe”: our egress policy trusted DNS, and the attacker trusted that too.
  • Logs without detections are recordings, not monitoring. Six rules now read what we collected for years.
  • Blocking became a sensor: after the domain was blocked, infected hosts kept asking for it. Those failed answers showed us which hosts were infected.
  • Public research is an early-warning system; subscribe, and pre-build the retro-hunt queries.
7

Mitigation and defense

You cannot turn DNS off, so defense has two goals: make the channel hard to build, and make it impossible to miss when someone builds it anyway. The controls below are grouped by area, followed by a prioritized table for planning.

Policy

  • Write an egress-DNS standard: clients use only internal resolvers; direct outbound 53 is denied by default.
  • Maintain an allowlist for the rare hosts that need external DNS (with owners and expiry).
  • Require security review for any new rule that opens UDP/TCP 53.

Identity

  • Least privilege: service accounts on jump hosts must not also hold admin rights elsewhere. Attackers can do far more damage when one account holds several roles.
  • Rotate credentials exposed on any host that showed derived-port traffic.
  • Watch for impossible-travel and new-device logins right after DNS alerts.

Endpoint

  • Deploy Sysmon (Event ID 22) or EDR DNS telemetry on every Windows and macOS host.
  • Block execution from user-writable paths — the implant in section 5.4 lived in AppData.
  • Patch browsers and mail clients; the loader that starts the chain needs one click.

Network

  • Force all internal DNS through approved resolvers; block everything else on port 53.
  • Run a protective-DNS (RPZ or managed filter) layer on the resolvers.
  • Baseline the destination ports each server process uses; alert on new high ports, and join DNS answers with the connections that follow (detections 1 and 2).

Cloud

  • Turn on DNS query logging for VPCs (for example managed-resolver query logging) and ship it to the SIEM like any other log.
  • Apply the same “one resolver, everything else denied” rule in cloud subnets.
  • Treat serverless and container DNS patterns as first-class telemetry, not noise.

Logging

  • Log every resolver query, with client IP, full name, record type, and rcode.
  • Never sample DNS logs — derived-port channels are low-volume and sampling deletes exactly the events that matter.
  • Retain at least 90 days hot; add passive-DNS storage if you can.

Monitoring

  • Run the six detections from section 5.5 in production, each with a named owner.
  • Add answers (IP, TTL) to monitoring, not only queries — the answer octets are the inputs of the port formula.
  • Alert on blocking anomalies: an NXDOMAIN storm is an infection map.

Response

  • Keep a DNS Calculation playbook: isolate host, block domain at resolver, test the port math offline, hunt siblings.
  • Pre-agree who rotates credentials and who calls legal for notification clocks.
  • Rehearse the playbook twice a year with the lab queries from section 3.

Home and small office

  • Use your router’s or a free protective-DNS service with query filtering.
  • Keep one DNS setting everywhere (router) instead of per-device surprises.
  • Update router firmware; check that management pages are not reachable from guest networks.
  • Back up computers to an offline copy monthly — recovery beats ransom negotiations.

ATT&CK mitigation stance

MITRE currently lists no single enterprise mitigation that prevents this technique outright — which is exactly why the detection path matters. Treat the controls above as layers: the network rules shrink the channel, and the detections make survivors visible.

Daily habits

  • Check that all six detections ran successfully — a silent broken search is worse than an alert.
  • Review new parent domains behind long-label hits for one minute each.
  • Skim NXDOMAIN storms; they are the cheapest early-warning radar you own.

Weekly habits

  • Compare per-host long-label counts against the rolling baseline; investigate outliers.
  • Triage the mute list: retire one noisy filter or add one missing allowlist entry.
  • Spot-check that resolver logs still arrive complete (no sampling, no gaps).

Monthly habits

  • Re-run the lab replay test from section 5.5 and record which detections hit.
  • Review the egress DNS allowlist: remove expired exceptions before auditors find them.
  • Read one new vendor write-up on DNS C2 and turn one idea into a retro-hunt.
Best practice in one line

Collect everything, pair DNS answers with the connections that follow, and let the arithmetic turn suspicion into proof — the pair always repeats, and repetition always loses to patience.

Cheat sheet and quick reference

Everything urgent, on one screen. Print this page (the print styles hide the controls) or keep it open next to your SIEM during triage.

Key facts

Technique
T1568.003 — DNS Calculation (sub-technique of T1568)
Tactic
Command and Control
Platforms
ESXi, Linux, Windows, macOS
Carrier
Crafted A-record answers; the octets carry the recipe for the C2 port
Formula
APT12-style: port = o1 × o2 + o3 — the port is never configured in advance
Giveaway
Connection to the answer IP on a port that equals the octet arithmetic; ports rotate with answers
Best logs
Resolver queries, Zeek dns.log + conn.log, Sysmon EID 22 + EID 3
First response
Isolate host, block domain at resolver, test the port math offline, hunt siblings

Response checklist

  • Confirm the source host and user; one host versus many matters.
  • Export 7–30 days of DNS answers and connection records for that host and domain.
  • Score the parent domain: registration age, name server, passive-DNS history.
  • Test the arithmetic offline: does the connection port equal a formula over the answer octets?
  • Map the query and the connection to a process with Sysmon EID 22 + EID 3 or EDR data.
  • Isolate the host; keep evidence if it is safe to do so.
  • Block the domain (and NS) at the resolver; expect NXDOMAIN storms from infected hosts.
  • Hunt siblings: every client that queried the same NS or domain in 30 days.
  • Rotate exposed credentials; write the timeline; feed the domain to protective DNS.
