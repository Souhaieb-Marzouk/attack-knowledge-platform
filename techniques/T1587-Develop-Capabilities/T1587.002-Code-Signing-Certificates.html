T1587.002 Code Signing Certificates

Attackers do not always break trust. Sometimes they build it themselves. This sub-technique covers adversaries who create their own code signing certificates - usually self-signed, under a fictitious or look-alike company name - so their malware arrives with a publisher string attached. Users and security tools may trust signed code even when they do not know the issuer. The guide walks through the attack life cycle, shows a simulation, and gives defenders the logs, Sigma rules, and Splunk queries that catch the effects.

Overview

A mental model of the sub-technique: what a code signing certificate is, why criminals make their own, and why defenders mostly see the effects, not the creation.

Code signing attaches a digital signature to a program, driver, or installer. The signature carries two claims: who published the file, and proof that the file has not changed since signing. The claim is anchored by a code signing certificate, an identity file that carries the key and name used to sign. A public Certificate Authority (CA) - a company whose job is to check that an applicant is a real, legal organization before it issues anything - is the usual source, but nothing forces one. A self-signed certificate has no CA behind it: the issuer and the subject are the same person, and here that person is the attacker. Users and security tools may trust a signed file more than an unsigned one even when they do not know who issued the certificate or who wrote the code. MITRE's official description says exactly this, and it is the reason a self-made certificate has value.

Attackers want that trust. A signature - even a self-signed one - calms users and tools that check the "signed" box instead of the chain, and some allow rules and inspection tools still skip deep analysis when a file carries a signature. On 64-bit Windows, a kernel driver without a trusted signature will not load at all; attackers close that gap separately, by talking a user into installing their own root certificate (T1553.004) or by stealing a real key. A trusted-looking name also helps phishing: an attachment named InvoiceTool.exe signed by a real-looking company is far more convincing than the same file unsigned.

MITRE ATT&CK records this behavior as T1587.002 - Develop Capabilities: Code Signing Certificates under the Resource Development tactic (TA0042), the PRE stage that happens before an intrusion. The defining behavior is that the attacker creates the certificate. The official page also names the timing: this happens prior to Code Signing (T1553.002), the step where the signature is used. Two patterns cover most cases:

Path A - A self-signed certificate under a fictitious name

  • Invent a company that does not exist, or copy the style of a real software company.
  • Generate a private key and a self-signed certificate with tools such as OpenSSL or PowerShell's New-SelfSignedCertificate, and mark it for code signing.
  • Stamp the fields yourself: common name, organization, validity period, algorithm.
  • Sign every build from your own infrastructure. No CA is ever contacted.

Path B - A self-signed certificate under a spoofed name

  • Pick a real software vendor and copy its name, one character away or exactly.
  • Create the self-signed certificate with that subject, so dialogs show a familiar publisher string.
  • Where the tool or the user accepts the signer string without checking the chain, the malware passes as that vendor.
  • Pair with Install Root Certificate (T1553.004) when the plan needs the full chain trusted.

Related but different - buying or stealing a certificate

Two other ATT&CK techniques cover certificates that already exist: T1588.003 - Obtain Capabilities: Code Signing Certificates (buy one, often through a front company - a fake business that exists only on paper - or steal one) and T1552.004 - Unsecured Credentials: Private Keys (steal the key material). Those paths inherit trust that a real CA or a real vendor built. T1587.002 is cheaper: the attacker is the issuer. This page stays on the creation path and marks the contrast where it changes detection or response.

Honest caveat about detection

The certificate creation happens on the attacker's own machines, far outside your telemetry, so there is rarely a direct alert for the act itself. The official detection analytic for this technique (DET0833) says much of this activity is outside the visibility of the target organization, and it points defenders at two follow-on behaviors: Code Signing (T1553.002) and Install Root Certificate (T1553.004). Defenders detect the effects: a first-seen or self-signed signer on an endpoint, a publisher name that imitates a known vendor, or samples that share one thumbprint. Everything that follows is built around those effects.

Written step-by-step story

The same eight steps in words. Each step names what the attacker does and what a defender could know at that moment.

Step 1

Invent the company identity

The attacker picks a name for the certificate: a company that does not exist, or a real software company copied letter for letter. Nothing is registered anywhere. The identity will exist only inside the certificate file.

Defender view: nothing to detect yet. This step leaves no public record, which is what makes the self-signed path cheap.

Step 2

Generate the key pair

On a machine the attacker controls, a private key and a self-signed code signing certificate are created with standard tools: OpenSSL or PowerShell's New-SelfSignedCertificate. The issuer and the subject are the same attacker. No CA is contacted, so no public log records anything.

Defender view: still invisible. The certificate now exists, but only on attacker infrastructure.

Step 3

Stamp the certificate fields

The attacker chooses what the certificate claims: the subject common name, the organization, the validity period, and the signature algorithm. These fields are the attacker's free choices - and they are exactly the fields the official detection analytic says to analyze later: thumbprint, algorithm, validity period, and common name.

Defender view: these choices become forensic keys. Repeated choices across samples let analysts cluster an attacker's work.

Step 4

Sign the malware

On a build box, the attacker compiles a custom backdoor and signs it with the new certificate. Every future sample now carries the same publisher string, serial number, and thumbprint, even though no CA stands behind any of it.

Defender view: nothing fires yet, but signer data is now attached to every build. It later becomes a pivot key - a detail that links related events together.

Step 5

Victim downloads the file

A user at the target company downloads the signed tool. The system reads the signature and shows a publisher string instead of an anonymous file. The chain may not be trusted, but the name is there, and it looks like a company.

Defender view: EDR and Sysmon record the signer and the file hash, even before execution starts.

Step 6

Trust heuristics lean in

This is the effect the official description names: users and security tools may trust a signed file more than an unsigned one even when they do not know the issuer. Filters score signed files lower, allow rules match on "is signed", and users read the company name and click. If the plan needs full chain trust, a second step installs the attacker's root certificate (T1553.004).

Defender view: public popularity says nothing here. Watch signer rarity inside your own estate instead.

Step 7

Malware calls home

The backdoor beacons - sends regular signals - to its command and control server. The SOC sees one event with three facts: a signature that is present, a signer that has never run here before, and an external connection.

Defender view: rare signer plus external command and control is a high-value alert. This is where the case opens.

Step 8

Block, sweep, share

The SOC blocks the hash and the certificate thumbprint, then sweeps endpoints for every binary signed by that certificate. Samples go to malware repositories, where researchers link new samples by the same certificate fields. For self-signed certificates there is no CA to notify, so sharing indicators is the lever that works.

Defender view: the thumbprint becomes a retro-hunt key across the estate, historical samples, and researcher repositories.

Red Team Perspective

How attackers reason about signatures, what it costs them, and where they slip up. The only hands-on part is a safe lab exercise with a certificate you create yourself.

Why a signature changes the game

A valid signature is one of the few things that changes software trust on every modern operating system at once. The official ATT&CK description states the core effect plainly: users and security tools may trust a signed file more than an unsigned one even when they do not know who issued the certificate or who wrote the code. That one sentence explains why a self-signed certificate - where the attacker is the issuer - is worth anything at all. On Windows, the publisher name appears in the User Account Control dialog and in Microsoft SmartScreen, the warning layer for downloads with no reputation. Antivirus engines rarely trust a signature by itself, but they score signed files lower, sandboxes flag them less, and some inspection tools still skip deep analysis when a signature is present. On 64-bit Windows, kernel drivers must be signed, so without a trusted chain an entire class of kernel tooling is unusable until the attacker installs a root certificate or steals a key. For an attacker, a certificate is not a luxury. It is a multiplier on every later step.

  • Fewer warnings: users see a company name instead of "unknown publisher".
  • Better delivery: mail filters and browsers handle signed downloads more gently.
  • Kernel access: signed drivers can load, which unsigned ones cannot, once the chain is trusted.
  • Faster analysis: analysts may close a ticket early because the file is signed.

Path A: a self-signed certificate under a fictitious name

This is the Patchwork pattern, the official procedure example for this sub-technique. The attacker invents a software company that does not exist, generates a key pair on a machine they control, and issues a self-signed certificate with code signing as the extended key usage. OpenSSL does it in one command; PowerShell does it with New-SelfSignedCertificate -Type CodeSigningCert. The attacker chooses every field: subject, organization, validity window, algorithm. Nothing is sent to a CA, so nothing appears in Certificate Transparency, and there is no application record for anyone to review. The cost is close to zero; the only thing missing is inherited trust, which the attacker replaces with the official trust effect: tools and users treat "signed" as a good sign even when they cannot name the issuer.

Path B: a self-signed certificate under a spoofed name

The same mechanics, aimed at a real vendor. The attacker copies a legitimate software company's name into the subject - sometimes exactly, sometimes one character away - so dialogs and log fields show a familiar publisher string. This pairs naturally with Install Root Certificate (T1553.004): talk one user into installing the attacker's root, and the self-signed chain turns trusted on that machine. It also pairs with expired-certificate tricks (below), where a rolled-back clock makes an old signature look alive. The detection story for both paths is the same: signer rarity, name similarity, and the UntrustedRoot status that a self-created chain produces on a stock host.

Related but different: buying or stealing a real certificate

Two other techniques cover certificates that already exist, and defenders should know the border. T1588.003 - Obtain Capabilities: Code Signing Certificates covers buying or stealing a certificate. The formal buying route uses a front company - a fake business that exists only on paper - assembled in a jurisdiction with fast, cheap incorporation, with documents that pass an Organization Validation (OV) check. OV means the CA confirms that the organization exists and matches registry data; it does not confirm that the directors are honest. Extended Validation (EV) adds deeper legal checks, so fraudsters prefer OV. Public price lists put OV code signing certificates in the low hundreds of dollars per year, which costs little compared with the possible gain. T1552.004 - Private Keys covers the theft route: private keys live on build servers, in code repositories, or inside hardware security modules (HSMs) - tamper-resistant devices that stop keys from leaving. HSM-based keys are hard to steal, but the machines allowed to use them are not always hard to breach, and an attacker inside a build pipeline can simply ask the build system to sign. A stolen key is more dangerous than anything on this page: the signer name is real, the reputation is real, and revocation hurts every legitimate customer of that vendor.

Variations

  • Self-signed trust chain: the attacker creates an own root certificate and talks a user or a script into installing it. That crosses into T1553.004, but the social engineering often starts here.
  • Test-signing abuse: developer test certificates and Windows test-signing mode are meant for labs, but the same tools sign malware, and a leftover test signer on a production host is exactly a rare-signer alert.
  • Expired certificate reuse: an old certificate plus a rolled-back system clock on the victim can make a dead signature look valid. Missing timestamps on old installers make this work more often than it should.
  • Renting a signer: brokers rent signing capacity per build. The attacker keeps clean hands, and the broker becomes a single point of failure shared by several campaigns.

Attacker mistakes that help defenders

  • Reusing one self-signed certificate across campaigns. A single hash pivot leads to every other sample signed by the same certificate.
  • Picking a name too close to a famous vendor. Analysts skim, but automated similarity checks do not.
  • Leaking identity through certificate fields: organization name, address strings, validity choices, and serial numbers stay in every file forever, even after the fake company disappears.
  • Leaving a long validity period and a distinctive algorithm on a self-made certificate, which makes the crafting pattern easy to cluster in malware repositories.

Lab exercise (safe)

Create a self-signed code signing certificate on your own machine, sign a harmless test script with it, and read the signature back. This reproduces exactly what a defender sees in signature fields - and exactly what this sub-technique describes, minus the crime - with zero risk: nothing is sent anywhere, no real CA is contacted, and the certificate never leaves your lab.

PowerShell
# Lab only. Creates a local test certificate. Nothing is sent anywhere.
$cert = New-SelfSignedCertificate `
  -Subject "CN=Lab Test Codesigner" `
  -Type CodeSigningCert `
  -KeyUsage DigitalSignature `
  -CertStoreLocation Cert:\CurrentUser\My `
  -NotAfter (Get-Date).AddDays(30)

# Export a copy so you can inspect the file itself
Export-Certificate -Cert $cert -FilePath C:\labs\test-codesigner.cer
PowerShell
# Create a harmless test file (a text script, not a program)
Set-Content -Path C:\labs\hello.ps1 -Value 'Write-Output "hello from the lab"'

# Sign it with the lab certificate
Set-AuthenticodeSignature -FilePath C:\labs\hello.ps1 `
  -Certificate (Get-ChildItem Cert:\CurrentUser\My -CodeSigningCert)[0]

# Inspect the result the way a defender would
Get-AuthenticodeSignature C:\labs\hello.ps1 |
  Format-List Status, StatusMessage, SignerCertificate
Bash
# Same idea without Windows: a self-signed code signing certificate
openssl req -x509 -newkey rsa:2048 -sha256 -days 30 \
  -keyout lab-codesigner.key -out lab-codesigner.crt \
  -subj "/CN=Lab Test Codesigner/O=Defender Lab" \
  -addext "extendedKeyUsage=codeSigning"

# Show the fields you would meet in a real certificate
openssl x509 -in lab-codesigner.crt -noout -subject -issuer -dates -purpose

While you inspect the output, notice what a detection engineer keys on: the subject name, the issuer, the validity window, and the extended key usage that marks it as a code signing certificate.

Ethics and legality

Never impersonate a real company or a real person, and never request a certificate from a real CA using false documents; that is fraud in most jurisdictions. This lab uses a self-signed certificate that trusts nothing outside your machine. Do not distribute files signed with test keys, and do not upload them to public scan services as if they were samples.

Blue Team / SOC Perspective

What signed malware looks like in your telemetry, which artifacts survive for pivoting, and a triage flow for the alert that matters most: validly signed but first seen.

What the defender actually sees

Sysmon, the Sysinternals logging tool, adds signature fields to process creation, driver load, and image load events (EventID 1, 6, and 7): Signed, Signature, and SignatureStatus. Windows writes its own CodeIntegrity operational log with policy and signing-level events. EDR consoles show the same fields in file and process views. Certificate Transparency (CT) logs are public, append-only records of every certificate issued by public CAs, usually within hours of issuance. None of these sources saw the certificate being created or bought; all of them see the certificate in use. CT matters here as the watch point for the contrast path, where an attacker buys a real certificate under a fake identity (T1588.003).

The strongest defender idea here is signer rarity. Most enterprises have a few hundred signers that account for nearly all executions. A validly signed binary from a signer outside that baseline is a rare event, and rare events are cheap to review. Signer reputation - how widely a publisher is seen, for how long, and from where - is the public mirror of that idea: attackers farm it, so you should not rely on it alone.

Artifacts left behind

  • The signed file itself, with the signature embedded in the binary.
  • The signer name (the subject of the certificate) shown in dialogs and logs.
  • The certificate serial number and SHA-1 thumbprint, stable pivot keys even if names change.
  • The validity window and the timestamp counter-signature, which say when signing happened.
  • The issuing CA name, which routes your abuse report.
  • For your own organization: issuance records that say who asked for which certificate.

Where to look

  • EDR console: signature columns on process and file views, filtered to "valid" plus "first seen".
  • Sysmon EventID 1, 6, and 7 with the signature fields shipped to your SIEM.
  • Windows Event Log: Microsoft-Windows-CodeIntegrity/Operational.
  • Sandbox reports, which record signer metadata during detonation.
  • Public scan databases (VirusTotal-style) for signer usage across the internet.
  • CT log monitors for new certificates that resemble your brand.
  • CA abuse channels, both to report and to learn from disclosed cases.
  • Proxy and download logs, for signed executables entering the estate.

Why it matters: trust is a control

A signature flips default decisions. Allowlists that trust signed code, filters that skip scanning, and humans who skim dialogs all move in the attacker's favor. In the attack chain, T1587.002 sits in Resource Development and feeds Defense Evasion (T1553.002), Execution, and Persistence. The work is PRE-stage, but its effects appear at the victim end, which is exactly where defenders can catch it.

Triage flow: validly signed but first seen

  1. Capture the basics: signer name, thumbprint, file hash, full path, host, and user.
  2. Check internal rarity: how many hosts ran it, how many times, since when (queries in section 5.5).
  3. Check external reputation: does the vendor exist, how old is the domain, does the certificate really cover this product? A CT lookup answers the last one when a real CA issued the certificate.
  4. Detonate a copy - run it in a sandbox, a safe test machine - and watch behavior, not the badge.
  5. Decide: known-good deployment (document it, grow the baseline) or unknown (contain).
  6. Contain: block the hash and the signer at the EDR layer; isolate affected hosts.
  7. Report: if a real CA issued the certificate, send evidence to the CA's abuse address (it is in the certificate details) and share through your ISAC. For a self-signed signer there is no CA to notify, so share the thumbprint and samples through your intel platform instead.
  8. Hunt: search the whole estate and historical samples for the signer name and thumbprint, and sweep endpoints for binaries signed by that certificate.

Attack-chain fit at a glance

PRE stage: the certificate is created (T1587.002) or obtained ready-made (T1588.003). Intrusion stage: the signed binary lands, passes filters, and executes; Defense Evasion (T1553.002) is where the trust subversion lands in the ATT&CK matrix. Your sensors sit at the intrusion end, so point the detections there and feed the answers back into intel (section 5.2).

Common triage questions

  • "The signature is valid, so can I close it?" Only after the signer is known in your baseline or the vendor is confirmed. Valid means the chain holds, nothing more.
  • "The vendor website looks real. Good enough?" Websites are cheap. Confirm the certificate covers this product and check the domain's age.
  • "It only ran once. Still worth a hunt?" Yes. One host is exactly the pattern of a targeted delivery; rarity, not volume, is the signal.
  • "Should I block the signer or the hash?" Hash is precise and immediate; the signer block stops the next build. Do both, in that order.
  • "The signer is self-signed. Is that bad?" On a stock host, a self-created chain shows as UntrustedRoot. It is normal for a few internal tools; anywhere else it is worth a look, because attackers create their own certificates too.

Do not auto-approve signatures

A rule that allows everything with a valid signature is a gap with a friendly name. Keep signature status as one input to the decision, together with signer rarity, reputation, and behavior. The detection engineering section turns that idea into concrete rules.

Official detection analytic - DET0833 / AN1965

ATT&CK's detection analytic for this technique recommends analyzing self-signed code signing certificates for features that may be associated with the adversary or their developers: the thumbprint, the algorithm used, the validity period, and the common name. Malware repositories can identify additional samples from the same adversary and reveal patterns in how the certificates are crafted. The analytic also warns that much of this activity happens outside the visibility of the target organization, so it recommends focusing on the follow-on behaviors: Code Signing (T1553.002) and Install Root Certificate (T1553.004). Broader context, clearly labeled

Public reporting sometimes cites older certificate-abuse cases - stolen vendor keys, certificates bought under false identities - next to this technique. Those are different ATT&CK techniques: T1552.004 (Private Keys) and T1588.003 (Obtain Capabilities: Code Signing Certificates). Keep them in your research, but map them correctly; the Stuxnet case study in section 6 shows why the distinction changes both detection and response.

Intel feedback loop

Run the loop on a calendar, not on inspiration: a monthly collect step, a quarterly review of what it caught, and an owner for every stage. The steps:

  1. Collect: pull signer names, serials, and thumbprints from reports and CT feeds into one table.
  2. Integrate: turn that table into lookups your detections can join against (see 5.5).
  3. Detect: alert on matches and on signers that resemble known-bad names.
  4. Confirm: validate hits with sandbox detonation and CA records before you escalate.
  5. Report back: return confirmed malicious signers to your intel platform and, where possible, to the CA.
  6. Tune: adjust thresholds and filters from what the loop taught you this month.

Five concrete threats cover this sub-technique, drawn from the official technique page and its procedure examples. High Windows / macOS / Linux T1 - Self-signed malware from a rare signer

The attacker creates a self-signed code signing certificate and signs every sample with it. The chain ends at a root no public CA backs, so a stock Windows host shows SignatureStatus UntrustedRoot - but the Signature field still carries a publisher name, and users and tools that score "signed" as good do not ask who issued it.

Detection pointer: first-seen signer plus rarity (few hosts, few executions), and UntrustedRoot status as a second trigger. The queries in 5.5 implement both.

High Windows / macOS T2 - Fictitious or spoofed company names

Patchwork created self-signed certificates from fictitious companies and from companies that imitate legitimate software vendors. One character separates "Acme Software" from "Acme S0ftware". Users and analysts skim names; machines do not.

Detection pointer: similarity rules on the Signature and Company fields for your top vendor names, plus brand-watch on certificate data for the acquisition contrast.

High macOS T3 - Signed macOS payloads

Daggerfly created code signing certificates to sign malicious macOS files. On macOS, the signature authority and team identifier are visible to EDR tools and to codesign; an attacker-made identity has an authority that equals its own subject and no Apple-rooted chain.

Detection pointer: EDR code-signature fields (authority, team identifier, notarized flag) joined to a first-seen baseline; quarantine and Gatekeeper events as secondary signals.

Medium Windows / macOS T4 - Signed installers and cloud/CLI utilities

PROMETHIUM created self-signed certificates to sign malicious installers; during Operation Dream Job, Lazarus Group digitally signed their malware and the dbxcli utility. Installers and utilities are run by hand, so the publisher string does the persuasion.

Detection pointer: signed installers that appear in user download paths with rare signers; signed CLI utilities that run from Temp or by service accounts, where no such tool belongs.

Medium Windows T5 - Test-signing abuse

The same tools that sign driver builds in a lab sign malware. Windows test-signing mode (enabled with bcdedit) accepts driver signatures that no production host should see, and leftover test certificates are exactly the low-prevalence signers that rarity rules catch.

Detection pointer: bcdedit test-signing changes on non-build hosts; driver loads signed by test signers; CodeIntegrity events naming test signatures.

Critical Contrast path Stolen or bought real certificates - a different technique

Not part of T1587.002, but it lands in the same alerts. Stealing a vendor's signing key maps to T1552.004, and buying a certificate under a false identity maps to T1588.003. The signature is real, the name is real, and only the hash is new - which is why the driver rule in 5.5 keys on valid signature plus unknown hash.

Detection pointer: vendor-signed files with unknown hashes; CodeIntegrity blocks; CT and CA records for brand-like organizations. Response differs: here a CA can revoke, where self-signed certificates cannot be revoked at all.

T1 - Self-signed low-prevalence signer: process and download evidence

Log sources: Sysmon EventID 1 (process creation) with signature fields; EDR first-seen tracking; proxy or firewall download records; your approved-signer lookup.

Data quality notes

Three field-level traps waste analyst time. First, Signature and Company are self-reported strings inside the file; only the chain to a trusted root makes them meaningful, so a tampered file can carry any name it likes and still fail - which is why SignatureStatus belongs beside the name in every query. Second, timestamp services fail now and then, so "no timestamp" alone is weak evidence. Third, some installers embed old signed components, so a first-seen signer can appear inside a legitimate suite; rarity rules need the whole-file hash before they accuse. Log all of these fields everywhere, and let correlation, not a single field, carry the verdict.

Retention and cost notes

Signature fields are small and stable, which makes them excellent long-term telemetry. Keep at least one year of Sysmon signature data hot enough to search, because retro hunts after a revocation look backward across months. The CA and CT feeds are cheap to keep forever; their value grows with age, since the gap between issuance and first malware is often weeks. Proxy download records age fastest - archive them with the file hashes included so the download-to-execution join survives rotation.

5.5 Sigma Rules and Splunk SPL

Five Sigma rules with matching Splunk SPL. R3 and R4 are the core rules for this technique: they catch the signed-but-rare and the look-alike effects of self-created certificates. R2 covers the contrast path (a real, validly signed certificate that should not exist), and R1 with R5 watch the acquisition side. The rules assume Sysmon data in the common XmlWinEventLog format; if your pipeline renames fields, adjust the field names first. Keep every rule behind a maintained lookup or filter list - these detections live or die by the quality of the baseline, not by the YAML.

Real-World Case Study

This section teaches the most important distinction on the page: creating your own certificate (T1587.002) versus using a certificate that already exists (T1552.004, T1588.003). Patchwork is the official example of the creation path. Stuxnet is the famous case of the theft path. Comparing them shows why the difference changes detection and response.

Patchwork: self-created certificates under invented names

Patchwork is the group MITRE lists under this sub-technique with a precise entry: the group created self-signed certificates from fictitious and spoofed legitimate software companies, and those certificates were later used to sign malware. Public reporting does not publish a full timeline for the certificate work, so this case study focuses on the pattern, which is the part you can detect and rehearse against.

The pattern has four moves. First, pick a name: invent a software company, or copy a real one closely enough to read as familiar. Second, create the certificate: the attacker generates a key pair and issues a self-signed certificate with code signing usage, choosing every field - common name, organization, validity period, algorithm. Third, sign the malware: each sample now carries a publisher string that dialogs, filters, and analysts see before anything else. Fourth, reuse: the same signer and the same field choices appear across campaigns, which is exactly what turns one sample into a cluster.

Why does a certificate nobody issued fool anyone? Because of the effect the official description states: users and security tools may trust signed code more than unsigned code even when they do not know the issuer. The signature answers "is this signed", and most people and many tools stop there. That is the whole trick, and it is why the low-prevalence-signer rules in section 5.5 matter more than any reputation service.

Response shape for this class: there is no CA to notify and nothing to revoke. The working levers are the thumbprint block, the endpoint sweep for everything signed by that certificate, sample sharing with malware repositories so researchers can cluster the campaign, and the look-alike-name patterns fed back into your detections.

Contrast case - Stuxnet: related but different

Stuxnet's drivers were signed with the stolen private keys of legitimate companies; public reporting links the key material to Realtek and JMicron. That is certificate theft - T1552.004 (Private Keys) feeding T1588.003 (Obtain Capabilities: Code Signing Certificates) - not certificate creation. ATT&CK therefore does not map Stuxnet's signing to T1587.002. The case is kept here because the contrast is the lesson: same warning dialog, different technique, different response.

Aftermath

Trust model rethink

Researchers and vendors rebuild their assumptions: a valid signature becomes a data point, not a verdict, and key protection moves toward hardware modules.

Two attack chains, side by side

  1. Stuxnet (theft path): signing key theft (T1552.004; acquisition of an existing signing identity, T1588.003) put valid signatures on the kernel drivers. This is certificate theft, not certificate creation, so ATT&CK does not map it to T1587.002.
  2. Stuxnet: with signatures accepted, the rootkit components install and hide their files and processes.
  3. Stuxnet: Persistence (T1547 - Boot or Logon Autostart Execution): scheduled tasks and driver autostart entries keep the worm alive across reboots.
  4. Stuxnet: PLC sabotage inside the target network rewrites PLC logic to speed centrifuges up and down while reporting normal operation.
  5. Patchwork (creation path): T1587.002 - self-signed certificates created from fictitious and spoofed legitimate software companies.
  6. Patchwork: T1553.002 - Code Signing: the malware arrives carrying the attacker-made signature.
  7. Patchwork: delivery and execution follow the trust effect: users and tools treat signed code as more credible even when the issuer is unknown.

Detection point

Both cases broke on signature data, in different ways. Stuxnet fell to treating the signature as data instead of as a verdict: researchers pivoted on the certificate thumbprints and signer names and found the same two signers across samples that otherwise looked unrelated. A Patchwork-pattern case falls to the low-prevalence logic this page builds into rules: a signer that appears on one host, once, with a name a character away from a real vendor, and an UntrustedRoot status that no legitimate enterprise tool should produce outside a lab. Log the signature fields and both stories become ordinary alerts.

Containment

For Stuxnet, the two certificates were revoked and revocation lists propagated to clients. Defenders added the certificate thumbprints and driver hashes to blocklists, and network teams cut the propagation paths by restricting removable media and shares. Revocation did not erase installed copies, but it stopped fresh signed builds from being trusted. For a self-created certificate, containment starts one lever earlier: block the hash and the thumbprint at the EDR layer, because there is no CA that can pull the certificate back.

Eradication

Removal meant deleting the worm's files, its scheduled tasks, and its registry autostart entries, then verifying that no hidden driver components remained. Because Stuxnet hid its files from the file system, cleanup used tools that inspected the raw volume and the loaded driver list. The Patchwork-pattern equivalent is a sweep: search every endpoint and every historical sample for the flagged thumbprint and signer name, and remove what the search finds.

Recovery

Engineering systems that had touched the worm were rebuilt from trusted media, and industrial networks were re-segmented so that office-side infections could not reach PLC networks again. Update and maintenance processes were re-verified, since the worm had also abused removable-drive workflows that engineers trusted. In a self-signed case, recovery adds one step: re-check any allow rules that trusted the signer string, and re-baseline the approved-signer list so the fraudulent signer cannot slip back in.

Impact

Stuxnet destroyed roughly 1,000 IR-1 centrifuges and set the enrichment program back by months or more. Beyond the plant, it was the first publicly documented cyber-physical weapon, and it changed security budgets, threat models, and - for this page - the meaning of a digital signature. The Patchwork-pattern impact is quieter but broader: every campaign that reuses a self-made signer keeps a stable, linkable trail, which is exactly what defenders and researchers turn back against the attacker.

Team response and communication

The Stuxnet response crossed many boundaries: the victim organization, the industrial control vendor, antivirus companies, national CERT teams, and intelligence organizations. Public disclosure carried real tension - naming the certificates helped every defender, while full technical detail also informed other attackers. Vendors coordinated on revocation and detection content quickly, and governments kept attribution separate from the defensive disclosures. Plan the communication for a signing incident the same way: who tells the CA (when one exists), who tells customers, who shares indicators, and who talks publicly.

Lessons learned

  • Classify the certificate path first: created (T1587.002), bought (T1588.003), or stolen (T1552.004). The classification decides whether a CA report or a revocation is even possible.
  • A valid signature is not proof of safety; treat it as one field among many.
  • Signing keys are critical infrastructure: protect them in hardware, with least privilege and audit logs.
  • Revocation lists matter only if systems actually check them - and many did not in 2010.
  • Signature metadata is a strong pivot source; log signer names, serials, and thumbprints everywhere.
  • Signed malware forced a rethink of default trust, from "signed means safe" to "rare signer means review".

Could it happen today?

Yes, with changes. Modern Windows enforces revocation more often, browsers ship their own trust stores, and HSM use is standard among large vendors. But the economics did not change: a self-signed certificate costs nothing and takes one command, fraud attempts still reach CAs every month, and small vendors still hold powerful keys behind weak build security. Hardware-protected keys raised the cost of theft, so attackers shifted toward abusing signing services and build agents - the key never leaves, and they never need to copy it. The detection ideas in this page target the constant in all versions: the signature itself, which must appear somewhere you can log it.

Mitigation and Defense

You cannot stop an attacker from creating a certificate or from obtaining one, but you can make the signature worthless inside your estate and protect the keys that matter most - your own.

Official mitigation view - M1056 Pre-compromise

ATT&CK lists one mitigation for this technique: M1056 Pre-compromise, with the note that it cannot be easily mitigated with preventive controls, because the behavior happens outside the scope of enterprise defenses. The creation of a self-signed certificate occurs entirely on attacker infrastructure. The controls below therefore target the follow-on behaviors - Code Signing (T1553.002) and Install Root Certificate (T1553.004) - which is where your estate actually meets the results.

Enterprise controls

First, keep security tools inspecting signed binaries. Configure EDR and antivirus so a valid signature reduces, but never removes, scrutiny. Microsoft SmartScreen reputation is a signal about download volume, not about intent; treat it accordingly. Second, deploy application allowlisting on servers and high-value hosts. Windows Defender Application Control (WDAC) and AppLocker both support publisher rules that trust a specific signer instead of a path. Third, collect the Microsoft-Windows-CodeIntegrity/Operational log everywhere; it records signing-level failures even when an allowlist is in audit mode, which gives you free detection coverage before enforcement. Fourth, block rare signers by default on servers: if a signer has never run there, require a ticket first. Fifth, watch Certificate Transparency for your own brand and report fraud to the issuing CA quickly - CAs revoke fast when the evidence is clean. Finally, verify vendor software signatures during procurement and intake, not only at runtime.

XML
<!-- Abbreviated WDAC publisher rule: trust one signer, any version -->
<FileRule FriendlyName="Trusted vendor ACME"
          MinimumFileVersion="0.0.0.0"
          SignerName="ACME Software Ltd"
          SignerType="Publisher" />

Real WDAC policies are more verbose; this excerpt shows the shape. The principle is what matters: name the signer, not the folder, and keep the trusted-publisher list as small as you can.

Protecting your own signing keys

If your organization ships software, your signing keys are a target, and the Stuxnet lesson applies to you. Keep private keys in a hardware security module (HSM) so they cannot be copied off a disk. Give build agents the narrow right to sign, nothing more, and run signing as a separate service with its own audit log. Alert on signing volume: ten signatures a day is a rhythm, ten thousand is an incident. Test your revocation process before you need it, and rehearse a stolen-key scenario so the first time is not real. Monitor your CA portal logins and your CT records the way you monitor a bank account.

PowerShell
# Before installing vendor software, read its signature yourself
$sig = Get-AuthenticodeSignature -FilePath .\vendor_setup.exe
$sig.Status                        # Valid, HashMismatch, NotSigned, ...
$sig.SignerCertificate.Subject     # who signed it
$sig.SignerCertificate.Thumbprint  # match against the vendor's published value
$sig.TimeStamperCertificate        # was signing time recorded

Home and small office

  • Keep SmartScreen on, and read the publisher line when it appears.
  • Do not click through "unknown publisher" warnings to install something you were not expecting.
  • Turn on automatic updates for the operating system and the browser.
  • Run antivirus and let it inspect downloads, including signed ones.
  • Avoid pirated software: cracks and key generators are the classic delivery path for signed malware.

Working with a vendor after key theft

If a supplier's key is stolen, your response is part of their incident. Ask for the certificate serial numbers and thumbprints involved, block them at your EDR layer, and treat every previously delivered binary from that vendor as unverified until hashes are re-confirmed. Request signed statements about which builds are safe, and add the affected signer to your rare-signer watch list for months, not days. Vendors handle this badly when customers only shout; you get better outcomes with a calm request for the same artifacts you would want for your own incident: serials, thumbprints, validity windows, and a remediation timeline.

Response checklist

  1. Confirm signer name, serial, and thumbprint from the file itself.
  2. Check rarity: hosts, executions, first-seen time across the estate.
  3. Detonate a copy in a sandbox; watch behavior, not the badge.
  4. Block the hash and the signer at EDR; isolate affected hosts.
  5. Sweep endpoints for binaries signed by the flagged certificate thumbprint.
  6. If a CA issued the certificate, report abuse with evidence and serial numbers; for a self-signed signer, share indicators with your intel platform instead.

  8. Add or update detection content (Sigma, SPL) and tune the lookups.

Mini glossary

Code signing certificate
An identity file that lets a publisher attach a verifiable digital signature to software.
Self-signed certificate
A certificate whose issuer is its own subject; the attacker plays the certificate authority. No public CA is involved.
Test signing
A Windows mode that accepts driver signatures from test certificates; meant for development labs, abused by attackers.
Certificate Authority (CA)
A trusted company that checks an applicant's identity and issues certificates.
OV / EV
Organization Validation and Extended Validation: two depth levels of CA identity checks.
SmartScreen
The Windows warning layer for downloads and programs with little or no reputation.
CT log
A public, append-only record of certificates issued by public CAs; watched by monitors.
Sysmon
A Sysinternals tool that logs detailed endpoint events, including signature fields.
Signer reputation
How widely and how long a publisher's signed files have been seen; attackers farm it.
Thumbprint
A short hash of the certificate; stable pivot key even when names change.
HSM
Hardware security module: a tamper-resistant device that protects private keys.
CRL / OCSP
The two standard ways clients learn that a certificate was revoked.
EDR
Endpoint detection and response: the agent and console that watch host activity.

Quick answers

Is a signed file always safe?
No. A signature identifies the publisher and protects integrity; it says nothing about intent. Stuxnet's drivers were perfectly signed, and the malware in the official examples carried self-created signatures.
Can we detect the certificate creation itself?
Almost never directly. The creation happens on attacker machines. Watch the effects: rare signers, self-signed chains, and public CT records for your brand when attackers buy instead of build.
Do we need a PKI team to use these detections?
No. The highest-value rules need only Sysmon signature fields and a maintained signer list.
What single change helps most?
Log signature fields everywhere, then alert on valid or self-signed signatures from first-seen signers with prevalence logic.
Which teams must be involved?
SOC for triage, detection engineering for rules and lookups, endpoint teams for rollout, PKI and legal for revocation and abuse reports when a real CA is involved.
Where do I start this week?
Enable the CodeIntegrity operational log, deploy Sysmon signature fields if missing, and export your first signer inventory.
