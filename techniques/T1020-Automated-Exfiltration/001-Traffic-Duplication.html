T1020.001Traffic Duplication

Traffic duplication turns a network's own copying feature into a hidden tap. An attacker reaches a switch, a router, or a cloud network console. Then they tell the device to copy user traffic and send the copy to them. No implant lands on the victim and no new connection leaves it. Data escapes while host tools see nothing.

Overview

Before you can detect a technique, you need a clear mental picture of it. This section explains traffic duplication in plain words. It shows where the technique sits in an attack. It also lists the facts you will use again later in this guide.

What is it?

Network devices have a built-in diagnostic feature that copies traffic. On a switch it is called a SPAN port or mirror port (SPAN means Switched Port Analyzer). You pick the ports to watch and one output port. The switch then forwards a copy of every packet there. Network teams use this every day to feed monitoring tools and packet analyzers.

T1020.001 is that same feature, abused. An attacker who can change device settings creates a mirror session. That needs access to a switch or router command line, or to a cloud console. The attacker points the session at a server they control. From that moment, a full copy of the chosen traffic flows to the attacker. No user computer is touched.

Cloud platforms offer the same power through APIs: AWS Traffic Mirroring, GCP Packet Mirroring, and Azure vTap. A user defines source instances and a target destination, and the platform does the copying. MITRE also notes that attackers may modify the device software itself. The copying then survives reboots and config rollbacks. Section 3 describes this ROMMONkit path.

Why it matters

  • No endpoint artifact. The victim computer runs nothing and stores nothing. Antivirus and EDR (endpoint detection and response) have nothing to find.
  • No new connection from the victim. Data leaves inside copies of traffic the host already sends. Egress rules — the rules for traffic leaving a network — see only normal flows on the victim segment.
  • It captures everything. One mirror session can cover a whole VLAN (a virtual LAN: a group of ports that acts as one network). That means many hosts at once, including traffic that never leaves the site.
  • It is quiet. Mirroring is a native, legitimate feature. A working tap looks like normal device operation.
  • It defeats host-side DLP. If your data-loss controls live only on computers, mirrored copies pass them by.

Where it fits in the attack chain

ATT&CK places T1020.001 under T1020 Automated Exfiltration, in the Exfiltration tactic (TA0010). A typical chain looks like this:

  1. Initial access — for example phishing a network contractor, as seen in Salt Typhoon reporting.
  2. Management-plane access — the attacker reaches switch, router, or cloud network administration (the management plane is the admin side of devices and clouds).
  3. T1020.001 — a mirror session copies chosen traffic to attacker infrastructure.
  4. Captured data is reassembled off-site; credentials and documents are mined from it.
  5. Quiet long-term espionage follows.

ATT&CK lists this technique as used together with Network Sniffing (T1040), Input Capture (T1056), and Adversary-in-the-Middle (T1557). All three are ways of seeing traffic the attacker should not see.

Written version of the simulation

This is the same story in text form. It covers every step the animation shows, so nothing is lost if you cannot see or play the canvas.

  1. Attacker logs in. With admin credentials stolen from a contractor, the operator reaches the management network and opens the switch CLI. SOC view: a VPN login to the management network from a new autonomous system (ASN), with no change ticket behind it.
  2. A mirror session is created. The attacker adds monitor session 1 on core-sw-01, copying the finance VLAN. SOC view: a config change at 03:12 with no matching ticket, and the session is not in the golden config.
  3. The destination points outward. The mirror target is set to 203.0.113.9, a rented server outside the approved list. SOC view: mirror destination outside the approved list, hosted at an ASN the company never uses.
  4. Users notice nothing. The finance host keeps its normal HTTPS sessions to the application server. SOC view: baseline unchanged — no new processes or destinations, which is exactly the problem.
  5. Every packet is duplicated. The switch sends a second copy of each packet toward the collector. SOC view: twin sessions with identical byte counts to two destinations within 2 seconds.
  6. The collector reassembles sessions. TLS content stays unreadable, but server names, sizes, and timing leak; cleartext protocols give up everything. SOC view: no host-side signal at all — the theft surface covers the whole VLAN.
  7. The pattern continues for weeks. Egress volume doubles, mostly at night, and an early anomaly is dismissed as a backup job. SOC view: egress volume 2.1x baseline at night — a dismissed anomaly that should have been triaged.
  8. The SOC correlates and contains. Config-change alerting and twin-flow analytics meet; the session is removed and the collector is blocked. SOC view: containment works — session removed, credentials rotated, collector blocked at egress and upstream.

Red team / hacker perspective

This section explains why attackers love traffic mirroring and how the machinery works. Everything here is described for defense, education, and safe lab practice. Do not run these ideas against systems you do not own.

When and why an attacker uses it

Mirroring solves three needs at the same time. Reach: one session covers every host on a segment, so the attacker sees traffic from machines they never touched. Stealth: the copying happens inside the switch, so no endpoint process runs and no new connection leaves the victim. Patience: after setup, the tap collects data around the clock while the operator is offline. CISA's September 2025 advisory describes Salt Typhoon enabling traffic mirroring on compromised telecom networks to steal data. A state-sponsored team chose a native feature over custom malware.

It also fits the device-compromise mindset: once you own the network's control plane, the network itself becomes your collection tool.

Mechanism 1: switch SPAN sessions

The classic path. On Cisco-style devices, the attacker enters configuration mode and adds a monitor session. The session copies chosen ports or VLANs to an output interface. Remote variants — RSPAN and ERSPAN — carry the copy across switches to a far destination. One short command block can mirror an entire finance VLAN.

Mechanism 2: Linux tc mirroring

On Linux gateways and routers, the tc traffic-control tool can copy packets with one rule. The rule adds a queueing rule (qdisc) on the incoming side, plus a mirred egress mirror action. No reboot is needed and no file is dropped. The rule disappears on reboot unless the attacker also edits startup scripts.

Mechanism 3: cloud mirror APIs

AWS Traffic Mirroring, GCP Packet Mirroring, and Azure vTap copy traffic between instances through API calls. An attacker with a cloud network role creates a mirror target inside their own VPC (a private, isolated cloud network). One API request is enough. There is no CLI session on any device — only an event in the control-plane log.

Advanced path: modify the device image

Instead of adding a config line, an attacker can change the software the device runs. Bootloaders can be manipulated — security researchers call this tradecraft family ROMMONkit. A bootloader such as ROMMON is the small program that starts a Cisco device. Firmware images can also be patched to embed a hidden mirror; MITRE tracks this path as Patch System Image (T1601.001). The behavior then lives in the image, not the config, so it survives reboots and config rollbacks. The path is rare and hard. Still, public reporting on nation-state device tradecraft shows the intent.

Where it applies and what it needs

  • Places: core and distribution switches, routers, virtualization hosts, cloud VPCs, and ISP or telecom edges — the Salt Typhoon pattern.
  • Preconditions: management-plane access (device CLI, SNMP write, or a cloud network role). The device also needs a route to the collector, and the collector needs enough storage.
  • Collector: a rented server that receives the copies, reassembles sessions, and stores whatever is mined from them.

Practical variations

  • Mirror only what matters: ports or VLANs of high-value systems, to keep copy volume believable.
  • Filter the copy: cloud mirror filters and select-style rules keep only interesting ports and protocols.
  • Tunnel the mirror leg: ERSPAN over GRE or VXLAN (common tunnel wrappers) can hide the copied content in transit to a far-away collector.
  • Limit duration: short off-hours sessions reduce the chance the volume doubling is noticed.

Attacker mistakes

  • Config changes are logged. Device syslog, AAA accounting (AAA means authentication, authorization, and accounting), and cloud API logs record who changed what, from where, and when.
  • The collector betrays them. Mirror destinations resolve to hosting providers in unexpected countries; the ASN stands out.
  • Mirroring everything doubles volume. A careless "mirror all" session shows up as 2x egress, especially at night.
  • Reused infrastructure. The same collector IP seen across victims links incidents together.
Lab only — safe and legal

The commands below are a harmless classroom demo. They create two dummy network interfaces inside one isolated test virtual machine. Then they mirror packets between the two. No real network and no real traffic is involved. Run it only on a Linux test VM you own, and run the cleanup commands afterwards. Using mirroring against systems without written permission is illegal.

lab_tc_mirror.sh — mirror between two dummy interfaces (no real traffic)
# LAB ONLY: isolated test VM with two dummy interfaces. Nothing here touches a
# real network. Mirroring eth1 -> eth2 on a machine you own shows the exact
# mechanics defenders must detect.

sudo ip link add eth1 type dummy
sudo ip link add eth2 type dummy
sudo ip link set eth1 up
sudo ip link set eth2 up

# Mirror every packet arriving on eth1 out of eth2 (classic tc mirred action)
sudo tc qdisc add dev eth1 handle ffff: ingress
sudo tc filter add dev eth1 parent ffff: u32 match u8 0 0 \
     action mirred egress mirror dev eth2

# Observe: any packet that arrives on eth1 is copied to eth2. Generate harmless
# test packets from another local interface, then check the copy:
#   sudo tcpdump -ni eth2 -c 10

# Cleanup (always run):
sudo tc qdisc del dev eth1 ingress
sudo ip link del eth1
sudo ip link del eth2

Blue team / SOC perspective

You will not see this technique on a computer, because nothing happens on a computer. Defense shifts to three other places: device configuration telemetry, cloud control-plane logs, and the shape of network traffic itself.

How defenders can see it

Three telemetry lanes matter. Device config telemetry tells you the tap was installed. Watch config-change syslog, AAA accounting, and daily diffs against a golden config — the approved reference copy of each device's settings. Cloud control-plane logs record every mirror API call together with the identity behind it. Examples are CloudTrail, the Azure Activity Log, and GCP audit logs. Network analytics reveal the result: a second copy of the same traffic leaving to one extra destination. Flow records and Zeek do that job. Any single lane can carry the detection; combining two turns a hunch into a case.

Where to look first

  • Config diffs for network devices: anything in the running config that is not in the golden config.
  • Cloud mirror API events from the last 30 days, filtered by identities outside the network team.
  • Flow analytics for one source talking to two destinations with near-identical byte counts.
  • Egress volume per site against its own baseline, focused on off-hours.
  • Approved-mirror inventory: compare live monitor session output against the documented list.

Why it matters and how it fits the chain

Mirroring is bulk passive theft. There is no malware to quarantine and no single "stolen file" event. The loss is continuous and invisible until you measure it. That makes the exposure window long and the compliance duty heavy. Regulators expect you to know what left, and when.

ATT&CK's detection strategy for this technique is DET0403. It has two analytics. AN1131 watches for configuration changes to virtual TAP or mirror policies that forward traffic to unapproved destinations. The best practice is to correlate each change with the mirrored traffic itself. AN1132 watches for unauthorized mirroring sessions on routers and switches. Think of monitor session or mirror port commands. It pairs them with outbound traffic from the mirrored interface to unexpected destinations.

Short triage flow

  1. Check the device. Pull the running config and diff it against the golden config. Look for monitor session, SPAN, RSPAN, ERSPAN, and mirror entries.
  2. Name the change. From syslog, AAA, or cloud audit logs, find who created it, from which address, and when. Compare against change tickets — the approved records of planned changes.
  3. Trace the destination. Resolve the mirror target. Is it internal and approved, or a rented host in a hosting ASN?
  4. Measure the loss. Use flow records to size the duplication: which sources, how many bytes, over what window.
  5. Contain and report. Remove the session. Block the collector at egress and upstream. Rotate device credentials. Then open the incident with a volume estimate.

Real-world case study

The case below is a composite written for training. It is inspired by Salt Typhoon-style intrusions into telecom and managed-network providers, merged into one coherent story. Names, hosts, and numbers are fictional; the behaviors follow public advisories.

Context

Nordline Telecom runs a national mobile network and hosts an enterprise tenant with 3,000 office users. Network device management lived on a flat management VLAN reachable over an old contractor VPN. Config backups ran nightly. But nobody diffed them, and flow data was kept for only 14 days.

Day 0 — initial access

Contractor credentials phished

A subcontractor's VPN credentials are phished through a fake scheduling site. The account has read-write access to the management network.

Day 2 — management-plane access

Quiet VPN login to the mgmt net

The attacker signs in to the management VLAN from a hosting ASN never seen before. They then reach core routers and switches over SSH. VPN logs exist, but no alert watches for "management login from a new ASN".

Day 3 — 03:12 local

Monitor session added on the finance VLAN

On core-sw-01 the attacker adds monitor session 1. It copies the finance VLAN to a mirror destination that tunnels toward an overseas collector. No change ticket exists; the nightly backup job stores the change without anyone reading it.

Day 3-33 — quiet theft

A month of silent duplication

Every packet from the finance VLAN is duplicated to the collector. The enterprise tenant's logins, email metadata, and file transfers are reassembled off-site. Nothing on any endpoint changes.

Day 19 — missed anomaly

Volume doubling dismissed

A capacity report flags egress volume at 2.1x baseline during off-hours. An engineer notes "looks like the new backup job" and closes the ticket. No off-hours baseline review exists.

Day 34 — detection point

Config-drift job flags the session

A newly deployed golden-config diff job reports monitor session 1 on core-sw-01 as drift. The running config does not match the approved baseline. The SOC joins the finding with twin-flow analytics and sees identical byte counts to 203.0.113.9.

Day 34 — containment

Session removed, collector blocked

Engineers remove the mirror session. They block the collector IP at egress and with upstream providers. They also disable the contractor VPN account. Device credentials are rotated the same day.

Day 35-40 — eradication

Image verification and mgmt-plane rebuild

Device images are verified against vendor hashes (clean). The management plane is moved behind MFA (multi-factor authentication) and a jump host. A jump host is a single guarded server that admins must pass through. Direct VPN reachability to device CLI is removed.

Day 41-60 — recovery

Exposure window quantified and reported

Twin-flow records and collector egress size the 31-day duplication window at roughly 45 GB leaving the site. The enterprise tenant and the national regulator are notified; monitoring coverage is formally extended to network devices.

Attack chain and tools used

  • Chain: phished contractor VPN login, then management-plane access, then T1020.001 mirroring, then off-site reassembly — the pattern from the section 1 overview.
  • Tools: a phishing kit, the stolen VPN account, an SSH client, and the switch's own monitor session feature with a tunneled mirror destination.
  • Infrastructure: one rented collector server for reassembly and storage. No malware touched any endpoint.

Who did what (team roles)

  • SOC analyst: triaged the config-drift alert and ran the twin-flow query that proved duplication.
  • Network engineer: removed the mirror session and rebuilt management-plane access rules.
  • Incident commander: ran the war room and the daily written updates.
  • Identity and cloud teams: rotated credentials and enforced MFA on admin paths.
  • Legal and compliance: sized the exposure window and filed the regulator and tenant notifications.

Impact and consequences

  • Enterprise tenant credentials and email metadata captured for a month.
  • Tens of gigabytes (about 45 GB) of regulated material duplicated off-site.
  • Regulatory notification and a supervised 60-day remediation plan.
  • Trust damage: the tenant moved traffic to a competitor link.

Team response and communication

  • A joint SOC and network-team war room stood up on day 34 with a single incident commander.
  • Daily 16:00 written updates replaced ad-hoc calls for the duration of the incident.
  • Upstream providers were engaged within hours to block the collector beyond the company's own edge.

Lessons learned

  • Golden-config diffs are the cheapest control. The drift job found in one run what 31 days of backups missed. Diffing stored configs against an approved baseline should have existed from day one.
  • Management plane needs MFA and a jump host. One phished contractor password reached core device CLI because the path was flat.
  • Twin-flow analytics catch what config drift misses. Short-lived mirror sessions may never appear in a nightly diff; the traffic shape is the durable clue.
  • Off-hours anomalies must be triaged, not dismissed. The day-19 volume report was closed with a guess; a 30-minute check would have found the truth.
  • Cloud mirroring APIs need their own alerts. The same intrusion pattern is one API call away in AWS, Azure, and GCP. Control-plane logs must be watched like device configs.
7

Mitigation and defense

Mirroring is a legitimate feature, so you cannot simply remove it. ATT&CK lists three mitigations for this technique: Data Loss Prevention (M1057), Encrypt Sensitive Information (M1041), and User Account Management (M1018). The rest of the defense is layered friction. Make the tap hard to install. Make its output hard to read. Make its effects impossible to miss.

Policy and change management

  • Keep a golden config for every device; back up configs nightly and diff automatically.
  • Allow mirror sessions only through ticketed change windows with named approvers.
  • Keep an approved-mirror inventory and audit live sessions against it.

Identity and management plane (M1018)

  • Put MFA on every device management path; reach CLI only through jump hosts.
  • Split network admin roles so mirror rights sit separate from routine rights.
  • Never grant users permissions to create or modify traffic mirrors unless explicitly required.

Network device hygiene

  • Verify device images against vendor hashes after every install.
  • Disable unused services (old SNMP versions, Telnet, HTTP) on switches and routers.
  • Patch bootloaders and firmware; keep ROMMONkit reporting in scope so firmware never falls off the list.

Cloud controls

  • Use AWS service control policies (SCPs) or Azure Policy to deny mirror creation outside approved roles.
  • Audit CreateTrafficMirror* and equivalent events daily (see section 5.5).
  • Tag approved mirror targets and alert when a target appears without the tag.

Encryption (M1041)

  • Encrypt internal traffic with TLS, not only the edge, so duplicated traffic is unreadable.
  • Prefer modern protocols (SSH, HTTPS, QUIC) over legacy cleartext on server VLANs.
  • Remember what still leaks: server names, DNS, sizes, and timing. Metadata is data too.

DLP (M1057) and monitoring

  • Run twin-flow analytics that flag one source feeding two destinations with equal byte counts.
  • Alert on mirror config changes and mirror API events regardless of the author.
  • Watch egress volume per site against an off-hours baseline.
Home and small office

You do not need a SOC. Change the default router password on day one. Keep the router firmware updated. Turn off remote administration. And do not enable port-mirroring features you do not need. If your line uploads for hours at night for no reason, ask your provider to check it.

Daily habits

  • Read the golden-config diff report; investigate every line, not just alarms.
  • Check overnight mirror API events and device logins from new ASNs.
  • Review the top egress talkers against yesterday's baseline.

Weekly habits

  • Run the twin-flow SPL over core links; demand a verdict for every new pair.
  • Compare live monitor sessions against the approved-mirror inventory.
  • Tune the noisiest rule and record the tuning note.

Monthly habits

  • Purple-test one rule end to end and store the evidence.
  • Verify device image hashes and backup job success for every device.
  • Refresh intel on device tradecraft: new advisories, new actors, new collector patterns.

Response checklist

  • Confirm the mirror session in the running config; capture show monitor session output as evidence.
  • Diff the config against the golden config and record every drift line.
  • Identify who created it, when, and from where (syslog, AAA, cloud audit logs) and match against tickets.
  • Remove the session and block the collector at egress and with upstream providers.
  • Verify the device image hash against the vendor manifest.
  • Rotate device and management-plane credentials, including the VPN and jump-host accounts.
  • Review cloud mirror APIs across all accounts and tenants for the same pattern.
  • Quantify the exposure window from twin flows and collector egress volume.
  • Notify legal and compliance with the volume and window estimate.
  • Add config-drift and twin-flow alerts to the detection backlog and purple-test them.
