    1

    Overview

    A plain-language tour of T1485.001: how one API call can schedule the destruction of a whole cloud storage bucket, and why you get an early warning before any damage.

    Lifecycle-Triggered Deletion means an attacker abuses the automatic cleanup rules of cloud storage to destroy data. A bucket is a named container for files in cloud object storage, such as Amazon S3, Azure Blob Storage, or Google Cloud Storage. A lifecycle policy is a set of automatic rules for objects as they age. It tells the storage service to move them to cheaper storage, to archive them, or to delete them after a set number of days. These rules exist to save money and keep storage tidy. An attacker who can write a lifecycle policy can weaponize it. One rule that expires every object after one day quietly schedules the destruction of the whole bucket.

    The attack feels strange because nothing breaks at first. The attacker sends one API call and leaves. The storage service does the deletion later, on a timer, often while the company sleeps. By the next day the objects are gone, and no attacker was connected when it happened. ATT&CK also warns about a second use of the same trick. The attacker applies the rule to the bucket that stores CloudTrail logs, the activity records of a cloud account. The audit trail then deletes itself. That turns an impact technique into a cover-up tool, because responders lose the very evidence they need.

    Where it sits in the attack chain

    The attacker does not need any server. A single set of stolen cloud keys is enough, which is why leaked access keys and token theft are the usual starting point. When you see this technique, the intruder already has working cloud credentials and has finished looking around.

    Written version of the simulation

    The same story in text, for screen readers and for printing. Each step names the action, the evidence it leaves, and what the defender should notice. The key lesson repeats in every step: the API call is the alarm, and the deletion only happens later.

    Step 1 — Use a leaked access key

    The attacker finds an IAM access key — a username and secret pair for the cloud API — that a developer pushed to a public code repository. A quick test call to the cloud API works, so the key is live. Evidence: a CloudTrail GetCallerIdentity call from an unknown internet address. The SOC should compare API caller addresses with known office, VPN, and build systems.

    Step 2 — Enumerate the buckets

    The attacker calls ListBuckets and receives the names of every bucket in the account. This is quiet recon; nothing is changed yet. Evidence: a ListBuckets event from the same key minutes later. The SOC should alert when an identity lists all buckets for the first time in its history.

    Step 3 — Pick the two targets

    The attacker reads bucket names and settings and chooses two targets: the backup data bucket and the central log bucket that stores CloudTrail records. Evidence: GetBucketLifecycleConfiguration and GetBucketVersioning lookups on both buckets. The SOC should treat reads of lifecycle settings on log buckets as preparation for an evidence wipe.

    Step 4 — Arm the data bucket

    The attacker sends PutBucketLifecycleConfiguration with one rule: expire every object after one day. The cloud now holds a destruction timer for the whole bucket. Evidence: a CloudTrail management event whose rule shows Expiration with Days: 1. The SOC should page on this call immediately, because it is the single best moment to act.

    Step 5 — Arm the log bucket

    The same one-day expiry rule is applied to the CloudTrail log bucket, so the audit trail will delete itself after the attacker exits. Evidence: another PutBucketLifecycleConfiguration call, this time with the log bucket name. The SOC should treat any lifecycle change on a log bucket as critical, because it destroys evidence, not just data.

    Step 6 — The timer runs

    Nothing else happens for 24 hours. The lifecycle service then deletes expired objects on schedule while no attacker is connected. Evidence: no security event at all — only shrinking object counts in storage inventory. The SOC should watch object counts on critical buckets so silent shrinkage is visible.

    Step 7 — The SIEM catches the call

    The SIEM is the security monitoring system that collects logs and raises alerts. It raised an alert the moment step 4 happened, because a role that never writes lifecycle policies suddenly wrote one. The SOC now works a destruction timer that is still hours away from doing damage. Evidence: a correlated alert with the identity, bucket, and expiry value. The SOC should page on short-expiry rules that have no matching change ticket.

    Step 8 — Remove, restore, revoke

    Responders delete the lifecycle rule, restore the data bucket from the cross-region replica, revoke the leaked key, and rotate credentials the identity could reach. Evidence: DeleteBucketLifecycle plus successful restore jobs. The SOC should verify the rule is gone in every region and check whether any logs were lost while the rule was active.

    3

    Red team / hacker perspective

    Understanding the attacker's choices helps you predict the move and place your sensors. Everything here is described for defense and for cloud labs you own.

    When and why attackers use it

    Cloud extortion is the main reason. In extortion, a crew steals or destroys data and demands payment to stop or undo the damage. The research this technique cites — Balassiano and Shaty's cloud ransomware study and the Halcyon RISE team's work on abused AWS services — describes crews that copy the data first. Then they destroy the originals, so the victim cannot simply restore and refuse to pay. The lifecycle rule is attractive because it is native: the attacker uses the cloud's own housekeeping feature, so no malware lands on any server and no antivirus ever fires. Pure disruption teams use the same call to wipe storage during sabotage. Intrusion teams use it on log buckets to delete the record of what they did. ATT&CK ties that second use to indicator removal: destroying the signs of an intrusion.

    Timing is the attacker's second advantage. The deletion happens hours after the person has logged off, so the moment of damage and the moment of access are different. Attribution becomes harder, and an automated timer keeps working even if the attacker loses access. A third appeal is reach: one permission, s3:PutLifecycleConfiguration, can affect every object in a bucket, including terabytes of backups. Attackers do not need to download or encrypt anything to cause loss.

    How it is performed

    The whole attack is a short API conversation. The attacker needs credentials with the PutLifecycleConfiguration permission, then writes a rule whose Expiration is one day or less and whose filter matches every object. The commands below are shown for lab study only. Run them exclusively in a dedicated test AWS account or sandbox that you own, on a bucket that holds nothing important, and delete the rule afterwards.

    Step 4 is the entire technique: one call, one rare event in CloudTrail. Hardened variants add preparation. An attacker may suspend versioning first. Versioning is the feature that keeps old copies of objects when they are overwritten or deleted. With versioning suspended, the later deletion leaves nothing to roll back. They may add a noncurrent-version expiration rule, which deletes those old copies on its own schedule. They may scope the rule to a prefix, a folder-like path inside the bucket, so the change looks like routine cleanup. Or they may set the expiry on the central log bucket, so the security team loses its own logs first. Public adversary emulation such as Stratus Red Team ships exactly this CloudTrail log impairment scenario so defenders can test against it.

    Prerequisites and conditions

    What the attacker needs first

    • Working cloud credentials: a leaked access key, a stolen session token, or a compromised role.
    • Permission to change lifecycle configuration on the target bucket, such as s3:PutLifecycleConfiguration.
    • Knowledge of bucket names, which ListBuckets or public exposure often reveals.
    • Patience: the payload is a timer, so they benefit from staying quiet afterwards.

    What limits them

    • Service control policies that deny PutBucketLifecycle except for approved roles.
    • Buckets they cannot see: separate accounts and restricted listing hide the log bucket.
    • Cross-region replicas and immutable copies the credentials cannot touch.
    • The CloudTrail event fires instantly, so a monitored environment gets a day of warning.

    Common variations and attacker mistakes

    The same abuse exists on other clouds. In Azure, the operation is a write to the storage account's management policy (managementPolicies/write), and in Google Cloud Storage it is a bucket update that adds a delete-after-days condition. Attackers also chain the technique with other cloud-native moves. One move is encrypting objects with customer-supplied keys before demanding payment. Another is following the lifecycle rule with a mass DeleteObjects call when they want data gone immediately. CloudWatch log groups have a related control: the PutRetentionPolicy call sets how long log events live, and shortening it is a similar cover-up move that CloudTrail also records. Each variant still travels through the control plane, which means each variant writes an audit event.

    Attacker mistakes are useful to know. A rule with a typo in the prefix silently matches nothing, so the timer arms but never fires. Applying the rule to the wrong bucket wastes their one quiet window. Reusing an interactive console session for the call links the change to a suspicious login. Forgetting that many organizations copy logs to a second account is the classic error. The audit trail survives in that copy. The destruction attempt then becomes the clearest evidence of intent.

    Danger · lab-only

    Never run these commands against a production or shared AWS account. A one-day expiry rule on a real bucket destroys its contents automatically and may also break backup chains. Use a dedicated test account or sandbox, keep nothing valuable in the target bucket, and remove the rule when the exercise ends.

    4

    Blue team / SOC perspective

    This technique gives you one of the cleanest early warnings in cloud security: a rare management event that fires before the damage. Here is how to see it, what it leaves behind, and how to triage it fast.

    How defenders can see it

    CloudTrail management events

    CloudTrail is AWS's audit log. It records every API call made to your account, with the caller, the source address, and the parameters. Management events record control-plane actions such as policy changes; data events record object-level actions such as reads and deletes. The events PutBucketLifecycleConfiguration, DeleteBucketLifecycle, and PutBucketVersioning are the core signals for this technique, and they are rare enough to alert on directly.

    Storage-level evidence

    Object counts, storage inventory reports, and replication metrics show the delayed effect: a bucket that quietly loses objects day after day. This is the only signal for the deletion phase itself, because the lifecycle service deletes objects without a security event.

    Other cloud audit logs

    Azure Activity Logs record managementPolicies/write on storage accounts, and Google Cloud audit logs record storage.buckets.update calls that add lifecycle rules. If you run more than one cloud, cover all three, because attackers follow the data.

    Why the timing helps you

    The gap between the call and the deletion is your window, and it is usually measured in hours. A one-day expiry rule does not delete anything for up to 24 hours, and removing the rule stops the timer completely. That means a page at 11:27 can save a bucket that would have vanished at 11:30 the next morning. The CloudTrail record is also worth more than it looks. The identity, source address, and user agent in the event usually point straight at the leaked credential. That lets you scope every other action that key has taken. Finally, remember that attackers often target the log bucket first. If a lifecycle change lands on the bucket that stores your CloudTrail records, assume the intruder wants to erase a specific investigation, and protect the copy immediately.

    Short triage flow

    1. Confirm the rule is real

      Open the raw CloudTrail event and read the rule: which bucket, which expiry, which identity. Read the bucket's current lifecycle configuration. Rule out your own automation by comparing with the change calendar.

    2. Stop the timer

      Delete the malicious rule with DeleteBucketLifecycle or an approved change, and apply a temporary denial on lifecycle writes for affected buckets. Removing the rule stops all future deletions at once.

    3. Protect the copies

      Check that versioning is still enabled, that the cross-region replica is intact, and that the organization trail copy is safe. Snapshot the bucket listing and object counts so you can measure loss.

    4. Revoke and scope

      Disable the access key or session that made the call, rotate credentials it could reach, and review everything that identity did. Pay attention to GetObject volume, because stolen data plus destruction means extortion.

    5. Restore and verify

      If objects already expired, restore from the replica or versioned copies. Verify object counts against the snapshot, confirm the log bucket kept its records, and write down the gap for the investigation.

    Good practice

    Write the triage steps above into your cloud incident runbook before you need them. The first minutes matter: a team that removes the rule and protects the replicas quickly converts a potential data loss event into a near miss with a clear story to tell.

    5.1 Regulation mapping

    This technique attacks two things auditors care about: the ability to recover data, and the integrity of records. A bucket that deletes itself breaks backup expectations, and a log bucket that deletes itself breaks record-keeping expectations. The table below shows what major frameworks expect and the evidence a detection program provides.

    Framework and controlWhy it appliesExpected evidence
    GDPR — Article 32 (security of processing). Requires the ability to restore availability of and access to personal data after an incident. A bucket wiped by a lifecycle rule makes restoration impossible and turns an intrusion into a prolonged, reportable breach. Documented backup and restore procedures for cloud storage, tested restorations, alerts on destructive policy changes, incident records showing recovery time.
    HIPAA Security Rule — §164.308(a)(7) contingency plan. Covered entities must keep a data backup plan and disaster recovery plan for electronic protected health information, including data stored in cloud buckets. Written contingency plan, backup success reports for storage buckets, restore test results, monitoring proof for policy changes on protected data.
    ISO/IEC 27001:2022 — A.8.13 (information backup), A.8.16 (monitoring activities). Backup copies must be maintained and protected, and activities that could undermine them must be monitored. Lifecycle abuse is the direct failure case for both controls. Backup policy with immutable or offsite copies, monitoring rules for lifecycle APIs, alert tickets for suspicious policy writes.
    SOC 2 — CC7.2 (anomaly detection), A1.2 (recovery infrastructure). Trust services criteria expect detection of unusual activity and tested recovery. A self-deleting log bucket hides exactly the anomalies auditors expect you to catch. Detection rule documentation, alert and response records for lifecycle changes, restore drill results, change management evidence.
    PCI DSS — 12.10.x (incident response plan and testing). Organizations handling cardholder data must prepare for scenarios that destroy or lock data, which a self-deleting bucket does at cloud scale. Incident response plan covering cloud destruction scenarios, quarterly tests, records of restore exercises from protected copies.
    NIST SP 800-53 Rev.5 — CP-9 (system backup), CP-10 (recovery), AU-9 (log protection). Federal-aligned controls require protected backups and recovery, and AU-9 specifically requires protection of audit information from deletion and tampering. Control implementation statements, protected replica configuration, monitoring coverage proof, log retention guarantees.
    EU DORA — Article 11 (backup policies and recovery). Financial entities must maintain ICT backup policies with restoration procedures for data in cloud infrastructure, including detection of destructive changes. Backup policy documents, restoration and testing records, detection coverage for cloud storage control planes.

    5.2 Threat intelligence

    Intelligence makes your rules stronger and your priorities honest. The picture for this technique is young — ATT&CK added it in September 2024 — but the underlying cloud ransomware research is solid and public. Collect from several source types, then record how confident you are in each finding before you change a rule or a runbook.

    MITRE ATT&CK

    Start with the T1485.001 page and its detection strategy DET0041. It names the exact API calls and the three attacker goals: impact, log removal, and extortion.

    Vendor research

    Balassiano and Shaty's cloud ransomware paper and the Halcyon RISE reports document native-service abuse in AWS with real API sequences. Turn their timelines into tuning notes.

    Adversary emulation

    Stratus Red Team publishes an open emulation of CloudTrail log impairment through an S3 lifecycle rule. Run it in a test account to prove your rules fire end to end.

    Government advisories

    CISA and partner agencies publish cloud credential abuse guidance under the StopRansomware banner. Their advisories list the permissions and APIs crews abuse. Vendor blogs and government advisories together are OSINT: open-source intelligence from free public sources.

    ISACs and commercial feeds

    Sector ISACs share member sightings of cloud attacks. Commercial feeds add actor infrastructure and campaign context. Treat both as secondary sources, and confirm their reports against your own logs before you tune a rule.

    Internal telemetry

    Your own CloudTrail history is the best source. Denied lifecycle calls, policy writes by automation roles, and near misses show what attackers actually try in your environment.

    Confidence levels

    High means several independent reports plus your own sightings. Medium means one solid public report. Low means a hypothesis that still needs testing. Write the level next to every intelligence note.

    5.3 Threats ranking and categorization

    Five realistic threats cover this technique well. The rank reflects how likely the threat is and how much damage it causes when it works. Preconditions describe what an attacker must already have; the justification explains the rank so you can defend it in planning meetings.

    ThreatRankPlatformDescription and preconditionsImpact and justification
    THR-01 · Short-expiry lifecycle rule applied to a data bucket. Critical Cloud (AWS S3) A PutBucketLifecycleConfiguration call sets Expiration to 1 day (or 0) with a filter that matches everything. Preconditions: credentials with PutLifecycleConfiguration on the bucket. One call schedules total loss of the bucket contents on a timer, with no malware and no further attacker activity. It is the core case of the technique and the cheapest attack to perform, hence Critical.
    THR-02 · Lifecycle rule applied to the central log or audit bucket. High Cloud (AWS S3) The same rule is written against the bucket that stores CloudTrail or SIEM exports, so audit evidence expires after the attacker leaves. Preconditions: write access to the log bucket, which is often a different account. Data loss plus evidence destruction in one move. The organization may still recover data, so this ranks High, but the investigation cost is severe and the intent is clearly hostile.
    THR-03 · Versioning suspended combined with noncurrent-version expiration. High Cloud (AWS S3) PutBucketVersioning switches versioning to Suspended, and a lifecycle rule deletes noncurrent versions. Preconditions: permission to change versioning on the bucket. Removes the rollback path that protects against both lifecycle abuse and ordinary deletes. Rare as a legitimate change, so it is high-signal, but it usually supports the main rule rather than standing alone.
    THR-04 · Equivalent lifecycle abuse in Azure Blob or Google Cloud Storage. Medium Cloud (Azure, GCP) A management policy write in Azure (managementPolicies/write) or a bucket update in GCP (storage.buckets.update) adds delete-after-days conditions. Preconditions: storage admin rights on the account or project. Same damage on the other clouds. Ranked Medium only because fewer organizations keep their primary data there and the event names are less commonly harvested yet; the trend is rising.
    THR-05 · Mass object or bucket deletion as an extortion destruction wave. High Cloud (AWS S3) After copying data, the attacker runs DeleteObjects in large batches or calls DeleteBucket, sometimes following a short-expiry rule. Preconditions: read and delete permissions, plus exfiltrated data used as pressure. Immediate, visible loss that pairs with extortion demands. Requires data events to be enabled to see it, which many organizations miss, so it stays dangerous; ranked High because it is louder and faster than the timer variant.

    Each threat below lists the log sources that see it and the fields that matter. It also shows what normal looks like, what suspicious looks like, and the detection logic in plain words. A realistic event example follows each table so you can validate your pipeline against real shapes.

    Threat 1 (THR-01) — Short-expiry lifecycle rule applied to a data bucket

    AspectDetails
    Log sourcesAWS CloudTrail management events for s3.amazonaws.com. Bucket-level S3 calls made through the global endpoint are recorded against us-east-1, so your trail must cover all regions and your searches must include it.
    Key fieldseventName, requestParameters.bucketName, requestParameters.LifecycleConfiguration.Rules[].Expiration.Days, userIdentity.arn, sourceIPAddress, userAgent.

    Threat 2 (THR-02) — Lifecycle rule applied to the central log or audit bucket

    5.5 Sigma rules and Splunk SPL

    Five complete Sigma rules follow, one per threat, each with a matching Splunk query. Sigma is an open format for writing detection rules; Splunk SPL is the search language that Splunk uses. If your CloudTrail lands in a different index, change the index name and keep the field logic. The Splunk queries assume the index and sourcetype conventions listed below, and each query states its own assumptions.

    Field assumptions for Splunk

    index=aws holds CloudTrail with sourcetype="aws:cloudtrail" and JSON fields extracted, such as eventName and userIdentity.arn. index=azure holds Activity Logs with sourcetype="azure:activity". index=gcp holds audit logs with sourcetype="gcp:audit". Nested CloudTrail lists need spath, as shown. Adjust index names to your environment and document the change.

    Rule 1 (THR-01) — Short-expiry lifecycle rule applied to an S3 bucket

    Assumptions: CloudTrail JSON is parsed by the AWS add-on. That lets spath reach the nested rule list. Adjust the index name if your trail lands elsewhere. Mapping note: the Sigma list-style rule match becomes the event filter, and the Days|lte: 1 modifier becomes spath plus a numeric comparison. False positives: real one-day cleanup policies for scratch data. Tuning: keep a lookup of approved short-expiry buckets and rule IDs. Page on every hit that is not on the list, because the deletion timer is already running.

    Rule 2 (THR-02) — Lifecycle rule on a central log or audit bucket

    Assumptions: replace the cloudtrail wildcard with your real log bucket names. Splunk term matches are case-insensitive. Mapping note: the Sigma regex becomes a wildcard match for simple names. For exact coverage, keep a lookup file of log bucket names and join on it. False positives: the logging team's own retention work. Tuning: keep the organization trail copy in a separate account, so this alert is never your only chance. Add the caller identity to the alert context, so triage can spot a role that never touches logging.

    Rule 3 (THR-03) — S3 versioning suspended ahead of destructive deletion

    Assumptions: the AWS add-on flattens requestParameters into dotted fields. Verify the extraction on one known event. Mapping note: the Sigma field path maps one to one to the Splunk field. False positives: approved migrations. Tuning: link the rule to your change calendar. Add a companion query for PutBucketLifecycleConfiguration events with small NoncurrentDays values, so the paired pattern is also detected.

    Rule 4 (THR-04) — Azure and Google Cloud lifecycle policy abuse

    Assumptions: Azure Activity Logs land in index=azure. GCP audit logs land in index=gcp. Both arrive through vendor add-ons, so run the two queries in this block separately. The GCP query keeps the term lifecycle, so only bucket updates that mention the policy survive. Mapping note: Sigma supports one log source per rule, so the Azure rule carries the detection. The GCP query covers the twin behavior in the same block. False positives: provisioning scripts and tiering projects. Tuning: extract the policy document on every hit. Page when delete actions carry thresholds of a few days. Require change tickets for any caller outside the storage admin allow list.

    Rule 5 (THR-05) — Mass object deletion or bucket deletion after credential theft

    Assumptions: DeleteObjects is a data event. S3 data events must be enabled on the trail before this query has anything to find. The key count of ten is a starting baseline, not a universal number. Mapping note: the two Sigma selections become one event filter with an IN clause. The batch size becomes a count of the extracted keys. False positives: scheduled cleanup of temporary prefixes. Tuning: baseline your normal batch sizes per bucket and identity. Exclude the known cleanup service identities by exact ARN, which is the unique ID string AWS gives each resource. Add GetObject volume to the alert context, so theft plus deletion is visible in one view.

    Real-world case study

    A composite incident built from public cloud attack research: a leaked key, a self-deleting bucket, and the CloudTrail alert that saved the data.

    Context — how to read this case study

    This incident is a composite: it was assembled from public cloud attack research rather than from one named breach. The ATT&CK references for this technique are all public research. They include the Balassiano and Shaty study Ransomware in the Cloud: Breaking Down the Attack Vectors (2023). They also include the Halcyon RISE report Abusing AWS Native Services (2025). A third source is the Stratus Red Team scenario CloudTrail Logs Impairment Through S3 Lifecycle Rule. Company names, bucket names, times, and numbers below are invented for teaching. Every step, API call, and log event is real-world plausible and matches the published research.

    The victim, "ACME Finance," runs its analytics and backups in AWS. The finance data bucket holds roughly 8,400 objects, including database dumps and invoice exports. The central CloudTrail log bucket in the same account holds the audit records for the whole organization. A cross-region replica of the data bucket exists in another region, and an organization trail copy is stored in a separate security account. Those two protected copies decide how this story ends.

    Credential leak→ Discovery→ Exfiltration→ Impact (T1485.001)→ Cover-up on the log bucket

    Timeline

    1. Day 0 · 08:15
      An access key leaks

      A developer pushes a personal script to a public repository with a hardcoded IAM access key. Automated scanners harvest the key within minutes and offer it for sale. The key belongs to a deployment user with broad storage permissions, including PutLifecycleConfiguration.

    2. Day 0 · 11:02
      The stolen key works

      The attacker validates the key with a GetCallerIdentity call from a hosting provider address and then calls ListBuckets. The response names 14 buckets, including the finance data bucket and the CloudTrail log bucket.

    3. Day 0 · 11:20
      Recon of cleanup settings

      The attacker reads the lifecycle configuration and versioning status of both target buckets. Versioning is enabled on the data bucket, and the log bucket has a 365-day retention rule. They now know exactly what they are about to change.

    4. Day 0 · 11:26
      Data bucket armed (T1485.001)

      A PutBucketLifecycleConfiguration call enables a rule named expire-all with Expiration Days: 1 and an empty prefix. CloudTrail records the event instantly. Nothing visible happens to the bucket.

    5. Day 0 · 11:27
      The saving detection fires

      The SIEM alert for lifecycle writes by unusual identities fires within a minute of the API call. The alert lands in the queue labeled like a routine configuration change and waits. The timer is now running, and the SOC has roughly 24 hours.

    6. Day 0 · 11:31
      Log bucket armed

      The attacker applies the same one-day expiry rule to the CloudTrail log bucket. If it runs, the audit trail for the entire organization will delete itself, hiding everything they did.

    7. Day 0 · 12:05 to 15:40
      Data theft and an extortion note

      The attacker downloads several gigabytes of database dumps and invoice exports with GetObject. Then they upload a ransom note object that demands payment before the cleanup job finishes. This matches the copy-then-destroy pattern described in the cloud ransomware research.

    8. Day 1 · 11:30
      The expiry wave begins

      Objects older than one day start disappearing. Storage monitoring shows the object count falling by hundreds per hour. No security event fires, because the lifecycle service is doing exactly what a lifecycle service does.

    9. Day 1 · 13:40
      The alert gets its hour

      An analyst works the Day 0 alert backlog, opens the raw CloudTrail event, and sees Days: 1 on a bucket that holds backups. The case is escalated immediately as an active destruction timer, one hour into the expiry wave.

    10. Day 1 · 14:20
      Containment

      Responders delete both malicious rules with DeleteBucketLifecycle. That one action stops the deletion wave at its source. They revoke the leaked access key. They also apply a temporary service control policy that denies lifecycle writes to all roles except the storage admin.

    11. Day 1 to Day 3
      Recovery and the remaining gap

      The team restores the data bucket from the cross-region replica and verifies object counts against a pre-incident snapshot. Several hours of log objects expired before the rule was removed, so the log bucket keeps a visible gap. The organization trail copy in the security account fills most of it.

    Detection point

    The saving detection was the CloudTrail alert on PutBucketLifecycleConfiguration, which fired one minute after the rule was armed — almost a full day before the first object expired. This is the core lesson of the technique: the API call is the alarm, and the deletion is only the echo. Even a delayed response on Day 1 arrived while the wave was still running, and the rule removal stopped all further loss within minutes.

    Containment

    Responders removed both lifecycle rules first, because that single action stops the automated destruction immediately. They then revoked the leaked key and the sessions that used it, applied a temporary service control policy blocking lifecycle writes, and protected the log bucket with an explicit deny. The ransom note object was preserved as evidence.

    Eradication

    The team reviewed every action the deployment identity had taken in the last 90 days, hunting for persistence beyond the keys. They found the exfiltration pattern but no new accounts, roles, or instances. The public repository contact removed the key, and a full credential rotation covered every secret the identity could reach.

    Recovery

    The cross-region replica made restoration a copy job instead of a crisis: the data bucket returned to its pre-incident object count within a day. The log gap could not be closed completely, but the organization trail copy in the security account preserved the critical window. Restore tests run the previous quarter proved their value here.

    Impact and consequences

    Data loss stayed small because the alert existed and a replica existed: roughly six hours of expired objects and a partial log gap. The costs that remained were investigation time, credential rotation across several systems, and a report to the regulator, since personal data had been exfiltrated before the destruction attempt. Had the alert been missing, the public research behind this case study points to a clear outcome. The bucket would have emptied silently. The log bucket would have erased the attacker's tracks. The extortion note would have been the only warning the company ever received.

    Team response and communication

    The SOC, cloud platform team, and legal team worked from the cloud incident runbook. The platform team removed rules and revoked keys. The SOC hunted the identity's history. Legal handled the extortion note and the regulatory clock. Executives received a single plain summary twice a day, with one message repeated: the timer is stopped, the data is being restored, no payment is needed. The calm tone mattered, because the first instinct of leadership on seeing a ransom note is to move fast and pay faster.

    Lessons learned

    • Alert on the API call, not on the deletion; lifecycle destruction announces itself a day early.
    • Give lifecycle alerts a named owner and a critical default, so they do not wait in a config-change queue.
    • Keep one copy the attacker cannot touch: a cross-region replica and an organization trail in a separate account.
    • Deny lifecycle writes by default with a service control policy, and allow only named storage admin roles.
    • Scan repositories for leaked keys, because the cheapest attack in this guide starts in a code commit.

    Mitigation and defense

    You cannot stop every key from leaking. But you can make this attack fail twice: first by denying the permission, then by keeping copies the attacker cannot reach. The controls below are ordered by how much risk they remove.

    Controls by domain

    Backup architecture (ATT&CK M1053)

    ATT&CK's first mitigation for this technique is data backup. In the cloud this means: enable cross-region replication (a second copy kept automatically in another region) for critical buckets, and keep S3 versioning on. Add Object Lock, a setting that freezes copies, so a window of protected versions cannot be deleted or shortened by anyone, including admins. Follow the 3-2-1-1-0 pattern: three copies, two media types, one offsite, one immutable or offline, zero restore-test errors.

    Permission design (ATT&CK M1018)

    ATT&CK's second mitigation is user account management: limit PutLifecycleConfiguration to only the accounts that require it. In AWS, use a service control policy (an organization-wide guardrail that denies listed API calls) to restrict PutBucketLifecycle to named storage admin roles. Remove lifecycle write permissions from developer, CI (continuous integration — automated build and test jobs), and deployment roles entirely.

    Protect the log bucket first

    Attackers use this technique on log buckets for indicator removal. The audit store therefore needs its own defenses. Use a separate security account. Add explicit deny policies for lifecycle and versioning changes. Keep an organization trail copy that no production credential can modify. If the main trail dies, the copy must live.

    Monitoring and detection

    Ship CloudTrail management events to the SIEM, confirm coverage in all regions including us-east-1, and deploy the five rules from section 5. Enable S3 data events so DeleteObjects is visible, and watch object counts on critical buckets so the silent phase of this attack is not silent to you.

    Change management for storage

    Treat lifecycle policy changes like firewall rule changes. Require a ticket, a named approver, and a maintenance window. Keep a lookup of approved rules, their prefixes, and their expiry values, and feed it to the detection rules so approved changes do not page.

    Response readiness

    Write the runbook before the timer starts: who removes the rule, who revokes the key, who protects the replicas, and who decides on restoration. Rehearse once with a table-top exercise and once against a Stratus Red Team scenario in a test account, so the first real run is not the first run.

    Small organization advice

    Protect your own buckets

    • Turn on versioning for every bucket that holds anything important.
    • Keep one copy outside the same account, such as a second account or a local offline export.
    • Never reuse the root account or an admin user for daily work or for CI pipelines.
    • Review your lifecycle rules once a quarter and delete the ones nobody can explain.

    Small-team quick wins

    • Turn on CloudTrail for all regions and send it somewhere you control, even a simple log archive.
    • Add a secret scanner to your repositories; leaked keys are the start of most of these incidents.
    • Once a quarter, restore one important file from backup and time how long it takes.
    • Set a calendar reminder to review who holds storage admin rights in your cloud account.

    Home and small-office advice

    This attack also works against personal cloud accounts, because home users often hold admin rights and keep only one copy of their files. The same two defenses still work: a protected copy, and fewer permissions. You do not need a security team to apply them; use the cards below as a checklist.

    Protect personal backups

    • Turn on versioning and Object Lock — a setting that blocks deletion for a time you choose — on the bucket that holds your backups.
    • Keep a second copy offline, such as an external drive that stays unplugged between backups.
    • Never rely on a single cloud bucket; keep copies in two different places or with two providers.
    • Test a restore once or twice a year, so you know the copies actually work.

    Separate accounts and rule checks

    • Use a normal, non-admin account for daily work; save the root or admin account for rare changes.
    • Give each person, app, or backup job its own account, so one leaked key does not open everything.
    • After any suspicious account activity, open the storage settings and check the "lifecycle" and "retention" rules for changes you did not make.
    • Turn on sign-in alerts from your cloud provider, and act on any alert you cannot explain.
    Warning

    Cloud providers hide lifecycle rules in a settings page named "management", "lifecycle", or "retention". Open that page once today and write down what you find. If files later vanish on schedule, that page is the first place to look, and it is the first place an attacker would have struck.

    Good practice

    The strongest defense against a self-deleting bucket is a copy that cannot be deleted. A cross-region replica with Object Lock, stored behind a permission boundary the attacker's stolen key cannot cross, does exactly that. It turns the entire technique into a harmless API call with a loud alert attached.

    Daily

    • Confirm CloudTrail and cloud log sources are reporting, including the us-east-1 feed.
    • Review every lifecycle and versioning alert from the last 24 hours.
    • Glance at object count dashboards for the buckets you would miss most.

    Weekly

    • Walk one lifecycle alert end-to-end and time the triage.
    • Review new IAM roles or keys with storage write permissions.

    • Test one rule against a lifecycle write in a sandbox account.

    Writes a lifecycle rule that deletes every object in a cloud storage bucket after a short delay, often on log buckets to erase evidence.

    One-line summary

    A lifecycle rule is a deletion timer for your data. The attacker leaves the receipt behind: the API call that arms it is logged the moment it happens. Alert on that call, keep one copy the attacker cannot reach, and the whole technique collapses into a loud, harmless page.
