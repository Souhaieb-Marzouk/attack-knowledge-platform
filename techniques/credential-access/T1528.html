What is T1528? Start here

Before the attack simulation, let us build the base. Take two minutes with this part. It makes the rest of the guide much easier to follow.

Plain words first. An access token is a small piece of text that a system gives you after you log in. It works like a hotel keycard. You show the card once at check-in (login). After that, you only show the card — you do not show your ID (password) again. If someone copies your keycard, they can open your room without ever seeing your ID. That is the whole idea of this technique.

1.1 The official definition, in simple words

MITRE ATT&CK technique T1528 — Steal Application Access Token means: an attacker takes an access token that belongs to an application (or a user session) and uses it to reach remote systems and data as if they were the real owner.

Applications and users get tokens all the time. A mail client gets a token to read your mailbox. A cloud command-line tool gets a token to manage servers. A browser holds a session cookie so you stay logged in. Each of these tokens is a usable credential. If an attacker copies one, they get the same access, with the same rights, until the token expires or is revoked.

1.2 The four sub-techniques

MITRE splits T1528 into four sub-techniques, one per token type. Learn these four and you can name almost any token theft attack you meet.

T1528.001 Application Access Token

What it is: a token that an application or a developer tool uses to talk to a cloud service API. Examples: an Azure CLI token, an AWS secret key used to sign API calls, a Google Cloud token.

Where attackers find it: in config files and caches on disk (like ~/.azure/msal_token_cache.json or ~/.aws/credentials), in memory, in environment variables, or in CI/CD pipeline secrets.

Real example: a developer's laptop is infected. The malware reads the .aws/credentials file and sends it out. The attacker now can call AWS APIs as that developer.

T1528.002 SAML Tokens

What it is: a SAML assertion is a signed XML statement that says "this user is who they claim to be". Your identity provider (IdP) signs it with a special certificate. Cloud apps trust the signature.

The extreme case: if an attacker steals the IdP's token-signing certificate, they can print their own assertions for any user, including fake admins. This is called Golden SAML.

Real example: in the SolarWinds case (2020), the SVR group exported the AD FS signing certificate and forged tokens to enter cloud services as any user — with no password and no MFA prompt anywhere.

T1528.003 OAuth Token

What it is: OAuth is the system that lets you click "Sign in with..." or "Allow this app to read my mail". The app then receives tokens (access token, refresh token) with specific permissions, called scopes.

How attackers get it: mostly by consent phishing (you approve a fake app) or by device code phishing (you type an attacker's code into a real login page). Malware can also steal refresh tokens from disk caches.

Real example: the Nobelium group (2021) registered OAuth apps with mail-reading permissions and tricked people into approving them. After approval, the apps used the Graph API to read mail — using valid tokens, not stolen passwords.

T1528.004 Web Session Cookie

What it is: when you log into a website, the site gives your browser a session cookie. It is a token too. While it is valid, the site treats requests that carry it as "logged in".

How attackers get it: with info-stealer malware that reads the browser's cookie database, or with a man-in-the-middle phishing kit (like Evilginx) that sits between the user and the real site and copies the cookie after login.

Real example: groups like Scattered Spider and Muddled Libra stole session cookies to take over Okta and Microsoft 365 sessions — MFA was enabled, and it did not matter, because the cookie was captured after MFA succeeded.

1.3 Why attackers love tokens

  • MFA does not help. Multi-factor authentication protects the login step. The token is created after that step. If the token is stolen, MFA is never asked again.
  • It looks normal. API calls with a valid token look exactly like trusted app traffic. There is no "failed login" noise, no password spray, no brute force.
  • One token, big access. A single app token can carry wide permissions, like "read all mailboxes" (for example the full_access_as_app role).
  • It survives password changes. Some tokens (refresh tokens, app credentials) keep working after the user resets a password, if you only reset the password and nothing else.
  • It is cloud-shaped. There may be no endpoint alert at all. The attacker may only touch the cloud, never the laptop.

2.1 The story, step by step

The same story in text, with the defender lesson for every step. This is the written version of the animation — useful for slides, training, and runbooks.

STEP 1

The bait

Vex sends Dana an email: "Sign a document". The link opens a real Microsoft login page and asks to approve a new app, "DocuSign Viewer", which Vex controls.

Detect: phishing reports, new consent prompts, mail security tools.
STEP 2

Consent given

Dana logs in and clicks Approve. Entra ID (the cloud identity service) checks password and MFA — both pass — and issues access and refresh tokens to Vex's app.

Detect: Office 365 audit event "Consent to application." (rule D1).
STEP 3

Token sent out

The app sends Dana's tokens to Vex's server. Vex never saw the password. He now holds a valid, signed credential.

Detect: unusual redirects, endpoint writes to token stores, proxy logs.
STEP 4

Token replay

Vex calls the cloud API from his own country with Dana's token. The cloud validates the token, not a password. No MFA challenge appears. The call succeeds.

Detect: non-interactive sign-in from a new country (rule D2).
STEP 5

Data theft

Using the Graph API, Vex reads Dana's mailbox and files. This traffic looks like a normal app working normally.

Detect: MailItemsAccessed volume spikes for one App ID; Graph activity baselines.
STEP 6

Backdoor

Vex adds a new client secret to the app he controls, so access can outlive token expiry and password resets.

Detect: Entra audit "Certificates and secrets management" events.
STEP 7

SOC detects

The SIEM compares the sign-in with the normal baseline: new country, single factor, rare App ID. A Sigma rule fires and an analyst opens a case.

Detect: rules D1–D8 in section 5 of this guide.
STEP 8

Lockout

The SOC revokes Dana's sessions and refresh tokens, disables the app, and removes the consent. Vex's next API call fails with 401 Unauthorized.

Respond: use the first-24-hours runbook in section 8.
What this story teaches. Every step happens in the real world, in some form, every week. The chain has one weak link that defenders own: step 2 (the consent) and step 7 (the detection). If the consent is blocked, or if the replay in step 4 alerts quickly, the whole chain fails. That is why sections 5 and 7 of this guide spend the most time on those two points.

Red team view: how attackers do it

This section explains the attacker's thinking. It stays at a teaching level: enough detail to understand and defend, written for beginners. Everything here must only be practiced in your own lab, on your own accounts, or inside an approved test.

Ethics and law first. Using these actions against systems you do not own, without written permission, is a crime in most countries (for example, under the US CFAA, the UK Computer Misuse Act, or the EU framework). Real red teams work with a signed scope: a document that says what systems and dates are allowed. If you are learning, build a small lab: a test Microsoft 365 developer tenant, a test AWS account, and a virtual machine.

3.1 When an attacker uses token theft

T1528 is not usually the first move. It comes after the attacker has some entry point. Typical moments:

  • Right after phishing. Instead of stealing the password, the phishing page steals the session cookie or tricks the user into approving an OAuth app. One click, full access.
  • After landing on a workstation. Malware or a hands-on operator reads the token caches and browser stores of the user who is already logged in.
  • After a cloud foothold. With one admin account, the attacker reads app secrets or identity keys, then jumps to every service that trusts them.
  • Inside CI/CD pipelines. A changed build step or a malicious package prints pipeline secrets (tokens) and sends them out.

3.2 What an attacker needs before starting

  • A way in. A phished user, malware on a laptop, a bought access from another criminal, or an insider.
  • Knowledge of the target's cloud. Which identity provider? Microsoft 365, Google Workspace, Okta, AWS, Azure? Each has different token stores.
  • Infrastructure. A server to receive tokens, a domain for phishing, and often a proxy tool to handle the login flow.
  • Patience with noise. Token replay still creates sign-in events. Good attackers try to blend in: same user agent, same working hours, small data volumes at first.

Playbook A: consent phishing (T1528.003)

  1. Register an app in any tenant and give it a harmless name like "Office Cleaner Pro". Copy its client ID.
  2. Ask for scopes with real value, for example Mail.ReadWrite or Files.ReadWrite.All.
  3. Build the consent link: the standard authorization URL plus client_id, redirect_uri, and response_type=code.
  4. Send the link by email or chat. The victim sees the real Microsoft login page — because it is the real page.
  5. After approval, exchange the returned code for tokens and start using the API.

Variant: device code phishing. The attacker asks the victim to open the real login page and type a code the attacker got from the device-code endpoint. If the victim finishes the flow, the attacker's session receives the token.

Playbook B: local token harvest (T1528.001 / .004)

  1. Get code execution on the endpoint (malware, malicious installer, physical access, or a red-team implant).
  2. Copy browser cookie databases, the Azure CLI cache (msal_token_cache.json), AWS profiles, and gcloud credentials.
  3. Decrypt what is needed (Chrome cookie decryption on Windows uses DPAPI; on macOS, Keychain) or just replay the files inside the same user context.
  4. Archive everything and send it out in small pieces.

Public tools exist for every step (infostealers, ROADtools, TokenTactics, and others). Mentioning names here is for defenders to know what to detect.

Playbook C: Golden SAML (T1528.002)

  1. Reach the AD FS server (or another SAML IdP) with admin rights — often from another stolen credential.
  2. Export the token-signing certificate and its private key (tools like ADFSDump plus DPAPI decryption were used in real cases).
  3. Forge a SAML assertion for any user — for example the global admin — signed with the stolen key.
  4. Send the forged assertion to the cloud app and get in as that user. No password event, no MFA event, nothing.

This is the most powerful version of T1528. It needs the most access, but it gives the quietest and widest access in return.

Playbook D: pipeline secrets (T1528.001)

  1. Find a repository with weak protection: open PRs, a compromised maintainer account, or a typo-squatted package.
  2. Add a step to the workflow that prints environment secrets or sends them to an external server.
  3. The pipeline itself publishes the tokens to the attacker. The GITHUB_TOKEN, npm tokens, or cloud keys can all leak this way.
  4. Use the tokens to push backdoors or move into the cloud account.

The 2025 "Shai-Hulud" npm worm did close to this at scale: it collected tokens from developer machines and pipelines and used them to publish infected packages.

3.3 Why a red teamer would pick this technique

  • To test reality, not theory. Many companies believe "we have MFA, so we are safe". Token theft shows the gap in a controlled way.
  • To stay quiet. Compared to password spraying or brute force, token replay makes far less noise.
  • To move to the cloud fast. One mail token can open dozens of mailboxes if it uses application permissions.
  • To build persistence. App secrets, refresh tokens, and forged certificates are long-lived "keys" that survive password resets.

3.4 A small, honest lab demo

This example shows what a token looks like, in a safe way. In your own test tenant:

bash · lab only
# 1. Ask the Azure CLI for a token for your own test account
az login
az account get-access-token --resource-type ms-graph
# Output shows a long "accessToken" string. This is the kind of text
# an attacker wants to copy. Look at it, then let it expire.

# 2. See where the CLI stored its own tokens on your machine
ls ~/.azure/msal_token_cache.json    # Linux / macOS
dir "%USERPROFILE%\.azure"           # Windows

# 3. Check who a token belongs to (paste only tokens you own, in your lab)
curl -s -H "Authorization: Bearer $MY_OWN_TOKEN" https://graph.microsoft.com/v1.0/me

Point of the demo: tokens are plain text from the app's point of view. Whoever holds the text, holds the access. That is why protecting and monitoring them matters.

What red teams should report. A good test report for T1528 tells the blue team exactly what to watch: which logs were created at each step, which rule would have caught the action, and which control (consent policy, token protection, cookie hardening) would have broken the chain. The value is not "we got in" — it is the detection gap that gets fixed.

Blue team view: how defenders see it

Now the same technique from the SOC chair. The good news: T1528 is invisible only if you do not collect the right logs. The bad news: the right logs are often not collected by default. This section tells you where to look and why it matters.

4.1 Why this technique matters to a SOC

  • It defeats controls you already paid for. Password policies and MFA work at login. Token theft walks around the login.
  • The footprint is mostly in the cloud. If the attacker only replays a token, there may be no endpoint, no VPN, and no firewall event at all.
  • Blast radius grows fast. One mailbox can become "all mailboxes" if the token has application permissions.
  • It supports long dwell time. Refresh tokens and app secrets can last weeks. Quiet access is expensive access.

4.3 Where to look, in order

  1. Identity logs first. Entra sign-in logs (both interactive and non-interactive), audit logs, Okta system log, Google Workspace login audit. Token replay lives here.
  2. SaaS application logs second. Microsoft 365 unified audit log (especially MailItemsAccessed and consent events), Google Workspace admin audit.
  3. Endpoint third. EDR and Sysmon for token store access; this catches the harvest step even when the replay is missed.
  4. Pipeline and repo logs fourth. GitHub/GitLab audit, CI runner logs, package manager publish events.
Golden rule. Password attacks are loud at the front door. Token attacks are quiet at the back door — but the back door keeps a guest book too: authentication and audit logs. If you stream them to your SIEM and baseline them, T1528 becomes very visible.

4.4 How it fits into the attack chain

T1528 sits in the Credential Access tactic. In a full chain you will usually see it like this:

1Initial AccessPhishing email, bought access, malware (T1566, T1078)
2Credential AccessT1528 lives here — token or cookie is taken

5Collection & ExfilMail and file download through the API (T1114, T1567)

Detection bonus: catching T1528 early breaks steps 3 to 5 completely. You cannot collect or exfiltrate through a revoked token.

4.5 Triage checklist for the analyst on duty

When a token-related alert fires, answer these questions before touching anything:

  • Which user and which App ID are involved? Is that App ID known and approved?
  • Was the sign-in interactive or non-interactive? (Refresh token replays are usually non-interactive.)
  • What country, ASN, and user agent? Do they match the user's normal pattern?
  • Which scopes or roles does the token carry? Read-only, or read-write, or global admin?
  • Was there a consent or secret change event shortly before?
  • Is the device known, managed, and compliant?
  • What did the token do after the sign-in? (Mail reads? Downloads? New rules?)

The intel loop, step by step

  1. Collect. Subscribe to the sources above. Set a weekly 30-minute review. Save anything about token theft into one shared place (a MISP instance, a document, or even a structured note).
  2. Analyze. For each report, extract: the actor, the sub-technique used (T1528.001–.004), the exact operations or events, and the indicators (App IDs, domains, IPs, user agents). Ask: "does this apply to our stack?" If you have no AD FS, Golden SAML moves down your priority list; if you run Okta, Okta session theft moves up.
  3. Apply. Turn the findings into work: a new Sigma rule, a tuning change, a hunting query, or an audit task (for example "check whether any App ID from this report exists in our tenant"). This is where intel becomes detection.
  4. Feedback. Track what fired and what was useless. Tell the intel provider (or your own notes) what worked. Repeat weekly.

D4 · Sysmon file events — browser cookie store touched by a non-browser process

Where it lives: Sysmon Event ID 11 (FileCreate) with a good configuration, or your EDR's file events. Note: Sysmon does not log plain file reads; it logs creates, overwrites, and renames. Malware usually copies the cookie database before parsing it, so the copy step shows up. Reads of the original file are caught by EDR telemetry or, on Linux, by auditd.

xml · sysmon event id 11
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">

    <EventID>11</EventID>
    <TimeCreated SystemTime="2026-09-14T02:31:08.442Z"/>
  </System>
  <EventData>
    <Data Name="Image">C:\Users\dana\AppData\Roaming\WinSvc\svhost.exe</Data>

Combine with D6: the same host often archives both cookies and cloud caches seconds later.

More log sources worth knowing

  • GitHub audit log (streamed to the SIEM): look at workflow changes, branch protection bypasses, new deploy keys, and secret scanning alerts. In Splunk: sourcetype=github:audit (name varies by add-on).

  • Entra audit log: "Update application — Certificates and secrets management", "Add OAuth2PermissionGrant", "Consent to application", service principal sign-ins.
  • Exchange MailItemsAccessed (part of Microsoft 365 E5/G5 audit Premium): shows mail reads at the protocol level, including app-only access — the best source for "did the stolen token actually read mail".

5.5 Sigma rules & Splunk SPL

Sigma is an open format for detection rules. You write the logic once in YAML and converters turn it into queries for Splunk, Elastic, Sentinel, and others. Each rule below has: the logic (detection), the expected noise (falsepositives), and a severity level. Under each Sigma rule you get the equivalent, runnable Splunk SPL. Field names assume common ingestion setups; verify against your own data and tune the country lists in D2 and D5 to where your users actually live.

HIGH D1 · Risky OAuth application consent grant · T1528.003

sigma · yaml
title: Risky OAuth Application Consent Grant
id: 7f0c1a2e-3b9d-4e5f-8a1b-2c3d4e5f6a70
status: experimental
description: >
  A user consented to an OAuth application that asks for risky mail or file
  permissions. Consent phishing gives the attacker a valid token without a
  password. Covers MITRE ATT&CK T1528.003 (OAuth Token).
references:
  - https://attack.mitre.org/techniques/T1528/
  - https://learn.microsoft.com/en-us/defender-office-365/detect-and-remediate-illicit-consent-grants
author: T1528 Detection Guide
date: 2026-09-25
tags:
  - attack.t1528.003
  - attack.credential_access
logsource:
  product: m365
  service: audit
detection:
  selection_consent:
    Operation: 'Consent to application.'
    ResultStatus: 'Success'
  selection_scope:
    ModifiedProperties|contains:
      - 'Mail.ReadWrite'
      - 'Mail.Send'
      - 'Mail.ReadBasic.All'
      - 'Files.ReadWrite.All'
      - 'full_access_as_app'
      - 'AppRoleAssignment.ReadWrite.All'
  condition: selection_consent and selection_scope
falsepositives:
  - Trusted apps such as Slack, Zoom, or CRM add-ins that read mail by design.
  - Admin-approved migration or backup tools with wide scopes.
level: high

Equivalent Splunk SPL:

spl
index=o365 sourcetype=o365:management:activity Operation="Consent to application." ResultStatus="Success"
| eval risky=if(like(ModifiedProperties,"%Mail.ReadWrite%") OR like(ModifiedProperties,"%Mail.Send%")
    OR like(ModifiedProperties,"%Mail.ReadBasic.All%") OR like(ModifiedProperties,"%Files.ReadWrite.All%")
    OR like(ModifiedProperties,"%full_access_as_app%") OR like(ModifiedProperties,"%AppRoleAssignment.ReadWrite.All%"),1,0)
| where risky=1
| table _time, UserId, ModifiedProperties, ClientIP, RecordType

Tuning: add an allowlist of approved App IDs (the ApplicationId property) and alert only on the rest. Admin consents can stay lower severity; user consents with mail scopes are the dangerous ones.

HIGH D2 · Stolen refresh token replay from a new country · T1528.001/.003

sigma · yaml
title: Possible Stolen Refresh Token - Non-Interactive Sign-In From New Country
id: 9d4e5f6a-1b2c-4d3e-8f90-a1b2c3d4e5f6
status: experimental
description: >

Real-world case study: Storm-0558 and the stolen signing key

In 2023, a China-based espionage group that Microsoft tracks as Storm-0558 forged authentication tokens and read the email of senior officials at roughly 25 organizations, including US government agencies. No password was phished, no malware touched the targets' laptops. This is the most instructive T1528 case in recent history, so we walk it end to end like an incident review.

6.1 What happened, in plain words

Microsoft issues tokens for its identity systems. Those tokens are signed with secret cryptographic keys — if a token carries a valid signature, every Microsoft service trusts it. Storm-0558 obtained a Microsoft account (MSA) consumer signing key that, because of a validation gap, could also be used to forge tokens accepted by Entra ID for enterprise Exchange Online. With a forged token, the group opened Outlook Web Access and the Exchange Web Services API as real users and read mail.

Two technical mistakes made this possible: the key was available on a developer debugging system that was reachable after a compromise of an engineer's corporate account, and the signing validation accepted that key for enterprise tokens (an audience and key-usage scoping gap). Both are exactly the class of problem this guide asks you to watch in your own identity platform.

6.2 Timeline

  • Before April 2023
    The key was minted in 2016 and, contrary to policy, never rotated. Storm-0558 compromised an engineer's corporate account, reached a debugging environment, and obtained the key from that system.
  • May 15, 2023
    The group began using forged tokens against Exchange Online, focusing on government and diplomatic targets. Access came through OWA and the EWS API with valid-looking signatures.
  • June 16, 2023
    A customer (the US State Department) reported anomalous mail activity. Microsoft opened an investigation. A logging gap made the first days hard to reconstruct: EWS activity was not captured in the standard audit stream.
  • June 27, 2023
    Microsoft completed revocation and replacement of the compromised key, stopping new forged tokens.
  • July 11, 2023
    Public disclosure. Wiz Research later published key findings that helped the industry understand the token validation gap.
  • September 6, 2023
    Microsoft's detailed MSRC post-mortem and a joint CISA advisory explained the full chain, the missed logs, and the fixes.
  • Aftermath
    Microsoft launched the Secure Future Initiative (security-first engineering, key governance, expanded logging), and Exchange added new audit sources such as session security logs and better MailItemsAccessed coverage.

6.3 How it was detected and contained

  • Detection came from a customer, not a rule. Anomalies in mail behavior were noticed by the victim organization. The lesson: neither signature checks nor the platform caught a forged token automatically. Behavioral review did.
  • Containment was a key rotation. The compromised key was revoked and replaced. All tokens signed by it stopped working. No laptop reimaging was needed — the fix lived in the identity layer.
  • Recovery meant rebuilding trust. Microsoft added logging (session security logs, richer MailItemsAccessed), hardened key issuance and validation, scoped key usage, and forced rotation policies. Customers were told what happened, and the industry gained a reference playbook for signing-key compromise.

6.4 Impact and consequences

  • Confidential mail of senior officials across about 25 organizations was read. For espionage actors, that is the payload: diplomatic planning, policy drafts, contacts.
  • Public trust damage for the platform vendor: congressional scrutiny, regulatory attention, and a public commitment to change engineering culture.
  • Industry-wide fixes: key governance reviews everywhere, faster adoption of token binding, and renewed pressure to stream identity logs to SIEMs.
  • A permanent lesson: "valid signature" means "valid key", not "honest holder". Key management is identity security.

6.5 What this case teaches a detection engineer

  • Watch the keys, not only the logins. Audit access to signing certificates and key vaults like you audit admin portals. (Rule D3, hunt H2.)
  • Behavior beats signatures. Forged tokens pass crypto checks. Baseline per user and per App ID: country, ASN, volume, time of day. (Rules D2, D7.)
  • Collect protocol-level audit. MailItemsAccessed and session logs answer "what did the token read", which sign-in logs alone cannot.
  • Log gaps are incident gaps. The EWS logging hole delayed the investigation. Maintain a log source inventory and test it.
  • Validate scope, not just validity. Push your identity team on audience restrictions, key scoping, and enforced rotation for every signing key you operate.

Mitigation & defense: layered protection

No single control stops token theft. The defense works as layers: make tokens hard to steal, make stolen tokens hard to use, make their use visible, and make response fast. Below, seven layers for an enterprise, then a simple set for home users, then a priority plan.

7.1 The seven enterprise layers

L1

Identity: make the token itself harder to misuse

  • Enable token protection (proof-of-possession) where your platform supports it: the token is cryptically bound to the device, so copying it to another machine fails.
  • Use Continuous Access Evaluation (CAE) so revocation takes effect in near real time on supported services.
  • Set short sign-in session and token lifetimes for privileged roles; require reauthentication for sensitive actions.
  • Turn off legacy authentication protocols (they cannot do MFA and love stolen tokens).
  • Demand phishing-resistant MFA (FIDO2 security keys, platform passkeys) for admins and high-risk users.
L2

OAuth governance: control who gets tokens

  • Disable user consent for most permissions, or allow only verified publishers with low-risk scopes; route everything else through an admin consent workflow.
  • Run a quarterly OAuth application review: owners, scopes, last used, permissions like Mail.ReadWrite or AppRoleAssignment.ReadWrite.All.
  • Block or expiring-allow unused enterprise applications; remove stale consent grants.
  • Use app governance tooling (Defender for Cloud Apps, Entra app policies) to flag apps with unusual API volume or new risky permissions.
L3

Keys and certificates: protect the crown jewels

  • Keep token-signing keys in HSMs or managed key vaults, with export disabled and access logged.
  • Rotate on schedule and force it — the Storm-0558 key was from 2016 and unrotated.
  • Never allow signing material on internet-reachable or developer machines; separate duties so no single engineer can reach a signing key.
  • If you run AD FS: dedicated servers, verbose auditing on, service account monitored, certificate access watched (rules D3 and H2).
L4

Endpoints: shrink the harvest

  • EDR on every platform (Windows, macOS, Linux) — token caches exist on all three.
  • Block unsigned or unusual software from profile directories; use browser profile isolation for admins and developers.
  • Deploy attack surface reduction rules (defend against LSASS and credential access), and keep OS/browser stores encrypted with current protections.
  • Warn-and-block on clipboard and archive tools reaching credential paths; teach developers that .aws, .azure, .ssh folders are secrets.
L5

CI/CD: kill static secrets

  • Replace long-lived pipeline secrets with OIDC federation (short-lived tokens minted per run).
  • Set minimum token permissions on workflows (for example, GITHUB_TOKEN read-only by default) and protected branches.
  • Enable secret scanning with push protection; use ephemeral runners; review workflow changes like code.
L6

Monitoring: see every token in motion

  • Stream all identity logs (interactive and non-interactive), SaaS audit logs, and IdP logs to the SIEM; retention of at least 12 months.
  • Deploy the Sigma rules D1–D8 from section 5 and track their health (events per source, last seen, field presence).
  • Baseline per-App-ID activity and per-user sign-in geography; investigate every "first time" for privileged users.
  • Collect MailItemsAccessed / protocol-level audit where licensed — it is the ground truth of "what the token read".
L7

Response readiness: revoke in minutes, not days

  • Keep the token-theft runbook (section 8.3) tested with a tabletop exercise at least yearly.
  • Pre-authorize SOC staff to revoke sessions, disable apps, and remove consents without waiting for long approvals.
  • Automate the first response steps with your SOAR where possible; measure and report MTTD/MTTR for token incidents.

7.2 For home users and small teams

Tokens matter at home too: your email, banking, and social accounts all run on session tokens. Simple habits close most of the risk.

  • Use passkeys or security keys where offered, and keep automatic updates on for your browser and OS.
  • Never approve unexpected prompts: no surprise "sign in with your code" requests, no app consents you did not start, no "please read me the code" phone calls.
  • Review connected apps a few times a year: Google Account → Security → Third-party access; Microsoft account → Privacy → App access; remove what you do not use.
  • Sign out on shared devices and avoid saving sessions on other people's computers; browsers expose "close all sessions" — use it if a device is lost.
  • Do not install random browser extensions or cracked software — infostealers are the main token thieves for home users.
  • Turn on sign-in alerts for new devices and check them when they arrive.

8.2 Best practices that make the difference

Logging and visibility

  • Maintain a log source registry with owners, fields, and health checks; alert when a source stops sending.
  • Document a one-page token data map: where every token type leaves its traces in your stack.
  • Collect protocol-level audit (MailItemsAccessed, session logs) wherever licensing allows.

Detection quality

  • Detection as code: rules in git, peer review, automated YAML validation, staged deployment.
  • Measure every rule: true-positive rate, false-positive rate, last validated date.
  • Map coverage in MITRE ATT&CK Navigator (Credential Access) so gaps are visible to everyone.

Response

  • Keep a tested token-theft runbook with pre-approved revocation actions for the SOC.
  • Practice with a tabletop: one key compromise, one consent phishing wave, one Okta session replay per year.
  • Automate the first five response steps in your SOAR; humans decide scope, machines revoke.

People

  • Teach Tier-1 analysts "what is a token" with the section 2 animation — triage quality jumps.
  • Run joint reviews with the identity team every quarter; detection engineers learn the platform, identity teams learn the detections.

8.3 First 24 hours: token theft runbook

The order matters. Evidence first, revocation immediately after, then scoping and cleanup.

  1. Confirm and classify. Is this really token misuse? Check the alert against the triage checklist in section 4.5. Assign severity and open the case channel.
  2. Preserve evidence. Export sign-in logs, audit logs, MailItemsAccessed, and relevant EDR data for the window (at least 30 days back) before anything changes.
  3. Revoke the tokens. Revoke the user's sessions and refresh tokens, and disable the suspect app / remove the consent. Do this within minutes of step 2.
  4. Rotate anything the attacker could copy. App secrets, OAuth client credentials, API keys, and — if an IdP key is suspected — trigger the key rotation procedure with the identity team.
  5. Freeze persistence. Block the attacker's app by App ID, remove malicious inbox rules, disable new deploy keys, and revert suspicious workflow changes.
  6. Scope backwards. Hunt 30–90 days back: same App ID, same IP ranges, same user agents, consent events, new secrets. Assume the first hit you saw was not the first touch.
  7. Assess data exposure. For mail access, use MailItemsAccessed and message records to list what was read; this feeds legal and privacy decisions (GDPR 72-hour clock if personal data is involved).
  8. Block and harden. Add IOCs to blocks (IPs, domains, App IDs), close the consent path used, and apply the immediate items of the section 7.3 plan.
  9. Communicate. Notify the user's management, identity team, legal/privacy, and — per policy — regulators and partners. Use the leadership brief from section 6.
  10. Watch for re-entry. Attackers replay tokens from new infrastructure. Keep heightened monitoring on the affected identities for 30 days.
  11. Review and improve. Within two weeks: what detected it, what should have, which rule or control changes follow, and whether the runbook needs edits.
SOAR idea. A small playbook covers most cases: on alert from D1/D2/D5 → enrich with user risk and App ID inventory → if App ID unknown and scope risky → auto-disable the app's service principals, revoke the user's refresh tokens, and open a ticket with the log bundle attached. The analyst starts at step 5 instead of step 1.

Cheat sheet & quick reference

The one page to keep next to your keyboard: signals, log checklist, revocation commands, glossary, and links.

Golden signals of token theft

  • Successful sign-in with no second factor from a new country or ASN
  • Non-interactive sign-in burst for a user who is not active
  • A rare App ID suddenly reading mail or files at volume
  • New consent grant or app secret shortly before the activity
  • Same user, two devices or IPs within minutes (Okta/Entra)
  • API activity with no matching authentication event at all
  • Archive or copy commands touching .azure, .aws, browser Cookies
  • Unknown process reading MachineKeys or AD FS configuration

Log source checklist

  • Entra ID sign-in logs — interactive and non-interactive
  • Entra ID audit log (apps, secrets, consents)
  • Microsoft 365 unified audit log (Consent to application, MailItemsAccessed)
  • Okta / Google Workspace system and login audit logs
  • AWS CloudTrail (STS, GetCallerIdentity) and GCP audit logs
  • Sysmon / EDR file and process events on all endpoints
  • AD FS security and admin logs (verbose auditing on)
  • GitHub / GitLab audit logs and secret scanning alerts

Glossary (simple words)

Access tokenA short text string that proves you are allowed to call a service. Like a hotel keycard.
Refresh tokenA longer-lived token used to get new access tokens without logging in again. Gold for attackers.
Session cookieA token stored by your browser that keeps you logged in to a website.
OAuthThe system that lets apps get tokens with specific permissions ("scopes") instead of your password.
ScopeThe permission list of a token, like Mail.ReadWrite. Read-only is safer than read-write.
SAMLAn older standard where an identity provider signs an XML statement ("assertion") that says who you are.
IdP (identity provider)The service that checks your login and issues tokens: Entra ID, Okta, Google, AD FS.
Golden SAMLForging SAML assertions with a stolen signing certificate. Any user, no password, no MFA.
AiTM"Attacker in the middle" phishing: a proxy site that passes your real login through and steals the session cookie.
Consent phishingTricking you into clicking "Approve" for an attacker's app, which then receives tokens.
SIEMThe central log platform (Splunk, Sentinel, Elastic) where detections run.
EDREndpoint detection and response: the agent on laptops and servers that watches files and processes.
SigmaAn open, YAML-based format for detection rules that works across SIEM products.
SPLSplunk's search language used in this guide for SIEM queries.
CAEContinuous Access Evaluation: revocation events reach services in near real time.
