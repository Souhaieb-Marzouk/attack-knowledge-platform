Overview

A plain starting point: what this technique describes, why it matters, and what you will learn on this page.

What is T1587?

MITRE ATT&CK is a public catalog of attacker behavior. T1587 is called Develop Capabilities. It describes a simple idea: some adversaries build their own attack tools instead of stealing or buying them. The tools can be malware, exploits for software bugs, or digital certificates that make harmful files look trusted.

Picture a small company whose only product is attack tools. It has planners, developers, testers, and a build process. That is what this technique covers. The output is a custom capability, made for one mission or for sale to other criminals.

The official ATT&CK description adds three details. First, development can support many phases of an attack, not only the first one. Second, the needed skills may sit in-house or be contracted out. ATT&CK counts a contractor as an extension of the adversary's own capability when the adversary shapes the requirements and keeps exclusive use of the result. Third, the description states that adversaries may use Artificial Intelligence (AI) for development. AI here means software that generates text or code on request, such as a large language model (LLM).

Why it matters to defenders

  • Exclusive tools bypass known signatures. A signature is a stored fingerprint of a known bad file. Antivirus matches those fingerprints. A brand-new tool matches nothing, so basic protection lets it through.
  • Long development shows high intent. Weeks of work, funding, and testing mean a serious group. Groups that build tools usually follow through and attack.
  • Development choices leak signals. The workshop is not invisible. Cloud accounts, new domains, certificates, and code platforms all leave small traces outside the attacker's walls.
  • Early detection buys time. A tool spotted at the workshop stage meets prepared defenses on day one, instead of surprising you on day thirty.

Where it fits in the attack chain

T1587 sits in the Resource Development tactic, in the PRE phase. PRE means before the attack touches any victim system. It runs before Initial Access techniques such as T1190 (Exploit Public-Facing Application) and T1566 (Phishing). Two related techniques sit next to it: T1583 (Acquire Infrastructure) rents servers and domains, and T1588 (Obtain Capabilities) buys or steals tools that already exist. T1587 is the third path: make it yourself.

  4. How to respond to a new custom tool, and which mistakes to avoid.

Written step-by-step story

Step 1 · Pick the capability
Plans come before code

The group picks the product: a backdoor with stealth features. They set a budget in crypto, assign six developers, and agree on one rule: no public samples. Nothing touches victim systems yet, so defenders see nothing here.

Step 2 · Set up dev infrastructure
A burst of fresh cloud VMs

The team rents cloud virtual machines (VMs) through accounts created minutes earlier and paid with crypto. A wave of RunInstances calls lands in the cloud account. A burst of launches by a brand-new user is the first loggable clue.

Step 3 · Write and build the tool
Compilation on a private VM

Developers commit code and compile a file named loader.bin on the build server. No telemetry leaves that VM, so there is no direct signal. Later, code-platform monitoring may catch a staged copy of the project.

Step 4 · Test in an isolated lab
A test victim and a test C2

The tool runs against a throwaway test VM and calls a test C2 server. C2 means command and control: the server a tool reports to. Its domain was registered about a week earlier. Passive DNS can show the first resolves days before any real attack.

Step 5 · SOC watches staging
Staging leaks a pattern

The staging host goes live with a fresh TLS certificate, cheap VPS hosting, and beacon checks every 60 seconds. A beacon is a short, regular call home. New domain plus short certificate plus steady timing is a strong hunt candidate.

Step 6 · Package and stage
A packed file waits for delivery

The binary is packed, which means compressed and wrapped to hide from antivirus, then uploaded to a public file platform. Downloads of rare packed files are worth an alert even before any victim appears.

Step 7 · Deliver to buyer or victim
First contact with a real target

A buyer on an underground forum pays, and the tool reaches a first victim organization. The endpoint sees a first-seen, unsigned binary that opens an outbound connection within seconds of execution.

Step 8 · Detect, learn, share
The loop closes

The SOC blocks the binary, saves the sample, and shares indicators with peers. Today's sample becomes tomorrow's early warning, so the next build cycle is caught earlier than this one.

Red Team Perspective

This section explains how adversary developers work. It is written for defenders and for authorized red teams. Knowing the workflow shows you where the workflow leaks.

When and why attackers build their own tools

Building a tool is expensive. It needs skill, time, and money. So attackers only do it for clear reasons. The three most common reasons are below.

Skip known signatures

Antivirus matches stored fingerprints of known bad files. A tool that nobody has scanned yet matches nothing. A fresh build gives the attacker days or weeks of free movement.

Fit one mission

Bought tools are general. Built tools are exact. A group can add the one protocol, language, or target type their campaign needs, and leave out everything else.

Own the roadmap

When a bought tool is discovered and blocked, the seller may disappear. A team that owns its code can patch it after every detection report. That keeps the capability alive for years.

How the build pipeline works

Adversary development mirrors normal software work. The same steps appear again and again in public reports.

Phase 1 · Environment
Set up the workspace

The team prepares a private development environment: code repositories, build machines, and shared test data. Everything sits on rented or stolen infrastructure, never on their home network.

Phase 2 · Build
Compile the capability

A build pipeline turns source code into a binary. Attackers strip debug data and sometimes randomize the build so two samples look unrelated.

Phase 3 · Test
Internal quality checks

The tool runs against test victims in an isolated lab. Developers check stealth against public antivirus scanners and adjust until the sample looks clean.

Phase 4 · Staging
Prepare for delivery

The finished build moves to a staging host with its command-and-control (C2) server. Only then does the capability face a real target.

Where the work happens

Cloud virtual machines

Quick to rent, hard to attribute. Accounts are new and paid with crypto, so billing trails go cold.

Rented anonymous hosting

Budget VPS providers (VPS means virtual private server) with loose identity checks host build and staging systems.

Offline labs

Air-gapped test networks let malware run with no outside visibility. Only lab results, never lab traffic, reach the internet.

Who does the work

Exploit specialist

Turns a software bug into working code. Small shops rent this skill by the job. That matches the official description, which says some skills may be contracted out, and it explains why exploit markets keep growing.

Stealth developer

Writes the loader, the packer, and the evasion tricks. This role decides how long the tool survives on endpoints.

Operations

Runs the servers, the payments, and the staging. Sloppy operators leave the trails that threat hunters find most useful, such as reused logins.

The official ATT&CK description names three ways to staff a workshop. All three change what defenders can expect to see.

The C0064 example deserves a second read. The adversary placed a pre-written document of techniques and procedures into the LLM. The AI then applied that document when set variables and conditions were met. That is a playbook plus automation, and it shows AI as a force multiplier, not as a separate kind of attack.

Prerequisites for a capability shop

  • Skill: developers who can write and hide native code, plus an exploit specialist for hard targets.
  • Funding: crypto for hosting, test hardware, and scanning services.
  • Time: weeks to months before a first usable build exists.
  • Test targets: throwaway VMs that imitate real victims, so the tool is tested honestly.

Missing any one of these slows the whole shop. That is why defenses that raise attacker cost, such as fast abuse reporting and payment friction, are real mitigation even when they feel indirect.

Common attacker mistakes

Where shops slip

  • Test C2 left online: a test server stays reachable for weeks. Hunters find it and pivot to the real one.
  • Shared code across families: the same helper function appears in two tool families. One detection now covers both.
  • Build habits: the same compiler version, paths, or usernames appear in every sample and link them together.
  • Leftover metadata: author names, project names, or passwords inside the binary give analysts instant context.

Lab exercise (safe)

In an isolated lab VM with no internet, build a harmless program and watch what your own logging agent records. This shows why a first-seen unsigned binary is interesting, without touching any real system.

Bash
# Lab only. Run inside an isolated VM that you own.
mkdir -p /lab/build && cd /lab/build
printf 'int main(void){return 0;}\n' > hello.c
gcc hello.c -o hello
file hello
sha256sum hello

Now check your logs. On Windows with Sysmon, look for Event ID 1 (process create) and note the Image, Hashes, and Signed fields. On Linux with auditd, look for the execve record. The lesson: even a boring binary leaves a trail. A real adversary tool leaves the same trail, plus network calls.

Ethics and scope

This page is defense-oriented. Reproducing attacker development is legal only in a lab you own, with written authorization. Never target, scan, or harm systems you do not control. Keep lab artifacts offline, because publishing capability code can cause real harm. Follow your local laws and your organization rules at all times.

Blue Team / SOC Perspective

A SOC is a security operations center: the team that watches alerts and hunts threats. For T1587 the SOC works mostly with indirect signals, gathered from outside your own network.

How defenders can see this technique

You will rarely watch a compile happen. Instead, you see the artifacts the workshop produces and drops. An artifact is any leftover object: a file, a domain, a certificate, or a message. Four artifact classes matter most.

Samples and tool fingerprints

First-seen files in sandbox submissions and sample databases. Sandbox means a safe test machine that runs unknown files and records their behavior. New samples often carry old, reused code.

Domains and certificates

Every build needs a test and staging domain. Domains are registered days early, then fitted with short-lived TLS certificates (TLS secures web traffic).

Repositories and personas

Staging copies of tools appear on code platforms. Fake developer personas (accounts with invented names) host them, and their history is short and hollow.

Forum and market posts

Sellers advertise custom builds on underground forums. Screenshots and demo videos leak family names and build dates that analysts can track.

Why pre-positioning matters

Catching the workshop means you can prepare before deployment. If you know a family name, a staging domain, or a sample hash today, you can build detections that fire the day the tool arrives. That is pre-positioning: placing your defenses while the attacker is still building. It converts surprise into routine.

Attack-chain fit

T1587 is the first link of the chain. It feeds T1190 and T1566, which deliver the tool. Your PRE-phase detections do not stop the workshop, but they shorten the window between delivery and detection from weeks to hours.

Triage flow: a new custom tool appears in an intel report

  1. Read the report fully. Note the capability name, family, file hashes, and command-and-control domains.
  2. Search your own telemetry for those indicators across the last 90 days. Any hit changes the case from interesting to urgent.
  3. Search sandbox and sample databases for the hashes and for similar first-seen files.
  4. Check CT logs and passive DNS for related domains and certificates around the report dates.
  5. Write or enable a detection, such as a Sigma rule, and test it against the last 30 days of logs.
  6. Hunt the staging pattern in your network logs: new domain, short certificate, budget hosting, steady periodicity.
  7. Brief stakeholders. Add the capability to your threat profile with a confidence level.
  8. Schedule a re-check and feed new findings back to the intel team, so the record stays current.

A good first week

Do not try to do everything at once. Turn on the CT-log watch on day one. Write the first-seen query on day two. Run one staging hunt on day five. That single week moves you from blind to covered on the highest-value signals.

How to triage a fresh report

Reports arrive faster than teams can read them. A fixed five-minute pass keeps the queue honest. Do these steps in order, and write the result down either way.

  1. Skim for the actor, the capability name, and the claimed ATT&CK techniques.
  2. Extract the hard evidence: hashes, domains, certificates, and dates.
  3. Check the source's track record and mark a confidence level.
  4. Decide: rule now, hunt later, or file with a reason.
  5. Log the decision where the whole team can see it.

Confidence, in plain words

High confidence means several independent sources agree. Medium means one good source, or two weak ones. Low means a single claim with no proof shown. Never let a low-confidence indicator block a business process. It can still become a watchlist entry, which costs nothing.

T1 — Bulk anonymous cloud procurement

A new cloud account launches many virtual machines in minutes, often with GPU types, and pays with crypto. Real companies do this too, so context decides. Precondition: a fresh account or card. Impact: every later step scales on this fleet. Justification: it is the earliest signal you can verify from logs alone, which earns High despite honest false positives from AI and rendering jobs.

T2 — Fake developer personas

Invented identities with short histories open accounts, join organizations, and publish repos. Precondition: time to stage a believable profile. Impact: staging gains cover and reach. Justification: the pattern is real and repeatable, but a single persona is weak evidence, so Medium is the honest rank until it links to tooling.

T3 — Staging infrastructure goes live

A newly registered domain gets a short-lived TLS certificate on a budget VPS network and starts beacon-like periodic calls. Precondition: domain plus hosting. Impact: the C2 channel is ready for a live tool. Justification: no single field is proof, but the combination is rare and cheap to hunt, which earns High.

T4 — First deployment of a custom capability

A first-seen, unsigned binary runs on a real endpoint and calls out fast. Precondition: the workshop finished and delivery worked. Impact: the intrusion has started and objectives follow. Justification: Critical, because this is the final moment where prevention is still cheaper than response.

T5 — Malicious npm and PyPI package development

ATT&CK lists this exact pattern twice on the T1587 page. Contagious Interview (G1052) developed malicious NPM packages for delivery to or retrieval by victims. Moonstone Sleet (G1036) did the same with npm packages. PyPI (the public Python package registry) sees the same pattern. Precondition: developer accounts on a package registry. Impact: victims fetch and run the malicious code themselves, which bypasses network defenses. Justification: Medium here, rising to High once package telemetry exists, because ATT&CK records it as current and repeated behavior.

T6 — Custom malware development

This is the heart of T1587 and its sub-technique T1587.001. A group writes its own backdoor, loader, or wiper, in-house or through a contractor that works only for them. Precondition: developers, build systems, and funds. Impact: exclusive tools that no signature knows. Justification: Critical, because almost every developed capability ends here, and ATT&CK's own detection advice (compiler traces, debug artifacts, code similarities) exists mainly for this threat.

T7 — Custom exploit development

A specialist turns a software bug into reliable attack code for one mission (sub-technique T1587.004). Precondition: deep product knowledge and test hardware. Impact: entry into targets that applied the public patches but face the private bug. Justification: Critical, because a custom exploit defeats the patch-time protection most organizations rely on.

T8 — Fraudulent code-signing certificate development

The adversary creates or repackages code-signing material so malware carries a valid-looking vendor signature (sub-technique T1587.002). Precondition: company shells, stolen publisher identities, or access to signing systems. Impact: security dialogs and allowlists trust the tool. Justification: High, because a signature is the strongest trust check on Windows, and defeating it weakens every later control.

T9 — Self-signed TLS and C2 certificates

The group mints its own TLS certificates (sub-technique T1587.003) for test and staging servers, and later for live C2. Precondition: tooling and a domain. Impact: encrypted channels that resist default inspection rules. Justification: Medium on its own; the value appears when you combine it with domain age and hosting reputation, as Rule 3 in section 5.5 does.

T10 — AI-assisted development and tooling

The official description states that adversaries may use Artificial Intelligence for development. The official C0064 example goes further: the adversary fed a pre-written document of techniques and procedures into an LLM and applied it when set conditions were met. Precondition: access to an AI model and a written playbook. Impact: faster builds, more variants, fewer language barriers. Justification: Medium. The direct signal for defenders is weak today, but the official record makes this threat real, not future.

T11 — Outsourced development via contractors

The official description says skills may be contracted out. A contractor counts as an extension of the adversary's capability when the adversary shapes the requirements and keeps exclusivity. Precondition: money and a written brief. Impact: skills on demand, from exploits to full toolchains. Justification: Medium. You will almost never see it directly, but it explains why samples from one group can look inconsistent, which weakens code-similarity hunting.

T12 — Spearphishing toolkit development

The group builds its own phishing sites and mailing tools. ATT&CK records this for Kimsuky (G0094): a created and used mailing toolkit for spearphishing attacks. Precondition: web skills and hosting. Impact: reusable attack pages with built-in credential theft. Justification: High, because a toolkit is used many times, so one build feeds many campaigns, and each use leaks its pattern.

Ranks are starting points, not verdicts. A bank should move T4 up after any report of custom banking tools. A research lab may care most about T1, because its GPU estate is a natural target for hidden build farms. A software company should raise T5 and T8, because its brand is what fake packages and stolen signatures imitate.

5.4 Logs and Detection Patterns

Each threat below lists its log sources, the fields that matter, what normal looks like, what suspicious looks like, and the detection logic. Two or more example events follow each threat so you can test your pipeline. Field names follow the real log formats. After the five patterns, a final block covers the official ATT&CK analytic about the built capability itself.

What good looks like

You do not need every field to be perfect. You need each of the five patterns below, plus the official-analytic features, to be answerable in one query. If a pattern takes three joins and a dashboard, simplify the data path first. Detection that is cheap to run gets run every day. Keep the example events in a test index, so new engineers can replay the five patterns locally.

T3 — Capability staging infrastructure going live

  • Log sources: Zeek ssl.log or Suricata TLS records (network sensors), proxy and DNS logs.
  • Key fields: id.orig_h, id.resp_h, sni, certificate.subject, certificate.issuer; proxy side: c-ip, cs-host, r-DNS.
  • Normal behavior: well-known domains, certificates from big providers, long validity, varied traffic timing.
  • Suspicious behavior: a domain registered days ago, a certificate valid for under two weeks, hosting in a budget VPS network, and calls every 60 seconds with small jitter.

Detection logic: join TLS metadata with domain age and hosting reputation. Score each weak signal and alert when the total crosses a line. Periodicity, meaning near-identical timing gaps, is the final tie-breaker.

T4 — First deployment of an adversary-built capability

  • Log sources: Sysmon on Windows (event IDs 1 and 3), EDR process and network events.

Official analytic: what to collect about the capability itself

The five patterns above watch the workshop from outside. ATT&CK's detection advice for T1587 (analytic DET0853) adds a second direction: collect features of the built capability, because the build process itself stays hidden. These are the features ATT&CK names, with practical collection notes.

Compiler usedWhich compiler and version built the fileStatic analysis of the binary: strings, headers, imported libraries
Debugging artifactsFile paths and usernames left in the buildPDB path extraction (PDB files store debug symbols), error strings, symbol tables
Code similaritiesFamilies that share helper code, which links samples to one developerSample comparison inside malware repositories

Detection efforts should focus on related stages of the adversary lifecycle, such as Defense Evasion or Command and Control. In practice: when a built capability finally reaches you, the evasion and C2 behavior is where your sensors win.

Rule 1 — Cloud burst provisioning (T1)

YAML
title: Burst of EC2 Instance Launches by a Single New IAM User
id: ad5ee227-3c19-4210-9036-cfe7dc9fc1aa
status: experimental
description: Many RunInstances calls by one young IAM account in a short
  window. Adversary build farms often appear as one fast wave of VM
  launches paid in crypto and never seen again.
references:
  - https://attack.mitre.org/techniques/T1587/
  - https://attack.mitre.org/techniques/T1583/003/
author: Detection Engineering
date: 2026-02-14
logsource:
  category: cloud
  product: aws
  service: cloudtrail
detection:
  selection:
    eventName: RunInstances
    eventSource: ec2.amazonaws.com
  timeframe: 15m
  condition: selection | count() by userIdentity.userName >= 10
fields:
  - userIdentity.userName
  - userIdentity.accountId
  - sourceIPAddress
  - awsRegion
  - requestParameters.instanceType
falsepositives:
  - Rendering farms and machine learning jobs that start many VMs at once
  - Autoscaling events during a busy season
level: medium
tags:
  - attack.t1587
  - attack.resource_development
  - attack.t1583
SPL
index=cloud sourcetype=aws:cloudtrail eventName=RunInstances eventSource=ec2.amazonaws.com
| bin _time span=15m
| stats count as launches dc(awsRegion) as regions values(requestParameters.instanceType) as types
  by userIdentity.userName _time
| where launches >= 10
| sort - _time

False positives: AI training and render farms. Tuning: raise the count for tenants that legally burst; add an account-age lookup to drop users older than 90 days. Severity: medium, high when the account is under a week old.

| stats count as downloads dc(c_ip) as clients values(sc_bytes) as sizes values(r_DNS) as hosts by cs_host cs_uri_stem
| sort - downloads

Field assumptions: the proxy sourcetype renames W3C fields with underscores; check your app mapping. False positives: firmware updaters. Tuning: drop known vendor hosts, then flag only artifacts under 90 days old using first-seen lookups. Severity: medium, high when several hosts fetch the same rare artifact within a week.

How to test before you deploy

Run every new rule in silent mode for two weeks. Compare its matches with known-bad and known-good traffic, and write down the false positive rate. Then choose the level that fits your team. A rule nobody trusts is worse than no rule, because it trains analysts to ignore warnings. Keep the silent-mode notes next to the rule, so the next engineer inherits the reasoning.

Real-World Case Study

NotPetya in 2017 shows the full cost of a developed capability. The Sandworm group built a destructive tool, staged it, and shipped it through a trusted update channel. ATT&CK records the NotPetya development detail under T1587.001 Malware, on the Sandworm group page. This parent-technique page keeps the case study because it shows the full arc from workshop to global damage.

Context

Sandworm (ATT&CK group G0034) is a Russia-nexus group tied to military intelligence. In early 2017 it developed a wiper: malware built to destroy data, dressed up as ransomware. Ransomware encrypts files and offers a key for payment. A wiper corrupts data and leaves nothing to recover.

The builders did not start from zero. They combined their own Petya codebase from 2016, credential theft code similar to Mimikatz, and two exploit tools named EternalBlue and EternalRomance. Public reporting describes EternalBlue as an exploit tool built by a state-linked actor. The Shadow Brokers leaked it online in April 2017, and many groups then reused it at scale. That mix of self-built and reused parts shows how the sibling techniques split: T1587 covers what the group built itself, and the reuse of leaked exploits maps to T1588.005 (Obtain Capabilities: Exploits), not to T1587.

The group chose a supply-chain path on purpose. Ukraine widely trusted the M.E.Doc update system, so one compromised channel beat thousands of phishing emails. Researchers later found early test builds and a signed fake update, which is how the development timeline was rebuilt. That reconstruction is the model for every T1587 investigation: work backwards from the artifact to the workshop.

Timeline

February to April 2017
Development and testing

Analysts later found early samples with build dates in this window. The team compiled, tested, and refined the payload across several variants.

Mid-June 2017
Turning the tool into a working attack

A fake update for M.E.Doc, Ukrainian accounting software, was prepared and signed on 22 June. The update carried the wiper inside a trusted channel.

27 June 2017
Release

The compromised M.E.Doc update server delivered the payload to Ukrainian customers, including government and energy targets, just before a national holiday.

Hours after release
Global spread

The wiper spread itself using EternalBlue and EternalRomance over SMB (Windows file sharing) and stole credentials to reach more hosts. It crossed borders within hours.

Days after release
Damage at scale

Public reporting has estimated total global damage near 10 billion US dollars. Major shippers, pharmaceutical firms, and ports reported week-long outages.

Attack chain mapped to ATT&CK

  1. T1587 Develop Capabilities: the wiper was built and tested by the group itself. ATT&CK records this development under T1587.001 Malware.
  2. T1195 Supply Chain Compromise: the M.E.Doc update mechanism was turned into a delivery channel.
  3. T1210 Exploitation of Remote Services: EternalBlue and EternalRomance spread the payload across networks.
  4. Credential theft and lateral movement: Mimikatz-style theft plus remote execution moved the wiper inside organizations.
  5. Destructive payload: master boot records and file tables were overwritten under a fake ransom screen.

Detection point

What SOC teams saw

  • Mass SMB scanning on port 445 inside networks, hours before encryption started.
  • Sudden writes to boot records, which normal software never performs.
  • A burst of first-seen files with high entropy (random-looking content).
  • Security vendors published signatures for ExPetr the same day, which later builds could no longer bypass.

The lesson for T1587: once a custom capability deploys, detection is reactive. Vendors caught NotPetya within a day, but the workshop had already succeeded. Earlier PRE-phase signals, such as staging domains or leaked test samples, buy lead time that reactive signatures never will.

Response in three phases

Containment

Teams isolated networks, blocked the M.E.Doc update server, patched MS17-010, and disabled SMBv1. Speed mattered more than elegance.

Eradication

There was nothing to clean. The wiper left machines unbootable, so eradication meant rebuilding hosts from trusted media.

Recovery

Restores came from offline backups. One shipping firm rebuilt tens of thousands of endpoints in about ten days from a single surviving domain controller.

Why the ransom demand failed

A wiper dressed as ransomware

The payload showed a ransom screen, but recovery was impossible by design. The payment contact was a single email address that authorities shut down fast. More importantly, the encryption routine destroyed data instead of protecting it. That mismatch is the clearest sign of a wiper pretending to be ransomware, and it is worth teaching to every triage analyst.

Team response and communication

Because Active Directory was destroyed, internal chat and mail failed too. Responders fell back to out-of-band channels: personal phones, messaging apps, and paper lists. Crisis communication worked where teams had already agreed on backup channels. Where they had not, coordination cost hours they did not have.

Lessons learned

  • Patch velocity beats patch perfection. The exploits used a fix published months earlier.
  • Segment networks so one wiper cannot reach everything from one host.
  • Keep offline, immutable backups and test restores on a schedule.
  • Treat update channels as supply-chain trust, and verify vendor updates independently.
  • Train triage for destructive events, so teams check data damage before paying or restoring.
  • Keep printed contact lists, because the channel you assume is the one that fails.

Mitigation and Defense

An honest start: you cannot patch the attacker's build server. Mitigation for T1587 is indirect. You raise the cost of building, shorten the life of the finished tool, and blunt its first deployment.

The official mitigation: Pre-compromise (M1056)

ATT&CK lists one mitigation for T1587: M1056 Pre-compromise. ATT&CK's own note says this technique cannot be easily mitigated with preventive controls, because it is based on behaviors performed outside of the scope of enterprise defenses and controls. Pre-compromise mitigation means acting early: remove what the workshop needs, such as weak cloud identity, unwatched domains, and silent egress, so the finished tool meets a hardened target. Advice for home and small offices

Basics that matter

  • Turn on automatic updates for system, browser, and router.
  • Run built-in antivirus and keep real-time protection on.
  • Keep one offline backup that stays unplugged.
  • Use a filtering DNS service to block fresh malicious domains.

Habits that help

  • Do not trust a green padlock or a "verified publisher" label alone. Custom tools can carry bought certificates.
  • Prefer official stores for software, and check publisher names letter by letter.
  • Unpack downloads in a scans folder your antivirus inspects first.
  • Rehearse one restore, so recovery is boring when it matters.

Router and smart home

  • Change the router admin password once, to something long.
  • Update the router firmware twice a year.
  • Put smart gadgets on a guest network, away from work devices.

Measure your progress

Mitigation without measurement drifts. Revisit these questions each quarter and answer them with evidence, not feelings.

  • How many hours passed between the last new tool report and your first working detection?
  • What share of egress destinations are domains you have never seen before?
  • How long does one full restore from offline backups actually take?
  • Which cloud accounts are older than 90 days but still unreviewed?

Numbers that stay stable across two quarters are your baseline. Numbers that get worse are your next project. This loop, not any single tool, is what blunts a developed capability.

One practical trick: keep a single page, visible to the whole team, that lists the twelve threats from 5.3 with the last date each one was hunted. Stale dates are a quiet, honest warning sign.

Common Mistakes and Best Practices

Twelve mistakes teams make with PRE-phase detection, each with the symptom you will notice, the root cause, the fix, and the prevention that keeps it fixed.

1. Treating PRE techniques as undetectable

Symptom: the team skips Resource Development entirely in its coverage map. Root cause: a belief that attacks before first contact are invisible. Fix: map the twelve threats in 5.3 to logs you already own. Prevention: add PRE rows to the detection backlog and review them quarterly.

2. Ignoring CT logs

Symptom: staging domains surprise everyone during an incident. Root cause: nobody watches Certificate Transparency issuance. Fix: start a CT watch for your brand and lookalike domains. Prevention: feed new-certificate events into the SOC queue every day.

3. No first-seen process handling

Symptom: custom tools run for weeks before anyone asks about them. Root cause: the endpoint stack has no concept of "first seen". Fix: enable first-seen blocking for unsigned binaries in user paths. Prevention: review the allowlist monthly and keep it small.

4. Alert fatigue from bad rarity tuning

Symptom: analysts mute the rarity alerts within a week. Root cause: thresholds set without measuring real traffic. Fix: re-baseline with 30 days of data, then tighten. Prevention: track alert-to-case ratios and tune on a schedule.

5. Missing egress visibility

Symptom: beacons are discovered by the victim, not the SOC. Root cause: outbound traffic is trusted by default. Fix: log all egress, then apply filtering to new domains. Prevention: treat unknown egress as a finding, not as noise.

6. Intel that never reaches detections

Symptom: reports are filed away and nothing changes. Root cause: no owner for the intel-to-detection pipeline. Fix: require every accepted report to produce a rule, hunt, or explicit skip note. Prevention: measure conversion in the weekly intel review.

7. No code-repo monitoring

Symptom: staged tooling is found by researchers before your team. Root cause: code platforms are not on any watchlist. Fix: monitor platforms for your brand, tool names, and persona clusters. Prevention: keep a small keyword set and check it weekly.

8. Weak security of your own build systems

Symptom: your build servers behave like attacker staging. Root cause: CI systems with broad credentials and no egress rules. Fix: isolate builders, rotate credentials, and monitor them like production. Prevention: include build infrastructure in pen tests.

9. Treating signed binaries as safe

Symptom: a signed malicious sample bypasses review. Root cause: the signature is read as a verdict, not as a fact. Fix: keep signer reputation, but keep behavior checks too. Prevention: train triage to ask what the binary does, not only who signed it.

10. No destructive-malware tabletop

Symptom: responders treat a wiper like ransomware and lose hours. Root cause: playbooks assume data is recoverable. Fix: run a tabletop where the only option is rebuild. Prevention: add a destructive branch to incident playbooks.

11. Ownership gaps for intel

Symptom: two teams answer the same question differently. Root cause: no named owner for threat intelligence. Fix: name one owner and one deputy, with a weekly slot. Prevention: write the ownership into the team charter.

12. Forgetting home and remote users

Symptom: the first real T4 deployment happens on a home laptop. Root cause: defenses stop at the office edge. Fix: extend endpoint protection and DNS filtering to remote devices. Prevention: include personal-device scenarios in awareness training.

13. Copying vendor rules without tuning

Symptom: an imported rule fires on every developer laptop on day one. Root cause: detections arrived with defaults and were never measured. Fix: run every import in silent mode for two weeks, then tune against your own data. Prevention: make silent-mode testing a required step in the rule checklist.

14. Assuming one product sees everything

Symptom: the team trusts a single agent for all PRE signals. Root cause: nobody owns log coverage as a whole. Fix: map the sources in 5.4 to products and find the empty cells. Prevention: review the coverage map whenever a contract changes.

Habits that keep you sharp

Daily

  • Review first-seen binary and new-domain queues.
  • Check CT-log watch results for your brand.
  • Scan sample feeds for new family names.

Weekly

  • Convert at least one intel report into a rule or hunt.
  • Review alert-to-case ratios and tune one noisy rule.
  • Check code platforms for staged artifacts.

Monthly

  • Test one restore from offline backups.
  • Review cloud accounts younger than 30 days.
  • Rehearse the destructive-malware playbook branch.

None of these mistakes is shameful. Every mature team has made several. What separates good teams is the speed of the fix, and whether the prevention got written down.

Common questions

Should I alert on every new domain my users touch?

No. Alert on the combination: new domain, short certificate, budget hosting, and steady timing. Single facts are too common to be useful on their own.

Can I see the build itself in my cloud tenant?

Only if the workshop runs in your tenant, which happens when accounts are stolen. Burst provisioning by a young account covers both that case and the rented one.

Do I need paid intel feeds to start?

No. ATT&CK pages, vendor blogs, CT logs, and your own logs already support every rule in section 5. Buy feeds once those sources are working well.

How often should PRE rules be reviewed?

Twice a year is enough for most rules. Review sooner when your cloud footprint, proxy platform, or endpoint agent changes.
