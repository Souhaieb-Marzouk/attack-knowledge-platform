    Overview

    A short tour of the technique: what it is, why attackers use it, and what this guide teaches you.

    Inhibit System Recovery means an attacker destroys or disables the ways a computer can be restored. Windows keeps shadow copies (point-in-time snapshots of files), a backup catalog (an index of what backups exist), and a recovery environment (a small repair system that starts when Windows cannot). Attackers delete or turn off these safety nets. After that, a wiped or encrypted machine is much harder to bring back.

    This technique matters because it changes the outcome of an incident. A company with working backups can lose a hundred machines and still be working the next morning. A company whose backups were destroyed first may face days of downtime or a real reason to pay a ransom. Attackers know this, so they often remove recovery options minutes before they start encrypting files. That short window is your best chance to catch them before the damage is done.

    Where it sits in the attack chain

    Attackers reach this stage late. They must already control the machine with admin rights, because only admins can delete shadow copies and change boot settings. When you see this technique, the attacker is done hiding and is ready to cause harm.

    Initial Access→ Execution→ Lateral Movement→ Privilege Escalation→ Impact — T1490

    What you will learn in this guide

    • How attackers remove shadow copies, backup catalogs, and recovery boot options.
    • Which exact log events show up when they do it.
    • Five ready-to-use Sigma rules and matching Splunk queries.
    • How to prioritize this alert during a live incident.
    • How to protect backups so this attack fails.

    Key facts at a glance

    ATT&CK ID
    T1490 — Inhibit System Recovery.
    Tactic
    Impact (availability).
    Platforms
    All official platforms: Windows, macOS, Linux, ESXi (VMware), IaaS (cloud), Containers, Network Devices. Windows is the most targeted.
    Typical actors
    Ransomware groups such as Conti, BlackCat, LockBit, Akira; also state-linked wiper teams.
    Main data sources
    Process creation with command line, service events, file deletion events, cloud audit logs.
    Note

    ATT&CK lists no sub-techniques under T1490. The technique also reaches far beyond Windows, and the official description makes this clear. On ESXi (VMware's virtualization platform), attackers delete or encrypt virtual machine snapshots, for example with vim-cmd vmsvc/snapshot.removeall. In the cloud, they turn off versioning and backup policies, then delete snapshots, database backups, machine images, and older object versions. On network devices, they delete backup firmware images and reload the device, which can leave it completely inoperable. Attackers also delete "online" backups: copies on network shares or in folders that sync to cloud services. This guide covers the Windows core in depth and points to those variants where they matter.

    Written version of the simulation

    The same story in text, for screen readers and for printing. Each step names the action, the evidence it leaves, and what the defender should notice.

    Step 1 — Get in with stolen admin rights

    The attacker signs in to FILE01, a Windows file server. The account is a stolen admin account, sold by infostealer malware (malware that saves passwords and sells them). Nothing looks broken yet. Evidence: a Security event 4624 logon from an unusual source address. The SOC should compare the logon source with known admin workstations.

    Step 2 — Confirm the power

    The attacker runs whoami /priv and checks for admin rights. Deleting shadow copies needs high privileges, so this check matters to them. Evidence: a Sysmon (free Windows logging tool) event 1 process creation with a rare parent chain. The SOC should flag admin tools started from an interactive session that is not a jump host (the hardened server admins must use to reach other servers).

    Step 3 — List the safety nets

    The attacker runs vssadmin list shadows to see the restore points that exist. This is recon for the next step. Evidence: the same command line appears in process logging. The SOC should treat shadow copy enumeration on a server as an early warning, not normal user behavior.

    Step 4 — Delete every shadow copy

    One command — vssadmin delete shadows /all /quiet — removes all restore points. The shadow copy store empties in seconds. Evidence: Sysmon event 1 and Security event 4688 with the full command line. The SOC should alert at high severity on any delete-shadows command outside approved maintenance.

    Step 5 — Erase the backup catalog

    The attacker runs wbadmin delete catalog -quiet to erase the index that tells Windows which backups exist. The backup files may still be on disk, but the system no longer knows about them. Evidence: process events for wbadmin.exe with a delete flag. The SOC should alert on any wbadmin delete action.

    Step 6 — Break the recovery boot options

    The attacker runs bcdedit /set {default} recoveryenabled No. The Windows repair environment will not start after the next reboot. Evidence: a process event for bcdedit.exe with recovery-enabled arguments. The SOC should alert on bcdedit changes to boot recovery settings.

    Step 7 — The SOC connects the dots

    The SIEM (the central log system) connects three events from one host and user within five minutes: shadow deletion, catalog deletion, recovery disabled. It raises one critical incident instead of three ignored alerts. Evidence: a correlated alert with the shared user and host fields. The SOC should build this correlation before the attack, not during it.

    Step 8 — Isolate and restore

    The SOC isolates FILE01 from the network, blocks the stolen account, and starts ransomware checks. The team restores data from the immutable backup copy (a copy nobody can change or delete) that the attacker could not reach. Evidence: incident ticket with timeline and scope. The lesson: one offline backup copy defeats this whole technique.

    3

    Red team / hacker perspective

    Understanding the attacker's choices helps you predict the move and place your sensors. Everything here is described for defense and for labs you own.

    When and why attackers use it

    Timing is the whole point. Ransomware crews run this technique in the final minutes before encryption. They first stop or weaken backups, then start the encryptor, so the victim has nothing left to restore from. Pure sabotage teams do the same before wiping disks, as seen in wiper campaigns such as NotPetya, Olympic Destroyer, and Prestige. A third group uses it slowly: they delete cloud restore points and snapshot chains days ahead, so nobody notices a single missing snapshot.

    The payoff is pressure on the victim. With recovery gone, the victim cannot simply roll back, and backup-based negotiation arguments disappear. ATT&CK procedure records show almost every major ransomware family doing this, including Conti, BlackCat, LockBit, REvil, Babuk, Akira, and Qilin. When nearly every crew uses the same commands, the commands become excellent detection targets.

    How it is performed

    On Windows, the attacker needs local admin or SYSTEM rights, then runs a short set of built-in tools. The commands below are the classic sequence, shown for lab study only. Run them exclusively inside a disposable virtual machine that you own, and take a snapshot before you start.

    Step 2 is the one most ransomware families use, but good crews combine steps. Some delete the C:\WindowsImageBackup folder and the registry backup in C:\Windows\System32\config\RegBack. ATT&CK records Ryuk resizing shadow storage with vssadmin resize shadowstorage, which forces out copies made by third-party backup tools. Others simply stop the Volume Shadow Copy (VSS) service, so new restore points can never be made.

    The same idea appears on every platform in the official description. On ESXi hosts, crews delete snapshot chains with vim-cmd vmsvc/snapshot.removeall. In the cloud, they turn off versioning and backup policies, then delete snapshots, machine images, and prior versions. AWS calls such as DeleteSnapshot and Azure recovery point deletes are the same move, as reported for Storm-0501. They also delete "online" backups on network shares and in cloud-synced folders. On network devices, they delete backup firmware images, reformat the file system, and reload the device, which leaves it completely inoperable.

    Prerequisites and conditions

    What the attacker needs first

    • Local admin or SYSTEM rights on the target host.
    • An interactive shell, an RDP (Remote Desktop Protocol) session, or a remote execution path such as a scheduled task.
    • For domain-wide damage: access to the backup server or its service account.
    • For cloud damage: standing IAM (identity and access management) permissions to delete snapshots or backups.

    What limits them

    • Shadow copies are per-volume and per-host, so they must touch every machine.
    • Immutable or offline backups cannot be deleted with local admin rights.
    • Application control can block the utilities they rely on.
    • Loud commands leave process logs even when the attacker works fast.

    Common variations and attacker mistakes

    Variations exist. Diavol called the Windows COM (Component Object Model) API directly, using the IVssBackupComponents interface to delete snapshots. Other malware uses PowerShell wrappers or native backup tools such as diskshadow.exe in script mode. Newer Windows builds phase out wmic, so attackers reach the same Windows Management Instrumentation (WMI) functions through PowerShell. Each variation still leaves a process trail unless the attacker brings a custom binary that talks to the same APIs in memory.

    Attacker mistakes are useful to know. Running the delete command without admin rights fails silently and shows up as an odd failed command. Typing the tool name wrong leaves typosquatted process names that are trivially detectable. Forgetting domain controllers and backup servers is common, which is why some victims still recover. And the biggest mistake is assuming every backup is reachable: the organizations that survive ransomware are the ones with one copy the attacker never touched.

    Danger · lab-only

    Never run the commands above on a production or shared system. They permanently remove restore points and can make a machine unrepairable. Use an isolated virtual machine with a fresh snapshot, and treat every command as if it were being logged by a real SOC.

    Blue team / SOC perspective

    This technique is one of the most reliable ransomware warnings you will ever get. Here is how to see it, what it leaves behind, and how to triage it fast.

    How defenders can see it

    Process telemetry

    Sysmon event 1 or Security event 4688 with command-line auditing shows the exact tools and arguments. This is the primary and strongest source, because the commands are rare in normal operations.

    Backup system logs

    Backup agents and applications log job failures, catalog changes, and service stops. A backup job that silently stops succeeding across many hosts is a strong secondary signal.

    Cloud audit logs

    AWS CloudTrail (the AWS audit log) and Azure Activity Log record snapshot and restore point deletions with the exact identity that made the call. Unusual deletion of recovery resources is a strong signal in any cloud account. The same logs show versioning and backup policies being turned off before the deletions.

    Artifacts the technique leaves behind

    Why it matters and how it fits the chain

    Treat any T1490 signal as a ransomware timer. Public incident reporting and ATT&CK procedure records show the gap between recovery inhibition and encryption is often minutes to a few hours. If you act inside that window, you can stop the encryption event entirely. If you miss it, this technique is the difference between restoring from backup and negotiating with criminals. It also has forensic value. The user, parent process, and source host in the process event usually point straight at the attacker's entry path. That context helps you scope every other machine they touched.

    Short triage flow

    1. Confirm the event is real

      Open the raw log. Check the user, parent process, and command line. Rule out backup administration by comparing with your change calendar.

    2. Check who and from where

      Was this an admin on a jump host, or a service account from a workstation? Pull the logon events around the same minute for the same account.

    3. Scope immediately

      Search the last 24 hours for the same commands on all hosts. Multiple hosts mean an active campaign, not a mistake.

    4. Protect backups now

      Disconnect or lock backup repositories, pause retention jobs that could rotate copies away, and enable any immutable or air-gapped mode you have.

    5. Contain and escalate

      Isolate affected hosts, force-reset the involved account, and page the incident commander. Prepare restoration steps before encryption starts.

    Good practice

    Write the triage steps above into your incident runbook before you need them. During a live event, the team that follows a prepared checklist protects backups minutes faster than the team that improvises.

    5.1 Regulation mapping

    This technique attacks your ability to recover data, so it maps directly to backup and continuity controls. Auditors ask for proof that backups exist, that they are protected, and that deletion is monitored. The table below shows what each framework expects and the evidence a detection program provides.

    Framework and controlWhy it appliesExpected evidence
    GDPR — Article 32 (security of processing) Requires the ability to restore availability of and access to personal data after an incident. Destroyed backups make restoration impossible, turning an attack into a reportable, prolonged breach. Documented backup and restore procedures, tested restoration records, alerts on backup deletion, incident reports showing recovery time.
    HIPAA Security Rule — §164.308(a)(7) contingency plan Covered entities must maintain a data backup plan, disaster recovery plan, and emergency mode operation plan for electronic protected health information. Written contingency plan, backup success and failure reports, restore test results, evidence that backup tampering is monitored.
    ISO/IEC 27001:2022 — A.8.13 (information backup), A.8.16 (monitoring activities) Backup copies must be maintained and protected, and activities that could undermine them should be monitored. T1490 is the failure case for both controls. Backup policy with immutable or offsite copies, monitoring rules for backup changes, alert tickets for recovery inhibition attempts.
    SOC 2 — CC7.4 (incident response execution), A1.2 (availability recovery infrastructure) Trust services criteria expect tested recovery and detection of attacks. Deleting recovery mechanisms defeats the availability commitment auditors check. Runbooks, tabletop or live restore drills, detection rule documentation, evidence of alerts and response for backup tampering.
    PCI DSS — 12.10.x (incident response plan and testing) Organizations handling cardholder data must prepare for scenarios that destroy or lock data, which is exactly what T1490 enables. IR plan covering ransomware and wiper scenarios, quarterly tests, records of backup integrity checks and restore exercises.
    NIST SP 800-53 Rev.5 — CP-9 (system backup), CP-10 (recovery) Federal and industry-aligned controls that require protected backups and tested recovery, including protection of backup copies at rest. Control implementation statements, backup protection configuration, monitoring coverage proof, restoration test logs.

    5.2 Threat intelligence

    Intelligence makes your detection rules stronger and your priorities honest. For this technique, the intelligence picture is unusually clear, because nearly every destructive campaign since 2017 has used the same small set of commands. Collect from several source types, then record how confident you are in each finding before you change a rule or a runbook.

    MITRE ATT&CK

    Start with the technique page and its procedure examples. The list of malware and groups that use T1490 is long and current, which makes rule coverage easy to justify.

    Vendor reporting

    Security vendor blogs publish exact commands, service names, and timelines for each crew. Turn their incident timelines into your detection logic and tuning notes.

    OSINT and ISACs

    Open-source intelligence (OSINT) sources share indicators and tactics early. Examples are advisories from the US Cybersecurity and Infrastructure Security Agency (CISA) and bulletins from sector ISACs (Information Sharing and Analysis Centers). Their sector-specific advice tells you which crews target organizations like yours.

    Commercial feeds

    Paid feeds add actor tracking, infrastructure, and malware families. Use them for context and prioritization rather than as a replacement for your own telemetry.

    Internal telemetry

    Your own logs are the most valuable source. Failed deletion attempts, unusual backup job behavior, and near misses show what attackers actually try in your environment.

    Confidence levels

    High means several independent reports plus your own sightings. Medium means one solid public report. Low means a hypothesis that still needs testing. Write the level next to every intelligence note.

    5.3 Threats ranking and categorization

    Five realistic threats cover this technique well. The rank reflects how likely the threat is and how much damage it causes when it works. Each threat has a code from THR-01 to THR-05, and sections 5.4 and 5.5 reuse those codes. Preconditions describe what an attacker must already have. The justification explains the rank, so you can defend it in planning meetings.

    ThreatRankPlatformDescription and preconditionsImpact and justification
    THR-01 — Shadow copy deletion with vssadmin or wmic Critical Windows One command removes all local restore points. Preconditions: local admin rights and process execution on the host. Removes the fastest recovery path right before encryption; documented in nearly every major ransomware campaign. Highest likelihood plus severe impact.
    THR-02 — Backup catalog deletion with wbadmin High Windows Destroys the index that describes existing backups. Preconditions: local admin rights on a host holding backup metadata. Restore tooling loses knowledge of valid backups, slowing recovery by hours or days. Less universal than shadow copy deletion, hence High.
    THR-03 — Recovery environment disabled with bcdedit High Windows Turns off the repair boot path so wiped or broken systems cannot self-repair. Preconditions: admin rights and boot configuration access. Multiplies the damage of a wiper and complicates digital forensics and incident response (DFIR). Rarer than shadow copy deletion but still common across destructive families.
    THR-04 — Deletion of backup files (WindowsImageBackup, RegBack) Medium Windows Removes the actual backup files of built-in Windows backup. Preconditions: admin rights plus file deletion on the host. Matters only where Windows Server Backup is used; third-party backup products dominate large estates, which caps the likelihood.
    THR-05 — Cloud snapshot and restore point deletion High IaaS Deletes EBS snapshots and Azure restore point collections, or turns off versioning and backup policies first. Preconditions: an IAM identity with deletion permissions. Recovery data may be gone in minutes across regions. Rising sharply with cloud-focused extortion crews such as Storm-0501.

    Each threat below lists the log sources that see it, the fields that matter, and what normal and suspicious behavior look like. Each threat also shows its detection logic in plain words. A realistic event example follows each table so you can validate your pipeline against real shapes.

    Threat 1 (THR-01) — Shadow copy deletion with vssadmin or wmic

    AspectDetails
    Log sourcesSysmon event 1 (process creation); Security event 4688 with command-line auditing; EDR (endpoint detection and response) tooling.

    5.5 Sigma rules and Splunk SPL

    MITRE's official detection strategy for this technique is DET0329, "Behavioral Detection for T1490 - Inhibit System Recovery". Its first analytic watches for process chains that use native utilities such as vssadmin, wbadmin, diskshadow, and bcdedit. The five Sigma rules below put that strategy into practice, one per threat, each with a matching Splunk query. The rules target Windows Sysmon and AWS CloudTrail. If you collect Security 4688 instead of Sysmon, swap the logsource and keep the field logic. The Splunk queries assume the index and sourcetype conventions listed below; adjust the index names to your environment and document the change. An allow-list is a short list of approved users, hosts, or roles that a rule may ignore.

    Field assumptions for Splunk

    index=sysmon holds Sysmon XML events with fields like Image, CommandLine, TargetFilename. index=aws holds aws:cloudtrail data with JSON fields like eventName and userIdentity.arn. Field extraction must be enabled for XML inputs before these queries work.

    Rule 1 (THR-01) — Shadow copy deletion

    Mapping note: the Sigma Image|endswith becomes a wildcard match on the full path. The two contains terms become repeated CommandLine tokens joined by AND. False positives: approved shadow copy cleanup. Tuning: allow-list your change windows and known backup admin accounts. Consider raising severity when the parent process is cmd, PowerShell, or WinRM (Windows remote management).

    Rule 2 (THR-02) — Backup catalog deletion

    Mapping note: the same one-to-one field mapping as rule 1. False positives: rare, documented catalog repairs. Tuning: require a matching change ticket before closing, and escalate immediately if the same host also matched rule 1.

    Rule 3 (THR-03) — Recovery disabled

    Mapping note: both Sigma selections collapse into one raw wildcard match in Splunk. Keep the terms in order, so the recoveryenabled*no pattern does not drift. False positives: provisioning hosts. Tuning: exclude imaging servers and MDT (Microsoft Deployment Toolkit) or Intune task sequences by host group. Watch for new bcdedit paths outside System32.

    Rule 4 (THR-04) — Backup file deletion

    Mapping note: Sigma contains maps to wildcard path matching. Sysmon event 26 covers deletes on hosts without archive mode. False positives: legitimate backup rotation. Tuning: allow-list the wbengine service (the Windows Server Backup engine) and known backup binaries per host. Alert only on interactive shells and unknown images elsewhere.

    Rule 5 (THR-05) — Cloud snapshot deletion

    Mapping note: CloudTrail JSON fields map directly to Splunk index-time or search-time extractions. The Sigma list of event names becomes the IN clause. False positives: scheduled lifecycle deletions under fixed role ARNs (Amazon resource names). Tuning: allow-list those automation roles, then page on any interactive identity, new source IP, or deletion volume above your daily baseline. For Azure, build the same rule for Microsoft.Compute/snapshots/delete and Microsoft.Compute/restorePointCollections/delete, as reported for Storm-0501.

    6

    Real-world case study

    NotPetya, June 2017: the best-documented example of this technique at global scale. It is the reason many SOCs treat shadow copy deletion as a critical, page-now alert.

    Context

    This case study describes a real, documented incident. It is based on public reporting, not a training scenario. Sources include the MITRE ATT&CK procedure records for NotPetya, ESET's and Kaspersky's outbreak analyses, Andy Greenberg's Wired reporting on the Maersk rebuild, and Maersk's annual report. NotPetya presented itself as ransomware but was built to destroy. It spread through a compromised Ukrainian accounting software update, then moved laterally with stolen credentials and the EternalBlue exploit (a Windows file-sharing flaw). A.P. Moller-Maersk, the global shipping giant, was among the hardest-hit companies. Terminals stalled, booking systems stopped working, and tens of thousands of machines needed rebuilding. In ATT&CK terms, the attack moved through Initial Access, Lateral Movement, and Impact, with T1490 as the final preparation for the wipe. On every host it touched, the attack ran the exact T1490 sequence this guide describes, so no machine could simply be rolled back.

    Timeline

    1. 27 June 2017 · ~10:30 local
      Delivery through a trusted update

      The M.E.Doc accounting package pulled a poisoned update and launched NotPetya on thousands of Ukrainian workstations, including systems connected to international companies.

    2. Minutes after infection
      Credential theft and lateral movement

      The payload harvested credentials in memory and spread over SMB (the Windows file-sharing protocol) and admin shares. It crossed networks and partner links the same way.

    3. On each host
      Recovery inhibited (T1490)

      On every machine it could reach, NotPetya ran vssadmin to delete shadow copies. It ran wbadmin to delete the backup catalog and bcdedit to disable recovery. Then it cleared event logs to slow investigation.

    4. ~1 hour after infection
      Forced reboot and wipe

      The malware forced a reboot and overwrote the boot structures. It then rendered the filesystem unusable and displayed a ransom note that was never meant to be honored.

    5. 27 June · afternoon
      Global impact becomes visible

      Maersk, Merck, FedEx TNT, and hundreds of other organizations lost machines at once. Shipping terminals and production lines stopped within hours.

    6. Days to weeks
      Manual rebuild at scale

      Because shadow copies and catalogs were gone, teams rebuilt machines from images. Maersk restored its domain by recovering one domain controller in Ghana that had lost power during the attack and was therefore untouched.

    Detection point

    The cleanest detection moment was the process event for vssadmin delete shadows /all /quiet, which fired on every host minutes before the wipe. Organizations with command-line logging saw the attack coming; those without it saw only mass reboot storms and dead machines. The lesson is clear: the T1490 signals are the ransomware early warning.

    Containment

    Teams disconnected networks, blocked the SMB ports used for spread, took the compromised software vendor offline, and powered down unaffected systems to preserve them. Password resets stopped the credential-based spread once accounts were locked down.

    Eradication

    Every affected machine needed a full rebuild, since the payload destroyed the operating system itself. Removable media and clean images replaced network-based deployment while the network was still untrusted, and the vulnerable update client had to be removed everywhere.

    Recovery

    Restoration came from golden images, surviving offline systems, and the famous Ghana domain controller. Where shadow copies had survived on isolated machines, files were recovered; where backups shared the destroyed network, they were lost with everything else.

    Impact and consequences

    Maersk reported costs between 250 and 300 million US dollars and rebuilt around four thousand servers and forty-five thousand PCs. Merck disclosed hundreds of millions in losses, and the total global damage is commonly estimated near ten billion dollars. Insurance disputes followed, because courts had to decide whether a state-linked destructive attack counted as an act of war. The attack reshaped how boards think about cyber risk.

    Team response and communication

    Response teams worked from printed runbooks because email and chat systems were down, which proved the value of out-of-band communication channels. Daily executive briefings set one clear priority: protect what still works, then rebuild in business-critical order. External incident response partners, vendors, and even competitors shared indicators, showing that pre-built trust networks shorten outages.

    Lessons learned

    • Keep one backup copy immutable or offline; it is the single control that defeats this technique.
    • Monitor backup deletion and command lines on servers; the attack announced itself on every host.
    • Segment networks and restrict admin shares so one infection cannot rebuild itself everywhere.
    • Test domain recovery, not just file recovery; identity is the hardest thing to lose.
    • Maintain out-of-band communication and printed procedures for the worst day.
    7

    Mitigation and defense

    You cannot stop every attacker from reaching one machine, but you can make recovery inhibition pointless. The controls below are ordered by how much risk they remove.

    Enterprise controls by domain

    Backup architecture

    Follow the 3-2-1-1-0 pattern: three copies, two media types, one offsite, one immutable or offline, and zero restore-test errors. The offline copy is the one an attacker with full admin rights still cannot delete, which is exactly what T1490 tries to do.

    Identity and privileges

    Separate backup administration from server administration. Use dedicated accounts with multi-factor authentication (MFA) for backup consoles. Remove standing deletion rights from cloud identities. ATT&CK mitigation M1018 (User Account Management) points here.

    Endpoint hardening

    Use application control to block or gate the utilities this technique abuses, such as diskshadow, on servers where they have no business running. This is ATT&CK mitigation M1038 (Execution Prevention). Enable tamper protection so security services cannot be stopped silently. M1028 (Operating System Configuration) adds technical controls as well. They stop the disabling of recovery services and the deletion of recovery files.

    Logging and monitoring

    Ship Sysmon or 4688 with command lines from every server, plus backup application and cloud audit logs, into the SIEM. Deploy the five Sigma rules from section 5 and review their alerts weekly.

    Cloud-specific protection

    Enable snapshot deletion protection. Use service control policies (SCPs) to restrict delete calls, as ATT&CK mitigation M1018 suggests. Turn on versioning for object storage, so deleted objects can be rolled back within a window. In cloud terms this also matches M1053 (Data Backup), which says to copy backups to other accounts or regions.

    Response readiness

    Write a recovery-inhibition runbook: who isolates, who protects the backup repository, who contacts the backup vendor, and who decides on restoration. Rehearse it twice a year with the real teams.

    Home and small office advice

    Protect your own recovery

    • Turn on File History (Windows) or Time Machine (macOS) to an external drive.
    • Disconnect the backup drive when the copy finishes, so ransomware cannot reach it.
    • Keep one cloud copy with version history enabled, such as OneDrive or iCloud file versions.
    • Create the vendor recovery USB once per year and store it with the backups.

    Small-office quick wins

    • Never let the only backup account be the same account people use daily.
    • Turn on multi-factor authentication for the backup console and the cloud account.
    • Once a quarter, restore one important file from backup and time how long it takes.
    • Keep a printed page with the backup vendor support number and your license keys.
    Good practice

    The strongest message from every major incident: attackers cannot delete what they cannot reach. One backup copy on disconnected or immutable storage turns T1490 from a catastrophe into a small, recoverable incident.

    Healthy operating habits

    Daily

    • Confirm critical log sources are reporting, including backup servers.
    • Review every recovery-inhibition alert from the last 24 hours.
    • Check backup job success dashboards for silent failures.

    Weekly

    • Walk one T1490 alert end-to-end and time the triage.
    • Review new exclusions and tuning changes with a second reviewer.
    • Sync with the backup team about scheduled maintenance windows.

    Monthly

    • Test one rule against a lab host running the technique safely.
    • Review IAM permissions for backup and snapshot deletion.
    • Update actor notes from new public incident reports.

    Cheat sheet and quick reference

    Everything important on one screen, for the wall and for the incident channel.

    Key facts

    Technique
    T1490 — Inhibit System Recovery.
    Tactic
    Impact.
    Platforms
    Windows (most targeted), macOS, Linux, ESXi, IaaS, Containers, Network Devices.
    What it does
    Deletes shadow copies, backup catalogs, and recovery boot options.
    Typical timing
    Minutes to hours before encryption or wipe.
    Signature commands
    vssadmin delete shadows /all /quiet, wbadmin delete catalog -quiet, bcdedit /set recoveryenabled no.
    Official mitigations
    M1053 Data Backup, M1038 Execution Prevention, M1028 Operating System Configuration, M1018 User Account Management.
    Best single defense
    One immutable or offline backup copy.

    Response checklist

    • Confirm the raw event: user, parent process, command line, host.
    • Isolate the host from the network immediately.
    • Disable or reset the involved account and review its recent logons.
    • Search all hosts for the same commands in the last 24 hours.
    • Protect backup repositories: lock, snapshot, and disconnect where possible.
    • Check for encryption activity: canary files (planted decoy files that alert when touched), mass renames, high CPU from unknown processes.
    • Record the exact commands, user, and parent process in the incident ticket for later threat hunting.
    • Preserve forensic copies before rebuilding, because recovery attacks destroy evidence too.
    • Notify the incident commander and open the recovery-inhibition runbook.
    • After containment, verify one restore path works before declaring safety.
    • After the incident closes, confirm backup jobs succeed again and review how the attacker got admin rights.

    One-line summary

    If recovery is being inhibited, the attack is already in progress on your systems. Treat the alert as a ransomware emergency, protect the backups first, and act fast. The organization that responds in minutes keeps its data. The one that spends hours debating attacker identity loses it.
