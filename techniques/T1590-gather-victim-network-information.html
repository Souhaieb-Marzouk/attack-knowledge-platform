01

Overview: What Is This Technique?

MITRE ATT&CK is a free, public catalog of attacker behavior. It lists the steps that real intruders take, one by one. Each step is called a technique and has an ID, for example T1590. Techniques sit under goals called tactics. One tactic is Reconnaissance: the attacker collects information about a target before any attack starts. Security teams, tool makers, and governments all use this catalog, so everybody can talk about attacks in the same clear language.

T1590, Gather Victim Network Information, describes the research an attacker does about a victim's networks before touching them. The official description says the information can include administrative data, for example IP ranges and domain names, plus details about the network's topology and operations. Attackers collect it in three main ways. They can scan actively (the T1595 Active Scanning technique). They can phish for information (the T1598 technique). Or they can read online data sets with the T1596 Search Open Technical Databases technique, which needs no scan at all. The picture they build shows them where the doors are. It helps them plan more research. It helps them set up their own attack resources (T1583 Acquire Infrastructure, T1584 Compromise Infrastructure). And it can reveal a quiet way in, for example through a trusted partner (the T1199 Trusted Relationship technique).

This page is the parent page of a series of seven. Think of the six sub-techniques as six doors into the same technique family. Each door looks at one kind of network fact. The attacker rarely uses only one door. They walk through several doors, combine the answers, and build one map. This page explains the whole family, and every section here works for all six doors. Each sub-page then goes deep on one door with its own simulation, rules, and scenario.

Why should you care?

  • The victim sees almost nothing. Most of this phase runs on public data, so normal security tools stay silent. You need a special view to notice it at all.
  • It shapes everything that follows. The entry points an attacker picks, such as a VPN portal or a mail server, come directly from this research.
  • Traces exist, but only at the edge. Public DNS logs, firewall logs, and web server logs hold the few signals there are. Section 5 shows the exact lines.
  • You can measure yourself the same way. Run the same public checks against your own company and close the gaps before attackers use them.
  • Detection engineers get a head start. Five ready Sigma rules, matching Splunk SPL, and a catalog of log patterns are included in Section 5.

  • Five Sigma rules with Splunk SPL, mapped to the five worst threats of this family.
  • A real campaign story: how HAFNIUM mapped Exchange servers before the 2021 exploitation wave.

What the story teaches

Scenes 1 to 3 are completely passive. The attacker reads documents that other people publish: search results, web pages, registry records, and job posts. Nothing here can alert your SOC, because no packet reaches you. This is the uncomfortable truth of the Reconnaissance tactic: the first third of the attack happens entirely on other people's servers.

Scenes 4 to 6 are the light active checks. The attacker must confirm that the names really resolve, that the doors really answer, and that the banners really say what the databases claim. Each check is small on purpose. One DNS question looks like any visitor. One short connection to port 443 looks like a user who gave up. The danger is not any single packet; it is the pattern over days.

Scene 7 shows why attackers accept even those small risks. The map turns scattered facts into a plan: four doors, one old appliance, one trusted vendor. Scene 8 shows the same story from your side. The SOC holds real evidence, but only in edge logs, and only if the logs are kept long enough to connect. That is the whole argument of this guide in eight scenes.

03

Red Team View: How Attackers Do It

This section explains the attacker method so you can predict it and test your defenses against it. It is written for learning and defense only. Run network research against systems you own, or against systems you have written permission to test.

When is it used?

Network profiling happens early, during attack planning and scoping. A group picks a target, then studies its network before any other step. A ransomware crew may spend several weeks here before sending one phishing mail, because a good map saves many loud mistakes later. Initial access brokers do the same work and sell the results. Red teams also use this technique on purpose, to test whether the blue team would notice a real intrusion being prepared.

How is it done, step by step?

Professional attackers start passive and stay quiet for as long as possible:

  1. Pick the scope: one company and its main domain.
  2. Collect domains and subdomains from search engines, certificate logs, and public records.
  3. Read WHOIS and routing databases for owners, providers, and address ranges.
  4. Resolve names to addresses and group them into blocks and networks.
  5. Read scan databases for exposed services, banners, and versions.
  6. Map trust links: vendors, partners, and outsourced IT providers.
  7. Add a few light active checks: some DNS questions, one banner read.
  8. Write the profile down and mark entry candidates, such as the VPN portal.

Heavy active scanning is a separate technique (T1595, Active Scanning). Careful attackers try to avoid it here, because it is the part that can be seen. The quiet parts of T1590 produce almost no events on the victim side.

Where is it done from?

From anywhere. A rented cloud server, a normal laptop, or a virtual private server in another country is enough. Every query looks like ordinary internet traffic, and the source can change from day to day. Attackers also use hosting providers and commercial VPN exits, because that traffic is hard to tell apart from normal users. This is why you cannot block your way out of the problem: the researcher has no fixed address to block.

Why do attackers invest in it?

The finished profile answers three questions. Where can I get in: a VPN portal, a mail server, a web shop, or a partner link. What will hurt me: security appliances and their versions, so exploits can be picked with care. What must I avoid: paths that are well monitored or that belong to somebody else. A correct map also prevents embarrassing mistakes, for example attacking an address block that belongs to a different organization than the target.

What is needed before starting?

Almost nothing. An internet connection and patience are enough, and most tools below are free or have free levels. The skill needed is reading public records carefully, not hacking. This low cost is the main reason almost every serious attack starts with this technique.

A safe lab example

The commands below only read public records for documentation domains and test addresses. They are safe to type in a lab.

safe-lab-profile.sh · read-only public lookups
# Safe: documentation domains and test addresses only.
# Run this against your OWN lab assets or with written permission.
whois 192.0.2.10
whois example.com
dig +short A    mail.example.com
dig +short A    vpn.example.com
dig +short mx   example.com
dig +short ns   example.com
host -t txt example.com
Warning

Only test what you own or have permission for. Looking up documentation domains like example.com is a harmless read of public data. But the same commands pointed at a real company without permission can break laws and company rules. Practice on lab systems and on domains you control.

How attackers stay quiet

The quiet parts of this technique share three habits. First, they use infrastructure that looks ordinary: home connections, cloud hosts, and commercial VPN exits instead of obvious bulletproof servers. Second, they spread queries over time, so no single hour looks strange. Third, they prefer stored answers over live probes. Reading a scan database is free of noise; scanning yourself is not. Defenders can copy all three habits for their own external reviews. Scan yourself the way an attacker would, from rented infrastructure, slowly, and compare the result with what your edge logs recorded.

04

Blue Team View: How Defenders See It

From the defender side, T1590 is the attack phase you will most likely never see directly. The work here has three parts. Reduce what is public. Know your own external surface better than the attacker does. And catch the few touches that this research must make.

Why detection is hard

Almost all of this technique happens outside your walls. WHOIS servers, routing databases, search engines, and scan databases log their users, but you cannot read those logs. Passive research creates zero events in your SIEM, which is the system that collects logs and raises alerts inside your company. Even the active parts are small: a handful of DNS questions or one connection that reads a banner hides easily inside normal internet noise. This is why defenders treat T1590 as a low-signal phase and prepare for it in a different way.

Where traces still appear

A few parts of the research must touch systems you control, and those touches can be recorded. Check these places:

  • Public DNS server logs: questions about your zones from outside, zone transfer attempts (AXFR), and long lists of NXDOMAIN answers. AXFR is a request for a full copy of your DNS records. An NXDOMAIN answer means a guessed name that does not exist.
  • Firewall and IDS alerts: scan patterns against your public ranges, even slow ones spread over days. IDS means intrusion detection system, a sensor that watches traffic for known bad patterns.
  • Web server logs: requests to paths such as /owa, /ecp, or /admin, and HEAD requests that only read headers, which is a classic banner check.
  • Zeek connection logs: many short connections from one source that end at once, which is the banner-grab shape shown in the simulation.
  • Certificate Transparency: public logs of every TLS certificate issued. New certificates for your brand, or for lookalike domains, appear there within hours.
  • Scan databases: your own assets are already listed in services like Shodan and Censys. Looking yourself shows exactly what an attacker sees, including banners and versions you forgot about.

Why early visibility matters

A recon alert is cheap to check and expensive to ignore. Most intrusions give a small outside hint days or weeks before the big event: a scan burst, a set of odd DNS questions, a probe of the VPN portal. If you log the edge and keep the history, you can connect one quiet alert today to one serious incident next month. If you do not, the attacker keeps the time advantage, and you start your investigation at the moment of the breach instead of before it.

How it fits the attack chain

T1590 is a Reconnaissance technique, so it sits before Initial Access in every attack chain. It works together with its sibling techniques: T1589 collects facts about people, T1592 collects facts about hosts, and T1593 collects facts from open websites. The network profile that T1590 produces feeds three follow-up paths. It guides more reconnaissance, for example active scanning against the doors it found. It guides resource setup, when the attacker rents or compromises infrastructure that fits the target. And it guides initial access, for example one quiet login on the VPN portal that the research discovered, or an intrusion through a trusted partner. When you investigate an intrusion, always reconstruct what the attacker knew about your network beforehand: it explains which entry points were planned and why the attack took the shape it did.

Defender mindset

You cannot stop someone from reading public data. You can decide what is public. Treat your external attack surface as a product you ship: inventory it, shrink it, and monitor the small part of the research that must touch your systems. Assume the attacker already holds a map of your network. Your job is to make that map wrong.

No regulation names T1590 directly. Regulators ask for something simpler: know your network, watch it, record evidence, and be ready to detect and report incidents. Pre-attack reconnaissance is often the first observable step of an incident, so the controls below connect to it directly.

5.2Threat Intelligence

Threat intelligence turns isolated log lines into a story. For T1590 the story is: which actors profile networks, how long they take, and what they do next. The sources below are a good starting kit, and most of them are free. OSINT (open source intelligence) means information collected from public sources, which is exactly what this technique is made of.

Set a fixed rhythm for reading these sources. One hour a week is enough to stay current on the technique family. Store what you find in one place: a shared folder or a ticket, with the date, the source, and one line on what changed for you. Intelligence that nobody can find later is only reading, not intelligence.

Useful sources

Intel workflow

  1. Collect: pull ATT&CK updates, CISA advisories, and your own scan-database change reports on a fixed weekly schedule.
  2. Analyze: match each new report to your own exposure and ask one question: would this actor method work against our edge today?
  3. Apply: turn findings into detections (the Sigma rules below), configuration changes (banners off, AXFR denied), and scan-database cleanup.

Close the loop: when an alert fires, record which intelligence item predicted it, then tune the rule or the threshold. Feed non-sensitive findings back to your sector sharing group (ISAC), so peers can watch for the same sources.

Keep the loop small and honest. One page per finding is enough: the source, the date, the actor, the door they used, and the rule that now watches for it. That page is also your memory when the same actor returns a year later under a new name.

Severity says nothing about how loud the attacker is; the quietest threat here is the one that feeds the worst breach. The top five threats map one to one to the Sigma rules in 5.5.

Use the ranking to decide where your tuning time goes. Rules for Critical and High threats deserve monthly reviews and real test traffic. Rules for Low threats can run with default thresholds until an incident gives you a reason to tune them. 5.4Logs and Patterns

These are the log sources where pre-attack network research leaves real traces. Each block shows fake but realistic entries with safe documentation values, followed by the patterns worth alerting on. Keep these logs long enough for slow scans to appear: weeks, not hours. The five threats from 5.3 appear here in the same order as the rules in 5.5, plus one host-level witness.

Before the examples, one word about where these logs live. The firewall and the DNS server sit at the edge, so their logs answer "who touched us from outside". The web server sits a step further in, so its log answers "what did they ask for once they could reach us". Zeek sits beside the edge and records connections the firewall may never alert on. The Windows host proves that some touches reach real systems. Together they cover every threat from 5.3.

Two habits make these patterns work in practice. First, store enough detail to rebuild a source's history: who scanned you, when, and at what rate. Second, agree on one field that joins the sources together. The external source IP is the practical choice, because it appears in firewall, DNS, web, and Zeek logs alike. When four logs agree about one address, your confidence stops being a guess.

What to look for:

  • Many block records from one source IP in a short window, across different destination hosts and ports. Sigma rule R1 catches exactly this burst shape.
  • Scans spread over hours with slowly growing source ports. That is the low-and-slow version, so add long-window rules too.
  • Connect attempts to management ports that should never be reachable from outside, for example 22 (SSH) or 3389 (RDP).
  • The same source later appearing in DNS or web logs. Correlation by source IP turns three small events into one story.

  • The same SourceIp appearing in firewall, DNS, and web events. Keep Sysmon data for public hosts even when volume is high.

A short note on retention before we move to the rules. A burst rule needs minutes of history. A low-and-slow scan needs days. A campaign like the HAFNIUM story in Section 6 needs weeks, because the quiet map was finished long before the exploitation started. If your edge logs are deleted after seven days, you can still catch bursts. But you lose the memory that connects one alert to the next. Ninety days hot, and a year cold, is a defensible target for these four sources.

5.5Sigma Rules (Detection as Code)

Sigma is an open rule format for log detection. You write the rule once, and a converter produces the query for your SIEM, whatever the product. The five rules below map one to one to the top five threats from 5.3, and each log source matches the examples shown in 5.4. Each rule is followed by a ready Splunk SPL version.

Tune before you trust. Every network has a different noise floor, so the thresholds below are starting points, not final answers. Deploy each rule in test mode first, collect two weeks of hits, and adjust the count until the alerts match real recon in your traffic. Add your approved scanners to an allowlist so the rules stay quiet for friendly noise.

medium R1 - External Port Scan Burst Against Public Range

This rule catches many blocked inbound connections from one external source inside five minutes, which usually means someone is mapping open doors. Level: medium. Main false positive: an approved vulnerability scanner, so keep an allowlist of scanner sources.

external_port_scan_burst.yml
id: 4f2b7c31-9a5e-4d62-8b17-3c9f21e5a7d4
title: External Port Scan Burst Against Public Range
status: stable
description: >
  Many blocked inbound connections to public-facing hosts from one external
  source in a short window. This pattern often appears during pre-attack
  network reconnaissance, when an intruder maps open services before an
  intrusion (MITRE ATT&CK T1590).
references:
  - https://attack.mitre.org/techniques/T1590/
author: Detection Engineering Team
date: 2026/09/29
logsource:
  category: firewall
  product: pfsense
  service: filterlog
detection:
  selection:
    action: deny
    dir: in
  condition: selection | count() by src_ip > 30
  timeframe: 5m
falsepositives:
  - Approved vulnerability scanners
  - Internet-wide scanning services that probe many ports
level: medium
tags:
  - attack.reconnaissance
  - attack.t1590

Splunk SPL - same logic (adjust index and sourcetype to your environment):

Splunk SPL · R1

Real-World Scenario: Mapping the mail doors — HAFNIUM and Exchange

This scenario is based on a real, well-documented campaign: the 2021 HAFNIUM exploitation of on-premises Microsoft Exchange servers. The Microsoft Threat Intelligence Center (MSTIC) reported it in March 2021, and CISA summarized it in advisory AA21-110A. The campaign parts follow that public reporting. The victim's inner view is a realistic composite of how affected teams responded, with all names and numbers invented and simplified for learning.

Background

HAFNIUM is a threat group that Microsoft's MSTIC began tracking and named in early March 2021. In the campaign, the group gathered fully qualified domain names (FQDNs) for targeted Exchange servers in the victim environment. It then exploited four zero-day vulnerabilities in Exchange Server 2013, 2016, and 2019. The first and most important one was CVE-2021-26855, a server-side request forgery (SSRF) flaw. SSRF means the attacker tricks the server into sending requests for them. Microsoft released out-of-band patches on March 2, 2021. Before that date, any internet-facing Exchange server was a door with no lock, and tens of thousands of organizations eventually found webshells or worse.

The campaign shows T1590 in its natural role. The attackers did not guess which servers to hit. They first worked out which names pointed at Exchange and OWA, which servers answered on the mail ports, and which doors were open. Then the exploits followed.

Attack and detection timeline

Late 2020 · before the campaign

The quiet map of the mail doors

From rented infrastructure, the attackers profiled their targets' public networks. Public records and DNS answers pointed at names like mail. and autodiscover. under the victim domains. Scan-database data and banner reads showed which servers ran Exchange and which answered on the mail and web ports. Not one packet of this phase looked unusual at the edge.

Early 2021

The first intrusions begin

Public reporting later traced the first known intrusions to early 2021, months before any patch existed. Using CVE-2021-26855, the attackers sent crafted requests that made the Exchange server itself talk to internal services. The server's own trust did the work, so the requests came from the inside and blended with normal traffic.

January to February 2021

Webshells on the mail servers

The attackers wrote webshells to predictable web paths on the Exchange servers. CISA's advisory AA21-110A documents China Chopper among the webshells used. A webshell is a small hidden page that runs attacker commands in the browser. From there the attackers could act on the server at will.

February 2021

Escalation and data theft

With the webshells in place, the campaign moved to remote execution and theft of data from mailboxes, as MSTIC described. Mailboxes hold everything: contracts, research, credentials in mail threads. For many victims, the data was leaving while the environment looked normal.

Late February 2021

The scale becomes visible

Telemetry showed the same exploitation pattern across sectors MSTIC had long associated with the group: infectious disease researchers, law firms, higher education institutions, defense contractors, policy think tanks, and NGOs. This was not one breach. It was one method repeated against many quiet maps at once.

March 2, 2021

Disclosure and patches

MSTIC published its HAFNIUM report and Microsoft released out-of-band security updates for Exchange Server 2013, 2016, and 2019. Defenders worldwide woke up to a race: patch the servers, then find out whether someone had already walked in.

March 2021

Patch, hunt, repeat

Organizations patched and then hunted for webshells, because patching closed the door but did not evict the guests. Detection guidance focused on web server logs showing POST requests to unusual paths and on process events where the Exchange worker process spawned scripting tools.

April 2021

CISA summarizes the campaign

CISA published advisory AA21-110A, pulling the timeline, the vulnerabilities, the webshells, and the detection and mitigation steps into one public document. The advisory remains a clean reference for how a recon-led campaign becomes a mass exploitation event.

How it was detected

In the composite victim team, two signals came together. First, the web team noticed web server logs full of POST requests to unusual paths. The clearest example was files dropped under /aspnet_client/, a path that should never receive requests. Second, the Windows team saw Sysmon process creation events where the Exchange web worker process spawned command interpreters and scripting tools. The SOC joined the two: the same server had both the odd web requests and the odd child processes. That combination is the campaign's signature, and it was already public in CISA's detection guidance.

Containment

The team patched every Exchange server the same day the guidance reached them. They then hunted webshells across all web roots and removed every hit, because a patch alone leaves an installed webshell running. They rotated credentials exposed in mail traffic and isolated one server that showed clear exploitation until it could be rebuilt. Access from the attacker's infrastructure was blocked at the edge while the hunt continued.

Recovery

The exploited server was rebuilt from clean media and rejoined with fresh certificates. The team re-enabled services one by one and watched the web and process logs closely for a full week. Mail forwarding rules and delegate access were reviewed mailbox by mailbox, because attackers who read mail leave quiet back doors there. External scan-database entries for the rebuilt servers were rechecked to confirm the version was current.

Impact and consequences

Business impact: three weeks of response work, an emergency patch window for every Exchange server, and an external forensic review. Some mailbox data had left the environment, which meant partner notifications and a regulator-ready incident file. Technical impact: the company learned that its mail doors had been mapped and probed for a long time. The edge logs held the evidence. Nobody had been reading them.

Lessons learned

  • The recon phase decided the campaign. The attackers knew where the mail doors were before the exploits existed, so the defense had to know its own doors even better.
  • Web server and process logs caught what the perimeter missed. Both log types were cheap to keep and decisive once someone looked.
  • Patching closed the door; hunting evicted the guests. Teams that only patched stayed compromised.
  • Mailboxes are a data store, not just mail. A mail intrusion is a data incident, with notification duties attached.
  • Public intelligence moved fast. Teams that applied the March guidance in week one finished the race; teams that waited raced alone.

Team response and communication

SOC

Led the hunt with the public indicators, wrote the incident record from hour one, and gave leadership one plain sentence a day: what was patched, what was found, what was still open.

IT and mail admins

Ran the emergency patch wave, cleared the webshells, rebuilt the exploited server, and reviewed every mailbox rule that could forward or leak mail.

Management

Approved the out-of-hours patch window, told staff what happened in short daily notes, and accepted that partner notifications were necessary. The calm, factual tone kept the response steady.

Communication notes: the team told leadership the truth early: the door had been mapped, the door had been used, and the fix was underway. One short internal note per day, one factual note to affected partners, and a regulator-ready file kept current from hour one. No blame, no downplaying; the timeline from CISA and Microsoft made the story clear enough on its own.

Public sources

  • CISA advisory AA21-110A, "Exploit the Microsoft Exchange On-Premises Vulnerabilities" (April 2021), with indicators, detection guidance, and mitigations.
  • Microsoft Threat Intelligence Center reporting, "HAFNIUM targeting Exchange Servers with 0-day exploits" (March 2, 2021), with the group profile, the vulnerabilities, and the campaign steps.

Mitigation and Defense

No single control stops network profiling, because most of it happens on other people's servers. The realistic goal is to make the public map wrong and expensive: fewer facts to find, fewer banners to read, and an edge that records every touch. Stack the layers below and review them on a schedule.

Order matters more than budget here. The first three layers in the table below cost almost nothing but policy and time. They also remove the facts that every later attack step depends on. Start there, then buy or tune the monitoring layers, and only then spend on advanced tooling.

Enterprise defenses

  • Reduce the attack surface. Close services you do not need and gather public access behind as few entry points as possible.
  • Harden DNS. Restrict zone transfers, deny AXFR from the internet, keep public records minimal, and split internal and external zones so internal names never leak.
  • Run external attack surface monitoring (EASM). Scan yourself with the same public services attackers use, such as Shodan and Censys, and remove what surprises you.
  • Hide and limit banners. Turn off version strings on VPN, mail, and web services where the product allows it. A missing version makes exploit choice guesswork.
  • Plant canaries. Add fake DNS records and honeypot ports that nobody legitimate should touch. Every hit is a strong early signal of recon.
  • Rate limit public services. Slow down repeated lookups and failed connections from one source so collection gets expensive.
  • Log everything at the edge. Firewall, public DNS, and web logs are the evidence base for every rule in Section 5, and Zeek on the edge adds the connection truth.
  • Deploy the five Sigma rules from 5.5 and tune their thresholds with your normal traffic. Re-tune them every quarter.
  • Fix the policy leaks. Limit company and technology details in job posts, press releases, and partner pages. Write about roles, not product versions.

Home & small business defenses

  • Update your router firmware on a schedule. Old versions are fingerprinted by automated scans within days of a release.
  • Disable remote management from the internet unless you truly need it. Most home routers do not need WAN-side admin at all.
  • Use strong unique passwords for the router and every smart device, so one leaked password never opens two doors.
  • Turn on automatic updates for anything that faces the internet: the router, the NAS, the smart doorbell.
  • Look yourself up. Search your own domain in a public scan database and close what surprises you.
  • Think before you share home network details publicly: your provider name, camera model, or smart home setup are all useful to strangers.

Small businesses should treat the enterprise list as a menu. Start with the first four items. They give most of the benefit for little money.

Common Mistakes and Best Practices

These patterns appear again and again in post-incident reviews of network intrusions. Each row pairs a common mistake with a better way that fits normal SOC work and normal budgets.

None of these mistakes come from lazy teams. They come from reasonable choices made under pressure: alert noise is tiring, storage costs money, and the PRE phase never fires an alarm of its own. The better way column therefore aims for small, durable changes that survive a busy quarter. It does not ask for a big program that nobody has time to run.

Notice one pattern across the rows: most fixes reuse data you already have. The logs exist; the scan databases are public; the Sigma rules are written. The gap is usually a process decision, not a purchase. That is good news, because process decisions are the cheapest controls you own.

One warning before the table. Do not copy the rows into a tool as eight new alert policies. Several of these fixes are about fewer, better alerts with longer memory, not more alerts. Read the better way column first, and only then decide what to switch on.

Best practices checklist

Print this list, pin it next to the SIEM dashboards, and walk through it once per quarter. Each line is small on its own. Together they cover the whole path from public facts to a tuned detection stack.

  • Keep a live inventory of every public asset, name, and range.
  • Deny AXFR from the internet and keep public DNS records minimal.
  • Ship full firewall, public DNS, web, and Zeek logs to the SIEM and keep them searchable for 90 days.
  • Run the five Sigma rules from Section 5.5 and tune thresholds with real traffic.
  • Check your assets in public scan databases every month and remove surprises.
  • Plant canary DNS records and alert on every lookup.
  • Review job posts and press pages for stack and vendor leaks.
  • Correlate recon signals by source IP across sources before closing any ticket.

If you can only do three items this quarter, pick the inventory, the edge logging, and the five rules. They turn everything else in this list from a promise into a measurement.

Closing thought

Reconnaissance is the attacker doing homework. You cannot stop the reading, but you decide what is there to read. Every fact you remove, every banner you hide, and every canary you plant makes the quiet map wrong. When the map is wrong, the attack gets loud, and loud attacks are exactly what your SOC is built to catch.

And when a map does come true, Section 5 and Section 6 are your proof that it did not have to. The logs were there. The rules were there. The story of HAFNIUM shows how much one well-placed recon alert can be worth.

Glossary of Key Terms

Every technical term used in this guide, explained in simple words. Terms appear here in the order a beginner will most likely meet them.

MITRE ATT&CK
A free, public catalog that describes what real attackers do, step by step. Security teams use it as a shared language for attacks and defenses.
Tactic
The goal of an attack step, in one word. Reconnaissance, for example, means the attacker is collecting information before acting. Each step is called a technique, and one tactic contains many techniques.
Sub-technique
A more specific version of a technique. T1590.002 is a sub-technique of T1590 and covers only DNS research.
Reconnaissance
The ATT&CK tactic where attackers collect information about a target before the attack. T1590 belongs here.
PRE
The ATT&CK platform label for techniques that run before an intrusion, outside the victim's systems.
OSINT
Open source intelligence: information collected from public sources such as search engines, WHOIS records, and social media. No intrusion needed.
WHOIS
A public directory that lists who owns a domain or an address block, and which registrar manages it.
DNS
The name system of the internet. It translates names like example.com into IP addresses that computers use to connect.
FQDN
Fully qualified domain name: the complete name of a host, for example mail.example.com, with every part spelled out.
Banner grabbing
Connecting to a service just long enough to read its greeting, which often names the software and version. Then the attacker hangs up.
Firewall
A device or program that allows or blocks traffic between networks. Your edge firewall decides what the internet can reach.
SIEM
Security information and event management: the system that collects logs from many sources, stores them, and raises alerts when rules match.
Canary
A fake but realistic asset, for example a DNS name that nobody should ever query. Any touch on a canary is a strong warning signal.
CVE
Common Vulnerabilities and Exposures: a public ID for one known software flaw, for example CVE-2021-26855 in Exchange.
SSRF
Server-side request forgery: a trick that makes a server send requests for the attacker, often into places the attacker cannot reach directly.
Webshell
A small hidden page on a web server that runs attacker commands in the browser. In the 2021 Exchange campaign, attackers used webshells named China Chopper.
Sigma
An open format for writing detection rules once and converting them to the query language of any SIEM product.
