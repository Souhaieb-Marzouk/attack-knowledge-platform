Remote Services (the full menu)

T1021 is the parent technique for remote services. These are built-in tools such as RDP, SMB, SSH, and WinRM. They let one computer work on another computer over the network. That includes ESXi (VMware hypervisor software that runs virtual machines) and IaaS (cloud infrastructure), not only desktops. Attackers use them to move sideways inside a network — a step called lateral movement. This guide covers all eight sub-techniques in one place, so you can defend the whole menu, not just one dish.

Written for beginners, SOC analysts, and detection engineers. Every example here is for learning and defense only. This guide shows the attack steps, the logs the attack leaves behind, and how to catch it.

What to notice

The same attack leaves three very different log trails. SMB creates share and service events. WinRM creates wsmprovhost.exe processes and network logons. SSH writes to auth.log on Linux. Red Team Perspective

Why attackers move sideways with the network's own tools, and which of the eight doors they pick.

Remote services are features that come with the operating system. They let one computer open a shell, a screen, or a file share on another computer over the network. For example, SSH (Secure Shell) is a tool that opens a text-only command window on a Linux machine from somewhere else. Attackers do not need to break anything to use them. If they have valid credentials, the service just lets them in. Credentials mean a working username and password, a password hash, an SSH key, or a cloud token. The login looks exactly like real admin work.

That is the whole appeal. An exploit (a software bug used to break in) can crash the target, gets patched, and looks strange in logs. A remote service login looks like normal work. Security teams call this style living off the land: using built-in, legitimate tools instead of attack software. Once inside, attackers use these services for four jobs: running commands on new machines, copying files, stealing more credentials, and reaching the next hop toward valuable data.

The menu — all eight sub-techniques

MITRE ATT&CK splits T1021 into eight sub-techniques. Think of them as eight doors into the same building. The attacker picks whichever door is open and matches the credentials they hold.

IDNameWhen an attacker uses itTypical port
T1021.001Remote Desktop Protocol (RDP)They want a full visual desktop. For example, to click through apps or use a browser on the target.TCP 3389
T1021.002SMB / Windows Admin SharesThey want to copy files and run services remotely — the classic PsExec path after stealing passwords or hashes.TCP 445
T1021.003DCOMThey want remote code execution through Windows COM objects, often from memory, with almost no files on disk.TCP 135 + high ports
T1021.004SSHThe next machine runs Linux or macOS, or they want an encrypted tunnel between two hosts.TCP 22
T1021.005VNCRDP is blocked but a cross-platform screen-control tool is installed — common on mixed or old fleets.TCP 5900
T1021.006WinRMThey want fast PowerShell remoting across many Windows servers — a favorite for domain controllers.TCP 5985 / 5986
T1021.007Cloud ServicesThey hold a cloud login or token and use the web console, cloud shells, or run-command features instead of the network.TCP 443 (API)
T1021.008Direct Cloud VM ConnectionsThey abuse the provider's direct channel to a virtual machine — SSH/serial consoles and session managers that skip normal network paths.Provider channels (443 + in-band)
Terms used above: SMB (Server Message Block) is the Windows file-sharing protocol. Admin shares are hidden folders like ADMIN$ and C$ that only administrators can open. DCOM (Distributed COM) lets programs call objects on other computers. WinRM (Windows Remote Management) is the service behind PowerShell remoting. VNC (Virtual Network Computing) shows a remote screen. A hash is the scrambled mathematical form of a password that Windows sometimes accepts for login instead of the password itself.

What an attacker needs first

1. Valid credentials

This is the hard part, and attackers solve it before T1021 ever starts. They steal passwords from memory (the Windows lsass.exe process stores logon material), grab password hashes, copy SSH private keys from disk, or phish a cloud login. Without a working credential, every door in the menu stays shut.

2. Network reachability

The attacker's machine must be able to send traffic to the target port. A firewall (a device that filters network traffic) may block the way. So attackers map what is open, often with simple port scans. Then they pick the path with the fewest blocks.

3. The service enabled and permitted

The target must actually run the service, and the stolen account must have the right to use it. A domain admin account opens WinRM on nearly every Windows server. A local account usually opens far less. This is why attackers always hunt for the most powerful account first.

4. Low noise, high cover

Good attackers choose the service your team watches least. If you alert on RDP but ignore WinRM, they use WinRM. Every step in this menu creates logs somewhere — the attacker's job is to blend those logs into the noise of real administration.

Tool landscape

Attackers rarely write their own remote-access code. They use the same tools administrators use. Knowing these names helps you read process and command-line logs later.

Commands like the ones below are safe to run in a lab you own — a small test network with machines only you control. They only list information or open a session; they do not install anything. Security students use them to learn exactly which logs each tool creates.

bash — lab-only examples
# LAB ONLY — run against your own test machines, never against systems you do not own

# Check which shares and sessions an account can see on one lab server (SMB)
nxc smb 10.1.20.10 -u labadmin -p 'LabPassword!' --shares

# Open an interactive PowerShell session on your lab domain controller (WinRM)
evil-winrm -i 10.1.20.5 -u labadmin -p 'LabPassword!'

# Log in to your lab Linux server with a key you own (SSH)
ssh -i ~/.ssh/lab_key deploy@10.1.20.40

# Confirm from the defender side which remote services are listening
ss -tlnp            # Linux: list listening ports
netstat -ano        # Windows: list listening ports
Watch out (OPSEC and noise): remote-service attacks are quiet but not silent. Every use writes logs: share connections, service installs, new processes, SSH logins. Attackers slow down, spread actions over hours, and reuse normal admin tools so their activity mixes with real administration. For a defender, the good news is simple: with every service monitored, each door creates evidence.
Ethics: Using remote services to enter systems you do not own — even with default passwords — is illegal in most countries. Red teams and students may only test systems they own, or systems they have written permission to test, inside an agreed scope and time window. Everything in this guide is written for building defenses, not for attacking.

Blue Team / SOC Perspective

What lateral movement looks like from inside the SOC, and why one rule for one service is never enough.

The SOC (Security Operations Center) is the team that watches alerts and logs all day. For T1021 the job has a special difficulty: remote services are supposed to be used. Real administrators log in with RDP, WinRM, and SSH every day. The attacker is doing the same things as an admin — connecting, copying files, running commands — from the wrong machine, at the wrong time, with the wrong account. Detection is therefore less about one magic event and more about context: who, from where, to how many machines, in how long. In the attack chain, T1021 sits in the middle. Attackers use it after their first way in, and before they steal data or run ransomware. Catching it here breaks the whole chain.

Why watching a single service fails

The door you watch is not their door

Teams often build one strong rule — usually for RDP, because RDP attacks are famous. The attacker simply reads the network like a menu. If RDP is watched, they take SMB. If SMB is watched, they take WinRM. On mixed networks they take SSH. One well-monitored door with seven unmonitored doors is a hallway, not a wall.

The trail splits across systems

Windows events go to the Windows Security log. Sysmon (a free Windows logging add-on) goes to its own channel. SSH writes text files on each Linux host. Cloud logins land in the provider's log service. If these sources sit in different tools, or different teams, no single person sees the full path. The fix is to send everything into one SIEM (Security Information and Event Management — a system that stores and searches logs from all sources).

The logon-type decoder

Every Windows logon event (4624 success, 4625 failure) carries a Logon Type number. This number tells you how the person logged in — and it is the single most useful field for T1021 detection. Learn these numbers and half the technique is visible to you:

TypeNameWhat it meansRemote-service link
2InteractiveSomeone typed the password at the keyboard of that machine.Not remote. Type 2 from a workstation is normal.
3NetworkThe user connected over the network — a share, a remote command, a mapped drive. No screen session.SMB, WinRM, DCOM, WMI all appear as Type 3. The workhorse type of lateral movement.
4BatchA scheduled task ran with stored credentials.Attackers sometimes abuse scheduled tasks to persist.
5ServiceA Windows service started with a service account.Appears after remote service installs (PsExec style).
7UnlockSomeone unlocked an already-logged-in screen.Sessions stolen or reused show as Type 7.
9NewCredentialsA process used different credentials for network connections only (runas with /netonly).A quiet way attackers split local and network identity.
10RemoteInteractiveA full remote screen session: RDP, or VNC routed through Windows.RDP. Type 10 should only come from jump servers and admin workstations.
11CachedInteractiveLogin with credentials cached on the machine (no domain controller contact).Common on laptops; not remote by itself.
The WSMAN note: WinRM logons are Type 3, so they look like ordinary share connections at first. But the event records a Logon Process Name of WSMAN (Windows Remote Management) and starts a wsmprovhost.exe process on the target. Filtering Type 3 events for WSMAN gives you a clean WinRM trail. For pass-the-hash, look for Type 3 with logon process NtLmSsp and a key length of 0 — that means no real password was ever typed.

What to look for

  • Type 3 or Type 10 logons from workstation subnets to servers — normal admins work through jump servers (dedicated admin machines), not from desks.
  • One source, many targets: the same computer or account reaching 3+ servers with remote services in minutes.
  • One source, many services: SMB from a host at 09:00, WinRM at 09:05, SSH at 09:12 — service-hopping is rare for real admins.
  • wsmprovhost.exe or sudden PSEXESVC-style services on servers that are not managed by automation.
  • Service installs (7045/4697) where the service path points to ADMIN$, %TEMP%, or random names.
  • SSH "Accepted publickey" from subnets that never SSH — a developer laptop reaching production is a pivot.
  • New authorized_keys lines or new local admins (4720) right after a remote session.
  • Cloud console or StartSession events where MFA was false or the source country is new.
  • Failed logons (4625) in bursts against several services from the same source — probing before the real attempt.
First response ideas: if an alert fires, do not close the session first — evidence lives in memory. Record the source IP, account, and target, then pull the surrounding hour of logs for all three. Disable the account, isolate the source machine at the switch or EDR level, and treat every host it touched as suspect. Section 4 gives you the exact queries.

Detection Engineering Deep Dive

The complete work of a detection engineer for this technique: mapping, intel, ranking, log samples, Sigma rules, and Splunk queries.

A detection engineer turns threats into working alerts. This section walks through the full job. You map the technique to rules and regulations. You study the actors who use it. Then you rank the threats, read real log samples, and write Sigma rules plus Splunk queries. Because T1021 is a parent technique, every rule here is written to catch several services at once — that is the big-picture mindset this guide is about.

Regulation Mapping

Rules like GDPR or PCI DSS do not say "detect remote services". They say "protect data" and "monitor access". Attackers moving sideways with stolen credentials break exactly those requirements, so auditors will ask how you detect and control this. Use this table when someone asks why this detection work is required:

RegulationControl / ArticleWhat it asks forHow T1021 relates
GDPRArt. 32 — Security of processingProtect personal data with suitable technical measures, including access control and monitoring.An attacker hopping between servers with remote services shows missing controls. MFA, segmentation, and monitoring close those gaps. Regulators expect detection of abnormal access paths.
GDPRArt. 33 — Breach notificationReport a personal-data breach to the authority within 72 hours.You can only report fast if lateral movement is visible. Cross-service logon alerts are usually the earliest reliable signal of a breach in progress.
HIPAA§164.312(a)(1) — Access controlOnly allowed people may access ePHI (protected health data).Remote-service logins with stolen admin accounts break access control. MFA on RDP/WinRM/SSH and jump-server-only admin paths are the expected answers.
HIPAA§164.312(b) — Audit controlsRecord and examine access to systems holding ePHI.Events 4624/4625, share access 5140/5145, and SSH auth.log lines are exactly this audit trail. Collect and review them, not just store them.
ISO 27001:2022A.8.2 — Privileged access rightsRestrict and manage privileged accounts, and review their use.Domain admin activity over SMB/WinRM from a workstation is a direct violation pattern. This guide detects it.
ISO 27001:2022A.8.16 — Monitoring activitiesMonitor networks and systems for abnormal behavior and record evidence.The Sigma rules and SIEM queries in this section are testable proof. Auditors can see the control working.
ISO 27001:2022A.8.22 — Segregation of networksSeparate network segments so one zone cannot freely reach another.A workstation reaching port 5985 or 445 on a server means segmentation is broken. The sweep rule catches it.

Threat Intelligence

Threat intelligence (often shortened to CTI) means learning about attackers before they hit you, and using that knowledge to build better defenses. For T1021 the picture is broad: nearly every major intrusion of the last decade used at least one remote service to move sideways. Here is how a detection engineer works with that knowledge, step by step:

  • Collect. Read the MITRE ATT&CK page for T1021 and its sub-techniques. Read CISA advisories (for example the AA20-302A-style Conti alerts) and vendor blogs from Microsoft, Sophos, Palo Alto, and Trend Micro. Free sharing platforms such as MISP (a free system for exchanging threat data) and AlienVault OTX help too. Save every report that mentions lateral movement tools or patterns.
  • Analyze. For each report, note: which actor, which credentials they stole first, which services they used to move, which tools, and which logs those tools would create. Tag everything with attack.t1021 so it stays searchable.
  • Apply. Turn findings into three things: new detection rules (like the Sigma rules below), hunting hypotheses (questions you search in your own logs), and purple-team tests. A purple-team test is a safe, planned check that proves your detections fire.

Official actors for T1021

The official MITRE ATT&CK page for T1021 documents these actors and what they did with remote services. The first seven rows follow that official record. We keep the words simple.

Aquatic Panda2020 – nowUsed remote scheduled tasks to install malicious software on victim systems. A scheduled task runs a program later, so one stolen account can plant tools on many machines.
Brute Ratel C42022 – nowAn attack framework that criminals abuse. It can use RPC for lateral movement. RPC (Remote Procedure Call) lets a program on one computer run code on another computer.

Hunting hypotheses for your environment

  • "Did one source host use 3 or more different remote services (SMB, WinRM, SSH, RDP) within 10 minutes?" Service-hopping is the signature of a menu-touring attacker.
  • "Did any non-admin workstation create network logons (Type 3) or remote-interactive logons (Type 10) on 3+ servers within 10 minutes?"
  • "Did a new service (7045) or a new SSH key appear on a server within 5 minutes of a remote logon from an unusual source?"

Logs & Patterns

Now the practical part. For each threat from the ranking, here are the logs to use. Each block shows a realistic sample of the log entry, plus the pattern to search for. All samples use fake names and reserved test addresses (like 203.0.113.x and 10.1.20.x). The XML entries are shown escaped for the web page; in your logs the angle brackets are real.

1. Multi-service ransomware propagation chain

Logs: Windows Security 7045/4697, Sysmon 1 and 3, EDR. Pattern: within minutes of a network logon, a new service appears on the server. Its program file points into ADMIN$ or a temp path. The attacker is chaining SMB and WinRM from server to server.

xml — Windows Security 7045 (service installed)
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Service Control Manager"/>
    <EventID>7045</EventID>
    <TimeCreated SystemTime="2026-09-12T02:21:57.612003400Z"/>
  </System>
  <EventData>
    <Data Name="ServiceName">PGMsvc</Data>
    <Data Name="ImagePath">%COMSPEC% /c powershell.exe -enc SQBFAFgAIAAoAE4AZQB3...</Data>
    <Data Name="ServiceType">user mode service</Data>
    <Data Name="StartType">auto start</Data>
    <Data Name="AccountName">LocalSystem</Data>
  </EventData>
</Event>
What to look for:
  • New services on servers whose name does not match your naming rules. Watch for paths that use -enc, ADMIN$, or %TEMP%.
  • The same service name appearing on many servers in one night — that is the chain, not a coincidence.
  • Right after: vssadmin delete shadows or backup services stopping (Sysmon 1, EDR).

2. Stolen domain admin used across services

Logs: Windows Security 4624, Sysmon 10, SIEM. Pattern: a domain admin account normally logs in on one jump server only. Suddenly it shows network logons (Type 3) from a workstation to several servers. That often happens minutes after LSASS was read on that workstation.

xml — Windows Security 4624 (network logon, WinRM)
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Security-Auditing"/>
    <EventID>4624</EventID>
    <TimeCreated SystemTime="2026-09-12T02:19:03.337811200Z"/>
  </System>
  <EventData>
    <Data Name="TargetUserName">admin_mike</Data>
    <Data Name="TargetDomainName">CORP</Data>
    <Data Name="LogonType">3</Data>
    <Data Name="LogonProcessName">WSMAN</Data>
    <Data Name="AuthenticationPackageName">Negotiate</Data>
    <Data Name="IpAddress">10.1.20.24</Data>
    <Data Name="WorkstationName">SALES-PC01</Data>
  </EventData>
</Event>
What to look for:
  • A Tier-0 admin (domain admin level) logging in from a workstation — the tiered admin model forbids this.
  • LogonType 3 with LogonProcessName WSMAN = a WinRM session, not just a file read.
  • Count distinct destination hosts for that account in 10 minutes; more than 2–3 from one source is an incident.
  • Check 10–30 minutes earlier for Sysmon 10 (LSASS access) on the source machine — that is where the credential came from.

3. Pass-the-hash over SMB admin shares

Logs: Sysmon 11 (file write), Windows Security 4624 + 5145. Pattern: a file appears inside an admin share without any interactive login. The matching 4624 shows NtLmSsp with key length 0 — a hash was used, never a password.

xml — Sysmon Event ID 11 (write into ADMIN$)
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Sysmon"/>
    <EventID>11</EventID>
    <TimeCreated SystemTime="2026-09-12T02:20:44.901557800Z"/>
  </System>
  <EventData>
    <Data Name="Image">System</Data>
    <Data Name="TargetFilename">\Device\Mup\FS01\ADMIN$\tool.dll</Data>
    <Data Name="CreationUtcTime">2026-09-12 02:20:44.887</Data>
    <Data Name="User">CORP\admin_mike</Data>
  </EventData>
</Event>
What to look for:
  • TargetFilename starting with \Device\Mup\ (the "network provider" path) and containing ADMIN$ or C$.
  • The paired 4624: LogonProcessName = NtLmSsp, LmPackageName = NTLM V2, KeyLength = 0 — the pass-the-hash fingerprint.
  • Share checks (5145) against ADMIN$ from hosts that never admin that server.

4. WinRM remote execution with encoded commands

Logs: Sysmon 1, PowerShell operational log 4104. Pattern: a powershell.exe process is born under wsmprovhost.exe (the WinRM host process) and its command line contains -enc or -EncodedCommand — Base64-packed code that hides its intent.

xml — Sysmon Event ID 1 (encoded PowerShell over WinRM)
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Sysmon"/>
    <EventID>1</EventID>
    <TimeCreated SystemTime="2026-09-12T02:19:09.220114500Z"/>
  </System>
  <EventData>
    <Data Name="Image">C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe</Data>

    <Data Name="User">CORP\admin_mike</Data>

What to look for:
  • ParentImage ending in wsmprovhost.exe — the process tree of remote PowerShell.
  • -enc, -EncodedCommand, or FromBase64String in the command line; decode the text in a sandbox to see the real code.
  • Script-block logging (4104) shows the decoded script even when -enc hides it from the command line.

5. SSH key theft: development to production pivot

Logs: Linux auth.log (Debian/Ubuntu) or /var/log/secure (Red Hat), Sysmon for Linux, cloud trail logs. Pattern: an SSH login with a public key appears from a subnet that never logs in that way. A stolen id_rsa file needs no password. It defeats password rules completely.

Sep 12 02:24:11 web01 sshd[20144]: pam_unix(sshd:session): session opened for user deploy by (uid=0)
Sep 12 02:26:38 web01 sudo:  deploy : TTY=pts/1 ; PWD=/tmp ; USER=root ; COMMAND=/usr/bin/tar czf /tmp/etc.tgz /etc
Sep 12 02:31:02 web01 sshd[20189]: Accepted publickey for deploy from 10.1.20.24 port 51490 ssh2: RSA SHA256:4kP9qL2mVxT8eRcJ
What to look for:
  • "Accepted publickey" from workstation or build-server subnets — production SSH should come from bastions only.
  • The same key fingerprint (the SHA256:... part) appearing on several servers — the key is touring.
  • Immediately followed by sudo lines, archive commands (tar), or edits to ~/.ssh/authorized_keys.

6. RDP password spraying against exposed hosts

Logs: Windows Security 4625 (failed logon), firewall flow records. Pattern: bursts of failed Type 10 (or Type 3 via network-level authentication) logons from one source, slowly and against few accounts to avoid lockouts — then, sometimes, a success.

xml — Windows Security 4625 (failed RDP logon)
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Security-Auditing"/>
    <EventID>4625</EventID>
    <TimeCreated SystemTime="2026-09-12T01:57:21.104552100Z"/>
  </System>
  <EventData>
    <Data Name="TargetUserName">svc_helpdesk</Data>
    <Data Name="LogonType">10</Data>
    <Data Name="IpAddress">203.0.113.7</Data>
    <Data Name="Status">0xc000006a</Data>
    <Data Name="WorkstationName">WIN-ATTACKER</Data>
    <Data Name="ProcessName">C:\Windows\System32\svchost.exe</Data>
  </EventData>
</Event>
What to look for:
  • Status code 0xc000006a = wrong password; 0xc0000234 = account locked (spraying hitting limits).
  • More than ~10 failures from one source IP in 10 minutes across any host with RDP enabled.
  • A 4624 Type 10 from the same IP shortly after failures — the guess worked; treat as an incident.

7. Cloud console or SSM access without MFA

Logs: AWS CloudTrail (and the Azure sign-in or GCP audit equivalents), cloud SIEM. Pattern: a console login or a Run Command session on a virtual machine. Multi-factor authentication (a second proof, like a phone code) was false or absent. The attacker skipped the network path entirely.

What to look for:
  • ConsoleLogin with MFAUsed: "No", or StartSession/SendSSHPublicKey events from new source IPs or countries.
  • Run-command features (SendCommand, SSM documents) targeting many instance IDs in a short window.
  • New access keys or login profiles created right after a console login (CreateAccessKey, CreateLoginProfile).

8. Legitimate multi-service admin usage (the false positive)

Logs: Sysmon 3 (network connection), Windows Security 4624. Pattern: the benign twin of the fan-out attack. A real admin workstation or jump server touches several servers on admin ports within minutes — same shape, different intent. Learn this shape so your rules can tell the two apart.

xml — Sysmon Event ID 3 (benign admin connections)
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Sysmon"/>
    <EventID>3</EventID>
    <TimeCreated SystemTime="2026-09-12T09:12:02.447803100Z"/>
  </System>
  <EventData>
    <Data Name="Image">C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe</Data>
    <Data Name="DestinationIp">10.1.20.10</Data>
    <Data Name="DestinationPort">5985</Data>
    <Data Name="User">CORP\pam_ops</Data>
    <Data Name="Initiated">true</Data>
  </EventData>
</Event>
What to look for (approve, not alert):
  • The source is a known jump server or admin workstation from your asset list.
  • The account is a named admin, the targets are in scope, and the hour matches working time.
  • Keep this pattern in a documented baseline; every list here needs review when the admin team changes tools.

Sigma Detection Rules

Sigma is a free, open format for writing detection rules once and running them in any SIEM. Each rule below matches one threat from the ranking, and because T1021 is a parent technique, most rules are written to catch several services at once. Under every rule you find the matching Splunk SPL query. SPL (Search Processing Language) is the search language used in Splunk. Adjust the index names to your own environment.

Rule 1 — One source using many remote services

The flagship rule for T1021. It counts distinct destination hosts behind successful network or remote-interactive logons from one source. Three or more servers in ten minutes is not admin work — it is a tour.

yaml — sigma
title: Single Source Logons to Multiple Hosts via Remote Services
id: 019b2047-4962-46de-a0b3-7a4c3abffe36
status: stable
description: >
  Detects one source IP creating successful logons (network Type 3 or remote
  interactive Type 10) on 3 or more different hosts within 10 minutes. This
  fan-out shape fits lateral movement with SMB, WinRM, and RDP, or a worm -
  it does not fit normal administration from a workstation.
references:
  - https://attack.mitre.org/techniques/T1021/
author: Detection Engineering Team
date: 2026/09/29
tags:
  - attack.lateral_movement
  - attack.t1021
  - attack.t1021.002
  - attack.t1021.006
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID: 4624
    LogonType:
      - 3
      - 10
  condition: selection | count(dest) by IpAddress >= 3
timeframe: 10m
falsepositives:
  - Jump servers and admin workstations that manage many hosts by design
  - Software distribution or monitoring tools that log in remotely
level: high
spl — splunk
index=wineventlog source="WinEventLog:Security" EventCode=4624 Logon_Type IN (3, 10)
| bin _time span=10m
| stats dc(dest) AS hosts, values(dest) AS targets, values(user) AS users BY _time, IpAddress
| where hosts >= 3
| sort - hosts

Rule 2 — Suspicious remote service install

Catches the PsExec-style pattern. A service is installed from the network, with a known-lazy name or an admin-share path. Event 4697 (service installed in the Security log) is included because some teams disable 7045 auditing.

yaml — sigma
title: Suspicious Remote Service Installation
id: 5dfd7086-94a8-4fd1-9abe-7e65d35fceb3
status: stable
description: >
  Detects a service installation with a PsExec-style name or a binary path
  inside an admin share. Attackers copy a small service program into ADMIN$
  and start it remotely to run commands as SYSTEM on the target host.
references:
  - https://attack.mitre.org/techniques/T1021/
  - https://attack.mitre.org/techniques/T1021/002/
author: Detection Engineering Team
date: 2026/09/29
tags:
  - attack.lateral_movement
  - attack.t1021
  - attack.t1021.002
  - attack.t1569.002
logsource:
  product: windows

    BY host, Account_Name
| sort - count

Rule 3 — Admin share access followed by remote execution

Ties two moments together. A client touched ADMIN$ on a server. Shortly after, a new process or service appeared on that same server. Each half alone is common; together they are the file-drop-and-run pattern.

yaml — sigma
title: Admin Share Access Followed by Remote Process Creation
id: 18da9a35-755b-48a9-b262-b590734ab467
status: stable
description: >
  Correlates an ADMIN$ share access (Event 5145) with a process creation
  (4688) or service install (7045) on the same host within 10 minutes. This
  shows the classic copy-then-execute lateral movement step over SMB.
references:
  - https://attack.mitre.org/techniques/T1021/002/
author: Detection Engineering Team
date: 2026/09/29
tags:
  - attack.lateral_movement
  - attack.t1021
  - attack.t1021.002
logsource:
  product: windows
  service: security
detection:
  selection_share:
    EventID: 5145
    ShareName|contains: 'ADMIN$'
  selection_exec:
    EventID:
      - 4688
      - 7045
  condition: near selection_share and selection_exec
timeframe: 10m
falsepositives:
  - Configuration management tools (SCCM, Ansible) writing and executing remotely
  - Administrators running approved update scripts
level: high
spl — splunk
index=wineventlog (EventCode=5145 ShareName="\\\\*\\\\ADMIN$") OR (EventCode IN (4688, 7045))
| bin _time span=10m
| stats values(EventCode) AS events, dc(EventCode) AS kinds,
    values(Source_Address) AS share_clients, values(New_Process_Name) AS processes

| where kinds >= 2 AND share_clients != ""
| sort - _time

Rule 4 — WinRM remote command with encoded PowerShell

Finds Base64-packed PowerShell (-enc) arriving through PowerShell script-block logging or process creation. Encoded commands over WinRM are almost never legitimate and are a favorite attacker trick.

Real-World Scenario

Ireland's Health Service Executive vs. Conti, 2021 — a real, documented case of lateral movement at national scale.

This is a real incident, not a composite. In March 2021, attackers entered the network of Ireland's Health Service Executive (HSE) — the national health service — through a phishing email. They then spent roughly eight weeks moving sideways with remote services and stolen credentials before launching Conti ransomware on 13 May 2021. More than 80% of the IT infrastructure was encrypted, and hospital appointments were canceled across the whole country. The Irish National Cyber Security Centre (NCSC) published a detailed incident report in December 2021. It describes the attacker path step by step. That makes this case perfect for learning.

The attack chain

1. Phishing Excel opened→ 2. Cobalt Strike beacon→ 3. Credentials stolen→ 4. SMB/RDP/WinRM spread→ 5. Data taken out→ 6. Conti runs

Timeline

16 MARCH 2021 — MORNING
One Excel attachment

A workstation user opens a phishing email attachment — an Excel document. Public reporting says this was the entry point. The file launched malware that gave the attackers a foothold (their first running code inside the network) and connected out to their command system. The user never saw a warning.

MARCH 2021 — FOLLOWING DAYS
Tools and credentials arrive

The attackers land more tools. One is Cobalt Strike — a legitimate penetration-testing product abused as an attack remote-control system. They begin credential theft. They read passwords from the memory of Windows machines. Each stolen password is another key on the ring.

LATE MARCH 2021
Mapping the hospital network

The attackers run AdFind, a command-line tool that queries Active Directory (the Windows directory of users and computers). They also run Advanced IP Scanner, a free network scanning tool. With these, they list every server, admin account, and trust relationship. They now know exactly which doors exist.

APRIL 2021
Eight weeks of sideways movement

Using stolen admin credentials, the attackers move between servers with SMB admin shares, RDP sessions, and WinRM, reaching critical systems. The NCSC report later recorded multiple attacker entries over the period. To defenders, much of this looked like ordinary administration — no rule was watching the whole menu at once.

EARLY MAY 2021
Staging and data theft

Before encrypting, the group prepares. They claim to have copied around 140 GB of unencrypted data. This is double extortion: encrypt systems, then threaten to publish the stolen data. Ransomware software is staged on many hosts in advance.

13 MAY 2021 — EARLY HOURS
Conti detonates

The Conti ransomware runs across the estate. Over 80% of the IT infrastructure encrypts. Staff cannot log in; laboratory, radiology, and scheduling systems stop; hospitals cancel appointments nationally. Public reports say the ransom demand was around 20 million US dollars — the HSE refused to pay.

13–14 MAY 2021
Detection and declaration

Staff spot encrypted filenames and unusual messages; the incident is declared a major emergency. The NCSC and national partners join. Networks are isolated to stop the encryption from spreading further — a hard decision, because isolation also breaks services the hospitals depend on.

MAY – AUGUST 2021
Rebuild, server by server

Engineers rebuild from clean images and backups. Public updates describe restoring 54 servers first to bring back the most critical functions, then working outward. Most core systems return over weeks; full recovery takes roughly four months.

DECEMBER 2021
The report everyone can learn from

The Irish NCSC publishes a detailed incident report describing the entry, the tools, the movement, and the response. It became standard reading for hospital defenders — and a public, step-by-step map of exactly what this guide teaches you to detect.

Containment and recovery

Containment (first days)

  • Infected segments isolated at the network level to stop the ransomware spreading further.
  • Domain credentials mass-reset; remote services locked down to approved jump hosts only.
  • National coordination stood up: HSE, the NCSC, and law enforcement worked from one command structure.
  • Clinical fallback to paper processes while IT was dark — the emergency plan that kept care going.

Recovery (weeks to months)

  • Priority rebuild: the first 54 servers restored were the ones clinical care needed most.
  • Machines rebuilt from clean images; credentials, certificates, and secrets replaced everywhere.
  • Logging, monitoring, and MFA added as systems came back — each rebuilt service returned safer than it left.
  • Full recovery took about four months; the ransom was never paid.

Impact and consequences

The damage reached far beyond servers. Hospitals canceled appointments and treatments nationally; some patients traveled for care that was postponed at home. Staff worked with paper records for weeks, and IT teams worked around the clock for months. Public reports put the direct response and recovery cost in the tens of millions of euros, before counting delayed care and lost public confidence. The Irish government announced a public inquiry into the attack, and the HSE published its own independent review with detailed recommendations. One workstation click — followed by eight quiet weeks of unmonitored lateral movement — became a national event.

Lessons learned

What failedFix applied after the incident
One phishing attachment gave a full footholdEmail filtering, macro blocking by policy, and phishing-resistant MFA. A stolen password alone is then not enough.
Eight weeks of lateral movement went undetectedCentral logging of all remote services (4624 types 3 and 10, 7045, share events). Add the cross-service rules from section 4 of this guide.
Admin credentials worked everywhere at onceTiered admin model: admin accounts only work on their own layer, through jump servers.
Flat network let the attackers reach everythingSegmentation between clinical, corporate, and server zones; only approved paths between them.
Legacy systems were hard to rebuildAsset inventory, tested offline backups, and rebuild plans for systems that cannot be re-imaged quickly.
Monitoring missed SMB, WinRM, and SSH trailsMonitor the whole T1021 menu, not just the famous door — exactly the mindset of this guide.

How the team communicated

Communication lessons: the HSE held daily public briefings during the emergency, in plain language, saying what worked, what did not, and what to expect next. A national coordination structure — the HSE, the NCSC, the health department, and law enforcement — met on a fixed rhythm, so decisions did not wait for luck. Clinicians got short, practical instructions (which systems are down, use paper for X). The lesson for any team: agree the update rhythm, the audience list, and the simple-word rule before the incident, and publish even when the news is bad. Trust is a containment tool too.

Read the source: the Irish NCSC incident report (December 2021) is public at ncsc.gov.ie, and the HSE published its own independent cyber incident review on hse.ie. Both are worth a full read — they match the patterns in this guide almost line by line.

Mitigation & Defense

Closing doors, shrinking the menu, and watching what stays open — in priority order.

You cannot remove every remote service — administrators need them. The goal is a smaller, safer menu: each service reachable only from approved places, only with strong authentication, and every use logged. The table below is ordered by what to do first. Effort means people-time, not money only.

ActionStops whatEffort
VPN or broker-only access to remote servicesInternet scanners and password sprays reaching RDP, SSH, or WinRM directly. Only the VPN or a jump broker touches those ports.Medium
MFA (multi-factor authentication) everywhereStolen passwords and sprayed passwords. A second factor blocks most of the credential-based entries in this guide, including cloud console logins.Medium
Tiered admin model + jump serversDomain admin credentials being typed on workstations where memory-readers can grab them. Admins log in only from dedicated, hardened jump hosts.High
LAPS (local admin password rotation)One stolen local admin password working on every machine. LAPS gives each computer its own random, regularly changed local password.Low
Per-role service enablement matrixDoor creep. Write down which servers actually need RDP, WinRM, SMB, or SSH — and turn the rest off. A service that is off cannot be used against you.Low
Network segmentationWorkstations reaching server admin ports directly, and one infected zone reaching another. This is what made the HSE chain possible.High
SMB signing required + SMBv1 disabledRelay attacks and tampering with SMB traffic, plus decades-old SMBv1 exploits still found in the wild.Low
WinRM over HTTPS + listener restrictionsCleartext and unauthenticated WinRM use; limits which hosts and accounts may start remote PowerShell sessions.Low
SSH key hygieneStolen key files pivoting from laptops to production. Passphrases on keys, short key lifetimes, no agent forwarding, bastion-only logins, and quarterly key audits.Medium
Cloud guardrailsConsole and run-command abuse without MFA, long-lived access keys, and silent VM session channels. Enforce MFA, short sessions, and audit every session.Medium
EDR + the SIEM rules from section 4The movement itself. Prevention fails sometimes; detection is the layer that catches what prevention misses.Medium
Official MITRE mitigations: ATT&CK lists six official mitigations for T1021. They are: Audit (M1047), Disable or Remove Feature or Program (M1042), Limit Access to Resource Over Network (M1035), Multi-factor Authentication (M1032), Password Policies (M1027), and User Account Management (M1018). The table above reflects all six. Audit means regular checks of accounts, services, and permissions. Disable or Remove means turning off services you do not need. Limit Access means only approved networks may reach these ports. MFA, Password Policies, and User Account Management map to the MFA, LAPS, and tiered-admin rows above.

Configuration examples

Run these on a lab machine first. Then roll them out through Group Policy (GPO — the Windows system for pushing settings to many computers at once) or your configuration management tool.

powershell — harden SMB and WinRM
# Run as administrator on a lab host first. Then deploy via GPO.

# Disable the ancient and abused SMBv1 protocol
Set-SmbServerConfiguration -EnableSMB1Protocol $false

# Require SMB signing so traffic cannot be tampered with or relayed
Set-SmbServerConfiguration -RequireSecuritySignature $true
Set-SmbClientConfiguration -RequireSecuritySignature $true

# WinRM: no unencrypted traffic, no basic auth, HTTPS listener only
winrm set winrm/config/service '@{AllowUnencrypted="false"}'
winrm set winrm/config/service/auth '@{Basic="false"}'

# Remove the default HTTP (5985) listener after HTTPS (5986) is in place
Get-ChildItem WSMan:\localhost\Listener | Where-Object { $_.Keys -contains "Transport=HTTP" } |
  Remove-Item -Force
cmd — check which remote doors are open
:: List listening remote-service ports on a Windows host
netstat -ano | findstr ":22 :445 :3389 :5985 :5900"

:: Show WinRM listeners and their transport
winrm enumerate winrm/config/Listener

:: Verify SMBv1 is really gone
Get-WindowsOptionalFeature -Online -FeatureName SMB1Protocol

For home users

Most of this guide is for companies. Home networks have the same doors, though. A short checklist:

  • Never expose RDP, VNC, or SMB to the internet. If you need remote access, use a VPN built into your router or a trusted remote-desktop service with MFA.
  • Turn your router's firewall on and do not forward ports 22, 3389, 445, or 5900.
  • Install operating system updates quickly — old Windows and NAS devices ship with these services enabled.
  • Use a strong, unique password plus MFA on any cloud service that can reach your computers.
  • If you do not know why a remote-access tool (VNC, RDP helper, "remote support" app) is installed, uninstall it.

Layers work together

1. Prevent: VPN, MFA, tiers→ 2. Reduce: fewer services on→ 3. Watch: cross-service rules→ 4. Respond: isolate and reset
Why this matters: each layer shrinks the attacker's menu. The HSE case shows the cost of a full menu with no watch. The best networks are not the ones with zero remote services — they are the ones where every remote service is intentional, guarded, and logged.

Common Mistakes & Best Practices

The traps teams fall into with remote-service detection — and the habits that avoid them.

Most failed detections of T1021 come from process problems, not tool problems. The logs were there; the team just watched one door, tuned the wrong number, or never tested the rule. Check your own setup against this table honestly:

MistakeWhat goes wrongThe fix
Watching only one serviceA great RDP rule exists, but SMB, WinRM, and SSH are dark. The attacker takes the unwatched door and never touches your alert.Detect the technique, not the port. Rules 1 and 7 in this guide count hosts and logon types, so they fire for any service mix.
Treating Type 3 logons as noiseNetwork logons are everywhere on Windows, so teams suppress them entirely. The attacker's Type 3 WinRM and share logons vanish with the noise.Baseline instead of silencing: allow Type 3 from jump servers and service accounts, alert on Type 3 from workstations to servers.
No logon-type literacy on the teamAnalysts cannot say what Type 10 or Type 3 means, so clues sit unread in front of them during triage.Train the whole team on the decoder table in section 3. Ten minutes of learning saves hours per incident.
Missing Linux and cloud hostsThe Windows rules are excellent, but nothing collects auth.log, SSH key logins, or cloud console events. Half the estate has no story.Ship Linux auth logs and cloud trails into the same SIEM. Cover every platform in the artifact table of section 3.
Tunnel blind spotsSSH or tooling tunnels carry remote services through firewalls over allowed ports like 443, so port-based walls see nothing.Watch process behavior (tunnel tools, -R flags) with EDR and Sysmon, not just network ports.
Field-name inconsistencies in the SIEMOne source sends LogonType, another Logon_Type; a rule that counts dest misses sources that only fill host. Silent misses, no errors.Normalize at ingestion with a common schema, and verify fields with a test event per source every month.
Static thresholds"More than 5 logons" fires on Monday patch day forever, or a patient attacker stays under the number for weeks.Tune against a 30-day baseline each quarter, and prefer distinct-count rules (3+ servers, 3+ services) over raw counts.
Rules never tested end to endThe rule exists on paper, but the log source is disabled, the index is wrong, or the field is empty. It has never fired — including during a real attack.Purple-team test each rule in a lab (run the action, watch the alert), and track "last tested" like a maintenance date.
Event 1102 not alertedThe attacker clears the Security log, and because nobody alerts on the clearing event itself, the loudest action of the whole intrusion passes silently.Alert on 1102 (and Sysmon log-clear behavior) at critical severity, always. Log clearing is never normal.
Treating every remote logon as an attackRules with no allow-list burn the team out in week one, get switched off, and leave the doors unwatched again.Build the admin baseline first (jump servers, automation accounts), then alert on deviation — section 4, threat 8 shows the benign shape.

Best practices for day-to-day detection engineering

  • Collect 4624/4625, 5140/5145, 7045, Sysmon 1/3/10/11, Linux auth, and cloud sign-in logs before writing any rule.
  • Write one cross-service fan-out rule (Rule 1) and keep it tuned — it is the highest-value rule in this guide.
  • Explain logon types in your runbook so every analyst reads Type 3 and Type 10 correctly at 03:00.
  • Keep a written matrix of which hosts may accept which remote service, and alert when a host breaks the matrix.
  • Allow-list jump servers and automation accounts by asset, not by "we know it when we see it".
  • Test every rule quarterly with a safe lab action, and record the test date next to the rule.
  • Alert critical on: log clearing (1102), LSASS access (Sysmon 10), and service installs with admin-share paths.
  • Review your admin baseline whenever the admin team, tooling, or infrastructure changes.
  • Rehearse the response: who isolates the host, who resets the credentials, who calls whom. Practice makes the real night boring.
Final thought: T1021 is not one attack — it is a menu. Defenders who watch the whole menu turn the attacker's greatest strength into a weakness. Their rules count sources, services, and servers together. Even an admin cannot touch four servers in nine minutes without a very good reason.
