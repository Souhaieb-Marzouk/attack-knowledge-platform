MITRE ATT&CK · IMPACT

T1531 Account Access Removal

Attackers do not always steal data. Sometimes they take away your ability to log in. In this technique, an attacker deletes, disables, or resets user accounts so that real people — including your security team — cannot sign in. Attackers often do this minutes before ransomware starts, or to hold an organization hostage during extortion.

Tactic: Impact Impact type: Availability Platforms: Windows · macOS · Linux · ESXi · SaaS · Office Suite · IaaS Version 1.5 No sub-techniques Guide v2.0 · audited
What it is

Attackers delete, lock, or reset accounts so real people cannot log in. It hurts availability, not data secrecy.

Main risk

Responders get locked out exactly when recovery is needed. Ransomware crews often do this just before encryption.

Where it happens

Domain controllers, identity providers such as Entra ID or Okta, ESXi hosts, SaaS admin consoles, and workstations.

Detection difficulty

Medium. Windows event logs give excellent coverage (4724, 4725, 4726, 4740). Cloud and SaaS audit logs are easy to miss.

Contents
1

Overview

This section explains the technique in plain words, shows where it sits in an attack, and lists the official ATT&CK metadata. No prior detection engineering experience is needed.

The idea in plain words

An account is a login identity: a name plus proof (a password, a token, a certificate) that says who you are. Systems use accounts to decide what you may open. Availability means people and services can use the system when they need it.

MITRE ATT&CK (a public catalog of attacker behavior) calls this technique Account Access Removal. The attacker takes away access on purpose. This is an Impact technique: the goal is damage and pressure, not quiet access. The official description says attackers may delete accounts, lock them, or manipulate them — for example change credentials or revoke SaaS permissions — and then log users off or restart systems.

"Manipulate" covers several concrete actions. All of them end with the same result: a real person cannot get in.

  • Delete the account object (it stops existing).
  • Disable the account (it exists but logon is refused).
  • Reset the password to a value only the attacker knows.
  • Revoke MFA factors or permissions, for example remove a Global Admin role or SharePoint access.
  • Force logoff or reboot, so current sessions die and new logons fail.

On Windows this can be done with the net utility, PowerShell cmdlets like Set-LocalUser or Set-ADAccountPassword, or Group Policy that disables accounts. On Linux, the passwd command can lock a password. On VMware ESXi (a hypervisor that runs virtual machines), the esxcli tool can remove system accounts. In the cloud, a stolen admin session can deactivate users in an identity provider in seconds.

Note — not the same as T1098

Do not confuse this with T1098 Account Manipulation. T1098 adds or changes access so the attacker can come back (persistence). T1531 removes access to deny availability. The contrast technique T1136 Create Account adds a brand-new account, usually for persistence too. Same domain — identity — but opposite goals.

Where it sits in the attack chain

ATT&CK sorts techniques into tactics, the stages of an attack. Account Access Removal belongs to Impact, usually the last stage. It rarely comes first. A typical ransomware-style sequence looks like this:

  1. Initial access — phishing (T1566) or a stolen session from an info-stealer log.
  2. Credential theft — dumping passwords from memory (T1003) or buying them.
  3. Privilege escalation — the attacker reaches domain admin or cloud Global Admin.
  4. Impact — T1531 removes access: admins get deleted, disabled, reset, or locked out. Security teams cannot react.
  5. More impact — data is encrypted (T1486), services stop (T1489), or backups are destroyed (T1485), then extortion follows.

ATT&CK notes that ransomware operators may perform account access removal before Data Encrypted for Impact (T1486) to impede response and recovery. The techniques that often appear around T1531 are T1486 (encryption), T1485 (data destruction), T1489 (service stop), T1499 (endpoint denial of service), and, in extortion chains, T1657 (financial theft).

Words this guide uses

Identity provider (IdP)

A cloud service that holds logins and decides who may sign in to other apps. Examples: Microsoft Entra ID, Okta.

Domain controller (DC)

A Windows server that holds all domain accounts and answers login requests. Deleting an account here removes it company-wide.

SIEM

Security Information and Event Management: a platform (for example Splunk) that collects logs from many systems and lets you search and alert on them.

EDR

Endpoint Detection and Response: agent software on computers that records processes and file actions, and can block behavior.

MFA

Multi-Factor Authentication: a second proof beyond the password, such as an app approval or a hardware key. Removing it weakens every account that uses it.

SOC

Security Operations Center: the team (and the room) that watches alerts and responds to incidents.

Break-glass account

A special emergency admin account kept for disasters, normally unused and tightly monitored. Attackers love to delete it, because responders need it most when everything else fails.

Burst

Many similar events in a short window, for example six password resets in four minutes. Bursts are the core detection idea in this guide.

The same story in words

Each step below matches one frame of the animation, including the evidence it produces.

  1. 1 · Stolen credentials. The attacker holds a domain-admin password stolen in a phishing campaign two days earlier. No account changes have happened yet, so the SIEM is quiet. The only early signal is the phishing report itself — which is why reporting culture matters.
  2. 2 · RDP logon to the domain controller. From the shared admin workstation ADM-WKS-04, the attacker opens a Remote Desktop (RDP) session to DC01 at 03:12 local time. Evidence: Event 4624 with Logon Type 10, plus 4672 "special privileges assigned" for the admin account. Few people ever RDP into a domain controller, and almost never at that hour.
  3. 3 · Password resets. The attacker resets the passwords of six admin and service accounts in four minutes, DEADWOOD-style — each password becomes a long random value only the attacker knows. Evidence: six 4724 events sharing one SubjectUserName within the same session.
  4. 4 · Security accounts disabled. Next, nine security-team and admin accounts are disabled, so analysts cannot log in to investigate. Evidence: a burst of 4725 events from the same subject. This step is why the SOC must alert on disables, not only on deletions.
  5. 5 · Admin accounts deleted. The attacker deletes four accounts, including two administrator accounts — the Akira pattern, performed right before encryption in real cases. Evidence: 4726 events, each recording the SubjectUserName of the stolen admin. That field names the attacker's path.
  6. 6 · Lockout storm. The attacker deliberately types wrong passwords against the remaining admin accounts. After repeated failures, account lockout policy kicks in: fourteen 4740 lockout events appear in ten minutes, all from the same source workstation. The remaining admins are now locked too.
  7. 7 · Cloud identity sabotage. In parallel, the attacker uses a stolen Global Admin session in the cloud identity provider. They remove MFA factors from admins and deactivate the break-glass account. Evidence: Entra ID audit records such as "Delete user" and "User deleted security info" — the LAPSUS$ pattern of locking an organization out of all access.
  8. 8 · SOC contains and recovers. The SIEM correlates the 4724 + 4725 + 4726 burst into one critical incident. The SOC revokes attacker sessions, blocks the source, activates the second break-glass account, and restores accounts and MFA settings from the identity configuration backup. Recovery time depends entirely on the quality of that backup and runbook.
Good practice

Notice that every destructive step wrote an event. The attacker was fast, but each burst was visible within seconds. The defense that worked was not a magic product — it was collecting identity logs, watching change rates, and keeping one untouched break-glass path.

Try it yourself — safe exercise

You do not need attack tools to learn this technique. You need one disposable Windows virtual machine and a free Splunk trial (or any lab SIEM). The exercise below only creates events that your own lab detects. It trains the muscle that matters: seeing a burst the way an analyst sees it.

  1. Prepare the lab VM and turn on the audit subcategories User Account Management and Logon/Logoff (run secpol.msc → Local Policies → Advanced Audit Policy).
  2. Create three throwaway users with net user lab01 /add. Then disable and delete them. Find the 4720, 4725, and 4726 events in Event Viewer and read their fields.
  3. Forward the Security log to your lab SIEM with the Splunk Add-on for Windows (or any log shipper).
  4. Run the TH-01 SPL query from section 5.5 against your own events. You should see one row with targets = 3.
  5. Repeat the same actions slowly, hours apart, and run the search again. The burst disappears — that is the whole idea of window-based detection.

Keep the VM off any real network. Take a snapshot before you start, and delete the VM afterwards. If the lab shares a network with systems you do not own, stop and ask first.

3

Red team perspective

This section explains how attackers think about account access removal and how ethical teams rehearse it in labs. Everything here is conceptual or lab-only. Nothing on this page should ever be run against systems you do not own.

Why attackers remove access

Removing access is not random vandalism. It serves four concrete goals, and each one increases the attacker's leverage:

Blind the defenders

If SOC analysts cannot log in to their workstations, the SIEM, or their EDR consoles, the attacker buys minutes or hours of no response time. Those minutes are when encryption runs.

Break the recovery path

Backup admin accounts, service accounts, and break-glass accounts are exactly what responders need. Removing them first turns a one-day incident into a week-long rebuild.

Increase extortion pressure

Every locked-out employee is visible pressure. Extortion messages often count the hours since "your organization lost all access" to push payment.

Cover the exit

Deleting the accounts that attackers used makes later forensic review harder. The stolen admin account that performed the deletion is evidence — so its trail matters.

When it happens in an attack

Account access removal appears late in the kill chain, after the attacker already holds privileged access. ATT&CK documents two main moments. Akira deletes admin accounts immediately before encryption. LAPSUS$ removed global admin accounts during extortion, to lock the organization out. Some campaigns also strip access on ESXi hypervisors before destroying virtual machines, because hypervisor accounts control every VM at once.

What attackers need first (prerequisites)

  • Privileged credentials — domain admin, Global Admin, Okta administrator, or ESXi root, usually stolen via phishing, info-stealer malware, or bought from a broker.
  • Network or session access — a foothold on an admin workstation, an RDP path, or a valid cloud session token.
  • Knowledge of the account landscape — which accounts are admins, which run services, which are break-glass. Attackers enumerate with simple directory queries before acting.
  • Time pressure tolerance — these actions are loud. Attackers accept that, because the payoff is that defenders cannot react at all.

Common variations

Bulk delete

Remove many account objects at once, especially admins. Akira pattern; leaves loud 4726 bursts.

Reset then logoff

Change passwords to random values, then force logoff or reboot. DEADWOOD, LockerGoga, MegaCortex, Meteor pattern.

Disable responders

Disable security-team and backup-admin accounts first, 4725 bursts, often before anything is deleted.

Lockout storm

Deliberately fail logons against admin and service accounts until lockout policy does the job. 4740 bursts.

IdP sabotage

Deactivate users, remove Global Admins, strip MFA in Entra ID or Okta. LAPSUS$ pattern; visible only in cloud audit logs.

Break-glass removal

Delete the emergency accounts and revoke SaaS permissions (for example SharePoint admin rights) so recovery has no starting point.

Mistakes attackers make

  • Using one stolen account for everything. Every 4724, 4725, and 4726 event records the SubjectUserName. One name on a burst is an incident lead handed to the SOC for free.
  • Forgetting lockout policy. Blind password guessing against accounts with lockout thresholds produces the very 4740 storm that raises the alert.
  • Assuming the cloud forgets. IdP audit logs are immutable and timestamped. Deleting accounts does not delete the record of deleting them.
  • Working at 3 a.m. Off-hours privileged changes are rare in normal business, so time-of-day baselines catch bursts quickly.
  • Ignoring break-glass backups. A second emergency account, stored offline and monitored, quietly defeats the whole strategy.

How this shows up on our side

SIEM burst alerts

The first signal is usually a rate change: N password resets, disables, or deletions within minutes from one subject account. If your SIEM has identity dashboards, this is where it appears.

Help-desk tickets

"I can't log in" calls spike. Correlating tickets with identity events tells you whether this is a simple sync mistake or an active attack.

EDR process alerts

On endpoints, process creation events show net user /delete, Disable-ADAccount, or esxcli running from an unexpected parent or at an unexpected hour.

Why it matters to defenders

An attacker who removes access has moved from stealing to denying. Response capability now depends on accounts that may no longer exist. The practical consequence: identity events must alert while responders can still log in, and every second between the first disable and containment matters. This is why identity bursts deserve near-real-time alerting, not next-morning review.

Position in the attack chain

  • Before: phishing and initial access, credential theft from memory or info-stealers, privilege escalation to admin level. If you see T1531 activity, assume the credentials of the SubjectUserName are fully compromised.
  • Alongside: service stops (T1489), backup destruction (T1485), hypervisor corruption (T1495).
  • After: encryption (T1486), endpoint denial of service (T1499), extortion and financial theft (T1657).

First-hour triage flow

  1. Validate the burst. Is there a planned change window, offboarding wave, or HR sync? If yes, close the alert with the ticket number. If no, treat it as an incident.
  2. Build the target list. Export every affected account from 4725/4726/4724 and IdP audit events. Who was disabled, deleted, reset, or stripped of MFA?
  3. Identify the subject. Which account performed the changes (SubjectUserName / IdP actor)? Assume its credentials are stolen. Do not "fix" using that account.
  4. Check the cloud identity provider. Look for matching admin operations, MFA removals, and role changes. Attackers often run on-prem and cloud actions in parallel.
  5. Protect your own access. Activate the break-glass account, and revoke attacker sessions (token revocation, disable the compromised account's sessions, block source IPs) before touching anything else.
  6. Restore from trusted state. Re-enable or recreate accounts from the identity configuration backup. Force password resets at first logon. Re-register MFA from documented recovery steps.
  7. Hunt persistence and preserve evidence. Look for new admin accounts (contrast T1136), new OAuth (third-party application) grants, and inbox rules. Export the full event trail before cleanup overwrites it.
Warning

Do not restore accounts using the possibly-compromised admin session. Attackers sometimes re-abuse restored accounts the moment they are re-enabled. Restore from a trusted path, then rotate the credentials of every restored privileged account.

Questions the first-hour lead keeps asking

  • Who is acting? — one SubjectUserName or IdP actor for the whole burst, or many? One actor is a person; many actors with one ticket is probably sanctioned change.
  • What class of accounts? — admins, service accounts, break-glass, or ordinary users? The higher the class, the faster the clock.
  • Did the attacker touch the cloud too? — check Entra and Okta for matching operations before declaring the blast radius on-prem only.
  • Can we still act? — does at least one responder path (break-glass, separate forest, out-of-band console) still work right now?
  • What is the restore source? — identity configuration export, AD Recycle Bin, or nothing? The answer decides whether recovery takes minutes or days.

5.2

Threat intelligence

Threat intelligence turns public reporting into the fields you can alert on. For this technique the loop is short: groups that use T1531 are well documented, and their behaviors map cleanly onto identity logs.

Sources and collection

  • MITRE ATT&CK and related resources — the technique page and group pages (first stop; each group page lists procedure examples you can turn into detections).
  • Vendor reports and blogs — incident response write-ups from security vendors describe how specific ransomware crews handled accounts before encryption.
  • ISACs — Information Sharing and Analysis Centers share anonymized member incidents; sector peers often face the same crews in the same weeks.
  • Commercial feeds — curated indicators and TTP (tactics, techniques, and procedures — the attacker's methods) feeds; useful if they include behavior, not just IPs and hashes.
  • OSINT — open-source intelligence: leaked negotiation chats, researcher threads, and malware sample repositories.
  • Internal telemetry — your own SIEM and EDR history. The best baseline of "normal" account administration comes from your own data.

From intel to detection

  1. Extract the behavior from the report: "group X deletes admin accounts before encryption."
  2. Map it to the technique (T1531) and the exact actions (4726 deletions by one subject; IdP admin removal).
  3. Name the fields it must touch in your logs (SubjectUserName, TargetUserName, EventID, ActivityDisplayName, eventType).
  4. Write the rule with a rate window (bursts, not single events) and set severity from business impact.
  5. Assign a confidence level and record where the idea came from, so you can revisit it when reporting changes.

Confidence levels

  • High — multiple independent sources, or official ATT&CK documentation with procedure examples.
  • Medium — one credible source, or partial evidence that has not been reproduced elsewhere.
  • Low — anecdotal or secondary reporting; treat as context, not as a detection driver.

Worked example — from a report to a rule

Here is the whole loop with real words, so you can copy the method. A vendor publishes an incident report. It says the crew deleted two administrator accounts on a domain controller eleven minutes before the ransomware started encrypting. You work through five short steps.

  1. Extract the behavior. Two 4726 deletions on a domain controller, eleven minutes before encryption, performed with a stolen domain-admin session.
  2. Map it. The behavior is T1531. The log is the Windows Security event log on domain controllers.
  3. Name the fields. EventID 4726, TargetUserName (the admins), SubjectUserName (the stolen admin), Computer (the DC), and the timestamp.
  4. Write the rule. Two deletions alone are normal. Two deletions within minutes, on one DC, by one subject, is the shape you want. Your first threshold starts at three or more in ten minutes, so a single ticket-backed cleanup never fires.
  5. Record the source and confidence. "Vendor report, behavior documented on the ATT&CK page — confidence High." Six months from now someone will ask "why do we alert on this?" The answer should be one click away.

Then you test. Replay the sample events from section 5.4 into a test index and check the rule fires. Fire one benign event at it — a single 4726 from your provisioning account — and check it stays quiet. A rule that was never tested is a guess with a name.

Free starting kit

You can build every detection in this guide with free material: the ATT&CK page for T1531 (behavior and procedure examples), the public Sigma rule repository (ready-made Windows account rules to compare against), your platform's own audit documentation (Microsoft and Okta both publish field references), and the sample events in section 5.4 of this guide. Start there before you buy anything — the gap is usually collection and attention, not tooling.

Critical Windows Identity TH-01 · Bulk domain account deletion or disablement

Description. An attacker with domain admin rights deletes or disables many accounts on the domain controllers in one burst — administrators first, then service and security-team accounts. This is the documented Akira pattern: delete admin accounts, then encrypt.

Preconditions. Compromise of a domain admin (or equivalent) and an interactive or remote path to a domain controller.

Why Critical. It strikes the identity layer that everything else depends on, removes the response team's own access, and in documented cases ransomware started within minutes.

Critical Identity Cloud TH-02 · Identity provider takeover

Description. Using a stolen Global Admin or Okta administrator session, the attacker deactivates users, removes Global Admins, and strips MFA security info in Entra ID or Okta. This is the LAPSUS$ pattern of locking an organization out of all access.

Preconditions. A compromised privileged cloud session (help-desk reset, token theft, or MFA fatigue) and knowledge of the tenant's admin structure.

Impact. Organization-wide lockout from email, files, and SaaS apps; attacker-controlled MFA re-registration; possible takeover of federation settings.

Why Critical. One cloud session can remove access for thousands of users in minutes. Many organizations also monitor cloud audit logs far less closely than on-prem Windows events.

High Windows TH-03 · Mass password changes with forced logoffs

Description. The attacker resets passwords of many local and domain accounts to random values (the DEADWOOD, LockerGoga, MegaCortex, and Meteor pattern) and logs users off or reboots systems so old sessions cannot survive.

Preconditions. Local admin on endpoints or domain admin in the domain; malware or hands-on-keyboard access.

Impact. Users cannot authenticate anywhere their password was reset; sessions die mid-work; help-desk is flooded; automated services break as their stored credentials stop working.

Why High. The scope is large, but execution is slower than TH-01 and TH-02. It leaves a clear 4724 trail from one subject, so detection odds are strong.

High Windows Identity TH-04 · Deliberate lockout storms

Description. Instead of touching accounts directly, the attacker intentionally fails logon attempts against admin and service accounts until lockout policy disables them, producing bursts of 4740 events.

Preconditions. Network reachability to a domain controller or authentication endpoint, plus a list of account names (usernames are usually easy to enumerate).

Impact. Chosen accounts become unusable without any privilege at all; attackers use it to deny access to admins, to punish non-payment, or as noise during a bigger operation.

Why High. It needs no stolen credentials — only reachability — so even low-skill actors can run it. Impact is bounded because lockouts auto-expire, but the timing can be surgical.

High ESXi Linux TH-05 · Hypervisor and server account sabotage

Description. On ESXi hosts, the attacker removes or re-credentials local accounts with esxcli; on Linux servers, accounts are locked with passwd -l / usermod -L or removed with userdel. Hypervisor access controls every virtual machine at once.

Preconditions. Root or admin shell on the host, usually via SSH (Secure Shell, the standard command-line remote login), after credential theft or exploitation of an exposed management interface.

Impact. Admins cannot manage hosts or VMs; backup and monitoring agents that run under removed service accounts silently die; recovery teams must rebuild host access.

Why High. ESXi holds the estate's most concentrated impact, yet host logs are the least monitored part of many environments. Detection coverage is usually the weakest here.

Medium SaaS Cross-platform TH-06 · Break-glass and backup-service account removal

Description. Quietly deleting emergency (break-glass) accounts and backup-service accounts, or revoking their SaaS permissions — for example removing SharePoint admin rights — so that recovery has no working starting point when it is needed.

Preconditions. Admin access to the IdP or the SaaS tenant; reconnaissance that identified which accounts are the recovery path.

Impact. On its own, users stay online; the damage appears during an incident, when responders reach for the emergency account that no longer exists or the backup agent has no permissions.

Why Medium. The immediate blast radius is small, which is exactly why it ranks below the others — but it multiplies the cost of every other threat. Detection is easy if break-glass accounts are inventoried and any touch on them alerts.

For each threat: the log sources to collect, the fields that matter, what normal looks like versus what suspicious looks like, a plain-language detection rule, and at least three realistic sample events. All samples are fabricated for teaching; the domains use .lab names on purpose.

TH-01 · Bulk domain account deletion or disablement

Log sources. Windows Security event log from all domain controllers (forward to the SIEM in near real time). Optional second opinion: EDR process events for the same host.

Key fields. EventID, TargetUserName (the account changed), SubjectUserName (who made the change — your prime suspect), SubjectDomainName, TargetSid, SubjectLogonId (join it to the matching 4624 logon to learn which workstation the subject used).

Detection logic

Alert when one subject account produces at least 4 account removal events (4725 or 4726 combined) within a 10-minute window on any domain controller. Raise to critical if any target is an admin account or if the hour is outside 07:00–20:00 local time.

Read the three events as one story. In 94 seconds, one subject (a.hollis) deleted two accounts and disabled a SOC analyst's account. The deleted accounts were a backup admin and a named administrator. The changes came from workstation ADM-WKS-04 at 01:14 local time. Any one of those facts alone is interesting; together they are an incident.

Benign look-alike · TH-01

Healthy environments delete accounts every day. This is what the quiet version looks like: one deletion, middle of the day, by the documented provisioning account, matching an HR ticket. Single events from a known service account at a known hour are exactly what your threshold should absorb without a page.

The tell is the shape, not the words: svc-offboard deletes accounts all day long, one at a time, from the same host. The attack shape is the opposite — a named human account, many targets, minutes apart.

TH-02 · Identity provider takeover

Log sources. Entra ID AuditLogs (Microsoft 365 audit or Azure Monitor export) and the Okta System Log, both streamed into the SIEM. These are the only records of cloud account removal — there is no on-prem event log for them.

Key fields. Entra: ActivityDisplayName (the operation name), actor UPN, Result, target user. Okta: eventType, actor.alternateId, target list, outcome.result.

BehaviorWhat it looks like
NormalDeactivations and deletions tied to offboarding tickets during business hours, executed by the provisioning tool's service principal; MFA security-info changes done by users for themselves (new phone) at a steady, low rate.
Suspicious"Delete user" or "Disable account" performed by a human admin account with no linked ticket; "User deleted security info" or factor removal on admin accounts; batches of operations within minutes; any of the above outside the change window.
Detection logic

Alert on any of: (a) 3 or more user deactivations/deletions within 10 minutes by one actor; (b) any MFA security-info deletion on an account holding an admin role; (c) any lifecycle operation on a break-glass account. Correlate with the help-desk ticket queue to dismiss planned changes.

Three records, one actor, four minutes: the emergency account deleted, a SOC lead disabled, and an admin's MFA authenticator removed — all from the same external IP. The actor is a real Global Admin whose session was stolen; the events look like normal admin work until you correlate ticket, timing, and IP.

Benign look-alike · TH-02

Cloud tenants also disable and delete users all the time — that is normal lifecycle work. The quiet version is initiated by an application (the HR sync service principal), not by a human session. That is why the TH-02 rule filters service-principal actions first: the filter removes this whole class of noise before it ever reaches an analyst.

TH-03 · Mass password changes with forced logoffs

Log sources. Windows Security events from DCs and endpoints (4723/4724 password changes and resets, 4738 user account changes, 4647 user-initiated logoff), plus EDR process creation to see the tool that did it.

Key fields. EventID, TargetUserName, SubjectUserName, WorkstationName; in EDR events: CommandLine, Image, parent process, user context.

BehaviorWhat it looks like
NormalPassword resets arrive from the service-desk tool or self-service portal, a handful per hour, different subjects, matched to tickets; scheduled service-account rotations change one account at a time in a maintenance window.
SuspiciousMore than 5 resets within 10 minutes by one SubjectUserName; resets on admin and service accounts without tickets; net.exe or Set-LocalUser spawning from a script or unexpected parent; logoff storms right after resets.
Detection logic

Alert when one subject account resets more than 5 passwords within 10 minutes, and add a second rule for any interactive tool (net.exe, net1.exe, PowerShell) performing account changes on servers. Boost severity if 4647 logoff events follow within 5 minutes — that is the LockerGoga/MegaCortex rhythm.

The Sysmon event adds detail. The Security log only says "someone reset a password". The process event shows the exact tool, the full command line, the user context, and the odd parent process. The random-looking 32-character password matches the documented DEADWOOD behavior of making accounts unloggable.

Benign look-alike · TH-03

Service desks reset passwords in batches, and a policy change can create dozens of 4724 events in an hour. The quiet version comes from the reset tool's service account, inside working hours, with a ticket wave behind it. Your tuning lever is the allowlist from the TH-03 rule: exclude the documented tool accounts, and this noise never fires the alert.

TH-04 · Deliberate account lockout storms

Log sources. Windows Security event 4740 from domain controllers (the PDC emulator — the domain role that sees every lockout — writes them all), plus firewall or VPN logs if the flood comes from outside.

Key fields. TargetUserName (locked account), CallerComputerName (where the bad attempts came from), count and uniqueness of targets per window.

BehaviorWhat it looks like
NormalA few lockouts per day, different source machines, classic pattern: a user changed a password but an old device kept trying, or a stale mapped drive holds old credentials. One target, one source, one or two events.
Suspicious5 or more unique locked targets within 10 minutes; the same CallerComputerName across many targets; targets concentrated on admin and service accounts; lockouts continuing after the source is rebooted.
Detection logic

Alert when at least 5 unique accounts are locked out within 10 minutes, grouped by source machine. Filter out the classic "one user, one stale device" pattern by requiring more than one distinct target. Group the targets: if they are all admins or all service accounts, treat as intentional denial and escalate.

Three lockouts, three different targets, one source machine, in under three minutes. The one-source-many-targets shape is the fingerprint of a deliberate storm; normal stale-credential noise almost never touches three admin-class accounts in a row.

Benign look-alike · TH-04

The classic false positive: one user changes a password on their phone, and an old laptop keeps trying the old password all afternoon. The result is many 4740 events — but always the same user, from the same machine. This is exactly why the SPL counts distinct targets. The burst below would fire a raw-event rule and should never fire the tuned one.

TH-05 · Hypervisor and server account sabotage

Log sources. ESXi: /var/log/auth.log (SSH sessions) and /var/log/shell.log (commands typed in the shell), forwarded by syslog. Linux servers: /var/log/auth.log or secure for userdel, usermod, passwd, and sudo records.

Key fields. Host, timestamp, process name (esxcli, userdel, usermod, passwd), the account argument, and the initiating user or session.

BehaviorWhat it looks like
NormalAccount changes on hosts are rare and tied to change tickets: a quarterly service-account rotation, one host, documented operator, inside the maintenance window. ESXi shells see mostly esxcli system account list during audits.
Suspiciousesxcli system account remove or account set commands by anyone outside a change window; bursts of userdel or locked passwords (usermod -L, passwd -l) across several servers in minutes; commands run from a session opened minutes earlier from an unknown IP.
Detection logic

Keyword-plus-rate rule: alert on any esxcli system account remove or esxcli system account set command, and on 2 or more userdel/passwd -l/usermod -L commands from one host or operator within 15 minutes. Host account changes are so rare that a zero-baseline works: almost any occurrence deserves a look.

Read from the top: on ESXi, a service account is removed, then the attacker changes the root password — so the login at 01:53:10 is probably the attacker, not root. On Linux, the svcops account (likely already stolen) uses sudo to lock backup-admin accounts. The pattern repeats across hosts; the individual lines look like routine admin noise until they are correlated.

Benign look-alike · TH-05

Host account changes do happen: service-account rotations, decommissioning old servers, and quarterly cleanup. The quiet version touches one host, comes from the automation account, and matches a change ticket. A zero-baseline rule will still show it to you — and that is fine, because a human glance takes seconds when the shape is familiar.

TH-06 · Break-glass and backup-service account removal

Log sources. Entra ID audit (delete or update operations on the break-glass UPNs — user principal names, the sign-in names), Okta system log (lifecycle events on service accounts), and Microsoft 365 / SharePoint audit for permission revocation. Feed a written inventory of break-glass and service account names into the SIEM as a watchlist.

Key fields. Operation name, target user principal name or display name, actor, timestamp, result. The watchlist match is what turns a routine operation into an alert.

BehaviorWhat it looks like
NormalEssentially nothing. A healthy break-glass account logs almost no events: a test sign-in each quarter, maybe a vault-driven credential rotation. Service-account lifecycle events happen only in documented migrations.
SuspiciousAny delete, disable, password reset, MFA change, or permission revocation touching a watchlisted break-glass or backup-service account — from anyone, at any time, for any reason.
Detection logic

Inventory-based rule: join identity audit events against the break-glass and service-account watchlist; alert on every match with zero-baseline sensitivity. This rule is intentionally noisy-proof: because these accounts never change under normal operations, false positives are near zero.

The recovery path dies in five minutes: the backup service account is deleted in Entra, a reporting service account is deactivated in Okta, and the second break-glass account loses its SharePoint admin rights. None of these events is dramatic alone — the watchlist join is what makes them impossible to miss.

Benign look-alike · TH-06

The one legitimate touch on a break-glass or vault-managed account is the scheduled credential rotation. It comes from the vault's own account, at a fixed minute, and your runbook documents it. The quiet version still fires your zero-baseline alert — by design — and the analyst closes it in one look. If these events start arriving at strange hours or from unknown actors, that is the signal.

How to test each rule before it goes live

Every rule in this section can be tested with the sample events you already have. The loop takes minutes and saves hours of tuning later.

  1. Replay the suspicious samples. Load the section 5.4 events into a test index and confirm the rule fires with the expected severity.
  2. Replay the benign look-alike. Feed the benign event from each threat's look-alike card. The rule must stay quiet. If it fires, tighten the filter before an analyst ever sees the alert.
  3. Test the window edges. Place two burst events 11 minutes apart and confirm a 10-minute rule does not join them. Edge bugs are the most common silent failure.
  4. Check the fields, not just the count. Confirm the alert shows TargetUserName, SubjectUserName, and the source host. An alert you cannot act on is a false positive with extra steps.
  5. Write the result down. One line per test: date, input, expected, seen. Attach it to the rule's ticket so the next editor inherits proof, not folklore.

Log-source readiness checklist

Before any rule in this section goes live, walk this list. A rule is only as good as the feed it reads.

  • Windows Security events arrive from every domain controller, not just one; check the host count in the last hour.
  • Entra ID AuditLogs and the Okta system log land in the SIEM, and field names are confirmed on a real sample event.
  • ESXi auth.log and shell.log forward through syslog, and the pipeline survives a host reboot.
  • Clock skew across sources is under two minutes, so burst windows line up correctly.
  • Retention covers at least 90 days of hot storage, so investigations can look back further than yesterday.
  • Each rule has a named owner and a runbook link in the alert text.

Real-world case study

Warning — composite scenario

This case study is a composite, invented for teaching. It does not describe one specific real company. It combines documented behaviors: the LAPSUS$ removal of global admin accounts, the Akira pattern of deleting accounts before encryption, and the 2023–2024 wave of help-desk identity attacks. All names, hosts, times, and figures are fictional.

Meridian Freight is a fictional logistics company with 4,000 employees. Mail, files, and the customer portal run on a SaaS estate managed through Entra ID; on-prem Windows servers and a small VMware cluster run the warehouse systems. Identity hygiene was decent on paper: MFA everywhere, a written offboarding process, and two break-glass accounts. But the service desk reset MFA over the phone, identity audit logs were retained but never alerted on, and nobody had ever rehearsed a mass-account-restore.

Timeline

Day −3 · 10:22
MFA fatigue push

An employee's phone is flooded with push approvals. They tap "approve" once at lunch — the attacker's relay captures the session cookie.

Day −1 · 15:48
Help-desk reset

Caller "from the CFO's office" loses their phone. The desk resets MFA after a friendly call — no callback to the number on file. The attacker now controls the Global Admin account's MFA.

Day 0 · 09:14
Attacker registers a device

From a residential proxy IP, the attacker registers their own phone as the admin's MFA method and signs in. Entra logs "User registered security info" — nobody is watching.

Day 0 · 23:47
Security accounts disabled

Six security-team accounts are deactivated in Entra in four minutes ("Disable account" ×6). The SOC's own access to cloud consoles begins to fail.

Day 1 · 00:12
Break-glass deleted, MFA stripped

Break-glass account bg-01 is deleted; MFA factors are removed from three admins; a SharePoint admin permission is revoked from bg-02.

Day 1 · 00:40
On-prem bursts

Using a compromised domain admin, the attacker resets six service passwords (4724 ×6), disables four accounts (4725 ×4), and triggers a 4740 lockout storm against remaining admins.

Day 1 · 06:05
Extortion demand

An email demands payment within 72 hours and points out that "your administrators no longer exist." Encryption has not started yet — access removal is the opening move.

Day 1 · 06:20
Detection

The SIEM's identity burst rule fires: 10-minute windows with 6+ lifecycle changes by one actor, joined with the service-desk ticket for the CFO reset. An analyst on a spare local account confirms and declares a major incident.

Attack chain

The chain is short and entirely identity-driven: an MFA-fatigue push, one weak help-desk verification, and a stolen Global Admin session. The attacker then moved in two directions at once — cloud (deactivate users, delete break-glass, strip MFA) and on-prem (reset, disable, delete, lock out). Removing access came before any encryption, matching the documented ransomware order where T1531 precedes T1486 to slow response.

Detection point

Two independent signals converged: the Entra audit burst (six deactivations in four minutes by one actor at 23:47) and the correlation between that actor and the help-desk ticket opened two days earlier. Neither was caught in real time — the alert fired at 06:20 on review. The lesson: the data was all there for 30 hours; what was missing was a live rule on ActivityDisplayName bursts, and a join between tickets and audit logs.

Containment

  • Revoked all refresh tokens for the compromised Global Admin and disabled its sessions; blocked the proxy IP range at the perimeter.
  • Activated break-glass account bg-02 (still alive) from the offline vault to regain tenant admin access.
  • Re-enabled the six SOC accounts from an on-prem Tier-0 admin workstation that the attacker never touched.
  • Froze all service-desk MFA resets company-wide until the verification procedure was fixed.

Eradication

  • Removed the attacker's registered MFA device and inspected every admin account for new security info.
  • Reset credentials for all Tier-0 and service accounts; re-registered MFA from documented recovery steps.
  • Reviewed OAuth grants and found none — the attacker never needed one; pure session abuse.
  • Hunted for persistence for five days: no new admin accounts (contrast T1136), no inbox rules, no rogue enterprise apps.

Recovery

Accounts and MFA settings were restored from a monthly IdP configuration export plus documented runbooks. Because the runbook had never been tested, restore work took twice the planned time. Service accounts needed manual re-permissioning where permissions had been revoked in SaaS consoles. Total SaaS outage for affected users: about 36 hours.

Impact and consequences

  • Roughly 3,700 users lost mail, files, and portal access for 12–36 hours; warehouse picking fell back to paper.
  • No confirmed data theft and no encryption — the impact was pure availability loss, which is exactly what T1531 alone can do.
  • Financial impact: lost throughput, overtime, and external response support (a fictional but realistic mid six-figure sum).
  • Regulatory: a 72-hour availability-incident notification was filed under NIS2; the audit trail helped the report.

Team response and communication

The SOC declared a major incident and opened a war room with IT, the service desk, and communications. Updates went to leadership every two hours with three numbers: accounts restored, services back, attacker access confirmed dead. The service desk was briefed with a one-page script so staff calls got one consistent answer. One analyst kept a plain-text timeline from the start — it became the backbone of the final report.

Evidence to preserve early

Account records are easy to recreate and hard to reconstruct. Before cleanup starts, export and store offline: the full 4724/4725/4726/4740 event trail from every domain controller for the incident window; the Entra and Okta audit exports; the help-desk tickets and call recordings for the affected days; the 4624 logon history of the subject accounts; and (if available) the EDR process timeline for the admin workstation. These five exports let you rebuild the story even after the attacker's changes are repaired.

Lessons learned

  • Two break-glass accounts, both monitored. bg-01 died; bg-02 saved the response. Had the attacker found both, recovery would have started days later.
  • Callback verification is cheap insurance. One callback to a number on file would have ended the attack before it started.
  • Live rules on IdP audit logs. Retention without alerting is data nobody acts on. Burst rules must run in near real time.
  • PIM would have shrunk the blast radius. A standing Global Admin role gave one session unlimited power; just-in-time elevation (Privileged Identity Management, PIM) would have limited it.
  • Test the restore. A quarterly two-account restore drill would have halved recovery time.

What worked, what failed

What worked

  • Two break-glass accounts meant one survived. bg-02 kept the response alive.
  • MFA was on everywhere, which forced the attacker into social engineering — a slower, noisier path than a straight credential dump.
  • Retention held: the Entra audit log kept everything, so the investigation could rebuild the full 30 hours.
  • Communication discipline: two-hour updates stopped rumor-driven password-reset stampedes that would have buried the SOC.

What failed

  • No live alert on identity bursts. The data waited 30 hours for a human to look.
  • Help-desk verification by plausibility instead of callback — the single point of failure of the whole story.
  • The restore runbook had never been run, so recovery took twice the planned time.
  • Service-account permissions lived only inside SaaS consoles. Nobody had an export, so re-permissioning was slow manual work.

Mitigation and defense

You cannot block every admin action — account administration must stay possible. The defenses below raise the cost of abuse, shrink the blast radius, and guarantee that recovery stays reachable.

Enterprise controls

Break-glass accounts (two of them)

These accounts live only in the cloud. They sit outside conditional-access rules. Their credentials stay sealed in an offline vault. Nobody uses them for daily work. Any sign-in or any change fires an alert, because the normal baseline is zero. Rehearse their use quarterly.

Just-in-time privileged access (PIM)

No standing Global Admin. Admin roles are activated for hours with approval and logging (Privileged Identity Management, PIM). A stolen account then holds no power until it elevates — and every elevation is an event you can alert on.

Tiered administration

Separate admin accounts per tier (workstation / servers / cloud), no admin mail on Tier-0 accounts, dedicated admin workstations. The account an attacker steals from a phishing mail should not be the account that runs the domain.

Help-desk identity verification

Callback to the number on file, video verification for privileged users, and a hard rule: no MFA resets for admin accounts without a second approver. This closes the entry point used in most identity takeovers.

Identity audit to SIEM, with rate alerts

Stream Windows Security (4724/4725/4726/4740), Entra AuditLogs, Okta system log, and ESXi/Linux auth logs into the SIEM. Deploy the burst rules from section 5.5 and page on critical ones.

Identity configuration backup

Export IdP configuration (users, roles, MFA policy, group memberships) on a schedule, store it offline, and test restoring two accounts from it every quarter. Without this, recovery means rebuild.

Protect service accounts

Inventory every service and backup account, forbid interactive logon, rotate credentials on schedule, and put their names on a watchlist so any touch alerts (TH-06 rule).

Practiced recovery runbook

A written, owned, tested procedure: scope from the target list, revoke sessions, activate break-glass, restore accounts, hunt persistence. Run it as a tabletop twice a year and a live drill once a year.

Home and small office

If you run a small business or just your own machines, you still face this technique — a stolen session can delete your only admin account and your recovery codes with it.

  • Use a password manager and keep offline recovery codes printed or on paper, not only in the cloud account they unlock.
  • Keep a secondary local admin account on your computers, with a strong unique password you store with the recovery codes.
  • Turn on MFA everywhere it exists, and register two factors (an app and a hardware key if possible).
  • Write a five-line recovery plan: where the codes are, which account is the backup admin, who to call. Update it when anything changes.

The one drill that pays for this whole guide

Once a quarter, in a change window, run this 45-minute exercise with two people:

  1. Restore one account from the identity configuration export. Time every step.
  2. Sign in to the cloud tenant with a break-glass account from the vault, and confirm the zero-baseline alert actually fired.
  3. Revoke your own sessions with the token-revocation runbook, then prove you can get back in.
  4. Write down every step that surprised you. Fix one of them before the next drill.

If step 1 takes more than 30 minutes, or step 2's alert never fired, you have found a real gap on a calm day instead of during a bad night.

Common mistakes and best practices

Thirteen concrete mistakes blue teams make around account access removal, each with the symptom you will notice, the root cause behind it, the fix, and the prevention that keeps it fixed. Then a habit list for daily, weekly, and monthly work.

1 · Treating every 4726 as routine deprovisioning

Symptom
Deletion alerts are closed as "HR offboarding" without checking any ticket.
Root cause
No linkage between identity events and the approval workflow, so every event looks equally boring.
Fix
Require a ticket reference in the alert triage note; escalate any 4726 with no matching ticket within the hour.
Prevention
Enrich identity alerts with the ticket queue feed so the correlation is automatic, not memory-based.

2 · No baseline of account-change rates

Symptom
Thresholds were guessed once; nobody knows whether 3 deletions an hour is normal for your estate.
Root cause
The rule was written from a vendor example, not from your own data.
Fix
Measure 90 days of 4724/4725/4726 rates per domain and per subject type, then set thresholds at the measured maximum plus margin.
Prevention
Re-baseline quarterly and after big org changes such as mergers or mass hiring waves.

3 · Cloud IdP audit logs never ingested into the SIEM

Symptom
The cloud takeover in section 6 would have been invisible; you only look at Windows events.
Root cause
On-prem-first habits; the IdP console "has logs" so nobody wired them anywhere.
Fix
Stream Entra AuditLogs and the Okta system log into the SIEM this week — both have supported export paths.
Prevention
Keep a source-coverage matrix listing every identity provider and its ingestion status; review it monthly.

4 · Alerting on deletes but not on disables

Symptom
Rules cover 4726 only; the attackers' preferred first move (4725 disable of responders) is not detected.
Root cause
"Delete" feels like the destructive step; "disable" feels administrative.
Fix
Add 4725 and IdP "Disable account" to the same burst rules, with the same or lower thresholds.
Prevention
Review coverage against the full event list in section 5.4 whenever the detection pack changes.

5 · No working break-glass account

Symptom
When the incident hit, the emergency account was expired, locked, or missing; responders used a compromised admin "just this once".
Root cause
Break-glass accounts rot because nobody owns them and nothing tests them.
Fix
Create two, vault the credentials offline, exclude from lockout and conditional-access restrictions, and log a test sign-in each quarter.
Prevention
Put break-glass verification in the quarterly access review with a named owner and a deadline.

6 · Correlation windows too short or too long

Symptom
Bursts split across two alert windows go unnoticed, or one alert aggregates a whole day into useless noise.
Root cause
Window copied from an example; never validated against real burst shapes.
Fix
Start at 10 minutes for removal bursts and 15 for host account operations (as in section 5.5), then tune with your own incident replays.
Prevention
Replay each real incident's timeline against current rules as part of the post-incident review.

7 · ESXi and Linux identity events unmonitored

Symptom
Nobody can answer "who deleted accounts on the hypervisors?" — those hosts do not forward logs.
Root cause
Hypervisors and infrastructure Linux sit outside the endpoint agent world and were never added to log forwarding.
Fix
Forward auth.log and shell.log via syslog into the SIEM; deploy the TH-05 keyword rule.
Prevention
Add "identity log source" to the host build checklist so every new host is monitored from its first day.

8 · Static thresholds that cause alert fatigue

Symptom
The burst alert fires daily for benign reasons; analysts mute it; one day it fires for real.
Root cause
One threshold for all subjects: service-desk bulk tools and human admins share the same rule.
Fix
Split rules by actor type; allowlist the provisioning service account; raise thresholds only with a recorded justification.
Prevention
Track each rule's true-positive rate monthly and retire or retune rules that never fire true.

9 · Identity alerts with no owner

Symptom
The burst alert pings a channel nobody reads; escalation paths were never written.
Root cause
Rules were deployed by a project, then the project ended and ownership dissolved.
Fix
Assign each rule an owner, an on-call path, and a documented escalation for critical severity.
Prevention
Quarterly rule-ownership review as a standing item in the detection engineering meeting.

10 · Recovery runbook never tested

Symptom
The restore that was "documented" takes twice as long as planned; steps reference a console menu that no longer exists.
Root cause
The runbook was written once for an audit and never exercised.
Fix
Run a live two-account restore drill from the IdP config export; update the runbook from what actually happens.
Prevention
Quarterly restore drill on the calendar with a named owner; track restore time as a metric.

11 · Help desk trusts a voice on the phone

Symptom
An MFA reset for "the CFO" is performed after a friendly call; the attacker registers their own device.
Root cause
Verification by plausibility (name, department, annoyance) instead of proof.
Fix
Mandate callback to the number on file for every reset; require a second approver for privileged accounts.
Prevention
Drill the desk with a live social-engineering test twice a year and track the failure rate.

12 · MFA-factor removal not monitored

Symptom
"User deleted security info" events pile up unreviewed; the attacker's first cloud step is invisible.
Root cause
Security-info events are classified as self-service noise, so no rule exists.
Fix
Alert on security-info deletion for admin-role accounts and on bursts for normal users; correlate with help-desk tickets.
Prevention
Add MFA lifecycle events to the identity source-coverage matrix so coverage is explicit, not assumed.

13 · Log retention shorter than the investigation

Symptom
The team wants to review the week before the attack and the SIEM answers "no data"; scope shrinks to what is still stored.
Root cause
Identity sources were added with default retention (often 7–30 days) and nobody raised it.
Fix
Set at least 90 days hot retention for identity sources and archive older data cheaply; export incident windows offline during every incident.
Prevention
Put retention per source into the source-coverage matrix and review it in the same monthly pass as ingestion status.

Habits that keep the defense healthy

Daily

  • Review the identity alert queue; confirm every 4725/4726 burst got a ticket check.
  • Verify the IdP log feeds are alive (heartbeat check), not just present.
  • Spot-check new admin-role activations if PIM is in place.

Weekly

  • Review account-change rate trends versus baseline; investigate drift.
  • Sample five deprovisioning events and match each to an approval.
  • Test that critical identity alerts route to a human, end to end.

Monthly

  • Restore two accounts from the IdP configuration export and time it.
  • Review rule true-positive rates; retune or retire what never fires true.
  • Confirm ESXi/Linux hosts still forward auth and shell logs.

Response checklist

  • Scope: export the full target list from 4725 / 4726 / 4724 and IdP audit events.
  • Identify the subject account behind the changes; assume its credentials are stolen.
  • Check IdP audit for admin operations, MFA removals, and role changes in the same window.
  • Activate the break-glass account from the vault before touching anything else.
  • Disable attacker sessions: revoke refresh tokens, block source IPs, remove rogue MFA registrations.
  • Restore accounts and MFA from the trusted identity configuration backup or runbook.
  • Hunt persistence: new admin accounts (T1136), new OAuth grants, inbox rules.
  • Preserve evidence: export the full event trail before cleanup overwrites it.
  • Notify leadership and, if required, the regulator within the reporting deadline.
  • Schedule the post-incident review and replay the timeline against current detection rules.

Quick questions

Is one 4726 event an incident?
No. One deletion with a matching ticket is normal work. Look for the burst: several removals, one subject, a short window.
We are fully in the cloud. Do Windows events matter to us?
Less — but sync tools often bridge both worlds. Watch the IdP audit log with the TH-02 and TH-06 rules, and keep one documented on-prem admin path.
Should we just block net.exe?
Rarely. It breaks daily IT work, and a blocker just pushes the attacker to PowerShell. Detect the burst and the odd parent process instead.
How often should thresholds change?
Review quarterly against your own event data. Raise a threshold only with a written reason, and always keep a stricter rule for admin-class targets.
Where do I start with one hour a week?
Stream the IdP audit log into the SIEM, deploy the TH-02 rule, and write the callback policy. Those three cut the most risk per hour spent.
Do we need EDR on domain controllers?
It helps — it shows the tool and the parent process behind each change — but the Security log alone already carries every 4724/4725/4726/4740 event. Ship the log first, then add the agent.
What is the single best early signal?
A disable burst (4725 or IdP "Disable account") aimed at security-team accounts. It is quieter than deletion, so attackers prefer it — and it means they expect you.
