T1491 Defacement

Defacement is an attack that changes the visible content of a website or an internal application. Attackers swap pages, templates, or database content for their own messages. This page explains how the attack works, how it looks from both the attacker and defender side, and how to detect it with logs, Sigma rules, and Splunk searches.

Overview

What defacement is, how the two sub-techniques differ, and why this loud attack is still a valuable detection target.

Defacement is an attack that changes the visible content of an application. The attacker does not break the software itself. Instead, the attacker changes what people see: page text, images, templates, or database rows that feed a page. MITRE ATT&CK places T1491 in the Impact tactic, because the goal is to change or damage what the victim delivers to its users. T1491 is the parent technique. Its two sub-techniques split by audience: T1491.001 Internal Defacement for pages visible only inside the network, and T1491.002 External Defacement for public websites.

The term CMS means Content Management System, a tool such as WordPress, Drupal, or vBulletin that lets people publish web content without writing code. Many defacements happen through a CMS, because a CMS stores content in files or in a database and renders it for every visitor. If an attacker can change that stored content, every visitor sees the change.

Defacement is often seen as a "loud" attack. It does not hide. That makes it look less dangerous than quiet data theft, but it is still a serious signal: an attacker had enough access to write content. The same access is often enough to plant a web shell (a hidden page that gives the attacker remote commands) or to steal data. Treat every defacement as proof of a breach, not just as graffiti.

T1491.001 - Internal Defacement

Internal targets Often ransomware-adjacent

The attacker changes pages that users see inside the victim network. Examples: a staff intranet portal, a desktop wallpaper changed across workstations, an internal wiki home page, or a login page of an internal tool. This variant often appears during destructive attacks, where malware also wipes data or changes system images.

Detection leans on file integrity monitoring on internal web roots and shares, EDR on workstations, and network shares audit logs.

T1491.002 - External Defacement

Public websites Most common variant

The attacker changes content on a public website. Visitors see an attacker banner, a political message, or "hacked by" text. The change may be a file (HTML, template), a database row (article or product text), a third-party script the site loads, or even the DNS record that points the domain somewhere else.

Detection leans on web access logs, WAF and CDN logs, file integrity monitoring of the web root, and external monitoring services.

Open the T1491.002 v2.0 page

Note

Defacement is the visible tip. After you confirm it, always hunt for deeper activity on the same host: new admin users, web shells, odd scheduled jobs, and large database reads.

Written story (text alternative)

The list below is the same story in text form. Screen readers and printed copies use this instead of the canvas.

  1. Recon. The attacker scans the public site and finds an outdated CMS with a vulnerable plugin. Defenders see: nothing yet. Scanning blends into normal internet noise, so there is no alert at this point.
  2. Probe. Crafted SQL injection requests hit the plugin. The WAF (web application firewall) sees odd encoded queries and starts counting them. Defenders see: WAF counter events that alone do not cross a threshold.
  3. Breach. The injection returns the CMS admin password hash. The attacker cracks it offline and logs in as an admin. Defenders see: a successful admin login from a new network, visible only if admin logins are logged.
  4. Stage. The attacker uploads a modified template file into the web root (the folder the website serves). Defenders see: a file integrity monitoring event about a new or changed file, often queued as low priority.
  5. Deface. The homepage HTML is replaced with the attacker's banner. Visitors see the defaced page, and the CDN (content delivery network) caches it. Defenders see: a CDN cache refresh and rising page views of the changed page.
  6. Expose. A monitoring user and the file-integrity system flag the changed web root. The SOC receives the first alert. Defenders see: a correlated alert that joins the FIM change with the CDN refresh and a user report.
  7. Triage. The SOC reviews access logs and finds the admin session and the SQL injection pattern from a new network. Defenders see: the full chain in logs - probe, login, upload - and they freeze the admin account.
  8. Recover. The team restores the homepage from a clean backup, patches the plugin, rotates credentials, and purges the CDN cache. Defenders see: a verified clean web root, a patched plugin, and repeat-attempt monitoring in place.

Red Team Perspective

How attackers think about defacement: why they do it, what they need, which paths they pick, and where they slip up.

When and why attackers deface

Defacement is one of the oldest public attacks, and attackers pick it for clear reasons. Public reporting groups the motives into a few clusters:

  • Hacktivism. The attacker wants to send a political or ideological message. The message only works if many people see it, so visibility is the goal, not secrecy.
  • Bragging rights. Some attackers collect "hacked by" screenshots like trophies. Defacement archives and social posts prove the win to their peers.
  • Protest. A group may deface a company site during a dispute, a war, or a public controversy to cause reputational harm.
  • Proving access. In extortion, the attacker changes one visible page or publishes a screenshot as evidence that the network is truly breached, before or instead of stealing data.
  • Distraction. A loud, visible change pulls defenders and managers toward the website while quieter work continues elsewhere: data theft, web shell persistence, or lateral movement. Section 5.3 tracks this as TH-07.

How it is performed: a staged pattern

Most defacements follow three stages. First, access: the attacker gains a foothold, often by exploiting a public-facing application or by using valid accounts (a real username and password, stolen or guessed). Second, persist: the attacker keeps a way back in, for example a second admin account or a web shell, because they expect the page to be restored quickly. Third, alter: the attacker changes the content, either once or on a schedule, and sometimes mirrors the change across many sites they control.

Where it applies and what it needs

Common target surfaces

  • Public web roots: the folder on the server that holds the site files.
  • CMS admin panels and their template or theme editors.
  • Templates and plugins that render pages for all visitors.
  • Database content tables (articles, product pages, menu items).
  • DNS records at the domain registrar.
  • Internal portals, wikis, and login pages inside the network.

Typical prerequisites

  • Write access to web content: a file upload path, an editor role, or shell access.
  • CMS or admin credentials, often reused from another breach or left at default values.
  • An unpatched public application, plugin, or server module.
  • For DNS defacement: access to the registrar account or a weak domain lock setting.
  • For internal defacement: a foothold on an internal host or an insider role.

Common variations

There are four main ways to change what visitors see. File change writes new HTML or template files to the web root. Database-driven change updates the rows that feed the page, which survives template restores and can be harder to notice. Third-party script injection changes a script that the site loads from a vendor, so every site using that script shows attacker content; this is the supply chain variant. DNS takeover points the whole domain at attacker infrastructure, so the real server is never touched at all.

Where attackers slip up

  • They leave shells, tools, and new accounts behind, which turns a content change into a full-compromise investigation.
  • They touch many files at once, which multiplies the file integrity events and makes the change stand out from normal publishing.
  • They forget caches: search engines, CDNs, and web archives keep copies of the defaced page, which preserves the evidence and the timestamps.
  • They reuse infrastructure (usernames, ASNs, hosting providers) across campaigns, which links incidents together.
  • They log in through the normal admin panel, so the access is fully recorded in audit logs if those logs exist.

Blue Team Perspective

How the SOC actually learns about a defacement, which artifacts the attacker leaves, and a triage flow that keeps the incident under control.

How defenders find out

In real incidents, defacement is discovered in four common ways. A user report arrives first surprisingly often: a customer or employee says "the site looks hijacked". File integrity monitoring (software that checks whether protected files changed) flags the web root. WAF and CDN alerts show odd traffic or a sudden cache refresh. And third-party trackers - public defacement archives, zone listings, or brand-monitoring feeds - may tell the victim before their own tools do. That last path is the painful one: it means an outsider knew first.

Artifacts the attacker leaves behind

On the server

  • Modified files with odd modification times (for example 03:41 on Sunday) and a mismatched owner.
  • New files in the web root that no deployment created: backup copies of templates, uploader pages, web shell remnants.
  • Changed database rows with an updated_by or audit value pointing to an unusual session.
  • New admin sessions in CMS audit logs, often right before the content change.

Around the server

  • Web access log lines showing the exploit request, the admin login, and the upload POST.
  • WAF events with encoded payloads that were counted but not blocked.
  • CDN logs showing a purge and refill of the defaced URL.
  • DNS query logs, if the domain itself was redirected, showing the new answer IP.
Warning

If WAF or web access logs were rotated away before triage, you lose the entry point evidence. Keep at least 90 days of web, WAF, and CMS audit logs in cold storage so an incident can be reconstructed.

Where to look, in order

  1. Web access logs (nginx, Apache, IIS): find the exploit request, the admin login, and the upload.
  2. CMS audit logs: which account changed which content, from which address.
  3. File integrity monitoring (AIDE, OSSEC, Wazuh): the exact file list and timestamps of the change.
  4. Database audit: which rows changed and through which SQL session.
  5. WAF and CDN logs: what was blocked, what passed, and what got cached.
  6. DNS and registrar logs: whether the domain itself was moved.

Why it matters

Defacement hurts in four ways at once. It is a breach indicator: someone had write access. It can accompany data theft, since the same exploit often dumps data before or after the visible change. It creates regulatory exposure, because it is hard to argue that a defaced public site was no incident. And it damages trust: customers who saw the banner, or a screenshot of it, now question every part of the service.

Where it fits the attack chain

Defacement rarely stands alone. It usually follows T1190 Exploit Public-Facing Application or T1078 Valid Accounts. While triaging, actively check for the neighbors: T1505.003 Web Shell (persistence on the same host), T1565 Data Manipulation (more changed content or records), and T1567 Exfiltration Over Web Service (data leaving through allowed channels). A defacement ticket that closes without these checks is a missed breach investigation.

Detection Engineering Deep Dive

The longest section: regulations, threat intelligence, a ranked threat model, the logs that matter, and ready-to-adapt Sigma and Splunk detections for each threat.

This section is written for detection engineers. It moves from "what the law and frameworks expect" down to "the exact rule you can paste into your SIEM". The seven threats defined in 5.3 are carried through 5.4 and 5.5, so the mapping from threat to log source to rule stays traceable.

5.1 Regulation mapping

Defacement rarely maps to one neat control, because it is both a security failure and often a reportable incident. The table below shows the frameworks that most commonly apply, why each one cares, and the evidence an auditor expects to see.

Regulation and framework controls that relate to defacement prevention, detection, and response
FrameworkControlWhy it appliesExpected evidence
GDPRArt. 32 - Security of processing A defaced public site shows that processing systems lacked appropriate technical safeguards. Hardening records for the CMS, patch history, WAF configuration, risk assessment for public web services.
GDPRArt. 33 - Breach notification (72 h) If personal data was also taken, the 72-hour clock starts at awareness. A defacement with no personal data breach may not trigger Art. 33 at all. Incident tickets with detection time, decision log, and any regulator notification with timestamps.
GDPRArt. 5(1)(f) - Integrity and confidentiality Changed content proves the integrity principle was not upheld for the affected service. Integrity controls on web content, change records, restore and verification evidence.
ISO/IEC 27001:2022A.8.15 - Logging You cannot reconstruct a defacement without web, CMS, and database logs. Log inventory showing web, WAF, CMS audit, and DB audit sources with retention times.
ISO/IEC 27001:2022A.8.16 - Monitoring activities Defacement detection is exactly "monitor for anomalous behavior on public services". Alert rules for web root changes, admin logins, and WAF thresholds; SOC triage records.
ISO/IEC 27001:2022A.8.13 - Information backup Fast recovery from defacement depends on verified backups of content and databases. Backup job records, restore test results, backup immutability settings.
SOC 2CC7.2 - CC7.5 Trust Services criteria require monitoring for anomalies and a working incident response process. Detection rule documentation, alert-to-response timelines, post-incident reviews.
SOC 2CC8.1 - Change management Unauthorized content change is the exact failure mode change management exists to prevent. Publishing workflow records, approval trails, unauthorized-change incident reports.
PCI DSS v4.06.4.3 - Payment page script integrity Every script that a payment page loads must be written down, authorized, and checked for integrity. Script inventory with owners, written authorization, and hash or SRI checks for third-party scripts.
PCI DSS v4.011.5.2 - Detect unauthorized modification of payment-page scripts If the site takes payments, script changes are a card-skimming risk, not just vandalism. Script integrity checks (hashes of loaded JavaScript), change alerts, response evidence.
PCI DSS v4.010.2 / 12.10 - Audit logging and incident response Cardholder-data environments must log access and rehearse incident response. Access logs with user attribution, IR plan, test records for web compromise scenarios.
HIPAA Security Rule164.308(a)(6) - Security incident procedures A defaced patient portal is a security incident requiring identifiable response steps. Written procedures, incident reports, evidence of detection and containment times.
HIPAA Security Rule164.312(b) - Audit controls Systems handling ePHI must record and examine activity, including content changes. Enabled audit logging on web and portal systems, periodic log review records.
NIST CSF 2.0DE.CM (Continuous monitoring) / RS.MI (Mitigation) DE.CM covers watching public services for defacement; RS.MI covers containing and restoring. Monitoring scope documents, containment playbooks, restore procedures with owners.

Two lessons stand out from the table. First, almost every framework expects evidence, not intention: logs, timestamps, approvals, and restore tests. Second, the 72-hour GDPR clock makes detection latency a compliance metric. A defacement found by a customer two days later is very different from one caught by your own FIM alert in minutes.

5.2 Threat intelligence

Threat intelligence for defacement answers three questions: who defaces sites like ours, what do their campaigns look like, and how would we know early? Build it from several sources and apply it in a simple loop.

Public and community sources

  • MITRE ATT&CK site and its STIX/TAXII feeds for technique and group data.
  • ISACs (Information Sharing and Analysis Centers) for sector-specific warnings.
  • Vendor blogs from security companies tracking hacktivist waves.
  • OSINT: public defacement archives and news reports of campaigns.

Commercial feeds

  • Brand and domain monitoring services that watch for hijacks and look-alike sites.
  • Digital risk protection platforms that alert when your brand appears on attacker channels.
  • Curated indicator feeds with actor attribution and confidence scores.

Internal telemetry

  • Your own web, WAF, CMS, and DNS logs - the highest-value source you own.
  • Past incident tickets, which show which attack paths actually hit you.
  • External scan results showing what an attacker sees first.

The collect - analyze - apply loop

  1. Collect. Pull technique updates (T1491 and its neighbors), actor names, and campaign indicators into one place, on a schedule.
  2. Analyze. Ask: does this apply to our stack? A vBulletin plugin story matters only if you run vBulletin; a domain-hijack wave matters if your registrar security is weak.
  3. Apply. Turn findings into detection content (rules in 5.5), hardening tasks (section 7), and hunt hypotheses for the SOC.

Best practice

Watch ATT&CK version updates and vendor reporting on a fixed cadence - for example monthly. When ATT&CK renames or regroups a cluster such as Ghostwriter, update your own notes and rules so your intelligence stays aligned with the framework.

5.3 Threats ranking and categorization

The seven threats below are the defacement paths that matter for most organizations. They are ranked by a mix of frequency and impact. The same IDs (TH-01 to TH-07) are used in 5.4 for log sources and in 5.5 for detection rules, so every rule traces back to one threat.

TH-01 - Exploit of a public web application Critical

Network External defacement

Description
SQL injection or remote code execution in a CMS or plugin on a public site leads directly to external defacement.
Preconditions
An unpatched public application, a reachable admin endpoint, and writable web content.
Impact
Public defacement, possible simultaneous data theft, and a visible breach of customer trust.
Rank justification
The highest-frequency real-world path - most defacements in public reporting start here.

TH-02 - Compromised CMS or admin credentials High

Identity External defacement

Description
Phishing, password reuse, or a default account hands the attacker a real CMS admin session, which is then used to alter published content.
Preconditions
Weak or reused credentials, no MFA on the admin panel, and admin sessions that are not monitored.
Impact
Defacement through the front door; the attacker may also read private content with the same rights.
Rank justification
Very common in practice, but usually caught by credential controls if they exist, so slightly below TH-01.

TH-03 - Compromised third-party script (supply chain) High

Network Rendered-page change

Description
A malicious or compromised vendor script changes the rendered page for all visitors, without any change on your own servers.
Preconditions
The site loads third-party JavaScript, and script integrity is not verified (no hashes, no strict CSP).
Impact
High blast radius: every visitor of every site using that script is affected at once.
Rank justification
Rare compared to TH-01, but a single event affects far more users, so it stays High.

TH-04 - DNS or registrar hijack Medium

Network Domain-level

Description
The attacker takes over the registrar account or poisons DNS records, so the whole domain resolves to attacker content.
Preconditions
Weak registrar security, no registrar lock, or a compromised account with DNS rights.
Impact
Strong impact on availability and trust; mail and other services on the domain can break too.
Rank justification
Lower frequency, but the impact reaches beyond the website, so it ranks Medium with high attention.

TH-05 - Insider misuses publishing rights Medium

Identity Internal or external

Description
An employee or contractor with publishing rights alters content for personal, ideological, or fraudulent reasons.
Preconditions
Broad publishing rights, no approval workflow, no review of unusual edit patterns.
Impact
Smaller blast radius, but the insider bypasses most outer controls and knows what hurts.
Rank justification
Low frequency and contained blast radius keep it Medium, but it defeats many perimeter assumptions.

TH-06 - Subdomain takeover serving fake content High

Network External content

Description
A forgotten DNS record still points a subdomain at a retired cloud service. The attacker claims that empty slot on the service and serves fake pages on your subdomain.
Preconditions
A dangling subdomain record, no watch on DNS answers, and no claim check on the cloud service.
Impact
Fake login pages or fake content on a trusted domain name, with no change on your own servers.
Rank justification
High - it needs one mistake (a dangling record), but public scanners hunt for it constantly, and the fake content is very convincing.

TH-07 - Defacement as distraction during a deeper intrusion High

Cross-platform Internal or external

Description
The attacker uses a loud defacement to pull all attention to one website while quieter work continues elsewhere: data theft, web shells, or lateral movement.
Preconditions
Two goals at once - a visible message, and time to work undisturbed on other systems.
Impact
The response team spends its best hours on the visible page while deeper damage grows on other hosts.
Rank justification
High - lower frequency, but very high cost, because it attacks the response process itself, not just a site.
Note

Rankings are context-dependent. A news publisher under political pressure may rank TH-04 above TH-01; a payments site may treat TH-03 as Critical because of card-skimming risk. Re-rank for your own environment.

5.4 Logs and patterns

Each threat below lists the log sources that will actually contain the evidence, the key fields, what normal looks like, what suspicious looks like, and the detection logic in one to three sentences. After the seven blocks, four realistic log examples show the raw shape of the events.

TH-01 - Exploit of a public web application

Log sources
Web access logs (nginx, Apache, IIS), WAF logs, CDN logs, file integrity monitoring, process creation on the web host.
Key fields
clientip, uri_path, uri_query, status, useragent, file_path, file_hash, process_name
Normal behavior
Steady traffic with typical user agents, 200 and 404 responses, deploy-time file changes from CI pipelines.
Suspicious behavior
Encoded SQL keywords in query strings, tool user agents (sqlmap, nikto), bursts of 500 errors from one client, then a POST to an upload endpoint, then web-root file changes from a non-deploy process.
Detection logic
Match SQL injection syntax in URLs and flag the same client if it later succeeds on an upload or admin route. Correlate WAF "counted" events with web-root file changes within an hour.

TH-02 - Compromised CMS or admin credentials

Log sources
CMS audit logs, web access logs for the login route, VPN or SSO logs, file integrity monitoring.
Key fields
user, role, source_ip, source_asn, session_id, action, object
Normal behavior
Admin logins from known office or VPN ranges during work hours; content edits by editor roles in a steady pattern.
Suspicious behavior
Admin login from a new ASN or country, password spray before it, then template or theme edits and file uploads within minutes of login.
Detection logic
Alert on high-risk CMS actions (template edit, plugin install, user create) when the session's network differs from the user's history. Chain login to content change by session_id.

TH-03 - Compromised third-party script

Log sources
Proxy or CDN logs for script fetches, browser monitoring (CSP violation reports, script hash checks), vendor status feeds, synthetic browser checks.
Key fields
url_path, cs_host, response_bytes, content_hash, cache_status
Normal behavior
Third-party scripts fetched with stable sizes and stable hashes between vendor releases.
Suspicious behavior
A script's size or hash changes outside a release window; a new script host appears; CSP reports show blocked inline scripts on payment pages.
Detection logic
Compare observed script hashes and sizes against a baseline table. Any drift outside a change window is an alert, since your own servers never changed.

TH-04 - DNS or registrar hijack

Log sources
Internal DNS query logs, external DNS monitoring, passive DNS feeds, registrar account audit logs, certificate transparency feeds.
Key fields
query, answer, ttl, nameserver, registrar_user, record_type
Normal behavior
Your domain resolves to your known address ranges and nameservers; registrar changes happen through named administrators.
Suspicious behavior
The domain resolves to an unknown address range, nameservers change, a new record appears with a long TTL, or the registrar logs an unexpected transfer request.
Detection logic
Alert when your own domains resolve outside approved address ranges, or when registrar audit events occur without a matching change ticket.

TH-05 - Insider misuses publishing rights

Log sources
CMS audit logs, publishing workflow logs, database audit, DLP alerts on content export.
Key fields
user, action, object, objects_changed, source_ip, timestamp
Normal behavior
Editors change a handful of pages per day inside working hours through the approval workflow.
Suspicious behavior
Bulk edits or publishes (dozens of pages in minutes), edits outside the approval workflow, changes to high-visibility pages by rarely active accounts.
Detection logic
Count content-changing actions per user per short window and alert above a baseline threshold. Flag publishes that skip the approval state.

TH-06 - Subdomain takeover serving fake content

Log sources
DNS record monitoring, passive DNS feeds, certificate transparency logs, external synthetic checks of every subdomain, registrar change logs.
Key fields
query, record_type, cname_target, answer, http_status, response_body
Normal behavior
Every subdomain resolves to a record you can match to a live service, and each service answers with your content or a redirect you control.
Suspicious behavior
A CNAME to a service you no longer use, a new certificate issued for a subdomain nobody uses, or synthetic checks showing vendor error pages such as a hosting service "site not found" message.
Detection logic
Alert when a CNAME target is unclaimed on the service, and when your own subdomains return vendor error fingerprints in HTTP responses.

TH-07 - Defacement as distraction during a deeper intrusion

Log sources
EDR on servers and admin workstations, authentication logs across the estate, proxy and DLP egress logs, web shell and persistence detections.
Key fields
user, host, process_name, destination_ip, bytes_out, event_time
Normal behavior
Steady background egress, logins from expected hosts, and few new services or admin sessions.
Suspicious behavior
During the defacement incident window, other hosts show new admin logins, unusual database reads, or upload bursts to external addresses.
Detection logic
When a defacement alert opens, pivot the same 24 to 48 hour window across authentication and egress logs. Alert on any second, unrelated host doing admin actions or large transfers in that window.

Four log examples with field explanations

  • 203.0.113.7 - client address (documentation range used here for the example).
  • [22/Oct/2026:09:14:07 +0000] - request time; a burst of similar lines within seconds is the tool signature.
  • option=com_example&view=1' OR '1'='1 - the injected SQL in the query string; quotes and OR 1=1 are classic markers.
  • 500 then 200 - the first probe crashed the query, the second succeeded; a successful response after errors is the moment to correlate.
  • sqlmap/1.7 - the user agent openly names a SQL injection tool; tools can spoof it, so also match the payload patterns.
  • EventID 11 - Sysmon file-create event; file writes to protected paths are its main value here.
  • Image - the process that wrote the file. A web server worker (w3wp, httpd, php-fpm) writing template files is normal; a child process from Temp doing it is not.
  • TargetFilename - inside the web root; match this path against your deploy process allowlist.
  • TimeCreated - compare with CMS audit log times to link the upload request to the file change.
  • action=template.update - a content-changing action; these are the events that feed the TH-02 and TH-05 rules.
  • user=admin1 with source_asn=64512 - the admin's sessions normally come from office or VPN networks; a new ASN is the anomaly.
  • session=8f3ac1d2e4b5 - the shared session ID links the CMS action and the SQL statement into one chain.
  • rows=1 - a single-row template update is quiet; bulk updates (rows in the hundreds) shift suspicion toward TH-05.
  • added: - AIDE (a file integrity tool) reports the file is new; the baseline did not contain it.
  • uid=33 gid=33 - the web server user owns the file, so the write happened through the web application, not through a deploy pipeline.
  • added_sha256 - the hash lets you compare the file against the clean backup and against malware repositories.
  • mtime - pairs with the Sysmon 11 event and the CMS audit entry to build one timeline.

5.5 Sigma rules and Splunk SPL

Below are six complete Sigma rules and six matching Splunk SPL queries. Rules TH-01 to TH-05 map one to one to the first five threats, and rule TH-06 covers subdomain takeover. TH-07 is a response-discipline threat; the triage flow in section 4 and the pivot logic in 5.4 cover it. The Sigma rules are written in valid YAML with spaces only and can be converted with any Sigma tooling. The SPL queries use realistic sourcetypes; adjust index names and field names to your deployment. Every query carries a "Field assumptions" note so you know exactly what must be true for it to run.

TH-01 - SQL injection probes against the public web application

Intent: catch the probe phase before the defacement happens. This rule watches for SQL injection syntax and known tool user agents in web requests.

Sigma to SPL field mapping: c-ip -> clientip, cs-uri-query -> uri_query, cs-uri-stem -> uri_path, sc-status -> status, User-Agent -> useragent (standard Splunk access_combined extractions).

Field assumptions: events live in index=web with sourcetype=access_combined, so clientip, uri_path, uri_query, status, and useragent are already extracted; the threshold 5 filters single-request noise.

  • False positives: your own approved scanners and any URL that legitimately contains SQL-like words.
  • Tuning: add a filter selection excluding scanner source IPs from your test provider; keep the count threshold low - probes precede the actual attack by minutes to days.
  • Severity: critical - this is the entry stage of the highest-frequency defacement path (TH-01).

TH-02 - High-risk CMS action from an unusual network

Intent: catch a stolen admin session by the one thing it cannot fake easily - the network it comes from. This rule alerts when an administrator performs a content-changing CMS action from an untrusted ASN.

Sigma to SPL field mapping: action, role, source_asn, session_id, user, and object keep the same names in the CMS audit sourcetype; event_time maps to Splunk's _time.

Field assumptions: CMS audit events land in index=cms with sourcetype=cms:audit and fields user, role, action, object, source_ip, source_asn, and session_id; ASNs 64500 and 64510 stand in for your trusted office and VPN networks - replace them with your own.

  • False positives: admins on new VPN ranges, new office networks, or publishing automation running in a hosting network.
  • Tuning: maintain the trusted ASN list in a lookup table instead of the rule text; add a time window (for example actions within 15 minutes of a login from the same new ASN) to raise precision.
  • Severity: high - matches the TH-02 rank; content-changing admin actions from an unknown network rarely end well.

TH-03 - Third-party script size drift

Intent: notice when a vendor script your site loads changes shape. Your servers did not change, so any drift in size or hash of a known script is suspect.

Sigma to SPL field mapping: cs-host -> cs_host, cs-uri-path -> cs_uri_path, sc-bytes -> sc_bytes, sc-status -> sc_status, c-ip -> src_ip (common proxy sourcetype extractions).

Field assumptions: proxy or CDN fetch logs in index=web with sourcetype=stream:http providing cs_host, cs_uri_path, sc_bytes; a lookup file thirdparty_js_baseline.csv holds one row per script with its baseline size (48213 for analytics.min.js, 11204 for widget.js) - update it after every planned vendor release.

  • False positives: vendor releases without notice and compression differences between edge nodes.
  • Tuning: prefer content hashes over byte counts when your logging captures them; keep a release calendar so tuning is a one-line update, not an alert-by-alert debate.
  • Severity: high - matches TH-03; the blast radius covers every visitor of every site using the script.

TH-04 - Corporate domain resolving outside approved ranges

Intent: catch a DNS or registrar hijack at resolution time. If your own domain starts answering with unknown addresses, everything downstream is untrusted.

Sigma to SPL field mapping: query -> query, record_type -> record_type, answer -> answer, ttl -> ttl, client_ip -> src (adjust to your DNS sourcetype field names).

Field assumptions: DNS query logs in index=dns with sourcetype=infra:dns providing query, record_type, answer, ttl, and src; the approved ranges 203.0.113.0/24 and 198.51.100.0/24 stand in for your real hosting ranges - replace them before use.

  • False positives: new hosting ranges, CDN edge nodes, and cloud providers with wide address pools.
  • Tuning: keep the approved list in a lookup keyed by domain; alert only on answers seen more than once to cut resolver-cache noise; pair with registrar audit log alerts.
  • Severity: medium - matches TH-04; rare, but when it fires the response clock is already running.

TH-05 - Bulk content changes by a single publisher

Intent: catch an insider who changes far more content than any normal workflow produces, or who publishes while skipping the approval step.

Sigma to SPL field mapping: user, action, object, objects_changed, and workflow_state keep their names in cms:audit; event_time maps to _time. In SPL the volume condition is computed with stats dc(object) instead of a stored field.

Field assumptions: CMS audit events in index=cms with sourcetype=cms:audit providing user, action, object, workflow_state, and source_ip; the value direct marks a publish that skipped approval - adapt to your workflow engine's state names.

  • False positives: planned mass updates (rebrands, migrations) and integration accounts doing bulk imports.
  • Tuning: baseline objects_changed per user role, not globally; allowlist scheduled migration jobs; require two signals (volume plus skipped approval) during a change freeze.
  • Severity: medium - matches TH-05; lower frequency and smaller blast radius, but it bypasses outer controls.

TH-06 - Subdomain serving a takeover error fingerprint

Intent: catch a claimed subdomain at the moment it serves attacker content. When your own subdomain answers with a hosting service error page, the DNS record was dangling and someone claimed it.

Sigma to SPL field mapping: host, url, and http_status keep their names in the synthetic monitor sourcetype; response_body carries the first bytes of the HTTP answer; event_time maps to Splunk's _time.

Field assumptions: results from scheduled external checks land in index=web with sourcetype=synthetic:http, providing host, url, http_status, and the first bytes of the answer in response_body. Replace example-corp.com with your own domain. Run one synthetic check per subdomain on a short interval.

  • False positives: a planned service retirement where the record removal is still pending.
  • Tuning: keep the fingerprint list in a lookup table and add the fingerprints of the services you actually use; pair the rule with a DNS monitor that flags CNAME targets outside your live-service list.
  • Severity: high - matches TH-06; fake content on a real subdomain is convincing enough for phishing, and your servers were never touched.

Detection maturity for T1491

  • Basic: centralized web logs plus the TH-01 SQL injection rule. Catches most opportunistic attacks.
  • Intermediate: add file integrity monitoring with a tuned scope, CMS audit logging, and the TH-02 and TH-05 rules.
  • Advanced: correlate FIM, WAF, CMS, and CDN signals automatically; add TH-03 script baselines, TH-04 DNS monitoring, and TH-06 subdomain checks; measure detection latency as a metric.
  • Optimized: rules tuned per site with lookup-driven allowlists, automated restore verification, threat intel that updates the rules on a cadence, and a TH-07 drill: when a loud impact event opens, check the whole estate for quiet work in the same window.

Real-World Case Study

The Ubuntu Forums breach of July 2013: SQL injection, a large data dump, and defaced pages - found late, fixed publicly.

Sourcing: items marked "public record" come from Canonical statements and security press from July 2013. Items marked "illustrative" are a realistic reconstruction for teaching; public reporting does not document them.

Context

Public record. The Ubuntu Forums, run by Canonical, was the community heart of the Ubuntu Linux distribution: millions of posts and a very large registered user base. The forum software was vBulletin with third-party add-ons on top. In July 2013, attackers used SQL injection (a trick that sends database commands through a web input) in one of those add-ons, changed forum content so visitors saw attacker material, and pulled the user database. About 1.8 million user records were exposed: usernames, email addresses, and hashed passwords (not plaintext); several press reports also list IP addresses. During the defacement, the site redirected visitors to a page on the forum's own domain, which security press identified as signaturepics/Sput.html. The stolen dump was later published, and Canonical forced password resets across the community.

The case is a textbook T1491 event with a twist: the defacement was the visible part of a data breach. Anyone who treated it as "just vandalism" would have missed the real damage - the user database was already gone.

Timeline

Dates follow the public reporting; some exact hours are approximated where sources differ. The weekend defacement reports, the data volume, and the password resets are public record. The attacker's working steps before the event are illustrative.

  1. Before July 2013 (public record context) The forums run vBulletin with third-party add-ons. Canonical later confirmed that the entry point was an SQL injection flaw in a third-party add-on. The exact add-on was never named publicly. (illustrative) No file integrity monitoring watches the web root, and no automated alert watches admin sessions.
  2. Early July 2013 (illustrative) Attackers find and test the injection point in the add-on, learning how to query the underlying database.
  3. Saturday, 20 July 2013 (public record) Visitors report defaced pages; the site redirected to attacker content. Security press reported that the forums went offline the same day after Canonical received reports of the defacement, and one news outlet reported the shutdown took only minutes.
  4. 20-21 July 2013 (public record) Canonical confirms that the attackers pulled usernames, email addresses, and password hashes from the forum database. Press coverage puts the number at about 1.8 to 1.82 million records. The passwords were hashed, not stored in plaintext.
  5. 21-22 July 2013 (public record) The stolen dump circulates, and Canonical forces password resets for all forum users and warns anyone who reused the password on other services. The forum stays offline while the team investigates.
  6. Late July 2013 (public record, with illustrative detail) The forums return after a rebuild. The vulnerable add-on path is closed and the deployment is hardened; the exact hardening steps are illustrative.

Attack chain mapped to ATT&CK

Detection point - the key lesson

According to public reporting, the intrusion surfaced through user reports and manual review, not through an automated alert. That is the lesson: with database audit, web access log monitoring, or file integrity monitoring in place, the story would have been different. A simple rule would have caught the event days earlier, before the dump was publicized. Examples: "alert on SELECT queries against the users table from the web application account" or "alert on web-root file changes outside deploy windows".

Tools involved

Illustrative. Public reporting does not name the attacker's tools, so treat this list as representative. It likely included generic SQL injection tooling or hand-made requests against the vulnerable add-on, plus database queries to extract the user table. The defacement itself was a simple HTML page served from the forum's own file path. Public record. On the defender side, the response used the forum's own account tooling for the forced password reset, and a manual review of the site while it was offline.

Response and recovery

  • Containment. The forums were taken offline completely, cutting off further exploitation and further changes while the team investigated. Press reporting at the time said this happened the same day the defacement was reported.
  • Communication. Canonical published statements explaining the breach, the data involved, and the password reset requirement - a strong example of open incident communication.
  • Eradication. The vulnerable add-on path was closed, the web root was reviewed and cleaned, and administrative credentials were rotated.
  • Recovery. The platform was rebuilt and brought back with a forced password reset for all users, so stolen hashes could not be replayed against the new system.

Response team roles

Illustrative. Canonical's statements do not list who did what, so the roles below show a typical setup for an incident of this size:

  • Incident lead: owns the timeline, decides when the site goes offline, and coordinates every team.
  • Platform engineers: rebuild the forum servers, restore clean content, and close the vulnerable add-on path.
  • Database administrator: checks which tables were read and confirms what data left.
  • Security analysts: review web and application logs, confirm the injection path, and check for web shells.
  • Communications lead: writes the public statements and the password reset instructions.
  • Community and support team: answers user questions and handles reports of password reuse problems.

Impact and consequences

The direct impact was a multi-day outage of a major community resource and a full password reset cycle for 1.8 million users. The lasting impact was trust: every user had to assume their email and password pair was in attackers' hands, and every site where those users reused passwords became a target. For the security community, the incident became a standing example that community platforms and their third-party add-ons are a real attack surface.

Lessons learned

  • Input validation and parameterized queries would have removed the entry point entirely; SQL injection is a code-level failure, not a configuration accident.
  • File integrity monitoring on web roots would have flagged the content changes within minutes instead of days.
  • Faster automated detection matters: humans noticed what tools should have caught, and every day of delay widened the exposure.
  • CMS and add-on hardening (minimal add-ons, prompt patching, review before install) reduces the attack surface that monitoring must then defend.
  • Prepare the response plan before the breach: offline switches, password reset tooling, and public statement templates made Canonical's response faster than it would otherwise have been.

Mitigation and Defense

Controls grouped by area, a home-user path, and a prioritized action table that shows where each hour of work buys the most risk reduction.

Enterprise controls by area

Policy

  • Formal change management for web content: no direct production edits.
  • Publishing approvals: content goes live only after a second pair of eyes.
  • A named owner for every public site and its logs.

Identity

  • MFA on every CMS and admin panel (Privileged Account Management).
  • Least privilege: editors publish, only a few admins change templates.
  • No shared admin accounts; unique credentials, rotation on departure.

Endpoint

  • Patch the CMS, plugins, and server OS on a fixed schedule (Update Software).
  • Remove unused plugins and add-ons; each one is attack surface.
  • EDR on admin workstations that reach production web servers.

Network

  • WAF with SQL injection rules in blocking mode (Exploit Protection).
  • CDN and DDoS protection in front of public sites.
  • Segmentation: the web server reaches the database, not the whole network.
  • Restrict admin panels to VPN or allowlisted ranges.

Cloud and hosting

  • Managed hosting hardening: provider-managed patching and isolation.
  • Immutable or write-once storage for backups where the provider supports it.
  • Least-privilege cloud roles for deploy pipelines.

Logging

  • Centralize web, WAF, CDN, CMS audit, and database audit logs.
  • Keep 90+ days hot, longer in cold storage (section 4 shows why).
  • Sync clocks so timelines can be stitched together.

Monitoring

  • File integrity monitoring on every web root (AIDE, OSSEC, Wazuh).
  • Third-party defacement monitoring for your public domains.
  • Script integrity checks on payment pages (PCI DSS 11.5.2 style).

Backup

  • Verified backups of web root and database (Data Backup).
  • Keep versions going back far enough to predate the intrusion.
  • Test restores on a schedule - an untested backup is a hope, not a plan.

Response

  • A defacement playbook: who takes the site offline, who rotates what.
  • Pre-approved communication templates for customers and regulators.
  • CDN purge steps documented and tested before you need them.

Home and small-office users

If you run a small site on managed hosting, keep the CMS and its plugins updated automatically where possible. Use a strong unique password plus MFA (Multi-Factor Authentication) on the admin panel. Install only plugins you truly need. Choose a host that makes backups and restores easy. Check how your site looks once a week - most small-site defacements are found by their owners, so find them first.

Common Mistakes and Best Practices

Twelve mistakes blue teams make around defacement detection, each with the symptom, the root cause, the fix, and the habit that prevents it from returning.

1. Treating defacement as vandalism, not breach

Symptom
Ticket closed after the page was restored.
Root cause
The visible change was fixed, the access path was not investigated.
Fix
Every defacement gets a full scoping: files, rows, accounts, shells.
Prevention
Make "scope before restore" a mandatory playbook step.

2. No owner for website logs

Symptom
Nobody can answer "where are the nginx logs?" during the incident.
Root cause
The site grew organically; log ownership was never assigned.
Fix
Assign each site an owner who maintains its logging.
Prevention
Asset inventory that lists log sources per public site.

3. WAF logs rotated away too fast

Symptom
The probe evidence is gone by the time triage starts.
Root cause
Default short retention on edge logs.
Fix
Ship WAF logs to the SIEM; keep 90+ days hot.
Prevention
Retention policy covering edge, web, and CMS logs.

4. FIM deployed but nobody reads it

Symptom
The FIM event existed two days before anyone looked.
Root cause
FIM events routed to a queue nobody owns.
Fix
Route web-root FIM events to the SOC with a priority tier.
Prevention
Alert routing review after every tool change.

5. One giant FIM rule, drowning in noise

Symptom
Thousands of cache-file events; real changes are invisible.
Root cause
Monitoring the whole web root including caches and uploads.
Fix
Split scopes: strict for templates and code, tolerant for uploads.
Prevention
Quarterly review of FIM scope against the deploy process.

6. Alert fatigue from unturned rules

Symptom
The SQLi rule fires on harmless URLs all day, so it gets ignored.
Root cause
Rule shipped with default thresholds and no tuning loop.
Fix
Baseline two weeks, add exclusions, then re-enable with a threshold.
Prevention
Every rule gets a false-positive review at 30 and 90 days.

7. Only watching the homepage

Symptom
Deep pages or the API were defaced; monitors saw nothing.
Root cause
External checks cover one URL.
Fix
Hash-check a page list, or monitor the whole web root locally.
Prevention
Include high-value pages in the monitoring list review.

8. Restoring without finding the entry point

Symptom
The banner returns within days after restore.
Root cause
The exploited plugin or stolen credential stayed in place.
Fix
Block the entry point before or during restore.
Prevention
Restore checklist item: "entry point closed? yes/no".

9. Forgetting the CDN cache

Symptom
Site is clean at origin, but visitors still see the banner.
Root cause
Cache was not purged after the fix.
Fix
Purge the full CDN cache as a recovery step.
Prevention
CDN purge step in the recovery playbook with an owner.

10. No CMS audit trail at all

Symptom
Content changed, but nobody can say which account did it.
Root cause
CMS audit logging was never enabled.
Fix
Enable audit logging and ship it to the SIEM.
Prevention
Audit logging in the CMS setup baseline.

11. Admin panel open to the whole internet

Symptom
Password spray events against the login route.
Root cause
Convenience: admin reachable from anywhere.
Fix
VPN or allowlist for admin routes; MFA regardless.
Prevention
External scan checks for exposed admin endpoints.

12. Weak tuning vocabulary

Symptom
Analysts argue each alert from scratch; decisions are inconsistent.
Root cause
No documented tuning rules or severity definitions.
Fix
Write tuning guidance per rule (the 5.5 format helps).
Prevention
Detection-as-code reviews with false-positive notes required.

Habits that keep the edge

Daily

  • Review web-root FIM events and admin logins to public CMS.
  • Check that last night's backups completed and verified.
  • Skim WAF blocks for new source networks hitting admin routes.

Weekly

  • Visually inspect key public pages or run your synthetic checks.
  • Review new plugins, scripts, and domains added to public sites.
  • Check external monitoring and brand-watch feeds for your domains.

Monthly

  • Patch review: CMS core, plugins, server packages.
  • Rule health: false-positive counts and threshold tuning for 5.5 rules.
  • Restore test of one web root plus database to a clean environment.
