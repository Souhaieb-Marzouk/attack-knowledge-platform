    Overview

    A plain-language tour of Service Stop: what it is, why attackers do it, and what this guide teaches you.

    Service Stop means an attacker stops or disables services on a computer or in the cloud. A service is a background program that runs without a window: antivirus protection, a database engine, a backup agent, or a mail system. Each service does quiet work that other programs depend on. When an attacker stops the right services, the business feels it at once. Websites stop answering, backups stop running, and protection tools go silent.

    Attackers use this technique for three main goals. First, they stop security tools so nothing records their next steps. Second, they stop backup agents, database engines, and shadow copy writers. These services keep files locked open; stopping them frees the files for encryption. Third, they stop many services at once to make whole systems unusable. On the cloud side, attackers with stolen admin roles can abuse cloud APIs as well. With the AWS DisableAPIServiceAccess call, they can stop a cloud service from creating its service-linked roles on new accounts across the organization. A service-linked role is a special role that connects one cloud service to one account.

    This technique matters because it changes how an incident ends. A ransomware crew that first stops your protection and your backups leaves you with two bad choices: restore from something they did not reach, or pay. ATT&CK procedure records show this pattern across many groups. Conti stopped up to 146 Windows services covering security, backup, database, and email tools. Lazarus stopped MSExchangeIS, so Exchange mail content became unreachable. RobbinHood stopped 181 services. Prestige stopped MSSQLSERVER before encrypting. When you see services stopping in a burst, you are usually watching the final minutes before encryption.

    Where it sits in the attack chain

    Attackers reach this stage late. Stopping services needs admin rights or a serious local flaw, so they must already control the machine or the cloud account. When you see this technique, the quiet phase is over and the attacker is causing harm or preparing to cause harm.

    T1489 and T1562.001 — the overlap

    ATT&CK also lists T1562.001 Impair Defenses, which covers defeating security tools. The difference is the goal. In T1489 the attacker stops a service to break availability or to free locked files. In T1562.001 the attacker stops a security tool to stay hidden. Stopping an EDR agent fits both goals, so the same event can map to both techniques. Log it once, and let your incident process decide the label.

    Written version of the simulation

    The same story in text, for screen readers and for printing. Each step names the action, the evidence it leaves, and what the defender should notice.

    Step 1 — Shell with stolen creds

    The attacker signs in to APP01, a Windows application server, and opens a command shell. The account is an admin account stolen by an infostealer; that is malware that saves passwords and sends them to attackers. Nothing looks broken yet. Evidence: a Security event 4624 logon from a source outside the admin jump hosts. The SOC should compare every admin logon source with the known list.

    Step 2 — Map the services

    The attacker runs sc query state= all and tasklist /svc to list running services and the programs behind them. This is target selection: they pick protection, backup, and database services. Evidence: Sysmon event 1 with those command lines. The SOC should flag service enumeration run from an interactive admin session on a server.

    Step 3 — Defender stop fails

    The attacker runs net stop WinDefend. Tamper protection blocks the stop, because Windows Defender refuses commands from untrusted callers. Evidence: a Defender configuration event and the failed command in process logs. The SOC should alert on any attempt to stop security services, even when it fails.

    Step 4 — Sysmon stops

    The attacker runs net stop Sysmon64. This logging service has no tamper protection, so it stops, and System event 7036 records the stopped state. The host now sends less telemetry, and the SOC view shows a missing line. The SOC should treat a silent log source as an alert, not as a network fault.

    Step 5 — Free the locked files

    The attacker stops the SQL Writer and the backup agent services, for example net stop SQLWriter and net stop VeeamVssSupport. These services keep data files locked open, so stopping them frees the files for encryption. Evidence: System 7036 stop events for both services. The SOC should page when backup or SQL services stop outside a change window.

    Step 6 — The bulk stop storm

    The attacker runs a script that stops a dozen services in seconds: web, print, time, update, and more. System 7036 events pour in, and service nodes gray out one after another. Evidence: more than ten 7036 stop events for one host in minutes. The SOC should alert on the burst pattern, not on each event.

    Step 7 — SIEM links the facts

    The SIEM, the central log platform that stores and links events, connects three facts from one host. It links a burst of 7036 stop events, a missing EDR heartbeat, and a failed Defender stop minutes earlier. An EDR agent is the endpoint detection and response software that watches the host and reports to the SOC. The rule raises one critical incident for review instead of a pile of noise. Evidence: a correlated alert with host and account fields. The SOC should build this correlation rule before the attack, not during it.

    Step 8 — Isolate and restore

    The SOC isolates APP01 from the network, blocks the stolen account, and restarts the stopped services from a clean session. Data comes back from the immutable backup copy the attacker never reached. Evidence: incident ticket with the full timeline. The lesson: an offline backup copy turns a stop storm into a short delay.

    3

    Red team / hacker perspective

    Understanding the attacker's choices helps you predict the move and place your sensors. Everything here is described for defense and for labs you own.

    When and why attackers use it

    Timing is the whole point. Ransomware crews run Service Stop in the final minutes before encryption, and they run it for one blunt reason: running services hold files open. A database engine keeps its data files locked, the Volume Shadow Copy service holds snapshots, and a backup agent locks what it is copying. An encryptor that hits locked files fails or skips them. Stopping those services first removes the locks. ATT&CK describes exactly this use: attackers stop services so that data destruction or encryption can follow.

    The second reason is blindness. Stopping the antivirus service, the Sysmon collector, or the EDR agent reduces what the victim can see while the attack runs. This is where T1489 overlaps with T1562.001 Impair Defenses, which covers defeating security tools. Crews do not care which label a defender picks; they simply stop what watches them. The leaked Conti playbooks told operators to stop security and backup services before doing anything else, and LockBit 3.0 terminates security, backup, and database services the same way.

    The third reason is sabotage. Some groups stop so many services that the system becomes unusable even without encryption. Lazarus stopped MSExchangeIS, the Exchange information store, which made mailbox content unreachable. RobbinHood stopped 181 services on victim machines. Olympic Destroyer used the ChangeServiceConfigW API to disable every service it could find, so repair after the wipe became far harder.

    How it is performed

    On Windows, the attacker needs local admin or SYSTEM rights, then uses small built-in tools. On macOS, they unload background agents with launchctl instead. The commands below are the classic sequence, shown for lab study only. Run them only inside a disposable virtual machine that you own, and take a snapshot first.

    Real crews use exactly these shapes. Conti scripts ran net stop against a list of up to 146 service names covering security, backup, database, and email software. Prestige ran net stop MSSQLSERVER on transport-sector servers before encryption. The Gentlemen Ransomware combined all three Windows steps: sc config with start=disabled, then net stop and sc stop, then taskkill. Medusa ransomware used taskkill /F /IM /T to kill whole process trees. Wizard Spider used taskkill.exe and net.exe against backup, catalog, and cloud services. EKANS stopped database, backup, and antivirus processes and even carried an industrial control list. Cheerscrypt ran esxcli vm process kill on ESXi hosts, and Ryuk used a kill.bat batch script. Indrik Spider reached remote servers with PsExec to stop services ahead of ransomware.

    Prerequisites and conditions

    What the attacker needs first

    • Admin, root, or SYSTEM rights on the Windows, Linux, or macOS host.
    • A shell, an RDP session, or a remote path such as PsExec or a scheduled task.
    • A service list, gathered with sc query, tasklist /svc, or systemctl list-units.
    • For the cloud variant: a role with rights over organization or service settings.

    What limits them

    • Tamper protection blocks stops of well-shielded security services.
    • Services with restricted access control lists refuse stop calls from normal admins.
    • A stopped service restarts automatically unless the start type was changed too.
    • Every stop attempt and result lands in the System log, even when process logs are missing.

    Common variations and attacker mistakes

    Variations mostly differ in which tool touches the service. Some attackers call the Windows Service Control Manager API directly from custom code, as Olympic Destroyer did with ChangeServiceConfigW. Others wrap the same calls in PowerShell with Stop-Service or in scripts with kill.bat style batch files. On Linux they may stop a service with systemctl, service, or a direct kill of the daemon process. On macOS they unload background jobs with launchctl bootout or launchctl remove. ATT&CK's macOS detection guidance for this technique also names follow-on tools such as rm and diskutil. On hypervisors they kill virtual machine processes with esxcli or vim-cmd. The variety of tools is wide, but every path still passes through one or two choke points: a process creation event, a service control event, or both.

    Attacker mistakes are worth studying. Stopping a service without changing its start type invites an automatic restart, so careless crews get their damage rolled back. Killing the wrong process can crash the encryptor itself, which ends the attack early. Some crews stop a monitoring service and forget the cloud-side heartbeat, so the vendor raises the alarm instead. And the loudest mistake is the stop storm: dozens of 7036 events in one minute is a pattern no legitimate maintenance produces, and it is the signature that catches Conti-style playbooks.

    Danger · lab-only

    Never run the commands above on a production or shared system. They stop real services, break running applications, and can disable protection tools. Use an isolated virtual machine with a fresh snapshot, and treat every command as if a real SOC were logging it.

    4

    Blue team / SOC perspective

    Service Stop is one of the most reliable ransomware warnings a SOC can get. Here is how to see it, what it leaves behind, and how to triage it fast.

    How defenders can see it

    Service control events

    The Windows Service Control Manager writes event 7036 when a service enters the stopped state. It writes event 7040 when a start type changes, and event 7034 when a service crashes. These events are cheap to collect and very hard for an attacker to avoid, because the manager itself records them.

    Process telemetry

    Sysmon event 1 or Security event 4688 with command-line auditing shows net stop, sc config, and taskkill with full arguments. PowerShell event 4104 shows Stop-Service script blocks. This source names the actor, the parent process, and the target service.

    Health and heartbeat signals

    A stopped logging service stops sending logs. SIEM source health monitors, EDR heartbeats, and Linux journal or auditd feeds all show a missing stream. A silent host is evidence on its own, and cloud audit logs show the API path on cloud platforms.

    Why it matters and how it fits the chain

    Treat a service stop burst as a ransomware timer. Public incident reporting shows the gap between mass service stops and encryption is often minutes to a few hours. If you act inside that window, you can stop the encryption event entirely, because the attacker is still preparing. The signals also carry forensics. The user, parent process, and source host in a process event point back at the entry path. The target list tells you what the attacker plans next. A host whose EDR went quiet is not just a logging problem; it is the host the attacker plans to hurt.

    The technique also multiplies recovery time. If a start type was changed to disabled, every restart leaves the service off, so the outage repeats until someone walks each host. That is why responders check 7040 events during recovery, not only 7036 events during detection.

    Short triage flow

    1. Confirm the burst is real

      Open the raw 7036 events for the host. Count the stops and list the service names. Compare with your change calendar to rule out planned maintenance.

    2. Find the actor

      Pull Sysmon 1 or 4688 events for net.exe, sc.exe, and taskkill.exe in the same window. Record the user, the parent process, and the source address.

    3. Check the security tools

      Confirm whether antivirus, EDR, or logging services were targeted. A failed stop with tamper protection still proves intent and deserves a high-severity alert.

    4. Protect and restore visibility

      Isolate the host, restart the stopped security services from a trusted session, and lock the involved account. Check 7040 events so disabled services do not stay off after reboot.

    5. Scope and escalate

      Search all hosts for the same commands and the same stop burst in the last 24 hours. Multiple hosts mean an active campaign, so page the incident commander and prepare ransomware checks.

    Good practice

    Write the triage steps above into your incident runbook before you need them. During a live event, the team that follows a prepared checklist restores visibility minutes faster than the team that improvises.

    5.1 Regulation mapping

    This technique attacks the availability of the systems that process data, so it maps to continuity and monitoring controls. Auditors ask for proof that services stay available, that outages are detected, and that recovery works. The table below shows what each framework expects and the evidence a detection program provides.

    Framework and controlWhy it appliesExpected evidence
    GDPR — Article 32 (security of processing) Requires the ability to restore availability of and access to personal data after an incident. Stopped services and backups turn an attack into a longer, reportable outage. Documented service and backup recovery procedures, monitoring of service stop events, incident reports with recovery times.
    HIPAA Security Rule — §164.308(a)(7) contingency plan Covered entities must keep an emergency mode operation plan and a data backup plan for electronic protected health information.     SOC 2 — CC7.4 (incident response execution), A1.2 (availability commitments) Trust services criteria expect detection of attacks and recovery of the service the organization promised to customers.     PCI DSS — 12.10.x (incident response plan and testing) Organizations handling cardholder data must prepare for attacks that take systems out of service, which is exactly what a stop storm does.     NIST SP 800-53 Rev.5 — CP-10 (recovery), SI-4 (system monitoring) Federal and industry-aligned controls that require monitoring for attacks and tested recovery of system services. Control implementation statements, monitoring coverage proof, service restoration test logs.

    5.2 Threat intelligence

    Intelligence makes your detection rules stronger and your priorities honest. For this technique the picture is unusually clear, because nearly every destructive campaign since 2017 has stopped services with the same small set of tools. Collect from several source types, then record how confident you are in each finding before you change a rule or a runbook.

    MITRE ATT&CK

    Start with the technique page and its procedure examples. The group and malware list for T1489 is long and current, which makes rule coverage easy to justify.

    Vendor reporting

    Security vendor blogs publish exact service names, command lines, and timelines for each crew. Turn their incident timelines into your detection logic and tuning notes.

    OSINT and ISACs

    Free sources such as CISA advisories (CISA is the US cyber defense agency) and the StopRansomware guide share tactics early. Sector ISACs, which are information sharing groups for each industry, tell you which crews target organizations like yours.

    Commercial feeds

    Paid feeds add actor tracking, infrastructure, and malware families. Use them for context and prioritization, not as a replacement for your own telemetry.

    Internal telemetry

    Your own logs are the most valuable source. Failed stop attempts, tamper protection blocks, and near misses show what attackers actually try in your environment.

    Confidence levels

    High means several independent reports plus your own sightings. Medium means one solid public report. Low means a hypothesis that still needs testing. Write the level next to every intelligence note.

    5.3 Threats ranking and categorization

    Five realistic threats cover this technique well, numbered THR-01 to THR-05. The rank reflects how likely the threat is and how much damage it causes when it works. Preconditions describe what an attacker must already have; the justification explains the rank so you can defend it in planning meetings.

    ThreatRankPlatformDescription and preconditionsImpact and justification
    THR-01 — Security tool service stopped (WinDefend, Sysmon64, EDR agents). Critical Windows Attacker with local admin runs net stop, sc stop, or taskkill against a protection or logging service. Preconditions: admin rights and a shell on the host. Removes visibility and defense right before the main attack, and a lost heartbeat blinds the SOC. Highest damage per event and the most common target in procedure reports.
    THR-02 — Bulk service stop burst before encryption. High Windows Script stops ten or more services in minutes, including SQL services, VSS writers, and backup agents. Preconditions: admin rights and a prepared service list. Frees locked data files for encryption and breaks business applications at once. The burst pattern is a strong ransomware timer, as documented for Conti and RobbinHood.
    THR-03 — Start type changed to disabled, then stopped. High Windows sc config <service> start= disabled followed by a stop. The Gentlemen Ransomware did this with sc config; Olympic Destroyer did it with the ChangeServiceConfigW API. Preconditions: admin rights over service configuration. Keeps the service down across reboots, so the outage repeats and recovery drags. Rarer than a plain stop but far more persistent, hence High.
    THR-04 — Critical Linux or macOS service stopped. Medium Linux macOS systemctl stop or kill against sshd, auditd, or a database daemon. On macOS, launchctl bootout or remove against security or backup agents. Preconditions: root, sudo, or admin rights on the host. Cuts remote access, logging, or the database behind an application. Less common in public reporting than the Windows case, which caps the likelihood.
    THR-05 — Hypervisor or cloud service kill. Medium IaaS ESXi esxcli vm process kill or vim-cmd on ESXi hosts, or the AWS DisableAPIServiceAccess call with stolen cloud admin rights. Preconditions: deep control of hypervisor or cloud organization settings. One hypervisor command stops many machines at once. The cloud call can stop a service from creating its roles on new accounts across the organization. Rising with ESXi-focused ransomware, but needs deep access first.

    5.5 Sigma rules and Splunk SPL

    Five complete Sigma rules follow, one per threat (THR-01 to THR-05), each with a matching Splunk query. The rules use the same log sources as the tables above; if you collect Security 4688 instead of Sysmon, swap the logsource and keep the field logic. The Splunk queries assume the index and sourcetype conventions listed below; adjust the index names to your environment and document the change. Rules 3 and 5 each carry a second query in the same block: a System log confirmation and an ESXi shell check.

    Field assumptions for Splunk

    index=sysmon holds Sysmon XML events with fields like Image and CommandLine. index=wineventlog holds XmlWinEventLog:System with param1 and param2 extracted. index=linux holds auditd records with a0 to a2. index=aws holds aws:cloudtrail JSON. Field extraction must be enabled for XML inputs before these queries work.

    Rule 1 — Security tool service stopped

    Mapping note: each Sigma param1|contains value becomes one OR branch of wildcard matches. The param2 filter keeps only stops, not starts. False positives: planned security tool upgrades inside change windows. Tuning: move the service name list into a lookup table. Add an exception for documented change records. Raise severity when the same host loses its log source heartbeat right after the stop.

    Rule 2 — Bulk service stop burst before encryption

    Mapping note: the Sigma count() by host condition becomes a bin plus stats count in Splunk. The timeframe and the where filter then keep only bursts. False positives: patch waves that restart many services at once. Tuning: raise the threshold for hosts with known maintenance jobs. Add weight to stops whose names match SQL, VSS, or backup keywords, since those free files for encryption.

    Rule 3 — Start type changed to disabled, then stopped

    Mapping note: the three contains|all terms become three required wildcard tokens. Splunk matches are case-insensitive, so start= with or without a space still matches. The second query in the block is the System log confirmation, and it also catches start type changes made by tools other than sc.exe. False positives: provisioning hosts that disable unused roles. Tuning: exclude imaging and configuration management hosts by group.

    Rule 4 — Critical Linux service stopped

    Mapping note: auditd EXECVE fields map one to one. The Sigma list of verbs for a1 becomes the Splunk IN clause. False positives: Ansible, Puppet, or package upgrades that restart services. Tuning: keep a protected unit list such as sshd, auditd, and mysql. Watch for kill -9 against daemon names from tmp paths as a second rule. Treat an auditd stop itself as critical, because it ends the evidence. On macOS, cover launchctl bootout and remove events through your Mac management feed.

    Rule 5 — Hypervisor or cloud service kill

    Mapping note: CloudTrail JSON fields map directly to Splunk search-time extractions. The event name list becomes the IN clause. ATT&CK writes DisableAPIServiceAccess; AWS documents the same call as DisableAWSServiceAccess, so the rule watches both spellings. False positives: approved governance work by the organization management account. Tuning: allow-list the fixed role ARN and page on any interactive user, new source IP, or call outside your change calendar. The second query in the block covers the ESXi half of this threat from shell and hostd logs; point index=linux at wherever your ESXi estate actually lands them.

    6

    Real-world case study

    The Conti ransomware playbook and the May 2021 attack on Ireland's Health Service Executive (HSE). This is the best-documented use of Service Stop against a national health system.

    Context

    This case study is a factual account of a real incident, based on public reporting; it is not a training scenario. Named sources include the HSE's independent post-incident review (PwC, 2021) and published analyses of the leaked Conti playbooks. Conti was a ransomware group linked to the Wizard Spider crew. When its internal playbooks leaked in 2021, defenders could read the operator manual step by step. The manual told operators to stop security tools, stop or delete backups, and only then start encryption. The Health Service Executive (HSE), Ireland's public health service, experienced this playbook directly. Public reporting describes how attackers reached the network around March 2021 through a malicious document, moved quietly for about two months, and launched ransomware across the organization on 14 May 2021. The HSE shut down thousands of its own systems to stop the spread, and patient services were disrupted for weeks.

    Attack chain mapping: a malicious document gave the attackers Initial Access. Stolen credentials enabled Lateral Movement and Privilege Escalation. The operators then prepared Impact with T1489, tampered with backups in the manner of Inhibit System Recovery (T1490), and finally ran Data Encrypted for Impact (T1486).

    Timeline

    1. March 2021
      A malicious document opens the door

      According to public reporting, an employee opened a malicious Excel attachment. The malware gave the attackers their first foothold inside the HSE network, and they began stealing credentials.

    2. March to May 2021
      About two months of quiet movement

      The attackers moved laterally, harvested accounts, and mapped the estate. The long dwell time matters: nothing visible broke, while the operators prepared the impact phase described in their playbook.

    3. Days before 14 May
      Preparing the impact phase

      Following the leaked playbook, the operators located high-value servers, backup infrastructure, and security tooling. The playbook's core instruction was to stop or remove anything that could interfere with encryption or help recovery.

    4. 13 to 14 May 2021
      Security and backup services targeted

      Just before the main attack, the operators worked to stop protection and backup services. They also tampered with backup data. These are the Service Stop and backup-removal steps this guide describes. Freeing locked files and cutting recovery were the goals.

    5. 14 May 2021
      Ransomware starts across the HSE

      Encryption began across many systems at once. The HSE made a defensive decision to shut down thousands of its own systems to stop the spread, which protected some sites but took services offline by design.

    6. Weeks after
      Patient services disrupted

      Appointments and treatments were canceled or delayed, staff reverted to paper, and teams rebuilt systems in business-critical order. Because recovery options had been tampered with, many systems had to be rebuilt rather than restored in place.

    7. Later in 2021
      A decryptor, but no short cut

      Under public pressure, Conti released a decryptor. Even with it, recovery took months, because the preparation phase had damaged or removed recovery paths before the encryption event.

    Detection point

    The playbook made the attack predictable. Stopping security and backup services produces System event 7036 entries, tamper alerts, and silent log sources, and these signals fire before encryption. The missed chance was visibility: service stop events and backup job failures were not being correlated into one alarm during the two months of preparation. A rule that pages on a burst of stops, or on a backup agent going quiet, would have raised the alarm while the attackers were still preparing.

    Containment

    The defining containment move was the mass shutdown of thousands of systems to stop the encryption wave from spreading. Teams then cut network paths, blocked the involved accounts, and preserved what still ran. The scale shows the trade-off of late detection: when the alarm comes at the last minute, containment looks like turning the organization off.

    Eradication

    Responders searched for every foothold, removed the attackers' access, and reset credentials at scale. Because the operators had targeted security tooling, teams had to confirm that protection services were running again on every host before trusting it. Each rebuilt machine also had to be checked for disabled services left behind in the start type changes.

    Recovery

    Recovery came from clean images, surviving systems, and whatever backups remained intact. The released decryptor helped with some data, but it did not repair the preparation damage, so the HSE rebuilt in a clinical-priority order and ran a long recovery program. The outages lasted weeks, and full restoration stretched into months.

    Impact and consequences

    The incident disrupted health services across Ireland for weeks. It forced the cancellation of appointments and procedures. It also required one of the largest IT recovery efforts in the country's history. Public reporting describes extensive rebuilding of servers and endpoints, and the event became a national reference case for health-sector cyber resilience. The financial and operational cost of the outage far exceeded the ransom demand, which underlines the real objective of the preparation phase: maximum disruption.

    Team response and communication

    The response ran as a national incident with a dedicated command structure, daily coordination between IT, clinical leadership, and government, and external incident response support. Communication channels had to survive the outage itself, which proved the value of an out-of-band channel that does not depend on the compromised estate. Teams published clear staff guidance, prioritized clinical systems, and kept a running public statement flow, which reduced confusion while systems were down.

    Lessons learned

    • A long dwell time is a planning window for the attacker; hunt for service enumeration and stop attempts, not only for encryption.
    • Stopping security and backup services is the playbook's signature; alert on those stops and on failed tamper-blocked attempts.
    • Keep one backup copy the playbook cannot reach, offline or immutable, and prove the restore path quarterly.
    • Shutting down thousands of systems defensively is a hard call; segment networks so one decision does not need to be that large.
    • Out-of-band communication and a rehearsed runbook decide how fast the organization moves on the worst day.
    7

    Mitigation and defense

    You cannot stop every attacker from reaching one machine, but you can make service stops fail, restart quickly, and stop mattering. The controls below follow the ATT&CK mitigation list for this technique and are ordered by how much risk they remove.

    Enterprise controls by domain

    Service protection and tamper resistance

    Turn on tamper protection for antivirus and EDR so a plain net stop cannot touch them. Also configure restricted service access control lists on critical services, so only approved accounts can stop them. These are the controls that turned step 3 of the simulation into a detection instead of a loss.

    Identity and privileges (M1018)

    Apply least privilege: most admins do not need to stop services on servers. Separate backup and security administration from general server administration, and remove standing rights over service configuration. User Account Management, ATT&CK mitigation M1018, is one of the five mitigations ATT&CK lists for this technique.

    Registry and file permissions (M1024, M1022)

    Restrict registry permissions on HKLM\SYSTEM\CurrentControlSet\Services (M1024), so a start type cannot be flipped to disabled by a normal admin. Also restrict file and directory permissions (M1022) on service binaries and agent folders. Together these controls block the persistent variant of the technique.

    Network segmentation (M1030)

    Segment server farms, backup infrastructure, hypervisor management, and cloud control planes away from workstations, and limit which hosts may call remote service control at all (M1030). A segmented estate turns one stop storm into one damaged host instead of a fleet, and it protects the management interfaces that ESXi attackers target.

    Out-of-band communications channel (M1060)

    Keep an alerting path that survives a stop storm (M1060). Use a SIEM or alerting service outside the attacked network. Add phone or messenger escalation that does not depend on the victim's own mail and chat. If the attacker blinds the estate, the alarm must still arrive somewhere else.

    Logging, monitoring, and readiness

    Ship System 7036, 7040, and 7034, Sysmon 1, Security 4688, PowerShell 4104, auditd, and cloud audit logs into the SIEM. Deploy the five rules from section 5, monitor log source heartbeats, and write a stop-storm runbook: who isolates, who restarts services, and who checks 7040 before declaring a host healthy.

    Home and small office advice

    Protect your own services

    • Keep the built-in antivirus on and leave tamper protection enabled.
    • Do not run daily work from an administrator account.
    • Let updates finish; stopped update services are how damage hides.
    • Restart a stopped protection service and check why it stopped.

    Small-office quick wins

    • Keep the backup agent on every machine and check its dashboard weekly.
    • Keep one backup copy offline or in cloud storage with version history.
    • Turn on alerts from the backup product so a stopped agent is noticed.
    • Once a quarter, restore one file and time how long it takes.
    Good practice

    Plan for the restart as well as the block. A stopped service that restarts in minutes is an incident; a stopped service that nobody noticed is an outage. Heartbeat monitoring plus a rehearsed runbook keeps the difference small.

    Healthy operating habits

    Daily

    • Confirm critical log sources are reporting, including security and backup agents.
    • Review every security-service stop alert and every tamper block.
    • Check backup job dashboards for agents that stopped reporting.

    Weekly

    • Walk one stop-burst alert end-to-end and time the triage.
    • Review new exclusions and tuning changes with a second reviewer.
    • Sync with the platform team about patch windows and restart plans.

    Monthly

    • Test one rule against a lab host running the technique safely.
    • Review service ACLs and admin group memberships.
    • Update actor notes from new public incident reports.

    Cheat sheet and quick reference

    Everything important on one screen, for the wall and for the incident channel.

    Key facts

    Technique
    T1489 — Service Stop.
    Tactic
    Impact.
    What it does
    Stops or disables services to break availability, blind defenses, or free locked files.
    Typical timing
    Minutes to hours before encryption, after admin rights are won.
    Signature commands
    net stop, sc config start= disabled, taskkill /F /IM, Stop-Service, systemctl stop, launchctl bootout, esxcli vm process kill.
    Key evidence
    System 7036, 7040, 7034; Sysmon 1; PowerShell 4104; auditd EXECVE; CloudTrail.
    Best single defense
    Tamper protection plus one offline backup copy and heartbeat monitoring.

    Response checklist

    • Confirm the burst: raw 7036 events, service names, count, and host.
    • Find the actor: Sysmon 1 or 4688 for net.exe, sc.exe, taskkill.exe, and PowerShell.
    • Check tamper alerts and failed stop attempts; they prove intent.
    • Isolate the host and block the involved account.
    • Restart security and logging services from a trusted session.
    • Review 7040 events and reset any start type set to disabled.
    • Search all hosts for the same commands in the last 24 hours.
    • Verify the backup copy is intact before declaring safety.

    One-line summary

    When services start stopping in a burst, the attacker is preparing the main attack. The stops free files for encryption and blind your defenses, so treat the burst as your ransomware alarm: protect backups first, and move. The SOC that notices a silent heartbeat in minutes keeps its data; the one that finds out after encryption loses weeks.
