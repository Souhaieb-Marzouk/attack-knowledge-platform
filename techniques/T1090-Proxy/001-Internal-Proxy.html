T1090.001 — Internal Proxy

An internal proxy is a compromised system inside a network that passes command and control (C2) traffic between two or more other systems. Per MITRE, attackers use it to manage C2 inside the environment, cut the number of outbound connections, survive connection loss, and ride trusted internal paths such as SMB. This guide shows how the trick works and how to detect it step by step.

🛡 Guide v2.0 · audited against ATT&CK v20.0

Sub-technique of T1090 · Proxy Tactic: Command and Control Platforms: ESXi, Linux, macOS, Network Devices, Windows ATT&CK v1.2 · modified 2026-09-08

What it is

A compromised internal host relays C2 for other infected hosts, so they never need their own path to the internet.

Typical tools

HTRAN, ZXProxy, ZXPortMap per MITRE; in practice also netsh portproxy, socat, and C2 frameworks with peer-to-peer beacons.

Why it matters

One egress flow can hide many infected hosts. Perimeter-only monitoring misses the whole chain.

How to catch it

Correlate pipe, process, and flow events: one host that receives from many and sends to one.

What is an internal proxy?

Attackers rarely want every infected host to talk to the internet. Some hosts sit in zones with no outbound access. Others would raise an alert if they opened a new connection.

So the attacker picks one host they already control. That host becomes the internal proxy. Other infected hosts send their C2 traffic to it. The proxy forwards that traffic onward, often to a single exit point that reaches the internet.

MITRE describes it this way (in simple words): an internal proxy directs C2 traffic between two or more systems in a compromised environment. By using a compromised internal system as a proxy, attackers hide the true C2 destination and need fewer connections to external systems.

MITRE also names known relay tools: HTRAN, ZXProxy, and ZXPortMap. In real incidents, attackers often use built-in features instead. Common examples are netsh portproxy on Windows, socat on Linux, and peer-to-peer beacons that pass traffic over SMB.

Key words in this guide

  • C2 (command and control) — the channel an attacker uses to send orders to infected hosts and receive stolen data.
  • Proxy / relay — a host that receives traffic and forwards it to another host.
  • Beacon — a small, regular signal an infected host sends to say "I am here" and fetch orders.
  • Egress — traffic leaving your network towards the internet.
  • East-west traffic — traffic between machines inside your network, not to or from the internet.
  • SMB — the Windows file-sharing protocol. It is normal between hosts, which is why attackers hide in it.
  • Named pipe — a labeled channel for program-to-program talk on Windows, carried over SMB.
  • Fan-in — many hosts connecting to one host. A C2 relay creates strong fan-in.

ChainWhere it fits in an attack

An internal proxy is never the first step. It appears after the attacker already controls one system. A typical chain looks like this:

Before · Initial access
Phishing, a vulnerable public service, or stolen remote-access credentials give the attacker their first foothold (for example T1566, T1190, or T1078).
Before · Execution & discovery
The attacker runs commands, maps the network, and finds a good relay host: a server that many hosts can reach and that is allowed to talk out (T1059, T1046).
This technique · T1090.001
The attacker turns that host into an internal proxy. Other infected hosts beacon through it. Peer-to-peer protocols such as SMB make the traffic look ordinary.
After · Lateral movement
The attacker uses the relay to reach servers, backups, and admin tools (T1021). One clean path now serves many actions.
After · Collection & exfiltration
Stolen data is staged on the relay and leaves through the same single, quiet egress flow (T1005, T1041).

Why detection is hard

The proxy hides two things at once. First, the true destination: victim hosts only talk to an internal server, which is normal-looking. Second, the number of victims: outside the network, everything looks like one host with one connection.

The traffic also rides protocols that are always on. SMB, WinRM, and WMI sessions run all day in a Windows network. A C2 channel inside them has no unusual look at first glance.

That is why single events rarely help. Detection works when you correlate: one host that receives from many and sends to one, plus a pipe or process event that should not exist.

Why it matters

An internal proxy turns one breach into many. Every host that beacons through the relay is a full compromise, but the firewall may show only a single connection.

It also breaks your response model. If you block the relay's egress IP, victims may still talk to the relay inside. You must find and clean the whole mesh, not one host.

Groups such as Volt Typhoon and Turla, and software such as Cobalt Strike, Duqu, and Stuxnet, have all used internal relaying. This is a real, current problem, not a lab idea.

StoryWritten story: the same eight steps in words

This text tells the same story as the animation. Screen readers and printers can use it instead of the canvas.

  1. Beachhead. The attacker exploits an internet-facing service and lands on an internal server, R1. R1 sits in a server zone that many hosts can reach and that is allowed to send traffic out. The SOC sees only a normal-looking web session. Defender view: without an endpoint agent on R1, the foothold is invisible at this point.
  2. One quiet exit. The attacker installs a beacon on R1. It opens one outbound link through the company firewall to the C2 server on the internet. The SOC sees one new egress flow from a server. It looks like ordinary HTTPS. Defender view: one flow, no content visibility without TLS inspection.
  3. Inside channel. On R1, the beacon starts an SMB named-pipe listener. Infected hosts inside the network will use this pipe to reach R1. Pipe creation is a local event; the firewall sees nothing. Defender view: without Sysmon event 17/18 or an EDR pipe event, this step never appears in the SIEM.
  4. Victim A joins. A phishing mail infected workstation A earlier. Its beacon cannot reach the internet. It finds the pipe on R1 and sends its C2 traffic through it. The SOC sees plain east-west SMB from A to R1, which happens all day. Defender view: the C2 content hides inside a trusted protocol.
  5. Victim B joins. A second workstation joins the same pipe. Now two victims are controlled through R1, but the firewall still shows only the one egress flow from step 2. Defender view: the egress count stays flat while the number of victims grows. That gap is the story of this technique.
  6. The gap, drawn out. The attacker now commands three hosts and needs only one external connection. If the attacker loses that one link, R1 keeps the inside channel alive and can re-connect later. Defender view: blocking one IP does not close the attack. The mesh lives inside.
  7. Detection. The EDR reports a new named pipe on R1 from a service host. Zeek shows many hosts opening SMB sessions to one server, plus odd pipe names. The correlation rule joins pipe event, fan-in, and the single egress flow. A high-severity alert fires with the whole chain pre-built. Defender view: this is Sigma rule 2 plus rule 6 in section 5.5.
  8. Respond and fix. The SOC isolates R1 and kills the pipe listener. The firewall team blocks the C2 address. The team hunts for the pipe name on every host to find victims A and B, then rebuilds R1 from a clean image. Defender view: contain the relay, then sweep the mesh — in that order.
Good practice

The turning point is step 7. No single event was enough. The chain "new pipe + fan-in from many hosts + one egress flow" is what exposed the mesh. Sections 4 and 5 build exactly that chain.

Red Team Perspective

Why attackers build relays inside a network, when they do it, and which mistakes leave traces. All examples in this section are lab-only and use ordinary admin commands.

Ethics

This section exists to help defenders practice. Use these ideas only in a lab you own. Running them on systems you do not own is illegal in most countries.

Q&AFour questions about internal proxies

Why do attackers use one?

Because it solves three problems at once. It reaches hosts that have no path to the internet. It hides how many hosts are infected. And it keeps C2 alive when one route dies.

When does it appear?

After the first foothold and after discovery. The attacker needs to know which hosts can reach which zones before they pick a relay. In long spying operations, the relay can stay for months.

How is it built?

Three common ways: a forwarding tool such as netsh portproxy or socat; a C2 framework with peer-to-peer beacons over SMB named pipes; or a tunnel tool installed as a service. MITRE names HTRAN, ZXProxy, and ZXPortMap as classic tools.

Where does it run?

On hosts that sit in the middle: file and app servers, jump hosts, sometimes network devices or ESXi hosts. The best relay host is one that many machines can reach and one zone trusts.

SetupTypical setup and variations

The attacker needs three things: control of the relay host, rights to start a listener or service, and a network path from the relay to the targets. Then the pattern is always the same. Bind a port or pipe. Forward what arrives. Send the answers back.

Variations defenders should know

  • Built-in first. netsh portproxy and socat need no download, so careful attackers prefer them.
  • Peer-to-peer beacons. C2 frameworks relay between hosts over SMB named pipes. No new TCP port is needed.
  • Service install. Tunnel tools registered as Windows services or Linux units survive reboots.
  • Device-level relay. A router, switch, or ESXi host can forward traffic too, and endpoint tools rarely watch it.
  • Trusted-path rides. C2 wrapped inside WinRM, WMI, or admin SMB sessions looks like management traffic.

Attacker mistakes that create detections

  • The portproxy rule is stored in the registry and survives reboots. It is a durable anchor for detection.
  • Tunnel tools keep their real names in process and service logs: chisel, frpc, socat.
  • A relay creates fan-in: many sources to one host. Baselines make this visible.
  • Long-lived connections from workstations to server zones are rare in honest traffic.
  • New listening ports on endpoints stand out against a listener inventory.
Danger — lab only

All commands below are lab only — use only on systems you own. They are standard admin commands. Run them in an isolated test network only.

ExamplesThree safe lab examples

Lab only · Windows netsh portproxy (needs Administrator)
:: Run on a Windows lab VM. Forwards local port 4444 to a lab database host.
netsh interface portproxy add v4tov4 listenaddress=0.0.0.0 listenport=4444 connectaddress=10.90.0.15 connectport=1433

:: Show the rule. Windows stores it under HKLM\SYSTEM\CurrentControlSet\Services\PortProxy
netsh interface portproxy show all

:: Remove it again when the lab is done
netsh interface portproxy delete v4tov4 listenaddress=0.0.0.0 listenport=4444
Lab only · SSH tunnel between two lab hosts (Linux / macOS)
# -L: local listener on 8443, forwarded through the SSH server to a lab web app
ssh -N -L 8443:web.lab:443 deploy@jump.lab

# -R: exposes a lab port back to the SSH server side
ssh -N -R 9999:127.0.0.1:3389 deploy@jump.lab

# -D: dynamic SOCKS proxy for lab tools
ssh -N -D 1080 deploy@jump.lab
Lab only · socat relay on a Linux lab host
# Listen on 8080 and forward every connection to the lab web server
socat TCP-LISTEN:8080,fork,reuseaddr TCP:10.90.0.20:80

# Quick check that the relay path works, then it exits
echo test | timeout 3 socat - TCP:127.0.0.1:8080

Blue Team Perspective

Where to look first, what normal looks like, and a concrete triage flow you can follow on your next shift.

SourcesWhere to look first

Process & registry eventsSysmon EID 1/13/17/18, EDRportproxy commands, tunnel tools, new named pipes

What normal looks like

  • Workstations open SMB to file servers and domain controllers, in known patterns.
  • Servers in one tier talk to their own tier and to a few management hosts.
  • Admins run SSH from named jump hosts, in work hours, to approved targets.
  • Listener counts per host stay stable from week to week.

What suspicious looks like

  • A workstation connects to another workstation on a port that is not 445, 139, or 5357.
  • Many hosts suddenly open sessions to one internal host that never received fan-in before.
  • A new named pipe appears from a service host, with a random-looking name.
  • One host holds both legs: an inbound listener and an outbound connection, on the same ports.

TriageA 7-step triage checklist

  1. Open the raw event. Copy host, time, user, process, and command line. Ask: is this a pipe event, a portproxy command, or a flow alert?
  2. Pull host context. On the same host, in a window of 15 minutes before to 15 after: list processes, logons, new listeners, and service installs.
  3. Build the chain. In Zeek, NetFlow, or firewall logs, find both legs. A relay shows traffic in and traffic out on the same host, close in time.
  4. Check fan-in. Count distinct sources that contacted this host in 24 hours. More than 15 on one port is a strong relay signal. Compare with last week.
  5. Score it. Registry or pipe evidence plus a cross-zone flow is high confidence. One SSH -L flag on a developer jump host alone is probably normal. Check the asset owner.
  6. Contain if confirmed. Isolate the relay host first. Then kill the listener or pipe. The mesh loses its exit and its meeting point at once.
  7. Escalate and document. Call IR when the relay reached a server zone or more than two hosts. Record which logs you missed, so the gap gets fixed.

Escalation criteria — call IR when

  • The PortProxy registry key or a suspicious pipe appears on any server.
  • Two or more hosts beacon through the same internal relay.
  • The relay host is a network device, ESXi host, or domain controller.
  • Stolen or service accounts appear in the chain.

Quick wins this week

  • Turn on Sysmon EID 17/18 (pipe created/connected) on all Windows hosts.
  • Deploy the six Sigma rules in section 5.5 into your SIEM.
  • Build one report: distinct internal sources per internal host per day.
  • Verify an agent exists on every server. List the gaps and fix the top three.

A 6-step intel workflow

  1. Collect. Pull the ATT&CK page, two or three vendor reports, and this week's abuse.ch feed into one place.
  2. Process. Strip noise. Keep behaviors: pipe names, ports, relay tool names, and flow shapes.
  3. Analyze. Compare each behavior with your baselines. Rate how likely it is in your sector.
  4. Apply. Load new indicators into the 5.5 rules. Write new rules for behaviors you cannot yet see.
  5. Review. After 30 days, check which feeds produced alerts and which produced only noise.
  6. Feed back. Send confirmed sightings to your ISAC and note gaps in your coverage plan.

Turn intel into hunts — three named hypotheses

H1 · Hidden pipe mesh
Hypothesis: an infected host runs a C2 named pipe that other hosts connect to. Hunt: search Sysmon EID 17/18 for pipes created by service hosts, then fan-in on the same host in Zeek or NetFlow.
H2 · Relay on a server
Hypothesis: a compromised server runs portproxy or socat to bridge two zones. Hunt: list all portproxy registry writes and socat listeners in 90 days of logs, then check each against change tickets.
H3 · One exit, many victims
Hypothesis: several hosts share one egress beacon because one internal relay consolidates them. Hunt: rank internal hosts by distinct internal sources per day; then for each top host, check whether it also holds the only egress flow for its group.

Case Study — "The Quiet Fan-In"

Composite scenario

This case study is fictional but realistic. The company, hosts, and dates are invented. Every step follows tradecraft documented in public incident reports. It does not describe one specific real company.

Context

"Aurora Freight" runs regional logistics. Its office workstations and a server zone share one routing design from an older merger. Server FS-APP-02 hosts a file application. It has an endpoint agent, but the agent was set to silent mode by a vendor installer, so pipe and process alerts never reached the SIEM.

Attack chain mapped to ATT&CK

  • Initial access — T1566.001 spear-phishing attachment to a finance mailbox.
  • Execution — T1204.002 user opens the attachment; T1059.001 PowerShell loader runs.
  • Persistence — T1543.003 a fake "Aurora Sync" Windows service on FS-APP-02.
  • Command and control — T1071.001 one HTTPS beacon out; T1090.001 SMB named-pipe relay for two workstations (this technique).
  • Lateral movement — T1021.006 WinRM sessions launched through the relay.
  • Objective — T1005 files collected from share folders; T1041 exfiltration over the C2 channel.

DetectionWhich rule and which log fired

The case opened from Sigma rule 6 (fan-in) in section 5.5, fed by Zeek conn.log. One host, FS-APP-02, received SMB sessions from 17 distinct sources in one day. Sigma rule 2 then confirmed a matching pipe event from the EDR pilot feed: a pipe named like a framework pipe, created by a service host. The analyst correlated three facts on one host: fan-in, pipe creation, and a single steady egress flow. That trio is the internal-proxy signature described in this guide.

Containment

Isolate FS-APP-02 first. The mesh loses its meeting point and its exit at once. Then isolate WS-OPS-07 and WS-WHS-02. Block the C2 address at the firewall.

Eradication

Remove the fake service, rebuild the three hosts from clean images, rotate every credential seen on them, and hunt the pipe name across the estate.

Recovery

Restore hosts, fix the silent agent mode, forward EID 17/18 and service installs, and re-check the segmentation rules that made the fan-in possible.

Impact and business consequences

Operational: three hosts offline for two days; the file app moved to a backup server with minor delays. Data: the attacker reached two share folders; SQL audit and flow volume analysis found no confirmed bulk exfiltration. Cost: roughly 180 staff hours of response, one external forensics engagement, and unplanned hardware for rebuilds.

Business consequences: a customer audit asked for evidence of the response; the insurer asked for the detection timeline; and the team had to explain why one server held both trust roles. The case became the driver for the segmentation project.

Team response and tools

Roles: SOC T1 opened and triaged the case; SOC T2 did the correlation; the IR lead ran the bridge; the network engineer pulled Zeek and firewall data and blocked the C2 IP; the IT owner rebuilt hosts; management approved overtime; comms prepared a customer note that was not needed after all.

Attacker tools: phishing kit, PowerShell loader, a Cobalt Strike-style beacon with SMB peer support, WinRM. Defender tools: Zeek, Sysmon, EDR, Splunk, the Sigma rules in 5.5, and a rebuild pipeline.

Lessons learned

  • Agent coverage is not the same as alert coverage. The agent was present but silent; only the SIEM pilot feed caught the pipe event.
  • Fan-in is a cheap, strong signal. One aggregation query found the exit host that no single flow alert had flagged.
  • Pipe auditing must be on before you need it. EID 17/18 was a checkbox item before the case; after it, a permanent rule.
  • Contain the relay first. Isolating the exit host broke the channel for every victim at once.
  • Hunt the indicator, not the host. Sweeping the pipe name estate-wide found two more suspicious hosts the alerts had missed.
  • One host, two trust roles. A server that serves users and reaches the internet is a design defect; segmentation removes the reward.

Mitigation and Defense

MITRE lists one official mitigation for this technique: Network Intrusion Prevention (M1031). Beyond that official mitigation, practitioners rely on layered prevention and detection controls, listed below.

Official MITRE mitigation

Network Intrusion Prevention (M1031). An IPS that inspects east-west traffic can spot relay behavior and known relay tools inside the network, not only at the edge. Place sensors between zones, not only at the perimeter.

Detective controls

  • Log pipeline. Ship Sysmon EID 1/3/13/17/18, service installs, Zeek or NetFlow, and firewall session logs to the SIEM.
  • Sigma deployment. Run the six rules from 5.5; test each one with a lab event every quarter.
  • Alert triage. Write a playbook for relay alerts: isolate, kill, trace both legs, sweep for the indicator.

Enterprise actions this quarter

  • Verify an agent in alerting mode on every server; publish the gap list with owners.
  • Remove any "any-any" rules between zones found in the last rule review.
  • Set IPS sensors on the two busiest east-west links first.
  • Add device and hypervisor management IPs to the monitoring scope.

HomeHome and remote workers

Home networks are flat. One infected laptop can reach every device, and a relay can form without any firewall to cross. Keep it simple:

  • Update the router firmware and disable remote management from the internet.
  • Never set up port forwarding on the router for work devices; use a reputable VPN instead.
  • Run reputable antivirus and keep it on.
  • Turn on a DNS filter that blocks known bad domains.
  • Keep work devices on a separate network profile from smart home and guest devices.
  • If something odd happens — new pop-ups, unknown programs, slow unexplained traffic — report it to IT the same day, before unplugging anything.

RulesTop detections (see section 5.5)

  • Rule 1 — netsh portproxy command line on any host (Critical, Sysmon EID 1).
  • Rule 2 — C2-style named pipe created by a service host (Critical, Sysmon EID 17).
  • Rule 3 — internal peer connection on a relay port (High, Sysmon EID 3).
  • Rule 4 — device or ESXi management IP reaching the internet (High, network logs).
  • Rule 5 — shell spawned by WinRM or WMI provider host (High, Sysmon EID 1).
  • Rule 6 — more than 15 internal sources converge on one host and port (Medium, flow aggregation).

Response checklist

  • ☐ Isolate the relay host — the mesh loses its meeting point.
  • ☐ Capture the listener process, command line, and pipe name first.
  • ☐ Kill the listener, pipe, or portproxy rule.
  • ☐ Trace both legs in flow logs: inbound sources and outbound exit.
  • ☐ Sweep the estate for the same pipe name, port, or service name.
  • ☐ Isolate every host that answered the sweep.
  • ☐ Block the C2 address and rotate exposed credentials.
  • ☐ Close the segmentation path and file the detection gaps found.

If you only remember one thing

Count your hosts' conversations. A compromised internal proxy is one host that many hosts suddenly talk to, while it alone talks outside. Find that shape, confirm it with a pipe or portproxy event, and you have the whole mesh — not just one host.
