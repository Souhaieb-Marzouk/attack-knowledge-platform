DETECTION GUIDE · T1090.003

T1090.003 — Multi-hop Proxy

A multi-hop proxy is a chain of two or more relays. Attackers chain proxies so the true source of their traffic is hard to find. You usually see only the first hop. This guide shows the whole chain, what you can see at each hop, and how to detect it.

Guide v2.0 · audited against ATT&CK v20.0

Sub-technique of T1090 Tactic: Command and Control Platforms: ESXi, Linux, macOS, Network Devices, Windows Official mitigation: M1037 Filter Network Traffic

What it is

Traffic passes through several relays before it reaches its target. The relay closest to your network is often the only one your logs can see.

Known users

MITRE lists Tor, SystemBC, FRP, Dridex, Ursnif, WannaCry, AsyncRAT, and Kobalos as software using this technique.

Why it matters

The chain hides the C2 source. Blocking one relay IP does not stop the campaign. The operator picks a new relay with little effort.

How to catch it

Match egress against relay lists. Flag relay tools on endpoints. Watch for onion addresses, odd ICMP, and peer-to-peer ports.

The technique in plain words

A relay (also called a proxy) is a server that passes traffic along without changing its meaning. A multi-hop proxy is a chain of two or more relays. Traffic enters the first relay, hops to the next one, and only the last relay talks to the final destination.

MITRE's description says it simply: attackers chain multiple proxies to disguise the source of malicious traffic. A defender can usually identify the last proxy before the traffic enters the network. Earlier hops are often impossible to see.

Tor is the best-known example. A Tor circuit uses three relays, and each relay only knows its neighbors. Attackers also build ORB networks (operational relay boxes) from rented servers, IoT devices, and old routers. Some chains run inside ICMP (the ping protocol) instead of TCP.

What MITRE says, in short

MITRE lists four ideas for T1090.003. One: chain proxies to hide the source. Two: use onion routing networks such as Tor to carry encrypted C2 traffic. Three: build ORB networks from virtual private servers, IoT devices, smart devices, and end-of-life routers. Four: compromise network devices with custom code (related technique T1584.008) so they relay traffic across a WAN boundary (related technique T1599).

MITRE also notes two more variants. Protocols such as ICMP can be the transport. Peer-to-peer and blockchain-style infrastructure can route traffic in a decentralized way.

Key words in this guide

  • C2 — command and control. The channel an attacker uses to send orders to malware.
  • Relay / proxy — a system that forwards traffic and hides the sender behind its own address.
  • Multi-hop — two or more relays in a row, so no single system knows both ends.
  • Egress — traffic leaving your network towards the internet. Egress logs are where the first hop shows up.
  • Onion address — a public name for a hidden Tor service. It ends in .onion.
  • ORB network — a relay chain built from rented servers, IoT devices, and old routers.
  • Beacon — a regular check-in from malware to its C2 server.
  • Pluggable transport — a plugin that disguises Tor traffic so it looks like normal web traffic.

Where it fits in the attack chain

This technique lives in the Command and Control tactic. It usually starts after the attacker has a foothold. First comes initial access, often phishing. Then execution and persistence on the endpoint. The multi-hop chain then carries the implant's beacon out.

After the channel works, attackers move further. They steal credentials, move sideways to other hosts, and collect data. The same chain can carry stolen data out. Ransomware groups also use onion sites for victim negotiation and leak pages.

Why detection is hard

Your firewall only sees the first relay. Tor has thousands of relays, and the client picks new ones on its own. ORB hops are rented servers or stolen devices, so blocking one address achieves little.

The hidden hops also cross networks you do not own. A relay in another country will never send you logs. That is why endpoint signals and traffic patterns matter more than destination addresses.

Why it still matters

The chain is not invisible. Relay lists are public and change on a schedule. Relay tools leave traces on endpoints. Onion addresses and odd protocols sometimes leak into logs.

Every later attack step depends on this channel. Catching the first beacon gives you days of lead time and breaks the attack at its cheapest point. This page turns those small signals into reliable detections.

Written story: the same eight steps in words

This text version is the text alternative for the animation above. It covers the same eight steps. Hover or tap any node in the diagram for a short description.

  1. The rented first hop. The attacker rents a cheap VPS from a cloud provider. They install a port-redirector tool on it. The server becomes hop 1. Nothing about it looks special. Defender view: nothing on your network yet. The rental is invisible to you.
  2. The compromised second hop. The attacker scans for an old router at a branch office and gets in. They install custom firmware code on the router. The router becomes hop 2 and joins an ORB relay network. Defender view: still nothing. The router vendor never tells you.
  3. The implant lands. A phishing email reaches a finance workstation. The user opens the attachment and the implant installs. Its configuration holds the VPS address of hop 1. Defender view: the mail gateway may log the attachment. The install itself is silent.
  4. The first hop — the only one you see. The implant beacons out. The firewall forwards the connection to the VPS on port 443. This is the last hop before your network boundary, and the only relay your logs can identify. Defender view: one new TLS destination on a rented cloud ASN. Volume is low and steady.
  5. Hidden hops and the ORB. The VPS forwards to the compromised router. The router hands the traffic into a Tor network, which reaches the hidden C2 service. These hops are dashed in the diagram because you cannot see them. Defender view: your egress logs show nothing new after the VPS.
  6. The ICMP variant. Between relay nodes the chain can use ICMP instead of TCP. The C2 commands ride inside ping-like packets. No TCP session appears. Defender view: a small rise in outbound ICMP volume on the WAN link, but no content is visible.
  7. SOC signal and correlation. Two alerts fire close together. First, the workstation beacons on a fixed schedule to a rented-ASN address. Second, EDR flags the implant process that owns the connection. Defender view: process plus pattern on the same host is high confidence. Open a case.
  8. Block, pivot, and hunt. The SOC blocks the VPS address at the firewall. The operator answers by rotating to a new hop 1 within hours. The team starts a hunt for the pattern, not just the IP. Defender view: block the first hop, then hunt for the next one by timing, process, and protocol.
03

Red team perspective: how attackers build the chain

To detect the technique well, you need to know why it is used and how it is set up. This section explains the attacker view for learning and defense only.

When do attackers use multi-hop chains?

They use them once they have a foothold and need a channel back to their operator. The chain appears when direct connections feel risky. A blocked country, a watchful SOC, or a previous takedown all push attackers to relay. Ransomware affiliates also use onion sites later for payments and leak pages.

How do they build the chain?

First they rent one or more virtual private servers. Cheap sign-up and anonymous payment make rentals easy. Then they compromise devices for the rest of the chain: old routers, cameras, or other IoT systems. They install relay tools such as SystemBC, FRP, or simple port redirectors. The last hop is often a Tor hidden service. Some groups add custom code to router firmware so the device itself relays traffic.

Where does the chain run?

Hop 1 is usually a rented server in a big cloud provider. Hop 2 is often a stolen device: an end-of-life router, a smart device, or a home office box. The last hop hides inside Tor or a peer-to-peer network. The mix spreads the chain across many providers and countries, which makes takedowns slow.

Why several hops instead of one?

One hop can be blocked or reported. A chain survives the loss of any single relay. Each hop also adds work for the defender: every extra hop means one more legal request or scan to trace the source. Operators accept slower traffic in exchange for that protection.

Typical setup and variations

A minimal chain has three parts. A relay tool runs on a rented server, and a second relay tool runs on another system. The implant knows the first address. Variations include Tor-only chains, VPN chains, and relay tools chained by hand. The command examples below show the mechanics. They are standard admin tools. Use them only in a lab you own.

Lab only — use only on systems you own. A simple two-relay proxychains config

Attacker mistakes that create detections

  • Reusing one rented VPS across many victims. Defenders link the incidents through that address.
  • Picking relay ports that no business process uses, such as plain TCP 1080 from workstations.
  • Shipping relay tools with weak or default configurations that EDR flags by name.
  • Switching to ICMP transport but sending a steady, machine-like rhythm that stands out in NetFlow.
  • Leaving the compromised router unpatched afterwards, so a researcher finds and reports the whole chain.

Why defenders should study this

Knowing the setup tells you which logs matter. Rental patterns point to egress and ASN analysis. Device compromise points to router logs and firmware monitoring. Tor points to endpoint process events.

Ethics — practice only in your lab

This section exists to help defenders practice. Use these ideas only in a lab you own. Never probe relays, bridges, or other people's systems. Unauthorized scanning is illegal in most countries.

Blue team perspective: what defenders can see

The chain hides the destination, but it does not hide everything. This section maps the official data sources to real log products, shows what normal looks like, and walks through a triage checklist.

ATT&CK data sourceTypical log productsWhat you see there
Network Traffic: Network Connection CreationSysmon Event ID 3, Windows Security 5156, EDR per-process connections, firewall session logsWhich process on which host opened a connection to the first relay.
Network Traffic: Network Traffic ContentZeek ssl.log/http.log, forward proxy logs, TLS inspectionHostnames, TLS fingerprints, onion strings, and relay tool banners.
Network Traffic: Network Traffic FlowNetFlow/IPFIX, Zeek conn.log, firewall byte countsBeacon timing, low steady volume, odd protocols such as heavy ICMP.

What normal looks like

  • Workstations talk to known SaaS and CDN ranges on standard ports.
  • Outbound ICMP is rare and comes from monitoring hosts only.
  • No processes named after relay tools run on standard endpoints.
  • TLS sessions go to destinations your asset list can explain.

What suspicious looks like

  • A fixed daily rhythm to one address on a rented-ASN range.
  • Relay tool names (frpc, frps, gost, iox) in process events.
  • Onion addresses or tor2web-style gateways in proxy or DNS logs.
  • Outbound ICMP from servers, or rising ICMP volume on a WAN link.
  • Workstations reaching Ethereum, Bitcoin, or IPFS ports for no reason.

Triage checklist: from alert to verdict

Work through these steps in order. Each step names the fields to pull and the question to answer.

  1. Confirm the alert data. Pull src_ip, dest_ip, dest_port, and process from the alert. Ask: is the destination on a rented-ASN range or a relay list?
  2. Check the endpoint. In EDR, look at the process tree, image path, and hash of the owning process. Ask: is this a known business application?
  3. Check the timing. Count connections per hour for 24 hours. A fixed rhythm with under 60 seconds of jitter is a beacon signature.
  4. Check the volume. Compare bytes in and out across beacons. Similar small sizes on every session point to C2, not human browsing.
  5. Check the protocol. For ICMP-heavy flows, compare current volume against the 30-day baseline. Ask: which host sends it, and does that host have a reason?
  6. Scope the estate. Search all endpoints for the destination IP, the process name, and the hash. One host means one implant. Several hosts mean a campaign.
  7. Enrich the indicator. Look up the destination in threat feeds and ASN databases. Ask: does any report already link this address or onion string to malware?
  8. Decide the verdict. If process, pattern, and enrichment agree, escalate. If only the network signal fired and the host is clean, keep monitoring for 72 hours.

When to escalate to incident response

  • The beacon continued after the first block, or a new relay address appeared within hours.
  • Two or more hosts show the same relay tool or the same beacon pattern.
  • The extracted onion address or relay address matches a feed entry for a known malware family.
  • A network device shows unexpected firmware changes, new local users, or unknown listening ports.
  • Data volume out of your network rose sharply during the beacon window.

Quick wins this week

  • Turn on full hostname logging on your forward proxy, then test that onion names would appear.
  • Load a relay and exit-node list into your SIEM as a lookup table and schedule a weekly refresh.
  • Add the six Sigma rules from section 5.5 to your detection content and route the severities.
  • Baseline outbound ICMP per host, so the ICMP variant stands out on day one.
  • Write a one-page policy that says who may use Tor and how exceptions are recorded.

The six-step intelligence workflow

  1. Collect. Pull the Tor relay lists weekly and subscribe to two C2 feeds.
  2. Process. Deduplicate, tag with T1090.003, and set expiry dates on every indicator.
  3. Analyze. Join the indicators against 90 days of egress logs and rank the matches.
  4. Apply. Turn confirmed matches into blocks, lookup rows, and new hunt queries.
  5. Review. Check monthly which indicators actually fired and drop the dead ones.
  6. Feed back. Report new relay addresses to your feeds and your ISAC.

How to turn intel into hunts

Run each hypothesis as a scheduled query. Keep the ones that fire, and retire the ones that stay silent for a quarter.

  • Hunt H1 — the rented first hop. Look for workstations that contact the same external address on the same port every day. The address should sit on a hosting or VPS ASN. Expect a short list; tune out your known backup and monitoring services.
  • Hunt H2 — low-and-slow ICMP. Compare per-host outbound ICMP counts against a 30-day baseline. Investigate servers and workstations that exceed their baseline by a factor of five.
  • Hunt H3 — relay tooling in the fleet. Search process events for the relay tool names from rule 2 and rule 3 of section 5.5 across 90 days. Every hit needs an owner and a reason.

Rank 4 is rare but almost impossible to see with endpoint tools alone, which is why it sits high. Rank 6 is real but still uncommon, so it ranks last despite being hard to detect.

5.4 Logs and patterns

Each threat below gets one card. Every card lists the log sources, the pattern, one synthetic example event, and short tuning notes. All examples are written for this guide. They are marked Example — synthetic.

Threat 1 — Tor-based C2 with hidden services

Log sources. Sysmon Event ID 1 (process) and Event ID 3 (network connection), EDR process events, firewall egress logs, Zeek ssl.log.

Pattern. A tor.exe or bundled Tor process starts on a workstation. It opens one long-lived TLS session to a relay IP on port 443. Volume is low and the rhythm is steady.

Example — synthetic · Sysmon Event ID 1, bundled Tor client on a workstation

OriginalFileName=tor.exe
CommandLine="tor.exe --SocksPort 9050 --HiddenServicePort 80 127.0.0.1:8080"

  • Tuning note: expect two or three false positives per month in firms with security researchers.

Threat 2 — SystemBC and FRP-style SOCKS5 chains

Log sources. Sysmon Event ID 1 (process), Windows Security 4688 (process creation), EDR process events, firewall logs for the relay ports.

Pattern. A relay binary such as frpc.exe or a SystemBC module starts and opens an outbound SOCKS5 session. Ports are commonly 1080, 8080, or 443, and the destination is a rented VPS.

Example — synthetic · Windows Security 4688, FRP client starting a relay

  • Tuning note: alert on the pairing of a relay binary name with an external destination, not on the name alone.

Threat 3 — ORB relay networks

Log sources. Linux auditd or EDR process events on IoT and server nodes, Zeek conn.log, NetFlow for long-lived relay sessions, firewall logs.

Pattern. A small relay daemon runs on a device that has no business running it. Known names are ew, frps, iox, nps, and gost. Sessions are long-lived and forward traffic between several partners.

Example — synthetic · Linux auditd process event, relay daemon on an IoT node

exe="/opt/.cache/ew"  pid=4412  ppid=1972  uid=0

  • Tuning note: baseline the software that runs on IoT and network devices; any new binary there deserves a look.
  • Tuning note: watch for relay daemons that restart after reboots, which shows persistence on the node.

Threat 4 — Chained compromised network devices

Log sources. NetFlow/IPFIX on WAN links, Sysmon Event ID 3 for ICMP connections, firewall logs, router syslog and configuration-change logs (TACACS+ or RADIUS accounting).

Pattern. Outbound ICMP from hosts that never ping the internet, or a rising ICMP volume on a WAN link. On the device side, firmware or config changes appear outside a change window.

  • Tuning note: allow ICMP only from named monitoring hosts; everything else is reviewable.
  • Tuning note: store router config backups and diff them daily; the diff is your device-side detector.

Threat 5 — Ransomware and worm C2 via multi-hop

Log sources. Sysmon Event ID 22 (DNS query), proxy logs, EDR process events, firewall logs.

Pattern. A ransomware or worm family reaches its relayed C2. Some families left named traces: WannaCry queried its kill-switch domain before encrypting, and Dridex and Ursnif used relayed C2 with named onion strings.

Example — synthetic · Sysmon Event ID 22, WannaCry kill-switch DNS query
2026-01-12T05:44:59.102Z  SYSMON  EventID=22
Image=C:\Users\jriver\AppData\Local\Temp\mssecsvc.exe
ProcessGuid={4a1c-77f9}
QueryName=iuqerfsodp9ifjaposdfjhgosurijfaewrwergwea.com
QueryStatus=0   QueryResults=;-
Computer=WS-4471   User=HQ\jriver
  • Tuning note: keep the named indicators of old worm families; they still catch unpatched and IoT-adjacent estates.
  • Tuning note: a kill-switch query means the payload is already running. Page the on-call team at once.

Threat 6 — Peer-to-peer and blockchain routing

Log sources. Sysmon Event ID 3 (network connection), firewall logs, NetFlow, EDR process events.

Pattern. A workstation opens peer connections on ports used by cryptocurrency or file-sharing networks (Ethereum 30303, Bitcoin 8333, IPFS 4001 and 5001). No relay server appears, because the peers talk to each other.

Example — synthetic · Sysmon Event ID 3, Ethereum peer port from a workstation
2026-01-12T06:05:22.415Z  SYSMON  EventID=3

SourceIp=10.20.9.17   DestinationIp=198.51.100.205   DestinationPort=30303
ProcessId=0x12f0   Computer=WS-2210
  • Tuning note: check the owning process first; miners and C2 implants both use these ports.
  • Tuning note: keep an allowlist for sanctioned research machines so the alert stays small.

Case study: The Onion Backbone

This case is composite and fictional, but the tradecraft is real. It combines patterns that incident reports describe again and again: relayed C2, a leak site, and a late detection.

Note — how to read this case

The company and the people are invented. The goal is to show where detection happened, what was missed before it, and which controls changed afterwards.

Context

Nordhelm Components is a mid-size industrial manufacturer with 1,800 staff across three sites. The security posture at the start was weak. The firewall ran default policies. EDR covered servers but only some laptops. No relay or Tor blocking existed, and no policy mentioned Tor. An affiliate of a ransomware brand buys access to Nordhelm and deploys an implant that keeps its C2 behind three relays.

How detection happened

Rule 2 from section 5.5 fired first: a relay binary with a config file on WS-4471. A scheduled beacon query added the timing signal on the same host. Together they beat either signal alone, because each had been seen and dismissed earlier in the incident.

The extracted onion string then matched a feed entry. That match moved the case from policy review to full incident response.

Containment, eradication, recovery

Containment. EDR isolation on all four hosts, the VPN account disabled, temporary blocks for the VPS and the onion address.

Eradication. Relay modules and implants removed, run keys cleaned, the router re-imaged with vendor firmware, and every touched credential rotated.

Recovery. The file server restored from backup. Downtime stayed under two days for one site, and monitoring stayed elevated for 30 days.

Impact and business consequences

Operational. One site ran on manual processes for two days. The order-desk queue grew by 900 orders before recovery finished.

Data. A small folder of drawings appeared on the leak site. Legal worked with the hosting provider to limit the spread.

Cost. About 210 person-hours for response, plus overtime and one hardware refresh. No ransom was paid.

Business consequences. Two customers asked for written assurances, one audit was moved forward, and the security roadmap gained funding it had lacked for a year.

Tools used on both sides

Attacker tools. The attacker used a phishing kit and an implant with a bundled relay module. FRP ran on the rented VPS. The branch router carried custom firmware code. The last hop was a Tor hidden service.

Defender tools. Defenders used EDR for process events and isolation. Sysmon covered Event IDs 1, 3, and 22. The SIEM ran the six rules from 5.5. NetFlow watched the WAN links, and a feed matched the onion string.

Lessons learned

  • Pair the signals. The relay tool event and the beacon timing were each seen and dropped. The correlation rule caught what two humans missed.
  • Watch the edge devices. The branch router relayed for days in silence. Config diffs and firmware monitoring would have exposed it.
  • Define a relay policy. The day-3 guess happened because no policy existed. With an exception list, the same observation becomes a phone call.
  • Monitor leak sites. The company name appeared there before internal detection. A daily check would have started response earlier.
  • Plan for rotation. Blocking hop 1 moved the attacker to a new address within hours. Pattern-based hunts must be ready before the block goes in.

Mitigation and defense

You cannot block every relay, but you can make the chain expensive for the attacker and visible to you. This section starts with the official mitigation, then layers prevention, detection, and response.

Official MITRE mitigation

MITRE lists one mitigation for T1090.003: M1037 — Filter Network Traffic — filtering traffic by protocol, port, or destination. Beyond this official list, practitioners also rely on the layered controls below.

LayerControlHow it helps
Network segmentationSplit user, server, and management zones with default-deny rules between them.A relay on a workstation cannot reach management interfaces or the cardholder zone.
Egress filtering and allow-listsPermit outbound traffic only to approved categories; deny hosting and anonymizer ranges.Rented VPS relays and onion gateways fail the allow-list before they connect.
DNS filteringResolve names through a filtered resolver with anonymizer categories denied.Onion gateways and known relay domains stop resolving on managed devices.
Web proxy and TLS inspectionRoute web traffic through a proxy that records full hostnames; inspect where policy allows.Relay URLs and onion strings appear in logs instead of hiding in TLS.
Intrusion preventionRun IPS signatures for tunneling and relay protocols at the boundary.Common relay handshakes are flagged even when the destination is new.
Block Tor and tunnel providersDeny relay lists and known tunnel-provider ranges; refresh the lists weekly.Removes the easiest relays and forces attackers onto costlier setups.
Harden network devicesDisable unused services, require MFA for admin access, and log configuration changes.Routers stop being free relay nodes, and changes leave evidence.
Asset inventoryKeep a live inventory of endpoints, servers, and edge devices with owners.Unknown devices, the raw material of ORB chains, stand out quickly.
Patch edge devicesUpdate router and appliance firmware on a schedule; replace end-of-life gear.Closes the entry point that makes hop 2 possible at all.

Detective controls

Prevention reduces the traffic; detection catches what remains. Keep the log pipeline complete first: proxy hostnames, firewall sessions, NetFlow, and Sysmon events 1, 3, and 22. Then deploy the six Sigma rules from section 5.5 and route their severities. Finally, run alert triage with the checklist in section 4, and review rule volumes monthly.

Enterprise actions in the first quarter

  • Publish a relay and Tor exception policy with named approvers.
  • Load relay lists into the SIEM as scheduled lookups.
  • Add device configuration diffs to daily review.
  • Baseline per-host ICMP and peer-port usage.
  • Test the egress blocks from a lab host and record the result.

Home and remote workers

Home networks are hop-2 territory for attackers. Give remote staff this short list.

  • Install router firmware updates within a week of release, and replace gear the vendor no longer supports.
  • Turn off port forwarding; use a mesh VPN to reach the office instead.
  • Use a reputable VPN service at home and keep reputable antivirus enabled.
  • Enable a DNS filter that blocks anonymizer categories for the whole household.
  • Keep work devices on a separate profile or SSID from smart-home gadgets.
  • Report anything odd through the normal channel: unknown processes, sudden slowdowns, or router reboots.
Good practice

Make the reporting path one click or one message. Reports that are easy to send arrive earlier.

Cheat sheet

The whole page in one screen: key facts, the top detections, a response checklist, and links for going deeper.

Key facts at a glance

TechniqueT1090.003 — Multi-hop Proxy (child of T1090 — Proxy)
TacticCommand and Control
PlatformsESXi, Linux, macOS, Network Devices, Windows
IdeaChain several relays so the source of the traffic is hard to trace
Visible to youThe first relay address, the relay process on the endpoint, and leaked onion strings
Invisible to youEvery hop after the first relay, and the content inside the tunnel
First checksRelay-list egress match, relay process on the host, beacon timing, ICMP baseline
Golden ruleCorrelate process plus network plus pattern. One signal alone is a guess.

Top detections

  • Rule 1 — Tor client or pluggable transport process (section 5.5).
  • Rule 2 — SOCKS5 relay tooling such as SystemBC and FRP (section 5.5).
  • Rule 3 — ORB relay daemons on Linux and IoT nodes (section 5.5).
  • Rule 4 — Outbound ICMP to external hosts (section 5.5).
  • Rule 5 — WannaCry-style worm C2 lookups (section 5.5).
  • Rule 6 — Peer-to-peer and blockchain relay ports (section 5.5).

Response checklist

  • Confirm the relay-list match against the current list file, and note the list date.
  • Confirm the relay or transport process event on the same host.
  • Isolate the host with EDR. Do not power it off.
  • Push temporary blocks for the relay address and any extracted onion string.
  • Extract relay addresses and the onion string from the implant configuration.
  • Check the indicators against threat feeds and leak-site trackers.
  • Hunt the fleet for the indicators over the last 90 days.
  • Eradicate, rotate credentials, then tune rules and update the exception policy.

If you only remember one thing

Your logs can only see the first relay. Even so, the chain leaves three traces. There is a relay process on the endpoint, a repeating pattern in egress traffic, and sometimes an onion string in a log. Watch all three and correlate them. Then the chain stops being invisible.
