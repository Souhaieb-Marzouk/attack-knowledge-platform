DETECTION GUIDE · T1090.004 · COMMAND AND CONTROL

T1090.004 — Domain Fronting

Domain fronting hides the real destination of HTTPS traffic inside a trusted content delivery network (CDN). The encrypted outer layer shows the CDN’s name. A hidden inner value points to the attacker’s server behind the same CDN. This guide explains the trick, shows it step by step, and gives you six ready-to-use detections.

✓ Guide v2.0 · audited against ATT&CK v20.0

  • Sub-technique of T1090 (Proxy)
  • Tactic: Command and Control
  • Platforms: Linux, macOS, Windows, ESXi
  • ATT&CK version 1.2 · modified 2025-10-24

What it is

The TLS handshake names a trusted CDN (the SNI value). The HTTP Host header inside the tunnel names the attacker’s zone on the same CDN. The CDN routes the request to the attacker.

Official mitigation

MITRE lists one mitigation for this technique: SSL/TLS Inspection (M1021). It is the only network control that can read both names.

Why it matters

Egress rules that trust big CDNs by name or IP become a hidden path to attacker servers. The path looks like normal business traffic.

How to catch it

Compare the TLS SNI value with the HTTP Host header. You need TLS inspection or an endpoint agent. Then check both values against your app inventory.

What is domain fronting?

A content delivery network (CDN) is a group of servers, rented by many companies, that serves websites and downloads fast. Networks see CDN traffic all day. Because of that, they often trust it.

When a program opens an HTTPS connection, the TLS handshake carries a clear-text field called SNI (Server Name Indication). It names the site the client wants to reach. Inside the encrypted tunnel, the first HTTP request carries the Host header. It names the site again.

Domain fronting puts a different name in each field. The SNI value names the trusted CDN. The Host header names a hidden zone that the attacker registered behind the same CDN. After the CDN removes the TLS layer, it reads the Host header and forwards the request to the attacker’s server. MITRE describes exactly this abuse of CDN routing to hide the true HTTPS destination.

Key words in this guide

  • C2Command and control. The channel an attacker uses to send commands to malware and receive stolen data.
  • CDNContent delivery network. Rented servers that host many companies’ websites on shared names and IP addresses.
  • SNIServer Name Indication. The domain name shown in the clear during a TLS handshake.
  • Host headerThe domain name inside the first HTTP request, protected by TLS.
  • TLSTransport Layer Security. The encryption that protects HTTPS traffic.
  • TLS inspectionA proxy that briefly opens encrypted sessions, records them, and encrypts them again.
  • EgressTraffic that leaves your network towards the internet.
  • BeaconA small, regular check-in message from malware to its C2 server.

Where it fits in an attack chain

Fronting is a Command and Control trick. It needs a foothold first. It usually sits in the middle of a chain, like this:

  1. Initial access — a phishing message or an exposed service delivers the implant (for example T1566.001).
  2. Execution and persistence — the implant runs and survives restarts (for example T1204.002, T1543.003).
  3. Command and control — T1090.004 Domain Fronting. The implant beacons through a trusted CDN (often with T1071.001 Web Protocols).
  4. Lateral movement — stolen credentials open other systems (for example T1021.001).
  5. Objective — the same trusted-looking channel carries stolen data out (for example T1041).

Why detection is hard — and why it matters

Hard: the Host header never leaves the TLS tunnel in plain text. A firewall sees only “trusted CDN, port 443”. The two names sit in different layers, so you must join two records, or inspect TLS, to compare them. A “domainless” variant even leaves the SNI field empty, so there is no clear name at all.

Matters: many organizations allow egress to big CDNs because their own apps need them. Fronting turns that permission into a hidden path to the attacker. Classic allowlists by domain or IP cannot see the difference. Catching this pattern stops an active intrusion that is already stealing data.

Written story: the same eight steps in words

This text says the same thing as the animation. Screen readers and printers can use it instead.

  1. Setting the stage. The attacker registers an app behind a popular CDN. The app shares the CDN’s trusted name and IP space. A hidden zone inside the app points to the attacker’s server. Defender view: your allowlist already trusts this CDN, so nothing looks wrong yet.
  2. Crafting the trick. The attacker configures the implant with two names. The TLS SNI value names the trusted CDN. The HTTP Host header names the hidden zone on the same CDN. Defender view: only a tool that reads inside TLS can ever see both names.
  3. The blind pass. The implant connects to the CDN through your firewall. The firewall sees the clear SNI value and it is trusted, so the session passes. Defender view: sensors see “trusted CDN, port 443”. This is the blind spot.
  4. The relay inside. The CDN edge removes the TLS layer. It reads the Host header and forwards the request to the attacker’s server. The CDN becomes an unwilling relay. Defender view: none of this crosses your network, so your logs stay empty.
  5. Beacon complete. Commands come back through the same path. Stolen data goes out as small, regular HTTPS uploads. Defender view: logs show only harmless-looking CDN traffic with a steady rhythm.
  6. Blank-SNI variant. The attacker switches to “domainless” fronting. The implant sends TLS with an empty SNI field but keeps the Host header. Some CDNs still route it. Defender view: there is no clear name left to judge, so name-based rules go quiet.
  7. Turning on the light. The SOC deploys TLS inspection at the web proxy. A rule now compares SNI and Host on every session. It fires on the mismatch and also flags sessions with an empty SNI. Defender view: the two names finally meet, and they do not match.
  8. Response and adaptation. The analyst blocks the hidden zone at the CDN vendor and at your proxy. A hunt finds two more infected hosts. The rules are generic, so they keep working when the attacker moves to a new provider. Defender view: detect the shape, not the brand.

Red team perspective

Why attackers use this trick and how it works. The goal is defensive: if you know the shape of the attack, you can build the right detections.

Why do attackers use it?

The front borrows the reputation of a big CDN. Millions of people use that CDN every day, so one more HTTPS session is noise. Egress rules that permit “the big CDNs” by name or IP range also permit the attacker’s channel. The real server stays hidden behind the provider, so blocking it needs the provider’s help.

When do they use it?

Fronting needs an implant first, so it appears after initial access. Attackers use it for the C2 channel, for tool downloads, and for sending stolen data out. It is most valuable in networks with strict egress rules, because one trusted name opens a hole in a tight policy.

How do they set it up?

First they register an app, a bucket, or a custom domain behind a CDN that does not check that SNI and Host match. Then they configure the implant with two values: the front name for TLS SNI, and the hidden name for the HTTP Host header. Public C2 frameworks make this easy. Cobalt Strike loads the two values from a Malleable C2 profile. Mythic agents and HTTP profiles can do the same.

Where does it appear?

Anywhere HTTPS egress is allowed and TLS is not inspected: office networks, VPN exits, and cloud workloads. After 2018, the big providers blocked classic fronting, so attackers moved to smaller CDNs, SaaS endpoints, and special transports. Tor’s meek bridge uses the same fronting idea to beat censorship.

Prerequisites and variations

What the attacker needs

  • ProviderA CDN or SaaS endpoint that routes by the Host header without checking it against the SNI value.
  • AccountAn app or bucket registered behind that CDN, so a hidden zone exists to route to.
  • Implant configTwo hard-coded values, or one fetched at runtime: SNI = front, Host = hidden.
  • Victim networkAn egress policy that allows the CDN by name or IP, with no TLS inspection.

Common variations

  • Classic fronting — different names in SNI and Host on the same CDN.
  • “Domainless” fronting — an empty SNI field. MITRE documents this variant. It can pass providers that try to match SNI and Host but ignore a blank SNI.
  • SaaS fronting — the front is a software-as-a-service endpoint. Tenant traffic and attacker traffic share the provider’s names.
  • meek-style transport — Tor traffic relayed through requests to big web platforms.

Safe lab demonstration of the SNI/Host split

You can show the mechanism on one machine you own. Both names point to your local server. The TLS layer always carries the front name. Only the Host header changes. A real sensor without TLS inspection would log both connections the same way.

Ethics — lab use only

This section exists to help defenders practice. Use these ideas only in a lab you own. Setting up fronting against real providers breaks their terms of service and supports covert access.

Attacker mistakes that create detections

  • Reused zoneThe same hidden domain across many victims becomes a stable indicator you can share.
  • Wrong TLS fingerprintJA3/JA4 are short hashes of the TLS handshake options. Malware libraries look different from real browsers, even when the names match.
  • Machine rhythmFixed intervals and near-constant sizes stand out against human browsing, even inside trusted CDN traffic.
  • Provider visibilityThe CDN provider sees the hidden Host value in plain text and can act on an abuse report.
  • Config leftoversFront values shipped in old implants keep beaconing long after providers change their routing.
4

Blue team perspective

What the trick leaves behind, where those traces live, and how to work an alert from first look to verdict.

Where to look first

  • TLS proxy logsBest source. Records with both tls_sni and http_host per session (Network Traffic: Network Traffic Content).
  • Zeek logsZeek is an open-source network monitor. Join ssl.log (SNI) with http.log (Host) on the connection uid.
  • EDR network eventsEndpoint Detection and Response tools log process-to-destination connections (Network Connection Creation). Some agents log the SNI value.
  • Firewall / NetFlowConnection records (Network Traffic Flow). Good for volume and history. Blind to the Host header.
  • DNS logsResolve hidden domains from the edge. Useful for pivoting once you have a name.

Normal vs suspicious

  • NormalSNI and Host match. Both names come from your approved app-to-CDN inventory. Browsing is irregular in size and time.
  • SuspiciousSNI names a big CDN while Host names an unrelated or fresh zone. Or SNI is empty on port 443. Or one host talks only to CDNs, at a machine rhythm, hour after hour.
  • Verdict question“Does any approved application use this exact pair of names?” If not, treat the session as hostile until proven safe.

Triage checklist for a mismatch or blank-SNI alert

  1. Confirm the sensor recorded both values: tls_sni and http_host for the same session. Note the connection ID, source IP, and timestamp.
  2. Check the pair against your app-to-CDN inventory. Ask: does any approved app use this Host zone?
  3. Research the hidden domain: registration date, registrar, reputation feeds, passive DNS. A zone registered days ago is a strong signal.
  4. Pivot in the SIEM: find every host that used the same pair or resolved the hidden domain in the last 30 days.
  5. Go to the endpoint: identify the process, the user, the parent process, and any persistence (services, scheduled tasks).
  6. Measure the impact: sum the bytes out per host. Large steady uploads mean data left the network.
  7. Decide the verdict with two questions: is the Host zone on the inventory, and is the process expected on this host? If both answers are no, escalate.
  8. Contain: block the hidden domain at proxy and DNS, isolate confirmed hosts, and report abuse to the CDN vendor.

When to escalate to IR

  • The implant process is confirmed, or persistence was found on the host.
  • More than one host used the same name pair.
  • Bytes out exceed your normal upload profile, or a document store was read.
  • The hidden zone appears on a threat feed or has a fresh registration date.
  • Sessions continued after a block, which means the attacker is adapting.

Quick wins this week

  • Turn on Host-header logging on every egress proxy that already inspects TLS.
  • Deploy the mismatch rule (5.5, Rule 1) in monitor mode and review one week of data.
  • Build a first app-to-CDN inventory from proxy logs: top 50 Host values, with owners.
  • Block the documented meek front domains (5.5, Rule 3) at DNS and proxy.
  • Alert on HTTPS sessions with an empty SNI value (5.5, Rule 2).
Warning — the visibility gap

Without TLS inspection or an endpoint agent, most of these patterns are invisible. Firewall and DNS logs alone cannot confirm fronting, because the Host header never leaves the tunnel. Name this gap in your risk register and decide on purpose how to close it.

Six-step intel workflow

  1. Collect — pull ATT&CK citations, vendor reports, and feed indicators into one place.
  2. Process — clean and normalize: one table with front domain, hidden zone, tool, date, source.
  3. Analyze — grade each claim by confidence and date. Provider behavior changed sharply in 2018, so old claims need re-checking.
  4. Apply — load the table into lookups and rules: front_domains.csv, the app-to-CDN inventory, Sigma list values.
  5. Review — retire stale entries each month and re-test that rules still fire on fresh data.
  6. Feed back — send your confirmed pairs to the ISAC and to the feed maintainers.

How to turn intel into hunts

Three named hypotheses you can run this month:

  1. Hidden-zone inventory check. For every CDN Host value seen in 30 days of proxy logs, ask who owns it. Anything outside the app-to-CDN inventory gets a verdict.
  2. Blank-SNI sweep. Find all HTTPS sessions with an empty SNI value. Split them into known apps and everything else. Investigate the rest.
  3. APT29-shaped beacon hunt. Look for steady-interval, single-URI HTTPS sessions to big CDNs with a user agent that no approved app uses.

5.4 Logs and patterns

Each threat maps to log sources, fields, and logic. All examples are fictional but shaped like real records.

Threat 1 — SNI/Host mismatch to CDN-hosted C2

  • Log sourcesTLS-inspecting proxy; Zeek ssl.log + http.log joined on uid; EDR network events
  • PatternOne session, two names: SNI is a trusted CDN, Host is an unrelated zone. Steady rhythm, one URI, one user agent.
  • TuningA few shared-certificate setups differ on purpose. Baseline two weeks, then filter verified pairs.

Threat 2 — Blank-SNI (“domainless”) fronting

  • Log sourcesTLS proxy session records; Zeek ssl.log (empty server_name) with http.log
  • PatternHTTPS on port 443 with an empty or missing SNI, but a Host header exists inside. Rare in normal estates.
  • TuningAllow legacy clients and IP-direct tools on purpose. Everything else gets a verdict per host and process.

Threat 3 — meek pluggable transport

  • Log sourcesProxy logs, DNS logs, firewall
  • PatternLong-lived POST sessions to documented meek front endpoints. Near-constant byte sizes.
  • TuningResearch and censorship-measurement teams test meek on purpose. Approve them by name.

Threat 4 — Fronting a trusted big-provider domain

  • Log sourcesTLS proxy with ASN enrichment; EDR network events; DNS logs
  • PatternEgress to a big CDN ASN where the Host zone is a generic app-hosting name that no approved app uses.
  • TuningThe app-to-CDN inventory is the control. Keep it honest, or this rule only makes noise.

Threat 5 — Mythic / SMOKEDHAM-style HTTP C2

  • Log sourcesEDR process network events; TLS proxy; Windows Security 5156
  • PatternA process in a user-writable folder talks to a CDN or cloud app zone, with an agent-like TLS fingerprint and a rare Host.
  • TuningGroup by user and process. Auto-update helpers live in similar paths, so confirm the process owner.

Threat 6 — Exfiltration through fronted domains

  • Log sourcesTLS proxy with byte counts; firewall; DLP summaries
  • PatternLarge POST/PUT uploads to a fronted zone, often at night, from one host, against one URI.
  • TuningSet the byte threshold above your biggest real sync jobs. Review the top 20 senders weekly.

5.5 Sigma rules and Splunk SPL

Each threat gets one Sigma rule and one matching Splunk SPL query. The SPL comment lines start with # and state the index and sourcetype assumptions. If your Splunk version does not accept comment lines, delete them before you run the query. Rule 2 — Blank-SNI (“domainless”) fronting (Threat 2) high

Good practice — honest expectations

A few legitimate CDN setups can show SNI/Host differences, so Rule 1 will never be free of false positives. Deploy it in monitor mode, tune it with the app-to-CDN inventory, and let the pattern, not the brand, carry the verdict.

Case study: The Invisible Channel

A composite story built from public reporting patterns. It is fictional, but every step matches how these incidents really unfold.

Note — realistic composite

This case study is a realistic composite, not one real incident. Company names, hosts, and domains are fictional. The sequence follows documented APT use of domain fronting.

Context

Northwind Circuits designs electronics for industrial customers. Its egress policy is strict by name: most destinations are blocked, but major CDNs and software vendors are allowed, because engineering tools depend on them. Northwind ran no TLS inspection in 2025. The rollout was scheduled for January 2026.

How detection happened

Rule 1 (SNI/Host mismatch, 5.5) fired on the first inspected session. The pair had passed unseen for eight days. The log that fired was the TLS proxy session record, with both tls_sni and http_host in one row. Rule 5 later matched the same host from the endpoint side, because winupd.exe ran from AppData\Roaming. Before T0 + 15 d, no sensor in the company could have seen the Host header at all.

Containment, eradication, recovery

  • Contain: hidden domain blocked at proxy and DNS within two hours; five endpoints isolated the same day; abuse report filed with the CDN vendor.
  • Eradicate: persistence service removed; hosts reimaged from known-good media; all credentials touched by affected users rotated, including VPN tokens.
  • Recover: five clean days confirmed no further beacons; Rule 1 switched to alert mode; the incident pair was added to front_domains.csv and shared through the sector ISAC.

Impact and business consequences

Operational: five hosts rebuilt; the engineering file server offline for one afternoon; two days of release work delayed. Data: two engineering documents found staged; uploads of about 60 MB confirmed; no evidence of completed large-scale exfiltration. Cost: roughly 60 staff-hours of response plus rebuild effort, about the price of a small project. Business: a customer audit asked new questions about egress monitoring, and management added ECH planning to the roadmap. The real cost was eight invisible days, and that was a visibility cost, not a tooling cost.

Lessons learned

  • Inspect TLS where lawful. Eight invisible days ended the moment both names became visible. Pair the rollout with a privacy review and clear exclusions.
  • Never blanket-trust CDNs. A name or IP is not an application. Allowlist by application and verify the Host values your apps really use.
  • Maintain an app-to-CDN inventory. The inventory turned “maybe legitimate” into “not ours” in minutes during triage.
  • Pivot on the hidden name. Endpoint telemetry missed the fifth host. DNS history found it.
  • Plan for ECH. When browsers hide SNI, endpoint agents and inspection points carry the load. Northwind added ECH planning before it became urgent.
  • Report abuse fast. The vendor suspended the zone within one day, which cut the attacker’s infrastructure out of the channel.

Mitigation and defense

Layered controls, from policy to response. No single layer catches fronting alone; the pattern is the target.

Official MITRE mitigation

MITRE lists one official mitigation for T1090.004: SSL/TLS Inspection (M1021). It decrypts TLS sessions at a controlled point, so the SNI value and the Host header can both be read. Everything below this box is practitioner advice, added on top of the official list.

Detective controls and enterprise actions

Detective controls

  • Log pipeline: keep proxy logs with tls_sni and http_host for at least 12 months.
  • Sigma deployment: run the six rules from 5.5; start in monitor mode, then alert.
  • Alert triage: use the Section 4 checklist; record a verdict per name pair.

Enterprise actions

  • Replace IP-based CDN allowlists with application-based rules.
  • Put MFA on CDN and SaaS admin consoles, and track who can register custom domains.
  • Alert when a new zone is added to a company CDN account.
  • Move remote and admin egress to a ZTNA broker (access to specific apps, not open egress).

Home and remote worker

Households rarely run TLS inspection, and they should not start with it. These steps still cut the risk:

  • Update router firmware promptly and change the default admin password.
  • Do not forward ports from the internet to home devices.
  • Use a reputable VPN and reputable antivirus on work devices.
  • Use a DNS filter that blocks known-malicious domains.
  • Keep work and personal activities on separate devices or profiles.
  • Report anything strange to IT with the time and the device, using the short checklist: what happened, when, which app, any warning shown.

Common mistakes

Twelve failure patterns seen in real programs. Each one has a symptom, a root cause, a fix, and a prevention habit.

MistakeSymptomRoot causeFixPrevention
Blanket allowlists for big CDN domains Any host can reach anything on those names or ranges. Rules written per name or IP range, not per application. Rebuild the rules per application with SNI/Host conditions. Quarterly rule review against the app-to-CDN inventory.
No TLS inspection anywhere Zero Host visibility; fronted C2 is invisible in logs. Privacy concerns unresolved, or performance fears never tested. Scoped egress inspection with a privacy review and exclusions. Classify what may stay encrypted; log SNI everywhere else.
IP-only CDN rules Rules break or drift as the CDN changes address ranges. CDNs run huge shared ranges that move constantly. Match on names (SNI/Host) plus ASN, not fixed IPs. Retire IP pinning; automate ASN references from a lookup.
Assuming fronting died in 2018 No monitoring for the pattern; no rules deployed. One headline read as permanent truth. Re-enable the detection set from section 5.5. Track ATT&CK and vendor reporting on the technique family.
Host header not logged Proxy records show SNI but no http_host field. Default logging was never extended. Enable Host capture on every egress proxy. Log-source checklist that requires both fields before onboarding.
No SNI/Host correlation Both fields exist but are never compared. No normalized pipeline field for the comparison. Add the sni_host_mismatch derived field and alert on it. Detection engineering review for every new log source.
Mismatch rule deployed without tuning False-positive storm; analysts stop trusting the alert. Legitimate shared-certificate setups were never baselined. Two-week monitor period; filter verified pairs; then alert. Monitor-mode rollout standard, with a false-positive budget per rule.
No app-to-CDN inventory Every CDN alert is “maybe legitimate” and dies in triage. Nobody owns the list. Build the inventory from proxy logs plus vendor documentation. Named owner; quarterly review; changes only through tickets.
Blank-SNI traffic never reviewed The domainless variant passes unnoticed forever. Nobody knows whether any legitimate client omits SNI. Run Rule 2 for two weeks; give every source host an owner. Annual re-check, because new tools appear.
Ignoring ECH rollout plans SNI visibility disappears for browsers; rules go quiet. No roadmap for the protocol change. Plan endpoint-agent and DNS-layer detections now. Track browser and CDN ECH adoption in the tech watch.
No privacy or legal review before inspecting TLS Project blocked late, or deployed unlawfully. Inspection touches personal data and regulated categories. Privacy assessment, exclusions (health, banking), retention limits. Standing review step in the inspection project plan.
Watching inbound only Egress anomalies never reviewed; fronting never considered. Mindset focused on perimeter entry. Add egress detections and a weekly egress review. ATT&CK coverage mapping that includes Command and Control.

Cheat sheet

The whole page in one screen: facts, detections, response steps, and links.

Key facts

  • TechniqueT1090.004 — Domain Fronting (parent T1090 Proxy; tactic: Command and Control)
  • PlatformsLinux, macOS, Windows, ESXi
  • Core patternTLS SNI names a trusted CDN; the HTTP Host header inside names the attacker’s zone on the same CDN. A blank SNI variant also exists.
  • Catches itSNI-vs-Host comparison at a TLS-inspecting proxy, or an endpoint agent
  • Blind withoutFirewall and DNS logs alone cannot confirm it
  • First checksIs http_host logged next to tls_sni? Do both values appear for the session? Is the Host zone on the app-to-CDN inventory?
  • Official mitigationSSL/TLS Inspection (M1021)

Top detections (from 5.5)

  • Rule 1 — SNI/Host mismatch on TLS sessions (critical, TLS proxy).
  • Rule 2 — blank SNI with a Host header, “domainless” fronting (high, TLS proxy).
  • Rule 3 — documented meek front endpoints (high, proxy).
  • Rule 4 — CDN ASN with a Host outside the inventory (high, proxy + ASN).
  • Rule 5 — user-writable process to a CDN app zone (medium, EDR).
  • Rule 6 — large uploads to fronted zones (high, proxy + bytes).

Response checklist

  • Confirm the sensor recorded both SNI and Host for the session.
  • Verify the name pair against the app-to-CDN inventory.
  • Check the registration date and reputation of the hidden domain.
  • Find every host that used the pair or resolved the domain.
  • Isolate confirmed hosts; identify the process and persistence.
  • Block the hidden zone at proxy and DNS; report abuse to the vendor.
  • Add the pair to front_domains.csv and your hunting lists.
  • Preserve logs; note any visibility gap that blocked a step.
