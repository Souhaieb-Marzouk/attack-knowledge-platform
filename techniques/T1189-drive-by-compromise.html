T1189 – Drive-by Compromise

🎯Tactic: Initial Access 💻Platforms: Windows · macOS · Linux · Identity Provider 🧩Complexity: Medium 🔎Detection difficulty: High 📊Technique version: 1.7

A drive-by compromise starts with something completely normal: a person opens a website. No email arrives. No download button is clicked. While the page loads, hidden code on the site quietly checks the visitor's browser. If it finds a weak point — an old browser build, a risky plugin, a missing patch — it attacks in silence. Seconds later the visitor's computer runs code chosen by the attacker, and the user noticed nothing. The malicious site can be one the attacker owns, a trusted site that was secretly hacked (a watering hole), or even a paid advertisement (malvertising). This makes T1189 one of the quietest ways into a network. In 2012 the Elderwood group made it famous: they hacked websites popular with defense and aerospace workers, planted hidden iframes (tiny invisible page windows), and waited for victims to simply browse. This guide explains the attack in plain words, walks through a real case, and gives you ten detection rules you can tune and deploy.

Think like the attacker

Red Team / Hacker Perspective

When attackers use this

Attackers use drive-by compromise when they want access without a user mistake. Phishing needs a click. A drive-by only needs a visit. That is why spyware teams like it: the victim just does their normal job — reading industry news, checking a supplier portal — and the infection happens in the background.

Timing matters. Watering-hole attackers first learn where their targets browse, then hack or rent that web space, and then wait. The attack can sit on the site for days and only serve chosen visitors: by country, by IP range, by browser build, even by time of day. Malvertising attackers move faster. They buy an ad placement, aim it at the audience they want, and let the ad network do the delivery.

How attackers do it, step by step

  1. Choose the audience. The team picks a group of people (an industry, a government, a region) and studies which websites they trust and visit often.
  2. Get control of web space. They hack a popular site, change a shared script or cloud storage file that the site loads, or buy malicious ads through a real ad network (T1583.008 Malvertising).
  3. Plant the hook. A hidden iframe — a tiny invisible window inside the page — or a changed script tag now points at attacker infrastructure. Visitors see no difference.
  4. Stand up the gate. A gate is a filter page on attacker infrastructure. It records the visitor's browser build, plugins, language and screen, and checks that the visitor does not look like a security researcher.
  5. Pick the exploit. The gate matches the fingerprint to a known browser or plugin weakness and chooses the exploit for that exact hole. Modern attackers may instead show a fake update page that tricks the user into running an "update".
  6. Deliver the payload. The exploit runs in the browser's memory. A dropper file is written to a temp folder and executed, or a script downloader pulls the next stage.
  7. Call home. The new implant opens a command and control (C2) channel, often HTTPS to a freshly registered domain or a raw IP address.
  8. Expand. From that one workstation the attacker harvests credentials, moves to other systems, and works toward the real goal — espionage, ransomware or fraud.

Where it works best

🏭Tight communities

Industries with a few big news sites and forums are ideal. One hacked site can reach many valuable victims at once.

🕰️Unpatched estates

Old browser builds and forgotten plugins turn a decent exploit into a reliable one. Legacy plugin attacks (Java, Flash) were the classic example.

🌐High-traffic ad slots

Malvertising buys reach instantly. One ad impression is enough, and the ad network adds trust the attacker never earned.

🧭Predictable users

Staff who visit the same five sites every morning are easy to target with a watering hole, even when their mail is locked down.

Why attackers like this technique

  • No user mistake needed. Security awareness training does not stop a hidden iframe.
  • Reusable infrastructure. One gate plus one exploit pack serves many victims; the attacker only changes the fingerprint rules.
  • Selector control. The attacker decides who gets served — by network, browser, language or referrer — which keeps the campaign small and quiet.
  • Trust inheritance. A hacked legitimate site or a paid ad arrives with reputation the attacker could never build alone.
  • Fast setup with kits. An exploit kit is a ready-made package that serves exploits to visitors. Historical kits (Blackhole, RIG, SUNDOWN, Neutrino) and modern fake-update kits made this technique work almost like a rented service.

What attackers need first

  • A place on the web the targets already visit — a hacked site, a shared script it loads, or paid ad space.
  • At least one working browser or plugin exploit, or a convincing fake update lure.
  • A gate or fingerprinting script to sort real victims from scanners and researchers.
  • Staging infrastructure: fresh domains, rotating DNS, or cloud buckets that hold the payload.
  • A C2 plan — where the implant reports and how the operator reaches it.
  • Patience: watering holes can run for weeks before the first victim matches the selector.

Tools and example commands

Defenders and authorized testers study this technique with browser-posture and simulation tools. BeEF (Browser Exploitation Framework) shows how much a web page can learn about a browser, and how a hooked browser can be steered — run it only on machines you own. Metasploit ships a browser_autopwn2 module that serves a range of browser tests, which is a good way to check whether your proxy (the server that forwards all web traffic) and your EDR (endpoint detection and response — software that watches what programs do on a computer) raise alerts on kit-like patterns. Ordinary HTTP tooling is enough to study redirect chains. The commands below are for a private lab with written permission:

beef-lab.sh — browser posture lab
# Authorized lab only: start BeEF and study what a page can learn
# about browsers that visit it (use your own test VM and network).
cd /opt/beef && ./beef
autopwn-lab.sh — isolated kit pattern
# Isolated lab only: serve browser test pages the way an exploit kit
# would, then confirm proxy, DNS and EDR raise the expected signals.
msfconsole -q -x "use auxiliary/server/browser_autopwn2; set SRVHOST 10.10.10.10; set LHOST 10.10.10.10; run"
chain-check.sh — follow a redirect chain
# Count the hops a suspicious ad-style link takes before it lands.
# Run this only against domains you own or are authorized to test.
curl -sIL --max-redirs 8 "https://lab.internal.test/landing" | grep -Ei "^(HTTP|location)"
Ethics and the law

Everything in this section is for learning and defense. Running exploit code, hooking browsers or serving fake updates against systems you do not own is a crime in most countries under computer misuse and unauthorized access laws. Test only in your own lab or with written permission, keep the range isolated from real users, and share findings with the site or team that is affected.

Think like the defender

Blue Team / SOC Perspective

What defenders can see

A drive-by compromise is silent for the user, but not for the telemetry. The attack needs three things, and each one leaves traces. The browser must fetch attacker content (network logs). The exploit must break into the browser's memory (crash and process logs). The implant must talk to its operator (more network logs). No single log tells the whole story — the power is in the join.

The strongest single signal is a browser process spawning something. Chrome, Edge or Firefox should never launch cmd.exe, mshta.exe or an unknown executable. The second strongest is an unexpected fetch chain: a request to a trusted page followed, within seconds, by calls to a never-seen domain or a raw IP address. The third is temp-folder activity: new executables appearing under the user's profile right after a browsing session.

Where to look

  • Proxy and web-filter logs — keep full URL and referrer (the page that sent the visitor), not just the domain.
  • Sysmon (a free Microsoft add-on that logs detailed endpoint events): EID 1 (process), EID 3 (network) and EID 11 (file write), with EID 11 joined to EID 1 by file name and time.
  • Zeek logs (Zeek is a network sensor that records connections) — http.log, dns.log and conn.log — for the fetch chain and the beacon rhythm.
  • Windows Application error and WER records for browser crashes around the visit time.
  • EDR alerts on process ancestry (which program started which), unsigned modules loaded into the browser, and temp-folder writes.
  • Identity provider logs for what happened after compromise: consents, tokens, new sign-ins.

Why this matters to the SOC

One visited page can become one owned machine, and one owned machine can become a full network intrusion. The blast radius — how far the damage spreads — is the whole company, because the entry point is an ordinary workstation with ordinary user rights. Drive-by attacks also bypass the controls many organizations trust most: the mail gateway never saw anything, and awareness training was never tested. The attacker gains what phishing gives them, without the phishing. That is why detection has to come from correlation — network plus endpoint — rather than from one silver-bullet alert.

There is also a second, often forgotten target: your own web estate. If attackers can turn your site into a watering hole, you become part of someone else's intrusion chain. Watch your public sites for unexpected file changes and unexpected third-party scripts, and keep the publishing pipeline locked down.

Where it fits in the attack chain

Before: the attacker prepares delivery with T1583.008 Malvertising (buying ad space) or T1608.004 Drive-by Target (staging the exploit content). It may also take over the site itself with T1190 Exploit Public-Facing Application. After: the implant typically continues with T1059 Command and Scripting Interpreter or direct execution, T1071 Application Layer Protocol for C2, persistence such as T1547 Boot or Logon Autostart, and T1003 OS Credential Dumping before lateral movement (moving from one machine to others inside the network). A drive-by can also end in a fake-update lure that still needs T1204 User Execution.

5.2 Threat Intelligence

Where threat intel comes from

📰Open source (OSINT)

Vendor blogs (Proofpoint, ESET, Secureworks, Google TAG, Mandiant), CISA advisories, abuse.ch URLhaus and ThreatFox, AlienVault OTX, VirusTotal and Shodan all carry drive-by indicators: gate URLs, fresh domains, dropper hashes.

🎯ATT&CK-based intel

The MITRE pages for T1189 list the groups and software that use it — Elderwood, APT28, APT37, Lazarus, Mustard Tempest, SocGholish and many more — each with procedure notes you can turn into hunt questions.

💳Commercial feeds

Paid feeds add context fast: WHOIS and registration age for fresh domains, active exploit kit URLs, ad-network fraud reports, and scored infrastructure lists you can push into your proxy.

🏠Internal telemetry

Your own proxy, DNS and EDR history is intel too. Which domains did your users never touch before yesterday? Which browser builds run in your fleet? That baseline powers every rule in this guide.

The intel cycle for this technique

  1. Define priorities. Decide which groups and malware families matter for your sector — for example espionage actors that water-hole industry media, or fraud crews that run malvertising.
  2. Collect. Pull indicators and behavior notes from the sources above, plus your own logs for the same time window.
  3. Process. Normalize domains, URLs and hashes; drop expired items; tag each item with the ATT&CK technique it supports.
  4. Analyze. Ask how each campaign would look in your telemetry: which log would catch the gate fetch, the drop, the beacon?
  5. Produce. Turn answers into hunts and detections — exactly the Sigma and SPL pairs in 5.5 — plus blocking rules for the proxy and DNS.
  6. Feedback. Track which indicators fired, which rules were noisy, and feed that back into priorities next cycle.

How to apply intel here

  • Pivot to hunts. Take a reported gate URL or dropper hash and search your proxy and Sysmon history for it — backwards in time, not just forwards.

  • Track the actors' browsers. Actor procedure notes (like RICECURRY fingerprinting) tell you which telemetry matters most for the campaigns you care about.

5.5 Sigma Rules & Splunk SPL

Every rule below pairs with the threat number above: Sigma #1 catches Threat #1, Sigma #2 catches Threat #2, and so on. Each rule has its own UUID, so you can copy them into your repository without collisions. Tune the domain, port and folder lists to your own baseline before you deploy, and always test in a staging index first.

Sigma Rule #1 — Browser Process Runs Executable from User Temp Folder (matches Threat #1)
sigma #1 — sysmon process creation
title: Browser Process Runs Executable from User Temp Folder
id: 3f1c8a52-9d47-4b6e-a2c1-8e5f0b7d3a94
status: stable
description: >
  A browser process spawns a child that runs from a user-writable location.
  This is the classic end of a drive-by chain (T1189): the exploited page
  drops a payload into the temp folder and the browser itself executes it.
  The rule also catches script interpreters spawned directly by the browser.
references:
  - https://attack.mitre.org/techniques/T1189/
  - https://attack.mitre.org/detectionstrategies/DET0176/
author: Detection Guide Team
date: 2026-01-15
tags:
  - attack.initial_access
  - attack.t1189
  - attack.execution
  - attack.t1059
logsource:
  category: process_creation
  product: windows
  service: sysmon
detection:
  selection_browser:
    ParentImage|endswith:
      - '\chrome.exe'
      - '\msedge.exe'
      - '\firefox.exe'
      - '\brave.exe'
      - '\opera.exe'
  selection_temp:
    Image|startswith:
      - 'C:\Users\'
      - 'C:\Temp\'
      - 'C:\Windows\Temp\'
  selection_script:
    Image|endswith:
      - '\cmd.exe'
      - '\powershell.exe'
      - '\mshta.exe'
      - '\wscript.exe'
      - '\cscript.exe'
      - '\rundll32.exe'
  condition: selection_browser and (selection_temp or selection_script)
falsepositives:
  - Developer tools and debugging extensions that start helper processes from user folders.
  - Some password managers and test harnesses spawn children from temp paths.
level: critical
Splunk SPL #1
spl #1 — sysmon process creation
index=sysmon EventCode=1 (ParentImage="*\\chrome.exe" OR ParentImage="*\\msedge.exe" OR ParentImage="*\\firefox.exe" OR ParentImage="*\\brave.exe" OR ParentImage="*\\opera.exe") (Image="C:\\Users\\*" OR Image="C:\\Temp\\*" OR Image="C:\\Windows\\Temp\\*" OR Image="*\\cmd.exe" OR Image="*\\powershell.exe" OR Image="*\\mshta.exe" OR Image="*\\wscript.exe" OR Image="*\\cscript.exe" OR Image="*\\rundll32.exe") | stats count dc(Image) as distinct_children values(Image) as Children values(CommandLine) as CommandLines by Computer, ParentImage, User | sort - count

Learn from a real incident

Real-World Case Study

Operation Elderwood — watering holes against the defense industry (2012)

In September 2012, Symantec published a report called The Elderwood Project. It described a group running one of the most organized watering-hole campaigns ever documented at that time. The same actor platform was already linked to Operation Aurora, the 2009–2010 attacks that hit Google, Adobe and more than twenty other large companies. What made Elderwood special was the method. Instead of sending phishing emails, the group compromised websites that employees of defense and aerospace companies liked to read. Then it simply waited for them to browse.

The recipe stayed the same across many sites. The attackers took control of a web server, injected a hidden iframe or a changed script tag, and pointed it at their own infrastructure. Visitor browsers that passed the fingerprint checks received exploit code. In 2012 the group used several zero-day exploits — including the Internet Explorer flaw CVE-2012-1876 in June of that year — to install backdoors on visitor machines. The intruders then moved laterally inside the victim networks. Researchers also linked the December 2012 compromise of the Council on Foreign Relations website, which served the Internet Explorer zero-day CVE-2012-4792, to the same platform. Public reporting does not document exactly how every site was taken over; weak website software and stolen credentials were the common routes at the time.

How the attack chain worked

  1. Selection. Sites popular with one sector were chosen, so one compromise could reach many valuable victims.
  2. Site takeover. The web server was compromised and a hidden iframe was added to real pages.
  3. Fingerprinting. Visiting browsers were profiled, and only matching visitors were served.
  4. Exploitation. Zero-day exploits for Internet Explorer and plugins ran in the browser.
  5. Installation. A dropper installed a backdoor with code execution on the visitor machine.
  6. Command and control. The backdoor connected out to attacker infrastructure.
  7. Expansion. The intruders moved laterally and collected data, reusing the same tools across sites.

How it was detected

There was no single magic alert in 2012. The campaign came to light through a combination of signals: anti-malware detections on dropped files, unusual outbound connections from workstations, and researcher work on the compromised sites themselves. Researchers found the hidden iframes and traced them back to shared infrastructure. Symantec's value was correlation: many different sites, exploits and backdoors turned out to share one codebase and one delivery platform. That is the same correlation logic this guide builds in Section 5, just with modern telemetry.

Containment

  1. Isolate the affected workstations from the network but keep them powered on for forensics.
  2. Block the C2 domains and IPs at the proxy, DNS resolver and firewall; sinkhole if possible.
  3. Reset credentials for every user who touched the affected machines, starting with privileged accounts.
  4. Revoke and re-issue sessions and tokens, since the implant may have copied them.
  5. Notify the owners of the compromised websites so the iframes can be removed.

Recovery

  1. Rebuild or clean-restore affected endpoints from known-good images.
  2. Patch the exploited browser and plugin flaws across the whole fleet immediately.
  3. Restore blocked domains for legitimate services only after review.
  4. Re-open services gradually while watching the same telemetry that caught the incident.

The concrete damage in Elderwood-era cases was espionage: stolen documents, credentials and email from defense-related organizations. The strategic impact was bigger. The campaign proved that trusted websites could be turned into mass delivery weapons, and it pushed browser vendors toward the sandboxing and rapid patching we rely on today.

Who did what

In a response like this, the SOC L1 triages the malware and connection alerts and opens the case. The L2 analyst joins the proxy, Sysmon and EDR timeline and finds the visited site. The IR lead runs containment and keeps evidence handling clean. Threat intel maps the iframes, hashes and domains to the actor platform and warns peer organizations. Comms and legal handle notifications — including breach notification duties if personal data was exposed — and coordinate with the website owners and, where relevant, law enforcement.

Lessons learned

  • A trusted website is a delivery channel, not a safety guarantee — monitor the fetch chain, not just the domain.
  • The browser is an execution platform. Give it process, network and file telemetry like any other runtime.
  • One iframe reached many victims. Correlate by shared paths and hashes across users, not per-user only.
  • Zero-days happen; layers (exploit protection, sandboxing, least privilege) decide the outcome when they do.
  • Identity telemetry matters: the implant's session, tokens and consents are part of the incident.
  • Share early. ISAC and peer notifications exposed many watering holes faster than any single victim could.
Connecting the case to T1189

Elderwood is T1189 in its purest form: a user visits a website, hidden code exploits the browser, and the attacker gains execution — no click, no attachment. Every detection in Section 5 exists because campaigns like this proved that a page view is a security event.

A modern companion: the fake-update malvertising chain (realistic composite)

This scenario is a realistic composite based on public reporting about malvertising and fake browser update waves from 2023 to 2025; it is not one single documented incident. The pattern echoes what Mustard Tempest's SocGholish fake update pages and the long-running Lumma Stealer malvertising waves have shown.

  1. An attacker buys search or display ads that promise a popular tool, aiming them at a chosen region and audience.
  2. The victim clicks the ad. The click bounces through two or three tracker domains within seconds.
  3. The landing page says "Your browser is out of date — install the update". It looks like the browser's own dialog.
  4. The user downloads and runs the "update" (a script or loader). No exploit is needed — the user executes it.
  5. The loader pulls an infostealer, which grabs saved passwords, cookies and session tokens within minutes.
  6. Stolen cookies let the attacker reuse the victim's logged-in sessions; follow-up access is often sold or handed to ransomware crews.

The lesson of both stories is the same core technique: the web itself becomes the delivery weapon, and the difference is only whether the code exploits the browser silently or tricks the user into helping.

Layered defenses that work

Mitigation & Defense

Defense in depth

No single control stops every drive-by. Patching removes old holes, the proxy blocks known-bad paths, exploit protection limits what an exploit can do, and detection catches what slips through — all four together are the defense.

Enterprise defenses

📝Policy & governance

Write browsing risk into the security policy: which staff may browse where, and on which networks. Give web risk a named owner, and review the browser fleet version report monthly.

🩹Hardening & patching (M1051)

Update Software is the official ATT&CK mitigation for a reason: keep browsers, extensions and runtimes on automatic updates. Remove legacy plugins (Java, Flash era) wherever the business allows, and track versions against an SLA (a promised fix-by time).

🌐Network controls (M1021)

Restrict Web-Based Content: proxy category blocking, ad and tracker blocking, DNS filtering on fresh cheap-TLD domains, and TLS inspection where policy allows. Block browser access to raw-IP URLs by default.

🧱Exploit mitigation (M1050, M1048)

Exploit Protection (Windows Defender Exploit Guard style) raises the cost of memory corruption. Application Isolation and Sandboxing keeps an exploited tab away from the rest of the system; isolated browsing (VDI — virtual desktops on a server) goes one step further for high-risk users.

🛡️Endpoint detection & EDR (M1049, supporting)

Antivirus/Antimalware plus EDR: process-ancestry alerts (browser → temp exe), exploit behavior blocking, and file-write alerts in user temp folders. Deploy the Section 5 rules and tune them on your baseline.

🧑‍🏫User training (M1017)

Training cannot stop a hidden iframe, but it still matters for the fake-update variant. Teach staff that real browsers never ask to download an "update" from a web page, and how to report odd pages.

🪪Identity safety

Short token lifetimes, device checks on sign-ins, admin consent workflow for OAuth apps, and alerts on new consents (Rule #6). Even a successful drive-by should not convert into lasting cloud access.

🏗️Protect your own sites

Your website can become someone's watering hole. Keep your CMS (the software that runs the site) and web servers patched, use integrity-checked subresources where possible, monitor for unexpected file changes and new third-party scripts, and alert on them.

Home user defenses

  • Turn on automatic updates for the operating system and the browser — this alone removes most drive-by tricks.
  • Use an ad blocker or a browser with strong tracking protection; most malvertising dies at this step.
  • Never install an "update" that a website offers. Updates come from the browser's own About page or the vendor site.
  • Say no to website notification prompts unless you really want them; prune old permissions now and then.
  • Keep built-in antivirus on and updated; let it block unsigned downloads that run right away.
  • Use a password manager with unique passwords, and turn on MFA everywhere — it limits what a stolen session is worth.
  • Back up important files automatically, so an infection is an annoyance, not a disaster.
  • When a page behaves strangely (pop-ups, fake warnings), close the tab and report it — do not click through.

The official ATT&CK mitigations listed for T1189 are M1051 Update Software, M1050 Exploit Protection, M1048 Application Isolation and Sandboxing, M1021 Restrict Web-Based Content, and M1017 User Training. Those five map exactly to the actions above. Modern enterprise tooling adds natural partners: EDR exploit mitigation and controlled folder access extend M1050, DNS filtering is a concrete form of M1021, and isolated browsing (VDI — virtual desktops on a server) is M1048 taken to its strongest form. Antivirus and antimalware platforms (M1049) support the endpoint layer, even though ATT&CK does not list M1049 for T1189 directly. The ATT&CK page also notes browser sandbox limits — sandbox escapes exist — which is exactly why detection (Section 5) must exist even with every mitigation in place.

8.2 Best practices for day-to-day SOC work

  1. Correlate three layers per click: proxy (the chain), endpoint (the process), and DNS (the resolution). One layer gives a hint; three layers give a verdict. Build a saved search that does this join automatically.
  2. Pivot from the victim, then from the infrastructure. For any confirmed landing: first list every host that visited the gate, then list every other gate the same attacker infrastructure served. Drive-by campaigns never have just one victim.
  3. Test your detections with the section 5.5 rules monthly. Replay the Sysmon and proxy events from 5.4 into a staging index. A rule that would not fire today is a gap you can fix before an attacker finds it.
  4. Keep a "newly registered domains" watchlist. Feed it from your DNS resolver. It is the single cheapest high-signal data source for drive-by and phishing infrastructure alike.
  5. Measure browser patch debt like vulnerability debt. Report the percentage of endpoints on the latest browser version. Push it below your agreed threshold and keep it there.
  6. Practice the fake-update lure in awareness training. Show employees a real (defanged) fake update page. The "close the popup, update from the browser menu" habit stops a whole threat family.
  7. Write the chain story in the ticket. Site → gate → exploit → dropper → C2. Future analysts inherit the pattern, not just the block action, and the next hunt starts from a map instead of a blank page.
The drive-by lesson in one line

You cannot patch users out of browsing, but you can patch the browser, watch the process, and question the chain. Do those three things and the silent infection from section 2 becomes a loud, catchable event.
