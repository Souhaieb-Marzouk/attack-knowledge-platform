Compromise Accounts: Cloud Accounts T1586.003

Cloud accounts control servers, storage, and data. When an attacker takes over a cloud or software-as-a-service (SaaS — an app you use in a browser) account, they can build attack infrastructure, steal data, and open backdoors, all inside a service the company already pays for. They get in with stolen passwords, info-stealer logs (password lists stolen from infected computers), or by bypassing multi-factor authentication (MFA — a second login step, like a code from an app). MITRE ATT&CK lists the platform for this technique as PRE (pre-compromise). PRE means the activity happens before an attack touches the target's own systems. This guide explains the technique, shows an animated attack story, and gives defenders ready-to-use detections. It is written for beginners in security operations.

Contents

    1Overview

    What T1586.003 is, why stolen cloud accounts are so valuable, and what this guide teaches you.

    Compromise Accounts: Cloud Accounts means an attacker takes over a cloud or SaaS account that belongs to someone else, and then uses that account for their own work. The attacker does not buy new servers or sign up with a fake identity. They log in as your company, with your keys, from your account.

    A cloud account can control a lot: virtual machines, storage buckets, databases, and the settings that decide who is allowed in. Because of this, one stolen cloud login can give an attacker three things at once. First, attack infrastructure: they can start virtual machines and send network traffic that appears to come from your company. Second, data: they can copy files from storage services. Third, persistence: they can create new users, keys, and trust settings so they stay inside even after a password reset.

    Infrastructure

    Virtual machines, serverless functions, and mail services run under your name. Attackers use them for scanning, command-and-control, spam, and phishing. Security tools may treat your IP addresses as the threat.

    Data access

    Storage buckets and cloud file services hold company files. A compromised account with read rights can copy huge amounts of data quietly, then demand money to keep it private.

    Persistence

    Inside the account, an attacker can add their own users, access keys, roles, and apps. These backdoors survive password resets and even the removal of the original stolen password.

    Where this technique sits in the attack chain

    MITRE ATT&CK places T1586.003 in the Resource Development tactic (TA0042). That is the phase before the visible attack, when the adversary prepares what they need. This technique feeds many later steps:

    • Initial Access — the attacker logs into cloud services or SaaS apps with the stolen identity (see T1078.004 Valid Accounts: Cloud Accounts).
    • Phishing — cloud email or messaging services are used to send phishing mail that looks trustworthy, because it comes from a real tenant.
    • Command and Control — virtual machines in your cloud talk to attacker systems, or serve as their relay.
    • Exfiltration — data is copied to cloud storage the attacker controls, or straight out of your buckets.
    Note

    MITRE ATT&CK defines this technique as the abuse of compromised cloud accounts that can be used during targeting. Attackers use cloud storage services such as Dropbox, Microsoft OneDrive, or Amazon S3 (part of AWS — Amazon Web Services) to hold stolen data (Exfiltration to Cloud Storage) or to upload tools. They use cloud compute to acquire infrastructure, such as virtual private servers or serverless services. And they abuse cloud messaging services such as Twilio, SendGrid, or AWS SES (Amazon's email-sending service) to send spam or phishing. Ways in: phishing for information, bought credentials, password spraying (guessing one weak password against many accounts), or stealing application access tokens. Some attackers target privileged service-provider accounts to abuse the trusted relationship between providers and their customers. MITRE also lists mitigation M1056 Pre-Compromise for this technique and credits Francesco Bigarella as contributor. Full definition: attack.mitre.org/techniques/T1586/003/.

    Words to know

    • IaaS — Infrastructure as a Service. You rent raw computing parts, such as virtual machines, storage, and networks. Examples: AWS, Microsoft Azure, and Google Cloud.
    • SaaS — Software as a Service. Ready-made apps you use through a browser, such as email, chat, or file sharing.
    • IAM — Identity and Access Management. The part of a cloud account that defines users, roles, and what each one may do.
    • Access key — A long password-like token used by programs to call a cloud's programming interface (API — the set of commands one program uses to talk to another). Keys often live for months or years.
    • MFA — Multi-factor authentication. A second proof of identity, such as a code or a push approval, in addition to the password.
    • Info-stealer — Malware on a person's computer that collects saved passwords, cookies, and tokens and sends them to criminals. The stolen data is packed into a "log" file that is sold.
    • Audit log — A record of every action taken in a cloud account: who did what, when, and from which address. In AWS this is CloudTrail; Azure and Google Cloud have similar logs.
    • Federation (OIDC) — A way to let outside systems sign into your cloud without local passwords, using open standards such as OpenID Connect. Attackers love to abuse it for backdoors.

    Written version of the simulation

    The same story as the animation above, in plain text, for screen readers and printing.

    1. Step 1 — Buy stealer logs with cloud creds. An attacker buys stealer logs on a criminal market. The logs hold passwords, cookies, and session tokens taken from infected computers. What defenders see: None. Stealer logs are sold in bulk on criminal markets; monitoring leak feeds is the only early warning.
    2. Step 2 — Console login without MFA. The attacker signs in to the AWS console with a stolen password. No MFA is enforced, so the session opens. What defenders see: CloudTrail ConsoleLogin with MFAUsed=No from a new network — top-priority alert.
    3. Step 3 — Enumerate permissions. Inside the session, the attacker runs IAM list and read calls to map users, roles, and permissions. What defenders see: Rare List/Get API burst from a new principal.
    4. Step 4 — Create rogue IAM user + keys. The attacker creates a rogue IAM user and long-lived access keys. The backdoor survives a password reset. What defenders see: New IAM user + access keys outside the joiner process (the standard steps for giving a new employee access) — critical.
    5. Step 5 — Launch VMs for attack infrastructure. The attacker launches virtual machines in an unusual region to use as attack infrastructure. What defenders see: Unusual instance launches; billing alarms fire.
    6. Step 6 — Download the data bucket. The attacker bulk-reads a storage bucket with repeated GetObject calls. What defenders see: GetObject volume spike; GuardDuty exfiltration finding.
    7. Step 7 — Cover tracks. The attacker tries to stop or delete the CloudTrail trail to hide the activity. What defenders see: Trail changes are themselves logged — alert on them.
    8. Step 8 — SOC response. The SOC disables keys, deletes the rogue user, revokes sessions, and rotates credentials. What defenders see: Keys disabled; rogue user removed; root-cause review of the stealer infection.

    3Red Team / Hacker Perspective

    Why attackers want your cloud account, how the takeover usually works, and which mistakes they make that help you catch them. Everything here is conceptual and for lab study only.

    When and why attackers use this technique

    Attackers compromise cloud accounts because it is cheap, fast, and hard to tell apart from normal work. A company's own cloud already has trusted IP space, real-looking mail domains, and billing that someone else pays. Using your account means the attacker does not need to register anything that could be traced back to them.

    • Trust. Traffic and mail from a real tenant looks legitimate. Filters and partners trust it more than random infrastructure.
    • Scale and speed. Hundreds of virtual machines or mail quotas are a few clicks away once the account is theirs.
    • Cost transfer. The victim pays the bill. Criminal groups treat cloud spend as someone else's problem.
    • Data in reach. Many accounts can read storage that holds business data, backups, or customer records.
    • Persistence options. Users, keys, roles, and apps can be created for long-term access without malware on any endpoint.
    Danger

    Information-stealer logs are sold in bulk on criminal markets and often hold working cloud console logins, cookie files, and access keys. This is the main supply chain for T1586.003 in real incidents reported by vendors. Treat any sign of stealer infections on staff machines as a cloud-security event, not only an endpoint event.

    How the takeover usually works (conceptual stages)

    The stages below describe attacker behavior in general terms so defenders can understand and detect it. They are not instructions. Never test them against cloud accounts you do not own; in a lab, use a throwaway account and keep billing alarms on.

    Where it applies and what it needs

    Applies to

    Any cloud or SaaS service with an account: IaaS platforms such as AWS, Azure, and Google Cloud; storage and file services; and messaging platforms such as Twilio or SendGrid. ATT&CK lists the platform for this technique as PRE — the takeover happens before the attacker touches the victim's systems.

    Prerequisites from the attacker's view

    Valid credentials or session tokens, a missing or bypassable MFA step, and permissions to read, launch, or change things. Admin rights open the worst options, but read-only accounts are already useful for data theft.

    Common variations

    Stealer logs

    Credentials and session cookies harvested from infected staff or contractor machines. The most common starting point in published cases.

    Password spraying

    Trying one common password against many accounts, slowly, to avoid lockouts. Old bought breach lists are reused the same way.

    Token theft

    Stolen session cookies or application access tokens are replayed directly, so the attacker never needs the password or the second factor.

    OAuth consent abuse

    A fake or malicious app asks a user for consent. Once granted, the app reads mail and files without ever logging in as the user.

    MSP and service-provider accounts

    Managed service providers and partners hold privileged accounts that reach many customers at once. One compromise opens every customer.

    Insider assistance

    A current or former employee sells or shares access. Detection depends on monitoring service-account and offboarded-user activity.

    Attacker mistakes that help defenders

    • Logging in from a new country or hosting network straight after a steal, instead of through a residential proxy.
    • Running the console session without the stolen user's normal MFA pattern, so MFAUsed=No appears in the log.
    • Creating users or keys outside working hours and outside the joiner process.
    • Launching virtual machines in regions or instance types nobody in the company uses.
    • Copying a whole bucket in hours when normal users open one file at a time.
    • Stopping or deleting the audit trail — a loud action that is itself recorded.
    • Reusing the same stolen email or wallet address across victims, which links cases together.
    Note

    Lab-only rule for red teams: simulate this technique against a sandbox account you own, with logging enabled, a billing cap, and written permission. The goal is to generate the signals in Section 5, not to harm a real tenant.

    4Blue Team / SOC Perspective

    How defenders notice a compromised cloud account, which artifacts the activity leaves, and a short triage flow from alert to closure.

    How defenders notice

    The cloud itself is your best sensor. Audit logs record nearly every action with the exact identity, time, source address, and parameters. The strongest early signals are:

    • A console login without MFA, or from a new country, network, or device fleet.
    • List and Get calls at a speed or volume the identity never had before.
    • New IAM users, access keys, roles, or OAuth apps created outside the normal joiner process.
    • Virtual machine launches in unusual regions or expensive instance families.
    • Bulk reads from storage buckets, especially many objects in a short window.
    • Changes to audit logging itself: StopLogging, DeleteTrail, or logging exclusions.
    • Billing alarms and budget alerts that fire with no matching change request.
    Warning

    Object-level storage events (S3 data events) are off by default in most trails. If they are not enabled, bulk exfiltration is nearly invisible. Check this setting on every trail; it is the most common blind spot for this technique.

    Why it matters and where it sits

    For defenders, this technique is a force multiplier for every other cloud attack. The same stolen account can feed initial access, command-and-control, phishing, and exfiltration. Because there is no malware on company servers, classic endpoint tools see nothing. The attack chain position is early: Resource Development, before the visible incident. Catching a rogue login or a rogue key at this stage prevents everything that follows.

    Triage flow: from alert to closure

    • Step 1 — minutesVerify the alert. Confirm the event is real in the raw audit log: identity, time, source address, MFA flags. Rule out known break-glass accounts (emergency admin accounts kept for outages) and approved changes.
    • Step 2 — minutesCheck the session context. Look at user agent, device, country, and network. Compare with the user's last 30 days of sign-ins.
    • Step 3 — first hourAssess blast radius. List what the identity touched after login: API calls, new objects, launched resources, mail sends. Query by session, not by single event.
    • Step 4 — first hourContain access. Disable new keys, revoke sessions and refresh tokens, force password reset with MFA re-registration, and remove rogue users or apps.
    • Step 5 — first dayProtect the trail. Verify logging is still on, export the evidence to a read-only store, and snapshot the current IAM and trust settings.
    • Step 6 — first dayTrace the source. Check for info-stealer infections on the user's machines, reused passwords, or phishing reports. Tell the user's manager and the security lead.
    • Step 7 — daysEradicate and recover. Rotate every credential the identity could see, review billing for abuse, remove attacker resources, and confirm no new backdoors remain.
    • Step 8 — weeksClose and improve. Write the report, update detections, tune false positives, and record lessons in the backlog with owners and dates.

    How to apply intel in four steps

    1. Collect. Subscribe to two or three sources you can actually read. Add stealer-log monitoring for your domains. Keep internal baselines in the same place.
    2. Analyze. Ask for each report: which of my six threats does this match, which log fields would show it, and what is new versus already covered?
    3. Deploy. Turn the answer into detections (Section 5.5), hunting queries, or control changes (Section 7). Note the source and date on each rule so you can retire it later.
    4. Review. Each quarter, check which intel-driven detections fired, which were noise, and which intel went stale. Delete what nobody uses.

    Warning

    Two collection gaps break most of these detections: S3 data events are disabled by default, and guardduty findings are not exported anywhere by default. Fix both before you trust any query in this section.

    T1 — Cloud console takeover via stealer-derived credentials

    Log sources: AWS CloudTrail management events (signin.amazonaws.com), Entra ID sign-in logs, Okta system logs, and GuardDuty findings. Key fields: eventName, additionalEventData.MFAUsed, userIdentity.userName, sourceIPAddress, userAgent, awsRegion.

    T1: normal versus suspicious console sign-in behavior.
    NormalSuspicious
    MFA used on nearly every interactive login; the exceptions are allowlisted break-glass accountsMFAUsed=No on an ordinary user, or a first-ever login without the user's normal second factor
    Same small set of countries, networks, and device types per userNew country, new autonomous system (a network operator range), or a hosting/residential-proxy network
    Browser user agent matches the fleet baselineOld or odd user agent strings, headless tooling, or console login followed by CLI traffic from another address

    Detection logic: alert on every ConsoleLogin (or SaaS equivalent) where MFAUsed=No and the identity is not an allowlisted break-glass account, then enrich with a first-seen check for source network and country.

    T1: field explanation for the console sign-in event.
    FieldMeaning
    eventNameThe action performed. ConsoleLogin means an interactive web-console sign-in.
    additionalEventData.MFAUsedWhether a second factor was used for this login. "No" is the core signal here.
    userIdentity.userNameThe named IAM user who signed in; map it to an employee record in your staff directory or identity system.
    sourceIPAddressClient address of the login. Enrich it with country and network data before judging.
    userAgentBrowser or tool signature; compare against the user's baseline.
    responseElements.ConsoleLoginSuccess or failure. Failures followed by success show password guessing or a fixed second factor.

    The Azure equivalent is a sign-in event. The interesting fields are the location block, the client application, and the conditional access result:

    T1: field explanation for the Entra ID sign-in event.
    FieldMeaning
    categorySignInLogs marks interactive sign-ins; audit changes go to AuditLogs.
    mfaDetailNull here means no MFA method was used for this authentication.
    conditionalAccessStatus"notApplied" means no conditional-access policy matched; every sign-in policy should either apply or be documented.
    location.countryOrRegionDerived from the source address; compare with the user's usual countries.

    T2 — Rogue IAM user and access-key persistence

    Log sources: AWS CloudTrail management events for iam.amazonaws.com; Entra ID audit logs for new users and app registrations; Google Cloud admin activity audit logs. Key fields: eventName (CreateUser, CreateAccessKey, AttachUserPolicy), requestParameters.userName, responseElements.accessKey.createDate, actor identity fields.

    T2: normal versus suspicious IAM provisioning.
    NormalSuspicious
    Users and keys created through an infrastructure-as-code pipeline from a known automation identityCreateUser followed by CreateAccessKey within minutes, done by a human session at night
    New keys appear on the joiner report the same weekNew user or key that matches no ticket, no joiner report, and no pipeline run
    Keys rotated on schedule; age visible in inventoryKey created and then used from a different address than the creator

    Detection logic: pair CreateUser with a CreateAccessKey for the same new user within 15 minutes, and raise severity when the creating session is interactive and outside the joiner window.

    Twenty-six seconds later, the attacker mints a long-lived key for that user:

    T2: field explanation for the key-creation event.
    FieldMeaning
    eventNameCreateAccessKey mints a programmatic credential that does not need the console or MFA.
    requestParameters.userNameThe target user for the new key; in this chain it is the user created seconds earlier.
    responseElements.accessKey.accessKeyIdThe key identifier. Track it: the secret itself is never in the log, but this ID marks every later use.
    userIdentity.userNameThe actor. A human user acting at 02:59 local time is the red flag; pipelines look different.
    userAgentaws-cli from a console-session address is a classic hands-on-keyboard sign.

    T3 — Bulk data exfiltration from object storage

    Log sources: AWS CloudTrail S3 data events, S3 server access logs, GuardDuty S3 protection findings, Azure storage diagnostics, Google Cloud data access logs. Key fields: eventName (GetObject, ListObjectsV2), requestParameters.bucketName, requestParameters.key, userIdentity.arn, additionalEventData.bytesTransferredOut.

    T3: normal versus suspicious storage reads.
    NormalSuspicious
    Users open a few named objects per session from known networksOne principal reads tens of thousands of objects across many prefixes in hours
    Backup and reporting jobs run on schedules with steady volumeBulk reads at night, outside job windows, often with command-line user agents
    Bucket-level list operations are rareListObjectsV2 followed by thousands of GetObject calls on the same prefix

    Detection logic: bucket GetObject counts per principal per 15 minutes against a 7-day baseline; alert when volume exceeds baseline by a wide margin, and attach any GuardDuty exfiltration finding to the same case.

    T3: field explanation for the S3 data event.
    FieldMeaning
    managementEvent: falseMarks a data event; these are only logged if you enable S3 data events on the trail.
    requestParameters.bucketName and keyExactly what was read; group by bucket and prefix to spot sweep patterns.
    userIdentity.arnWho read it. Here it is the rogue user from T2 — chain your threats, not just your alerts.
    additionalEventData.bytesTransferredOutBytes sent to the caller; two gigabytes for one object is a strong staging signal.
    userAgentSDK user agents are normal for jobs; unexpected SDK traffic at night is not.

    GuardDuty summarizes the same story as a finding. Treat findings as corroboration and enrichment, not as a replacement for the raw data events:

    T3: field explanation for the GuardDuty finding.
    FieldMeaning
    typeFinding family. "Exfiltration:S3" groups data-staging behavior on buckets.
    severityGuardDuty scale of 0 to 10; route findings of 7 and above to a human queue.
    service.action.awsApiCallActionThe summarized API call, including the remote IP and its geolocation.
    service.countAggregated call count behind the finding; large counts confirm bulk behavior.

    T4 — Cloud resource abuse: VMs for C2, phishing, or crypto mining

    Log sources: AWS CloudTrail (ec2.amazonaws.com), Azure activity logs, Google Cloud audit logs, cost and usage reports, budget alerts. Key fields: eventName (RunInstances, StartInstances), requestParameters.instancesSet.items[].instanceType, awsRegion, userIdentity.arn.

    T4: normal versus suspicious resource launches.
    NormalSuspicious
    Launches in approved regions, approved instance families, through pipelinesLaunches in a region the company never uses, or expensive GPU (graphics processing unit) families nobody owns
    Instances get names, tags, and owners within minutesUntagged instances, odd machine images (AMIs), fresh security groups open to the internet
    Cost curve matches the change calendarCost spike with no ticket; budget alarms at unusual hours

    Detection logic: alert on RunInstances where the region is not on your approved list or the instance family is in a watchlist (GPU and high-memory families), and confirm with a billing anomaly check.

    T4: field explanation for the RunInstances event.
    FieldMeaning
    awsRegionWhere the machines run. A region outside your footprint is the first filter.
    requestParameters.instancesSet.items[].instanceTypeSize and family. GPU families such as g5 point at crypto mining or AI tooling abuse.
    minCount / maxCountHow many machines at once; bursts of four or more deserve a look.
    userIdentity.arnThe role session behind the launch; trace it back to the stolen login from T1.
    responseElements.instancesSet.items[].instanceIdThe resource IDs responders must quarantine or terminate during cleanup.

    T5 — Backdoor federation or OIDC trust, or a malicious OAuth app

    Log sources: AWS CloudTrail (iam.amazonaws.com, sts.amazonaws.com), Entra ID audit logs (app registrations, consent grants), Google Cloud admin activity logs. Key fields: eventName (UpdateAssumeRolePolicy, CreateOpenIDConnectProvider, AddClientIDToOpenIDConnectProvider), requestParameters.url, requestParameters.policy.

    T5: normal versus suspicious federation changes.
    NormalSuspicious
    Federation set up once by the platform team through change controlA new OIDC provider created by a human session, with an unknown external address
    Role trust policies only ever narrow to known accounts and conditionsTrust policy edit that adds an external account ID or removes conditions
    OAuth consents match an approved app catalogNew consent grant with high-privilege scopes to an unvetted tenant

    Detection logic: alert on any UpdateAssumeRolePolicy and any CreateOpenIDConnectProvider or consent-grant event; treat each one as a change request that must match a ticket within minutes.

    The sibling action is rewriting a role's trust policy to welcome an outside account:

    T5: field explanation for the federation events.
    FieldMeaning
    requestParameters.urlThe OIDC identity source. Anything outside your sanctioned providers is a backdoor candidate.
    requestParameters.policyThe new trust policy as a JSON string; parse it and extract every Principal account ID.
    Principal account IDThe external account that may assume the role; 999900111222 in this example is unknown to the company.
    requestParameters.roleNameThe role being rewired; high-privilege roles make this a critical alert.

    T6 — Log and trail tampering to hide activity

    Log sources: AWS CloudTrail (self-referential events for cloudtrail.amazonaws.com), AWS Config rules, EventBridge notifications from the organization trail, Azure diagnostic-settings audit, Google Cloud log-router audit. Key fields: eventName (StopLogging, DeleteTrail, UpdateTrail, PutEventSelectors), requestParameters.name.

    T6: normal versus suspicious logging changes.
    NormalSuspicious
    Trail changes happen only in change windows, through the platform pipelineStopLogging or DeleteTrail at night from a human session with no ticket
    Organization trail managed by a delegated admin account onlyAttempts on the org trail from a member account, which should fail — and still alert
    Selectors change to add coverageSelectors that quietly exclude regions, services, or data events

    Detection logic: alert on every event that stops, deletes, or narrows audit logging, regardless of who calls it, and cross-check each against a change ticket; also verify the trail health from outside the logged account.

    T6: field explanation for the StopLogging event.
    FieldMeaning
    eventNameStopLogging pauses recording; DeleteTrail removes it. Both are incident-level events.
    requestParameters.nameThe trail under attack; a shared org trail name shows company-wide intent.
    userIdentityThe actor session; link it to T1 and you have the whole chain in one query.
    Event existence itselfEven a failed StopLogging attempt proves intent and is worth alerting on.

    5.5 Sigma Rules and Splunk SPL

    Each of the six threats gets one Sigma rule and one matching Splunk SPL query. Sigma is an open rule format for log detections; you can convert these rules to your SIEM (security information and event management — the central platform that collects logs and raises alerts) with the free sigmac converter. The SPL queries mirror the Sigma logic and add the baselines and enrichments that a stateless rule cannot hold. Every query starts with the same sourcetype mapping, listed below, so the searches run in a standard Splunk deployment with the Splunk Add-on for AWS, Microsoft Azure, or Google Cloud.

    Sigma logsource to Splunk sourcetype mapping used throughout this page.

    product: aws, service: guarddutyindex=awsaws:guarddutyFindings must be exported to S3 or EventBridge first
    product: azure, service: signinlogsindex=azurems:aad:signinEntra ID sign-in logs via the Microsoft Azure Add-on
    product: azure, service: auditlogsindex=azurems:aad:auditEntra ID audit logs for users, apps, and consents
    product: oktaindex=identityOktaIM2:logSplunk Add-on for Okta Identity Cloud

    Note

    Tuning order: deploy, watch the false-positive list for two weeks, allowlist the approved patterns from your change system, then tighten the thresholds. A detection that fires only on real evil does not exist on day one — it is built by writing down every benign case.

    High S1 — Console login without MFA from a new network

    Threat T1. The Sigma rule matches the stateless core: a successful console login with no MFA from a user that is not break-glass. The SPL adds country enrichment and a per-user summary so analysts can prioritize new networks.

    • Mapping: logsource aws/cloudtrail to index=aws sourcetype=aws:cloudtrail.
    • False positives: the two allowlisted break-glass accounts, plus any human outside your country on business travel.
    • Tuning: add a lookup of expected countries per team, or join with your IAM export so new-employee first logins are suppressed for their first week.

    Critical S2 — IAM user created, then keys created within minutes

    Threat T2. Sigma pairs the two events with a near condition; the SPL rebuilds the pair with transaction so analysts get one row per backdoor attempt.

    • Mapping: logsource aws/cloudtrail to index=aws sourcetype=aws:cloudtrail.
    • False positives: automation identities that provision ephemeral build users; keep their automation role identifiers in the filter list.
    • Tuning: join target_user against this week's joiner report; shorten maxspan to 5 minutes once the noise drops.

    High S3 — Bulk GetObject volume spike by principal

    Threat T3. Sigma holds the stateless core; the baseline math lives in the SPL, where a 7-day eventstats average and standard deviation per principal set the alarm level.

    Corroborate with GuardDuty, which packages the same behavior as a finding:

    • Mapping: logsource aws/cloudtrail to index=aws sourcetype=aws:cloudtrail; the GuardDuty query uses index=aws sourcetype=aws:guardduty.
    • False positives: nightly backups and scheduled exports; baseline them by schedule instead of deleting the alert.
    • Tuning: raise the floor to your largest known job volume, and split the alert by data classification so finance buckets alarm first.

    Medium S4 — Instances launched in an unapproved region or expensive family

    Threat T4. Both the region allowlist and the family watchlist are environment-specific; the rule names the lists, your pipeline fills them in.

    • Mapping: logsource aws/cloudtrail to index=aws sourcetype=aws:cloudtrail.
    • False positives: autoscaling, spot-fleet jobs, and one-off approved experiments.
    • Tuning: keep the family watchlist as a lookup so teams can request exceptions without code changes; alert harder at night when no autoscaling runs.

    Critical S5 — Federation backdoor: trust policy edit or new OIDC provider

    Threat T5. Any hit should be treated as a change request with a deadline: the account either has a ticket for it within minutes, or responders cut it.

    • Mapping: logsource aws/cloudtrail to index=aws sourcetype=aws:cloudtrail.
    • False positives: sanctioned CI/CD identity provisioning; document each one as an approved provider URL.
    • Tuning: extract the Principal account IDs from every hit and compare with a lookup of known partner accounts; unknown IDs page immediately.

    High S6 — CloudTrail stopped, deleted, or narrowed

    Threat T6. The alert fires on the action, not the outcome: even failed attempts prove intent.

    • Mapping: logsource aws/cloudtrail to index=aws sourcetype=aws:cloudtrail.
    • False positives: planned trail maintenance; require a ticket number in the change record and suppress only the exact window.
    • Tuning: pair with an independent health check, for example AWS Config rule cloudtrail-enabled or a scheduled describe from a separate security account, so a short StopLogging gap is still noticed.

    6Real-World Case Study

    The 2024 Snowflake customer breaches: info-stealer logs turned into mass account takeover and extortion. Based on public reporting (source links below); details simplified for teaching.

    In 2024, a financially motivated group that Mandiant tracks as UNC5537 used credentials stolen by info-stealer malware to break into Snowflake customer accounts. Snowflake is a SaaS data platform that stores huge business datasets. The attackers replayed old, saved passwords through residential proxy networks into accounts that had no multi-factor authentication and no network restrictions. They copied large amounts of data and demanded payment. Public reporting by Mandiant and Snowflake describes the campaign as affecting roughly 165 customer organizations, with well-known companies such as Ticketmaster and Santander publicly disclosing incidents.

    This case is the clearest public example of T1586.003 thinking: the attackers did not hack Snowflake itself. They compromised accounts — the cheapest door in the building. All dates below come from the public sources linked at the end of this section.

    Case facts as reported publicly. Where numbers are claims by the extortionists, we say so.

    Technique shownT1586.003 (compromised cloud/SaaS accounts) feeding T1078.004 (valid accounts) and bulk data theft
    Time windowStealer infections months earlier; access waves April to May 2024; disclosures May to June 2024
    Entry methodSaved Snowflake passwords and session data harvested by info-stealer malware, replayed via residential proxies
    Main weaknessAccounts without MFA and without network allowlists; old credentials never rotated

    Attack chain steps

    1. Steal: info-stealer malware collects saved passwords, cookies, and tokens from real users' machines.
    2. Sell: the harvested data is sold as "logs" on criminal markets; buyers search them for company names and cloud logins.
    3. Replay: the buyer tests old Snowflake logins through residential proxies so the traffic looks like normal home-user traffic.
    4. Enter: accounts without MFA and without network restrictions accept the old password; the attacker now acts as the customer.
    5. Persist and take: the attacker copies large datasets and, in some reported cases, adjusts account settings to keep access.
    6. Extort: victims receive demands; stolen data is leaked or sold when they do not pay.
    Detection point

    How it was actually caught: anomalous logins in Snowflake audit logs — new locations, new devices, and residential proxy networks — combined with unusual bulk query activity. This maps directly to the detections in Section 5: sign-ins without MFA from new networks (S1) and bulk reads far above baseline (S3). Stealer-log monitoring services also flagged company credentials in sold logs before the intrusion wave.

    Containment

    Organizations disabled or reset the compromised accounts, revoked active sessions, enforced MFA immediately, and restricted access to known networks and IP ranges. Snowflake and Mandiant published step-by-step guidance and free checking tools so customers could act fast.

    Eradication

    Teams rotated exposed credentials, including service and integration accounts, reviewed connected tools and OAuth grants for backdoors, and validated that no new users, keys, or apps had been created by the attacker.

    Recovery

    Access was restored with stronger controls in place: MFA enforced, allowlists applied, and monitoring raised. Regulators, customers, and partners were notified where laws required it, and teams watched for re-entry attempts for weeks.

    Impact and consequences

    Large datasets were stolen and offered for sale; extortion followed; companies faced regulatory exposure, lawsuits, and reputation damage. The platform owner had to enforce MFA by default — a platform-wide change driven by customer-level weakness.

    Team response and communication

    Public reporting shows a coordinated pattern worth copying: security teams worked jointly with the platform vendor and incident-response firms; leadership communicated through required disclosures within legal deadlines; customers received practical guidance instead of vague warnings; and findings were shared with the wider community through detailed blog posts and free tools. Clear ownership mattered: one team tracked identity fixes, one tracked logging and monitoring, and one handled legal and customer communication.

    Lessons learned

    • Phishing-resistant MFA enforced on every account, not offered as an option — most affected accounts simply had no MFA.
    • Watch the supply of stolen credentials: monitor stealer logs for your domains, because the intrusion starts on an endpoint you may not own.
    • Network allowlists for administrative and high-value data platforms remove whole classes of replay attacks.
    • Rotate old credentials and kill saved-password reuse; credentials can work years after the infection that captured them.
    • Build session revocation into your runbook — password resets alone do not end live sessions.
    • Monitor for bulk queries and exports, not just logins; the data movement is the loudest signal.

    • Mandiant / Google Cloud: UNC5537 Snowflake data extortion campaign
    • Live Nation / Ticketmaster: Form 8-K filed 2024-05-31 (SEC EDGAR) — the primary disclosure for the Ticketmaster incident
    • Snowflake: multi-factor authentication (MFA) guidance — the documentation behind the platform-wide MFA enforcement

    7Mitigation and Defense

    There is no single switch that stops cloud account compromise. Defense in depth — identity, endpoint, network, cloud configuration, and monitoring working together — is the answer.

    Note

    MITRE ATT&CK maps this technique to the mitigation M1056 Pre-Compromise and notes that it cannot be easily mitigated with preventive controls, because it is based on behaviors performed outside the scope of enterprise defenses and controls. You cannot patch "a stolen password". The mitigations below reduce the chance of takeover, limit what a taken-over account can do, and shorten the time to detection.

    Identity controls

    Enforce phishing-resistant MFA for all humans, with no exceptions and no text-message (SMS) codes. Use single sign-on with conditional access (device health, location, risk). Prefer short-lived federated access over passwords. Remove standing admin rights; require just-in-time elevation with approval.

    Cloud configuration

    Turn on an organization trail with data events for buckets. Enable GuardDuty or an equivalent. Apply service control policies (SCPs — guardrail rules that apply to every account in an AWS organization) that block trail changes and key creation outside the pipeline. Set billing alarms and budgets. Run a cloud security posture scanner weekly.

    Endpoint controls

    The supply chain starts on laptops. Run EDR on every device that touches the cloud, block saving passwords in plain browser stores, push a password manager, and treat any info-stealer detection as a cloud credential incident with forced resets.

    Network controls

    Allowlist source networks for console and admin access. Block hosting-provider and anonymizer ranges from reaching login pages. Require a VPN (virtual private network — a private connection through your network) or a zero-trust broker for administrative sessions. Watch proxy logs for console traffic from new networks.

    Logging and monitoring

    Ship CloudTrail, Entra ID, Okta, and Google Cloud (GCP) audit logs to a SIEM with at least one year of searchable retention. Deploy the six detections from Section 5.5. Alert on IAM diffs, federation changes, and billing anomalies. Test the alerts monthly.

    Response readiness

    Keep a tested runbook: disable keys, revoke sessions, remove rogue users, rotate credentials, and preserve evidence. Pre-delegate authority so responders can act at night. Rehearse the Snowflake-style scenario in a tabletop twice a year.

    Home and small office

    Small teams use cloud accounts too, and attackers know it. Turn on MFA everywhere — email, file storage, the cloud console — and use an authenticator app rather than text codes. Keep business and personal accounts separate. Remove old accounts when a staff member leaves. Check the billing alerts on your cloud subscription and enable login notifications. If a device is ever infected by password-stealing malware, change those passwords from a clean device and sign out all sessions.

    8Common Mistakes and Best Practices

    Twelve blue-team mistakes that keep showing up in cloud account incidents, each with the symptom, the root cause, the fix, and the prevention habit.

    Mistake 1: assuming the cloud provider watches for you.

    Symptom: the team believes "AWS or Microsoft would tell us if we were attacked", so no own alerts exist.

    Root cause: shared responsibility is misunderstood — the provider secures the platform, you secure identities, configuration, and data.

    Fix: write down the responsibility split for your account, then deploy your own detections from Section 5.5.

    Prevention: include the responsibility map in onboarding for every engineer and audit it yearly.

    Mistake 2: data events left off, S3 reads invisible.

    Symptom: after an exfiltration, nobody can answer "which user read which object".

    Root cause: S3 data events are disabled by default and cost money, so they were never switched on.

    Fix: enable data events on sensitive buckets now; start with finance and customer data.

    Prevention: a posture rule that fails every trail without data events, checked weekly.

    Mistake 3: alerts only on the root account.

    Symptom: root activity alerts exist, but a rogue IAM user created by an attacker never alerts.

    Root cause: old guidance from the era when root was the only dangerous identity.

    Fix: alert on IAM diffs, key creation, and role edits for all identities (S2, S5).

    Prevention: review alert coverage against a list of top IAM actions every quarter.

    Mistake 4: no billing alarms.

    Symptom: the first sign of resource abuse is an invoice, weeks later.

    Root cause: billing is seen as finance's job, not a security signal.

    Fix: add budget alerts and anomaly alerts on every account, routed to the SOC.

    Prevention: include billing alerts in the account baseline checklist for new accounts.

    Mistake 5: pipelines with keys and no anomaly monitoring.

    Symptom: a service account with full rights is used at 03:00 and nobody asks why.

    Root cause: automation identities are treated as invisible plumbing.

    Fix: inventory every automation identity, baseline its normal hours and calls, and alert on deviations.

    Prevention: quarterly key audit with owners; expired or unused keys are deleted, not disabled.

    Mistake 6: federation changes unmonitored.

    Symptom: an OIDC provider or role trust edit is discovered during a manual review months later.

    Root cause: nobody owns identity-provider change detection; console changes feel too rare to matter.

    Fix: deploy S5; treat every federation change as a change request that must match a ticket.

    Prevention: add federation events to the monthly change-review meeting with the platform team.

    Mistake 7: no session revocation tooling.

    Symptom: after a password reset, the attacker keeps working from an already-open session.

    Root cause: the runbook only says "reset the password".

    Fix: script session and token revocation per identity provider and add it as step one of containment.

    Prevention: test revocation in the quarterly access drill, not just on paper.

    Mistake 8: detections copied from templates, never validated.

    Symptom: rules from the internet generate either silence or constant noise; nobody trusts them.

    Root cause: field names, sourcetypes, and thresholds were never matched to real data.

    Fix: validate each rule against captured events like the JSON examples in 5.4 before production.

    Prevention: a rule goes live only with test evidence, an owner, and a review date.

    Mistake 9: false positives ignored instead of tuned.

    Symptom: the S1 alert fires for travel and break-glass so often that analysts auto-close it.

    Root cause: no allowlist process; tuning feels like weakening security.

    Fix: document every recurring benign case, allowlist it precisely, and keep the alert strict for everything else.

    Prevention: a two-week tuning window after every new rule, with a named owner.

    Mistake 10: alert fatigue from unranked alerts.

    Symptom: everything pages; analysts ignore all pages.

    Root cause: severities copied from rule templates instead of mapped to real impact.

    Fix: rank alerts by the threat ranking in 5.3 — rogue keys and no-MFA logins page, low-value events queue.

    Prevention: review paging volume monthly; anything over a dozen pages per analyst per week gets retuned.

    Mistake 11: log retention too short for investigations.

    Symptom: when the incident surfaces, the first attacker login is already aged out of the SIEM.

    Root cause: default 90-day retention treated as enough.

    Fix: keep one year searchable plus cold archive; export trail logs to immutable storage.

    Prevention: retention tested yearly with a real query for a 10-month-old event.

    Mistake 12: cloud team and SOC working in silos.

    Symptom: the SOC cannot read CloudTrail fields; the cloud team does not know which alerts fired.

    Root cause: no shared ownership or joint reviews.

    Fix: give the SOC read access and a mapping table like the one in 5.5; hold a joint detection review.

    Prevention: monthly joint review of cloud detections, false positives, and coverage gaps.

    Habits that prevent these mistakes

    Daily

    • Review overnight critical cloud alerts (S1, S2, S5).
    • Check that all trails and GuardDuty are still healthy.
    • Look at billing alarms with no matching change.

    Weekly

    • Review new IAM users, keys, roles, and OAuth grants against tickets.
    • Tune the top three noisy alerts; document benign causes.
    • Check posture scanner findings and close the easy ones.

    Monthly

    • Run the joint cloud and SOC detection review.
    • Test session revocation and one response runbook step.
    • Audit a sample of identities: owner, purpose, last use, MFA status.

    Response checklist

    • Confirm the suspicious event in raw logs: identity, time, source, MFA flags.
    • Rule out allowlisted break-glass accounts and approved change windows.
    • Query the full session, not one event: what did this identity touch?
    • Disable rogue access keys and delete rogue users or apps.
    • Revoke sessions and tokens; force a password reset with new MFA.
    • Verify logging is still on and export evidence to read-only storage.
    • Rotate every credential the identity could reach, including services.
    • Review billing for attacker-created resources and remove them.
    • Check the user's devices for info-stealer infections.
    • Notify stakeholders: manager, security lead, legal, and regulators if needed.
    • Update detections and write the report with lessons and owners.
