Stored Data Manipulation T1565.001

Stored data manipulation is when an attacker inserts, deletes, or changes data at rest — data saved on disks or in databases. The system keeps running, so the attack can stay invisible for a long time. This guide shows how the attack works, what proof it leaves in logs, and how to detect it with Sigma and Splunk.

1. Overview

Start here to learn what stored data manipulation means, where it sits in an attack chain, and how it differs from its two sibling techniques.

“Adversaries may insert, delete, or manipulate data at rest in order to influence external outcomes or hide activity, thus threatening the integrity of the data. By manipulating stored data, adversaries may attempt to affect a business process, organizational understanding, and decision making.”

“Stored data could include a variety of file formats, such as Office files, databases, stored emails, and custom file formats. The type of modification and the impact it will have depends on the type of data as well as the goals and objectives of the adversary.”

— MITRE ATT&CK, T1565.001 — Stored Data Manipulation (v1.1, modified 2025-11-13)

What this means in plain words

Data at rest is data that is saved somewhere: rows in a database, files on a share, configuration files, or stored logs. The attacker does not break the system. They change the content so that people and other systems act on false information. Because the false value is saved, it survives reboots and keeps misleading users until someone compares it with a known-good copy.

The change usually needs write access — permission to modify a database, a share, or a protected path. That is why this technique often follows credential theft. The official ATT&CK procedure example is APT38 (a financially motivated group): it used the tool DYEPACK to create, delete, and alter records in databases used for SWIFT payments.

Where it fits in the attack chain

T1565.001 belongs to the Impact tactic (TA0040), so it normally comes late in a chain: after Initial Access, Privilege Escalation, and Discovery. The attacker first needs to know where the data lives and then needs write rights to it.

One partial exception is log manipulation: attackers often trim or delete logs early and repeatedly as a Defense Evasion companion (technique T1070) so the intrusion stays dark. Watch both angles: the business change and the evidence change.

Integrity means data is complete and trustworthy. This technique attacks integrity directly: money amounts, medical entries, or system settings no longer match reality.

How this relates to the parent technique

The parent technique T1565 (Data Manipulation) covers changing data in general. The three sub-techniques split it by where the data is when the change happens.

Terms used in this guide

FIM (file integrity monitoring) watches files and alerts when they change against a known-good baseline. DB audit is the database's own record of who ran which statement. DAM (database activity monitoring) is a tool that watches database traffic from the outside. SIEM is the system that collects logs and runs alerts. Sigma is an open rule format for detections; SPL is Splunk's search language.

The log sources listed in Sections 5.4 and 5.5 are practitioner guidance from our own experience. ATT&CK now links this technique to detection strategies instead of a fixed data-source list, so treat our list as a strong starting point, not as an official ATT&CK statement.

    1. Step 1 — Lateral move to the DB host. The attacker already controls a file server (FS-03) through a stolen service account. From there, they reach FIN-DB-01, the host running the finance database, using admin access that the account should never have had. Defender view: an off-hours network logon on FIN-DB-01, sourced from FS-03, not from the application tier.
    2. Step 2 — UPDATE the balances table. The attacker opens a SQL client and runs an UPDATE statement that rewrites the balance column for a customer account. The stored value changes permanently. Defender view: the database activity monitor captures the statement, because it ships audit rows off the host in near real time.
    3. Step 3 — Edit and delete audit rows. To hide the change, the attacker deletes rows from the local audit table and removes the audit log files on the host. Defender view: the local audit trail goes quiet — but the copy already shipped to the monitor still exists.
    4. Step 4 — SIEM raises a log-gap alert. The SIEM expects a steady stream from FIN-DB-01. When the stream stops during business hours, a gap alert fires. Silence is treated as a signal, not as peace.
    5. Step 5 — The database activity monitor flags the UPDATE. Because the monitor received the audit rows before deletion, it can still alert on the direct UPDATE from a non-application user. Two independent views of the same write now exist.
    6. Step 6 — FIM shows a changed config under /etc. File integrity monitoring reports that /etc/my.cnf on the DB host left its baseline — the attacker tried to weaken the audit plugin settings for the next boot. FIM proves the file-level edit even without host logs.
    7. Step 7 — The analyst compares last good backup with current data. The analyst pulls the last known-good backup and diffs the balances table. The diff shows exactly which rows changed, when, and by which session — this scopes the incident and becomes evidence.
    8. Step 8 — Restore, rotate, and close the hole. The team restores the changed rows from the trusted backup, rotates the stolen credentials, re-enables and protects the audit configuration so it cannot be switched off silently, and fixes the preconditions: least privilege on the DB host, MFA on admin paths, and FIM coverage on the config files.

    3. Red Team Perspective

    How attackers approach data at rest: their goals, the conditions they need, a safe lab exercise that shows the evidence side, and the mistakes that expose them. Educational use only — practice on systems you own.

    When and why attackers use it

    Changing data at rest is the attacker's way of editing the paperwork. It suits goals where the value sits in the record itself: moving balances, passing an audit, hiding stolen goods inside stock counts, or changing payment details on an invoice. It also serves cover: trimming logs to remove the steps that led to the change.

    Compared with its siblings, the stored variant is the most durable. A transit change (T1565.002) affects one message. A runtime change (T1565.003) disappears when the program closes. A stored change keeps lying until someone compares it with a trusted copy — which is exactly why it appears in the biggest financial crime cases, including Bangladesh Bank 2016 (Section 6).

    Prerequisites and conditions

    Four things must line up. Write access: a database role, a share permission, or local admin. Knowledge: which table, file, or setting holds the value; complex systems need study time. Timing: a window where the write looks plausible or nobody is watching. Evidence awareness: an idea of which logs record the change, so they can be trimmed or switched off.

    Attacks fail when any of these is missing — most often timing, because change calendars and off-hours analytics catch writes that happen outside normal maintenance windows.

    A safe lab exercise

    This exercise uses only a local test database and read-only system tools, so you can study the evidence side of a stored change. Run it on a machine you own.

    lab-only · produce and then detect a stored-record change
    # Lab only — never run on systems you do not own.
# 1. Build a tiny test table
sqlite3 lab.db "CREATE TABLE accounts (id INTEGER, owner TEXT, balance INTEGER);"
sqlite3 lab.db "INSERT INTO accounts VALUES (1,'TRAINING-A',500);"

# 2. Defender step: record a baseline hash of the DB file
sha256sum lab.db | tee baseline.txt

# 3. The tampering action: change a stored record
sqlite3 lab.db "UPDATE accounts SET balance=99000 WHERE id=1;"

# 4. Defender check: the baseline no longer matches
sha256sum lab.db | diff - baseline.txt && echo "no change" || echo "INTEGRITY DRIFT"

# 5. Defender question: what wrote, and when?
stat lab.db; ls -l --time-style=full-iso lab.db
    What you should notice

    Step 4 is the whole defense idea: a cheap baseline makes silent changes loud. In production, the same pattern appears as FIM for files, DB audit rows for statements, and row checksums or ledger tables for critical data.

    Common variations and attacker mistakes

    Variations you will meet

    Selective log trimming — deleting single lines to avoid clear events. Backdated edits — resetting file times to look old. Shadow writes — changing the reporting layer (views, exports) instead of base tables. Snapshot edits — changing data in a copy that is later restored as truth. Each variation still touches something that can be measured: a hash, a timestamp, an audit row, or a cloud log entry.

    Mistakes that expose them

    They test changes against production instead of staging, leaving audit rows. They forget the reporting cache, so numbers disagree between systems. They switch off audit logging and never turn it back on — silencing the very alarm that catches them. And they act without a change-window story, so timing analytics flag the write.

    Danger — lab only

    Never point these workflows at systems you do not own, and never use real customer or patient data in exercises. Changing records without authorization is a crime in most places, regardless of intent.

    4. Blue Team Perspective

    For defenders the question is never only "is the data wrong?" but "who changed it, when, and can I prove it?". This section shows where evidence lives, what artifacts to expect, and a fast triage path.

    How defenders can see it

    Three layers work together. Provenance: database audit and file-integrity records answer "who wrote what, when, from where". Comparison: baselines, checksums, and backup diffs answer "what exactly changed". Correlation: the SIEM links audit rows with process and identity events, turning a quiet UPDATE into a case with a name attached.

    The strongest setup ships audit rows off the host in near real time. Then even a successful local log deletion leaves the remote copy intact — this is the pattern the Section 2 simulation shows.

    What artifacts it leaves

    Expect a trail even after careful attacks: audit rows from unusual client hosts, files whose hashes left the baseline, moved file times, log streams with gaps, restore jobs that changed more than announced, and users reporting numbers that "do not add up". The absence of logs after a period of normal flow is itself a high-value artifact.

    Where to look

    PlaceWhat to collectWhy it matters
    Database audit / DAMStatements, roles, client IPs, row counts, session metadata for sensitive tablesPrimary proof of stored changes and of the account used
    FIM / baselinesHash and time diffs for configs, hosts files, web roots, log directoriesProves file-level edits even without process visibility
    Windows event logs1102 clears, 5136 directory changes, 4663 file access, 4688 process creationCatches log tampering and identity changes behind data edits
    EDR telemetryProcess tree of client tools, script blocks, unsigned writers on protected pathsGives the change a face: which binary, which parent, which user
    Cloud control planeCloudTrail data events on sensitive buckets and backup storesShows object overwrites and deletes that never touch an endpoint
    Backups and exportsLast good backup, row-level diffs, export checksumsIndependent truth for scope and recovery
    Business reportsReport values versus underlying rows, cross-system reconciliationSurfaces manipulation that pure IT telemetry misses

    Why it matters for the SOC

    Stored manipulation attacks the SOC's own raw material: evidence. If logs can be edited or switched off on the host, every other detection weakens. That is why off-host, append-only logging is the foundation, and why audit-gap alerts rank among the highest-value rules a SOC can own. When integrity monitoring and correlation are in place, this technique moves from "invisible crime" to "noisy, well-evidenced case".

    Short triage flow

    1. 1. Verify the change is real. Cross-check the suspicious write against the change calendar, then against the backup diff. Two independent sources beat one.
    2. 2. Freeze the evidence. Snapshot the database or copy the affected files. Export the audit rows for the window. Note which log sources went quiet, and when.
    3. 3. Identify the writer. Follow the account: which host, which process, which parent. EDR process trees usually reveal the entry point quickly.
    4. 4. Scope the blast radius. Count every row or file touched by the same session, account, or tool. Assume more than the alert shows.
    5. 5. Contain. Disable the account, isolate the host, block the path. If logging was switched off, re-enable and protect it first.
    6. 6. Restore and verify. Recover from the last good backup and prove correctness with checksums and a reconciliation report.
    Warning

    If audit logging was disabled, treat every value in the affected period as unproven until it is reconciled against a backup. Re-enabling logging is the first containment step, not an afterthought.

    5. Detection Engineering Deep Dive

    The working core of this guide: regulation mapping, threat intelligence, ranked threats, realistic log patterns, and ready-to-adapt Sigma and SPL rules for the five top-ranked threats.

    5.1 Compliance and Regulation Mapping

    Most organizations think of compliance as a paperwork duty. For stored data it is something stronger: a legal duty to keep records correct and provable. Stored data manipulation attacks that duty directly, and it does so even when nothing is stolen. A silently changed balance, diagnosis code, or payment detail is a failure of integrity whether or not money moves.

    This creates a compliance problem with an unusual shape. A data theft at least leaves gaps you can find. A data alteration leaves false values that people keep using, so the breach continues as long as the wrong data is trusted. Several frameworks therefore require exactly the controls this guide recommends: change detection (FIM, DB audit), protected logs, and tested restores. GDPR is the clearest example — Article 33 treats silent alteration of personal data as a notifiable breach, even if no record left the building.     5.2 Threat Intelligence

    Threat intelligence for stored manipulation answers three questions: which actors target data like yours, how do they reach it, and what do their tools leave behind? You do not need a large team to use it well. You need a small, repeatable workflow and honest confidence labels.

    Sources worth your time

    MITRE ATT&CK gives the shared vocabulary, and its STIX/TAXII feeds can be loaded into tools. CISA advisories (IDs like AA-XX-XXX) carry confirmed indicators. Vendor reports — FireEye/Mandiant, Cisco Talos, Sygnia, Kaspersky, ESET — document the campaigns in the table below. Sector groups such as FS-ISAC share warnings your peers already verified. Sharing platforms like MISP feeds, AlienVault OTX, and VirusTotal collections move indicators between teams.

    From collection to action

    Work in four steps. Collect from a short source list you actually read. Deduplicate — the same indicator arrives from many feeds. Map each campaign to ATT&CK techniques, including T1565.001, so it connects to your detections. Apply: backtest your Sigma rules against the new indicators, write one hunting hypothesis per campaign, and set triage bias so alerts matching top actors jump the queue. Brief leadership with impact, not indicator counts.

    Confidence and refresh

    Label every claim. High means an ATT&CK procedure example or the primary vendor report. Medium means several public reports agree. Confidence goes up when your own telemetry matches the report, and down when a single source claims it. Review the actor list quarterly: campaigns fade, names change, and the behaviors — UPDATE storms, audit disabling, log deletion — stay recognizable even when the group rebrands.

    5.4 Logs and Patterns

    For each threat: the log sources that show it and one realistic sample event (sample event, fields abbreviated). Field names match the SPL in Section 5.5, so you can parse-test the samples against the queries.

    TH-01 — Payment / DB record fraud

    Log sources: MySQL/MariaDB audit plugin (or any DB audit stream), shipped off-host. Watch for: UPDATE/DELETE statements touching balance or amount columns, run by a user account that is not the application service account, from a client IP outside the app tier. After ingestion the rule reads src_user, src_ip, dest, and query.

    6. Real-World Case Study

    The 2016 Bangladesh Bank SWIFT heist is the most studied stored-data-manipulation case. Attackers moved real money and then rewrote and deleted the stored records that would have exposed them. This deep dive stays with the stored-data angle and is based on public reporting, including the FireEye APT38 report and SWIFT customer communications. Counts are reported figures.

    Context

    Bangladesh Bank, the country's central bank, sent payment messages over the SWIFT network through an internal server running the SWIFT Alliance Access software. A group widely attributed to APT38 (also called Lazarus) had operated inside the bank's network for weeks before the fraud. They studied the payment process, captured operator credentials, and prepared malware for the manipulation phase. For this page, one detail matters most: the fraud only worked because the messages were genuine — and it stayed hidden because the stored records behind those messages were edited and deleted.

    The attack chain, step by step

    Public reporting describes this chain. First, the attackers got inside the bank network and moved laterally until they reached the SWIFT interface server. Second, they captured operator credentials for the payment software. Third, on 4–5 February 2016 they submitted 35 fraudulent payment requests worth about 951 million USD to the Federal Reserve Bank of New York. Fourth, the requests carried malware-side cover: per ATT&CK, APT38 used DYEPACK to create, delete, and alter records in the databases used for SWIFT transactions, and FireEye reported an "eraser" component that deleted logs and database records so operators would find no matching entries. Fifth, most requests were blocked — a routing typo ("Dinstiution" instead of "Institution" on a Jupiter Street address) and other technicalities stopped many transfers — but five requests totaling about 81 million USD cleared and moved on through the Philippines.

    The stored-data manipulation is the heart of the case for defenders. Without the record deletion, the mismatch between outgoing messages and stored records would have surfaced within hours. With it, the only surviving signals were physical: a printer that stayed silent when confirmations should print, and records that did not match. This is the classic stored-manipulation failure mode — the attacker deleted the digital evidence, so detection depended on signals outside the attacked system.

    Why detection failed, and what would have worked

    The gaps

    Logs and database records lived on the attacked machines, where the eraser could reach them. No file integrity monitoring watched the SWIFT folder. No database activity monitoring flagged direct record changes outside the application. Nobody alerted on a silent log stream, so deletion itself raised no alarm. Reconciliation between messages and records was manual.

    The counterfactual

    Off-host audit shipping would have preserved the DELETE/UPDATE statements (DET-001's pattern). An ingestion-gap alert would have fired when logs went quiet. FIM on the SWIFT folder would have shown record and configuration changes. Reconciliation would have shown 35 outgoing requests with no matching stored records — the fraud would have surfaced on 5 February, before the money cleared.

    Lessons learned

    • Logs must survive the attacker. Evidence stored only where attackers have admin rights will be edited or deleted. Ship it off-host, append-only.
    • Baseline business-critical databases. Row-level reconciliation against a second source exposes deleted or edited records even when local logs are gone.
    • Watch for audit silence. A quiet log source during active business hours is an alert, not a comfort.
    • Least privilege on payment systems. Operators, the database, and the messaging gateway shared one compromise path; segregation of duties and MFA narrow it.
    • Recovery was limited. About 81M USD left; only about 15M USD was reported recovered. Prevention is cheaper than clawback.
    • Rehearse the scenario. Response quality in the first hours decided how much was recoverable; run integrity-incident tabletops on payment systems.

    7. Mitigation and Defense

    Defense against stored manipulation stands on three pillars: make writes authorized and rare, make every write visible, and make every change reversible. ATT&CK lists three mitigations for this technique; this section maps them to concrete work and adds the practical controls experience adds.

    ATT&CK mitigation mapping

    ATT&CK mitigationATT&CK guidanceHow to implement it here
    M1022 — Restrict File and Directory PermissionsEnsure least privilege principles are applied to important information resources to reduce exposure to data manipulation riskSplit DB admin, app, and backup identities; write access only where a job needs it; jump-host-only access for direct SQL; remove standing write rights nobody uses
    M1053 — Remote Data StorageImplement IT disaster recovery plans with regular backups that can restore organizational data; store backups off-system and protect them3-2-1 backups with one immutable copy outside the attack path; quarterly restore tests with checksums; versioning on cloud buckets holding exports
    M1040 — Encrypt Sensitive InformationConsider encrypting important information to reduce an adversary's ability to perform tailored data modificationsEncrypt sensitive tables and files so casual edit tools fail; pair with integrity checks (hashes, signatures, ledger features) — encryption alone does not prove integrity

    ATT&CK does not list software updating as an official mitigation for this technique, but patching still matters in practice: unpatched database and web servers are the entry path that leads to the stored data in the first place.

    Enterprise controls by area

    Policy and people

    Classify data so "sensitive tables and paths" is a technical list, not an opinion. Write change-window rules precise enough for analytics: who may change which objects, from which hosts, in which hours. Enforce segregation of duties on payment systems — the person who creates a payment must not be the person who approves it.

    Identity

    Least privilege on databases, shares, and log stores. Separate admin identities per role. MFA on all remote and admin paths. Short-lived credentials for service accounts. Watch for identity attribute changes with DET-006, because reset hijack is the fast road to stored data.

    Endpoint

    EDR with tamper protection on servers. Application control so arbitrary clients cannot run. Block Office macros from the internet. Run FIM agents on systems holding critical files, with baselines stored off the host.

    Data stores

    Enable DB auditing on sensitive tables with a protected audit destination. Use row checksums or ledger features where the engine offers them. Restrict direct SQL access to named jump hosts. Keep backups immutable and versioned, including cloud buckets with finance exports.

    Logging and monitoring

    Ship security, DB audit, and application logs off-host in near real time; make the stores append-only. Alert on clears (DET-004) and on ingestion gaps — silence is a signal. Deploy the Section 5.5 rules and validate them monthly with lab tests.

    Response readiness

    Keep an integrity-incident runbook that starts with evidence preservation, not with "fixing" the data. Rehearse the Bangladesh Bank question: if 35 payments left and the records are gone, what proves what happened? Answer it with backup diffs, off-host audit rows, and reconciliation reports.

    Home and small-office advice

    At home, stored-data attacks mostly arrive as ransomware, fake payment requests, or account takeovers that change saved details. Four moves protect you. Keep automatic backups that are offline or immutable, and test a restore twice a year. Use a password manager with unique passwords, so one stolen login cannot reach your files. Turn on two-factor authentication everywhere it is offered, especially for email, banking, and cloud drives. Verify any request to change payment details by calling a number you already trust — never the number in the message.

    Healthy habits

    Daily

    Check pipeline health for every log source — silence is an alert. Review DB audit alerts on sensitive tables. Spot-check one report against its source rows.

    Weekly

    Review FIM deltas with system owners. Verify backup jobs completed and one immutable copy exists. Sweep for new writers in protected paths.

    Monthly

    Validate one detection end to end with a lab test. Re-baseline one system with its owner. Refresh the allowlists. Report integrity metrics upward.

    9. Cheat Sheet

    The whole page compressed for incident use.

    Key facts

    Definition
    Insert, delete, or change data at rest — saved data in databases, files, configs, or logs — to influence outcomes or hide activity
    ATT&CK
    T1565.001 · Impact (TA0040) · Windows, Linux, macOS · v1.1
    Attack chain
    5 steps: gain write access → learn the data model → change stored values → edit or delete evidence → let false records flow
    Best evidence
    DB audit rows, FIM diffs, 1102/5136 events, CloudTrail data events, backup diffs, ingestion gaps
    First response
    Verify with a second source → isolate → preserve evidence → compare to known-good → restore → report

    What to collect

    • DB audit / DAM streams for sensitive tables (shipped off-host)
    • Windows Security 1102 and 5136; Sysmon 1/11 file and process events
    • Linux auditd watches on identity files, web roots, log dirs
    • CloudTrail data events on finance and backup buckets
    • FIM baselines and reports; backup job logs and restore-test results

    Detection rules (from 5.5)

    • DET-001 — direct UPDATE/DELETE on balance or amount columns from non-service users (MySQL audit)
    • DET-002 — writes to /etc/passwd, /etc/shadow, /etc/sudoers (Linux auditd)
    • DET-003 — hosts file modified (Sysmon 11)
    • DET-004 — Windows Security audit log cleared (Event 1102)
    • DET-005 — PutObject on finance/backup buckets by non-allowlisted principals (CloudTrail)
    • DET-006 — sensitive AD attribute changes: mail, phone, proxy, cert mapping (Event 5136)

    Quick SPL queries

    quick · who cleared a Windows audit log?
    -- Tune index/sourcetype names to your environment
index=win sourcetype="XmlWinEventLog:Security" EventCode=1102
| stats count, values(SubjectUserName) AS subjects BY Computer
    quick · recent balance-column changes in MySQL audit
    -- Tune index/sourcetype names to your environment
index=database sourcetype="mysql:audit"
| regex query="(?i)UPDATE\s.+(balance|amount)"
| stats count, values(src_ip) AS client_ips, latest(query) AS sample
    BY src_user, dest
    quick · which log sources went quiet? (10-minute buckets)
    -- Tune index/sourcetype names to your environment
| tstats count WHERE index=database OR index=linux OR index=win
    BY host, index, _time span=10m
| streamstats window=2 current=f sum(count) AS next_count BY host, index
| eval gap=if(count=0 AND next_count>0, "gap suspected", null())
| where isnotnull(gap)
| table _time host index gap
