Runtime Data Manipulation T1565.003

Runtime data manipulation means an attacker changes information inside a running program — in memory, while the data is being read and shown. The files on disk stay clean, so file checks pass, and the screen still shows lies. This v2.0 guide follows the official ATT&CK entry, adds the Stuxnet and APT38 case studies, and gives you tested detection logic.

Overview

Start here to learn what runtime manipulation means, where the official ATT&CK definition comes from, and how this sub-technique differs from its siblings.

The official ATT&CK definition

Adversaries may modify systems in order to manipulate the data as it is accessed and displayed to an end user, thus threatening the integrity of the data. By manipulating runtime data, adversaries may attempt to affect a business process, organizational understanding, and decision making.

Adversaries may alter application binaries used to display data in order to cause runtime manipulations. Adversaries may also conduct Change Default File Association and Masquerading to cause a similar effect. The type of modification and the impact it will have depends on the target application and process as well as the goals and objectives of the adversary. For complex systems, an adversary would likely need special expertise and possibly access to specialized software related to the system that would typically be gained through a prolonged information gathering campaign in order to have the desired impact.

Source: https://attack.mitre.org/techniques/T1565/003/ — ATT&CK v1.2, Impact tactic (TA0040)

What this means in plain words

The attack happens in memory — the working storage of a running program. The files on disk stay untouched, so hashes and file-integrity checks pass. The program then shows or produces false data while it runs. ATT&CK names two main paths: alter the program while it runs (patch its memory or inject code), or swap the program that displays the data (a trojanized viewer, a changed default file association, or a renamed fake tool — Masquerading, T1036).

The official procedure example is APT38, a bank-theft group. Its tool DYEPACK.FOX manipulated PDF data as it was accessed so that fraudulent SWIFT payment transactions disappeared from the statements the staff viewed on screen. The records on disk stayed truthful — only the view lied.

Why it is dangerous

Three defenses fail at once. File checks see nothing, because nothing on disk changed. Server-side logs look normal, because the real database row was never edited. Human review fails, because the fraud appears on a genuine application window that the victim trusts. Only telemetry that watches process behavior — who opened whom, who wrote into whose memory — can expose it.

The attacker needs code running on the endpoint and enough rights to reach the target process. That makes this an Impact-tactic technique: it lands late in an attack chain, after the intrusion already exists.

Note

Terms used on this page: a process is a running program. Injection means placing code into another process and making it run. Hooking means redirecting a program's own function so attacker code runs first. A handle is a permission ticket that one process holds on another. ptrace is the Linux facility to inspect and control another process. In-memory patching means overwriting values or instructions in that memory while the program runs.

The database stays true; the screen lies. The EDR sensor catches the cross-process tampering, and the analyst confirms it with a memory dump.     Written version of the attack story

    The same story as text. It works without JavaScript and matches the animation step by step.

    Full transcript — "Patched while it runs" (8 steps)
    1. Step 1 — Foothold on the reporting host. A finance user opens a phishing payload. It runs as that user from a temp folder. The file on disk is new and unsigned, but no antivirus rule fires yet.
    2. Step 2 — Handle opened on the accounting app. The attacker's tool calls OpenProcess against the running accounting application (finapp.exe) and asks for full rights, including write to memory. Sysmon Event 10 records the pair and the requested rights (GrantedAccess 0x1FFFFF).
    3. Step 3 — Code injected. The tool writes a small payload into the application and starts it with CreateRemoteThread. Sysmon Event 8 shows a remote thread whose start address belongs to no module (StartModule "-") — a classic injected-code signature.
    4. Step 4 — In-memory values patched. The injected code finds the balance and report values in the application's memory and overwrites them. No file changes, no database query, no log on the database side.
    5. Step 5 — Screen shows a fake normal balance. A reviewer opens the report and sees a healthy number. The database still holds the true value. Only the view lies. Server-side checks pass; human review passes.
    6. Step 6 — EDR catches the tampering. The EDR sensor correlates the ProcessAccess with write rights and the remote thread into the business application and raises an alert. Neither event belongs to any allowlisted software pair.
    7. Step 7 — Memory dump confirms it. The analyst captures a triage memory image before remediation. Forensic analysis finds the injected region and the patched values, and compares them with the database. The mismatch proves runtime manipulation.
    8. Step 8 — Restore from known good and tune. The team isolates the host, restarts the application from a known-good binary, blocks the payload source, and feeds the confirmed true positive back into the DET-001 and DET-002 rules and their allowlists.

    Red Team Perspective

    How attackers approach runtime manipulation: goals, conditions, mechanics at a conceptual level, and the mistakes that expose them. Educational use only — practice only in labs you own.

    When and why attackers use it

    Runtime manipulation is chosen when the value sits inside a running application: a finance report, an ERP approval, a trading terminal, an HMI panel in a plant, or a PDF viewer that renders payment statements. Editing memory avoids three defenses at once: disk integrity checks, file signatures, and most user suspicion. The screen shows what the attacker wants, so the victim cooperates.

    It also hides scale. One loader can target many applications by loading different rules at runtime, with no new file dropped per target. APT38's DYEPACK.FOX shows the specialized end of this: a tool built to change PDF data as it is accessed, so hidden fraud never appears in the rendered statement.

    Prerequisites and conditions

    Four needs. Code execution on the endpoint, usually from a phishing payload, a trojanized installer, or a compromised update. Enough rights to reach the target process — the same user account is usually enough for user-mode apps, while kernel or driver paths need admin or a vulnerable driver. Target knowledge: process names, window titles, memory offsets, or file-format markers that identify the right moment and address. Stealth: the patch must survive redraws and focus changes without crashing the host process.

    What you should notice

    Healthy systems produce process-access events too — from EDR agents, updaters, and developer tools. The detection problem is allowlisting known-good pairs and alerting on the rest, which is exactly what the tuning notes in section 5.5 address.

    Common variations and attacker mistakes

    Variations you will meet

    Display-only fakes — change what is drawn, nothing else. Form rewriting — alter data at submit time. Clipboard swapping — replace wallet addresses in memory or clipboard at paste time. Config-driven flexibility — one loader, many targets via downloaded rules. Hardware-adjacent — HMI and payment software patched at runtime through vendor tooling or a compromised engineering host.

    Mistakes that expose them

    They crash the host process (users notice), leave unsigned modules mapped in signed applications, run debuggers on production hosts where no debugger belongs, load unsigned or vulnerable drivers that EDR vendors blocklist, and fetch runtime configs from domains that threat feeds already know. Sloppy hooks also break certificate checks and produce visible errors.

    Danger

    Do not experiment with injection, hooking, or ptrace on real banking, trading, industrial, or payment systems, and never on machines you do not own. Beyond legal risk, these techniques exist to commit fraud against real people. Keep practice inside isolated labs with synthetic targets.

    Blue Team Perspective

    Runtime manipulation is an endpoint-visibility problem. This section shows which telemetry sees it, what artifacts to collect, and how to triage cross-process alerts without drowning in noise.

    How defenders can see it

    Five telemetry layers. Cross-process behavior: Sysmon 8 (remote thread) and 10 (process access) show who touched whom and with which rights. Load integrity: Sysmon 6 and 7 plus EDR module lists flag unsigned or vulnerable drivers and unsigned modules inside signed apps. Script and tool telemetry: PowerShell 4104 script blocks and Sysmon 1 catches script-driven hooking and debugger use. Linux syscalls: auditd records ptrace with the calling executable. Behavioral: memory forensics confirms the injected regions, and business checks compare what a display showed against a second source of the same data.

    What artifacts it leaves

    Expect CreateRemoteThread events into business applications, open-process handles with write or VM-operation rights from non-allowlisted sources, unsigned modules in signed processes, debugger or automation tools on production hosts, unsigned driver loads, and crashed or restarted target applications. Memory captured in time shows the injected regions themselves. None of this appears in file-integrity or database logs — that absence is itself a clue when a display mismatch exists.

    Where to look

    PlaceWhat to collectWhy it matters
    Sysmon 8 / 10SourceImage, TargetImage, GrantedAccess, StartModule, CallTraceThe core cross-process tamper evidence (DET-001, DET-002)
    Sysmon 1 / 6Debugger binary executions; driver loads with Signed and Signature fieldsCatches debugger use (DET-003) and kernel-path tampering (DET-005)
    auditd (Linux)SYSCALL records for ptrace with exe, auid, ppidSame story on Linux, with syscall-level evidence (DET-004)
    EDR memory-tamper eventsInjection blocks, hook detections, unsigned-module alertsVendor-tuned versions of the same signals; useful corroboration
    PowerShell 4104Script blocks declaring SetWindowsHookEx, WriteProcessMemory, CreateRemoteThreadCatches script-driven hooking attempts
    Memory forensicsTriage RAM capture of the suspect process; module and code-region listsConfirms injected regions and patched values after the fact
    Business second sourceDatabase value vs displayed value; sensor reading vs HMI valueTurns "possible tampering" into a proven display lie

    Why it matters for the SOC

    Cross-process alerts are noisy: updaters, EDR agents, and developer tools create legitimate events. The differentiator is target quality — injection or write access into a finance, ERP, payment, or HMI process is never routine. Teams that allowlist known-good source/target pairs and alert on the rest get a high-precision signal. Correlating that signal with a business mismatch (the number on screen differs from the number in the database) upgrades the case from hypothesis to confirmed impact.

    Short triage flow

    1. 1. Classify the pair. Source process → target process. Known-good pairs (EDR, updater, APM) get closed; anything touching business apps, browsers on finance hosts, or HMI software continues.
    2. 2. Read the rights and lineage. GrantedAccess shows intent (read vs write vs VM operations). The parent lineage shows how the source process arrived on the host.
    3. 3. Freeze the evidence. Capture a triage memory image and module lists before remediation — injected regions are volatile and vanish on reboot.
    4. 4. Check the second source. Compare the displayed values with the database or sensor values for the same period. A mismatch proves the manipulation and scopes the fraud window.
    5. 5. Contain. Isolate the host, kill the affected sessions, block the payload source. Restart the application from a known-good binary; rebuild the host rather than cleaning it.
    6. 6. Feed back. Add the source binary to denylists, tune the DET rules, and add the case pattern to your correlation searches.
    Warning

    Do not "fix" a tampered host by killing the payload and moving on. Without a memory capture you lose the proof; without a rebuild you keep a host whose trust is broken; and without session revocation the attacker keeps the stolen access even after the alert closes.

    Detection Engineering Deep Dive

    The working core for runtime manipulation: compliance mapping, threat intelligence, ranked threats, realistic endpoint log patterns, and ready-to-adapt Sigma and Splunk rules for injection, debugger use, ptrace, and driver tampering.

    5.1 Compliance and Regulation Mapping

    Integrity attacks are a compliance problem even when nothing is stolen. A manipulated balance, report, or sensor reading changes decisions: staff release payments, managers approve limits, operators keep processes running. Nothing may leave the network, yet the organization has already acted on false data, and that is the exact risk that integrity rules are written for. Silent alteration also breaks the duty to keep accurate records. If personal or payment data is changed without permission, GDPR treats it as a personal-data breach even when no record leaves the building, so the 72-hour notification clock can start with no "theft" at all. Regulators therefore care about two things: can you detect that data in use was changed, and can you prove which values were true. The table below maps each framework to the controls that runtime manipulation threatens and to the detection hooks in section 5.5.

    How auditors test it

    Auditors ask for evidence, not promises. Typical asks: file-integrity monitoring (FIM) reports for application and viewer folders, database audit configurations and sample rows, log-review records with sign-off, change tickets matched against detected changes, and the alert history of your cross-process detection rules. Keep one quarter of DET-rule alert handling and two resolved tampering drills as ready evidence.

    The intelligence workflow, step by step

    Collect and deduplicate

    Pull from a small, stable set of sources: MITRE ATT&CK (and its STIX/TAXII feeds), CISA advisories (AA-XX-XXX format), vendor reports — FireEye/Mandiant, Cisco Talos, Sygnia, Kaspersky, ESET — sector ISACs such as FS-ISAC, MISP feeds, AlienVault OTX, and VirusTotal collections. Deduplicate: one behavior seen in five reports is one intelligence record, not five.

    Map and apply

    Map each record to ATT&CK (this page is T1565.003). Then apply it: backtest your Sigma rules from 5.5 against the new reporting, write one hunting hypothesis per campaign (for example, "unsigned module mapped in finapp.exe"), bias triage toward your top actors, and brief leadership with the business risk, not the malware trivia. Review actor and campaign relevance quarterly; refresh sooner after a major vendor report.

    How to use this table

    Family names churn; behavior endures. The durable shapes are: write-capable handles into business processes, module-less remote threads, debugger use on production, unsigned drivers, and display values that disagree with the stored truth. The detections in 5.5 target those shapes, not the names.

    Tuning and false positives

    Cross-process telemetry is noisy by nature, so allowlist discipline decides whether these rules survive their first month. Build the allowlist from observed evidence: one week of Sysmon 8/10 on a reference group gives you the real source/target pairs, including EDR agents, APM profilers, and updaters. Allowlist by signed source path plus vendor, never by file name alone, and route every new allowlist entry through change management with an owner and an expiry date. Re-test after every tuning change: keep one recorded benign replay and one confirmed true positive per rule, so you can prove the rule still catches the attack. Expect DET-001 and DET-002 to be nearly silent on a clean estate — silence is the point; a single hit is then a case, not a needle to find.     Real-World Case Study

    Stuxnet (discovered 2010) is the clearest public case of runtime data manipulation: the code changed what operators saw while machines broke. We pair it with ATT&CK's enterprise-native example — APT38's DYEPACK.FOX — so the lesson maps directly to corporate endpoints. Facts below are hedged public reporting; counts are approximate.

    Context

    Stuxnet is a worm that targeted industrial control systems — the computers that run factories and plants. Public research places its main target at the Natanz enrichment plant in Iran, where cascades of IR-1 gas centrifuges spin uranium hexafluoride gas. The worm was built around Siemens STEP 7 software and S7-315 and S7-417 PLCs (programmable logic controllers — small industrial computers that drive machinery). It reached isolated networks on USB drives, using a Windows shortcut-file vulnerability (MS10-046), and also spread over networks using several file-sharing and print-spooler exploits. To stay trusted, it signed its drivers with two stolen code-signing certificates (Realtek and JMicron) — a shocking detail in 2010, because the signatures belonged to real, reputable hardware vendors.

    The runtime manipulation itself

    On the compromised systems, Stuxnet injected code into STEP 7 and communicated with the PLCs. It changed the centrifuge speeds — researchers documented sequences that pushed rotors up and down across safe limits — and it manipulated the process values that operators saw, so panels kept showing safe, normal readings. Researchers describe a replay technique: recorded normal-state values were fed back to the displays while the real machines ran outside their limits. The stored engineering data stayed plausible; the view lied; operators had no reason to intervene. This is exactly the T1565.003 pattern — data altered as it is accessed and displayed — executed against industrial software instead of a bank application.

    The enterprise-native counterpart is APT38, the bank-theft group ATT&CK lists as the procedure example. FireEye's October 2018 report documents that APT38 used DYEPACK.FOX to manipulate PDF data as it was accessed, removing traces of fraudulent SWIFT transactions from the statements displayed to bank staff. Same shape as Stuxnet, different target: the record on disk stayed truthful, the rendered view hid the fraud, and employees approved what they saw.

    Detection story and response

    Stuxnet was not found by the plants it hit. It surfaced in June 2010 when VirusBlokAda, an antivirus company in Belarus, examined samples and published its discovery. Symantec, Kaspersky, and control-systems expert Ralph Langner then reverse-engineered the code. Three findings drove the response: the stolen Realtek/JMicron signing certificates (a trust failure at vendors, not at the victim), the LNK zero-day that spread it, and the PLC payload that proved manipulation of both machinery and displays. Siemens issued detection and removal tools; ICS-CERT published advisories; and the incident moved industrial control security from a niche topic to a board-level one. In the APT38 case, bank incident-response teams engaged FireEye, which tied the display tampering to fraudulent SWIFT transfers; SWIFT's customer security programme followed industry-wide in 2016 after related bank attacks.

    PeriodEvent

    Impact and consequences

    Public reporting attributes the failure of about 1,000 IR-1 centrifuges to the campaign — an unusually precise number in threat intelligence, sourced to inspection-based assessments. The harder impact was conceptual: a program could damage physical equipment while every display said "normal". For banks, the DYEPACK.FOX lesson is the mirror image: staff reconciled statements that hid the attacker's transfers. Both cases shifted integrity from a storage concern to a display concern.

    Which teams responded, and how

    An antivirus vendor (VirusBlokAda) made the first publication. Vendor researchers (Symantec, Kaspersky, Ralph Langner) performed the deep reverse engineering. Siemens supported detection and cleanup for its customers. ICS-CERT and regulators spread advisories and pushed segmentation and integrity controls into industrial guidance. Plant operators hardened engineering workstations and removable-media use. In the bank cases, internal security teams ran incident response with external forensics (FireEye), the SWIFT community tightened controls, and central banks pressed for reconciliation between displayed statements and record-level data.

    Lessons learned

    • The display is not evidence. Stuxnet kept panels normal while machines failed; DYEPACK.FOX kept statements clean while fraud ran. Compare what is shown against a second source — a database value, a sensor, a computed checksum — and alert on disagreement.
    • Code signing is not proof of safety. Stuxnet's drivers carried valid signatures from stolen vendor certificates. Protect signing keys, and treat "signed" as one signal among several.
    • Air gaps leak. USB drives carried the worm past the perimeter. Control removable media and monitor the hosts adjacent to "isolated" networks.
    • Runtime manipulation has enterprise telemetry. Injection into STEP 7 or an HMI produces the same Sysmon 8/10 shapes as injection into a finance app — run DET-002 on engineering hosts.
    • Tampering aims at trust. The attacker needs your operator, accountant, or reviewer to act. Train staff to report display oddities, and treat such reports as signals, not noise.
    • Recovery means re-establishing truth. After discovery, teams restored from known-good images and revalidated displayed values against record-level data before trusting either again.
    7

    Mitigation and Defense

    Defense against runtime manipulation has three layers: make injection hard, make tampering visible, and limit what one compromised endpoint can do. Official ATT&CK mitigations come first, then practical enterprise controls, then home advice.

    Official ATT&CK mitigations

    ATT&CK lists exactly two mitigations for T1565.003. Treat them as the official baseline:

    MitigationIDOfficial ATT&CK note
    Network SegmentationM1030Identify critical business and system processes that may be targeted by adversaries and work to isolate and secure those systems against unauthorized access and tampering.
    Restrict File and Directory PermissionsM1022Prevent critical business and system processes from being replaced, overwritten, or reconfigured to load potentially malicious code.
    Note on patching

    ATT&CK does not map M1051 (Update Software) to this technique. Patching is still recommended here as practical defense: fewer exploitable footholds means fewer paths to the code execution this technique needs. Keep it as good practice, not as an official mapping.

    Enterprise controls by area

    Endpoint

    EDR with tamper protection and injection detection; exploit-mitigation policies (arbitrary code guard, child-process limits) for business applications; application control (WDAC or AppLocker) on servers, payment, and engineering endpoints. Deploy Sysmon with Events 1, 6, 8, and 10 enabled.

    Identity and privilege

    Run business applications as standard user; remove local admin from finance and engineering workstations; separate admin identities from daily accounts. Injection usually needs the target user's rights — less privilege means less reach.

    Application integrity

    M1022 in practice: write-protect application and viewer directories; sign and verify business binaries; block user-writable paths from loading modules into signed apps; enforce driver-signature policy and a vulnerable-driver blocklist; keep known-good binaries for fast restore.

    Monitoring

    Sysmon 8/10 collection with the DET-001/DET-002 allowlist workflow; DET-003 debugger policy on production hosts; DET-004 auditd ptrace rules on Linux servers; DET-005 unsigned-driver alerting; PowerShell 4104 script blocks; and display-vs-source reconciliation for finance and HMI values.

    Network and OT (M1030 in practice)

    Segment payment and industrial VLANs away from user networks; restrict which hosts may reach engineering workstations; block payload and config infrastructure via DNS and proxy; on OT, add protocol monitoring for unexpected write function codes with no maintenance ticket.

    Response

    Injection runbook: capture triage memory before remediation; classify the source→target pair; compare displayed values with the second source; isolate the host; restart the app from a known-good binary or rebuild; revoke sessions and rotate credentials; notify fraud. Rehearse quarterly with a simulated injection alert.

    Home and small-office advice

    Home users meet runtime manipulation as banking fraud or wallet theft. Keep the browser and operating system updated — modern versions carry strong injection mitigations. Install software only from official stores; the payload in our simulation came from a temp-folder helper, the classic pattern after a bad download. Leave your OS protections on (SmartScreen and App Control on Windows, Gatekeeper on macOS) and never approve unsigned helpers. Prefer your bank's official app over the browser, and enable transaction notifications so a manipulated payment shows on your phone within seconds. If you use cryptocurrency wallets, verify the receiving address on the device screen, not only in the clipboard paste.

    Cheat Sheet

    The whole page compressed for incident use.

    Key facts

    Definition
    Adversaries modify systems to manipulate data as it is accessed and displayed to an end user (T1565.003, Impact).
    Target
    Memory of running processes: business apps, viewers, browsers, HMI and payment software
    Core idea
    Inject, hook, or patch so the program displays and submits false data while files and databases stay clean
    Best evidence
    Sysmon 8/10 pairs, unsigned modules in signed apps, debugger use, unsigned drivers, ptrace, display-vs-source mismatch
    Official mitigations
    M1030 Network Segmentation · M1022 Restrict File and Directory Permissions
    First response
    Verify with second source → isolate → preserve memory evidence → compare to known-good → restore → report

    Attack chain in five bullets

    • Foothold: code execution on the endpoint (payload, trojanized installer, abused update)
    • Reach: open a handle to the target process with write or VM rights (Sysmon 10)
    • Install: inject code or attach a debugger (Sysmon 8/1, auditd ptrace)
    • Manipulate: patch in-memory values, hook display or submit paths, or swap the viewer
    • Profit or cover: trigger the fraudulent action while the screen and logs look normal

    DET rules

    • DET-001 — remote thread into a business application (Sysmon 8)
    • DET-002 — write-capable access into a critical process (Sysmon 10)
    • DET-003 — debugger binary on production or finance host (Sysmon 1)
    • DET-004 — ptrace by unexpected binary (Linux auditd)
    • DET-005 — unsigned driver load (Sysmon 6)

    What to collect

    • Sysmon Events 1, 6, 8, 10 with default field names
    • EDR memory-tamper, hook-detection, and injection events; module lists
    • Linux auditd SYSCALL records for ptrace (rule key ptrace_watch)
    • PowerShell 4104 script blocks; Defender Operational 1116 detections
    • Business side: displayed values vs database values, HMI values vs independent sensors

    Quick SPL — write-capable access (24h)

    splunk · triage query
    -- Tune index/sourcetype names to your environment
index=edr sourcetype="XmlWinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=10
    earliest=-24h
    GrantedAccess IN ("*0x1F0FFF*", "*0x1FFFFF*", "*0x143A*", "*0x1410*", "*0x1A0FFF*")
| stats count AS events, values(TargetImage) AS targets, values(SourceImage) AS sources BY host
