MITRE ATT&CK · EXFILTRATION · TA0010

T1567Exfiltration Over Web Service

Data is sent to a trusted third-party web service — a cloud drive, a code site, a paste page, or a chat webhook — so the stolen traffic hides inside normal HTTPS to popular sites. HTTPS is the encrypted protocol that carries the web, so the stolen bytes look like everyday browsing. This page teaches you how the move works, what it looks like in your logs, and how to write detections that catch it.

Tactic: Exfiltration ID: T1567 Platforms: ESXi · Linux · Office Suite · SaaS · Windows · macOS Sub-techniques: .001 Code Repository · .002 Cloud Storage · .003 Text Storage Sites · .004 Webhook Type: Technique ATT&CK Version 1.5 Created 09 March 2020 Last modified 12 May 2026

What happens

Stolen data is uploaded to a popular SaaS (software-as-a-service) site the attacker does not own, such as a file host or a code repository.

Chain position

Final stage. It comes after the attacker has collected and archived the data they want.

Biggest risk

The traffic blends with real SaaS use. The same trusted service can even carry attacker command-and-control and stolen data at once.

Detect with

Proxy and secure web gateway (SWG) logs, cloud access security broker (CASB) alerts, DNS (domain name system) queries, upload-volume baselines, and rare user agents on large POST (data-sending web) requests.

Overview

What this technique is, why it hurts, and what you will learn on this page.

Exfiltration Over Web Service means an attacker sends stolen data out of your network through a popular web service that you already trust. Think of a well-known cloud drive, a code hosting site, a public paste page, or a chat app with incoming webhooks. The connection is normal HTTPS to a domain with a good reputation. Your firewall usually allows it. Your users use the same services every day. That is exactly why attackers like it: the stolen data rides on a road that nobody wants to close.

The technique sits at the very end of the attack chain. By the time data leaves, the attacker is already inside, has found the files, and has usually archived them (see T1560 Archive Collected Data and T1074 Data Staged). Exfiltration is the moment the loss becomes real. After a successful upload, the attacker holds a copy that you cannot delete, and that copy can drive extortion, fraud, or spying. This is also why exfiltration is often paired with ransomware: crews steal data first and threaten to publish it if you do not pay.

MITRE ATT&CK splits this technique into four sub-techniques. Each one deserves its own attention on your detection roadmap, and each has a dedicated guide page linked below.

MITRE lists the official platforms for T1567 as ESXi, Linux, Office Suite, SaaS, Windows, and macOS. The three entries beyond the desktop operating systems are worth a pause. ESXi is VMware’s virtualization host platform — one ESXi machine can run dozens of virtual machines, so an upload from it can drain every guest at once. Office Suite and SaaS mean the technique also covers abuse of cloud office tenants themselves. One example: an attacker grants an OAuth application — an app authorized through the tenant’s identity system — permission to read files from your managed office tenant. Any host or tenant with web egress is in scope.

Note — Why this page matters to you. Endpoint tools often miss this technique, because uploading a file with curl, a browser, or a sync client looks harmless. The strongest signals usually live in egress telemetry: proxy and secure web gateway logs, CASB inventories, DNS queries, and upload-volume baselines. The full written story (text alternative)

  1. Beachhead. A phishing email gave the attacker a foothold on the workstation. A user opened an attachment and the malware called home. Defender view: nothing yet — no alert has fired; EDR will show the phishing process only in a later hunt.
  2. Finding the valuables. The attacker lists the finance and personal-data folders, looking for the best files to steal. Defender view: EDR later shows odd dir and Get-ChildItem sweeps between 02:00 and 04:00 — a night-time inventory nobody does by hand. Evidence: EDR sweep.
  3. Packing. The attacker zips the chosen folders with a password into %TEMP%\reports.zip, a name that imitates normal business reports. Defender view: an archive tool appears on a host where it was never seen before, and the archive name mimics a finance report. Evidence: Archive create.
  4. Choosing a trusted road out. The attacker picks a well-known file-sharing site — not because it is special, but because company policy allows that category. Defender view: still no alert, and this is the design problem: the category is “allowed”, the destination is trusted, and nobody has baselined how much data should leave this subnet.
  5. The upload. The workstation pushes roughly 800 MB with steady HTTPS POST requests — POST is the web request method that sends data to a server; the user agent pretends to be a normal sync tool. Defender view: the proxy writes one row per request — URL, bytes out, user agent — and the per-host volume crosses its 30-day baseline. Evidence: Proxy POST row.
  6. The SOC sees something new. Correlation shows a first-ever SaaS category from this subnet plus a rare user agent. Defender view: a CASB “unmanaged app” alert fires; the analyst opens a ticket and calls the user. Evidence: CASB unmanaged-app alert.
  7. Attacker retrieves. On their own machine, outside your network, the attacker downloads the archive from the service using their account. Defender view: nothing in the corporate network — this hop happens entirely outside your telemetry. That blind spot is why early detection of the upload matters so much.
  8. Verdict. The SOC links the baseline break, the new SaaS category, and the staged archive into one incident. Egress policy for storage categories is rewritten; consumer storage is blocked by default. Defender view: the lasting lesson — baselines beat single events, because the volume change was visible before any signature knew the tool. Evidence: Baseline-break ticket, Egress policy change.

Good practice — Read steps 4 and 7 again. Step 4 shows that an allow-listed category without a volume baseline is a silent door. Step 7 shows that once the data sits on the service, the attacker can collect it from anywhere. Your best chance to stop the loss is between those two moments: detect the unusual upload while it is still leaving.

Red Team / Hacker Perspective

Why attackers pick a trusted web service as their exit path, what they need first, and how authorized labs rehearse it safely.

From the attacker’s side, this technique solves three expensive problems at once. First, reachability: HTTPS to popular SaaS sites is allowed in almost every company, so no firewall change or tunnel is needed. Second, cost: free accounts and free tiers cost the attacker nothing, and a flagged account can be replaced in minutes. Third, attribution: the traffic points at a famous service, not at attacker infrastructure, so there is no server to register, pay for, or get seized. Some services also give a stable URL or credential model, which lets the attacker keep using the same exit for weeks.

When and where attackers use it

In time, this technique appears at the end of an intrusion, after the attacker has collected and archived data. It often runs outside business hours, when volume changes attract less attention. In place, it works from any host that may reach the chosen service: user workstations, servers, and build systems. Per the official platform list, it also covers ESXi virtualization hosts draining whole datastores, and managed SaaS tenants abused from inside. The four sub-technique pages show the same pattern specialized to code sites, cloud drives, paste pages, and chat webhooks.

Attackers choose the variant that fits the stolen data. Big archives of documents go to consumer cloud storage (rclone against a personal drive account is the classic modern pattern). Source code and its history go to a code repository, often pushed straight with git. Small, high-value items such as passwords, VPN (virtual private network) settings, and database dumps fit neatly into paste sites. Chat webhooks are a common choice for infostealer operators: a single POST delivers the stolen logs, and the same channel can carry attacker instructions back. The four variants are described in depth on the sub-technique pages: T1567.001 code repository, T1567.002 cloud storage, T1567.003 text storage, and T1567.004 webhook.

Prerequisites an attacker needs

  • A foothold with egress. The compromised host must be allowed to reach the service. On user networks this is nearly always true; on server VLANs (isolated network segments) it is the main thing attackers check first.
  • Collected, staged data. Exfiltration comes late. Files are usually listed, copied, and archived (often password-protected) before the first upload.
  • An account or an address. A free account on the service, an anonymous paste, or a webhook URL. Webhooks are the weakest link: one leaked URL is enough for anyone to post.
  • Patience with volume. Steady, chunked uploads look more like a sync client than a giant one-off transfer, so attackers pace the traffic.

Danger — LAB-ONLY The commands below are for rehearsal on machines and tenants you own, with fake or synthetic data, and with written authorization. Never point them at a real company, a real user’s data, or a service account you are not allowed to use.

Common variations

  • Consumer storage with a real client. The rclone-to-Mega pattern: a purpose-built sync tool, a personal account, and chunked uploads that imitate normal traffic.
  • Code hosting as a drop box. A git push of an entire repository, or a bundle file attached through the web UI. Covered on the T1567.001 page.
  • Paste sites for small dumps. One POST with curl from a non-browser process; no account needed on many sites. Covered on the T1567.003 page.
  • Chat webhooks. A single HTTPS POST to a webhook URL drops files or text straight into a channel. Covered on the T1567.004 page.

Mistakes attackers make (and you should expect)

  • Uploading the entire user profile. It is far too big and too slow; it creates a huge volume spike and often times out. What lands in your logs is a beautiful anomaly — use it.
  • Ignoring rate limits. Free tiers throttle aggressively. Retries and back-offs look strange in proxy logs and stretch the transfer window, giving defenders more time to catch it.
  • Reusing an already-flagged account. Accounts reported for abuse are watched by the provider too, so uploads can fail silently or be quarantined.

Note — Every one of those attacker mistakes is a defender opportunity. Oversized transfers, retry storms, and failing uploads all write loud rows into egress logs. Section 5 builds detections on exactly these cracks.

Blue Team / SOC Perspective

How this technique shows up for defenders, which artifacts it leaves, and a triage flow you can run the moment an upload anomaly appears.

Defenders rarely see this technique on the endpoint first. The strongest picture comes from the network egress side. The proxy or secure web gateway sees every request. The CASB knows which SaaS apps are managed versus personal. DNS shows which storage endpoints hosts try to resolve. The endpoint still matters: EDR can name the process that opened the connection and show the archive it read. Even so, the “something big is leaving” signal is almost always a network signal.

The uncomfortable truth is that a single proxy row proves very little. One 40 MB upload can be a design file going to a partner. The technique becomes visible when you compare against a baseline: this host, this subnet, this hour, this category — how much data normally leaves, and how different is now? That is why the story in section 2 ends with one lesson: baselines beat single events.

Why it matters and how it fits the chain

Exfiltration is the last chance to reduce harm. Catching it before the transfer completes can save an entire customer database from a leak-site listing, and in double-extortion ransomware cases it removes the crew’s main leverage. In the chain, you are watching the road between T1074 Data Staged / T1560 Archive Collected Data on your side and the attacker’s hands on the other side. A good egress control set also helps with T1048 (alternative protocols) and T1041 (exfil over the C2 channel), because the same baselines and the same logs apply.

Triage flow: from volume anomaly to containment

  1. Confirm the volume anomaly. Compare bytes out for the host and user against their 30-day baseline. Is this 10× normal, or just month-end reporting?
  2. Check category and user agent. Which SaaS category received the traffic? Which client sent it — a browser, a sync tool, curl? A rare agent on a large POST is a strong flag.
  3. Identify host and user. Pull the proxy row’s source IP (the machine’s network address) into asset and identity context. Is this a workstation, a jump host, or a server that should never talk to consumer storage?
  4. Look for staging on the host. With EDR, check for recently created archives (zip, 7z, tar), password flags, and the process that created them — especially in temp folders.
  5. Confirm the content. Use DLP matches or a safe sample to verify the data was actually sensitive. Note the file names and sizes involved.
  6. Contain. If the transfer is still running, block the destination at the proxy or firewall and isolate the host. Preserve the evidence, then decide on the response with the incident owner.

Good practice — Keep a saved timeline query for “bytes out by host per hour” in your SIEM. When the anomaly call comes, the first three triage steps take minutes, not hours, because the comparison view already exists.

Detection Engineering Deep Dive

The working core of this page: compliance anchors, threat intelligence, a ranked threat model, the logs that expose each threat, and ready-to-adapt Sigma and Splunk rules.

Everything in this section follows one idea: for exfiltration over web services, the most valuable telemetry is egress telemetry, and the most valuable detection pattern is change against a baseline. Single events — one upload, one DNS query — are usually legal business behavior. Combinations and deviations are what turn rows into incidents. 5.2 Threat intelligence

Threat intel makes your detections smarter before you get hit. The workflow has three phases. Collection: pull reports, indicators, and ATT&CK updates into one place your team actually reads. Analysis: decide what is relevant for your stack — for T1567 that means tool names (rclone, azcopy, MEGAync), service domains and API hosts, user agents, and behavior patterns like “archive first, upload at night.” Application: turn those findings into tuning notes, watchlists, and new rules, then measure whether the intel actually changed your detections. Intel that never reaches a rule or a hunt is decoration.

Sources worth wiring into that loop

Free and authoritative

  • MITRE ATT&CK site + STIX/TAXII — the technique definition, sub-technique changes, and machine-readable data (STIX/TAXII are the standard format and transport for sharing threat data) to feed your own tooling.
  • abuse.ch — malware and infrastructure blocklists that flag known bad upload destinations.
  • malware-traffic-analysis.net — real packet captures and PCAP write-ups showing exfil traffic patterns.
  • Any.run and vx-underground — interactive sandbox runs and sample collections where upload behavior is visible.

Vendor, commercial, community

  • Vendor blogs (Microsoft, Mandiant, CrowdStrike, ESET, Kaspersky, Red Canary) — deep reports such as Red Canary’s 2021 rclone-to-Mega extortion coverage.
  • Commercial feeds (Recorded Future, VirusTotal) — domain reputation, newly registered domains, and C2 (command-and-control) infrastructure tagging.
  • ISACs (information sharing and analysis centers) — MS-ISAC, FS-ISAC, H-ISAC, E-ISAC, and ICS-ISAC share sector-relevant incidents, including SaaS abuse patterns.
  • Internal telemetry — your past incidents, honeypots, and EDR history. The best “new tool” watchlist is the one seeded with what you already caught.

Threat 1 · Exfil to consumer cloud storage (rclone / Mega style)

Threat 2 · Exfil to code repository

Log sources and key fields. Proxy logs (method, url, user_agent, src_ip), EDR process events for git.exe with command lines, and — if you run one — your own code-hosting audit log. Key extra field: the role of the source host (workstation vs server), taken from your asset inventory.

Normal behaviorSuspicious behavior
Developers push from named workstations to the corporate org; CI (continuous integration) runners fetch, they rarely push; agents are git or browsers Push traffic (git-receive-pack) from server subnets; personal-space URLs; pushes outside CI windows; oversized bundles

Detection logic. Alert on POST .../git-receive-pack (or push endpoints of public hosts) originating from server or CI subnets, or to any repository outside your approved organization list.

Example · proxy access log (key=value)
ts=2025-03-05T04:02:11Z src=10.20.30.44 host=srv-app01 method=POST
url=https://github.com/nightbuild-archive/svc-creds/git-receive-pack cat=Code-Hosting
bytes_out=12884901 bytes_in=512 ua="git/2.43.0" decision=allow rule=EGRESS-GEN-HTTPS
  • src + host — srv-app01 lives in a server VLAN; servers pushing to public git hosts is the core anomaly.
  • url — path ends in git-receive-pack, which means a push, not a fetch; the account nightbuild-archive is not your org.
  • bytes_out — ~12 MB upward in one POST; backups of whole repos show much larger values.

Threat 3 · Exfil via chat / webhook services

Log sources and key fields. DNS logs (query, src_ip, answer), proxy/SNI logs for the API (application programming interface) hosts, EDR process-to-network correlation (which process resolved and contacted the endpoint). Key chat API names: discord.com/api, discordapp.com, api.telegram.org, hooks.slack.com.

Normal behaviorSuspicious behavior
Users reach chat apps from browsers or the official desktop client; your own workspace hosts only; daytime rhythm API or webhook hosts contacted by non-browser processes; workspaces you have never seen; bursts of small POSTs from a single host

Detection logic. Alert when a non-browser process on an endpoint queries or connects to a chat API/webhook host, especially outside your sanctioned workspace names.

Example · DNS query log (JSON view)
{
  "ts": "2025-03-05T22:41:07Z", "client": "10.12.8.77", "host": "WS-SALES-09",
  "query": "discord.com", "qtype": "A",
  "answers": ["162.159.128.233"], "process": "certutil.exe",
  "rcode": "NOERROR"

  • process — enriched from EDR; certutil.exe doing chat lookups is a known hand-off tool for small dumps.
  • client + host — pinpoints the endpoint for the responder to isolate and inspect.

Threat 4 · Exfil to text / paste sites

Log sources and key fields. Proxy logs (method, url, user_agent, bytes_out), DNS for paste domains, EDR for the calling process. The user agent is the pivot: curl, wget, and script runtimes posting to paste domains is almost never a human workflow.

Normal behaviorSuspicious behavior
Almost none from work hosts; a rare browser GET to a paste link a user clicked; tiny bytes_out POST requests to paste domains; browser-less agents; repeated POSTs from servers or build hosts; content sizes in the megabytes

Detection logic. Alert on POST requests to known paste domains where the user agent is a command-line tool (curl, wget, PowerShell, python-requests) or the source is a server subnet.

Example · proxy access log (key=value)
ts=2025-03-05T02:58:44Z src=10.20.30.44 host=srv-app01 method=POST
url=https://pastebin.com/api/api_post.php cat=Text-Storage bytes_out=48211 bytes_in=96
ua="curl/8.5.0" decision=allow rule=EGRESS-GEN-HTTPS
  • method + url — a POST with an API path on a paste site means content was uploaded, not read.
  • ua — curl/8.5.0 from a server; humans paste through browsers, scripts paste through curl.
  • bytes_out — ~47 KB fits a credentials file or config dump; watch for sums across repeated POSTs.

Threat 5 · Unmanaged personal-account file sharing

Log sources and key fields. CASB alerts and app inventory (app, app_category, managed, user, bytes_up), proxy logs for the same flows, and identity-provider audit logs for OAuth grants (OAuth is the open authorization standard that lets apps access a tenant on a user’s behalf; key fields are Operation, TargetResources, Result). The OAuth consent is often the first artifact — before any bytes move.

Normal behaviorSuspicious behavior
Managed-tenant apps dominate; occasional small personal sync from known users; consents only to approved apps Uploads to apps marked unmanaged; OAuth consent to unknown storage apps; several users granting the same unfamiliar app in days

Detection logic. Alert on CASB “upload to unmanaged app” events in the File Sharing category, and on OAuth consents to storage applications that are absent from your approved-app list.

Example · CASB unmanaged-app alert (JSON view)
{
  "alert_id": "CSB-2025-118742", "ts": "2025-03-05T03:07:31Z",
  "alert_type": "unmanaged_app_upload",
  "user": "j.hale@corp.example", "src_ip": "10.12.8.41",
  "app": "Mega", "app_category": "File Sharing", "managed": false,
  "bytes_up": 418381824, "files_seen": 1, "session_id": "s-88412",
  "policy_hit": "UEBA-unmanaged-storage-uploads"
}
  • alert_type + managed: false — the core pair: content is going to an app your org does not control.
  • bytes_up — ~418 MB and climbing; join to proxy rows by src_ip and time for the full transfer.
  • policy_hit — links the alert to the UEBA (user and entity behavior analytics) policy so the ticket lands with the right queue.
Example · identity-provider OAuth consent (JSON view)

  "time": "2025-03-05T02:55:02Z", "Operation": "Consent to application",
  "Result": "success", "User": "j.hale@corp.example",

  "IpAddress": "10.12.8.41"

  • Operation — a consent event; filter out your approved-app allow-list before alerting.
  • Application — an unverified storage helper; the name pattern is worth a threat-intel lookup.
  • Scope — wide file scopes plus offline_access means the app keeps reading files indefinitely.

Threat 6 · Exfil over attacker-hosted web service with valid TLS

Log sources and key fields. DNS logs with first-seen enrichment (query, first_seen_hours), proxy/SNI logs for rare server names, newly-registered-domain intelligence, and optional TLS fingerprints (JA3/JARM). This threat defeats category rules, so novelty is the signal: new domain, new SNI, new certificate.

Normal behaviorSuspicious behavior
Endpoints talk to domains seen for months; SNI values repeat across the estate; certificates belong to big providers A domain first seen hours ago, registered in the last weeks, reached by few or one host, with large POST volume and a valid but unusual certificate

Detection logic. Alert on egress sessions where the destination domain is first seen in your environment within 24 hours, is not on the allow-list, and carries more than a small POST volume — then enrich with domain-age intelligence.

Example · DNS log with first-seen enrichment (JSON view)
{
  "ts": "2025-03-05T03:22:19Z", "client": "10.12.8.41", "host": "WS-FIN-22",
  "query": "cdn-updates-secure.com", "qtype": "A",
  "answers": ["185.199.110.153"], "rcode": "NOERROR",
  "first_seen_hours": 3.5, "domain_age_days": 11,
  "rdns": "vps-4471.hivelocity.host"
}
  • first_seen_hours — an enrichment field your pipeline computes against 30 days of history; small values mean novelty.
  • domain_age_days — from registrar intel; eleven days old plus valid TLS is the classic look-alike endpoint.
  • query — a generic “cdn-updates” style name; the follow-up proxy session shows the POST volume and SNI.

Note — Six threats, four telemetry families: proxy, DNS, EDR, and CASB/identity. If your SIEM only receives two of them today, that gap is your first tuning item — a rule can only be as good as the logs it reads.

Rule 1 · Consumer storage upload with sync-tool user agent Severity: high

Maps to: Threat 1 (rclone/Mega style) · Sigma fields cs_user_agent, cs_method, r_host → SPL fields of the same names; assumes index=proxy sourcetype=proxy:access key=value proxy logs where r_host holds the destination domain and bytes_out the upload volume. The SPL below is a one-to-one translation of the Sigma logic: user-agent match, or POST to a known consumer endpoint, minus the corporate-domain filter. If your gateway exports different names (for example cs_User-Agent or sc_bytes), rename in both places.

Sigma — consumer storage upload
title: Consumer Cloud Storage Upload with Sync Tool User Agent

status: stable
description: >

Splunk SPL — consumer storage upload
index=proxy sourcetype=proxy:access
| eval ua_hit=if(like(cs_user_agent, "%rclone%") OR like(cs_user_agent, "%azcopy%") OR like(cs_user_agent, "%MEGAync%"), 1, 0)

| lookup domain_age query AS query OUTPUT domain_age_days
| stats count values(answers) AS answers max(first_seen_hours) AS first_seen values(domain_age_days) AS domain_age_days by src_ip, host, query
| sort - count

False positives: this rule is noisy by design — every legitimate new cloud vendor lands here. That is acceptable because its job is to feed a short list for enrichment, not to page anyone.

Tuning: Join the results with proxy POST volume and keep only domains that also received more than a few megabytes; add JARM or JA3 enrichment when available; feed confirmed-bad hits back into the allow-list process and into threat intel. Severity: low as a rule, high as a hunt — the same logic in a weekly hunt with analyst review is one of the highest-value exercises for this technique.

Real-World Case Study

“Project Largewave” — a mid-size company vs. a double-extortion crew that tried to steal 240 GB before encrypting.

Note — Honest labeling: this is an illustrative composite based on public incident reporting. The main sources are Red Canary’s 2021 coverage of rclone-to-Mega extortion tooling and the leaked ransomware playbooks that described it. Names, hosts, and numbers are invented; the behavior pattern is real and widely reported.

Context. A mid-size company with roughly 900 employees ran a standard stack: managed Windows endpoints, an egress proxy, EDR, and a cloud backup. The proxy and DNS logs flowed into the SIEM, but nobody had built upload-volume baselines per subnet, and consumer storage categories were allowed by policy. A ransomware crew that follows the steal-then-encrypt playbook got in through a phishing attachment and spent five days preparing.

Attack chain

  • Initial access: phishing with a malicious document → foothold on a finance workstation (WS-FIN-22).
  • Discovery and staging: night-time folder sweeps, then archives staged in %TEMP% with business-like names.
  • Tooling: rclone deployed with a config for a Mega account the crew controlled.
  • Exfiltration (T1567.002): roughly 240 GB pushed to Mega between 03:00 and 05:00 — about six hours before encryption started.
  • Impact: encryption started later the same morning; a double-extortion note followed.

Timeline

  • Day 0 · 10:12

    Access

    A finance user opens a malicious document from a spoofed supplier thread. The macro drops a loader; EDR records the process but the alert is buried in low-priority noise. The attacker now has a user-level foothold.

  • Day 4 · 02:00–03:30

    Staging

    Over several nights the attacker lists finance shares and personal-data folders and creates password-protected archives such as %TEMP%\q4-reports-final.zip. The archive tool is first-seen on this host, but file-create telemetry is not yet alerted.

  • Day 4 · 03:40

    rclone config appears

    rclone lands in C:\Windows\Temp with a pre-built config pointing at the crew’s Mega account. The binary name imitates a backup utility. No signature fires; the tool is legitimate software.

  • Day 5 · 03:00–05:00

    Uploads — the detection point

    Steady HTTPS POSTs drain the staged archives to Mega. At 03:52 the SIEM’s new upload-volume rule breaks: WS-FIN-22 is at 41× its 30-day hourly baseline, category “Consumer Storage”, user agent rclone/v1.65.2. The on-call analyst confirms a staged archive on the host via EDR at 04:10 — the transfer is caught mid-flight.

  • Day 5 · 04:15–05:30

    Containment

    The proxy team blocks the storage category for the subnet and the firewall drops the session mid-transfer; the host is isolated by EDR at 04:30. Roughly 40% of the data had left; the rest never did. The crew’s retrieval window is cut short.

  • Day 5 · 09:00

    Encryption starts anyway

    The crew proceeds with encryption — but their leak-site leverage is now broken, because the stolen set is provably incomplete. The incident bridge moves to ransomware response mode.

  • Day 5–7

    Eradication

    Persistence is removed, the phishing origin is confirmed, and three more hosts that received the same loader are rebuilt. All credentials exposed on WS-FIN-22 are treated as compromised.

  • Week 2–3

    Recovery and secrets rotation

    Systems are restored from backup; every secret that lived on the affected shares is rotated — service accounts, API keys, VPN certs. The partial dump that the crew published is matched against DLP findings to confirm scope.

  • Week 4

    Verdict and policy change

    Consumer storage categories move to default-block with a documented exception process; rclone and azcopy get first-seen alerts; upload baselines are extended to every subnet.

Impact and team response

Encryption caused a two-day outage for finance systems, but the double-extortion payout demand failed. Negotiators could demonstrate that the exfil was cut mid-transfer, and the crew published only a small partial dump. Its contents matched the files the company had already queued for rotation and notification. The SOC, network team, identity team, and legal worked from one incident channel with a shared timeline; the proxy rule change was written the same week, while details were fresh.

Lessons learned

  • Egress baselines did the winning work. No signature knew rclone; the volume deviation did.
  • Default-allow for consumer storage was the root condition. Fix the policy, not just the alert.
  • First-seen tool alerts shorten the story. rclone appeared on day 4 — a first-seen rule would have flagged it a day earlier.
  • Mid-transfer blocking matters. Cutting a big upload turns “total loss” into “partial, provable loss.”

Mitigation and Defense

Controls that reduce this technique’s chances across policy, identity, endpoint, network, cloud, logging, monitoring, backup, and response — plus advice for small offices and home users.

ATT&CK lists no single mitigation that stops this technique, because the abused services are the same ones your business needs. The defense is a layered egress posture: decide what may leave, restrict the rest, log everything that moves, and measure normal so you can see abnormal. The cards below follow that logic control-family by control-family.

Policy

  • Write an explicit egress and acceptable-use policy: which SaaS categories are allowed, for whom, and with what data.
  • Default-block consumer storage and paste categories; run a documented exception process instead of silent allow-lists.
  • Name the approved upload tools (sync clients, CLI tools) and forbid undocumented ones.

Identity

  • Govern OAuth grants: approve-app workflow, monthly consent review, and instant revoke for unknown storage apps.
  • Block legacy auth so stolen passwords alone cannot mount service accounts.
  • Alert on consent grants with wide file scopes plus offline access.

Endpoint

  • Alert on first-seen CLI upload tools: rclone, azcopy, MEGAync, and unusual archive tools with password flags.
  • Watch temp-folder archive creation at night; tie file events to process lineage.
  • Keep browser and client versions current so stolen-session tricks fail.

Network

  • Enforce category rules at the proxy/SWG with per-subnet exceptions, not one global allow.
  • Build upload-volume baselines per host and subnet; treat 5× deviations as alerts.
  • For servers: default-deny consumer categories entirely and require a named business case.

Cloud & SaaS

  • Deploy CASB (or proxy app intelligence) and keep the managed/unmanaged inventory current.
  • In tenants you own, log file downloads and admin exports; alert on mass download sessions.
  • Restrict webhook creation to approved teams; audit existing webhook URLs.

Logging

  • Ship proxy, DNS, EDR, CASB, and identity-audit logs to the SIEM with enough retention for 30-day baselines.
  • Keep bytes-in and bytes-out fields; many stacks drop the outbound direction.
  • Preserve DLP verdicts so analysts can confirm content quickly.

Monitoring

  • Run the six rules from section 5.5 and review their false-positive budget monthly.
  • Hunt weekly on first-seen egress domains joined with POST volume.
  • Track “first-seen tool” and “first-seen category” metrics as program health indicators.

Backup

  • Keep offline or immutable backups — exfil plus encryption is the standard double-extortion pair.
  • Restore-test quarterly; a backup that never restored is storage, not resilience.
  • Include SaaS data in backup scope where the tenant supports it.

Response

  • Pre-authorize mid-transfer blocking: proxy and firewall owners know who can stop the transfer, and how, at any hour.
  • Rehearse the triage flow from section 4 twice a year as a tabletop.
  • Keep a secrets-rotation runbook ready — exfil response is also a credential-reset sprint.

Good practice — home and small office You will not run a CASB, and you should not need one. Keep only the cloud accounts you actually use, review the connected apps in those accounts twice a year, remove old browser extensions, and turn on your router’s basic DNS filtering. If a family PC suddenly uploads gigabytes at night, that is worth investigating — the same baseline instinct scales down perfectly.

Common Mistakes and Best Practices

Twelve concrete blue-team mistakes around web-service exfiltration. Each one lists the symptom you will notice, the root cause, the fix, and the habit that prevents it.

Almost every incident review in this area finds the same small set of wounds: a log nobody ships, an alert nobody tuned, a queue nobody owns. Use this section as a checklist during retrospectives — the “Symptom” lines are written the way they show up in a real SOC week.

1 · Allowing “trusted” SaaS categories without volume baselines

Symptom: the incident starts with “we saw it in a report three weeks later,” not with an alert.

Root cause: category allow-lists were treated as a finished control; nobody measured how much data those categories carry.

Fix: build per-host and per-subnet upload baselines now, even coarse ones, and alert on 5× deviations.

Prevention: make “new category allowed” a change ticket that always includes a baseline task.

2 · Never learning what normal nightly egress looks like per subnet

Symptom: analysts argue “that might be normal for servers” during every anomaly review.

Root cause: baselines were never segmented; one global average hides the servers that upload patches at 02:00.

Fix: split baselines by subnet and role; annotate backup windows; re-baseline after big architecture changes.

Prevention: a monthly 30-minute “what left the network last night” review per subnet keeps the picture honest.

3 · Treating CASB alerts as IT tickets instead of security events

Symptom: “unmanaged app” alerts get answered with license requests and password resets, days late.

Root cause: the CASB queue was handed to service-desk tooling with IT service-level targets, not detection ones.

Fix: route CASB upload and consent alerts to the SOC with triage targets measured in hours.

Prevention: define alert dispositions (benign / needs review / incident) and audit a sample monthly.

4 · Watching only download volume and ignoring uploads

Symptom: dashboards look green while 800 MB leaves a workstation.

Root cause: network dashboards were copied from availability monitoring, where inbound traffic matters most.

Fix: add bytes-out panels per subnet and per category; alert on direction, not just totals.

Prevention: every new network dashboard ships with an outbound view by default.

5 · Relying on a single log source (only DNS, or only proxy)

Symptom: an investigation stalls at “we know the domain, not the process” — or the reverse.

Root cause: one team shipped its logs; the others were “planned next quarter” for two years.

Fix: close the missing pipe first — proxy, DNS, EDR, CASB, identity — before writing more rules.

Prevention: keep a telemetry coverage map and review it when new tools or network segments appear.

6 · Blocking one famous domain and stopping there

Symptom: after blocking mega.nz, uploads move to another host the next week.

Root cause: the control targeted a name instead of a behavior; attacker tooling rotates destinations freely.

Fix: block the whole consumer-storage category and keep behavior rules (first-seen tools, volume) on top.

Prevention: review egress policy by category quarterly; never by anecdote.

7 · Alert fatigue from untuned per-request alerts

Symptom: the chat-API rule fires 400 times a day; analysts mute the channel.

Root cause: the rule was written from a vendor blog and pointed at every request, not at unusual callers.

Fix: add allow-lists, process attribution, and volume conditions; measure firing rates after each change.

Prevention: no rule goes live without a stated false-positive budget and an owner who checks it.

8 · Missing CLI upload tools in tool reviews

Symptom: rclone or azcopy is discovered on a server during an incident, and nobody knows who installed it.

Root cause: software inventories track browsers and office suites; single-binary utilities slip through.

Fix: deploy first-seen process alerts for known upload tools and inventory their presence now.

Prevention: include CLI tools in the software-approval list and in endpoint hardening baselines.

9 · Ownership gaps — nobody owns egress policy

Symptom: exception emails go to three teams; the block list says one thing, the firewall another.

Root cause: egress sits between network, security, and IT, so each assumed the other had it.

Fix: name one accountable owner and one review forum; put the category rules under change control.

Prevention: the RACI row (who is responsible, accountable, consulted, informed) for “egress policy” exists and is exercised in the quarterly review.

10 · Weak tuning — rules never tested against real traffic

Symptom: the rule looked perfect in the vendor demo but fired on the first legitimate backup job.

Root cause: detections were validated only in the lab and never replayed against production history.

Fix: replay 30 days of data before go-live; track precision for two weeks; tune from evidence.

Prevention: rule lifecycle includes a backtest step and a two-week observation window.

11 · Not logging SaaS audit events for tenants you own

Symptom: the attacker’s retrieval from your own tenant is invisible; only the upload side exists.

Root cause: tenant audit logs were never connected, or their license tier was never purchased.

Fix: connect tenant audit streams (sign-ins, consents, downloads, exports) to the SIEM.

Prevention: tenant onboarding checklist includes “audit logs to SIEM” as a required step.

12 · Monitoring only user workstations, not servers

Symptom: the first git-push case involves a build server nobody watched.

Root cause: egress monitoring grew out of user-behavior tooling and inherited its scope.

Fix: extend proxy and DNS coverage to server VLANs with stricter default-deny rules.

Prevention: the coverage map from mistake 5 includes every subnet, servers first.

Habits that keep the program healthy

Daily

  • Review new high-severity egress alerts with the triage flow from section 4.
  • Check the overnight “bytes out by subnet” panel before stand-up.

Weekly

  • Hunt on first-seen egress domains joined with POST volume.
  • Sample five closed CASB alerts and confirm the dispositions were right.

Monthly

  • Review rule firing rates and false-positive budgets; retire or retune the worst rule.
  • Re-run the OAuth consent review and the approved-tool list with identity and IT.

Response checklist — suspected web-service exfiltration

  • Capture the proxy rows and byte counts for the suspect session (host, user, URL, category, user agent).
  • Identify the host and user; pull asset and identity context.
  • Find the staged archive on the host (temp folders, password flags, creating process).

  • Rotate the exposed data: credentials, keys, and tokens that lived on the affected shares.
  • Scope across the subnet: other hosts with the same tool, category, or volume pattern.
  • Add detection for the exact tool and destination observed.
  • Review egress policy for the category involved and record the change.
