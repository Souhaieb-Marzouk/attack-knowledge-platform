T1189 Drive-by Compromise

Sometimes visiting a website is enough. In a drive-by compromise, a page hides exploit code that attacks the visitor's browser. The user does not click anything beyond opening the page. This page explains the attack and shows defenders exactly where it becomes visible.

  • Tactic: Initial Access
  • Platforms: Windows, Linux, macOS, Identity Provider
  • Added: 2018 (v2) · checked vs ATT&CK v20
  • Guide version: 2.0
  • Data sources: Network traffic, Process creation, Web/proxy logs
  • Detection difficulty: Medium

What it is

Malicious code on a website that exploits the visitor's browser or plugins during a normal visit.

Primary risk

A silent foothold on an endpoint with no user action to blame.

Where it happens

Compromised legitimate sites, attacker-built pages, malicious ads, and watering holes.

Detection difficulty

The exploit itself is quiet, but the payload's execution and call-home traffic are loud.

Contents

    1

    Overview

    What a drive-by compromise is, why it matters, and where it sits in an attack.

    The idea in plain language

    A drive-by compromise happens when a user visits a website during normal browsing and the website itself attacks the user's browser. The site may be built by the attacker, a legitimate site that was compromised, or a page reached through a malicious advertisement. The page contains exploit code - program code that abuses a software bug. If the browser or a plugin has that bug, the attacker's code runs on the user's machine with the browser's permissions.

    The name comes from how effortless it looks: the attacker "drives by", the user does not install anything, and no warning appears. Two special cases matter. A watering hole is a site a specific group is expected to visit, such as an industry news portal. An exploit kit is ready-made attack infrastructure: it profiles the visitor and automatically serves the right exploit for that browser.

    Why it matters

    Drive-bys remove the human firewall. Security-aware users cannot prevent an exploit they never see. One visit from a high-value employee can hand the attacker a foothold inside the corporate network. Because exploitation often crashes or slows the browser, and because payloads behave in unusual ways, defenders have several chances to catch it - if the right telemetry exists.

    Where it fits in the attack chain

    T1189 is an Initial Access technique. The exploit stage pairs with T1203 Exploitation for Client Execution, and the payload usually beacons out over T1071.001 Web Protocols. Content injection (T1659) is a common way the malicious code gets onto an otherwise trustworthy site.

    Animated simulation

    A watering-hole attack against an employee reading an industry blog. The SOC panel shows what defenders could see at each step.

    Step 1/8
    What is happening

    Defender hint

    The same story in text

    1. Normal morning. An employee reads a trusted industry blog over coffee. Nothing looks wrong. Defender hint: normal browsing; nothing to alert on yet.
    2. The trap was set earlier. A week before, attackers compromised the blog and added a hidden one-pixel iframe pointing at their landing server. Defender hint: if you operate the site, file-integrity monitoring catches the iframe; as a visitor you cannot see it.
    3. Silent redirect. The browser quietly fetches the attacker's landing page through the iframe. The egress proxy logs the request. Defender hint: watch for requests to newly registered or low-reputation domains right after a known-good page loads.
    4. Fingerprinting. The landing page checks the browser version and plugins, and picks the right exploit. Defender hint: fingerprint requests often carry unusual query strings; most proxies see them as plain GETs.
    5. Exploitation. The exploit fires against an unpatched browser vulnerability. The page looks blank or loads normally. Defender hint: the browser may crash here; Windows Error Reporting events are a weak but real signal.
    6. Payload lands. The shellcode downloads a payload, which runs - and the EDR sees the impossible: the browser spawning cmd.exe. Defender hint: browser processes should never spawn shells or script interpreters. This is the highest-value alert.
    7. Call home. The payload beacons to a C2 server over HTTPS. DNS and proxy logs record the new destination. Defender hint: new external domains with regular beacon intervals are the signature of C2.
    8. Response. The SOC isolates the laptop, blocks the C2 and landing domains, and starts patching the exploited browser across the fleet. Defender hint: hunt for other visitors of the same page during the exposure window.
    3

    Red team / hacker perspective

    When attackers use drive-bys, how the delivery chain works in principle, and the mistakes they make. Conceptual and lab-only.

    When and why attackers use it

    Drive-bys fit three goals. Mass compromise: exploit kits served through malvertising infect whoever passes by. Targeted espionage: watering holes wait for a specific group (an industry blog, a conference site). Access brokering: infections are sold to ransomware crews. The common thread: the attacker does not need to convince the victim of anything.

    Where it applies and prerequisites

    Anywhere browsers run: Windows, macOS, Linux desktops, kiosks. Prerequisites: a vulnerable browser, plugin, or rendering component. Plus a way to steer victims to the page - a compromise, an ad, or the victims' own habits. And infrastructure to serve exploits and collect sessions. Modern exploit kits also fingerprint first and abort on researchers, VMs, or patched browsers.

    Delivery chain in principle

    The chain runs like this. Lure: a trusted site or an ad. Gate/fingerprint: check the browser, its tools, and the geography. Exploit: abuse a memory or logic bug. Payload: download and execute a first-stage implant. C2: beacon out. Each stage is a detection opportunity, and the later stages are the loudest.

    LAB-ONLY: safe drive-by observation in an isolated VM
    # Goal: SEE the detection signals, without any real exploit code.
# Use a disposable VM snapshot with NO Internet and NO production data.

# 1) Simulate "browser spawns a shell" the boring way, to build the rule:
#    In the VM, from a browser-driven context, run:
cmd.exe /c echo LAB-ONLY-TEST
#    Confirm your EDR/SIEM rule for "browser as parent of cmd.exe" fires.

# 2) Simulate a redirect chain with a local HTML file:
#    page1.html redirects to page2.html redirects to page3.html (all local).
#    Watch how your proxy-format parsing counts hops.

# 3) Generate a fake crash entry with Windows Error Reporting by ending
#    a test process, and confirm your crash-correlation query works.
# Never run real exploit kits, and never point anything at systems you do not own.

    Common variations

    Exploit kit chains: malvertising to gate to kit (Angler 2014-16, RIG, Fallout 2018-19 - all historical now). Watering holes: carefully chosen sites for one target group. Mobile drive-bys: the same idea against mobile browsers. Extension delivery: convincing installs of malicious browser extensions. Zero-day vs N-day: unknown bugs for high-value targets, patched bugs against unpatched fleets.

    Attacker mistakes that help defenders

    Long-lived landing pages that researchers eventually sinkhole. Reused payload hashes across campaigns. Redirect chains long enough to stand out in proxies. Beacons with metronome timing. And kits that keep exploiting bugs long after patch adoption. Each one becomes a durable detection.

    Danger

    Deploying real browser exploits against any system you do not own is a crime. This guide is for learning and defense. Build detections in your lab; never rehearse attacks on production or third-party systems.

    4

    Blue team / SOC perspective

    Drive-bys are quiet until the payload moves. Those movements are the defender's chance.

    How defenders can see it

    Three reliable views exist. Process telemetry: the moment a payload runs, the browser becomes the parent of a shell, script interpreter, or downloader - a relationship that should never happen. Network telemetry: the redirect chain, the fingerprint fetch, and the C2 beacon all appear in proxy and DNS logs. Stability telemetry: exploitation often crashes the browser, and crash reports are collected even on machines with thin logging.

    Endpoint artifacts

    Browser process spawning cmd.exe, mshta.exe, rundll32.exe, or PowerShell; new files in user temp dirs; browser crash events (WER 1001); new scheduled tasks or run keys right after browsing.

    Network artifacts

    GET requests to low-reputation or newly registered domains right after known-good pages; multi-hop 30x redirect chains; beacon-like regular intervals to one destination; odd user-agent switches mid-chain.

    Threat-intel artifacts

    Sinkholed landing domains, reported exploit-kit URL patterns, published payload hashes and C2 certificates from vendor reporting.

    Where to look (log sources)

    • EDR / Sysmon: Event ID 1 process creation with parent-child context; Event ID 11 file creation; Event ID 13 registry writes.
    • Windows Event Log: Application Error (Event ID 1001) for browser crashes; Windows Defender operational events.
    • Proxy and DNS: full request URLs, referer chains, response codes, newly observed domains.
    • IDS: Suricata/Snort ET EXPLOIT_KIT and ET TROJAN rule categories.

    Short triage flow

    1. Validate the process alert. Confirm the parent is truly a browser and the child is a script interpreter or downloader. Screenshot the tree.
    2. Freeze the host. Isolate at the EDR level; keep the session alive for memory artifacts if the tool allows.
    3. Collect. Pull the child command line, written files, and the proxy/DNS context for the previous 15 minutes.
    4. Identify the page. Find the URL the user visited before execution; check its reputation and take a screenshot if it is still up.
    5. Scope. Search proxy logs for other users who fetched the same landing URL in the window.
    6. Respond. Patch the exploited component fleet-wide, block landing/C2 indicators, and report the campaign to your ISAC.
    Warning

    If a drive-by is missed, the next stage usually runs within minutes: credential dumping, lateral movement, ransomware staging. The cheap detections in section 5.5 - especially "browser as parent of a script interpreter" - are the best early tripwire you can own.

    5.2

    Threat intelligence

    Where drive-by intelligence comes from and how to make it operational.

    Sources worth following

    MITRE ATT&CK for technique structure. Vendor reporting: Google TAG, Microsoft MSTIC, Cisco Talos, ESET, Proofpoint for watering-hole and kit campaigns. OSINT: URLhaus, URL scanner feeds, sinkhole publications. Commercial feeds: exploit-kit URL and C2 lists. ISACs: sector warnings about compromised sites. Internal telemetry: your proxy history is the best source of "what did we already touch".

    How to apply it

    Maintain a landing/C2 watchlist and load it into proxy, DNS, and EDR blocklists. Convert each new vendor report into a hunt (search your 90 days of proxy history for the reported patterns) and, where stable, into a Sigma rule. Record confidence per indicator, and retire indicators that age out to keep alert quality high.

    5.3

    Threats ranking and categorization

    Five realistic drive-by threats, ranked and categorized. These five are reused in sections 5.4 and 5.5.

    RankThreatSeverityPlatform
    1Zero-day browser exploit at a targeted watering holeCriticalWindows / macOS
    2N-day browser exploit via exploit kit or compromised siteHighWindows / macOS / Linux
    3Malvertising redirect chain to exploit kit or phishingHighNetwork
    4Mobile browser drive-by exploitMediumNetwork (mobile devices)
    5Drive-by install of a malicious browser extensionLowWindows / macOS

    Threat 1 - Zero-day at a watering hole Critical

    Description: a previously unknown browser bug exploited on a site the target group trusts.

    Preconditions: attacker holds a zero-day and knows the target's browsing habits.

    Impact: silent compromise of high-value users before any patch exists.

    Justification: no preventive patch is possible; only behavior detections save you.

    Threat 2 - N-day via kit or compromised site High

    Description: known, already-patched bugs used against unpatched fleets through kits or compromised pages.

    Preconditions: unpatched browsers or legacy plugins in the environment.

    Impact: bulk initial access, often sold onward to ransomware crews.

    Justification: entirely preventable by patching, but patch gaps are common and kits automate it.

    Threat 3 - Malvertising redirect chains High

    Description: malicious ads on legitimate sites redirect users through hops to kits or phishing.

    Preconditions: ad network abuse or hijacked advertiser accounts; users browsing ad-supported sites.

    Impact: broad exposure of the whole user base; feeds Threats 1 and 2.

    Justification: very common; detectable in proxy logs, so impact is containable.

    Threat 4 - Mobile drive-by Medium

    Description: mobile browsers exploited via crafted pages, sometimes leading to app-side follow-on.

    Preconditions: outdated mobile browser or webview; users on device browsers without mitigations.

    Impact: device compromise or credential capture on BYOD fleets.

    Justification: less common than desktop kits, harder to detect with current telemetry.

    Threat 5 - Drive-by extension install Low

    Description: a page tricks or forces installation of a malicious browser extension that then reads pages and cookies.

    Preconditions: social-engineering moments or policy gaps allowing third-party extensions.

    Impact: session and data theft on managed browsers.

    Justification: policy controls (extension allow-lists) make it rare in managed fleets.

    5.4

    Logs and patterns

    For each of the five threats: log sources, key fields, normal vs suspicious behavior, detection logic, and a realistic event example.

    Threat 1 - Zero-day at a watering hole Critical

    Log sources: Sysmon Event ID 1 (process creation) with parent-child context; EDR alerts; Windows Error Reporting Event ID 1001.

    Key fields: ParentImage, Image, CommandLine, User, Host.

    Normal: browsers start helpers like their own crashpad or GPU processes; those children share the browser's executable path.

    Suspicious: any shell, script interpreter, or downloader as a child of a browser process.

    Detection logic: alert when a browser executable is the parent of a command-line interpreter or scripting host - zero-day or N-day, this fires the same way.

    Example event - Sysmon Event ID 1 (XML)
    <Event>
  <System>
    <Provider Name="Microsoft-Windows-Sysmon"/>
    <EventID>1</EventID>
    <TimeCreated SystemTime="2025-03-14T09:12:44.310Z"/>
    <Computer>FIN-W7-221.corp.local</Computer>
  </System>
  <EventData>
    <Data Name="ParentImage">C:\Program Files\Google\Chrome\Application\chrome.exe</Data>
    <Data Name="Image">C:\Windows\System32\cmd.exe</Data>
    <Data Name="CommandLine">cmd.exe /c powershell -enc SQBFAFgAIAAoAE4AZQB3...</Data>
    <Data Name="User">CORP\j.reyes</Data>
  </EventData>
</Event>

    ParentImage is the browser - the shell should never inherit from it. The encoded PowerShell child is the payload's first command. CommandLine alone justifies an incident.

    Threat 2 - N-day via kit or compromised site High

    Log sources: Windows Error Reporting (Application log, Event ID 1001); EDR; Defender operational events.

    Key fields: FaultingApplicationName, FaultingModuleName, ApplicationName, time.

    Normal: occasional browser crashes with module names inside the browser or GPU drivers.

    Suspicious: a browser crash followed within minutes by unusual child processes or network callbacks; repeated crashes on the same page.

    Detection logic: correlate browser crash events with process-creation and network events in a short window after the crash.

    Example event - Windows Error Reporting Event ID 1001
    Fault bucket , type 5
Event Name: AppCrash
Response: Not available
Faulting application name: chrome.exe, version 109.0.5414.74
Faulting module name: unknown, version 0.0.0.0
Exception code: 0xc0000005
Application Timestamp: 63c2a1f4
Report Id: 9f1c2d3a-77b4-4f2e-8d5c-1a2b3c4d5e6f

    Exception code 0xc0000005 is an access violation - typical of memory-corruption exploits. Faulting module name: unknown (module outside the browser's own files) strengthens the case. Join the Report Id window to nearby EDR events.

    Threat 3 - Malvertising redirect chains High

    Log sources: egress proxy logs (Squid, Zscaler-style), DNS query logs.

    Key fields: client_ip, status, url, referrer, user_agent.

    Normal: one or two redirects for ad selection between known networks; stable domains per site.

    Suspicious: three or more 30x hops in seconds, ending on a domain unrelated to the page the user clicked; hops through newly registered domains.

    Detection logic: count redirect responses per user in a short window, then inspect the final landing domain.

    Example event - Squid proxy access log (chain)
    1710399601.002 118 10.20.4.31 TCP_MISS/302 488 GET http://news-site.example/ad?slot=7 - DIRECT/203.0.113.141 text/html
1710399601.221 89 10.20.4.31 TCP_MISS/302 602 GET http://ad-rtb.example/redir?z=4412 - DIRECT/198.51.100.44 text/html
1710399601.407 133 10.20.4.31 TCP_MISS/302 512 GET http://gate-9x.example/in?p=1 - DIRECT/198.51.100.90 text/html
1710399602.110 240 10.20.4.31 TCP_MISS/200 40122 GET http://land-final.example/ - DIRECT/198.51.100.201 text/html

    Four hops in one second for one click. The last hop domain shares nothing with the first. Chains like this feed both exploit kits and phishing - the count per user is the detection.

    Threat 4 - Mobile drive-by Medium

    Log sources: proxy logs (device user-agents), MDM/MAM network events, DNS logs.

    Key fields: user_agent, url, method, status, device_id.

    Normal: mobile browsers fetch the same host mix as desktops; webviews only hit app backends.

    Suspicious: mobile user-agents POSTing to interstitial or "gate" pages, long random paths, then app-store or profile-download attempts.

    Detection logic: flag mobile user-agents with anomalous POST patterns to unclassified domains.

    Example event - proxy log (mobile UA)
    1710400211.902 173 10.44.2.19 TCP_MISS/200 912 POST http://m-gate.example/tk/Xk29fjq2LaPq8Zx - DIRECT/198.51.100.88 application/json "Mozilla/5.0 (iPhone; CPU iPhone OS 16_3 like Mac OS X) AppleWebKit/605.1.15"

    A mobile user-agent POSTing to a long random path on an unclassified domain. The response is JSON - typical of gate/fingerprint services. Correlate 10.44.2.19 to a device in MDM.

    Threat 5 - Drive-by extension install Low

    Log sources: Sysmon Event ID 13 (registry set) and Event ID 11 (file create); browser enterprise policies logs.

    Key fields: TargetObject, Details, Image.

    Normal: extension keys written by the browser installer or admin deployment; update URLs point to the official store.

    Suspicious: extension registration keys with third-party update_url values, or .crx files written outside the store flow.

    Detection logic: alert on extension update_url registry values that are not your approved store endpoints.

    Example event - Sysmon Event ID 13 (XML)
    <Event>
  <System>
    <Provider Name="Microsoft-Windows-Sysmon"/>
    <EventID>13</EventID>
    <TimeCreated SystemTime="2025-03-14T09:13:52.002Z"/>
    <Computer>FIN-W7-221.corp.local</Computer>
  </System>
  <EventData>
    <Data Name="Image">C:\Program Files\Google\Chrome\Application\chrome.exe</Data>
    <Data Name="TargetObject">HKU\S-1-5-21-...\Software\Google\Chrome\Extensions\afcekkgpmjoklndnmlnbhojjdbfkcnhb\update_url</Data>
    <Data Name="Details">https://clients2.othercdn.example/service/update2/crx</Data>
  </EventData>
</Event>

    The extension ID is new to the fleet and its update_url is not the official Chrome Web Store endpoint - a strong sign of a side-loaded extension. Maintain an allow-list of approved extension IDs.

    5.5

    Sigma rules and Splunk SPL

    One complete Sigma rule and one matching Splunk SPL query per threat, with assumptions, false positives, and tuning notes.

    Threat 1 - Zero-day at a watering hole Rule level: high

    Sigma rule (YAML)
    title: Browser Process Spawning Script Interpreter
id: 4a1b9e2c-8d73-4f56-9c21-6b0a7d4e3f18
status: stable
description: Detects a web browser spawning command-line interpreters or script
  hosts. This relationship appears when drive-by exploits hand off to a payload,
  regardless of which vulnerability was used.
references:
  - https://attack.mitre.org/techniques/T1189/
  - https://attack.mitre.org/techniques/T1203/
author: Detection Engineering Team
date: 2024-10-15
logsource:
  category: process_creation
  product: windows
  service: sysmon
detection:
  selection_parent:
    ParentImage|endswith:
      - '\chrome.exe'
      - '\msedge.exe'
      - '\firefox.exe'
      - '\iexplore.exe'
      - '\brave.exe'
      - '\opera.exe'
  selection_child:
    Image|endswith:
      - '\cmd.exe'
      - '\mshta.exe'
      - '\rundll32.exe'
      - '\regsvr32.exe'
      - '\wscript.exe'
      - '\cscript.exe'
      - '\powershell.exe'
  condition: selection_parent and selection_child
fields:
  - ParentImage
  - Image
  - CommandLine
  - User
falsepositives:
  - Rare developer workflows that launch browsers via scripts (allow-list by host)
level: high
tags:
  - attack.t1189
  - attack.t1203
  - attack.tactic.initial-access
  - attack.tactic.execution
    Splunk SPL
    index=edr sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=1
  ParentImage IN ("*\\chrome.exe","*\\msedge.exe","*\\firefox.exe","*\\iexplore.exe")
  Image IN ("*\\cmd.exe","*\\mshta.exe","*\\rundll32.exe","*\\regsvr32.exe","*\\wscript.exe","*\\cscript.exe","*\\powershell.exe")
| table _time host, User, ParentImage, Image, CommandLine
| sort -_time

    Field assumptions: Sysmon XML in index=edr; EventCode=1 with ParentImage/Image fields. False positives: QA hosts that drive browsers via automation - exclude by host group. Tuning: keep the child list strict; add curl.exe/certutil.exe variants as a second, lower-level rule.

    Threat 2 - N-day via kit or compromised site Rule level: high

id: b7e2f5a0-3c69-4d18-8f4a-2d9c6b1e7a55
status: stable
description: Detects encoded PowerShell commands whose parent is a browser process.
  Encoded command lines under browsers are a common post-exploitation hand-off after
  drive-by exploitation with known (N-day) bugs.
references:
  - https://attack.mitre.org/techniques/T1189/
  - https://attack.mitre.org/techniques/T1059/001/
author: Detection Engineering Team
date: 2024-10-15
logsource:
  category: process_creation
  product: windows
  service: sysmon
detection:
  selection_parent:
    ParentImage|endswith:
      - '\chrome.exe'
      - '\msedge.exe'
      - '\firefox.exe'
      - '\iexplore.exe'
  selection_child:
    Image|endswith: '\powershell.exe'
    CommandLine|contains:
      - ' -enc '
      - ' -EncodedCommand '
      - 'FromBase64String'
  condition: selection_parent and selection_child

  - ParentImage
  - CommandLine
  - User
falsepositives:

  - attack.t1059.001
  - attack.tactic.initial-access
    Splunk SPL
    index=edr sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=1
  ParentImage IN ("*\\chrome.exe","*\\msedge.exe","*\\firefox.exe","*\\iexplore.exe")
  Image="*\\powershell.exe"
  (CommandLine="* -enc *" OR CommandLine="* -EncodedCommand *" OR CommandLine="*FromBase64String*")
| table _time host, User, ParentImage, CommandLine | sort -_time

    Field assumptions: same Sysmon source; command lines are captured verbatim. False positives: rare; some admin tools encode commands - scope exclusions to specific hosts. Tuning: decode the base64 payload offline and add its indicators to the case.

  - user
  - url
  - referer
  - domain
falsepositives:
  - SSO, MFA, and consent redirect flows; allow-list identity providers
level: medium
tags:
  - attack.t1189
  - attack.tactic.initial-access
    Splunk SPL
    index=proxy sourcetype=squid:access status IN (301,302,307)
| bin _time span=5m
| stats count as redirects values(url) as sample_urls by _time, user

    Field assumptions: proxy fields status, url, user; adjust index/sourcetype to your product. False positives: identity-provider redirect flows. Tuning: exclude known SSO domains; then review the final landing domain of each remaining chain.

    Threat 5 - Drive-by extension install Rule level: low

id: 1c7d4e93-58b2-4f0a-8c69-3b2f7d1a9e04

  product: windows
  service: sysmon

    TargetObject|endswith: '\update_url'

    Details|contains:
      - 'clients2.google.com'
      - 'edge.microsoft.com'
      - 'addons.mozilla.org'

fields:
  - Image
  - TargetObject
  - Details

  - attack.t1189
  - attack.t1176
  - attack.tactic.persistence
    Splunk SPL
    index=edr sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=13
  TargetObject="*\\Extensions\\*\\update_url"

| stats count by host, TargetObject, Details | sort -_time

    Field assumptions: Sysmon registry events with TargetObject/Details. False positives: corporate extension deployments - add your internal update server to the filter. Tuning: maintain an allow-list of approved extension IDs and alert on any ID outside it.

    Good practice

    Testing: in a lab VM, launch cmd.exe manually with a browser set as the parent is hard - instead replay the exact Sysmon XML from section 5.4 into a test index, or use an attack-simulation harness that only creates process events.     Real-world case study

    The Council on Foreign Relations (CFR.org) watering hole, December 2012: a compromised think-tank site used to exploit visitors' browsers.

    Context

    In late December 2012, security researchers found that the website of the Council on Foreign Relations - one of the most visited foreign-policy sites in the United States - was serving malicious code to its readers. The visitors were exactly the audience an espionage actor wants: government, military, and policy professionals. The incident became a textbook example of a watering-hole attack, years before ATT&CK named the pattern.

    Timeline

    • Late 2012Attackers compromise the CFR website and inject a hidden script into its pages.
    • December 2012The injected script fingerprints visitors: browser version, plugins, and platform.
    • December 2012Internet Explorer 8/9 visitors receive a hidden iframe pointing to the exploit server.
    • December 2012The exploit abuses CVE-2012-4792, a use-after-free bug in IE, and drops the Poison Ivy remote access trojan.
    • Late December 2012Researchers (FireEye and others) detect and publish the campaign; attribution reporting points to China-linked actors.
    • Early 2013The injected code is removed; defenders add proxy blocks and begin patching campaigns.

    Detection point

    The campaign surfaced through researcher analysis of injected page content and the exploit's C2 traffic, not through victim SOC alerts - a sign of the times. Today the same chain would trip browser-child-process alerts, crash correlations, and proxy reputation blocks within minutes.

    Containment

    The malicious script was removed from CFR.org, and the exploit/C2 infrastructure was flagged to security vendors and blocklists. Visitors who had already executed the payload needed endpoint remediation - Poison Ivy infections were hunted by its well-known traffic and mutex behaviors.

    Eradication

    Infected visitors rebuilt or cleaned their systems. The wider community responded by prioritizing the IE patch (MS13-003 era fixes for the CVE) and by adding watering-hole awareness to threat models for high-profile sites.

    Recovery

    Restore the site from a known-good state and remove every injected script. Verify with clean crawls and integrity baselines before trusting the pages again. Keep the proxy blocks and new detections in place, and monitor for re-injection in the following weeks.

    Impact and consequences

    Confirmed compromise of site visitors with a full remote-access trojan, embarrassment for a high-profile organization, and a lasting demonstration that even sites with strong reputations can be turned into attack delivery. It shaped a decade of watering-hole reporting that followed.

    Team response and communication

    The response required the site owner, security vendors, and the browser vendor to move in parallel: remove the injection, flag indicators, ship the patch. Public write-ups by researchers created shared intelligence that other organizations used to hunt their own networks - an early example of community-driven defense.

    Lessons learned

    1. High-profile websites are targets because of who reads them, not what they store.
    2. Browser patch velocity is a security control; delay equals exposure.
    3. Proxy and egress visibility catches the follow-on traffic even when the exploit is invisible.
    4. Layered detection beats signature-only defense: process trees and crash correlation still work today.
    5. Site owners need integrity monitoring for their own pages.

    Mitigation and defense

    Defense in depth: remove the bugs, narrow the browser, and watch the loud stages.

    Policy

    Browser patch SLAs measured in days. A policy for plugins/extensions (allow-list only). Exceptions for legacy apps isolated into separate profiles or VMs.

    Identity

    Users without local admin rights so payload execution cannot disable defenses. Phishing-resistant MFA limits what a stolen session is worth.

    Endpoint

    EDR with behavioral detections (browser-child-process rules). Attack Surface Reduction rules (for example, block executable content from email/web clients). Remove legacy plugins (Flash, old Java).

    Network

    Proxy and DNS filtering with newly-registered-domain and reputation controls. TLS inspection where policy allows. IDS signatures for exploit-kit patterns.

    Cloud / SaaS

    Isolated browsing (remote browser isolation or VDI) for high-risk users. Conditional Access restricting unmanaged-device browsing to low-risk sites.

    Logging & monitoring

    Retain proxy logs at least 90 days. Collect Sysmon process, file, and registry events. Run the section 5.5 rules and hunt sinkhole-reported domains monthly.

    Backup & resilience

    Fast reimage capability for endpoints - a drive-by victim should be rebuilt in hours. Keep golden images and user profiles separated.

    Response

    A drive-by runbook: isolate, collect the child-process command line, find the referring URL, scope by proxy history, patch, and sweep for other visitors.

    Good practice - home and small office

    Turn on automatic updates for your browser and operating system. Use an ad blocker - most malvertising chains die at that step. Keep your antivirus on and updated. If a page looks blank and your browser crashes twice in a row, close it and run a scan. Never ignore a "your browser is out of date" banner for long.

    Common mistakes and best practices

    Ten blue-team mistakes seen in real drive-by incidents, with symptom, root cause, fix, and prevention.

    1. Slow browser patching

    Symptom Fleet reports show browsers three versions behind after a public exploit.

    Root cause Browsers not treated as critical patch surface like the OS.

    Fix Add browsers to the emergency patch SLA with version dashboards.

    Prevention Monthly version-compliance review with escalation for stragglers.

    2. Trusting allow-listed sites blindly

    Symptom Infection traced back to a category "News" site in the proxy allow-list.

    Root cause Category trust assumed to equal safety.

    Fix Treat allow-list as trust-but-verify; keep egress detection active for all categories.

    Prevention No blanket suppressions by URL category in SIEM rules.

    3. Blocking only known-bad domains

    Symptom Each new campaign needs a new block; defenders always one step behind.

    Root cause Blacklist-only egress posture.

    Fix Add reputation, category, and newly-registered-domain controls; not just IoC blocks.

    Prevention Weekly review of proxy blocks by category effectiveness.

    4. Ignoring browser crash telemetry

    Symptom Exploit era reconstructed later only from packet captures.

    Root cause WER/Application Error events not collected.

    Fix Ship Event ID 1001 to the SIEM; add the crash-then-execute correlation query.

    Prevention Coverage inventory includes crash and error channels.

    5. No EDR on executive and admin endpoints

    Symptom First sign of compromise is fraud or a help-desk call, not an alert.

    Root cause "Special" devices excluded from tooling for performance or political reasons.

    Fix Deploy the same telemetry to VIPs with tuned (not missing) policies.

    Prevention Coverage KPI includes 100% of privileged users.

    6. Proxy logs without URLs or referers

    Symptom Cannot reconstruct the redirect chain after an incident.

    Root cause Minimal logging configured for storage savings.

    Fix Log full URL, referer, status, user-agent; keep 90 days hot.

    Prevention Log field checklist per data source in the SIEM onboarding guide.

    7. No process-tree context in alerts

    Symptom "cmd.exe executed" alerts flood in; none show the browser parent.

    Root cause Endpoint tool not configured to enrich with parent/ancestry.

    Fix Enable full ancestry in process events; rewrite rules on parent-child pairs.

    Prevention Detection engineering standard: rules must state lineage assumptions.

    8. Banning PowerShell instead of instrumenting it

    Symptom Attackers switch to mshta/rundll32; defenders see nothing new.

    Root cause One-tool blocking replaces monitoring.

    Fix Combine constrained-language policies with full logging of all LOLBINs.

    Prevention Detection coverage matrix across LOLBIN hand-offs.

    9. Testing detections only with real malware

    Symptom Rules untested for months; fail during a real event.

    Root cause No safe validation path.

    Fix Replay recorded events (like the section 5.4 examples) into the SIEM in CI.

    Prevention Rule repos ship with test events; pipeline blocks untested rules.

    10. No scoping hunt after an infection

    Symptom Reinfection a week later from the same landing page.

    Root cause Case closed on one host; exposure window never searched.

    Fix Mandatory proxy-wide hunt for the landing URL and C2 during the window.

    Prevention Incident checklist includes a "scope by network" step.

    Daily habits

    • Review browser-child-process alerts with full lineage.
    • Check new external domains contacted right after known-good sites.
    • Track browser version compliance for the top 20 at-risk users.

    Weekly habits

    • Review crash-then-execute correlation hits.
    • Update the landing/C2 watchlist from vendor reports.
    • Hunt last week's sinkhole publications in your proxy history.

    Monthly habits

    • Replay section 5.5 test events against production rules.
    • Review proxy filter effectiveness by category.
    • Rehearse the drive-by runbook with a tabletop.
