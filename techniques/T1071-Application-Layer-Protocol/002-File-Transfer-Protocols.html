T1071.002 File Transfer Protocols

File transfer protocols are the delivery vans of a network: SMB, FTP, SFTP, and TFTP move files all day. Attackers use the same vans to carry tools in and stolen data out, because many networks let them drive through without a check. This page shows what that looks like on the wire and how to catch it.

Overview

What this technique is, why it matters, and where it sits in the attack chain - in plain language.

File Transfer Protocols (T1071.002) is a sub-technique of T1071, Application Layer Protocol, in the Command and Control tactic. It describes attackers who use normal file transfer protocols to move their own tools and your data. Five names matter. FTP (File Transfer Protocol) runs on TCP port 21. FTPS is FTP wrapped in TLS encryption on port 990. SFTP (SSH File Transfer Protocol) runs on port 22. TFTP (Trivial File Transfer Protocol) uses UDP port 69 and needs no login. SMB (Server Message Block) is the Windows file-sharing protocol, and it uses ports 445 and 139.

This page is version 2.0 of this guide, re-checked against MITRE ATT&CK in October 2026 (sub-technique version 1.4). MITRE's official description names SMB, FTP, FTPS, and TFTP as the example protocols. MITRE also warns that data can be hidden inside the transferred files themselves.

These protocols are the delivery vans of a network. Staff use them to ship software, backups, and partner files. An attacker who rides the same vans gets three advantages. First, firewall rules written years ago often still allow the traffic. Second, TFTP needs no username and no password. Third, SFTP is encrypted, so defenders cannot read the commands inside it.

SMB deserves a special note. Staff use it to open shared folders and map network drives, so most of it stays inside the network. The parent technique T1071 names SMB as a common protocol for connections inside an enclave (a protected internal network zone). Attackers ride the same pipes. Malware frameworks such as Cobalt Strike, Dragonfly, and Mythic have used SMB peer-to-peer channels for C2, and stolen data is often staged on shares before it leaves. SMB rarely crosses the border, so an SMB session to an outside address is a strong signal by itself.

In the attack chain, this technique shows up three times. Early on, attackers pull a toolkit in with TFTP or FTP. That step is called staging: placing tools on a host before they run. It overlaps with T1105, Inbound Tool Transfer. In the middle, some malware families use FTP for C2 (command and control - the channel an attacker uses to send orders to malware). At the end, they push stolen data out over FTP or SFTP. That last step is exfiltration - moving data out of the network - and it overlaps with T1048, Exfiltration Over Alternative Protocol.

This page follows one realistic story. An intruder enters a Windows file server over RDP (Remote Desktop Protocol, the Windows remote screen tool). The intruder stages a toolkit over TFTP in seconds, then works quietly for hours. At 02:47 the attacker sends 1.8 GB of card records out over FTP. You will see the network view, the defender view, six Sigma rules with matching Splunk SPL, and a real case from 2015 to 2016.

Defender view: TCP/3389 reachable from the internet plus a failure burst followed by a success means MFA is missing and the account is exposed.

Defender view: a server speaking TFTP is nearly always wrong. Watch for tftp.exe starting and for UDP/69 egress (traffic that leaves your network).
  3. Step 3 — Tools land. The 6.2 MB payload arrives in about four seconds. The attacker drops it in C:\Users\Public and starts it. Defender view: match the tftp.exe process with a new binary on disk, then check the hash on other hosts.
  4. Step 4 — Quiet hands-on time. Over RDP the attacker lists payment folders such as Finance\Cards and starts using a new local admin account. Defender view: odd-hours interactive logons on servers and new local admin use deserve a phone call, not a ticket.
  5. Step 5 — Data out the back. At 02:47 the attacker uploads 1.8 GB of card records to ftp-heavyhaul[.]net with one FTP PUT as user cardops. Defender view: servers rarely speak FTP outbound. Big volume, a first-seen external host, and night time make a strong exfiltration signal.
  6. Step 6 — Firewall log alert. The rule "server subnet to external FTP" fires. The analyst opens the Zeek ftp.log session and sees USER cardops and STOR cards_2026_08.csv. Defender view: command-level logs let you name the stolen file in the first ten minutes of the case.
  7. Step 7 — Scope the damage. Hunting finds three FTP sessions to the same destination. FIN-FS-01 tried the same TFTP fetch, but the egress rule blocked it. Defender view: hunt TFTP and FTP across every server for at least 30 days before you say only one host was hit.
  8. Step 8 — Contain and close. The team blocks 198.51.100.140 and 198.51.100.150 plus the domain, isolates FIN-FS-02, rotates the service account, and enables MFA on RDP. Defender view: fix identity and egress rules, not only the malware. Re-image the host before it returns to service.

Red Team / Hacker Perspective

Why attackers pick file transfer protocols, how they use them at concept level, and what you can safely try in a lab.

Warning

This section describes attacker behavior at concept level so that defenders can recognize it. It is for defense education only. Run the lab commands on systems you own, inside an isolated lab network. Never use them against systems you do not own.

When and why attackers use it

Intruders choose file transfer protocols for boring but powerful reasons:

  • The traffic is often allowed. Firewall rules written years ago still open ports 21 and 69.
  • TFTP needs no username and no password. One GET command moves a whole file.
  • FTP is plaintext and easy to script from any shell or malware implant.
  • SFTP is present on almost every server and is encrypted, so the session looks like normal admin work.
  • Files move in bulk. One short session can carry gigabytes, which is ideal for stolen card records.

How it is done (concept level)

  • Staging in: a compromised Windows host pulls a toolkit with a TFTP GET. No login is needed and the transfer takes seconds.
  • Data out: an FTP client, or curl with an ftp:// URL, uploads stolen files to attacker-owned servers as simple STOR commands.
  • Admin-style cover: SFTP with a stolen SSH key moves data while hiding inside the noise of daily operations.

Prerequisites

  • A foothold: an RDP session, a shell, or an active malware beacon on one host.
  • A network path: outbound 21, 69, or 22, or an internal FTP server to hop through.
  • Sometimes credentials: an FTP account or an SSH key taken in an earlier step.

Lab examples (safe)

Lab only — run against systems you own. The two blocks below work inside one lab VM. Start a local FTP server, upload a test file, and watch the plaintext handshake:

In the tcpdump output you will see the USER and PASS lines in clear text. That is why FTP exfiltration is easy to spot at the network layer. It is also why the Zeek ftp.log examples later on this page can name both the user and the file.

Common variations and attacker mistakes

  • Modern Windows no longer ships ftp.exe, so intruders use curl.exe -T with ftp:// URLs instead. Watch curl the same way you watch ftp.
  • One weak password often works on both FTP and RDP. A leaked FTP password can become a full server login.
  • Rogue staging servers with default passwords are scannable. Defenders can find attacker FTP boxes with the same port scans they already run.
  • Attackers sometimes forget to clean staged dumps on their own servers. Public scans of those boxes turn private mistakes into shared evidence.

Blue Team / SOC Perspective

How defenders see file transfer abuse, which traces it leaves, and a short triage flow for the alert.

How defenders see it

The endpoint rarely complains. The server keeps working, no crash happens, and no antivirus signature fires for a plain file move. The evidence lives in network logs, plus small endpoint traces around the transfer. That is why logging, not blocking, is the first battle: if you never record FTP and TFTP sessions, the theft happens in silence.

Artifacts left behind

  • A tftp.exe process with a UDP/69 connection on a server.
  • A new binary in C:\Users\Public or %TEMP% right after the transfer.
  • Zeek ftp.log rows with USER, PASS, STOR, and the file name.
  • A firewall session with sentbyte near 1.9 GB at 02:47.
  • A dns.log that shows no query for the destination IP address.
  • A Windows event chain: many 4625 logon failures, then one 4624 success from the same external IP.

Where to look

Why it matters

Volume plus rarity makes this a high-signal area. A server that speaks FTP or TFTP is so unusual that one honest rule can catch an entire intrusion class. The FIN1 case study in section 6 shows the same pattern hurting many banks at once, years before most SOCs added an egress rule for it.

How it fits the attack chain

The technique can appear at staging (tools in), at C2 (a low-and-slow channel), and at exfiltration (data out). That gives defenders three separate chances to detect one intrusion. Section 5 turns each chance into a finished rule.

Triage flow

  1. Pull the flow: which source host, which external IP, which port, how many bytes.
  2. Check direction and time: egress from a server subnet at 02:00 is not a user upload.
  3. Get command-level logs: Zeek ftp.log gives the user, the command, and the file name.
  4. Pivot to the endpoint: which process started the transfer, and what landed on disk next.
  5. Check identity: who logged on around the transfer, and was MFA in use.
  6. Decide: a ticketed business transfer, or an incident. If unsure, open the case and call IR.
  7. Contain: block the destination, isolate the host, and rotate any exposed credentials.

THR-01 - TFTP payload staging

Log sources
Sysmon EventCode 3 (sourcetype XmlWinEventLog:Microsoft-Windows-Sysmon/Operational); Zeek tftp.log (sourcetype zeek:tftp)
Key fields
Image, DestinationIp, DestinationPort, User; zeek: id.orig_h, id.resp_h, file, block_size
Normal
TFTP is rare on servers at any hour. Where it exists, it serves device imaging from one known host.
Suspicious
tftp.exe on a server fetching a .exe from an external IP, or any UDP/69 flow from a datacenter subnet at night
Detection logic
Alert when a TFTP client process opens a network connection, or when a TFTP session touches a server subnet

THR-02 - FTP exfiltration

Log sources
Zeek ftp.log (sourcetype zeek:ftp); firewall traffic (sourcetype fortigate_traffic)
Key fields
user, command, arg, reply_code, size; firewall: srcip, dstip, dstport, sentbyte
Normal
Small partner uploads from known hosts during business hours, or none at all from servers.
Suspicious
A STOR upload from a server subnet to a first-seen external host at 02:47, with sentbyte near 1.9 GB
Detection logic
Alert on STOR from server subnets to non-internal hosts; add a volume check for very large sessions

Field meanings: command STOR means upload; reply_code 226 means the transfer finished; size is the file size in bytes (184 MB for this one file).

Log sources
Zeek ssh.log (sourcetype zeek:ssh); SFTP server command logs
Key fields
id.orig_h, id.resp_h, id.resp_p, auth_success, auth_attempts, client, server

Suspicious

Log sources
Zeek conn.log (sourcetype zeek:conn); Zeek ssl.log for the TLS details

id.orig_h, id.resp_h, id.resp_p, service, duration, orig_bytes, resp_bytes

Zeek smb.log (sourcetype zeek:smb) and conn.log rows to port 445 cover the SMB side; flag first-seen external SMB and sudden share writes between internal hosts

Almost nothing. Port 990 is rare on business networks, so any use is worth a look.
Suspicious
A server holds a TLS session on port 990 for many minutes, repeating at fixed intervals

Flag connections to 21, 69, or 990 that are new for the subnet, then compare with the baseline

Log sources

5.5 Sigma Rules and Splunk SPL

Six finished detections follow, one per threat. Each has a complete Sigma rule, a matching Splunk SPL query, a mapping note, false positives, and tuning guidance. The example indexes are index=network, index=edr, and index=firewall - adjust them to your environment. MITRE's official detection strategy DET0416 flags FTP, SMB, and TFTP traffic from suspicious processes with large outbound transfers, and these rules follow that idea.

Rule 1 - TFTP client network activity on a Windows Server High

Covers THR-01. The built-in TFTP client should never speak from a server. One connection is enough to review.

Assumption: Sysmon EventCode 3 events land in index=edr - adjust the index and sourcetype to your environment.

Mapping note: the Sigma selection (EventCode 3 plus Image ending in tftp.exe) is exactly the SPL filter line before the first pipe. Keep the same two conditions when you port the rule to another EDR search language.

False positives
Approved imaging or firmware jobs that fetch with TFTP from servers; short ticketed tests.
Tuning
If a patch server truly needs TFTP, allowlist its destination IP and keep the alert for every other source.

Rule 2 - Outbound FTP upload from a server subnet to an external host High

Covers THR-02. A STOR command from a server to a non-internal host is the core exfiltration signal from the FIN1 story.

Assumption: Zeek ftp.log is normalized to src_ip, dest_ip, user, command, arg, and size in index=network - adjust to your CIM field mapping.

Mapping note: the STOR command, the source range, and the three CIDR filters in Sigma map one to one to the SPL search filters. The stats line only adds context such as bytes and file names; it does not change the match set. For a volume-focused variant, add | where bytes_out > 100000000.

False positives
Ticketed partner uploads; a backup appliance that appears with a routed external address.
Tuning
Keep the allowlist in a lookup table, not in the rule text, so approvals stay reviewable. Review the bytes column weekly to spot slow exfiltration under the threshold.

Rule 3 - SFTP session from a workstation subnet to an external host Medium

Covers THR-03. Successful SSH from a workstation to a first-seen external host is how stolen keys quietly move data.

Assumption: Zeek ssh.log ships to index=network with auth_success and client fields; workstation ranges 10.20.4.0/24 and 10.20.5.0/24 match this page's example network.

Mapping note: auth_success=true is the key filter. Without it, every failed SSH attempt on the internet-facing segment would page the on-call. The Sigma condition (selection and not filter_internal) equals the two SPL filter lines.

False positives
Cloud engineers who reach approved hosts by IP; pentest windows.
Tuning
Add a dest_ip allowlist lookup for approved SFTP endpoints. Alert faster when the same source touches several destinations in one hour.

Rule 4 - First-seen file transfer port per server subnet (21, 69, 990) Medium

Covers THR-04 and general coverage. Attackers pick FTPS on port 990 because TLS hides the commands, so a first-seen view per subnet is the main signal.

Assumption: ftp_ports_baseline is a lookup you refresh monthly from the same search. Pairs found in the lookup are marked seen_before and drop out of the alert.

Mapping note: Sigma alone cannot know history, so this rule ships as experimental and the first-seen logic lives in the lookup join. If you use another SIEM, keep the same pair key: source host plus destination port.

False positives
A legitimately new file transfer service; approved scanner traffic.
Tuning
Refresh the baseline monthly and after change windows. Split the alert by port: 990 events deserve a faster review than 21. Port 445 (SMB) is left out on purpose, because it is normal inside the LAN; watch it with Zeek smb.log and a first-seen rule for external SMB instead.

Rule 5 - FTP or TFTP straight to a raw IP address Medium

Covers THR-05. Rogue tool hosting runs on short-lived servers with no DNS name, so nameless destinations stand out.

Assumption: approved_ftp_hosts lists your approved FTP destinations (this example allows 203.0.113.10 only). For a DNS-aware version, join dest_ip against zeek:dns lookups from the last 24 hours and require an empty match.

Mapping note: the raw-IP idea is expressed as an allowlist exclusion here, which keeps the rule honest in any SIEM. The stronger DNS-absence version needs a join, and the note above shows exactly where to add it.

False positives
Approved hosts missing from the lookup; one-off security scans.
Tuning
Feed every confirmed alert into the firewall blocklist the same day. Keep the allowlist short and owned by one named person.

Rule 6 - Legacy FTP service account seen from a new source host Medium

Covers THR-06. An old service account appearing on a host that never used it is quiet lateral movement with a shared password.

Assumption: ftp_users_baseline maps each legacy account to the hosts allowed to use it; anything else prints as a new pair and stays in the alert.

Mapping note: the USER command row in zeek ftp.log carries the account name, and reply_code tells you whether the server accepted it (230 means success). Add reply_code="230" if your Zeek build logs the final reply on the PASS row, otherwise review both rows of the pair.

False positives
Documented integrations; migration projects between old systems.
Tuning
Retire the accounts you can, and shrink the list over time. Every removal makes this rule sharper.

Real-World Case Study

How a real actor used this technique against banks, told as a teaching case with the defender view at every stage.

Context

Between 2015 and 2016, the group tracked as FIN1 (also called Anunak) attacked banks and payment processors. Public reporting by FireEye describes how the group targeted payment systems, watched test transactions, and moved card data out over FTP from finance and database servers. The summary below follows that reporting and is written as a teaching case.

Note

Public reporting gives the outline but not exact dates, byte volumes, or victim names. The rows below are generalized to periods. Do not quote them as exact timestamps for a specific victim.

Timeline

Date or periodEvent
2015, reported period startEntry through phishing messages and RDP access into the bank network
Weeks after entryA VBS backdoor named BOOTRAMP planted on domain controllers for persistence (a way to survive reboots and stay inside)
Following weeksHands-on exploration of payment-processing hosts over RDP and VNC (a second remote-control tool) sessions
Before the theftAttackers watch test transactions to learn the payment flow and file formats

2016, reportedAttempts to manipulate chip-card processing appear in reporting

Attack chain

  1. Enter the network with phishing and RDP access.
  2. Plant the BOOTRAMP VBS backdoor on domain controllers.
  3. Explore payment-processing hosts and map the data flow.
  4. Watch test transactions to confirm formats and timing.
  5. Stage gigabytes of card records on internal shares.
  6. Exfiltrate with FTP from finance servers to attacker hosts.
  7. Push further with chip-card manipulation attempts.
Detection point

Where defenders could have caught it: outbound FTP from database and finance servers to rare external IPs, plus odd-hours RDP on domain controllers. Both signals are cheap to detect and almost free of false positives.

Response stages

Containment

The response blocked FTP egress at the border, isolated the affected payment servers, and disabled the compromised accounts.

Eradication

Teams removed BOOTRAMP by rebuilding domain controllers instead of cleaning them, then rotated domain and service credentials.

Recovery

Payment logs were reconciled against fraud records, clean images were restored, and domain controller access rules were tightened.

Impact and consequences

Card data theft led to fraud losses and regulatory scrutiny. Rebuilding trust in the domain controller fleet took months, and payment operations ran under heightened review until the environment was proven clean.

Team response and communication

Fraud analysts, the incident response team, and law enforcement worked from one shared evidence timeline. Daily bridge calls kept decisions moving, and a single owner recorded every action so legal and regulators received one consistent story.

Lessons learned

Domain controllers stay offline

Domain controllers never need internet egress. Block it, then prove the block with logs.

FTP from a server is an incident

Treat any FTP session from a server subnet as a potential theft in progress, not a curiosity.

Watch identity stores

The backdoor lived in startup scripts and accounts. Identity monitoring finds persistence that file scans miss.

Long dwell needs retro-hunts

The intruders stayed for months. When a new detection ships, replay it over stored logs to cover the silent period.

Good practice

DLP on bulk egress closes the last gap. When a rule sees hundreds of megabytes leaving a server, the bytes matter more than the protocol name.

Note

MITRE lists two official mitigations for this technique. M1037 Filter Network Traffic means: filter outbound FTP and SFTP traffic from sensitive systems, and inspect what does leave. M1031 Network Intrusion Prevention means: give network sensors and IPS signatures a chance to spot and stop malicious file transfer sessions. The table above turns both into concrete actions with owners.

Home and small office

Small networks carry the same risk in miniature. NAS boxes and routers often run FTP by default. Turn the FTP service off and use SFTP with a strong key instead. Update router firmware and close port 21 on the modem. If you truly need FTP, allow it only from one PC, and read the router log once a month. A free flow view from your router is enough to spot a device suddenly pushing gigabytes at night.

Daily

Response checklist

  • Isolate the server that sent data out, and keep it powered on for forensics.
  • Block the destination IPs and the domain at the firewall and the proxy.
  • Rotate the service account password and any credentials reused with it.
  • Enable MFA on all RDP and SSH entry points.
  • Hunt TFTP and FTP activity across all servers for the last 30 days.
  • Check Zeek smb.log and firewall logs for SMB sessions to external hosts on port 445.
  • Check which systems still have the TFTP client installed, and remove it.
  • Add or verify the egress rule that blocks 21, 69, and 990 from servers.
  • Write a short incident note and share the indicators with your ISAC.
