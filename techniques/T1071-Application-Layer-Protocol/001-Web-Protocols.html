1

Overview

Web protocols are the most common language of the internet. Attackers know this, so their malware speaks it too. This page explains T1071.001 and shows how to detect it with logs you already have.

This page is version 2.0 of this guide, re-checked against MITRE ATT&CK in October 2026 (sub-technique version 1.5).

After an attacker gets code running on one computer, they need a channel back to that computer. They use the channel to send orders and to steal data (this theft is called exfiltration — moving stolen data out of the network). Security teams call this channel C2 (command and control — the channel an attacker uses to send orders to malware inside a victim network).

Technique T1071.001 covers C2 that uses web protocols: HTTP and HTTPS on ports 80 and 443. It also covers WebSocket — a protocol that keeps a web connection open for two-way messages. The official MITRE description makes two points. First, web traffic is extremely common, so it is a perfect hiding place. Second, HTTP and HTTPS packets have many fields and headers, and attackers can hide data in them. An implant (the malware piece that lives on the victim host) acts like a small web client. It sends POST and GET requests to a server the attacker controls, and it reads orders from the answers. Well-made implants copy the look of normal browser traffic, so they blend in. Because every office allows web traffic, this channel passes most firewalls without any special setup.

The strongest form is HTTPS beaconing. A beacon is a repeated check-in call from malware to its C2 server. TLS (the encryption that protects HTTPS) hides the content of each call. But a proxy (a server that forwards the company's web traffic and logs every request) still sees the destination, the timing, and the sizes. Those three signals are what detection engineering works with.

Why it matters

Web traffic is the biggest traffic class on almost any network, so web C2 hides in a crowd. Real intrusions use it at every stage. Loaders (small programs that fetch the real malware) pull more code in over HTTP. Beacons keep a steady heartbeat over HTTPS. Stolen data leaves inside plain POST bodies. If you catch the beacon, you catch the intrusion while it is still young.

The same story in words

This list is the text version of the simulation. It is the full alternative for screen readers and for readers with JavaScript turned off.

  1. Step 1 — Delivery. An employee opens invoice.docm on FIN-WS-04. A macro runs a small loader (a tiny program that downloads the real malware). The loader makes its first web call through the corporate proxy. Defender view: the proxy logs winword.exe as the client process, and cdn-updates[.]com appears for the first time on the estate.
  2. Step 2 — Check-in. The loader POSTs host details to /wp-content/uploads/gate.php. It hides the data in a cookie value encoded with base64 (a text encoding that turns any data into letters and digits). The C2 answers with a task inside a Set-Cookie header. Defender view: a POST of exactly 1042 bytes to a blog URL, with a large Set-Cookie response, deserves a second look.
  3. Step 3 — The 60-second metronome. The implant beacons every 60 seconds plus or minus 3 seconds of jitter (small random changes in timing). Every POST body is 1042 bytes. Defender view: 18 regular beacons with a size spread below 1 percent. Humans browse at random, so timing this clean is a machine.
  4. Step 4 — Masquerade. The beacon claims to be Internet Explorer 7 and shifts some traffic to quiet hours to look like legacy web use. Defender view: the user-agent (UA — the browser name string a client sends with each request) does not match the Windows 11 operating system. The JA3 hash (a fingerprint of the client's TLS handshake) also does not look like a real browser.
  5. Step 5 — Task: harvest and send. The implant collects saved browser passwords. It splits them into eight POST bodies and uploads about 4.1 MB in total. Defender view: egress bytes per process rise, and the uploads go to a domain that is only 21 days old.
  6. Step 6 — C2 rotation. DNS for cdn-updates[.]com now returns 198.51.100.77 instead of 198.51.100.23. The beacon follows the new address without any change on the host. Defender view: the destination IP changed mid-session while the SNI (the domain name a client names during the TLS handshake) and the URL path stayed the same. Watch the domain, not one IP.
  7. Step 7 — Proxy alert fires. The SIEM (the central system that collects logs and raises alerts) joins the legacy user-agent with the 60-second periodicity. Rule BEACON-01 fires for FIN-WS-04. Defender view: pull 24 hours of proxy logs for the host, then check domain age and reputation before you escalate.
  8. Step 8 — Contain. The proxy denies cdn-updates[.]com. The host is isolated from the network. A 30-day retro hunt (a search through stored old logs) finds no other host with the same pattern. Defender view: block the domain first, because the IP rotates. Preserve logs, then reimage the host.

Red Team / Hacker Perspective

This section explains, at concept level, why attackers pick web protocols and what their tooling looks like. It contains no working attack code. Everything shown runs only in a closed lab you own.

Warning

This page exists for defense education. Use the lab commands only against systems you own or have written permission to test. Using them against other people's systems is illegal in most countries.

When and why attackers use web protocols

  • Firewalls already allow ports 80 and 443 out of most networks, so no new holes are needed.
  • TLS hides commands and stolen data from passive network capture.
  • Web traffic is huge and noisy, so a few extra requests rarely stand out.
  • Infrastructure is cheap: a compromised WordPress blog, a free host, or a rented VPS (a cheap rented server) with a valid certificate all work.
  • Domain fronting hides the real C2 domain behind the name of a large, trusted provider. CDNs (content delivery networks — firms that serve web content from many locations) can also carry the traffic, so the visible destination is a trusted name.

How it is performed, at concept level

A typical implant runs a simple loop: sleep, check in, fetch a task, run it, sleep again. Modern frameworks such as Cobalt Strike, Empire, and Mythic let the operator shape this traffic with a malleable profile. That profile is a configuration file. It sets the URIs (the path part of each web address), the user-agent, headers, and certificates the beacon uses. Common shapes include:

  • POST check-ins with task data hidden in cookies or body, as in this page's story.
  • GET polls that read orders from an image path, a favicon, or an API endpoint.
  • Staged fetches where the first request downloads the real payload.
  • Exfiltration by chunked POST uploads that imitate file sync clients.

Prerequisites an attacker needs

  • Code execution on at least one host inside the network.
  • Outbound access to ports 80 or 443, directly or through the proxy.
  • A reachable C2 server: a registered domain, a TLS certificate, and a redirector (a middle server that hides the real C2).

Common variations and attacker mistakes

  • Fixed timing. Sleeping exactly 60 seconds with no jitter makes the beacon trivial to graph.
  • Hardcoded single IP. One address in the binary means one blocklist entry stops the campaign.
  • Wrong OS in the user-agent. Claiming IE7 on a Windows 11 host is a mismatch a defender can join on.
  • Default framework URIs. Stock paths land in every public blocklist within weeks.
  • Certificate reuse. The same self-signed certificate across campaigns links them together.

Blue Team / SOC Perspective

Defenders cannot read encrypted HTTPS content, but they do not need to. Timing, sizes, destinations, and client fingerprints carry enough signal to find beacons.

How defenders see web C2

The corporate proxy is the main window. Every user request lands in the proxy log with a source address, a destination host, a method, a URL, a byte count, and often a user-agent. TLS adds more metadata. The SNI (server name indication — the domain name a client names during the TLS handshake) tells you which name the client asked for. The certificate details and the JA3 hash (a fingerprint of how the client builds its TLS hello message) describe the client program. None of these fields reveal content, yet together they describe the client very well.

Good practice

Baseline your estate first. One week of proxy data shows your normal gaps and sizes. Every detection in section 5 gets sharper when you know what normal looks like.

Artifacts web C2 leaves behind

  • Regular request intervals with small, steady body sizes.
  • User-agents that do not match the operating system (a UA masquerade — the malware pretends to be another program).
  • Cookies or parameters that carry long base64 blobs.
  • Outbound POST uploads that no business process explains.
  • Fresh domains, short DNS TTLs, and rotating destination IPs.
  • TLS sessions straight to raw IP addresses with no SNI.

Where to look

The main sources are proxy logs, Zeek (a free network sensor that records connections, TLS, HTTP, and DNS), EDR, and flow logs.

Why it matters in the attack chain

Web C2 sits in the Command and Control tactic, right after initial access. It is the attacker's lifeline: without C2 there are no hands-on-keyboard actions, no payload delivery, and no staged exfiltration. Cutting it early usually freezes the intrusion where it stands.

Triage flow for a suspected beacon

  1. Note the host, user, and process from the alert. Write down the destination host and IP.
  2. Pull 24 hours of proxy logs for that source. Graph requests per minute as a timechart.
  3. Measure the gaps between requests and the spread of body sizes. Regular gaps and flat sizes point to a beacon.
  4. Check the domain: age, reputation, category, and whether the SNI or JA3 looks like a real browser.
  5. Join with EDR (endpoint detection and response — software that watches the host). Which process made the calls, and does its process tree make sense for this user?
  6. Decide: block the domain at the proxy, isolate the host, and open an incident ticket.
  7. Hunt the same user-agent, SNI, and destination across the last 30 days to find other hosts.

Detection Engineering Deep Dive

This is the working part of the page. Five subsections map the technique to frameworks, threat intelligence, ranked threats, raw log examples, and detections you can adapt today. MITRE now ships an official detection strategy for this technique: DET0027, "Detection of Web Protocol-Based C2 Over HTTP, HTTPS, or WebSockets". 5.2 Threat Intelligence

Intelligence turns a single alert into a campaign view. These are the source types a small team can realistically combine.

Free and vendor neutral. The T1071.001 page lists 431 procedure examples — Cobalt Strike, Amadey, Anchor, APT18, Agent Tesla, the 3CX supply-chain attack, and more. Turn them into detection tests.

Vendor reports

Research from security vendors often publishes the exact user-agents and URI paths taken from malleable profiles.

OSINT feeds

OSINT (open-source intelligence — public feeds anyone can read): abuse.ch URLhaus and ThreatFox, and AlienVault OTX pulses, share live C2 URLs and domains with tags.

Commercial feeds

Risk scores, domain age, and fronting infrastructure lists. Best used for enrichment at alert time.

ISACs

Internal telemetry

Your own proxy history is your best feed. It shows what normal looks like on your estate.

5.4 Logs and Patterns

Each card pairs one threat with the logs that reveal it and one realistic event. All events come from the same story: host FIN-WS-04 (10.20.4.17) infected on 2026-08-11, talking to cdn-updates.com behind proxy 10.10.0.20.

THR-01 — HTTPS C2 beaconing

Critical
Log sources
index=network sourcetype=zeek:conn and zeek:ssl; index=proxy sourcetype=squid
Key fields
id.orig_h, id.resp_h, orig_bytes, resp_bytes, duration; proxy: src, cs_method, cs_host, sc_bytes
Normal
Browsing comes in bursts. Sizes vary a lot, gaps are random, and hosts idle for long stretches.
Suspicious
A fixed request rhythm with body sizes that barely change, continuing through the night.
Detection logic
Bin POSTs per source and destination into 1-minute buckets. Alert when 15 or more arrive in 15 minutes and the size spread stays under 1 percent of the mean.

Field meanings: orig_bytes counts bytes client to server, resp_bytes the reply, duration is session seconds, service shows the detected protocol. Watching orig_bytes stay flat across beacons is the tell.

THR-02 — Exfiltration via HTTP POST

High
Log sources
index=proxy sourcetype=squid; index=network sourcetype=zeek:conn for volume
Key fields
cs_method, sc_bytes, cs_host, cs_uri_path; zeek: orig_bytes
Normal
Uploads match business apps: email, sync clients, ticket attachments, each to known hosts.
Suspicious
Eight POSTs of 524288 bytes each to a 21-day-old blog domain, outside approved categories.
Detection logic
Sum POST body bytes per source and host in 5-minute bins; alert above 1 MB to a non-approved category or young domain.

Field meanings: the first number 1786442820.642 is a Unix epoch time (seconds counted since 1970-01-01 UTC). It decodes to 2026-08-11 10:07 UTC, five minutes after the beacon. TCP_MISS/200 is the proxy result, 524288 is the body size in bytes, DIRECT names the resolved peer, and the last string is the user-agent. Eight chunks of half a megabyte make the 4.1 MB from the story.

THR-03 — C2 behind domain fronting or trusted SaaS

High
Log sources
index=network sourcetype=zeek:ssl; proxy with TLS inspection or ICAP where lawful
Key fields
server_name (SNI), ja3, id.resp_h, certificate subject
Normal
SNI and the HTTP Host header inside TLS match, and both belong to the same provider.
Suspicious
SNI names a shared CDN while the HTTP Host inside names the attacker domain; JA3 is not a browser.
Detection logic
Alert when SNI and inner HTTP host differ on a shared-CDN destination, or when a non-browser JA3 pairs with a trusted SaaS name.

Field meanings: server_name is the SNI, ja3 is the client TLS fingerprint, validation_status summarizes the certificate check. In this session the HTTP Host header inside TLS was cdn-updates.com. That header is visible only with lawful TLS inspection or an ICAP proxy (an add-on that inspects web sessions for the proxy). Without decryption, SNI plus JA3 plus reputation still carries signal.

THR-04 — Dropper fetch from rare host

Medium
Log sources
index=proxy sourcetype=squid; index=network sourcetype=zeek:http
Key fields
cs_method, cs_host, cs_uri_path, sc_bytes, response content type
Normal
Software fetches go to vendor update domains with stable categories.
Suspicious
A GET for a .dat payload from a 21-day-old domain, content type octet-stream, minutes after a document macro ran.

Alert on executable-looking content types fetched from domains younger than 30 days or outside approved categories.

Field meanings: the leading 1786442280.118 is a Unix epoch time; it decodes to 2026-08-11 09:58 UTC, minutes before the check-in. TCP_MISS/200 means the proxy fetched the object fresh, 48231 is the object size, and the URL sits inside a blog uploads folder. A payload named like a patch, served by a blog, is a classic dropper fetch.

THR-05 — Header and user-agent masquerade

Medium
Log sources
index=proxy sourcetype=squid; index=network sourcetype=zeek:ssl for JA3
Key fields
cs_user_agent, src, cs_host; asset OS build from the CMDB (device inventory) or EDR
Normal
User-agents match installed browsers and OS builds, and change with patch cycles.
Suspicious

Field meanings: the first number, 1786442520.911, is a Unix epoch time — seconds counted since 1970-01-01 UTC. THR-06 — Direct-IP HTTPS with no SNI or domain

Medium
Log sources
index=network sourcetype=zeek:ssl; firewall or proxy CONNECT logs
Key fields
server_name (empty or IPv4), id.resp_h, ja3, certificate subject
Normal
Workstations resolve names first, so almost every TLS session carries an SNI.
Suspicious
HTTPS straight to an IP with an empty SNI and a self-signed certificate.

Alert on TLS where the SNI is empty or IPv4-shaped and the source sits in a workstation range.

Field meanings: an empty server_name means the client never named a domain, and validation_status flags the certificate. Some printers and appliances behave the same way, so keep an appliance allowlist handy.

5.5 Sigma Rules and Splunk SPL

Six complete Sigma rules, one per threat, each with a matching Splunk SPL query. Copy, adjust the index and field names, then deploy.

Note

Field names below assume squid logs mapped to CIM-style names (src_ip, cs_method, cs_host, cs_user_agent, sc_bytes) and Zeek logs in index=network. Adjust the index and field names to your environment before you deploy.

SIG-01 — Beacon periodicity (THR-01)

Critical

Mapping note: Sigma counts POSTs per source and host in a 15-minute window. The SPL rebuilds the same window in 1-minute bins. It adds the size-variance check from the story: stdev (standard deviation — a number that measures how spread out values are) under 1 percent of the mean.

Assumption: index=proxy sourcetype=squid with fields src_ip, cs_method, cs_host, sc_bytes — adjust index and field names to your environment.

False positives: backup agents, sync clients, and monitoring probes also poll on a schedule.

Tuning: exclude known software-update hosts, require the destination to sit outside approved web categories, and raise the threshold for server ranges.

SIG-02 — Large POST uploads (THR-02)

High

Mapping note: the Sigma rule sums body bytes per source-host pair over 5 minutes. The SPL mirrors the same window and the 1 MB threshold exactly.

Assumption: index=proxy sourcetype=squid with sc_bytes mapped from the proxy byte field — adjust index and field names to your environment.

False positives: large webmail attachments and approved cloud sync uploads.

Tuning: allowlist your backup and sync destinations by category, and set the byte threshold per user group rather than globally.

SIG-03 — Long machine-generated host labels (THR-03)

High

Mapping note: the Sigma regex (a text pattern that matches strings) matches long first labels. It checks both DNS and TLS name fields. The SPL covers the DNS side; add the same eval over server_name on zeek:ssl if you store it.

Assumption: index=network sourcetype=zeek:dns with the query field extracted — adjust index and field names to your environment.

False positives: real CDNs that bake content hashes into long subdomains.

Tuning: allowlist the long-label CDNs your business uses, and add an entropy score (a measure of how random a string looks) before alerting.

SIG-04 — Traffic to recently registered domains (THR-04)

Medium

Mapping note: Sigma reads the enrichment field domain_age_days, which your pipeline adds from a domain-age feed at ingest. The SPL pulls the same field from a lookup instead. Keep the lookup fresh or the rule goes blind.

Assumption: index=proxy sourcetype=squid plus a lookup table local_domain_intel refreshed daily from your domain-age feed — adjust names to your environment.

False positives: new marketing campaign domains and fresh SaaS onboarding.

Tuning: feed the allowlist from procurement, and drop the threshold only for high-risk categories such as file sharing.

SIG-05 — Legacy IE7 user-agent (THR-05)

Medium

Mapping note: both checks look for the same two substrings of the user-agent. The CIDR filter (a match on an IP range) keeps the scanner subnet quiet. Join with CMDB (your device inventory) or EDR data to confirm the OS mismatch on the source host.

Assumption: index=proxy sourcetype=squid with cs_user_agent extracted — adjust index and field names to your environment.

False positives: legacy intranet clients and embedded devices.

Tuning: keep the scanner exclusion tight and add a per-OS join so the alert fires only on modern builds.

SIG-06 — TLS to a raw IP address (THR-06)

Medium

Mapping note: Sigma matches an IPv4-shaped SNI or an empty SNI on port 443. The SPL implements both branches in one where clause; the ja3 hash rides along for context.

Assumption: index=network sourcetype=zeek:ssl with server_name and ja3 extracted — adjust index and field names to your environment, and add a cidrmatch filter for appliance subnets if needed.

False positives: IP-based updates from printers and appliances.

Tuning: exclude appliance subnets, and alert only for workstation source ranges.

Real-World Case Study

Conti was one of the most damaging ransomware brands of 2021. Public advisories describe how its intrusions leaned on HTTPS beacons. This section retells that pattern for learning.

Note

Public reporting (CISA advisory AA21-265A and the 2021 Conti leak) describes the typical order of operations, not exact times for each victim. The dates below follow the advisory; real hours differed per victim.

Context

Conti worked as a hands-on-keyboard ransomware service: after the initial access, attackers typed commands themselves instead of relying on automation. Initial access came from IcedID or BazarLoader phishing. After the loader ran, operators used Cobalt Strike HTTPS beacons with malleable profiles as their main channel. The beacons looked like small web requests to fresh domains, which is why proxy telemetry mattered so much.

Timeline

WhenEvent
Feb 2021, day 0Employee opens a phishing attachment. The IcedID or BazarLoader loader lands and calls out.
Hours after accessCobalt Strike HTTPS beacon checks in to a newly registered domain behind a malleable profile.
Days 1 to 3Hands-on-keyboard discovery: nltest (a Windows command that lists domain trusts) and BloodHound-style tooling map Active Directory.
Before encryptionVolume shadow copies (Windows backup snapshots) deleted; data staged and exfiltrated to Mega (a public file-sharing service) and via multipart POSTs.
About 3 to 8 days after access (median)Conti encryption runs across file servers and endpoints. A ransom note appears.

Attack chain

  1. Phishing delivers the loader. The user opens the attachment on a standard workstation.
  2. The loader fetches and starts the Cobalt Strike beacon over HTTPS to a fresh domain.
  3. The beacon keeps a steady check-in rhythm. Operators log in through it and map out Active Directory (the company's central user and computer directory).
  4. Attackers escalate privileges, reach domain admin, and delete shadow copies.
  5. Data is staged and exfiltrated before encryption to add leak-site pressure.
  6. Conti encrypts the estate, and a ransom demand follows.
Detection point

The beacon was visible days before encryption: proxy logs showed periodic traffic to a newly registered domain with a legacy user-agent. EDR separately flagged the beacon process lineage. Either signal, joined in the SIEM, offered time to act.

Containment

Responders blocked the C2 domains and IPs at the proxy and firewall, isolated affected segments, and disabled the VPN accounts the attackers used. Blocking the domain, not just the IP, mattered because the beacons rotated addresses.

Eradication

Teams removed beacon implants from every host, revoked Kerberos tickets (the passes that prove identity inside a Windows network), and rotated credentials, including service accounts. Beacons that reappeared after cleanup usually meant a missed host, so the sweep repeated until proxy telemetry stayed quiet.

Recovery

Restores ran from backups in phases. VPN access returned with extra controls, and the new proxy rules stayed in place. Each phase had an owner and a rollback path.

Impact and consequences

Victims faced multi-day outages, a ransom demand, and the threat of a data leak site. Some victims paid, and public costs often ran into the millions. The channel that carried the attack — steady HTTPS beacons — was also the signal that could have stopped it days earlier.

Team response and communication

Effective responses ran a war room with one incident lead. Executives got short updates every 4 to 6 hours. Legal and insurers joined early, because payment decisions and disclosure rules carry deadlines. The SOC kept a written log so shift handovers stayed accurate.

Lessons learned

Keep proxy logs 90 days or more

Retro hunts work only when history exists. Short retention erases the evidence you need most.

Allowlist server egress

Servers rarely need general web access. Tight egress lists shrink the beacon surface fast.

Alert on periodicity

Timing and size math catch beacons that content filters miss.

Watch new domains

Fresh domains carried the C2. A 30-day age rule is cheap and effective.

Test restores

Recovery speed decided downtime. Untested backups failed when it mattered.

Rehearse communication

One incident lead and a clear update cadence kept the response calm and auditable.

Mitigation and Defense

No single control stops web C2. The table below lists the control areas that matter, who owns each one, and what it buys you.

Official ATT&CK mitigations

MITRE lists two official mitigations for this technique. M1037 Filter Network Traffic means: restrict and monitor outbound web traffic (HTTP/HTTPS) through a managed proxy, with allowlists and logging. M1031 Network Intrusion Prevention means: inspect web sessions at the network boundary and block beacon-like patterns. The controls below put both into practice.

Home and small office

You will not run Zeek at home, and you do not need to. Turn on your router's DNS filtering, or point devices at a filtering resolver. Keep operating systems and browsers on automatic updates. Remove browser extensions you do not use. Keep one offline backup and one cloud backup, and test a restore once. For a tiny business, a hosted secure web gateway gives you proxy logs without new hardware.

Where TLS inspection fits

TLS inspection shows the URLs and hosts inside HTTPS, which lifts detection quality a lot. It also touches privacy, so scope it: inspect guest and standard user traffic where policy and law allow, and keep metadata-only analytics for the rest. Timing, sizes, and JA3 work with no decryption at all.

Habits that keep detections healthy

Daily

Review every beacon alert and record one line: true or false positive, and why. Note any new allowlist request the same day.

Weekly

Tune the three noisiest rules. Check the log pipeline for missing sources and stale lookups. Close the loop on false positives with the rule owner.

Monthly

Replay the lab beacons and score the rules. Audit retention and log coverage. Review rule ownership so no alert is an orphan.

Response checklist

  • Record host, user, process, destination host, and destination IP from the alert.
  • Pull 24 to 48 hours of proxy history for the source and graph the request rhythm.
  • Check the beacon pattern: regular gaps, flat sizes, odd user-agent or JA3.
  • Check domain age, category, and reputation for the destination.
  • Block the domain at the proxy and add the host to the watchlist.
  • Isolate the endpoint and preserve memory and disk images if the case is serious.
  • Retro-hunt the same user-agent, SNI, and destination across 30 days.
  • Hand the case to the IR lead with the timeline and the evidence bundle.
