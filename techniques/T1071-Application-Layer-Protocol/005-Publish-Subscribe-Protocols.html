1

Overview

Publish/subscribe protocols are the message system behind many smart devices and cloud apps. Attackers use them as a quiet command channel. This section explains the idea in plain words.

This page is version 2.0 of this guide, re-checked against MITRE ATT&CK in October 2026 (sub-technique version 1.1, last modified 15 April 2025).

MITRE ATT&CK calls this behavior Application Layer Protocol: Publish/Subscribe Protocols (T1071.005). An implant (malware planted on a device) connects to a message broker. The broker is a server that moves small messages between programs. The implant waits for orders on a named channel, called a topic. The attacker publishes commands to that topic. The implant publishes results back. All data flows through the broker, so the device and the attacker never talk to each other directly.

Why should defenders care? Three reasons. First, the traffic looks like normal cloud messaging, which many networks allow out by default. Second, IoT devices (Internet of Things — small connected devices such as cameras and sensors) often have no egress rules for traffic leaving the network. One open port is then enough for the attacker. Third, the connection can sit idle for days and only blink with tiny keepalive messages (small "I am still here" packets), which few tools flag. The technique belongs to the Command and Control (C2) tactic — C2 is the channel an attacker uses to send orders to malware. After the attacker gets in, this is how they stay in touch and pull data out.

NOTE · Explain first — publish/subscribe for beginners

A broker is a server that holds channels called topics, for example home/cam1/commands. A publisher writes messages to a topic. A subscriber receives copies of the messages on every topic it follows. The two sides never meet directly: the broker connects them.

Four protocols dominate this space. MQTT is lightweight and very common on IoT devices; port 1883 is plaintext and port 8883 adds TLS (transport layer security — the standard encryption for connections). AMQP is heavier and common in enterprise and cloud messaging; port 5672 is plaintext and port 5671 adds TLS. STOMP is a simple text protocol over TCP, often on port 61613. XMPP (also called Jabber) is best known as a chat protocol. It also carries publish/subscribe message flows through a standard extension, so chat servers can act as brokers; clients usually connect on port 5222.

Written version of all 8 steps

  1. Step 1 — Weak door. The attacker logs in to the lobby camera IOT-CAM-17 (192.168.8.34) with the default admin password, which was never changed. The camera sits on a flat IoT VLAN — one shared network segment for devices — that can reach the internet. Defender view: A login from a new source plus a new process on a camera is already strange — cameras rarely start new programs.
  2. Step 2 — Post office opens. Malware on the camera opens an MQTT CONNECT to the attacker broker mqtt.badstream[.]net (198.51.100.90) on port 1883. From this moment the device has a live command channel. Defender view: Cameras should never speak MQTT to the internet. TCP/1883 egress from the IoT VLAN is the first alarm.
  3. Step 3 — Subscribe to orders. The implant subscribes to the topic cmd/cam-17 and waits silently. A subscription carries no message body, so the quiet connection pattern is the tell, not the traffic volume. Defender view: An idle connection with a 60-second keepalive from a camera deserves a look.
  4. Step 4 — Heartbeat publish. Every 60 seconds the camera publishes a small status message with uptime and load to stat/cam-17. This proves the channel works. Defender view: Periodic small publishes from one device look exactly like a beacon — a regular signal that shows malware is alive. Measure the cadence per host.
  5. Step 5 — Order arrives. The attacker publishes a command to cmd/cam-17: scan the local network 192.168.8.0/24 for new targets. Defender view: The broker is the command injection point. Broker-side topic ACLs would stop a write from an untrusted client.
  6. Step 6 — Results flow back. The camera publishes scan results to data/cam-17. It found 11 hosts and sends them in small chunks of a few kilobytes. Defender view: Data topics can carry stolen files. Size limits force chunking, so watch for many similar messages.
  7. Step 7 — Odd port alert. The SIEM (security information and event management — the log platform the SOC watches) raises the rule for outbound 1883/8883 from the IoT VLAN. The analyst checks the destination: it is not on the broker allowlist. Defender view: Allowlist known brokers only. Anything else on these ports is a candidate incident.
  8. Step 8 — Close the post office. The team blocks 198.51.100.90 and the domain, rebuilds the camera from known firmware (the device's built-in software), moves the IoT VLAN to deny-by-default egress, and rotates device passwords. Defender view: Fix the policy, not only the device — the next implant should find a closed door.

Red Team / Hacker Perspective

This section explains, at concept level, why attackers like publish/subscribe channels and how they are built. It stays defensive: the only commands shown are safe lab exercises on machines you own.

WARNING · Ethics

This page is for defense education only. Use the lab commands exclusively against systems you own or are explicitly allowed to test. Attacking other people's devices, brokers, or networks is illegal and harmful. We describe attacker behavior so defenders can recognize and stop it — never to provide a working attack recipe against real targets.

Why attackers choose publish/subscribe

  • Decoupling. The implant and the operator both talk only to the broker. The operator's IP address never appears in the device's traffic.
  • Asynchronous delivery. The implant can come online hours after a command was sent. The broker queues or retains the message, which survives short network gaps.
  • One-to-many tasking. A single publish to a wildcard topic (a pattern that matches many topics) can reach hundreds of bots at once. That is a built-in broadcast to the botnet — the network of infected machines.
  • Innocent-looking traffic. Encrypted broker sessions on 8883 or 5671 look like ordinary cloud messaging to a web-focused proxy.
  • Existing tooling. Standard client libraries make a small implant, and public red team frameworks already support MQTT-style channels.

How the channel is built (concept level)

  1. Get device access. Common entries are default credentials on cameras, an exposed management interface, or a vulnerable web application on a Linux server.
  2. Install a small implant. It only needs to connect, subscribe, publish, and run one command at a time — a few hundred lines of code.
  3. Connect to a broker. Either an attacker-run broker on rented infrastructure, or — sneakier — the victim organization's own internal broker with weak ACLs. ACLs (access control lists) are broker rules that say which client may read or write which topic.
  4. Subscribe to a command topic. For example cmd/<device-id> or h/<campaign>/cmd. The implant then waits.
  5. Publish heartbeats and results. Status to a stat/ topic, results or stolen data to a data/ topic, often in small chunks.
  6. Receive tasking. The operator publishes commands; the implant runs them and reports back. QoS levels (quality of service — how firmly the broker confirms delivery) control delivery guarantees.

Where it applies and what it needs

  • IoT VLANs. Cameras, badge panels, sensors — often Linux-based, often with factory passwords.
  • Linux servers. Application servers that already speak AMQP fit in naturally.
  • Cloud messaging. Managed queues and service buses can be abused with stolen long-lived credentials.
  • Prerequisites. Network egress to a broker port (1883/8883/5671/5672/61613), a credential or open ACL, and knowledge of the topic naming scheme.

Lab-only examples

Both examples run entirely on your own lab VMs. They show the protocol mechanics that the detections in section 5 look for.

On port 1883 the CONNECT packet carries the client ID, user name, and password in cleartext. Anyone on the path can read and replay them. On port 8883 with TLS the same packets are unreadable — that is why broker hardening matters.

Variations and attacker mistakes

  • Variation: abusing the organization's own broker, where traffic never crosses the internet boundary.
  • Variation: retained messages (messages the broker keeps and hands to every new subscriber) as a hiding place — the new implant reads the last command immediately.
  • Variation: QoS 1 for reliable delivery of results, QoS 0 for fire-and-forget tasking.
  • Mistake: default ports stand out. Most estates have almost no broker traffic, so 1883 egress is loud.
  • Mistake: predictable client IDs such as cam17-8f2 give defenders an instant pivot into scope.
  • Mistake: a fixed 60-second publish cadence is a beacon signature that per-host baselines catch.
  • Mistake: forgetting that TLS SNI still names the broker domain even when the payload is encrypted.

Blue Team / SOC Perspective

From the SOC side, a publish/subscribe channel looks like one long, quiet connection to an unusual destination. A small set of records names the device behind it. Here is what to look for and how to triage. The log names below come from Zeek, an open network monitor that watches traffic and writes conn, ssl, and mqtt logs.

How defenders see the channel

Most networks carry very little broker traffic. That scarcity is the defender's advantage: one session on 1883 or 8883 from a camera VLAN is an outlier even before you read any payload. The connection often stays open for hours with tiny keepalive flows. Payload sizes stay small — hundreds of bytes per minute — until stolen data starts to move out in chunks.

Artifacts left behind

  • Long-lived TCP sessions to broker ports (1883, 8883, 5671, 5672, 61613) with low but steady byte counts.
  • MQTT CONNECT records in zeek mqtt.log with a client ID that often encodes the device name.
  • Subscription and publish records naming topics such as cmd/, stat/, or data/.
  • TLS SNI values in zeek ssl.log. SNI is the server name a client announces when it opens an encrypted session. It reveals the broker domain even when the content is encrypted.
  • Broker-side audit entries: authentication results, ACL denials, and per-client publish counts.
  • On Linux servers: an unknown process holding the broker socket, or a miner spawned right after a command message.

Where to look

Why it matters and how it fits the attack chain

T1071.005 is a Command and Control technique: it is the corridor an attacker keeps open after initial access. Through it they run discovery, launch further tool downloads, and push stolen data out in small pieces. Stopping the corridor does not remove the implant, but it blinds the operator. Most IoT malware has no working fallback channel, so the device effectively drops out of the botnet.

Short triage flow

  1. Confirm the destination: is the broker on the approved broker allowlist?
  2. Pull zeek conn and mqtt records for the source device for the last 30 days.
  3. List every client that contacted the same broker — scope before you act.
  4. Check broker audit logs for commands published to cmd/ topics for that client.
  5. Isolate the device segment; block the broker IP, domain, and SNI at egress.
  6. Rebuild the device from known firmware, rotate its credentials, and file the incident.

5.2 Threat Intelligence

Threat intelligence turns isolated log lines into named behavior. For publish/subscribe C2, the useful sources are worm research, botnet trackers, and your own telemetry. The cards below show where to collect, and the table shows what has actually been observed in the wild.

MITRE ATT&CK

The T1071.005 page names the behavior and links procedure examples. Use it as the shared language for rules and reports. MITRE also ships an official detection strategy for this technique: DET0002, Behavioral Detection of Publish/Subscribe Protocol Misuse for C2. It flags non-standard processes that beacon to message brokers. GLOOXMAIL is the page's only official procedure example.

Vendor reports

Research teams such as Trend Micro, Unit 42, and Talos publish studies of worms (self-spreading malware) and botnets (networks of infected machines). They share broker addresses, module names, and spread patterns.

OSINT feeds

Free open-source feeds (OSINT — public intelligence anyone can collect) such as abuse.ch and AlienVault OTX share indicators. They list broker IPs, broker domains, and file hashes you can match in logs.

Commercial feeds

Paid platforms add context, actor attribution, and confidence scores. Useful for triage, but verify against your own data before blocking.

ISACs

Sector information sharing groups (Information Sharing and Analysis Centers) pass vetted alerts and indicators between member companies quickly — often days before public write-ups.

Internal telemetry

Your zeek and firewall logs reveal which brokers actually matter to your estate. Intelligence works best when it explains what you already see.

From collection to application

  1. Collect. Pull ATT&CK updates, vendor blog posts, and OSINT indicators into one tracker. Record the date and the source with every item.
  2. Analyze. Match indicators against your retained logs. Mark confidence, and drop stale items quickly — attacker brokers often rotate weekly.
  3. Apply. Turn confirmed items into Sigma and SPL detections, egress blocklists, and hunt tasks. Review the hits monthly and retire what never fires.

5.4 Logs and Patterns

Each threat below gets its log sources, key fields, a normal-versus-suspicious comparison, one detection logic sentence, and one realistic event example. The examples use one consistent lab estate. Two cameras sit on the IoT VLAN: IOT-CAM-17 (192.168.8.34) and IOT-PANEL-03 (192.168.8.51). A Linux server, FIN-SRV-12 (10.20.12.12), hosts applications. The corporate broker is mqtt.fin-example.com (10.10.0.40). The attacker runs an MQTT broker at 198.51.100.90 (mqtt.badstream[.]net) and an AMQP host at 203.0.113.140 (amqp.harbormail[.]net).

THR-01 — MQTT C2 on IoT devices High

Log sources
zeek:mqtt (CONNECT records), zeek:conn, firewall traffic logs
Key fields
client_id, mqtt_version, connect_status, id.orig_h, id.resp_h, id.resp_p — client_id names the device; connect_status 0x00 means the broker accepted the session
Normal
Cameras talk RTSP and ONVIF inside the VLAN; no MQTT sessions leave the site at all
Suspicious
An MQTT CONNECT from the IoT VLAN to a public IP, followed by subscriptions to cmd/ topics
Detection logic
Alert when a device on the IoT VLAN opens MQTT to a public address that is not on the broker allowlist, or subscribes to a command topic.

This single record already proves the threat. A camera negotiated an MQTT 3.1 session with an external broker. The client ID cam17-8f2 tells you exactly which device to isolate.

THR-02 — Exposed or malicious broker takeover High

Log sources
zeek:conn, firewall traffic logs, internet-facing broker scan results
Key fields
duration, orig_bytes, resp_bytes, orig_pkts, resp_pkts, service — long durations plus two-way traffic show an active session, not a scan
Normal
Dozens of internal clients connect to one or two approved internal brokers only
Suspicious
Many different internal sources, across VLANs, converging on one external broker; or your own broker reachable from the internet without authentication
Detection logic
Alert when more than five distinct internal sources connect to one external broker address in 24 hours, or when the corporate broker accepts unauthenticated sessions.

Read the fields as a story. The session lasted 30 minutes (duration 1803.2 seconds). Both sides sent data, and the service is confirmed MQTT. One host is interesting; several hosts doing this to the same broker is an incident.

THR-03 — AMQP abuse in cloud pipelines Medium

Log sources
zeek:ssl (SNI for 5671), zeek:conn, cloud VPC flow logs
Key fields
server_name, version, cipher, established, validation_status — server_name reveals which broker the server trusted, even though the payload is encrypted
Normal
Application servers speak AMQP only to the corporate message queue or a known managed vendor endpoint
Suspicious
An application server establishes TLS to port 5671 on a hostname no pipeline config mentions
Detection logic
Alert when a server subnet host opens AMQP (5671/5672) to an endpoint outside the internal ranges and the approved vendor list.

The session is fully encrypted, so the SNI field carries the case. FIN-SRV-12 trusted a hostname that looks like a message relay. That hostname appears in no pipeline configuration.

THR-04 — Topic hijack / ACL bypass Medium

Log sources
Broker audit logs (broker_audit.log), zeek:mqtt
Key fields
client_id, remote_addr, action, topic, qos, retain, result — result shows whether the broker's ACL allowed or denied the publish
Normal
Each device publishes only to its own stat and data topics; command topics accept writes from the management service only
Suspicious
A client ID publishing to another device's cmd/ topic, wildcard writes, or a burst of denied_by_acl results
Detection logic
Alert on any publish to a cmd/ topic from a client that is not the approved management service, and on any ACL denial from an internal address.

The badge panel tried to publish to the camera's command topic and the ACL stopped it. A denial is not a breach, but it proves someone probes the broker's permissions — investigate before the next attempt is not denied.

THR-05 — Exfiltration via publish topics Medium

Log sources
zeek:mqtt publish records, zeek:conn byte counters
Key fields
action, topic, payload_len, qos, client_id — payload_len shows chunk sizes; repeated similar values indicate automated splitting
Normal
Status topics carry roughly 100-byte messages once a minute; data topics are quiet
Suspicious
Dozens of publishes per hour to a data topic with payloads of tens of kilobytes each
Detection logic
Alert when one client publishes more than 200 non-status messages per hour, or when one data topic moves more than 5 MB per hour.

A 60-kilobyte publish is far above camera telemetry. Seeing this shape repeat 40 times with rising sequence numbers in the payload means a file is walking out in pieces.

THR-06 — Plaintext broker credentials Medium

Log sources
zeek:mqtt (port 1883 sessions), packet captures for the CONNECT payload
Key fields
id.resp_p (1883 means no TLS), client_id, connect_status — on 1883 the CONNECT packet also carries the user name and password in cleartext
Normal
Modern brokers on the sensitive VLANs accept only TLS sessions on 8883 with client certificates
Suspicious
Any successful CONNECT on 1883, because the credentials inside it are readable by everyone on the path
Detection logic
Alert on every plaintext MQTT CONNECT from a sensitive VLAN, and treat the credentials as compromised once it is confirmed.

Port 1883 is the giveaway: the badge panel authenticated to the corporate broker in the clear. zeek does not log the password, but the packet capture of the same session shows it — which is the point of the alert.

5.5 Sigma Rules and Splunk SPL

One Sigma rule and one Splunk SPL query per threat. Sigma is an open rule format for detections; YAML is the text format the rules use. SPL is the Splunk search language. Each rule is complete YAML with all standard fields. Each query states its data assumptions under the block — adjust index and sourcetype names to your environment. The Sigma rules use zeek field names. The SPL queries use the CIM field names that the Zeek Technical Add-On provides. CIM (Common Information Model) is Splunk's standard set of field names.

Rule 1 of 6 — MQTT egress from the IoT VLAN High (maps to THR-01)

Mapping note: the selection matches destination port and source VLAN and excludes the approved internal broker, mirroring the THR-01 detection sentence. The SPL keeps the same three conditions but reads the firewall view; the zeek:conn equivalent swaps only the index and sourcetype.

Assumes index=firewall with sourcetype=pan:traffic (Palo Alto traffic logs; CIM fields src_ip, dest_ip, dest_port, bytes) — adjust index and sourcetype to your environment. A zeek:conn query with the same filters gives the network view.

  • False positives: a newly approved broker missing from the filter; a vulnerability scanner probing the VLAN from the inside.
  • Tuning: keep the allowlist in a lookup table — | lookup broker_allowlist dest_ip OUTPUT approved | where isnull(approved) — and review it monthly with the network team.

Rule 2 of 6 — First-seen external broker Medium (maps to THR-02)

Mapping note: the newvalue modifier fires only when the broker address appears for the first time in the backend's history window. If your backend does not keep history, use the SPL below, which computes first-seen directly.

Assumes index=network with sourcetype=zeek:conn and at least 30 days of retention — adjust index, sourcetype, and the history window to your environment.

  • False positives: legitimate new SaaS message queues during a project launch; broker migrations.
  • Tuning: add a lookup of approved external brokers and filter it the same way as rule 1; shorten the window to 24 hours only if retention allows.

Rule 3 of 6 — Outbound AMQP from servers Medium (maps to THR-03)

Mapping note: the rule keeps the server-subnet source constraint from the threat definition and drops internal destinations; the SPL adds a vendor lookup so managed queues can be allowlisted without editing the rule.

Assumes index=network with sourcetype=zeek:conn, CIM field names, and an optional amqp_vendor_ranges lookup — adjust names and the lookup to your environment.

  • False positives: licensed managed message buses not yet in the vendor lookup.
  • Tuning: maintain the vendor lookup from your cloud team's service inventory; alert on new entries rather than editing the rule each time.

Rule 4 of 6 — High publish volume per device Medium (maps to THR-05)

Mapping note: the aggregation counts non-status publishes per client over the rule's window and fires above 200. The SPL groups by client and topic in one-hour bins so you can see which topics carry the volume.

Assumes index=network with sourcetype=zeek:mqtt providing action, topic, and payload_len fields — adjust index and sourcetype to your environment.

  • False positives: genuinely chatty firmware sending telemetry to data topics on purpose.
  • Tuning: baseline per device type for a week, then set the threshold per class. Cameras rarely exceed 60 publishes per hour. Also sum payload bytes and alert above 5 MB per topic per hour.

Rule 5 of 6 — Plaintext MQTT on sensitive VLANs Medium (maps to THR-06)

Mapping note: the rule is a single selection — protocol, port, and VLAN — because any plaintext CONNECT on a sensitive VLAN is worth a ticket. The SPL lists the client IDs per source so the migration backlog builds itself.

Assumes index=network with sourcetype=zeek:mqtt (protoname, client_id fields) — adjust index and sourcetype to your environment.

  • False positives: legacy devices that still use 1883 against the approved internal broker.
  • Tuning: if full migration takes months, split the alert into two levels. Deny new client IDs at once and send a weekly report for known ones. Retire each legacy device as it moves to 8883.

Rule 6 of 6 — Broker protocols from workstations Medium (maps to THR-01/THR-02 spillover)

Mapping note: this rule widens the port list to STOMP (61613) and watches the workstation subnet 10.20.4.0/24. Its logic is deliberately simple — any broker-port session from a desk is rare enough to review.

Assumes index=network with sourcetype=zeek:conn and CIM field names — adjust index, sourcetype, and the workstation subnet to your environment.

  • False positives: developer machines testing against lab brokers; IoT vendor tools on engineer laptops.
  • Tuning: allowlist the lab broker range explicitly; if a team has a legitimate use, move it to a documented segment instead of silencing the rule globally.

Real-World Case Study

The Muhstik botnet is the clearest public case of MQTT used as a command and control channel. The details below follow the published research by Trend Micro and Unit 42.

NOTE · What public reporting can and cannot tell us

Public reporting does not give exact victim counts, and the botnet's broker addresses rotated over time. The timeline below therefore follows the published behavior of the worm rather than the dates of a single victim. Nothing here is invented beyond the research.

Context

Muhstik was a Linux and IoT worm (malware that copies itself to other machines) active from 2018 through about 2020. It exploited known bugs in web applications and devices — including WebLogic servers, DD-WRT routers, and Joomla-era components. It then installed modules with simple download tools (wget and TFTP). For command dispatch it connected to attacker-operated MQTT brokers and subscribed to command topics. Tasks included crypto-mining and DDoS participation (flooding a target with traffic from many machines). The worm then scanned for new victims and repeated the loop, which kept the botnet growing for years.

Timeline

PeriodEvent
2018 Q2Trend Micro reports Muhstik attacking Linux servers and IoT devices; modules arrive via wget and TFTP; MQTT brokers carry command dispatch.
2018–2019Self-spread loops keep adding victims. Operators publish scan, mine, and DDoS commands to topic subscribers; results are published back to the brokers.
2020New variants keep exploiting fresh application bugs; Unit 42 documents continued activity; broker addresses rotate as defenders blocklist the old ones.
OngoingExposed brokers remain indexed by Shodan at large scale, showing how much publish/subscribe surface sits open on the internet.

Attack chain

  1. Exploit lands. A known web-application or device bug gives the worm code execution on a Linux server or IoT device.
  2. Modules install. A droplet pulls additional modules over wget and TFTP, including the MQTT client module and the task modules.
  3. Broker subscription. The implant subscribes to command topics on hard-coded attacker MQTT brokers.
  4. Commands publish. The operator publishes commands — scan, mine, DDoS — to the topics the bots follow.
  5. Results publish back. Bots report status and task output through publish messages on the same brokers.
  6. Spread repeats. Scan modules search for new victims; successful infections join the same loop.
GOOD PRACTICE · Detection point

The chain has three detectable moments. One: outbound TCP/1883 from servers or cameras to non-corporate IPs. Two: MQTT client records in zeek mqtt.log with device-shaped client IDs. Three: the process noise of mining right after a command message. Rules 1 and 4 in section 5.5 catch the first two directly.

Containment

Block the known broker IPs and domains at the egress firewall. Isolate the device or server segments that called them. Kill the implant and miner processes on Linux hosts.

Eradication

Rebuild devices from clean firmware rather than cleaning in place. Patch the exploited applications that let the worm in. Rotate all device and application credentials the implant could have read.

Recovery

Bring services back in order of business value. Then keep them safe: move IoT segments to deny-by-default egress, monitor broker ports continuously, and schedule recurring audits of the device estate.

Impact and consequences

Victims paid in three currencies: electricity and compute for crypto-mining, bandwidth and reputation for DDoS participation, and downtime during rebuilds. The deeper cost was structural — flat IoT networks let one infected camera reach management interfaces that should never have been exposed.

Team response and communication

Effective responses joined three teams. IoT device owners knew what each device was allowed to do. The network team owned egress rules. The SOC ran the detection side. Vendor firmware tickets tracked the rebuilds. Shared indicator lists between these teams cut the re-infection rate the most.

Lessons learned

Segment and control egress

IoT needs its own VLANs with deny-by-default internet egress. Most devices need zero outbound access.

Default credentials are the top cause

Worms that guess factory passwords still work because someone shipped the device without a password step in the rollout.

Pub/sub ports belong on allowlists

Ports 1883, 8883, 5671, 5672, and 61613 should connect to named brokers only. Anything else is a finding.

zeek mqtt logging is cheap detection

One passive sensor plus two alert rules covered this entire case — a high return for a small logging change.

Mitigation and Defense

Publish/subscribe C2 fails closed when brokers are allowlisted and devices cannot reach the internet. The table lists the controls per area, and the top five actions show where to start.

NOTE · Official MITRE mitigations for this technique

MITRE lists two official mitigations for T1071.005. M1037 Filter Network Traffic means: decide which brokers are allowed, and consider filtering publish/subscribe protocol requests to untrusted or known-bad destinations. M1031 Network Intrusion Prevention means: let network security tools inspect broker protocols and block the harmful patterns they see. The controls below put both into practice.

Home and small office

  • Change every router and camera password from the factory value on day one.
  • Put smart devices on the guest network, away from laptops and phones.
  • Disable UPnP so devices cannot open internet ports by themselves.
  • Update firmware when the vendor asks — old device bugs feed worms like Muhstik.
  • If you do not use remote access to devices, block ports 1883, 8883, 5671, 5672, and 61613 at the router.

Habits that keep the detections healthy

Daily

  • Check broker-port alerts and first-seen broker hits.
  • Confirm zeek conn and mqtt logs actually flowed overnight.
  • Verify new external brokers against the allowlist before closing tickets.

Weekly

  • Review false positives and tune with allowlist filters, not silences.
  • Check publish-volume outliers per device class.
  • Scan asset lists for new device types that joined the IoT VLANs.

Monthly

  • Replay sample events through every rule and record the result.
  • Review the broker allowlist with owners and retire stale entries.
  • Audit device credentials and confirm firmware levels across the estate.

Response checklist

  • Isolate the affected device or the whole IoT VLAN from the rest of the network.
  • Block the broker IP, domain, and TLS SNI at the egress firewall.
  • Pull zeek conn and mqtt records for the host for the last 30 days.
  • List every client that contacted the same broker to finish scoping.
  • Rebuild the device from known-good firmware; do not clean in place.
  • Rotate device, broker, and any reusable application credentials.
  • Add the broker indicators to blocklists and to your intel tracker.
  • Write the incident note and tune the rules that fired.
