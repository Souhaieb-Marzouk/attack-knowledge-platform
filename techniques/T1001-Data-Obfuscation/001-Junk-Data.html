T1001.001 Junk Data

Attackers hide their control traffic by adding random junk data to it. This page shows how that padding defeats hash lists and content signatures, and why it cannot hide sizes, timing, and structure. It is written for beginners in security operations centers (SOCs) and detection engineering.

    Overview

    Junk Data is one of the oldest stealth tricks in command-and-control traffic. This section explains the idea in plain words and shows where it sits in an attack.

    What is Junk Data?

    When malware talks to its operator, it must send messages over the internet. With sub-technique T1001.001, the malware appends random bytes — called padding or junk data — to every message before sending it. A 128-byte check-in can become 700 bytes today and 200 bytes tomorrow, with random content each time.

    Two words explain why this works. A hash is a digital fingerprint of a file or message: change one byte and the hash changes completely. A signature is a fixed byte pattern that defenders search for. Random padding changes the hash of every message and breaks every fixed pattern, so both defenses stop matching.

    Junk Data is sub-technique .001 of T1001 (Data Obfuscation), the parent technique for traffic-shape tricks. ATT&CK lists the platform set as ESXi, Linux, Windows, and macOS. ESXi is VMware software that runs many virtual machines on one physical server. Padding lives in protocol payloads, so it works the same way on a virtualization host as on a laptop.

    Why it matters to defenders

    Padding is cheap for attackers and annoying for defenders — but it has a hard limit. Random bytes change the content of a message, not its metadata: how big it is, when it is sent, which direction it flows, and which name it connects to. Those facts still tell a story.

    Even better, randomness itself is measurable. Entropy measures how random data is, and variance measures how widely values spread. Normal software has predictable message sizes; padded malware does not. That gap is the core detection idea of this whole page.

    Red Team / Hacker Perspective

    This section explains the technique from the attacker's side, so you understand the goal before you build detections.

    When / Where / Why / How attackers use junk data

    When: after the first foothold is stable and before bulk theft. Padding is a tuning step — the implant proves the channel first, then the operator turns junk data on.

    Where: on any egress path that tolerates variable message sizes: HTTPS APIs, DNS query labels, UDP peer traffic, and uploads to cloud note or storage services.

    Why: a few lines of code defeat hash blocklists, content signatures, and naive data-loss rules — cheaper than rotating infrastructure after every signature update.

    How: the implant draws random bytes at runtime and appends or prepends them to each message; files get padded before upload, and sizes rotate on a schedule.

    When attackers reach for junk data

    Malware authors add padding when they expect defenders to inspect content. Three goals come up again and again in public reporting:

    • Defeat hash blocklists: a file with junk appended has a new hash, so reputation lists built from older samples stop matching.
    • Defeat content signatures: intrusion prevention systems (IPS) match fixed byte patterns; padding breaks the pattern without breaking the protocol.
    • Disguise exfiltration: a padded screenshot looks like a media upload to a note app or social service.

    What the attacker gains — and gives up

    The gain is cheap stealth: a few lines of code defeat whole classes of content checks. The cost is a behavior change the attacker cannot fully hide. Padding needs randomness at runtime, and randomness shows up as size variance and entropy. If the malware pads beacons but keeps a fixed cadence and a fixed URI template, defenders can still build a stable fingerprint.

    How the technique is performed

    1. Phase 1 — Beacon. The implant checks in with a small, fixed payload so the channel works before any stealth tuning.
    2. Phase 2 — Pad. The operator enables the junk-data option. The implant draws a random length (for example 0 to 900 bytes) from the operating system's random generator and appends it to each beacon.
    3. Phase 3 — Upload. Files such as screenshots or stolen documents get junk appended before upload, so every copy leaves with a different hash.
    4. Phase 4 — Rotate. The malware rotates sizes, padding seeds, header order, or cover domains on a schedule, so nothing except the protocol structure stays constant.

    Prerequisites an attacker needs

    Implant with a padding option

    The malware must generate randomness at runtime and mix it into messages. Malware builders often expose padding as a simple on/off setting.

    Tolerant channel

    The receiving side must accept variable sizes. HTTP APIs, DNS names with spare label space, and cloud storage uploads all tolerate junk easily.

    Control of both ends

    The operator must keep the C2 server in sync with size limits and padding schedules, or messages may break parsing rules.

    Lab-only demonstration

    BASH — LAB ONLY
    # Lab only: run this on a virtual machine you own. It shows why
# padding defeats hashes. No network traffic is generated.
cp /bin/true payload.bin
head -c $((RANDOM % 900)) /dev/urandom >> payload.bin   # pad run 1
sha256sum payload.bin
cp /bin/true payload2.bin
head -c $((RANDOM % 900)) /dev/urandom >> payload2.bin  # pad run 2
sha256sum payload2.bin
# The two hashes differ even though the base file is identical.
# Defender exercise: log the file sizes of both runs and compare
# the spread against the un-padded original.

    /dev/urandom is the Linux source of random bytes, and sha256sum prints a file's hash. Both commands are read-only and safe in a lab.

    Common variations

    • Random padding appended to beacons (this sub-technique in its purest form).
    • Junk appended to files before upload, so hashes churn.
    • Randomized HTTP header order and random header values.
    • Junk bytes hidden in DNS query labels during tunneling.
    • Padding inside fake software-update downloads to inflate plausible traffic shapes.

    Mistakes attackers make

    • Uniform padding: drawing sizes from an even range leaves a flat, machine-looking distribution instead of natural clustering.
    • Forgetting TLS: encryption hides content, but sizes and timing still leak through; padding does not remove the metadata problem.
    • Reused padding seed: a fixed random seed produces the same size sequence on every host — a pattern defenders can match across victims.
    • Partial padding: padding beacons but not uploads (or the reverse) splits behavior into two profiles that are easier to spot.

    Blue Team / SOC Perspective

    Defenders cannot read encrypted content, but they never need to. This section shows where padded traffic leaves traces you can see.

    Proxy and web logs

    Proxies record method, host, URI, user agent, and byte counts per request. Padded beacons appear as same-URI POSTs whose body size jumps around.

    Flow and firewall records

    Netflow and firewall logs summarize each conversation: bytes in, bytes out, duration. They work even when the proxy cannot decrypt traffic.

    Packet capture and Zeek

    Full capture and Zeek (a network security monitor that turns packets into protocol-level logs) expose body lengths, header order, and TLS details without needing the keys.

    Endpoint telemetry

    Sysmon and EDR show which process owns the connection. A random-padding implant often runs from user-writable folders and holds long-lived HTTP loops.

    File reputation logs

    Antivirus verdicts matter as context: repeated "clean" verdicts on files whose hashes change every upload is itself a suspicious pattern.

    Cloud audit logs

    When uploads go to note or storage apps, the service's audit log shows object sizes and timestamps — a second, independent view of the exfil.

    Artifacts padding leaves behind

    ArtifactWhere it showsWhy it matters
    Same URI, jumping body sizeProxy, Zeek httpStable template plus random sizes is the core padded-beacon shape.
    Steady cadenceProxy, flow, firewallPadding randomizes content, not the sleep loop between check-ins.
    Hash churn on one file nameFile reputation, cloud auditThe same name uploaded with a different hash each time means content is rebuilt per send.
    High-entropy labelsDNS logsRandom junk in query names produces long, character-mixed labels.
    Odd header names or valuesProxy, packet captureRandomized headers rarely match the software they pretend to be.

    Warning

    Do not judge padded traffic by content alone. With TLS in the way, the proxy often sees only metadata — and that is enough. If your proxy configuration drops byte-count fields to save space, you are blinding exactly the detections this page relies on.

    Good practice

    Triage flow when a variance alert fires:

    1. Open the alerted host's proxy or flow history and confirm the size spread is real, not one outlier event.
    2. Check the cadence: are the requests evenly spaced like a sleep loop?
    3. Extract the URI template and search it across all hosts to find other victims.
    4. Check the endpoint: which process made the connections, from which folder, as which user?
    5. Compare upload hashes in cloud or file logs to confirm churn on a fixed file name.
    6. If two or more signals hold, open an incident and move to containment (section 6 shows a full example).

    5.2

    Threat Intelligence

    Threat intelligence tells you who pads traffic and how, so your detections match real behavior instead of a guess. Feed each source below into your rules, and record what you learned.

    MITRE ATT&CK

    Start here. The T1001.001 page lists the official platform set (ESXi, Linux, Windows, macOS), data sources, mitigation M1031, detection strategy DET0011, and procedure examples for 18 groups and malware families. Map your rules to the technique ID so coverage is reportable.

    Vendor reports

    Malware analysis reports often state padding behavior in one line ("appends random data before upload"). Those lines are gold: they tell you which fields to watch.

    OSINT

    Open-source research, sandbox traces, and blog write-ups show real beacon shapes and URI templates you can turn into hunt queries.

    Commercial feeds

    Feeds supply C2 domains and IPs quickly. For this technique, treat them as context: padding survives blocklists, so structure matters more than the address.

    ISACs

    Sector sharing groups (ISACs) pass along peer sightings — for example "padded uploads to note apps seen in our sector" — that tune your thresholds.

    Internal telemetry

    Your own baseline is the strongest source. Per-host size profiles and cadence tables make variance thresholds defensible.

    Collection

    Store actor names, malware families, padding ranges, and protocol choices in one table. Note the report and date for every claim so you can re-check it later.

    Analysis

    Ask what the intelligence changes: a new padding range, a new cover service, a new URI template. Translate each fact into a field or threshold you can measure.

    Application

    Update Sigma and SPL rules, add the template to hunt lists, and brief analysts on the tell: structure survives padding, hashes do not.

    These six threat models cover the realistic ways an organization meets T1001.001. The table ranks them; the cards give the detail that sections 5.4 and 5.5 build on.

    TH-01 — Size-randomized C2 beacons

    Description: an implant adds 0 to 900 random bytes to each check-in, keeping one URI template and a fixed cadence.

    Preconditions: malware running on a host; an HTTP-capable C2 API; an egress path that does not block the destination.

    Impact: persistent stealth channel for commands and small data; survives hash and content signature refreshes.

    Severity justification: common in reporting, cheap for attackers, and it defeats two control classes at once — high.

    TH-02 — Junk-appended image and file exfiltration

    Description: stolen files, often screenshots, get junk appended before upload, so hash-based data loss prevention (DLP) never matches.

    Preconditions: access to collect files; an upload channel such as PUT to a web service or a paste site.

    Impact: silent data loss; each stolen copy is unique, so takedown and hash sharing find nothing.

    Severity justification: direct data impact, with padded content documented in official examples (APT28 junk-length strings, Mori's 200 MB junk) — high.

    TH-03 — Padded uploads to cloud note and storage apps

    Description: the implant rides trusted cloud services, padding uploads so they look like ordinary document sync.

    Preconditions: user account or anonymous tier on a note or storage service; network access to it.

    Impact: exfiltration over a destination most proxies allow, hiding inside legitimate app traffic.

    Severity justification: likely but constrained by account and quota limits — medium.

    TH-04 — Randomized HTTP header padding

    Description: junk goes into header names, values, or order — for example a 32-character random user agent — instead of the body.

    Preconditions: implant controls raw HTTP output; proxy or IDS logs capture headers.

    Impact: fingerprint rules on user agents and header sets stop matching.

    Severity justification: real but often paired with other tells; medium.

    TH-05 — Junk bytes in DNS query names

    Description: commands or data hide in long random-looking subdomain labels; junk bytes widen the label space.

    Preconditions: attacker-controlled authoritative DNS; clients that resolve arbitrary names.

    Impact: a slow but robust channel that passes many firewalls unnoticed.

    Severity justification: noisy to run at scale and well-met by DNS logging — medium.

    TH-06 — Padding in fake software-update traffic

    Description: a fake updater downloads "updates" that carry junk bytes or deliver payloads over alternate ports.

    Preconditions: a plausible updater identity; a domain or port path that looks update-like.

    Impact: lowers immediate suspicion; mostly a delivery or cover channel rather than sustained C2.

    Severity justification: less common and easy to disrupt with signed-update policies — low.

    5.5

    Sigma Rules & Splunk SPL

    Each threat from 5.3 gets one detection card: a Sigma rule for the stable structure, and a matching Splunk SPL query for the statistics. Sigma cannot compute variance or entropy, so the rules match structure — URI templates, content types, header shapes — and the SPL queries carry the size math. Keep both in your detection library.

    Note

    Field-name assumptions: Sigma rules use common W3C proxy field names (cs-method, c-uri, cs-bytes, c-ip); SPL queries use Splunk Stream names (http_method, uri_path, bytes_in, client_ip). Adjust both to your own mapping, and keep the logic identical when you do.

    TH-01 — Size-randomized C2 beacons High

    Mapping note: the Sigma rule catches the shape (versioned API path plus binary body); the SPL query adds the variance check (stdev of request body size per client and URI over 60 minutes). Map cs-method to http_method, c-uri to uri_path, and cs-bytes to bytes_in.

    SIGMA

    TH-02 — Junk-appended image and file exfiltration High

    Mapping note: the Sigma rule fires on the name/type mismatch that padding causes; the SPL query finds the hash-churn behavior — the same object name uploaded with many distinct sizes. Both views should be joined in the case notes.

    TH-03 — Padded uploads to cloud note and storage apps Medium

    Mapping note: the Sigma rule names the process behind the connection from Sysmon network events; the SPL query aggregates those events per host and process. Byte-level proof then comes from the TH-02 proxy query, since Sysmon does not carry sizes.

    Real-World Case Study

    A composite incident that shows every stage of the technique: quiet beaconing, padded image uploads, a missed hash defense, and the hunt that broke it open.

    Note

    This case is a composite written for teaching. It is not a single real incident. The behaviors follow official ATT&CK T1001.001 procedure examples. GoldMax (S0588) surrounded its malicious traffic with decoy traffic. SUNBURST (S0559) added junk bytes to its C2 over HTTP. APT28 (G0007) gave each implant a "junk length" value, so decoding required the junk-removal algorithm. Organization names, dates, host counts, and internal details are illustrative.

    Context

    A policy research organization (a think tank) with around 400 staff is a regular target for state-aligned groups: researchers publish material that interests foreign governments, and staff email addresses are public. The organization runs a SOC of eight analysts with a SIEM, a web proxy, and endpoint antivirus. Cloud note apps are allowed for daily work.

    The behaviors modeled here are inspired by the official examples named in the note above — GoldMax decoy traffic, SUNBURST junk bytes, and APT28 junk-length encoding — not by one documented event.

    What made this hard to see

    The implant hid in plain sight. It sent HTTPS beacons with junk bytes added to each request, in the style of SUNBURST. Around that real channel, the operator's tooling generated decoy sessions from other compromised hosts, in the style of GoldMax, so analysts had to find the true pattern first. Screenshots of internal documents left with random junk appended, so every upload carried a new hash.

    Incident timeline

    1. Day 0 — Phishing. A researcher opens a malicious document; the implant installs from the user's temp folder and starts beacons with a fixed 128-byte POST body.
    2. Day 2 — Steady channel. The implant settles into a 60-second beacon loop. Nothing looks wrong: the hashes are new but the API path looks generic, and no rule watches sizes yet.
    3. Day 9 — Padding enabled. The operator switches on junk data. Beacon sizes now swing between roughly 100 and 1,000 bytes; uploads of screenshots carry appended random bytes.
    4. Day 15 — Padded uploads begin. Screenshots of internal documents go to the note app every few hours. Antivirus inspects each upload and reports clean — the hash is different every time.
    5. Day 34 — Anomaly hunt. During a routine egress review, an analyst plots POST body sizes per host and sees a standard deviation of 310 bytes against a normal baseline of 12. The size-variance rule from section 5 is written that day and fires immediately.
    6. Day 35 — Scoping. A hunt for the URI template /api/v1/collect finds four hosts using it; one was not yet on the analysts' radar.
    7. Day 35 — Containment. The C2 addresses are blocked at the firewall, all four hosts are isolated, and accounts on them are reset.
    8. Day 36–40 — Eradication and recovery. The implant is removed, affected hosts are rebuilt, and the variance rule runs in alert mode with zero false positives that week.

    Attack chain (numbered)

    1. Phishing email with a malicious document gains the first foothold.
    2. Implant installs and establishes a fixed-size beacon channel.
    3. Attacker enables junk-data padding; beacons and uploads change shape on every send.
    4. Screenshots of sensitive material upload to a note app with junk appended.
    5. Size-variance analytics expose the channel; template hunting finds all victims.
    Good practice

    The detection point that mattered was never content. The upload hashes changed constantly, and the traffic was encrypted. What exposed the implant was variance plus cadence plus template — three metadata facts the padding could not change.

    Containment

    Firewall blocks on the C2 addresses and domains; host isolation on all four systems; password resets and session revocation for affected users; the note-app token used by the implant was revoked.

    Eradication

    The implant was removed from two hosts and the other two were rebuilt. Analysts confirmed the padding behavior in sandbox runs, then searched 30 days of proxy history for the same size pattern to find nothing else.

    Recovery

    Hosts returned to the network after clean checks. The variance rule stayed in production, and the URI template joined the standing hunt list for the next quarter.

    Impact

    Hosts affected
    4 of about 400 endpoints
    Dwell time
    Roughly 34 days from first beacon to detection
    Data at risk
    Screenshots of internal policy documents; no confirmed mass export
    Detection cost
    One analytics rule plus about 12 analyst hours during scoping
    What worked
    Per-host byte-size baselines and cross-host template hunting

    Team communication

    • The SOC sent leadership a one-page summary: what was seen, what was blocked, what users should expect.
    • IR shared indicators (URI template, C2 addresses, size pattern) with the sector ISAC.
    • IT notified the owners of the four hosts directly before isolation, to avoid work loss.

    Lessons learned

    • Hash-based checks could not see the technique; metadata analytics could, and they are cheap to run.
    • Byte-count fields must be kept in proxy logs — a storage-saving change almost removed them months earlier.
    • Template hunting across all hosts turned one detection into four findings.
    • Cloud note apps need endpoint-side context: the proxy could not name the process, Sysmon could.
    • Keeping the tuned rule in place turned a one-time catch into standing coverage.

    Mitigation & Defense

    You cannot stop an attacker from sending random bytes, but you can shrink the space where padded traffic works and catch it faster when it does.

    ATT&CK lists one direct mitigation for this technique: M1031 Network Intrusion Prevention. The official description is modest: network intrusion detection and prevention systems that use network signatures can mitigate some obfuscation activity at the network level. That is honest but incomplete — the full answer pairs prevention with the analytics from section 5, because padding is designed to beat content-only controls.

    Home and small office

    Keep updates signed and boring

    Use only built-in update mechanisms for the OS and apps. Fake-update channels depend on users running "updaters" from search results.

    Filter DNS

    Watch your egress basics

    Most home routers show per-device traffic totals. A device that pushes far more than it pulls deserves a look — that is flow analysis in miniature.

    Common Mistakes & Best Practices

    These are the mistakes teams actually make against padding. Each card gives the symptom you will notice, the root cause, the fix, and the habit that prevents a repeat.

    1. Trusting hashes alone

    Symptom: repeated "clean" verdicts while uploads continue.
    Root cause: hash lists cannot match content that changes per send.
    Fix: add size-variance and template analytics next to file checks.
    Prevention: treat "clean hash" as one signal, never the verdict.

    2. Ignoring metadata because of TLS

    Symptom: the team assumes encrypted traffic is invisible traffic.
    Root cause: confusion between content (encrypted) and metadata (not encrypted).
    Fix: build the dashboard on sizes, timing, and destinations.
    Prevention: metadata-first detection design reviews.

    3. Averaging instead of measuring spread

    Symptom: average beacon size looks normal, alerts stay silent.
    Root cause: a mean hides a wide distribution by design.
    Fix: switch to standard deviation, min/max, and distinct-size counts.
    Prevention: always pair averages with a spread measure.

    4. Hard-coding absolute size limits

    Symptom: a "500-byte beacon" rule fires all week on one app, then is deleted.
    Root cause: fixed thresholds age badly across apps and hosts.
    Fix: replace with per-host baselines and relative variance.
    Prevention: require a baseline step before any size rule ships.

    5. One global baseline for every host

    Symptom: backup servers flood the alert queue.
    Root cause: hosts have different jobs, so one baseline fits nobody.
    Fix: baseline by host role and app, then tune per group.
    Prevention: keep an asset-role table next to detection configs.

    6. Dismissing entropy alerts as noise

    Symptom: long DNS names are closed as "CDN stuff".
    Root cause: no allowlist review, so the first alerts train analysts to ignore them.
    Fix: allowlist known CDNs, then re-enable and investigate the rest.
    Prevention: budget tuning time when entropy rules ship.

    7. Rules never tested with lab traffic

    Symptom: the rule exists, but nobody knows if it fires.
    Root cause: detections ship without a replay step.
    Fix: replay padded payloads in a lab and record the alert proof.
    Prevention: add replay evidence to the definition of done.

    8. Tuning once, then never again

    Symptom: a 0.5% false-positive rate becomes 40 alerts a day, forever.
    Root cause: no owner or cadence for rule maintenance.
    Fix: assign an owner and review thresholds monthly.
    Prevention: false-positive rate tracked per rule on a dashboard.

    9. Believing content-type fields

    Symptom: "image/png" traffic is exempted from review.
    Root cause: attackers set the header they want; padding often breaks the claim anyway.
    Fix: cross-check declared type against URI, size, and magic bytes where visible.
    Prevention: never exempt a category on a self-reported field.

    10. Watching the proxy, missing the cloud API

    Symptom: proxy looks clean, uploads still leave.
    Root cause: cloud sync clients and APIs bypass the inspected path.
    Fix: collect cloud audit logs and Sysmon network events together.
    Prevention: map every approved egress path to at least one log source.

    11. Dropping byte fields to save storage

    Symptom: the new SIEM routing saves 20% space; variance detection dies quietly.
    Root cause: field trimming without a detection impact review.
    Fix: restore bytes_in-style fields for egress sources.
    Prevention: detection engineers review every log-routing change.

    12. Closing one host instead of hunting the campaign

    Symptom: the alerted host is reimaged; the implant returns on another one.
    Root cause: the shared URI template was never searched fleet-wide.
    Fix: run the template hunt across all hosts before closing the case.
    Prevention: make cross-host hunt a required case step.

    13. Forgetting the virtualization layer

    Symptom: endpoint and network dashboards look clean, while an ESXi host shows odd HTTPS beacons.
    Root cause: hypervisors sit outside the classic agent fleet, so padded C2 touching them is missed.
    Fix: stream hostd and vpxa logs to the SIEM and alert on non-standard payloads (analytic AN0033).
    Prevention: include ESXi hosts in every detection coverage review.

    Habits that keep you ready

    Daily

    Check the beacon-cadence and size-variance dashboards. Skim new high-variance talkers; most are legitimate, and knowing them makes the odd one obvious.

    Weekly

    Hunt the top URI templates across all hosts and review the false-positive rate of every variance rule. Feed changes back into thresholds.

    Monthly

    Replay padded lab traffic through the full detection path, refresh per-host baselines, and confirm byte-count fields still survive log routing.
