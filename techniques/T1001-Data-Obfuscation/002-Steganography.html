    Overview

    A calm, high-level view of the technique before we go deeper.

    What is steganography in ATT&CK terms?

    Steganography is the practice of hiding data inside other data. Attackers embed commands, files, or stolen documents inside media such as PNG or JPEG pictures, video, or audio. The carrier file still opens, renders, and passes checks like a normal image. A security analyst who opens the picture sees an ordinary photo.

    Under MITRE ATT&CK, T1001.002 covers this trick as a sub-technique of T1001, Data Obfuscation. It usually serves two goals: smuggling a payload past inspection on the way in, and moving stolen data out inside image uploads. ATT&CK lists the platforms as ESXi, Linux, Windows, and macOS. ESXi is VMware software that runs many virtual machines on one physical server; media-handling tools on such a host can hide data in files the same way. The classic embedding method is LSB (least significant bit) steganography, which changes the last bit of each color value in an image. The change is invisible to the eye, but it doubles the "noise" in the file, which is one detectable hint.

    Why this matters to defenders

    Most security tools judge a file by what it is: its hash, its signature, its file type. A stego file defeats all three checks. Antivirus says "clean PNG". A sandbox sees a valid picture and reports nothing. Mail gateways deliver it happily.

    But the attacker still needs a workflow: fetch the picture, extract the hidden data, run it, and later upload images back out. Each step touches logs — proxy, endpoint, firewall. This page shows how to turn those small, odd events into reliable detections. Content review says "it is just a picture"; workflow review says "a workstation that never uploads images just uploaded one".

    Where it fits in the attack chain: attackers use steganography mainly for Command and Control, and sometimes for Defense Evasion or Exfiltration.

    Animated Simulation

    Watch a payload smuggle itself in, and see which signals the defenders can catch.

    The story below follows one Windows workstation, 10.2.4.15. A user visits a small blog that looks harmless. The blog serves a banner picture that carries a hidden payload. An implant on the workstation extracts and runs the payload, then uploads a screenshot with stolen data hidden inside it. Content filters see only valid images. The defenders catch the case with a workflow rule: a first-ever image upload, from a workstation, to a nine-day-old image host. Press Play, or step through the eight steps.

    Attacker Victim / target Attacker infrastructure or abused service Defender / SOC visibility
    Step 1 of 8
    Defender view
    Evidence in logs
    1. chip:'Browse' Load the cover page. The user opens a blog page on gallery.example. The page itself is clean; nothing malicious is downloaded yet. Defender view: plain browsing, nothing to alert on yet — this is the baseline.
    2. chip:'Fetch PNG' Download the carrier image. The browser fetches banner.png, about 1.2 MB. The picture is served only to this organization, so its hash will look unique and unknown. Defender view: a full-size PNG from a small, rare image host — note the size and the host.
    3. chip:'Extract' Read the hidden data. The implant on the workstation opens the PNG as a file and reads the embedded bytes. The picture is never executed — it is only read, which is why the file itself stays clean. Defender view: Sysmon EID15 logs the stream hash of the image file.
    4. chip:'Run' Start the extracted stage. The extracted code runs in memory through rundll32.exe. No new file of its own is written, so file-based tools see little. Defender view: process lineage shows rundll32 with an image-file event right before it.
    5. chip:'Stego exfil' Upload data inside a screenshot. The implant takes a screenshot, hides collected data in it, and POSTs shot.png back to the image host. It looks like a normal image upload. Defender view: a 640 KB image POST — the first image upload this workstation has ever made.
    6. chip:'Hash miss' Content checks pass. Antivirus and DLP inspect the upload. It is a structurally valid PNG with an unknown hash, so the verdict is clean. Defender view: AV/DLP verdict clean — this is the blind spot of content-only review.
    7. chip:'Workflow alert' Analytics catch the pattern. A workflow rule fires: first-ever image POST from 10.2.4.15, to an image host registered nine days ago. Defender view: workflow beats content — rarity and lineage, not the picture itself, raise the alert.
    8. chip:'Respond' Contain and investigate. The SOC blocks the image host at the firewall, isolates the workstation, and keeps the PNG as evidence. Analysts confirm the hidden data with stego tools in the lab, on their own copy. Defender view: quick containment, then careful lab analysis — never on production systems.

    This animation shows an isolated lab setup. Steganography tools such as steghide are safe to study only on files you own, inside your own lab. Never run extraction or payload tests on production systems, and never test against systems you do not own.

    3

    Red Team / Hacker Perspective

    Understand the attacker's playbook so you can spot the seams it leaves open.

    When, where, and why attackers use steganography

    QuestionAnswer
    WhenTwo moments stand out. Early, to smuggle a second stage past a mail or web gateway. Late, once a foothold exists, to run a quiet command channel and to send stolen data out.
    WhereOn HTTPS flows to image hosts, compromised sites, and social media CDNs, usually ports 80 and 443. On the endpoint, carrier files land in Temp, Downloads, or browser cache folders before extraction.
    WhyIt buys invisibility: the payload is a valid picture, so hash, signature, and sandbox verdicts come back clean. Against plain encoded traffic, image carriers also blend into everyday media downloads.
    HowEmbed data with LSB bit changes, metadata fields, or appended bytes; serve the carrier from controlled or trusted infrastructure; extract it on the endpoint. The six-step timeline below shows the build.

    When attackers pick steganography

    Attackers reach for stego when content inspection blocks obvious payloads: a naked EXE or a script in an HTTP response gets stopped, but an image usually passes. Hiding a payload inside a picture turns a "blocked download" into a "clean image fetch".

    C2 inside media traffic

    Instead of a raw command channel, the implant polls for images and reads commands from them. The traffic looks like ordinary browsing: GET a picture, upload a picture. Permitted destinations such as image hosts or social media make the channel even quieter.

    Exfiltration as pictures

    Stolen files, keystrokes, or screenshots can be encoded into outgoing images. DLP rules that look for documents and text may let the upload pass, because the body is, technically, a photo.

    How an attacker builds a stego channel

    1. Step 1 — Pick a carrier. Choose a medium the target will accept: a PNG for lossless detail, a JPEG for a "normal photo" look, sometimes video or audio. Larger carriers hold more data.
    2. Step 2 — Embed the data. Hide the payload with an embedding method: LSB bit changes in a PNG, metadata fields, palette reordering, or appended data after the image's real end. Commercial and open-source tools exist; defenders study them in labs.
    3. Step 3 — Publish or serve the carrier. Upload the picture to an attacker-controlled host, a compromised site, or a public platform. The URL must look boring and stable.
    4. Step 4 — Target fetches the image. A phishing page, an injected iframe, or an already-running implant causes the victim to download the picture.
    5. Step 5 — Extract. The implant on the endpoint reads the embedded bytes. No execution of the image is needed — reading is enough.
    6. Step 6 — Run and iterate. The extracted stage executes in memory. Later, the same channel carries new commands in fresh images, and stolen data back out in uploaded ones.

    Prerequisite: control of a serving point

    The attacker needs a place that serves the images: an attacker-owned host, a compromised legitimate site, or a public platform account. Domains are sometimes freshly registered, which helps defenders.

    Prerequisite: code on the endpoint

    Something must read the picture and extract the data. An implant, a malicious script, or a loader must already be on the host. Steganography hides the payload delivery; it does not create the initial access by itself.

    Prerequisite: agreement on a format

    Sender and receiver must use the same embedding rule and the same order of data. This fixed rule is a weakness: once analysts understand the format, they can read the whole channel.

    BASH — LAB DEMO ONLY
    # LAB ONLY — run on your OWN files, in an isolated lab, never on systems you do not own.
# Educational demo: watch a payload round-trip through a JPEG carrier.

mkdir /tmp/stego-lab && cd /tmp/stego-lab
cp ~/Pictures/photo.jpg carrier.jpg          # your own, harmless photo
echo "benign-demo-note" > secret.txt         # stand-in for a payload

# Embed (this is the attacker-side action, demonstrated on a local file):
steghide embed -cf carrier.jpg -ef secret.txt -p labpass

# Inspect: the file is still a valid JPEG, but its size grew:
file carrier.jpg
sha256sum photo.jpg carrier.jpg              # hashes differ, viewers show the same photo

# Extract (the defender-side reconstruction, in the lab):
steghide extract -sf carrier.jpg -p labpass -xf extracted.txt
diff secret.txt extracted.txt && echo "payload round-trips intact"

# Clean up the demo artifacts:
rm -rf /tmp/stego-lab

    Variations defenders should know

    Metadata channels: data hidden in EXIF or comment fields; easy to read, easy to strip. Palette reordering: PNG palettes rearranged to encode bits; breaks some optimizers. Appended data: bytes added after the image's end marker; viewers ignore them. Video and audio: the same ideas spread over many frames, which holds far more data.

    Common attacker mistakes

    Size jump: embedding makes the file noticeably larger than a re-encode of the same picture. Re-compression kills the payload: if any gateway resizes or re-encodes the image, hidden bits are destroyed. Repeated names: the same banner.png served on many days is easy to hunt. Fingerprintable host: a small, young, rarely seen image host stands out against a fleet's baseline.

    Note

    Everything above is described to help defenders. Running stego tooling against files or systems you do not own is unlawful. Red teams should mirror these actions only inside authorized lab ranges with written approval.

    Blue Team / SOC Perspective

    What the SOC can actually see when a stego channel runs, and where to look first.

    A SOC (Security Operations Center) is the team that watches alerts and logs. For steganography, no single log line says "stego here". Instead, defenders combine three weak views — network, endpoint files, and endpoint processes — into one strong view. The cards below show each view and what it contributes.

    Proxy and HTTP logs

    Web proxies record every image fetch and upload: host, path, MIME type, bytes, user agent. They reveal workflow: first-ever image hosts, odd sizes, repeated downloads of one file, and uploads from hosts that never upload.

    Zeek and packet capture

    Zeek (an open-source network sensor) turns traffic into structured logs. HTTP logs show image MIME types and body lengths even when TLS hides content. Full packet capture lets analysts reassemble a suspect image for lab analysis.

    Endpoint file events

    Sysmon (a Windows logging add-on) event 15, FileCreateStreamHash, logs hashes when a downloaded file gets a stream such as Zone.Identifier. It is the best "this image arrived here" record, with a hash you can match to the network capture.

    Process lineage

    Sysmon event 1 chains parent and child processes. A rundll32.exe appearing right after an image event, with no installer in between, is exactly the "extract then run" seam the technique cannot avoid.

    DLP and antivirus verdicts

    DLP (Data Loss Prevention) tools check outgoing content; antivirus checks files. Both will usually say "clean" for stego media. Log the verdicts anyway: a clean verdict paired with an odd workflow is itself an investigative clue.

    DNS and network metadata

    New image-host domains, short domain ages, and rare destination ASN (network owner) values enrich every other signal. They rarely stand alone, but they upgrade "large PNG" into "large PNG from a nine-day-old host".

    Warning

    Do not chase stego theory on every large image. Designers and marketers move multi-megabyte PNGs all day. Anchor every alert to a workflow fact: rarity, first-seen, or lineage. Otherwise you will drown in noise and tune the signal away.

    Good practice

    Triage flow when an image-workflow alert fires:

    1. Confirm the basics: which host, which user, which image URL and hash.
    2. Check rarity: has this host or domain been seen before, from this subnet or user?
    3. Check lineage: what file and process events happened within two minutes of the image event?
    4. Check outbound: did the same host upload images afterwards, and how large?
    5. If lineage is odd, isolate the host, preserve the image as evidence, and confirm embedding in the lab.

    5.2

    Threat Intelligence

    Where intelligence on this technique comes from

    MITRE ATT&CK

    The technique page for T1001.002 lists platforms, data sources, and mitigation M1031, Network Intrusion Prevention. It also lists detection strategy DET0235, Detecting Steganographic Command and Control via File + Network Correlation, with four analytics, AN0651 to AN0654. ATT&CK gives you the stable ID and vocabulary, not the live infrastructure.

    Vendor reports

    Malware family reports describe stego carriers in detail: which format, which URL patterns, which extractor. The table below lists the official ATT&CK procedure examples; vendor write-ups describe most of them in depth.

    OSINT

    Open-source intelligence: research blogs, conference talks, and public repositories of Sigma rules. Good for learning embed formats and building test carriers for the lab.

    Commercial feeds

    Feeds supply IOCs (indicators of compromise): image-host domains, file hashes of known stego carriers, and extractor signatures. Use them for matching, not as the core logic.

    ISACs

    Information Sharing and Analysis Centers circulate sector-specific reports, for example financial ISAC alerts about image-hidden C2 in a campaign hitting member banks.

    Internal telemetry

    Your own proxy baselines, first-seen domain tables, and past incidents. This is the most valuable source for workflow rules, because rarity only means something against your own normal.

    Collect

    Pull technique context from ATT&CK, IOCs from feeds, and formats from vendor write-ups. Store them in one place with tags for T1001.002 so detection engineers can find them.

    Analyze

    Ask which parts become detections: a carrier hash (weak, short-lived), an image-host domain (medium), a workflow pattern such as "first image upload" (strong and durable). Rank ideas by how long they stay true.

    Apply

    Turn the durable patterns into Sigma and SPL like the ones in 5.5. Track intel-driven detections back to their source, and retire them when the intel expires or the campaign ends.

    5.3

    Threats Ranking & Categorization

    Below are the six stego threat scenarios we defend against on this page, ranked by how likely and how harmful they are in a typical enterprise. Each threat gets its own log patterns in 5.4 and its own Sigma and SPL in 5.5. Severity combines likelihood (how often this is seen in the wild) with impact (what it costs you if it succeeds).

    IDThreatPlatformSeverity
    TH-01Payload hidden in the LSB of a PNG fetched from the webWindowsHigh
    TH-02C2 instructions hidden in JPEG responsesWindowsHigh
    TH-03Stego exfiltration via image upload to cloud storageWindows / CloudMedium
    TH-04Stego carriers served from compromised legitimate sitesNetworkMedium
    TH-05Stego via social media imagesCloudMedium
    TH-06Video and audio carriersCross-platformLow

    TH-01 — Payload hidden in a fetched PNG High

    Description: an implant or malicious page causes a PNG download whose least significant bits carry an executable stage. The implant extracts it and runs it in memory, so the picture itself never looks malicious.

    Preconditions: an implant or script host on the endpoint; a serving host the attacker controls; a way to make the victim fetch the image.

    Impact: full code execution turns into further stages, persistence, and data access; the delivery step evades file-based review.

    Severity justification: leads directly to compromise, and ATT&CK lists a real example: ZeroT retrieved stage 2 payloads as Bitmap images that use LSB steganography. Ranked High.

    TH-02 — C2 instructions in JPEG responses High

    Description: the implant polls a server that answers with JPEG files; commands are encoded in the image data. The channel survives as long as image fetching is allowed.

    Preconditions: a running implant; an attacker server; egress that permits outbound HTTPS to arbitrary hosts.

    Impact: durable command channel; attacker keeps control even when other protocols are blocked.

    Severity justification: gives attackers sustained control; ATT&CK lists HAMMERTOSS, which is controlled via commands appended to image files. Ranked High.

    TH-03 — Stego exfil via cloud image upload Medium

    Description: collected files are encoded into images and uploaded to cloud storage or file-sharing endpoints. The traffic pattern resembles a user syncing photos. The official Duqu example shows the classic form: data appended to a blank JPG and uploaded to the controller.

    Preconditions: implant with data collection; network path to an upload service; often a valid account or anonymous upload API.

    Impact: silent data loss that bypasses DLP tuned for documents; regulatory exposure if personal data leaves.

    Severity justification: serious for data, but needs an implant already present; upload workflow is detectable. Ranked Medium.

    TH-04 — Carriers on compromised legitimate sites Medium

    Description: a real website is breached and serves the stego image inside its own pages, giving the carrier instant reputation. Watering-hole style delivery is possible.

    Preconditions: attacker compromises or spoofs a site your users visit; users browse it from managed endpoints.

    Impact: high trust means more victims; reputation-based filtering fails; harder to attribute.

    Severity justification: likely when it happens, but requires a successful site compromise first. Ranked Medium.

    TH-05 — Stego via social media images Medium

    Description: the implant uses image CDNs of large social platforms as the channel, fetching commanded images from accounts the attacker controls. Platform reputation is excellent, so blocks are rare.

    Preconditions: attacker runs platform accounts; implant fetches from platform CDN hostnames; egress to consumer sites allowed.

    Impact: very hard to block without harming users; blends with heavy legitimate media traffic.

    Severity justification: stealthy, but usually needs consumer-site access, which many companies restrict. Ranked Medium.

    TH-06 — Video and audio carriers Low

    Description: the same ideas applied to video frames or audio samples. Carriers hold far more data, but files are large, slow to transfer, and need more capable tooling on both ends.

    Preconditions: implant able to parse containers like MP4 or WAV; higher bandwidth tolerance on both sides.

    Impact: potentially large data movement; operationally noisy because of transfer sizes.

    Severity justification: rare in reporting, heavier to run, and easier to spot by size. Ranked Low, but keep it in scope for media-heavy sectors.

    Sigma Rules & Splunk SPL

    Sigma is an open format for describing detection rules in YAML; most SIEMs can convert it to their own query language. SPL (Search Processing Language) is the query language of Splunk. This section gives every threat from 5.3 a Sigma rule and a matching SPL query. The two use the same field dictionary. Proxy queries assume stream:http fields: method, site, uri_path, content_type, bytes_in, bytes_out, client, and useragent. Endpoint queries assume XmlWinEventLog:Microsoft-Windows-Sysmon/Operational. Network queries assume the Zeek and firewall fields listed in 5.4. Copy each rule, rename fields to your sources, and test in the lab first. One assumption line sits under every query.

    TH-01 — Payload hidden in a fetched PNG High

    Mapping: endpoint process and file lineage — Sigma categories process_creation and image_load. The image_load rule is the high-precision companion; remember its limit: in-memory extraction never reaches the module loader, so keep the process rule too.

    SIGMA
    title: Rundll32 Starting a File From Temp or Downloads (TH-01)
id: e4f7b2c1-9a3d-4e8f-b2a6-1c5d7f0e3b92
status: experimental
description: >
  Detects rundll32.exe starting a module from a user-writable folder such as Temp
  or Downloads. Attackers that hide a stage inside an image file often drop the
  extracted file next to the picture and start it with rundll32. This rule is a
  workflow cue, not proof of steganography: correlate the same host with a recent

    title: Windows Loads a Media File as a Code Module (TH-01, TH-02)

    Real-World Case Study

    A public campaign that used exactly this trick, retold as an enterprise incident.

    Case background: Duqu's blank-JPG exfiltration channel

    Duqu is an espionage platform that surfaced in 2011. It was named after the "~DQ" file prefix its components used, and researchers at the CrySyS lab and Kaspersky described it as a close cousin of the Stuxnet tooling. The official ATT&CK procedure example for T1001.002 describes the channel this page is about. When the Duqu command and control was operating over HTTP or HTTPS, Duqu uploaded data to its controller by appending it to a blank JPG file. The request looked like an ordinary image upload. The body began with a valid JPEG header, and the encrypted stolen data sat behind it, so content checks saw a real picture.

    Sources: public research from 2011 (CrySyS, Kaspersky, Symantec) and the official ATT&CK S0038 procedure example, verified October 2026. The incident timeline below is adapted and composite — we retell the documented channel as a generic enterprise incident, with invented dates, hosts, and names for teaching. No confidential or non-public details are included.

    Public reporting timeline

    1. September 2011 — Discovery. CrySyS publishes "Duqu: The Precursor to the Next Stuxnet" and describes a new espionage framework active in the wild.
    2. October 2011 — Analysis. Kaspersky and Symantec publish technical deep dives; Duqu's information-collecting modules and command-and-control behavior get names and signatures.
    3. 2011-2012 — The image channel is documented. Researchers describe the HTTP and HTTPS C2 that appends stolen data to a blank JPG file. ATT&CK later lists this behavior as an official T1001.002 procedure example.

    Adapted enterprise incident timeline (teaching version)

    1. Day 0, 09:12 — Phishing email. A research analyst opens a themed document lure; an exploit drops a small loader DLL.
    2. Day 0, 09:14 — Loader installs. The loader writes its payload with a random name, sets persistence, and loads an information collector.
    3. Day 1-20 — Collection and staging. The collector gathers documents and credentials, writes them to files with a ~DQ-style prefix, and encrypts them.
    4. Day 21, 02:03 — Blank JPG channel opens. Over HTTPS, the implant creates a blank JPG, appends the encrypted data behind the image header, and uploads it. Proxy logs show routine image POSTs.
    5. Day 21-55 — Quiet repetition. The same pattern repeats every few nights: small, valid-image uploads, always clean on content checks.
    6. Day 56, 08:47 — Detection. A scheduled hunt correlates three weak signals. Image POSTs came from a server-class asset that never uploads images. Upload sizes grew after a ~DQ-style file appeared on disk. A non-browser process owned the connection. The blank-JPG channel was confirmed in the lab.

    Attack chain (numbered)

    1. Phishing email with a document lure delivers a loader.
    2. Loader installs persistence and an information collector.
    3. Collector stages stolen data in encrypted, prefix-named files.
    4. Implant opens an HTTPS channel to the controller.
    5. Stolen data is appended to a blank JPG and uploaded as "image" traffic.
    6. The controller strips the image part and reads the appended data.
    Good practice

    The detection point that mattered: neither antivirus nor the sandbox flagged the uploads, because each body began with a valid JPEG header. The case broke open when the hunt joined three weak signals. The first was a first-ever image upload from an asset with no media role. The second was staged files that appeared just before each upload. The third was a non-browser process owning the session. That is workflow detection, exactly as practiced in sections 4 and 5.

    Containment

    Isolate the analyst workstation, block the carrier and C2 domains at the proxy and firewall, and reset credentials used on the host. Preserve memory before reboot.

    Eradication

    Remove the loader, the collector, and their persistence; delete the staged files; and re-image the host. Search the fleet for the C2 domain, the file prefix, and the upload pattern.

    Recovery

    Return the host with updated baselines, add the indicators to proxy and DNS blocks, and schedule a 30-day lookback for the same pattern in all sites.

    Initial access
    Phishing email with a malicious document (adapted from reporting).
    Carrier
    Blank JPG with encrypted data appended behind the image header.
    Dwell time
    About 56 days in the adapted timeline.
    Primary impact
    Collection of research documents; credential exposure.
    Systems affected
    One workstation plus the persistence artifacts (adapted scope).

    How the team communicated

    SOC to IR: one page with the timeline, the three correlated signals, and the evidence hashes. IR to management: what data could have left, what was blocked, and the containment state, updated twice daily. Everyone: one incident channel, no side threads, and a single spokesperson for user-facing questions.

    Lessons learned

    • Content verdicts ("valid image") are not safety verdicts; keep workflow rules in the alert queue.
    • The exfil channel used an upload direction nobody expected from that asset; direction baselines matter as much as size.
    • A file-naming habit gave defenders a durable pivot; unusual local file names are cheap to hunt.
    • Correlating file events with proxy uploads turned a hunt lead into a confirmed case within minutes.
    • The C2 endpoint was fixed, so one proxy block cut the whole channel.
    • Historic campaigns still teach current defense; the official ATT&CK example list is a ready-made source of patterns to detect.

    Mitigation & Defense

    Controls that raise the cost of image-hidden channels, from enterprise to home office.

    ATT&CK lists Network Intrusion Prevention as the mitigation class for this technique. In practice, prevention is layered: make the channel hard to reach, hard to use, and expensive to keep hidden. ATT&CK also lists detection strategy DET0235 for this technique. Its four analytics, AN0651 to AN0654, pair file events with network events, which is exactly the layering this section builds.     Home and small-office defenses

    Keep updates automatic

    Most stego delivery needs an implant already on the device. Automatic OS and browser updates close the holes that implants use to arrive.

    Use built-in protections

    SmartScreen, browser safe-browsing, and router-level DNS filtering block many young domains for free. Turn them on and leave them on.

    Separate your risks

    Use a different browser profile, or device, for banking and work than for browsing galleries and downloads. One compromise should not reach everything.

    Do not block all image traffic or strip every image blindly. Designers, marketers, and support teams depend on media, and over-blocking pushes users to unmanaged tools, which removes your visibility completely. Measure, then enforce where it hurts the attacker and not the business.

    Common Mistakes & Best Practices

    Thirteen mistakes teams really make with this technique, then the habits that prevent them. Each card follows the same shape: Symptom, Root cause, Fix, and Prevention.

    1. "Valid image, therefore safe"

    Symptom: image alerts are auto-closed because the file renders fine.
    Root cause: judging safety by file validity, not workflow.
    Fix: reopen alerts that pair a valid image with rare hosts or odd lineage.
    Prevention: write the triage SOP so validity alone can never close a case.

    2. Hash-only matching for carriers

    Symptom: the team waits for an AV signature of the carrier PNG.
    Root cause: carriers change daily; hashes expire in hours.
    Fix: shift weight to first-seen host, size, and lineage rules.
    Prevention: track indicator age; retire hash rules aggressively.

    3. Ignoring outbound image uploads

    Symptom: proxy rules watch downloads but never uploads.
    Root cause: exfil attention stays on documents and archives.
    Fix: add image-content POST monitoring per 5.5 TH-03.
    Prevention: review proxy rule coverage by direction, not just by site.

    4. No endpoint-network correlation

    Symptom: image events and process events live in separate queues.
    Root cause: no join on host and time window in the SIEM.
    Fix: build the 15-minute host-window join once, reuse everywhere.
    Prevention: make correlation queries part of the detection template.

    5. Tuning away "large image" alerts entirely

    Symptom: after noise complaints, all image-size rules are disabled.
    Root cause: thresholds set without baselines, then abandoned.
    Fix: re-enable with rarity gates and per-team exceptions.
    Prevention: tune by data-driven exception lists, never by deletion.

    6. Trusting file extension and MIME alone

    Symptom: rules match ".png" and stop there.
    Root cause: MIME and extension are trivially spoofed.
    Fix: verify magic bytes and parse structure where possible.
    Prevention: document that content-type fields are leads, not verdicts.

    7. No first-seen baseline for domains

    Symptom: analysts argue about whether a host is "normal".
    Root cause: nobody keeps a fleet-wide first-seen table.
    Fix: build the table from proxy and DNS logs; age domains daily.
    Prevention: fund the baseline job; it powers a dozen detections.

    8. Skipping lab confirmation

    Symptom: cases close on circumstantial evidence alone.
    Root cause: no standard, safe procedure to check embedding.
    Fix: adopt the 5.4 lab flow: copy the file out, analyze on isolated lab hardware.
    Prevention: keep a written, pre-approved lab runbook.

    9. Over-blocking all media

    Symptom: blanket image bans cause user revolt and shadow IT.
    Root cause: prevention without measurement.
    Fix: replace bans with targeted re-encoding and rarity rules.
    Prevention: pilot every egress control for two weeks first.

    10. Ignoring Sysmon event 15 and 7

    Symptom: Sysmon runs with defaults; streams and module loads are dark.
    Root cause: untested base config, no coverage review.
    Fix: deploy events 1, 3, 7, 15 and test each one end-to-end.
    Prevention: add logging coverage to the quarterly audit.

    11. Treating video/audio as out of scope

    Symptom: all detections assume images only.
    Root cause: the obvious carriers dominate training material.
    Fix: extend size-and-flow rules to media-classified apps (TH-06).
    Prevention: review technique scope, not tool scope, each quarter.

    12. Forgetting re-encoding destroys evidence

    Symptom: the gateway stripped the image before anyone saved a copy.
    Root cause: no evidence-preservation step before transformation.
    Fix: archive a copy of flagged media to evidence storage first.
    Prevention: put "preserve, then transform" in the gateway runbook.

    13. Assuming stego needs rare, exotic tools

    Symptom: the team dismisses image-hidden payloads as spy-agency-only tradecraft.
    Root cause: training shows only famous cases, so the pattern feels out of reach.
    Fix: teach that open tools and a few script lines can embed data; hunt the workflow, not the tool.
    Prevention: keep the monthly lab drill so analysts see how cheap embedding really is.

    Habit trio

    Daily

    Review first-seen image hosts and every image upload from a workstation. Five minutes; catches the loudest patterns early.

    Weekly

    Run the TH-02 repetition hunt and the TH-04 rarity hunt. Check Sysmon 7 media module loads; there should be zero.

    Monthly

    Rebuild one lab stego carrier on your own test file, push it through your controls, and confirm at least one rule fires. Update thresholds, the first-seen table, and the approved-upload lookup.

    Response checklist

    • Identify host, user, image URL, and file hash from the alert.
    • Check first-seen status of the host or domain, and fleet-wide rarity.
    • Pull Sysmon events 1, 3, 7, 15 for the host, 15 minutes around the event.
    • Look for a matching image upload from the same host within hours.
    • If lineage is odd: isolate the host and preserve the image as evidence.
    • Confirm embedding only in the lab, on your own copy, with written approval.
    • Block the carrier host and reset credentials exposed on the endpoint.
    • Run a 30-day lookback for the same pattern across all sites.
    • Compare the image size with a re-encoded copy of the same picture.
    • Check the case-study pattern: first-ever image upload from an asset with no media role.
    • Escalate on media files loaded as code modules; treat every hit as a strong lead.
