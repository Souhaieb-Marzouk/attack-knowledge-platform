T1608.004 Drive-by Target

Some attackers stop waiting for clicks. They prepare a website you already visit so that simply opening a page can attack your browser. Preparing that trap is called staging a drive-by target - and it turns trusted websites into weapons.

Tactic: Resource Development Platform: PRE Parent: T1608 Created: 17 March 2021 ATT&CK data: 1.3 (Oct 2025) Detection difficulty: Hard Guide: v2.0
Zero-click deliveryThe victim only browses normally. No download decision is ever made, so training that focuses on clicks does not help.
Borrowed trustThe attack lives on a legitimate, popular website. The padlock, the domain, and the content all belong to the real owner.
Selective fireHidden checks decide which visitors get attacked and which see nothing. The rest of the world is a witness that sees no crime.
Best signalsInjected scripts in your own web estate, redirect chains seen at the proxy, and strange child processes started by a browser.

Contents

    1

    Overview

    This section explains what a drive-by target is in plain words. It shows how the preparation differs from the attack itself. It also explains why defenders should care about a phase that mostly happens on somebody else's website.

    What the technique is

    Drive-by Target means an attacker prepares a website so that people who simply visit it get attacked. In most cases the attacker first breaks into a trusted site, then plants a hidden script or a hidden frame. A hidden frame is a small invisible window inside the page that quietly loads a second page from the attacker's server.

    Think of a shop window in a street you walk every day. One morning it hides a trap behind the glass. You did nothing unusual - you just walked past, exactly like every other morning.

    Parent technique and child technique

    This page covers a sub-technique, which is a more specific version of a bigger technique. The parent is T1608 Stage Capabilities: preparing resources before an attack. The child T1608.004 is one exact way to do it: prepare a web page that attacks its visitors.

    The wording matters. The preparation on the website is T1608.004 and belongs to the Resource Development tactic. The moment the visitor is actually exploited is a different technique: T1189 Drive-by Compromise, in the Initial Access tactic. ATT&CK splits the story this way, and this page keeps the same split.

    Why it matters

    Drive-by staging defeats the most trained human habit: not clicking strange things. There is no strange thing to click. The site is real, the visit came from a habit or a colleague, and the padlock is genuine.

    It also gives the attacker an automatic victim supply. Every visitor is a candidate, and a small filter - defenders call it a gate - picks only the chosen ones. A single compromised blog can therefore reach a whole industry without sending one email.

    Where it fits in the attack chain

    The chain looks like this. First, T1584 Compromise Infrastructure: the attacker gains control of a server, website, or account that already has trust. Second, T1608.004: the attacker turns that site into a drive-by target. Third, a user visits and T1189 Drive-by Compromise happens on their machine. Fourth, the code abuses a browser weakness, which ATT&CK calls T1203 Exploitation for Client Execution, and the payload starts.

    Everything before the visit is preparation. This page shows you how to see it, and how to break it.

    Good practice

    Defend two surfaces at once. The first is your estate: your own websites, so nobody can stage a drive-by target on them. The second is your users: their browsers, so a staged page somewhere else cannot land. Teams that only do one half keep getting surprised by the other half.

    Defender view

    Attacker Attacker infrastructure Victim side Defender / SOC

    The same story in text (screen-reader and no-JS friendly)

    1. Step 1 — Scan for soft targets The attacker scans many websites and looks for content-management systems that are months behind on updates. A popular local news site shows an old, unpatched version. Defender view: scanning noise is visible to the targets' web application firewalls (WAFs) as fingerprint probes, but almost nobody can tell yet which site will be chosen.
    2. Step 2 — Compromise the trusted site Using credentials stolen from a plugin developer, the attacker logs into the news site's admin panel. The site still looks perfectly normal. Defender view: the CMS audit log records an admin login from an unusual country - the first strong signal, if anyone is watching.
    3. Step 3 — Inject the hidden loader The attacker edits the site footer template and adds one obfuscated script tag. The script quietly loads a hidden second page that visitors never see. Defender view: file-integrity monitoring (FIM) on the web root flags the template change within minutes.
    4. Step 4 — Arm the gate On the hidden landing server the attacker configures gate checks: visitor country, browser and plugin versions, and one visit per victim. Only chosen users are attacked; everyone else sees nothing. Defender view: none of this is visible to ordinary visitors - only a crawler that knows where to look ever meets the gate.
    5. Step 5 — Silent redirect chain An employee opens the morning news as usual. The injected script silently chains the browser through redirects to the exploit landing page. No click, no download, no warning. Defender view: the proxy records the redirect chain: the referer is your trusted site, the next hops are a shortener and a domain registered last week.
    6. Step 6 — Exploit runs in the browser The landing code tests the browser, finds a weakness, and runs inside the browser process. The news page on screen still looks completely normal. Defender view: EDR sees the browser crash once, or open a local port it never uses - small signs that are easy to miss.
    7. Step 7 — Payload dropped and started The running code fetches a small payload and starts it. On this machine the EDR blocks the launch - but on two other visitor machines outside your company it starts quietly. Defender view: EDR logs the browser spawning a script interpreter - a browser has no honest reason to do that.
    8. Step 8 — SOC response The analyst isolates the workstation, patches the browser fleet, helps clean the news site with its hosting provider, and reports the kit infrastructure. The site owner posts a notice to its readers. Defender view: hunting finds two more visitors were attacked before the block. Their hosts are cleaned too, and the injected script path is added to every watchlist.

    Note

    The simulation is a simplified teaching model. Real drive-by staging often spreads the chain across many domains and services, moves the gate between hosts, and can sit behind legitimate advertising networks.

    3

    Red Team / Hacker Perspective

    This section looks at drive-by staging through the eyes of an attacker. Understanding why they prepare a trusted site, and how the staging steps fit together, helps you predict what to look for. Everything here is described for defensive learning; the lab exercise is harmless and runs only on your own machine.

    When and why attackers stage a drive-by target

    Security teams call the target choice the watering-hole logic: instead of hunting animals one by one, wait at the water hole they all visit. Attackers apply the same idea. They do not email you. They wait at the websites your industry already reads - local news portals, professional forums, supplier sites, or industry groups.

    The benefits are clear. There is no phishing email for a gateway to catch. The trust belongs to somebody else. And the victim supply is automatic: every visitor is a candidate, so one staged site keeps working for weeks without further effort from the attacker.

    How staging works

    A typical staging run has five steps. Each step needs only modest skill, which is why this technique appears in both high-end espionage and everyday eCrime.

    • Gain write access. Stolen credentials from a staff member or a plugin vendor can give control of the site. So can an unpatched plugin or a hosting panel takeover. The target is the content-management system (CMS) - the software that publishes the site.
    • Inject the loader. A small obfuscated script tag or a hidden frame goes into a template that every page includes, usually in the footer.
    • Arm the gate. A filter on the landing server checks visitor country, IP address, browser and plugin versions, and a one-visit cookie, then decides who is attacked.
    • Chain the redirects. Shorteners and adtech hops carry the chosen browser to the exploit-kit landing page - a ready-made attack package that tests visitors and runs exploits.
    • Deliver the payload. After a browser weakness is abused, a small loader downloads and starts the real payload.

    Where it applies

    Staging happens in the PRE environment: the compromised website and the attacker's landing infrastructure, before any victim is touched. The victim-side part - the actual visit and exploitation - belongs to T1189 Drive-by Compromise.

    Favorite hosting spots for the trap are popular regional news sites, hobby and professional forums, ministry and municipal portals, and supplier or partner sites with little security staff. Sites that publish many files - documents, plugins, fonts - are especially useful, because one more script file attracts no attention.

    Prerequisites and conditions

    • Write access to a website the target group visits: CMS account, plugin supply chain, ad slot, or a third-party script.
    • Knowledge of the victims' software: which browser, which operating system, which browser plugins are common in the target group.
    • An exploit kit or private exploits (T1587 / T1588) that matches those versions.
    • Landing infrastructure and redirect hops (T1583 / T1584): fresh domains, a gate server, shortener accounts.
    • Patience: the trap must stay unnoticed, so attackers often delay it and test it only on themselves first.

    Lab only — harmless concept demo

    The core idea of a drive-by target is a hidden frame: a page the visitor never asked for, loaded quietly inside the page they did ask for. You can teach yourself this concept with two harmless local files and no internet. Nothing here attacks anything - the "hidden page" only prints one friendly sentence, and the demo is never visible to anyone but you.

    Build the two files below on your own test machine, open the first page in a browser, and then change the frame height from 20 to 0 and reload. You will see how a second page can sit inside a trusted page, fully loaded, with almost no trace on screen. That is the whole trick behind step 3 of the simulation - and why file-integrity monitoring on the template matters more than anything users could notice.

    lab_frame_demo.sh — creates two harmless local pages, LAB ONLY
    # LAB ONLY - harmless frame-visibility demo on your own machine (no internet needed)
# Contains no exploit code, no malware, and no network calls. Delete the folder after use.
mkdir -p ~/lab/driveby && cd ~/lab/driveby

# File 1: the "second page" the hidden frame will load. It is a plain sentence.
cat > page2.html <<'EOF'
<!doctype html>
<p style="font:16px sans-serif">Page two is harmless. It only shows this sentence,
so you can see exactly when the frame loads it.</p>
EOF

# File 2: the "trusted page". The frame tag is the attacker trick, slowed down
# for teaching: change height="20" to height="0" and the frame disappears from view.
cat > frame_demo.html <<'EOF'
<!doctype html>
<p style="font:16px sans-serif">This is the trusted page you decided to visit.</p>
<iframe src=page2.html height="20" width="100%"></iframe>
EOF

# Serve the folder locally and open http://localhost:8000/frame_demo.html
python3 -m http.server 8000

    Common variations

    Malvertising buys the trap space as an advertisement on a legitimate site, so no break-in is needed. Fake update popups claim the browser or a plugin is out of date. Abused script supply hides the loader inside a popular analytics or tag-manager script, so one poisoned script touches thousands of sites. Mobile variants do the same with mobile browsers and app-store redirects. Each variation keeps the same shape: trusted surface, hidden loader, selective gate.

    Attacker mistakes you can catch

    Poor gating is the classic one: the geo list includes security vendors, so researchers find the kit early. Obfuscation still shows up in web access logs as a strange script path that no other site serves. Attackers forget referrer clues: their test clicks leave referer strings that map the whole redirect chain. And gate test visits come from hosting IP ranges, which threat feeds flag.

    Cost of failure

    If the staging is found early, the attacker loses the access, the kit domain, the redirect accounts, and weeks of preparation. That is why serious teams watch their own estate obsessively - and why they rotate landing infrastructure fast. For defenders, every early find also burns attacker trust in that site as a future stage.

    4

    Blue Team / SOC Perspective

    A drive-by target gives defenders two different jobs at the same time: keep attackers from staging on your websites, and keep staged pages elsewhere from reaching your users. This section shows the signals for both sides, the artifacts each one leaves, and a triage flow that works for both.

    Side one: defend your own estate

    Your websites are future drive-by targets until you make them hard ones. The controls that matter most:

    • File-integrity monitoring (FIM) on web roots: a sensor that warns when protected files change outside a deployment.
    • CMS audit logs shipped to the SIEM, with alerts on admin logins from new countries, new devices, or odd hours.
    • Fast patching of the CMS core and every plugin; remove plugins nobody uses.
    • Two-factor authentication (2FA) on every admin panel, hosting panel, and CMS account - including vendor accounts.
    • A web application firewall (WAF) that blocks injection attempts and rate-limits admin paths.
    • Deployment windows: changes to web roots happen only from the release pipeline, which makes every other change a signal.

    Side two: defend your users

    Staged pages live on sites you do not own, so your users' browsers are the sensors:

    • Proxy redirect-chain telemetry: log the referer - the web address a visitor came from - and follow full chains, not single requests.
    • EDR browser child-process rules: alert or block when a browser process starts a script interpreter or command shell.
    • DNS logs with client IP, so every hop of a chain can be replayed later.
    • Domain-age checks: enrich proxy and DNS logs with newly-observed-domain feeds and alert on young domains inside chains.
    • Fast browser updates across the fleet; retire legacy browser modes that no longer get security fixes.
    • Script and ad blockers for high-risk staff such as administrators and researchers.

    Artifacts a drive-by target leaves

    • Unknown scripts or frames in your templates - visible in FIM diffs and in code reviews.
    • Odd outbound requests from web servers themselves, for example the CMS fetching the loader after an edit.
    • Web access logs where many unrelated visitors fetch the same strange script path.
    • Browser crashes, or short-lived child processes, right after a page visit.
    • Proxy chains that start at a trusted site and end at a domain nobody has ever seen.

    Why this split matters

    The two surfaces produce different evidence at different times. Estate signals arrive before any user is harmed - a template change is a gift of time. User signals arrive at the moment of harm - a browser child process means the trap already fired. A SOC that runs both sides can often clean the trap before it hurts anyone, and prove it with the logs.

    Triage flow for a suspected drive-by target

    1. 1 — Receive the signal Either an estate signal - FIM template change, CMS audit anomaly, WAF injection block - or a user signal arrives in the queue. User signals look like a browser child-process alert, a crash cluster, or a proxy chain to a young domain.
    2. 2 — For estate signals: diff and pull Compare the changed template against the last release, save the injected script, and hand it to a sandbox from outside the network. Never open staged content from a corporate device.
    3. 3 — For user signals: walk the chain Pull the proxy records starting at the trusted referer. List every hop, resolve each host, and check the registration age of the landing domain.
    4. 4 — Scope the blast radius Search 30 days of proxy, DNS, and web logs for the same script path, the same chain pattern, and the same landing domain. For estate events, count which visitor IPs fetched the injected path.
    5. 5 — Contain on both fronts Isolate hosts that executed anything. Revert templates from known-good copies. Block the chain domains and kit IPs. Ask the hosting provider to clean the site if it is not yours.
    6. 6 — Report, notify, share Record the kit fingerprints. Notify the site owner, or its readers if your estate was used. Share the indicators with your ISAC and the hosting provider's abuse team.

    Good practice

    Measure one number: the time from a web-root change alert to a verified clean template. If that number is under one hour, an attacker's drive-by investment on your estate dies before the first victim visit - and your proxy chain rules cover the rest.

    No regulator can force a stranger's website to be safe. What they expect from you is visibility.     5.2Threat intelligence

    Drive-by staging is found by joining sources: kit feeds, freshly registered domains, and your own estate and proxy telemetry. This section lists the sources worth feeding into your program, how to work them into a cycle of collection, analysis, and action, and how to grade confidence before you act.

    Core sources

    • MITRE ATT&CK - the shared language for staging (T1608.004), the victim-side hit (T1189), and the browser exploitation that follows (T1203).
    • Vendor reporting - ESET, Kaspersky, Google Threat Intelligence Group, Microsoft, and others publish drive-by and watering-hole campaigns with kit fingerprints.
    • Kit and URL feeds - abuse.ch URLhaus and ThreatFox, URL scanning services, and exploit-kit trackers list landing URLs and gate paths.
    • Newly-observed-domain (NOD) feeds - drive-by chains nearly always end at a young domain; age enrichment turns this into a strong signal.
    • ISACs - sector sharing communities exchange compromised-site lists; if a peer's portal is staged, your visitors may be next.
    • Internal telemetry - your proxy chains, DNS logs, FIM records, and EDR browser events show which staged pages actually met your organization.

    Collection, analysis, application

    Collect by automating three things: kit URL ingestion, NOD enrichment for every proxy and DNS record, and FIM watching on every public web root. Analyse by joining what others see with what you see: a feed-flagged landing URL plus one trusted referer inside your proxy is a confirmed chain, not a rumor.

    Apply the intelligence in three ways. Set preventive blocks for chain patterns, such as a young domain after a shortener hop. Build detection content from the Sigma rules in section 5.5. Write short intel notes that tell leadership which watering holes your industry uses.

    Record every decision. When a blocked chain domain later appears in a vendor report, that feedback loop proves your pipeline works - and it often reveals who was behind the stage.

    ConfidenceMeaningTypical drive-by exampleSafe action
    HIGHYou observed the full chain or the full injection yourself, or several independent sources agree.FIM shows the injected script; the proxy shows the trusted referer leading to the same kit domain; the domain is 2 days old.Revert the template, isolate affected hosts, block the chain at proxy and DNS, and hunt the kit path.
    MEDIUMOne strong source or several weak signals combined.Feed lists a landing URL for your industry; no internal contact yet.Watchlist the chain pattern, alert on any internal referer to it, scan passively; no fleet-wide action yet.
    LOWSingle unverified report or weak automated classification.An anonymous post claims a site serves a kit; your crawler saw nothing.Keep as enrichment only; never auto-block a popular site on low confidence - the business cost is real.

    Confidence in practice: why drive-by intel is special

    Drive-by staging hides from scanners by design. The gate shows the attack only to chosen visitors, so a scanning service often records a clean page while real victims get exploits. This is why confidence must weigh who saw what: your own FIM diff and your own proxy chain are worth more than any outside claim. A useful rule: estate evidence proves staging; proxy evidence proves delivery; feed evidence alone only earns a watchlist entry.

    Actors and ecosystems known for drive-by staging

    Mustard Tempest
    Injected malicious JavaScript into compromised websites to run the SocGholish fake-update drive-by chain (SentinelOne 2022, Red Canary 2024, Microsoft). The group MITRE documents most prominently under this technique.
    Lazarus Group
    Documented watering-hole staging against legitimate South Korean websites, including an online news portal, in Operation Eclipse, 2018 (Kaspersky) — see the case study below.
    APT32
    Built sites filled with scraped articles to look legitimate, with hidden script to profile visitors or serve fake software updates (Volexity, 2020). Documented by MITRE under this technique.
    Threat Group-3390
    Embedded code into websites to screen visitors' IP addresses and exploit only browsers worth attacking (Gallagher, 2015). Documented by MITRE under this technique.
    Dragonfly and Transparent Tribe
    Dragonfly compromised websites to redirect traffic and host exploit kits (Gigamon, 2021); Transparent Tribe set up sites with malicious iframes to deliver Crimson and njRAT (Proofpoint 2016, Talos 2021). Both documented by MITRE under this technique.
    Malvertising and skimmer crews
    Crews buy ad slots on legitimate sites and inject scripts into e-commerce pages; the staging pattern matches drive-by preparation, only the payload differs. Vendor-documented context.

    5.3Threats ranking and categorization

    The five threats below are the realistic ways drive-by staging turns into harm for an organization. Each has a severity, the platforms it touches, what must be true before it can happen, its impact, and why the severity was chosen. Severity reflects combined likelihood and business damage for a typical mid-size organization.

    IDThreatSeverityPlatformPreconditionsImpactJustification
    TH-01 Exploit-kit landing staged on a compromised trusted site - a popular site your users read is wired to a kit that attacks selected visitors. CRITICAL NetworkEndpoint Attacker has write access to a site your staff visits; the kit holds a working browser exploit for their versions. Silent initial access for every selected visitor; one day of visits can hit many machines before anyone notices. Zero interaction, borrowed trust, and automation at scale; sandboxing lowers success rates, but the blast radius of one success justifies Critical.
    TH-02 CMS account compromise used to stage the injection on your estate - stolen admin or vendor credentials turn your own website into the trap. HIGH CloudNetwork Credential theft or an unpatched plugin; weak or missing 2FA on the CMS or hosting panel. Your brand attacks your readers; regulatory exposure, trust damage, and an incident that is public by definition. Credential theft is ubiquitous and estate monitoring is often immature, so likelihood is real; impact is severe but survivable with fast revert and honest notification.
    TH-03 Zero-day browser exploit delivered via the staged page - a previously unknown browser weakness is saved for the highest-value visitors. HIGH EndpointNetwork Attacker has bought or found a zero-day; the gate filters for the chosen victims. Full code execution from a single page view; typical of targeted espionage with long dwell time. Rare and expensive, so likelihood is low for most organizations - but impact is extreme and signatures do not exist, so only behavior rules save you.
    TH-04 Redirect chains through adtech and shorteners to the kit - the delivery path hides the landing server behind hops that look like advertising. MEDIUM Network Attacker rents or abuses redirect and ad infrastructure; victims browse normally. Delivers selected visitors to the kit, defeats referer-only blocking, and hides the operator's origin. High volume but usually broken by category blocking and chain-depth rules; alone it does not exploit anything, so it ranks as an enabler.
    TH-05 Fake storefront or fake update page used as the lure inside a trusted site - a subpage pretends to offer a plugin, document, or update. LOW Cloud Attacker controls a subpage, subdomain, or ad slot of a trusted property. Users install or run what the lure offers; the blended trust makes the payload more believable. Needs a user action beyond browsing, so it is weaker than a true drive-by; still worth a rule because it shares the same staging infrastructure.

    Note

    Ratings are starting points. Adjust them to your sector: TH-02 jumps toward Critical if your website touches payments or patient data, and TH-03 rises for organizations that intelligence services care about. A regional bank and a bakery should not share the same numbers.

    TH-03 — Zero-day browser exploit delivered via the staged page

    Log sources
    EDR process creation with parent-child links, EDR crash telemetry, proxy logs, DNS logs, browser error reports
    Key fields

    (parent_image is a browser) AND (child is powershell, cmd, wscript, cscript, or mshta) - level Critical; plus a lower-severity rule for browser crash clusters
    endpoint event — browser spawns a script interpreter (Sysmon Event ID 1, JSON)

    Real-World Case Study

    Operation Eclipse is the cleanest public example of this technique. Lazarus Group compromised legitimate South Korean websites, including an online news portal. There they staged a drive-by chain that attacked selected visitors. The documented chain below comes from public reporting; the victim-organization timeline afterwards is a labeled reconstruction for teaching purposes.

    Context (public reporting: Kaspersky, September 2018)

    Kaspersky researchers documented Operation Eclipse as a Lazarus watering-hole campaign. The attackers compromised legitimate South Korean websites - among them an online news portal - and prepared them as drive-by targets. Instead of sending lures, they waited where their targets already read the news.

    What made the campaign notable was the selectivity. The staged chain checked each visitor and delivered its exploit only to chosen ones. Most visitors - and most scanners - saw a clean page.

    Documented attack chain

    • Compromise of legitimate, trusted South Korean websites (staging infrastructure, T1584).
    • Preparation of the sites as drive-by targets (T1608.004): hidden delivery wired into the pages visitors already loaded.
    • Visitor selection, so only chosen users met the attack - everyone else saw the ordinary site.
    • Delivery of an exploit for a zero-day weakness in Internet Explorer (CVE-2018-8174) through the staged chain (T1189 / T1203).
    • Follow-on payload installed on machines of successful targets.

    Timeline of one victim organization (reconstructed for teaching - not from public reporting)

    1. Day 0, 09:12 An employee reads the morning briefing on the trusted news portal. A hidden loader wired into the page quietly chains the browser to the kit landing server. No click, no dialog, no warning.
    2. Day 0, 09:14 EDR raises the first detection: the browser process crashes twice, then attempts to start a script interpreter. The parent-child rule fires and blocks the launch.
    3. Day 0, 09:26 The analyst isolates the workstation and pulls the proxy chain: referer is the news portal, next hops are a shortener and a domain registered four days earlier.
    4. Day 0, 11:00 Hunting finds two more visitors reached the landing domain that morning. Their hosts show no execution, because the gate served them only the decoy - proof that selectivity works in both directions.
    5. Day 1 The SOC contacts the news site's hosting provider. The provider confirms the compromise, reverts the templates from clean copies, and rotates the CMS credentials. The SOC shares the kit URLs with the abuse team.
    6. Day 2 Eradication: the fleet's browsers are force-updated, legacy browser modes are disabled, and the chain domains are blocked at proxy and DNS. The site owner publishes a notice to its readers.
    7. Day 5 Recovery: all three hosts are verified clean, the browser child-process rule moves to block mode for everyone, and the campaign is written up with the ISAC.

    Detection point

    The winning alert was the endpoint rule: a browser process attempting to start a script interpreter. The proxy chain provided the second, independent signal that connected the event to a staged page, and the domain-age lookup confirmed the landing server was four days old.

    Containment and eradication

    The workstation was isolated within fourteen minutes of the alert. Investigators confirmed the payload never ran. They searched thirty days of proxy history for the chain pattern. They also worked with the hosting provider, so the site stopped attacking its own readers the same day.

    Recovery

    The user returned to a patched machine the same afternoon. The fleet update removed the exploited weakness, and blocklists covered the chain. The injected script path joined the estate watchlist in case the attackers returned to the same host.

    Impact and consequences

    Because EDR blocked the launch, the organization's loss was measured in analyst hours, not in stolen data. The bill: roughly ninety staff-hours across three days, one host rebuilt as a precaution, and one honest notification to the affected readers through the site owner. The unblocked alternative - a successful zero-day implant on a finance workstation - would have been a different story entirely.

    Team response and communication

    A single incident channel coordinated SOC, IT, web platform, and communications. Leadership received three numbers each morning: hosts affected, chain domains blocked, and hours since the site was verified clean. That simple set prevented both panic and complacency while the hosting provider finished its cleanup.

    Lessons learned

    • Patch speed is a drive-by defense. The exploited weakness had a patch for weeks in the modern-browser world; the lingering legacy install was the door.
    • EDR on execution paths is the net under the rope. Even a zero-day must run code, and the browser child-process rule caught it running.
    • Monitor your own estate. The site compromise was invisible to the victim organization until they looked - the hosting provider's logs had the whole story.
    • Selectivity cuts both ways. The gate spared two staff members by accident; without that luck, three hosts would have needed forensics instead of two.

    Mitigation and Defense

    You cannot stop attackers from preparing websites. You can make the preparation worthless. Use hard browsers that refuse to run old exploits. Keep an estate that refuses to host the trap. Run a network that refuses to carry the chain. Controls below are grouped by layer, with a priority table at the end.

    Official mitigation position

    ATT&CK lists exactly one mitigation for T1608.004: M1056 Pre-Compromise. The staging work happens on sites the attacker compromises, outside your estate, so it cannot be prevented directly. Every control below therefore hardens what staging feeds — users, mail, web, and endpoints — and shortens the time between staging and abuse.

    Browsers and operating systems

    Keep browsers and operating systems on fast auto-update rings, and remove legacy browser modes that no longer receive security fixes. Most kit exploits rely on weaknesses that were patched weeks or months earlier - a current browser closes the majority of drive-by attacks before they start.

    Endpoint protection

    Run EDR in block mode with attack-surface-reduction (ASR) rules - policies that stop risky behavior patterns - especially the rule that blocks office and browser applications from launching child processes. A blocked child process turns a drive-by into a log entry.

    Script blockers for sensitive roles

    For administrators, researchers, and finance staff, add script-control extensions or application allowlisting on their workstations. These users are the gate's favorite targets, and their machines should not run website-supplied scripts by default.

    Defend your own estate

    Patch the CMS and every plugin, enforce 2FA on all admin and vendor accounts, add file-integrity monitoring to web roots, and put a WAF in front of public sites. Deploy only from the pipeline, so any other change to a template is automatically a signal.

    Network controls

    Enrich proxy and DNS logs with domain age and block freshly registered domains that appear behind a redirect chain. Log full chains, not single requests, and alert on trusted referers that lead somewhere young.

    Ad and script blockers

    A reputable ad and script blocker for high-risk users removes a large share of malvertising and third-party script risk at zero maintenance cost. It is not a security boundary - but it deletes most of the gate's parking lot.

    Home and small-office advice

    Set the operating system and browser to update automatically, and add a reputable ad blocker. Never install "missing players" or "urgent updates" that a webpage offers you. Be mildly suspicious even of pages you trust. If a news site makes your browser stutter, close it and report it. Turn on multi-factor authentication for your main accounts, and back up important files to a service that keeps history.

    Common Mistakes and Best Practices

    These are the failures detection teams actually make around drive-by targets. Each card shows the symptom you will notice first, the root cause behind it, the fix, and the prevention that stops it from coming back.

    1. Assuming modern browsers remove the risk

    Symptom
    The technique is marked out of scope because "nobody runs Internet Explorer".
    Root cause
    Confusing "harder" with "impossible": fresh weaknesses still appear, and old builds linger everywhere.
    Fix
    Scope the technique again; measure how many fleet browsers are behind on updates.
    Prevention
    Review browser version dashboards monthly as part of the drive-by coverage.

    2. No file-integrity monitoring on web roots

    Symptom
    The estate team learns about an injection from a researcher's tweet.
    Root cause
    Web servers are treated as an infrastructure box, not as a monitored asset.
    Fix
    Put FIM on every public web root and alert outside deploy windows.
    Prevention
    Add web roots to the logging coverage matrix next to domain controllers.

    3. Ignoring browser crash telemetry

    Symptom
    "Chrome crashes a lot on that site" is treated as a support ticket.
    Root cause
    Crash clusters are routed to IT, never to security.
    Fix
    Forward crash bursts per host and per domain into the SIEM as a signal.
    Prevention
    Write a rule that joins crash clusters with the proxy referer of the same minute.

    4. Blocklist-only defense

    Symptom
    Every incident starts with "the domain was new, no list had it".
    Root cause
    Blocks on identity (lists) instead of behavior (chains, ages, parent-child).
    Fix
    Add chain and age logic next to lists - the rules in section 5.5.
    Prevention
    Track what percentage of confirmed incidents a list caught; keep it under review.

    5. Not monitoring referer chains

    Symptom
    The kit domain appears in logs weeks later, but the trusted referer was never noticed.
    Root cause
    Proxy logs are kept but chains are never reconstructed.
    Fix
    Enable chain capture and store referer with every request.
    Prevention
    Run the TH-04 rule weekly as a hunt, not only as an alert.

    6. Treating the website estate as someone else's problem

    Symptom
    "Our site is run by marketing/agency/hosting - not our scope."
    Root cause
    Ownership of the public web estate is split and the security team assumes the rest.
    Fix
    Write one owner per public site into the asset register, with monitoring duties.
    Prevention
    Include the estate in the purple-team scenario every quarter.

    7. No EDR execution telemetry

    Symptom
    Exploit attempts are invisible; the first artifact is a helpdesk call.
    Root cause
    EDR exists but process and file events are not shipped or retained.
    Fix
    Ship process-creation and file events for all users, with 90-day retention.
    Prevention
    Alert when any endpoint source drops below its normal daily volume.

    8. Tuning away browser-child-process alerts

    Symptom
    The rule was silenced after two false positives from a test tool.
    Root cause
    Alert fatigue plus a noisy first version of the rule.
    Fix
    Re-enable with documented, narrow exclusions and a second engineer's review.
    Prevention
    Replay a labeled test set after every tuning change to this rule.

    9. No owner for estate monitoring rules

    Symptom
    FIM alerts go to a shared mailbox nobody reads.
    Root cause
    Rules exist but have no named owner, no review date, no runbook.
    Fix
    Assign an owner and a triage runbook for every rule in section 5.5.
    Prevention
    Detection-as-code repository with owners and review dates enforced by review.

    10. Never validating rules

    Symptom
    Nobody can say whether the rules would actually fire today.
    Root cause
    No purple-team testing of drive-by scenarios end to end.
    Fix
    Rehearse one scenario quarterly - the harmless lab demo from section 3 makes a start.
    Prevention
    Track detection coverage against T1608.004 / T1189 / T1203 in the charter.

    11. Assuming only old software matters

    Symptom
    Attention goes only to legacy systems; current-browser events are ignored.
    Root cause
    The "modern browsers are safe" myth again, now in monitoring scope.
    Fix
    Keep the browser child-process and file-drop rules on every Windows host.
    Prevention
    Review which rules exclude modern browsers; none should.

    12. Ignoring supply-chain script risk

    Symptom
    Third-party analytics and tag scripts are added to the site without review.
    Root cause
    Tag managers make adding scripts a one-click, no-process action.
    Fix
    Inventory every third-party script, require a review step, and pin integrity hashes where possible.
    Prevention
    Alert on new script sources on payment or login pages (PCI DSS 6.4.3 helps here).

    Daily habits

    • Check estate alerts: FIM, CMS audit, WAF blocks.
    • Review browser child-process alerts from the night.
    • Confirm NOD enrichment still refreshes.

    Weekly habits

    • Hunt the trusted-referer chain pattern across 7 days.
    • Review the third-party script inventory for changes.
    • Walk one live proxy chain end to end as practice.

    Monthly habits

    • Check fleet browser versions against the update policy.
    • Replay the test event set against all five rules.
    • Report drive-by metrics and estate drift MTTR to leadership.

    Cheat Sheet and Quick Reference

    Everything urgent from this page on one screen: the facts, the highest-value detections, the response checklist, and the official links.

    Key facts

    Technique
    T1608.004 - Drive-by Target (Resource Development, PRE; sub-technique of T1608)
    Victim-side outcome
    T1189 Drive-by Compromise; browser weakness abuse is T1203
    What the attacker needs
    Write access to a website the target group already visits
    Seen in
    Lazarus Operation Eclipse (2018), exploit-kit ecosystems (Angler/RIG era), malvertising, web-skimmer injections
    Fastest win
    Web-root FIM plus the EDR browser child-process rule in block mode

    Top detections (from 5.5)

    • First-seen script path served from upload or template directories (webserver, Medium)
    • Web server user modifies web roots outside the deploy window (file_event Linux, High)
    • Browser process spawns a script interpreter or command shell (process Windows, Critical)
    • Trusted-site referer chained to a young domain (proxy, High)
    • Browser process writes an executable into Temp or Downloads (file_event Windows, High)

    Response checklist when a drive-by target is confirmed

    • Isolate every host where a browser started a child process or dropped a file.
    • Save the injected script and the kit URLs as evidence, then revert templates from known-good copies.
    • Search 30 days of proxy, DNS, and web logs for the chain pattern and the script path.
    • Block the chain domains and kit IPs at proxy, DNS, and mail level.
    • Force-update the browser fleet and remove legacy browser modes.
    • If the staged site is not yours, work with its hosting provider and notify its readers through the owner.
    • Share the indicators with your ISAC and record the kit fingerprints for the next hunt.
