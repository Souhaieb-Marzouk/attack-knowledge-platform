T1608.003 Install Digital Certificate

A padlock icon is cheap. Attackers install TLS certificates on their staging and command servers so browsers show the same trust indicator as your bank. This page shows how certificates become attacker tools - and how the public certificate log gives you a free early-warning radar.

Contents

    1

    Overview

    This section explains what Install Digital Certificate means in plain words, why one small file creates so much false trust, and where this sub-technique sits in the attack chain.

    What the sub-technique is

    Install Digital Certificate means an attacker puts a TLS certificate on servers or services they control. TLS is the technology that encrypts web traffic and shows the padlock icon in the browser. A certificate is a small digital ID file, signed by a certificate authority (CA), that says "this domain speaks real TLS".

    The attacker does not need to fool the CA with a fake identity. Free CAs check only that the requester controls the domain - and an attacker always controls their own domain. So a name registered 3 days ago can carry a perfectly valid certificate today.

    Why it matters

    Many security tips end with "look for the padlock". Attackers know this, so they install certificates to pass exactly that check. A valid padlock on a fake supplier portal defeats a careful user, and it also hides the site from mail filters that flag plain-HTTP links.

    For defenders this sub-technique is a gift in disguise. Certificates cannot be installed in secret for long: every public issuance is written to Certificate Transparency (CT) logs, a global public record that anyone can read. Watching those logs gives you one of the earliest warnings available anywhere in the attack chain.

    Not the same as T1588.003

    Two ATT&CK sub-techniques involve certificates, and they are easy to mix up. T1608.003 installs server TLS certificates on attacker infrastructure, so a website looks trustworthy to visitors. T1588.003, Code Signing Certificates, acquires certificates used to sign files, so malware looks like trusted software on disk.

    Rule of thumb: if the certificate protects a website the victim visits, think T1608.003. If it is baked into a file the victim runs, think T1588.003. This page is only about the first kind.

    Where it fits in the chain

    The certificate rides on infrastructure the attacker already has. In ATT&CK terms they first acquire the domain (T1583.001, Acquire Infrastructure: Domains). Then they install the certificate (T1608.003) and stage content behind it - a drive-by page (T1608.004) or a link target (T1608.005).

    The finished site then supports later tactics: phishing mails with links (T1566, especially T1566.002), or command-and-control channels that hide in normal web traffic (T1071.001). One free certificate serves all of these purposes.

    3

    Red Team / Hacker Perspective

    This section looks at certificate staging through the eyes of an attacker. Understanding why and how they get a padlock so cheaply helps you predict what to look for. Everything here is described for defensive learning; the lab example runs only on your own machine.

    Why attackers install certificates

    The padlock is the cheapest trust trick on the internet. A phishing page behind a valid TLS certificate survives longer in mail gateways. It matches the "does the address start with https" advice many users follow. And it copies the exact look of a real portal. For command servers, TLS also blends the traffic into the sea of normal encrypted web flows.

    There is an operational benefit too: some phishing kits and management panels refuse to run on plain HTTP, and some browsers restrict features (camera, clipboard, autofill behaviour) on insecure pages. A certificate removes those small frictions for the attacker.

    How the automation works (ACME)

    Nearly all free certificates come through ACME, a public protocol for automatic certificate issuance. An ACME client on the attacker's server creates an order for a domain. The CA posts a challenge - for example a file with a secret token, or a DNS text record. The client answers it. The CA then signs a certificate, usually valid for 90 days, and the whole loop never involves a human.

    Because the check is "do you control the domain", not "who are you", an attacker who just registered the domain passes it instantly. Renewal repeats automatically every couple of months, which is why certificate staging keeps working after defenders block the first domain.

    Free CAs and certificate options

    Attackers use the same free CAs as everyone else: Let's Encrypt, ZeroSSL, and Google Trust Services are the common ones. A standard certificate covers one name or a short list of names in its SAN field - the Subject Alternative Name, which lists every host the certificate protects.

    A wildcard certificate covers any single-level subdomain of one name, and needs a DNS-based challenge to issue. Some attackers pay a few dollars for longer-validity certificates; that choice is rare on fresh domains and is itself a weak signal defenders can use.

    Prerequisites and conditions

    • Control of a domain - usually freshly registered (pairs with T1583.001).
    • A server, cloud instance, or hosting panel where the certificate can be installed.
    • An ACME client such as certbot, acme.sh, lego, or win-acme.
    • Reachable DNS or a web root, to answer the CA challenge.
    • No money and no identity: the whole chain is free and automated.

    Lab only — safe practice setup

    You can rehearse the defender side by making a self-signed certificate on your own test machine. A self-signed certificate is one signed by its own key - browsers will warn about it, which is exactly what you want to practise inspecting. This uses no real attack tooling and must never be exposed to the internet.

    lab_selfsigned_cert.sh — runs only on your own test VM
    # LAB ONLY - harmless local certificate for defender practice
mkdir -p ~/lab/cert && cd ~/lab/cert

# Create a self-signed certificate for localhost, valid 7 days
openssl req -x509 -newkey rsa:2048 -sha256 -nodes -days 7 \
  -keyout key.pem -out cert.pem \
  -subj "/CN=localhost" \
  -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"

# Serve one folder over HTTPS on port 8443, listening on 127.0.0.1 only
python3 -c "import ssl,http.server,functools; \
h=functools.partial(http.server.SimpleHTTPRequestHandler); \
srv=http.server.ThreadingHTTPServer(('127.0.0.1',8443),h); \
ctx=ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER); ctx.load_cert_chain('cert.pem','key.pem'); \
srv.socket=ctx.wrap_socket(srv.socket,server_side=True); srv.serve_forever()"

# In a second terminal, inspect it like a defender would
openssl s_client -connect 127.0.0.1:8443 -servername localhost < /dev/null 2> /dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName

    The last command prints the subject, issuer, validity dates, and SAN list - the same fields your detection rules use in section 5. Read them as an analyst: issuer "same as subject" means self-signed, and a 7-day validity on a brand-new key is a classic test or throwaway pattern.

    Common variations

    Multi-SAN phishing kits request one certificate that covers dozens of lookalike host names at once. Some operators clone internal-looking hostnames, or rotate short-lived certificates across fresh domains every few days. Bulletproof hosting providers - hosts that ignore abuse reports - often ship certificates for their customers as part of the package.

    Attacker mistakes you can catch

    Paid or long-validity certificates on days-old domains draw attention because the pattern is unusual. CT exposure is unavoidable, so the whole issuance history of a campaign is public. Reused infrastructure across campaigns and SAN lists that spell out an entire fake-brand family are also common slips.

    Cost of failure

    A CT watchlist can burn a staged domain days before the first mail is sent, and a take-down request destroys the attacker's whole front-door investment. That is why serious operators automate rotation - and why your monitoring must be continuous, not a weekly review of old lists.

    4

    Blue Team / SOC Perspective

    Defenders cannot watch the attacker request a certificate, but the certificate itself becomes public the moment it is issued. This section shows where certificate staging is visible, which fields carry the signal, and how to triage a hit in minutes.

    How defenders can see it

    Certificate Transparency monitoring is the anchor. CT is a family of public logs where every publicly trusted certificate must be recorded before browsers accept it. Services let you search all certificates for a name (crt.sh is the classic example) and subscribe to real-time streams (CertStream delivers each issuance within seconds). A watchlist on your brand and supplier keywords turns this stream into a queue.

    TLS metadata adds more, all from the network: the issuer name, the SAN list, and JA3/JA4 fingerprints. JA3/JA4 are short hashes that describe how a client or server performs the TLS handshake. Proxy SNI logs record the hostname a browser announces during the TLS handshake, so you see which hosts your users visit even when content is encrypted. Registrar and passive-DNS feeds give the domain age that makes all of this meaningful.

    Artifacts certificates leave

    • A certificate issued minutes or hours after domain registration - the age mismatch is the strongest single signal.
    • A free automated issuer on a lookalike name on a cheap top-level domain.
    • SAN lists that contain many brand-like names at once (a whole campaign in one record).
    • A steady reissue rhythm every 60-90 days as free certificates are renewed.
    • Self-signed or unusual issuers on hosts your users visit internally.
    • In proxy and DNS logs: first contact with a domain that has no history and no reputation.

    Where to look

    Feed the CT stream into your SIEM or a lightweight watcher. Match it against a vocabulary list: your brand, product names, suppliers, payment partners, and common words like "portal", "invoice", or "login". Join every hit with domain age and WHOIS. Inside your own telemetry, keep a standing hunt for TLS connections to hosts whose certificate is younger than 7 days.

    Why it matters

    Catching the certificate is catching the attack before the phish is even written. A blocklist entry costs seconds; an incident costs weeks. It also feeds the whole program: confirmed lookalike domains become training examples, blocklist entries, and ISAC reports that protect your peers.

    Short triage flow for a suspicious certificate issuance

    1. 1 — Receive the alert The CT watchlist fires on a name containing your brand or supplier keywords. Note the exact common name and SAN list from the alert.
    2. 2 — Check age and ownership Look up domain registration date and WHOIS. Certificate age minus domain age near zero is the classic staging pattern. Check whether the name is on any approved marketing or partner list.
    3. 3 — Look, do not log in Inspect the site in an online URL scanning service, from outside the corporate network. Never open a suspected staging page from a work device or with real credentials.
    4. 4 — Decide Harmless parked domain or real partner: close with a note. Cloned login page or malicious content: continue. Unclear: watch passively and re-check in 24 hours.
    5. 5 — Block and hunt Block the domain at DNS, proxy, and mail. Search the last 90 days of proxy, DNS, and mail logs for any earlier contact, and alert on the users who touched it.
    6. 6 — Report and enrich Send a take-down request to the registrar and hoster, share the indicator with your ISAC, and add the lure pattern to awareness training.

    Good practice

    Measure "time from issuance to block". A CT alert is available within minutes of issuance. If your process reaches a block decision in under an hour for in-scope keywords, most certificate-staging campaigns never get to fire a single mail.

    5.2Threat intelligence

    Certificate-staging detection lives on external data. This section lists the sources worth feeding into your program. It explains the cycle of collection, analysis, and action. It also shows how to grade confidence before you block something.

    Core sources

    • MITRE ATT&CK — the shared language for certificate staging (T1608.003) and the techniques around it.
    • Vendor reporting — Microsoft, Proofpoint, ESET, Mandiant, and others publish certificate patterns with campaign reports.
    • OSINT services — crt.sh certificate search, CertStream real-time issuance feed, urlscan.io, WHOIS, passive DNS, abuse.ch URLhaus and ThreatFox.
    • Commercial feeds — newly-observed-domain feeds and phishing-infrastructure feeds, many with issuer and SAN fields included.
    • ISACs — sector sharing communities exchange lookalike-domain indicators seen against peers.
    • Internal telemetry — your own proxy, DNS, mail, and identity logs show which staged certificates actually reached users.

    Collection, analysis, application

    Collect by automating CT-log monitoring for your brand and supplier vocabulary and subscribing to one new-domain feed. Analyse by joining signals: fresh domain + free-CA issuer + brand-like words + no business owner is a strong staging pattern even before any content is confirmed.

    Apply the intelligence in three ways. Set preventive blocks for high-confidence indicators. Build detection content from the Sigma rules in section 5.5. Write short intel notes that tell leadership who is staging sites against your brand and how early you see them.

    Record every decision. When a blocked lookalike domain later appears in a vendor report, that feedback loop proves your pipeline works and justifies its budget.

    Actors and campaigns known for certificate staging

    Sea Turtle
    Captured legitimate SSL certificates from victim organizations and installed them on attacker-controlled infrastructure to run adversary-in-the-middle operations (Cisco Talos, 2019). The group MITRE documents under this technique — see the case study below.
    Nobelium (APT29)
    Vendor reporting during the 2020–2021 campaigns documented free certificates on new attacker infrastructure so fresh domains looked legitimate at a glance. Useful context; MITRE does not list it as a procedure example here.
    Phishing-kit ecosystems
    Kit sellers ship TLS-ready panel templates, and free certificate authorities make the padlock instant and free, so even low-skill crews stage behind valid certificates. Vendor-documented context.
    Commodity phish crews
    Thousands of small operators request free certificates for lookalike domains every day; Certificate Transparency logs record every single one. Vendor-documented context.

    How confident can you be?

    Vendor reporting is the strongest layer. A named group's certificate habits - such as Nobelium's use of Let's Encrypt in 2021 - are documented with technical detail. They deserve HIGH confidence for planning detections. Claims about the phishing-kit economy are MEDIUM by nature: the kits are real and widely reported, but exact market numbers change fast and are hard to verify.

    Attribution of any single certificate issuance is usually LOW: a free certificate proves control of a domain and nothing about the person behind it. Treat every individual issuance as unattributed infrastructure, and let confidence grow only through corroboration - content confirmation, hoster reputation, and reporting from trusted vendors.

    5.3Threats ranking and categorization

    The five threats below are the realistic ways installed certificates turn into harm for an organization. Each has a severity, the platforms it touches, what must be true before it can happen, its impact, and why the severity was chosen. Severity reflects combined likelihood and business damage for a typical mid-size organization.

    IDThreatSeverityPlatformPreconditionsImpactJustification
    TH-01 Free-CA certificate on a fresh lookalike domain as staged front door — a newly registered brand-lookalike gets a valid TLS certificate before any attack mail is sent. MEDIUM NetworkCloud Attacker registers domains at will; free CAs issue automatically in seconds. Enables phishing, payload delivery, and C2 that padlock-aware users trust. Very high volume, but the CT public log gives defenders a strong and free early signal, and the site still needs a lure to cause harm.
    TH-02 Cloned SSO or login portal with valid TLS harvesting credentials — the certificate-protected page copies your identity provider or supplier portal and collects passwords. MEDIUM IdentityNetwork A lookalike front door exists (TH-01) and a lure reaches a user. Direct account compromise; with MFA the attacker pivots to fatigue or helpdesk tricks.     TH-03 Certificate on bulletproof-hosting C2 pre-staging — command-and-control servers get certificates so their encrypted channels blend in before an intrusion starts. LOW Network Attacker rents abuse-tolerant hosting and prepares C2 domains in advance. Ready-made encrypted C2 shortens dwell time once an intrusion begins. Only harmful when combined with an intrusion; the hosters are often already known, and no user interaction is required.
    TH-04 Multi-SAN certificate covering dozens of lookalike hosts at once — one issuance lists many brand-like names, staging a whole family of fake portals in a single step. MEDIUM CloudNetwork Attacker registered several lookalike domains or one wildcard-capable parent domain. One blocked domain does not end the campaign; the SAN list reveals the full set to defenders who read it. Scale amplifies both harm and signal - the SAN list is a gift to CT watchers who parse it.
    TH-05 Unusual or self-signed certificates served to internal users — someone stages a trusted-looking service inside your network, or a rogue admin service appears with a fresh self-signed certificate. LOW Network Attacker or misbehaving insider already has some foothold, or a team ships a service without following PKI process. Users may trust a fake internal portal; unmanaged certificates resist inventory and expiry tracking. Requires prior access, so it is rare as an entry vector, but it is a clean hygiene signal worth alerting on.

    Note

    Ratings are starting points. Adjust them to your sector. TH-02 jumps toward High for an organization whose staff work daily in supplier portals. TH-01 rises if your brand is actively impersonated in current campaigns.

    Real-World Case Study

    Sea Turtle is the group MITRE documents under T1608.003. Cisco Talos reported in 2019 that the group captured legitimate SSL certificates from victim organizations and installed them on infrastructure it controlled. Its adversary-in-the-middle pages then carried certificates that browsers had no reason to doubt. Vendor reporting on Nobelium (APT29) shows the same staging logic with free certificates on new infrastructure during the 2020-2021 campaigns. The timeline below is a labeled composite for teaching purposes.

    Context (public reporting)

    In 2019 Cisco Talos described Sea Turtle's campaign against telecommunications providers, government bodies, and internet infrastructure in the Middle East and North Africa. Instead of buying or forging certificates, the group stole valid ones from victim organizations through phishing, then installed them on its own servers. That one move let the group impersonate real services behind certificates browsers trusted.

    The lesson for defenders was uncomfortable and useful at once. If a capable group treats certificates as cheap staging parts - stolen, free, or bought - then valid-looking certificates are the baseline assumption for every threat model. The Certificate Transparency (CT) log is the sensor that sees every publicly issued one of them.

    Documented attack pattern

    • Phish target organizations until a valid SSL certificate is captured (the Sea Turtle method), or request a free one for a lookalike domain.
    • Install the certificate on attacker-controlled infrastructure (T1608.003).
    • Stage the impersonation pages and tools behind the certificate-protected front door.
    • Redirect victims through DNS or links so they reach the clone and type their credentials.
    • Rotate infrastructure quickly; certificates follow the rotation automatically.

    Composite timeline — one defender organization (reconstructed for teaching)

    This timeline is a composite built from public reporting to show how the detection chain works end to end. It does not describe one specific named victim organization.

    1. Day −3, 21:40 The CT watchlist fires: vendor-portal-sharepoint[.]top, a brand-keyword match on a cheap TLD, certificate from Let's Encrypt. The domain is 1 day old. Nobody in the brand registry owns it.
    2. Day −3, 22:15 The analyst checks WHOIS (privacy-protected, fresh) and scans the URL in an external service: a clone of the supplier portal login page. Verdict: high confidence staging.
    3. Day −3, 23:00 The domain is blocked at DNS, proxy, and mail; the block covers all six SAN-related names from the certificate family. Hunting over 90 days of logs finds no earlier internal contact.
    4. Day −1 A phishing wave hits the sector, including mail to your staff carrying the same lookalike link. The mail gateway blocks delivery at the URL-reputation check because the domain is already on the blocklist and 4 days old.
    5. Day 0 Vendor research confirms the same lookalike-domain family active in a staged-phishing campaign against the sector. Your block from three days earlier is now externally corroborated; the case note upgrades to confirmed intelligence.
    6. Day 1 The registrar and hoster receive a take-down request via your brand-protection service; indicators go to the ISAC. Awareness training gets a new screenshot: the padlock, the clone, and the CT alert that caught it first.

    Detection point

    The winning signal was the CT watchlist rule from section 5.5 (TH-01), firing three days before the phish landed. The independent second signal was the mail gateway age check, which blocked the link at delivery time. No endpoint was ever involved.

    Containment and eradication

    Blocks landed at DNS, proxy, and mail for the full SAN name family, not just the one domain. Because hunting found no clicks, no endpoint work was needed; the take-down request started against the hoster and registrar instead.

    Recovery

    Recovery here means returning to normal monitoring with new knowledge. The brand vocabulary list grew by the words the attacker used. The lookalike pattern joined the next phishing simulation for staff.

    Impact and consequences

    Impact was near zero: one analyst-hour, one blocklist change, no credential loss. The counterfactual is the real story. Without the CT alert, the same wave that hit peers would have delivered a clone of a supplier portal to employees. At least one password would likely have been typed into it.

    Team response and communication

    The SOC handled it as a routine outside-in case: one ticket, one decision, one block. The vendor report three days later triggered a short briefing to leadership. It carried three numbers: time from issuance to block (82 minutes), internal contacts found (zero), and peers protected through ISAC sharing (three confirmed overlaps).

    Lessons learned

    • CT monitoring converts attacker preparation time into defender preparation time - here, three free days.
    • Block the whole SAN family, not the single name; the certificate hands you the campaign map.
    • Outside-in wins need no endpoint involvement, so measure and fund them as first-class detections.
    • Vendor reporting closes the loop: publish or share what you block, because peers enrich it.

    Mitigation and Defense

    You cannot stop an attacker from requesting a certificate for their own domain. You can make the certificate useless: watch the public logs, harden the delivery paths, and make stolen passwords worthless. Controls below are grouped by layer, with a priority table at the end.

    Official mitigation position

    ATT&CK lists exactly one mitigation for T1608.003: M1056 Pre-Compromise. Certificate issuance happens at public authorities anyone can use for free, so it cannot be prevented directly. Every control below therefore hardens what staging feeds — users, mail, web, and endpoints — and shortens the time between staging and abuse.

    Certificate Transparency watchlist automation

    Stand up a consumer for the CT stream and match every issuance against your brand and supplier vocabulary. Route matches to a queue with domain age and WHOIS already attached, and measure time from issuance to block. This is the single highest-value control for this sub-technique.

    Newly-observed-domain feeds

    Subscribe to a new-domain feed and use it to enrich DNS, proxy, and mail logs with domain age. Age-based scoring catches the whole staging family - lookalike domain, fresh certificate, first click - with one enrichment.

    TLS inspection where lawful

    TLS inspection decrypts traffic at your proxy so tools can see inside. It is powerful but legally sensitive, so run it only with a documented privacy review and only where the law allows. Where inspection is not allowed, SNI logging and passive certificate capture still give you hostnames and issuers without opening content.

    Phishing-resistant MFA

    Phishing-resistant MFA means authentication that cannot be replayed by a fake site, such as FIDO2 security keys or platform passkeys. A cloned portal with a valid certificate still harvests a password - it just cannot use it. This control devalues the entire credential-harvesting business model.

    Brand monitoring and take-down service

    A brand-protection service watches registrars, CT logs, and mail traffic for your names and files abuse reports. A fast take-down burns the attacker's staged investment and shortens the life of any portal that slips past your blocks.

    Cheap-TLD risk scoring with an exception process

    Give cheap-abuse TLDs (.top, .icu, .cfd, .click, .sbs) a higher risk score in mail and DNS filtering, and block the worst of them by default. Keep a simple exception path for real business needs, so the policy survives its first contact with marketing.

    Home and small-office advice

    Teach one sentence at home: the padlock means encryption, not honesty. A site can encrypt your password straight to a criminal. Prefer a password manager that autofills only on the true domain - it refuses to fill on a lookalike, which makes it a built-in lookalike alarm. Turn on multi-factor authentication everywhere it is offered, and keep the browser and system updated. If a portal suddenly asks you to log in again through a new address, stop. Type the address yourself instead of clicking.

    Common Mistakes and Best Practices

    These are the failures detection teams actually make around certificate staging. Each card shows the symptom you will notice first, the root cause behind it, the fix, and the prevention that stops it from coming back.

    1. Training that says "padlock = safe"

    Symptom
    Users forward fake sites as proof they "checked security".
    Root cause
    Old awareness material equated TLS with trustworthiness.
    Fix
    Retrain with the sentence "padlock means encryption, not honesty" and real lookalike screenshots.
    Prevention
    Annual training refresh includes one padlock-abuse example.

    2. No CT feed at all

    Symptom
    Lookalike domains appear "suddenly" during incidents.
    Root cause
    Nobody consumes the free, real-time issuance stream.
    Fix
    Stand up a CT watchlist for brand and supplier keywords.
    Prevention
    Add CT coverage to the logging coverage matrix.

    3. Blocking a free CA globally

    Symptom
    Half the internal web breaks after a blunt block of a big free issuer.
    Root cause
    Punishing the issuer instead of the name-age-issuer pattern.
    Fix
    Block specific names and young-certificate patterns, never whole CAs.
    Prevention
    Every block policy documents its expected business impact.

    4. No TLS/SNI logging

    Symptom
    Encrypted traffic is a black box; hostnames appear only in random tools.
    Root cause
    SNI and certificate metadata were never shipped to the SIEM.
    Fix
    Log SNI, issuer, and certificate age at the proxy or sensor.
    Prevention
    Include TLS metadata in the logging coverage matrix.

    5. Ignoring the SAN field

    Symptom
    You block one domain; two days later its "sibling" hits a user.
    Root cause
    Rules read only the common name, not the full name list.
    Fix
    Parse SAN arrays and block or watch every name in the family.
    Prevention
    Detection templates always include san as a field.

    6. No brand and supplier vocabulary

    Symptom
    CT rules exist but never match anything meaningful.
    Root cause
    The keyword list is a guess, not a maintained asset.
    Fix
    Build the vocabulary with marketing, procurement, and IT; version it.
    Prevention
    Quarterly vocabulary review with named owners.

    7. Static allowlists

    Symptom
    False positives repeat for weeks, then someone widens the rule too far.
    Root cause
    Allowlists never expire and never re-verify.
    Fix
    Add review dates to allowlist entries and re-check them.
    Prevention
    Allowlist report shows entries older than 6 months.

    8. No owner for the watchlist

    Symptom
    CT queue items age out unread; vocabulary rots.
    Root cause
    The pipeline has no named maintainer.
    Fix
    Assign an owner with a monthly health check and a backup.
    Prevention
    Dashboard shows queue age and feed freshness.

    9. Never validating the rules

    Symptom
    Rules pass review but have never fired on real or test data.
    Root cause
    No purple-team test of a certificate-staging scenario.
    Fix
    Rehearse one staging scenario quarterly (see section 7).
    Prevention
    Track detection coverage against the T1608 family.

    10. Missing wildcard abuse

    Symptom
    One name is blocked; subdomains of the same host keep working.
    Root cause
    Rules treat a wildcard certificate like a single name.
    Fix
    Expand wildcards and watch the parent, not one leaf.
    Prevention
    CT rules flag wildcard issuances on young domains.

    11. Assuming certificates only matter for phishing

    Symptom
    Rules watch mail only; encrypted C2 domains go unnoticed.
    Root cause
    The use case was scoped to one delivery channel.
    Fix
    Watch TLS metadata for C2 too (TH-03 rule), not just mail links.
    Prevention
    Review scope against ATT&CK: staging supports many tactics.

    12. No historical hunt after a hit

    Symptom
    Blocking today, but nobody checks who touched it last month.
    Root cause
    The runbook stops at the block action.
    Fix
    Add "search 90 days of proxy/DNS/mail for the name family" to the runbook.
    Prevention
    Metrics track hunts run per confirmed indicator.

    Daily habits

    • Review the CT watchlist queue and domain-age context.
    • Check proxy hits to flagged lookalike names.
    • Confirm the CT feed and lookups still refresh.

    Weekly habits

    • Walk one live candidate through the triage flow.
    • Review alert volume and exclusion drift.
    • Share two indicators with your ISAC or peers.

    Monthly habits

    • Replay the test issuance set against all five rules.
    • Review the brand and supplier vocabulary with owners.
    • Report issuance-to-block time to leadership.

    Cheat Sheet and Quick Reference

    Everything urgent from this page on one screen: the facts, the highest-value detections, the response checklist, and the official links.

    Key facts

    Technique
    T1608.003 — Install Digital Certificate (Resource Development, PRE, sub-technique of T1608)
    One-line meaning
    Attacker installs TLS certificates on their own servers so browsers show the trusted padlock
    Not to confuse with
    T1588.003 Code Signing Certificates (signs files, not websites)
    Seen in
    Nobelium/APT29 2021 campaigns (Let's Encrypt on staging and C2, Microsoft reporting); commodity phishing-kit ecosystems since 2021
    Victim logs during staging
    None - detection is outside-in, driven by the public CT log
    Fastest win
    CT watchlist on brand and supplier keywords + phishing-resistant MFA

    Top detections (from 5.5)

    • Fresh free-CA certificate for a lookalike domain on a cheap TLD (CT stream, Medium)
    • Mail link to a domain younger than 7 days (mail gateway, High)
    • Internal TLS connection to a host with a certificate younger than 7 days (proxy TLS, High)
    • Resolver queries matching lookalike TLD patterns for your brand vocabulary (DNS, Medium)
    • ACME client executed on your own web servers outside the change window (Linux process, Medium)

    Response checklist when a staged certificate is confirmed

    • Block the domain, its IP, and every SAN family name at DNS, proxy, and mail.
    • Search 90 days of proxy, DNS, and mail logs for earlier contact with the name family.
    • For each contact: verify the user, check the endpoint for downloads and typed credentials.
    • Rotate credentials and revoke sessions for anyone who reached a login page on the lookalike.
    • Send a take-down request to the registrar and hoster; add the name family to brand monitoring.
    • Share the indicators with your ISAC and note the campaign vocabulary for future watchlist hits.
    • Log the case with time-from-issuance-to-block so the metric improves next time.
