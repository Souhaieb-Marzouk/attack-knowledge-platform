MITRE ATT&CK - Exfiltration - Sub-technique

T1011.001 Exfiltration Over Bluetooth

T1011.001 covers stolen data that leaves a device over a Bluetooth radio link instead of the command and control (C2) channel. C2 is the connection that attacker software uses to talk to its operator. Attackers pick this path when they already control the device and can stand within Bluetooth range of a second device, because the short-range link usually has fewer defenses. This guide was reviewed against MITRE ATT&CK v20 in October 2026.

    Overview

    This page explains how attackers move stolen data out over a short-range radio link. It is written for beginners in security operations. Every term is explained at first use.

    Exfiltration means moving stolen data out of a network or a device. MITRE ATT&CK technique T1011.001 covers one specific path: the data leaves over Bluetooth rather than over the command and control (C2) channel. Bluetooth is the short-range wireless technology that connects phones, headsets, and laptops over distances of a few meters to tens of meters. It is a sub-technique of T1011, Exfiltration Over Other Network Medium.

    Attackers choose this path when they have sufficient access and proximity: they control a device that holds the data, and a second Bluetooth device sits close enough to receive it. The short-range link often has weaker defenses than the main connection, because Bluetooth traffic is not routed through the enterprise network. Firewalls, proxies, and data loss prevention (DLP) tools never see it, so the usual network evidence does not exist.

    One correction to the record: this sub-technique is about the Bluetooth radio path. Splitting a transfer into small chunks to stay under a size limit is a different behavior. MITRE ATT&CK calls that separate technique T1030, Data Transfer Size Limits. Do not mix the two, even though both can look like "data leaving quietly".

    In the attack chain this step comes late. Collection gathers the data, staging parks it in one folder or archive, and exfiltration moves it out. Catching this step early is the last chance to stop the loss, so the endpoint signals in this guide matter.

    Animated Simulation

    The animation shows a compromised office laptop. The attacker stages an archive on it, finds two Bluetooth devices nearby, pairs, and pushes the files out over OBEX while the corporate network logs stay empty. Press Play to watch the flow, or use Next to move step by step.

    Written step-by-step story
    1. Foothold. The attacker controls the victim laptop through a phished session and plans a quiet exit, because the C2 channel is watched. Local rights are enough to run the built-in Bluetooth tools. SOC view: EDR records the office document spawning a script, but no network transfer has happened yet.
    2. Stage the data. The attacker packs finance files into one 1.8 GB archive in a temp folder. Staging keeps the transfer short and tidy. SOC view: file telemetry shows a large after-hours archive write, which is the first half of the story.
    3. Find devices. A Bluetooth inquiry lists radios in range, and a phone on the next desk plus an attacker laptop answer. SOC view: the Bluetooth stack logs an inquiry started by a non-interactive session, not by a user opening settings.
    4. Pair. The laptop pairs with the attacker laptop, which creates a trusted link. The attacker controls both ends, so confirmation steps finish unnoticed. SOC view: a new pairing event appears on a host with no approved pairing list.
    5. Push over OBEX. The archive leaves in staggered pieces over OBEX, the Bluetooth file-push profile, using the built-in fsquirt tool on Windows. Nothing crosses the corporate firewall or proxy. SOC view: fsquirt runs under the script lineage while egress logs stay silent.
    6. Wipe traces. The attacker removes the pairing and deletes the temp folder. The radio link leaves no corporate records to clean. SOC view: the config change lands minutes after the transfer, which is a timing signal by itself.
    7. SOC correlates. The analyst joins EDR process lineage with Bluetooth device events: inquiry, pairing, transfer, clean-up. The egress silence changes meaning once the radio story appears. SOC view: the case opens on a correlation rule, not on a network alert.
    8. Isolate and hunt. The team isolates the laptop, disables Bluetooth for the office through a Group Policy Object, and starts a peer hunt with the same Sigma rules. SOC view: the incident closes with a policy change that removes the path for everyone else.

    Red Team Perspective

    This section describes how the technique works so defenders can recognize it. It is educational only. The command example is labeled LAB-ONLY and must never be used on systems you do not own.

    When attackers use it

    Attackers pick this technique when the main channel is defended well and they can get close to the device. Open offices are friendly to it, because desks sit a few meters apart. The corporate Bluetooth stack then becomes a second, quieter door.

    It also suits places where the wired network is locked down. A lab or a finance floor can allow no uploads at all, while a laptop still carries a working radio. Insiders use it too, because they need no extra hardware beyond a phone.

    Prerequisites

    The attacker needs three things: control of a device that holds the data, a second Bluetooth device within radio range that the attacker controls, and time, because Bluetooth is slow compared with any office network.

    Helpful extras are a radio that policy left enabled, local admin rights that allow new hardware, and a user who accepts a pairing prompt without reading it. On macOS, blueutil, a macOS command line tool for the Bluetooth radio, and networksetup, its tool for network services, drive the stack; blueutil is often installed through the Homebrew package manager. On Linux, the command line tools hcitool, bluetoothctl, and rfcomm are usually already present.

    How it works

    1. Pick the device and the moment. The attacker wants a host that holds the data, a radio that is on, and hours when nobody watches the desk.
    2. Discover nearby devices. A Bluetooth inquiry, a discovery scan, lists the phones, laptops, and headsets within range and their addresses.
    3. Pair with a device the attacker controls. Pairing creates a trusted link. A stale pairing from a departed employee works without any prompt at all.
    4. Stage the data. Files are copied into one archive so the slow radio link carries a tidy set of objects instead of many small files.
    5. Push the archive over OBEX. OBEX stands for Object Exchange, and it is the Bluetooth file-push profile. Windows ships the fsquirt tool for it. A Bluetooth PAN, a personal area network link that carries IP traffic, is the second option when raw file push does not fit.
    6. Wipe traces. The attacker removes the pairing, clears transfer history, and deletes the temp folder. The radio path leaves no corporate records to clean.

    Variation: push to a phone

    The compromised laptop pushes files to a phone the attacker holds or has left nearby. OBEX file push makes this a few clicks or one command. The phone then walks out of the building in a pocket.

    Variation: pull from a nearby PC

    A second laptop in the next desk pairs with the victim and receives the archive. The attacker collects it later. This suits bigger archives than a phone, because laptop radios and storage handle long transfers better.

    Variation: Bluetooth PAN tethering

    The victim laptop joins a PAN hosted by a phone and routes traffic through the phone's mobile connection. That turns the technique into a full internet channel that skips the corporate egress point.

    Attackers make mistakes, and each mistake is a detection opportunity. Device discovery leaves inquiry records in the Bluetooth stack. Pairing creates events, on-screen prompts, and stored device objects. The built-in transfer tools run as visible processes that EDR can join to their parent lineage. Transfers are slow, so a large archive needs a long window and often more than one session. And a stale pairing that skips prompts also skips the cover of a normal user story.

    Blue Team / SOC Perspective

    The blue team defends the company. The SOC, or Security Operations Center, is the group that watches alerts. This section lists what the attack leaves behind, where to look, and how to triage.

    What it leaves behind

    Bluetooth tool execution

    Linux logs hcitool, bluetoothctl, or rfcomm runs. macOS logs blueutil and networksetup. Windows logs fsquirt.exe and bthpropscpl.exe, the file transfer and settings tools. The parent process matters more than the tool itself.

    Pairing and device events

    Pairing creates Bluetooth stack events and stored device objects. On Windows, a new radio or USB dongle also creates a Kernel-PnP device install event, event 4101, in the configuration log.

    Transfer traces

    OBEX pushes leave a received-files folder on the far device and transfer history in the stacks at both ends. The victim side keeps records of objects sent, even after the attacker clears the temp folder.

    Radio state changes

    Power toggles, discoverable-mode changes, and PAN interfaces that appear and vanish are all logged by the stacks. On Linux, rfkill shows the radio state. Egress silence plus radio activity is the pattern to remember.

    Where to look

    Log sourceWhat to look forWhy it helps
    EDR process and peripheral logsBluetooth tools run by non-interactive sessions; peripheral connect and pair events on sensitive hostsEDR is the only source that joins the process lineage to the device activity in one place.

    Why it matters

    Exfiltration is often the last step of an attack. If you see it, an earlier stage already succeeded, so an incident starts even when the malware is gone. Confirming what left helps legal and data owners decide on notifications.

    Catching T1011.001 also fixes a blind spot you can measure. A path that skips the egress point works for any attacker who can reach the desk. Closing it with the M1042 and M1028 mitigations raises the floor for the whole site.

    Triage flow: alert to closure

    1. Receive the alert: a Bluetooth tool run by a non-interactive process, a new pairing, or a new radio install.
    2. Confirm the host: owner, data level, and whether the user was active at that time.
    3. Pull process lineage for the Bluetooth tool: who started it, and what started that parent.
    4. Pull Bluetooth device events for the window: inquiry, pairing, connect, transfer, and removal times.
    5. Check for staged archives and for received-file folders on host and peripheral pairs.
    6. Decide containment: isolate the host, block or remove the pairing, and disable the radio by policy.
    7. Hunt siblings with the same rule: other hosts with staging plus Bluetooth activity.
    8. Close with a report, then tune the rules and clean up stale pairings fleet-wide.

    5.2 Threat Intelligence

    Threat intelligence is information about how attackers work, shared by other defenders. For this sub-technique the most reliable source is the official ATT&CK page itself, which documents one procedure example and one detection strategy.

    MITRE ATT&CK plus STIX/TAXII

    ATT&CK gives you the behavior model, and STIX/TAXII is a standard format for sharing it as data. Subscribe to the enterprise data and diff each release. Watch the T1011.001 page for new procedure examples and detection analytics.

    Vendor threat reports

    Endpoint vendors publish research on Bluetooth abuse, from legacy worms to modern tradecraft. Translate each report into one question your endpoint logs could answer.

    CISA and FBI advisories

    Government advisories describe observed tradecraft in plain language. They are free and reliable for pattern learning, including insider risk and wireless misuse.

    Open source intelligence (OSINT)

    Security research documents how OBEX push, pairing abuse, and Bluetooth reconnaissance work. Use it to test your sensors in a lab, never on live networks.

    Commercial feeds

    Paid feeds add context such as Bluetooth tool fingerprints and campaign tooling. Judge them by whether they change your detections, not by volume.

    ISACs

    An ISAC, or Information Sharing and Analysis Center, shares patterns between companies in one sector. Ask peers which Bluetooth policies and alerts actually work.

    Internal telemetry

    Your own history is the best intel you own. Keep a register of Bluetooth tool runs, pairings, and exceptions. Repeat patterns in your own data deserve rules.

    1. Turn each documented pattern into one detection hypothesis you can answer with logs you already collect.

    5.4 Logs and Patterns

    Each threat below lists its log sources, the fields that matter, and the difference between normal and suspicious behavior. Full event examples follow the threats that need them.

    Threat 1 - Staged-file Bluetooth push from a compromised laptop High

    Log sources
    Sysmon event 1 (process creation) for fsquirt.exe and bthpropscpl.exe; EDR process lineage; file telemetry for archive writes.
    Key fields
    Image, CommandLine, ParentImage, User, Computer, EventCode, and the file path plus size from file telemetry.
    Normal
    Users sending their own photos or files to a personal phone, with explorer.exe as the parent and during working hours.
    Suspicious
    fsquirt.exe started by a script, a shell, or an office document lineage, minutes after a large archive was written.
    Detection logic
    Alert on the Bluetooth transfer tools when their parent is not the shell a user would open them from.

    Field notes: Image pins the built-in transfer wizard; CommandLine -send shows a push rather than a receive; ParentImage of cmd.exe under a hidden PowerShell script is the lineage signal; CurrentDirectory sits inside the temp staging folder. Sysmon field names (Image, CommandLine, ParentImage, User, Hashes) are stable across the Splunk Add-on for Sysmon and most EDR normalizers.

    Threat 2 - Suspicious process using the Bluetooth stack after staging High

    Log sources
    Linux auditd (syscall execve plus EXECVE records) forwarded as JSON by a log shipper; bluetoothd messages; EDR process events.
    Key fields
    exe, comm, auid, euid, pid, ppid, argc, argv, host, success, and the session type behind auid.
    Normal
    Admins run bluetoothctl interactively to pair a headset; desktop sessions call the stack during login.
    Suspicious
    hcitool or rfcomm run with auid unset (a background session), or bluetoothctl started by a service or a web-server user after a burst of file reads.
    Detection logic
    Alert on the Linux Bluetooth command line tools when the session is non-interactive or the caller is a service account.

    Field notes: the raw auditd line is type=EXECVE msg=audit(1760489021.552:8841) argc=2 a0="hcitool" a1="scan"; the shipper joins it with the SYSCALL record. auid: unset (numeric 4294967295) means the caller has no login session, which is the non-interactive flag from official analytic AN1532. exe is the absolute path that Sigma matches with endswith; process.parent.name shows a python3 launcher, not an admin shell. Field names shown are the Elastic-style auditd integration; Splunk users typically see exe, comm, auid, euid after field extraction.

    Threat 3 - Rogue pairing to a nearby device as a pivot Medium

    Log sources
    Microsoft-Windows-Kernel-PnP/Configuration event 4101 (device installed); setupapi.dev.log; EDR peripheral events; Bluetooth stack pairing events.
    Key fields
    EventID, DeviceInstanceId, DeviceDescription, ClassId, Computer, and pairing partner name plus MAC from stack events.
    Normal
    Approved docks and laptops re-enumerate their built-in radios after driver updates; imaging jobs install known hardware.
    Suspicious
    A Bluetooth radio appears on a desktop that never had one, or a new pairing lands on a host outside the approved list, especially after hours.
    Detection logic
    Alert on new Bluetooth adapter installs on hosts that should not gain a radio, and on pairings outside the approved list.

    Field notes: the ClassGuid above is the Windows Bluetooth class; DeviceInstanceId exposes the USB vendor and product IDs, which you can check against an allowlist; ClassName: Bluetooth is the field the Sigma rule matches on via the description. Kernel-PnP EventData fields are extracted automatically only from XML event input, so classic WinEventLog input needs a field extraction.

    Threat 4 - Bluetooth beaconing and device discovery abuse (Flame-style) Medium

    Log sources
    EDR Bluetooth or peripheral telemetry with a vendor field contract; bluetoothd and BTHPORT stack logs as a fallback.
    Key fields
    Contract fields: event_type, process_name, host, user, device_count, local time. Stack fallback: inquiry start and stop, device answers, advertising reports.
    Normal
    The stack scans briefly when a user opens Bluetooth settings or reconnects a headset; IT radio surveys run from known tooling on known hosts.
    Suspicious
    Repeated inquiry or advertising by an unusual process, especially a service or a process with no window, in the pattern of the Flame BeetleJuice module.
    Detection logic
    Alert on Bluetooth inquiry or beacon actions reported by EDR when the calling process is not an approved management tool.

    Field notes: this is a vendor-specific source, so the rule in 5.5 defines an explicit field contract: event_type, process_name, host, user, device_count. Build one mapping table from your product's raw fields (shown under vendor_raw) to the contract names, and the rule works unchanged. The unusual caller, a temp-folder binary doing an inquiry, is the Flame BeetleJuice-style pattern.

    Threat 5 - macOS blueutil or networksetup toggling by a non-GUI process Medium

    Log sources
    macOS process telemetry (EDR, osquery, or the unified log) for blueutil and networksetup; unified log bluetoothd messages.
    Key fields
    process or Image path, CommandLine or args, user, host, parent process, and the file-read volume around the event.
    Normal
    Admin scripts manage Bluetooth across a fleet; a user toggles Bluetooth for a headset from the terminal once.
    Suspicious
    blueutil -p 1 or networksetup toggling Bluetooth by a process with no GUI session, right after large file reads (official AN1533).
    Detection logic
    Alert on blueutil power or connect commands and networksetup Bluetooth service toggles, and check the caller for a GUI session.

    Field notes: the top half is the unified-log shape (process, senderImagePath, eventMessage); the edr block is enrichment from process telemetry. The signal is the pair session_type: ssh plus parent: python3, a non-GUI caller, next to 612 MB of recent file reads. blueutil is not a macOS built-in, so its presence under /opt/homebrew/bin is itself worth an inventory check. The Sigma rule in 5.5 uses process_creation fields (Image, CommandLine, User, ParentImage); map them once from your EDR.

    Threat 6 - Covert Bluetooth audio or headset channel Low

    Log sources
    EDR peripheral telemetry with the same vendor contract as threat 4 (event_type BluetoothAudioConnected or HandsfreeConnected); unified log or BTHENUM stack events as a fallback.
    Key fields
    Contract fields: event_type, device_name, device_class, host, user, local time, plus session duration.
    Normal
    Headsets, speakers, and conference gear connect all day; mice and keyboards with audio profiles reconnect after docking.
    Suspicious
    An audio or hands-free session with no matching user activity, or a long session on a host the user left, especially while a background process runs.
    Detection logic
    Alert on Bluetooth audio sessions that no interactive user activity explains, and check what ran on the host during the session.

    This threat has no realistic JSON example here because the evidence is the same EDR peripheral contract as threat 4, only with audio event types. Reuse that mapping table and change the event_type list. No network example is possible at all: the hands-free audio link is not IP traffic, so it never reaches a network sensor.

    5.5 Sigma Rules and Splunk SPL

    Sigma is an open rule format for log detections, and Splunk SPL is the search language of the Splunk platform. Each threat gets one Sigma rule and one SPL query with the same logic. Adapt indexes, sourcetypes, and field names to your own pipeline before use.

    One honest limit first: Bluetooth traffic (RFCOMM, L2CAP, OBEX, audio) does not cross an IP network, so Zeek or firewall flow rules cannot see it. That is why all six rules in this section use host telemetry, and each mapping note says so. Two sources are vendor specific: the EDR peripheral telemetry in threats 4 and 6, and macOS process fields in threat 5. Their rules define a clear field contract, for example event_type, process_name, host, and user. Build a small mapping table from your product's real fields to these names, and the rules work unchanged.

    Threat 1 - Staged-file Bluetooth push from a compromised laptop Severity: high

    The rule hunts the built-in Windows Bluetooth transfer tools, fsquirt.exe and bthpropscpl.exe. Normal users start them from the settings UI or the file explorer, so an unexpected parent is the signal.

    Mapping: Sigma matches Sysmon event 1 process creations where the image ends in fsquirt.exe or bthpropscpl.exe and the parent is not explorer.exe; the SPL applies the same filter and groups by the same fields, with no threshold beyond the filter. Field assumptions: the SPL expects Sysmon data indexed as index=edr sourcetype=sysmon with Splunk Add-on for Sysmon naming (EventCode, Image, ParentImage, CommandLine, User, Computer). This is a host rule by design: OBEX rides the Bluetooth radio link, so no network source can see it.

    False positives: users pushing their own photos to a phone, IT repair sessions, and imaging jobs that touch the wizard during setup.

    Tuning: join the alert with file telemetry for a large archive write in the previous 30 minutes on the same host. Scope the explorer exception tighter by also allowing known pairing UIs, and raise the rule to critical if the parent is an office document lineage.

    Threat 2 - Suspicious process using the Bluetooth stack after staging Severity: high

    The rule hunts the Linux Bluetooth command line tools, hcitool, bluetoothctl, and rfcomm, the utilities that initialize a Bluetooth connection. Interactive headset pairing is normal; a background session calling them is not.

    Mapping: Sigma requires a Bluetooth tool image in a session whose auid is unset; the SPL requires the same tool names via exe or comm plus the same unset-auid condition (kept both as the string and the numeric 4294967295 form), grouped by host and effective user. Field assumptions: the SPL expects auditd records indexed as index=nix sourcetype=linux:auditd with fields exe, comm, auid, euid, and parent extracted; if your shipper nests them, map before use. Host rule again: the Bluetooth link never reaches a network sensor.

    False positives: fleet management agents scripting radio state, provisioning tools probing adapters at boot, and vendor agents onboarding devices.

    Tuning: per official AN1532, join with file-read telemetry by the same euid in the previous 15 minutes and alert on the overlap. If you must allow a management agent, allowlist its exact exe path, not its name, and keep the auid condition.

    Threat 3 - Rogue pairing to a nearby device as a pivot Severity: medium

    The rule watches the Windows Kernel-PnP configuration log for a Bluetooth radio install, event 4101. A small USB dongle adds a radio to a host that never had one, which is the setup step for a pairing pivot.

    Mapping: Sigma requires event 4101 with a Bluetooth device description; the SPL applies the same two filters and groups by host and description, with no extra threshold. Field assumptions: the SPL expects XML Windows event input as sourcetype="XmlWinEventLog:Microsoft-Windows-Kernel-PnP/Configuration" with EventData fields (DeviceInstanceId, DeviceDescription, ClassName) auto-extracted; classic WinEventLog input needs a manual extraction first. Host rule: the pairing and the dongle live below the network layer, so flow tools see nothing.

    False positives: approved hardware re-enumerating after driver updates, imaging jobs, and docks that expose a paired radio.

    Tuning: keep an allowlist of approved DeviceInstanceId vendor and product pairs, and alert only on first-seen pairs per host group. On servers and lab assets, where the baseline should be zero new radios, raise the rule to high. If a paired pivot device later bridges traffic onto the corporate network, ordinary flow logs will show generic IP from that host, which is a follow-up search, not this rule.

    Threat 4 - Bluetooth beaconing and device discovery abuse (Flame-style) Severity: medium

    The rule uses EDR peripheral telemetry with a stated field contract, because inquiry and beacon actions are not standard Windows events. The Flame BeetleJuice module made this pattern famous: transmitting encoded data over Bluetooth, acting as a beacon, and identifying nearby devices.

    Mapping: Sigma requires one of the three discovery or beacon event types and excludes two known tools; the SPL applies the same event_type list and the same exclusion, then aggregates the same way (count and devices_seen per host, user, and process). Field assumptions: the SPL expects the contract fields (event_type, process_name, host, user, device_count) indexed as index=edr sourcetype=edr:peripheral; create an eval or lookup that maps your vendor's raw fields to the contract once, per the definition line. Host rule: inquiry and advertising stay on the radio link, invisible to network taps.

    False positives: IT radio surveys, headset and mouse reconnect scans, and provisioning agents during device rollouts.

    Tuning: alert only when the caller is a service, a process in a temp path, or a user with no active console session, and require at least three inquiry bursts in one hour before paging. Add your legitimate radio survey tools to the exclusion list by exact path.

    Threat 5 - macOS blueutil or networksetup toggling by a non-GUI process Severity: medium

    The rule watches blueutil and networksetup, the macOS command line tools, for Bluetooth power toggles, connect commands, and service changes. The official AN1533 analytic flags exactly these commands when a non-GUI process runs them after large file reads.

    Mapping: Sigma fires on blueutil with a power or connect argument, or networksetup with -setnetworkserviceenabled Bluetooth; the eval in the SPL encodes exactly those two branches before the where clause, so both engines accept the same events and group by the same keys. Field assumptions: the SPL expects macOS process telemetry indexed as index=edr sourcetype=macos:process with fields process (full path), CommandLine, user, host, and ParentImage; rename to your EDR's names once in a macro. Host rule: the toggled radio talks to nearby devices only.

    False positives: fleet admin scripts, users fixing their own headset from the terminal, and MDM agents enforcing radio policy.

    Tuning: per official AN1533, join with file telemetry for large reads in the previous 15 minutes and treat the overlap as the real signal. Check the parent for a GUI session; a terminal run by the logged-in user is a ticket, while an SSH or daemon parent is a case.

    Threat 6 - Covert Bluetooth audio or headset channel Severity: low

    The rule reuses the EDR peripheral contract from threat 4 with audio event types. A compromised host can encode data into a headset or hands-free link, and no network sensor will ever see it.

    Mapping: Sigma selects the two audio event types; the SPL selects the same event types and adds the one aggregation the rule's description implies, a long session on the host, using the same grouping keys. Field assumptions: the SPL expects the contract fields indexed as index=edr sourcetype=edr:peripheral, with session_ms in milliseconds; the threshold 3600000 means one hour of total audio session time per host and user in the search window. Host rule by necessity: hands-free audio rides eSCO links inside the Bluetooth band, so no zeek or flow rule can be honest here, and that is why the host source is used.

    False positives: headsets and speakers for normal calls, conference room gear on wake, and mice or keyboards with audio profiles reconnecting after docking.

    Tuning: keep level low and page only when the audio session overlaps a non-interactive process burst or occurs on a host whose user is not logged in. Exclude conference room asset groups, and review the device_class allowlist quarterly.

    Real-World Case Study

    This is a composite case study built from common public incident patterns. Company names are fictional.

    A regional logistics company, Veratex Freight, ran a finance office in an open-plan building. A phished workstation held customer shipment records. The attacker staged them into archives and pushed each one over Bluetooth to a phone in the next desk, night after night. The corporate network logs never showed a byte. EDR process lineage plus Bluetooth device events ended the case within two days of the first push.

    1. Day 1 - 21:36

      Foothold

      A finance user opens a macro workbook from a phishing mail. EDR later shows the document spawning a hidden PowerShell script. No network rule fires, because the C2 traffic blends into normal HTTPS.

    2. Day 1 - 22:14

      Discovery

      The script runs a Bluetooth inquiry and lists a phone left discoverable on the next desk. The Bluetooth stack logs the inquiry, but that source is not wired into the SIEM yet, so nobody sees it.

    3. Day 2 - 23:02

      First push

      After a burst of file copies into a temp archive, the attacker launches fsquirt.exe from the script lineage and pushes 60 MB over OBEX to the phone. The phone owner accepts one transfer prompt without reading it. Egress logs stay empty.

    4. Day 3 - 23:11

      Second push

      The pattern repeats with another 60 MB archive. The pairing is now trusted, so no prompt appears. File telemetry records the archive writes; no alert exists for them either.

    5. Day 4 - 02:40

      Detection point

      A new correlation rule, deployed that week for a different reason, joins EDR process lineage with Bluetooth device events. It flags fsquirt.exe under a script parent plus an inquiry and a pairing on the same host. The case opens.

    6. Day 4 - 08:20

      Triage

      The analyst confirms the lineage, pulls the Bluetooth event timeline, and finds two transfers totaling about 120 MB. The temp archives are still on disk, which makes scoping easy.

    7. Day 4 - 09:05

      Containment

      The host is isolated remotely. Bluetooth is disabled for the office through a Group Policy Object. The phone owner hands in the device, and the transfer history on it is preserved as evidence.

    8. Day 4 - 14:30

      Eradication

      Investigators remove the script, the scheduled task that kept it alive, and the staged archives. The stale pairing is revoked. A hunt for the same fsquirt and pairing pattern across the fleet finds no other host.

    9. Day 5 - 11:00

      Recovery

      The workstation is rebuilt from a known-good image. Bluetooth returns for approved users only, with a documented exception process. The correlation rule moves from monitoring to paging.

    10. Day 6 - 16:00

      Review

      The review records the win and the gaps. Detection took two nights of pushes, and the Bluetooth logs had sat uncollected for months. Both gaps get fixes with owners and dates.

    Detection point

    The true detection was the correlation of EDR process lineage with Bluetooth device events. Neither source alone told a full story, because the script looked routine and the stack logs were unnamed. The 120 MB estimate came from file telemetry on the archives, not from any network tool. After the incident, the rule paged on the first push instead of the third.

    Containment

    The team isolated the workstation within minutes of triage. They disabled Bluetooth for the whole office OU through a Group Policy Object, which implements mitigation M1042. The phone was handed in voluntarily, and its transfer history was preserved before any wiping. The pairing was revoked at both ends.

    Eradication

    Investigators removed the script, its scheduled task, and the staged archives from the host. They revoked the stale pairing and checked MDM records for pairings that survived past offboarding. The fleet hunt for fsquirt and pairing patterns found no second host, so the blast radius stayed at one machine.

    Recovery

    The workstation was rebuilt from a known-good image and returned to service the next day. Bluetooth came back for approved users only, with a written exception process. The correlation rule was raised to paging priority, and the Bluetooth stack logs were wired into the SIEM permanently.

    Impact and consequences

    About 120 MB of customer shipment records left the company, which triggered a data protection assessment. The assessment found no obligation to notify regulators, but customers in the affected cohort were offered credit monitoring. The incident closed with no downtime, which is the quiet cost of this technique.

    Team response and communication

    SOC, endpoint IT, and the data protection officer shared one incident channel. Legal guided what could be written down and when. The phone owner was treated as a witness, not a suspect, which kept cooperation high. Daily short updates stopped office rumors from filling the silence.

    Lessons learned

    Bluetooth is a real exfiltration path in open offices, and it leaves no network evidence, so endpoint and stack logs must lead. Stale pairings are free infrastructure for attackers, so pairings need an owner and an expiry. Disabling unused radios by policy is cheaper than investigating them. Finally, the first push should page, not the third, which is what the tuned correlation rule now does.

    7

    Mitigation and Defense

    No single control stops this technique. The strongest defense layers radio policy, endpoint coverage, and pairing hygiene, because the traffic itself never crosses a network control point. The cards below group the actions by team.

    Policy and people

    Write a clear rule about Bluetooth on corporate devices: enabled by exception, disabled by default where the data is sensitive. Explain the reason in training, not only the rule. Give managers a fast way to approve a headset and to report an unexpected pairing prompt.

    Identity and endpoint

    Disable Bluetooth by local security settings or Group Policy on hosts that do not need it, which is official mitigation M1042. Use device control to prevent the creation of new network adapters, including USB Bluetooth dongles, which is official mitigation M1028. Remove local admin rights so a dongle cannot install its driver silently.

    Network and egress

    Treat the radio as a second egress point in your path map. Block or warn on Bluetooth PAN interfaces on managed laptops, because they carry IP traffic you cannot inspect. Keep egress baselines anyway, so the egress silence that this technique produces stays visible.

    Cloud and logging

    Send EDR process and peripheral events, Kernel-PnP installs, Linux auditd, and macOS unified logs to one SIEM. SIEM stands for Security Information and Event Management, the system that stores and searches security logs. Normalize the Bluetooth fields with one mapping table so correlation works across vendors.

    Monitoring and response

    Run the six detections from section 5.5 in monitoring, and build one triage runbook that joins process lineage with device events. Page on the first staging-plus-Bluetooth overlap. Practice the runbook twice a year with a lab push, so the first real case is not the first rehearsal.

    Backup and resilience

    Backups do not stop exfiltration, but they bound the harm. Keep offline copies of the most sensitive datasets and test restores. Keep a data inventory current, so when an incident happens you can say quickly what could have left and over which window.

    Home and small office

    Small sites have the same paths with fewer guards. Turn Bluetooth off on machines that only need it for charging. Remove pairings you no longer use, especially on shared computers. Update the operating system, because pairing and OBEX bugs get patched. If a device asks to pair and you did not start it, read the prompt before clicking, and unpair anything you do not recognize.

    Common Mistakes and Best Practices

    Each mistake below describes a real failure pattern seen in detection programs. The fix is usually small once you see the root cause. The habit cards at the end keep the improvements alive.

    1) Treating Bluetooth as office comfort, not an egress path

    Symptom
    Radio policy lives in a comfort checklist and never in the threat model.
    Root cause
    The team assumed all data leaves through the network doorway.
    Fix
    Add the radio to the path map and assign it an owner and detections.
    Prevention
    Review the path map each quarter, including short-range wireless paths.

    2) Stale pairings left on shared machines

    Symptom
    A departed employee's phone is still paired to a finance workstation.
    Root cause
    Offboarding removed accounts and badges, but never checked device pairings.
    Fix
    Sweep and revoke stale pairings, then add pairings to the offboarding checklist.
    Prevention
    Expire pairings automatically and audit them quarterly with MDM data.

    3) Trusting egress monitoring to catch everything

    Symptom
    Dashboards look clean while archives leave over the radio link.
    Root cause
    The monitoring design never asked where else data could physically go.
    Fix
    Add host process, stack, and device sources as first-class evidence.
    Prevention
    Write the "network is blind here" statement into the detection plan.

    4) Radios left enabled on servers and labs

    Symptom
    Servers and lab hosts sit with Bluetooth on and no reason for it.
    Root cause
    Default images were never reviewed against mitigation M1042.
    Fix
    Disable Bluetooth on those asset classes and verify with compliance scans.
    Prevention
    Build images with the radio off and an exception process to turn it on.

    5) Watching pairings but not new radios

    Symptom
    Pairing alerts exist, while a USB dongle install passes unnoticed.
    Root cause
    Nobody connected Kernel-PnP event 4101 to the exfiltration path.
    Fix
    Alert on first-seen Bluetooth adapter installs per host group.
    Prevention
    Enforce M1028 by blocking new network adapters by default.

    6) Collecting Bluetooth logs but normalizing nothing

    Symptom
    Stack events arrive with vendor names, so no correlation rule can join them.
    Root cause
    Collection was a checkbox, and field mapping was never designed.
    Fix
    Adopt the field contract from 5.5 and map vendor fields once.
    Prevention
    Test correlation rules with synthetic events after every onboard.

    7) Assuming macOS has no relevant command line

    Symptom
    No rule exists for blueutil or networksetup on the Mac fleet.
    Root cause
    The team only knew Windows Bluetooth tools.
    Fix
    Deploy the threat 5 rule and inventory which hosts carry blueutil.
    Prevention
    Map official analytics (AN1533) to your platforms at release time.

    8) Ignoring non-interactive sessions

    Symptom
    Rules match admin users only, so a service account slips through.
    Root cause
    The design assumed a person always drives the Bluetooth stack.
    Fix
    Alert on tool runs with unset auid or service-style parents.
    Prevention
    Baseline interactive use and treat non-interactive use as a signal.

    9) Tuning peripheral alerts into silence

    Symptom
    Every Bluetooth alert is closed as "headset noise", including the real one.
    Root cause
    The rule lacked scoping, so the fix was a mute instead of a tune.
    Fix
    Scope by asset group, session type, and overlap with process activity.
    Prevention
    Tune, never mute; document every alert decision.

    10) Skipping the peer hunt after one catch

    Symptom
    The incident closes on one host, and the same pattern fires elsewhere a month later.
    Root cause
    Nobody reran the detection fleet-wide after containment.
    Fix
    Hunt siblings with the same rules as part of closure.
    Prevention
    Make the peer hunt a required step in the response checklist.

    Daily habit

    Review Bluetooth tool alerts and new pairing events once per shift. Check that the staging-plus-Bluetooth correlation rule still fires on the lab test host. Read the last five closed alerts and ask what made them quiet.

    Weekly habit

    Confirm that EDR, Kernel-PnP, auditd, and unified log feeds all arrived during the week. Review pairing exceptions and remove the expired ones. Spot-check one host for stale pairings and unexpected radios.

    Monthly habit

    Audit pairings fleet-wide against MDM records. Test one alert path end to end, from host event to ticket. Update the approved radio and adapter list from real purchases, and re-run the lab exercise from section 3.
