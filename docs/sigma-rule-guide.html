Why Sigma, and why test it?

Sigma is a vendor-neutral way to write a detection once and convert it to many SIEM query languages. A rule is a small YAML document: it says which log source to read, which fields to match, and how the matches combine.

A rule that passes a YAML parser is not a working detection. It can still be wrong in three expensive ways:

  • It never matches a real event because the field name, case, path or logsource is wrong.
  • It matches everything because a condition is too broad or a filter is missing.
  • It cannot convert because it uses a backend feature, tag or condition the converter does not support.

That is why this project uses three layers for every rule: schema (sigma check), conversion (Splunk), and log tests (positive and negative JSONL). The four deliberately broken rules in tests/sigma/negative/ prove the gate rejects bad input.

The rule of the project: a rule is not “done” when the YAML looks right. It is done when a real-shaped positive event matches it, a real-shaped negative event does not, and CI reproduces both.

1. Rule anatomy

Start with the smallest complete rule. Every field below is required by this library's style guide.

sigma/rules/t1059.001-powershell-download-cradle.yml
title: PowerShell Download Cradle with Invoke-Expression
id: c2e8d5a1-9b47-4f3a-8d6c-3e1b7f9a2c02
status: stable
description: Detects PowerShell processes combining download methods with expression invocation.
references:
  - https://attack.mitre.org/techniques/T1059/001/
author: "Souhaieb Marzouk"
date: 2026-09-26
tags:
  - attack.execution
  - attack.t1059.001
logsource:
  category: process_creation
  product: windows
detection:
  selection_img:
    Image|endswith: '\powershell.exe'
  selection_cmdline:
    CommandLine|contains|all:
      - 'DownloadString'
      - 'IEX'
  condition: selection_img and selection_cmdline
falsepositives:
  - Administrative or deployment scripts that legitimately use Invoke-Expression
level: high
FieldWhat it doesCommon mistake
titleHuman name shown in the library.Two rules with the same title; make it specific.
idUUID v4. Stable for the life of the rule.Random 32-hex strings or reused IDs.
statusstable or test.testing or experimental in a strict schema.
descriptionWhat behavior is detected and why it matters.Restating the title without the behavior.
referencesATT&CK page plus vendor/research links.No technique URL; an unverifiable blog link.
tagsATT&CK tactic + technique tags.Underscore tactic tags; no attack.tXXXX tag.
logsourceThe telemetry contract: category/product/service.Mixing a Windows field into a Linux rule.
detectionSelections + condition.Condition refers to a selection that does not exist.
falsepositivesKnown benign triggers.“None” when a real installer or admin script will fire it.
levellow, medium, high, critical.Everything is critical, so nothing is.
Status values: this project standardises on stable and test. The Sigma spec has more statuses, but the validator and the library UI expect these two. When importing a rule from a blog, normalise the status before committing.

2. Logsource and telemetry: choose the event before the rule

The logsource is the contract between the rule and the data. If you cannot name the exact event and fields, you are not ready to write the detection.

TelemetrySigma logsourceFields you will useTypical mistake
Sysmon process createcategory: process_creation / product: windowsImage, CommandLine, ParentImage, UserUsing ProcessName when the event has Image.

Linux auditdproduct: linux / service: auditdtype, exe, a0, a1, auidUsing Windows field names.
Linux auth / SSHproduct: linux / service: authmessage, src_ip, userMatching a substring that also appears in a failure message.
AWS CloudTrailcategory: cloud / product: aws / service: cloudtraileventName, eventSource, userIdentity.arn, sourceIPAddressUsing userName without the nested userIdentity.
Entra ID sign-inproduct: azure / service: signinlogsproperties.status.errorCode, properties.location.countryOrRegionDropping the properties. prefix.
Microsoft 365 auditproduct: m365 / service: auditOperation, UserId, ClientIP, ModifiedPropertiesExact operation string differs by workload.
Zeek DNScategory: dns / product: zeekquery, qtype_name, rcode_name, id.orig_hUsing src_ip instead of id.orig_h.
pfSense firewallcategory: firewall / product: pfsensesrc_ip, dst_ip, dst_port, actionIgnoring direction; a deny is not a success.
Apache accesscategory: webserver / product: apacheclient_ip, request, status, user_agentMatching the URL in the wrong field.

Practical rule: open one real event from the source before writing YAML. Copy the exact field names. Sigma is case-insensitive for values, but field paths and nesting are not forgiving.

3. Detection logic: selections and modifiers

A detection is a set of named selections plus a condition. A selection is a map of field constraints. By default, all constraints inside one selection must match (AND).

Modifiers

ModifierMeaningExample
containsSubstring match.CommandLine|contains: 'IEX'
startswith / endswithPrefix / suffix match.Image|endswith: '\cmd.exe'
allEvery value in the list must match.CommandLine|contains|all: ['DownloadString','IEX']
reRegular expression (use sparingly).host_header|re: '^\d{1,3}(\.\d{1,3}){3}$'
cidrIP address inside a network.src_ip|cidr: '203.0.113.0/24'
gt / gte / lt / lteNumeric comparison.bytes_out|gt: 1000000000
existsField presence.TargetObject|exists: true
base64Match a base64-encoded value.CommandLine|base64: 'whoami'
windashTreat - and / as equivalent.CommandLine|windash: '-enc'

Lists are OR by default: Image|endswith: ['\cmd.exe','\powershell.exe'] means either suffix. Add all when every value must be present.

One selection, many fields

selection:
  EventID: 4688
  Image|endswith: '\rundll32.exe'
  CommandLine|contains: 'comsvcs.dll'
  CommandLine|contains|all:
    - 'MiniDump'
    - 'full'

This is one event: a process creation for rundll32 with a comsvcs.dll command line that also contains both strings. If the fields come from different events, the rule needs a correlation, not a wider selection.

4. Conditions: how selections combine

The condition is a small boolean expression over selection names.

ConditionMeaning
selectionThe named selection must match.
selection_a and selection_bBoth selections must match the same event.
selection_a or selection_bEither selection matches.
selection and not filterSelection matches and the filter does not.
1 of selection_*At least one matching selection.
all of selection_*Every matching selection.
1 of themAt least one selection, regardless of name.
AND is not correlation. selection_type10 and selection_type3 on one event is impossible: one logon event has one LogonType. That is a temporal correlation. In this project it becomes a base rule plus kind: "near" metadata, and the log harness checks both event types.

5. Counts, sums and thresholds

Older Sigma rules use a pipe such as selection | count() by src_ip > 20. Modern pySigma rejects that syntax. This project keeps the portable event-level rule and records the threshold separately:

tests/sigma_cases/thresholds.json
{
  "sigma/rules/t1590.004-horizontal-sweep-across-external-range.yml": {
    "kind": "count",
    "field": "",
    "group_by": ["src_ip"],
    "operator": ">",
    "value": 25,
    "timespan": "5m",
    "original_condition": "selection | count(distinct dst_ip) by src_ip > 25"
  }
}

The rule itself is valid and portable; the log harness counts the positive fixture events, groups them, applies the comparison, and still fails a below-threshold negative case. In production, the SIEM applies the same threshold.

When to use count

Brute force, fan-out, scanning, enumeration, high-volume egress. The event alone is noisy; the shape over time is the signal.

When to use near

Two different event types that must happen close together: share access then process creation, key creation then key use, failed logons then a success.

6. Positive and negative tests

Every rule in this library has two JSONL files:

  • positive.jsonl — at least one event that must match.
  • negative.jsonl — at least one real-shaped event that must not match.

A good negative case is not random noise. It should be the nearest benign neighbor: the same event shape, one field changed to a legitimate value.

Weak negative

{"message":"hello"} — it fails every rule, so it proves nothing.

Strong negative

The same rundll32 event with a legitimate DLL, or the same RDP logon from the approved jump host.

For aggregation rules, the negative case is below the threshold, not absent. The harness must see a realistic near-miss and still refuse to alert.

The T1566.001 pair

positive.jsonl
{"@timestamp":"2026-10-19T08:30:00Z","Channel":"Microsoft-Windows-Sysmon/Operational","EventID":1,"Computer":"WIN-WS01","User":"CORP\\alice","Image":"C:\\Program Files\\Microsoft Office\\root\\Office16\\WINWORD.EXE","CommandLine":"WINWORD.EXE /n invoice.docx","ParentImage":"C:\\Windows\\explorer.exe"}
{"@timestamp":"2026-10-19T08:30:02Z","Channel":"Microsoft-Windows-Sysmon/Operational","EventID":1,"Computer":"WIN-WS01","User":"CORP\\alice","Image":"C:\\Windows\\System32\\cmd.exe","CommandLine":"cmd.exe /c powershell -nop -w hidden -enc SQBFAFgA","ParentImage":"C:\\Program Files\\Microsoft Office\\root\\Office16\\WINWORD.EXE"}
negative.jsonl
{"@timestamp":"2026-10-19T08:31:00Z","Channel":"Microsoft-Windows-Sysmon/Operational","EventID":1,"Computer":"WIN-WS01","User":"CORP\\alice","Image":"C:\\Program Files\\Microsoft Office\\root\\Office16\\WINWORD.EXE","CommandLine":"WINWORD.EXE /n invoice.docx","ParentImage":"C:\\Windows\\explorer.exe"}
{"@timestamp":"2026-10-19T08:31:02Z","Channel":"Microsoft-Windows-Sysmon/Operational","EventID":1,"Computer":"WIN-WS01","User":"CORP\\alice","Image":"C:\\Windows\\System32\\cmd.exe","CommandLine":"cmd.exe /c whoami","ParentImage":"C:\\Windows\\explorer.exe"}

The only meaningful difference is the parent-child pair: Office spawning a script interpreter in the positive case, and a normal explorer→cmd in the negative.

7. Real log fixtures: shapes that behave like production

“Real” in a public repository means real event schemas and real field paths, not a dump of a customer's logs. This library models the events analysts actually see:

  • Sysmon 1/3/10/11/13/22 and Windows Security 4624/4688/4697/5145/7045.
  • auditd EXECVE and Linux auth/sshd messages.
  • CloudTrail (eventName, userIdentity.arn, sourceIPAddress).
  • Entra ID sign-in (properties.status.errorCode, country, auth requirement).
  • M365 audit, Okta system log, Zeek DNS/conn, pfSense filterlog, Apache access, BIND query.
No secrets, no customer data. Fixtures use documentation ranges (RFC 5737), example domains, and synthetic hostnames. Replace them with a lab export when you tune for your environment.

Shape matters more than volume

One accurate event is worth fifty random ones. For each positive case, ask: does this look like the event a real sensor would write? For each negative, ask: would a tired analyst call this benign? If yes, it is a useful test.

Generation is a draft, not the source of truth

tests/sigma_cases/generate_fixtures.py derives a matching event from the rule's selection fields, then mutates the negative case. It is a fast first draft. Review the values, make them realistic, and commit the reviewed JSONL. The generator is deterministic, so a diff shows every change.

8. The test harness

tests/sigma_match.py is a small, dependency-free evaluator for the subset of Sigma this library uses. It reads a rule, resolves field paths such as properties.status.errorCode, applies modifiers, evaluates the condition, and supports the count/sum/near metadata.

Run one rule's tests
# from the repository root
py -m venv .venv
.venv\Scripts\activate
pip install sigma-cli pySigma-backend-splunk pyyaml
python tests/test_sigma.py

The gate prints one line per rule:

[PASS] t1566.001-outlook-child-process.yml (schema + convert + positive/negative logs)

What the gate checks

  1. sigma check accepts the YAML and its schema.
  2. sigma convert -t splunk -p splunk_windows produces a query.
  3. The positive JSONL matches.
  4. The negative JSONL does not match.
  5. The four negative-control rules are rejected.

Add a new case

tests/sigma_cases/
  my-rule-stem/
    positive.jsonl
    negative.jsonl

If the rule has a count/sum/near condition, add its metadata to thresholds.json. Then run python tests/test_sigma.py.

Fast feedback: run the matcher directly while editing a case—no Sigma toolchain needed:
python - <<'PY'
import json, sys
from pathlib import Path
sys.path.insert(0, "tests")
from sigma_match import load_rule, evaluate_case
rule = load_rule("sigma/rules/my-rule.yml")
events = [json.loads(l) for l in Path("tests/sigma_cases/my-rule/positive.jsonl").read_text().splitlines()]
print(evaluate_case(rule, events, None))
PY

9. CI pipeline

The Quality Gate runs on every push and pull request. It does not need a SIEM, secrets, or paid minutes on a public repository.

.github/workflows/sigma-validate.yml (excerpt)
- name: Validate data layer
  run: python scripts/validate_data.py
- name: Check internal links
  run: python scripts/check_links.py
- name: Check site consistency
  run: python scripts/check_site.py
- name: Run Sigma test suite
  run: python tests/test_sigma.py
- name: Rebuild sigma index
  run: python scripts/build_sigma_index.py

The workflow commits the regenerated data/sigma-index.json back to main with a [skip ci] marker, so the library page stays current without a loop.

Why both a broken rule and a negative control?

A gate that only checks valid rules can silently stop checking. The four deliberately broken rules must fail; if they ever pass, the gate is broken. This is the difference between a test suite and a rubber stamp.

10. Debugging a failing rule or test

SymptomLikely causeFix
sigma check: condition errorSelection name typo, unsupported pipe syntax, missing detection key.Compare the condition names with the selections; move counts to threshold metadata.
Conversion failsBackend does not support a modifier or logsource.Simplify the modifier, choose the right pipeline, or keep the rule schema-only with a documented reason.
Positive log does not matchField path, case, list vs string, or an all constraint.Print the event and evaluate each selection separately; check the exact field names.
Negative log matchesThe negative is too close to malicious behavior, or the rule is too broad.Add a filter (approved host, signed binary, known account) or choose a different benign neighbor.
Count rule never firesGroup-by field missing from the fixture or threshold metadata.Add the group field to every event; confirm operator/value.
Near rule never firesOnly one of the two event types is present.Add one event for each selection; confirm the kind: "near" metadata.

Read the event, not the rule

When a positive fails, print the event with json.dumps(event, indent=2) and the rule's detection block. Evaluate one selection at a time. Most failures are a field path or a value that is a list when the rule expects a scalar.

11. Authoring checklist

  • Telemetry: I named the exact event, product, service and fields.
  • Technique: the rule has a real attack.tXXXX tag and a reference.
  • Logic: every selection is used; the condition matches the intended combination.
  • False positives: at least one realistic benign trigger is documented.
  • Level: severity reflects confidence and impact, not enthusiasm.
  • Positive test: a real-shaped event matches.
  • Negative test: a near-benign event does not match.
  • Schema: sigma check passes.
  • Conversion: Splunk conversion produces output.
  • CI: python tests/test_sigma.py is green.
  • Library: the rule is linked in the technique row's sigma array.
Definition of done: a reader can copy the rule, run the test command, and see the positive/negative evidence for themselves. That is detection-as-code.
